19.4 Zero-copy, offload és hálózati teljesítmény

19.4.1 1. A hálózati adatút optimalizálása: a csomag útja és a másolások problémája

Az előző alfejezetben (Csomagfeldolgozás, netfilter és eBPF) láttuk, hogy egy beérkező csomag a hálózati kártyától (NIC) a megszakításon, a DMA-n és a kernel hálózati veremén (TCP/IP stack) keresztül jut el a felhasználói alkalmazásig. Ez az útvonal az általános célú operációs rendszerekben hagyományosan többszöri memóriamásolással és kontextusváltással jár, ami a modern, nagy sebességű hálózatokon (10 Gbit/s, 25 Gbit/s, 100 Gbit/s) komoly szűk keresztmetszetté válik.

A naiv adatút a következőképpen néz ki egy csomag fogadásakor:

  1. A NIC DMA-val az előre lefoglalt RX-pufferbe írja a keretet; a meghajtó ehhez sk_buff-ot rendel (másolás nélkül).
  2. A protokollverem feldolgozza a fejléceket, és az sk_buff-ot a socket fogadósorába fűzi (másolás nélkül).
  3. Az alkalmazás meghívja a read() rendszerhívást, amelynek során a CPU a kernelpufferből a felhasználói térben lévő pufferbe másolja az adatot (copy_to_user).

Fogadáskor így egy CPU-másolás (kernel → felhasználói tér) és két kontextusváltás jut egy read()-re; nagy sebességnél ezt a másolást és a csomagonkénti feldolgozást kell csökkenteni, mert jelentősen terheli a CPU-t, rontja a cache kihasználtságát, növeli a késleltetést, és csökkenti az elérhető maximális sávszélességet.

A hálózati adatút optimalizálásának célja kettős:

  • CPU-teher csökkentése: A CPU-nak a csomagok másolgatása helyett az alkalmazáslogikával kellene foglalkoznia.
  • Késleltetés és áteresztőképesség javítása: Kevesebb másolás és kontextusváltás közvetlenül jobb latency-t és nagyobb throughputot eredményez.

Az optimalizálás három fő pilléren nyugszik: a zero-copy technikák, a hardveres offload és a CPU-affinitás / NUMA-tudatos elhelyezés.

19.4.2 2. Zero-copy technikák a rendszerhívásokban

A “zero-copy” kifejezés némileg félrevezető: nem azt jelenti, hogy egyáltalán nincs másolás a memóriában, hanem azt, hogy a CPU nem végez felesleges másolást a felhasználói és a kernelcímterek között. A cél, hogy a memóriabuszon és a CPU L1/L2/L3 cache-én keresztül történő adatmozgatások száma minimális legyen.

Az alábbi ábra a négy küldési technikát hasonlítja össze egy blokkra: melyik átvitelt végzi DMA, melyiket a CPU, és hol marad csak hivatkozás.

19.4.2.1 2.1 sendfile() és a kernel belső másolása

A legegyszerűbb és legelterjedtebb zero-copy minta a fájlok kiszolgálása a hálózaton (pl. webkiszolgáló). A hagyományos megoldás a read() majd write():

/* Hagyományos, nem hatékony másolás – ellenőrzött socketkapcsolattal */
int in_fd = open("fajl.bin", O_RDONLY);
if (in_fd < 0) { perror("open"); return 1; }

int out_fd = socket(AF_INET, SOCK_STREAM, 0);
if (out_fd < 0) { perror("socket"); return 1; }

struct sockaddr_in sa = { .sin_family = AF_INET, .sin_port = htons(PORT) };
if (inet_pton(AF_INET, "127.0.0.1", &sa.sin_addr) != 1) {
    fprintf(stderr, "inet_pton\n");
    return 1;
}
/* A küldő csak egy létrehozott, fogadó oldalon listen()-elő
 * kapcsolathoz csatlakozhat; enélkül a write() hibára futna. */
if (connect(out_fd, (struct sockaddr *)&sa, sizeof(sa)) != 0) {
    perror("connect");
    return 1;
}

char buffer[16384];
ssize_t n;
while ((n = read(in_fd, buffer, sizeof(buffer))) > 0) {
    ssize_t off = 0;
    while (off < n) {                 /* rövid write() is lehet */
        ssize_t w = write(out_fd, buffer + off, (size_t)(n - off));
        if (w < 0) {
            if (errno == EINTR) continue;
            perror("write");
            return 1;
        }
        off += w;
    }
}
if (n < 0) { perror("read"); return 1; }   /* a 0 az EOF, a negatív hiba */

Itt az adat négyszer mozog: kétszer DMA-val (lemez → page cache, socketpuffer → NIC), kétszer a CPU másolja (page cache → felhasználói puffer → socketpuffer), és két rendszerhívás jut minden blokkra. A sendfile() rendszerhívás ezt a műveletet egyetlen hívássá olvasztja össze, de a hívás rövid is lehet, ezért ciklusban kell futtatni:

/* Zero-copy adatküldés a kernelben maradva; a rövid átvitelt
 * a ciklus kezeli, a visszatérési érték ellenőrzött. */
off_t offset = 0;
size_t total = 0;
while (total < file_size) {
    ssize_t sent = sendfile(out_fd, in_fd, &offset, file_size - total);
    if (sent < 0) {
        if (errno == EINTR) continue;
        perror("sendfile");
        return 1;
    }
    if (sent == 0) {                  /* nem várt EOF a fájlon */
        fprintf(stderr, "sendfile: váratlan EOF\n");
        return 1;
    }
    total += (size_t)sent;
}

A sendfile működése során a kernel közvetlenül a page cache-ből tölti be a fájl adatait, és azt a socket pufferbe helyezi. Habár ez még mindig egy memóriamásolás a kernel címtartományán belül (page cache -> socket buffer), a CPU-nak nem kell átlépnie a kernel/user határt kétszer, és nem kell a felhasználói pufferbe másolnia. A modern Linux kernelekben a sendfile képes arra is, hogy a socket bufferbe ne a teljes adatot másolja, hanem csak egy leírót (descriptor) illesszen be, ami a háttérben a page cache lapjaira mutat (ez a splice és a hálózati alrendszer együttműködése).

19.4.2.2 2.2 splice()

A splice() rendszerhívás egy általánosabb kernel-belső adatmozgató mechanizmus. Két fájlleíró között mozgat adatot anélkül, hogy az elhagyná a kernelteret. A két leíró közül az egyiknek pipe-nak kell lennie (különben EINVAL).

/* adat mozgatása fájlból socketbe splice-szal; a pipe kapacitása véges */
int pipefd[2];
if (pipe(pipefd) != 0) { perror("pipe"); return 1; }

const size_t MAX_SPLICE = 64 * 1024;   /* az alapértelmezett csőkapacitás felső korlátja */
off_t offset = 0;
size_t total = 0;
for (;;) {
    size_t want = file_size - total;
    if (want == 0) break;
    if (want > MAX_SPLICE) want = MAX_SPLICE;

    /* Fájl -> pipe. A betöltött részt azonnal el kell fogyasztani,
     * különben a cső megtelik, és a hívás elakad vagy rövidül. */
    ssize_t n = splice(in_fd, &offset, pipefd[1], NULL, want, SPLICE_F_MOVE);
    if (n < 0) {
        if (errno == EINTR) continue;
        perror("splice fájl->pipe");
        return 1;
    }
    if (n == 0) break;                 /* EOF */

    /* Pipe -> socket, a ténylegesen betöltött bájtszámmal. */
    ssize_t marad = n;
    while (marad > 0) {
        ssize_t m = splice(pipefd[0], NULL, out_fd, NULL, (size_t)marad,
                           SPLICE_F_MOVE | SPLICE_F_MORE);
        if (m < 0) {
            if (errno == EINTR) continue;
            perror("splice pipe->socket");
            return 1;
        }
        if (m == 0) {                  /* nem várható: a cső nem üres */
            fprintf(stderr, "splice: váratlan 0\n");
            return 1;
        }
        marad -= m;
    }
    total += (size_t)n;
}

A negatív visszatérési értéket nem szabad size_t méreteként továbbadni: hiba esetén a hívás nem részleges átvitelt jelöl, hanem sikertelenséget, ezért külön ágban kell kezelni. A rövid átvitel (a kértnél kisebb n) viszont normális, ezt a ciklus folytatásával kell kezelni; az n == 0 a fájl végének jele.

Itt a kernel a page cache lapjaira mutató hivatkozásokat adja át a csövön keresztül a socketnek (a SPLICE_F_MOVE csak tipp, a mai kernelek figyelmen kívül hagyják), nem pedig másolja a lapokat, amennyiben a hardver és a kernel támogatja a scatter-gather DMA-t. A küldés helyességét a fogadó oldal ellenőrzi: a beérkezett bájtok száma egyezik-e a fájl méretével, és a teljes tartalom SHA-256 hash-e megegyezik-e a forrásfájléval. Csak egyező bájtszám és hash mellett értékelhető a mért átviteli sebesség és CPU-terhelés.

19.4.2.3 2.3 MSG_ZEROCOPY (Linux-specifikus)

A fenti példák fájlból (page cache-ből) küldenek. Ha az alkalmazás a saját memóriájából generált adatot akar küldeni, hagyományosan a send() rendszerhívás bemásolja a felhasználói puffert a kernel socket pufferébe. A Linux 4.14 óta elérhető MSG_ZEROCOPY flag ezt kerüli meg:

/* Verziófüggő API: a célkernel támogatását és a szükséges fejlécet
 * (linux/errqueue.h) a fordítás előtt ellenőrizni kell. */
#define _GNU_SOURCE
#include <errno.h>
#include <time.h>           /* a linux/errqueue.h előtt: struct timespec */
#include <linux/errqueue.h>
#include <netinet/in.h>
#include <poll.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/mman.h>
#include <sys/socket.h>

int one = 1;
if (setsockopt(fd, SOL_SOCKET, SO_ZEROCOPY, &one, sizeof(one)) != 0) {
    /* Régi kernel vagy nem támogató socket: essünk vissza a másoló
     * send() útra, és a mérésben jelöljük, hogy nem zero-copy futott. */
    perror("SO_ZEROCOPY");
}

char *buf = mmap(NULL, size, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
if (buf == MAP_FAILED) { perror("mmap"); return 1; }
/* ... adat feltöltése a buf-ba ... */

/* A küldés rövid is lehet, ezért ciklus kell; a visszatérési érték
 * ellenőrzött, a negatív érték hibát, nem méretet jelent. */
size_t off = 0;
unsigned int elkuldott_darab = 0;      /* a MSG_ZEROCOPY-s sendmsg hívások száma */
while (off < size) {
    struct iovec iov = { .iov_base = buf + off, .iov_len = size - off };
    struct msghdr msg = { 0 };
    msg.msg_iov = &iov;
    msg.msg_iovlen = 1;

    ssize_t sent = sendmsg(fd, &msg, MSG_ZEROCOPY);
    if (sent < 0) {
        if (errno == EINTR) continue;
        if (errno == ENOBUFS) {       /* optmem/zárolt-lap korlát: csak a befejezési
                                       * értesítések kiolvasása szabadítja fel */
            olvasd_ki_az_ertesiteseket(fd, &befejezve);   /* lásd alább: nem blokkoló MSG_ERRQUEUE-olvasás */
            continue;
        }
        perror("sendmsg");
        return 1;
    }
    if (sent == 0) break;
    off += (size_t)sent;
    elkuldott_darab++;
}

A fenti vázlatban az olvasd_ki_az_ertesiteseket és a befejezve számláló az alábbi, második blokk ciklusmagjának függvénybe emelt, nem blokkoló változata (vázlat, nincs lefordítva).

A sendmsg() sikeres visszatérése csak azt jelenti, hogy a kernel átvette az adatleírót; a puffer tulajdonjoga nem kerül vissza azonnal. Az alábbi kódban elkuldott_darab a MSG_ZEROCOPY jelzővel elindított sendmsg hívások száma (a fenti küldő ciklus minden sikeres hívás után eggyel növeli). Amíg a befejezési értesítés meg nem érkezik, a kernel (vagy a hálózati kártya DMA-ja) még hivatkozhat a felhasználói lapokra, ezért a puffer tartalma nem módosítható, és a memória nem szabadítható fel. A befejezéseket a socket error queue-jából kell kiolvasni MSG_ERRQUEUE jelzővel, és a kapott azonosítókat párosítani kell az elindított küldésekkel:

/* A befejezési értesítések olvasása. Az azonosítók a MSG_ZEROCOPY-s
 * sendmsg hívásokhoz rendelt, egyesével növekvő értékek; az
 * ee_info/ee_data a befejezett tartomány első és utolsó azonosítója. */
unsigned int befejezve = 0;            /* az eddig befejezett küldések száma */
while (befejezve < elkuldott_darab) {
    char control[512];
    struct msghdr msg = { .msg_control = control, .msg_controllen = sizeof(control) };
    ssize_t n = recvmsg(fd, &msg, MSG_ERRQUEUE);
    if (n < 0) {
        if (errno == EINTR) continue;
        if (errno == EAGAIN) {         /* még nincs értesítés: várakozás */
            struct pollfd p = { .fd = fd, .events = POLLERR };
            if (poll(&p, 1, 1000) <= 0) { perror("poll"); return 1; }
            continue;
        }
        perror("recvmsg(MSG_ERRQUEUE)");
        return 1;
    }
    for (struct cmsghdr *c = CMSG_FIRSTHDR(&msg); c != NULL; c = CMSG_NXTHDR(&msg, c)) {
        if (c->cmsg_level != SOL_IP) continue;   /* IPv6 esetén SOL_IPV6 */
        struct sock_extended_err *ee = (struct sock_extended_err *)CMSG_DATA(c);
        if (ee->ee_origin != SO_EE_ORIGIN_ZEROCOPY) continue;
        if (ee->ee_errno != 0) {
            /* a tartomány elküldése hibára futott: a puffer visszanyerhető,
             * de az adatot újra kell küldeni */
            fprintf(stderr, "zerocopy hiba: %s\n", strerror(ee->ee_errno));
        }
        if (ee->ee_code == SO_EE_CODE_ZEROCOPY_COPIED) {
            /* a kernel másolásra esett vissza: a puffer szabad, de ez a
             * küldés nem zero-copy volt, ezért a mérésből ki kell zárni
             * vagy külön kell jelölni */
            fprintf(stderr, "figyelmeztetés: a kernel másolt (fallback)\n");
        }
        if (ee->ee_data + 1 > befejezve) {
            befejezve = ee->ee_data + 1;
        }
    }
}
/* Innen a buf tartalma újra írható, a memória felszabadítható. */

Ebben az esetben a kernel a hálózati kártya DMA-képességét használva közvetlenül a felhasználói térben lévő lapokról olvassa be az adatot, ha a hardveres scatter-gather ezt lehetővé teszi. A MSG_ZEROCOPY a laprögzítés és a befejezési értesítések kezelése miatt kis írásoknál drágább a másolásnál; a kernel dokumentációja (msg_zerocopy) szerint általában kb. 10 KB fölötti írásoknál térül meg (a küszöb hardver- és kernelfüggő, mérni kell). A mérés értelmezésénél figyelembe kell venni, hogy a másoló fallback esetén a küldés nem zero-copy, hanem a hagyományos úton történt; ezt a SO_EE_CODE_ZEROCOPY_COPIED kód jelzi.

Tipikus hiba és helyes megoldás: A kezdő fejlesztők gyakran alkalmaznak zero-copy megoldásokat kicsi, pár száz bájtos üzenetekre. Ebben az esetben a rendszer a lapok lefoglalásával és rögzítésével (page pinning) több munkát végez, mintha egyszerűen átmásolná a néhány száz bájtot (copy_from_user). A helyes megoldás a döntési táblázat használata: zero-copy csak akkor, ha a payload mérete meghalad egy mérésből meghatározott küszöbértéket (a kernel dokumentációja szerint nagyságrendileg 10 KB), vagy ha a CPU a szűk keresztmetszet.

19.4.3 3. Hardveres offload: DMA, stateless offload és TOE

Az operációs rendszernek nem kell minden feladatot szoftveresen elvégeznie. A hálózati kártyák (NIC-ek) egyre több intelligens funkcióval rendelkeznek. Az offload célja, hogy a CPU helyett a hardver végezze el az ismétlődő, alacsony szintű munkát.

19.4.3.1 3.1 DMA (Direct Memory Access) és Descriptor gyűrűk

A DMA a hálózati adatút legalapvetőbb offload mechanizmusa. Programozott I/O (PIO) esetén a CPU minden bájtot egyesével olvasna ki a kártyáról. A DMA lehetővé teszi, hogy a kártya közvetlenül a rendszermemóriába írjon (RX) és onnan olvasson (TX).

A kernel és a NIC közötti együttműködés descriptor gyűrűkkel (ring buffer) történik:

  • TX Ring: A kernel lefoglal egy gyűrűt, amelyben a memóriacímeket és hosszakat adja meg. A kernel létrehoz egy sk_buff-ot, majd a fizikai címét beírja a TX ring következő elemébe. A NIC DMA-val elolvassa ezt a mutatót, kiolvassa az adatot a RAM-ból, és elküldi a hálózatra.
  • RX Ring: A kernel előre lefoglal üres puffereket, és azok címeit beírja az RX ringbe. Amikor csomag érkezik, a NIC DMA-val beleír a megadott memóriacímre, majd megszakítást (IRQ) küld.

A scatter-gather DMA az a hardveres képesség, amely a zero-copy technikák alapja. Ha a TCP stream adatai nem folytonos fizikai memóriában vannak, a CPU-nak külön be kellene másolnia őket egy folytonos pufferbe, hogy a hálózati kártya el tudja küldeni. Ha a NIC támogatja a scatter-gather-t, a kernel egyszerűen átad egy láncolt listát (iovec) a fizikai címekről, és a NIC hardvere szétszórva olvassa be azokat, összerakva a keretet a hálózaton.

19.4.3.2 3.2 Stateless offload: Checksum, TSO, LRO/GRO

A TCP/IP protokoll több ellenőrző összeget és szegmentálási feladatot ír elő, amelyeket hagyományosan a CPU számolt ki.

  • Checksum Offload (CSUM): Az IP és TCP fejléc ellenőrző összegének kiszámítása nagy CPU-terhelést jelent nagy sávszélességnél. Ha a NIC hardvere támogatja, a kernel beírja a fejlécbe a pszeudo-fejléc adatait, és a kártya kiszámítja a végleges checksumot. Ez tipikusan mindig bekapcsolt állapotban marad, mert a nyereség hatalmas, a kockázat pedig alacsony.
  • TCP Segmentation Offload (TSO): A kernel hálózati verme és az alkalmazás gyakran nagy (akár 64 KiB-os) pufferekkel dolgozik, de a fizikai hálózat MTU-ja 1500 bájt. Ha a CPU-nak kellene feldarabolnia a nagy TCP szegmenseket, az rengeteg apró művelet lenne. TSO esetén a kernel átadja a nagy puffert a kártyának, és a hálózati hardver végzi el a szegmentálást a kicsi IP-csomagokra. Ez drámaian csökkenti a per-bájt CPU-költséget.
  • Large/Generic Receive Offload (LRO/GRO): A TSO ellentéte. A hálózaton sok kicsi, egymáshoz tartozó szegmens érkezik. Ha a kernel mindegyiket külön dolgozná fel, óriási overhead lenne. A GRO a szoftveres, de az alsóbb rétegben (NAPI) elvégzett aggregáció: a NAPI poll (NET_RX softirq) összegyűjti az egymáshoz tartozó szegmenseket, és egyetlen nagy sk_buff-ként adja fel a TCP veremnek. (Az LRO hardveres vagy régi szoftveres összevonás; az összevont csomag továbbításkor (routing/bridge) nem állítható vissza pontosan, ezért routeren és bridge-en tiltani kell, és a Linux inkább a GRO-t preferálja.)

19.4.3.3 3.3 TOE (TCP Offload Engine)

A TOE a “teljes” offload megvalósítása. Itt a hálózati kártya nem csak a checksum-ot számolja, vagy a szegmentálást végzi, hanem a teljes TCP state machine-t lefuttatja a hardverben (háromfázisú handshake, torlódásvezérlés, nyugtázás, retransmission).

Előny: Az elméleti CPU-teher a nullához közelíthet, hiszen a hoszt CPU-ja szinte nem vesz részt a TCP feldolgozásában. Hátrány és jelenlegi helyzet: A modern, nagysebességű hálózatokban az általános célú operációs rendszerek (különösen a Linux) nem használnak teljes TOE-t. Ennek okai:

  1. Biztonság és tűzfal (netfilter, eBPF): Ha a TCP handshake és a kapcsolatállapot a hardverben él, akkor a kernel tűzfala (pl. iptables, nftables) és az eBPF programok nem látják a kapcsolat állapotát, így nem tudnak beavatkozni (pl. SYN cookie, DDoS védelem).
  2. Rugalmasság és debuggolás: A kernel TCP verme (pl. CUBIC, BBR torlódásvezérlés) folyamatosan fejlődik. A hardverbe égetett implementációk elavulnak, nem frissíthetők, és nehezen debuggolhatók.
  3. Virtualizáció és live migration: Ha a TCP állapot a hardverben van, lehetetlen egy virtuális gépet élőben átköltöztetni (live migration) egy másik szerverre, mert a kapcsolat állapota nem exportálható.

Ezért a gyakorlatban a stateless offload (TSO, CSUM, RSS) és az intelligens DMA a nyerő stratégia, a teljes TOE-t pedig főleg speciális beágyazott környezetekben vagy régebbi eszközökön találjuk.

19.4.4 4. Latency, Throughput és CPU-affinitás

Az optimalizálás célja a mérőszámok javítása, tehát meg kell értenünk a hálózati teljesítmény metrikáit és a CPU-architektúra hatását.

  • Throughput (Áteresztőképesség): Az időegység alatt átvitt hasznos adat mennyisége (Mbit/s vagy csomag/s). A throughput növelése főként a nagy másolások kiküszöbölésén (zero-copy) és az offload-on (TSO/LRO) múlik.
  • Latency (Késleltetés): Az az idő, ami alatt egy csomag eljut a forrástól a célig (vagy a végponttól a végpontig az alkalmazásban). A latency csökkentése gyakran a megszakítások késleltetésének csökkentésén és az ütemezés optimalizálásán múlik.

19.4.4.1 4.1 CPU-affinitás és RSS (Receive Side Scaling)

A többmagos rendszerekben a hálózati adatút egyik legnagyobb ellensége a cache thrashing és a lock contention. Ha egy csomag megszakítása a 0. CPU-n fut le, a felhasználói alkalmazás pedig a 4. CPU-n, akkor az adatot a cache-koherencia protokollnak (MESI) át kell mozgatnia a processzorok között, ami jelentős késleltetést ad hozzá.

Receive Side Scaling (RSS): A hálózati kártyák támogatják a hardveres terheléselosztást. Az RSS a TCP/IP fejléc (IP-címek és portok) hash-e alapján a bejövő csomagokat több RX ringbe osztja szét. Minden RX ringhez külön megszakítási vektor tartozhat, amelyet a kernel egy adott CPU-hoz köthet.

Interrupt Coalescing és Busy Polling: A nagy sebességű hálózatoknál a megszakítások áradata (interrupt storm) miatt a CPU soha nem jut el az alkalmazás futtatásáig. Két stratégia létezik:

  1. Interrupt Coalescing (Adaptive RX/TX): A kártya nem küld megszakítást minden csomag után, hanem vár egy kicsit (néhány mikroszekundum), vagy vár, amíg N csomag összegyűlik. Ez növeli a batch méretet és növeli a throughputot, de növeli a késleltetést is! Ez a klasszikus latency vs. throughput trade-off.
  2. Busy Polling (SO_BUSY_POLL): Alacsony késleltetésű környezetekben az alkalmazás nem alszik el a recv hívásra várva, hanem a kernel aktívan pörög egy CPU magon, és pollozza a hálózati kártya RX gyűrűjét. Ez drasztikusan csökkenti a latency-t (akár 10-20 mikroszekundumra), de 100%-os CPU-terhelést jelent.

CPU-affinitás beállítása a laborban: A taskset vagy a cpuset cgroup segítségével az alkalmazást ugyanarra a NUMA node-ra és CPU magra kötjük, mint ahol a NIC megszakítása fut.

# Példa: IRQ affinity beállítása (emulált labor kontextusban)
# A NIC megszakításszámát a /proc/interrupts mutatja, a NUMA-csomópontját a
# /sys/class/net/<iface>/device/numa_node (-1: nincs NUMA-információ).
IRQ=<irq-szám>        # helyőrző
NODE=<numa-csomópont> # helyőrző
# Az IRQ-t a 2-es CPU-hoz kötjük (a 2-es CPU-nak a $NODE csomóponthoz kell tartoznia: numactl -H)
echo 2 > /proc/irq/$IRQ/smp_affinity_list

# Az alkalmazást ugyanahhoz a CPU-hoz és NUMA-csomóponthoz kötjük
numactl --cpunodebind=$NODE --membind=$NODE taskset -c 2 ./halozati_app

A CPU-affinitás csökkenti a lock contention-t, biztosítja, hogy az adat az L2/L3 cache-ben marad, és kiszámíthatóbbá teszi a késleltetést.

19.4.5 5. Labor: Zero-copy és offload döntési táblázat

Környezet: Emulált labor QEMU-ban, virtio-net hálózati kártyával. Rögzített konfiguráció: 4 vCPU, 8 GiB RAM, Linux kernel 6.x (a pontos verzió a reprodukciós naplóban rögzítendő, mert az API-k verziófüggőek lehetnek).

19.4.5.1 5.1 Cél

Megmérni és összehasonlítani a hagyományos másolás és a zero-copy/offload technikák hatását a latency-re, throughputra és CPU-terhelésre. A mérések alapján létrehozni egy döntési táblázatot.

19.4.5.2 5.2 Eszközök és mérési módszer

  • Források: egyetlen közös küldő és fogadó programpár (sender.c, receiver.c); a könyv csak a küldő vázlatát közli (az atut_* függvények a 2. szakasz mintáiból, a receiver.c és a connect_receiver az olvasó saját megvalósítása), kész forráscsomag nincs mellékelve. Az adatutat a küldő --mod kapcsolója választja ki: copy (read+write), sendfile, splice (és opcionálisan zerocopy a MSG_ZEROCOPY méréshez). A fájlméret, a pufferméret, a socketbeállítások és a naplóformátum minden módban azonos; a receiver.c a fogadott bájtok számát és a tartalom SHA-256 hash-ét ellenőrzi, és csak egyezés esetén ad sikeres kilépési kódot. Minden futás a szabványos hibakimenetre kiírja a választott módot, a fájlméretet és a verziókat, így a naplóból utólag megállapítható, melyik adatút futott.
  • Topológia: a küldő és a fogadó a virtio-net interfész két oldalán fut (például a vendég és a hoszt tap-interfésze, vagy két QEMU-vendég közös -netdev socket/bridge-en); a kliens a fogadó nem loopback címére (<receiver-ip> helyőrző) csatlakozik, és az ethtool -K a ténylegesen használt interfészre vonatkozik. Loopbacken (127.0.0.1) az offload-beállítások hatástalanok, és a MSG_ZEROCOPY mindig másol (SO_EE_CODE_ZEROCOPY_COPIED); ezért a mérés a virtio-net interfészen át fut.
  • Hálózati konfiguráció: ethtool -K <iface> tx on rx on tso on gro on (offload be), majd ugyanazon a kapcsolaton kikapcsolt állapot mérése. Az ethtool -k <iface> kimenetét minden méréshez naplózni kell, mert a virtuális virtio-net offload-képessége a hoszt beállításaitól is függ.
  • Mérés: iperf3 a TCP throughputra, qperf vagy ping -f a latency-re és csomagvesztésre. perf stat a CPU-ciklusok és cache-miss mérésére. A hálózati kapacitás felső korlátja külön kontrollmérés: az iperf3 eredménye a labor hálózatának elérhető sávszélességét adja, ehhez képest kell a másolási módok hatását értékelni. Minden kísérletben egyszerre csak egy tényező változzon (másolási mód, offload, affinitás); a többi beállítás rögzített.

A közös küldő vázlata, amelyben az adatút egyetlen kapcsolóval választható:

/* sender.c – közös küldő, választható adatúttal (vázlat) */
static int atut_copy(int out_fd, int in_fd, size_t meret);
static int atut_sendfile(int out_fd, int in_fd, size_t meret);
static int atut_splice(int out_fd, int in_fd, size_t meret);

int main(int argc, char **argv) {
    const char *mod = "copy";
    const char *fajl = "adat.bin";
    for (int i = 1; i < argc; ++i) {
        if (strcmp(argv[i], "--mod") == 0 && i + 1 < argc) {
            mod = argv[++i];
        } else if (strcmp(argv[i], "--fajl") == 0 && i + 1 < argc) {
            fajl = argv[++i];
        }
    }
    /* A kapcsolatot a receiver.c fogadja (listen/accept), a küldő connect()-ál;
     * a fájlméret és a pufferméret minden módban ugyanaz. */
    int in_fd = open(fajl, O_RDONLY);
    int out_fd = connect_receiver("<receiver-ip>", PORT);   /* helyőrző: nem loopback cím */
    if (in_fd < 0 || out_fd < 0) return 1;
    size_t meret = (size_t)lseek(in_fd, 0, SEEK_END);
    lseek(in_fd, 0, SEEK_SET);

    /* A választott mód a naplóból minden futásnál azonosítható. */
    fprintf(stderr, "MOD=%s FAJL=%s MERET=%zu\n", mod, fajl, meret);

    if (strcmp(mod, "copy") == 0)     return atut_copy(out_fd, in_fd, meret);
    if (strcmp(mod, "sendfile") == 0) return atut_sendfile(out_fd, in_fd, meret);
    if (strcmp(mod, "splice") == 0)   return atut_splice(out_fd, in_fd, meret);
    fprintf(stderr, "ismeretlen mod: %s\n", mod);
    return 1;
}

A connect_receiver a receiver.c listen/accept oldalához csatlakozó segédfüggvény; a lseek visszatérési értékét a teljes programban ellenőrizni kell, mert -1 esetén a méret érvénytelen. A nehéz mérési logika az atut_* függvényekben van, amelyek a 2. szakasz mintái szerint, ciklusban és ellenőrzött visszatérési értékekkel dolgoznak.

19.4.5.3 5.3 Elvárt (levezetett) vs. Mért eredmények

A mérés előtt rögzítsük az elvárt viselkedést: - Elvárt: A sendfile nagy fájloknál kevesebb CPU-ciklus/bájt értéket ad, mert a felhasználói másolat és a rendszerhívások fele elmarad; a nyereség mértéke mérendő (nem levezetett szám). - Elvárt: A TSO bekapcsolása a virtio-net interfészen csökkenti a küldő CPU-ciklus/bájt értékét; az abszolút sávszélesség a hoszt beállításaitól függ (a hálózat felső korlátját az iperf3 kontrollmérés adja). - Elvárt: A latency a legjobb akkor lesz, ha Busy Polling (SO_BUSY_POLL) van, a legrosszabb pedig Interrupt Coalescing bekapcsolásával.

(A mérési naplóba a mért értékeket ide kell beilleszteni, és az eltéréseket elemezni.)

19.4.5.5 5.5 Tipikus hibák és megoldások a labor során

  1. Hiba: Az offload-ot kikapcsolják, mert “az hamis képet ad”. Megoldás: Ez téves. A modern virtuális környezetek (VirtIO) szoftveresen emulálják a TSO/GRO-t; letiltása a host CPU-t terheli, és nem méri a valós elérhető teljesítményt. Mindig dokumentálni kell az ethtool állapotát.
  2. Hiba: A CPU-affinitást nem ellenőrzik, és a mérési eredmények nagy szórást mutatnak. Megoldás: A QEMU vCPU szálait is rögzíteni kell (taskset a QEMU szálakra), mert a virtuális környezetben a hoszt ütemezője felülírhatja a vendég affinity beállításokat.
  3. Hiba: A sendfile-t kisméretű, interaktív üzenetekre használják. Megoldás: Ilyenkor a hívás overheadje és a kontextusváltás a domináns, nem a másolás. Ilyen esetekben a batch feldolgozás vagy az io_uring a helyes válasz.

19.4.6 6. Összegzés

Ebben az alfejezetben láthattuk, hogy a hálózati teljesítmény nem csak a CPU órajelétől függ, hanem attól, hogyan szervezzük meg az adatok útját. A zero-copy technikák (sendfile, splice, MSG_ZEROCOPY) megszüntetik a felesleges CPU-másolásokat. A hardveres offload (Checksum, TSO, GRO) kiveszi a per-packet terhelést a CPU-ból. Végül a CPU-affinitás és a modern interrupt kezelés (RSS, Busy Polling) biztosítja, hogy a megfelelő adat a megfelelő cache-ben legyen a megfelelő időben.

Két terhelési eset és értékelési rubrika. A döntési táblázat önmagában nem elég: a választást két, egymástól lényegesen eltérő terhelésen kell ellenőrizni, és a döntést a mérés előtt rögzíteni kell. A rubrika három dolgot kér számon:

  1. A választott optimalizáció (másolási mód, offload, affinitás) és annak indoklása a munkaterhelés profilja alapján.
  2. A mérőszám, amellyel a döntés igazolható (például CPU-ciklus/bájt, elért throughput, p95 latency, cache-miss arány), a mérési módszerrel együtt.
  3. Egy lehetséges negatív mellékhatás és annak ellenőrzése (például megnövekedett memóriafoglalás, romló latency kis csomagokon, hoszt CPU-terhelés emulált offload mellett).
Eset Terhelés Elvárt döntés Mit kell mérni Lehetséges negatív mellékhatás
A: nagy, folyamatos átvitel több GiB-os fájl, hosszú életű TCP kapcsolat sendfile/splice, TSO/GRO be, rögzített CPU-affinitás CPU-ciklus/bájt, elért Mbps, perf stat cache-miss a zero-copy a page cache memóriáját foglalja; a TSO növeli az egy csomagra jutó késleltetést
B: kis interaktív üzenetek néhány száz bájtos kérések, nagy másodpercenkénti darabszám hagyományos send/recv, az offload célzott beállítása, alacsony latency p50/p95/p99 válaszidő, csomagvesztés, perf stat context-switch a zero-copy laprögzítése drágább a másolásnál; az agresszív offload/coalescing rontja a válaszidőt

Az olvasónak a mérés előtt ki kell töltenie a választott optimalizációt, a mérőszámot és a várt mellékhatást, majd a mérés után a rubrika alapján kell eldöntenie, hogy a döntés helyes volt-e. A kisebb CPU-terhelés nem azonos a kisebb másolási költséggel és a kisebb késleltetéssel: ezeket külön mérőszámmal kell igazolni.

Önellenőrző kérdések:

  1. Az A esetben a sendfile 30%-kal kevesebb CPU-ciklust használ, mint a read+write, de a p95 latency 5%-kal nő. Hogyan döntöd el, melyik szempont élvez elsőbbséget, és milyen további méréssel támasztod alá a döntést?
  2. A B esetben a MSG_ZEROCOPY kisebb CPU-terhelést mutat, mint a send, de a kis üzeneteknél a mért átviteli idő nem javul. Mi lehet ennek az oka, és hogyan ellenőriznéd, hogy a kernel nem másoló fallbacket hajtott-e végre?

Válaszok röviden: (1) A döntés az üzleti célhoz igazodik: nagy átvitelnél a CPU-ciklus/bájt a fő mérőszám, interaktívnál a p95 latency; további mérés: a p95/p99 és a CPU-ciklus/bájt azonos terhelésen, több futásból (szórással). (2) Kis üzeneteknél a laprögzítés és a befejezési értesítések költsége meghaladja a másolásét, és a kernel gyakran másol (fallback); ellenőrzés: az MSG_ERRQUEUE értesítések ee_code mezője SO_EE_CODE_ZEROCOPY_COPIED értékű-e.

Fontos megérteni, hogy a hálózati verem optimalizálása mindig kompromisszum. Nincs “egy jó beállítás” mindenre: a nagy áteresztőképességet igénylő fájltranszfer más konfigurációt igényel, mint az alacsony késleltetést igénylő valós idejű alkalmazás. A mérnök feladata a munkaterhelés profilozása és a bemutatott döntési táblázat alapján a helyes kernel- és hardverparaméterek kiválasztása. A következő alfejezetben (DNS, DHCP és konfiguráció) ezt a tudást alkalmazzuk a hálózati szolgáltatások (DNS, DHCP) építésekor, ahol a kis csomagok miatt a latency és az affinity kiemelt szerepet kap.
