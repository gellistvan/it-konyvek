32.3 Ütemező, rendszerhívások és shell

A záróprojekt ezen pontján már van egy bootoló, memóriakezeléssel rendelkező kernel. Ebben a fejezetben a rendszer futtathatóvá válik: megvalósítjuk a feladatmodellt, a round-robin ütemezőt, a rendszerhívás-belépési pontot, az init folyamatot és egy minimális shellt. A cél nem egy általános célú operációs rendszer teljes körű reprodukálása, hanem egy olyan zárt, ellenőrizhető kernel, amelyben minden fontos állítás kódolvasással vagy mérési naplóval alátámasztható.

A fejezet feltételezi, hogy az os123 egység után rendelkezésre áll egy bootoló kernel, egy egyszerű memóriatérkép és egy buildrendszer. Az itt bemutatott kódrészletek RISC-V példát használnak, mert a QEMU virt gépe jól reprodukálható; az elv azonban x86-on vagy más architektúrán is azonos. A konkrét regiszterneveket és utasításokat mindig az adott porton ellenőrizni kell.

32.3.1 1. Feladatmodell és adatstruktúrák

A futtatható egységet itt feladatnak nevezzük. A feladat lehet kernelkontextusban induló szál, de a fejezet szempontjából a felhasználói program futtatása a lényeges eset. A feladatmodell minimális, de kellően bővíthető ahhoz, hogy az os125 fájlrendszer-integrációt rá lehessen építeni.

A központi struktúra a PCB (process control block), amelyet itt task néven valósítunk meg:

/* task.h – a minimalis feladatmodell */
#define TASK_UNUSED  0
#define TASK_READY   1
#define TASK_RUNNING 2
#define TASK_SLEEP   3
#define TASK_ZOMBIE  4

#define KSTACK_SIZE  4096

struct cpu_context {
    uint64_t ra;      /* visszateresi cim */
    uint64_t sp;      /* kernel veremmutato */
    uint64_t s0;
    uint64_t s1;
    uint64_t s2;
    uint64_t s3;
    uint64_t s4;
    uint64_t s5;
    uint64_t s6;
    uint64_t s7;
    uint64_t s8;
    uint64_t s9;
    uint64_t s10;
    uint64_t s11;
};

struct task {
    uint64_t pid;
    int      state;
    uint64_t kernel_stack_top;
    struct cpu_context ctx;
    uint64_t user_pc;
    uint64_t user_sp;
    uint64_t satp;            /* hasznalt lapkeptabla, ha van MMU */
    struct trapframe *trapframe; /* user->kernel belepesi munkaterulet */
    uint64_t quantum_left;    /* hatralevo idoszelet, tickben */
    struct task *next;
};

A cpu_context a callee-saved regisztereket tartalmazza. Ez a kiválasztás fontos: egy C függvényből hívott switch_to után a hívó csak azokat a regisztereket látja konzisztensnek, amelyeket a hívott függvénynek meg kell őriznie. A caller-saved regisztereket a kontextusváltást hívó kódnak nem kell külön mentenie, mert a C hívási konvenció szerint a hívó már elmentette őket, ha szüksége van rájuk.

A state mező a folyamatállapot-gépet írja le. A állapotátmenetek:

UNUSED -> READY        (letrehozas, init)
READY   -> RUNNING     (utemezo kivalasztja)
RUNNING -> READY       (idoszelet lejart)
RUNNING -> SLEEP       (rendszerhivas varakozasra kenyszeriti)
SLEEP   -> READY       (esemeny megerkezett)
RUNNING -> ZOMBIE      (kilepes)
ZOMBIE  -> UNUSED      (takaritas, szulo begyujtotte)

A kezdeti kernel a boot szakasz után létrehoz egy init feladatot, amely az első felhasználói programot futtatja. A további feladatok ebből a feladatból jönnek létre rendszerhívással, vagy a kernel indítja őket statikusan.

A feladatok egyetlen körkörösen láncolt listában, illetve külön futásra kész (READY) sorban állnak. A round-robin ütemező ebből választja a következő TASK_READY állapotú elemet. A választás költsége attól függ, milyen adatszerkezetet használunk:

  • Ha a listában vegyesen vannak READY, SLEEP és ZOMBIE elemek, akkor a kurzortól induló bejárás legrosszabb esetben a teljes listát végigjárja, tehát a döntés 𝒪(n)\mathcal{O}(n); az „amortizált 𝒪(1)\mathcal{O}(1)” csak akkor igaz, ha a lista hossza állandó és minden eleme READY, amit a blokkolt feladatok jelenléte megbont.
  • Ha külön READY sort tartunk fenn, akkor a fejről 𝒪(1)\mathcal{O}(1) a kivétel, és a lefutott feladatot a sor végére betéve 𝒪(1)\mathcal{O}(1) a visszahelyezés. A sor így pontosan a round-robin sorrendet adja, és a blokkolt feladatok nem lassítják a döntést.

A gyakorlatban a lista hossza a záróprojektben nagyon kicsi, ezért a lineáris bejárás is elfogadható, de a kurzorszabályt ilyenkor is rögzíteni kell: a kurzor mindig az utoljára kiválasztott elemre mutat, és a keresés az ő következő elemétől indul, különben egy READY elem tartósan kimaradhat, és a sorrend nem lesz fair.

32.3.2 2. Timer interrupt és round-robin ütemezés

A round-robin ütemező alapja a hardveres időzítő megszakítása. A záróprojektben a QEMU virt gép CLINT (Core Local Interruptor) eszköze adja az mtime számlálót és a hartonkénti mtimecmp összehasonlítót. Fontos részlet, hogy a CLINT MMIO-regiszterei csak M-módban érhetők el; az S-módban futó kernel ezért nem írhatja közvetlenül a mtimecmp-t, hanem az SBI (Supervisor Binary Interface) TIME kiterjesztését használja: az a7 = 0x54494D45 EID, a0 = 0 FID hívás az a0 regiszterben kapott abszolút határidőt (timebase-tickben) programozza be, és egyúttal törli a függőben lévő STIP bitet. Az OpenSBI ezt a hívást M-módban hajtja végre.

A periódus nem ezredmásodpercben, hanem a timebase óraütéseiben értendő. A virt gép DTB-je megadja a timebase-frequency értéket (jellemzően 10 MHz), ebből a 10 ms-os periódus timebase_freq / 100 tick. A konfiguráció a kernel/timer.c-ben történik:

/* timer.c – periodikus timer beallitasa S-mode kernelbol, SBI TIME hivassal */
#define TIMER_HZ        100u          /* 10 ms periodus */
extern uint64_t timebase_freq;        /* a DTB timebase-frequency erteke, pl. 10 000 000 */

static uint64_t ticks_per_period(void) {
    /* a CLINT mtime/mtimecmp a timebase orauteseiben szamol, nem ms-ban */
    return timebase_freq / TIMER_HZ;
}

void timer_rearm(void) {
    uint64_t now  = r_time();               /* rdtime: timebase tickek */
    uint64_t next = now + ticks_per_period();
    sbi_set_timer(next);                    /* SBI TIME, EID 0x54494D45, FID 0 */
}

void timer_init(void) {
    timer_rearm();
    /* STIE engedelyezese a sie CSR-ben; az SIE a sstatus-ban, a trap belepes
       a trapframe-ben tortenik */
    w_sie(r_sie() | SIE_STIE);
}

Az sbi_set_timer hívás nélkül a megszakítás nem törlődne, és a timer_interrupt_handler újra meg újra belépne; a következő határidőt ezért minden megszakítás elején újra kell programozni.

A timer megszakítás kezelője tick-et ad. Ha az aktuális feladat quantum_left értéke eléri a nullát, a kernel beállítja a feladatot TASK_READY állapotba, és meghívja az ütemezőt. A kezelőnek minden belépéskor újra kell programoznia a következő határidőt, különben a megszakítás függőben marad:

void timer_interrupt_handler(void) {
    timer_rearm();          /* kovetkezo hatarido; egyben torli a fuggoben levo STIP-et */

    if (!current || current->state != TASK_RUNNING) {
        return;             /* bootstrap vagy idle: nincs mitol idoszeletet venni */
    }
    if (current->quantum_left > 0) {
        current->quantum_left--;
    }
    if (current->quantum_left == 0) {
        current->state = TASK_READY;
        schedule();
    }
}

A schedule függvény kiválasztja a lista következő futtatható elemét, és ha az eltér az aktuálistól, kontextust vált. Három esetet külön kell kezelni: az első váltást, amikor még nincs prev; az azonos next/current esetet, amikor nincs értelme váltani; és azt, amikor nincs futtatható feladat, ilyenkor az idle feladatra váltunk:

void schedule(void) {
    struct task *prev = current;
    struct task *next = pick_next_task(prev);   /* a kurzor a prev-tol indul */

    if (!next)
        next = idle_task;                       /* nincs futtathato feladat */
    if (!next)
        panic("nincs idle feladat es nincs futtathato task");

    if (next == prev) {
        /* csak ez az egy feladat futtathato: nem valtunk, de ujratoltjuk az idoszeletet */
        prev->state = TASK_RUNNING;
        prev->quantum_left = QUANTUM;
        return;
    }

    current = next;
    next->state = TASK_RUNNING;
    next->quantum_left = QUANTUM;

    if (prev) {
        switch_to(&prev->ctx, &next->ctx);
    } else {
        /* bootstrap: az elso valtasnal meg nincs elozo feladat. A boot szal
           kontextusa eldobhato, ide soha nem terunk vissza. */
        static struct cpu_context boot_ctx;
        switch_to(&boot_ctx, &next->ctx);
    }
}

A schedule csak letiltott megszakítás mellett hívható. A switch_to visszatérése már az új feladat vermén történik; amikor egy korábbi feladatra kerül a sor, az a saját schedule hívásából switch_to után folytatódik, és visszatér a megszakítás-kezelőbe. Az idle feladat feladata, hogy a processzort alvó utasítással (wfi) adja át, ha nincs más futható munka.

A pick_next_task(prev) a prev körkörös listabeli következő elemétől indul, és az első TASK_READY elemet adja vissza; ha a prev az egyetlen READY elem, akkor őt magát. Így a sorrend valóban körkörös, és nem kell a lista elejére visszaugrani. Külön READY sor esetén ugyanez a szabály: a fejről kivesszük a feladatot, és a futás után a sor végére tesszük vissza. A round-robin Gantt-diagramja három feladattal, 10 ms időkerettel:

P1: 0---10 30---40 60---70
P2: 10--20 40---50 70---80
P3: 20--30 50---60 80---90

Az első kör válaszideje ebben a példában, ha mindhárom feladat 10 ms-ot használ fel: P1P_1 0 ms, P2P_2 10 ms, P3P_3 20 ms, átlag 10 ms. Állandósult állapotban viszont minden feladat a saját 10 ms-os futása után 20 ms-ot vár a következő 10 ms-os szeletéig, tehát az átlagos várakozási idő 20 ms. A valóságban, ha egy feladat letiltja a megszakításokat vagy rendszerhíváson keresztül blokkol, az átlagos várakozási idő tovább nő.

A kontextusváltás a kernel legalacsonyabb szintű része, ezért assemblyben írjuk. A RISC-V mentési és visszatöltési sorrendje:

# switch_to(a0 = &old_ctx, a1 = &new_ctx)
.globl switch_to
switch_to:
    sd ra, 0(a0)
    sd sp, 8(a0)
    sd s0, 16(a0)
    sd s1, 24(a0)
    sd s2, 32(a0)
    sd s3, 40(a0)
    sd s4, 48(a0)
    sd s5, 56(a0)
    sd s6, 64(a0)
    sd s7, 72(a0)
    sd s8, 80(a0)
    sd s9, 88(a0)
    sd s10, 96(a0)
    sd s11, 104(a0)

    ld ra, 0(a1)
    ld sp, 8(a1)
    ld s0, 16(a1)
    ld s1, 24(a1)
    ld s2, 32(a1)
    ld s3, 40(a1)
    ld s4, 48(a1)
    ld s5, 56(a1)
    ld s6, 64(a1)
    ld s7, 72(a1)
    ld s8, 80(a1)
    ld s9, 88(a1)
    ld s10, 96(a1)
    ld s11, 104(a1)
    ret

A ra és sp mentése/utolsó betöltése nem triviális: a ret a ra értékét használja, ezért a ra-t utoljára kell betölteni. A fenti sorrendben a ret előtt az ra már az új kontextus visszatérési címét tartalmazza. A sp pedig az új kernel veremre mutat.

Fontos tervezési döntés, hogy a kontextusváltás mindig kernel módból kernel módba történik. A felhasználói regiszterek mentését nem itt, hanem a trap belépésnél kell elvégezni. Ha a kernel a felhasználói feladatot timer interrupt miatt váltja, a felhasználói regisztereket a trapframe már tartalmazza. Ezért a task struktúrában lévő trapframe mutató erre a munkaterületre mutat; a korábbi uint64_t trapframe_ptr típus helyett szándékosan típusos pointert használunk, hogy a fordító a mező hozzáférését ellenőrizze.

32.3.3 3. Trap belépés és rendszerhívás-dispatcher

A felhasználói programok futtatásához a kernelnek meg kell valósítania a user/kernel átlépést. RISC-V-n ez az ecall utasításon keresztül történik. A felhasználói program a syscall számot az a7 regiszterbe, az argumentumokat az a0–a5 regiszterekbe teszi, majd ecall-t hajt végre. A hardver átvált kernel módra, és a trap_vector-ben lévő kódra ugrik.

A trap belépés során a kernelnek el kell mentenie a felhasználói regisztereket egy trapframe struktúrába:

/* A trapframe mezosorrendje pontosan egyezik a trap_vector mentesi
   sorrendjevel; a ketto egyezeset statikus asszert ellenorzi. */
struct trapframe {
    uint64_t ra;                                  /* x1  */
    uint64_t sp;                                  /* x2  */
    uint64_t gp;                                  /* x3  */
    uint64_t tp;                                  /* x4  */
    uint64_t t0, t1, t2;                          /* x5-x7 */
    uint64_t s0, s1;                              /* x8-x9 (s0 = fp) */
    uint64_t a0, a1, a2, a3, a4, a5, a6, a7;      /* x10-x17 */
    uint64_t s2, s3, s4, s5, s6, s7, s8, s9, s10, s11; /* x18-x27 */
    uint64_t t3, t4, t5, t6;                      /* x28-x31 */
    uint64_t sepc;    /* visszateresi cim user modba */
    uint64_t sstatus; /* elozo privilegium szint (SPP) */
};

_Static_assert(offsetof(struct trapframe, sepc) == 31 * sizeof(uint64_t),
               "trapframe/sepc elteres: az assembly es a C nem egyezik");

Az x0 (zero) regisztert nem kell menteni. A 31 mentett általános regiszter után a sepc a 248., a sstatus a 256. bájttal kezdődik, így a keret 264 bájt, amelyet 16 bájtra igazítva 272 bájtra kerekítünk.

Az alvó feladatok ébresztése: a struct task egészüljön ki uint64_t wake_at; mezővel; a sys_sleep(ms) wake_at = r_time() + ms * timebase_freq / 1000, state = TASK_SLEEP, majd schedule(); a timer_interrupt_handler elején minden TASK_SLEEP feladatra if (r_time() >= t->wake_at) t->state = TASK_READY;. Az idle feladat: for (;;) { intr_on(); wfi(); }. A trap_vector S-módú belépésnél (kernel-futás alatt, például az idle wfi megszakítása) ne cseréljen vermet: user-futás alatt az sscratch a kernelverem teteje, kernel-futás alatt 0; belépéskor csrrw sp, sscratch, sp; bnez sp, from_user; csrrw sp, sscratch, sp (S-mód: az eredeti sp marad).

A trap_vector assembly kód először a kernel stackre lép, elmenti az összes regisztert, meghívja a C trap_handler függvényt, majd visszatöltve a regisztereket sret-tel visszalép user módba:

# trap_vector: user modbol erkezo ecall/timer lep be ide.
# A kernel stack teteje a task sscratch mezoben van.
.globl trap_vector
.align 4

    addi  sp, sp, -272          # 31 regiszter + sepc + sstatus, 16-ra igazitva

    sd    gp,  16(sp)

    sd    t0,  32(sp)
    sd    t1,  40(sp)
    sd    t2,  48(sp)

    sd    s1,  64(sp)
    sd    a0,  72(sp)

    sd    a5, 112(sp)
    sd    a6, 120(sp)
    sd    a7, 128(sp)
    sd    s2, 136(sp)
    sd    s3, 144(sp)
    sd    s4, 152(sp)
    sd    s5, 160(sp)
    sd    s6, 168(sp)
    sd    s7, 176(sp)
    sd    s8, 184(sp)
    sd    s9, 192(sp)
    sd    s10,200(sp)
    sd    s11,208(sp)

    sd    t4, 224(sp)
    sd    t5, 232(sp)
    sd    t6, 240(sp)
    csrr  t0, sscratch

    ld    t4, 224(sp)
    ld    t5, 232(sp)

    addi  sp, sp, 272
    csrrw sp, sscratch, sp      # sp = user sp, sscratch = kernel stack teteje

A trap belépéskor a hardver kikapcsolja az SIE bitet, a sepc a megszakított utasításra, a scause az okra, az stval pedig szükség esetén a hibás címre mutat. Az sret az sstatus.SPP és sstatus.SPIE alapján állítja vissza a privilegizált szintet és az SIE bitet. Ha a feladatváltás sscratch-et használ a kernel stack megkeresésére, akkor a switch_to-nak a new task kernel_stack_top értékét is be kell írnia az sscratch CSR-be, különben a következő trap a régi feladat vermére lépne.

A teljes trap entry/exit útvonal tehát négy dolgot garantál: minden GPR mentése és visszaállítása szimmetrikus; a sepc a handler által módosítható; az assembly és a C struktúra offsetjei statikusan egyeznek; és a sstatus visszaállítása után az sret a megfelelő privilegizált szintre tér vissza.

Az alábbi ábra a kétféle mentett állapot (trapframe: user regiszterek; cpu_context: kernel callee-saved regiszterek) helyét és egy timer-preempció hét lépését mutatja két feladat között; az interaktív változatban az ecall útja is lejátszható.

A C oldali trap_handler megvizsgálja a megszakítás okát, és ha ecall-t észlel, a syscall_dispatch függvényt hívja:

void trap_handler(struct trapframe *tf) {
    uint64_t cause = r_scause();

    if (cause & SCAUSE_INTERRUPT) {          /* a legfelso bit jelzi a megszakítast */
        if (cause == SCAUSE_TIMER) {         /* S-módú timer: 0x8000...0005 */
            timer_interrupt_handler();
            return;
        }
        panic("ismeretlen megszakitas");
    }

    if (cause == SCAUSE_ECALL_USER) {
        /* A visszateresi PC-t MEG a diszpecser elott leptetjuk: a fork
           igy mar a kovetkezo utasitas cimet masolja a gyermekbe. */
        tf->sepc += 4;
        syscall_dispatch(tf);
        return;
    }

    panic("ismeretlen kivetel");
}

A sepc növelésének a syscall_dispatch előtt kell megtörténnie. Ha utána növelnénk, a fork belsejében készülő gyermek trapframe még az ecall saját címét tartalmazná, és a gyermek visszatérésekor újra végrehajtaná ugyanazt a rendszerhívást. A megszakítás-oknál a scause felső bitje különbözteti meg a szinkron kivételtől, ezért a nyers érték összehasonlítása helyett előbb ezt a bitet kell vizsgálni.

A syscall_dispatch a rendszerhívási táblát használja. A tábla egy függvénypointer-tömb, ahol az index a syscall szám:

/* Minden rendszerhivas ugyanazt a trapframe-et kapja; a parametereket a
   hivas sajat maga olvassa ki. Igy nincs variadikus atadasi ut, es a
   fordito minden hivast ellenoriz. */
typedef long (*syscall_fn_t)(struct trapframe *tf);

long sys_write(int fd, uint64_t user_buf, size_t n);
long sys_read(int fd, uint64_t user_buf, size_t n);
long sys_exit(int code);
long sys_fork(void);
long sys_ps(void);
long sys_sleep(unsigned ms);
long sys_wait(int pid);
long sys_halt(void);

/* include/syscall_nr.h: enum { SYS_WRITE, SYS_READ, SYS_EXIT, SYS_FORK, SYS_WAIT,
   SYS_PS, SYS_SLEEP, SYS_HALT, SYS_NR }; */

static long sys_write_adapter(struct trapframe *tf) {
    return sys_write((int)tf->a0, tf->a1, (size_t)tf->a2);
}
static long sys_read_adapter(struct trapframe *tf) {
    return sys_read((int)tf->a0, tf->a1, (size_t)tf->a2);
}
static long sys_exit_adapter(struct trapframe *tf) {
    return sys_exit((int)tf->a0);
}
static long sys_ps_adapter(struct trapframe *tf) {
    (void)tf;
    return sys_ps();
}
static long sys_sleep_adapter(struct trapframe *tf) {
    return sys_sleep((unsigned)tf->a0);
}
static long sys_fork_adapter(struct trapframe *tf) {
    (void)tf;                    /* a sys_fork a current trapframe-jéből dolgozik */
    return sys_fork();
}
static long sys_wait_adapter(struct trapframe *tf) {
    return sys_wait((int)tf->a0);
}
static long sys_halt_adapter(struct trapframe *tf) {
    (void)tf;
    return sys_halt();
}

static const syscall_fn_t syscall_table[] = {
    [SYS_WRITE] = sys_write_adapter,
    [SYS_READ]  = sys_read_adapter,
    [SYS_EXIT]  = sys_exit_adapter,
    [SYS_FORK]  = sys_fork_adapter,
    [SYS_WAIT]  = sys_wait_adapter,
    [SYS_PS]    = sys_ps_adapter,
    [SYS_SLEEP] = sys_sleep_adapter,
    [SYS_HALT]  = sys_halt_adapter,
};

void syscall_dispatch(struct trapframe *tf) {
    uint64_t nr = tf->a7;        /* 64 biten marad: nincs 32 bites szukites */
    if (nr >= ARRAY_SIZE(syscall_table) || !syscall_table[nr]) {
        tf->a0 = (uint64_t)-ENOSYS;
        return;
    }
    tf->a0 = (uint64_t)syscall_table[nr](tf);
}

A NULL bejegyzés szándékos: a SYS_FORK külön ágon fut, mert a copy_task a current->trapframe-ből dolgozik, nem a hívás argumentumaiból. A diszpécser a NULL bejegyzést -ENOSYS-szel utasítja el, tehát egy hiányzó implementáció nem okoz ugrást nullára. A syscall szám uint64_t, ezért nincs értelme negatív értéket vizsgálni; a nr >= ARRAY_SIZE ellenőrzés a 32 bites szűkítés nélkül is helyes.

A diszpécser feladata kettős: egyrészt a syscall számot ellenőrzi, másrészt a visszatérési értéket az a0 regiszterbe írja. A hibakódot az errno-hoz hasonlóan negatív értékként adjuk vissza. A felhasználói oldali libc-wrapper ezt lefordítja -1-re és beállítja az errno-t. Például:

/* user/lib/syscall.c */
ssize_t write(int fd, const void *buf, size_t n) {
    ssize_t ret = syscall(SYS_WRITE, fd, (uint64_t)buf, n, 0, 0, 0);
    if (ret < 0) {
        errno = -ret;
        return -1;
    }
    return ret;
}

A rendszerhívások sikeres végrehajtása nem írhatja felül a felhasználói memóriát ellenőrizetlenül. A sys_write például a felhasználói puffer címeit a kernel címfordítási tartományába kell konvertálnia, és meg kell vizsgálnia, hogy az adott tartomány valóban a felhasználóhoz tartozik. A minimális kernelben ez két részből áll: egy kivonásos tartományellenőrzésből, amely nem tud túlcsordulni, és egy fault-biztos másolásból, amely a leképezés hiányát és a hiányzó U bitet is kezeli:

long sys_write(int fd, uint64_t user_buf, size_t n) {
    if (fd != 1 && fd != 2)
        return -EBADF;
    /* kivonasos ellenorzes: a user_buf + n kifejezes tullcsordulhatna */
    if (user_buf >= USER_TOP || n > USER_TOP - user_buf)
        return -EFAULT;
    /* a cimtartomany onmagaban nem bizonyitja a lekepezest es az U bitet:
       a copy_from_user fault-biztos, a hibat a trap fixup-ja alakítja -EFAULT-tá */
    return (long)copy_from_user_to_uart(user_buf, n);
}

/* A copy_from_user a megszakitas-kezelo fixup tablajan keresztul EFAULT-t ad,
   ha a lap hianyzik, a PTE U bitje 0, vagy a tartomany atnyulik USER_TOP-on.
   A fuggveny nem dereferalja kozvetlenul a felhasznaloi cimet. */
long copy_from_user(void *dst, uint64_t src, size_t n);

A puszta numerikus határellenőrzés nem elég: a [0, USER_TOP) tartományban lehetnek nem leképezett lapok, lehetnek csak S-módban olvasható lapok (U = 0), és a felhasználó olyan címet is adhat, amely a tartományon belül van, de a fizikai lapja nem az övé. Ezért a másolásnak minden laphatárt külön kell kezelnie, a hibát pedig a trap-kezelő fixup-táblája alakítja -EFAULT-tá, nem a kernel pánikol. A negatív tesztekhez tartozik a nem leképezett lap, a kernelcím (például 0x8000_0000), a USER_TOP fölé nyúló puffer és a USER_TOP körüli átfordulás (n nagy értéke) esete.

32.3.4 4. Init folyamat és felhasználói programok betöltése

A kernel inicializálása után az init feladat létrehozása a következő lépésekből áll:

  1. A kernel lefoglal egy task struktúrát, egy kernel stacket és egy trapframe-et; mindhárom foglalás hibáját külön kell kezelni.
  2. Lefoglalja és leképezi a felhasználói képet: a szöveg-, adat- és vermet U = 1 lapokkal, a kernelterületet pedig csak S-módban elérhetően.
  3. Beállítja a feladat állapotát TASK_READY-re, a PID-et 1-re, az időszeletet QUANTUM-ra.
  4. A trapframe-ben beállítja a sepc belépési pontot, a felhasználói sp-t, valamint a sstatus.SPP = 0 és sstatus.SPIE = 1 értéket.
  5. Elkészíti a felhasználói satp értéket; a címváltás után sfence.vma szükséges.
  6. A feladatot hozzáadja az ütemező listájához.
  7. Hibás foglalás vagy leképezés esetén a már lefoglalt erőforrásokat felszabadítja, és a részleges feladatot nem teszi a listára.

Az init programot a kernelbe ágyazzuk, vagy egy egyszerű initrd-ből töltjük be. A záróprojektben a legegyszerűbb, ha a init bináris kódját a kernel ELF szekciójába linkeljük, és a kernel a init_start/init_end szimbólumokból másolja a felhasználói memóriába.

Példa a betöltésre:

struct task *alloc_task(void);              /* nullazott PCB vagy NULL */
uint64_t alloc_kstack(void);                /* kernel stack teteje vagy 0 */
struct trapframe *alloc_trapframe(void);    /* belepesi keret vagy NULL */
void free_task(struct task *t);
void free_kstack(uint64_t top);
void free_trapframe(struct trapframe *tf);
int  map_user_image(struct task *t);        /* user text/data/stack, U=1 */

int init_task_create(void) {
    struct task *t = alloc_task();
    if (!t)
        return -ENOMEM;

    t->kernel_stack_top = alloc_kstack();
    t->trapframe        = alloc_trapframe();
    if (!t->kernel_stack_top || !t->trapframe)
        goto fail;

    if (map_user_image(t) != 0)             /* a felhasznaloi lapok U=1-gyel */
        goto fail;

    t->pid          = 1;
    t->state        = TASK_READY;
    t->quantum_left = QUANTUM;
    t->satp         = build_user_satp(t);   /* U-mod cimter; a kernel S-modbol latja */

    /* teljes bootstrap trapframe: az sret ide ter vissza user modba */
    t->trapframe->sepc    = USER_ENTRY;
    t->trapframe->sp      = USER_STACK_TOP;
    t->trapframe->sstatus = (r_sstatus() & ~SSTATUS_SPP) | SSTATUS_SPIE;

    list_add(&task_list, t);
    return 0;

fail:
    free_trapframe(t->trapframe);
    free_kstack(t->kernel_stack_top);
    free_task(t);
    return -ENOMEM;             /* reszleges task nem kerul a listara */
}

A build_user_satp által visszaadott azonosító beírása a satp CSR-be csak sfence.vma-val együtt érvényes; enélkül a TLB a régi leképezést használhatja. A felhasználói lapok PTE_U bitjét kötelező beállítani, a kernel lapjait pedig PTE_U = 0-val kell leképezni, különben a user mód hozzáférhet a kernelhez. A trapframe sstatus mezőjében a SPP törlése user módot, a SPIE beállítása pedig azt jelenti, hogy az sret után az SIE engedélyezve lesz.

A felhasználói init program a kernelben előre definiált ELF szimbólumként vagy egy egyszerű C függvényként szerepel, amelyet a kernel user módban indít el. A sret úgy tér vissza, hogy a PC az init_entry értékét veszi fel.

A init program első feladata, hogy létrehozza a shell folyamatot, majd várakozzon a gyermek folyamatok befejeződésére. A minimális kernelben a fork és wait rendszerhívásokat is implementálni kell. Ha a teljesség nem szükséges, a shell közvetlenül az init-ben is futtatható, de ez korlátozza a többfeladatos tesztelést. A laborban ezért fork és wait is szerepel.

Egy egyszerű fork implementáció:

int sys_fork(void) {
    struct task *child = copy_task(current);
    if (!child) return -ENOMEM;
    child->pid = next_pid++;
    child->state = TASK_READY;
    /* a gyermek visszateresi erteke 0 lesz */
    child->trapframe->a0 = 0;
    list_add(&task_list, child);
    return child->pid;
}

A copy_task a struct task-ot, a trapframe-et (*child->trapframe = *current->trapframe) és a felhasználói címteret másolja; a kernelvermet nem másolja. A trap_vector a keretet a current->trapframe területére menti (a kernelverem teteje a trapframe egy mezőjében van, sscratch a user/kernel váltást kezeli). Az új feladat első indításához a ctx kezdőértéke: t->ctx.ra = (uint64_t)user_return; t->ctx.sp = t->kernel_stack_top;, ahol a void user_return(void) a current->trapframe-ből visszatölti a regisztereket, a satp-t (csrw satp, %0; sfence.vma zero, zero a current->satp értékével), majd sret-tel lép user módba (a trap_vector kilépő ágának közös része); így a schedule() switch_to-ja a ret-tel a user_return-be ugrik. A gyermek saját laptáblát kap: a copy_task a szülő minden U-lapjához új frame-et foglal (frame_alloc), a tartalmat a kernel direct mapen át memcpy-vel másolja, és a gyermek laptáblájába ugyanarra a virtuális címre képezi le (COW a bővítés). A kernel minden felhasználói laptáblában ugyanúgy (U = 0) le van képezve, hogy a satp-váltás után is fusson. A sys_wait a megadott gyermeket várja, a sys_halt az SBI SRST hívással leállítja a gépet (csak a PID 1 hívhatja).

32.3.5 5. Minimális shell

A shell egy felhasználói program, amely a szabványos bemenetről olvas, parancsokat értelmez, és a szabványos kimenetre ír. A minimális shell a következő parancsokat ismeri:

  • help: kiírja a parancsok listáját.
  • echo <szöveg>: visszaírja a szöveget.
  • ps: a kernel sys_ps hívásával listázza a feladatokat.
  • sleep <ms>: a sys_sleep hívásával várakozik; az argumentumot ellenőrizni kell (0 és 600000 ms között), mert a atoi a hibás bemenetet csendben 0-nak veszi, a negatív értéket pedig átadná a kernelnek.
  • exit: a SYS_EXIT hívással csak a shellt zárja be.
  • halt: a külön SYS_HALT hívással leállítja a laborgépet (SBI SRST vagy a sifive_test eszköz); csak a PID 1 hívhatja meg, és nem azonos az exit-tel.

A shell kódja:

/* user/init.c – minimalis shell */
static int read_line(char *buf, int cap) {
    int n = 0;
    for (;;) {
        char c;
        if (read(0, &c, 1) != 1)
            return -1;
        if (c == '\r' || c == '\n')
            break;                  /* soros konzolon az Enter CR; a CR LF második bájtja üres sort ad, amit a főciklus kihagy */
        if (n < cap - 1)
            buf[n++] = c;           /* a hosszabb sort levagjuk, de tovabb olvassuk */
    }
    buf[n] = '\0';
    return n;
}

static char *skip_spaces(char *p) {
    while (*p == ' ')
        p++;
    return p;
}

/* 0..600000 ms kozotti egesz; hibanal -1 */
static long parse_ms(const char *s, char **end) {
    errno = 0;
    long v = strtol(s, end, 10);
    if (errno == ERANGE || v < 0 || v > 600000)
        return -1;
    return v;
}

int main(void) {
    char line[128];
    for (;;) {
        puts("$ ");
        int n = read_line(line, sizeof(line));
        if (n < 0) {
            puts("\nread hiba vagy EOF, kilepes\n");
            exit(1);
        }
        char *cmd = skip_spaces(line);
        if (*cmd == '\0')
            continue;

        if (strcmp(cmd, "help") == 0) {
            puts("help         - ez a lista\n");
            puts("echo <text>  - kiirja a szoveget\n");
            puts("ps           - feladatok listazasa\n");
            puts("sleep <ms>   - varakozas (0..600000)\n");
            puts("exit         - a shell bezarasa\n");
            puts("halt         - a laborgép leallitasa\n");
        } else if (strncmp(cmd, "echo ", 5) == 0) {
            puts(cmd + 5);
            puts("\n");
        } else if (strcmp(cmd, "ps") == 0) {
            ps();
        } else if (strncmp(cmd, "sleep ", 6) == 0) {
            char *p = skip_spaces(cmd + 6);
            char *end;
            long ms = parse_ms(p, &end);
            if (end == p || ms < 0 || *skip_spaces(end) != '\0') {
                puts("sleep: ervenytelen idotartam (0..600000 ms)\n");
                continue;
            }
            sleep((unsigned)ms);
        } else if (strcmp(cmd, "exit") == 0) {
            exit(0);                /* csak a shellt zarja be */
        } else if (strcmp(cmd, "halt") == 0) {
            halt();                 /* SYS_HALT: SBI SRST, csak a laborgépet allitja le */
            puts("halt: nem sikerult\n");
        } else {
            puts("ismeretlen parancs: ");
            puts(cmd);
            puts("\n");
        }
    }
}

A shell működése bemutatja a rendszerhívások használatát: a read a SYS_READ-et, a puts a SYS_WRITE-et, a ps a SYS_PS-et, az exit a SYS_EXIT-et, a halt a SYS_HALT-ot hívja. A fork-ot a shell indításakor a kernelben, vagy az init felhasználói programban használjuk. A read_line kezeli a CR/LF pár mindkét bájtját, a parancsot szóközök mentén vágja le, és a hosszabb sort levágja, de a maradékát kiolvassa, hogy a következő iteráció ne a sor közepéről induljon.

A sys_ps implementációja a kernelben bejárja a feladatlistát, és a feladat állapotát egy belső pufferbe írja, amit a felhasználói program a SYS_PS hívással kérhet le. A kimeneti formátum egyszerű, például:

PID  STATE   PC
1    running 0x1000
2    ready   0x1000
3    sleep   0x1000

A shell tehát nem közvetlenül éri el a kernel adatszerkezeteit, hanem a rendszerhíváson keresztül kapja az adatokat. Ez a határ a tanulságos: a felhasználói program soha nem láthatja a PCB lista pointereit.

32.3.6 6. Hibakezelés és tipikus hibák

A fenti komponensek megvalósítása során több tipikus hibát kell elkerülni. A legfontosabbak:

  1. A trapframe nem mentett regiszterei. Ha a trap_vector nem menti el az összes felhasználói regisztert, a rendszerhívásból való visszatérés után a felhasználói program korrupt regisztereket lát. Ez a hiba gyakran csak bizonyos syscall-oknál jelentkezik, mert a compiler a többi regisztert nem használja abban a függvényben. A megoldás: a trapframe minden felhasználói regisztert tartalmazzon, és a mentés/visszatöltés szigorúan szimmetrikus legyen.

  2. A sepc nem növelése ecall után. Ha a syscall_dispatch után nem növeljük a sepc-t, a visszatérés újra ugyanazt az ecall-t hajtja végre, ami végtelen ciklust okoz. A hiba jellemző tünete, hogy a shell az első rendszerhívás után lefagy.

  3. A felhasználói mutatók ellenőrzésének hiánya. A kernelben a sys_read és sys_write közvetlenül használja a felhasználói címet. Ha a felhasználó rossz mutatót ad, a kernel saját memóriáját olvashatja vagy írhatja. Ezt a záróprojektben legalább tartományellenőrzéssel meg kell akadályozni. A teljes izolációhoz user page table és hardveres védelem szükséges.

  4. Versenyhelyzet a schedulerben. A schedule hívásakor a megszakításokat le kell tiltani, különben a timer interrupt a kontextusváltás közben újra beléphet. A kernelben a megszakítás-tiltás a r_sstatus SIE bitjének törlésével történik. A switch_to előtt le kell tiltani, utána pedig a visszatéréskor engedélyezni.

  5. Kernel stack túlcsordulás. A KSTACK_SIZE 4096 bájt elegendő a minimális kernelhez, de ha a fork vagy a sys_ps nagy helyi változót hoz létre, a stack átfolyhat. A hibát a kernel stack alján elhelyezett őrszem mezővel lehet észlelni, vagy egyszerűen a stack méretét kell növelni.

  6. A fork gyermek visszatérési értéke nem nulla. Ha a gyermek folyamat a fork-ból ugyanazzal a PID-del tér vissza, mint a szülő, a shell logikája elromlik. A copy_task után a gyermek trapframe->a0 értékét nullára kell állítani.

  7. A wait implementációja nem takarítja a ZOMBIE-t. Ha a wait nem felszabadítja a gyermek task struktúráját, a rendszer feladatlistája lassan megtelik TASK_ZOMBIE elemekkel, és a pick_next_task egyre lassabb lesz. A megoldás a wait-ben a gyermek erőforrásainak felszabadítása.

A teszteléshez a következő negatív eseteket érdemes beilleszteni:

  • Érvénytelen syscall szám hívása: a SYS_DISPATCH -ENOSYS-szel térjen vissza, ne panic-eljen.
  • A read hívása a shellben 0 byte hosszúsággal: a kernel ne lépjen ki.
  • A fork 100-szor egymás után: a rendszer ne telítse be a memóriát.
  • A sleep közben a timer interrupt akkor is működjön, ha az aktuális feladat TASK_SLEEP állapotba kerül.

32.3.7 7. Labor: round-robin ütemező, syscallok és shell

A labor célja, hogy a fenti komponenseket egy emulált környezetben összeállítsuk és mérjük. A labor a os123 állapotára épül, és a os125 számára előkészíti a fájlrendszer-integrációt.

32.3.8 7.1 Kiinduló állapot

  • QEMU virt gép, RISC-V 64, 128 MiB RAM, 1 CPU.
  • Kernel forráskódja a kernel/ könyvtárban.
  • Boot és memóriakezelés az os123-ból.
  • Buildrendszer: Makefile, linkerscript kernel.ld.
  • Debug eszköz: GDB, QEMU monitor.

32.3.9 7.2 Build és futtatási parancsok

# a kernel forditasa az os123-ban rogzitett OpenSBI + ELF profil szerint
make clean
make kernel.elf ARCH=riscv64 CROSS=riscv64-unknown-elf-

# futtatas OpenSBI firmware-rel; a kernel 0x8020_0000-re van linkelve
make run ARCH=riscv64

# debug: QEMU gdbstubbal, a kernel sajat szimbolumaival
make debug ARCH=riscv64

A hivatkozott Makefile-részek és a QEMU-parancsok:

CROSS   ?= riscv64-unknown-elf-
QEMU    ?= qemu-system-riscv64
CFLAGS  := -march=rv64imac_zicsr -mabi=lp64 -mcmodel=medany -mno-relax -ffreestanding -fno-builtin -fno-common -fno-stack-protector -fno-tree-loop-distribute-patterns -O2 -g -Wall
OBJS    := entry.o trap.o switch.o kernel.o uart.o fdt.o frame.o vm.o heap.o string.o task.o timer.o syscall.o sbi.o
LDFLAGS := -T kernel.ld -nostdlib

all: kernel.elf

kernel.elf: $(OBJS) kernel.ld
    $(CROSS)ld $(LDFLAGS) -o $@ $(OBJS)

run: kernel.elf
    $(QEMU) -machine virt -m 128M -smp 1 -display none -serial mon:stdio \
      -bios default -kernel kernel.elf

debug: kernel.elf
    $(QEMU) -machine virt -m 128M -display none -serial mon:stdio \
      -bios default -kernel kernel.elf -s -S

A -bios none és a -kernel kernel.bin kombináció nem ehhez a profilhoz tartozik: -bios none esetén nincs firmware: a QEMU reset-kódja a DRAM elejére (0x80000000) ugrik, a kernel M-módban indul, és nincs SBI, így az sbi_set_timer hívás nem működne. Ebben a fejezetben ezért OpenSBI-t (-bios default) használunk, a kernel ELF-et pedig 0x8020_0000-re linkeljük. Aki -bios none-t akar, annak saját M-módú timerkezelést és nyers bináris linkelést kell adnia; ez külön bootprofil.

A debug indítás előtt ellenőrizni kell, hogy a szimbólum valóban benne van a kernelben:

riscv64-unknown-elf-nm kernel.elf | grep ' trap_handler$'

# kulon terminalban, a make debug ( -s -S ) elinditasa utan:
riscv64-unknown-elf-gdb kernel.elf \
  -ex 'target remote :1234' \
  -ex 'break trap_handler' \
  -ex 'continue'

A break trap_handler csak akkor áll be, ha a szimbólum létezik és a GDB az ELF szimbólumtábláját látja; a -s -S nélkül indított QEMU-hoz nem lehet csatlakozni.

A mérési naplóba rögzíteni kell a QEMU verzióját, a host CPU-t, az órajelét és a fordítási beállításokat. A példa mérési napló:

32.3.10 7.3 Implementációs lépések

  1. Hozd létre a task.h és task.c fájlokat, és implementáld a feladatlistát.
  2. Implementáld a timer megszakítást a timer.c-ben.
  3. Implementáld a switch_to assembly függvényt.
  4. Készítsd el a trap belépést és a trapframe mentést.
  5. Implementáld a syscall_dispatch-et és a syscall táblát.
  6. Hozd létre az init feladatot és a shell user programot.
  7. Kössd be a fork, wait, exit, sleep és halt syscallokat.
  8. Teszteld a ps parancsot és a fork-ot.
  9. Ellenőrizd két egymást követő periodikus ticket: a timer_interrupt_handler mindkét alkalommal újraprogramozza a következő határidőt, a tick számláló monoton nő, és a rendszer nem ragad be a timer megszakításba.
  10. Futtass egyszálas esetet: a schedule a next == prev ágon nem vált, csak újratölti az időszeletet, nem dereferálja a prev mutatót, és a feladat a következő tickig fut tovább.

32.3.11 7.4 Elvárt eredmény

A boot után a soros konzolon a következő jelenik meg:

[KERN] boot successful
[INIT] starting shell
$ help
help         - ez a lista
echo <text>  - kiirja a szoveget
ps           - feladatok listazasa
sleep <ms>   - varakozas (0..600000)
exit         - a shell bezarasa
halt         - a laborgép leallitasa
$ echo Hello
Hello
$ ps
PID  STATE   PC
1    running 0x1000
2    ready   0x1000
$ sleep 100
$ halt
[KERN] system halted

Az exit parancs csak a shellt zárja be; ha az init újraindítja, új shell indul, a rendszer nem áll le. A halt ezzel szemben a SYS_HALT híváson keresztül az egész emulált gépet leállítja; ez a labor egyetlen szándékos leállítási útja.

A ps kimenetben a PID 1 az init/shell, a PID 2 egy második folyamat lehet, amelyet a fork hozott létre. A pontos sorrend a shell indítási módjától függ.

32.3.12 7.5 Mérési napló

A mérés során a következő metrikákat rögzítjük. Minden időértékhez meg kell adni az időalapot és a felbontást: a rdcycle a hart CPU-ciklusszámlálóját olvassa (QEMU alatt ez nem valós idő, és a hoszt terhelésétől is függ), a rdtime pedig a timebase óraütéseit (a QEMU virt DTB timebase-frequency értéke, jellemzően 10 MHz). A két mértékegységet nem szabad keverni.

  1. Kontextusváltás költsége. A mérés két pontja ugyanahhoz a váltáshoz tartozik. A schedule a switch_to előtt rdcycle-t vesz, és az értéket a hartonkénti, váltásonkénti rekordba írja egy növekvő switch_seq sorszámmal; a switch_to visszatérése után – immár az új feladat vermén – a schedule folytatása szintén rdcycle-t vesz, és csak akkor számol különbséget, ha a rekord switch_seq értéke azonos. Így kizárjuk, hogy egy korábbi váltás páratlan rekordját egy későbbi váltással párosítsuk. A várakozási idő nem része a különbségnek, mert a két pont ugyanazon a harton, ugyanabban a megszakítási útvonalban van; a switch_to által elmentett és visszatöltött regiszterek számát dokumentálni kell.
  2. Rendszerhívás költsége. A trap_handler belépésén és az sret előtt vett rdcycle pár, ugyanazon a harton, ugyanahhoz a rendszerhíváshoz tartozó syscall_seq sorszámmal párosítva. A mérésbe nem számít bele a syscall által végzett tényleges I/O (például az UART lassú írása); ezt külön kell mérni.
  3. Timer-jitter. A timer_interrupt_handler minden hívásakor rdtime-et rögzítünk, és a szomszédos értékek különbségéből számítjuk a szórást. A jittert timebase-tickben adjuk meg; átszámításhoz a DTB timebase-frequency értékével kell osztani. A QEMU alatt a jitter a hoszt ütemezőjétől is függ, ezért a mérés legalább 1000 tickre és több, egymástól független futásra terjedjen ki, és a szórást a nyers mintákból kell számolni, nem becsülni.

A mérési napló táblázata (sablon; a „Mért érték” oszlop a laborban töltendő ki):

Mérés Módszer Egység Várt érték Mért érték Megjegyzés
Context switch rdcycle, azonos switch_seq pár ciklus – (kitöltendő) hart, futások száma
Syscall rdcycle, azonos syscall_seq pár ciklus – (kitöltendő) syscall számonként külön
Timer-jitter rdtime szomszédos különbségek szórása timebase-tick – (kitöltendő) timebase-frequency, tickek száma

A naplóban a mért és a várt értéket külön kell jelölni. A várt érték a hardver specifikációjából vagy egy korábbi, dokumentált mérésből származik; a mért érték a tényleges futásból. A nyers mintákat (hart-azonosító, sorszám, belépő/kilépő óraérték, számított különbség) is mellékelni kell, különben a szórás és az átlag nem ellenőrizhető. A QEMU verzióját, a hoszt CPU-t és pillanatnyi terhelését, valamint a fordítási beállításokat szintén rögzíteni kell; determinisztikus összehasonlításhoz a QEMU -icount módja használható, de ezt a naplóban külön jelölni kell.
