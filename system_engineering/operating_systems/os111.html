29.2 Blokk-eszköz és driver implementáció

A blokk-eszköz illesztése a kernelhez látszólag egyszerű feladat: a fájlrendszer kér egy logikai blokkot, a driver pedig visszaadja a bájtokat. A gyakorlatban azonban ez a határfelület koncentrálja a tárolórendszer legnehezebb kérdéseit: aszinkron végrehajtás, pufferelt I/O, DMA és a hardverhibák kezelése. Ebben a fejezetben egy olyan minimális blokk-illesztőt építünk fel, amely a saját rendszerünkben (emulált környezetben) működőképes, és amelyre a következő fejezetben a VFS-integrációt ráépíthetjük.

A fejezet célja nem egyetlen konkrét meghajtó (például NVMe vagy SATA AHCI) teljes implementációja – az messze meghaladná a keretet –, hanem az általános minta bemutatása, amelyet valós hardveren is alkalmazhatunk. A driverünk egy virtuális blokk-eszközt (például a QEMU virtio-blk eszközét vagy egy RAM-lemezt) vezérel, és a kernel belső blokk-rétegéhez kapcsolódik. A hangsúly a kérésbeadás, a completion, a DMA-pufferek és a hibakezelés helyes szerkezetén van.

29.2.1 A tárolóeszköz illesztése: szektor, blokk és eszközmodell

A blokk-eszközök (merevlemezek, SSD-k, NVMe-meghajtók, emulált lemezek) a rajtuk tárolt adatot rögzített méretű egységekben, szektorokban címzik. A klasszikus szektorméret 512 bájt, de a modern eszközök gyakran 4096 bájtos fizikai szektorral dolgoznak; a logikai szektorméret és a fizikai szektorméret eltérhet egymástól (Advanced Format, 4Kn). A kernel szempontjából az eszköz egy lineáris szektortömb: a 0..N-1 sorszámú szektorok, ahol N az eszköz kapacitása szektorban kifejezve.

A fájlrendszer és a blokk-réteg általában nagyobb egységekkel, logikai blokkokkal operál, amelyek mérete a szektorméret többszöröse (gyakran 4 KiB). A driver feladata, hogy ezeket a logikai blokk-kéréseket lefordítsa szektor-hozzáférésekre, és a hardverrel végrehajtassa az adatátvitelt. Ez a fordítás tipikusan a kernel blokk-rétegében történik, de egy saját, egyszerű kernelben ezt a feladatot a driver vagy a felső réteg közösen látja el. Fontos, hogy a határokat pontosan rögzítsük: a driver a szektor szintjén dolgozik, a felső réteg pedig logikai blokkokat ad át. Ez lehetővé teszi, hogy a driver egyszerű maradjon, és a cache-elés vagy az ütemezés a felsőbb rétegben valósuljon meg.

A kernelben minden blokk-eszközt egy azonosítóval és egy műveleti vektorral reprezentálunk. Saját rendszerünkben ez a következő egyszerű struktúrákat jelentheti:

/* freestanding C – saját kernel, nem vendégkód */
typedef uint64_t sector_t;   /* szektorcím */
typedef uint32_t blk_size_t; /* méret bájtban */

struct blkdev;

struct blkdev_ops {
    int (*read)(struct blkdev *dev, sector_t start,
                void *buf, size_t nsectors);
    int (*write)(struct blkdev *dev, sector_t start,
                 const void *buf, size_t nsectors);
    int (*flush)(struct blkdev *dev);
};

struct blk_queue;              /* a kérés-várólista, lentebb definiálva */

struct blkdev {
    char name[32];
    sector_t total_sectors;
    uint16_t sector_size;      /* logikai szektorméret, tipikusan 512 */
    uint16_t max_request_sectors;
    struct blk_queue *queue;   /* az eszköz saját kérés-várólistája */
    void *driver_data;         /* a driver privát állapota */
    const struct blkdev_ops *ops;
    uint32_t flags;            /* például BLKDEV_FLAG_DMA */
};

A regisztráció során a driver létrehoz egy struct blkdev példányt, kitölti a kapacitást, a szektorméretet és a műveleti vektort, majd egy globális listához adja. A felső réteg (például a VFS vagy a fájlrendszer) innen kapja meg az eszközt, és meghívja a read/write műveleteket. A szinkron műveleti vektor egyszerű, de nem skálázódik: egyetlen lassú I/O blokkolja a hívót, és a kernel nem tud párhuzamos kéréseket kezelni. Ezért a valódi interfész aszinkron kérésekkel dolgozik, amit a következő pontban tárgyalunk.

29.2.2 Request queue: aszinkron kérések és a completion modell

A blokk I/O természeténél fogva aszinkron: a lemez mechanikus feje (vagy az SSD vezérlője) időbe telik a kérés teljesítéséhez, és ezalatt a CPU-t nem érdemes blokkolni. A kernel ezért egy request queue-t (kérés-várólistát) tart fenn az eszközhöz: a felső réteg egy kérést (request) helyez el a sorban, majd visszatérhet. A driver feldolgozza a sor elején lévő kérést, elindítja a hardver I/O-t, és amikor az befejeződik (interrupt vagy polling jelzi), meghívja a completion callbacket, amely értesíti a várakozó folyamatot.

Saját minimális kernelünkben a kérés a következő struktúrával írható le:

/* freestanding C – saját kernel, illusztráció */
#define BLK_REQ_READ  0x01
#define BLK_REQ_WRITE 0x02
#define BLK_REQ_BARRIER 0x04  /* sorrendező/kiírás kényszerítés */
#define BLK_REQ_FAILED 0x80   /* a kérés hibával zárult */

typedef void (*blk_completion_fn)(void *cookie, int status);

struct blk_request {
    uint32_t flags;
    sector_t start;
    size_t nsectors;
    void *buf;                  /* adatpuffer (DMA-képes, ha szükséges) */
    blk_completion_fn complete; /* befejezés callback */
    void *cookie;               /* a hívó privát adata */
    struct blk_request *next;   /* láncolt lista a queue-hoz */

    /* Állapot, amelyet a driver és a retry-logika használ. */
    struct blkdev *dev;         /* melyik eszközön fut a kérés */
    int status;                 /* a legutóbbi befejezés hibakódja (0 = siker) */
    uint8_t retries;            /* eddigi újrapróbálkozások száma */
    struct work_struct retry_work; /* késleltetett újrapróbálás munkája */
};

struct blk_queue {
    struct blk_request *head;
    struct blk_request *tail;
    uint32_t pending_count;
    uint32_t max_pending;       /* a sor maximális hossza (backpressure) */
    bool busy;                  /* éppen feldolgozás alatt */
};

/* Egységes queue-interfész: 0 = sikeres beadás, negatív = hiba. */
int  blk_submit_request(struct blk_queue *q, struct blk_request *req);
/* Befejezés: bármely kontextusból (interruptból is) hívható, nem alszik. */
void blk_complete_request(struct blk_request *req, int status);

A kérésbeadási függvény – a kernel nevezheti blk_submit_request-nek – a kérést a sor végére fűzi, majd ha a driver éppen szabad, jelzi a feldolgozás megkezdését. A driver start_next_request rutinja kiveszi a sor elejét, beállítja a hardvert, majd visszatér. Amikor az interrupt jelzi a befejezést, az interrupt-kezelő meghívja a kérés complete callbackjét, és ha a sor nem üres, elindítja a következő kérést. Ez a modell biztosítja a sorba állítást, a párhuzamosítást és a hibakezelés egységes helyét.

Egy fontos tervezési döntés a pufferkezelés. A felső réteg által átadott puffer lehet a felhasználói memóriában, vagy a kernel lapozható memóriájában. A DMA-hoz a puffert fizikailag összefüggő, nem lapozható (pinned) memóriában kell elhelyezni. A blk_request struktúrában ezért a buf mezőnek olyan memóriára kell mutatnia, amelyet a driver DMA-hoz használhat. A saját kernelünkben ezt egy egyszerű, nem lapozható kernel-allokátorból (például a korábbi kmalloc analógjából) biztosíthatjuk. A VFS vagy a fájlrendszer felelőssége, hogy a felhasználói adatokat először egy ilyen pufferbe másolja, vagy a DMA-t közvetlenül a felhasználói memóriából végezze (ez utóbbi bonyolult, és a kezdeti implementációban nem javasolt).

Példa a kérésbeadásra és a completionre:

/* freestanding C – saját kernel, illusztráció */
struct completion {
    bool done;                /* a kérés befejeződött-e */
    int  err;                 /* 0 vagy negatív hibakód */
    wait_queue_head_t wait;   /* a várakozó folyamatok listája */
};

void blk_complete_read(void *cookie, int status) {
    struct completion *done = (struct completion *)cookie;
    done->err = status;       /* 0 = siker, negatív = hiba */
    done->done = true;
    wake_up(&done->wait);     /* interruptból is biztonságos: nem alszik */
}

int blk_sync_read(struct blkdev *dev, sector_t start, void *buf, size_t nsectors) {
    struct completion done;   /* csak a szinkron hívás idejére él */
    struct blk_request req = {
        .flags    = BLK_REQ_READ,
        .start    = start,
        .nsectors = nsectors,
        .buf      = buf,
        .complete = blk_complete_read,
        .cookie   = &done,
        .dev      = dev,
        .status   = 0,
        .retries  = 0,
    };
    int err;

    init_completion(&done);
    err = blk_submit_request(dev->queue, &req);
    if (err)
        return err;           /* például -EAGAIN: a kérés el sem indult */

    /* A feltétel újraellenőrzése zárja ki az elveszett ébresztést: ha a
       completion már a várakozás előtt lefutott, azonnal visszatérünk. */
    wait_event(&done.wait, done.done);
    return done.err;
}

Három részlet, amelyet a fenti példa szándékosan helyesen mutat. (1) A done változó a hívó vermében él, és a wait_event feltétele minden ébresztés után újraellenőrzi a done.done jelzőt, ezért egy azonnali completion (amikor a driver még a blk_submit_request visszatérése előtt készül el) sem veszik el. (2) A blk_submit_request hibakódját ellenőrizni kell; ha a sor tele van (-EAGAIN), a kérés el sem indult, és várakozni értelmetlen lenne. (3) A blk_request csak azért lehet a hívó vermében, mert a szinkron hívás a completion előtt nem tér vissza. Aszinkron beadásnál a kérésnek és a puffernek a completionig élnie kell: ilyenkor a kérést egy előre lefoglalt poolból kell venni, és a completion adja vissza.

29.2.3 DMA és adatmozgatás

A Direct Memory Access (DMA) lehetővé teszi, hogy a periféria közvetlenül a memóriába írjon vagy onnan olvasson, a CPU folyamatos beavatkozása nélkül. Egy blokk-eszköz driverében ez elengedhetetlen a teljesítményhez: a szektorok átvitele során a CPU nem másolhat minden bájtot kézzel, különben a rendszer I/O-ja drámaian lelassulna. A DMA használata azonban több követelményt támaszt:

  1. Fizikai címzés: A DMA-vezérlő fizikai memóriacímeket használ. A kernel virtuális címtérrel dolgozik, így a drivernek ismernie kell a puffer fizikai címét. A saját kernelünkben ezt egy virt_to_phys makróval vagy függvénnyel érhetjük el, feltéve, hogy a puffer nem lapozható (pinned).

  2. Összefüggő memória: A DMA-vezérlő descriptorai egyenként fizikailag összefüggő darabokat írnak le; a virtio-blk több adat-descriptort is elfogad (scatter-gather). Egyszerű driverünk egyetlen, lapon belüli 4 KiB-os puffert használ, ezért elég egy adat-descriptor; a puffereket nem lapozható régióból kell biztosítani.

  3. Cache-koherencia: A CPU és a DMA-vezérlő közötti cache-konzisztenciát biztosítani kell. Írásnál (az eszköz olvas a memóriából) a kiadás előtt vissza kell írni (flush) a puffer cache-sorait; olvasásnál (az eszköz ír) a kiadás előtt érvényteleníteni kell őket, hogy piszkos sor ne írhassa felül a beérkező adatot, és a completion után ismét érvényteleníteni, mert a CPU közben spekulatívan betölthette a régi tartalmat. A x86 architektúrán a hardver gondoskodik a koherenciáról, de sok ARM vagy RISC-V platformon a drivernak explicit cache-karbantartást kell végeznie. A mi emulált x86 környezetünkben ez nem jelent gondot, de a hordozhatóság érdekében érdemes absztrahálni: dma_cache_inv(buf, len) és dma_cache_flush(buf, len) függvények.

  4. Szórt-gyűjtő (scatter-gather) támogatás: A valós rendszerekben a fájlrendszer gyakran nem összefüggő memóriát ad át; a DMA-vezérlő képes szórt darabokból egyetlen I/O-t végrehajtani egy SG-lista alapján. A mi egyszerű driverünkben egyelőre egyetlen összefüggő puffert használunk, de a blk_request kiterjeszthető lenne egy SG-listával.

Példa egy minimális DMA-átvitelre a virtio-blk eszközhöz. A virtio 1.2 specifikáció szerint a kérés bájtszerkezete: fejléc, adat, státusz; mi ezt a szokásos három descriptor láncára bontjuk: a fejléc (device-readable), az adatpuffer (irányfüggő) és egy 1 bájtos státusz (device-writable). A fejléc wire-formátuma kötelező: type, reserved (ennek nullának kell lennie) és sector, további mező nélkül.

/* freestanding C – saját kernel, vázlat */
#define VIRTIO_BLK_T_IN   0   /* olvasás: az eszköz ír a memóriába */
#define VIRTIO_BLK_T_OUT  1   /* írás:   az eszköz olvas a memóriából */

struct virtio_blk_outhdr {     /* a specifikáció szerinti wire-formátum */
    uint32_t type;
    uint32_t reserved;         /* kötelezően 0 */
    uint64_t sector;
} __attribute__((packed));

/* A kérés a descriptor-lánc leírása; a completionig élnie kell. */
struct virtio_blk_req {
    struct virtio_blk_outhdr hdr;   /* device-readable */
    uint8_t  status;                /* device-writable: az eszköz írja */
    uint16_t desc[3];               /* a descriptor-lánc indexei */
    struct blk_request *owner;      /* visszavezetés a felső szintű kérésre */
};

int start_dma_request(struct blkdev *dev, struct blk_request *req) {
    struct virtio_blk_dev *vdev = dev->driver_data;
    struct virtio_blk_req *vreq = blk_req_priv(req);  /* pool-elem, nem stack! */
    size_t bytes = req->nsectors * dev->sector_size;   /* itt sector_size == 512 */
    /* virtio-ban a sector mindig 512 B-os egység */

    vreq->hdr.type     = (req->flags & BLK_REQ_READ) ? VIRTIO_BLK_T_IN
                                                     : VIRTIO_BLK_T_OUT;
    vreq->hdr.reserved = 0;
    vreq->hdr.sector   = req->start;
    vreq->status       = 0xFF;      /* "még nincs válasz" */

    if (req->flags & BLK_REQ_WRITE)
        dma_cache_flush(req->buf, bytes);   /* az eszköz olvassa a memóriát */
    else
        dma_cache_inv(req->buf, bytes);     /* az eszköz ír: piszkos sor ne írja felül */

    /* 1) fejléc: device-readable (nincs WRITE jelző) */
    vring_desc_set(&vdev->vq, vreq->desc[0],
                   virt_to_phys(&vreq->hdr), sizeof(vreq->hdr), 0);
    /* 2) adat: olvasásnál az eszköz ír (WRITE), írásnál a vendég ír */
    vring_desc_set(&vdev->vq, vreq->desc[1], virt_to_phys(req->buf), bytes,
                   (req->flags & BLK_REQ_READ) ? VRING_DESC_F_WRITE : 0);
    /* 3) státusz: mindig device-writable */
    vring_desc_set(&vdev->vq, vreq->desc[2],
                   virt_to_phys(&vreq->status), 1, VRING_DESC_F_WRITE);
    vring_desc_chain(&vdev->vq, vreq->desc[0]);

    return virtqueue_kick(&vdev->vq);
}

Egy kérés három descriptort foglal; q egyidejű kéréshez legalább 3q méretű virtqueue kell (indirekt descriptorral – VIRTIO_RING_F_INDIRECT_DESC – kérésenként egy). A queue-size=32 mellett ⌊32/3⌋ = 10 lánc fér el, így a labor 8 egyidejű kérése teljesíthető. A driver a szabad descriptorok számát ellenőrzi, és ha kevesebb mint 3, a kérést a sorban tartja.

A vreq tulajdonjoga: a start_dma_request a poolból vesz egy vreq-et (blk_req_get(vdev)), három szabad descriptort foglal (virtq_alloc_desc), és a vdev->req_pool[vreq->desc[0]] = vreq bejegyzést állítja be; az ISR a used-ring id-je (a fejdescriptor indexe) alapján keresi ki, felszabadítja a három descriptort és a vreq-et. Újrapróbálásnál a start_dma_request új vreq-et vesz.

Két élettartam-szabály következik ebből. Egyrészt a virtio_blk_req és az adatpuffer a descriptor közzétételétől a used-ring bejegyzésig él; ha a kérés a hívó vermében lenne, a start_dma_request visszatérése után az eszköz már érvénytelen memóriát olvasna. Ezért a kérés pool-elem, amelyet csak a completion ad vissza. Másrészt a cache-karbantartás iránya a DMA irányához igazodik: írásnál a küldés előtt flush, olvasásnál a kiadás előtt és a completion után is invalidálás szükséges (lásd az interrupt-kezelőt).

A befejezést az interrupt jelzi: a virtio-blk eszköz egy interruptot küld, amikor a kérés teljesült. Az interrupt-kezelő először nyugtázza a megszakítást az ISR status register kiolvasásával, majd a used-ringből kiolvassa a befejezett descriptor-láncokat, megnézi a státuszbyte-ot, és ha sikeres, meghívja a completiont; ha hibás, akkor a hibakezelési útra tereli a kérést. A DMA-pufferrel kapcsolatos cache-műveleteket olvasásnál a befejezés után el kell végezni (invalidálás):

/* freestanding C – saját kernel, interrupt vázlat */
void virtio_blk_isr(struct blkdev *dev) {   /* a device-ot a hívó adja át */
    struct virtio_blk_dev *vdev = dev->driver_data;
    uint8_t isr = virtio_read_isr_status(vdev);  /* az olvasás nyugtázza az IRQ-t */

    if (!(isr & VIRTIO_PCI_ISR_QUEUE))
        return;                              /* nem a kérés-sor jelez */

    for (;;) {
        uint16_t id = virtqueue_get_used(&vdev->vq);
        struct virtio_blk_req *vreq;
        struct blk_request *req;

        if (id == VIRTQUEUE_NO_ID)
            break;
        vreq = vdev->req_pool[id];           /* a descriptor-lánchoz tartozó elem */
        req  = vreq->owner;

        switch (vreq->status) {            /* virtio-blk státuszok */
        case 0:                            /* VIRTIO_BLK_S_OK */
            if (req->flags & BLK_REQ_READ)
                dma_cache_inv(req->buf, req->nsectors * dev->sector_size);
            req->status = 0;
            break;
        case 2:                            /* VIRTIO_BLK_S_UNSUPP */
            req->status = -EOPNOTSUPP;
            break;
        default:                           /* S_IOERR (1) és ismeretlen */
            req->status = -EIO;
            break;
        }
        /* -ETIMEDOUT: a kérés beadásakor indított időzítő lejártakor keletkezik */
        /* sikernél req->complete(); hibánál req->status beállítása és
           schedule_work(&req->retry_work), a complete callbacket ilyenkor a
           blk_retry_work hívja */
        blk_complete_request(req, req->status);
        blk_req_put(vdev, vreq);                 /* pool-elem visszaadása */
    }

    blk_start_next(dev);   /* a következő kérés indítása, ha van */
}

Ez a minta jól mutatja a driver felépítését: a hardver-indítás, az interrupt-kezelés és a completion szétválasztása. A példa egyúttal azt is megmutatja, miért nem elég egyetlen current mutató: a virtqueue egyszerre több kérést is tárolhat, ezért az ISR a used-ringből ciklusban dolgozza fel a befejezéseket.

29.2.4 Hibakezelés és újrapróbálás

A tárolóeszközök nem megbízhatóak: szektorhibák, időtúllépések, DMA-hibák, parancs-visszautasítások fordulhatnak elő. A drivernek ezeket kezelnie kell, és csak a valóban végzetes hibákat kell a felső réteg felé továbbítania. A hibakezelés három fő területből áll:

  1. Hibaosztályozás: A hibakódok különbséget tesznek a visszavonható és a végzetes hibák között. Például egy időtúllépés lehet átmeneti (a lemez nem válaszolt, de a kérés újra elküldhető), míg egy MEDIUM ERROR (adathordozó-hiba) általában nem javítható újrapróbálással. A kernelben ezt a -EAGAIN, -EIO, -ETIMEDOUT és hasonló hibakódok reprezentálják; a driver a hardver-specifikus hibaállapotot ezekre fordítja le.

  2. Újrapróbálási stratégia: A visszavonható hibáknál a driver automatikusan újrapróbálhatja a kérést, mielőtt a felső rétegnek hibát jelentene. Ez különösen fontos az időtúllépéseknél és a parity hibáknál, amelyek átmeneti zavarok miatt lépnek fel. Az újrapróbálás tipikusan korlátozott számú (például 3-5 alkalom), és exponenciális backoffot alkalmazhat a túlterhelés elkerülésére.

  3. Hibanaplózás és diagnosztika: A kernelnek naplóznia kell a hibát a hozzá tartozó kérés azonosítójával, a szektorcímmel és a hardver állapotával. Ez segíti a későbbi hibakeresést. A naplózás nem helyettesíti a hiba javítását, de elengedhetetlen a rendszer megbízhatóságához.

Példa egy újrapróbálási ciklusra. A blk_request fentebb már tartalmazza a szükséges mezőket: status, retries, dev és retry_work.

/* freestanding C – saját kernel, retry vázlat */
#define MAX_RETRIES 3
#define RETRY_DELAY_MS 5

/* Csak az átmeneti hibák újrapróbálhatók. Az -EIO végzetes: a lemez
   adathordozó-hibát jelzett, azt ismételt küldéssel nem lehet javítani. */
static bool is_retryable(int status) {
    return status == -EAGAIN || status == -ETIMEDOUT || status == -EBUSY;
}

/* Az újrapróbálás munkasorban (processz-kontextusban) fut, nem az
   interrupt-kezelőben: itt szabad aludni és késleltetni. */
void blk_retry_work(struct work_struct *work) {
    struct blk_request *req = container_of(work, struct blk_request, retry_work);
    struct blkdev *dev = req->dev;

    if (req->status == 0) {                 /* közben sikerült */
        req->complete(req->cookie, 0);
        return;
    }
    if (req->retries < MAX_RETRIES && is_retryable(req->status)) {
        req->retries++;
        msleep(RETRY_DELAY_MS << (req->retries - 1));  /* exponenciális backoff */
        start_dma_request(dev, req);        /* a kérés és a puffer még él */
        return;
    }

    /* végleges hiba */
    req->flags |= BLK_REQ_FAILED;
    req->complete(req->cookie, req->status);
}

A completion az IRQ-ból csak annyit tesz, hogy beállítja req->status-t, majd schedule_work(&req->retry_work) hívással ütemezi a fenti függvényt; így az interrupt-úton nincs blokkoló várakozás. Két következményt kell betartani. Egyrészt a kérést a retry befejezéséig nem szabad felszabadítani, tehát a completion nem adhatja vissza a poolba, amíg a munkasor fut. Másrészt a késleltetés hossza a próbálkozás számával nő; a fix, hosszú busy-wait az interrupt-út foglalása miatt nem elfogadható megoldás.

Egy másik fontos hibatípus a request queue overflow. Ha a felső réteg túl gyorsan ad be kéréseket, a queue megtelhet. Ekkor a blk_submit_request -EAGAIN hibával tér vissza (-ENOMEM csak akkor, ha a kérés leírójának lefoglalása nem sikerül), és a hívónak kell várnia. A drivernek nem szabad egyszerűen eldobnia a kérést; a felső réteg felelőssége a visszanyomás (backpressure) alkalmazása. Ez a mi egyszerű kernelünkben úgy valósítható meg, hogy a queue maximális hossza rögzített, és a submit függvény ellenőrzi a pending_count mezőt.

29.2.5 Gyakorlati minta: egy RAM-lemez driver

A blokk-illesztő fogalmainak kipróbálásához nem feltétlenül szükséges valódi hardver. Egy RAM-lemez (ramdisk) tökéletes kiindulópont: a háttértár egy egyszerű memóriaterület, a driver pedig a read/write műveleteket memóriamásolással valósítja meg. Bár nincs valódi DMA vagy interrupt, a kérésbeadás, a completion és a hibakezelés ugyanúgy gyakorolható.

Példa egy minimális RAM-lemez driverre:

/* freestanding C – saját kernel, ramdisk illusztráció */
#define RAMDISK_SIZE (64 * 1024 * 1024)  /* 64 MiB */
#define RAMDISK_SECTOR_SIZE 512
#define RAMDISK_MAX_REQUEST 128          /* legfeljebb 64 KiB egy kérésben */

struct ramdisk_dev {
    struct blkdev blk;
    uint8_t *data;   /* a háttértár memória */
};

/* Közös ellenőrzés: a [start, start+nsectors) tartomány az eszközön belül
 * van-e, és a bájtszám kiszámítása nem csordul-e túl. A kivonásos alak
 * (nsectors <= total - start) akkor is helyes, ha az összeg túlcsordulna. */
static int ramdisk_check(struct blkdev *dev, sector_t start, size_t nsectors,
                         size_t *bytes_out) {
    if (nsectors == 0)
        return -EINVAL;
    if (nsectors > dev->max_request_sectors)
        return -EINVAL;
    if (start >= dev->total_sectors)
        return -EIO;
    if (nsectors > dev->total_sectors - start)
        return -EIO;
    *bytes_out = nsectors * dev->sector_size;   /* már korlátos */
    return 0;
}

static int ramdisk_read(struct blkdev *dev, sector_t start, void *buf, size_t nsectors) {
    struct ramdisk_dev *rdev = container_of(dev, struct ramdisk_dev, blk);
    size_t bytes;
    int err = ramdisk_check(dev, start, nsectors, &bytes);
    if (err)
        return err;
    memcpy(buf, rdev->data + (size_t)start * dev->sector_size, bytes);
    return 0;
}

static int ramdisk_write(struct blkdev *dev, sector_t start, const void *buf, size_t nsectors) {
    struct ramdisk_dev *rdev = container_of(dev, struct ramdisk_dev, blk);
    size_t bytes;
    int err = ramdisk_check(dev, start, nsectors, &bytes);
    if (err)
        return err;
    memcpy(rdev->data + (size_t)start * dev->sector_size, buf, bytes);
    return 0;
}

static int ramdisk_flush(struct blkdev *dev) {
    (void)dev;
    return 0;  /* RAM-lemezen nincs mit kiírni */
}

/* File-scope, statikus élettartamú műveleti tábla: a cím a program
 * teljes futása alatt érvényes marad. */
static const struct blkdev_ops ramdisk_ops = {
    .read  = ramdisk_read,
    .write = ramdisk_write,
    .flush = ramdisk_flush,
};

struct ramdisk_dev *ramdisk_create(void) {
    struct ramdisk_dev *rdev = kmalloc(sizeof(*rdev), GFP_KERNEL);
    if (!rdev)
        return NULL;
    memset(rdev, 0, sizeof(*rdev));

    /* CPU-val másolt RAM-lemezhez virtuálisan összefüggő memória elegendő
     * (vzalloc); nem kell fizikailag összefüggő DMA-zóna. A tár tartalmát nullázzuk, hogy ne szivárogjon
     * ki korábbi memóriatartalom. */
    rdev->data = vzalloc(RAMDISK_SIZE);   /* felszabadítás: vfree */
    if (!rdev->data) {
        kfree(rdev);
        return NULL;
    }

    /* A nevet másolni kell: string literál nem rendelhető tömbhöz. */
    strncpy(rdev->blk.name, "ram0", sizeof(rdev->blk.name) - 1);
    rdev->blk.name[sizeof(rdev->blk.name) - 1] = '\0';
    rdev->blk.total_sectors       = RAMDISK_SIZE / RAMDISK_SECTOR_SIZE;
    rdev->blk.sector_size         = RAMDISK_SECTOR_SIZE;
    rdev->blk.max_request_sectors = RAMDISK_MAX_REQUEST;
    rdev->blk.queue               = NULL;   /* szinkron eszköz, nincs sora */
    rdev->blk.flags               = 0;      /* nincs DMA */
    rdev->blk.ops                 = &ramdisk_ops;
    rdev->blk.driver_data         = rdev;

    if (blkdev_register(&rdev->blk) != 0) { /* hibaágon takarítás */
        vfree(rdev->data);
        kfree(rdev);
        return NULL;
    }
    return rdev;
}

A példa három gyakori hibát kerül el: (1) egy char[32] tömbnek nem adható értékül string literál (rdev->blk.name = "ram0" nem fordul), ezért másolunk; (2) a műveleti tábla file-scope és static const, mert egy függvényen belüli compound literal a függvény visszatérése után érvénytelenné válik, a regisztrált ops mutató pedig később is használatos. (3) a tartományellenőrzés a szorzás előtt történik, így sem a lemez végén túlnyúló, sem a size_t-et túlcsordító kérés nem jut el a memcpy-ig; a háttértár pedig virtuálisan összefüggő, lapokból álló nullázott memória (vzalloc), mert CPU-val másoljuk; a fizikailag összefüggő kmalloc ekkora méretre nem is adna memóriát. Szinkron (sor nélküli) eszköznél a felső réteg közvetlenül az ops->read/write-ot hívja; a blk_sync_read csak dev->queue != NULL esetén használható (a blk_sync_read elején: if (!dev->queue) return dev->ops->read(dev, start, buf, nsectors);).

Ez a driver szinkron, és nincs szüksége interruptra vagy DMA-ra, de a blkdev_ops interfésze megegyezik a bonyolultabb eszközökével. A laboratóriumi feladatban azonban egy aszinkron, interrupt-vezérelt drivert is implementálunk, hogy a request queue és a completion valódi működését is lássuk.

29.2.6 Labor: egyszerű blokkdriver és interruptkezelés QEMU-ban

A labor célja egy olyan blokkdriver elkészítése, amely a QEMU virtio-blk eszközét vezérli, aszinkron kérésekkel, interrupt-kezeléssel és újrapróbálással. A labor a könyv saját OS projektjének része, ezért feltételezzük, hogy a korábbi fejezetekből már rendelkezésre áll a minimális kernel, a memória-allokátor, a megszakítás-kezelő keretek és a kmalloc/kfree függvények.

Kiinduló állapot: a resz7 projekt aktuális állapota, amelyben a boot, a memóriatérkép, a lapozás és az alapszintű megszakítás-kezelés már működik. A os110 fejezetben definiáltuk a fájlrendszer logikai blokk-méretét (4 KiB) és a szektor-méretét (512 bájt). A labor a drivers/virtio_blk.c fájlban valósítja meg a drivert.

Hardverkonfiguráció (emulált): - QEMU 8.2.0 (x86_64) - CPU: 1 db qemu64, kikapcsolt KVM (TCG módban, hogy az időmérés reprodukálható legyen) - RAM: 512 MiB - Blokk-eszköz: virtio-blk-pci hátterű, 128 MiB kapacitású nyers lemezkép - Megszakítások: legacy PCI interrupt (INTx), nem MSI-X. A QEMU alapértelmezett virtio-blk-pci eszköze transitional (device ID 0x1001); a labor ezt legacy módban kezeli (a spec 0.9.5/legacy leírása szerint), az ISR státuszt a legacy I/O-régióból olvassa (modern interfésznél a VIRTIO_F_VERSION_1 és az ISR-capability régió használandó; a konkrét viselkedés a QEMU-verzióval ellenőrzendő)

Fordítási beállítások: - GCC 13.2.0, freestanding, -O2 -march=x86-64 -mno-red-zone -ffreestanding -fno-stack-protector - Linker script: kernel.ld, amely a text, data, bss szegmenseket határozza meg, és a kernel fizikai címe 0x100000.

Futtatási parancs (TCG emuláció, hoszt KVM nélkül):

qemu-system-x86_64 -accel tcg -cpu qemu64 -m 512M -smp 1 \
  -device virtio-blk-pci,drive=disk0,queue-size=32 \
  -drive id=disk0,if=none,file=disk.img,format=raw \
  -kernel build/kernel.elf

A disk.img fájl előállítása (128 MiB nullákkal; a driver tesztjei nyers blokkokat írnak és olvasnak, fájlrendszer-kép nem szükséges):

dd if=/dev/zero of=disk.img bs=1M count=128 status=progress

TCG-ben futunk, hogy a laborgép KVM nélkül is használható legyen; az időmérés így sem determinisztikus, ezért a hoszt adatai és a szórás a jegyzőkönyv része (determinisztikus virtuális időhöz -icount shift=auto).

Mérési módszer: A kernelben időbélyeget (TSC) olvasunk a kérés beadása előtt és a completion után; a kettő különbsége a kérés késleltetése. Minden futásnál rögzíteni kell a queue depthet (az egyszerre kiadott kérések számát), mert az átviteli sebesség csak ezzel együtt értelmezhető:

S≈q⋅BL‾S \approx \frac{q \cdot B}{\bar{L}}

ahol qq a queue depth, BB a blokk mérete, L‾\bar{L} az átlagos késleltetés. A nyers, kérésenkénti mintákat mentjük, és az átlag mellett a mediánt, a maximumot és a 99. percentilist is jelentjük. Öt különálló tesztet futtatunk, mindegyiknél 1000 db 4 KiB-os kérés:

Teszt Queue depth Hibainjektálás Elvárt eredmény
T1 1 nincs mind az 1000 kérés 0 státusszal; átlag/medián/max rögzítve
T2 8 nincs mind az 1000 kérés 0 státusszal; a T1-nél nagyobb átviteli sebesség
T3 8 időtúllépés minden 10. kérésnél mind az 1000 kérés végül 0; a retry-számláló nő, 100 időtúllépés, 100 újrapróbálás, 0 végső hiba (a számláló az eredeti kérések sorszámát számolja 1-től, n = 10)
T4 8 EIO minden 10. kérésnél a hibás kérések -EIO-val zárulnak, retry nélkül; pontosan 100 hibás kérés
T5 8 EIO minden 10. kérésnél, retry engedélyezve ugyanannyi hiba, mint T4-nél: az EIO nem újrapróbálható

A T3 és a T5 eltérő elvárt eredményt ad, mert a két hibatípus osztályozása különbözik: az időtúllépés átmeneti (is_retryable igaz), az EIO végleges. Ha a driver mindkettőt újrapróbálná, a T5 hibaszáma lecsökkenne – éppen ez jelzi a hibát.

Példa eredmény (illusztratív, NEM mért): az alábbi számok csak a jegyzőkönyv formátumát mutatják, és belsőleg konzisztensek a fenti képlettel; futási eredményként nem idézhetők. - T1, queue depth 1: átlagos késleltetés 0,97 ms → 4 KiB / 0,97 ms ≈ 4,0 MiB/s - T2, queue depth 8: átlagos késleltetés 1,6 ms → 8 · 4 KiB / 1,6 ms ≈ 19,5 MiB/s - T3: 1000 kérésből 100 timeout, mind a 100 egy újrapróbálás után sikeres - T5: 1000 kérésből 100 EIO, mindegyik azonnal hibával zárul

A tényleges értékek a hoszt CPU-jától, a QEMU verziójától és a TCG fordítási gyorsítótárának állapotától függenek, ezért a jegyzőkönyvben a hoszt konfigurációját is rögzíteni kell. Ellenőrző összefüggések: a T2 sebessége azonos késleltetés mellett nem lehet kisebb a T1-énél, és a T5 hibaszáma nem térhet el a T4-étől.

Visszaállítás: A labor után a disk.img fájl törölhető, és a fenti dd parancs újra előállítja a tiszta képet. A kernel forráskódja a verziókezelőben v0.7-blkdrv címkével ellátva.

A labor során a következő implementációs lépéseket hajtjuk végre:

  1. Eszköz felderítése: A PCI buszon megkeressük a virtio-blk eszközt (vendor ID: 0x1AF4, device ID: 0x1001), és beállítjuk a BAR-okat.
  2. Virtqueue inicializálása: A virtio-blk eszköz egyetlen virtqueue-t használ a kérések számára. Lefoglalunk egy DMA-képes memóriaterületet a descriptor- és ring-puffereknek.
  3. Kérés küldése: A blk_request-ből egy virtio_blk_req struktúrát töltünk fel, és a virtqueue-ba helyezzük.
  4. Interrupt-kezelés: A PCI interrupt-kezelőben meghívjuk a virtio_blk_isr-t, amely kiolvassa a felhasznált descriptorokat, meghatározza a státuszt, és meghívja a completiont.
  5. Retry logika: A befejezési callbackben a hibakódot az is_retryable szerint osztályozzuk: az -ETIMEDOUT/-EAGAIN/-EBUSY kérést legfeljebb MAX_RETRIES = 3-szor újrapróbáljuk, az -EIO-t azonnal a hívónak adjuk. A mesterséges hibainjektáláshoz a driverbe egy debug-flaget (blk_debug_fail_every_nth) építünk, amely minden n-edik eredeti kérést hibával buktat (T3-ban -ETIMEDOUT, T4/T5-ben -EIO állapottal); az újrapróbálás nem lépteti a számlálót.

Az önellenőrző kérdés a laborhoz:

Mi történik, ha a virtio_blk_isr interrupt-kezelőből közvetlenül meghívjuk a blk_complete_request-et, és az a várakozó folyamatot felébreszti? Miért lehet ez veszélyes, és hogyan oldható fel?

A válasz: az interrupt-kontextusban nem szabad aludni – blokkoló várakozást, msleep-et vagy laphibát okozó memóriahozzáférést végezni –, mert az IRQ-útnak nincs feladatstruktúrája, és a megszakítás alatt a többi eszköz kiszolgálása is késne. A completion jelzése viszont IRQ-biztos: a complete()/wake_up() csak egy zárt listát módosít és ébreszt, nem alszik, ezért az ISR-ből is hívható. A tényleges blokkoló várakozás a folyamat kontextusában futó wait_event() oldalán van, nem az ISR-ben. Ha viszont valódi alvó háttérmunka kell (késleltetett retry, összetett feldolgozás), azt munkasor (workqueue) vagy kernel-szál végzi; a softirq és a tasklet nem alvó kontextus, ezért ilyen munkára nem alkalmas.

29.2.7 Tipikus hibák és a helyes megoldások

A blokkdriver fejlesztése során több jellegzetes hiba fordul elő. Ezeket érdemes már a tervezéskor elkerülni:

  1. A DMA-puffer cache-koherenciájának figyelmen kívül hagyása. A legtöbb ARM és RISC-V rendszeren a CPU cache és a DMA-vezérlő nem koherens. Ha a drivernél nem hívunk dma_cache_flush/dma_cache_inv műveletet, az adat sérülhet. A x86-on ez gyakran működik, ezért a hibát csak később, portoláskor veszik észre. Megoldás: A DMA-műveleteket mindig architektúra-független cache-kezelő függvényeken keresztül végezzük, és a hordozhatósági tesztekben más architektúrát is használjunk.

  2. A kérés-puffer felhasználói memóriából való közvetlen használata. A felhasználói tér memóriája lapozható és akár fizikailag nem összefüggő. A DMA közvetlenül nem használhatja. Megoldás: A felső réteg mindig kernel-puffert adjon át, vagy a blk_request előállításakor másoljuk az adatot egy DMA-képes kernel-pufferbe. Ez a másolás költséges, de kezdeti implementációban elfogadható.

  3. Alvó művelet az interrupt-kezelőben. Az IRQ-kontextusból hívott blokkoló várakozás vagy késleltetés holtponthoz, legalábbis súlyos késéshez vezet. Megoldás: Az ISR csak a kész állapotot rögzítse, és hívja a complete()/wake_up() jelzést, ami IRQ-biztos. A blokkoló várakozás a folyamat kontextusában marad; ha pedig alvó háttérmunkára van szükség, azt munkasor vagy kernel-szál végzi.

  4. A retry logika hiánya vagy túlzott alkalmazása. Ha a driver minden hibát újrapróbál, a végzetes hibák elrejtése a rendszer inkonzisztens állapotához vezethet. Ha viszont soha nem próbál újra, az átmeneti zavarok miatt feleslegesen hibát jelent. Megoldás: Hibakód-alapú osztályozás, korlátozott retry-szám és exponenciális backoff. A retry-k naplózása elengedhetetlen.

  5. A request queue pufferének túlcsordulása. Ha a felső réteg nem kezeli a submit függvény hibakódját, a queue memóriaszivárgáshoz vagy elveszett kérésekhez vezet. Megoldás: A blk_submit_request maximális queue-hosszt ellenőriz, és -EAGAIN hibával visszautasítja a kérést (-ENOMEM: ha a leíró lefoglalása nem sikerül); a hívó köteles ezt kezelni.

29.2.8 Összefoglalás

A blokk-eszköz illesztése a kernelhez egy olyan réteget hoz létre, amely a fájlrendszerek és a hardver között közvetít. Az általános minta a következő: az eszközt egy struct blkdev reprezentálja, a felső réteg aszinkron blk_request-eket ad be egy request queue-ba, a driver DMA-val végzi az adatátvitelt, és interrupt jelzi a befejezést. A hibakezelés osztályozza a hibákat, újrapróbálja a visszavonható eseteket, és csak a végleges hibákat továbbítja. A laborban ezt a mintát a QEMU virtio-blk eszközére tervezzük, és a mérési terv a fenti öt teszt eredményéből ellenőrzi az aszinkron modell működését. A következő fejezetben erre a driverre építve integráljuk a VFS-t, és megvalósítjuk a fájlleírók szintjét.
