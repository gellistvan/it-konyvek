29.4 Shell és alapszolgáltatások

A minimális userland nem attól működik, hogy a kernel mindent el tud végezni; attól válik használhatóvá, hogy a felhasználói térben néhány apró, jól megírt program a fájlleírókat, a folyamatokat és a környezeti állapotot a POSIX-elvárásokhoz hasonlóan kezeli. Az os112 alfejezetben felépítettük a VFS-t és a fájlleíró réteget. Most arra a rétegre egy parancsértelmezőt és a hozzá tartozó alapszolgáltatásokat helyezünk. A kernel továbbra is ugyanaz marad: rendszerhívásokat ad, a munka nagy része a userlandben történik.

29.4.1 1. Mi a minimális userland?

A userland az operációs rendszer azon része, amely nem fut privilegizált módban. Egy minimális, oktatási célú rendszerben a userland általában a következőkből áll:

  • egy indító program (init vagy sh közvetlenül),
  • a rendszerhívások vékony C-burkolói (a libc helyett egy syscalls.h és syscalls.c),
  • egy parancsértelmező (shell),
  • néhány alapvető segédprogram (például cat, echo, ls, mkdir, rm),
  • szükség esetén egy-két eszközfájl (/dev/console, /dev/null) és a /bin könyvtár.

A cél az, hogy a rendszer elindulása után a felhasználó vagy a tesztkörnyezet parancsokat tudjon kiadni, scripteket tudjon futtatni, és ellenőrizni tudja a fájlrendszer, illetve a folyamatok működését.

A shell nem kernelkomponens. Ugyanolyan felhasználói program, mint a cat vagy a ls; annyi különbséggel, hogy a felhasználó által begépelt sorokat parancsokká alakítja, majd ezeket más programok futtatásával hajtja végre. Ez a kialakítás azért fontos, mert a parancsok nagy része nem a shell kódjában él, hanem külön futtatható fájlokban. A shell feladata a „társalgás” a felhasználóval és a folyamatok összekapcsolása.

29.4.2 2. A shell indítása és a fő ciklus

A minimális rendszer bootolás után, az os103 és os104 alfejezetekben leírt kernel-inicializálást követően elindítja az első felhasználói folyamatot. A leggyakoribb választás: a kernel megnyitja a /bin/sh fájlt, futtathatóvá teszi, majd átadja neki a konzolt mint szabványos be- és kimenetet. A shell ezután a következő ciklust futtatja:

  1. promptot ír a szabványos kimenetre;
  2. beolvas egy sort a szabványos bemenetről;
  3. a sort tokenekre bontja;
  4. ha beépített parancs, akkor közvetlenül végrehajtja;
  5. egyébként létrehoz egy gyermekfolyamatot, amely betölti a megfelelő programot;
  6. a szülő megvárja a gyermeket, majd kiértékeli a kilépési állapotot;
  7. visszatér az 1. lépésre.

Ezt mutatja a következő, szándékosan lecsupaszított C-vázlat. A kód nem éles rendszerre való, hanem a fejezetben épített emulált környezethez.

/* user/sh.c – minimális shell szemléltető vázlata */
#include "syscalls.h"

#define MAX_LINE 128
#define MAX_ARGS 16

static char line[MAX_LINE];
static char *args[MAX_ARGS + 1];   /* tokenvektor: kizárólag a tokenize írja */

int main(int argc, char **argv)
{
    (void)argc;
    (void)argv;

    for (;;) {
        ssize_t n;
        int nargs;

        write(STDOUT_FILENO, "mini$ ", 6);

        n = read(STDIN_FILENO, line, sizeof(line) - 1);
        if (n < 0) {
            if (errno == EINTR)
                continue;
            perror("read");
            return 1;
        }
        if (n == 0) {
            /* EOF: a shell kilép */
            return 0;
        }
        line[n] = '\0';

        nargs = tokenize(line, args, MAX_ARGS);
        if (nargs < 0) {
            static const char msg[] = "sh: túl sok argumentum\n";
            write(STDERR_FILENO, msg, sizeof(msg) - 1);
            continue;
        }
        if (nargs == 0) {
            /* üres sor */
            continue;
        }

        if (run_builtin(args) == 1)
            continue;

        (void)run_external(args);   /* a hibát az run_external már kiírta */
    }
}

A tokenize egyelőre csak a whitespace-ek mentén vág szét; a gyakorlatban a minimális shell is támogathatja a "..." és '...' idézést, illetve a \ escape-et. A laborban érdemes az idézést legalább alapszinten implementálni, mert enélkül a fájlnevekben lévő szóközök nem kezelhetők. A tokenize szerződése legyen rögzített: csak a kapott args tömbbe ír, a maxargs korlátot betartja, a tömböt NULL-lal zárja, és a tokenek számát adja vissza; hibánál (túl sok token) -1-et. Ha viszont a vektor nem a tokenizáló saját, dedikált puffere, a hiba könnyen memóriaszemét lesz.

Tipikus hiba: a static char *argv[MAX_ARGS + 1] globális tömböt a main(int argc, char **argv) paramétere elfedte, így a tokenize valójában a program indításakor kapott argv-ba írt. argc == 1 esetén ennek a tömbnek mindössze két érvényes bejegyzése van (argv[0] és a NULL lezáró), ezért a második beolvasott szó már a veremben túlra ír, és a harmadik token a vermet is felülírhatja. A javítás nem stíluskérdés: a tokenek tömbje args néven külön él, a main paramétere pedig csak a program saját argumentumaihoz tartozik, amelyeket ez a shell nem is használ. A laborban a tokenizálót argc == 1 mellett, legalább három tokenes sorral teszteld (például echo egy kettő három; a kimenet egy kettő három), mert a hiba kis bemenetnél tünetmentes maradhat, és csak hosszabb soroknál vagy nagyobb argumentumszámnál okoz összeomlást.

29.4.3 3. Belső és külső parancsok

A shell parancsai két csoportba sorolhatók.

  • Belső parancsok (builtin): olyan parancsok, amelyek a shell saját processzét módosítják, vagy nem éri meg külön folyamatként futtatni őket. Például:
    • cd <útvonal> – a munkakönyvtár megváltoztatása; ha ezt külön folyamat tenné, a változás nem lenne hatással a szülő shellre.
    • exit [kód] – a shell kiléptetése.
    • export NÉV=ÉRTÉK – környezeti változó beállítása.
    • pwd – az aktuális munkakönyvtár kiírása.
    • help – a rendelkezésre álló belső parancsok listája.
  • Külső parancsok: önálló futtatható fájlok, például /bin/cat, /bin/ls. Ezeket a shell fork + execve + waitpid hármassal futtatja. A /bin könyvtárban lévő programok a minimális userland részét képezik.

A shell cd parancsának belső volta klasszikus hibaforrás. Ha valaki úgy próbálja megvalósítani, hogy fork után a gyermekben meghívja a chdir-t, akkor a gyermek munkakönyvtára megváltozik, de a szülőé nem; a shell a következő promptnál ugyanott marad, ahonnan indult. Ezért a cd-t a shell saját folyamatában kell végrehajtani.

A belső parancsok vázlata:

/* kis segédfüggvény: a teljes puffert kiírja, EINTR után újrapróbál */
static int write_all(int fd, const char *buf, size_t len);

#define ENV_NAME_MAX 64
#define ENV_VALUE_MAX 192

/* a shell saját, kétargumentumos környezetkezelője */
int env_store(const char *name, const char *value);

int run_builtin(char **args)
{
    if (strcmp(args[0], "cd") == 0) {
        const char *path = args[1] ? args[1] : "/";
        if (chdir(path) < 0)
            perror("cd");
        return 1; /* kezelve */
    }

    if (strcmp(args[0], "exit") == 0) {
        int code = args[1] ? atoi(args[1]) : 0;
        exit(code & 0xFF);
    }

    if (strcmp(args[0], "export") == 0) {
        char name[ENV_NAME_MAX];
        char value[ENV_VALUE_MAX];
        const char *eq = args[1] ? strchr(args[1], '=') : NULL;
        size_t nlen;

        if (eq == NULL || eq == args[1]) {
            static const char usage[] = "használat: export NÉV=ÉRTÉK\n";
            write_all(STDERR_FILENO, usage, sizeof(usage) - 1);
            return 1;
        }

        nlen = (size_t)(eq - args[1]);
        if (nlen >= sizeof(name) || strlen(eq + 1) >= sizeof(value)) {
            static const char big[] = "export: a név vagy az érték túl hosszú\n";
            write_all(STDERR_FILENO, big, sizeof(big) - 1);
            return 1;
        }

        /* a nevet és az értéket külön másoljuk: a token puffere érintetlen marad */
        memcpy(name, args[1], nlen);
        name[nlen] = '\0';
        strcpy(value, eq + 1);

        if (env_store(name, value) < 0) {
            static const char full[] = "export: a környezeti tár megtelt\n";
            write_all(STDERR_FILENO, full, sizeof(full) - 1);
        }
        return 1;
    }

    if (strcmp(args[0], "pwd") == 0) {
        char buf[256];
        if (getcwd(buf, sizeof(buf)) == NULL) {
            perror("pwd");
        } else {
            write_all(STDOUT_FILENO, buf, strlen(buf));
            write_all(STDOUT_FILENO, "\n", 1);
        }
        return 1;
    }

    return 0; /* nem belső parancs */
}

Itt a chdir, a getcwd, a strcmp és a memcpy a minimális libc-ből, illetve a rendszerhívás-burkolókból származnak. A tényleges implementáció a laborban az os112-ben már elkészített VFS-re épül.

Két részletet külön meg kell indokolni. Az egyik az export szétbontása: a NÉV=ÉRTÉK bejegyzést a shell bontja fel névre és értékre, mert így a név üressége, hossza és az érték hossza külön ellenőrizhető, és a hibaüzenet is pontosabb. A másik a függvénynév: a minimális libcben nem szabad setenv-et definiálni, mert a POSIX setenv(const char *name, const char *value, int overwrite) háromargumentumos, és egy azonos nevű, egyargumentumos függvény csendben eltérő viselkedést eredményezne. Ezért a shell saját környezetkezelője env_store(name, value) néven él, a env_store pedig -1-et ad vissza, ha a környezeti tár megtelt – ezt a híváskor ellenőrizni kell, különben a felhasználó azt hiszi, hogy a beállítás sikerült.

A stringliterálok hosszát mindenhol sizeof(literal) - 1 adja, nem kézi számlálás. Tipikus hiba a kézi számlálás: a "sh: túl sok argumentum\n" hossza 23 helyett 24, a "sh: parancs nem található: " hossza pedig 27 helyett 29 bájt (a magyar ékezetes betűk UTF-8-ban két bájtot foglalnak), így a write levágja az üzenet végét, illetve a puffer határán túl olvas.

29.4.4 4. Külső program futtatása: fork, execve, waitpid

A külső parancsok futtatása a folyamatkezelés három rendszerhívását használja.

fork

pid_t fork(void);

A fork létrehozza a hívó folyamat másolatát. A gyermek a hívás után a 0 értéket kapja vissza, a szülő a gyermek pozitív folyamatazonosítóját. Hibánál -1 a visszatérési érték, és a burkoló az errno-t beállítja; tipikus értékek:

  • EAGAIN – elértük a folyamatszám-korlátot (RLIMIT_NPROC) vagy a PID-tartomány elfogyott;
  • ENOMEM – nincs elég memória a gyermek létrehozásához.

A shell ezt használja arra, hogy a gyermekben lecserélje a programképet.

execve

int execve(const char *pathname, char *const argv[], char *const envp[]);

Az execve betölti a pathname fájlt, beállítja az argumentumlistát és a környezetet, majd lecseréli az aktuális folyamat címterét. Sikeres hívás nem tér vissza. Hiba esetén -1-gyel tér vissza, és az errno tartalmazza az okot. A leggyakoribb okok:

  • ENOENT – az útvonal egy komponense vagy az ELF-interpreter nem létezik (az execve nem keres a PATH-ban);
  • EACCES – nincs végrehajtási jog;
  • ENOEXEC – a fájl nem futtatható formátumú, vagy nincs érvényes fejléc;
  • E2BIG – az argumentumlista, a környezet vagy mindkettő túl nagy;
  • EFAULT – a felhasználói mutatók érvénytelenek.

A minimális rendszerben az execve a VFS open rétegén keresztül olvassa a fájlt, ellenőrzi az ELF-fejlécet, betölti a szegmenseket, beállítja a vermet, és az entry pontra ugrik. A shellnek a gyermekben az execve hiba után azonnal _exit(127)-et kell hívnia, különben a gyermek a shell kódját futtatná tovább, és egy második shellt indítana.

waitpid

pid_t waitpid(pid_t pid, int *_Nullable wstatus, int options);

A waitpid a szülőt várakoztatja a megadott gyermek befejeződésére. A wstatus mutató egy bitmezőt kap, amelyből a shell megállapíthatja a kilépés módját:

  • WIFEXITED(wstatus) igaz, ha a gyermek normálisan fejeződött be; ekkor WEXITSTATUS(wstatus) adja a kilépési kódot.
  • WIFSIGNALED(wstatus) igaz, ha a gyermeket szignál állította le; a shell ilyenkor 128 + jel kódot szokott visszaadni.

A shell run_external függvénye ezt a hármast foglalja össze:

int run_external(char **args)
{
    static const char notfound[] = "sh: parancs nem található: ";
    char path[128];
    pid_t pid;
    int status;

    if (find_in_path(args[0], path, sizeof(path)) < 0) {
        write_all(STDERR_FILENO, notfound, sizeof(notfound) - 1);
        write_all(STDERR_FILENO, args[0], strlen(args[0]));
        write_all(STDERR_FILENO, "\n", 1);
        return -1;
    }

    pid = fork();
    if (pid < 0) {
        perror("fork");
        return -1;
    }

    if (pid == 0) {
        /* gyermek: program betöltése */
        execve(path, args, environ);
        /*
         * Ide csak akkor jutunk, ha az execve hibázott.
         * A _exit megakadályozza, hogy a gyermek
         * a shell kódját futtassa tovább.
         */
        _exit(127);
    }

    /* szülő: várakozás a gyermekre, megszakítás után újrapróbálva */
    if (wait_child(pid, &status) < 0) {
        perror("waitpid");
        return -1;
    }

    return report_status(status);
}

A find_in_path a shell saját segédfüggvénye. A PATH környezeti változót kettőspontok mentén bontja fel, és minden elemből útvonal/parancsnév jelöltet készít. A minimális rendszerben a PATH általában /bin:/usr/bin. A find_in_path megpróbálhatja az open-t O_RDONLY módban minden jelöltre; ha a fájl létezik, visszaadja az elérési utat. A végrehajthatósági bit ellenőrzése a VFS-ben és az execve-ben történik.

A wait_child a waitpid EINTR-biztos burkolója: a SIGCHLD vagy más, kezelt szignál megszakíthatja a várakozást, ilyenkor a hívás -1-et ad errno == EINTR mellett, és a várakozást meg kell ismételni, különben a shell azt hinné, hogy a gyermek begyűjtése meghiúlt. Ugyanez érvényes a waitpid többi hibakódjára is: csak a valódi hibát (ECHILD, EINVAL) szabad hibaként kezelni. A SIGCHLD alapértelmezett kezelése mellett a waitpid blokkolva vár, és nem ad EINTR-t, de ha a shell később saját kezelőt telepít a SIGCHLD-re, a SA_RESTART nélküli kezelő miatt a hiba elő fog fordulni – ezért a burkoló már most kell.

A gyermek ágban a perror helyett szándékosan csak _exit(127) szerepel: a fork és az execve között a POSIX csak az async-signal-safe függvényeket engedi meg, a perror és a malloc nem tartozik közéjük, és egy többszálú shell esetén holtpontot okozhat. Egyszálú shellben ez nem kötelező szabály, de a gyermekágat a jövőbeli szálkezelés miatt egyszerűen így tartjuk. A shell kilépési kódjai közé tartozik a 126 is: a parancs megvan, de nem futtatható (EACCES, ENOEXEC).

Az argumentumok átadása POSIX-konvenció szerint történik: argv[0] a program neve, argv[1] az első parancssori argumentum, és az argv tömb végét NULL jelöli. A shellnek ügyelnie kell arra, hogy a NULL lezáró elem elférjen, ezért a MAX_ARGS tömb mérete MAX_ARGS + 1.

29.4.5 5. Pipe és átirányítás

A shell igazi erejét a folyamatok közötti csővezetékek és a fájlba irányítások adják. A | karakter két parancsot köt össze: a bal oldali parancs szabványos kimenetét a jobb oldali szabványos bemenetére irányítja. Ehhez a kernel pipe rendszerhívását használjuk.

pipe

int pipe(int pipefd[2]);

A pipe egy csővezetéket hoz létre. A pipefd[0] az olvasó vég, a pipefd[1] az író vég. A csőben lévő adatok a kernel memóriájában tárolódnak; amíg van nyitott író vég, az olvasó blokkol, ha a cső üres; amikor az összes író vég bezáródik, az olvasó read hívása 0-t ad vissza, ami EOF-ot jelez. A minimális rendszerben a pipe puffer mérete például 4096 bájt lehet; a labor mérésénél ezt érdemes rögzíteni.

A csővezeték végrehajtásához a shell két gyermekfolyamatot hoz létre. A dup2 rendszerhívás segítségével a cső megfelelő végét a STDOUT_FILENO, illetve a STDIN_FILENO fájlleíróra másolja.

dup2

int dup2(int oldfd, int newfd);

A dup2 a newfd fájlleírót az oldfd-re mutató nyitott fájlleíró-másolatává teszi. Ha a newfd korábban nyitva volt, a kernel először bezárja. A shell ezt az átirányításoknál használja:

  • > fájl esetén: open("fájl", O_CREAT|O_WRONLY|O_TRUNC, 0644), majd dup2(fd, STDOUT_FILENO).
  • >> fájl esetén: O_CREAT|O_WRONLY|O_APPEND.
  • < fájl esetén: open("fájl", O_RDONLY), majd dup2(fd, STDIN_FILENO).

Egy fontos részlet, amit a vázlatok rendszerint elfelejtenek: ha oldfd == newfd, a dup2 nem csinál semmit, de sikeresen visszatér, és ilyenkor a hívás után tilos az oldfd-et bezárni, mert az éppen a newfd – vagyis a szabványos bemenet vagy kimenet – maga. Ez a helyzet nem elméleti: ha a shell a saját fájlleíróit 0-ról indulva osztja ki, könnyen kaphatja a cső író végére a 1-es fájlleírót, ekkor a dup2(1, 1) no-op, a rákövetkező close(1) viszont lezárja a szabványos kimenetet. A helyes minta: if (fd != target) { if (dup2(fd, target) < 0) fail(); if (close(fd) < 0) fail(); }.

A hibakezelésre ugyanez vonatkozik: a dup2 hibáját a gyermekben nem lehet perror-ral jelenteni (a fork után csak async-signal-safe hívás megengedett), ezért _exit-cel kell kilépni, a szülő pedig a waitpid-del később begyűjti a gyermeket. Ha a második fork hibázik, a már elindult bal oldali gyermeket is be kell gyűjteni, különben az a szülő élettartama alatt zombit hagy maga után, és a waitpid sosem hívódik meg rá.

A pipe-os példa vázlata:

/* EINTR-biztos várakozás; 0 = sikeres begyűjtés, -1 = hiba */
static int wait_child(pid_t pid, int *status)
{
    for (;;) {
        pid_t r = waitpid(pid, status, 0);
        if (r == pid)
            return 0;
        if (r < 0 && errno == EINTR)
            continue;
        return -1;
    }
}

int run_pipeline(char **left_argv, char **right_argv)
{
    int fd[2];
    pid_t left, right;
    int left_status = 0, right_status = 0;
    char left_path[128], right_path[128];

    if (find_in_path(left_argv[0], left_path, sizeof left_path) < 0 ||
        find_in_path(right_argv[0], right_path, sizeof right_path) < 0) {
        /* "parancs nem található" */
        return 127;
    }

    if (pipe(fd) < 0) {
        perror("pipe");
        return -1;
    }

    left = fork();
    if (left < 0) {
        perror("fork");
        close(fd[0]);
        close(fd[1]);
        return -1;
    }

    if (left == 0) {
        /* bal oldali gyermek: írás a csőbe */
        close(fd[0]);
        if (fd[1] != STDOUT_FILENO) {      /* azonosság: ilyenkor nincs teendő */
            if (dup2(fd[1], STDOUT_FILENO) < 0)
                _exit(1);
            close(fd[1]);
        }
        execve(left_path, left_argv, environ);
        _exit(127);
    }

    right = fork();
    if (right < 0) {
        perror("fork");
        close(fd[0]);
        close(fd[1]);
        /* a már elindult bal gyermeket itt is be kell gyűjteni */
        (void)wait_child(left, &left_status);
        return -1;
    }

    if (right == 0) {
        /* jobb oldali gyermek: olvasás a csőből */
        close(fd[1]);
        if (fd[0] != STDIN_FILENO) {       /* azonosság: ilyenkor nincs teendő */
            if (dup2(fd[0], STDIN_FILENO) < 0)
                _exit(1);
            close(fd[0]);
        }
        execve(right_path, right_argv, environ);
        _exit(127);
    }

    /*
     * Kulcsfontosságú lépés: a szülőnek mindkét csővéget
     * be kell zárnia. Különben a jobb oldali gyermek a
     * pipe EOF-ját soha nem látja, mert a szülőben nyitva
     * maradt az író vég.
     */
    close(fd[0]);
    close(fd[1]);

    if (wait_child(left, &left_status) < 0)
        perror("waitpid");

    if (wait_child(right, &right_status) < 0) {
        perror("waitpid");
        return -1;
    }

    return report_status(right_status);
}

A főciklus a tokenek között keresi a | jelet: ha van, a vektort a | helyén NULL-lal kettévágja, és run_pipeline(args, &args[i+1])-et hív; a <, >, >> tokent és a fájlnevet a gyermekben egy apply_redirections(char **argv) függvény kezeli open + dup2 hívásokkal (a </>/>> token és a fájlnév kikerül az argumentumvektorból). A fenti kódban a left_path és a right_path kiszámítását a find_in_path végzi. A close(fd[0]) és close(fd[1]) a szülőben lévő felesleges fájlleírókat szünteti meg. Ez az egyik leggyakoribb hibaforrás: ha a szülő nem zárja be a cső író végét, a jobb oldali folyamat a read-ben örökre blokkolhat, mert az író vég sosem záródik be a szülő miatt.

Három tipikus hiba, amelyek mindegyike csendben rossz viselkedést okoz:

  1. A dup2 azonossági esete. Ha fd[1] == STDOUT_FILENO, a dup2(fd[1], STDOUT_FILENO) no-op, de a rá következő close(fd[1]) lezárja a szabványos kimenetet. A javított kód ezért csak akkor zárja be az eredeti leírót, ha az nem azonos a céllal. Ugyanez áll a fd[0] == STDIN_FILENO esetre a jobb oldali gyermekben.
  2. A hibás ág begyűjtetlen gyermeke. Ha a második fork hibázik, a bal oldali gyermek már létezik; wait_child nélkül a szülő zombit hagy maga után, és a waitpid soha nem hívódik meg rá.
  3. A waitpid EINTR-kezelése. A waitpid megszakítható, ilyenkor -1-et ad errno == EINTR mellett; a wait_child ezt megismétli. Ha a hibát egy inicializálatlan left_status/right_status értékkel együtt adjuk tovább a WIFEXITED makrónak, az definiálatlan viselkedéshez vezet.

A shell parser először a | és az átirányítási karakterek mentén bontja fel a sort. Az átirányítások elvileg tetszőleges sorrendben előfordulhatnak:

cat < /etc/motd | head > /tmp/elso_sor

Itt a bal oldali parancs bemenetét a /etc/motd fájlból, a jobb oldali parancs kimenetét a /tmp/elso_sor fájlba kell irányítani. A minimális shell kezdetben megelégedhet azzal, hogy a > és < jeleket egyetlen parancs után keresi, és a | jelet legfeljebb egyszer támogatja. A laborban ez elegendő a gyakorlati célhoz.

29.4.6 6. Környezeti változók és környezet átadása

A UNIX-szerű rendszerekben minden folyamat rendelkezik egy környezeti blokkal, amely NÉV=ÉRTÉK formájú sztringekből áll. A shell indulásakor ezt a blokkot a kerneltől kapja. A C-kódban a environ globális mutató hivatkozik rá:

extern char **environ;

A fork a gyermeknek ugyanazt a környezetet adja. Az execve harmadik paramétere a környezet; a shell a run_external és a run_pipeline hívásokban a saját environ mutatóját adja át. Ha a shell export parancsot kap, akkor a saját környezeti blokkját módosítja, és ez a változás a később indított gyermekekre is érvényes lesz.

A minimális környezetkezelő (env_store(name, value)) a következőket teszi:

  • megkeresi az adott névhez tartozó bejegyzést,
  • ha létezik, lecseréli az értéket,
  • ha nem létezik, új bejegyzést fűz a tömbhöz.

A függvény neve szándékosan nem setenv: a POSIX setenv háromargumentumos, a minimális libc-nek viszont nincs szüksége az overwrite kapcsolóra, és egy azonos nevű, eltérő aritású függvény csak összezavarná a kódot. Ha a tár megtelt, a visszatérési érték -1, amit a hívónak ellenőriznie kell – a run_builtin export ága ezt meg is teszi.

A környezeti tár mérete korlátozott; a laborban érdemes 32 vagy 64 bejegyzést engedélyezni, és a túlcsordulást -1 visszatéréssel jelezni.

A leggyakrabban használt környezeti változók:

  • PATH – a külső parancsok keresési útvonala;
  • HOME – a felhasználó otthoni könyvtára;
  • USER vagy LOGNAME – a felhasználónév;
  • PWD – az aktuális munkakönyvtár (informatív jelleggel; a tényleges állapotot a kernel tartja).

A shellnek a PATH-ot minden külső parancs előtt be kell olvasnia. Ha a felhasználó megváltoztatja a PATH-ot, a változásnak a következő parancsra már érvényesülnie kell. A biztonság szempontjából fontos, hogy a PATH-ba ne kerüljön a . (aktuális könyvtár) implicit módon; a minimális rendszerben ezt csak akkor vegyük fel, ha a felhasználó kifejezetten beállította.

29.4.7 7. Hibakódok, errno és kilépési állapot

A rendszerhívások hibáinak kezelése a userlandben két szinten történik.

A C-szinten a burkolók visszaadják a -1 értéket, és beállítják a errno nevű globális változót. A perror vagy a strerror segítségével a hiba szöveges leírása kiírható. A perror a hívás előtti szöveget, kettőspontot és az errno-hoz tartozó üzenetet írja a szabványos hibakimenetre. A minimális libc-ben a strerror csak a leggyakoribb hibakódokat ismerheti; a laborban legalább az ENOENT, EACCES, ENOMEM, EBADF, EINVAL, EIO és EEXIST kódokat érdemes leképezni.

A shell szintjén a kilépési állapot a következő:

  • 0 – sikeres végrehajtás;
  • 1 – általános hiba;
  • 2 – helytelen parancssori használat;
  • 127 – a parancs nem található, vagy az execve hibázott;
  • 128 + N – a folyamatot az N számú szignál állította le.

A shell a $? belső változóban tárolja az utolsó parancs kilépési állapotát. Ez a scripting alapja: egy script megvizsgálhatja, hogy az előző parancs sikeres volt-e.

A report_status függvény a waitpid által adott wstatus értéket alakítja át:

int report_status(int wstatus)
{
    if (WIFEXITED(wstatus)) {
        return WEXITSTATUS(wstatus);
    }
    if (WIFSIGNALED(wstatus)) {
        return 128 + WTERMSIG(wstatus);
    }
    return 1;
}

A shell a promptnál az utolsó kilépési állapotot a $? kérdésre adott válaszként jeleníti meg. A minimális megvalósításban ezt a változót a shell a run_external vagy a run_pipeline visszatérési értékéből frissíti.

29.4.8 8. Scripting a minimális userlandben

A shellscriptek használata akkor válik lehetővé, ha a rendszer két dolgot támogat:

  1. a futtatható szövegfájlokat a kernel vagy a shell interpreterhez tudja kötni;
  2. a shell képes soronként értelmezni egy fájlt, nem csak az interaktív bemenetet.

A hagyományos UNIX-rendszerekben az execve a fájl első két bájtját ellenőrzi. Ha azok #! karakterek, a kernel az első sor hátralevő részéből (az újsorig) olvassa ki az interpreter útvonalát és egy opcionális argumentumát, majd az interpretert indítja el, és argumentumként átadja neki a script elérési útját (/bin/sh script.sh …). A minimális rendszerben erre két lehetőség van:

  • a kernel execve-je felismeri a #!-et, és az interpreter programot tölti be;
  • a shell érzékeli, hogy a fájl nem bináris, hanem szöveges script, és maga olvassa be, majd soronként végrehajtja.

Az oktatási célú rendszerben gyakran a második megoldás az egyszerűbb, mert nem igényel kernelváltoztatást. Ekkor a shell source vagy közvetlenül a fájlnevet kapja argumentumként, és a read ciklust a szabványos bemenet helyett egy fájlból futtatja.

Egy minimális script:

#!/bin/sh
# laborbemutató.sh – nem éles rendszerre
echo "Mini OS shell indítása"
mkdir -p /tmp/log
cat /etc/motd > /tmp/log/motd_masolat
echo $?

A mkdir -p az EEXIST hibát is elfogadja, ha a könyvtár már létezik. A laborban elegendő a $? kifejtését megvalósítani (last_status); az if-szerkezet választható bővítés, a labor elfogadási tesztje nem tartalmazza. A script futtatása közben a shell a sorokat ugyanúgy tokenizálja, mint az interaktív módban, ezért a kód újrahasznosítható.

A script futtatásának lépései:

  1. a shell open-nel megnyitja a scriptfájlt;
  2. ha a fájl #!-tel kezdődik, az interpretert beazonosítja, és a scriptfájlt argumentumként átadva fork + execve segítségével elindítja;
  3. a kiválasztott interpreter a fájl tartalmát feldolgozza;
  4. a script kilépési állapota az interpreter kilépési állapota lesz.

A script soronkénti beolvasásához a shell főciklusa nem a nyers read pufferre épül (egy read több sort és sorközépen vágott töredéket is hozhat), hanem egy soronkénti olvasóra: static ssize_t read_line(int fd, char *buf, size_t cap) a belső 512 bájtos pufferből az első \n-ig ad vissza, a maradékot megőrzi, túl hosszú sorra hibát ad. A bemenet int in = (argc > 1) ? open(argv[1], O_RDONLY) : STDIN_FILENO;, és a prompt csak in == STDIN_FILENO esetén íródik ki. A tokenize a #-tól sor végéig kommentet vág, és kezeli a "…" idézést; a $? token kifejtése a last_status értékére történik (last_status = run_external(args);).

A laborban a shell sh script.sh formában futtathat scripteket; ez kiváltja a kernel shebang-támogatását, és a shell maga olvassa be a fájlt.

29.4.9 9. Alapszolgáltatások: cat, echo, ls, mkdir, rm

A minimális userland néhány apró, jól körülhatárolt programot tartalmaz. Mindegyik ugyanazokat a rendszerhívásokat használja, mint a shell, így a VFS és a fájlleíró réteg egységesen tesztelhető.

cat

A cat a megadott fájlok tartalmát másolja a szabványos kimenetre. Ha nincs argumentum, a szabványos bemenetet olvassa. A megvalósítás kulcsa a read és write ciklus:

/* user/cat.c – fájl tartalmának másolása */
#include "syscalls.h"

/* a teljes puffert kiírja; EINTR után újrapróbál, 0 hosszú írást hibának vesz */
static int write_all(int fd, const char *buf, size_t len)
{
    size_t off = 0;

    while (off < len) {
        ssize_t w = write(fd, buf + off, len - off);

        if (w < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        if (w == 0)
            return -1;      /* nem haladunk előre: ez hiba, nem siker */
        off += (size_t)w;
    }
    return 0;
}

static int copy_fd(int in_fd)
{
    char buf[512];
    ssize_t n;

    for (;;) {
        n = read(in_fd, buf, sizeof(buf));
        if (n < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        if (n == 0)
            return 0;       /* EOF */
        if (write_all(STDOUT_FILENO, buf, (size_t)n) < 0)
            return -1;
    }
}

int main(int argc, char **argv)
{
    int i;
    int ret = 0;

    if (argc < 2)
        return copy_fd(STDIN_FILENO) < 0 ? 1 : 0;

    for (i = 1; i < argc; i++) {
        int fd = open(argv[i], O_RDONLY, 0);

        if (fd < 0) {
            perror("cat");
            ret = 1;
            continue;
        }
        if (copy_fd(fd) < 0) {
            perror("cat");
            ret = 1;
        }
        close(fd);
    }

    return ret;
}

Három hibaforrásra kell itt ügyelni. Az első, hogy a write nem feltétlenül írja ki a teljes puffert: csővezetéken, terminálon vagy megtelt lemezen rövidebb írás is előfordulhat, ezért a maradékot ciklusban, eltolással kell kiírni – ezt teszi a write_all. A második, hogy EINTR esetén a hívást meg kell ismételni, nem szabad hibaként kezelni; a kezeletlen megszakítás adatvesztést okoz. A harmadik, hogy a nulla hosszú write nem siker: a write(fd, buf, 0) legálisan 0-t ad vissza, de ha nem nulla hosszra kérünk írást és mégis 0-t kapunk, akkor a ciklus soha nem érne véget, ezért ezt hibaként kell kezelni.

A hibát a kilépési kódba is propagálni kell: a cat csak akkor adjon 0-t, ha minden fájl teljesen átíródott. A fenti main ezért ret-et gyűjt, és a hibás fájl után is folytatja a többi feldolgozását – ez a klasszikus cat viselkedése. Csővezetékben a cat írása EPIPE-ot kaphat, ha az olvasó fél időközben kilépett; ilyenkor alapértelmezés szerint a SIGPIPE szignál megöli a folyamatot, amit a 128 + 13 = 141 kilépési kód jelez. A shell ezt a 128 + N szabály szerint értelmezi; ha a program inkább saját hibaüzenettel akar kilépni, a SIGPIPE-ot figyelmen kívül kell hagynia és az EPIPE-ot kezelnie kell.

echo

Az echo az argumentumait szóközzel elválasztva a szabványos kimenetre írja, majd egy újsor karaktert ad hozzá. A minimális verzió nem feltétlenül értelmezi a -n kapcsolót, de a laborban érdemes bevezetni, mert a scriptekben gyakran használják. Az echo belső parancs is lehet, de külön programként egyszerűbb tesztelni a fork + execve útvonalat.

ls

Az ls a VFS könyvtárbejegyzéseit listázza. A minimális rendszerben a getdents rendszerhívás vagy annak burkolója adja vissza a bejegyzések nevét. A program minden bejegyzést kiír, a . és .. kivételével. A hosszú formát, a jogosultságokat és a fájlméretet az os110 fájlrendszer-metaadatainak beolvasásával lehet megjeleníteni; a minimális laborban elég a nevek felsorolása.

mkdir és rm

A mkdir egy új könyvtárat hoz létre. A rm fájlt töröl; a könyvtárak törléséhez a minimális rendszerben külön rmdir programot vagy a rm -r kapcsolót implementálhatjuk. Mindkettő a VFS megfelelő műveletére támaszkodik, és a hibakódokat a szabványos módon jelzi.

A shell és a segédprogramok együttesen adják ki azt a minimális felhasználói környezetet, amelyen a kernel további részei, például a hálózat vagy a tesztelési keretrendszer, kényelmesen gyakorolhatók.

29.4.10 10. Gyakori hibák és helyes megoldások

A shell és a userland építése során a következő hibák a leggyakoribbak.

  1. Zombie folyamatok. Ha a szülő nem hívja a waitpid-et, a befejeződött gyermek a folyamattáblában marad. Idővel a rendszer kifogy a folyamat-helyekből. Megoldás: minden fork után a szülőben waitpid, vagy a SIGCHLD szignál kezelése.

  2. execve utáni kód futása. Ha az execve hibázik, a gyermek a shell kódját folytatja. Megoldás: a gyermek ágban azonnal _exit-et hívni, lehetőleg a 127 kilépési kóddal.

  3. Nyitva maradt pipe-végek. Ha a szülő nem zárja be a cső mindkét végét, a jobb oldali folyamat sosem kap EOF-ot, és a pipeline örökre blokkol. Megoldás: a fork után a szülőben close(fd[0]); close(fd[1]);, a gyermekekben pedig a felesleges végét zárni.

  4. A cd nem beépített. Ha a cd-t külön folyamat futtatja, a szülő munkakönyvtára nem változik. Megoldás: a cd-t a shell saját folyamatában kezelni.

  5. PATH-feloldás biztonsági hibája. Ha a find_in_path a .-t is figyelembe veszi, egy rosszindulatú program elfoglalhatja a rendszerparancs nevét. Megoldás: a . csak akkor legyen a PATH-ban, ha a felhasználó kifejezetten felvette.

  6. Puffer-túlcsordulás a tokenizálásban. A hosszú bemeneti sorok vagy a nagyszámú argumentum túlírhatja a vermet. Megoldás: hosszkorlát, MAX_ARGS ellenőrzés, és a tokenizáló nullázza a tömb végét.

  7. Az errno késői olvasása. A rendszerhívás után más hívások felülírhatják az errno értékét. Megoldás: a hibát azonnal le kell kérdezni, hibaüzenetet írni, és az errno-t nem szabad több hívás után feltételezni.

  8. A $? nem frissül. Ha a shell nem tárolja az utolsó kilépési állapotot, a scriptek feltételes elágazásai hibásan döntenek. Megoldás: a report_status visszatérési értékét a shell egy változóban tárolja, és a $? ezt olvassa.

29.4.11 11. Labor: shell és alapszolgáltatások

A fejezet laborja a shell és a minimális segédprogramok implementálását, valamint azok emulált környezetben történő ellenőrzését foglalja magában.

Kiinduló állapot.

A labor az os112 alfejezet kódjára épül. Adott:

  • QEMU emulált környezet, rögzített konfiguráció: qemu-system-riscv64, 32 MiB RAM, virtio blokk-eszköz. Ez az alfejezet a projekt RISC-V alternatív portja: a Blokk-eszköz és driver implementáció–VFS integráció és fájlleírók x86-64-es driver- és mérőkódja (TSC, qemu64) itt nem használható, a x86-64 változathoz a crt0.S, a Makefile és a link script x86-64-re írandó át (-m64 -mno-red-zone, syscall utasítás), az i386 változathoz külön crt0.S kell (cdecl verem, int 0x80/saját syscall-konvenció);
  • a kernel rendszerhívásai: open, read, write, close, fork, execve, waitpid, pipe, dup2, chdir, getcwd, mkdir, unlink, rmdir, getdents, exit;
  • a VFS-ben a /bin, /etc, /home, /tmp könyvtárak;
  • az os112 VFS-re épülő fájlleíró réteg.

Feladatok.

  1. Valósítsd meg a user/sh.c shellt a fenti tokenize, run_builtin, run_external, run_pipeline, find_in_path és report_status függvényekkel.
  2. Írd meg a user/cat.c, user/echo.c, user/ls.c, user/mkdir.c (-p kapcsolóval), user/rm.c, user/true.c és user/wc.c programokat; a help a shell run_builtin ágában valósul meg.
  3. Fordítsd le a programokat freestanding C-környezetben, és helyezd a /bin könyvtárba egy initramfs építő segítségével.
  4. Indítsd a rendszert QEMU-ban, és ellenőrizd az alábbi parancsokat:
    • echo Hello Mini OS
    • cat /etc/motd
    • ls /bin
    • cd /tmp majd külön sorban pwd
    • cat /etc/motd | cat > /home/motd2
    • sh laborbemutato.sh
  5. Készíts reprodukálható jegyzőkönyvet.

Build és futtatási parancsok. A laborban használt parancsok szemléltető jellegűek; a pontos keresztszerkesztő és QEMU-változat a reprodukciós csomagban található.

A build három dolgot igényel: külön objektumcélokat a közös forrásokhoz, egy tényleges crt0-t, valamint egy link scriptet. A közös objektumok külön célként készülnek el, ezért a make -j párhuzamos futása sem írja ugyanazt a syscalls.o-t hatszor egyszerre – ha a közös objektumot minden célban újra előállítanánk, ez valódi versenyhelyzet lenne, és időnként csonka objektumot vagy „file changed while being read” hibát eredményezne.

# user/Makefile – a userland programok fordítása (szemléltetés)
CROSS    ?= riscv64-linux-gnu-
CFLAGS   := -O2 -march=rv64imac -mabi=lp64 -ffreestanding -nostdinc \
            -I../include -fno-builtin -fno-stack-protector \
            -fno-asynchronous-unwind-tables -fno-pie
LD       := $(CROSS)ld
LDFLAGS  := -T user.ld -nostdlib
INITRAMFS := ../initramfs
CPIO      := ../build/initramfs.cpio

USER_PROGS := cat echo ls mkdir rm sh
LIB_OBJS   := syscalls.o string.o
CRT0       := crt0.o

all: $(USER_PROGS) $(CPIO)

# Közös objektumok: egy-egy önálló cél, egyszer lefordítva.
syscalls.o: ../lib/syscalls.c ../include/syscalls.h
    $(CROSS)gcc $(CFLAGS) -c $< -o $@

string.o: ../lib/string.c ../include/string.h
    $(CROSS)gcc $(CFLAGS) -c $< -o $@

crt0.o: crt0.S
    $(CROSS)gcc $(CFLAGS) -c $< -o $@

%.o: %.c ../include/syscalls.h
    $(CROSS)gcc $(CFLAGS) -c $< -o $@

# A program a saját objektumából, a crt0-ból és a közös objektumokból linkelődik.
$(USER_PROGS): %: %.o $(CRT0) $(LIB_OBJS) user.ld
    $(LD) $(LDFLAGS) -o $@ $(CRT0) $< $(LIB_OBJS)
    mkdir -p $(INITRAMFS)/bin
    cp $@ $(INITRAMFS)/bin/

# Determinisztikus initramfs: rögzített mtime, uid/gid, inode- és devnumszám.
$(CPIO): $(USER_PROGS)
    mkdir -p $(dir $@) $(INITRAMFS)/bin
    find $(INITRAMFS) -exec touch -h -d @0 {} +
    cd $(INITRAMFS) && find . -print | LC_ALL=C sort | \
        cpio -o -H newc --reproducible -R 0:0 | gzip -n > $(abspath $@)

clean:
    rm -f *.o $(USER_PROGS) $(CPIO)

.PHONY: all clean

A crt0.S adja a program belépési pontját; enélkül a linker _start szimbólum nélkül dolgozna, és az execve a belépési címen szemétkódot futtatna:

# user/crt0.S – a userland programok belépési pontja (szemléltetés)
#include "syscall_nr.h"      /* SYS_exit; a .S fájlt a gcc előfeldolgozza */
    .section .text.start
    .globl _start
_start:
    # a minimális kernel execve-ja: a0 = argc, a1 = argv, a2 = envp
    la   t0, environ         # az envp átvétele a main hívása előtt
    sd   a2, 0(t0)
    addi sp, sp, -16
    sd   ra, 8(sp)
    call main
    # main visszatérési értéke a0-ban: rendszerhívással kilépünk
    li   a7, SYS_exit        # a saját rendszerhívási táblánk száma
    ecall
1:  j 1b                     # ha az exit mégis visszatérne, ne fussunk tovább

A user.ld link script rögzíti a betöltési címet és a szekciók sorrendjét:

ENTRY(_start)
SECTIONS {
    . = 0x10000;                       /* a userland betöltési címe a laborban */
    .text   : { *(.text.start) *(.text*) }
    .rodata : { *(.rodata*) }
    .data   : { *(.data*) }
    .bss    : { *(COMMON) *(.bss*) }
}

Az initramfs-kép gzip-tömörített newc cpio; ha a kernel nem tud kibontani, hagyd el a gzip -n lépést. Az env_store az environ tömböt módosítja (vagy egy saját tömböt, amelyre az environ-t átállítja). A 0x10000 a labor konfigurációja: a kernel execve-jának ugyanezt a címet kell használnia a szegmensek betöltéséhez, különben a program abszolút címekkel hibás memóriára mutat. A crt0 és a user.ld nélkül a linker ugyan létrehoz egy fájlt, de az execve nem talál belépési pontot, vagy a program a kernel területére próbál betöltődni.

A QEMU futtatás (a példa következetesen a riscv64 változatot használja; az i386 változathoz ugyanezek a célok és linkelési szabályok érvényesek, csak a CROSS és a -march/-mabi értéke más):

qemu-system-riscv64 \
  -machine virt \
  -m 32M \
  -kernel build/kernel.elf \
  -initrd build/initramfs.cpio \

A shell prompt megjelenése után a fenti tesztek futtathatók. A labor reprodukálhatósága érdekében a kernelverziót, a fordítási konfigurációt és a QEMU-verziót rögzíteni kell. A build helyességét érdemes tiszta állapotból (make clean && make -j"$(nproc)") ellenőrizni: így derül ki, hogy nincs-e hiányzó függőség, és hogy a párhuzamos futás nem ír-e ugyanabba a fájlba.

29.4.12 12. Önellenőrző kérdés

A shell csővezeték futtatásakor a következő parancsot adjuk ki:

cat /etc/motd | cat > /home/motd2

A szülő shell a pipe és a két fork után mindkét csővéget bezárja, majd waitpid-del vár mindkét gyermekre. Tegyük fel, hogy a /etc/motd fájl 1024 bájt, a pipe puffer mérete 4096 bájt, és mindkét cat a read/write hívásokat 512 bájtos pufferekkel végzi. Válaszolj a következőkre:

  1. Miért nem fordulhat elő az, hogy a jobb oldali cat a read-ben örökre blokkol?
  2. Hány read hívást hajt végre a bal oldali cat, amíg az EOF-t meg nem kapja?
  3. Mi történik, ha a szülő elfelejti bezárni a pipe író végét a második fork után?

A válasz elemei:

  1. A bal oldali cat a fájl végére érve kilép, ami bezárja a pipe író végét. Mivel a szülő is bezárta a saját író végét, a pipe-nak nem marad nyitott írója, így a jobb oldali read 0-t ad vissza.
  2. A bal oldali cat 1024 / 512 = 2 read hívással beolvassa a fájlt, majd a harmadik read adja a 0 visszatérést; ezután nem olvas tovább. Tehát összesen 3 read, de ebből 2 szolgáltat adatot.
  3. Akkor a jobb oldali cat nem kap EOF-ot, mert a szülőben nyitva maradt az egyik író vég; a pipeline a read-ben blokkol, és a waitpid sosem tér vissza. Ez a klasszikus pipe-szivárgás.

A fejezetben bemutatott shell és alapszolgáltatások a következő egység (os114) számára alapot adnak: a tesztelési keretrendszer már parancssori eszközökkel indítható, a shell pedig alkalmas az automatikus tesztek futtatására és az eredmények összegyűjtésére.
