3.1 Monolitikus, mikrokernel és hibrid kernel

A kernelarchitektúra megválasztása alapvetően meghatározza az operációs rendszer teljesítményét, hibatűrését, karbantarthatóságát és biztonsági tulajdonságait. Az előző alfejezetben bevezetett kernel, folyamat és rendszerhívás fogalmakra építve most három klasszikus felépítést vizsgálunk: monolitikus, mikrokernel és hibrid kernel. A kérdés mindig az, hogy a szolgáltatások mely része fut a privilegizált kernel módban, és mely része kerül felhasználói módba, külön folyamatokba. A válasz kompromisszumok sorozata a közvetlen hívás sebessége, az izoláció erőssége és a hibatűrés képessége között.

3.1.1 Monolitikus kernel

A monolitikus kernel (monolithic kernel) esetén az operációs rendszer magja egyetlen binárisban, közös címtérben fut, teljes egészében privilegizált módban. A folyamatkezelés, memóriakezelés, fájlrendszer, hálózati stack, eszközmeghajtók és a rendszerhívások implementációja mind ugyanabban a kódbázisban található. A komponensek egymást közvetlen függvényhívással érik el, nincs közöttük üzenetküldés vagy kontextusváltás.

Klasszikus példa a korai UNIX, a Linux, a BSD család és számos beágyazott rendszer magja. A Linux esetében a modulrendszer lehetővé teszi, hogy a kernelt futás közben bővítsük, de a betöltött modul továbbra is a kernel címtérbe kerül, és kernel módban fut. Ezért a Linux alapvetően monolitikus, annak ellenére, hogy a modulok dinamikus betöltése és eltávolítása bizonyos rugalmasságot ad.

Előnyök. A monolitikus kernel fő előnye a teljesítmény. Mivel a kernelkomponensek között nincs IPC réteg, egy rendszerhívás kiszolgálása általában egyetlen privilegizált módba lépésből és néhány függvényhívásból áll. Nincs szükség további kontextusváltásra vagy üzenetmásolásra. Ez különösen akkor előnyös, ha a rendszerhívások gyakoriak, vagy ha az eszközmeghajtók közvetlenül, alacsony késleltetéssel akarnak hozzáférni a hardverhez. A fejlesztés első iterációja is gyakran egyszerűbb, mert a komponensek közvetlenül láthatják egymás adatszerkezeteit.

Hátrányok és hibahatás. A monolitikus kialakítás legnagyobb gyengesége, hogy bármely komponens hibája a teljes kernel összeomlását okozhatja. Egy hibás mutató az eszközmeghajtóban a kernel címtérben lévő memóriát írhatja felül, ami rendszerösszeomláshoz (panic) vagy csendes adatsérüléshez vezet. A hibahatás (fault blast radius) az a rendszerrész, amelyre egy komponens hibája kiterjedhet; monolitikus kernelnél ez a teljes kernel: nincs izoláció a kernelkomponensek között. Emiatt a megbízhatóság szempontjából a monolit kernelben minden kódnak közel azonos minőségi szintet kell elérnie, és a hibakeresés is nehezebb, mert a hiba hatása nem lokalizált.

A karbantarthatóság szintén kihívás. A nagy méretű, szorosan összekapcsolt kódban a változtatások könnyen nem várt mellékhatásokat okoznak. A Linux fejlesztői ezt szigorú review-folyamattal, a modulinterfészek ellenőrzésével és a hibás modulok eltávolíthatóságával kezelik, de az alapvető szerkezeti tulajdonság változatlan marad.

Egy egyszerű illusztráció arra, hogyan néz ki egy monolitikus kernelben egy UART-írás. A közös címtér nem jelenti azt, hogy a felhasználótól kapott cím és hosszúság ellenőrzés nélkül használható: a user/kernel határ ellenőrzése a monolitikus felépítésben is kötelező.

// monolit_vazlat.c – freestanding C, csak szemléltetés
#define UART_MAX_WRITE 256u          /* egy hívásban átvihető max. bájt */
#define USER_BASE      0x00400000u
#define USER_TOP       0x80000000u

/* A [ptr, ptr+len) intervallum a felhasználói címtérben marad-e? */
static bool user_range_ok(uintptr_t ptr, size_t len) {
    if (ptr < USER_BASE || ptr >= USER_TOP)
        return false;                /* kernelcím vagy érvénytelen cím */
    if (ptr + len < ptr)             /* számtani átfordulás */
        return false;
    return (ptr + len) <= USER_TOP;  /* határon átnyúló puffer */
}

int syscall_uart_write(uintptr_t uptr, size_t len) {
    char kbuf[UART_MAX_WRITE];

    if (len == 0)
        return 0;                    /* a POSIX write nulla hosszra 0-t ad */
    if (len > UART_MAX_WRITE)
        return -EINVAL;              /* túl nagy méret, még semmit sem olvastunk */
    if (!user_range_ok(uptr, len))
        return -EFAULT;              /* érvénytelen cím vagy határon átnyúló puffer */

    /* A kernel nem dereferálja közvetlenül a felhasználói címet:
       ellenőrzött másolással viszi át a saját pufferébe. */
    if (copy_from_user(kbuf, (const void *)uptr, len) != 0)
        return -EFAULT;              /* nem leképezett vagy nem olvasható lap */

    return uart_hw_write(kbuf, len); /* 0 vagy -EIO */
}

int syscall_handler(int nr, uintptr_t a1, uintptr_t a2, uintptr_t a3) {
    switch (nr) {
    case SYSCALL_UART_WRITE:
        return syscall_uart_write(a1, a2); /* a hibakód a hívóhoz megy vissza */
    default:
        return -ENOSYS;
    }
}

Három hibaesetet külön kell kezelni. Érvénytelen cím (a felhasználói tartományon kívül, például kernelcím): a user_range_ok még a másolás előtt elutasítja, -EFAULT-tal. Túl nagy méret: a hívás -EINVAL-lal tér vissza, mielőtt bármit olvasnánk (nulla hossznál a hívás 0-t ad; az EFAULT csak címhibát jelent). Határon átnyúló puffer (a puffer eleje a felhasználói címtérben van, a vége már nem): a ptr + len ellenőrzés fogja meg, és ha a cím érvényesnek látszik, de a lap nincs leképezve, a copy_from_user ad -EFAULT-ot. A copy_from_user azért kell, mert a nyers dereferálás a felhasználói címre nem ellenőrzött: hibás címnél a kernel összeomlana a hívó folyamat helyett. A uart_hw_write közvetlen hívása így is semmilyen további réteget nem igényel, a hibakezelés egyszerű, de ha maga a driver hibás, az egész rendszer megáll.

3.1.2 Mikrokernel

A mikrokernel (microkernel) filozófiája a minimalizmus: a lehető legkevesebb funkcionalitást futtassuk privilegizált módban. A kernel magjában általában csak a következők maradnak:

  • alacsony szintű folyamat- és szálütemezés,
  • memóriakezelés és címfordítás,
  • inter-process communication (IPC) primitívek,
  • legalapvetőbb megszakításkezelés és hardver-elérési mechanizmus.

Minden egyéb szolgáltatás – fájlrendszer, hálózati stack, eszközmeghajtók, felhasználói azonosítás, magasabb szintű folyamatkezelés – felhasználói módban futó szerverfolyamatokba kerül. Ezek a szerverek egymással és a kliensekkel üzenetküldéssel kommunikálnak. A mikrokernel feladata elsősorban az izoláció biztosítása, az üzenetek továbbítása és a hardver-hozzáférés szabályozott delegálása.

Példák mikrokernelre: Mach, L4 (és leszármazottai: seL4, Fiasco.OC, OKL4), QNX, Minix. A QNX különösen a beágyazott és valós idejű piacon bizonyította, hogy a mikrokernel architektúra ipari környezetben is működőképes lehet.

Előnyök: izoláció és hibatűrés. A legfontosabb előny, hogy egy hibás fájlrendszer-szerver vagy eszközmeghajtó nem dönti le a teljes rendszert. A szerver összeomlása helyi hibaként kezelhető: újraindítható, miközben a kernel és a többi szolgáltatás tovább működik. Ez a tulajdonság erős alapot ad a biztonsági izolációhoz is, hiszen egy feltört szerver csak a saját jogosultságán belül tud kárt okozni. A formálisan verifikált seL4 projekt azt is demonstrálta, hogy a minimális kernel bizonyíthatóan helyes implementációja elérhető, ami a biztonságkritikus rendszerekben kulcsfontosságú.

Hátrányok: IPC-költség és komplexitás. A mikrokernel ára a kommunikáció költsége. Ahol a monolit kernelben egy rendszerhívás egyszerű függvényhívás, ott a mikrokernelben a kérés átmegy egy IPC csatornán: a kliens folyamatból a kernelbe, onnan a szerver folyamatba, majd vissza. Ez legalább két kontextusváltást, valamint az üzenet másolását jelenti. A korai mikrokernel implementációk (például a Mach az 1990-es években) éppen emiatt teljesítményproblémákkal küzdöttek, ami hozzájárult a hibrid megoldások elterjedéséhez.

A modern mikrokernel tervezések azonban jelentősen csökkentették ezt a költséget. Az L4 családban a szinkron IPC műveletet a processzor regiszterein keresztül, üzenetmásolás nélkül, néhány száz ciklus alatt hajtják végre. Emellett a „zero-copy” üzenetátadás és a közvetlen folyamatok közötti hardver-hozzáférés (capability alapú delegálás) tovább javítja a teljesítményt. Ennek ellenére a mikrokernel rendszerhívás útja általában hosszabb, mint egy hasonló monolitikus műveleté.

Mikrokernelben ugyanaz az UART-írás például így nézhet ki. A lényeg, hogy a szerver más címtérben fut, ezért a kliens nyers virtuális címét nem tudja általánosan dereferálni: az csak a kliens címtérben érvényes. A bájtokat ezért vagy be kell másolni az üzenetbe, vagy explicit megosztási (grant) protokollal kell átadni.

// mikrokernel_vazlat.c – freestanding C, csak szemléltetés
#define IPC_INLINE_MAX 64u

typedef struct {
    uint32_t type;
    uint32_t len;                    /* <= IPC_INLINE_MAX */
    uint8_t  data[IPC_INLINE_MAX];   /* a bájtok az üzenetben utaznak */
} ipc_msg_t;

int syscall_uart_write(uintptr_t uptr, size_t len) {
    char kbuf[IPC_INLINE_MAX];
    ipc_msg_t msg = { .type = IPC_UART_WRITE, .len = 0 };

    if (len == 0)
        return 0;
    if (len > IPC_INLINE_MAX)
        return -EMSGSIZE;            /* nem fér az üzenetbe: nagyobb átvitelhez lásd a grant utat */

    /* A kliens címét a kernel ellenőrzi és másolja, a szerver már
       csak a lemásolt bájtokat látja. */
    if (copy_from_user(kbuf, (const void *)uptr, len) != 0)
        return -EFAULT;

    msg.len = (uint32_t)len;
    memcpy(msg.data, kbuf, len);

    /* A hívó blokkol, amíg a szerver vissza nem jelez. */
    return ipc_call(uart_server_cap, &msg, sizeof msg);
}

A uart_server_cap a szerver elérésére jogosító capability, nem puszta azonosító: a kernel a hívásnál ellenőrzi, hogy a kliens rendelkezik-e a küldési joggal. Az ipc_call magában foglalja a kontextusváltást, a jogosultságellenőrzést és az üzenet átadását; a szerver a válaszüzenetben adja vissza az eredményt. A szerveroldal csak az átvett data tömböt használhatja, a kliens címére nem hivatkozhat.

A IPC_INLINE_MAX-nál nagyobb átvitelhez grant/memória-leképezési protokoll kell, négy rögzített elemmel:

  • jogosultság: a kliens csak olvasási (esetleg írási) jogot adhat a megosztott memóriaobjektumra, a szerver a kapott capability révén érheti el;
  • élettartam: a leképezés a kérés kiszolgálásáig, azaz a válaszüzenetig él;
  • visszavonás: a kernel a válasznál (vagy a kliens halálakor) visszavonja a leképezést és érvényteleníti a capabilityt;
  • tulajdonjog: a memóriaobjektum tulajdonosa a kliens marad, a szerver csak a kapott joggal él.

E nélkül a szerver vagy nem éri el az adatot, vagy a kliens címtartományára mutató, érvénytelen címre dereferál – ez utóbbi a mikrokernelben is a szerver összeomlását okozná, csak éppen nem a kernelét.

Tipikus hiba a mikrokernellel kapcsolatban: abszolutizálni a teljesítményhátrányt, és azt állítani, hogy a mikrokernel „mindig lassú”. A modern implementációk, mint az L4 vagy a QNX, valós idejű környezetben is versenyképesek lehetnek. A helyes megközelítés az, hogy a költséget a rendszer céljaihoz viszonyítjuk: ha a hibatűrés és az izoláció elsődleges, a mérsékelt IPC-többlet elfogadható. A Linuxban például a FUSE (és a felhasználói térben futó NFS-Ganesha szerver) felhasználói módú szervereken keresztül működik, ami mikrokernel-szerű mintát valósít meg egy monolitikus magon belül; a beépített NFS-kliens és -szerver viszont a kernelben fut.

3.1.3 Hibrid kernel

A hibrid kernel (hybrid kernel) a monolitikus és a mikrokernel közötti köztes megoldás. Célja, hogy a teljesítménykritikus szolgáltatásokat – például az ütemezőt, a memóriakezelőt, az alacsony szintű eszközmeghajtókat – a kernel címtérben tartsa, míg egyes, kevésbé kritikus vagy jobban izolálandó komponensek felhasználói módba kerülhetnek. Így a gyakori műveletek gyorsak maradnak, de bizonyos hibák nem döntik le a rendszert.

Jellegzetes példa a Microsoft Windows NT család. A Windows kernel (ntoskrnl) tartalmazza az ütemezőt, a memóriakezelést, a fájlrendszer-keretrendszert és számos alacsony szintű eszközmeghajtót. Ugyanakkor a Win32 környezeti alrendszer folyamata (csrss.exe), a felhasználói módú meghajtók (UMDF) és a grafikus meghajtók felhasználói módú része (WDDM user-mode driver) felhasználói módban futnak; a Win32k (USER/GDI) viszont az NT 4.0 óta teljesítményokból kernel módban fut (win32k.sys; az NT 4.0-s dátum ellenőrzendő). A régebbi POSIX/SUA alrendszer a Windows 8.1-ig létezett (ellenőrzendő). A macOS XNU magja hasonlóan hibrid: a Mach mikrokernel biztosítja az IPC-t, az ütemezést és a memóriakezelést, míg a BSD réteg monolitikus jelleggel valósítja meg a fájlrendszert, a hálózati stacket és a rendszerhívásokat.

Kompromisszumok. A hibrid kernel előnye, hogy a legfontosabb teljesítményigényeket kielégíti, miközben némi izolációt és modularitást biztosít. A hátránya viszont az, hogy a határvonal a kernel és a felhasználói mód között kevésbé éles, és a tervezés bonyolultabbá válhat. A hibrid rendszerben is igaz, hogy a kernel címtérben futó kód hibája összeomlást okoz, ezért a kritikus komponenseknek továbbra is megbízhatónak kell lenniük. A hibrid architektúra tehát nem szünteti meg a monolitikus kernel alapvető hibahatás-problémáját, csak szűkíti a kockázatos kód felületét.

Fontos megjegyezni, hogy a „hibrid” kifejezést gyakran pontatlanul használják. Egyes források a moduláris monolitikus kerneleket (például a Linuxot) is hibridnek nevezik, mert a modulok dinamikusan tölthetők. Ez azonban félrevezető: a Linux modulok továbbra is a kernel címtérben futnak, ezért az architekturális értelemben vett izoláció nem valósul meg. Helyes tehát hibrid kernelnek azokat a rendszereket nevezni, amelyek mikrokernel-eredetű belső szerkezetet (üzenet- vagy objektumalapú rétegek, külön mag és szolgáltatásréteg) követnek, de a szolgáltatásokat teljesítményokból a kernel címterében futtatják; egyes szolgáltatások ezen felül felhasználói módba kerülhetnek.

3.1.4 Összehasonlítás és kompromisszumok

Az alábbi táblázat összefoglalja a három architektúra legfontosabb jellemzőit.

Szempont Monolitikus kernel Mikrokernel Hibrid kernel
Kernel módban futó kód majdnem minden csak minimális mag kritikus részek
Szolgáltatások helye kernelben felhasználói téri szerverek vegyesen
Kommunikáció függvényhívás IPC vegyes
Teljesítmény legjobb általában alacsonyabb jó, de nem mindig optimális
Hibatűrés gyenge, egy hiba mindent visz erős, szerverek újraindíthatók közepes
Komplexitás közepes magas (IPC tervezés) magas (kettős architektúra)
Példák Linux, BSD, régi UNIX L4, seL4, QNX, Minix Windows NT, macOS XNU

A választás sosem abszolút: a rendszer követelményei döntik el, hogy melyik kompromisszum elfogadható. Egy általános célú szerver operációs rendszerben a teljesítmény és a széles hardvertámogatás gyakran a monolitikus megoldás felé tol. Egy biztonságkritikus vagy valós idejű beágyazott rendszerben az izoláció és a determinizmus a mikrokernel mellett szól. A hibrid megoldás akkor előnyös, ha a rendszer egyszerre igényel magas teljesítményt és bizonyos fokú modularitást, például asztali operációs rendszerekben.

3.1.5 Tipikus hibák és helyes megoldás

A fejezet tanulási céljaihoz kapcsolódva három gyakori tévhitet érdemes kiemelni.

  1. „A monolitikus kernel mindig gyors, tehát a legjobb.” Ez a hiba figyelmen kívül hagyja a hibahatást és a karbantarthatóságot. Egyetlen hibás eszközmeghajtó is rendszerösszeomlást okozhat, ami bizonyos környezetekben elfogadhatatlan. A helyes megoldás a követelmények elemzése: ha a rendelkezésre állás és a biztonság kritikus, a teljesítményt kell mérsékelten feláldozni.

  2. „A mikrokernel mindig lassú, ezért alkalmatlan.” Ez a múltbeli Mach-tapasztalatok túláltalánosítása. A modern L4-alapú mikrokernel IPC-költsége néhány száz processzorciklus, ami sok alkalmazásban elhanyagolható. A helyes megoldás az, hogy konkrét mérésekkel ellenőrizzük a teljesítményt az adott hardveren és munkaterhelésen, és ne általános sztereotípiák alapján döntsünk.

  3. „A hibrid kernel ugyanaz, mint a moduláris monolitikus kernel.” Ez a fogalmi hiba összemossa a dinamikus modulbetöltést a felhasználói módú szolgáltatásokkal. A helyes megoldás az, hogy a moduláris monolitikus kernel (Linux) modulrendszere csak betöltési rugalmasság, a hibrid kernel (XNU, NT) belső szerkezete viszont mikrokernel-eredetű; egyik sem jelent automatikusan felhasználói módú izolációt.

3.1.6 Labor: monolit és mikrokernel hívási útja

A labor alapfeladata papíron végigjátszható: ugyanarra a feladatra két teljes hívási útvonalat rajzolunk fel, és megszámoljuk a vezérlési eseményeket. A feladat: egyetlen szolgáltatás – egy UART-eszközre írt rövid üzenet rendszerhíváson keresztül. Az összehasonlítás tárgya nem a futási idő, hanem az, hogy hány módváltás, másolás, IPC-üzenet és kontextusváltás kell ugyanahhoz az eredményhez. A QEMU-s futtatás külön, későbbi bővítés (lásd a szakasz végén), mert teljes mintaprojektet, bootfejlécet és rögzített mérési naplót igényel.

Alapfeladat: két hívási útvonal. Az üzenet 16 bájt (Kernel vazlat OK), a felhasználói puffer érvényes és olvasható.

Monolitikus út:

  1. A kliens rendszerhívó utasítása: U→K átlépés, a diszpécser kiválasztja a SYSCALL_UART_WRITE ágat.
  2. Tartomány- és méretellenőrzés (user_range_ok), majd copy_from_user: a 16 bájt a kernel pufferébe kerül (1 másolás).
  3. uart_hw_write: 16 outb, mindegyik előtt LSR-várakozás.
  4. Visszatérés: K→U átlépés, a hívó megkapja a hibakódot.

Nincs IPC, nincs másik címtér, nincs kontextusváltás.

Mikrokernel út:

  1. A kliens rendszerhívó utasítása: U→K átlépés; a kernel ellenőrzi a küldési capabilityt.
  2. Méretellenőrzés és copy_from_user a kernel pufferébe (1. másolás), majd memcpy az üzenetbe (2. másolás).
  3. ipc_call: a kliens blokkol, a kernel átadja az üzenetet a szervernek → 1. kontextusváltás; a szerver U módban fut.
  4. A szerver a saját üzenetpufferéből 16 outb-t végez (a device-capability birtokában), majd válaszüzenetet küld; a szerver saját rendszerhívása U→K és K→U átlépéssel jár, a válasz átadása a 2. kontextusváltás.
  5. A kliens felébred, a rendszerhívás K→U átlépéssel visszatér.

Eseményszámlálás. Az alábbi táblázat a fenti két útvonalból levezetett eseményszám, nem mért érték:

Esemény Monolitikus Mikrokernel
U→K / K→U átlépés (kliens) 1 + 1 1 + 1
U→K / K→U átlépés (szerver) 0 1 + 1
Adatmásolás 1 (16 bájt) 2 (16 bájt)
IPC üzenet 0 2 (kérés + válasz)
Kontextusváltás (más címtér) 0 2
Eszköz-hozzáférés (outb) 16 16
Összes vezérlési esemény 19 26

A számlálás szabálya rögzített: egy outb egy esemény, egy másolás akkor is egy esemény, ha 16 bájtról van szó, és a szerver válasza külön rendszerhívásnak számít. Az üzenethossz növelésével a különbség szerkezete nem változik, csak az outb-k száma nő mindkét oldalon; a mikrokernel fix többlete 1 további másolás, 2 IPC-üzenet, 2 kontextusváltás és 2 további módváltás, összesen 7 esemény (26 − 19 = 7). Feltételezés: az üzenet a kernelből a szerverhez regiszterekben (L4-stílusban) jut; ha a kernel a szerver pufferébe másol, a mikrokernel oszlop 3 másolással és 27 eseménnyel számol.

Későbbi bővítés: QEMU-s futtatás. A futtatható változathoz a következő fájlok kellenek, amelyeket ez a fejezet nem tartalmaz:

A futtatható változat a Definíciók: erőforrás-kezelő, absztrakció és virtuális gép minimal-os projektjére épül (multiboot, QEMU -kernel, ACPI S5-tel történő leállítás); a két változat ennek két külön könyvtárba másolt, azonos induló állapotú példánya. A monolitikus ág a syscall_uart_write-ot közvetlen hívással, a mikrokernel ág egy kernel-taskként futó UART-szerverrel valósítja meg. Saját boot szektor ehhez nem kell: a kernelbetöltést (1 MiB fölé töltés, védett mód) a multiboot-betöltő végzi, ezért az itt korábban tervezett 512 bájtos boot szektor elmarad. Az UART-inicializálás (115200 8N1: IER=0, LCR=0x80, DLL/DLM osztó, LCR=0x03, FCR=0xC7) a kernel.c-be kerül; a futás befejezéséhez a Definíciók: erőforrás-kezelő, absztrakció és virtuális gép ACPI-leállítása használandó (a cli; hlt ciklus a QEMU-t nem állítja le).

A helyes illusztratív UART-írás nem ír vakon az adóregiszterbe, hanem megvárja annak ürülését:

static void uart_putc(uint8_t c) {
    while ((inb(0x3FD) & 0x20) == 0)   /* LSR 5. bit: THR üres */
        ;
    outb(0x3F8, c);
}

A bővítés mérési naplójában rögzíteni kell a hardvert, a QEMU verzióját és kapcsolóit, a fordító és a kapcsolók verzióját, a mérési módszert (monoton óra a hoszton, KVM-mel; TCG alatt csak az eseményszám értelmezhető, a TSC emulált), az órajelet és a bizonytalanságot. E fejezet nem közöl mért ciklusszámot: a fenti táblázat levezetett eseményszám, és a QEMU-s futásig minden ciklusérték illusztratív lenne.

Visszaállítás. Az alapfeladat nem futtat semmit a gépen. A bővítés futtatásakor minden fájl eldobható munkakönyvtárban van; a futtatás után ezt a könyvtárat töröljük, a QEMU lemezképfájlját (ha volt) eltávolítjuk. A hoszt gép bootloaderét és lemezpartícióit nem érintettük, mert a kernelünk csak az emulált gépen futott.

A labor rámutat a fejezet fő üzenetére: a két architektúra ugyanazt a felhasználói eredményt adja, de a belső út és a hibahatás alapvetően különbözik. A mikrokernel változatban az UART-szerver önállóan újraindítható lenne, míg a monolitikus változatban egy hibás outb hívás az egész kernelt megállíthatja.
