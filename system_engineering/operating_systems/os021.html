6.4 POSIX, Windows API és hordozhatóság

A hordozható rendszerprogramozás alapkérdése nem az, hogy „melyik operációs rendszer a jobb”, hanem az, hogyan tudunk úgy interfészt tervezni, hogy a programunk viselkedése előre jelezhető legyen több platformon. A POSIX és a Windows API két eltérő filozófiát képvisel: az előbbi a Unix-szerű rendszerek közös, szabványos rétegét adja, az utóbbi egyetlen operációs rendszer-család stabil, dokumentált natív felületét. Ebben az alfejezetben a két modellt, a köztük lévő hidakat, valamint a feltételes fordításra épülő absztrakciós technikákat vizsgáljuk.

6.4.1 1. Szabványos és platformspecifikus interfészek

Operációs rendszeri szempontból a programozási interfész (API) az a szerződés, amelyen keresztül a felhasználói térben futó kód a kernel szolgáltatásait eléri. Ez a szerződés több rétegből állhat: a processzor által kikényszerített privileged utasításokból, a kernel által exportált rendszerhívásokból, a libc vagy futásidejű könyvtár által nyújtott burkolófüggvényekből, valamint a nyelvi szabványkönyvtárakból.

Szabványos interfész alatt olyan, független szervezet által rögzített specifikációt értünk, amelyet több implementáció is követ. Ilyen a POSIX (IEEE 1003, illetve a Single UNIX Specification része), a C szabványkönyvtár (ISO/IEC 9899), valamint a hálózati programozásban gyakran hivatkozott BSD socket API. A szabványosítás célja, hogy a forráskód – ideális esetben – újrafordítás után más rendszeren is azonos szemantikával fusson.

Platformspecifikus interfész ezzel szemben egy adott operációs rendszerhez vagy gyártói ökoszisztémához kötődik. A Win32 API a Microsoft Windows rendszerek natív programozási felülete; a macOS-en a Cocoa és a Darwin alrendszer, a Linux kernelben pedig bizonyos, a POSIX-on túlmutató kiterjesztések (például epoll, inotify, io_uring) is platformspecifikusnak számítanak. A platformspecifikus API-k gyakran gazdagabbak, de használatuk csökkenti a forráskód átjárhatóságát.

A mérnöki dilemma tehát az, hogy meddig érdemes a szabványos rétegre támaszkodni, és hol kell platformfüggő kódot bevezetni. A válasz a projekt követelményeitől függ: egy beágyazott eszközön futó szoftvernél a determinizmus fontosabb lehet a forráshordozhatóságnál, míg egy szerveroldali szolgáltatásnál a konténeres telepítés és a CI-mátrix a hordozhatóságot kényszeríti ki.

6.4.2 2. POSIX: a Unix-szerű rendszerek közös nyelve

A POSIX (Portable Operating System Interface) szabványcsalád a nyolcvanas évek végétől kezdve az Unix-változatok közötti átjárhatóságot célozta. Az IEEE 1003.1 ma már a Single UNIX Specification része, és a legtöbb Unix-szerű rendszer – Linux, macOS, FreeBSD, Solaris, QNX – deklaráltan POSIX-kompatibilis vagy ahhoz közeli. A POSIX nem csupán rendszerhívásokat ír le: tartalmazza a libc függvényeit, a shell nyelvet, a segédprogramokat (ls, grep, awk), a fájlrendszer-szemantikát, a szignálkezelést, a szálakat (POSIX Threads, pthread) és a folyamatok közötti kommunikációt is.

A rendszerhívási rétegben a POSIX a Unix-filozófiát tükrözi: „minden fájl”. A fájlműveletek a open, read, write, close, lseek, fsync függvényeken keresztül érhetők el, a folyamatkezelés pedig a fork, exec*, wait* családdal. A hálózati programozásban a socket API a socket, bind, listen, accept, connect, send, recv hívásokkal dolgozik. A szálkezelést a pthread_create, pthread_join, pthread_mutex_lock és társai biztosítják.

A hibakezelés a POSIX-rendszerekben jellemzően a következő mintát követi: a rendszerhívás-burkolók többsége -1 értékkel tér vissza hiba esetén, és a hiba pontos okát az errno szálankénti változó tárolja. Kivételek: a pthread-függvények a hibakódot közvetlenül visszatérési értékként adják (siker: 0), az mmap MAP_FAILED-et, a fopen NULL-t, a getaddrinfo saját EAI_* kódot ad. A strerror(errno) vagy a perror segítségével olvasható üzenetté alakíthatjuk. Példa egy minimális fájlíró programra:

#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    /* Emulált laborban a /tmp a konténer saját tmpfs-e. */
    const char *path = "/tmp/hello-posix.txt";
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) {
        fprintf(stderr, "open: %s\n", strerror(errno));
        return 1;
    }
    const char *msg = "hello from POSIX\n";
    size_t left = strlen(msg);
    const char *p = msg;
    while (left > 0) {
        ssize_t n = write(fd, p, left);
        if (n < 0) {
            if (errno == EINTR) continue;
            fprintf(stderr, "write: %s\n", strerror(errno));
            close(fd);
            return 1;
        }
        if (n == 0) {
            fprintf(stderr, "write: nulla előrehaladás\n");
            close(fd);
            return 1;
        }
        p += (size_t)n;
        left -= (size_t)n;
    }
    if (close(fd) != 0) {
        fprintf(stderr, "close: %s\n", strerror(errno));
        return 1;
    }
    return 0;
}

A man 2 open, man 2 write hivatkozások a Linux Programmer’s Manual megfelelő szakaszaira mutatnak; a fenti függvények pontos paraméterezését és hibakódjait a rendszer dokumentációja tartalmazza. A POSIX szabvány egyes részei – például a valós idejű kiterjesztések, az aszinkron I/O vagy a folyamatütemezési opciók – opcionálisak, ezért a hordozható kódnak ellenőriznie kell az adott opciós makró értékét (_POSIX_ASYNCHRONOUS_IO, _POSIX_TIMERS stb.): −1 esetén nem támogatott, 0 esetén a sysconf(_SC_ASYNCHRONOUS_IO) dönt futásidőben, pozitív érték esetén támogatott.

A POSIX erőssége a széles körű elterjedtség és a stabil szemantika. Korlátai közé tartozik, hogy nem fed le minden modern kernelképességet; a Linux specifikus epoll, signalfd, timerfd vagy io_uring interfészek már platformfüggő kódréteget igényelnek. Emellett a POSIX implementációk között is vannak eltérések – például a fájlzárolás szemantikája vagy a szignálok kézbesítési sorrendje –, ezért a „POSIX-kompatibilis” címke nem garantálja a bitre azonos viselkedést.

6.4.3 3. Win32 API: a Windows natív felülete

A Windows NT családban a kernel és a felhasználói tér közötti határ másképp épül fel. A natív rendszerhívások az ntdll.dll-en keresztül érhetők el, de a dokumentált, stabil programozási felületet a Win32 API (más néven Windows API) adja. Ez a felület a kernel32.dll, user32.dll, advapi32.dll és más rendszer-DLL-ekben található, és a C nyelvű fejlécek (windows.h) segítségével érhető el.

A Win32 API alapvető absztrakciója a handle: egy átlátszatlan, pointer méretű azonosító (HANDLE, a Win32 fejlécekben void *-ként definiálva), amely egy kernel-objektumra – fájlra, folyamatra, szálra, eseményre, mutexre – hivatkozik. A handle-t nem szabad int-té alakítani vagy 32 bitre csonkolni: 64 bites Windowson ezzel a pointer felső bitjei elvesznének. A handle-t a megfelelő Create* vagy Open* függvény adja vissza, és a CloseHandle szabadítja fel. A hibaérték nem egységes: a fájlműveleteknél INVALID_HANDLE_VALUE (azaz (HANDLE)-1), sok más Create* függvénynél NULL. A fájlkezelés tipikus függvényei: CreateFile, ReadFile, WriteFile, SetFilePointer, FlushFileBuffers. Példa ugyanarra a fájlíró műveletre:

#include <windows.h>
#include <stdio.h>
#include <string.h>

int main(void) {
    /* A C:\Temp létezése nem garantált; a saját temp könyvtárat kérdezzük le. */
    char dir[MAX_PATH];
    char path[MAX_PATH];
    DWORD n = GetTempPathA(MAX_PATH, dir);
    if (n == 0 || n >= MAX_PATH) {
        DWORD err = GetLastError();
        fprintf(stderr, "GetTempPathA failed: %lu\n", (unsigned long)err);
        return 1;
    }
    if (snprintf(path, sizeof path, "%shello-win32.txt", dir) >= (int)sizeof path) {
        fprintf(stderr, "path too long\n");
        return 1;
    }

    HANDLE h = CreateFileA(path,
                           GENERIC_WRITE,
                           0,                  /* nincs megosztás */
                           NULL,               /* alap biztonsági leíró */
                           CREATE_ALWAYS,
                           FILE_ATTRIBUTE_NORMAL,
                           NULL);
    if (h == INVALID_HANDLE_VALUE) {
        DWORD err = GetLastError();   /* azonnal, más API-hívás előtt */
        fprintf(stderr, "CreateFileA failed: %lu\n", (unsigned long)err);
        return 1;
    }

    const char *msg = "hello from Win32\n";
    DWORD total = (DWORD)strlen(msg);
    DWORD written = 0;
    while (written < total) {
        DWORD chunk = 0;
        if (!WriteFile(h, msg + written, total - written, &chunk, NULL)) {
            DWORD err = GetLastError();
            fprintf(stderr, "WriteFile failed: %lu\n", (unsigned long)err);
            CloseHandle(h);
            return 1;
        }
        if (chunk == 0) {
            fprintf(stderr, "WriteFile: nulla előrehaladás\n");
            CloseHandle(h);
            return 1;
        }
        written += chunk;
    }

    if (!CloseHandle(h)) {
        DWORD err = GetLastError();
        fprintf(stderr, "CloseHandle failed: %lu\n", (unsigned long)err);
        return 1;
    }
    return 0;
}

A Win32 hibakezelés eltér a POSIX-tól, és önmagában sem egységes: sok függvény BOOL-lal tér vissza (TRUE/FALSE), mások HANDLE, DWORD, LONG vagy HRESULT értéket adnak. A GetLastError() csak akkor értelmezhető, ha a függvény dokumentációja szerint hiba esetén beállítja; sikeres hívás után nem hordoz jelentést. A hibakódot közvetlenül a sikertelen hívás után kell kiolvasni, mert egy közbeiktatott Win32-hívás felülírhatja. A DWORD hibakódot a FormatMessage funkcióval alakíthatjuk szöveggé. A CreateFileA dokumentált hibaértéke például INVALID_HANDLE_VALUE, nem NULL.

A Windows API szoros kapcsolatban van a Unicode támogatással: a legtöbb szöveges függvénynek létezik A (ANSI, azaz a rendszer aktuális kódlapja szerinti) és W (wide, UTF-16) változata. A CreateFile alias például a UNICODE makrótól függően oldódik CreateFileW-re vagy CreateFileA-ra. A _UNICODE makró ezzel szemben a C futásidejű könyvtár (CRT) széles karakteres függvényeit, például a _tcs* családot vezérli; a két makró nem azonos, bár a Visual Studio és a MinGW buildek általában együtt definiálják őket (-DUNICODE -D_UNICODE). A modern Windows rendszerek belsőleg UTF-16-ot használnak, ezért új kódban a W változatok előnyben részesítendők; a CreateFileA az aktuális ANSI kódlap szerint értelmezi a nevet.

A Win32 API előnye a stabilitás: a Microsoft komoly kompatibilitási garanciákat vállal, a dokumentált függvények viselkedése évtizedeken át megmarad. Hátránya viszont a platformkötöttség: a Win32 kód nem fordul le más operációs rendszeren natívan, és a szemantika – például a fájlleírók öröklése, a szignálkezelés, a folyamatindítás – jelentősen eltér a Unix-modelltől.

6.4.4 4. .NET és kompatibilitási rétegek

A modern, keresztplatformos fejlesztés gyakran nem közvetlenül a natív API-kat használja, hanem egy magasabb szintű keretrendszert. A .NET (korábban .NET Core, a páros főverziók – például .NET 8, .NET 10 – hosszú távú támogatásúak (LTS), a páratlanok rövid támogatásúak (STS); a támogatott verziót mindig a hivatalos kiadási jegyzékből kell ellenőrizni, az ellenőrzés dátumával) egy managed futásidejű környezetet ad, amely a Base Class Library-n (BCL) keresztül egységes absztrakciót kínál a fájlkezelésre, hálózatra, szálakra és sok más területre. A System.IO.File.WriteAllText hívás ugyanazt a műveletet végzi el Linuxon, Windowson és macOS-en, a mögöttes natív hívást a .NET runtime fordítja le a megfelelő platform API-ra.

A .NET lehetőséget ad a natív kód elérésére is a Platform Invoke (P/Invoke) mechanizmussal. Ilyenkor a fejlesztő explicit módon deklarálja a külső függvényt és a hívási konvenciót:

using System;
using System.IO;
using System.Runtime.InteropServices;

class Program
{
    [DllImport("libc", SetLastError = true)]
    private static extern int getpid();

    static void Main()
    {
        string path = Path.Combine(Path.GetTempPath(), "hello-dotnet.txt");
        File.WriteAllText(path, "hello from .NET\n");
        Console.WriteLine($"pid={getpid()}");
    }
}

A P/Invoke erőteljes, de megtöri a platformfüggetlenséget: a libc elnevezés Linuxon libc.so.6, macOS-en libSystem.B.dylib, Windowson pedig nem is létezik ilyen függvény. Ezért a valóban hordozható .NET kód a BCL-re támaszkodik, és csak jól elkülönített modulokban használ P/Invoke-ot.

A kompatibilitási rétegek célja, hogy az egyik platform programjait egy másik platformon futtassák. A legismertebbek:

Réteg Működés Tipikus használat Korlátozás
Cygwin POSIX API-t biztosító DLL Windows felett, a POSIX hívásokat Win32-re fordítja Unix eszközök futtatása Windowson Lassabb, a fájlrendszer-szemantika eltér
MSYS2 Cygwin alapú, csomagkezelővel ellátott környezet Fordítási környezet Windowson Hasonló korlátok
Wine Win32 API implementáció Unix-szerű rendszereken Windows programok futtatása Linuxon Nem minden API tökéletes, a teljesítmény változó

A kompatibilitási rétegek hasznosak fejlesztéshez és migrációhoz, de nem helyettesítik a natív tesztelést. Egy hordozhatósági mátrixban a rétegek eredményeit külön kell jelölni, mert a szimulált környezetben mért értékek nem feltétlenül azonosak a natív rendszeren kapott értékekkel.

6.4.5 5. Absztrakció és feltételes fordítás

A C nyelvű rendszerprogramozásban a hordozhatóság klasszikus eszköze a feltételes fordítás. A preprocesszor #ifdef, #if defined direktíváival a forráskód különböző részeit fordíthatjuk platformtól függően. A legegyszerűbb minta egy közös interfész, amely mögött platformonként eltérő implementáció áll.

Tegyük fel, hogy egy portable_write_file függvényt akarunk, amely adott útvonalon létrehoz egy fájlt, és kiír egy bájtsorozatot. A közös fejléc (portable_file.h) így nézhet ki:

#ifndef PORTABLE_FILE_H
#define PORTABLE_FILE_H

#include <stddef.h>

/* Mindkét függvény: 0 siker, -1 hiba. Hiba esetén a platform hibakódja
   (POSIX: errno, Windows: GetLastError) a visszatérés pillanatában
   érvényes; a függvény a takarítás során megőrzi.
   A portable_read_file *len bemenete a puffer mérete, kimenete a
   beolvasott bájtok száma; a fájl ennél hosszabb is lehet. */
int portable_write_file(const char *path, const void *data, size_t len);
int portable_read_file(const char *path, void *buf, size_t *len);

#endif

A POSIX implementáció (portable_file_posix.c):

#define _POSIX_C_SOURCE 200809L
#include "portable_file.h"
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <limits.h>

int portable_write_file(const char *path, const void *data, size_t len) {
    if (path == NULL || (data == NULL && len != 0)) {
        errno = EINVAL;
        return -1;
    }
    int fd = open(path, O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (fd < 0) return -1;

    const unsigned char *p = (const unsigned char *)data;
    size_t left = len;
    while (left > 0) {
        size_t chunk = left > (size_t)SSIZE_MAX ? (size_t)SSIZE_MAX : left;
        ssize_t n = write(fd, p, chunk);
        if (n < 0) {
            if (errno == EINTR) continue;
            int saved = errno;
            (void)close(fd);
            errno = saved;
            return -1;
        }
        if (n == 0) {
            /* Nulla előrehaladás: nem lehet végtelen ciklusba kerülni. */
            (void)close(fd);
            errno = EIO;
            return -1;
        }
        p += (size_t)n;
        left -= (size_t)n;
    }

    if (close(fd) != 0) return -1;   /* errno a close-tól származik */
    return 0;
}

A Windows implementáció (portable_file_win.c):

#include "portable_file.h"
#include <windows.h>

int portable_write_file(const char *path, const void *data, size_t len) {
    if (path == NULL || (data == NULL && len != 0)) {
        SetLastError(ERROR_INVALID_PARAMETER);
        return -1;
    }
    HANDLE h = CreateFileA(path, GENERIC_WRITE, 0, NULL,
                           CREATE_ALWAYS, FILE_ATTRIBUTE_NORMAL, NULL);
    if (h == INVALID_HANDLE_VALUE) return -1;

    const unsigned char *p = (const unsigned char *)data;
    size_t left = len;
    while (left > 0) {
        /* A WriteFile egy hívásban legfeljebb 0x7FFFFFFF bájtot fogad el. */
        DWORD chunk = left > 0x7FFFFFFFu ? 0x7FFFFFFFu : (DWORD)left;
        DWORD written = 0;
        if (!WriteFile(h, p, chunk, &written, NULL)) {
            DWORD saved = GetLastError();
            (void)CloseHandle(h);
            SetLastError(saved);
            return -1;
        }
        if (written == 0) {
            (void)CloseHandle(h);
            SetLastError(ERROR_WRITE_FAULT);
            return -1;
        }
        p += written;
        left -= written;
    }

    if (!CloseHandle(h)) return -1;   /* GetLastError a CloseHandle-tól */
    return 0;
}

A build rendszer (például CMake) választja ki a megfelelő forrásfájlt:

cmake_minimum_required(VERSION 3.16)
project(portable_file C)

if(WIN32)
    add_library(portable_file STATIC portable_file_win.c)
else()
    add_library(portable_file STATIC portable_file_posix.c)
endif()
target_include_directories(portable_file PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})

A közös fejléc tartalmazza az interfészt; maga a megvalósítás a platformfüggő forrásfájlban van, ezért nincs szükség külön, üres portable_file.c fájlra. Így a platformfüggő kód fizikailag is elkülönül, és a hordozható részben nincs #ifdef-hegy.

A feltételes fordításnál gyakori hibák:

  • Elérési útvonalak eltérése: a Windows hagyományosan \ jelet és meghajtóbetűjelet használ, a Unix /-et. A Path.Combine (.NET) vagy a boost::filesystem használata csökkenti a hibát, de natív C kódban explicit konverzió kell.
  • Endianness: a hálózati bájtsorrend (htons, ntohl) platformfüggetlen, de a bináris fájlformátumoknál a gépi bájtsorrend csapdát jelent.
  • Hibakódok: a POSIX errno, a Windows GetLastError, a .NET kivételek – három külön modell. A platformrétegnek egységes hibakódot kell visszaadnia.
  • Szignálok és aszinkron események: a POSIX signal/sigaction és a Windows SetConsoleCtrlHandler eltérő; a valós idejű viselkedés is más.
  • Fájlleírók és handle-ök: a POSIX fájlleíró egy kis egész szám, a Windows handle átlátszatlan. A Windows CRT _open_osfhandle (HANDLE → fd) és _get_osfhandle (fd → HANDLE) függvényei hidat adnak, de az öröklési és lezárási szemantika eltérhet; az fdopen csak fájlleíróból készít FILE * adatfolyamot, nem handle-híd.
  • Szálak: a pthread_create és a CreateThread paraméterezése, a TLS kezelése, a megszakítási pontok mind különböznek.

A tiszta megoldás az, ha a platformfüggő részt egy vékony rétegbe zárjuk, és a felett egyetlen, jól tesztelt absztrakciót használunk. Ez a réteg lehet C függvénykönyvtár, C++ osztály, vagy akár egy IPC-alapú szolgáltatás, ha a platformok folyamatmodellje nagyon eltér.

6.4.6 6. Példa: hordozható fájlművelet

A fenti portable_write_file függvény már demonstrálja a minimális platformréteget. Bővítsük egy másik művelettel, a fájl tartalmának beolvasásával, hogy lássuk a hibakezelés és a pufferkezelés különbségeit.

A közös fejlécben szereplő beolvasó függvény:

int portable_read_file(const char *path, void *buf, size_t *len);

A len bemenetként a puffer méretét adja, kimenetként a ténylegesen beolvasott bájtok számát. A függvény legfeljebb *len bájtot olvas; ha a fájl hosszabb, a visszatérési érték 0, a kimeneti *len pedig megegyezik a kapacitással – a csonkolást a függvény nem jelzi külön. Ha a teljesség fontos, a hívó nagyobb puffert adjon (vagy előre kérdezze le a fájl méretét), és a *len == kapacitás esetet gyanúsként kezelje. A POSIX implementáció az open/read/close hármast használja:

#define _POSIX_C_SOURCE 200809L
#include "portable_file.h"
#include <fcntl.h>
#include <unistd.h>
#include <errno.h>
#include <limits.h>

int portable_read_file(const char *path, void *buf, size_t *len) {
    if (path == NULL || len == NULL || (buf == NULL && *len != 0)) {
        errno = EINVAL;
        return -1;
    }
    int fd = open(path, O_RDONLY);
    if (fd < 0) return -1;

    unsigned char *p = (unsigned char *)buf;
    size_t capacity = *len;
    size_t total = 0;
    while (total < capacity) {
        size_t chunk = capacity - total;
        if (chunk > (size_t)SSIZE_MAX) chunk = (size_t)SSIZE_MAX;
        ssize_t n = read(fd, p + total, chunk);
        if (n < 0) {
            if (errno == EINTR) continue;
            int saved = errno;
            (void)close(fd);
            errno = saved;
            return -1;
        }
        if (n == 0) break;   /* EOF */
        total += (size_t)n;
    }

    if (close(fd) != 0) return -1;   /* errno a close-tól származik */
    *len = total;
    return 0;
}

A Windows implementáció a CreateFileA/ReadFile/CloseHandle hármast használja. A ReadFile mérete DWORD, ezért a nagy pufferelést darabolni kell, és a rövid olvasást is kezelni kell:

#include "portable_file.h"
#include <windows.h>

int portable_read_file(const char *path, void *buf, size_t *len) {
    if (path == NULL || len == NULL || (buf == NULL && *len != 0)) {
        SetLastError(ERROR_INVALID_PARAMETER);
        return -1;
    }
    HANDLE h = CreateFileA(path, GENERIC_READ, FILE_SHARE_READ, NULL,
                           OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
    if (h == INVALID_HANDLE_VALUE) return -1;

    unsigned char *p = (unsigned char *)buf;
    size_t capacity = *len;
    size_t total = 0;
    while (total < capacity) {
        size_t left = capacity - total;
        DWORD chunk = left > 0x7FFFFFFFu ? 0x7FFFFFFFu : (DWORD)left;
        DWORD got = 0;
        if (!ReadFile(h, p + total, chunk, &got, NULL)) {
            DWORD saved = GetLastError();
            (void)CloseHandle(h);
            SetLastError(saved);
            return -1;
        }
        if (got == 0) break;   /* EOF */
        total += got;
    }

    if (!CloseHandle(h)) return -1;   /* GetLastError a CloseHandle-tól */
    *len = total;
    return 0;
}

A két implementáció csak a bezárásig ír, tartós tárolást nem garantál; ehhez POSIX-on fsync, Windowson FlushFileBuffers kellene. A példaprogram fájlneve test_portable.c, és a saját, egyedi temp könyvtárában dolgozik. A pontos tartalmat a visszaolvasás után hosszra és bájtokra is ellenőrzi:

#define _POSIX_C_SOURCE 200809L
#include "portable_file.h"
#include <stdio.h>
#include <string.h>
#include <stdlib.h>

#ifdef _WIN32
#include <windows.h>
#else
#include <unistd.h>
#endif

static int make_temp_dir(char *dir, size_t size) {
#ifdef _WIN32
    char base[MAX_PATH];
    char tmp[MAX_PATH];
    DWORD n = GetTempPathA(MAX_PATH, base);
    if (n == 0 || n >= MAX_PATH) return -1;
    if (GetTempFileNameA(base, "pft", 0, tmp) == 0) return -1;
    (void)DeleteFileA(tmp);
    if (!CreateDirectoryA(tmp, NULL)) return -1;
    if (strlen(tmp) + 1 > size) {
        (void)RemoveDirectoryA(tmp);
        return -1;
    }
    memcpy(dir, tmp, strlen(tmp) + 1);
    return 0;
#else
    const char *base = getenv("TMPDIR");
    if (base == NULL || *base == '\0') base = "/tmp";
    if (snprintf(dir, size, "%s/portable-test-XXXXXX", base) >= (int)size)
        return -1;
    return mkdtemp(dir) == NULL ? -1 : 0;
#endif
}

static int make_file_path(char *path, size_t size, const char *dir) {
#ifdef _WIN32
    /* A GetTempFileNameA-ból képzett könyvtárnév nem végződik \\-re. */
    return snprintf(path, size, "%s\\portable-test.bin", dir) >= (int)size ? -1 : 0;
#else
    return snprintf(path, size, "%s/portable-test.bin", dir) >= (int)size ? -1 : 0;
#endif
}

static void cleanup(const char *path, const char *dir) {
#ifdef _WIN32
    (void)DeleteFileA(path);
    (void)RemoveDirectoryA(dir);
#else
    (void)unlink(path);
    (void)rmdir(dir);
#endif
}

int main(void) {
    char dir[256];
    char path[512];
    const char *msg = "portable data\n";
    size_t msg_len = strlen(msg);

    path[0] = '\0';
    if (make_temp_dir(dir, sizeof dir) != 0) {
        fprintf(stderr, "temp dir failed\n");
        return 1;
    }
    if (make_file_path(path, sizeof path, dir) != 0) {
        fprintf(stderr, "path too long\n");
        cleanup(path, dir);
        return 1;
    }

    int rc = 1;
    char buf[64];
    size_t len = 0;

    if (portable_write_file(path, msg, msg_len) != 0) {
        fprintf(stderr, "write failed\n");
        goto out;
    }

    len = sizeof buf;
    if (portable_read_file(path, buf, &len) != 0) {
        fprintf(stderr, "read failed\n");
        goto out;
    }
    if (len != msg_len || memcmp(buf, msg, msg_len) != 0) {
        fprintf(stderr, "content mismatch: got %zu bytes\n", len);
        goto out;
    }
    printf("read %zu bytes, content OK: ", len);
    (void)fwrite(buf, 1, len, stdout);
    rc = 0;

out:
    cleanup(path, dir);
    return rc;
}

6.4.7 7. Labor: hordozhatósági mátrix készítése

A fejezet laborjának célja egy hordozhatósági mátrix előállítása, amely rögzíti, hogy egy kiválasztott API-művelet hogyan viselkedik különböző környezetekben. A mátrix nemcsak a sikerességet, hanem a visszatérési értéket, a hibakódot, a futási időt és a megjegyzéseket is tartalmazza.

6.4.8 7.1. Kiinduló állapot és konfiguráció

A labor a következő emulált környezeteket használja:

  • Linux natív: QEMU/KVM virtuális gép, 4 vCPU, 8 GiB RAM, kernel 6.1 LTS, glibc 2.37, build: GCC 12.2, -O2.
  • Windows natív: Windows Server 2022 VM, 4 vCPU, 8 GiB RAM, MSVC 19.3, -O2, x64.
  • WSL2: ugyanaz a Linux kernel, de Windows gazdán, 4 vCPU, 8 GiB RAM, glibc 2.35.
  • Wine: Wine 8.0, Linux gazdán, a Windows EXE futtatása.
  • Cygwin: Cygwin 3.4, a POSIX program futtatása Windows VM-en.
  • .NET: .NET 8.0 (LTS; támogatási ideje a kiadási jegyzék szerint ellenőrizendő, a labor naplójában a ténylegesen használt verzió és az ellenőrzés dátuma szerepeljen), Linux és Windows fölött.

A mérési módszer: minden környezetben egy shell script vagy batch fájl futtatja a tesztprogramot tízszer, és rögzíti a kimenetet, a visszatérési kódot és a time (Linux) vagy Measure-Command (PowerShell) által mért időt. A pontos parancsok a reprodukciós csomagban szerepelnek.

6.4.9 7.2. A tesztprogram

A tesztprogram három műveletet hajt végre:

  1. create_write: létrehoz egy fájlt, kiír 1 MiB adatot, bezárja.
  2. read_verify: megnyitja a fájlt, visszaolvassa, és ellenőrzi a tartalmat.
  3. delete: törli a fájlt.

A program C-ben készül el, két változatban: az egyik a POSIX API-t használja, a másik a Win32 API-t. A forráskód a portable_file könyvtárra épül, így mindkét implementáció ugyanazt a közös felületet valósítja meg. A .NET változat a BCL File osztályát használja.

6.4.11 7.4. Kiértékelés és tipikus hibák

A labor során gyakori csapdák:

  • Elérési út problémák: a Windows C:\Temp útvonalat vár, a Linux /tmp-et. Ha a kód nem használ platformfüggő útvonalválasztást, a teszt rossz könyvtárban próbálkozik.
  • Fájlmegosztási mód: a Win32 CreateFile harmadik paramétere a megosztási mód; ha 0-t adunk, más folyamat nem nyithatja a fájlt. A POSIX open alapértelmezetten megengedi a megosztást. Párhuzamos tesztnél emiatt a második megnyitás ERROR_SHARING_VIOLATION hibával meghiúsulhat.
  • Hibakód félreértelmezése: a POSIX errno értéke a hívás után azonnal érvényes, de egy következő könyvtári hívás felülírhatja. A Win32-ben a GetLastError hasonlóan azonnal hívandó.
  • Puffer típusa: a WriteFile DWORD méretet vár, a POSIX write size_t-t. 64 bites Windowson a size_t 64 bites, a DWORD 32 bites, ezért 4 GiB feletti méret közvetlen konverziónál csonkolódik; ezért kell a hívásokat darabolni (lásd a 6. példát).
  • Kompatibilitási réteg téves értékelése: Wine alatt a hibakódok és a teljesítmény eltérhet a natív Windowstól; ezt a mátrixban külön kell jelölni, nem szabad a natív eredménnyel összekeverni.

A labor eredménye a reprodukálható jegyzetfüzet (például Jupyter notebook vagy Markdown + parancsnaplók), amely tartalmazza a build parancsokat, a pontos konfigurációt, a mért és várt értékeket elkülönítve, valamint a következtetéseket. Az átadandó mátrix a fenti táblázathoz hasonló, de a cellákban a hibakódok és a mérési idők is szerepelnek.

6.4.12 8. Összefoglalás és önellenőrző kérdések

Ebben az alfejezetben áttekintettük a szabványos (POSIX) és platformspecifikus (Win32) interfészeket, a .NET absztrakciót, valamint a kompatibilitási rétegeket. Bemutattuk a feltételes fordításra épülő platformréteg mintáját, és egy hordozhatósági mátrix laborral demonstráltuk a gyakorlati ellenőrzés módszerét. A következő alfejezet (Folyamatmodell, PCB és állapotátmenetek) a folyamatmodellre és a folyamatvezérlő blokkra épít; a fork/exec modellt a Kontextusváltás, fork/exec és folyamatéletciklus tárgyalja (a CreateProcess összevetése ott csak említés szintjén szerepel).

Önellenőrző kérdések:

  1. Mi a különbség a POSIX errno és a Win32 GetLastError hibakezelési modellje között? Adj példát mindkettőre.
  2. Hogyan oldanád meg, hogy egy C program ugyanazt a műveletet (például könyvtárlistázást) Linuxon és Windowson is elvégezze anélkül, hogy a fő logika #ifdef-ekkel lenne tele?
  3. Melyik kompatibilitási réteget választanád egy Unix-szerű build pipeline Windowson való futtatásához, és miért? Milyen korlátokra kell figyelni?
  4. A hordozhatósági mátrixban miért kell a várt és a mért értéket külön oszlopban szerepeltetni? Milyen következménye van, ha ezt elmulasztjuk?

Válaszok röviden:

  1. POSIX: a hívás -1-et ad, az ok az errno-ban van (például open → ENOENT); Win32: a visszatérési érték típusa függvényenként eltér (INVALID_HANDLE_VALUE, FALSE, NULL), az ok a közvetlenül utána hívott GetLastError()-ból olvasható (például ERROR_FILE_NOT_FOUND).
  2. Közös fejléc, platformonkénti forrásfájl, és a változat kiválasztása a build-rendszerben (lásd 5. rész).
  3. MSYS2/Cygwin vagy WSL2; figyelni kell a fájlrendszer-, jogosultság- és teljesítménybeli eltérésekre.
  4. A várt érték a specifikációból, a mért a futásból származik; ha összevonjuk, az eltérés (hiba) nem látszik, és a mérés a várakozást igazolná vissza.

A labor kérdéseire adott válaszok a fejezet fogalmi része alapján ellenőrizhetők; a labor jegyzőkönyvében a mért értékeket a saját környezetben kell reprodukálni.
