6.2 Rendszerhívások, ABI és libc

A rendszerhívási interfész (syscall) az operációs rendszer magjának az a programozási felülete, amelyen keresztül a felhasználói térben futó programok a kernel szolgáltatásait igénybe vehetik. A hordozható programozási felület ezzel szemben gyakran egy felhasználói könyvtár, tipikusan a libc, amely a nyers rendszerhívásokat a programozó számára ismerős függvényhívásokká alakítja. Ebben a fejezetben a kettő közötti határt, az ABI-t, valamint a libc wrapper réteget vizsgáljuk.

Először tisztázzuk a fogalmakat. Az API (Application Programming Interface) forráskód szintű szerződés: megmondja, hogy egy függvény milyen paramétereket vár, milyen típusú értéket ad vissza, és milyen szemantikát garantál. Az ABI (Application Binary Interface) ezzel szemben bináris szintű szerződés: meghatározza, hogy a lefordított kód milyen regiszterekben adja át az argumentumokat, milyen utasítással vált privilegizált módba, hogyan jelzi a hibát, és milyen struktúra-elrendezést használ. A rendszerhívási interfész elsősorban ABI, míg a libc által nyújtott felület API. A hordozhatóság érdekében a programozó általában az API-t használja, a rendszer futás közben az ABI-t.

A kernel szolgáltatásainak elérése privilegizált átmenetet igényel, mert a kernel a védett, magasabb jogosultságú szinten fut. A Privilégiumszintek és átlépés a felhasználói tér és a kernel között alfejezetben tárgyaltuk a privilege szinteket és a trap/syscall mechanizmust. Ebben a fejezetben feltételezzük, hogy van egy ilyen átmenetünk; most arra koncentrálunk, hogy mi történik azután, hogy a vezérlés a kernelbe került.

6.2.1 A rendszerhívási interfész alapjai

A kernel belépési pontja egy úgynevezett syscall dispatcher, amely a rendszerhívási szám alapján kiválasztja a megfelelő kernel függvényt. A rendszerhívási szám egy egész szám, amely egyedi azonosítót ad minden egyes szolgáltatásnak. A számokat általában központi fejlécfájlban definiálják, és a kernel egy táblázatban tárolja a hívható függvények mutatóit. Az alábbi egyszerű példa egy minimalista kernelben mutatja a táblázatot és a dispatchert:

/* A rendszerhívási számok rögzítettek (közös ABI-fejléc) */
#define SYS_WRITE  1
#define SYS_EXIT   60
#define SYS_NOOP   3      /* mérési célra: azonnal 0-val tér vissza */

/* A belső implementációk típushelyesek és kevés argumentumot vesznek át. */
static long sys_write(unsigned int fd, const char __user *buf, size_t count);
static long sys_exit(int status);
static long sys_noop(void);

/* A táblázat egységes adaptereket tárol: mind a hat szót átveszi, és a
 * belső implementációt a megfelelő típusokkal hívja. */
typedef long (*syscall_fn)(unsigned long, unsigned long, unsigned long,
                           unsigned long, unsigned long, unsigned long);

static long sys_write_adapter(unsigned long a0, unsigned long a1, unsigned long a2,
                              unsigned long a3, unsigned long a4, unsigned long a5)
{
    (void)a3; (void)a4; (void)a5;   /* a write csak három argumentumot használ */
    return sys_write((unsigned int)a0, (const char __user *)a1, (size_t)a2);
}

static long sys_exit_adapter(unsigned long a0, unsigned long a1, unsigned long a2,
                             unsigned long a3, unsigned long a4, unsigned long a5)
{
    (void)a1; (void)a2; (void)a3; (void)a4; (void)a5;
    return sys_exit((int)a0);
}

static long sys_noop_adapter(unsigned long a0, unsigned long a1, unsigned long a2,
                             unsigned long a3, unsigned long a4, unsigned long a5)
{
    (void)a0; (void)a1; (void)a2; (void)a3; (void)a4; (void)a5;
    return sys_noop();
}

static syscall_fn sys_call_table[256] = {
    [SYS_WRITE] = sys_write_adapter,
    [SYS_NOOP]  = sys_noop_adapter,
    [SYS_EXIT]  = sys_exit_adapter,
};

long handle_syscall(struct syscall_frame *f)
{
    unsigned long nr = f->rax;           /* a rendszerhívás száma a keretből */

    if (nr >= ARRAY_SIZE(sys_call_table))
        return -ENOSYS;
    if (sys_call_table[nr] == NULL)
        return -ENOSYS;
    return sys_call_table[nr](f->rdi, f->rsi, f->rdx, f->r10, f->r8, f->r9);
}

Az adapterekre azért van szükség, mert a táblázatnak egységes, hat unsigned long paraméteres aláírásra van szüksége, a belső implementáció viszont típushelyes, három argumentumos (unsigned int fd, const char __user *buf, size_t count). Ha a táblázatba közvetlenül a három paraméteres sys_write kerülne, a fordító típusütközést jelezne, és a függvénymutató más aláíráson át történő meghívása a C szabvány szerint nem definiált viselkedés (a hívási konvenció eltérő regiszterhasználata miatt a gyakorlatban is hibás eredményt adhat). Az adapter a hat szót fogadja, elveti a nem használtakat, és a megfelelő típusokra konvertálva hívja a belső függvényt.

A felhasználói regiszterszerződés azonos az előző alfejezetével; a kernelen belül a belépési pont a keret mutatóját adja át, a diszpécser abból olvassa a számot és az argumentumokat, a visszatérési értéket pedig a belépési pont a keret rax mezőjébe írja. A példa C, szemléltetés. A -ENOSYS egy negatív hibakód; a kernel oldalán a hibákat negatív errno értékekkel szokás jelezni. Ez fontos eltérés a libc API-tól: a write() függvény hiba esetén -1-et ad vissza, és a hibakódot a errno globális (valójában szálhoz kötött) változóba írja, míg a kernel közvetlenül a negatív hibakódot adja vissza. A libc wrapper feladata ezt a konvenciót összekötni.

Nézzük az argumentumátadást. A felhasználói térből a kernelbe történő átmenetkor az argumentumok nem a szokásos függvényhívási konvenció szerint utaznak, hanem a syscall ABI szerint. Az x86-64 Linuxon például a rendszerhívási számot a rax regiszterben, az argumentumokat pedig a rdi, rsi, rdx, r10, r8, r9 regiszterekben adják át. A visszatérési érték a rax regiszterben érkezik. Más architektúrák eltérnek, de a lényeg ugyanaz: a hívó és a hívott oldal között pontos, bináris szinten rögzített szerződés van. A libc wrapper elrejti ezt a részletet; a programozó a write() függvényt hívja, a wrapper pedig a megfelelő regiszterekbe tölti az értékeket, kiadja a syscall utasítást, majd feldolgozza a visszatérést. A következő pszeudokód a write wrapper működését mutatja:

/* Nyers ABI-hívás, pontosan három argumentummal (x86-64 `syscall` utasítás).
 * Visszatérési szerződés: a `rax` nyers értéke, átalakítás nélkül:
 *   >= 0            : siker, az érték a szolgáltatás eredménye;
 *   [-4095, -1]     : hiba, az érték maga a -errno;
 *   egyéb negatív   : a kernel nem ad ilyet, a hívó nem értelmezheti eredményként.
 * Az errno-t ez a függvény NEM állítja be. */
static inline long raw_syscall3(long nr, long a0, long a1, long a2);

/* Wrapper a nyers hívás fölött: ez végzi az errno-konverziót. */
ssize_t my_write(int fd, const void *buf, size_t count)
{
    long ret = raw_syscall3(SYS_WRITE, (long)fd, (long)buf, (long)count);

    if (ret < 0) {
        errno = (int)-ret;
        return -1;
    }
    return (ssize_t)ret;
}

Itt a raw_syscall3 egy alacsony szintű függvény vagy makró, amely kiadja a tényleges trap utasítást és változatlanul visszaadja a regiszter értékét. A hibakezelés kulcsa a negatív visszatérési érték felismerése. A kernel általában a hibakódok egy kis tartományát használja (Linuxon -4095 és -1 között), így a negatív érték egyúttal hibát is jelent. A ret < 0 ellenőrzés a write-nál megfelelő, de általánosan nem: egyes rendszerhívások sikeres eredménye előjelesen negatív lehet (32 bites rendszeren az mmap 0x80000000 fölötti címe, a ptrace(PTRACE_PEEKDATA) adatszava). Ezért a glibc csak a [-4095, -1] tartományt tekinti hibának ((unsigned long) ret > -4096UL, glibc: INTERNAL_SYSCALL_ERROR_P; a kernelben ugyanezt a tartományt az IS_ERR_VALUE makró jelöli; a pontos nevek ellenőrzendők). Általános wrapperben tehát: if ((unsigned long)ret > -4096UL).

A libc által biztosított, dokumentált syscall(long number, ...) függvény ettől eltérő szerződésű: a variadikus argumentumlista mellett maga elvégzi a hibaátalakítást, azaz hiba esetén -1-et ad vissza, és az errno-t is beállítja. Ezért a syscall() eredményén még egyszer elvégezni az errno = -ret konverziót hiba: a második átalakítás a már beállított errno-t felülírná egy értelmetlen értékkel. A helyes használat:

/* A libc syscall(2) már -1/errno konvenciót ad: NEM alakítjuk tovább. */
static pid_t getpid_via_libc(void)
{
    long n = syscall(SYS_getpid);      /* variadikus, dokumentált libc-hívás */

    if (n == -1) {
        perror("getpid");              /* az errno itt már a valódi hiba */
        return -1;
    }
    return (pid_t)n;
}

A mutatóargumentumok külön figyelmet érdemelnek. A felhasználói program által átadott címek a felhasználói címtérbe mutatnak. A kernel nem dereferálhatja ezeket közvetlenül, mert (1) a kernel más címtérrel futhat, (2) a mutató érvénytelen lehet, ami kernel oops-hoz vezet, (3) a felhasználó megpróbálhat kernel memóriát olvasni. Ezért a kernelnek minden felhasználói mutatót ellenőriznie kell, és speciális másoló függvényekkel kell adatot mozgatnia a két tér között. A Linuxon ezek a copy_from_user és copy_to_user függvények. Az alábbi sys_write vázlat mutatja a helyes mintát:

#define CONSOLE_FD 1   /* a minimális kernelben egyetlen konzol van */

long sys_write(unsigned int fd, const char __user *buf, size_t count)
{
    char kbuf[128];
    size_t to_copy, done = 0;

    if (fd != CONSOLE_FD)
        return -EBADF;                  /* csak a konzol fd-je érvényes */
    if (count == 0)
        return 0;

    to_copy = min(count, sizeof(kbuf));
    if (copy_from_user(kbuf, buf, to_copy) != 0)
        return -EFAULT;

    /* A sikerérték a konzolmeghajtó által TÉNYLEGESEN kiírt bájtok száma,
     * nem a kért (to_copy) mennyiség. */
    while (done < to_copy) {
        long w = console_write(kbuf + done, to_copy - done);

        if (w < 0)
            return done > 0 ? (long)done : w;   /* rövid írás vagy hiba */
        if (w == 0)
            break;
        done += (size_t)w;
    }
    return (long)done;
}

Itt a __user annotáció dokumentálja, hogy a mutató felhasználói térből származik, és a copy_from_user végzi az ellenőrzést és másolást. A példa leegyszerűsített, de rávilágít a legfontosabb biztonsági szempontra. Két további részlet is lényeges: a fd ellenőrzése nélkül a hívó bármely fájlleíró-számmal írhatna a konzolra, ami a minimális kernelben hibás szerződés; a console_write visszatérési értékét pedig fel kell használni, mert a konzolmeghajtó rövidebb írást is végezhet, és a hívó csak a ténylegesen kiírt bájtok számából tud a maradékról.

6.2.2 ABI-stabilitás és verziózás

A rendszerhívási szám és a táblázat stabilitása az ABI-stabilitás sarokköve. Ha egyszer egy rendszerhívási számot publikáltak, a bináris kompatibilitás érdekében nem lehet újra felhasználni más célra, még akkor sem, ha az eredeti syscallt elavultnak nyilvánították. A Linux kernel különösen szigorú ebben: a felhasználói térbe exportált syscall ABI örök érvényű. Új szolgáltatásokhoz új rendszerhívási számokat vezetnek be, a régiek pedig megmaradnak. Ha egy struktúra mérete megváltozik, akkor vagy új syscallt hoznak létre (például stat → statx), vagy a struktúrát méretmezővel verziózzák (clone3, openat2: a hívó átadja a struktúra méretét, a kernel ebből tudja, melyik változatot kapta). A Windows esetében a helyzet kissé más: a hivatalos hordozható felület a Win32 API, amely mögött a natív rendszerhívási réteg (ntdll) nem garantáltan stabil; a Microsoft fenntartja a jogot a natív interfész megváltoztatására, ezért a programozóknak a dokumentált Win32 függvényeket kell használniuk.

A verziózás és a szimbólumkezelés a libc oldalán is megjelenik. A C könyvtár dinamikus linkelés esetén szimbólumverziókat használhat, hogy a régebbi binárisok továbbra is a nekik megfelelő implementációt kapják. A glibc például az x86-64 architektúrán a legkorábbi, az x86-64 porttal bevezetett szimbólumokat a GLIBC_2.2.5 verziócsomópontba teszi; a readelf --version-info kimenetében ilyen bejegyzés látható például memcpy@GLIBC_2.2.5 formában. Ez konkrét szimbólum- és architektúrapélda, nem általános szabály: más architektúrán – és más libc-nél, például a musl-nál – más verziózási séma érvényes, a verziószám önmagában nem hordozható. Ha egy függvény viselkedése megváltozik, a régi verzió megmarad a régi szimbólum mögött, az új pedig új verziót kap. Ez lehetővé teszi, hogy ugyanaz a könyvtár egyszerre szolgálja ki a régi és az új programokat.

Egy másik fontos aspektus az ABI és az API közötti különbség a gyakorlatban: a forráskód újrafordítása az API-t használja, a lefordított bináris futtatása az ABI-t. Ha a programozó renameat2-t hív, a glibc-ben ennek deklarációja a stdio.h fejlécben van, és csak akkor látszik, ha a _GNU_SOURCE feature-test makró a fordítás előtt definiálva van. A _GNU_SOURCE-t C-ben a fordító alapértelmezésben nem definiálja (sem -std=c11, sem az alapértelmezett gnu17 mellett), ezért a definíciót a legelső #include elé kell tenni, vagy a fordítónak -D_GNU_SOURCE kapcsolót kell adni. A deklaráció birtokában a fordító egy hívást generál a libc renameat2 függvényéhez, amely viszont a megfelelő syscallt hívja. A bináris azonban nem tartalmazza a syscall számot, csak a libc függvényhívást; a syscall szám a libc-n belül van. Ezért a libc frissítése önmagában megváltoztathatja a syscall hívást anélkül, hogy a programot újra kellene fordítani. Ez a rétegelt tervezés teszi lehetővé, hogy a kernel ABI-ja és a libc API-ja egymástól függetlenül fejlődjön.

A rendszerhívási számok és a kapcsolódó makrók általában a felhasználói tér számára is elérhetők. A Linux az __NR_write, __NR_exit nevű makrókat definiálja az asm/unistd.h fejlécben, amelyeket a programok a syscall() függvénnyel együtt használhatnak. Ez ugyan nem hordozható, de lehetővé teszi, hogy a fejlesztő közvetlenül a syscall ABI-t célozza. A hordozható programok ehelyett a libc magas szintű függvényeit használják, és a libc felel a megfelelő syscall kiválasztásáért. A glibc Linuxon a fork()-ot nem a clone3-ra, hanem a clone syscallra képezi le az arch_fork útvonalon, fork szemantikával: a gyermek a hívó címterét örökli és a hívó egyetlen szálát folytatja, a többi szál nem másolódik. A programozó továbbra is a POSIX fork() API-t hívja; az, hogy mögötte melyik syscall áll, a libc és a platform belső döntése, és verzióról verzióra változhat.

6.2.3 A libc szerepe

A libc (C standard könyvtár) több, mint egyszerű syscall-gyűjtemény. Feladatai közé tartozik:

  • Wrapper függvények biztosítása: minden POSIX vagy C standard függvényhez, amely mögött syscall áll, egy olyan függvényt nyújt, amely kezeli a regisztereket, az errno-t és a visszatérési konvenciót.
  • errno kezelése: a hibaállapotot szálanként tárolja (thread-local storage, TLS), így a párhuzamos programokban nem keverednek össze a hibakódok.
  • Hordozhatóság: ugyanaz a C forrás több operációs rendszeren is lefordul, mert a libc elrejti a rendszerspecifikus hívásokat.
  • Dinamikus linkelés: a megosztott könyvtárak betöltését és a szimbólumfeloldást a dinamikus linker (például ld-linux-x86-64.so.2) végzi, amely maga is a libc része.
  • Magasabb szintű absztrakciók: a stdio pufferezése, a malloc memóriakezelő, a pthread szálkezelés mind a libc részei, és ezek jelentősen túlmutatnak a puszta syscall wrappereken.

A libc syscall(long number, ...) függvénye egy speciális eszköz: lehetővé teszi tetszőleges syscall közvetlen meghívását a szám és az argumentumok megadásával, és – ahogy fentebb láttuk – a -1/errno konvenciót is ő állítja elő. Nem hordozható, de hasznos lehet kernel fejlesztésénél vagy olyan új syscallok tesztelésekor, amelyekhez még nincs libc wrapper.

Az alábbi példa ezzel nem azonos: ez egy saját, nyers hatargumentumos belépő (raw_syscall6), amely a kernel ABI szerződését adja vissza, és nem állítja be az errno-t. A két függvényt érdemes megkülönböztetni, mert a libc syscall() nevének újradefiniálása a fejléc deklarációjával ütközne:

/* Nyers hatargumentumos belépő Linux x86-64-re. A visszatérési érték a
 * kernel nyers eredménye (>= 0 siker, [-4095, -1] esetén -errno);
 * az errno-t NEM állítja be, azt a hívó wrappernek kell kezelnie. */
long raw_syscall6(long nr, long a0, long a1, long a2, long a3, long a4, long a5)
{
    register long rax asm("rax") = nr;
    register long rdi asm("rdi") = a0;
    register long rsi asm("rsi") = a1;
    register long rdx asm("rdx") = a2;
    register long r10 asm("r10") = a3;
    register long r8  asm("r8")  = a4;
    register long r9  asm("r9")  = a5;
    asm volatile("syscall"
                 : "+r"(rax)
                 : "r"(rdi), "r"(rsi), "r"(rdx), "r"(r10), "r"(r8), "r"(r9)
                 : "rcx", "r11", "memory");
    return rax;
}

Ez a függvény erősen architektúra-függő, és csak szemléltetésre szolgál. A valódi glibc syscall() hasonló elven működik, de hordozhatóbb módon, a cél architektúrának megfelelően van lefordítva, és a nyers eredményt -1/errno alakra alakítja.

A libc wrapper generálása gyakran makrókkal történik, hogy elkerüljék az ismétlést. Például a Linux kernelben a SYSCALL_DEFINE makrók állítják elő a syscall bejegyzéseket, a libc oldalán pedig a weak_alias és a libc_hidden_def mechanizmusok segítenek a szimbólumok kezelésében. A hétköznapi fejlesztő számára azonban elegendő a deklarációk és a wrapper logika ismerete.

A statikus és dinamikus linkelés is érinti az ABI-t. Statikus linkelés esetén a libc kódja a végrehajtható fájlba kerül, így a futtatáshoz nincs szükség külső könyvtárra, de a bináris nagyobb, és a libc biztonsági frissítései nem érvényesülnek újrafordítás nélkül. Dinamikus linkelésnél a program a futás közben tölti be a megosztott libc-t, így a frissítések azonnal hatnak, de a binárisnak kompatibilisnek kell lennie a betöltött verzió ABI-jával. A szimbólumverziózás ezt a kompatibilitást hivatott biztosítani.

6.2.4 Labor: syscall-táblázat és libc-wrapperek vázlata

A labor célja egy egyszerű syscall-táblázat és libc-wrapperek vázlatának elkészítése egy emulált környezetben. A kiindulópont a Privilégiumszintek és átlépés a felhasználói tér és a kernel között alfejezetben bemutatott trap kezelő, amely már rendelkezik a felhasználói/kernel átmenettel. A minta pontosan azt a szerződést követi, amit a Privilégiumszintek és átlépés a felhasználói tér és a kernel között alfejezet rögzít: a rendszerhívás számát a rax, az argumentumokat a rdi, rsi, rdx, r10, r8, r9 regiszter adja át; a belépés a syscall utasítással, az IA32_LSTAR MSR-ben beállított címen történik; a visszatérési érték a rax-ben jön, hiba esetén -errno alakban. Ha a saját, a Privilégiumszintek alfejezet szerinti implementáció ettől eltér (más vektor, más regiszterkiosztás), előbb a közös abi.h-t kell összehangolni, különben a mérés értelmezhetetlen.

Környezet: QEMU x86-64, 1 virtuális CPU, 128 MiB RAM, freestanding C, GCC vagy Clang. A pontos verziókat (QEMU, GCC/Clang, binutils, grub-file) a reprodukciós jegyzőkönyvben rögzíteni kell. A boot mechanizmus adott (például a Bootloader, kernel betöltése és init alfejezet Multiboot2-laborjából), a labor a syscall rétegre koncentrál.

Bootprotokoll. A -kernel kapcsoló x86-on Linux bzImage-et, Multiboot 1 fejlécű 32 bites ELF-et (vagy a.out-kludge képet) és PVH ELF-et tölt be; Multiboot2-t és ELF64-et nem (a hibaüzenet és a viselkedés a használt QEMU-verzión ellenőrzendő). A minta kernel Multiboot 1 fejlécet állít elő, és a 64 bites linkelés után objcopy -O elf32-i386 build/kernel.elf build/kernel.bin alakítja 32 bites konténerré; a belépő kód 32 bites védett módban indul, és maga vált hosszú módba. Ezt a futtatás előtt ellenőrizni kell:

$ make clean && make
$ grub-file --is-x86-multiboot build/kernel.bin && echo multiboot-ok
$ readelf -h build/kernel.bin | grep Class     # várt: ELF32
$ qemu-system-x86_64 -cpu qemu64 -m 128M -nographic -no-reboot \
      -kernel build/kernel.bin

A grub-file sikere önmagában nem garantálja a -kernel sikerét (ELF64 képet a GRUB tölt, a QEMU -kernel nem). Ha az ELF32 konverzió nem megoldható, a megbízható út a GRUB-os ISO (grub-mkrescue, lásd a Bootloader, kernel betöltése és init alfejezet laborját), és a vendég arról bootol. A fenti parancsok mindegyike a gazdagépen fut, és csak a munkakönyvtárban lévő fájlokat írja.

Feladat: Implementáljuk a sys_write, sys_noop és sys_exit rendszerhívásokat, valamint az adaptereket használó dispatchert. Készítsünk felhasználói tesztprogramot, amely a libc wrapper vázlatot használja: my_write(), my_noop() és my_exit() függvényeket, amelyek a rendszerhívási ABI-t hívják, beállítják az errno-t, és a teszt kiírja a “hello syscall” üzenetet, majd 0 kóddal kilép.

A syscall táblázat és a dispatcher kódja megegyezhet a fenti példával. A nyers belépő és a wrapper vázlat a következő (a raw_syscall3 külön fordítási egységben van, hogy a unit teszt stubbal helyettesíthesse):

/* user/syscall_asm.c – x86-64-re specifikus nyers belépő, három argumentummal.
 * Visszatérési szerződés: a `rax` nyers értéke (>= 0 siker, [-4095, -1] hiba);
 * az errno-t NEM állítja be. */
#include "syslib.h"

long raw_syscall3(long nr, long a0, long a1, long a2)
{
    register long rax asm("rax") = nr;
    register long rdi asm("rdi") = a0;
    register long rsi asm("rsi") = a1;
    register long rdx asm("rdx") = a2;
    asm volatile("syscall"
                 : "+r"(rax)
                 : "r"(rdi), "r"(rsi), "r"(rdx)
                 : "rcx", "r11", "memory");
    return rax;
}

/* user/lib.c – a wrapper réteg: itt történik az errno-konverzió.
 * A syslib.h a freestanding környezet size_t/ssize_t típusait is deklarálja. */
#include "syslib.h"

int my_errno;                    /* az errno helyett: a gazdagépes unit teszt a hoszt libc errno-jával ne ütközzön */

ssize_t my_write(int fd, const void *buf, size_t count)
{
    long ret = raw_syscall3(SYS_WRITE, (long)fd, (long)buf, (long)count);

    if (ret < 0) {
        my_errno = (int)-ret;
        return -1;
    }
    return (ssize_t)ret;
}

long my_noop(void)
{
    long ret = raw_syscall3(SYS_NOOP, 0, 0, 0);

    if (ret < 0) {
        my_errno = (int)-ret;
        return -1;
    }
    return ret;
}

void my_exit(int status)
{
    raw_syscall3(SYS_EXIT, (long)status, 0, 0);
    __builtin_unreachable();      /* ide nem tér vissza */
}

Itt a raw_syscall3 inline assembly, x86-64-re specifikus. A wrapper pontosan a korábban leírt logikát követi: hívja a syscallt, ellenőrzi a negatív visszatérést, beállítja az errno-t. A minimális környezetben az errno helyett a my_errno globális változót használjuk (a syslib.h-ban extern int my_errno;), hogy a gazdagépes unit teszt a hoszt libc errno-jával ne ütközzön; valós libc-ben ez TLS-ben lévő errno. A test_lib.c minimális mintája: assert(my_write(1, "abc", 3) == -1 && my_errno == EBADF); a stub -EBADF beállítása mellett. A kód szemléltetés, nem éles rendszeren futtatandó.

Unit teszt (gazdagépen). A wrapper errno-konverziója kernel nélkül is ellenőrizhető: a tests/stub_syscall.c a raw_syscall3 helyett előre rögzített értékeket ad vissza, a user/lib.c-t pedig ezzel a stubbal linkeljük. A teszt így közönséges gazdagép-programként fut:

$ cc -std=c11 -Wall -Wextra -Werror -Iinclude -o build/test_lib \
      tests/test_lib.c user/lib.c tests/stub_syscall.c
$ ./build/test_lib

Integrációs próbák (vendégben). A tesztprogram a vendégben fut, és a sikeres írás mellett három izolált negatív esetet ellenőriz. Az alábbi táblázat ABI-oszlopait a futás előtt kell kitölteni – ez az előre rögzített szerződés –, és a futás csak azt ellenőrizheti; a várható értékeket utólag nem szabad a mért eredményhez igazítani.

Eset Hívás Várt kernel ABI-eredmény (rax) Várt felhasználói eredmény Várt errno
sikeres írás my_write(CONSOLE_FD, "hello", 5) 5 5 változatlan
érvénytelen rendszerhívási szám raw_syscall3(999, 0, 0, 0) -ENOSYS -1 (a wrapper konverziójával) ENOSYS

Az érvénytelen rendszerhívási számhoz nincs név szerinti wrapper, ezért ezt a nyers hívással kell kiváltani, és az eredményt a wrapperrel azonos konverziós függvénnyel kell -1/errno alakra hozni; a lib.c-ben ez long to_posix(long ret) { if ((unsigned long)ret > -4096UL) { my_errno = (int)-ret; return -1; } return ret; }, és a wrapperek ezt hívják; a táblázat ezt jelöli a „wrapper konverziójával” megjegyzéssel. A tiltott cím a kernel címtartományába esik (0xFFFF800000000000), ezért a copy_from_user tartomány-ellenőrzésének el kell utasítania; a konkrét tesztcímet a jegyzőkönyvben rögzíteni kell, és annak a felhasználói címtérben nem szabad leképezve lennie.

Mérés. A teljes syscall round-trip idejét sorosított időbélyeggel kell mérni, és a mérési alapot le kell vonni:

  1. Sorosítás. Az óraolvasást lfence előzi meg, és rdtscp zárja, mert a rdtsc önmagában nem sorosít: a processzor átrendezheti a körülötte lévő utasításokat, és a mérés pontatlan lesz. A mintavétel lfence; rdtsc a ciklus előtt, rdtscp; lfence utána.
  2. Bázisciklus. Mérd meg ugyanazt a ciklust üres törzzsel (csak a ciklusszámláló), és a mért értéket vond ki; így a ciklusvezérlés és a két óraolvasás költsége nem torzítja az eredményt.
  3. Bázis-syscall. Mérd meg a SYS_NOOP round-tripjét is, mert ez adja a tiszta belépés-visszatérés költségét; a write idejét ehhez viszonyítva is közöld.
  4. TCG virtuális idő. QEMU TCG módban a vendég rdtsc-je a virtuális órából származik, nem a hoszt CPU ciklusszámlálója, ezért az eredmény nem értelmezhető hoszt-CPU-ciklusként. A mérést TSC-egységben („TSC-lépés”) kell közölni (a „tick” szó a könyvben az időzítő-megszakítás periódusát jelenti). Időre váltani csak ismert órafrekvenciájú forrással lehet: a vendégben a PIT (1 193 182 Hz) vagy a HPET számlálóját olvasva, legalább 1 s-os intervallumon kalibrálva; TCG alatt ez is virtuális idő. A labor kernelében nincs clock_gettime. Csak azonos konfigurációjú futások hasonlíthatók össze.
  5. Ismétlés és napló. Sorozatonként 1 000 000 hívás, legalább öt sorozat; a mediánt és a szóródást (minimum–maximum) kell közölni. A napló rögzítse a hoszt CPU típusát és órajelét, a QEMU verzióját, az -accel módot (tcg vagy kvm), az -icount és -rtc clock= beállítást, a -cpu modellt, az -m értéket, a fordítási beállításokat (-O0, -O2) és a ciklusszámot.

A várt nagyságrendet előre nem adjuk meg: a mérési napló a saját, ebben a környezetben mért értéket rögzíti, és az eredményt mindig a reprodukciós körülményekkel együtt kell értelmezni.

Elvárt eredmény: A tesztprogram kiírja a “hello syscall” üzenetet, a négy integrációs eset a fenti táblázat szerint teljesül, és a program 0 kilépési kóddal fejeződik be. A napló tartalmazza a mért tickértékeket, a hibakódokat, valamint az esetleges eltéréseket az előre rögzített szerződéstől.

6.2.5 Tipikus hibák és helyes megoldások

A gyakorlat során az alábbi tipikus hibák fordulhatnak elő:

  1. Hibás rendszerhívási szám. Ha a wrapperben 1 helyett 0-t írunk, a dispatcher ENOSYS hibát ad, vagy rossz függvényt hív. A megoldás: a syscall számokat központi fejlécfájlban definiáljuk, és a wrapper is ugyanazt a definíciót használja.

  2. Elmaradt argumentum-ellenőrzés a kernel oldalán. Ha a sys_write közvetlenül dereferálja a felhasználói mutatót, a kernel összeomolhat. A helyes megoldás a copy_from_user használata, valamint a hossz és a célpuffer ellenőrzése.

  3. Az errno beállításának hiánya. Ha a wrapper nem írja be az errno-t, a hívó félrevezető hibakódot kap, vagy nem is tudja, hogy hiba történt. A wrappernek mindig be kell állítania az errno-t, mielőtt -1-et ad vissza.

  4. A visszatérési érték helytelen értelmezése. A kernel negatív hibakódot ad vissza, de ha a wrapper azt hiszi, hogy a -1 a hibajelzés, és nem a negatív hibakódot, akkor rossz lesz az errno. A helyes minta az, hogy a ret negatív értékét vizsgáljuk, és az abszolút értékét adjuk az errno-nak.

  5. Típushibák a hosszoknál. A size_t és ssize_t keverése, valamint a 32/64 bites regiszterek közötti eltérés hibás adatátvitelhez vezet. A wrappernek pontosan követnie kell a syscall ABI típusait.

  6. ABI-törés a struktúrákban. Ha egy syscall argumentumaként struktúrát adunk át, és a struktúra elrendezése megváltozik, a régi binárisok eltörnek. A megoldás a struktúrák verziózása vagy új syscall bevezetése.

A fejezet végére az olvasó képes lesz elmagyarázni a rendszerhívási interfész és a hordozható programozási felület közötti különbséget, felépíteni egy egyszerű syscall táblázatot, és megírni a megfelelő libc wrapper vázlatot. A következő alfejezet (Shell, init, daemonok és a userland felépítése) ezekre az alapokra épít, és bemutatja, hogyan épül fel a userland: a shell, az init folyamat és a daemonok.

6.2.6 Önellenőrző kérdések

  1. Mi a különbség az API és az ABI között? Miért fontos a különbség a rendszerhívásoknál?
  2. Miért ad vissza a kernel negatív hibakódot a libc -1 visszatérési értéke helyett?
  3. Hogyan biztosítja a libc wrapper az errno helyes beállítását?
  4. Mi történik, ha a felhasználói program érvénytelen mutatót ad át egy syscallban? Hogyan védekezik a kernel?
  5. Miért nem lehet egy publikált rendszerhívási számot újra felhasználni?

Megoldási vázlat (Rendszerhívások, ABI és libc): 1. Az API a forrásszintű felület (függvények, típusok), az ABI a bináris szintű (regiszterkiosztás, számok, struktúraelrendezés); a bináris az ABI-ra támaszkodik. 2. Mert a regiszterben egyetlen érték fér el: a kernel a hibát a [-4095, -1] tartományban, magát az -errno-t visszaadva jelzi, így nincs szükség szálankénti állapotra a kernel–felhasználó határon; a -1 + errno a libc API-konvenciója, a wrapper alakítja át. 3. A wrapper a nyers eredményt vizsgálja, és hiba esetén a szálhoz kötött errno-ba írja a -ret értéket, majd -1-et ad. 4. A kernel a felhasználói mutatót nem dereferálja közvetlenül: a copy_from_user/copy_to_user ellenőrzi a címtartományt és kezeli a laphibát, hiba esetén -EFAULT-ot ad. 5. Mert a bináris kompatibilitás megszűnne: a régi programok az adott számot a régi jelentéssel hívják.
