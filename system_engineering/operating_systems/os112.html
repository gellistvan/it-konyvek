29.3 VFS integráció és fájlleírók

A VFS-integráció akkor válik hasznos réteggé, amikor a fájlrendszer már nem a saját, belső hívásaival dolgozik, hanem beilleszkedik a rendszer közös, hierarchikus névterébe. Ebben a fejezetben azt vizsgáljuk meg, hogyan lehet egy egyszerű fájlrendszert csatlakoztatni a virtuális fájlrendszerhez (VFS), milyen adatszerkezetek és művelettáblák szükségesek ehhez, és miként kapcsolódik a mount, a dentry, az inode és a file object a folyamatok fájlleíró-táblájához. A cél nem egy teljes értékű kernel VFS felépítése, hanem egy ellenőrizhető, tanulható minimális minta, amelyen a fontos fogalmak mérhetők és reprodukálhatók.

29.3.1 1. Miért közös névtér?

A UNIX-szerű rendszerek egyik alapgondolata, hogy a felhasználói programok számára a tárolóeszközök nem külön betűjelekkel vagy külön API-val jelennek meg, hanem egyetlen hierarchikus fában. A merevlemez-partíció, az initrd, a hálózati fájlrendszer és a RAM-ban lévő ideiglenes tároló egyaránt ugyanazzal az open, read, write, close felülettel érhető el. A VFS ezt az egységesítést valósítja meg: a felső réteg egy közös rendszerhívás-felületet és közös adatszerkezeteket ad, az alsó réteg pedig az egyes fájlrendszerek specifikus műveleteit.

A réteges szerkezet a következőképpen ábrázolható:

felhasználói program
        |
      sys_open / sys_read / sys_write
        |
 +------+-------------------------+
 | VFS réteg: path feloldás, mount |
 | dentry, inode, file object      |
 +------+-------------------------+
        |
 +------+------------+------------+
 | memfs | ext4-szerű | ...       |
 | (RAM) | blokkfs    |            |
 +------+------------+------------+
        |
    blokk-eszköz driver (os111)

Jelmagyarázat: a függőleges vonal a hívás irányát (fentről lefelé), a keretek az alrendszerek határait jelölik. A VFS rétegnek nem szabad az alsó fájlrendszer belső lemezszerkezetéről tudnia.

29.3.2 2. A mount mint névtérkapcsoló

A mount művelet az a pillanat, amikor egy fájlrendszer gyökere bekerül a közös fába. A VFS ezért megkülönbözteti a fájlrendszer saját gyökerét (root dentry) és a beillesztési pontot (mountpoint dentry). A struct mount a kettő közötti kapcsolatot rögzíti. Egy egyszerűsített kernelbeli ábrázolás így nézhet ki:

struct mount {
    struct mount *next;
    struct dentry *mountpoint;   /* a közös fában lévő pont */
    struct dentry *root;         /* a csatolt fs gyökere */
    struct super_block *sb;      /* a csatolt fs szuperblokkja */
    unsigned int flags;
};

A mount folyamata lépésenként a következő:

  1. Ellenőrizzük, hogy a target útvonal létező könyvtárra mutat, és a dentry inode-ja valóban könyvtár.
  2. Az fstype alapján meghívjuk a fájlrendszer fill_super vagy mount metódusát, amely beolvassa a szuperblokkot, felépíti a gyökér-inode-ot és a root dentry-t.
  3. Lefoglalunk egy struct mount-ot, beállítjuk a mountpoint-ot és a root-ot.
  4. A mount-ot beillesztjük a processz mount-névterébe (egyszerű esetben egy globális listába).
  5. A path feloldás során a VFS ügyel arra, hogy ha a bejárás eléri a mountpoint-ot, átlépjen a hozzá tartozó root-ra.

Ezt a lépést egy szándékosan egyszerű függvényben így lehet összefoglalni:

int vfs_mount(const char *source, const char *target,
              const char *fstype, unsigned long flags)
{
    struct dentry *d = path_resolve(target);
    if (IS_ERR(d))
        return PTR_ERR(d);

    if (!S_ISDIR(d->d_inode->i_mode)) {
        dput(d);
        return -ENOTDIR;
    }

    struct file_system_type *fs = lookup_fs(fstype);
    if (!fs) {
        dput(d);
        return -ENODEV;
    }

    struct super_block *sb = fs->mount(source, flags);
    if (IS_ERR(sb)) {
        dput(d);
        return PTR_ERR(sb);
    }

    struct mount *mnt = kzalloc(sizeof(*mnt));
    if (!mnt) {
        sb->s_op->put_super(sb);
        dput(d);
        return -ENOMEM;
    }

    mnt->mountpoint = d;
    mnt->root = sb->s_root;
    mnt->sb = sb;
    mnt->flags = flags;

    mount_list_insert(mnt);
    return 0;
}

A példa adatszerkezetei szándékosan egyszerűsítettek; valós kernelben a mount névtér per processz, a lockolás finomabb, és a mount pontok referencia-számlálása is részletesebb. A lényeg az, hogy a source, target, fstype fogalmak már ebben a minimális modellben is szétválnak. A source lehet blokk-eszköz (/dev/vdb1) vagy virtuális forrás ("none" memfs esetén); a target mindig egy már létező könyvtár a közös fában.

A referencia-szerződés ebben a modellben is explicit: a path_resolve egy referenciát ad a hívónak, a vfs_mount ezt sikeres csatolás esetén átadja a struct mount-nak (mnt->mountpoint), hibaágon pedig dput-tal elengedi. A mnt->root a szuperblokk saját s_root dentry-je, amelyet a szuperblokk életciklusa tart életben; a mount leválasztásakor mindkét referencia felszabadul.

A mount pont alatti korábbi tartalom nem vész el, csak átmenetileg eltűnik a path feloldás elől. Ha a mount-ot leválasztjuk, az eredeti dentry-inode pár ismét láthatóvá válik. Ezt a tulajdonságot a VFS-nek úgy kell kezelnie, hogy a path bejárás közben minden komponensnél megvizsgálja, van-e aktív mount az adott dentry-n.

29.3.3 3. Dentry: a névtér komponense

A dentry (directory entry) a VFS memóriabeli névtér-eleme. Nem feltétlenül egyezik meg a lemezen tárolt könyvtárbejegyzéssel; a VFS dentry-ket gyorsítótárként is használ. Egy dentry jellemzően a következő mezőket tartalmazza:

struct qstr {
    const char *name;
    unsigned int len;
};

struct dentry {
    struct qstr d_name;
    struct inode *d_inode;
    struct dentry *d_parent;
    struct list_head d_hash;    /* a dentry cache hash-láncának eleme */
    atomic_t d_count;           /* hivatkozások száma */
};

A d_count referencia-számláló. A VFS szabály: amíg egy kód dentry-mutatót tart, a számlálót növelnie kell (dget), és ha már nincs szüksége rá, csökkentenie kell (dput). Ez megakadályozza, hogy a dentry-t felszabadítsuk, miközben egy másik útvonal-feloldás még használja. A d_parent a szülőre mutat, így a felfelé haladás és a relatív útvonalak is kezelhetők.

A dentry cache célja, hogy ugyanazon név feloldását ne kelljen minden open-nél a lemezen kezdeni. A VFS egy hash-táblában tárolja a (parent, name) párokat. A lookup nagyjából így működik:

struct dentry *d_lookup(struct dentry *parent, struct qstr *name)
{
    unsigned int hash = dentry_hash(parent, name) & (DHASH_SIZE - 1);
    struct dentry *d;

    list_for_each_entry(d, &dentry_hashtable[hash], d_hash) {
        if (d->d_parent == parent &&
            qstr_equal(&d->d_name, name)) {
            dget(d);
            return d;
        }
    }
    return NULL;
}

Ha nincs találat, a VFS a szülő inode lookup műveletét hívja, amely a fájlrendszer-specifikus könyvtárbeolvasást végzi. A lookup ABI: int lookup(struct inode *dir, struct dentry *child), ahol a child a path_resolve által lefoglalt (d_alloc), a szülőhöz kötött, elnevezett (d_name, d_parent), de a hash-be még be nem tett dentry; a fájlrendszer a megtalált inode-ot d_add(child, inode)-dal köti be a cache-be (d_add = d_instantiate + hash-be szúrás), hiány esetén d_add(child, NULL)-lal negatív dentry-t hoz létre. Negatív dentry-ket is érdemes cache-elni: ha egy név nem létezik, a negatív bejegyzés gyors ENOENT választ ad a következő keresésnél.

Az útvonal-feloldás (path_resolve) komponensenként halad. Az alábbi ábra a /mnt/demo.txt feloldását lépésenként mutatja, a kód utána következik.

/* A hívó egy referenciát kap vissza; ezt dput-tal köteles elengedni.
 * A függvény a kezdő dentry-re maga vesz referenciát, és minden
 * közbenső dentry-re pontosan egy referencia van érvényben. */
struct dentry *path_resolve(const char *path)
{
    struct dentry *d;

    if (*path == '/') {
        d = dget(current->fs->root);
        while (*path == '/')
            path++;
    } else {
        d = dget(current->fs->pwd);   /* relatív út a cwd-ből indul */
    }

    while (*path) {
        const char *end = strchrnul(path, '/');
        struct qstr name = { path, end - path };
        struct dentry *child;

        if (!d->d_inode || !S_ISDIR(d->d_inode->i_mode)) {
            dput(d);
            return ERR_PTR(-ENOTDIR);
        }

        if (name.len == 1 && name.name[0] == '.')
            goto next;                 /* "." : ugyanaz a dentry marad */
        if (name.len == 2 && !memcmp(name.name, "..", 2)) {
            struct dentry *up;
            if (d == current->fs->root)
                goto next;             /* a gyökér szülője önmaga */
            while (is_mount_root(d)) { /* mount gyökeréből a mountpontra lépünk vissza */
                up = dget(mountpoint_of(d));
                dput(d);
                d = up;
            }
            up = dget(d->d_parent);
            dput(d);
            d = up;
            goto next;
        }

        /* A d_lookup találat esetén már megnövelt referenciával adja
         * vissza a gyermeket; a szülő referenciája a hívóé marad. */
        child = d_lookup(d, &name);
        if (!child) {
            int err;
            /* d_alloc: a szülőhöz kötött, elnevezett, még nem hash-elt dentry */
            child = d_alloc(d, &name);
            if (!child) {
                dput(d);
                return ERR_PTR(-ENOMEM);
            }
            /* a lookup d_add(child, inode)-t vagy d_add(child, NULL)-t hív */
            err = d->d_inode->i_op->lookup(d->d_inode, child);
            if (err) {
                dput(child);
                dput(d);
                return ERR_PTR(err);
            }
        }
        if (!child->d_inode) {        /* negatív dentry a cache-ből */
            dput(child);
            dput(d);
            return ERR_PTR(-ENOENT);
        }

        dput(d);                      /* a szülőre már nincs szükség */
        d = child;

        while (mount_here(d)) {       /* egymásra csatolt mountok is lehetnek */
            struct dentry *mroot = mount_root(d);
            dput(d);                  /* a mountpont referenciáját elengedjük */
            d = dget(mroot);          /* a mount gyökere külön referenciát kap */
        }

next:
        path = end;
        while (*path == '/')
            path++;
    }

    return d;
}

A . komponens a dentry-t változatlanul hagyja; a .. komponenst a VFS maga oldja fel a d_parent alapján, a mount gyökerénél előbb a mountpontra lép vissza, a folyamat gyökerénél pedig helyben marad. A példa három további dolgot rögzít, amit a naiv változat elrontott. Először: a cache-találat és a lookup eredménye külön child változóba kerül, így a d_lookup utáni NULL esetén nem történik NULL-dereferálás (d->d_inode). Másodszor: abszolút út a fs->root-ból, relatív út a fs->pwd-ből indul, és a kezdő dentry-re a függvény maga vesz referenciát. Harmadszor: a mount-átlépésnél a mountpont referenciáját elengedjük, a mount gyökerére pedig újat veszünk, így a bejárás végén a hívó pontosan egy referenciát kap. A lookup sikeres visszatérése is referenciával adja vissza a dentry-t (ezt a d_splice_alias biztosítja), hiba esetén pedig ERR_PTR-t ad; a path_resolve mindkét esetet kezeli. A fejezet lookup ABI-ja egységesen (struct inode *dir, const char *name, size_t len); a valódi Linux VFS ezzel szemben (struct inode *dir, struct dentry *dentry, unsigned int flags) szignatúrát használ, tehát a tanuló modell és a valódi kernel ABI-ja nem azonos.

29.3.4 4. Inode és inode operations

Az inode az objektumot (fájlt, könyvtárat, eszközt) írja le a fájlrendszer szempontjából. A VFS inode nem a lemezes inode, hanem annak memóriabeli reprezentációja. A közös mezők mellett a fájlrendszer-specifikus adatok egy privát mutatóban élnek:

struct inode {
    unsigned long i_ino;
    uint32_t i_mode;
    size_t i_size;
    struct super_block *i_sb;
    const struct inode_operations *i_op;
    const struct file_operations *i_fop;
    void *i_private;       /* fs-specifikus adat */
    spinlock_t i_lock;
};

A i_mode a típust és a jogosultságokat hordozza; a S_ISDIR és S_ISREG makrókkal vizsgálható. A i_private például egy memfs esetén a RAM-beli inode-ra mutató pointer lehet.

Az inode-műveletek a névtér-műveletek egy részét fedik le:

struct inode_operations {
    int (*lookup)(struct inode *dir, struct dentry *child);
    int (*create)(struct inode *dir, const char *name,
                  size_t len, mode_t mode);
    int (*unlink)(struct inode *dir, const char *name,
                  size_t len);
    int (*mkdir)(struct inode *dir, const char *name,
                 size_t len, mode_t mode);
    int (*rmdir)(struct inode *dir, const char *name,
                 size_t len);
    int (*setattr)(struct dentry *d, struct iattr *attr);
    int (*getattr)(const struct path *p, struct kstat *stat);
};

A lookup feladata a könyvtárbejegyzés megkeresése. A memfs példában egy láncolt listát vagy tömböt járunk be:

struct memfs_inode {
    unsigned int ino;
    uint32_t mode;
    size_t size;
    unsigned char *data;
    struct list_head children; /* könyvtár bejegyzések */
    struct mutex lock;         /* a data, size és children védelme */
};

A lookup implementáció például:

int memfs_lookup(struct inode *dir, struct dentry *child)
{
    struct memfs_inode *m = dir->i_private;
    struct memfs_entry *e;
    struct inode *ino = NULL;

    mutex_lock(&m->lock);
    list_for_each_entry(e, &m->children, list) {
        if (strlen(e->name) == child->d_name.len &&
            memcmp(e->name, child->d_name.name, child->d_name.len) == 0) {
            ino = memfs_iget(e->ino);   /* referenciát vesz a zár elengedése előtt */
            break;
        }
    }
    mutex_unlock(&m->lock);

    d_add(child, ino);                  /* ino == NULL: negatív dentry */
    return 0;
}

A d_add a dentry-t és az inode-ot összekapcsolja, és felviszi a dentry cache-be. A példa itt leegyszerűsített; a tanulási szempontból fontos, hogy a lookup nem hoz létre új fájlt, csak meglévőt keres (hiány esetén negatív dentry-t hagy). A létrehozás külön create művelet. A memfs_lookup szignatúrája pontosan az inode_operations fenti ABI-ját követi: (struct inode *dir, struct dentry *child); a path_resolve a d_alloc-kal elkészített child dentry-vel hívja.

29.3.5 5. File operations és file object

Az inode a fájlrendszerben tárolt objektumot írja le, de a megnyitott fájlhoz tartozó állapotot a struct file tárolja. Ez a különválasztás az egyik leggyakoribb félreértés forrása: az inode nem tartalmaz fájlleíró-tulajdonságot, mint az aktuális eltolás (offset), a nyitási mód vagy a legutóbbi pozíció.

struct file {
    struct mutex f_lock;
    struct inode *f_inode;
    uint32_t f_flags;
    loff_t f_pos;                 /* aktuális offset */
    unsigned int f_mode;
    const struct file_operations *f_op;
    void *f_private;
    atomic_t f_count;             /* hivatkozások száma: fd-táblák, dup, fork */
};

A f_flags az open(2) nyers flagjeit őrzi (például O_RDWR), a f_mode pedig a kernel belső, származtatott hozzáférési bitjeit (FMODE_READ, FMODE_WRITE) tartalmazza. A két mező nem keverendő: az O_RDONLY értéke 0, ezért az f_mode & O_RDONLY alakú ellenőrzés mindig hamis, és a jó szándékú !(f_mode & O_RDONLY) feltétel minden olvasást elutasítana. A hozzáférési módot mindig f_mode & FMODE_READ/FMODE_WRITE vagy f_flags & O_ACCMODE vizsgálja.

A f_count számláló a dup/fork miatt kell: a close/fput csökkenti, és csak nullánál hívja a release-t, majd szabadítja fel a struct file-t.

A f_pos a következő olvasási vagy írási pozíció. A read és write rendszerhívás ezt a mezőt automatikusan növeli. A lseek rendszerhívás ezt a mezőt módosítja. A pread és pwrite ezzel szemben nem módosítják a f_pos-t.

A file_operations tábla a megnyitott fájlra vonatkozó műveleteket tartalmazza:

struct file_operations {
    int (*open)(struct inode *ino, struct file *f);
    ssize_t (*read)(struct file *f, char __user *buf, size_t count,
                    loff_t *pos);
    ssize_t (*write)(struct file *f, const char __user *buf,
                     size_t count, loff_t *pos);
    loff_t (*llseek)(struct file *f, loff_t offset, int whence);
    int (*release)(struct inode *ino, struct file *f);
};

A __user jelölés dokumentálja, hogy a mutató felhasználói címre mutat; a kód csak copy_to_user/copy_from_user segítségével érheti el, közvetlen memcpy-vel nem. A jelölést a sparse ellenőrzi, a fordító önmagában nem kényszeríti ki.

A read és write implementációjának a pos mutatón keresztül kell frissítenie az offsetet. Ez a VFS-szerződés része, és a fájlrendszer írója nem hivatkozhat közvetlenül a f_pos mezőre a file_operations-ön belül. Egy példa memfs-olvasás:

ssize_t memfs_read(struct file *f, char __user *buf, size_t count,
                   loff_t *pos)
{
    struct inode *ino = f->f_inode;
    struct memfs_inode *m = ino->i_private;
    size_t n;
    ssize_t ret;

    /* Zárolási sorrend: először az inode, utána a file object.
     * A fordított sorrend más útvonalon holtpontot okozhat. */
    mutex_lock(&m->lock);     /* data, size: más open is ezt használja */
    mutex_lock(&f->f_lock);   /* *pos: csak ezt a file objectet védi */

    if (*pos < 0) {
        ret = -EINVAL;
        goto out;
    }
    if ((uint64_t)*pos >= m->size) {
        ret = 0;              /* EOF */
        goto out;
    }

    n = min(count, (size_t)(m->size - *pos));
    if (copy_to_user(buf, m->data + *pos, n)) {
        ret = -EFAULT;        /* hibás felhasználói cím, az offset nem nő */
        goto out;
    }
    *pos += n;
    ret = (ssize_t)n;

out:
    mutex_unlock(&f->f_lock);
    mutex_unlock(&m->lock);
    return ret;
}

A f_lock csak az azonos file objectet használó hívásokat sorosítja: két külön open két külön struct file-t és két külön f_lock-ot kap. Az inode adatpufferét (m->data) és méretét (m->size) ezért külön, inode-szintű zár (m->lock) védi, különben egy másik fd-en végzett write vagy truncate átallokálhatja vagy felszabadíthatja a puffert, miközben a read még másol belőle. A copy_to_user a felhasználói címre ír, fault-biztos módon: hibás cím esetén -EFAULT-ot ad, nem omlik össze a kernel, és a *pos változatlan marad. A zárolási sorrend mindenhol inode-tól a file object felé halad; a fordított sorrend (file, majd inode) két párhuzamos műveletnél holtpontot okozhat.

29.3.6 6. Fájlleírók és offset kezelése

A felhasználói program számára a open visszatérési értéke egy kis egész szám, a fájlleíró (fd). A kernel ezt a számot indexként használja a folyamat files táblájában:

#define MAX_FD 256

struct task_struct {
    struct file *files[MAX_FD];
};

A fájlleíró-allokáció a legkisebb szabad indexet adja. A open sikeres végrehajtásakor a struct file mutató bekerül a táblába. Ettől kezdve a read, write, lseek, close mind ezen a számon hivatkozik a fájlra.

Az offset kezelése az egyik legkritikusabb VFS-szerződés. A struct file f_pos-a az open file description része, nem a fájlé. Ha ugyanazt a fájlt két külön open hívással nyitjuk meg, két külön struct file jön létre, és az offsetek függetlenek. Ha azonban a fájlleírót dup-pal vagy fork-kal másoljuk, a két fd ugyanarra a struct file-ra mutat, ezért az offsetet megosztják. Ez a POSIX-szemantika fontos oka annak, hogy a struct file referencia-számlálást is igényel.

Egy minimális dup implementáció a következő:

int sys_dup(int oldfd)
{
    struct file *f = fd_get(oldfd);   /* referenciát ad a file objectre */
    int newfd;

    if (!f)
        return -EBADF;

    newfd = fd_alloc();
    if (newfd < 0) {
        file_put(f);                  /* a sikertelen dup nem tart referenciát */
        return newfd;
    }

    fd_set(newfd, f);   /* a fd_get referenciáját az új fd átveszi */
    return newfd;
}

A fd_get a fájlleíró-táblából kikeresi a struct file-t, és referenciát vesz rá; ezt a rendszerhívás végén file_put-tal kell elengedni. A dup esetében a megszerzett referencia átkerül az új fájlleíróba, így a két fd közös életciklusúvá válik. A close csak az egyik fd táblabejegyzését szünteti meg; a struct file akkor szabadul fel, amikor az utolsó hivatkozás is megszűnik. A táblát a keresés idejére rövid kritikus szakaszban kell zárni, de a tényleges I/O már a referenciával, a táblazáron kívül fut.

A fájlleíró-tábla és a struct file kapcsolata a rendszerhívások rétegében:

/* Az open() a nyers flagből belső hozzáférési módot származtat. */
#define FMODE_READ  0x1u
#define FMODE_WRITE 0x2u

static void file_set_mode(struct file *f, unsigned int flags)
{
    switch (flags & O_ACCMODE) {
    case O_RDONLY: f->f_mode = FMODE_READ;               break;
    case O_WRONLY: f->f_mode = FMODE_WRITE;              break;
    case O_RDWR:   f->f_mode = FMODE_READ | FMODE_WRITE; break;
    default:       f->f_mode = 0;                        break;
    }
}

ssize_t sys_read(int fd, char __user *ubuf, size_t count)
{
    struct file *f = fd_get(fd);        /* referenciát ad */
    ssize_t ret;

    if (!f)
        return -EBADF;
    if (!(f->f_mode & FMODE_READ)) {
        ret = -EBADF;                   /* írásra nyitott fd-n nincs olvasás */
        goto out;
    }
    if (!f->f_op->read) {
        ret = -EINVAL;                  /* hiányzó read metódus */
        goto out;
    }

    ret = f->f_op->read(f, ubuf, count, &f->f_pos);
out:
    file_put(f);                        /* a fd_get referenciáját elengedjük */
    return ret;
}

loff_t sys_lseek(int fd, loff_t offset, int whence)
{
    struct file *f = fd_get(fd);
    loff_t ret;

    if (!f)
        return -EBADF;
    if (!f->f_op->llseek) {
        ret = -ESPIPE;                  /* nem seekelhető objektum, pl. pipe */
        goto out;
    }

    ret = f->f_op->llseek(f, offset, whence);
out:
    file_put(f);
    return ret;
}

Az O_RDONLY értéke 0, ezért a hozzáférési módot nem f_mode & O_RDONLY alakban kell vizsgálni: a file_set_mode az O_ACCMODE maszkból származtatja a belső FMODE_* biteket, és a rendszerhívás ezeket ellenőrzi. A hiányzó read metódus -EINVAL, a hiányzó llseek metódus -ESPIPE hibát ad; a fd_get által szerzett referenciát minden kimeneti ágon file_put engedi el. A copy_to_user a memfs_read-ban történik, mert a felhasználói címet csak a fájlrendszer-specifikus read metódus ismeri; a rendszerhívás rétege nem dereferálja közvetlenül a ubuf pointert.

Az llseek tipikus megvalósítása ellenőrzi a whence értéket, ellenőrzött összeadással számolja az új offsetet, és ugyanazzal a f_lock zárral sorosít, mint a read/write:

loff_t generic_file_llseek(struct file *f, loff_t offset, int whence)
{
    loff_t newpos;
    bool ok;

    mutex_lock(&f->f_lock);   /* közös offset: ugyanaz a zár, mint read/write-nál */

    switch (whence) {
    case SEEK_SET:
        newpos = offset;
        ok = true;
        break;
    case SEEK_CUR:
        ok = !check_add_overflow(f->f_pos, offset, &newpos);
        break;
    case SEEK_END:
        ok = !check_add_overflow(f->f_inode->i_size, offset, &newpos);
        break;
    default:
        mutex_unlock(&f->f_lock);
        return -EINVAL;
    }

    if (!ok) {
        mutex_unlock(&f->f_lock);
        return -EOVERFLOW;    /* loff_t túlcsordulás */
    }
    if (newpos < 0) {
        mutex_unlock(&f->f_lock);
        return -EINVAL;       /* negatív fájlpozíció nem értelmezett */
    }

    f->f_pos = newpos;
    mutex_unlock(&f->f_lock);
    return newpos;
}

A check_add_overflow (<linux/overflow.h>) túlcsordulás esetén true-val tér vissza, és az eredményt nem használjuk; a hívó ilyenkor -EOVERFLOW-ot ad. A SEEK_END ág az i_size pillanatképét használja, miközben csak a f_lock-ot tartja; párhuzamos truncate esetén az eredmény közelítő, de nem ad memóriahibát. A valódi kernel ehhez i_size_read-ot és finomabb inode-zárolást használ. A sys_lseek hiányzó llseek callbackje nem dereferálható: ilyenkor -ESPIPE a helyes válasz, amit a sys_lseek fenti ellenőrzése ad.

Hibakódok és errno a VFS rétegben is szigorúan elválik: a kernel belső hívásai negatív hibakódot adnak vissza, a rendszerhívás ugyanezt a negatív értéket adja vissza a felhasználói térbe (x86-64-en rax-ben). A -1 + errno alakot a felhasználói C-könyvtár csomagolója állítja elő: ha a visszatérési érték −4095 és −1 közé esik, errno = -ret, és a függvény -1-et ad. A fejezet példáiban a return -ENOENT alakot használjuk a kernelbelsőben.

29.3.7 7. Integrációs példa: memfs mount a /mnt könyvtárra

A következő példa egy minimális memfs-t csatlakoztat a közös fába. A memfs nem használ blokk-eszközt; minden fájl és könyvtár a RAM-ban él. A mount source paramétere ilyenkor lehet "none", a fstype pedig "memfs".

A memfs mount metódusa felépíti a szuperblokkot és a gyökércsomópontot:

struct super_block *memfs_mount(const char *source,
                                unsigned long flags)
{
    struct super_block *sb = kzalloc(sizeof(*sb));
    if (!sb)
        return ERR_PTR(-ENOMEM);

    sb->s_blocksize = 4096;
    sb->s_magic = 0x4D454D46;   /* "MEMF" */
    sb->s_op = &memfs_super_ops;

    struct inode *root_ino = memfs_new_inode(S_IFDIR | 0755);
    if (!root_ino) {
        kfree(sb);
        return ERR_PTR(-ENOMEM);
    }

    sb->s_root = d_alloc_root(root_ino);
    if (!sb->s_root) {
        memfs_free_inode(root_ino);
        kfree(sb);
        return ERR_PTR(-ENOMEM);
    }

    return sb;
}

A mount után a felhasználói program a szokásos módon hívja az open-t:

int fd = open("/mnt/demo.txt", O_RDWR | O_CREAT, 0600);
if (fd < 0) {
    perror("open");
    return 1;
}

ssize_t n = write(fd, "hello\n", 6);
if (n != 6) {
    perror("write");
    close(fd);
    return 1;
}

lseek(fd, 0, SEEK_SET);
char buf[16] = {0};
n = read(fd, buf, sizeof(buf));
close(fd);

A kernelben ezek a hívások így kapcsolódnak össze:

  1. A open átadja a /mnt/demo.txt útvonalat a path_resolve-nak.
  2. A / komponenst a folyamat root dentry-je oldja fel.
  3. A mnt komponensnél a VFS észleli a memfs mount-ot, és átlép a memfs root-jára.
  4. A demo.txt komponenst a memfs lookup keresi; ha nincs ilyen fájl, a create művelet létrehozza.
  5. A VFS lefoglal egy struct file-ot, beállítja az f_op-ot a memfs file_operations-re, és beilleszti a files táblába.
  6. A read és write a struct file f_pos mezőjén keresztül frissíti az offsetet.

Az open útja vázlatban (a nem létező utolsó komponens esetét a path_resolve_parent kezeli, amely a szülő dentry-t és az utolsó komponens qstr-ját adja):

int sys_open(const char *path, int flags, mode_t mode)
{
    struct qstr last;
    struct dentry *dir = path_resolve_parent(path, &last);   /* referenciát ad */
    struct dentry *d;
    struct file *f;
    int fd, err;

    if (IS_ERR(dir))
        return PTR_ERR(dir);
    d = d_lookup(dir, &last);                  /* cache; miss esetén d_alloc + lookup */
    if (!d || !d->d_inode) {                   /* nem létezik */
        if (!(flags & O_CREAT)) { err = -ENOENT; goto out_dir; }
        err = dir->d_inode->i_op->create(dir->d_inode, last.name, last.len, mode);
        if (err) goto out_dir;
        if (d) dput(d);
        d = d_lookup(dir, &last);              /* újra: most már létezik */
    } else if ((flags & O_CREAT) && (flags & O_EXCL)) {
        err = -EEXIST; goto out_d;
    }
    f = file_alloc();                          /* f_count = 1 */
    if (!f) { err = -ENOMEM; goto out_d; }
    f->f_inode = d->d_inode;
    f->f_op    = d->d_inode->i_fop;
    f->f_flags = flags;
    f->f_mode  = file_set_mode(flags);         /* FMODE_READ | FMODE_WRITE */
    f->f_pos   = 0;
    fd = fd_alloc();
    if (fd < 0) { fput(f); err = fd; goto out_d; }
    fd_set(fd, f);
    dput(d); dput(dir);
    return fd;
out_d:   dput(d);
out_dir: dput(dir);
    return err;
}

A O_CREAT és a mode paraméter a create inode-műveletbe kerül. Az O_RDWR az f_mode-ot állítja (FMODE_READ | FMODE_WRITE); a file_operations tábla az inode i_fop-jából jön. A VFS ezeket a flag-eket már a open rendszerhívás rétegében ellenőrzi.

29.3.8 8. Tipikus hibák és helyes kezelésük

A VFS-integráció során a következő hibák fordulnak elő leggyakrabban:

  1. Az offset nem a file-ban, hanem az inode-ban él. Ha a fejlesztő az inode-ba teszi a pozíciót, akkor két párhuzamos open ugyanazt a pozíciót módosítja, és a dup szemantika is elromlik. Helyes megoldás: struct file f_pos, és a file_operations mindig a kapott pos pointerrel dolgozik.

  2. A dentry referencia-számláló hiánya. A path_resolve után a dentry d_count-ját növelni kell, és a használat után dput-ot hívni. Ha ez elmarad, a dentry felszabadítása use-after-free hibát okozhat. A dentry cache lookup és a mount átlépés során is meg kell őrizni a referenciákat.

  3. A mount-átlépés kihagyása. A path_resolve-nak minden komponensnél ellenőriznie kell a mount-táblát. Ha ezt kihagyjuk, a /mnt alatt a háttér-fájlrendszer könyvtára marad látható, és a csatolt fájlrendszer elérhetetlen.

  4. A read/write/lseek offset-ellenőrzés hiánya. Az offset lehet negatív (hibás lseek után), és a SEEK_CUR/SEEK_END számítás túlcsordulhat. A memfs_read-ben a *pos < 0 és a m->size - *pos ellenőrzés szükséges; a generic_file_llseek-ben check_add_overflow és -EOVERFLOW, negatív eredménynél -EINVAL a helyes válasz. A puszta f_pos + offset összeadás előjeles túlcsordulása definiálatlan viselkedés C-ben, ezért tilos.

  5. A fájlleíró-tábla túlcsordulása. A fd_alloc-nak ellenőriznie kell a MAX_FD határt, és EMFILE-t kell adnia, ha nincs szabad slot. A EBADF a nem létező fd-re utal, a kettőt nem szabad összekeverni.

  6. Versenyhelyzet a file offseten és az inode adatán. Két különböző verseny van. Az azonos file objectet használó hívások (például dup után) közös f_pos-ját a f_lock védi, különben két szál ugyanazt a pozíciót növelné, és adat veszne el. A külön open-ből származó, külön f_lock-ú leírók viszont ugyanazt az inode-ot és adatpuffert használják: a memfs_read másolása közben egy másik fd-en végzett write vagy truncate átallokálhatja a puffert, ezért kell inode-szintű zár (m->lock) is. A két zár megszerzési sorrendje rögzített: először az inode-zár, utána a file-zár; a fordított sorrend holtpontot okozhat.

  7. Hibakód-konverzió a user/kernel határon. A kernel negatív hibakódokat ad; a felhasználói tér felé a libc csomagolója fordítja -1-re és errno-ra. Ha a read -EBADF-et ad vissza, a felhasználó -1-et és errno == EBADF-et kap.

A labor lépései.

  2. Implementáld a vfs_mount és a mount-léptetés logikáját a path_resolve-ban, a fejezet referencia-szerződése szerint (minden közbenső dentry-re egy referencia, a mount-átlépésnél csere).

  4. Indítsd el a kernelt, és hívd a következő tesztet:
static int vfs_checks;
static unsigned long dentry_hits, dentry_misses;

#define CHECK(cond) do {                                          \
    if (!(cond)) {                                                \
        printk(KERN_ERR "vfs_test: %s failed (line %d)\n",        \
               #cond, __LINE__);                                  \
        return;                                                   \
    }                                                             \
    vfs_checks++;                                                 \
} while (0)

/* Relatív út: ideiglenesen a memfs gyökerére állítjuk a cwd-t. */
static bool vfs_relative_test(void)
{
    struct dentry *saved = current->fs->pwd;
    struct dentry *root = path_resolve("/mnt");
    bool ok = false;
    int fd;

    if (IS_ERR(root))
        return false;

    current->fs->pwd = root;      /* a path_resolve referenciáját átvesszük */
    fd = open("test.txt", O_RDONLY);
    if (fd >= 0) {
        ok = true;
        close(fd);
    }
    dput(current->fs->pwd);
    current->fs->pwd = saved;     /* a mentett referencia visszakerül */
    return ok;
}

static void vfs_test(void)
{
    const char *msg = "vfs-integration\n";
    char buf[32] = {0};
    ssize_t n;
    int fd;

    /* 1. Abszolút út, első feloldás: a dentry cache még üres, tehát
     *    legalább egy lookup missnek kell történnie. */
    dentry_hits = 0;
    dentry_misses = 0;
    fd = open("/mnt/test.txt", O_RDWR | O_CREAT, 0600);
    CHECK(fd >= 0);
    CHECK(dentry_misses >= 1);

    n = write(fd, msg, strlen(msg));
    CHECK(n == (ssize_t)strlen(msg));

    CHECK(lseek(fd, 0, SEEK_SET) == 0);
    n = read(fd, buf, sizeof(buf));
    CHECK(n == (ssize_t)strlen(msg));
    CHECK(memcmp(buf, msg, (size_t)n) == 0);
    close(fd);

    /* 2. Relatív út a cwd-ből, majd egy ismételt open: ez már cache
     *    találat kell legyen. */
    CHECK(vfs_relative_test());
    fd = open("/mnt/test.txt", O_RDONLY);
    CHECK(fd >= 0);
    CHECK(dentry_hits >= 1);
    close(fd);

    printk(KERN_INFO "vfs_test: OK (%d ellenőrzés)\n", vfs_checks);
}

A CHECK makró a hibát a sor számával együtt naplózza, és nem hagyja, hogy a teszt tovább fusson hibás állapotban. A relatív út tesztje megmutatja, hogy a path_resolve a fs->pwd-ből indul, és a cwd ideiglenes átállítása után a referencia-számlálás kiegyensúlyozott marad. A tanulókernelben nincs külön felhasználói címtér, ezért a teszt pufferjei kernelcímek, és a copy_to_user itt közvetlen másolásként viselkedik; valódi user/kernel szeparáció mellett a fault-biztos másolás kötelező.

  1. Mérd meg a VFS-műveletek idejét a következő mikrobenchmarkkal. A mérés előfeltétele egy pontosan 4096 bájtos /mnt/file, amelyet a mérés előtt ellenőrzötten létrehozunk; a hívások sikerét és az időbélyegek rendezését minden iterációban ellenőrizzük:
#define ITERS 1000

struct sample {
    uint64_t open_cyc, read_cyc, write_cyc, close_cyc, total_cyc;
};

static struct sample samples[ITERS];
static char tmp[64];

static bool vfs_bench_prepare(void)
{
    char block[4096] = {0};
    ssize_t n;
    int fd = open("/mnt/file", O_RDWR | O_CREAT | O_TRUNC, 0600);

    if (fd < 0)
        return false;
    n = write(fd, block, sizeof(block));
    close(fd);
    return n == (ssize_t)sizeof(block);
}

static bool vfs_bench(void)
{
    for (int i = 0; i < ITERS; i++) {
        uint64_t t0, t1, t2, t3, t4;
        ssize_t r, w;
        int fd;

        t0 = rdtsc();
        fd = open("/mnt/file", O_RDWR);
        t1 = rdtsc();
        if (fd < 0)
            return false;

        r = read(fd, tmp, sizeof(tmp));
        t2 = rdtsc();
        w = write(fd, tmp, sizeof(tmp));
        t3 = rdtsc();
        close(fd);
        t4 = rdtsc();

        if (r != (ssize_t)sizeof(tmp) ||
            w != (ssize_t)sizeof(tmp))
            return false;
        /* Időbélyeg-rendezés: érvénytelen minta nem kerülhet a táblába. */
        if (!(t0 <= t1 && t1 <= t2 && t2 <= t3 && t3 <= t4))
            return false;

        samples[i].open_cyc  = t1 - t0;
        samples[i].read_cyc  = t2 - t1;
        samples[i].write_cyc = t3 - t2;
        samples[i].close_cyc = t4 - t3;
        samples[i].total_cyc = t4 - t0;
    }
    return true;
}

Minden iteráció friss open-nal indul, ezért a f_pos 0-ról kezd: a read a 0..63, a write a 64..127 bájtot érinti, a fájl mérete 4096 bájt marad. A négy művelet idejét külön mintaként tároljuk, így műveletenként számítható átlag, szórás, minimum és maximum; a teljes ciklus ideje külön oszlop, nem a műveleti idők helyett. A rdtsc nem sorosító utasítás; a rendezés-ellenőrzés kiszűri az out-of-order végrehajtásból adódó inkonzisztens mintákat, és ha megsérül, a mérést rdtscp-vel vagy lfence-szel megerősítve meg kell ismételni.

A cikluson belül ugyanazt a 4 KiB-os fájlt nyitjuk meg. A TSC-t sorosító párral olvassuk (lfence; rdtsc a kezdetnél és rdtscp; lfence a végnél), mert a sima rdtsc nem sorosító: a mért kód egy része az ablakon kívülre csúszhat; a rendezés-ellenőrzés csak a durva hibát (magváltás, TSC-ugrás) szűri. A ciklusszámot rögzítjük; átszámításhoz a vendég TSC-frekvenciáját a PIT/HPET-kalibráció adja (a qemu64 modell a CPUID 0x15/0x16 levelet nem adja), és a kalibráció bizonytalanságát is fel kell tüntetni. QEMU-ban a TSC virtuális, ezért az eredmény az emulált környezetre, nem fizikai hardverre jellemző; ezt a naplóban külön meg kell jelölni.

Kiinduló elvárás és a mért érték elkülönítése. A naplóban a következő táblázatot kell kitölteni; a „várt trend” oszlop hipotézis, nem mért eredmény:

| művelet        | várt trend                             | mért átlag | szórás | min | max |
|----------------+----------------------------------------+------------+--------+-----+-----|
| open           | hash lookup, átlag O(1), első minta miss| ? ciklus  | ?      | ?   | ?   |
| read 64 B      | 64 bájt másolása, O(n), n = 64 B         | ? ciklus  | ?      | ?   | ?   |
| write 64 B     | 64 bájt másolása, O(n), n = 64 B         | ? ciklus  | ?      | ?   | ?   |
| close          | O(1)                                    | ? ciklus  | ?      | ?   | ?   |
| teljes ciklus  | a négy művelet és a hívási overhead     | ? ciklus  | ?      | ?   | ?   |

A „várt trend” oszlopban az O(1) átlagos esetre vonatkozik: a dentry cache hash-tábla, ütközés esetén a lánc hosszával lineáris; ezért a szórás és a maximális érték fontos információ. A táblába csak ellenőrzött, rendezett időbélyegű minták kerülhetnek; a ciklusszámot, a dentry cache találati arányát és a TSC-kalibráció bizonytalanságát a táblázat alatt kell rögzíteni.

Elvárt működés. A vfs_test sikeres futtatása után a mount-névtér konzisztens: a /mnt/test.txt a memfs rootjában jön létre. Az első open legalább egy dentry cache miss-t, a második open találatot mutat; a találati arány növekedése várható, de az open átlagos idejének csökkenése nem garantált, ezért csak mért adattal szabad állítani. A read/write idő a másolt 64 bájttal közel lineáris, az offset minden érvényes iterációban helyes marad, és a fájl mérete nem változik.

Reprodukciós napló. A naplóba a következő parancsok kimenete tartozik:

make -C vfs-lab clean
make -C vfs-lab build
./qemu-run.sh | tee logs/boot.log

A boot.log végén a vfs_test: OK sor, a mérési táblázat és a verziók szerepelnek. A labot eldobható QEMU környezetben vagy külön vendégképen futtasd; a hoszt rendszerpartícióját és bootloaderét tilos módosítani.

29.3.10 10. Önellenőrző kérdések

  1. Mi a különbség a dentry, az inode és a struct file szerepe között? Melyik tárolja az offsetet és miért?
  2. Mit kell tennie a path_resolve-nak, amikor egy aktív mount point-ot ér el?
  3. Hogyan osztozik az offset két fájlleíró között dup után? Melyik kernelbeli adatszerkezet referencia-számlálóját kell növelni?
  4. Milyen hibát okoz, ha a read művelet közvetlenül az inode-ba menti a pozíciót, és miért nem elég az inode zára?
  5. Miért kell a dentry d_count referencia-számlálóját a d_lookup után növelni? Milyen hibakódot adunk, ha egy útvonalkomponens nem könyvtár?

Ezek a kérdések a fejezet fő ellenőrzési pontjait fedik le. A megoldásuk a 8. szakasz hibakezelési megjegyzéseiből és a példakódból levezethető.
