23.3 WCET, megszakítási késleltetés és erőforrás-elemzés

A valós idejű rendszer egyik legfontosabb tervezési kérdése, hogy a futó feladatok minden esetben a határidejükön belül elvégezzék a munkájukat. Az átlagos végrehajtási idő ehhez nem elegendő, mert a rendszer időnként a legkedvezőtlenebb útvonalon fut, és ez az a pont, ahol a határidő-túllépés először bekövetkezik. Ebben a fejezetben a legrosszabb végrehajtási idő (WCET), a megszakítási késleltetés és a veremszükséglet elemzését, valamint az időzítési zárolás módszerét tárgyaljuk.

23.3.1 1. Legrosszabb végrehajtási idő és rendszerterhelés

Egy PiP_i feladat végrehajtási ideje nem konstans. A bemeneti adatoktól, a gyorsítótár állapotától, az elágazásoktól és a megszakításoktól függően az egyes futások ideje szóródik. A valós idejű elemzéshez három értéket szokás megkülönböztetni:

  • BCET (best-case execution time): a lehető legrövidebb futási idő.
  • ACET (average-case execution time): a mérésekből számolt átlagos futási idő.
  • WCET (worst-case execution time): a lehető leghosszabb futási idő, amely a feladat összes lehetséges végrehajtása közül előfordulhat.

A WCET tehát egy felső korlát. Ha a feladat tényleges futási ideje minden esetben legfeljebb CiC_i, akkor az ütemezési analízis biztonságos módon használhatja a CiC_i értéket. A rendszerterhelést az egyszerű periodikus feladatmodellben az

U=∑i=1nCiTi U = \sum_{i=1}^{n} \frac{C_i}{T_i}

összefüggéssel számítjuk, ahol TiT_i a PiP_i feladat periódusideje, CiC_i pedig a WCET. Egyprocesszoros környezetben a U≤1U \le 1 feltétel szükséges a megvalósíthatósághoz, de nem elégséges: az ütemező algoritmus és a határidők is befolyásolják, hogy a feladatkészlet valóban ütemezhető-e. Az ütemezési teszteket az előző alfejezet (23.2) tárgyalta, ezért itt csak annyit rögzítünk, hogy a rendszerterhelés-számítás megbízhatósága közvetlenül a CiC_i becslés megbízhatóságától függ.

Az átlagos futási idő használata tipikus hiba. Ha egy motorvezérlő feladat átlagosan 120 µs alatt fut, de ritkán, például egy hibakezelési ágban 280 µs-ig is eltarthat, akkor az átlag alapján számolt terhelés hamisan alacsony. A határidő-túllépés éppen a ritka, hosszú ágban következik be. A WCET-elemzés célja ezért a farok-késleltetés biztonságos felső korlátjának meghatározása.

23.3.2 2. WCET-becslési módszerek

A WCET meghatározására három alapvető megközelítés létezik:

  1. Statikus analízis: a forráskód vagy a bináris vezérlési gráfjának elemzése a hardvermodell figyelembevételével.
  2. Mérés-alapú becslés: a feladat végrehajtása sok, különböző bemenettel, majd a mért idők statisztikai kiértékelése.
  3. Hibrid megközelítés: mérésekkel kalibrált statikus elemzés, vagy statikus útvonalelemzéssel kiegészített mérés.

A statikus analízis lépései egy egyszerű példán jól bemutathatók. Tekintsük a következő pszeudokódot:

/* pszeudokód: ciklikus feladat – 12 együtthatós FIR szűrő */
#define TAPS 12          /* együtthatók száma (N) */

/* Fixpontos ábrázolás:
 *   x[n] : 12 bites előjel nélküli minta, 0..4095
 *   h[i] : 16 bites előjeles együttható, Q1.14 ([-2, 2) tartomány)
 *   acc  : 32 bites előjeles gyűjtő is elég (|acc| < 1,62·10^9 < 2^31);
 *          a 64 bit tartalék a nagyobb együtthatószámhoz
 * A kimenet 32 bitre vágott, telített érték, 2^14 skálával osztva. */
static const int16_t h[TAPS] = { /* ... Q1.14 együtthatók ... */ };
static uint16_t      hist[TAPS];   /* x[n], x[n-1], ..., x[n-(TAPS-1)] */
static unsigned      head;         /* a legfrissebb minta helye */

int32_t fir_filter(uint16_t x) {
    int64_t acc = 0;

    hist[head] = x;                                       /* új minta */
    for (int i = 0; i < TAPS; i++) {
        unsigned k = (head + TAPS - (unsigned)i) % TAPS;  /* x[n-i] */
        acc += (int32_t)h[i] * (int32_t)hist[k];
    }
    head = (head + 1u) % TAPS;

    acc /= (1 << 14);                                     /* Q1.14 -> egész */
    if (acc > INT32_MAX) acc = INT32_MAX;                 /* telítés: védelmi ág, */
    if (acc < INT32_MIN) acc = INT32_MIN;                 /* a megadott tartományban nem aktív */
    return (int32_t)acc;
}

void task_control(void) {
    uint16_t x = read_sensor();        /* 0..4095 */
    int32_t  y = fir_filter(x);
    if (y > THRESHOLD) {
        actuator_write(y);
    } else {
        actuator_write(0);
    }
}

A task_control vezérlési gráfja a következő alapblokkokból áll:

  • A: read_sensor hívása.
  • B: fir_filter előkészítése és a ciklus belépése.
  • C: a ciklusmag egy iterációja.
  • D: a ciklus kilépése és a visszatérés.
  • E: az if feltétel kiértékelése.
  • F: az igaz ág (actuator_write(y)).
  • G: a hamis ág (actuator_write(0)).

A statikus elemzéshez minden alapblokkhoz felső időkorlátot rendelünk. Az alábbi blokkidők oktatási feltételezések egy 50 MHz-es Cortex-M3-ra, nem mért eredmények: a példa a számítás menetét mutatja be, nem egy konkrét buildet jellemez.

Alapblokk Leírás Idő (µs)
A szenzorolvasás (MMIO + konverzió) 1,0
B ciklus inicializálás, minta beírása 0,6
C ciklusmag egy iteráció (szorzás, összeadás, index) 0,4
D ciklus kilépés, telítés, skálázás 0,5
E feltétel 0,2
F igaz ág (aktuátor írás) 1,0
G hamis ág 0,4

A ciklus iterációszáma konstans N=12N = 12. A fir_filter blokk WCET-je:

Cfir=B+N⋅C+D=0,6+12⋅0,4+0,5=5,9 µs. C_{\text{fir}} = B + N \cdot C + D = 0{,}6 + 12 \cdot 0{,}4 + 0{,}5 = 5{,}9 \text{ µs}.

A task_control teljes WCET-je a hosszabb ágat választva:

Ctask=A+Cfir+E+max⁡(F,G)=1,0+5,9+0,2+1,0=8,1 µs. C_{\text{task}} = A + C_{\text{fir}} + E + \max(F, G) = 1{,}0 + 5{,}9 + 0{,}2 + 1{,}0 = 8{,}1 \text{ µs}.

Ez a számítás feltételezi, hogy a blokkok időkorlátjai ismertek. Valós processzoron ezek a korlátok a folyamatarchitektúrától függenek: a pipeline, az elágazásbecslés, a gyorsítótár és a memória-várakozások mind növelhetik az egyes blokkok idejét. A statikus elemző eszközök ezért a CPU-időzítési modelljét is tartalmazzák. Az egyszerű mikrokontrollereken (például ARM Cortex-M3) a gyorsítótár nélküli, determinisztikus végrehajtás miatt a blokkok ciklusszinten számolhatók, de a flash-memória várakozási állapotait itt is figyelembe kell venni.

A mérés-alapú becslés során a feladatot a céleszközön vagy emulált környezetben futtatjuk, és időbélyeggel mérjük a futás hosszát. A mérésekből hisztogramot készítünk. A gond az, hogy a bemeneti tér ritkán teljesen lefedhető, ezért a mért maximum nem feltétlenül éri el a valódi WCET-et. A mérés megfigyelést ad, nem felső korlátot: a minta nagysága és a lefedettség együtt korlátozza, milyen állítás tehető. Felső korláthoz vagy a leghosszabb útvonal statikus igazolása, vagy a lefedett állapotteret kimerítő, dokumentált mérési kampány kell; a mért maximumot utólag megszorzó „biztonsági tényező” önmagában nem ad garanciát, mert nem köti sem az útvonalhoz, sem a hardverállapothoz.

A hibrid megközelítés a statikus útvonalelemzést használja a maximális útvonal megtalálására, majd az egyes alapblokkokat méréssel kalibrálja. Így a ritka útvonalak is bekerülnek az elemzésbe, a hardvermodell hibáját pedig a mérés csökkenti.

23.3.3 3. Megszakítási késleltetés

A megszakítási késleltetés (interrupt latency) az az idő, amely a megszakítási kérelem hardveres megjelenésétől a megszakítás-kiszolgáló rutin (ISR) első utasításának megkezdéséig eltelik. A válaszidő (response time) ennél tágabb fogalom: magában foglalja az ISR végrehajtását és az ütemező által elindított feladat futását is. A valós idejű rendszerben az interrupt latency a legrosszabb esetben is korlátos kell hogy legyen.

A késleltetés összetevői:

  • Hardveres késleltetés: a megszakításkérő periféria és a megszakításvezérlő közötti terjedés, a prioritás döntése.
  • Megszakítás-tiltott ablak: az az idő, amíg a CPU a megszakításokat letiltva tartja, például kritikus szakaszokban.
  • ISR-belépési idő: a CPU automatikus állapotmentése (regiszterek, visszatérési cím) és a vektortábla olvasása.
  • Szoftveres belépés: a C ISR függvény bevezető kódja, amely a további regisztereket menti.

Az alábbi táblázat egy ARM Cortex-M3 alapú, QEMU-ban emulált rendszer tipikus, tervezési célként használt értékeit mutatja. Az értékek nem mérési eredmények, hanem a gyártói dokumentáció és az elemzés alapján becsült felső korlátok; a tényleges mérés eltérhet.

Összetevő Idő (µs)
Hardveres késleltetés 0,1
Megszakítás-tiltott ablak (maximális kritikus szakasz) 3,0
ISR belépés (hardveres mentés + vektortábla) 0,5
Szoftveres belépés és regisztermentés 1,0
Összesen (legrosszabb eset) 4,6

A megszakítási késleltetés mérésére az egyik legegyszerűbb módszer, ha egy GPIO kimenetet a szoftver a megszakítási kérelem pillanatában magasra állít, az ISR első utasításában pedig alacsonyra; a jelszélességet logikai analizátorral mérjük. Emulált környezetben vagy GPIO nélkül a mérést szabadon futó számláló (SysTick, DWT) időbélyegével végezzük, az alábbi módon.

Az alábbi pszeudokód a késleltetés mérését mutatja:

/* pszeudokód: interrupt latency mérés a SysTick szabadon futó számlálójával.
 * Cortex-M3: a SYST_CVR 24 bites, lefelé számláló; a módszer csak egy
 * SysTick-perióduson belüli késleltetésre érvényes. */
#define SYST_CVR (*(volatile uint32_t *)0xE000E018u)
#define NVIC_STIR (*(volatile uint32_t *)0xE000EF00u)  /* szoftveres IRQ-kiváltás */
#define IRQ_NUM   5u                                   /* a cél MCU adatlapja szerint választandó */

volatile uint32_t start, samples[1024];
volatile unsigned n;

void trigger_interrupt(void) {
    start = SYST_CVR;
    NVIC_STIR = IRQ_NUM;       /* valódi IRQ szoftverből (vagy NVIC->ISPR) */
}

void irq_handler(void) {       /* az ISR első utasításai */
    uint32_t lat = (start - SYST_CVR) & 0x00FFFFFFu;   /* lefelé számláló */
    if (n < 1024u) samples[n++] = lat;                 /* tárolás */
}

A STIR-regiszter használatához a CCR.USERSETMPEND bit vagy privilegizált mód kell, a konkrét címek és bitek ellenőrzendők a Cortex-M3 és a cél MCU dokumentációjában. Az svc szinkron kivétel, nem megszakítás, ezért erre a mérésre nem alkalmas: nem érvényes rá a megszakítás-tiltott ablak, így éppen a legdominánsabb összetevőt (a táblázat 3,0 µs-os tagját) nem mérné.

A mérést elegendően sokszor megismételve a maximális értéket keressük. A legrosszabb esetet gyakran a leghosszabb megszakítás-tiltott kritikus szakasz okozza, ezért a kódban a kritikus szakaszok hosszát is ismerni kell.

23.3.4 4. Stack usage

A veremszükséglet elemzése azért kritikus, mert a verem túlcsordulása nem determinisztikus hibához, hanem memóriasértéshez vezet, amely a rendszer bármely pontján jelentkezhet. A valós idejű rendszerben a legrosszabb veremmélységet kell meghatározni minden feladathoz és az ISR-ekhez.

A veremhasználat forrásai:

  • A hívási lánc minden függvényének helyi változói.
  • A megszakítási kontextusban mentett regiszterek.
  • A fordító által generált ideiglenes értékek.
  • A könyvtári függvények belső keretei.

A veremmélység meghatározásának három fő módszere:

  1. Festékes mérés (stack painting): a verem területét ismert mintázattal (például 0xDEADBEEF) töltjük fel, majd a feladat futtatása után megkeressük a legmélyebb, azaz legkisebb című felülírt szót vagy bájtot. Lefelé növő veremnél a csúcsot nem a legmagasabb, hanem a legmélyebb módosított cím jelzi: a magas címek a kiinduló veremmutató közelében vannak, és ott egy lefoglalt, de érintetlen tartomány nem írja felül a festéket. A használt mélység ekkor SPkezdet−cminSP_{\text{kezdet}} - c_{\min}, ahol cminc_{\min} a legmélyebb felülírt cím. A módszer a futás során elért, megfigyelt high-water markot adja, amely nem feltétlenül éri el a legrosszabb esetet, ha a ritka útvonal nem futott le. Felfelé növő veremnél (ritkább, de létezik ilyen architektúra) a keresés iránya fordított: a legmagasabb felülírt cím számít.

  2. Statikus analízis: a hívási gráf alapján minden függvény keretméretét összegezzük a leghosszabb útvonalon. A függvények rekurziója esetén a rekurzió mélységét is korlátozni kell.

  3. MPU/guard page védelem: a hardveres memóriavédelmi egység a verem alján tiltott régiót helyez el, így a túlcsordulás azonnal megszakítást generál. Ez nem helyettesíti az elemzést, de megakadályozza a csendes memóriakorrupciót.

Az alábbi példa egy hívási lánc statikus elemzését mutatja:

main -> task_control -> fir_filter

A keretméretek:

Függvény Keretméret (bájt)
main 32
task_control 48
fir_filter 16
Összesen 96

Ha a megszakítási kontextus a feladat veremét használja, akkor az ISR keretét és a hardveres mentést is hozzá kell adni. ARM Cortex-M3-on a megszakítás belépésekor a hardver automatikusan elmenti az exception frame-et: R0–R3, R12, LR, PC és xPSR, azaz 8 szó, 32 bájt; a hardver a keretet 8 bájtos határra igazíthatja (STKALIGN), ilyenkor egy kitöltő szóval legfeljebb 36 bájt. (FPU-val rendelkező magon – Cortex-M4F/M7 – a lusta FPU-mentés további 18 szót foglalhat; a Cortex-M3-on ez nem fordul elő.) PSP-t használó RTOS-nál ez a keret a megszakított taszk vermén jön létre, az ISR további kerete viszont a fő (MSP) vermen; a kettőt külön kell méretezni. Ezt a keretet a statikus összeghez külön tételként kell hozzáadni, és a verem legmélyebb pontját a megszakítás pillanatában kell számítani, azaz a megszakított függvény keretei alatt. A statikus elemzés a hívási gráf leghosszabb útját adja, a festékes mérés ehhez képest csak ellenőrzés: a kettő együtt elfogadható, önmagában egyik sem. A gyakorlatban a feladatok veremét elkülönített területre helyezzük, és minden feladathoz a statikus elemzés szerinti legrosszabb méretet rendeljük, rögzített, dokumentált ráhagyással.

23.3.5 5. Időzítési zárolás és analízis

Az időzítési zárolás (timing closure) azt a módszertani lépést jelenti, amikor a rendszer időzítési modelljének elemeit – a WCET-becsléseket, a megszakítási késleltetést, a veremkorlátokat és a rendszerterhelést – egyetlen, konzisztens, dokumentált állapotba zárjuk. A cél az, hogy a tervezési és mérési eredmények között ne legyen ellentmondás, és minden követelmény számszerűen ellenőrizhető legyen.

Az időzítési zárolás lépései:

  1. Feltételrögzítés: rögzítjük a hardverkonfigurációt (CPU típus, órajel, memória, gyorsítótár, perifériák), a fordító beállításait, az ütemező konfigurációt és a megszakítási prioritásokat.
  2. Korlátok összegyűjtése: minden feladathoz, ISR-hez és kritikus szakaszhoz felvesszük a WCET-et, a veremmélységet és a késleltetési korlátot.
  3. Terhelés-ellenőrzés: kiszámítjuk a rendszerterhelést és az ütemezési teszteket a becsült WCET-ekkel.
  4. Mérési ellenőrzés: a mért értékeket összevetjük a becsült korlátokkal. Ha a mért érték meghaladja a becsültet, a modell hibás, és újra kell nyitni az elemzést.
  5. Lezárás: ha minden ellenőrzés sikeres, a modellt lezárjuk, és a dokumentációban rögzítjük az érvényességi feltételeket.

Az időzítési zárolás akkor válik igazán fontossá, amikor a rendszer több csapata párhuzamosan fejleszt, vagy amikor egy későbbi változtatás hatását kell értékelni. A lezárt modell biztosítja, hogy a határidő-számítás nem légből kapott átlagokra, hanem dokumentált, konzisztens korlátokra épül.

23.3.6 6. Gyakorlati példa és tipikus hibák

Tekintsünk egy kis rendszert három periodikus feladattal:

Feladat Periódus TiT_i (ms) WCET CiC_i (µs) Prioritás
P1P_1 1 220 magas
P2P_2 5 800 közepes
P3P_3 20 4500 alacsony

A rendszerterhelés:

U=2201000+8005000+450020000=0,22+0,16+0,225=0,605. U = \frac{220}{1000} + \frac{800}{5000} + \frac{4500}{20000} = 0{,}22 + 0{,}16 + 0{,}225 = 0{,}605.

Implicit határidővel és független feladatokkal az RMS Liu–Layland-tesztje (0,605≤3(21/3−1)≈0,7800{,}605 \le 3(2^{1/3}-1) \approx 0{,}780) teljesül, sőt a periódusok harmonikusak (1, 5, 20 ms), így U≤1U \le 1 is elegendő. Blokkolás és megszakítási késleltetés esetén viszont a válaszidő-analízis kell (23.2.6): blokkolásmentesen R1=220R_1 = 220 µs, R2=800+2⋅220=1240R_2 = 800 + 2 \cdot 220 = 1240 µs, R3=4500+8⋅220+2⋅800=7860R_3 = 4500 + 8 \cdot 220 + 2 \cdot 800 = 7860 µs, mind a saját periódusa alatt (kézi számítás). Ezt a számítást rontják el a következő tipikus hibák:

  • Átlagos futási idő használata: ha P3P_3 átlagos ideje 3500 µs, de a legrosszabb ág 4500 µs, az átlaggal számított UU alacsonyabb, és a határidő-túllépés a ritka ágban következik be.
  • Megszakítási késleltetés elhanyagolása: ha a megszakítás-tiltott ablak a P1P_1 feladat felébresztését késlelteti, a magas prioritású feladat válaszideje megnő, és a határidő-túllépés a látszólag jó terhelés ellenére bekövetkezik.
  • Veremtúlcsordulás figyelmen kívül hagyása: ha a P3P_3 feladat egy ritka hívási láncban nagyobb veremmélységet ér el, mint amit a festékes mérés látott, a memóriakorrupció a rendszer nem determinisztikus összeomlását okozza.
  • Hiányos mérési terv: ha a mérés csak a tipikus bemeneteket fedi le, a maximális útvonal nem jelenik meg a mintában, és a becsült WCET alulmarad.

A helyes megoldás az időzítési zárolás: a WCET-et statikus analízissel és méréssel is meghatározzuk, a megszakítási késleltetést a leghosszabb kritikus szakaszból számítjuk, a veremmélységet statikusan és festéssel is ellenőrizzük, majd az összes korlátot egy konzisztens modellben zárjuk le.

23.3.7 7. Labor: WCET-becslési és mérési terv

23.3.8 7.1. Cél

Készítsen WCET-becslési és mérési tervet egy egyszerű, emulált feladat számára. A tervben válassza el a várt (levezetett) és a mért eredményt, és rögzítse a reprodukálhatóság feltételeit.

23.3.9 7.2. Kiinduló állapot

A labor két ágra bomlik. Az A) ág (kötelező, reprodukálható) hoszton fut, és a blokk-idő modellt értékeli ki egy CSV-ből; nem kell hozzá keresztfordító. A B) ág (opcionális, célhardveres) ugyanezt a feladatot futtatja QEMU-ban emulált Cortex-M3-on; ehhez teljes forrás- és buildkészlet kell, ezért külön szerepel.

  1. ág:
  • Hoszt: x86_64 Linux, gcc.
  • Bemenet: blocks.csv (a 23.3.2 szakasz blokk-idő táblázata).
  • Kimenet: a levezetett WCET.
  1. ág:
  • Hoszt: x86_64 Linux, QEMU 8.2 vagy újabb, arm-none-eabi-gcc 12.3.
  • Cél: QEMU által emulált ARM Cortex-M3 (LM3S6965EVB), szimulált órajel 50 MHz.
  • Szükséges fájlok: main.c (a task_control és a fir_filter), startup.c (vektortábla és Reset_Handler), systick.c (ellenőrzött időforrás), linker.ld.
  • A labor csak emulált környezetben fut, a hoszt lemezét nem módosítja.

23.3.10 7.3. Build parancs

  1. ág:
gcc -std=c11 -Wall -Wextra -O2 -o wcet_model wcet_model.c

A modell forrása:

/* wcet_model.c – a 23.3.2 szakasz blokk-idő modelljének reprodukálható számítása */
#include <stdio.h>

#define N_BLOCKS 7

int main(int argc, char **argv) {
    const char *path = (argc > 1) ? argv[1] : "blocks.csv";
    FILE *f = fopen(path, "r");
    if (!f) { perror(path); return 1; }

    double t[N_BLOCKS] = {0};
    char line[256];

    if (!fgets(line, sizeof line, f)) { fclose(f); return 1; }   /* fejléc */
    while (fgets(line, sizeof line, f)) {
        char name;
        double us;
        int n;
        if (sscanf(line, " %c,%lf,%d", &name, &us, &n) != 3) continue;
        if (name >= 'A' && name <= 'G')
            t[name - 'A'] = us * n;        /* a blokk összideje */
    }
    fclose(f);

    double fir     = t['B'-'A'] + t['C'-'A'] + t['D'-'A'];
    double p_true  = t['A'-'A'] + fir + t['E'-'A'] + t['F'-'A'];
    double p_false = t['A'-'A'] + fir + t['E'-'A'] + t['G'-'A'];
    double wcet    = (p_true > p_false) ? p_true : p_false;

    printf("fir_filter = %.3f us\n", fir);
    printf("task_control (igaz ag)  = %.3f us\n", p_true);
    printf("task_control (hamis ag) = %.3f us\n", p_false);
    printf("WCET (hosszabb ag)      = %.3f us\n", wcet);
    return 0;
}

A blocks.csv bemenet:

blokk,ido_us,darabszam
A,1.0,1
B,0.6,1
C,0.4,12
D,0.5,1
E,0.2,1
F,1.0,1
G,0.4,1
  1. ág:
arm-none-eabi-gcc -O2 -mcpu=cortex-m3 -mthumb -ffreestanding -nostdlib \
  -T linker.ld -Wl,--gc-sections \
  -o wcet_lab.elf main.c startup.c systick.c

A linker.ld minimális váza (flash 0x00000000, RAM 0x20000000):

ENTRY(Reset_Handler)
MEMORY {
  FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 256K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 64K
}
_estack = ORIGIN(RAM) + LENGTH(RAM);
SECTIONS {
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH
  .text       : { *(.text*) *(.rodata*) } > FLASH
  .data       : { _sdata = .; *(.data*) _edata = .; } > RAM AT > FLASH
  _sidata = LOADADDR(.data);
  .bss        : { _sbss = .; *(.bss*) *(COMMON) _ebss = .; } > RAM
}

A startup.c-ben a vektortábla első két szava kötelező: a kezdeti veremmutató (_estack) és a Reset_Handler címe. A Reset_Handler a .data szakaszt a flash-ből a RAM-ba másolja (_sidata → _sdata.._edata), nullázza a .bss-t (_sbss.._ebss), majd hívja a main-t. E nélkül a C változók nem inicializálódnak, és a mérés értelmezhetetlen.

Időforrás: a QEMU lm3s6965evb modelljében a SysTick használható; a DWT CYCCNT nem garantált. A SysTicket a processzorórára kell állítani, ismert reload értékkel:

/* systick.c – 1 ms-os tick 50 MHz-en (50 000 ciklus) */
#define SYST_CSR (*(volatile uint32_t *)0xE000E010u)
#define SYST_RVR (*(volatile uint32_t *)0xE000E014u)
#define SYST_CVR (*(volatile uint32_t *)0xE000E018u)

void time_init(void) {
    SYST_RVR = 49999u;   /* 50 000 ciklus - 1 */
    SYST_CVR = 0u;
    SYST_CSR = 0x7u;     /* processzoróra, megszakítás engedélyezve, indítás */
}

23.3.11 7.4. Futtatási parancs

  1. ág:
./wcet_model blocks.csv
  1. ág:
qemu-system-arm -M lm3s6965evb -icount shift=0,align=off -nographic -kernel wcet_lab.elf

A B) ágban QEMU alatt csak utasításszámot mérhetünk megbízhatóan: -icount mellett a SysTick-különbség a végrehajtott utasítások számával arányos (az -icount pontos beállításai a QEMU-verzió dokumentációjában ellenőrizendők). Ez az útvonal-lefedettség és a modell konzisztenciájának ellenőrzésére alkalmas, ciklusidejű WCET-hez nem, mert a QEMU nem ciklushű, és a -d in_asm fordításkori napló, nem végrehajtási számláló. A mérési pontok elhelyezése maga is többletköltséggel jár, ezért azt a jegyzőkönyvben rögzíteni kell.

23.3.12 7.5. Várt (levezetett) eredmény

A statikus blokkidő-modell alapján a task_control WCET-je 8,1 µs. A becslés feltételezi, hogy a memória-hozzáférés várakozás nélküli, a blokkidők a fenti oktatási feltételezések, és a fir_filter ciklusa pontosan 12 iterációt futtat. Az A) ág ezt az értéket számítja, nem méri; a B) ág ezzel szemben megfigyelést ad, amelyet a statikus értékkel össze kell vetni.

23.3.13 7.6. Mérési terv

A mérési terv a B) ágra vonatkozik; az A) ág determinisztikus, ezért ott nincs statisztikai mérés.

  1. Futtassuk a feladatot 10 000 alkalommal, minden futásban determinisztikus álvéletlen bemenettel.
  2. Minden futásnál rögzítsük a belépési és kilépési timestamp értékét.
  3. Készítsünk hisztogramot a futási időkről a timestamp felbontásának megfelelő lépésközzel.
  4. Jegyezzük fel a mért minimumot, maximumot, átlagot és a 99,9%-os percentilist.
  5. Töltsük ki az alábbi hárommezős mérési lapot.
Mező Jelentés
Megfigyelt maximum a 10 000 futás legnagyobb mért értéke; csak a lefedett bemenetekre érvényes
Feltételezett vagy igazolt felső korlát a statikus modellből (blokkidők + útvonal) számított érték, vagy statikus analízissel igazolt korlát
Nem fedett állapotok a mintából hiányzó bemenetek, gyorsítótár-állapotok, megszakítás-konfigurációk

Az értékelés szabálya aszimmetrikus, és csak célhardveres (DWT CYCCNT-tel vagy logikai analizátorral végzett) mérésre alkalmazható; QEMU-mérésre alkalmazva hamis cáfolatot vagy hamis összhangot adhat. Ha a megfigyelt maximum meghaladja a feltételezett felső korlátot, az a statikus becslést cáfolja: a blokkidő-modell vagy az útvonal-feltételezés hibás, és az elemzést újra kell nyitni. Ha a megfigyelt maximum a korlát alatt marad, az csak összeegyeztethető a becsléssel, nem bizonyítja azt, mert a minta nem feltétlenül fedte le a leghosszabb útvonalat. Tényleges felső korláthoz külön kell igazolni, hogy (a) az elemzett útvonal a leghosszabb, és (b) a hardverállapot a modellben feltételezett legrosszabb értéken van. A mintaszám növelése egyiket sem pótolja.

A mérési naplóban minden futtatási paramétert rögzíteni kell: QEMU verzió, -d kapcsolók, GCC verzió, órajel, bemenetgenerátor seedje, mintaszám.

Értékelési kérdés. Tegyük fel, hogy célhardveren, egy flash-wait-state-et okozó konfigurációban (vagy egy megszakítás közbeiktatásával) a mért futásidő 8,4 µs, ami meghaladja a statikus modell 8,1 µs-os korlátját. Melyik állítás dőlt meg: a megfigyelt maximum, a feltételezett felső korlát, vagy a kettő viszonya? Indokolja, és mondja meg, milyen további lépés szükséges.

23.3.14 7.7. Visszaállítás

A QEMU folyamat megszakítása (Ctrl-A X) után az emulált gép megszűnik, a hoszt fájlrendszere változatlan marad. A mérési adatokat a laboron kívüli munkakönyvtárban tároljuk.

23.3.15 8. Összefoglalás

A WCET, a megszakítási késleltetés és a veremszükséglet elemzése együttesen adja a valós idejű rendszer időzítési alapját. A WCET a feladat leghosszabb végrehajtási útjának felső korlátja, és nem az átlagos futási idő. A megszakítási késleltetés a hardveres és szoftveres összetevőkből származó felső korlát, amely a kritikus szakaszok hosszától és a megszakítás-tiltott ablakoktól függ. A veremszükséglet elemzés a memóriasértések megelőzését szolgálja. Az időzítési zárolás ezeket a korlátokat egy konzisztens, dokumentált modellbe zárja, amelyet méréssel ellenőrzünk.

Önellenőrző kérdések:

  1. Miért nem elegendő az átlagos futási idő a rendszerterhelés számításához?
  2. Mely összetevők alkotják a megszakítási késleltetést?
  3. Hogyan ellenőrzi a festékes mérés a veremmélységet, és mi a korlátja?
  4. Mi a szerepe az időzítési zárolásnak a WCET-becslés és a mérési eredmény összevetésében?

Mintaválasz / értékelési szempontok. (1) A határidő-túllépés a ritka, hosszú ágban következik be; az átlag a terhelést alulbecsli. (2) Hardveres késleltetés, megszakítás-tiltott ablak, ISR-belépési idő (hardveres mentés), szoftveres belépés. (3) Ismert mintázattal töltjük fel a vermet, és a legmélyebb felülírt címből számoljuk a használt mélységet; csak a megfigyelt (high-water mark) értéket adja, a ritka útvonalat nem látja. (4) Egy konzisztens, dokumentált modellbe zárja a WCET-, késleltetési és veremkorlátokat, és kimondja, hogy a mért érték a korlát fölött a modell hibáját jelenti. Az értékelési kérdésre: a feltételezett felső korlát dőlt meg (a statikus modell nem fedte a wait state-et/megszakítást); a további lépés a modell újranyitása és a hardverállapot-feltételezések felülvizsgálata.
