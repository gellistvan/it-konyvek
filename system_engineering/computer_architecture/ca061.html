18.3 Gyenge modellek: ARM és RISC-V

18.3.1 Motiváció

Egy kétmagos programban a termelő beírja az adatot, majd 1-re állítja a jelzőt; a fogyasztó addig olvassa a jelzőt, amíg 1-et nem lát, aztán olvassa az adatot. TSO: az x86 memóriamodellje alatt ez az MP-minta kerítés nélkül is helyes, és a laborgépen mintegy 9 millió ismétlésből egyszer sem hibázott. Ha ugyanezt a gépi kódot egy ARM- vagy RISC-V-processzoron futtatjuk, az architektúra megengedi, hogy a fogyasztó a jelzőt már 1-nek, az adatot viszont még a réginek lássa.

Ezt a könyv x86-os gépén nem tudjuk megmérni (ellenőrizendő: saját ARM-gépen a bench_litmus programmal), de modellel megmutathatjuk, melyik lépéssorozat vezet ide, és melyik utasítás zárja el az utat. Aki mobiltelefonra, beágyazott vezérlőre vagy ARM-szerverre fordít, ezen a modellen dolgozik.

18.3.2 Szemlélet

A gyenge vagy relaxált (weak, relaxed) memóriamodellben a programsorrend önmagában keveset ígér. Egy szál memóriaműveletei bármilyen sorrendben hathatnak, amelyet semmi sem tilt: sem azonos cím, sem kerítés, sem acquire/release jelölés, sem adatfüggőség. Gondoljunk a szál utasításaira úgy, mint egy teendőlistára, amelyben csak a nyíllal összekötött tételek sorrendje kötött. Az ábra a négy klasszikus tesztet mutatja különböző védelmekkel a három modellben.

Olvassuk soronként. A „csak P0: fence w,w” sor még megengedett: az üzenetátadásnak mindkét oldala hibázhat. A „vezérlési függőség” az MP fogyasztójánál nem véd, az LB-nél viszont igen. A release/acquire sor az SB-nél TSO alatt sárga marad, mert x86-on ezek a jelölések sima mov-ok.

18.3.3 A négy átrendezés

Két, különböző című memóriaművelet programsorrendi párja négyféle lehet. Mindegyik lazítást egy teszt mutatja ki:

Pár SC TSO gyenge Kimutató teszt
tárolás → betöltés (W→R) marad lazul lazul SB
tárolás → tárolás (W→W) marad marad lazul MP termelője
betöltés → betöltés (R→R) marad marad lazul MP fogyasztója, IRIW
betöltés → tárolás (R→W) marad marad lazul LB

A mikroarchitektúra felől nézve ezek hétköznapi optimalizálások: a tárolópuffer nem feltétlenül FIFO, ezért egy későbbi, találatos tárolás megelőzhet egy korábbi, hibás tárolást; a betöltések sorrenden kívül végezhetők el, és nem kell őket újrafuttatni, ha közben a sor érvénytelen lesz. Egyszálú program ebből semmit sem vesz észre.

18.3.4 Mi őrzi meg a sorrendet?

Definíció. A megtartott programsorrend (preserved program order, ppo) egy szál műveletpárjainak az a részhalmaza, amelyeknek a memóriasorrendben is a programsorrend szerint kell hatniuk.

A könyv egyszerűsített gyenge modellje egy a<pba <_{\text{p}} b párt a következő esetekben tart meg:

Szabály Mikor?
azonos cím kivéve tárolás → betöltés: ott a betöltés a saját, még nem látható tárolásból is olvashat
kerítés a kettő között olyan kerítés áll, amelynek előd-halmazában aa, utód-halmazában bb fajtája szerepel
acquire aa acquire betöltés: minden későbbi művelet utána hat
release bb release tárolás: minden korábbi művelet előtte hat
release → acquire aa release tárolás, bb acquire betöltés (az erős, ún. RCsc változat)
adat- és címfüggőség bb a tárolt értéket vagy a címet aa eredményéből számolja
vezérlési függőség aa eredményétől függő elágazás után álló bb tárolás

Az RCsc (release consistency, sequentially consistent) elnevezés azt jelzi, hogy a release és az acquire műveletek egymáshoz képest is sorban maradnak.

18.3.4.1 Függőségek

Definíció. Adatfüggőség: a bb tárolás értéke az aa betöltés eredményéből származik. Címfüggőség: bb címe származik belőle. Vezérlési függőség: aa eredménye dönti el egy bb előtti elágazás irányát.

A címfüggőség mesterségesen is előállítható: olyan eltolást adunk a címhez, amelynek értéke mindig 0, de a processzor nem „tudhatja” előre.

        # RISC-V: r2 = adat címfüggőséggel r1-től
        lw    a2, 0(a1)       # r1 = jelző
        xor   a3, a2, a2      # mindig 0, de függ r1-től
        add   a3, a0, a3
        lw    a4, 0(a3)       # r2 = adat

AArch64-en ugyanez: eor w3, w2, w2, majd ldr w4, [x0, w3, sxtw]. A vezérlési függőség a betöltéseket nem rendezi: a processzor az elágazást megjósolhatja, és a második betöltést spekulatívan, a jelző beérkezése előtt elvégezheti. Egy spekulatív tárolás viszont nem válhat láthatóvá, ezért a tárolást a vezérlési függőség is megköti.

18.3.5 Kerítések RISC-V-n és AArch64-en

A RISC-V fence utasítása két halmazt nevez meg: a fence pred, succ a kerítés előtti, pred típusú műveleteket (r, w) rendezi a kerítés utáni, succ típusúak elé. A fence rw,rw teljes memóriakerítés; a fence.tso az R→R, R→W és W→W párokat tartja meg, a W→R-t nem [S-RISCV-ISA]. Az A-kiterjesztés atomi utasításai (amoswap, amoadd, lr, sc) .aq (acquire) és .rl (release) jelölést kaphatnak. A sima betöltés és tárolás acquire/release alakja a Zalasr kiterjesztéshez tartozik: az LLVM 21 assemblere az lw.aq-t csak ennek engedélyezésével fogadja el (ellenőrizendő: a célprocesszor támogatja-e).

AArch64-en a dmb (data memory barrier) utasítás a kerítés: dmb ish teljes, dmb ishld a korábbi betöltéseket rendezi minden későbbi művelet elé, dmb ishst a tárolásokat a tárolások elé (az ish a közös memóriát látó magok körét, az inner shareable tartományt jelöli). Acquire és release formájú utasítás az ldar és az stlr; az Armv8.3-tól elérhető ldapr gyengébb acquire, amely egy korábbi stlr-től nem rendezett [S-ARM-DOC]. Az ARM-utasításkészlettel az ARM assembly könyv (books/dsk-arm-assembly) foglalkozik részletesen.

Ugyanaz az MP-minta a két ISA-n, a bal oldalon RISC-V, utána AArch64:

# RISC-V, termelő: a0 = &adat, a1 = &jelzo
        sw    t0, 0(a0)       # adat = 42
        fence rw, w           # release
        sw    t1, 0(a1)       # jelzo = 1
# RISC-V, fogyasztó
1:      lw    t0, 0(a1)       # jelzo
        beqz  t0, 1b
        fence r, rw           # acquire
        lw    t2, 0(a0)       # adat
// AArch64, termelő: x0 = &adat, x1 = &jelzo
        str   w2, [x0]        // adat = 42
        stlr  w3, [x1]        // jelzo = 1, release
// AArch64, fogyasztó
1:      ldar  w2, [x1]        // jelzo, acquire
        cbz   w2, 1b
        ldr   w3, [x0]        // adat

A termelő release-e azt mondja: „minden, amit eddig írtam, látszódjon a jelző előtt”. A fogyasztó acquire-je: „semmit se olvassak a jelző előtt, ami utána áll”. A kettő párban véd.

Továbbvitt eredmény. A release tárolás a korábbi műveleteket a tárolás elé, az acquire betöltés a későbbieket a betöltés mögé köti; RISC-V-n ez fence rw,w + sw, illetve lw + fence r,rw, AArch64-en stlr, illetve ldar. A fence rw,rw és a dmb ish teljes kerítés. Ezt a hardveres jelentést használja A hardver és a C++ memóriamodell, Atomi műveletek a hardverben az atomi utasítások .aq/.rl jelöléseinél, és Zárak és tranzakciós memória a zár megszerzésénél (acquire) és elengedésénél (release).

18.3.6 Többmásolatos atomicitás és az IRIW

Definíció. Egy modell többmásolatos atomicitású (multi-copy atomic), ha egy tárolás az összes többi mag számára egyszerre válik láthatóvá. A saját magja korábban is láthatja (ezt angolul other-multi-copy atomic néven is emlegetik).

Az IRIW (independent reads of independent writes) teszt két írót és két olvasót tartalmaz; a vizsgált kimenetben a két olvasó ellentétes sorrendben látja a két független írást. Többmásolatos atomicitás mellett ez csak úgy lehetséges, ha valamelyik olvasó a saját két betöltését rendezi át. Ezért elég mindkét olvasóba fence r,r (vagy címfüggőség). A mai ARMv8 és az RVWMO többmásolatos atomicitású; egyes régebbi gyenge architektúrákon, például a POWER-en, ez nem igaz, ott a betöltések rendezése nem elég [S-PRIMER].

18.3.7 RVWMO és ARMv8: a hivatalos modellek

A RISC-V memóriamodellje az RVWMO (RISC-V weak memory ordering) [S-RISCV-ISA]. Nem gépet ír le, hanem axiómákat: létezik egy globális memóriasorrend, amely megtartja a ppo szabályait (a specifikáció tizenhárom szabályt sorol fel); minden betöltés a programsorrendben vagy a globális sorrendben őt megelőző, legkésőbbi azonos című tárolás értékét kapja; az atomi műveletek oszthatatlanok; és minden tárolás előbb-utóbb láthatóvá válik. Az ARMv8 modellje hasonló felépítésű axiomatikus modell [S-ARM-DOC]. Mindkettőt a herd7 eszköz képes végrehajtani: a hivatalos modellfájlok alapján egy litmus-tesztre felsorolja a megengedett végrehajtásokat [S-HERD].

18.3.8 Az egyszerűsített modell és korlátai

Az archkit.consistency weak modellje ennél egyszerűbb gép: egyetlen közös memórián a szálak bármely olyan sorrendben hajtják végre műveleteiket, amely a fenti táblázat ppo-szabályait betartja, és egy betöltés a saját, még végre nem hajtott tárolásából is kaphat értéket. Tudnunk kell, mit nem tud:

  • Nem RVWMO és nem ARMv8. Hiányzik például az a szabály, hogy egy címfüggő művelet utáni minden későbbi tárolás is rendezett a függőség forrásához képest. Ilyen tesztnél a modell megengedhet olyat, amit az architektúra tilt (5. feladat).
  • Az azonos című betöltéseket mindig sorban tartja, ami egyes finom esetekben szigorúbb az architektúránál.
  • Nem kezeli az LR/SC párokat, a vegyes méretű hozzáféréseket, az eszközmemóriát, és AArch64 isb-t sem.

Tanulásra és a klasszikus tesztekre alkalmas; valódi, zármentes kód igazolására a herd7 és a specifikáció a mérvadó.

Egy kimenet tehát megengedett, ha van a ppo-t betartó végrehajtás, amely előállítja. Ha nincs, azt gyakran körérveléssel is beláthatjuk: a kimenet feltételezése a memóriasorrendben kört adna.

18.3.9 Kézi számpélda

MP védelem nélkül. A ppo üres: P0 két tárolása különböző című, P1 két betöltése is. A modell tehát választhat:

Lépés Esemény x y r1r_1 r2r_2
1 P0: y=1 (előreszalad) 0 1 – –
2 P1: r1=y 0 1 1 –
3 P1: r2=x 0 1 1 0
4 P0: x=1 1 1 1 0

MP fence w,w és fence r,r kerítéssel. A ppo most két párt tartalmaz: x=1 → y=1 és r1=y → r2=x. Tegyük fel, hogy r1=1r_1 = 1 és r2=0r_2 = 0. Ekkor a memóriasorrendben y=1 megelőzi r1=y-t, r2=x pedig x=1-et. A két ppo-párral:

x=1<my=1<mr1=y<mr2=x<mx=1. \text{x=1} <_{\text{m}} \text{y=1} <_{\text{m}} \text{r1=y} <_{\text{m}} \text{r2=x} <_{\text{m}} \text{x=1}.

Kör, tehát a kimenet tiltott. Bármelyik kerítést elhagyva a lánc egy szeme hiányzik, és a kör felszakad.

18.3.10 Kód

A ppo függvény megadja, mely párok maradnak sorban egy szálon, és miért:

import sys; sys.path.insert(0, "code")
from archkit import consistency as mm

demo = mm.litmus("p", "x=1; fence w,w; y=1; r1=z; r2=x [addr r1]; v=1")
th = demo.threads[0]
for (i, j), why in mm.ppo(th).items():
    print(f"{th[i].text:6} → {th[j].text:14} ({', '.join(why)})")
x=1    → y=1            (kerítés)
r1=z   → r2=x [addr r1] (addr)
x=1    → v=1            (kerítés)

Három pár maradt sorban. A kerítés az x=1 tárolást a két későbbi tároláshoz köti, a címfüggőség pedig a két betöltést egymáshoz. Az x=1 → r2=x pár hiányzik: azonos című tárolás–betöltés, amelyet a fence w,w sem rendez (az utód-halmaza csak tárolás), ezért a betöltés akár a még nem látható saját tárolásból is olvashat. Az r1=z és a v=1 között sincs kapcsolat.

Most keressük meg tesztenként azt a legszűkebb kerítéspárt, amely tiltja a vizsgált kimenetet:

from itertools import product

fences = ["", "fence w,w", "fence r,r", "fence r,w", "fence w,r", "fence rw,rw"]
cost = lambda f: len(f.split()[-1].replace(",", "")) if f else 0     # a két halmaz mérete
for name in ("SB", "MP", "LB", "IRIW"):
    base = mm.LITMUS[name]
    slots = [t for t, th in enumerate(base.threads) if len(th) == 2]
    good = []
    for combo in product(fences, repeat=len(slots)):
        test = base
        for t, f in zip(slots, combo):
            test = test.insert(t, 1, f) if f else test
        if not mm.explore(test, "weak").allowed:
            good.append((sum(map(cost, combo)), combo))
    _, best = min(good)
    print(f"{name:5}", ", ".join(f"P{t}: {f}" for t, f in zip(slots, best)))
SB    P0: fence w,r, P1: fence w,r
MP    P0: fence w,w, P1: fence r,r
LB    P0: fence r,w, P1: fence r,w
IRIW  P2: fence r,r, P3: fence r,r

A keresés visszaadja a táblázat logikáját: minden teszthez pontosan azt a párt kell megtartani, amelyet a kör használ.

18.3.11 Próbáld ki

  1. Az ábra lapján a Teszt legyen MP. A P0 védelme legyen „fence w,w”, a P1 védelme maradjon „nincs”. Olvasd el a panel „végrehajtási sorrend” listáját: melyik betöltés szaladt előre?
  2. Állítsd a P1 védelme mezőt előbb „vezérlési függőség”, majd „címfüggőség” értékre. Miért csak a második tilt?
  3. Válts SB-re, nyomd meg a Védelmek törlése gombot, majd válaszd mindkét szálban a „release / acquire” védelmet. Miért tér el a TSO és a gyenge modell ítélete?
  4. IRIW-nél adj P2 és P3 olvasónak védelmet egyesével; a Védelmek törlése gombbal kezdd újra. Elég-e egy?

18.3.12 Tipikus hibák

  • Tünet: a termelőben van kerítés, a fogyasztó mégis régi adatot olvas. Ok: a másik oldal betöltései átrendeződnek. Javítás: release a termelőben és acquire a fogyasztóban.
  • Tünet: „az if (jelzo) megvédi az adatolvasást.” Ok: a vezérlési függőség a betöltést nem rendezi, a processzor spekulál. Javítás: acquire betöltés vagy fence r,rw a jelző után.
  • Tünet: x86-on hibátlan kód ARM-on ritkán elromlik. Ok: a tesztgép erősebb modellje elfedi a hiányzó rendezést. Javítás: az algoritmust a célmodellen (vagy a C++ modellen) igazold, ne a fejlesztőgép viselkedésén.
  • Tünet: fence.tso-t írunk az SB-minta közé, és nem segít. Ok: a fence.tso a W→R párt nem rendezi. Javítás: fence rw,rw (vagy legalább fence w,r).

18.3.14 Feladatok

  1. (A) Az LB teszten döntsd el a gyenge modellben: (a) csak P0-ban fence r,w; (b) P0-ban adatfüggőség, azaz P0: r1=x; y=r1, P1-ben vezérlési függőség a tárolás előtt. Lehet-e az (b) esetben mindkét regiszter 1?
  2. (A) Írd fel RISC-V-n és AArch64-en a legkisebb kerítéseket, amelyek az SB-t megvédik.
  3. (B) Mutasd meg a modellel, hogy az SB-t az stlr + ldar páros (RCsc) megvédi, az stlr + ldapr nem.
  4. (B) Körérveléssel bizonyítsd be, hogy IRIW-ben címfüggőséggel mindkét olvasóban a vizsgált kimenet tiltott. Hol használod a többmásolatos atomicitást?
  5. (C, programozós) Vizsgáld a következő tesztet: P0: r1=y; r2=z [addr r1]; x=1, P1: r3=x; fence r,w; y=1, vizsgált: r1=r3=1r_1 = r_3 = 1. Mit mond a modell? Mit mondana az a szabály, hogy a címfüggő művelet utáni tárolás is a függőség forrása után hat?

18.3.15 Rövid összefoglaló

Gyenge modellben (ARMv8, RVWMO) egy szál különböző című műveletei mind a négy párosításban (W→R, W→W, R→R, R→W) átrendeződhetnek. A sorrendet a megtartott programsorrend őrzi: azonos cím, kerítés, acquire/release, adat- és címfüggőség; vezérlési függőség csak tárolásokra. RISC-V-n a release fence rw,w + tárolás, az acquire betöltés + fence r,rw; AArch64-en stlr és ldar; teljes kerítés a fence rw,rw és a dmb ish. Az üzenetátadás mindkét oldala védelmet igényel. A mai ARMv8 és az RVWMO többmásolatos atomicitású, ezért IRIW-hez a betöltések rendezése elég. A könyv weak modellje tanulóeszköz, hiányos; mérvadó a specifikáció és a herd7.

18.3.16 Megoldások

18.3.16.1 Válaszok az önellenőrző kérdésekre

  1. W→R, W→W, R→R és R→W (különböző címek között).
  2. Előd-halmaz: betöltések; utód-halmaz: betöltések és tárolások. A korábbi betöltések minden későbbi művelet előtt hatnak.
  3. A spekulatív betöltés eredménye eldobható, ha a jóslat hibás, a spekulatív tárolás viszont nem tehető láthatóvá, mert nem vonható vissza.
  4. Azt, hogy a két olvasó a két írást magától a memóriától kapja ellentétes sorrendben; ehhez saját betöltéseit kell átrendeznie.
  5. Például a címfüggőség utáni tárolásokra vonatkozó szabályt és az LR/SC párokat (továbbá vegyes méretű hozzáférést, isb-t).

18.3.16.2 A feladatok megoldásai

1.

a = mm.LB.insert(0, 1, "fence r,w")
b = mm.litmus("LB+data+ctrl", "r1=x; y=r1", "r2=y; x=1 [ctrl r2]", cond="r1 == 1 and r2 == 1")
for t in (a, b):
    print(t.name, mm.explore(t, "weak").allowed)
LB True
LB+data+ctrl False
  1. Megengedett: P1 tárolása még mindig megelőzheti a betöltését. (b) Tiltott: mindkét tárolás kötve van a saját betöltéséhez (adat-, illetve vezérlési függőséggel), így a kör teljes.

2. Mindkét szálban, a tárolás és a betöltés közé: RISC-V fence w,r (vagy rw,rw); AArch64 dmb ish. A dmb ishld és dmb ishst nem elég, mert egyik sem rendez tárolást betöltés elé.

3.

sb = mm.SB.annotate(0, 0, "rel").annotate(1, 0, "rel")
for note in ("acq", "acqpc"):
    t4 = sb.annotate(0, 1, note).annotate(1, 1, note)
    print(f"stlr + {note:6} → megengedett: {mm.explore(t4, 'weak').allowed}")
stlr + acq    → megengedett: False
stlr + acqpc  → megengedett: True

Az acq az ldar, az acqpc az ldapr modellje.

4. Tegyük fel r1=1r_1 = 1, r2=0r_2 = 0, r3=1r_3 = 1, r4=0r_4 = 0. Egyetlen közös memóriasorrend van (ez a többmásolatos atomicitás), ezért: x=1 << r1=x << r2=y (címfüggőség) << y=1 (mert r2=0r_2 = 0) << r3=y << r4=x (függőség) << x=1 (mert r4=0r_4 = 0). Kör. Ha egy írás magonként más időben válhatna láthatóvá, a két olvasó láncát nem lehetne egy sorrendbe fűzni.

A modell megengedi, mert x=1-et semmi sem köti r1=y-hoz. Az RVWMO-ban (és az ARMv8-ban is) a címfüggő művelet utáni tárolás a függőség forrása után hat: amíg r2=z címe ismeretlen, a processzor nem tudhatja, nem ugyanarra a címre mutat-e, mint x. Ezzel r1=y → x=1 megmarad, és a kör y=1 → r1=y → x=1 → r3=x → y=1 tiltaná. Ez a modell kimondott korlátja.
