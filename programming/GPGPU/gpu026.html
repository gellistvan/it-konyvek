8.1 Blokk-szintű szinkronizáció

A blokkon belüli szálak akkor tudnak hatékonyan együttműködni, ha van egy közös, gyors adatterületük – ez jellemzően a shared memory. A shared memory azonban csak akkor válik használhatóvá, ha a szálak írásai és olvasásai között megfelelő sorrendet biztosítunk. Erre szolgál a CUDA blokk-szintű szinkronizációs eszköze, a __syncthreads().

8.1.1 A __syncthreads szemantikája

A __syncthreads() egy blokk-szintű barrier, azaz szinkronizációs korlát. A hívás helye a kernel végrehajtásában egy olyan pontot jelöl ki, ahol a blokk minden szála találkozik. Amikor egy szál eléri a __syncthreads() hívást, nem lép tovább addig, amíg a blokk összes többi szála is el nem érte ugyanezt a hívást. Amint minden szál elérte a barriert, mindegyikük folytathatja a végrehajtást.

A __syncthreads() kettős szerepet tölt be:

  1. Végrehajtási szinkronizáció: biztosítja, hogy a barrier előtti utasítások minden szálon befejeződjenek, mielőtt bármelyik szál a barrier utáni utasításokat elkezdené.
  2. Memória-láthatóság: a barrier előtti írások – akár global memory-ba, akár shared memory-ba – a barrier után minden szál számára láthatóvá válnak. Ez a blokk szintű memória-konzisztencia alapja.

Az alábbi ábra a 8.1.2 block_sum_kernel-jének sematikus idővonalán mutatja a barrier két szerepét, valamint az elfelejtett és a divergens barrier következményét.

Fontos, hogy a __syncthreads() csak a blokkon belül szinkronizál. Különböző blokkok szálai nem találkoznak ezen a barrieren; a blokkok közötti szinkronizációhoz más eszközökre van szükség (például kernelhatárokra vagy a később tárgyalt cooperative groups-ra).

A __syncthreads() a CUDA C++ nyelvi kiterjesztés része, és nem igényel külön include-ot. A hívásnak a blokk minden (nem kilépett) szála által elérhetőnek kell lennie. A blokk legfeljebb 1024 szálas lehet; a rögzített méretű shared tömbbel dolgozó kerneleknél (pl. sdata[256]) a blokkméretnek ennél nem nagyobbnak kell lennie, különben a kód túlindexel. A __syncthreads_count, __syncthreads_and és __syncthreads_or változatok a barrier mellett a feltétel teljesülését is összegzik a blokkon, a __syncwarp() pedig egyetlen warpra vonatkozó barrier. A hívás szintaxisa egyszerű:

__syncthreads();

A függvény nem ad vissza értéket, és nem fogad paramétert. A hívás során a szál felfüggeszti a végrehajtását, amíg a blokk többi szála is el nem éri ugyanezt a hívást.

8.1.2 Szinkronizációs pontok a kernelben

A __syncthreads() hívások a kernel logikai szakaszokra bontását teszik lehetővé. Egy tipikus minta a következő:

  1. Minden szál betölt egy értéket a global memory-ból a shared memory-ba.
  2. A szálak elérik a __syncthreads() barriert.
  3. A barrier után minden szál a shared memory-ban lévő, már teljesen feltöltött adatokat használja.

Ez a minta biztosítja, hogy egyik szál se kezdjen el olyan shared memory-beli adatot olvasni, amelyet egy másik szál még nem írt meg. A barrier előtti és utáni szakaszok közötti határvonalat szinkronizációs pontnak nevezzük.

Tekintsük a következő egyszerű példát, amelyben egy blokk szálai egy-egy lebegőpontos értéket írnak a shared memory-ba, majd a 0. szál összegzi azokat:

__global__ void block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    // Betöltés global memory-ból shared memory-ba
    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    // Szinkronizációs pont: minden szál befejezte az írást
    __syncthreads();

    // A 0. szál összegzi a blokk részösszegét
    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

Ebben a kernelben a __syncthreads() előtt minden szál a saját sdata[tid] rekeszébe ír. A barrier nélkül a 0. szál elkezdhetné az összegzést, mielőtt a többi szál befejezte volna az írást, ami versenyhelyzetet okozna. A __syncthreads() garantálja, hogy az összegzés csak akkor kezdődik el, amikor a teljes sdata tömb már feltöltődött.

A szinkronizációs pontok száma és elhelyezése jelentős hatással van a teljesítményre. Minden barrier várakozást jelenthet, ha a blokk szálai nem egyszerre érkeznek. Ezért a szinkronizációs pontokat tudatosan kell elhelyezni, és kerülni kell a felesleges hívásokat.

8.1.3 A __syncthreads korlátai

A __syncthreads() használatának szigorú szabályai vannak. A leggyakoribb hibák az alábbi korlátok figyelmen kívül hagyásából adódnak.

8.1.3.1 Feltételes hívás és divergens barrier

A __syncthreads()-et a blokk minden szálának el kell érnie. Ha a hívás egy feltételes ágban van, akkor a feltételnek a blokk minden szálára azonosan kell kiértékelődnie. Ellenkező esetben a viselkedés meghatározatlan (undefined behavior): holtpont, hibás eredmény vagy látszólag helyes működés is lehet; Volta és újabb architektúrán (független szálütemezés) és a kilépett szálak kezelése miatt a holtpont nem garantált. A compute-sanitizer --tool synccheck az ilyen hibákat jelzi.

A következő kód hibás:

__global__ void wrong_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid < n) {
        sdata[tid] = data[tid];
        __syncthreads();  // HIBA: nem minden szál éri el
    }

    // ... további feldolgozás
}

Ha n < blockDim.x, akkor a tid >= n szálak nem lépnek be az if ágba, így nem hívják a __syncthreads()-et. A belépő szálak viszont olyan barrieren várnak, amelyet a többi szál nem ér el, ami holtponthoz, hibás működéshez vagy látszólag helyes futáshoz vezethet (meghatározatlan viselkedés). Még ha n éppen egyenlő is a blokkmérettel, a kód akkor is veszélyes, mert a feltétel a szálak indexétől függ, és a jövőbeli módosítások során könnyen hibássá válhat.

A helyes megoldás az, hogy a barrier a feltételes ágon kívül helyezkedik el, így minden szál eléri:

__global__ void correct_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid < n) {
        sdata[tid] = data[tid];
    }
    __syncthreads();  // Minden szál eléri

    // ... további feldolgozás
}

Ebben a változatban a feltétel csak azt befolyásolja, hogy mely szálak írnak a shared memory-ba, de a barrier minden szál számára közös. Ez biztosítja, hogy az írások befejeződése után minden szál továbbléphessen.

8.1.3.2 Különböző ágakban elhelyezett barrierek

Előfordulhat, hogy a fejlesztő több __syncthreads() hívást helyez el, például egy if-else szerkezet két ágában. Ez akkor helyes, ha a feltétel minden szálra azonosan értékelődik ki. Ha azonban a feltétel szálanként eltérő, akkor a két ág szálai nem ugyanazon a barrieren találkoznak, ami meghatározatlan viselkedést (többek között holtpontot) okozhat. Ezért a barriereket lehetőleg a feltételes szerkezeteken kívül kell elhelyezni, vagy biztosítani kell, hogy a feltétel a teljes blokkra nézve egységes legyen.

8.1.3.3 Ciklusok és változó iterációszám

Hasonló probléma léphet fel, ha a __syncthreads() egy olyan ciklusban van, amelynek iterációszáma szálanként eltérő. Például:

__global__ void wrong_loop_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;       // feltétel: blockDim.x <= 256
    sdata[tid] = 0.0f;

    for (int i = tid; i < n; i += blockDim.x) {
        sdata[tid] += data[i];
        __syncthreads();  // HIBA: az iterációszám szálanként eltérő lehet
    }
}

Itt a szálak különböző számú iterációt hajthatnak végre (például n = 300, blockDim.x = 256 esetén a 0–43. szál kétszer, a többi egyszer éri el a barriert), így a barrierhívások száma eltér, ami meghatározatlan viselkedést (holtpont, hibás eredmény) okoz. A megoldás az, hogy a ciklust úgy szervezzük, hogy minden szál azonos számú iterációt végezzen, vagy a barriert a cikluson kívülre helyezzük, esetleg a ciklus előtt és után.

A helyes változat egységes iterációszámot használ, és a határellenőrzést a ciklus belsejébe teszi:

__global__ void correct_loop_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;       // feltétel: blockDim.x <= 256
    sdata[tid] = 0.0f;
    int iters = (n + blockDim.x - 1) / blockDim.x;   // minden szálra azonos
    for (int it = 0; it < iters; ++it) {
        int i = it * blockDim.x + tid;
        if (i < n) sdata[tid] += data[i];
        __syncthreads();      // minden szál ugyanannyiszor éri el
    }
}

Itt minden szál iters iterációt végez, így a barrierhívások száma minden szálon azonos.

8.1.3.4 Nem blokkok közötti szinkronizáció

A __syncthreads() nem alkalmas arra, hogy különböző blokkok szálait szinkronizálja. A blokkok egymástól függetlenül futnak, és a GPU ütemezője nem garantálja, hogy minden blokk egyszerre van jelen az SM-eken. Ezért a blokkok közötti szinkronizációhoz más mechanizmusok szükségesek, például a kernel befejezése és egy új kernel indítása, vagy a cooperative groups grid-szintű szinkronizációja (amelyet a későbbi fejezetben tárgyalunk).

8.1.3.5 A blokkméret hatása

A __syncthreads() a teljes blokkra vonatkozik, ezért a blokkméret növelése növeli a barrier várakozási idejét is, ha a szálak nem egyszerre érkeznek. A blokkméret növelése a barrier miatt önmagában nem okoz helyességi problémát, csak teljesítménycsökkenést, de az erőforrás-korlátok miatt az indítás meghiúsulhat (pl. too many resources requested for launch), és a rögzített méretű sdata[256] kerneleknél 256-nál nagyobb blokk túlindexelést okoz. A blokkméretet az erőforrás-korlátok (regiszterek, shared memory) és a feldolgozási logika alapján kell megválasztani.

8.1.3.6 A __syncthreads hardveres háttere

Bár a __syncthreads() magas szintű absztrakciónak tűnik, a hardveren a barrier a blokk warpjainak szinkronizálásával valósul meg. Minden blokk warpokból áll, és a barrier akkor teljesül, ha a blokk összes warpja elérte a barriert. Az SM-en a warpütemező figyeli a warpok állapotát; amikor egy warp a barrierhez ér, várakozó állapotba kerül. Amint az utolsó warp is megérkezik, az összes warp felszabadul, és folytathatja a végrehajtást.

Fontos, hogy amíg egy blokk várakozik a barrieren, az SM más blokkokat is futtathat. Ez azt jelenti, hogy a barrier nem feltétlenül okoz üresjáratot a hardveren, ha elegendő másik blokk van, amelyekkel az SM ki tudja tölteni a várakozási időt. Ez a latency hiding része, amelyet a későbbi fejezetekben részletesen tárgyalunk.

A __syncthreads() a PTX szinten egy bar.sync utasításnak felel meg. A PTX ISA dokumentációja leírja, hogy a barrier a blokk szintjén működik, és a szálak elérik a barriert. A CUDA C++ fordító ezt az utasítást generálja, és a hardver hajtja végre.

8.1.4 Gyakori hibák és megelőzésük

A fenti korlátokon túl érdemes áttekinteni a leggyakoribb hibákat, amelyek a __syncthreads() használatával kapcsolatban felmerülnek.

8.1.4.1 Elfelejtett barrier

A leggyakoribb hiba, amikor a fejlesztő shared memory-ba ír, majd szinkronizáció nélkül olvassa azt egy másik szálból. Ez versenyhelyzetet okoz, mert az olvasó szál még azelőtt olvashat, hogy az író szál befejezte volna az írást. A tünet gyakran nem determinisztikus: a program néha helyes eredményt ad, néha hibásat, attól függően, hogy az ütemező milyen sorrendben futtatta a szálakat. A megoldás mindig az, hogy az írás és az olvasás közé __syncthreads() kerüljön.

8.1.4.2 Felesleges barrier

Bár a __syncthreads() hasznos, a felesleges hívások fölösleges várakozást okozhatnak. Ha nincs szükség arra, hogy minden szál befejezze az írást a következő olvasás előtt, akkor a barrier elhagyható. Például ha minden szál csak a saját sdata[tid] rekeszét írja és olvassa, akkor nincs szükség barrierre. A barrierre akkor van szükség, ha egy szál más szál által írt adatot olvas. Tévhit, hogy egy warpon belül a szálak implicit szinkronban futnak: Volta+ architektúrán ez nem garantált, a warpon belüli szinkronizációhoz __syncwarp() kell.

8.1.4.3 A barrier utáni feltételezések

A __syncthreads() csak a blokkon belüli láthatóságot garantálja. Nem szabad feltételezni, hogy a barrier után a global memory-ba írt adatok más blokkok számára is láthatóvá válnak. A blokkok közötti láthatósághoz kernelhatár vagy más szinkronizációs mechanizmus szükséges.

8.1.4.4 A __syncthreads() hiánya az elágazás után

Gyakori minta, hogy a szálak egy feltételes részben dolgoznak, majd a feltételes rész után közös kód következik, amely a feltételes részben módosított shared memory-t használja. Ilyenkor a feltételes rész után szükség van egy __syncthreads()-re, mert a közös kód más szálak által írt adatot olvas, és a barrier garantálja, hogy ezek az írások befejeződtek és láthatók. (A példában a feltételes részben nincs barrier; a barrier a közös kód elé kerül, a feltételes szerkezeten kívülre.)

Például:

__global__ void example_kernel(float* data, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;

    if (tid % 2 == 0) {
        sdata[tid] = data[tid] * 2.0f;
    } else {
        sdata[tid] = data[tid] * 0.5f;
    }

    __syncthreads();  // Szükséges, mert a közös kód minden sdata elemet olvas

    // Közös feldolgozás, amely az sdata minden elemét használja
    float val = sdata[(tid + 1) % blockDim.x];
    // ...
}

Itt a __syncthreads() nélkül az sdata[(tid + 1) % blockDim.x] olvasása versenyhelyzetet okozna.

8.1.5 Labor: shared memory-t használó kernel szinkronizálása

A labor célja a __syncthreads() helyes használatának bemutatása egy egyszerű, ellenőrizhető példán keresztül. A feladat egy olyan kernel írása, amely egy blokkban összegzi a bemeneti tömb elemeit úgy, hogy a szálak először a saját értéküket a shared memory-ba írják, majd a barrier után a 0. szál kiszámítja az összeget. A labor szándékosan egyszerű: a 0. szál egymaga összegez 256 elemet; a hatékony, faalapú redukcióval a későbbi fejezetek foglalkoznak. A kernel futását CUDA eventekkel mérjük, és az eredményt a CPU által számított referenciaértékkel hasonlítjuk össze.

8.1.5.1 Kernel implementáció

A korábban bemutatott block_sum_kernel alkalmas erre a célra. Az alábbiakban a teljes CUDA C++ programot adjuk meg, amely tartalmazza a hibakezelést és a mérést is.

#include <cuda_runtime.h>
#include <iostream>
#include <vector>
#include <numeric>
#include <cmath>
#include <cstdlib>

// Hibakezelő makró
#define CUDA_CHECK(call)                                                      \
    do {                                                                      \
        cudaError_t err = (call);                                             \
        if (err != cudaSuccess) {                                             \
            std::cerr << "CUDA hiba: " << cudaGetErrorString(err)             \
                      << " (" << __FILE__ << ":" << __LINE__ << ")"           \
                      << std::endl;                                           \
            std::exit(EXIT_FAILURE);                                          \
        }                                                                     \
    } while (0)

// Kernel: blokkszintű összegzés shared memory-val és __syncthreads()-szel
__global__ void block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    // Betöltés global memory-ból shared memory-ba
    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    // Szinkronizációs pont: minden szál befejezte az írást
    __syncthreads();

    // A 0. szál összegzi a blokk részösszegét
    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

int main() {
    const int N = 1024;          // Bemeneti elemek száma
    const int BLOCK_SIZE = 256;  // Blokkméret
    const int GRID_SIZE = (N + BLOCK_SIZE - 1) / BLOCK_SIZE;

    // Bemeneti adatok előkészítése
    std::vector<float> h_input(N);
    std::iota(h_input.begin(), h_input.end(), 0.0f); // 0, 1, 2, ..., N-1
    float h_output[GRID_SIZE] = {0.0f};

    float* d_input;
    float* d_output;
    CUDA_CHECK(cudaMalloc(&d_input, N * sizeof(float)));
    CUDA_CHECK(cudaMalloc(&d_output, GRID_SIZE * sizeof(float)));
    CUDA_CHECK(cudaMemcpy(d_input, h_input.data(), N * sizeof(float),
                          cudaMemcpyHostToDevice));

    // CUDA eventek az időméréshez
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    // Warm-up
    block_sum_kernel<<<GRID_SIZE, BLOCK_SIZE>>>(d_input, d_output, N);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaDeviceSynchronize());

    // Mérés: 10 ismétlés
    const int REPEAT = 10;
    float total_time_ms = 0.0f;
    float times_ms[REPEAT];
    for (int i = 0; i < REPEAT; ++i) {
        CUDA_CHECK(cudaEventRecord(start));
        block_sum_kernel<<<GRID_SIZE, BLOCK_SIZE>>>(d_input, d_output, N);
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaEventRecord(stop));
        CUDA_CHECK(cudaEventSynchronize(stop));
        float elapsed_ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&elapsed_ms, start, stop));
        times_ms[i] = elapsed_ms;
        total_time_ms += elapsed_ms;
    }

    float avg_time_ms = total_time_ms / REPEAT;
    float variance_ms = 0.0f;
    for (int i = 0; i < REPEAT; ++i) {
        variance_ms += (times_ms[i] - avg_time_ms) * (times_ms[i] - avg_time_ms);
    }
    float std_ms = std::sqrt(variance_ms / (REPEAT - 1));   // minta-szórás (n-1)

    // Eredmény visszamásolása
    CUDA_CHECK(cudaMemcpy(h_output, d_output, GRID_SIZE * sizeof(float),
                          cudaMemcpyDeviceToHost));

    // Referencia számítás CPU-n
    float ref_sum = std::accumulate(h_input.begin(), h_input.end(), 0.0f);

    // GPU összegzés: a blokkok részösszegeit összegezzük
    float gpu_sum = 0.0f;
    for (int i = 0; i < GRID_SIZE; ++i) {
        gpu_sum += h_output[i];
    }

    // Ellenőrzés
    float abs_err = std::fabs(gpu_sum - ref_sum);
    std::cout << "Referencia összeg (CPU): " << ref_sum << "\n";
    std::cout << "GPU összeg:              " << gpu_sum << "\n";
    std::cout << "Abszolút hiba:           " << abs_err << "\n";
    std::cout << "Átlagos kernel idő:      " << avg_time_ms << " ms\n";
    std::cout << "Szórás (n-1):            " << std_ms << " ms\n";
    std::cout << "Ismétlések száma:        " << REPEAT << "\n";

    if (abs_err < 1e-3f) {
        std::cout << "Ellenőrzés: SIKERES\n";
    } else {
        std::cout << "Ellenőrzés: SIKERTELEN\n";
    }

    // Takarítás
    CUDA_CHECK(cudaFree(d_input));
    CUDA_CHECK(cudaFree(d_output));
    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));

    return 0;
}

8.1.5.3 Mérési napló

A mérés protokollja: 1 warm-up hívás, utána 10 mért ismétlés, cudaEvent időzítéssel; a program az iterációnkénti időkből átlagot és minta-szórást (n−1) számol. A kódot nem fordítottuk és nem futtattuk, ezért az időkre és a mért eredményre nincs adatunk; a táblázat sablon, a várt érték az aritmetikából következik, a mért értékeket a futtatás után kell kitölteni. 8.1.5.4 A divergens __syncthreads hiba szemléltetése

A labor során – csak izolált környezetben, timeouttal – kipróbálható egy hibás változat is, de a kimenetele meghatározatlan: lefagyhat, hibás eredményt adhat, vagy látszólag helyesen futhat. Ehhez a block_sum_kernel egy módosított változatát használjuk, ahol a __syncthreads() egy feltételes ágba kerül:

__global__ void wrong_block_sum_kernel(const float* input, float* output, int n) {
    __shared__ float sdata[256];
    int tid = threadIdx.x;
    int idx = blockIdx.x * blockDim.x + tid;

    sdata[tid] = (idx < n) ? input[idx] : 0.0f;

    if (tid == 0) {
        __syncthreads();  // HIBA: csak a 0. szál éri el
    }

    if (tid == 0) {
        float sum = 0.0f;
        for (int i = 0; i < blockDim.x; ++i) {
            sum += sdata[i];
        }
        output[blockIdx.x] = sum;
    }
}

Ha ezt a kernelt futtatjuk, a viselkedés meghatározatlan: a 0. szál várakozhat egy barrieren, amelyet a többi szál nem ér el (ilyenkor a kernel nem tér vissza, és a cudaDeviceSynchronize() blokkol), de a kernel hibás eredménnyel is visszatérhet. Az ilyen hibák az eszköz leállásához vezethetnek, ezért a laborban izolált környezetben, timeout beállításával szabad csak kipróbálni. A mérési környezetben a nvidia-smi és a konténer erőforrás-korlátai biztosítják, hogy a hiba ne érintse a többi felhasználót.

A hibás kernel futtatása előtt ellenőrizzük a GPU állapotát, és legyen terv a visszaállításra (például a CUDA context megszakítása vagy a folyamat leállítása). A jelenség megértése segít elkerülni a hasonló hibákat a valós kódban.

8.1.6 Önellenőrző kérdés

Mi történik, ha a következő kódot futtatjuk?

__global__ void faulty_kernel() {
    __shared__ float sdata[64];
    int tid = threadIdx.x;

    if (tid % 2 == 0) {
        sdata[tid] = 1.0f;
        __syncthreads();
    }

    // ...
}

Válasz: A páros tid-vel rendelkező szálak belépnek az if ágba, és elérik a __syncthreads() hívást, míg a páratlan szálak nem. A páros szálak a barrierhez érnek, a páratlanok nem. A viselkedés meghatározatlan: holtpont, hibás eredmény vagy látszólag helyes működés is lehet (nem garantált a holtpont), és a GPU leállhat. A hiba a compute-sanitizer --tool synccheck eszközzel kimutatható. A helyes megoldás az, ha a __syncthreads() a feltételes ágon kívülre kerül.

8.1.7 Összefoglalás

A __syncthreads() a CUDA blokk-szintű szinkronizáció alapvető eszköze. Megfelelő használatával biztosítható, hogy a blokk szálai által közösen használt shared memory-ban lévő adatok konzisztensek legyenek. A barrier előtti írások a barrier után minden szál számára láthatóvá válnak, és a barrier garantálja, hogy minden szál befejezte a barrier előtti utasításokat. A __syncthreads() azonban szigorú szabályokhoz kötött: minden szálnak el kell érnie ugyanazt a hívást, és a hívás nem lehet feltételes ágban, ha a feltétel nem egységes a blokkra nézve. A divergens barrier meghatározatlan viselkedést okoz (holtpont, hibás eredmény vagy látszólag helyes működés). A helyes minta az, hogy a szinkronizációs pontokat a feltételes szakaszokon kívül, a logikai fázisok határára helyezzük, és a barriereket tudatosan, a szükségességük szerint alkalmazzuk. A következő alfejezet az atomi műveletekre épít, amelyek a szinkronizáció alternatíváját kínálják olyan esetekben, amikor a barrier nem elegendő vagy nem hatékony.
