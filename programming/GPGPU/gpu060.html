16.3 Histogram

A hisztogram a párhuzamos számítás egyik leggyakoribb építőköve: adott egy bemeneti sorozat és egy véges számú rekesz (bin); minden elemhez hozzárendelünk egy rekeszt, majd megszámoljuk, hány elem esik az egyes rekeszekbe. Az eredmény egy gyakorisági eloszlás, amelyet képfeldolgozásban (színtónus-hisztogram), statisztikai elemzésben, gépi tanulási jellemzők számításakor és szimulációkban is használunk. GPU-n a hisztogram számítása elsőre egyszerűnek tűnik: minden szál feldolgoz egy elemet, és növeli a megfelelő rekesz számlálóját. A kihívást az jelenti, hogy több szál egyszerre ugyanabba a rekeszbe írhat – ezt a versenyhelyzetet atomi műveletekkel vagy privatizációval kezeljük. Ez az alfejezet a hisztogram mint atomi és privatizált művelet fogalmát járja körbe, bemutatja a blokkszintű privatizációt, elemzi a shared memory bank conflict és az atomi kontenció jelenségét, és egy laborfeladaton keresztül mérhetővé teszi a megközelítések teljesítményét. A hisztogram tipikus alkalmazásai: 256 rekeszes képfeldolgozási hisztogram, lebegőpontos adatok binningje, és a CUB DeviceHistogram könyvtári megoldása (a CUB általános használatát a következő alfejezet, a 16.4 mutatja be; a cub::DeviceHistogram::HistogramEven hívását a CUB dokumentációja írja le).

16.3.1 A hisztogram mint atomi művelet

A legegyszerűbb GPU-s megvalósításban minden bemeneti elemhez egy szál tartozik. A szál kiszámítja az elem rekeszindexét, majd egy atomi összeadást hajt végre a globális memóriában tárolt hisztogramtömbön. Az atomicAdd garantálja, hogy az olvasás-módosítás-írás műveletsor oszthatatlan, így a végeredmény helyes marad még akkor is, ha több szál egyszerre ugyanabba a rekeszbe ír.

A naiv kernel CUDA C++-ban:

// CUDA C++ (C++17)
constexpr int NUM_BINS = 64;

__global__ void hist_naive(const int* data, int* hist, int n)
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;

    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&hist[bin], 1);
    }
}

A grid-stride loop lehetővé teszi, hogy a kernel akkor is lefusson a teljes bemenetet, ha az elemszám nagyobb, mint az indított szálak száma. A bin számítása itt a % operátorral történik; ha a rekeszek száma kettő hatványa, bitművelettel (& (NUM_BINS-1)) gyorsabban elvégezhető, de az általánosság kedvéért a modulo marad.

A naiv megoldás előnye a rendkívüli egyszerűség: nincs szükség bonyolult szinkronizációra, a kód kevés sorból áll, és az atomi műveletek garantálják a helyes eredményt. Hátránya viszont a súlyos teljesítményprobléma: ha sok elem esik ugyanabba a rekeszbe, a globális memóriában lévő hist[bin] címre irányuló atomi műveletek sorosítva hajtódnak végre. A globális atomi művelet egy read-modify-write ciklus, amely a memóriavezérlőn keresztül megy; nagy kontenció esetén a szálak várakozni kényszerülnek, és a kernel átbocsátóképessége drasztikusan lecsökken. Erősen ferde eloszlásnál a naiv atomi megoldás a kontenció miatt várhatóan lassabb a privatizált változatnál; a különbség mértéke eszköz- és eloszlásfüggő (a Maxwell óta a shared memory atomikus műveletei natívak, az L2 atomik is gyorsak), ezért mérni kell.

16.3.2 Privatizált hisztogram: blokkszintű shared memory

A kontenció csökkentésének alapötlete az, hogy a globális atomi műveleteket részben kiváltjuk gyorsabb, blokkon belüli műveletekkel. Minden szálblokk saját, privát hisztogramot tart fenn a shared memóriában. A blokk szálai a bemeneti elemek feldolgozása során csak ebbe a privát tömbbe írnak atomi módon. A blokk végén, egy __syncthreads() után a privát hisztogramot egyetlen globális atomi összeadással egyesítik a globális hisztogrammal. Így a globális atomi műveletek száma blokkonként NUM_BINS darabra csökken, szemben a naiv megoldás N darabjával.

Az alábbi ábra a labor három változatának adatútját foglalja össze: hol keletkeznek az atomi műveletek, hány éri el a globális memóriát, és hol áll a két __syncthreads().

A privatizált kernel:

// CUDA C++ (C++17)
__global__ void hist_shared(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS];

    // 1. A privát hisztogram inicializálása nullára
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    // 2. Feldolgozás: atomi összeadás a shared memóriában
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&shist[bin], 1);
    }
    __syncthreads();

    // 3. A privát hisztogram egyesítése a globális tömbbel
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i]);
    }
}

A shared memóriás atomicAdd lényegesen gyorsabb, mint a globális megfelelője, mert a shared memória a blokkhoz közeli, nagy sávszélességű memória, és az atomi művelet hardveres támogatása is hatékonyabb. Ráadásul a globális atomi műveletek száma N-ről blokkok száma × NUM_BINS-re csökken, ami a memóriavezérlő terhelését mérsékli.

A privatizált megoldás korlátja a shared memória mérete. A NUM_BINS * sizeof(int) értéknek bele kell férnie a blokk számára elérhető shared memória keretbe (statikusan legfeljebb 48 KiB; ennél nagyobb dinamikus shared memory csak cudaFuncSetAttribute-tal kérhető, és a felső korlát compute capability-függő, lásd a CUDA Programming Guide Compute Capabilities táblázatát). Ha a rekeszek száma nagyon nagy (például több ezer), akkor a privát hisztogram nem fér el, és részleges privatizációra vagy többszintű megoldásra van szükség. Ilyenkor az egyik lehetőség, hogy a rekeszeket csoportokra osztjuk, és blokkonként csak egy csoportot tárolunk shared memóriában; a feldolgozást többször is elvégezzük, vagy a bemenetet partícionáljuk.

A blokkméret és a gridméret megválasztása is fontos. A grid-stride loop használatával a grid méretét a rezidens kapacitáshoz igazíthatjuk: grid = SM-szám × rezidens blokk/SM, ahol az utóbbit a cudaOccupancyMaxActiveBlocksPerMultiprocessor adja (256 szálas blokknál CC 8.6/8.9-en 6, mert egy SM legfeljebb 1536 szálat tart rezidensen; ellenőrzendő a célgép compute capabilityje és a kernel regiszterhasználata szerint). Ez a perzisztens kernel mintája: a blokkok száma a hardver rezidens kapacitásával egyezik, és minden blokk több bemeneti elemet dolgoz fel. Így a globális atomi műveletek száma (blokkok száma × NUM_BINS) lényegesen kisebb a bemenet méreténél, és elkerüljük a túl sok blokk indítási költségét. A block méretet úgy érdemes megválasztani, hogy az occupancy magas legyen, de a shared memória foglalása ne korlátozza túlzottan az aktív blokkok számát. Jelen példában NUM_BINS=64 és blockDim.x=256 esetén a shared memória 256 bájt, ami elhanyagolható; a blokk méretét a feldolgozási teljesítmény és a regiszterhasználat határozza meg.

16.3.3 Bank conflict és atomi kontenció a privatizált hisztogramban

A shared memória 32 bankra van osztva; minden bank egy 4 bájtos szót szolgál ki ciklusonként. A hisztogramban a shist[bin] elérések címei adatfüggők, és két különböző jelenség léphet fel:

  • Azonos bin (azonos szó): az atomi műveletek ugyanarra a címre sorosítva hajtódnak végre; ez atomi kontenció, nem bank conflict.
  • Különböző bin, azonos bank: például 64 rekesz esetén a 0. és a 32. bin ugyanabba a bankba esik (bin % 32), de különböző szó; ez bank conflict, a hozzáférések több lépésben szolgálódnak ki.

Ezért a hisztogram ütközései nem szüntethetők meg egyszerű címtranszformációval. A klasszikus padding (index + index / 32) a soros, szabályos stride-ú hozzáférések ütközését szünteti meg (például a scan-nél), a véletlen címzésű hisztogramét nem. Ugyanez igaz a szorzós „padding”-re: ha a bin indexet egy páratlan számmal (pl. 5-tel) szorozzuk, a bank = (5 · bin) mod 32 leképezés kölcsönösen egyértelmű mod 32, vagyis két bin pontosan akkor ütközik, ha bin_a ≡ bin_b (mod 32) – ugyanazok a párok, mint a szorzás nélkül –, miközben ötszörös shared memóriát foglalunk. Ez a megoldás tehát nem csökkenti az ütközések számát, ezért nem is mutatjuk be kernelként.

Az alábbi ábra egy warp 32 atomicAdd(&shist[bin], 1) kérését képezi le a 32 bankra négy bemenetnél: az azonos binre irányuló kérések sorosított atomi frissítést, az azonos bankba eső különböző szavak bank conflictot okoznak, és az 5-ös szorzó ugyanazokat a párokat ütközteti.

A tényleges csökkentési technikák:

  1. Per-warp privatizáció (replikáció): minden warp saját hisztogram-másolatot kap (shist[WARPS_PER_BLOCK][NUM_BINS]), így a warpok nem versengenek egymással; a blokk végén a másolatokat összegezzük. A warpon belüli azonos-bin kontenciót ez nem szünteti meg.
  2. Warp-szintű aggregáció: a __match_any_sync (CC 7.0+) a warpon belül azonos bin-t kereső szálakat csoportosítja, és csoportonként egyetlen szál egyetlen atomicAdd-del adja hozzá a csoport méretét. Ez a warpon belüli azonos-bin kontenciót csökkenti.
  3. A rekeszek számától függően regiszterben tartott (kis rekeszszámnál) számlálók.

A laborban az 1. technikát (per-warp replikáció) mérjük a naiv és a blokkszintű privatizált változat mellett. A shared atomikus műveletek és a bank conflict hatását Nsight Compute-tal lehet ellenőrizni (az atomikus shared műveletekre vonatkozó ..._op_atom metrikacsalád tagjai, például l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_atom.sum; a pontos metrikanevet a telepített verzióban ncu --query-metrics adja meg). A ..._op_ld metrika csak a betöltéseket számolja, ezért atomikus hisztogramnál nem informatív.

16.3.4 Tipikus hibák és helyes megoldások

A hisztogram implementálása során több gyakori hiba fordul elő. Az első a shared memória inicializálásának elmulasztása. A shist tömb tartalma definiálatlan, ha nem nullázzuk minden blokk elején, ezért a végeredmény szeméttel szennyezett lesz. A helyes megoldás a fenti kódban látható ciklus, amely a blokk minden szálával párhuzamosan nullázza a tömb elemeit, majd __syncthreads() hívás következik.

A második tipikus hiba a szinkronizáció elhagyása. A privatizált kernelben két __syncthreads() hívásra van szükség: az első biztosítja, hogy az inicializálás befejeződjön, mielőtt bármely szál elkezdi a feldolgozást; a második pedig garantálja, hogy minden szál befejezte a privát hisztogram frissítését, mielőtt a blokk elkezdi az egyesítést. Ha ezek hiányoznak, a szálak versenyt futnak egymással, és az eredmény nemdeterminisztikus lesz.

A harmadik hiba az out-of-range bin index. Ha a bemeneti adatok negatívak lehetnek, az int % operátor eredménye negatív szám is lehet (C++-ban a maradék előjele az osztandó előjelét követi), ami a tömb határain kívülre mutat. A helyes megoldás a bemeneti értékek normalizálása, unsigned modulo, vagy bitmaszk használata: kettes komplemensben az & (NUM_BINS - 1) negatív bemenetre is nem negatív indexet ad, de más leképezést ad, mint a %, ezért a CPU-referenciának ugyanazt a leképezést kell használnia. A laborban determinisztikus bemenetet használunk, ahol ez a hiba nem fordul elő, de éles kódban mindig védeni kell.

A negyedik hiba a shared memória méretének túlbecslése. Ha a rekeszek száma nagy, a __shared__ deklaráció meghaladhatja a statikus shared memória limitet. Ilyenkor fordítási hibát kapunk, vagy a kernel nem indul el. A megoldás a dinamikus shared memória (extern __shared__) használata, a rekeszek csoportosítása, vagy a probléma átdolgozása többmenetes feldolgozássá.

Az ötödik hiba a mérési módszertan hiányossága, és a nullázás elhagyása az ismételt méréseknél. A hisztogram kernel hozzáadja az eredményt a globális tömbhöz, ezért minden indítás előtt nullázni kell (cudaMemset), különben a tömb a futások számával arányosan nő. Minden mérés előtt legalább 5 warm-up futás, majd legalább 20 mért ismétlés kell cudaEvent-tel; a mediánt és a szórást (vagy IQR-t) közöljük. A futásidő önmagában nem elegendő, mert a GPU órajele és a háttérterhelés ingadozhat. A laborban ezt a módszertant követjük.

Végül érdemes megemlíteni a % művelet költségét. Ha a rekeszek száma kettő hatványa, a modulo helyettesíthető bitművelettel: bin = data[idx] & (NUM_BINS - 1);. Ez gyorsabb, de csak akkor alkalmazható, ha a rekeszszám ténylegesen kettő hatványa; negatív bemenetre a leképezés eltér a %-étől (lásd fent). A laborban NUM_BINS = 64, így ezt a trükköt is kipróbálhatjuk.

16.3.5 Labor: hisztogram atomi műveletekkel és privatizációval

A labor célja a naiv atomi, a blokkszintű privatizált és a per-warp privatizált hisztogram mérése több bemeneti eloszláson. Az alábbi forrás histogram.cu néven menthető, és CUDA C++ (C++17) nyelven fordul (statikusan átnézett, nem futtatott kód).

16.3.5.1 Teljes forráskód

// CUDA C++ (C++17)
// histogram.cu – hisztogram atomicsal és privatizált shared memory-val
#include <algorithm>
#include <cstdint>
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>
#include <cuda_runtime.h>

// a könyv kanonikus hibamakrója (1.2)
#define CUDA_CHECK(call)                                                        \
    do {                                                                        \
        cudaError_t err = (call);                                               \
        if (err != cudaSuccess) {                                               \
            std::fprintf(stderr, "CUDA hiba: %s:%d: %s\n", __FILE__, __LINE__,  \
                         cudaGetErrorString(err));                              \
            std::exit(EXIT_FAILURE);                                            \
        }                                                                       \
    } while (0)

constexpr int NUM_BINS = 64;
constexpr int N = 1 << 20;          // 1 048 576 elem
constexpr int BLOCK_SIZE = 256;
constexpr int WARPS_PER_BLOCK = BLOCK_SIZE / 32;

// --- Naiv globális atomics ---
__global__ void hist_naive(const int* data, int* hist, int n)
{
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&hist[bin], 1);
    }
}

// --- Blokkszintű privatizáció (shared memory) ---
__global__ void hist_shared(const int* data, int* hist, int n)
{
    __shared__ int shist[NUM_BINS];
    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        shist[i] = 0;
    }
    __syncthreads();

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&shist[bin], 1);
    }
    __syncthreads();

    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        atomicAdd(&hist[i], shist[i]);
    }
}

// --- Per-warp privatizáció: minden warp saját hisztogram-másolatot kap ---
__global__ void hist_shared_warp(const int* data, int* hist, int n)
{
    __shared__ int shist[WARPS_PER_BLOCK][NUM_BINS];   // 8 * 64 * 4 = 2 KiB
    int* flat = &shist[0][0];
    for (int i = threadIdx.x; i < WARPS_PER_BLOCK * NUM_BINS; i += blockDim.x) {
        flat[i] = 0;
    }
    __syncthreads();

    const int warp = threadIdx.x >> 5;
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int stride = gridDim.x * blockDim.x;
    for (; idx < n; idx += stride) {
        int bin = data[idx] % NUM_BINS;
        atomicAdd(&shist[warp][bin], 1);
    }
    __syncthreads();

    for (int i = threadIdx.x; i < NUM_BINS; i += blockDim.x) {
        int sum = 0;
        for (int w = 0; w < WARPS_PER_BLOCK; ++w) sum += shist[w][i];
        atomicAdd(&hist[i], sum);
    }
}

// --- CPU referencia ---
void cpu_histogram(const std::vector<int>& data, std::vector<int>& hist)
{
    std::fill(hist.begin(), hist.end(), 0);
    for (int v : data) hist[v % NUM_BINS]++;
}

// --- Bemeneti eloszlások (determinisztikus) ---
const char* DIST_NAMES[] = {"periodikus (i % 64)", "egyenletes véletlen",
                            "minden elem azonos", "ferde (kb. 90% a 0. binbe)"};
void fill_input(std::vector<int>& d, int dist)
{
    uint32_t x = 12345u;                          // LCG
    for (int i = 0; i < (int)d.size(); ++i) {
        x = x * 1664525u + 1013904223u;
        switch (dist) {
            case 0: d[i] = i % NUM_BINS; break;
            case 1: d[i] = (x >> 16) % NUM_BINS; break;
            case 2: d[i] = 7; break;
            default: d[i] = ((x >> 8) % 10 < 9) ? 0 : (int)((x >> 16) % NUM_BINS); break;
        }
    }
}

// --- Időmérés CUDA eventekkel; minden indítás előtt nullázás ---
void run_kernel(void (*kernel)(const int*, int*, int),
                const int* d_data, int* d_hist, int n,
                int grid_size, int block_size, int num_iter,
                cudaStream_t stream, float& median_ms, float& sd_ms)
{
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    // Warm-up (10 indítás, mindegyik előtt nullázás)
    for (int w = 0; w < 10; ++w) {
        CUDA_CHECK(cudaMemsetAsync(d_hist, 0, NUM_BINS * sizeof(int), stream));
        kernel<<<grid_size, block_size, 0, stream>>>(d_data, d_hist, n);
    }
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaStreamSynchronize(stream));

    std::vector<float> t(num_iter);
    for (int i = 0; i < num_iter; ++i) {
        CUDA_CHECK(cudaMemsetAsync(d_hist, 0, NUM_BINS * sizeof(int), stream));
        CUDA_CHECK(cudaEventRecord(start, stream));
        kernel<<<grid_size, block_size, 0, stream>>>(d_data, d_hist, n);
        CUDA_CHECK(cudaEventRecord(stop, stream));
        CUDA_CHECK(cudaEventSynchronize(stop));
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaEventElapsedTime(&t[i], start, stop));
    }
    // A d_hist az utolsó (egyetlen nullázott) indítás eredményét tartalmazza.
    double m = 0.0, v = 0.0;
    for (float x : t) m += x;
    m /= num_iter;
    for (float x : t) v += (x - m) * (x - m);
    std::vector<float> sorted(t);
    std::sort(sorted.begin(), sorted.end());
    median_ms = 0.5f * (sorted[num_iter / 2 - 1] + sorted[num_iter / 2]);   // páros num_iter
    sd_ms = (float)std::sqrt(v / (num_iter - 1));
    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));
}

int main()
{
    int device = 0, sm_count = 0;
    CUDA_CHECK(cudaGetDevice(&device));
    CUDA_CHECK(cudaDeviceGetAttribute(&sm_count, cudaDevAttrMultiProcessorCount, device));
    // perzisztens grid: SM-szám x rezidens blokk/SM (a legkisebb a három kernel közül)
    int blocks_per_sm = 0;
    {
        int b = 0;
        CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks_per_sm, hist_naive, BLOCK_SIZE, 0));
        CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&b, hist_shared, BLOCK_SIZE, 0));
        if (b < blocks_per_sm) blocks_per_sm = b;
        CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&b, hist_shared_warp, BLOCK_SIZE, 0));
        if (b < blocks_per_sm) blocks_per_sm = b;
    }
    const int grid_size = sm_count * blocks_per_sm;
    const int num_iter = 20;                      // mért ismétlés (a warm-up: 5 vagy több, itt 10)

    int *d_data, *d_hist;
    CUDA_CHECK(cudaMalloc(&d_data, N * sizeof(int)));
    CUDA_CHECK(cudaMalloc(&d_hist, NUM_BINS * sizeof(int)));
    cudaStream_t stream;
    CUDA_CHECK(cudaStreamCreate(&stream));

    struct Variant { const char* name; void (*fn)(const int*, int*, int); };
    const Variant variants[] = {{"naiv", hist_naive},
                                {"shared", hist_shared},
                                {"shared/warp", hist_shared_warp}};

    std::printf("Hisztogram labor (N=%d, B=%d, block=%d, grid=%d)\n",
                N, NUM_BINS, BLOCK_SIZE, grid_size);
    std::printf("%-30s %-12s %-10s %-10s %-8s\n",
                "Eloszlás", "Változat", "Medián (ms)", "Szórás", "Helyes?");

    for (int dist = 0; dist < 4; ++dist) {
        std::vector<int> h_data(N), h_ref(NUM_BINS), h_out(NUM_BINS);
        fill_input(h_data, dist);
        cpu_histogram(h_data, h_ref);
        CUDA_CHECK(cudaMemcpy(d_data, h_data.data(), N * sizeof(int),
                              cudaMemcpyHostToDevice));
        for (const Variant& v : variants) {
            float median_ms, sd_ms;
            run_kernel(v.fn, d_data, d_hist, N, grid_size, BLOCK_SIZE,
                       num_iter, stream, median_ms, sd_ms);
            CUDA_CHECK(cudaMemcpy(h_out.data(), d_hist, NUM_BINS * sizeof(int),
                                  cudaMemcpyDeviceToHost));
            bool ok = (h_out == h_ref);
            std::printf("%-30s %-12s %-10.4f %-10.4f %-8s\n", DIST_NAMES[dist],
                        v.name, median_ms, sd_ms, ok ? "igen" : "NEM");
        }
    }

    CUDA_CHECK(cudaStreamDestroy(stream));
    CUDA_CHECK(cudaFree(d_data));
    CUDA_CHECK(cudaFree(d_hist));
    return 0;
}

16.3.5.4 Kiegészítő lehetőségek

A labor bővíthető a következőkkel:

  • OpenCL implementáció: az OpenCL C-ben a atomic_add függvény hasonlóan működik, a local memória használatával. A kernel szerkezete szinte azonos, csak a memóriamodell és a szinkronizáció (barrier(CLK_LOCAL_MEM_FENCE)) különbözik. A méréshez az OpenCL időmérőit (clGetEventProfilingInfo) használhatjuk.
  • JAX implementáció: a JAX-ben a jax.lax.segment_sum vagy az jax.numpy.bincount függvény hasonló műveletet végez, de ott a háttérben az XLA fordítja a kódot GPU/TPU kernelre. A hisztogram ott is atomi műveleteket vagy redukciót használ, és a teljesítmény az eszköztől függ.
  • Warp-szintű aggregáció: a hist_shared_warp kiegészítése __match_any_sync-kel (CC 7.0+), és a hatás mérése a ferde eloszláson.
  • Nsight Compute: a shared atomik és a bank conflict metrikák (..._op_atom család, nevek: ncu --query-metrics) összehasonlítása a kernelek között.
  • CUB DeviceHistogram: könyvtári referencia a helyesség és a teljesítmény összevetéséhez (a CUB általános kétlépcsős hívási mintáját a 16.4 mutatja be; a HistogramEven paraméterezését a CUB dokumentációja adja, ellenőrizendő a telepített verzióban).

16.3.6 Összefoglalás és önellenőrző kérdés

Ebben az alfejezetben megvizsgáltuk a hisztogram két GPU-s megvalósítását: a naiv, globális atomi műveleteken alapuló megoldást és a blokkszintű privatizációt, amely a kontenció csökkentésére shared memóriát használ. Bemutattuk a shared memória bank conflict és az azonos-bin atomi kontenció különbségét, valamint azt, hogy a padding nem old meg adatfüggő ütközéseket; a per-warp replikáció és a warp-szintű aggregáció a használható technikák. A laborban egy teljes CUDA C++ program (nem futtatott, statikusan átnézett) segítségével mérhető a három megközelítés teljesítménye több eloszláson, és ellenőrizhető a helyesség a CPU referencia alapján.

Önellenőrző kérdés: Miért gyorsabb a blokkszintű privatizált hisztogram, mint a közvetlen globális atomi összeadás, és milyen feltételek mellett nem érvényesül ez az előny? (Válasz: mert a globális atomi műveletek sorosítják a hozzáférést a memóriavezérlőn, míg a shared memóriás atomi műveletek gyorsak és blokkon belül maradnak; az előny akkor csökken, ha a rekeszek száma olyan nagy, hogy a shared memória nem fér el, vagy ha a bank conflict miatt a shared memória hozzáférés is sorosítódik, illetve ha a bemeneti eloszlás nagyon egyenletes és a kontenció eleve kicsi. A shared memóriás atomik ütközései adatfüggők: azonos bin atomi kontenciót, különböző bin azonos bankban bank conflictot okoz.)
