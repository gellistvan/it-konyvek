30.2 Work-group, barrier és local memory

Az OpenCL végrehajtási modelljének középpontjában a work-group áll: ez az a szerveződési szint, ahol a work-itemek egymással szinkronizálhatnak, és ahol a local memory megosztott tárolóként jelenik meg. A work-group fogalma analóg a CUDA thread blockjával, de az OpenCL terminológiája és egyes részletszabályai sajátosak.

30.2.1 A work-group mint a szinkronizáció alapegysége

Az OpenCL kernel indításakor a host egy N-dimenziós indexteret (NDRange) ad meg. Az NDRange felosztható work-groupokra; minden work-group azonos méretű, és a work-itemeket a csoport indexével azonosítjuk. A work-group méretét a kernel indításakor a clEnqueueNDRangeKernel local_work_size paraméterében adjuk meg (a C++ burkolóban az enqueueNDRangeKernel local paramétere). A work-itemek a következő beépített függvényekkel kérdezhetik le saját helyüket:

  • get_global_id(dim) – a work-item globális azonosítója az adott dimenzióban.
  • get_local_id(dim) – a work-item azonosítója a work-groupön belül.
  • get_group_id(dim) – a work-group azonosítója.
  • get_local_size(dim) – a work-group mérete.
  • get_num_groups(dim) – a work-groupok száma.
  • get_global_size(dim) – a teljes indexméret.
  • get_work_dim() – az NDRange dimenzióinak száma.

Ezek a függvények lehetővé teszik, hogy a kernel a globális indexből kiszámítsa a feldolgozandó adatelem helyét. Az 1D-s esetben a következő azonosság érvényes:

global_id = group_id * local_size + local_id

Többdimenziós esetben minden dimenzióra külön kell elvégezni ezt a számítást. A work-group méretét a get_local_size értéke adja; ez a kernel indításakor rögzített, és a kernel belsejében csak lekérdezhető, nem módosítható.

A work-groupok egymástól függetlenül hajtódnak végre: az ütemező bármilyen sorrendben futtathatja őket, akár párhuzamosan, akár sorosan. Ezért a globális szinkronizáció nem megoldható a work-groupok között a kernel belsejében; az OpenCL nem definiál grid-szintű barriert. A work-groupön belüli szinkronizáció viszont a barrier függvénnyel lehetséges, és ez az együttműködés alapegysége. A work-groupok közötti adatcsere csak a kernel befejeződése után, a globális memórián keresztül, vagy atomi műveletekkel oldható meg, de ez utóbbi nem garantálja a teljes szinkronizációt.

30.2.2 Local memory: a work-group gyors memóriája

A local memory az OpenCL memóriamodelljének az a rétege, amely egy work-groupön belül osztozik. A CUDA shared memory megfelelője, azzal a különbséggel, hogy az OpenCL terminológiájában a local a work-group láthatóságú memóriát jelöli, míg a private a work-item saját változóit. A local memory a device-on belüli gyors, alacsony késleltetésű tároló, amelynek mérete korlátozott; a tipikus GPU-kon néhány tíz KiB (például 48–96 KiB) áll rendelkezésre work-groupönként. A pontos méretet a CL_DEVICE_LOCAL_MEM_SIZE eszközadat adja meg.

A local memory a kernelben a __local minősítővel jelölhető. Kétféleképpen allokálható:

  1. Statikus allokáció a kernelben: a kernel törzsében __local float tile[256]; alakban. A méretnek fordítási időben ismert konstansnak kell lennie.
  2. Dinamikus allokáció kernelargumentumként: a kernel egy __local float* paramétert kap, és a host a kernel indítása előtt megadja a méretet bájtban. Ez lehetővé teszi, hogy ugyanaz a kernel különböző work-group méretekkel fusson anélkül, hogy újra kellene fordítani.

A következő kernelrészlet dinamikus local memóriát használ:

// Fordítás: OpenCL C 1.2+
__kernel void use_local(__global const float* input,
                        __global float* output,
                        __local float* tile) {
    int lid = get_local_id(0);
    int gid = get_global_id(0);
    tile[lid] = input[gid];
    // ... további feldolgozás
}

A host oldalon a local memória méretét a clSetKernelArg hívással adjuk meg; az argumentum értéke NULL, a méret pedig a szükséges bájtok száma:

// OpenCL C API (host oldal)
clSetKernelArg(kernel, 2, local_bytes, nullptr);

A local_bytes értéke például workgroup_size * sizeof(float). Fontos, hogy a local memória mérete nem haladhatja meg az eszköz által támogatott maximumot, és a kernel által igényelt local memória mérete befolyásolja az occupancyt: minél nagyobb local memóriát foglal egy work-group, annál kevesebb work-group lehet egyszerre aktív egy compute uniton.

A local memory élettartama a work-group végrehajtásához kötött; amikor a work-group befejeződik, a local memória tartalma elvész. A host közvetlenül nem férhet hozzá; az adatokat a kernelnek kell feltöltenie a globális memóriából, és az eredményt a kernelnek kell visszaírnia.

30.2.3 Barrier és memóriakerítés

A barrier függvény a work-groupön belüli szinkronizáció eszköze. A hívás azt jelenti, hogy a work-group minden work-itemjének el kell érnie a barriert, mielőtt bármelyikük továbbhaladhat. A barrier(flags) hívás kötelező memóriakerítési zászlót kap (CLK_LOCAL_MEM_FENCE és/vagy CLK_GLOBAL_MEM_FENCE, szükség esetén |-pal kombinálva):

  • CLK_LOCAL_MEM_FENCE: a local memóriába írt adatoknak a work-group többi work-itemje számára láthatóvá kell válniuk.
  • CLK_GLOBAL_MEM_FENCE: a globális memóriába írt adatoknak a work-group többi work-itemje számára kell láthatóvá válniuk.

A memóriakerítés nélkül a work-itemek által végrehajtott írások sorrendje nem garantált; a barrier biztosítja, hogy a barrier előtti írások befejeződjenek, mielőtt a barrier utáni olvasások megkezdődnek.

A legegyszerűbb és leggyakoribb minta a következő:

// 1. Minden work-item betölt egy értéket a local memóriába
tile[lid] = input[gid];

// 2. Barrier: minden betöltésnek be kell fejeződnie
barrier(CLK_LOCAL_MEM_FENCE);

// 3. Most már olvasható a local memória
float value = tile[(lid + 1) % get_local_size(0)];  // a határon túli olvasás elkerülése

A barrier nélkül az egyik work-item olvashatná a local memóriát, mielőtt a másik work-item befejezte volna az írást, ami nem determinisztikus és hibás eredményhez vezet.

A fa-alapú redukcióban a barriert minden iterációban meg kell hívni:

for (int offset = local_size / 2; offset > 0; offset >>= 1) {
    if (lid < offset) {
        tile[lid] += tile[lid + offset];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
}

Az alábbi ábra egy 8 elemes work-group redukciójának lépéseit és a barrierek helyét mutatja.

Itt a barrier azért szükséges, mert a következő iterációban a work-itemek a tile[lid + offset] értéket olvassák, amelyet az előző iterációban egy másik work-item írhatott. A barrier garantálja, hogy az összes írás befejeződött, mielőtt bármely work-item a következő iterációba lép.

A barrier használatakor a leggyakoribb hiba a divergens barrier. Ez akkor fordul elő, ha a barrier hívása feltételes ágban van, és nem minden work-item éri el. Például a következő kód hibás:

// HIBÁS: a barrier csak azoknak fut le, akik beléptek az if ágba
if (lid < offset) {
    tile[lid] += tile[lid + offset];
    barrier(CLK_LOCAL_MEM_FENCE); // <-- hibás!
}

A fenti esetben a barrier nem garantálja, hogy minden work-item eléri; a work-group viselkedése nem definiált, tipikusan holtpont vagy hibás eredmény. A helyes megoldás az, hogy a barriert a feltételes ágon kívül, minden work-item által végrehajtott helyen hívjuk:

if (lid < offset) {
    tile[lid] += tile[lid + offset];
}
barrier(CLK_LOCAL_MEM_FENCE); // <-- helyes

Általános szabály, hogy a kernelben a barrier hívásoknak a work-group minden work-itemje által elérhető úton kell lenniük. A fordító nem mindig figyelmeztet a divergens barrierre, ezért a fejlesztő felelőssége a helyes használat.

30.2.4 Bank conflict a local memoryben

A local memory a GPU-kon bankokra oszlik, hogy a párhuzamos hozzáférést gyorsítsa. A tipikus kialakítás 32 bank, mindegyik 32 bites szóval. Ha egy wavefront (NVIDIA-terminológiában warp) work-itemjei egyszerre ugyanabba a bankba, de különböző címekre próbálnak írni vagy olvasni, akkor a hozzáférés sorosítva történik, ami bank conflictet okoz. A bank conflict nem ad helytelen eredményt, de a memória-hozzáférést lassítja, és jelentős teljesítménycsökkenést okozhat.

A bank conflict leggyakoribb forrása a local memóriában tárolt mátrix transzponálása. Tekintsünk egy 32×32-es float mátrixot. Indítás: global = {W, H} (W és H 32 többszöröse), local = {32, 32}; a kernel feltételezi, hogy get_local_size(0) == get_local_size(1) == 32, más local mérettel csendben hibás eredményt ad (a host indítás előtt assert-tel ellenőrizze). Ha az eszköz kernelszintű work-group korlátja (CL_KERNEL_WORK_GROUP_SIZE) 1024-nél kisebb, a hordozható változat 32×8-as work-groupot használ, és minden work-item négy sort tölt be és ír ki (for (int j = 0; j < 32; j += 8) tile[ly + j][lx] = …).

__kernel void transpose_naive(__global const float* in,
                              __global float* out) {
    // statikus local tömb a kernelben (kernel-argumentum nem lehet többdimenziós tömb)
    __local float tile[32][32];
    int x = get_global_id(0);
    int y = get_global_id(1);
    int lx = get_local_id(0);
    int ly = get_local_id(1);

    tile[ly][lx] = in[y * get_global_size(0) + x];
    barrier(CLK_LOCAL_MEM_FENCE);

    // A csempe transzponált helyre kerül: a kimeneti sor a csoport x-indexéből,
    // az oszlop a csoport y-indexéből adódik (H = get_global_size(1)).
    out[(get_group_id(0) * 32 + ly) * get_global_size(1)
        + get_group_id(1) * 32 + lx] = tile[lx][ly];
}

A fenti kernelben a tile[lx][ly] olvasás oszlopos hozzáférést jelent. Egy wavefronton belül a work-itemek az x dimenzió mentén szomszédosak, így lx változik, ly pedig fix. A 4 bájtos szó indexe lx * 32 + ly, a bank indexe a szóindex modulo 32 (32 darab, 4 bájt széles bank): (lx * 32 + ly) mod 32 = ly mod 32. Mivel ly ugyanaz minden work-itemre a hullámfrontban, mind ugyanabba a bankba próbálnak olvasni, ami 32-szeres bank conflictet okoz.

A megoldás a padding: a local memória tömbjét eggyel szélesebbre választjuk, például tile[32][33] méretűre. Ekkor a sor hossza 33, és a bank index számítása (lx * 33 + ly) mod 32 = (lx + ly) mod 32 lesz, ami a wavefronton belül változik, így a hozzáférés conflictmentessé válik:

__kernel void transpose_padded(__global const float* in,
                               __global float* out) {
    __local float tile[32][33];   // egy extra oszlop (padding)
    // ... ugyanaz, mint fent ...
}

Az alábbi ábra a 32 bankot és a csempe szavait mutatja: a naiv esetben a warp 32 olvasása egyetlen bankba esik, paddinggal 32 különböző bankba.

Ha a csempét dinamikusan, __local float* kernel-argumentumként adjuk át, a host oldalon a méret 32 * 33 * sizeof(float) bájt, és az indexelés kézzel történik (tile[ly * 33 + lx], illetve tile[lx * 33 + ly]). A transzponálás helyességét kis méretű (pl. 64×64) mátrixon CPU-referenciával kell ellenőrizni.

A padding tehát egyetlen extra oszloppal megszünteti a bank conflictet. Az OpenCL specifikáció nem írja elő a bankok számát, ezért a padding méretét az adott hardverhez kell igazítani; a gyakorlatban a 32 bank és a 32 bites szó a leggyakoribb. A bank conflict fogalma analóg a CUDA shared memory bank conflictjével, de az OpenCL-ben a local memory bankok elrendezése implementációfüggő, ezért a méréseknek mindig hardverspecifikusnak kell lenniük.

30.2.5 Tipikus hibák és megelőzés

A work-group, barrier és local memory használata során a következő hibák fordulnak elő leggyakrabban:

  1. Divergens barrier: a barrier feltételes ágban van, és nem minden work-item hívja meg. Megelőzés: a barrier hívásokat mindig a vezérlési gráf olyan pontjára helyezzük, amelyet minden work-item elér; a feltételes ágakban csak a memóriaműveletek vannak, a barrier utána következik.

  2. Local memory inicializálás elmulasztása: a local memória a work-group indulásakor nem definiált tartalommal rendelkezik. Ha a kernel nem tölti fel, akkor hibás eredményt adhat. Megelőzés: a local memóriába mindig írunk, mielőtt olvasnánk, és a barrier után olvasunk.

  3. Bank conflict figyelmen kívül hagyása: a local memória elérési mintája sorosítást okoz, ami lassítja a kernelt. Megelőzés: padding, vagy az elérési minta átalakítása (például soronkénti feldolgozás).

  4. Work-group méret és local memory méret korlátjainak túllépése: ha a work-group a kernelre vonatkozó korlátnál nagyobb, az indítás CL_INVALID_WORK_GROUP_SIZE hibával meghiúsul (nem fordítási hiba); ha a korláton belül, de nagy local memóriát vagy sok erőforrást igényel, az occupancy drasztikusan csökken. Megelőzés: a CL_DEVICE_MAX_WORK_GROUP_SIZE és a CL_DEVICE_LOCAL_MEM_SIZE eszközadatok lekérdezése; a clGetKernelWorkGroupInfo a kernelre vonatkozó korlátokat is megadja.

  5. A globális szinkronizáció téves feltételezése: a work-groupok közötti függőséget nem lehet barrierrel megoldani. Megelőzés: a kernelhatárokra vagy atomi műveletekre kell támaszkodni, és a tervezés során a work-groupok függetlenségét kell alapul venni.

30.2.6 Labor: local memoryt használó OpenCL redukció

A labor célja egy olyan OpenCL kernel írása, amely work-groupönként egy részösszeget számít ki local memory és barrier használatával. Az eredményt a host CPU-s referenciával ellenőrzi, és mérési naplót készít. A kernel a korábban bemutatott fa-alapú redukciót valósítja meg.

30.2.6.1 Kernel

A kernel dinamikus local memóriát használ, így a work-group mérete a host oldalon megadható anélkül, hogy a kernelt újra kellene fordítani. A kernel argumentumai: bemeneti tömb, kimeneti tömb (work-groupönként egy érték), és a local memória pointer.

// Fordítás: OpenCL C 1.2+
// Feltétel: a globális méret = num_groups * workgroup_size
__kernel void partial_reduce(
    __global const float* input,
    __global float* output,
    __local float* tile)
{
    int gid = get_global_id(0);
    int lid = get_local_id(0);
    int group_id = get_group_id(0);
    int local_size = get_local_size(0);

    // 1. lépés: betöltés a globális memóriából a local memóriába
    tile[lid] = input[gid];

    // Minden work-itemnek el kell érnie a barriert,
    // mielőtt bármelyik olvasná a local memóriát.
    barrier(CLK_LOCAL_MEM_FENCE);

    // 2. lépés: fa-alapú redukció a work-groupön belül
    for (int offset = local_size / 2; offset > 0; offset >>= 1) {
        if (lid < offset) {
            tile[lid] += tile[lid + offset];
        }
        // A barrier a ciklusban is kötelező:
        // a következő iteráció olvasása csak akkor kezdődhet,
        // ha az összes hozzáadás befejeződött.
        barrier(CLK_LOCAL_MEM_FENCE);
    }

    // 3. lépés: az eredmény kiírása
    if (lid == 0) {
        output[group_id] = tile[0];
    }
}

A kernel a __local float* tile argumentumot dinamikus local memóriaként kapja; a méretet a host adja meg.

30.2.6.2 Host kód

A host kód C++ és a Khronos OpenCL C++ burkolót (CL/opencl.hpp) használja; a hibakezelés kivételekkel történik (CL_HPP_ENABLE_EXCEPTIONS), így minden API-hívás hibája (build, setArg, enqueue, olvasás) cl::Error kivételként jelentkezik, és egyetlen helyen kezelhető. A platform- és eszközkiválasztás a 29.1–29.2 alfejezet témája, itt egyszerűsítve szerepel. A kód a szöveg elkészítésekor nem lett lefordítva és futtatva.

// Fordítás: g++ -std=c++17 -O2 reduce.cpp -lOpenCL -o reduce
// Fejléc: Khronos OpenCL-CLHPP (CL/opencl.hpp), célverzió: OpenCL 1.2
#define CL_HPP_ENABLE_EXCEPTIONS
#define CL_HPP_TARGET_OPENCL_VERSION 120
#define CL_HPP_MINIMUM_OPENCL_VERSION 120
#include <CL/opencl.hpp>
#include <algorithm>
#include <cmath>
#include <iostream>
#include <string>
#include <vector>

int main() {
    constexpr size_t workgroup_size = 256;
    constexpr size_t num_groups = 4096;
    constexpr size_t N = workgroup_size * num_groups;
    constexpr int warmup = 10, reps = 20;

    try {
        std::vector<cl::Platform> platforms;
        cl::Platform::get(&platforms);
        if (platforms.empty()) { std::cerr << "Nincs OpenCL platform\n"; return 1; }

        // Platformbejárás (29.2.8): az első olyan platform első GPU-ja kell, amelyen van GPU.
        // CL_HPP_ENABLE_EXCEPTIONS mellett a getDevices GPU hiányában cl::Error-t
        // (CL_DEVICE_NOT_FOUND) dob, ezért try/catch kell, nem üresség-ellenőrzés.
        cl::Device device;
        bool found = false;
        for (auto& pl : platforms) {
            std::vector<cl::Device> devs;
            try {
                pl.getDevices(CL_DEVICE_TYPE_GPU, &devs);
            } catch (const cl::Error& e) {
                if (e.err() != CL_DEVICE_NOT_FOUND) throw;
                continue;
            }
            if (!devs.empty()) { device = devs[0]; found = true; break; }
        }
        if (!found) { std::cerr << "Nincs GPU\n"; return 1; }
        std::cout << "Eszköz: " << device.getInfo<CL_DEVICE_NAME>() << "\n";

        cl::Context context(device);
        cl::CommandQueue queue(context, device, CL_QUEUE_PROFILING_ENABLE);

        std::string source = R"(
            __kernel void partial_reduce(
                __global const float* input,
                __global float* output,
                __local float* tile)
            {
                int gid = get_global_id(0);
                int lid = get_local_id(0);
                int group_id = get_group_id(0);
                int local_size = get_local_size(0);
                tile[lid] = input[gid];
                barrier(CLK_LOCAL_MEM_FENCE);
                for (int offset = local_size / 2; offset > 0; offset >>= 1) {
                    if (lid < offset) {
                        tile[lid] += tile[lid + offset];
                    }
                    barrier(CLK_LOCAL_MEM_FENCE);
                }
                if (lid == 0) {
                    output[group_id] = tile[0];
                }
            }
        )";

        cl::Program program(context, source);
        try {
            program.build({device});
        } catch (const cl::BuildError& e) {
            for (const auto& entry : e.getBuildLog())
                std::cerr << "Build hiba:\n" << entry.second << "\n";
            return 1;
        }
        cl::Kernel kernel(program, "partial_reduce");

        // A work-group méret nem haladhatja meg a kernelre vonatkozó korlátot
        size_t max_wg = kernel.getWorkGroupInfo<CL_KERNEL_WORK_GROUP_SIZE>(device);
        if (workgroup_size > max_wg) {
            std::cerr << "A work-group méret (" << workgroup_size
                      << ") nagyobb a kernel korlátjánál (" << max_wg << ")\n";
            return 1;
        }

        std::vector<float> input(N);
        for (size_t i = 0; i < N; ++i)
            input[i] = static_cast<float>(i % 100) * 0.01f;  // helyőrző adat
        std::vector<float> output(num_groups);

        cl::Buffer d_input(context, CL_MEM_READ_ONLY, sizeof(float) * N);
        cl::Buffer d_output(context, CL_MEM_WRITE_ONLY, sizeof(float) * num_groups);
        queue.enqueueWriteBuffer(d_input, CL_TRUE, 0, sizeof(float) * N, input.data());

        size_t local_bytes = workgroup_size * sizeof(float);
        kernel.setArg(0, d_input);
        kernel.setArg(1, d_output);
        kernel.setArg(2, local_bytes, nullptr);

        // Warm-up + mért ismétlések; az idő az eseményprofilozásból (ns) származik
        std::vector<double> times_ms;
        for (int r = 0; r < warmup + reps; ++r) {
            cl::Event event;
            queue.enqueueNDRangeKernel(kernel, cl::NullRange, cl::NDRange(N),
                                       cl::NDRange(workgroup_size), nullptr, &event);
            event.wait();
            if (r >= warmup) {
                cl_ulong t0 = event.getProfilingInfo<CL_PROFILING_COMMAND_START>();
                cl_ulong t1 = event.getProfilingInfo<CL_PROFILING_COMMAND_END>();
                times_ms.push_back((t1 - t0) * 1e-6);
            }
        }
        double mean = 0.0;
        for (double t : times_ms) mean += t;
        mean /= times_ms.size();
        double var = 0.0;
        for (double t : times_ms) var += (t - mean) * (t - mean);
        double stdev = std::sqrt(var / (times_ms.size() - 1));
        std::vector<double> sorted = times_ms;
        std::sort(sorted.begin(), sorted.end());
        size_t h = sorted.size();
        double median = 0.5 * (sorted[h / 2 - 1] + sorted[h / 2]);  // páros h

        queue.enqueueReadBuffer(d_output, CL_TRUE, 0,
                                sizeof(float) * num_groups, output.data());

        // CPU referencia double pontossággal; relatív tűrés (a részösszegek ~10^2 nagyságúak,
        // egy float ulp itt ~8e-6, ezért az 1e-5 abszolút tűrés hamis hibát adna)
        bool ok = true;
        for (size_t g = 0; g < num_groups && ok; ++g) {
            double ref = 0.0;
            for (size_t i = 0; i < workgroup_size; ++i)
                ref += static_cast<double>(input[g * workgroup_size + i]);
            if (std::abs(output[g] - ref) > 1e-5 * std::abs(ref) + 1e-6) {
                std::cerr << "Eltérés a(z) " << g << ". csoportban: "
                          << output[g] << " vs " << ref << "\n";
                ok = false;
            }
        }
        if (ok) std::cout << "Az eredmény helyes.\n";
        std::cout << "Futásidő: medián " << median << " ms, szórás " << stdev << " ms\n";
        std::cout << "Effektív átbocsátás (bemenet / medián idő): "
                  << (sizeof(float) * N) / (median * 1e-3) / 1e9 << " GB/s\n";
    } catch (const cl::Error& e) {
        std::cerr << "OpenCL hiba: " << e.what() << " (" << e.err() << ")\n";
        return 1;
    }
    return 0;
}

A kód a CL/opencl.hpp fejlécet használja (a régi CL/cl.hpp a mai Khronos fejlécekben már nincs meg; a CL/cl2.hpp átmeneti név). A laborban a lényeg az algoritmus és a mérési módszertan, nem a konkrét API-változat.

A warm-up (10) és az ismétlésszám (20) meghaladja a protokoll minimumát; a medián a protokoll szerinti központi érték, az átlag csak kiegészítés.

30.2.6.4 Elemzés

A redukciós kernel jól szemlélteti a work-group, barrier és local memory együttműködését. A local memóriába való betöltés után a barrier biztosítja, hogy minden work-item lássa a többiek által beírt értékeket. A fa-alapú redukció minden iterációja után a barrier garantálja a közbülső részösszegek láthatóságát. A 4 MiB-os bemenet a mai GPU-k L2-jében (például 32–40 MB; ellenőrzendő az adott eszközre) végig cache-ben marad, és a kernel csak néhány tíz mikroszekundumig fut, ezért a kiírt érték az L2-ből olvasó, indítási többlettel terhelt effektív átbocsátás, nem DRAM-sávszélesség. DRAM-méréshez a bemenet legyen az L2 többszöröse (például N = 2^26 float = 256 MiB, 262 144 work-group), vagy a mért indítások között egy L2-nél nagyobb puffert írjunk felül. A mért idő ennél a méretnél az indítási többlettől is függ; a local memória sávszélességét ez a mérés nem adja meg, azt külön mikrobenchmarkkal kellene mérni. A bemutatott redukcióban a tile[lid] és tile[lid + offset] hozzáférések a szomszédos work-itemek szomszédos szavait érik el, ezért a legtöbb GPU-n nem okoznak jelentős bank conflictet (ezt mérés nélkül nem állítjuk).

30.2.7 Önellenőrző kérdés

A következő kernelrészlet egy work-groupon belüli redukciót (összegzést) próbál megvalósítani local memóriában. Melyik hiba található benne, és hogyan javítható?

__kernel void broken_reduce(__global const float* input,
                            __global float* output,
                            __local float* tile) {
    int lid = get_local_id(0);
    int gid = get_global_id(0);
    tile[lid] = input[gid];
    if (lid < 128) {
        tile[lid] += tile[lid + 128];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
    if (lid < 64) {
        tile[lid] += tile[lid + 64];
    }
    barrier(CLK_LOCAL_MEM_FENCE);
    // ...
    output[get_group_id(0)] = tile[0];
}

Válasz vázlata: A fő hiba a hiányzó barrier a betöltés után: a tile[lid] = input[gid]; után közvetlenül következik a tile[lid] += tile[lid + 128];, amely egy másik work-item által írt elemet olvas, így versenyhelyzet (adatverseny) alakul ki. Javítás: a betöltés után barrier(CLK_LOCAL_MEM_FENCE); kell. A barrierek a feltételes ágakon kívül vannak, tehát nem divergensek. További hiba, hogy a kimenetet minden work-item írná (tile[0]-t pedig csak a végső lépések után szabad olvasni, és csak egy work-item írja ki): a kimeneti írás if (lid == 0) alá tartozik. A javított változatban a ciklusos forma (for (offset = local_size / 2; offset > 0; offset >>= 1) minden iteráció végén barrierrel) a hibát általánosan kezeli. A kérdés tanulsága, hogy a barrier helyes elhelyezése (betöltés után és minden olvasás előtt) a divergencia elkerülése mellett ugyanolyan fontos.
