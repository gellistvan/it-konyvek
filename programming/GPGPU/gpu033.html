9.4 Összetett együttműködési minták

A thread block, a cluster és a grid együttműködési szintjei külön-külön is hatékony eszközöket adnak, de a valódi erejüket akkor mutatják meg, amikor egyetlen kernelben kombináljuk őket. Ez az alfejezet azt a gyakorlati mintát tárgyalja, amelyben egy többlépcsős számítás egyidejűleg támaszkodik blokkszintű szinkronizációra, klaszteren belüli megosztott memóriára, valamint grid-szintű barrierre. A cél nem az egyes csoporttípusok újbóli bemutatása – azokat a megelőző alfejezetek tárgyalták –, hanem azok összehangolt alkalmazása, a belőlük adódó teljesítmény-, hordozhatósági és helyességi kérdésekkel együtt.

9.4.1 Miért van szükség kombinált együttműködésre?

A GPU programozási modellje hierarchikus. Egy tipikus, adatpárhuzamos kernel esetében a gridben lévő blokkok egymástól függetlenül, a hardver által meghatározott ütemezésben futnak. Ez a laza csatolás egyszerűvé és skálázhatóvá teszi a végrehajtást, ugyanakkor korlátozza azokat az algoritmusokat, amelyekben a blokkoknak részeredményeket kell kicserélniük anélkül, hogy a globális memórián keresztül drága, kétszeri adatmozgatást (írás, majd újraolvasás) végeznének.

A Cooperative Groups API három szinten vezetett be finomabb vezérlést:

  1. Blokkszintű csoportok (thread_block, tiled_partition): a hagyományos __syncthreads() általánosítása, amely lehetővé teszi alcsoportok explicit szinkronizálását és kollektív műveletek használatát.
  2. Klaszterek (cluster_group): a Hopper (CC 9.0) és újabb architektúrákon a hardver lehetővé teszi blokkok egy csoportjának szoros együttműködését, klaszterszintű barrierrel (cluster.sync()) és klaszteren belüli megosztott memóriával (Distributed Shared Memory, DSM). A blokkok így közvetlenül olvashatják egymás shared memóriáját, anélkül hogy a globális memórián keresztül kellene kommunikálniuk.
  3. Grid-szintű csoport (grid_group): a this_grid().sync() olyan barrier, amelyet a grid minden blokkjának el kell érnie. Ez kizárólag kooperatív kernelindítás (cudaLaunchCooperativeKernel) esetén garantálható, amikor a futtatókörnyezet biztosítja, hogy az összes blokk egyidejűleg rezidens legyen az SM-eken.

A három szint kombinálása lehetővé teszi olyan algoritmusok hatékony megvalósítását, amelyek korábban csak többszöri kernelindítással, globális memórián keresztüli kommunikációval vagy atomi műveletekkel voltak megoldhatók. A tipikus alkalmazási területek közé tartoznak az iteratív megoldók (például Jacobi-típusú stencilek; a Gauss–Seidel red-black rendezést igényel), a többszintű redukciók, a szemcsés részecskeszimulációk, valamint a mélytanulási kernelek bizonyos rétegei, ahol a blokk és a grid közötti finom adatcsere elengedhetetlen. (A kombináció támogatottsága és az indítás módja a klaszter + kooperatív indítás esetén külön ellenőrzendő; lásd alább.)

9.4.2 A kombinált minta általános szerkezete

Egy összetett, többlépcsős kernel általában a következő fázisokra bontható:

  1. Lokális számítás: minden blokk a saját, globális memóriából beolvasott adattartományán dolgozik, és az eredményt a saját shared memóriájában vagy regisztereiben tartja.
  2. Klaszterszintű együttműködés: a klaszter blokkjai kicserélik a szükséges részeredményeket a DSM-en keresztül, majd cluster.sync()-kel biztosítják, hogy minden blokk befejezte az írást, mielőtt bármelyikük olvasna.
  3. Grid-szintű szinkronizáció: amikor a klaszterek közötti adatcsere is szükséges – például egy újabb iteráció megkezdése előtt – a kernel eléri a this_grid().sync() pontot. Ez biztosítja, hogy az előző fázis minden klaszterben befejeződött.
  4. Második számítási fázis: a kernel a frissen elérhető adatokkal folytatja a munkát, például egy korrekciós lépést hajt végre, vagy egy következő időlépést számol.

Ez a minta akkor előnyös, ha a fázisok közötti adatmennyiség kicsi a számítási munkához képest, és ha a grid-szintű szinkronizáció ritkán következik be – tipikusan egy-egy iteráció végén. Ellenkező esetben a globális barrier miatt kialakuló várakozás felemésztheti a nyereséget.

A következő kódvázlat egy ilyen mintát mutat be. A példa nem egy teljes alkalmazás, hanem a szerkezet illusztrálására szolgál; a hiányzó részeket ... jelzi, nem futtatott és nem fordított vázlat.

// CUDA C++ (illusztráció, nem teljes kernel; nem fordított)
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void __cluster_dims__(4, 1, 1)
combined_pattern_kernel(float* partial, float* result, int n) {
    cg::thread_block block   = cg::this_thread_block();
    cg::cluster_group cluster = cg::this_cluster();   // CC 9.0+
    extern __shared__ float smem[];

    // Lokális számítás: minden blokk kiszámítja a saját részeredményét.
    float local_sum = 0.0f;
    // ... adatbetöltés, számítás ...

    if (block.thread_rank() == 0) {
        smem[0] = local_sum;      // a blokk részösszege a saját shared memóriájában
    }
    // A klaszter-barrier a blokkon belüli szálakat is összehangolja,
    // külön block.sync() nem kell.
    cluster.sync();

    // Klaszterszintű redukció: minden blokk kiolvassa a klasztertársak részösszegét.
    float cluster_sum = 0.0f;
    for (unsigned int i = 0; i < cluster.num_blocks(); ++i) {
        const float* remote_smem = cluster.map_shared_rank(smem, i);
        cluster_sum += remote_smem[0];
    }
    // A távoli olvasások után egy második klaszter-barrier kell, hogy egyik
    // blokk se léphessen ki, amíg a többi még az ő shared memóriáját olvassa.
    cluster.sync();

    if (cluster.block_rank() == 0 && block.thread_rank() == 0) {
        partial[blockIdx.x / cluster.num_blocks()] = cluster_sum;
    }

    // Grid-szintű szinkronizáció a klaszterek közötti adatcsere előtt.
    // (Csak kooperatív indítással érvényes.)
    cg::grid_group grid = cg::this_grid();
    grid.sync();

    // Második fázis: a friss globális adatok alapján folytatódik a munka,
    // például a klaszterösszegek normalizálása.
    // ...
}

A kombinált indítás megjegyzése. A cudaLaunchCooperativeKernel híváshoz nem adható klaszterdimenzió-paraméter; a klaszter a kernel __cluster_dims__ attribútumával, vagy cudaLaunchKernelEx-szel adható meg (cudaLaunchAttributeClusterDimension), a kooperatív indítás pedig cudaLaunchAttributeCooperative attribútummal kérhető. Hogy a két attribútum együtt támogatott-e, és milyen gridméret-korlát érvényes ilyenkor (a cudaOccupancyMaxActiveClusters klaszterek számát ad, nem blokk/SM-et), a használt CUDA Programming Guide kiadásában ellenőrizendő; a szerzők ezt nem fordították és nem futtatták. A fenti vázlat a szerkezetet mutatja, nem igazolt indítási receptet.

Ebben a vázlatban látható a három szint kombinációja: a blokkszint (thread_block, a részösszeg a blokk saját shared memóriájában), a klaszterszint (cluster.sync(), amely a blokkon belüli szinkronizációt is magában foglalja, és a DSM-olvasás) és a gridszint (a klaszterek közötti grid.sync()).

9.4.3 Munkaelosztás a kombinált kernelben

A többlépcsős kernel egyik legfontosabb tervezési döntése, hogy a számítási munkát miként osztjuk fel a grid, a klaszter és a blokk szintjei között. A helyes felosztás határozza meg, hogy a szinkronizációs pontokon mennyi időt kell várakozni, és mennyire használjuk ki az SM-ek erőforrásait.

9.4.3.1 Hierarchikus tiling

A leggyakoribb megközelítés a hierarchikus csempézés (tiling). A globális adattartományt négy szintre bonthatjuk:

  • Grid-szint: a grid felel az adatok nagy, diszjunkt tartományaiért. Kooperatív indítás esetén a grid mérete nem lehet nagyobb annál, amennyi blokk egyidejűleg rezidens az összes SM-en, ezért a tartományok száma korlátozott. Emiatt gyakran érdemes perzisztens kernel stílust használni: minden blokk egy for ciklusban több kisebb tartományt dolgoz fel (grid-stride loop), ahelyett hogy a grid mérete egyenlő lenne a feldolgozandó részek számával.
  • Klaszter-szint: a klaszter a blokkok egy közeli csoportját fogja össze. A klaszteren belül a blokkok közösen fednek le egy nagyobb, összefüggő adatterületet, és a szomszédos határokon átnyúló adatcserét a gyors DSM-mel oldják meg. A klaszter méretét a hardverkorlát (hordozhatóan legfeljebb 8 blokk, Hopperen nem hordozható módon 16; lásd az előző alfejezetet) és a feladat szomszédsági szerkezete határozza meg.
  • Blokk-szint: egy blokk a klaszter által lefedett tartomány egy részét (csempéjét) kapja. A blokkméretet a memória-hozzáférési minták, a szükséges shared memory és a regiszterhasználat együttesen befolyásolják.
  • Warp- és szál-szint: a blokkon belül a warpok és szálak végeznek vektorizált betöltést és számítást. A cg::tiled_partition segítségével a blokkot kisebb, önállóan szinkronizálható csoportokra oszthatjuk.

A hierarchikus felosztás előnye, hogy minden szinten a lehető legkisebb kommunikációs távolságot használjuk: a leggyakoribb adatcsere a blokkon belül shared memórián, a ritkább klaszteren belül DSM-en, a legritkább pedig grid-szinten, globális memórián keresztül történik.

9.4.4 Példa: stencil iteratív megoldó

Vegyünk egy 2D stencilt Jacobi-iterációval: minden belső cella új értéke a négy szomszéd átlaga, a határ rögzített (Dirichlet-feltétel). Ez a Laplace-egyenlet Jacobi-iterációja; a hővezetési egyenlet explicit Euler-lépése u + r·(Σszomszéd − 4u) alakú (r = αΔt/h²), ami r = 1/4 esetén egyezik meg a Jacobi-lépéssel. A párhuzamosítás során a tartományt csempékre osztjuk, és minden csempe szélén egy halo-réteget kell cserélni a szomszédos csempékkel. (A Gauss–Seidel-iteráció párhuzamosításához red-black rendezés kell; az itteni minta Jacobi-típusú.)

Kombinált együttműködéssel ez a következőképpen valósítható meg:

  1. Minden blokk betölti a saját csempéjét a globális memóriából a shared memóriába. A klaszteren belüli szomszédos blokkok közötti halo-cellákat ekkor nem a globális memóriából, hanem a szomszéd blokk shared memóriájából (DSM) olvassuk, a klaszter külső határán lévő halót viszont a globális memóriából.
  2. A DSM-halo olvasása előtt cluster.sync() biztosítja, hogy minden blokk befejezte a shared memóriájának írását; a távoli olvasások után újabb cluster.sync() kell.
  3. Minden blokk kiszámítja a következő iterációs értékeket a saját belső celláira.
  4. A klaszterek közötti határokon a halo-csere globális memórián keresztül zajlik: miután minden blokk kiírta a szélső celláit a globális memóriába, a grid.sync() biztosítja, hogy minden klaszter befejezte az írást, és a következő iteráció elején minden blokk biztonságosan beolvashatja a globális halót.
  5. A ciklus a következő iterációval folytatódik.

Ez a felépítés a klaszteren belüli határokon megspórolja a globális memória forgalmát, csak a klaszterek közötti határokon használjuk a lassú utat. A grid-szinkronizáció iterációnként egyszer következik be.

9.4.5 Perzisztens kernelek és grid-stride loop

A kooperatív indítás egyik következménye, hogy a grid mérete legfeljebb annyi blokk lehet, amennyi egyidejűleg rezidens. Ha egy problémához több független tartomány tartozik, mint amennyi blokk elfér, akkor a blokkoknak több tartományt kell feldolgozniuk. Ezt a gyakorlatban grid-stride loop segítségével érjük el:

// Grid-stride loop perzisztens kernelben (vázlat)
__global__ void persistent_kernel(float* data, int n, int phases) {
    cg::grid_group grid = cg::this_grid();
    for (int phase = 0; phase < phases; ++phase) {   // phases minden szálon azonos
        for (int tid = blockIdx.x * blockDim.x + threadIdx.x; tid < n;
             tid += gridDim.x * blockDim.x) {
            // feldolgozás
        }
        grid.sync();   // minden szál eléri, a ciklus uniform
    }
}

Ez lehetővé teszi, hogy a kernel a teljes futás alatt az eszközön maradjon, és a globális barrierrel szabályozza a fázisokat. A grid.sync() hívásnak minden szálra nézve uniform helyen és (ha ciklusban van) azonos számú alkalommal kell lennie, mert különben holtpont alakul ki; a fenti phases ezért minden szálon ugyanaz az érték.

9.4.6 Szinkronizációs szabályok és gyakori hibák

A kombinált minta helyessége szempontjából a legfontosabb, hogy minden szinten betartsuk a csoportokra vonatkozó kollektív hívások szabályait. A leggyakoribb hibák a következők:

9.4.6.1 Hiányzó vagy nem kollektív sync

A cluster.sync() és a grid.sync() kollektív művelet: a csoport minden szálának meg kell hívnia, uniform vezérlési úton. Ha egy szál (vagy blokk) egy if feltétel miatt kihagyja a hívást, a hívó szálak örökre várakoznak.

Hibás minta:

// HIBÁS: a sync feltételes ágban van, nem minden szál éri el
__global__ void bad_cluster_sync(float* data) {
    cg::cluster_group cluster = cg::this_cluster();
    if (threadIdx.x == 0) {
        // ...
        cluster.sync(); // HIBA: a cluster.sync() a klaszter összes szálának kollektív hívása;
                        // a többi szál kihagyja az if-et és befejezi a kernelt,
                        // a hívó szálak örökre várnak
    }
}

Helyes megoldás: a szinkronizálást a csoport minden tagjának, minden feltételtől függetlenül el kell érnie, vagy a feltételt úgy kell megfogalmazni, hogy a csoport minden tagja azonos döntést hozzon (uniform feltétel, pl. kernelparaméter).

9.4.6.2 A grid-szinkronizáció nem kooperatív indítással

A cg::this_grid().sync() csak akkor érvényes, ha a kernelt kooperatív indítással futtattuk, és a grid minden blokkja egyszerre rezidens. Egyszerű <<<grid, block>>> indítással a grid.sync() nem támogatott: a mai (CUDA 11+) toolkitekben a kernel megszakad, és a következő szinkronizáló hívás cudaErrorLaunchFailure hibát ad (sticky hiba; a lektor NVRTC/RTX-es ellenőrzése szerint, a pontos viselkedés Toolkit-verziófüggő lehet). A kernelben a grid.is_valid() lekérdezhető, ha a kód mindkét indítási módot el akarja viselni.

Hibás minta:

// HIBÁS: grid.sync() normál <<< >>> indítással
__global__ void bad_grid_sync() {
    cooperative_groups::grid_group grid = cooperative_groups::this_grid();
    grid.sync(); // NEM TÁMOGATOTT normál indításnál
}

// hívás:
// bad_grid_sync<<<num_blocks, block_size>>>();

Helyes megoldás: a kernelt cudaLaunchCooperativeKernel függvénnyel kell indítani, és előtte ellenőrizni kell, hogy a kívánt blokkszám és egyéb erőforrások lehetővé teszik-e a kooperatív futást. A cudaOccupancyMaxActiveBlocksPerMultiprocessor segítségével meghatározható, hogy hány blokk lehet rezidens egy SM-en, és ebből a maximális gridméret.

// Helyes vázlat: kooperatív indítás
int numBlocksPerSm = 0;
CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&numBlocksPerSm, kernel, blockSize, smemSize));
int maxBlocks = numBlocksPerSm * numSMs;
if (gridBlocks > maxBlocks) {
    // csökkenteni kell a grid méretét vagy más stratégiát használni
}
void* args[] = { /* a kernelparaméterek címei */ };
CUDA_CHECK(cudaLaunchCooperativeKernel((void*)kernel, dim3(gridBlocks), dim3(blockSize), args, smemSize, stream));

A grid méretének ellenőrzése kötelező, mert a hardver erőforrás-korlátai miatt előfordulhat, hogy a kért blokkszám nem fér el egyszerre. A túl nagy gridet a cudaLaunchCooperativeKernel a cudaErrorCooperativeLaunchTooLarge hibakóddal elutasítja, a kernel nem indul el (lásd az előző alfejezetet).

9.4.6.3 DSM hozzáférés cluster.sync nélkül

A Distributed Shared Memory lehetővé teszi, hogy egy blokk olvassa egy másik, ugyanabban a klaszterben lévő blokk shared memóriáját. Az olvasás előtt azonban biztosítani kell, hogy a forrásblokk befejezte az írást. Ezt a cluster.sync() hívás garantálja, amely a klaszter összes blokkját szinkronizálja.

Hibás minta:

// HIBÁS: DSM olvasás cluster.sync() nélkül
__global__ void __cluster_dims__(2, 1, 1) bad_dsm_access(float* data) {
    cg::cluster_group cluster = cg::this_cluster();
    extern __shared__ float smem[];

    if (cluster.block_rank() == 0) {
        smem[0] = 1.0f; // 0. blokk ír
    }
    // HIÁNYZIK a cluster.sync()

    float* remote = cluster.map_shared_rank(smem, 0);
    float val = remote[0]; // versenyhelyzet: lehet, hogy az írás még nem történt meg
}

Helyes megoldás: a DSM írás után, de még a DSM olvasás előtt hívjuk meg a cluster.sync()-et, az olvasások után pedig még egyszer, hogy a tulajdonos blokk ne léphessen ki idő előtt. A block.sync() nem elegendő, mert az csak a blokkon belül szinkronizál.

9.4.6.4 A klaszterméret és a hardverkorlát figyelmen kívül hagyása

A klaszterek mérete architektúrafüggő. A hordozható klaszterméret legfeljebb 8 blokk; Hopperen nem hordozható módon 16 is engedélyezhető (lásd az előző alfejezetet). A klaszter dimenzióit a __cluster_dims__ attribútummal vagy cudaLaunchKernelEx-szel kell megadni, és a kernelben a this_cluster() által visszaadott csoport dimenziói a ténylegesen elindított értéket tükrözik. Ha a kód feltételezi, hogy a klaszter mindig egy bizonyos méretű, a hordozhatóság sérül.

Helyes megoldás: a kernelben dinamikusan kérdezzük le a klaszter méretét (cluster.num_blocks()), és a kódot úgy írjuk meg, hogy bármilyen támogatott méretre működjön, vagy fordítási időben static_assert-tel szűrjük ki a nem támogatott eseteket.

9.4.7 Teljesítmény és hordozhatóság

A kombinált együttműködési minták teljesítménye erősen függ attól, hogy a szinkronizációs pontok mennyire ritkák, és hogy a DSM-mel kiváltott globális memóriaforgalom mekkora megtakarítást eredményez.

9.4.7.1 Klaszter előnyei

A klaszter használatának legnagyobb előnye a blokkok közötti kommunikáció felgyorsítása. A DSM hozzáférés késleltetése alacsonyabb, mint a globális memória elérése, ezért az olyan minták, amelyek gyakori szomszédos blokkok közötti adatcserét igényelnek, sávszélesség-megtakarítást érhetnek el. A klaszter emellett lehetővé teszi a shared memória együttes kihasználását: a klaszter blokkjainak shared memóriája együtt nagyobb, összefüggő csempék kezelését teszi lehetővé anélkül, hogy az adatot a globális memórián keresztül kellene mozgatni.

Ugyanakkor a klaszterindítás klaszterszintű rezidencia-feltétellel jár: egy klaszter blokkjait együtt kell elhelyezni (a klaszter blokkjai egy GPC-n belül futnak), ami korlátozhatja az occupancyt. A cluster.sync() hívás is többletköltséggel jár, ezért érdemes megfontolni, hogy egy adott feladatban tényleg szükség van-e klaszterre, vagy a hagyományos blokkszintű megoldás is elegendő.

9.4.7.2 Grid-szinkronizáció költsége

A grid.sync() a teljes gridet szinkronizálja, ami azt jelenti, hogy a leglassabb blokk befejeződéséig minden más blokk várakozik. A várakozási idő a blokkok munkamennyiségének kiegyensúlyozatlanságától függ. Ezért a grid-szintű szinkronizációt lehetőleg ritkán, és csak akkor érdemes használni, ha a fázisok közötti adatfüggőség valóban megköveteli.

Ráadásul a kooperatív indítás korlátozza a grid méretét, ami csökkentheti az occupancy-t, ha a kernel egyébként sok blokkal jobban skálázna. A perzisztens kernelek és a grid-stride loop ezt a korlátot enyhítik, de a tervezés során mindig mérni kell, hogy a grid-szinkronizációból származó nyereség ellensúlyozza-e a kisebb grid miatti veszteséget.

9.4.7.3 Hordozhatósági megfontolások

A kombinált minták hordozhatósága két szinten korlátozott:

  • Hardver-szint: a klaszterek csak a Hopper (CC 9.0) és újabb architektúrákon érhetők el. A grid-szinkronizáció (kooperatív indítás) CC 6.0-tól jellemzően támogatott, de a pontos feltételt (cudaDevAttrCooperativeLaunch, maximális gridméret) futásidőben kell lekérdezni. A klasztert igénylő részeket ezért érdemes feltételes fordítás és futásidejű ellenőrzés mögé tenni.
  • Szoftver-szint: a Cooperative Groups API a CUDA 9.0 óta elérhető; a klaszter-API (cluster_group, DSM, __cluster_dims__) a CUDA 12.0-tól érhető el, Hopper-támogatással együtt. A pontos verziókat a használt toolkit dokumentációjában ellenőrizd.

A gyakorlatban a hordozhatóság érdekében a következő stratégiát érdemes követni:

  1. A kernel magját úgy írjuk meg, hogy a thread_block és tiled_partition szintű együttműködés mindig elérhető legyen, mert ezek a legszélesebb körben támogatottak.
  2. A klasztert használó kódot külön függvénybe vagy fordítási egységbe szervezzük, és #ifdef-fel vagy futásidejű cudaDeviceGetAttribute ellenőrzéssel kapcsoljuk be, ha az eszköz támogatja.
  3. A grid-szinkronizációt igénylő részt úgy tervezzük, hogy alternatív, többszöri kernelindításon alapuló megoldás is létezzen azokra az eszközökre, ahol a kooperatív indítás nem elérhető vagy nem hatékony.

OpenCL-ben a munkacsoportok (work-group) közötti közvetlen szinkronizáció és megosztott memória nem része a hordozható mag szabványnak; a hasonló mintát általában több kernelindítással vagy atomi műveletekkel kell megvalósítani. JAX/XLA esetében a magas szintű, gráf alapú modell elrejti a blokkok közötti kommunikációt, így az ilyen finomhangolású együttműködés nem közvetlenül alkalmazható.

9.4.8 Labor: grid-szintű Jacobi-stencil kooperatív indítással

A labor célja, hogy a grid-szintű együttműködést egy mérhető, ellenőrizhető példán gyakorolja: egy Jacobi-iterációt futtatunk egyetlen kooperatív kernelben (grid.sync() iterációnként), és összevetjük egy iterációnként külön kernelt indító baseline-nal és egy CPU-referenciával. A klaszteres DSM-halo változat a végén feladat, nem kész megoldás (lásd a kombinált indítás megjegyzését).

9.4.8.1 Feladatleírás

  • A tartomány N×N cellából álló hálópontos grid, minden cella egy float; a határcellák rögzítettek (felső sor 1,0, a többi határcella 0,0), a belső cellák kezdetben 0,0.
  • Minden iterációban egy belső cella új értéke a négy szomszéd átlaga: u_new[i][j] = 0.25f * (u[i-1][j] + u[i+1][j] + u[i][j-1] + u[i][j+1]).
  • A kooperatív kernel T iterációt futtat egyetlen indítással, két pufferrel (ping-pong), grid.sync() iterációnként.
  • Ellenőrzés: maximális abszolút eltérés a CPU-referenciától.

9.4.8.2 Labor kód

// stencil_lab.cu  (CUDA C++17, nvcc 12.x; nem futtatott és nem fordított példa)
#include <cooperative_groups.h>
#include <cuda_runtime.h>
#include <algorithm>
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <vector>
namespace cg = cooperative_groups;

#define CUDA_CHECK(call)                                                   \
    do {                                                                   \
        cudaError_t err_ = (call);                                         \
        if (err_ != cudaSuccess) {                                         \
            std::fprintf(stderr, "CUDA hiba %s:%d: %s\n", __FILE__,        \
                         __LINE__, cudaGetErrorString(err_));              \
            std::exit(EXIT_FAILURE);                                       \
        }                                                                  \
    } while (0)

__device__ __forceinline__ void update_cell(const float* src, float* dst,
                                            long long k, int N) {
    const int i = (int)(k / N), j = (int)(k % N);
    if (i > 0 && i < N - 1 && j > 0 && j < N - 1)
        dst[k] = 0.25f * (src[k - N] + src[k + N] + src[k - 1] + src[k + 1]);
    else
        dst[k] = src[k];                       // rögzített határ
}

// Kooperatív változat: T iteráció egyetlen kernelben.
__global__ void jacobi_coop(float* a, float* b, int N, int T) {
    cg::grid_group grid = cg::this_grid();
    const long long total  = (long long)N * N;
    const long long stride = (long long)gridDim.x * blockDim.x;
    for (int it = 0; it < T; ++it) {           // T minden szálon azonos
        const float* src = (it % 2 == 0) ? a : b;
        float*       dst = (it % 2 == 0) ? b : a;
        for (long long k = (long long)blockIdx.x * blockDim.x + threadIdx.x;
             k < total; k += stride)
            update_cell(src, dst, k, N);
        grid.sync();                           // minden szál eléri
    }
}

// Baseline: egyetlen iteráció, a host ciklusban indítja.
__global__ void jacobi_step(const float* src, float* dst, int N) {
    const long long total  = (long long)N * N;
    const long long stride = (long long)gridDim.x * blockDim.x;
    for (long long k = (long long)blockIdx.x * blockDim.x + threadIdx.x;
         k < total; k += stride)
        update_cell(src, dst, k, N);
}

static void cpu_reference(std::vector<float>& u, int N, int T) {
    std::vector<float> v(u);
    for (int it = 0; it < T; ++it) {
        for (int i = 0; i < N; ++i)
            for (int j = 0; j < N; ++j) {
                const int k = i * N + j;
                v[k] = (i > 0 && i < N - 1 && j > 0 && j < N - 1)
                     ? 0.25f * (u[k - N] + u[k + N] + u[k - 1] + u[k + 1]) : u[k];
            }
        u.swap(v);
    }
}

int main(int argc, char** argv) {
    const int N = (argc > 1) ? std::atoi(argv[1]) : 512;
    const int T = (argc > 2) ? std::atoi(argv[2]) : 100;
    const int block = 256, warmup = 5, reps = 20;
    const size_t bytes = (size_t)N * N * sizeof(float);

    int dev = 0, coop = 0, sms = 0, per_sm = 0;
    CUDA_CHECK(cudaSetDevice(dev));
    CUDA_CHECK(cudaDeviceGetAttribute(&coop, cudaDevAttrCooperativeLaunch, dev));
    if (!coop) { std::fprintf(stderr, "Nincs kooperatív indítás.\n"); return 1; }
    CUDA_CHECK(cudaDeviceGetAttribute(&sms, cudaDevAttrMultiProcessorCount, dev));
    CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(&per_sm, jacobi_coop, block, 0));
    const int coop_blocks = std::min(sms * per_sm,
                                     (int)(((long long)N * N + block - 1) / block));
    if (coop_blocks == 0) { std::fprintf(stderr, "Nem fér el blokk.\n"); return 1; }

    std::vector<float> init((size_t)N * N, 0.0f);
    for (int j = 0; j < N; ++j) init[j] = 1.0f;          // felső sor = 1,0

    float *d_a = nullptr, *d_b = nullptr;
    CUDA_CHECK(cudaMalloc(&d_a, bytes));
    CUDA_CHECK(cudaMalloc(&d_b, bytes));

    cudaEvent_t t0, t1;
    CUDA_CHECK(cudaEventCreate(&t0));
    CUDA_CHECK(cudaEventCreate(&t1));
    float ms_coop[reps], ms_base[reps];
    const long long total = (long long)N * N;
    const int base_blocks = (int)std::min<long long>((total + block - 1) / block, 1 << 20);

    for (int r = -warmup; r < reps; ++r) {                // r < 0: warm-up (5)
        CUDA_CHECK(cudaMemcpy(d_a, init.data(), bytes, cudaMemcpyHostToDevice));
        CUDA_CHECK(cudaMemcpy(d_b, init.data(), bytes, cudaMemcpyHostToDevice));
        int n = N, t = T;
        void* args[] = { &d_a, &d_b, &n, &t };
        CUDA_CHECK(cudaEventRecord(t0));
        CUDA_CHECK(cudaLaunchCooperativeKernel((void*)jacobi_coop, dim3(coop_blocks),
                                               dim3(block), args, 0, 0));
        CUDA_CHECK(cudaEventRecord(t1));
        CUDA_CHECK(cudaEventSynchronize(t1));
        CUDA_CHECK(cudaGetLastError());
        if (r >= 0) CUDA_CHECK(cudaEventElapsedTime(&ms_coop[r], t0, t1));
    }
    // Eredmény a kooperatív futásból: T páros -> d_a, páratlan -> d_b.
    std::vector<float> gpu((size_t)N * N);
    CUDA_CHECK(cudaMemcpy(gpu.data(), (T % 2 == 0) ? d_a : d_b, bytes, cudaMemcpyDeviceToHost));

    for (int r = -warmup; r < reps; ++r) {
        CUDA_CHECK(cudaMemcpy(d_a, init.data(), bytes, cudaMemcpyHostToDevice));
        CUDA_CHECK(cudaMemcpy(d_b, init.data(), bytes, cudaMemcpyHostToDevice));
        CUDA_CHECK(cudaEventRecord(t0));
        for (int it = 0; it < T; ++it) {
            float* src = (it % 2 == 0) ? d_a : d_b;
            float* dst = (it % 2 == 0) ? d_b : d_a;
            jacobi_step<<<base_blocks, block>>>(src, dst, N);
        }
        CUDA_CHECK(cudaEventRecord(t1));
        CUDA_CHECK(cudaEventSynchronize(t1));
        CUDA_CHECK(cudaGetLastError());
        if (r >= 0) CUDA_CHECK(cudaEventElapsedTime(&ms_base[r], t0, t1));
    }

    std::vector<float> ref(init);
    cpu_reference(ref, N, T);
    float max_err = 0.0f;
    for (size_t k = 0; k < ref.size(); ++k)
        max_err = std::max(max_err, std::fabs(ref[k] - gpu[k]));

    auto stats = [&](const float* x, float& med, float& iqr) {
        std::vector<float> sorted(x, x + reps);
        std::sort(sorted.begin(), sorted.end());
        med = 0.5f * (sorted[reps / 2 - 1] + sorted[reps / 2]);   // reps páros
        iqr = sorted[3 * reps / 4] - sorted[reps / 4];
    };
    float mc, sc, mb, sb;
    stats(ms_coop, mc, sc);
    stats(ms_base, mb, sb);
    std::printf("N=%d T=%d coop_blocks=%d max_abs_err=%g\n", N, T, coop_blocks, max_err);
    std::printf("kooperativ: median %.3f ms (IQR %.3f)\nbaseline  : median %.3f ms (IQR %.3f)\n",
                mc, sc, mb, sb);

    CUDA_CHECK(cudaEventDestroy(t0));
    CUDA_CHECK(cudaEventDestroy(t1));
    CUDA_CHECK(cudaFree(d_a));
    CUDA_CHECK(cudaFree(d_b));
    return 0;
}

A kód megjegyzései szerint a kooperatív kernelben T és a ciklusszerkezet minden szálon azonos, ezért a grid.sync() uniform. A baseline a T darab kernelindítás költségét is tartalmazza, ami éppen a kooperatív változattal szemben összehasonlítandó tényező.

9.4.8.5 Feladat: klaszteres DSM-halo bővítés

Bővítsd a kernelt úgy, hogy a blokkok csempéket (pl. 16×16) dolgozzanak fel, és a klaszteren belüli szomszéd csempék halo-celláit DSM-ből (cluster.map_shared_rank) olvassák, a klaszterek közötti halo-t pedig a globális memóriából, grid.sync() után. Ehhez nem a cudaLaunchCooperativeKernel, hanem cudaLaunchKernelEx kell a kooperatív és a klaszter-attribútummal; az együttes támogatást először a dokumentációban és a célhardveren ellenőrizd. A DSM-olvasások után mindig legyen záró cluster.sync().

9.4.8.6 Ellenőrző kérdés

A fejezet lezárásaként válaszold meg a következő kérdést:

Milyen feltételek mellett biztonságos a this_grid().sync() hívása egy kernelben, és mi történik, ha a grid egyik szála nem éri el ezt a hívást?

A helyes válasznak tartalmaznia kell, hogy a kernelnek kooperatív indítással kell futnia, a grid minden blokkjának egyidejűleg rezidensnek kell lennie, és a szinkronizálási hívásnak minden szálon ugyanazon a vezérlési úton kell elhelyezkednie. Ha egy szál nem éri el a hívást, a többi szál örökre várakozik, ami holtponthoz vezet.

9.4.9 Összegzés

A Cooperative Groups eszköztárának kombinált használata lehetővé teszi olyan összetett, többlépcsős kernelek írását, amelyek a blokkszintű finom szinkronizációt, a klaszteren belüli gyors adatcserét és a grid-szintű fázisvezérlést egyetlen kernelben egyesítik. A minta hatékonysága azon múlik, hogy a munkaelosztást hierarchikusan tervezzük-e, a szinkronizációs pontokat ritkán és szabályosan helyezzük-e el, valamint hogy tiszteletben tartjuk-e a hardver- és szoftverkorlátokat. A kooperatív indítással elkerülhető a többszöri kernelindítás overheadje, a klaszterekkel támogatott DSM pedig csökkentheti a globális memóriaforgalmat, de a pontos nyereség erősen függ a probléma méretétől és a GPU architektúrájától; ezt a labor mérési táblázatának kitöltésével kell az olvasónak igazolnia. A következő alfejezet a CUDA hibakezelésével és hibakeresésével foglalkozik, amely a kombinált minták helyességének ellenőrzéséhez is elengedhetetlen.
