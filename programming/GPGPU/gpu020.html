6.3 Grid-stride loop és perzisztens kernelek

Az előző alfejezetben (6.2) megismerkedtünk a többdimenziós indexelés alapjaival. Láttuk, hogyan képezzük le a logikai adatszerkezeteket a hardver által biztosított blockIdx, blockDim és threadIdx változókra. Az ott bemutatott minták azonban egy kényes feltételezésre épültek: a rács (grid) mérete pontosan illeszkedett az adat méretére. Ha a vektorunk hossza N, akkor ceil(N / blockDim.x) darab blokkot indítottunk.

Ez a megközelítés a legtöbb egyszerű tankönyvi példában tökéletesen működik, de a valódi, nagy teljesítményű alkalmazásokban ritkán kielégítő. Az adatméret gyakran futásidőben változik, 2D/3D leképezésnél meghaladhatja a y/z irányú blokkszám-korlátot, vagy éppen ellenkezőleg: olyan kicsi, hogy a hardver erőforrásainak túlnyomó része kihasználatlanul marad. A grid-stride loop (rácslépéses ciklus) mintájával az 5.3 alfejezetben és az 5.4 alfejezet laborjában már találkoztunk; itt a használatát, a rács méretezését és a vele rokon perzisztens kernel (persistent kernel) koncepcióját dolgozzuk ki, amely a „kevés blokk, sok munka” elv mentén tovább növeli a vezérlési rugalmasságot.

6.3.1 A rugalmas méretű feldolgozás mintája

A GPU programozási modelljének egyik központi kihívása a hardveres végrehajtási egységek és a logikai probléma méretének szétválasztása. Ha minden egyes adatelemhez egy szálat rendelünk, akkor a kernel indításakor ismernünk kell a pontos adatméretet, és a rácsot ahhoz kell igazítanunk. Ez a gyakorlatban nem mindig lehetséges vagy hatékony:

  1. Változó méret: Egy szimulációban a részecskék száma, egy gráfbejárásban a csúcsok száma, vagy egy képfeldolgozó pipeline-ban a képméret futásról futásra változhat.
  2. Rácsméret-korlátok: x irányban a rács legfeljebb 231−12^{31}-1 blokkból állhat, ami 1D-s tömbnél a GPU memóriájánál jóval nagyobb adatot is lefed; a y és z dimenzió viszont legfeljebb 65 535 blokk, és a host oldali int gridméret-számítás is túlcsordulhat. A grid-stride loop ezektől a korlátoktól függetlenné teszi a kernelt.
  3. Hullámok (waves) és telítettség: Az SM-ek egyszerre csak korlátozott számú blokkot tudnak futtatni. Ha a rezidens kapacitásnál több blokkot indítunk, a többi blokk sorban, „hullámokban” hajtódik végre. Ha az utolsó hullám csak részben tölti fel az SM-eket, akkor teljesítményt veszítünk (tail effect).

A grid-stride loop egy elegáns megoldás az első két problémára, és a harmadikat is mérsékelheti. A minta lényege, hogy a szálak száma fix (a probléma méretétől függetlenül korlátozott), és minden szál egy ciklusban lépeget végig az adatokon. Az ugrás mérete megegyezik a teljes rácsban lévő összes szál számával: blockDim.x * gridDim.x.

Tekintsük a következő CUDA C++ kódot, amely egy vektorösszeadást valósít meg grid-stride loop segítségével. A kódot a szerző nem fordította le és nem futtatta; a fordítás és a futtatás az olvasó feladata.

// CUDA C++ (C++17), grid-stride loop példa; nvcc -std=c++17 -O3 -arch=native
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

// Hibamakró (a könyv labor-szerződése szerint kötelező)
#define CUDA_CHECK(call)                                                        \
  do {                                                                          \
    cudaError_t err = (call);                                                   \
    if (err != cudaSuccess) {                                                   \
      std::fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__,       \
                   cudaGetErrorString(err));                                    \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

__global__ void vectorAddGridStride(const float *A, const float *B, float *C,
                                   long long N) {
  // A szorzás is 64 biten történik: a (long long) kasztolás a szorzás ELŐTT kell.
  long long idx = (long long)blockIdx.x * blockDim.x + threadIdx.x;
  long long stride = (long long)blockDim.x * gridDim.x;

  for (long long i = idx; i < N; i += stride) {
    C[i] = A[i] + B[i];
  }
}

int main() {
  const long long N = 1LL << 28;            // 268 435 456 elem, tömbönként 1 GiB
  const size_t bytes = (size_t)N * sizeof(float);   // összesen 3 GiB
  float *d_A, *d_B, *d_C;

  CUDA_CHECK(cudaMalloc(&d_A, bytes));
  CUDA_CHECK(cudaMalloc(&d_B, bytes));
  CUDA_CHECK(cudaMalloc(&d_C, bytes));
  // inicializálás (a lefoglalt memória nem nullázott)
  CUDA_CHECK(cudaMemset(d_A, 0, bytes));
  CUDA_CHECK(cudaMemset(d_B, 0, bytes));

  // A rács méretét blokkokban a GPU-hoz igazítjuk, nem N-hez.
  const int blockSize = 256;
  int dev = 0, numSMs = 0, blocksPerSM = 0;
  CUDA_CHECK(cudaGetDevice(&dev));
  CUDA_CHECK(cudaDeviceGetAttribute(&numSMs, cudaDevAttrMultiProcessorCount, dev));
  CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
      &blocksPerSM, vectorAddGridStride, blockSize, 0));
  const int numBlocks = numSMs * blocksPerSM;   // egy hullámnyi rezidens blokk

  vectorAddGridStride<<<numBlocks, blockSize>>>(d_A, d_B, d_C, N);
  CUDA_CHECK(cudaGetLastError());
  CUDA_CHECK(cudaDeviceSynchronize());

  CUDA_CHECK(cudaFree(d_A));
  CUDA_CHECK(cudaFree(d_B));
  CUDA_CHECK(cudaFree(d_C));
  return 0;
}

A fenti kódban a stride a teljes rács szélessége. A szál indexe (idx) határozza meg a kiindulási pozíciót. Ha N nagyobb, mint a szálak száma, a szálak egyszerűen továbblépnek a következő ciklusiterációban. Ha N kisebb, a for ciklus feltétele (i < N) gondoskodik a boundary checkről, vagyis a szál nem ír a lefoglalt tömbön kívülre. A blokkok számát numSMs * blocksPerSM adja, ahol a blocksPerSM az occupancy API eredménye (a 256 szálas blokk és CC 8.6/8.9 esetén legfeljebb 1536 / 256 = 6, CC 8.0-n legfeljebb 2048 / 256 = 8, és a regiszter- vagy shared memory-használat ennél kevesebbre is levihet).

Az alábbi ábra egy kis példán mutatja, melyik szál melyik elemet dolgozza fel iterációnként, és mi történik, ha a stride hibásan csak blockDim.x.

Miért rugalmas ez a minta? Ugyanazt a kernel binárist és ugyanazt a launch konfigurációt használhatjuk akár 1 milliós, akár 1 milliárdos vektorra. A rács mérete csak a GPU hardveres képességeitől függ, nem az adat méretétől. Ez lehetővé teszi a kernel újrahasznosítását anélkül, hogy a host kódban minden méretváltozásnál újra kellene számolni a rácsot. A grid-stride loop nem csökkenti az utolsó blokk tétlen szálait, és a coalescinget sem rontja: egy iteráción belül a warp szomszédos szálai szomszédos elemeket érnek el (lásd az 5.3 alfejezetet).

6.3.2 Kevés blokk, sok munka

A grid-stride loop hatékonyságának kulcsa a „kevés blokk, sok munka” elv. Ez az elv azt mondja ki, hogy a GPU teljesítményének maximalizálásához elegendő annyi blokkot indítani, amennyi a hardveres erőforrásokat (SM-ek, regiszterek, shared memory) teljesen lefoglalja. A többi munkát a szálaknak kell elvégezniük a ciklus ismétlésével.

A hagyományos, minden elemet külön szállal lefedő megközelítés (elem-per-szál, naiv kernel) esetén az ütemezőnek rengeteg blokkot kell befejeznie és újat indítania. Ez a blokk-indítási overhead általában kicsi, de ha a kernel futási ideje maga is nagyon rövid, akkor a mérési eredményeket torzíthatja.

A grid-stride loop esetén a kernel indításakor a hardver az összes SM-et feltölti, és a blokkok a teljes futás alatt rezidensek maradnak. Ez csökkentheti a blokkütemezési többletterhet; modern GPU-n ez a hatás gyakran kicsi, ezért előnyként csak mérés alapján szabad kezelni. A rezidens kapacitásra méretezett grid statikus stride-dal sem szünteti meg a tail effectet: az egyenlőtlen munka vagy az utolsó iteráció miatt a blokkok továbbra sem fejeződnek be egyszerre; csak a blokkszintű hullámkvantálás szűnik meg.

Gyakorlati kérdés: hány blokkot indítsunk? Ha túl kevés blokkot indítunk, a GPU nem lesz teljesen telített. Ha túl sokat, a grid-stride loop elveszíti az előnyeit. Kiindulópont: numSMs * blocksPerSM blokk (egy hullám), amelyet kísérletileg egy kis egész szorzóval (pl. 2–4 hullámnyi blokk) lehet növelni a terheléskiegyenlítés érdekében; a legjobb szorzót a mérés adja. A blokkméret és a launch konfiguráció hibakezelése a 6.4, az occupancy részletes számszerűsítése a 12.4 alfejezet témája. Addig is elmondható: a grid-stride loop tipikusan akkor hatékony, ha a grid mérete a GPU erőforrásaihoz mérten „ésszerűen kicsi”.

6.3.3 Perzisztens kernel

A grid-stride loop logikai továbbfejlesztése a perzisztens kernel (persistent kernel). Míg a grid-stride loop esetén a szálak statikusan, előre meghatározott lépésközzel haladnak, a perzisztens kernelnél a blokkok dinamikusan kérnek új munkát egy globális munkaszámlálóból (atomi „jegy”, work queue). Ez nem munkalopás (work stealing): nincs másik blokk soráról elvett munka, csak közös számlálóból kiosztott feladat.

A perzisztens kernel definíciója: olyan kernel, amely legfeljebb annyi blokkot indít, amennyit a hardver egyidejűleg, egy hullámban futtatni tud, és a kernel a kilépés előtt egy belső ciklusban, atomi műveletek segítségével addig dolgozik, amíg az összes feladat el nem készül.

Ez a megközelítés különösen hasznos, ha a munkaegységek mérete nem egyenletes, vagy ha a feldolgozási idő elemektől függően nagyon változó. A statikus grid-stride loop esetén előfordulhat, hogy az egyik blokk nagyon hosszú ideig dolgozik egy adott adatszeleten, míg a többi blokk már végzett.

Tekintsünk egy példát, ahol egy nagy, numRows × numCols méretű mátrix sorait kell feldolgozni, de a feldolgozási idő soronként nagyon eltérő lehet (pl. ritka mátrixok). A blokk kér új sort, nem az egyes szálak: a sorindexet egyetlen szál szerzi meg és osztja meg shared memory-n keresztül, a sor elemeit a blokk szálai közösen összegzik, és a blokkon belüli redukció után a 0. szál írja ki az eredményt. A kódot a szerző nem fordította le és nem futtatta.

// CUDA C++ (C++17), perzisztens kernel dinamikus munkakiosztással
#include <cstdio>
#include <cstdlib>
#include <cuda_runtime.h>

#define CUDA_CHECK(call)                                                        \
  do {                                                                          \
    cudaError_t err = (call);                                                   \
    if (err != cudaSuccess) {                                                   \
      std::fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__,       \
                   cudaGetErrorString(err));                                    \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

constexpr int BLOCK = 256;                 // kettő hatványa (a redukció miatt)
__device__ unsigned int globalWorkCounter = 0;   // globális munkaszámláló

// Feladat: minden sorra kiszámoljuk a sorösszeget.
__global__ void processRowsDynamically(const float *matrix, float *output,
                                       unsigned int numRows, int numCols) {
  __shared__ unsigned int row;             // a blokk aktuális sora
  __shared__ float sdata[BLOCK];

  while (true) {
    if (threadIdx.x == 0) {
      row = atomicAdd(&globalWorkCounter, 1u);   // egy sor a blokknak
    }
    __syncthreads();                       // minden szál lássa a `row` értékét
    if (row >= numRows) {
      break;                               // blokk-uniform feltétel: nincs több munka
    }

    const float *rowPtr = matrix + (size_t)row * numCols;
    float sum = 0.0f;
    for (int col = threadIdx.x; col < numCols; col += blockDim.x) {
      sum += rowPtr[col];
    }

    // Blokkon belüli fa-redukció shared memory-ban
    sdata[threadIdx.x] = sum;
    __syncthreads();
    for (int s = blockDim.x / 2; s > 0; s >>= 1) {
      if (threadIdx.x < s) sdata[threadIdx.x] += sdata[threadIdx.x + s];
      __syncthreads();
    }
    if (threadIdx.x == 0) {
      output[row] = sdata[0];
    }
    __syncthreads();   // a következő iteráció `row`-írása és `sdata`-használata előtt
  }
}

int main() {
  const unsigned int numRows = 10000;
  const int numCols = 512;
  float *d_matrix = nullptr, *d_output = nullptr;
  CUDA_CHECK(cudaMalloc(&d_matrix, (size_t)numRows * numCols * sizeof(float)));
  CUDA_CHECK(cudaMalloc(&d_output, numRows * sizeof(float)));
  CUDA_CHECK(cudaMemset(d_matrix, 0, (size_t)numRows * numCols * sizeof(float)));

  // Blokkszám: egy hullám a GPU-hoz igazítva (occupancy API), nem kitalált konstans
  int dev = 0, numSMs = 0, blocksPerSM = 0;
  CUDA_CHECK(cudaGetDevice(&dev));
  CUDA_CHECK(cudaDeviceGetAttribute(&numSMs, cudaDevAttrMultiProcessorCount, dev));
  CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
      &blocksPerSM, processRowsDynamically, BLOCK, 0));
  const int numBlocks = numSMs * blocksPerSM;

  // A munkaszámláló nullázása MINDEN indítás előtt
  const unsigned int init = 0;
  CUDA_CHECK(cudaMemcpyToSymbol(globalWorkCounter, &init, sizeof(unsigned int)));

  processRowsDynamically<<<numBlocks, BLOCK>>>(d_matrix, d_output, numRows, numCols);
  CUDA_CHECK(cudaGetLastError());
  CUDA_CHECK(cudaDeviceSynchronize());

  CUDA_CHECK(cudaFree(d_matrix));
  CUDA_CHECK(cudaFree(d_output));
  return 0;
}

A perzisztens kernel működési elve: 1. Inicializálás: A kernel indítása előtt a globális globalWorkCounter értékét nullára állítjuk (minden indítás előtt újra). 2. Lefoglalás: A blokk 0. szála az atomicAdd utasítással egyedi értéket szerez a számlálóból, és shared memory-ba írja; a __syncthreads() után a blokk minden szála ezt a sort dolgozza fel. (Ha az atomicAdd minden szálban lefutna, minden szál más sort kapna, és az eredmények elvesznének.) 3. Feldolgozás: A blokk szálai közösen összegzik a sor elemeit, majd blokkon belüli redukcióval egyetlen értéket írnak ki. 4. Újrapróbálkozás: A ciklus addig ismétlődik, amíg a megszerzett azonosító el nem éri a sorok számát (numRows). Ekkor a blokk kilép.

Miért előnyös ez a minta? * Automatikus terheléselosztás: Ha az egyik sor feldolgozása 10-szer annyi ideig tart, mint a többi soré, a többi blokk nem vár rá a statikus elosztás miatt. Amint végeznek, automatikusan lekérnek egy újabb sort a közös számlálóból. A terhelés így dinamikusan kiegyenlítődik. * Csökkentett indítási overhead: A kernel egyetlen hullámnyi blokkal fut végig; a „blokk soronként” változattal szemben (ahol 10 000 blokk indul és ér véget) nincs blokkonkénti indítás és leállítás. Többfázisú feladatoknál, ahol egyébként fázisonként külön kernelt indítanánk, a perzisztens kernel a kernelindítások számát is csökkentheti; mindkét hatás feladatfüggő, mérni kell. * Lehetséges cache-előnyök: Bizonyos feladatoknál a hosszú életű blokkok a kernel élettartama alatt újrahasznosíthatnak shared memory-ba töltött adatot; ez feladatfüggő, és mérni kell.

Az alábbi ábra modellidőben veti össze a statikus és a dinamikus kiosztást egy olyan esetre, amelyben az egyik sor tízszer annyi ideig tart, mint a többi.

Korlátok és buktatók: A perzisztens kernel egyik legnagyobb veszélye a deadlock (holtpont). Ha a GPU-n nem fér el az összes blokk egyidejűleg, az ütemező csak akkor indítja el a következő blokkot, ha egy korábbi már befejeződött. Ha egy perzisztens kernelben a blokk egy olyan globális szinkronizációra vár (pl. grid.sync() a cooperative groups használatával), amelyet az összes blokknak el kellene érnie, de néhány blokk még el sem indult, mert a hardver nem tudta ütemezni őket, a rendszer örökre várni fog.

Ezért a perzisztens kernel indításakor szigorúan garantálni kell, hogy a megadott blokkok száma nem haladja meg a hardver által egyidejűleg futtatható blokkok számát (numSMs * blocksPerSM). Az occupancy-számítást a 12.4 alfejezet részletezi. Emellett a perzisztens kernelek nem használhatják a blokkok közötti szinkronizációt anélkül, hogy megbizonyosodnánk a teljes foglaltságról; grid-szintű szinkronizációhoz cooperative launch szükséges (9.3 alfejezet).

A grid-stride loop és a perzisztens kernel közötti választás gyakran a feladat természetétől függ. Szabályos, jól kiegyensúlyozott feladatoknál (pl. vektorösszeadás, képkonvolúció) a statikus grid-stride loop egyszerűbb, és jó választás. Erősen szabálytalan, változó költségű feladatoknál (pl. ritka lineáris algebra, gráfbejárás, változó hosszúságú részecskeszimuláció) a perzisztens kernel dinamikus munkakiosztása teljesítménynövekedést hozhat, ennek mértékét azonban mérni kell.

6.3.4 Labor: grid-stride loop implementálása

A labor célja a grid-stride loop gyakorlati elsajátítása és a „kevés blokk, sok munka” elv mérése. Ugyanazt a feladatot két módon oldjuk meg: elem-per-szál (direct) és grid-stride kernellel, azonos memória-hozzáférési mintával (mindkettőben egy warp szomszédos szálai szomszédos elemeket érnek el). A különbség tehát kizárólag a rács méretezése és a blokkok élettartama, a coalescing nem változik. A labor célja vizsgálat, nem előre eldöntött eredmény.

Környezet (helyőrző, a saját gépen rögzítendő): * GPU: <kitöltendő> * Driver: <kitöltendő> * CUDA: <kitöltendő, 12.x>; compute capability: <kitöltendő> * OS: <kitöltendő> * Pontosság: FP32; ismétlés: a könyv mérési protokollja szerint (≥ 5 warm-up, ≥ 20 mért futás, medián és IQR)

Feladat: Írjon CUDA C++ kernelt, amely egy N = 2^26 elemű float tömb minden elemének négyzetét számítja ki (out[i] = in[i] * in[i])! Készítse el az elem-per-szál változatot (ceil(N / blockSize) blokk) és a grid-stride változatot (numSMs * blocksPerSM blokk)! Mérje meg mindkettőt cudaEvent_t-vel 5 warm-up futással és 20 mért ismétléssel (medián és IQR), és számítsa ki a hatékony sávszélességet a ténylegesen mozgatott adatból (2 · 4 · N bájt: egy olvasás és egy írás elemenként)! Kiegészítő feladat: valósítsa meg a sorösszeg feladatot (N = 2^20 sor, M = 128 oszlop; a blokkméret legyen 128 (BLOCK = 128), vagy rendeljen egy sort egy warphoz – jegyezze fel, hogy a 256 szálas blokk fele tétlen lenne) a fenti perzisztens kernellel és egy „egy blokk soronként” kernellel, és hasonlítsa össze őket; ez a feladat külön tanulság, mert itt a memóriaelérés és a munkaelosztás is változik.

Várt eredmény (modell, nem mérés): A négyzetelés memóriakorlátos, mindkét kernel azonos mennyiségű adatot mozgat azonos hozzáférési mintával, ezért a futásidő alsó korlátja 2 · 4 · 2^26 bájt (≈ 537 MB) / (az eszköz legnagyobb elérhető memória-sávszélessége); a két változat ideje várhatóan közel esik egymáshoz, és a különbség nagyságát (akár előjelét is) a mérés dönti el. Nem állítjuk előre, hogy a grid-stride változat gyorsabb. Ha a különbség elhanyagolható, az is érvényes tanulság: ilyen feladatnál a grid-stride loop fő előnye a rugalmasság, nem a sebesség.

CUDA C++ kód:

// CUDA C++ (C++17), labor: direct vs. grid-stride; nvcc -std=c++17 -O3 -arch=native
#include <algorithm>
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <vector>
#include <cuda_runtime.h>

#define CUDA_CHECK(call)                                                        \
  do {                                                                          \
    cudaError_t err = (call);                                                   \
    if (err != cudaSuccess) {                                                   \
      std::fprintf(stderr, "CUDA error %s:%d: %s\n", __FILE__, __LINE__,       \
                   cudaGetErrorString(err));                                    \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

__global__ void squareDirect(const float *in, float *out, long long n) {
  long long i = (long long)blockIdx.x * blockDim.x + threadIdx.x;
  if (i < n) out[i] = in[i] * in[i];
}

__global__ void squareGridStride(const float *in, float *out, long long n) {
  long long stride = (long long)blockDim.x * gridDim.x;
  for (long long i = (long long)blockIdx.x * blockDim.x + threadIdx.x; i < n; i += stride)
    out[i] = in[i] * in[i];
}

template <typename K>
static void bench(K k, const float *in, float *out, long long n, int grid, int block,
                  double *med, double *iqr) {
  cudaEvent_t t0, t1;
  CUDA_CHECK(cudaEventCreate(&t0));
  CUDA_CHECK(cudaEventCreate(&t1));
  for (int w = 0; w < 5; ++w) {                   // warm-up
    k<<<grid, block>>>(in, out, n);
    CUDA_CHECK(cudaGetLastError());
  }
  CUDA_CHECK(cudaDeviceSynchronize());
  const int iters = 20;
  std::vector<float> t(iters);
  for (int r = 0; r < iters; ++r) {
    CUDA_CHECK(cudaEventRecord(t0));
    k<<<grid, block>>>(in, out, n);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaEventRecord(t1));
    CUDA_CHECK(cudaEventSynchronize(t1));
    CUDA_CHECK(cudaEventElapsedTime(&t[r], t0, t1));
  }
  std::sort(t.begin(), t.end());
  *med = t[iters / 2];
  *iqr = t[(3 * iters) / 4] - t[iters / 4];
  CUDA_CHECK(cudaEventDestroy(t0));
  CUDA_CHECK(cudaEventDestroy(t1));
}

// Ellenőrzés: out[i] == in[i] * in[i] (azonos IEEE szorzás, pontos egyezés)
static bool check(const std::vector<float> &h_in, const float *d_out, long long n,
                  const char *name) {
  std::vector<float> h_out((size_t)n);
  CUDA_CHECK(cudaMemcpy(h_out.data(), d_out, (size_t)n * sizeof(float),
                        cudaMemcpyDeviceToHost));
  for (long long i = 0; i < n; ++i) {
    if (h_out[i] != h_in[i] * h_in[i]) {
      std::printf("%s: HIBA i=%lld\n", name, i);
      return false;
    }
  }
  std::printf("%s: OK\n", name);
  return true;
}

int main() {
  const long long n = 1LL << 26;
  const size_t bytes = (size_t)n * sizeof(float);
  std::vector<float> h_in((size_t)n);
  for (long long i = 0; i < n; ++i) h_in[i] = (float)(i % 1000) * 0.001f;
  float *d_in, *d_out;
  CUDA_CHECK(cudaMalloc(&d_in, bytes));
  CUDA_CHECK(cudaMalloc(&d_out, bytes));
  CUDA_CHECK(cudaMemcpy(d_in, h_in.data(), bytes, cudaMemcpyHostToDevice));

  const int block = 256;
  int dev = 0, numSMs = 0, blocksPerSM = 0;
  CUDA_CHECK(cudaGetDevice(&dev));
  CUDA_CHECK(cudaDeviceGetAttribute(&numSMs, cudaDevAttrMultiProcessorCount, dev));
  CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
      &blocksPerSM, squareGridStride, block, 0));

  const int gridDirect = (int)((n + block - 1) / block);
  const int gridStride = numSMs * blocksPerSM;
  double m1, s1, m2, s2;
  // minden kernel előtt a kimenet jelölése, hogy a régi eredmény ne takarja a hibát
  CUDA_CHECK(cudaMemset(d_out, 0xFF, bytes));
  bench(squareDirect, d_in, d_out, n, gridDirect, block, &m1, &s1);
  bool ok1 = check(h_in, d_out, n, "Direct");
  CUDA_CHECK(cudaMemset(d_out, 0xFF, bytes));
  bench(squareGridStride, d_in, d_out, n, gridStride, block, &m2, &s2);
  bool ok2 = check(h_in, d_out, n, "GridStride");

  const double traffic = 2.0 * bytes;             // 1 olvasás + 1 írás
  std::printf("Direct:     grid=%d  median %.4f ms (IQR %.4f)  %.1f GB/s\n",
              gridDirect, m1, s1, traffic / (m1 * 1e6));
  std::printf("GridStride: grid=%d  median %.4f ms (IQR %.4f)  %.1f GB/s\n",
              gridStride, m2, s2, traffic / (m2 * 1e6));

  CUDA_CHECK(cudaFree(d_in));
  CUDA_CHECK(cudaFree(d_out));
  return (ok1 && ok2) ? 0 : 1;
}

Önellenőrző kérdés: Mi történik, ha a grid-stride loopban az N értéke 0? Válasz: A grid-stride változatnál a rács mérete nem függ N-től, ezért N = 0 esetén is érvényes indítás történik, és a ciklusfeltétel (i < N) miatt nincs memóriahozzáférés. Az elem-per-szál változatnál viszont ceil(0/256) = 0 blokk adódik, és 0 méretű grid indítása indítási hibát ad (a cudaGetLastError() jelzi); ott a hostnak kell az n == 0 esetet kiszűrnie.

6.3.5 Tipikus hibák és a helyes megoldások

A grid-stride loop és a perzisztens kernelek használata során a kezdő fejlesztők gyakran elkövetnek néhány jellegzetes hibát. Az alábbiakban ezeket vesszük sorra, és megadjuk a helyes megoldást.

1. hiba: Helytelen stride használata Sokan a stride-ot blockDim.x-re állítják a gridDim.x * blockDim.x helyett. Ez akkor működik, ha a kernel indítása pontosan egy blokkal történik, de több blokk esetén a szálak átfedésben dolgoznak, vagyis ugyanazokat az adatokat írják és olvassák. Helyes megoldás: A stride mindig a teljes rács szélessége: stride = (long long)blockDim.x * gridDim.x.

2. hiba: Túlcsorduló integer típus használata Nagy méretű adatoknál (pl. 2312^{31} feletti elemszám) a int típusú indexelés túlcsordul. Fontos, hogy a blockIdx.x, blockDim.x és gridDim.x mind unsigned int, ezért a (long long)(blockIdx.x * blockDim.x) alak még 32 biten szoroz, és a kasztolás már későn jön; a helyes alak a (long long)blockIdx.x * blockDim.x + threadIdx.x (ahogy az első példakódban és a 6.1 alfejezetben a static_cast<size_t>(blockIdx.x) * blockDim.x minta is mutatja). Helyes megoldás: Az indexeket és a stride-ot a szorzás előtt kell 64 bitesre kasztolni, és a ciklusváltozó is 64 bites (long long vagy size_t).

3. hiba: A rács méretének helytelen megválasztása Ha a rács mérete túl nagy (pl. a naiv kernelhez hasonlóan minden adatelemhez egy szálat rendelünk), a grid-stride loop elveszíti az előnyét. Ha túl kicsi, akkor az SM-ek nem lesznek telítve. Helyes megoldás: A rács méretét a GPU hardveres jellemzőihez kell igazítani: numSMs * blocksPerSM, ahol a blocksPerSM a cudaOccupancyMaxActiveBlocksPerMultiprocessor eredménye.

4. hiba: Perzisztens kernel holtpontja (deadlock) Ha a perzisztens kernelben a blokkok száma meghaladja a hardver által egyidejűleg futtatható blokkok számát, és a kernelben blokkok közötti szinkronizációt alkalmazunk, a kernel soha nem fog befejeződni. Az SM-ek nem tudják elindítani a maradék blokkokat, mert a futó blokkok a szinkronizációs ponton várnak. Az ilyen kísérletet csak timeouttal, izolált környezetben szabad kipróbálni. Helyes megoldás: A perzisztens kernel indításakor soha ne lépjük túl a foglaltsági limitet. Ha lehetséges, kerüljük a blokkok közötti szinkronizációt ebben a mintában, vagy használjunk cooperative groups-ot (lásd a 9.3 alfejezetet), amely a hardveres képességet explicit módon ellenőrzi.

A grid-stride loop egy olyan alapvető építőelem, amely lehetővé teszi, hogy a kerneleink méretfüggetlenek és hardverbarátok legyenek. A következő alfejezetben (6.4) a launch konfiguráció hibakezelésének mélyebb rétegeivel foglalkozunk, és megvizsgáljuk, hogyan kezeljük a kernelindítási hibákat és az aszinkron végrehajtás buktatóit. A perzisztens kernelek és a dinamikus munkakiosztás fogalmai a későbbi fejezetekben, a ritka mátrixok és a gráfalgoritmusok esetében kulcsfontosságú szerepet fognak játszani.
