33.3 Optimalizálás és mérés

A záróprojekt ezen szakasza a 33.2 alfejezetben elkészült, funkcionálisan már helyes kernel teljesítményét veszi célba. A hangsúly nem az újabb funkciókon, hanem a mérésen, a profilkép értelmezésén és a hangolási döntések igazolásán van. A módszertant egy kis, ellenőrizhető 1D, 3 pontos stencil mikrobenchmarkon mutatjuk be, mert ezen a tiling, az occupancy és a stream-alapú átfedés hatása jól elkülöníthető, a numerikus ellenőrzés (CPU-referencia) pedig egyszerű. Ez nem helyettesíti a záróprojekt kernelét: az utolsó feladatban (6.) ugyanezt a ciklust a 33.2 heat_step_tiled kernelére és a 33.1 charter metrikáira kell alkalmazni, ugyanazzal a mérési protokollal.

33.3.1 A teljesítmény hangolása mint mérésvezérelt folyamat

A teljesítmény hangolása nem azt jelenti, hogy „kipróbálunk néhány trükköt, és megnézzük, gyorsabb lett-e”. Ez egy irányított kísérleti ciklus:

  1. Baseline rögzítése: a jelenlegi változat futásideje, átbocsátóképessége, erőforrás-használata és környezeti paraméterei.
  2. Profilkép készítése: Nsight Compute vagy Nsight Systems segítségével megállapítjuk, hogy a kernel mire vár: memóriára, számításra, szinkronizációra vagy ütemezésre.
  3. Hipotézis: a profilkép alapján megfogalmazzuk, mi a szűk keresztmetszet, és milyen beavatkozás javíthat rajta.
  4. Beavatkozás: egyetlen változtatást hajtunk végre, például shared memory tilinget vezetünk be, módosítjuk a blokkméretet, vagy streamre bontjuk a feldolgozást.
  5. Mérés és döntés: a változtatást ugyanazon a bemeneten, azonos környezetben megmérjük; ha javult, megtartjuk, ha romlott, visszaállítjuk, és finomítjuk a hipotézist.

A folyamat legfontosabb eleme a mérés. GPU-n egyetlen futásidő nem bizonyíték: a boost-órajel, a hőmérséklet, a driver ütemezése és a háttérterhelés is torzíthat. Ezért minden állítást ismételt méréssel, szórással és rögzített környezettel kell alátámasztani.

33.3.3 Mérési protokoll

A kernel időmérésre a cudaEvent_t a legmegbízhatóbb, mert a GPU streamjén belül mér, és nem tartalmazza a host oldali std::chrono késleltetéseit. A minta:

cudaEvent_t start, stop;
CUDA_CHECK(cudaEventCreate(&start));
CUDA_CHECK(cudaEventCreate(&stop));

// Warm-up
for (int i = 0; i < 5; ++i) {
    stencil_naive<<<grid, block>>>(d_in, d_out, n);
}
CUDA_CHECK(cudaDeviceSynchronize());

// Mérés: legalább 20 ismétlés, ismétlésenként külön eseménypárral
const int iters = 20;
std::vector<float> t(iters);
for (int i = 0; i < iters; ++i) {
    CUDA_CHECK(cudaEventRecord(start, 0));
    stencil_naive<<<grid, block>>>(d_in, d_out, n);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaEventRecord(stop, 0));
    CUDA_CHECK(cudaEventSynchronize(stop));
    CUDA_CHECK(cudaEventElapsedTime(&t[i], start, stop));
}
std::sort(t.begin(), t.end());
float median_ms = 0.5f * (t[iters / 2 - 1] + t[iters / 2]);   // iters páros

A medián mellett a szórást (vagy IQR-t) és a relatív szórást is közölni kell. Ha a szórás 5 %-nál nagyobb, akkor a mérés nem tekinthető stabilnak: ellenőrizni kell a boost-órajelet, a hőmérsékletet, a háttérfolyamatokat vagy a kernelben lévő nem determinisztikus műveleteket.

A sávszélességet a tényleges adatmozgatásra számítjuk, nem a névleges csúcsértékre. Két különböző forgalmat kell megkülönböztetni. A logikai load/store-forgalom a naiv kernelnél kimeneti elemenként 3 olvasás + 1 írás = (3 + 1) * 4 = 16 bájt, a tiled kernelnél a halótól eltekintve (a globális memóriából) 1 olvasás + 1 írás = 8 bájt. A DRAM-forgalom viszont mindkét változatnál közel az algoritmikus minimum, elemenként 8 bájt (4 bájt olvasás + 4 bájt írás), mert a szomszédos szálak ismételt olvasásait az L1/L2 gyorsítótár elnyeli. Az effektív sávszélességet ezért mindkét kernelre azonos, algoritmikus alapon (8 bájt/elem) számítjuk, hogy az értékek összehasonlíthatók legyenek; a valódi DRAM-forgalmat ncu-val kell megmérni (dram__bytes_read.sum, dram__bytes_write.sum). A mérési jegyzőkönyvben fel kell tüntetni, melyik definíciót használtuk.

33.3.4 Tiling: a gyorsítótár- és load/store-terhelés csökkentése

Az 1D stencil számítása:

out[i] = (in[i - 1] + in[i] + in[i + 1]) / 3.0f;

A naiv kernel közvetlenül a globális memóriából olvassa a három bemeneti elemet:

__global__ void stencil_naive(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float acc = 0.0f;
    for (int r = -RADIUS; r <= RADIUS; ++r) {
        int j = min(max(i + r, 0), n - 1);
        acc += in[j];
    }
    out[i] = acc / (2 * RADIUS + 1);
}

Itt minden bemeneti elemet három különböző szál is beolvas. Az L1/L2 cache ezt nagyrészt elnyeli, de a load/store-egységek és a gyorsítótár terhelése így is nagyobb a szükségesnél. A shared memory tiling lényege, hogy a blokk betölti a szükséges bemeneti tartományt a gyors on-chip memóriába, majd a belső számítások már onnan dolgoznak:

__global__ void stencil_tiled(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    extern __shared__ float s[];
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    int local = threadIdx.x + RADIUS;

    // Minden szál tölt (az n-en túli szálak is, az utolsó elemre fogva),
    // így a részleges utolsó blokkban sincs inicializálatlan shared elem.
    s[local] = in[min(i, n - 1)];

    if (threadIdx.x < RADIUS) {
        int left = blockIdx.x * blockDim.x - RADIUS + (int)threadIdx.x;
        s[threadIdx.x] = in[max(left, 0)];

        int right = (blockIdx.x + 1) * blockDim.x + (int)threadIdx.x;
        s[blockDim.x + RADIUS + threadIdx.x] = in[min(right, n - 1)];
    }

    __syncthreads();

    if (i < n) {
        float acc = 0.0f;
        for (int r = -RADIUS; r <= RADIUS; ++r) {
            acc += s[local + r];
        }
        out[i] = acc / (2 * RADIUS + 1);
    }
}

A kernel indítása dinamikus shared memory-val:

const int block = 256;
const int shared_bytes = (block + 2 * RADIUS) * sizeof(float);
stencil_tiled<<<grid, block, shared_bytes>>>(d_in, d_out, n);

A __syncthreads() garantálja, hogy minden szál befejezte a shared memóriába írást, mielőtt bármelyik olvasná azt. A 3 pontos stencil átfedő ablakokat használ: a blokk belső elemeit többször is felhasználjuk, de globális memóriából mindegyiket csak egyszer olvassuk be; a halókezelés a blokkhatároknál a szomszédos elemeket is elérhetővé teszi. Ez azonban nem garantál gyorsulást: mivel az L1/L2 a naiv változatban is újrahasznosít, a DRAM-forgalom alig változik, és a __syncthreads() meg a halo-betöltés miatt a tiled kernel 1D, kis sugarú stencilnél akár lassabb is lehet. Hogy a tiling segít-e, mérés dönti el.

33.3.5 Bank conflict a tiled stencilben

A shared memóriás olvasás s[local - 1], s[local], s[local + 1] mintája egységnyi (stride-1) hozzáférés: egy warp 32 szála 32 egymást követő 4 bájtos szót olvas, ezek 32 különböző bankba esnek, tehát nincs bank conflict. A három olvasás egymástól független utasítás, nem kerül egy időben ugyanabba a bankba. Bank conflict akkor keletkezne, ha a szálak eltolása a bankszámmal (32) nem relatív prím, például s[2 * tid] (2-way conflict) vagy egy 32 széles 2D tömb oszlopirányú olvasása; az utóbbi tipikus gyógymódja a padding (float tile[32][33]). Az 1D stencilnél ezért ez nem szűk keresztmetszet, de a l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum metrikával ellenőrizhető (várt érték: 0; a metrikanevet ncu --query-metrics kimenettel ellenőrizzük). A 33.2 alfejezet 18 × 18-as csempéje viszont 16 × 16-os blokkal 2-utas konfliktust ad: egy warp két 16 szálas sora 18 szónyi eltolással olvas, így két-két szál ugyanarra a bankra esik (a konfliktusfok Pythonban számolva, nem mérve). Megszüntethető 32 × 8-as blokkal (egy warp = egy csempesor, tile[TILE_Y + 2][32 + 2]), vagy úgy, hogy a sorhossz 16-tal kongruens legyen 32 szerint (pl. 48 szó, több padding); hogy megéri-e, a metrika és a futásidő dönti el.

33.3.6 Occupancy és launch paraméterek

A tiling önmagában nem elég, ha a kernel nem tud elég aktív warpot futtatni a késleltetés elrejtéséhez. Az occupancy azt mutatja meg, hogy az SM-en elérhető maximális warpszámhoz képest mennyi aktív warp van:

occupancy = aktív warpok / maximális warpok SM-enként

A korlátokat a regiszterhasználat, a shared memory, a szálszám és a blokkszám együtt adja; a legszigorúbb dönt. A számítás a CC 8.6-os referencia-GPU-ra érvényes (SM-enként legfeljebb 1536 szál = 48 warp, legfeljebb 16 blokk, 65 536 regiszter, 100 KB shared memory; a 8.0 és 9.0 más: 64 warp). A példakódban a stencil_tiled block = 256 mérettel és shared_bytes = (256 + 2) * 4 = 1032 bájttal fut. Ha a fordító 32 regisztert használ szálanként (az érték a fordítótól függ, -Xptxas -v-vel kell megnézni), a regiszterkorlát:

65536 / (256 * 32) = 8 blokk

A shared memory korlátot 100 KB SM-enkénti kerettel számolva (a blokkonkénti futásidejű foglalás miatt kissé kevesebb, de nagyságrendileg):

100 * 1024 / 1032 ≈ 99 blokk

A szálkorlát:

1536 / 256 = 6 blokk  (6 * 8 = 48 warp)

A legszigorúbb korlát tehát a szálkorlát: 6 blokk, azaz 48 aktív warp, ami a 48 warpos maximumhoz képest 100 %-os elméleti occupancy (a regiszterkorlát 8 blokkot engedne, de ez nem érvényesül). Ez kedvező, de nem szabad vakon maximalizálni.

Az alacsonyabb occupancy nem mindig rossz. Ha egy kernel compute-bound, és a szálaknak több regiszterre van szükségük, a magas blokkszám miatti regiszterkiömlés (spill) drágább lehet, mint a kisebb foglaltság. Ilyenkor a __launch_bounds__ direktíva segíthet a fordítónak a regiszterhasználat korlátozásában:

__global__ __launch_bounds__(256, 2)
void stencil_tiled(...) { ... }

Ez azt mondja a fordítónak, hogy SM-enként legalább 2 blokkot szeretnénk futtatni. A nvcc ekkor úgy osztja el a regisztereket, hogy a cél elérhető legyen. A cudaOccupancyMaxActiveBlocksPerMultiprocessor API-val futásidőben lekérdezhetjük az elméleti (a kernel erőforrásigényéből számolt) foglaltságot; a ténylegesen elért értéket az Nsight Compute mutatja:

int num_blocks_per_sm = 0;
CUDA_CHECK(cudaOccupancyMaxActiveBlocksPerMultiprocessor(
    &num_blocks_per_sm, stencil_tiled, block, shared_bytes));

A laborban érdemes a blokkméretet 128, 256 és 512 között is megvizsgálni. A túl kicsi blokk növeli a halók relatív költségét, a túl nagy blokk csökkenti az ütemezési rugalmasságot, és a tail-effect miatt az utolsó blokk kihasználatlan lehet. A Nsight Compute Occupancy szekciója megmutatja a tényleges értéket (például az sm__warps_active.avg.pct_of_peak_sustained_active metrika); a metrikaneveket ncu --query-metrics kimenettel ellenőrizzük.

33.3.7 Streamek és átfedés

A záróprojekt gyakran nem egyetlen kernelből áll: host-device másolás, több kernel és utófeldolgozás is tartozik hozzá. Ha a host sorosan vár minden lépésre, a GPU kihasználatlan marad. A stream-ek segítségével a memóriamásolást és a kernelszámítást átfedhetjük.

Az 1D stencil streamesített változata a bemenetet négy darabra bontja. A stencil a chunk határán a szomszéd chunk elemeit is olvassa, ezért a kernel csak akkor indulhat, ha a két szomszédos chunk H2D másolása is befejeződött; ezt eseményekkel (cudaStreamWaitEvent) biztosítjuk. A kernel a teljes (device-oldali) bemeneten dolgozik, és csak a [begin, begin + count) tartományt számolja ki (a teljes kód a laborban):

const int num_chunks = 4;                    // n % (num_chunks * block) == 0 szükséges
const int chunk = n / num_chunks;
// st[]: a streamek; ev[]: chunkonként egy H2D-kész esemény (cudaEventDisableTiming)

for (int c = 0; c < num_chunks; ++c) {       // 1. kör: az összes H2D másolás
    cudaStream_t s = st[c % num_streams];
    CUDA_CHECK(cudaMemcpyAsync(d_in + c * chunk, h_in + c * chunk,
                          chunk * sizeof(float), cudaMemcpyHostToDevice, s));
    CUDA_CHECK(cudaEventRecord(ev[c], s));
}
for (int c = 0; c < num_chunks; ++c) {       // 2. kör: kernel + D2H
    cudaStream_t s = st[c % num_streams];
    if (c > 0)              CUDA_CHECK(cudaStreamWaitEvent(s, ev[c - 1], 0));
    if (c + 1 < num_chunks) CUDA_CHECK(cudaStreamWaitEvent(s, ev[c + 1], 0));
    stencil_tiled<<<chunk / block, block, shared_bytes, s>>>(
        d_in, d_out, n, c * chunk, chunk);
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaMemcpyAsync(h_out + c * chunk, d_out + c * chunk,
                          chunk * sizeof(float), cudaMemcpyDeviceToHost, s));
}
CUDA_CHECK(cudaDeviceSynchronize());
// Validáció: h_out == CPU-referencia;
// a streames és az egy streames változat eredménye egyezzen.

A h_in és h_out pinned (cudaMallocHost), a streamek és az események a végén felszabadítandók (cudaStreamDestroy, cudaEventDestroy, cudaFreeHost); a teljes lista a laborkódban szerepel.

Fontos, hogy a host memória pinned (cudaMallocHost) legyen: a lapozható memóriából a DMA-motor nem tud aszinkron módon másolni. Az átfedés akkor működik, ha a másolások és a kernelek különböző streamekhez tartoznak, és a GPU-nak van szabad másoló és számító egysége. A Nsight Systems timeline nézete mutatja meg, hogy a H2D másolás, a kernel és a D2H másolás valóban átfed-e.

Ha csak egy streamet használunk, a hívások sorba állnak. A streames változat akkor hoz nyereséget, ha a másolási idő összemérhető a kernelidővel. Ha a kernel és a másolás ideje nagyon eltér, az átfedés legfeljebb a rövidebbiket rejti el, a nyereség kicsi, és a több stream csak bonyolítja a kódot. Ezért ezt is méréssel kell igazolni.

33.3.8 Benchmark és összehasonlítás

A hangolás során minden változatot ugyanazzal a bemenettel, pontossággal és mérési protokollal kell összehasonlítani. A laborban az alábbi négy változatot érdemes megmérni:

Változat Rács Blokk Shared Regiszter Kernelidő Effektív sávszélesség Relatív Szórás
Naiv 262144 256 0 B 32 [mért] ms [mért] GB/s 1,0× [mért]
Tiled 262144 256 1032 B 32 [mért] ms [mért] GB/s [mért]× [mért]
Tiled, hangolt blokk [mért] [mért] [mért] [mért] [mért] ms [mért] GB/s [mért]× [mért]

A táblázatban a [mért] mezőket a labor során kell kitölteni. A streames lánc (H2D + kernel + D2H) nem kernelidő: saját táblába kerül.

Teljes lánc (H2D + kernel + D2H) Medián idő (ms) Szórás (ms) Nyereség (ms és %)
1 stream [mért] [mért] –
2 stream [mért] [mért] [mért]

Várt: a nyereség felső korlátja ≈ min(kernelidő, másolási idő) ≈ a kernelidő, mert n = 2^26 mellett a másolás (≈ 2 × 10 ms PCIe 4.0 x16-on; becslés, ellenőrzendő) sokkal hosszabb. A pipeline-ismétlések száma 20, a közölt érték a medián. A „várt” becslést a memóriamodellből adhatjuk meg. Ha a bemenet N = 2^26 float elem, mindkét kernel algoritmikus DRAM-forgalma N * 8 bájt (4 bájt olvasás + 4 bájt írás elemenként); a naiv kernel logikai load/store-forgalma N * 16 bájt, de ezt az L1/L2 nagyrészt elnyeli. A referencia-GPU (RTX A4000) névleges 448 GB/s sávszélességén az alsó korlát:

mindkét kernelre: 2^26 * 8 / 448e9 = 536 870 912 / 448e9 ≈ 1,20 ms

A valós kernel ennél lassabb lesz (egy valós GPU a névleges csúcsnak jellemzően csak egy részét éri el), és a modell nem jósol különbséget a naiv és a tiled változat között: ha a mérés különbséget mutat, azt a profilkép (L1/L2 találati arány, szektorszám, szinkronizációs költség) alapján kell magyarázni, és a tiled változat akár lassabb is lehet. Ez a várt érték csak modellszámítás, nem ellenőrzött hardveres mérés. A laborban a tényleges mért értékek eltérhetnek a modelltől; az eltérés elemzése éppen a tanulási cél része.

33.3.9 Nsight-alapú optimalizálás

A Nsight Compute a kernelen belüli metrikákat mutatja meg. A laborban használt parancsok:

# -arch a saját GPU-hoz igazítva
nvcc -O3 -std=c++17 -arch=sm_86 -lineinfo stencil.cu -o stencil

# Egy kernel egy indítása teljes profillal (pozicionális argumentumok: n, block, streams);
# -s 5: az 5 warm-up indítás kihagyása, -c 1: egy mért indítás
ncu --set full --csv -k regex:stencil_naive -s 5 -c 1 ./stencil 67108864 256 0 > ncu_naive.csv
ncu --set full --csv -k regex:stencil_tiled -s 5 -c 1 ./stencil 67108864 256 0 > ncu_tiled.csv

# Célzott mérés
ncu --section SpeedOfLight \
    --section Occupancy \
    --section MemoryWorkloadAnalysis \
    ./stencil 67108864 256 0

A következő metrikákat érdemes figyelni:

  • gpu__time_duration.avg: a kernel átlagos futásideje.
  • sm__throughput.avg.pct_of_peak_sustained_elapsed: az SM-ek kihasználtsága a csúcsteljesítményhez képest.
  • l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum: a globális memóriából az L1-be beolvasott 32 bájtos szektorok száma. A naiv és tiled változat között itt csökkenést várunk; a DRAM-forgalom (dram__bytes_read.sum) ettől függetlenül alig változhat.
  • l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum: shared memory bank conflict.
  • launch__occupancy_limit_shared_mem: a shared memory miatti occupancy korlát.
  • smsp__average_warp_latency_per_inst_issued.ratio: átlagos warp-késleltetés (a metrikaneveket ncu --query-metrics kimenettel ellenőrizzük a telepített verzióban).

A Nsight Systems a teljes alkalmazás idővonalát mutatja. A streames változat ellenőrzésére:

nsys profile -o stencil_2s --stats=true ./stencil 67108864 256 2

Az elkészült stencil_2s.nsys-rep fájlban a H2D, kernel és D2H sávok átfedése vizuálisan ellenőrizhető. Ha a sávok szorosan egymás után következnek, akkor az átfedés nem jött létre, és a memóriamásolás valószínűleg lapozható memóriából történik, vagy a stream szinkronizációs pontja sorosít.

33.3.10 Tipikus hibák és helyes megoldások

  1. Túl korai optimalizálás mérés nélkül.
    Hiba: valaki a kód első változatába azonnal beépíti a tilinget, az occupancy-hangolást és a streameket, de nem készít baseline-t.
    Helyes: először a naiv verziót mérjük meg, és a profilkép alapján döntünk.

  2. Csak a kernelidőt nézzük, a host-device másolást nem.
    Hiba: a kernel gyors, de a teljes alkalmazás lassú a sok cudaMemcpy miatt.
    Helyes: a mérési naplóban külön soroljuk fel a H2D, a kernel és a D2H időket.

  3. Az occupancy-t öncélként maximalizáljuk.
    Hiba: a regiszterhasználatot mesterségesen leszorítjuk, ami spillt okoz, csak hogy magasabb legyen az occupancy.
    Helyes: az occupancy-t a profilkép kontextusában értelmezzük. Ha a kernel memória-késleltetésre vár, akkor hasznos a magas foglaltság; ha számításkorlátos, akkor a kevesebb aktív warp is elég lehet.

  4. Bank conflict feltételezése vagy figyelmen kívül hagyása mérés nélkül.
    Hiba: a stride-1 stencil-olvasást (s[local - 1], s[local], s[local + 1]) conflictosnak gondoljuk, vagy a valóban conflictos mintát (például s[2 * tid], 2D tömb oszlopirányú olvasása) nem ellenőrizzük.
    Helyes: a stride-1 olvasás conflict-mentes; a gyanús mintákat a Nsight Compute metrikájával mérjük, és szükség esetén paddinget alkalmazunk.

  5. Nem elegendő ismétlés vagy hideg cache.
    Hiba: egyetlen futásból vonunk le következtetést.
    Helyes: legalább 5 warm-up, legalább 20 ismétlés, medián és szórás.

  6. Változó órajel és hőmérséklet.
    Hiba: a GPU boost-órajele a mérés közben ingadozik, a mérési naplóban mégis állandó csúcsértékkel számolunk.
    Helyes: a mérés előtt rögzítjük a power limitet, az órajelet és a hőmérsékletet; szükség esetén nvidia-smi naplót készítünk.

  7. Stream esetén lapozható host memória.
    Hiba: malloc-kal, new-val vagy std::vector-ral foglalt lapozható host memóriából hívunk cudaMemcpyAsync-et, ami nem fedhető át teljesen a számítással (a driver közbülső pufferen át másol). (A cudaMalloc eszközmemóriát foglal, nem host memóriát.)
    Helyes: cudaMallocHost vagy cudaHostRegister használata. Darabolt feldolgozásnál a chunk-határokon a stencil halo elemei is kellenek: a szomszéd chunk másolásának befejezését eseménnyel kell bevárni, és a streames változat eredményét a nem streames változattal kell összevetni.

  8. Nem ellenőrzött kernelhiba.
    Hiba: a kernel indítása után nem hívunk cudaGetLastError-t, és a mérési eredményt hibás kernelre is rögzítjük.
    Helyes: minden API-hívást ellenőrizni kell, a mérés előtt cudaDeviceSynchronize-et hívunk.

33.3.11 Labor: Nsight-alapú optimalizálás

33.3.11.1 Kiinduló kód

A labor az alábbi, teljes példát használja. A kód FP32 pontossággal, 1D, 3 pontos stencilt számol, és pozicionális parancssori argumentumokból veszi az n méretet, a blokkméretet és a streamszámot (./stencil [n] [block] [streams]). Minden kernelindítás után hibaellenőrzés van, minden változat eredményét CPU-referenciához hasonlítja, és az időket eseményenként mérve szórással adja meg. A kódot a könyv szerzői nem fordították és nem futtatták hardveren.

// stencil.cu
// CUDA C++ (C++17); nvcc 12.x; GPU: a 33.1 referencia-GPU (CC 8.6 -> sm_86), verziók a naplóba
// Fordítás: nvcc -O3 -std=c++17 -arch=sm_86 -lineinfo stencil.cu -o stencil
// Futtatás: ./stencil [n] [block] [streams]    pl. ./stencil 67108864 256 2
#include <cuda_runtime.h>
#include <algorithm>
#include <chrono>
#include <cmath>
#include <cstdio>
#include <cstdlib>
#include <vector>

#define CUDA_CHECK(call)                                               \
    do {                                                               \
        cudaError_t err_ = (call);                                     \
        if (err_ != cudaSuccess) {                                     \
            std::fprintf(stderr, "CUDA error %s:%d: %s\n",             \
                         __FILE__, __LINE__, cudaGetErrorString(err_)); \
            std::exit(EXIT_FAILURE);                                   \
        }                                                              \
    } while (0)

constexpr int RADIUS = 1;
constexpr int ITERS = 20;

__global__ void stencil_naive(const float* __restrict__ in,
                              float* __restrict__ out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    float acc = 0.0f;
    for (int r = -RADIUS; r <= RADIUS; ++r) {
        int j = min(max(i + r, 0), n - 1);   // CUDA beépített int min/max
        acc += in[j];
    }
    out[i] = acc / (2 * RADIUS + 1);
}

// Az out[begin .. begin+count) tartományt számolja; `in` a teljes bemenet (device).
// Egy blokk blockDim.x elemet dolgoz fel. A nem streames futás: begin = 0, count = n.
__global__ void stencil_tiled(const float* __restrict__ in,
                              float* __restrict__ out, int n,
                              int begin, int count) {
    extern __shared__ float s[];
    int base = begin + blockIdx.x * blockDim.x;
    int i = base + threadIdx.x;
    int local = threadIdx.x + RADIUS;

    s[local] = in[min(i, n - 1)];            // minden szál tölt: nincs inicializálatlan elem
    if (threadIdx.x < RADIUS) {
        s[threadIdx.x] = in[max(base - RADIUS + (int)threadIdx.x, 0)];
        s[blockDim.x + RADIUS + threadIdx.x] =
            in[min(base + (int)blockDim.x + (int)threadIdx.x, n - 1)];
    }
    __syncthreads();

    if (i < begin + count && i < n) {
        float acc = 0.0f;
        for (int r = -RADIUS; r <= RADIUS; ++r) {
            acc += s[local + r];
        }
        out[i] = acc / (2 * RADIUS + 1);
    }
}

static void mean_sd(const std::vector<double>& t, double& m, double& sd) {
    m = 0.0;
    for (double x : t) m += x;
    m /= t.size();
    double v = 0.0;
    for (double x : t) v += (x - m) * (x - m);
    sd = t.size() > 1 ? std::sqrt(v / (t.size() - 1)) : 0.0;
}

// Medián (a vektor másolatán rendez)
static double median(std::vector<double> t) {
    std::sort(t.begin(), t.end());
    size_t k = t.size();
    return (k % 2) ? t[k / 2] : 0.5 * (t[k / 2 - 1] + t[k / 2]);
}

// Kernel mérése: 5 warm-up, majd ITERS külön eseménypárral mért futás
template <typename Launch>
static void bench(const char* name, Launch launch, double bytes_per_iter) {
    for (int w = 0; w < 5; ++w) launch();
    CUDA_CHECK(cudaGetLastError());
    CUDA_CHECK(cudaDeviceSynchronize());
    cudaEvent_t e0, e1;
    CUDA_CHECK(cudaEventCreate(&e0));
    CUDA_CHECK(cudaEventCreate(&e1));
    std::vector<double> t;
    for (int it = 0; it < ITERS; ++it) {
        CUDA_CHECK(cudaEventRecord(e0, 0));
        launch();
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaEventRecord(e1, 0));
        CUDA_CHECK(cudaEventSynchronize(e1));
        float ms = 0.0f;
        CUDA_CHECK(cudaEventElapsedTime(&ms, e0, e1));
        t.push_back(ms);
    }
    CUDA_CHECK(cudaEventDestroy(e0));
    CUDA_CHECK(cudaEventDestroy(e1));
    double m, sd;
    mean_sd(t, m, sd);
    double med = median(t);
    std::printf("%-8s medián %.3f ms +- %.3f ms (%.1f %%), "
                "eff. savszelesseg (8 B/elem): %.1f GB/s\n",
                name, med, sd, 100.0 * sd / m, bytes_per_iter / (med * 1e-3) / 1e9);
}

int main(int argc, char** argv) {
    int n = (argc > 1) ? std::atoi(argv[1]) : (1 << 26);
    int block = (argc > 2) ? std::atoi(argv[2]) : 256;
    int streams_count = (argc > 3) ? std::atoi(argv[3]) : 0;
    const int num_chunks = 4;
    if (n <= 0 || block <= 0 || block < RADIUS ||
        (streams_count > 0 && n % (num_chunks * block) != 0)) {
        std::fprintf(stderr, "hibas argumentum "
                     "(streames futashoz n %% (4 * block) == 0 kell)\n");
        return 1;
    }

    const size_t bytes = (size_t)n * sizeof(float);
    float *h_in = nullptr, *h_out = nullptr;
    CUDA_CHECK(cudaMallocHost(&h_in, bytes));
    CUDA_CHECK(cudaMallocHost(&h_out, bytes));
    for (int i = 0; i < n; ++i) h_in[i] = static_cast<float>(i % 1000) * 0.001f;

    // CPU-referencia (azonos műveleti sorrend: bitazonos eredményt várunk)
    std::vector<float> ref(n);
    for (int i = 0; i < n; ++i) {
        float acc = 0.0f;
        for (int r = -RADIUS; r <= RADIUS; ++r) {
            int j = std::min(std::max(i + r, 0), n - 1);
            acc += h_in[j];
        }
        ref[i] = acc / (2 * RADIUS + 1);
    }
    auto validate = [&](const char* name) {
        double maxdiff = 0.0;
        for (int i = 0; i < n; ++i)
            maxdiff = std::fmax(maxdiff, std::fabs((double)h_out[i] - ref[i]));
        std::printf("%-8s max |GPU - CPU| = %.3e\n", name, maxdiff);
    };

    float *d_in = nullptr, *d_out = nullptr;
    CUDA_CHECK(cudaMalloc(&d_in, bytes));
    CUDA_CHECK(cudaMalloc(&d_out, bytes));
    CUDA_CHECK(cudaMemcpy(d_in, h_in, bytes, cudaMemcpyHostToDevice));

    const int grid = (n + block - 1) / block;
    const int shared_bytes = (block + 2 * RADIUS) * sizeof(float);
    // algoritmikus forgalom: 4 B olvasás + 4 B írás / elem
    const double bytes_alg = 8.0 * n;

    bench("naive", [&] { stencil_naive<<<grid, block>>>(d_in, d_out, n); }, bytes_alg);
    CUDA_CHECK(cudaMemcpy(h_out, d_out, bytes, cudaMemcpyDeviceToHost));
    validate("naive");

    bench("tiled", [&] {
        stencil_tiled<<<grid, block, shared_bytes>>>(d_in, d_out, n, 0, n);
    }, bytes_alg);
    CUDA_CHECK(cudaMemcpy(h_out, d_out, bytes, cudaMemcpyDeviceToHost));
    validate("tiled");

    if (streams_count > 0) {
        const int chunk = n / num_chunks;
        // Teljes (H2D + kernel + D2H) futás `ns` streammel; a végén a host-órás idő (ms)
        auto pipeline = [&](int ns) {
            std::vector<cudaStream_t> st(ns);
            for (auto& x : st) CUDA_CHECK(cudaStreamCreate(&x));
            std::vector<cudaEvent_t> ev(num_chunks);
            for (auto& e : ev)
                CUDA_CHECK(cudaEventCreateWithFlags(&e, cudaEventDisableTiming));
            auto t0 = std::chrono::steady_clock::now();
            for (int c = 0; c < num_chunks; ++c) {
                cudaStream_t s = st[c % ns];
                CUDA_CHECK(cudaMemcpyAsync(d_in + (size_t)c * chunk, h_in + (size_t)c * chunk,
                                      chunk * sizeof(float), cudaMemcpyHostToDevice, s));
                CUDA_CHECK(cudaEventRecord(ev[c], s));
            }
            for (int c = 0; c < num_chunks; ++c) {
                cudaStream_t s = st[c % ns];
                if (c > 0)              CUDA_CHECK(cudaStreamWaitEvent(s, ev[c - 1], 0));
                if (c + 1 < num_chunks) CUDA_CHECK(cudaStreamWaitEvent(s, ev[c + 1], 0));
                stencil_tiled<<<chunk / block, block, shared_bytes, s>>>(
                    d_in, d_out, n, c * chunk, chunk);
                CUDA_CHECK(cudaGetLastError());
                CUDA_CHECK(cudaMemcpyAsync(h_out + (size_t)c * chunk,
                                           d_out + (size_t)c * chunk,
                                           chunk * sizeof(float),
                                           cudaMemcpyDeviceToHost, s));
            }
            CUDA_CHECK(cudaDeviceSynchronize());
            auto t1 = std::chrono::steady_clock::now();
            for (auto& e : ev) CUDA_CHECK(cudaEventDestroy(e));
            for (auto& x : st) CUDA_CHECK(cudaStreamDestroy(x));
            return std::chrono::duration<double, std::milli>(t1 - t0).count();
        };
        for (int ns : {1, streams_count}) {
            for (int w = 0; w < 5; ++w) pipeline(ns);        // 5 warm-up
            std::vector<double> t;
            for (int it = 0; it < 20; ++it) t.push_back(pipeline(ns));   // 20 ismétlés
            double m, sd;
            mean_sd(t, m, sd);
            std::printf("pipeline, %d stream: medián %.3f ms +- %.3f ms "
                        "(teljes lánc: H2D + kernel + D2H)\n", ns, median(t), sd);
            validate("pipeline");
        }
    }

    CUDA_CHECK(cudaFree(d_in));
    CUDA_CHECK(cudaFree(d_out));
    CUDA_CHECK(cudaFreeHost(h_in));
    CUDA_CHECK(cudaFreeHost(h_out));
    return 0;
}

33.3.11.2 Feladatok

  1. Baseline: futtasd a naiv és a tiled változatot n = 67 108 864 mérettel, block = 256 blokkmérettel. Töltsd ki a mérési napló táblázatát. Számítsd ki az effektív sávszélességet a tényleges adatmozgatásból.

  2. Tiling elemzése: készíts Nsight Compute profilt a naiv és a tiled kernelről. Hasonlítsd össze a gpu__time_duration.avg, a globális memória szektorok számát és a DRAM-bájtokat (dram__bytes_read.sum). Fogalmazd meg, hogy a tiling mit változtatott a load/store- és a DRAM-forgalmon, és miért. Mérd meg a bank-konfliktus metrikát a 33.2 heat_step_tiled kernelére is.

  3. Occupancy hangolás: futtasd a tiled kernelt block = 128, 256, 512 értékekkel. Jegyezd fel a regiszterhasználatot és a shared memory méretet. A Nsight Compute Occupancy szekciójával ellenőrizd a foglaltságot. Döntsd el, melyik blokkméret a legjobb, és indokold meg.

  4. Streamek: implementáld a 2 streames változatot a fenti minta alapján. Készíts Nsight Systems profilt, és ellenőrizd a H2D, kernel és D2H átfedést. Ha nincs átfedés, keresd meg a sorosítás okát.

  5. Dokumentáció: a mérési naplóban tüntesd fel a GPU típusát, a drivert, a CUDA-verziót, az FP32 pontosságot, a warm-up és ismétlésszámot, az átlagot és a szórást. A mért eredményt külön oszlopban jelöld, a modellből számított várt értéket pedig külön.

  6. Visszakötés a záróprojekthez: alkalmazd ugyanezt a ciklust (baseline, profil, hipotézis, egyetlen beavatkozás, mérés) a 33.2 alfejezet heat_step_naive és heat_step_tiled kernelére a 33.1 charter metrikáival (4096 × 4096, 1000 lépés, effektív sávszélesség a 448 GB/s névleges értékhez viszonyítva), és hasonlítsd össze a következtetéseket a 1D mikrobenchmarkéval.

A feladatokhoz nem tartozik megoldás: a válasz a saját mérésből és profilból adódik.

33.3.12 Önellenőrző kérdés

Miért nem elegendő a kernelidőt nézni akkor, ha a záróprojekt rendszere host-device másolást is végez?
Válaszvázlat: A teljes alkalmazás futásideje a H2D másolás, a kernel és a D2H másolás összege, illetve átfedés esetén azok időbeli ütemezése. Ha csak a kernelidőt mérjük, nem látjuk a lapozható memória, a szinkron másolás vagy a stream nélküli sorosítás hatását. A Nsight Systems timeline és külön eseményekkel mért fázisidők együttesen mutatják meg, hol vész el az idő, és hol érdemes streameket vagy pinned memóriát bevezetni.

33.3.13 Összegzés

A teljesítmény hangolása a záróprojektben nem egyetlen nagy optimalizálás, hanem egymásra épülő, méréssel igazolt lépések sorozata. A tiling csökkenti a globális load/store-forgalmat és a gyorsítótár-terhelést (a DRAM-forgalmat csak akkor, ha az L1/L2 nem úgyis elnyeli az újraolvasást), az occupancy-hangolás a késleltetés elrejtését javítja, a streamek pedig a másolás és számítás átfedését teszik lehetővé. Minden beavatkozást ugyanazon bemeneten, rögzített környezetben kell mérni, és a profilképnek meg kell erősítenie a várt hatást. Csak így lehet különválasztani a valódi nyereséget a zajtól, és így készíthető elő a 33.4 alfejezetben következő validációs és dokumentációs szakasz.
