17.3 Keresés és binary search

Ez az alfejezet a rendezett tömbökben végzett keresést tárgyalja GPU-n: a lower_bound/upper_bound szemantikát, a batch binary search kernelt, a divergencia és a memóriaelérés következményeit, majd egy ellenőrizhető labort. A korábban tárgyalt rendezések (radix sort, bitonic rendezés) után természetes folytatás: a rendezett adat keresése a hisztogram-, join- és tartománylekérdezés-szerű műveletek építőeleme.

17.3.1 A párhuzamos keresés problémája

Az előző alfejezet rendezési anyagára építve most feltesszük, hogy a bemeneti tömb monoton növekvően rendezett. A rendezett tömbön a keresés nem egyetlen elemi művelet, hanem egy egész lekérdezési család: megkereshetjük egy konkrét kulcs első előfordulását, azt az indexet, ahová a kulcs beszúrható, vagy egy intervallum két határát. A GPU-n a keresés nem úgy párhuzamosítható, hogy a logaritmikus lépéseket szétosztjuk a szálak között – ez a naiv szemlélet a bináris keresés belső függőségei miatt csak korlátozott (logaritmikus alapváltásnyi) gyorsulást ad; a fő párhuzamosság a lekérdezések tömegéből jön. A párhuzamosság forrása a lekérdezések tömege: ha sok kulcsot kell keresni ugyanabban a rendezett tömbben, minden kulcshoz tartozhat egy szál, és a szálak egymástól függetlenül futhatnak.

Ezt a mintát batch binary searchnek nevezzük. Ez az alfejezet a batch binary search kernel építőköveit, a lower_bound és upper_bound szemantikáját, a SIMT-divergencia következményeit és a memóriaelérési mintákat tárgyalja. A hangsúly a gyakorlati, ellenőrizhető kernelíráson van. A következő alfejezet (selection és order statistics) más technikákat (quickselect, radix select) használ; a keresés ott nem épül közvetlenül a lower_bound-ra.

17.3.2 lower_bound és upper_bound a rendezett tömbön

A C++ STL lower_bound algoritmusa egy rendezett tartományban megadja azt a pozíciót, ahová a keresett kulcs a monoton növekvő sorrend megtartásával beilleszthető. Precízebben:

lower_bound⁡(q)=|{j|0≤j<n,data[j]<q}|. \operatorname{lower\_bound}(q) = \left|\{\,j\;|\;0 \le j < n,\; data[j] < q\,\}\right|.

Ez az első olyan j index, amelyre data[j]≥qdata[j] \ge q teljesül, vagy n, ha ilyen elem nincs. A upper_bound az első olyan index, amelyre data[j]>qdata[j] > q, másképpen:

upper_bound⁡(q)=|{j|0≤j<n,data[j]≤q}|. \operatorname{upper\_bound}(q) = \left|\{\,j\;|\;0 \le j < n,\; data[j] \le q\,\}\right|.

A kettő közötti tartomány az összes q-val egyenlő elem folytonos intervallumát adja. Tekintsük a következő kis példát:

data = [1, 3, 3, 5, 7]

lower_bound(3) -> 1
upper_bound(3) -> 3
lower_bound(4) -> 3
lower_bound(0) -> 0
lower_bound(8) -> 5

A GPU-s keresési kernelekben ritkán van szükség a std::lower_bound C++-os verziójának közvetlen hívására, de a szemantika pontos ismerete kritikus. A kulcskeresés, a range query, a hisztogram és a join jellegű műveletek mind ezt az alsó/felső határ definíciót használják.

A párhuzamos keresés szempontjából a lower_bound azért előnyösebb a lineáris keresésnél, mert a lépésszáma O(log⁡n)O(\log n). Ez a GPU-n azonban csak a lépések számát korlátozza; a memóriaelérés mintája ettől még lehet kedvezőtlen.

17.3.3 Batch binary search: a párhuzamosság forrása

A bináris keresés belső szerkezete szekvenciális: a következő középindex az aktuális intervallum határaitól függ. Egyetlen kulcs keresése a lépések egymásra épülése miatt csak korlátozottan párhuzamosítható: pp szál egy lépésben p+1p+1 részre osztja az intervallumot, így ⌈log⁡p+1(n+1)⌉\lceil \log_{p+1}(n+1) \rceil lépés kell (32 szállal n=224n = 2^{24}-re 5 lépés, a bináris keresés 24–25 lépése helyett), de lépésenként pp-szer annyi olvasással. A GPU-n viszont három eltérő stratégiát érdemes megkülönböztetni.

  1. One-thread-per-query batch: minden szál egyetlen kulcsot keres. Ez a legegyszerűbb és a leggyakoribb olyan esetekben, amikor a lekérdezések száma nagy. A párhuzamosság a query-k darabszámából jön.
  2. Warp-per-query: egyetlen kulcs keresésére egy egész warp dolgozik. Az intervallumot a warp szálai közösen, ugrásszerűen vizsgálják; ez akkor hasznos, ha a query-k száma kicsi, és a memóriaelérést a warp jobban ki tudja használni.
  3. Redukció-alapú tartomány-összevonás: nagyon nagy tömb és kevés kulcs esetén minden blokk egy tartományt vizsgál, majd atomi művelettel vagy kétfázisú redukcióval áll elő a globális alsó határ.

Az alfejezet fókusza az első stratégia, mert ez a legjobban illeszkedik a rendezés utáni táblaműveletekhez, és a leggyakrabban használt minta. A második és harmadik stratégia akkor válik fontossá, ha a lekérdezési arány m/nm/n kicsi; a másodikat a divergenciáról szóló szakasz végén vázoljuk, a harmadikat csak megemlítjük.

17.3.4 Naiv batch lower_bound kernel

Az alábbi kernel egy CUDA C++ template, amely minden szálra elvégzi a szekvenciális lower_bound logikát. A lo és hi a keresési intervallum határa (a [lo, hi) félig nyílt: a lo benne van, a hi már nem), a mid a középindex:

// CUDA C++ (C++17)
template <typename T>
__global__ void batch_lower_bound_kernel(
    const T* __restrict__ data, std::size_t n,
    const T* __restrict__ queries, std::size_t m,
    int* __restrict__ out)
{
    std::size_t tid = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    if (tid >= m) return;

    const T q = queries[tid];
    std::size_t lo = 0;
    std::size_t hi = n;

    while (lo < hi) {
        std::size_t mid = lo + ((hi - lo) >> 1);
        if (data[mid] < q) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = static_cast<int>(lo);
}

A kernelben a szekvenciális lower_bound szokásos szerkezetét tartjuk meg: a lo az alsó (zárt), a hi a felső (kizáró) intervallumhatár, a mid a lo és hi közötti, lefelé kerekített közép. A data[mid] < q összehasonlítás után az intervallum feleződik, és az elágazás a keresett kulcs helye szerint dönt.

A kernel launch alakja:

dim3 block(256);
dim3 grid(static_cast<unsigned int>((m + block.x - 1) / block.x));
cudaStream_t stream = 0;

batch_lower_bound_kernel<int><<<grid, block, 0, stream>>>(
    d_data, n, d_queries, m, d_out);

A grid- és blockdimenziók a m lekérdezésszámhoz igazodnak. A data és queries pointerek const és __restrict__ minősítőt kapnak; a __restrict__ azt ígéri a fordítónak, hogy a mutatók nem aliasolódnak, így a compiler read-only cache-t és agresszívabb optimalizációt alkalmazhat. A kernelben az out[tid] írása coalesced, mert a szomszédos szálak szomszédos indexeket írnak. A queries[tid] olvasása szintén coalesced, ha a szálak lineárisan indexeltek. A nehéz memóriaelérés tehát nem ezeknél, hanem a data[mid] olvasásnál jelenik meg.

17.3.5 Divergencia és memóriaelérés

A batch binary search kernel legfontosabb jellemzője, hogy a szálak egymástól függetlenül, más-más intervallumhatárokkal dolgoznak. Egy warp 32 szálat futtat egyszerre. A while ciklus feltétele és a belső if elágazás miatt a szálak egy része különböző vezérlési útra lép.

A lépésszám-divergencia abból adódik, hogy a szekvenciális bináris keresés lépésszáma az intervallum hosszától és a kulcs elhelyezkedésétől függ. Ha nn nem kettőhatvány, a különböző kulcsoknál a ciklus hossza eltérhet. A laborban az n=224n = 2^{24} méretet ezért választjuk kettőhatványnak: ebben az esetben a lépésszám minden szálra 24 vagy 25 (az eredménytől függően ±1 eltérés lehet, például 25, ha az eredmény 0), így a lépésszám-divergencia gyakorlatilag eltűnik, és a megfigyelés a memóriaelérésre összpontosítható. Ez a választás didaktikailag fontos: a batch binary search megértéséhez a vezérlési és memória-divergenciát külön kell kezelni.

A memóriaelérési divergencia a gyakorlatban nagyobb teljesítményhatású. A data[mid] utasítás a warp 32 szálában 32 különböző címéről olvas, mert minden szál más mid-et számolt. A global memória coalescing – amelyet a memóriahierarchiáról szóló fejezet részletez – ilyenkor töredezetté válik. Egy 4 bájtos int elemeket tartalmazó tömbben a 32 szál által kért 32 cím legfeljebb 32 különböző 32 bájtos szektort (és legfeljebb 32 cache line-t) érint, így a memória-alrendszer a hasznos adatnál sokkal többet mozgat. A bináris keresés memóriateljesítménye ezért inkább a véletlen hozzáférésű cache-viselkedéshez, nem a streaming sávszélességhez hasonlít.

A cache-viselkedés lépésenként eltérő: a keresési fa felső szintjein (az első néhány lépésben) minden szál ugyanazt vagy néhány azonos elemet olvas (broadcast), ezek az L1/L2 cache-ben forrón maradnak; véletlen lekérdezésekből álló warpnál az első 3–4 lépésben még közös vagy kevés elemet olvasnak a szálak (broadcast), a 8. lépés körül azonban már mind a 32 szál külön szektort ér el (lektori szimuláció, ellenőrzendő); a fa felső szintjei globálisan kevés elemet jelentenek, ezért az L2-ben forrók maradnak, L2-hibát főként az alsó néhány szint okoz. Rendezett lekérdezéssorrendnél a közös útvonal sokkal tovább (n = 2^24-nél kb. 12 lépésig) megmarad. Ebből következik, hogy a lekérdezések előzetes rendezése vagy csoportosítása (így a szomszédos szálak hasonló útvonalon járnak), a cache-barát elrendezés (Eytzinger-elrendezés, B-fa jellegű tömb) és a több elágazású keresés (lásd alább) javíthat a teljesítményen. Ezek hatását mindig mérni kell, rendezett és véletlen lekérdezéssorrenddel is.

A C++ kódban a const T* __restrict__ data segíti a fordítót abban, hogy a data hozzáférést a read-only cache (LDG) útvonalon keresztül valósítsa meg. Ez a lookup-tábla jellegű hozzáféréseknél csökkentheti a L1-nyomást, de a coalescing jellegzetességein nem változtat. Ha a rendezett tömb kicsi, a shared memory használata is szóba jöhet:

// Részlet: shared memory tiling, ha a rendezett tömb befér egy blokkba.
extern __shared__ int s_data[];
// Betöltés coalesced módon, __syncthreads() után a bináris keresés.

A shared memory-ben a bináris keresés sebességére a bank conflictok is hatással lesznek, mert a szálak itt is különböző címeket olvasnak. A legtöbb valós esetben a rendezett tömb jóval nagyobb, mint a shared memory, ezért a batch binary search global memory és cache-hierarchia függő.

Egy további megoldás a warp-szintű, 32-ary keresés (egy warp egy kulcsot keres). Minden lépésben az aktuális [lo, hi) intervallumot 32 egyenlő szakaszra osztjuk, a 32 szál a szakaszok utolsó elemét olvassa (32 elágazási pont egyetlen lépésben), a __ballot_sync és a __popc megadja, hány szakasz van teljesen a kulcs alatt, és az intervallum a megfelelő szakaszra szűkül. Egy lépés így 5 bináris lépést vált ki; az első lépésekben a 32 olvasás szétszórt (n/32 távolságú), a nyereség a függő memóriaolvasások számának csökkenése. A vázlat (nem fordított, nem futtatott):

// CUDA C++ vázlat: egy warp egy kulcsot keres; az egész warp meghívja (teljes maszk)
__device__ std::size_t warp_lower_bound(const int* data, std::size_t n, int q)
{
    const unsigned lane = threadIdx.x & 31u;
    std::size_t lo = 0, hi = n;                       // [lo, hi) félig nyílt
    while (hi - lo > 32) {
        std::size_t step = (hi - lo + 31) / 32;       // egy szakasz hossza
        std::size_t p = lo + (lane + 1) * step - 1;   // a szakasz utolsó eleme
        if (p > hi - 1) p = hi - 1;
        unsigned b = __ballot_sync(0xFFFFFFFFu, data[p] < q);
        std::size_t c = __popc(b);                    // a q alatti szakaszok száma
        std::size_t new_lo = lo + c * step;
        if (new_lo > hi) new_lo = hi;
        std::size_t new_hi = new_lo + step;
        if (new_hi > hi) new_hi = hi;
        lo = new_lo; hi = new_hi;
    }
    std::size_t pos = lo + lane;                      // ≤ 32 elem: egy lépésben
    bool less = (pos < hi) && (data[pos] < q);
    return lo + __popc(__ballot_sync(0xFFFFFFFFu, less));
}

A batch (egy szál – egy kulcs) és a warp-szintű keresés közötti választás a lekérdezések száma, a tömb mérete és a cache-paraméterek függvénye, ezért mérni kell. A redukció-alapú tartomány-összevonás (a fejezetben felsorolt harmadik stratégia) kevés kulcs és nagyon nagy tömb esetére való; ebben az alfejezetben csak megemlítjük, nem valósítjuk meg.

17.3.6 Gyakori hibák és helyes megoldások

A batch binary search kernelben több hiba ismétlődően felbukkan.

  1. Rendezetlen bemenet: ha a data nem monoton növekvő, a lower_bound eredménye undefined. Ez a leggyakoribb szemantikai hiba, mert a kernel nem ellenőrzi a rendezettséget. A labor előtt a generált data rendezettségét a CPU-oldali std::is_sorted-del ellenőrizni kell.
  2. Túlfolyás a középindexben: a (lo + hi) / 2 kifejezés nagy nn esetén túlcsordulhat. A helyes formula lo + (hi - lo) / 2 vagy lo + ((hi - lo) >> 1). A labor kód ezt használja.
  3. int méretindexek: ha nn meghaladja az INT_MAX-ot, a kimeneti index nem fér int-be. A laborban n=224n = 2^{24}, tehát az int elegendő, de nagyobb tömböknél size_t kimenetet kell használni.
  4. Nem ellenőrzött CUDA-hívások: a launch utáni cudaGetLastError és a cudaDeviceSynchronize hiánya elrejtheti a hibákat. A könyvlaborkód minden API-hívást a CUDA_CHECK makróval ellenőriz.
  5. Lépésszám-divergencia: ha nn nem kettőhatvány, a szálak különböző számú iterációt futnak. A kettőhatvány méret a labormérésben ezt nagyrészt kontrollálja (az iterációszám ±1-gyel még változhat).
  6. Határesetek és ismétlődő kulcsok tesztelésének hiánya: ha a tesztadat minden kulcsa egyedi és a lekérdezések a tartományon belül vannak, a lower_bound és az upper_bound közötti különbség, valamint az alsó és felső szélső eset nem tesztelődik. A laborban ezért ismétlődő kulcsok és tartományon kívüli lekérdezések szerepelnek.
  7. Rossz __restrict__/const minősítés: ha a data pointer nem const restrict, a compiler nem feltételezhet read-only hozzáférést, és a cache-útvonal kevésbé hatékony.
  8. Nincs warmup és túl rövid mérési ablak: a laborban 10 warm-up futtatást és 20 egyedileg, eseménypárral mért futást írunk elő; a mediánt, az IQR-t, a minimumot és a maximumot közöljük.
  9. Végtelen ciklusveszély: ha a kernelben a lo/hi frissítése hibás, a while ciklus sosem ér véget, és az eszköz leállását okozhatja. A labor kernelét izolált környezetben, időkorláttal kell futtatni.

A helyes alsó határ ebben a fejezetben a szekvenciális lower_bound szabályok pontos megtartásával, de a GPU párhuzamossági modelljéhez illesztve készül.

17.3.7 Labor: batch binary search

A labor célja egy batch binary search kernel elkészítése, amely rendezett int tömbben végzi a lower_bound és az upper_bound lekérdezést (egy bool sablonparaméter választ a kettő között). A bemeneti méret n=224n = 2^{24}, a lekérdezések száma m=220m = 2^{20}. A tesztadat szándékosan ismétlődő kulcsokat tartalmaz (data[i] = i / 4, így minden érték négyszer fordul elő), a lekérdezések pedig a tömb értéktartományán kívülre is esnek (-1 és a maximum fölött), így a két határfüggvény különbsége és a szélső esetek is tesztelődnek. A referencia a CPU std::lower_bound és std::upper_bound. A kód nem fordított, nem futtatott vázlat; az első futtatás után a mérési naplót kell kitölteni.

// CUDA C++ (C++17)
// batch_lower_bound.cu
#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>
#include <cstddef>
#include <vector>
#include <algorithm>
#include <random>
#include <cmath>

#define CUDA_CHECK(call)                                                        \
  do {                                                                          \
    cudaError_t err_ = (call);                                                  \
    if (err_ != cudaSuccess) {                                                  \
      std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__, __LINE__,     \
                   cudaGetErrorString(err_));                                   \
      std::exit(EXIT_FAILURE);                                                  \
    }                                                                           \
  } while (0)

// UPPER = false: lower_bound (első data[j] >= q), UPPER = true: upper_bound (első data[j] > q)
template <bool UPPER>
__global__ void batch_bound_kernel(
    const int* __restrict__ data, std::size_t n,
    const int* __restrict__ queries, std::size_t m,
    int* __restrict__ out)
{
    std::size_t tid = static_cast<std::size_t>(blockIdx.x) * blockDim.x + threadIdx.x;
    if (tid >= m) return;

    const int q = queries[tid];
    std::size_t lo = 0;
    std::size_t hi = n;

    while (lo < hi) {
        std::size_t mid = lo + ((hi - lo) >> 1);
        const bool go_right = UPPER ? !(q < data[mid]) : (data[mid] < q);
        if (go_right) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = static_cast<int>(lo);
}

int main() {
    const std::size_t n = std::size_t{1} << 24;  // 16 777 216
    const std::size_t m = std::size_t{1} << 20;  // 1 048 576

    // Bemeneti rendezett tömb ismétlődő kulcsokkal: minden érték 4-szer fordul elő
    std::vector<int> data(n);
    for (std::size_t i = 0; i < n; ++i) {
        data[i] = static_cast<int>(i / 4);
    }
    if (!std::is_sorted(data.begin(), data.end())) {   // előfeltétel-ellenőrzés
        std::fprintf(stderr, "A data tomb nem rendezett\n");
        return EXIT_FAILURE;
    }

    // Lekérdező kulcsok: -1 (a minimum alatt) .. n/4 (a maximum fölött)
    std::vector<int> queries(m);
    std::mt19937 rng(1234);
    std::uniform_int_distribution<int> dist(-1, static_cast<int>(n / 4));
    for (std::size_t i = 0; i < m; ++i) {
        queries[i] = dist(rng);
    }

    // CPU referencia (lower_bound és upper_bound)
    std::vector<int> ref_lo(m), ref_up(m);
    for (std::size_t i = 0; i < m; ++i) {
        ref_lo[i] = static_cast<int>(
            std::lower_bound(data.begin(), data.end(), queries[i]) - data.begin());
        ref_up[i] = static_cast<int>(
            std::upper_bound(data.begin(), data.end(), queries[i]) - data.begin());
    }

    // Device allokációk
    int* d_data = nullptr;
    int* d_queries = nullptr;
    int* d_out = nullptr;
    CUDA_CHECK(cudaMalloc(&d_data, n * sizeof(int)));
    CUDA_CHECK(cudaMalloc(&d_queries, m * sizeof(int)));
    CUDA_CHECK(cudaMalloc(&d_out, m * sizeof(int)));

    CUDA_CHECK(cudaMemcpy(d_data, data.data(), n * sizeof(int), cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(d_queries, queries.data(), m * sizeof(int), cudaMemcpyHostToDevice));

    dim3 block(256);
    dim3 grid(static_cast<unsigned int>((m + block.x - 1) / block.x));
    cudaStream_t stream = 0;

    // Warm-up
    for (int i = 0; i < 10; ++i) {
        batch_bound_kernel<false><<<grid, block, 0, stream>>>(
            d_data, n, d_queries, m, d_out);
        CUDA_CHECK(cudaGetLastError());
    }
    CUDA_CHECK(cudaDeviceSynchronize());

    // Mérési kör
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));

    const int reps = 20;                 // mért ismétlés (>= 20), egyedi eseménypárral
    std::vector<float> t(reps);
    for (int r = 0; r < reps; ++r) {
        CUDA_CHECK(cudaEventRecord(start, stream));
        batch_bound_kernel<false><<<grid, block, 0, stream>>>(
            d_data, n, d_queries, m, d_out);
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaEventRecord(stop, stream));
        CUDA_CHECK(cudaEventSynchronize(stop));
        CUDA_CHECK(cudaEventElapsedTime(&t[r], start, stop));
    }
    std::sort(t.begin(), t.end());
    const float med_ms = 0.5f * (t[reps / 2 - 1] + t[reps / 2]);   // reps páros
    const float iqr_ms = t[3 * reps / 4] - t[reps / 4];

    std::printf("batch_lower_bound: median=%.4f ms, IQR=%.4f ms, min=%.4f ms, max=%.4f ms (csak lower_bound merve)\n",
                med_ms, iqr_ms, t.front(), t.back());

    // Eredmény ellenőrzése mindkét határfüggvényre
    std::vector<int> host_out(m);
    std::size_t mismatches = 0;
    for (int variant = 0; variant < 2; ++variant) {
        if (variant == 0) {
            batch_bound_kernel<false><<<grid, block, 0, stream>>>(d_data, n, d_queries, m, d_out);
        } else {
            batch_bound_kernel<true><<<grid, block, 0, stream>>>(d_data, n, d_queries, m, d_out);
        }
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaDeviceSynchronize());
        CUDA_CHECK(cudaMemcpy(host_out.data(), d_out, m * sizeof(int), cudaMemcpyDeviceToHost));
        const std::vector<int>& ref = (variant == 0) ? ref_lo : ref_up;
        std::size_t mm = 0;
        for (std::size_t i = 0; i < m; ++i) {
            if (host_out[i] != ref[i]) {
                if (mm < 10) {
                    std::printf("%s mismatch at %zu: got=%d expected=%d\n",
                                variant == 0 ? "lower" : "upper", i, host_out[i], ref[i]);
                }
                ++mm;
            }
        }
        std::printf("%s_bound: %zu/%zu egyezik\n", variant == 0 ? "lower" : "upper", m - mm, m);
        mismatches += mm;
    }

    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));
    CUDA_CHECK(cudaFree(d_data));
    CUDA_CHECK(cudaFree(d_queries));
    CUDA_CHECK(cudaFree(d_out));

    return mismatches == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}

17.3.8 OpenCL és JAX kitekintés

A batch binary search ugyanazt az egy-szál-per-kulcs logikát követheti OpenCL-ben is:

// OpenCL C
__kernel void batch_lower_bound(
    __global const int* data, ulong n,
    __global const int* queries, ulong m,
    __global int* out)
{
    size_t tid = get_global_id(0);
    if (tid >= m) return;

    int q = queries[tid];
    size_t lo = 0;
    size_t hi = n;

    while (lo < hi) {
        size_t mid = lo + ((hi - lo) >> 1);
        if (data[mid] < q) {
            lo = mid + 1;
        } else {
            hi = mid;
        }
    }

    out[tid] = (int)lo;
}

A JAX eszközláncban a searchsorted funkcionális, vektorizált lekérdezést nyújt:

# JAX
import jax.numpy as jnp

# data: (n,) rendezett tömb, queries: (m,) lekérdezési tömb
idx_left = jnp.searchsorted(data, queries, side="left")    # lower_bound
idx_right = jnp.searchsorted(data, queries, side="right")  # upper_bound
# A kimenet backendenként (CPU/GPU/TPU) és verziónként eltérő módszerrel készülhet; a szemantikát ellenőrizni kell.

A JAX és XLA háttérrendszerén a searchsorted implementációja architektúra- és verziófüggő. A TPU-n a rendezettségi előfeltétel, a NaN-kezelés és a hibaszemantika nem minden változatban azonos a C++ STL-lel. Az OpenCL/JAX részletek itt csak API-szintű minták; a laborban a CUDA C++ verzió az ellenőrzött út. A hordozhatósági korlátokat minden valós mérés előtt a használt opencl/xla verzió dokumentációjával egyeztetni kell.

17.3.9 Önellenőrző kérdés

Egy warp 32 szálat futtat a batch binary search kernelből, és a data 4 bájtos int rendezett tömb. Miért nem elég a kernelünkben a const és __restrict__ minősítő ahhoz, hogy a data[mid] hozzáférés coalescingjét garantáljuk? Mely laborparaméterekkel (például n, m, grid, block, a lekérdezések sorrendje) tudná a memória-access hatékonyságát vizsgálni, és milyen Nsight Compute metrikával igazolná a diagnózist?

Válasz vázlat: a const/__restrict__ csak a fordítónak ad információt, a szálak címei a mid értékekből adódnak, ezért a 32 szál különböző szektorokat olvas. Vizsgálható a lekérdezések rendezett és véletlen sorrendje (a rendezett sorrend növeli a közös útvonalat), valamint az n (cache-be férés). Metrikák (a használt Nsight Compute verzióban a ncu --query-metrics listával ellenőrizendő nevek): l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum és l1tex__t_requests_pipe_lsu_mem_global_op_ld.sum hányadosa (szektor/kérés), smsp__sass_average_data_bytes_per_sector_mem_global_op_ld.pct, l1tex__t_sector_hit_rate.pct, lts__t_sector_hit_rate.pct.
