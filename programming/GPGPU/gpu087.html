23.2 CUTLASS

A CUTLASS (CUDA Templates for Linear Algebra Subroutines and Solvers) az NVIDIA nyílt forráskódú, kizárólag C++ sablonokra épülő könyvtára, amely hatékony GPU-implementációkat ad a lineáris algebrai primitívekhez, elsősorban a GEMM-hez. A CUTLASS nem egy fekete doboz: a fejlesztő fordítási időben dönt a tile méretekről, a memória-elrendezésről, a pipeline mélységéről és az epilogue műveletéről. Ez az alfejezet a CUTLASS GEMM hierarchiáját mutatja be, és egy izolált laboron keresztül demonstrálja a használatát.

23.2.1 A CUTLASS sablonkönyvtár és a GEMM hierarchia

A CUTLASS alapgondolata az, hogy a GEMM-et rétegesen bontja fel, és minden réteget külön sablonparaméterként kezel. A hierarchia alulról felfelé a következő:

  • Thread szint: a legelemibb szint, amely a memória-hozzáférésekért és az epilogue műveleteiért felel. Itt történik a vektorizált betöltés, a kimeneti elemek megformázása, valamint a skálázás és az aktiváció.
  • Warp szint: a warpok a Tensor Core mma.sync utasításokat hajtják végre, és a hozzájuk tartozó fragmenteket kezelik. A CUTLASS itt definiálja a warp tile méreteit, amelyek meghatározzák, hogy egy warp hány adatelemen dolgozik egyszerre.
  • Threadblock szint: egy SM-re kerülő szálblokk, amely a threadblock tile-t birtokolja. A threadblock felelős a shared memory-ba való betöltésért, a warpok közötti munkamegosztásért és a K dimenzió mentén történő iterációért.
  • Kernel szint: a GPU kernel függvénye, amely a gridet és a threadblockok közötti swizzle-t vezérli.
  • Device szint: a teljes GEMM művelet, amely a kernel launch konfigurációját, a workspace memóriát és a streamet foglalja össze.

A hierarchia lelkét a tile fogalma adja. A CUTLASS a teljes mátrixszorzást kisebb, jól meghatározott méretű blokkokra osztja. Például egy FP16 Tensor Core GEMM esetében tipikus konfiguráció:

using Gemm = cutlass::gemm::device::Gemm<
    cutlass::half_t, cutlass::layout::RowMajor,   // A
    cutlass::half_t, cutlass::layout::RowMajor,   // B
    float, cutlass::layout::RowMajor,             // C
    float,                                         // akkumulátor
    cutlass::arch::OpClassTensorOp,                // Tensor Core
    cutlass::arch::Sm80,                           // compute capability
    cutlass::gemm::GemmShape<128, 128, 32>,        // threadblock tile
    cutlass::gemm::GemmShape<64, 64, 32>,          // warp tile
    cutlass::gemm::GemmShape<16, 8, 16>,           // instruction shape (mma.sync.m16n8k16)
    cutlass::epilogue::thread::LinearCombination<
        float, 128 / cutlass::sizeof_bits<float>::value,
        float, float>,
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>,
    3                                                // pipeline stages
>;

Ebben a konfigurációban a threadblock tile 128×128×32: minden szálblokk egy 128 sorból, 128 oszlopból és 32 K-mélységből álló mátrixszeletet dolgoz fel. A warp tile 64×64×32: a threadblock 4 warpja (2×2) ilyen altile-eket kap. Az instruction shape 16×8×16 az Sm80 FP16 Tensor Core mma.sync.m16n8k16 utasítás geometriája (a 16×8×8 a Turing-örökség). A pipeline stages értéke 3, ami azt jelenti, hogy a CUTLASS a K dimenzió mentén három K-tile-t tölt be előre a shared memory-ba, átfedve a memória-hozzáférést és a számítást.

23.2.2 Tile, warp és threadblock

A CUTLASS GEMM végrehajtása a következő lépésekből áll. A grid a M és N dimenziók mentén osztja fel a kimeneti mátrixot. Minden threadblock egy (CTileM × CTileN) kimeneti régiót kap. A K dimenzió mentén a threadblock szekvenciálisan halad: minden iterációban betölt egy (CTileM × CTileK) méretű A-szeletet és egy (CTileK × CTileN) méretű B-szeletet a global memóriából a shared memory-ba. Ezt követően a warpok a shared memory-ból olvasnak, és a Tensor Core mma utasításokkal kiszámítják a részösszeget, amelyet a regiszterekben akkumulálnak. Amikor a teljes K dimenziót bejárták, az epilogue kiírja az eredményt a global memóriába.

A threadblock tile méretének megválasztása kulcsfontosságú. A nagyobb tile jobb adat-újrafelhasználást tesz lehetővé, mert a shared memory-ból többször olvassák be ugyanazt az elemet, csökkentve a global memória forgalmát. Ugyanakkor a nagyobb tile több shared memory-t fogyaszt, és kevesebb szálblokk fér el egy SM-en, ami rontja az occupancy-t. A CUTLASS a shared memory igényt a tile méretekből és a pipeline stage-ekből számítja ki. Ha a konfiguráció nem fér el az SM shared memory limitjében, a kernelindítás (futásidőben) hibát jelez; a CUTLASS dinamikus shared memóriát használ.

A warp tile határozza meg, hogy a threadblockon belül hogyan oszlanak meg a feladatok. A fenti példában a 128×128-as threadblock tile-t 2×2-es warp rácsra osztjuk, így minden warp egy 64×64-es altile-t kap. A warp az MmaTensorOp operátorral dolgozik, amely a Tensor Core mma.sync utasítást használja. Az instruction shape 16×8×16 azt jelenti, hogy egyetlen mma.sync hívás egy 16×8-as kimeneti csempét számol 16 K-mélységgel. A warp a saját altile-jét több ilyen mma utasításra bontja.

Az alábbi ábra a labor konfigurációjával mutatja a négy szintet: a threadblock tile-t a C-ben, a 2×2 warp tile-t, egy warp 32 mma.sync csempéjét és a 3 stage-es shared körpuffert.

A CUTLASS 3.x-ben a CuTe absztrakció tovább egyszerűsíti a hierarchiát. A cute::gemm ugyanazt a hardvert célozza, de magasabb szintű, funkcionálisabb felületet ad. A klasszikus CUTLASS 2.x API azonban továbbra is elérhető, és jól szemlélteti a hierarchikus tiling fogalmát. A laborban ezért a klasszikus API-t használjuk.

23.2.3 Epilogue

Az epilogue a CUTLASS azon rétege, amely a Tensor Core kimeneti fragmentjeit feldolgozza és a global memóriába írja. Az epilogue elkülönítése azért fontos, mert a GEMM magja nem változik, ha például bias-t, ReLU-t vagy skálázást akarunk hozzáadni. A CUTLASS az epilogue-ot funktorként valósítja meg, így a felhasználó saját epilogue-ot írhat anélkül, hogy a kernel többi részét módosítaná.

A leggyakoribb epilogue a cutlass::epilogue::thread::LinearCombination, amely a
C=α⋅A⋅B+β⋅C C = \alpha \cdot A \cdot B + \beta \cdot C műveletet végzi. A fenti sablonparaméterben a LinearCombination az ElementC típusú kimeneti elemeket kezeli, és az FP32 akkumulátor értékeket a kívánt kimeneti típusra konvertálja. Az epilogue elemenkénti (thread-szintű) műveleteket végez, de a threadblock-szintű epilogue shared memóriát és vektorizált tároló iterátorokat használ a kimenet kiírásához.

Elemenkénti aktivációhoz a CUTLASS kész epilogue-osztályokat ad, például a cutlass::epilogue::thread::LinearCombinationRelu osztályt (C=max⁡(0,αAB+βC)C = \max(0,\ \alpha AB + \beta C)), amelyet a LinearCombination helyére kell tenni a Gemm sablonban:

// nem fordított vázlat; a sablonparaméterek a CUTLASS verziója szerint ellenőrizendők
using EpilogueRelu = cutlass::epilogue::thread::LinearCombinationRelu<
    ElementC,                                       // kimeneti elem
    128 / cutlass::sizeof_bits<ElementC>::value,    // vektorhossz
    ElementAccumulator,                             // akkumulátor
    ElementAccumulator>;                            // skálázás típusa

Saját epilogue-funktor írásakor a CUTLASS epilogue-interfészét kell megvalósítani (Params struktúra, is_source_needed(), operator()(accumulator, source) hívás, CUTLASS_HOST_DEVICE minősítők); nincs általános cutlass::epilogue::thread::Epilogue sablon, amelybe egy tetszőleges funktor beilleszthető volna. Az interfész pontos alakját a cutlass/epilogue/thread/ fejlécek mintái (pl. linear_combination_relu.h) mutatják.

23.2.4 Stream-K

A hagyományos data-parallel GEMM a gridet az M és N dimenziók mentén osztja fel, és minden threadblock a teljes K dimenziót bejárja. Ez a megközelítés akkor optimális, ha a threadblockok száma jól illeszkedik az SM-ek számához, és a K dimenzió elegendően nagy ahhoz, hogy a pipeline feltöltődjön. Ha azonban a K dimenzió rövid, vagy a threadblockok száma nem tölti ki a GPU-t, a terhelés egyenetlen lesz, mert néhány SM hamarabb végez, mint a többi.

A stream-K a CUTLASS-ban már a 2.11-es kiadástól elérhető (GemmUniversalStreamk, Ampere-példa az examples/47_ampere_gemm_universal_streamk könyvtárban; a pontos verziótörténetet a CUTLASS release notes tartalmazza), a 3.x-ben pedig StreamKScheduler tile scheduler néven érhető el. Ahelyett, hogy minden threadblock a teljes K dimenziót dolgozná fel, a stream-K a K dimenzió mentén is partícionál: a threadblockok egyenlő mennyiségű MMA-iterációt kapnak, és a részösszegeket workspace-alapú (szemaforos) fixup-pal vonják össze; a redukció módja (determinisztikus vagy nem determinisztikus) konfigurálható.

A stream-K a hullámkvantálás problémáját kezeli: ha a kimeneti csempék száma nem osztható egyenletesen az SM-ek számával, az utolsó hullámban sok SM tétlen marad. Ezért akkor előnyös, ha a csempék száma kicsi az SM-ek számához képest, vagy nem osztható vele; nem a pipeline stage-ek és a K oszthatósága számít. A laborban a hagyományos data-parallel konfigurációt használjuk, mert az itt mutatott klasszikus device::Gemm API a hierarchia fogalmait szemlélteti jobban; a stream-K konfigurálását a CUTLASS dokumentációja és mintái mutatják.

23.2.5 Gyakori hibák és megoldások

A CUTLASS használata során a következő tipikus hibákra érdemes figyelni:

  1. A shared memory limit figyelmen kívül hagyása. A CUTLASS dinamikus shared memóriát használ, ezért a túl nagy tile vagy túl sok pipeline stage miatt a szükséges shared memory meghaladja az SM/blokk limitjét; ezt nem a fordító, hanem a futásidő jelzi (a cudaFuncSetAttribute vagy a kernelindítás hibát ad, a CUTLASS Status visszatérési értékében). A -Xptxas -v csak a statikus shared memory használatát mutatja. Megoldás: csökkentsük a tile méretet vagy a stage-ek számát, és ellenőrizzük a gemm.initialize()/gemm() státuszát.

  2. A mutatók és leading dimension-ök igazításának elhagyása. A CUTLASS vektorizált betöltést használ, amely a konfigurált igazítást feltételezi (általában 16 bájt). A nem megfelelően igazított operandust a Gemm::can_implement(args) jelzi (pl. Status::kErrorMisalignedOperand), nem lassulás vagy hibás eredmény. Megoldás: a cudaMalloc által adott igazított címeket használjuk, ügyeljünk a leading dimension osztható voltára, és mindig ellenőrizzük a can_implement státuszát.

  3. Az epilogue típusainak eltévesztése. Ha a kimeneti mátrix típusa FP16, de az epilogue FP32-re van beállítva, a LinearCombination nem konvertál megfelelően, és a numerikus tartomány túlcsordulhat. Megoldás: mindig ellenőrizzük az ElementC és az epilogue kimeneti elemtípusának (a LinearCombination első sablonparamétere) egyezését.

  4. A stream-K redukciós módja és a determinizmus. A stream-K részösszegeit a CUTLASS workspace-alapú fixup-pal vonja össze; a nem determinisztikus redukciós mód a lebegőpontos összeadás sorrendje miatt nem garantál bit-azonos eredményt. Ha determinizmus szükséges, válasszuk a determinisztikus redukciós módot, vagy használjunk hagyományos data-parallel konfigurációt, és rögzítsük a konfigurációt.

  5. A pipeline stage-ek helytelen beállítása. Túl kevés stage nem fedi át a memória-hozzáférést és a számítást, túl sok stage pedig feleslegesen foglalja a shared memory-t. A legtöbb Tensor Core konfigurációnál a 3–5 stage optimális.

23.2.6.2 CUDA C++ kód

// CUDA C++17, nvcc 12.4, CUTLASS 2.x device::Gemm API; nem fordított és nem futtatott példa
#include <algorithm>
#include <cmath>
#include <cstdlib>
#include <iostream>
#include <vector>
#include <cuda_runtime.h>
#include <cutlass/cutlass.h>
#include <cutlass/gemm/device/gemm.h>
#include <cutlass/util/host_tensor.h>
#include <cutlass/util/device_memory.h>

#define CUDA_CHECK(call)                                                      \
    do {                                                                      \
        cudaError_t err_ = (call);                                            \
        if (err_ != cudaSuccess) {                                            \
            std::cerr << "CUDA error at " << __FILE__ << ":" << __LINE__      \
                      << ": " << cudaGetErrorString(err_) << std::endl;       \
            std::exit(EXIT_FAILURE);                                          \
        }                                                                     \
    } while (0)

#define CUTLASS_CHECK(call)                                                   \
    do {                                                                      \
        cutlass::Status status_ = (call);                                     \
        if (status_ != cutlass::Status::kSuccess) {                           \
            std::cerr << "CUTLASS error at " << __FILE__ << ":" << __LINE__   \
                      << ": " << cutlass::cutlassGetStatusString(status_)     \
                      << std::endl;                                           \
            std::exit(EXIT_FAILURE);                                          \
        }                                                                     \
    } while (0)

using ElementA = cutlass::half_t;
using ElementB = cutlass::half_t;
using ElementC = float;
using ElementAccumulator = float;
using LayoutA = cutlass::layout::RowMajor;
using LayoutB = cutlass::layout::RowMajor;
using LayoutC = cutlass::layout::RowMajor;

using Gemm = cutlass::gemm::device::Gemm<
    ElementA, LayoutA,
    ElementB, LayoutB,
    ElementC, LayoutC,
    ElementAccumulator,
    cutlass::arch::OpClassTensorOp,
    cutlass::arch::Sm80,
    cutlass::gemm::GemmShape<128, 128, 32>,
    cutlass::gemm::GemmShape<64, 64, 32>,
    cutlass::gemm::GemmShape<16, 8, 16>,
    cutlass::epilogue::thread::LinearCombination<
        ElementC,
        128 / cutlass::sizeof_bits<ElementC>::value,
        ElementAccumulator,
        ElementAccumulator>,
    cutlass::gemm::threadblock::GemmIdentityThreadblockSwizzle<>,
    3
>;

int main() {
    // C: 16384^2 float = 1,07 GB; A, B: 0,54 GB-onként
    const int M = 16384, N = 16384, K = 16384;

    // Host mátrixok (a HostTensor a device-oldali másolatot is kezeli)
    cutlass::HostTensor<ElementA, LayoutA> A(cutlass::MatrixCoord(M, K));
    cutlass::HostTensor<ElementB, LayoutB> B(cutlass::MatrixCoord(K, N));
    cutlass::HostTensor<ElementC, LayoutC> C(cutlass::MatrixCoord(M, N));

    for (size_t i = 0; i < A.size(); ++i) A.host_data()[i] = ElementA(0.5f);
    for (size_t i = 0; i < B.size(); ++i) B.host_data()[i] = ElementB(0.5f);
    for (size_t i = 0; i < C.size(); ++i) C.host_data()[i] = 0.0f;

    A.sync_device();
    B.sync_device();
    C.sync_device();

    // CUTLASS argumentumok: a Gemm saját Arguments típusa, TensorRef-ekkel
    ElementAccumulator alpha = 1.0f;
    ElementAccumulator beta = 0.0f;

    typename Gemm::Arguments args({M, N, K},
                                  A.device_ref(),
                                  B.device_ref(),
                                  C.device_ref(),   // C (forrás, beta = 0)
                                  C.device_ref(),   // D (kimenet)
                                  {alpha, beta});

    Gemm gemm;
    CUTLASS_CHECK(gemm.can_implement(args));
    size_t workspace_size = Gemm::get_workspace_size(args);
    cutlass::device_memory::allocation<uint8_t> workspace(workspace_size);
    CUTLASS_CHECK(gemm.initialize(args, workspace.get()));
    // Warm-up: a könyv protokollja szerint 5 hívás
    for (int i = 0; i < 5; ++i) CUTLASS_CHECK(gemm());
    CUDA_CHECK(cudaDeviceSynchronize());

    // Mérés: 20 ismétlés, az eseménypár egyszer létrehozva
    const int num_runs = 20;
    std::vector<float> t(num_runs);
    cudaEvent_t start, stop;
    CUDA_CHECK(cudaEventCreate(&start));
    CUDA_CHECK(cudaEventCreate(&stop));
    for (int i = 0; i < num_runs; ++i) {
        CUDA_CHECK(cudaEventRecord(start));
        CUTLASS_CHECK(gemm());
        CUDA_CHECK(cudaEventRecord(stop));
        CUDA_CHECK(cudaEventSynchronize(stop));
        CUDA_CHECK(cudaEventElapsedTime(&t[i], start, stop));
    }
    CUDA_CHECK(cudaEventDestroy(start));
    CUDA_CHECK(cudaEventDestroy(stop));

    float mean_ms = 0.0f;
    for (float v : t) mean_ms += v;
    mean_ms /= num_runs;
    float ss = 0.0f;
    for (float v : t) ss += (v - mean_ms) * (v - mean_ms);
    float std_ms = std::sqrt(ss / (num_runs - 1));
    std::sort(t.begin(), t.end());
    float med_ms = 0.5f * (t[num_runs / 2 - 1] + t[num_runs / 2]);

    // Eredmény visszamásolása
    C.sync_host();

    // Ellenőrzés CPU referencia ellen
    float max_error = 0.0f;
    for (size_t i = 0; i < C.size(); ++i) {
        float expected = static_cast<float>(K) * 0.5f * 0.5f;  // 4096.0
        max_error = std::max(max_error, std::fabs(C.host_data()[i] - expected));
    }

    double flops = 2.0 * static_cast<double>(M) * static_cast<double>(N)
                   * static_cast<double>(K);
    double tflops = flops / (med_ms * 1e-3) / 1e12;

    std::cout << "Median time: " << med_ms << " ms (" << num_runs
              << " runs), stddev " << std_ms << " ms" << std::endl;
    std::cout << "Achieved TFLOPS: " << tflops << std::endl;
    std::cout << "Max abs error: " << max_error << std::endl;

    return 0;
}

23.2.6.3 Build és futtatás

A buildparancs (a CUTLASS include útvonalait a saját környezethez kell igazítani):

# nem futtatott parancs
nvcc -std=c++17 -O3 -arch=sm_80 \
     -I/path/to/cutlass/include \
     -I/path/to/cutlass/tools/util/include \
     cutlass_gemm_lab.cu -o cutlass_gemm_lab

A kernel regiszter- és shared memory használatát a következő kapcsolóval ellenőrizhetjük:

nvcc -std=c++17 -O3 -arch=sm_80 -Xptxas -v \
     -I/path/to/cutlass/include \
     -I/path/to/cutlass/tools/util/include \
     cutlass_gemm_lab.cu -o cutlass_gemm_lab

Futtatás:

./cutlass_gemm_lab

23.2.7 Önellenőrző kérdés

Mi a különbség a threadblock tile, a warp tile és az instruction shape között a CUTLASS GEMM hierarchiájában, és miért fontos az epilogue elkülönítése a GEMM kerneltől?

Válasz: A threadblock tile (itt 128×128×32) az egy szálblokk által a shared memóriába töltött és kiszámított C-régió és K-szelet; a warp tile (64×64×32) egy warp része ebből (itt 2×2 warp); az instruction shape (16×8×16) egyetlen mma.sync utasítás csempéje – egy warp tile K = 16-os lépésenként (64/16)·(64/8) = 32 ilyen utasításra bomlik. Az epilogue elkülönítése miatt a skálázás, a bias, az aktiváció és a típuskonverzió a GEMM-mag változtatása nélkül cserélhető (például LinearCombination → LinearCombinationRelu), és a kimenet egyszer, a regiszterekből íródik ki, külön kernel és extra global memóriaforgalom nélkül.
