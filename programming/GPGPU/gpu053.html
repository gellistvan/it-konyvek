14.4 Tiling és pipeline mérése

A tiling és a pipeline hatásának mérése nem egyszeri futásidő-mérésből áll. A memória-hozzáférési minták, az occupancy, a bankütközések és a latency hiding együttesen határozzák meg, hogy egy optimalizálás valóban csökkenti-e a végrehajtási időt. Ebben az alfejezetben egy olyan mérési keretet építünk fel, amely a tiling és a double buffering hatását reprodukálhatóan, számszerűen és Nsight-alapú metrikákkal vizsgálja. A példa egy mátrix transzponálás lesz; a módszertan azonban változtatás nélkül alkalmazható stencil-, konvolúció- vagy bármely memória-intenzív tiled kernelre.

14.4.1 Mérési keret és reprodukálhatóság

Mielőtt bármilyen GPU-n futó kísérletet értékelünk, rögzíteni kell a környezetet. A könyv mérési szerződése szerint minden állításhoz tartoznia kell GPU-modellnek, driververziónak, CUDA-verziónak, compute capabilitynek, operációs rendszernek, órajelnek, power limitnek, valamint annak, hogy ECC, MIG vagy virtuális GPU aktív-e. Ez nem formalitás: ugyanaz a kernel egy A100-on és egy RTX 4090-en más okból lehet gyors vagy lassú.

A mérési protokoll lépései:

  1. Warm-up. Az első kernelindítások inicializálják a modulokat, a konstans memóriát, a driver belső állapotait. Legalább 10 bemelegítő iterációt végezzünk (a 14.3 laborral egyezően), mielőtt mérni kezdünk.
  2. Többszöri ismétlés. Minden konfigurációt legalább 20-szor mérünk (a könyv mérési protokollja szerint), és a mediánt a szórással vagy IQR-rel közöljük, mert a GPU-órajel, a hőmérséklet és a háttérterhelés fluktuál.
  3. Azonos input. A tiling és pipeline összehasonlításánál ugyanazt a bemeneti mátrixot, ugyanazt a memóriafoglalást és ugyanazt a kimeneti puffert használjuk.
  4. Környezetrögzítés. A mérés előtt és után kérdezzük le a nvidia-smi-vel az órajelet, a hőmérsékletet és a power limitet. Ha a GPU throttlingol, a mérést meg kell ismételni.
  5. Hibakezelés. Fejlesztői (debug) buildben minden CUDA-hívást ellenőrizzünk (CUDA_CHECK), és minden kernelindítás után hívjunk cudaGetLastError-t. A mérési szakaszban viszont ne szinkronizáljunk hívásonként, mert az torzítja az időt: az időmérést CUDA-eseményekkel fogjuk körbe, és a mérési ciklus végén egyszer ellenőrizzünk (cudaGetLastError, cudaDeviceSynchronize).

A mérési célok három kernelvariánsra:

  • Baseline: naiv globális memóriás transzponálás.
  • Tiled: shared memory csempézés, bankütközés elkerülése paddinggel.
  • Pipelined: shared memory csempézés és aszinkron másolás (cp.async) double bufferinggel.

A várt hatás iránya ismert: a tiling csökkenti a globális memória tranzakciók számát, a pipeline pedig elrejti a globális memória késleltetését. A mérés feladata ennek számszerűsítése, nem pedig a „gyorsabb” kijelentés bizonyítása.

14.4.2 A példa: FP32 mátrix transzponálás

A transzponálás azért alkalmas kísérleti terep, mert memória-intenzív, és a naiv változat egyik memória-hozzáférése szükségképpen nem koaleszkált. A tiled változat mindkét irányban koaleszkált olvasást és írást valósít meg; a pipelined változat ezen felül a globális betöltést a számítás alá csúsztatja.

Input: A mátrix M sorral és N oszloppal, FP32 elemekkel. Output: B mátrix N sorral és M oszloppal, B[n, m] = A[m, n]. A teljes adatforgalom pontosan 2 * M * N * sizeof(float) byte, mert minden elemet egyszer olvasunk és egyszer írunk.

A kernelváltozatok vázlata CUDA C++-ban (C++17, nvcc):

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

#define CUDA_CHECK(call)                                                       \
  do {                                                                         \
    cudaError_t err = (call);                                                  \
    if (err != cudaSuccess) {                                                  \
      std::fprintf(stderr, "CUDA error at %s:%d: %s\n", __FILE__, __LINE__,    \
                   cudaGetErrorString(err));                                   \
      std::exit(EXIT_FAILURE);                                                 \
    }                                                                          \
  } while (0)

constexpr int TILE_DIM = 32;

// 1. Naive: global memory only
__global__ void transpose_naive(const float* A, float* B, int M, int N) {
    int x = blockIdx.x * blockDim.x + threadIdx.x;
    int y = blockIdx.y * blockDim.y + threadIdx.y;
    if (x < N && y < M) {
        B[x * M + y] = A[y * N + x]; // one side is uncoalesced
    }
}

// 2. Tiled: shared memory with padding
__global__ void transpose_tiled(const float* A, float* B, int M, int N) {
    __shared__ float tile[TILE_DIM][TILE_DIM + 1]; // padding avoids bank conflicts

    int x = blockIdx.x * TILE_DIM + threadIdx.x;
    int y = blockIdx.y * TILE_DIM + threadIdx.y;

    if (y < M && x < N) {
        tile[threadIdx.y][threadIdx.x] = A[y * N + x];
    }
    __syncthreads();

    x = blockIdx.y * TILE_DIM + threadIdx.x;
    y = blockIdx.x * TILE_DIM + threadIdx.y;

    if (y < N && x < M) {
        B[y * M + x] = tile[threadIdx.x][threadIdx.y]; // shared load, transposed
    }
}

A harmadik változat az aszinkron másolás (cp.async) primitívjeit használja a <cuda_pipeline.h> fejlécből (__pipeline_memcpy_async, __pipeline_commit, __pipeline_wait_prior; CUDA 11.0+, compute capability 8.0+). Ahhoz, hogy a double buffering egyáltalán értelmezhető legyen, a blokknak több csempét kell feldolgoznia: ezért a kernel persistent/grid-stride jellegű, a blokk a t, t + gridDim.x, … sorszámú csempéket dolgozza fel, és amíg az aktuális csempét transzponálja, a következő már töltődik. Egy blokk egyetlen csempét kezelő változatában nincs „következő csempe”, így ott a pipeline semmit sem rejthetne el. Az alábbi kód teljes (CUDA 12.x, sm_80; csak statikusan átnézett, nem futtatott vázlat), de leegyszerűsítve feltételezi, hogy M és N a TILE_DIM többszöröse, a blokk pedig dim3(TILE_DIM, TILE_DIM):

// Fordítás: nvcc -O3 -std=c++17 -arch=sm_80 (CUDA 12.x); M, N a TILE_DIM többszöröse
#include <cuda_pipeline.h>

// Egy TILE_DIM x TILE_DIM csempe aszinkron másolása szálanként 4 bájtonként
__device__ void load_tile(const float* A, float* dst, int tile, int tilesX, int N) {
    int ty = tile / tilesX, tx = tile % tilesX;
    const float* src = A + (size_t)(ty * TILE_DIM + threadIdx.y) * N
                         + tx * TILE_DIM + threadIdx.x;
    __pipeline_memcpy_async(dst + threadIdx.y * (TILE_DIM + 1) + threadIdx.x,
                            src, sizeof(float));
}

// Dinamikus shared memória: 2 * TILE_DIM * (TILE_DIM + 1) * sizeof(float)
__global__ void transpose_pipelined(const float* A, float* B, int M, int N) {
    extern __shared__ float smem[];
    float* buf[2] = { smem, smem + TILE_DIM * (TILE_DIM + 1) };

    const int tilesX   = N / TILE_DIM;
    const int numTiles = tilesX * (M / TILE_DIM);
    int cur = 0;
    int t   = blockIdx.x;

    if (t < numTiles) load_tile(A, buf[0], t, tilesX, N);
    __pipeline_commit();                       // 0. köteg: az első csempe

    for (; t < numTiles; t += gridDim.x) {
        int next = t + gridDim.x;
        if (next < numTiles) load_tile(A, buf[cur ^ 1], next, tilesX, N);
        __pipeline_commit();                   // a következő csempe (vagy üres köteg)
        __pipeline_wait_prior(1);              // az aktuális csempe megérkezett
        __syncthreads();                       // más szálak másolatai is láthatók

        int ty = t / tilesX, tx = t % tilesX;
        B[(size_t)(tx * TILE_DIM + threadIdx.y) * M + ty * TILE_DIM + threadIdx.x]
            = buf[cur][threadIdx.x * (TILE_DIM + 1) + threadIdx.y];
        __syncthreads();                       // mielőtt a puffert újra írjuk
        cur ^= 1;
    }
}

A host oldali indításnál a grid egydimenziós, például min(numTiles, 4 * smCount) blokk, a block dim3(TILE_DIM, TILE_DIM), a dinamikus shared memória pedig 2 * TILE_DIM * (TILE_DIM + 1) * sizeof(float) = 8448 byte (ez 48 KiB alatt van, így cudaFuncSetAttribute nem szükséges).

Itt a lényeg, hogy a __pipeline_memcpy_async a globális memóriából a shared memóriába másolást a memória-utasítás szintjén aszinkron módon hajtja végre (a szál nem várja meg az adatot), a __pipeline_commit lezárja a köteget, a __pipeline_wait_prior(N) pedig megvárja, hogy legfeljebb N kötegnél több ne legyen folyamatban. A cp.async használatához compute capability 8.0 vagy újabb szükséges; ezt a cudaDeviceProp::major >= 8 feltétellel (vagy a cudaDevAttrComputeCapabilityMajor attribútummal) kell ellenőrizni. Az asyncEngineCount nem alkalmas erre: az a másolómotorok (copy engine) számát adja, amely a cudaMemcpyAsync/kernel átfedésre vonatkozik, nem a cp.async támogatására.

A launch konfiguráció mindhárom kernelnél:

  • Naiv: dim3 block(32, 32, 1), grid: ((N + 31)/32, (M + 31)/32, 1).
  • Tiled: ugyanaz, de a tile méret TILE_DIM; a block dimenzió TILE_DIM x TILE_DIM (a TILE_DIM = 32 mellett 1024 szál; nagyobb csempe csak a lentebb bemutatott, szálanként több elemet másoló változattal valósítható meg).
  • Pipelined: egydimenziós grid (blokkonként több csempe), block TILE_DIM x TILE_DIM, a dinamikus shared memória mérete 2 * TILE_DIM * (TILE_DIM + 1) * sizeof(float) byte.

A grid- és blockdimenziót minden mérési jegyzőkönyvben rögzíteni kell.

  • Driver: 535.xx (helyőrző)

Ez a konfiguráció illusztratív, és eltér a 14.3 labor környezetétől (más GPU és CUDA-verzió); a mérés mindig a saját hardveren készül, és a tényleges környezetet kell a naplóba írni.

A kód build parancsa:

nvcc -O3 -std=c++17 -arch=sm_80 -o transpose_lab transpose_lab.cu

A futtatás előtt ellenőrizzük a hibákat, majd a mérési kernelt hívjuk:

./transpose_lab --m 8192 --n 8192 --repeat 20

ncu --set full --launch-count 1 --kernel-name transpose_tiled ./transpose_lab --m 8192 --n 8192

Célzott metrikák lekérdezése:

ncu --metrics \
  l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum,\

A mérési naplóban külön oszlopban szerepeljen a várt (elméleti) érték és a mért érték. Az ncu metrikanevei verziófüggők, ezért a telepített változatban ellenőrizzük őket (ncu --query-metrics). A várt értékeket a memóriamodellből, a szektorszámításból és az occupancy-előrejelzésből becsüljük, a mért értékeket pedig a Nsight-riportból vagy a saját timerből nyerjük.

Példa várt értékek:

  • Naiv globális szektorok: A transzponálásnál az egyik oldal nem koaleszkált. A minimális szektorszám M*N/8 irányonként (32 byte = 8 float). A naiv kernel nem koaleszkált oldalán egy warp 32 külön szektort érint a minimális 4 helyett, így ezen az oldalon nagyjából 8-szoros szektorszám várható. A pontos érték a hozzáférési mintától és a cache-viselkedéstől függ, de a tiled kernelhez képest többszörös szektorszám várható.
  • Tiled globális szektorok: Koaleszkált hozzáféréssel minden 32 byte-os szektor pontosan egyszer érintett: a load szektorszáma (l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum) ≈ M*N/8, a store szektorszáma (..._op_st.sum) ≈ N*M/8. (A régi nvprof-os gld_transactions/gst_transactions metrikák Nsight Compute-ban nem léteznek.)
  • Bankütközések: A TILE_DIM+1 padding miatt a shared memória olvasásnál a bankütközések száma közel nulla. Padding nélkül 32x32-es csempénél a transzponált olvasás 32-way bank conflictot okozna.
  • DRAM forgalom: Mindhárom kernelnél várhatóan közel 2 * M * N * 4 byte, mert az alkalmazás minden elemet egyszer mozgat; a naiv kernel részleges szektoros írásai az L2-ben jellemzően összefésülődnek, de kis L2 vagy kedvezőtlen minta esetén többlet-olvasás és read-modify-write jelentkezhet, ezért az eltérés mérendő jelenség, nem hiba. A tiling nem csökkenti a teljes DRAM forgalmat, csak a szektorok számát és a késleltetést.
  • Sávszélesség: sávszélesség = 2 * M * N * 4 / (futásidő * 1e9) GB/s. A viszonyítási alap az ugyanazon a GPU-n mért cudaMemcpyDtoD sávszélesség (nem a névleges csúcs); a tiled kernel ennek nagy hányadát (kitöltendő, mért) várhatóan eléri.

14.4.4 Eredmények értelmezése: Nsight-metrikák és a hatásmechanizmus

A nyers futásidő önmagában keveset mond. A Nsight Compute metrikái megmutatják, miért változott a teljesítmény.

14.4.4.1 Globális memória tranzakciók

Az l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum és ..._op_st.sum metrikák a globális load/store által érintett 32 byte-os szektorok számát adják (a szektor/kérés arány a ..._per_request típusú hányadosokból olvasható le). A naiv transzponálásnál az egyik oldal nem koaleszkált, ezért egy warp 32 elemhez a minimális 4 helyett 32 külön szektort érint. A tiled kernelben a shared memórián keresztül mindkét oldal koaleszkált: a betöltés soronként folyamatos, a kiírás is soronként folyamatos. A várt hatás a tranzakciószám drasztikus csökkenése.

A mérés során a load és store szektorszámot összehasonlítva a tiled kernelnek közel a minimális M*N/8 értéket kell mutatnia. Ha a mért érték magasabb, akkor a hozzáférési minta nem optimális, vagy a grid méretezése miatt határfeltételek rontják a koaleszkálást.

14.4.4.2 Shared memory bankütközések

A tiled kernelnél a __shared__ float tile[TILE_DIM][TILE_DIM + 1] deklaráció a padding miatt elkerüli a bankütközést. A Nsight-ban a l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum metrika mutatja a shared memória olvasási bankütközéseit. Padding nélkül 32x32-es csempénél a transzponált olvasás során a warp mind a 32 szála ugyanabba a bankcsoportba ütközne, ami 32-szeres konfliktust jelent. A +1 oszlop eltolja a sorokat, így a konfliktus megszűnik.

A várt érték: paddinggel a bankütközések száma nulla vagy elhanyagolható. Ha a mért érték magas, akkor a paddinget elfelejtettük, vagy a tile méret és a bankek száma nem illeszkedik.

14.4.4.3 Occupancy és erőforrás-korlátok

Az sm__warps_active.avg.pct_of_peak_sustained_active metrika az aktív warpek arányát mutatja. A tiled kernel shared memóriát foglal: TILE_DIM * (TILE_DIM + 1) * 4 byte. 32x32-es tile esetén ez 32334 = 4224 byte blokkonként. A pipelined változat két puffert használ, így 8448 byte-ot. Egy A100 SM-en 164 KB shared memória áll rendelkezésre, ezért a shared memória nem korlátozza erősen az occupancyt. A regiszterhasználat azonban igen: ha a compiler túl sok regisztert rendel, az aktív warpek száma csökken.

A várt hatás: a tiled kernel occupancyje hasonló vagy kissé alacsonyabb a naiv kernelhez képest, de a csökkent memória-tranzakciók miatt a tényleges teljesítmény nő. A pipelined kernelben a double buffering miatt több shared memória kell, de a latency hiding javulhat, így a foglaltság csökkenése ellenére is gyorsabb lehet (nem garantált, mérendő).

A mérésnél rögzíteni kell a regiszterhasználatot (launch__registers_per_thread) és a shared memória foglalást is, mert ezek magyarázzák az occupancyt.

14.4.4.4 DRAM forgalom és sávszélesség

A dram__bytes.sum metrika a tényleges DRAM-forgalmat mutatja. A várt érték mindhárom kernelnél közel azonos: 2 * M * N * 4 byte. Ha a mért érték ettől eltér, akkor a cache vagy a memória-hozzáférési minta extra forgalmat generál (például a határfeltételek miatt, vagy a naiv kernel részleges szektoros írásai miatt, ha azok az L2-ben nem fésülődnek össze); az eltérés éppen a mérés tárgya. A tiling és pipeline nem csökkenti a teljes forgalmat, csak a tranzakciók számát és a késleltetést.

A sávszélesség számítása a fenti képlettel történik. A naiv kernel sávszélessége várhatóan alacsonyabb, mert a nem koaleszkált hozzáférések sok részleges szektort és többletforgalmat okoznak az L2/DRAM oldalon. A tiled kernel sávszélessége várhatóan megközelíti a mért memcpy-sávszélességet. A pipelined kernel javíthat a sávszélességen, ha a tiled kernel késleltetése nincs elrejtve; ez nem garantált, és mérendő.

14.4.4.5 A pipeline hatása: latency hiding

A cp.async pipeline lényege, hogy a globális memória kéréseket a számítással párhuzamosítja. A Nsight Compute-ben a smsp__average_warp_latency_per_inst_issued vagy a smsp__warp_issue_stalled_long_scoreboard_per_warp_active.pct metrika mutatja, mennyi időt töltenek a warpek memória-várakozással. A pipelined kernelben ennek az értéknek csökkennie kell a tiled kernelhez képest, mert a consumer nem közvetlenül a globális load után vár, hanem a már megérkezett shared pufferen dolgozik.

Várt eredmény (nem garantált): a transzponálásban nincs számítási fázis, ezért a pipeline csak akkor gyorsíthat, ha a tiled kernel occupancyja alacsony (kevés rezidens warp rejti el a késleltetést). Ha a pipelined kernel nem gyorsabb vagy lassabb, az nem a szinkronizáció hibájára utal: a többletbarrierek, a 4 B-os cp.async és a kisebb rács költsége meghaladhatja a nyereséget. Helyességét a validáció és a compute-sanitizer --tool racecheck igazolja, nem a futásidő.

14.4.5 Tileméret-hangolás

A tile méretének megválasztása közvetlenül befolyásolja a shared memória foglalást, a bankütközéseket, az occupancyt és a határfeltételek kezelését. A hangolást méréssorozattal végezzük, ahol a tile méretet változtatjuk, és minden konfigurációra rögzítjük a fenti metrikákat.

Gyakori tile méretek FP32 transzponálásnál:

  • 8x8: kis shared memória, sok kis blokk; a szektorszám minimális marad (8 float = 1 szektor), de a blokkonkénti overhead és a rövid sorok a kéréshatékonyságot ronthatják.
  • 16x16: 16174 = 1088 byte shared memória blokkonként. Jó egyensúly, de a bankütközések elkerülhetők paddinggel.
  • 32x32: 32334 = 4224 byte. A legtöbb GPU-n ez a standard választás, mert a warp méret (32) illeszkedik a sorhosszhoz, és a koaleszkálás optimális.
  • 64x64: 64654 = 16640 byte. Magas shared memória igény, alacsonyabb occupancy, de kevesebb blokk és határfeltétel. Nagy mátrixoknál előnyös lehet, de a latency hiding romolhat.

A blokk legfeljebb 1024 szálas lehet, ezért a fenti TILE_DIM x TILE_DIM blokkal 64x64-es csempe nem indítható (4096 szál: érvénytelen launch). Ehhez, és a futásidőben választható csempemérethez sablonparaméteres kernel kell, ahol egy szál TILE / ROWS elemet másol (ROWS osztja TILE-t, TILE * ROWS <= 1024):

// block = dim3(TILE, ROWS); pl. <8,8>, <16,16>, <32,8>, <64,16> (utóbbi 1024 szál)
template <int TILE, int ROWS>
__global__ void transpose_tiled_t(const float* A, float* B, int M, int N) {
    __shared__ float tile[TILE][TILE + 1];
    int x = blockIdx.x * TILE + threadIdx.x;
    int y = blockIdx.y * TILE + threadIdx.y;
    for (int j = 0; j < TILE; j += ROWS)
        if (x < N && y + j < M)
            tile[threadIdx.y + j][threadIdx.x] = A[(size_t)(y + j) * N + x];
    __syncthreads();
    x = blockIdx.y * TILE + threadIdx.x;
    y = blockIdx.x * TILE + threadIdx.y;
    for (int j = 0; j < TILE; j += ROWS)
        if (x < M && y + j < N)
            B[(size_t)(y + j) * M + x] = tile[threadIdx.x][threadIdx.y + j];
}

A --tile kapcsoló a hoston egy switch, amely a megfelelő sablonpéldányt indítja. A mérési sorozat:

for tile in 8 16 32 64; do
    ./transpose_lab --m 8192 --n 8192 --tile $tile --repeat 20
done

A kapott futásidőket, sávszélességeket és occupancyket táblázatba foglaljuk. A várt trend: a különbségek GPU-függők és jellemzően kicsik; a mérés dönti el, melyik a legjobb. A 64x64 csempét <64,16> (1024 szálas) blokkal indítjuk, ennek occupancyját a blokk szálszáma korlátozza (cudaOccupancyMaxActiveBlocksPerMultiprocessor).

A pipelined kernelnél a tile méret mellett a shared memória pufferek száma is hangolható. A double bufferinghez két puffer kell; ha a tile túl nagy, a pufferek kiszoríthatják a blokkokat az SM-ből, így az occupancy drasztikusan csökken. A statikusan foglalt shared memória 48 KiB-nál nem lehet több; ennél nagyobb dinamikus pufferhez a cudaFuncSetAttribute(..., cudaFuncAttributeMaxDynamicSharedMemorySize, bytes) hívás kell, de figyelni kell a maximális kapacitásra.

A hangolás eredményét a következő táblázatban rögzítjük (várt és mért külön):

Tile Block Shared memória/block (byte) Regiszter/thread Occupancy (várt: kalkulátorból) Sávszélesség (mért)
8x8 8x8 894=288 mérendő kalkulátorból mérendő
16x16 16x16 16174=1088 mérendő kalkulátorból mérendő
32x32 32x8 32334=4224 mérendő kalkulátorból mérendő
64x64 64x16 64654=16640 mérendő kalkulátorból mérendő

A mért értékeket a Nsight és a saját timer alapján kell kitölteni. A várt occupancyt a cudaOccupancyMaxActiveBlocksPerMultiprocessor API-val előre lehet becsülni; a laborban ezt is érdemes lefuttatni.

14.4.6 Tipikus hibák és elhárításuk

14.4.6.1 Nem ellenőrzött környezet

Hiba: a mérés közben a GPU órajele változik, thermal throttling lép fel, vagy más folyamat terheli a GPU-t. A kapott eredmény nem reprodukálható.

Megoldás: mérés előtt és után nvidia-smi --query-gpu=clocks.sm,clocks.mem,power.draw,temperature.gpu --format=csv rögzítése. Ha throttlingot látunk, csökkentsük a mérés időtartamát, vagy alkalmazzunk hűtési szünetet. Többfelhasználós környezetben használjunk MIG-et vagy kérjünk dedikált GPU-időt.

14.4.6.2 Túl kicsi input

Hiba: a mátrix mérete kicsi, a kernelindítási overhead dominál, a tiling hatása nem mérhető.

Megoldás: a bemenet és a kimenet együtt legyen legalább a GPU L2-méretének 4–8-szorosa (cudaDevAttrL2CacheSize); a 8192x8192 FP32 mátrix 256 MiB, ez a mai GPU-kon elegendő. Kisebb méretnél az eredmény L2-sávszélesség, és a naplóban így kell jelölni.

14.4.6.3 Csak egy mérés

Hiba: egyetlen futásidőt rögzítünk, a zajt nem szűrjük.

Megoldás: warm-up után legalább 20 ismétlés, medián és szórás (vagy IQR) közlése. A szórás nagy értéke (pl. >5%) környezeti problémára utal.

14.4.6.4 Bankütközés figyelmen kívül hagyása

Hiba: a tiled kernelben __shared__ float tile[TILE_DIM][TILE_DIM] deklarációt használunk padding nélkül. A 32x32-es transzponált olvasás 32-way bank conflictot okoz, és a tiling előnye elvész.

Megoldás: mindig TILE_DIM + 1 oszlopot használjunk, vagy használjunk XOR-swizzle-t a shared memória indexelésében (a cudaFuncSetAttribute csak a méretkorlátot állítja, a bankleképezést nem befolyásolja). A Nsight bankütközés-metrikájával ellenőrizzük.

14.4.6.5 A cp.async pipeline helytelen szinkronizációja

Hiba: a cuda::pipeline producer és consumer fázisainak sorrendje hibás, például a consumer_wait előtt a shared puffert olvassuk, vagy a puffert felülírjuk, mielőtt a consumer végzett volna. Ez versenyhelyzetet okoz.

Megoldás: kövessük a pipeline-primitívek szabályait. A producer oldal a __pipeline_memcpy_async hívások után __pipeline_commit-ot hajt végre; a consumer oldal __pipeline_wait_prior(N)-nel vár a megfelelő köteg befejezésére, majd __syncthreads()-szel gondoskodik arról, hogy a többi szál másolata is látható legyen. A puffert csak akkor írjuk újra, ha minden szál végzett az olvasásával (újabb __syncthreads). A teljes, működő minta a 2. szakasz transpose_pipelined kernelje; itt a hibás minta:

// HIBÁS: nincs commit/wait, a kernel azonnal olvas
__pipeline_memcpy_async(&buffer[threadIdx.x], &source[threadIdx.x], sizeof(float));
__syncthreads();
use(buffer); // lehet, hogy a másolás még nem fejeződött be

A helyes minta:

__pipeline_memcpy_async(&buffer[threadIdx.x], &source[threadIdx.x], sizeof(float));
__pipeline_commit();
__pipeline_wait_prior(0);
__syncthreads();
use(buffer);
__syncthreads(); // mielőtt a puffert újra írjuk

14.4.6.6 Túl nagy tile, alacsony occupancy

Hiba: a 64x64-es tile csökkenti az aktív blokkok számát, a latency hiding romlik, és a kernel lassabb lesz.

Megoldás: mérjük az occupancyt, és a regiszterhasználatot (--maxrregcount vagy launch bounds) hangoljuk. Ha a shared memória a korlát, csökkentsük a tile méretet, vagy használjunk kisebb puffert a pipeline-ban. A cél az, hogy legalább 2–4 blokk aktív legyen SM-enként, hogy a warpütemező elrejthesse a memória-késleltetést.

14.4.7 Labor: Nsight-alapú elemzés

A labor célja, hogy a fenti három kernelváltozatot saját környezetben lefuttassa, és a mérési naplót Nsight-metrikákkal töltse ki. A transpose_lab.cu programot a hallgató állítja össze a fenti kernelvázlatokból (a fejezet nem tartalmazza a teljes forrást); a --m, --n, --repeat, --tile parancssori kapcsolók feldolgozását is neki kell megírnia. A fordítás és futtatás parancsai:

nvcc -O3 -std=c++17 -arch=sm_80 -o transpose_lab transpose_lab.cu
./transpose_lab --m 8192 --n 8192 --repeat 20

A Nsight Compute futtatás:

ncu --set full --launch-count 1 --kernel-name transpose_naive ./transpose_lab --m 8192 --n 8192
ncu --set full --launch-count 1 --kernel-name transpose_tiled ./transpose_lab --m 8192 --n 8192
ncu --set full --launch-count 1 --kernel-name transpose_pipelined \
  ./transpose_lab --m 8192 --n 8192

A mérési naplóban rögzíteni kell:

  • GPU-modell, driver, CUDA-verzió, compute capability, operációs rendszer, power limit, ECC/MIG állapot.
  • A három kernel futásideje, szórása, sávszélessége.
  • A Nsight-ből: l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum, ..._op_st.sum, dram__bytes.sum, l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum, sm__warps_active.avg.pct_of_peak_sustained_active, regiszter/thread, shared memória/block.
  • A várt értékeket a fenti becslésekkel, a mért értékeket a kísérletből.

A labor átadandó dokumentuma egy rövid jelentés, amelyben a mért és várt értékeket táblázatban összeveti, és legalább egy Nsight-képernyőképet vagy riportrészletet mellékel. A jelentésben válaszolni kell a kérdésre: Miért nő a sávszélesség a tiled kernelnél, ha a DRAM-forgalom (közel) azonos? A válasz: a koaleszkált hozzáférések miatt a warpok szektorszáma (az LSU/L1 oldali kérések) a töredékére csökken, az L2 és a DRAM pedig teljes szektorokat és hosszabb, sorban elhelyezkedő hozzáféréseket kap (kevesebb részleges írás, kevesebb sor-újraaktiválás); ezek együtt teszik lehetővé, hogy ugyanannyi byte mozgatása kevesebb időt vegyen igénybe. A pipelined kernel pedig a globális memória késleltetését rejti el, így a memória-vezérlő folyamatosan telített.

Megjegyzés: A fenti parancsok és a kódvázlat szemléltető jellegű; a laborban a tényleges GPU-paramétereket és a mérési naplót a hallgatónak kell rögzítenie. A cp.async pipeline használatához compute capability 8.0+ szükséges; ha a labor GPU-ja régebbi, a pipeline részt ki kell hagyni, és a mérési jegyzőkönyvben ezt jelezni kell.

14.4.8 Összefoglalás és önellenőrző kérdés

A tiling és a pipeline hatásának mérése akkor értékes, ha a futásidő mellett a memória-tranzakciókat, a bankütközéseket, az occupancyt és a sávszélességet is vizsgáljuk. A mátrix transzponálás példáján a naiv, tiled és pipelined változat összehasonlítása megmutatja: a tiling a tranzakciók számát csökkenti, a pipeline a késleltetést rejti el, a tileméret pedig az erőforrás-korlátokon keresztül hangolja az optimális pontot.

Önellenőrző kérdés: Miért csökken a globális memória tranzakciók száma a tiled transzponálásnál, és miért nem csökken a DRAM-forgalom? Válaszát a Nsight-metrikák alapján indokolja.

A következő alfejezet (15.1) a cache-ekre, az L2 persistence-re és a memóriamodellekre épít; az itt megismert mérési protokoll és a Nsight-metrikák ott is alapvető eszköztárként szolgálnak.
