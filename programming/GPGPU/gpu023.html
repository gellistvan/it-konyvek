7.2 Shared memory és élettartam

A shared memory a CUDA memóriahierarchia egyik legnagyobb teljesítményt befolyásoló eleme. Míg a global memória a grid összes threadje számára elérhető, de nagy késleltetésű, a shared memory egyetlen blokk threadjei között osztozik, és a global memóriánál nagyságrendekkel kisebb késleltetésű hozzáférést biztosít (tipikusan ≈ 20–30 órajelciklus, architektúrafüggő; a regiszternél lassabb). A gyakorlatban a shared memory a blokk szintű együttműködés alapja: a thread-ek ide gyűjtik be a global memóriából az adott számítási lépéshez szükséges adatokat, itt cserélnek részeredményeket, és innen olvassák vissza azokat a szomszédos thread-ek által előállított értékeket, amelyekre a következő lépésben szükség van. Ebben az alfejezetben a __shared__ deklaráció formáit, a dinamikus allokációt, a szinkronizáció szerepét és a shared memory bankokból fakadó bank conflict jelenséget tárgyaljuk, majd egy mátrixszorzó tiling kernelen keresztül mutatjuk be a gyakorlati használatot.

7.2.1 __shared__ és a shared memory élettartama

A shared memory-t a kernelben a __shared__ kulcsszóval deklaráljuk. A legegyszerűbb forma a statikus méretű tömb:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
__shared__ float tile[32][32];

Ez a deklaráció minden blokk számára létrehoz egy 32×32 elemű lebegőpontos tömböt. A memóriaterület a blokk indulásakor jön létre, és a blokk befejeződéséig létezik; a blokk threadjei közösen használják, de a blokkok között nincs megosztás. A shared memory fizikailag az SM-en belüli gyors memória; a mérete a GPU generációjától és a konfigurációtól függ: SM-enként a konfigurálható shared memória CC 7.5-ön 64 KiB, CC 8.0-n 164 KiB, CC 8.6/8.9-en 100 KiB, CC 9.0-n 228 KiB (az L1-gyel közös tárból; a CUDA Programming Guide értékei alapján, emlékezetből, ellenőrzendő); blokkonként alapesetben 48 KiB, opt-innel ennél több (lásd 6.4); például A100 esetén SM-enként 164 KiB, blokkonként opt-in módon legfeljebb 163 KiB. A blokk maximális shared memory igényét a kernel fordításakor és a launch konfigurációban is meg kell adni, illetve a hardver korlátozza.

A statikus deklaráció mellett létezik dinamikus shared memory is. Ezt a kernelben extern __shared__ előtaggal jelezzük, a tényleges méretet pedig a kernel indításakor a launch konfiguráció harmadik paraméterében adjuk meg bájtokban:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
extern __shared__ float s[]; // méretét a launch adja meg

__global__ void kernelDinamikus(float* out, int n) {
    int tid = threadIdx.x;
    if (tid < n) {
        s[tid] = tid * 0.5f;
    }
    __syncthreads();            // feltétel nélkül: minden szál eléri
    if (tid < n) {
        out[tid] = s[tid] * 2.0f;
    }
}

A kernel indítása:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
// n <= 256; a blokk 256 szálas, ezért n < 256 esetén a feltételes
// ágon kívüli __syncthreads() elengedhetetlen
dim3 grid(1), block(256);
size_t sharedBytes = n * sizeof(float);
kernelDinamikus<<<grid, block, sharedBytes, 0>>>(d_out, n);

Itt a sharedBytes értékét a n elemű float tömbhöz igazítjuk. Ha több dinamikus shared tömböt szeretnénk, akkor egyetlen extern __shared__ tömböt kell deklarálni, és azon belül kell pointer-aritmetikával elhelyezni a résztömböket; eltérő típusoknál a nagyobb igazítást igénylő típust kell előre venni (az igazítást a hívó felelőssége tartani). Például:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
extern __shared__ float s[];
float* a = s;                 // első rész
float* b = &s[n];             // második rész

A dinamikus allokáció előnye, hogy a kernel fordításakor nem kell ismerni a pontos méretet, így ugyanaz a bináris többféle blokkmérettel is futtatható, feltéve, hogy a shared memória igénye a hardveres korláton belül marad. A dinamikus shared memória tényleges méretét mindig a launch harmadik paramétere adja. A cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, bájt) hívás csak a megengedett maximumot emeli meg; a 48 KiB feletti dinamikus shared memóriához ez az opt-in kötelező.

A shared memory láthatósága kizárólag a blokk threadjeire terjed ki. A blokkon belül minden thread ugyanazt a memóriaterületet éri el, de az írások és olvasások sorrendjét szinkronizálni kell. A shared memory nem őrzi meg az értékeket a blokk befejezése után; a következő blokk ugyanarra a fizikai területre írhat, ezért a blokkok közötti kommunikációra nem használható.

7.2.2 Szinkronizáció: __syncthreads() és a veszélyes feltételes használat

A shared memory akkor hasznos, ha a thread-ek adatot cserélnek: az egyik thread ír, egy másik olvas. Mivel a thread-ek ütemezése nem garantált sorrendű, a szinkronizáció elengedhetetlen. A __syncthreads() barriere a blokk összes threadjét bevárja: minden thread csak akkor lép tovább, ha minden thread elérte ugyanezt a hívást. Ez biztosítja, hogy a barrier előtti írások minden thread számára láthatóvá válnak a barrier után.

A tiling kernel tipikus sémája:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
__shared__ float As[TILE][TILE];
__shared__ float Bs[TILE][TILE];

int tx = threadIdx.x, ty = threadIdx.y;
// global indexek
int row = blockIdx.y * TILE + ty;
int col = blockIdx.x * TILE + tx;

float sum = 0.0f;

for (int t = 0; t < (N + TILE - 1) / TILE; ++t) {
    // betöltés a global memóriából a shared tömbökbe
    As[ty][tx] = (row < N && t * TILE + tx < N) ? A[row * N + t * TILE + tx] : 0.0f;
    Bs[ty][tx] = (t * TILE + ty < N && col < N) ? B[(t * TILE + ty) * N + col] : 0.0f;

    __syncthreads(); // minden thread befejezte a betöltést

    // számítás a shared memóriából
    for (int k = 0; k < TILE; ++k) {
        sum += As[ty][k] * Bs[k][tx];
    }

    __syncthreads(); // a következő csempe betöltése előtt mindenki befejezte az olvasást
}

if (row < N && col < N) {
    C[row * N + col] = sum;
}

A két __syncthreads() nélkülözhetetlen. Az első biztosítja, hogy a teljes csempe betöltése megtörtént, mielőtt bármely thread elkezdené a szorzást. A második megakadályozza, hogy egy gyors thread a következő iterációban felülírja a shared memóriát, mielőtt a lassabb thread-ek befejezték volna az aktuális csempe olvasását. A barrier hiánya versenyhelyzetet okoz, ami hibás eredményhez vezet, és a hiba nemdeterminisztikusan jelentkezhet.

Gyakori hiba a __syncthreads() feltételes ágon belüli elhelyezése. A következő kód hibás:

// HIBÁS: a __syncthreads() csak egyes thread-ekre fut le
if (tx < 16) {
    // valamilyen részleges munka
    __syncthreads();
}

Mivel a barriernek a blokk összes threadjére ki kell terjednie, a feltételes hívás nem definiált viselkedés: régebbi architektúrákon jellemzően holtpontot okoz, Volta óta gyakran lefut, de ilyenkor a barrier nem garantálja a szinkronizációt, és az eredmény csendben hibás lehet. Az, hogy a kernel egy próbafuttatáson nem akad meg, tehát nem bizonyítja a helyességet; a hibát a compute-sanitizer --tool synccheck mutatja ki. A helyes minta az, hogy a __syncthreads() hívás a feltételen kívül, a vezérlési folyamattól függetlenül szerepeljen. Ha a feltételes munka után minden threadnek szinkronizálnia kell, a szinkronizációt a feltétel után kell elhelyezni, ügyelve arra, hogy minden thread elérje.

7.2.3 Bankok és bank conflict

A shared memory hardveres szervezése 32 bankra oszlik (a warp méretének megfelelően). Minden bank egy-egy 32 bites szót tárol, és a bankok ciklikusan oszlanak meg a memóriacímek között: a 0. cím a 0. bankba, az 1. cím az 1. bankba, …, a 31. cím a 31. bankba, a 32. cím újra a 0. bankba tartozik, és így tovább. Ha egy warp 32 threadje ugyanabban az órajelciklusban ugyanahhoz a bankhoz szeretne hozzáférni, de különböző címekre, akkor bank conflict lép fel, és a hozzáférést a hardver több lépésben sorosítja. Ez csökkenti a tényleges sávszélességet.

A legegyszerűbb esetben, ha a warp threadjei egyenletesen, stride = 1 módon érik el a memóriát (például s[threadIdx.x]), minden thread más bankba kerül, és nincs conflict. Ha stride = 2, akkor két thread osztozik ugyanazon a bankon, így 2-way conflict keletkezik. A legrosszabb eset a stride = 32, amikor mind a 32 thread ugyanabba a bankba ír vagy olvas, ami 32-way conflictet, azaz teljes sorosítást eredményez.

Két szabályt kell kimondani. (1) Ha egy warp minden szála ugyanarra a 32 bites szóra hivatkozik, az broadcast, nem bank conflict; conflict csak akkor van, ha ugyanabban a bankban különböző szavakat érnek el. (2) A conflict jellemzően oszlopirányú elérésnél keletkezik: ha egy warp szálai egy 32 széles tömb egy oszlopát olvassák (tile[tx][ty]), akkor a címek 32 szavanként követik egymást, így mind ugyanabba a bankba esnek (32-way conflict).

A bank conflict elkerülésére a leggyakoribb technika a padding, azaz a tömb második dimenziójának eggyel való megnövelése. A tipikus példa a mátrix-transzponálás:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva; blokk: dim3(32, 32), N a mátrix mérete
__global__ void transposeTile(const float* in, float* out, int N) {
    __shared__ float tile[32][32 + 1];   // padding nélkül (32) az oszlopolvasás 32-way conflict
    int x = blockIdx.x * 32 + threadIdx.x;
    int y = blockIdx.y * 32 + threadIdx.y;
    if (x < N && y < N) tile[threadIdx.y][threadIdx.x] = in[y * N + x];
    __syncthreads();
    int xo = blockIdx.y * 32 + threadIdx.x;
    int yo = blockIdx.x * 32 + threadIdx.y;
    if (xo < N && yo < N) out[yo * N + xo] = tile[threadIdx.x][threadIdx.y]; // oszlopolvasás
}

Az oszlopolvasásnál (tile[threadIdx.x][threadIdx.y]) a cím tx * W + ty, ahol W a sorszélesség. W = 32 esetén a bank ty (mod 32), azaz egy warp minden szála ugyanabba a bankba kerül: 32-way conflict. W = 33 esetén a bank (tx + ty) mod 32, ami a warp 32 szálára mind különböző, így nincs conflict. A fenti mátrixszorzó tilingben viszont az As[ty][tx] (egy warp = egy ty sor, tx = 0..31: egymást követő szavak), az As[ty][k] (a warp minden szálán azonos cím: broadcast) és a Bs[k][tx] (egymást követő szavak) is conflictmentes, ezért ott a TILE + 1 padding nem szükséges.

Az alábbi ábra egy warp (ty = 0, tx = 0..31) bankjait mutatja a négy jellemző elérési mintára.

A bank conflict mérésére a compute-sanitizer --tool synccheck nem alkalmas (az a barrier-használati hibákat ellenőrzi), de a Nsight Compute profilozó a l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum és hasonló metrikákkal mutatja a shared memória bank conflictjeit. A mérés a transposeTile két változatán (W = 32 és W = 33) javasolt gyakorlat; a fejezet nem közöl hozzá mért adatot.

7.2.4 Gyakorlati minta: shared memory tiling mátrixszorzással

A tiling célja, hogy a global memória ismételt olvasását csökkentsük azáltal, hogy az adatokat egyszer betöltjük a gyors shared memóriába, és onnan többször felhasználjuk. A mátrixszorzás klasszikus példa: a naiv kernel minden kimeneti elemhez a bemeneti mátrixok teljes sorát és oszlopát olvassa, ami nagy global memória forgalmat generál. A tilinges változat viszont egy TILE×TILE méretű csempét betölt a shared memóriába, és a csempén belüli szorzatösszegeket a shared memóriából számolja, így a shared memóriába betöltött minden elemet TILE-szor használja fel (egy A- vagy B-elemet a teljes szorzás során N/TILE-szer töltünk be a global memóriából).

Az alábbi ábra egy kis példán (N = 8, TILE = 4) mutatja a matmul_tiled két iterációját egy kimeneti blokkra; az interaktív változatban a két barrier szerepe is lépésenként követhető.

A labor meghatározása szerint a feladat a shared memory tiling implementálása. Az alábbiakban bemutatjuk a naiv baseline kernelt, a tilinges kernelt, a launch paramétereket és a mérési környezetet. A kódok a CUDA C++ (C++17) nyelvet használják, és a hibakezelést a cudaGetLastError() és cudaDeviceSynchronize() hívásokkal végezzük.

Naiv kernel (baseline):

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
__global__ void matmul_naive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; ++k) {
            sum += A[row * N + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

Tilinges kernel:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
constexpr int TILE = 32;

__global__ void matmul_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[TILE][TILE];     // padding itt nem szükséges (lásd a bank conflict szakaszt)
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float sum = 0.0f;
    int numTiles = (N + TILE - 1) / TILE;

    for (int t = 0; t < numTiles; ++t) {
        // Betöltés a global memóriából, határellenőrzéssel
        int aRow = row;
        int aCol = t * TILE + tx;
        int bRow = t * TILE + ty;
        int bCol = col;

        if (aRow < N && aCol < N)
            As[ty][tx] = A[aRow * N + aCol];
        else
            As[ty][tx] = 0.0f;

        if (bRow < N && bCol < N)
            Bs[ty][tx] = B[bRow * N + bCol];
        else
            Bs[ty][tx] = 0.0f;

        __syncthreads();

        // Számítás a shared memóriából
        for (int k = 0; k < TILE; ++k) {
            sum += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();
    }

    if (row < N && col < N) {
        C[row * N + col] = sum;
    }
}

A launch konfiguráció a következő:

// CUDA C++ (C++17), nvcc 12.4, nem fordítva
const int N = 2048;                  // TILE: a kernel előtt definiált constexpr
dim3 block(TILE, TILE);              // 32 x 32 = 1024 thread
dim3 grid((N + TILE - 1) / TILE, (N + TILE - 1) / TILE); // 64 x 64 blokk
matmul_tiled<<<grid, block>>>(d_A, d_B, d_C, N);
// shared memória mérete statikus, így a harmadik paraméter 0

A kernelben a shared memória mérete 2 * TILE * TILE * sizeof(float) = 2 * 32 * 32 * 4 = 8192 bájt, ami jóval a limit alatt van. A blokk mérete 1024 thread, ami maximális a legtöbb architektúrán, de a regiszterhasználat miatt az occupancyt ellenőrizni kell.

A labor célja a naiv és a tilinges mátrixszorzó kernel összehasonlítása, valamint a shared memory hatásának számszerűsítése. A mérési környezet az alábbi helyőrző paraméterekkel rendelkezik, mivel a labor izolált környezetben fut, és a megadott hardveradatok nem valós rendszerre vonatkoznak:

  • Driver: 550.54.15 (placeholder)
  • CUDA verzió: 12.4 (placeholder)
  • Compute capability: 8.0
  • Operációs rendszer: Ubuntu 22.04 (placeholder)

Build parancs:

nvcc -O3 -arch=sm_80 -o matmul_shared matmul_shared.cu

Futtatási parancs:

./matmul_shared

A teljes forrás (a fenti két kernellel egy fájlban, a TILE csak egyszer szerepel; nem fordítva, nem futtatva). A fenti kernelblokkokat külön ne másoljuk ide, mert a constexpr int TILE újradefiniálása fordítási hibát adna:

// matmul_shared.cu -- CUDA C++ (C++17), nvcc 12.4, nem fordítva
#include <cstdio>
#include <cstdlib>
#include <cmath>
#include <vector>

#define CUDA_CHECK(call) do { cudaError_t e_ = (call); if (e_ != cudaSuccess) { \
    fprintf(stderr, "CUDA hiba %s:%d: %s\n", __FILE__, __LINE__, cudaGetErrorString(e_)); \
    exit(EXIT_FAILURE); } } while (0)

constexpr int TILE = 32;

__global__ void matmul_naive(const float* A, const float* B, float* C, int N) {
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;
    if (row < N && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < N; ++k) sum += A[row * N + k] * B[k * N + col];
        C[row * N + col] = sum;
    }
}

__global__ void matmul_tiled(const float* A, const float* B, float* C, int N) {
    __shared__ float As[TILE][TILE];   // padding itt nem szükséges
    __shared__ float Bs[TILE][TILE];
    int tx = threadIdx.x, ty = threadIdx.y;
    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;
    float sum = 0.0f;
    for (int t = 0; t < (N + TILE - 1) / TILE; ++t) {
        int aCol = t * TILE + tx, bRow = t * TILE + ty;
        As[ty][tx] = (row < N && aCol < N) ? A[row * N + aCol] : 0.0f;
        Bs[ty][tx] = (bRow < N && col < N) ? B[bRow * N + col] : 0.0f;
        __syncthreads();                // a csempe betöltése kész
        for (int k = 0; k < TILE; ++k) sum += As[ty][k] * Bs[k][tx];
        __syncthreads();                // az olvasás kész, jöhet a következő csempe
    }
    if (row < N && col < N) C[row * N + col] = sum;
}

int main() {
    const int N = 2048;
    const size_t bytes = (size_t)N * N * sizeof(float);
    std::vector<float> hA((size_t)N * N), hB((size_t)N * N), hC((size_t)N * N);
    for (size_t i = 0; i < hA.size(); ++i) {
        hA[i] = (float)(i % 7) * 0.5f;
        hB[i] = (float)(i % 5) * 0.25f;
    }
    float *dA, *dB, *dC;
    CUDA_CHECK(cudaMalloc(&dA, bytes));
    CUDA_CHECK(cudaMalloc(&dB, bytes));
    CUDA_CHECK(cudaMalloc(&dC, bytes));
    CUDA_CHECK(cudaMemcpy(dA, hA.data(), bytes, cudaMemcpyHostToDevice));
    CUDA_CHECK(cudaMemcpy(dB, hB.data(), bytes, cudaMemcpyHostToDevice));

    dim3 block(TILE, TILE);
    dim3 grid((N + TILE - 1) / TILE, (N + TILE - 1) / TILE);
    cudaEvent_t t0, t1;
    CUDA_CHECK(cudaEventCreate(&t0));
    CUDA_CHECK(cudaEventCreate(&t1));

    auto run = [&](void (*k)(const float*, const float*, float*, int), const char* name) -> bool {
        bool ok = true;
        CUDA_CHECK(cudaMemset(dC, 0xFF, bytes));   // NaN-mintázat: nem írt elem eltér
        for (int w = 0; w < 5; ++w) k<<<grid, block>>>(dA, dB, dC, N);   // warm-up
        CUDA_CHECK(cudaGetLastError());
        CUDA_CHECK(cudaDeviceSynchronize());
        float ms[10], mean = 0.0f;
        for (int r = 0; r < 10; ++r) {
            CUDA_CHECK(cudaEventRecord(t0));
            k<<<grid, block>>>(dA, dB, dC, N);
            CUDA_CHECK(cudaEventRecord(t1));
            CUDA_CHECK(cudaGetLastError());
            CUDA_CHECK(cudaEventSynchronize(t1));
            CUDA_CHECK(cudaEventElapsedTime(&ms[r], t0, t1));
            mean += ms[r] / 10.0f;
        }
        float var = 0.0f;
        for (int r = 0; r < 10; ++r) var += (ms[r] - mean) * (ms[r] - mean);
        float sd = sqrtf(var / 9.0f);                       // minta-szórás (n-1)
        double gflops = 2.0 * N * N * (double)N / (mean * 1e-3) / 1e9;   // 2*N^3 / t
        printf("%s: átlag %.3f ms, szórás %.3f ms, %.1f GFLOP/s\n", name, mean, sd, gflops);
        // ellenőrzés: néhány kimeneti elem a CPU-referenciához képest (double)
        CUDA_CHECK(cudaMemcpy(hC.data(), dC, bytes, cudaMemcpyDeviceToHost));
        for (int q = 0; q < 64; ++q) {
            int i = (q * 131) % N, j = (q * 257) % N;
            double ref = 0.0;
            for (int kk = 0; kk < N; ++kk) ref += (double)hA[(size_t)i * N + kk] * hB[(size_t)kk * N + j];
            // a NaN-ra az összehasonlítás hamis, ezért !(a <= b) alakot használunk
            if (!(fabs(hC[(size_t)i * N + j] - ref) <= 1e-3 * fabs(ref) + 1e-3)) {
                printf("  ELTÉRÉS (%d,%d): %f vs %f\n", i, j, hC[(size_t)i * N + j], ref);
                ok = false;
                break;
            }
        }
        printf("%s: ellenőrzés %s\n", name, ok ? "OK" : "HIBA");
        return ok;
    };
    bool ok1 = run(matmul_naive, "matmul_naive");
    bool ok2 = run(matmul_tiled, "matmul_tiled");

    CUDA_CHECK(cudaEventDestroy(t0));
    CUDA_CHECK(cudaEventDestroy(t1));
    CUDA_CHECK(cudaFree(dA));
    CUDA_CHECK(cudaFree(dB));
    CUDA_CHECK(cudaFree(dC));
    return (ok1 && ok2) ? EXIT_SUCCESS : EXIT_FAILURE;
}

A mérési napló sablon: a programot nem futtattuk, ezért mért érték nincs. A GFLOP/s oszlop a 2N^3 / t képlettel számolt hasznos műveletszám (N = 2048: 2N^3 ≈ 1,72 · 10^10 FP-művelet) osztva az idővel; a global memória-forgalmat külön, az ncu dram__bytes_read.sum metrikájával kell mérni.

A várt eredmény: a tilinges kernel gyorsabb a naivnál, mert a global memóriából kiadott olvasások száma körülbelül TILE-ed részére csökken. A naiv kernel minden kimeneti elemhez 2N float-t olvas (A egy sorát és B egy oszlopát), így összesen 2N^3 = 2 · 2048^3 ≈ 1,72 · 10^10 float-olvasást ad ki (≈ 68,7 GB, ha minden olvasás a DRAM-ig jutna; a gyorsítótárak ezt csökkentik). A tilinges kernelnél minden A- és B-elemet N/TILE = 64-szer töltünk be a global memóriából, így a kiadott olvasások száma 2N^3 / TILE ≈ 5,4 · 10^8, azaz elméletileg 32-szer kevesebb. A tényleges gyorsulás ennél kisebb (a shared memória hozzáférések, a szinkronizáció és a gyorsítótárak miatt), és konkrét értéket nem állítunk: azt a kitöltött napló mutatja meg.

A mért eredmény a labor során keletkező tényleges adat. A kitöltéshez a kernelt le kell fordítani, izolált környezetben futtatni, és a cudaEvent időket rögzíteni; a mérés előtt a warm-up stabilizálja az órajelet. A kapott átlag és szórás alapján lehet megítélni a teljesítményt.

A labor során érdemes a Nsight Compute profilozót is futtatni a shared memória bank conflictjeinek ellenőrzésére. A fenti mátrixszorzó tilingben a bank conflict metrikának nullához közelinek kell lennie padding nélkül is (lásd a bank conflict szakaszt); a magas conflictet a transposeTile W = 32 változatán lehet látni. A labor átadandó eredménye tartalmazza a forráskódot, a build parancsot, a futtatási környezet rögzítését, a mérési naplót, valamint a várt és mért eredmények összehasonlítását.

7.2.6 Tipikus hibák és helyes megoldások

A shared memory használata során több gyakori hiba léphet fel. Az alábbiakban összefoglaljuk ezeket, és megadjuk a helyes megoldást.

  1. Hiányzó __syncthreads() a tiling ciklusban. Ha a betöltés után nincs szinkronizáció, egyes thread-ek még a régi shared memória tartalommal számolnak, mert a többi thread még nem fejezte be az írást. Ez hibás eredményhez vezet. A helyes minta: minden shared memória írás után, mielőtt bármely thread olvasná az adatot, __syncthreads() szükséges, és minden olvasás után, mielőtt a következő iterációban felülírnánk, szintén.

  2. Feltételes __syncthreads() használata (a compute-sanitizer --tool synccheck az ilyet jelzi). A korábban említett módon a barrier nem lehet feltételhez kötve, mert a viselkedés nem definiált (holtpont vagy csendben hibás szinkronizáció). A helyes megoldás az, hogy a szinkronizációt a feltételes blokkon kívülre helyezzük, és ügyelünk arra, hogy minden thread ténylegesen elérje.

  3. Túl nagy shared memória igény a launch konfigurációban. Ha a kernel statikus vagy dinamikus shared memória igénye meghaladja a hardveres limitet, a kernel indítása hibával meghiúsul: cudaErrorInvalidValue, cudaErrorInvalidConfiguration vagy cudaErrorLaunchOutOfResources kódot kapunk (lásd 6.4). A 48 KiB feletti dinamikus shared memóriához a cudaFuncSetAttribute(…, cudaFuncAttributeMaxDynamicSharedMemorySize, …) opt-in is kell. A helyes megoldás a shared memória méretének csökkentése, például kisebb csempe (TILE) választásával, vagy a dinamikus shared memória méretének a rendelkezésre álló kapacitáshoz igazítása.

  4. Bank conflict figyelmen kívül hagyása oszlopelérésnél. Ha egy warp szálai egy 32 széles tömb oszlopát olvassák (például transzponálásnál tile[tx][ty]), 32-way bank conflict keletkezik, mert az oszlop minden eleme ugyanabba a bankba esik. A helyes megoldás a padding: a második dimenzió TILE + 1. A sorirányú (As[ty][tx]) és az azonos címre hivatkozó (broadcast) elérés viszont nem okoz conflictet, ott a padding felesleges.

  5. A shared memória inicializálásának elmulasztása. A shared memória tartalma a blokk indulásakor definiálatlan. Ha a kernel a betöltés előtt olvassa, szemét értéket kap. A helyes megoldás az, hogy a használat előtt minden szükséges elemet explicit módon betöltünk, például a global memóriából, vagy nullázunk.

  6. A dinamikus shared memória pointerének hibás kezelése több tömb esetén. Ha több dinamikus tömböt szeretnénk, egyetlen extern __shared__ deklarációt kell használni, és azon belül pointer-aritmetikával kell elhelyezni a részeket. A résztömbök határait (eltolásait) a launch-méretből kell következetesen kiszámolni, és az igazítást is tartani kell. A helytelen eltolás-számítás gyakori hiba.

Ezek a hibák mind a shared memory alapvető tulajdonságaiból fakadnak, és a fenti megoldásokkal elkerülhetők. A fejezet laborjában a fő ellenőrzési pont a tiling kernel helyes __syncthreads()-elhelyezése és az eredmény CPU-referenciával való egyezése; a padding hatását a transposeTile W = 32 és W = 33 változatán lehet megfigyelni.

7.2.7 Önellenőrző kérdések

  1. Mi a különbség a statikus és a dinamikus shared memory között? Hogyan adjuk meg a dinamikus shared memory méretét a kernel indításakor?
  2. Miért szükséges a __syncthreads() a tiling ciklus betöltési és számítási fázisa között? Mi történik, ha elhagyjuk?
  3. Magyarázza el, mi a bank conflict, és miért okoz teljesítményromlást? Hogyan kerülhető el egy 32×32-es shared tömb esetén?
  4. A fenti tilinges mátrixszorzó kernelben miért nem szükséges a TILE + 1 padding, és a transzponáló kernelben miért igen?
  5. Hogyan ellenőrizhető a shared memória bank conflictjeinek száma a Nsight Compute profilozóval?

Válaszvázlatok. (1) A statikus méretet fordításkor rögzítjük (__shared__ float t[32][32]), a dinamikusat extern __shared__ jelöli, és a launch harmadik paramétere adja meg bájtban. (2) Az első barrier a betöltés befejezését, a második az olvasás befejezését biztosítja; nélküle versenyhelyzet (race condition) keletkezik. (3) Bank conflict: ugyanabban a bankban különböző szavak egy warp-on belüli elérése, ami sorosít; padding vagy elrendezésváltás kerüli el. (4) Mátrixszorzásnál a sor- és broadcast-elérés conflictmentes, transzponálásnál az oszlopolvasás 32-way conflict, W = 33 esetén a bank (tx + ty) mod 32. (5) ncu --metrics l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_st.sum ./program két változaton.

A következő alfejezet (7.3) a local, constant és texture memóriatereket tárgyalja, és épít az itt bevezetett shared memory fogalmakra, különösen a memóriahierarchia kiválasztási szempontjaira. A shared memory a gyors, blokkszintű együttműködés alapja, és a későbbi fejezetekben (tiling, redukció, stencil) újra előkerül.
