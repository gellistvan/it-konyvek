33.3 Tesztelés, benchmark és hibaanalízis

33.3.1 A helyesség és a teljesítmény igazolásának szerepe a záróprojektben

A tervezés és az implementáció – az alg127 alfejezet témája – után a záróprojekt legsúlyosabb mérnöki kihívása annak bizonyítása, hogy a megoldásunk nem csupán lefordul és fut, hanem helyesen fut, valamint a kitűzött teljesítménycélokat is reprodukálható módon teljesíti. A tesztelés és a benchmarkolás itt nem utólagos formalitás, hanem az algoritmus validációjának aktív eszköze: a hibás invariánst, a rossz komplexitású adatszerkezet-választást vagy a hibás memóriakezelést gyakran éppen a jól megtervezett mérés és a szisztematikus szélsőeset-vizsgálat leplezi le.

Ebben az alfejezetben a következő kérdésekre adunk választ:

  1. Hogyan igazoljuk, hogy a megoldás a bemenet–kimenet szerződést minden releváns inputra teljesíti?
  2. Hogyan találjuk meg a szélső eseteket és hogyan használjuk a stressztesztelést?
  3. Hogyan mérjük a teljesítményt úgy, hogy a mérés ne legyen önámítás?
  4. Hogyan hasonlítsuk a megoldást egy baseline-hoz, és hogyan végezzünk hibaanalízist?

Az alfejezet laborja egy olyan záróprojekt-tesztriport elkészítését várja el, amely a mért és a várt eredményt szigorúan elkülöníti, és a mérési naplót reprodukálható formában tartalmazza.

33.3.2 Helyességvizsgálat: a szerződés, az orákulum és a tesztpiramis

33.3.2.1 A szerződés mint a tesztelés alapja

A korrektségi szerződés – amelyet a könyv minden algoritmusánál rögzítettünk – a tesztelés elsődleges forrása. Ha az alg127 során megtervezett függvényünk vagy osztályunk rendelkezik

  • bemenettel és előfeltétellel,
  • kimenettel és utófeltétellel,
  • valamint leállási feltétellel,

akkor ezekből mechanikusan generálhatók a tesztesetek.

Példa (tömörített trie – a záróprojekt egyik gyakori komponense).
Tegyük fel, hogy a projekt egy gyakori szóelőtag-keresőt (prefix_search) valósít meg egy tömörített trie (lásd alg038) fölé.

  • Bemenet: egy szöveges korpuszból épített tömörített trie, valamint egy prefix sztring.
  • Előfeltétel: a trie érvényes (a gyökérből minden csúcs egyetlen úton érhető el); a tárolt szavakat terminális jelölés rögzíti, amely állhat egy csúcson vagy egy tömörített él címkéjének végén; a prefix az ábécé karaktereiből áll.
  • Kimenet: az összes olyan tárolt, terminális szó listája, amely prefix-szel kezdődik.
  • Utófeltétel: a lista pontosan a prefix-szel kezdődő tárolt szavakat tartalmazza, mindegyiket egyszer (a bemeneti duplikátumok kiszűrve), lexikografikusan növekvő sorrendben; a rendezési kulcs a szó kódpont-sorozata.
  • Leállási feltétel: a trie mélysége véges, így a bejárás terminál.

A prefix a tömörített trie egy élcímkéjének belsejében is végződhet. Nyomkövetés: a root –„almafa”→ levél trie-ban a prefix = „alm” az egyetlen él harmadik karakteréig jut; a prefix csúcsa az él alatti részfa, ezért a találat az almafa szó.

Az alábbi ábra ugyanezt a lenti differenciális teszt fixed szótárán (al, alma, almafa, körte, körtefa) mutatja: ott az „alm” prefix a „ma” élcímke belsejében, az első karaktere után áll meg.

A tesztelő kódnak nem csupán a kimenetet kell ellenőriznie, hanem az invariánsokat is. Egy trie esetén például ellenőrizhető, hogy a beszúrás után nem keletkezett-e kör, és hogy a gyermek-mutatók a definiált ábécé szerint konzisztensek-e.

33.3.2.2 Az orákulum és a differenciális tesztelés

A záróprojektben ritkán adott a „helyes” kimenet kézzel. A differenciális tesztelés (más néven orákulum-tesztelés) azt használja ki, hogy optimalizált, bonyolult algoritmusunkat összehasonlítjuk egy lassú, de magától értetődően helyes referencia-implementációval.

Módszer.
Írjunk egy naiv naive_prefix_search referenciát, amely az összes tárolt szóból szűri a prefix-szel kezdődőket, majd a szerződés szerint deduplikál és növekvő sorrendbe rendez. Ugyanabból a words listából a ciklus minden lépésében épül fel a vizsgált tömörített trie, így a got és az expected ugyanarra az adathalmazra vonatkozik. Az alábbi fájl önállóan futtatható (python3 test_prefix_search.py), és a generátor külön állít elő egyező, nem egyező, üres, valamint élcímke belsejében végződő prefixet:

# Python: önálló differenciális teszt (teljes fájl)
import random


class Node:
    __slots__ = ("label", "children", "terminal")

    def __init__(self, label=""):
        self.label = label       # a szülőből ide vezető él címkéje
        self.children = {}       # első karakter -> gyermek
        self.terminal = False    # itt végződik tárolt szó


def _insert(node, word):
    if not word:
        node.terminal = True
        return
    child = node.children.get(word[0])
    if child is None:
        leaf = Node(word)
        leaf.terminal = True
        node.children[word[0]] = leaf
        return
    lab = child.label
    i = 0
    while i < len(lab) and i < len(word) and lab[i] == word[i]:
        i += 1
    if i == len(lab):
        _insert(child, word[i:])
        return
    mid = Node(lab[:i])
    old = Node(lab[i:])
    old.children = child.children
    old.terminal = child.terminal
    mid.children[lab[i]] = old
    node.children[word[0]] = mid
    if i == len(word):
        mid.terminal = True
    else:
        leaf = Node(word[i:])
        leaf.terminal = True
        mid.children[word[i]] = leaf


def build(words):
    root = Node()
    for word in sorted(set(words)):
        _insert(root, word)
    return root


def _collect(node, acc, out):
    if node.terminal:
        out.append(acc)
    for first in sorted(node.children):
        child = node.children[first]
        _collect(child, acc + child.label, out)


def prefix_search(root, prefix):
    node, acc, rest = root, "", prefix
    while rest:
        child = node.children.get(rest[0])
        if child is None:
            return []
        lab = child.label
        j = 0
        while j < len(rest) and j < len(lab) and rest[j] == lab[j]:
            j += 1
        if j == len(lab):
            node, acc, rest = child, acc + lab, rest[j:]
        elif j == len(rest):
            # a prefix az él címkéjének belsejében végződik
            node, acc, rest = child, acc + lab, ""
        else:
            return []
    out = []
    _collect(node, acc, out)
    return out   # a _collect rendezett gyermekbejárása miatt a lista már növekvő


def naive_prefix_search(words, prefix):
    """A szerződés szerinti referencia: deduplikál és rendez."""
    return sorted({word for word in words if word.startswith(prefix)})


def random_words(rng, count, max_len=20, alphabet="abcdefghij"):
    return ["".join(rng.choice(alphabet)
                    for _ in range(rng.randint(1, max_len)))
            for _ in range(count)]


def random_prefix(rng, words):
    kind = rng.randrange(4)
    if kind == 0:
        return ""                                   # üres prefix
    if kind == 1:
        length = rng.randint(1, 22)
        return "".join(rng.choice("abcdefghij") for _ in range(length))  # többnyire nem egyező
    word = rng.choice(words) if words else "almafa"
    cut = rng.randint(1, len(word))                 # szóprefix: gyakran él belsejében
    return word[:cut]


def main():
    # 1) Célzott esetek: egyező, nem egyező, üres, él belsejébe eső prefix.
    fixed = ["alma", "almafa", "al", "körte", "körtefa", "alma"]
    cases = [
        ("al", ["al", "alma", "almafa"]),                    # egyező, csúcshatáron
        ("alm", ["alma", "almafa"]),                         # élcímke belsejében
        ("z", []),                                           # nem egyező
        ("", ["al", "alma", "almafa", "körte", "körtefa"]),  # üres prefix
        ("almafafelé", []),                                  # hosszabb, mint bármely szó
    ]
    for prefix, expected in cases:
        assert prefix_search(build(fixed), prefix) == expected, prefix
    # 2) Determinisztikus véletlen esetek.
    for seed in range(200):
        rng = random.Random(seed)
        words = random_words(rng, rng.randint(0, 40))
        for _ in range(5):
            prefix = random_prefix(rng, words)
            got = prefix_search(build(words), prefix)
            expected = naive_prefix_search(words, prefix)
            assert got == expected, (seed, words, prefix, got, expected)
    print("OK: célzott esetek és 200 seed × 5 differenciális teszt")


if __name__ == "__main__":
    main()

A generátor random.Random(seed) példányt használ, így minden futás ugyanazt az esetsorozatot állítja elő, és egy hiba a seed értékével reprodukálható. Ez a minta a záróprojektben szinte minden optimalizált struktúránál kötelező: a szegmensfa (alg041) ellenőrzése naiv intervallum-összegzéssel, a Dinic-féle áramlás (alg096) ellenőrzése naiv útkeresővel, a KMP (alg058) ellenőrzése naiv karakterillesztéssel stb.

33.3.2.3 A tesztpiramis és a determinisztikus tesztkészlet

A laborban elvárt tesztkészlet három szintből áll:

  1. Egységtesztek (unit tesztek). Minden publikus műveletre, izoláltan. Például:
    • Üres trie létrehozása.
    • Egyetlen szó beszúrása, majd keresése.
    • Duplikált beszúrás.
    • Törlés.
    • Üres prefix keresése.
  2. Szélső esetek és tulajdonság-alapú tesztek (property-based). Nem konkrét bemenetre, hanem tulajdonságra fogalmazunk meg állítást. Például: „bármely beszúrás után a trie mérete növekszik, ha a szó új, és változatlan, ha a szó már létezett”; „bármely törlés után a keresés Nem található értéket ad”.
  3. Stressz- és differenciális tesztek. Nagy, véletlen inputhalmazok, amelyek a fenti orákulumos összehasonlítást használják.

A könyv korrektségi szerződése szerint a teszteknek ki kell terjedniük az üres, egyelemű, duplikált, rendezett, fordított és véletlen inputokra, valamint a szélső értékekre. A záróprojekt szöveges kontextusában ez azt jelenti, hogy:

  • Üres szótárat és üres prefixet tesztelünk.
  • Egyetlen karakterből álló szavakat.
  • Olyan szavakat, amelyek közös tővel rendelkeznek (pl. alma, almás, almafa).
  • A teljes ábécé első és utolsó karakterét tartalmazó szavakat.
  • Olyan inputot, ahol a prefix hosszabb, mint bármely tárolt szó.
  • Véletlen, nagy korpuszt (n = 10^5), hogy a rekurzió mélységét és a memóriahasználatot is terheljük.

33.3.3 Szélső esetek, stressztesztelés és a hibák osztályozása

33.3.3.1 A szélső esetek katalógusa

A záróprojekt-tesztriportban külön szekciót érdemes szentelni a szélső eseteknek. A tipikus hibák, amelyeket ezek felfednek:

  • Üres bemenet: A legtöbb algoritmus meghibásodik, ha a bemeneti tömb, lista vagy gráf üres. Például egy üres szegmensfa építése 0 méretű tömbre gyakran futás idejű hibát okoz, ha nem figyelünk az indexelésre.
  • Egyelemű bemenet: A rekurzív felosztásoknál (oszd meg és uralkodj) a legkisebb nem triviális eset.
  • Duplikátumok: A rendezéseknél a stabilitás kérdése; a keresőfáknál és szótáraknál a duplikált kulcs kezelése szerződésfüggő (számláló, frissítés vagy elutasítás).
  • Rendezett és fordítottan rendezett bemenet: A quicksort (alg052) esetén a rossz pivotválasztás itt okoz O(n2)O(n^2) futásidőt. A kiegyensúlyozatlan bináris keresőfa példája mutatja, hogy itt valóban a beszúrási sorrend számít: az 1, 2, 3, …, n növekvő beszúrási sorrend láncszerű, O(n)O(n) mélységű fát ad, ugyanezek az elemek véletlen sorrendben O(log⁡n)O(\log n) várható mélységet érnek el. A trie alakját ezzel szemben nem a beszúrási sorrend, hanem a tárolt szavak prefixhalmaza határozza meg: bármely beszúrási permutáció ugyanazt a trie-t adja, ezért a permutációs teszt itt az azonos funkcionális eredményt ellenőrzi, nem a mélységet.
  • Szélső értékek: A INT_MIN, INT_MAX, -1, 0, 1 értékek, mivel a túlcsordulás (overflow) és az off-by-one hibák itt jelentkeznek. C-ben a (l + r) / 2 kifejezés túlcsordulhat, ha l + r meghaladja az egész típus tartományát; helyette l + (r - l) / 2 használandó.

A trie mélységét célzottan teszteljük: hosszú közös prefixű szavakkal (pl. a, aa, aaa, … a maximális szóhosszig), a maximális hosszúságú szóval, valamint egymás prefixét alkotó szavakkal (a, ab, abc). A nagy véletlen korpusz önmagában nem garantál nagy mélységet, mert a véletlen szavak hamar elágaznak; a rekurzív bejárás terhelését ezért ezekkel a célzott esetekkel kell biztosítani. A tömörített trie csúcsmélysége legfeljebb a szavak száma, az élek címkéinek összhossza pedig a bemeneti szöveg hosszával arányos.

Példa (szegmensfa off-by-one hibája). A csúcs a [lo,hi][lo, hi] tartományt fedi, mid=lo+(hi−lo)/2mid = lo + (hi-lo)/2, a bal gyerek [lo,mid][lo, mid], a jobb [mid+1,hi][mid+1, hi]. A helyes rekurzió: range_sum(node.left, lo, mid, left, min(right, mid)) és range_sum(node.right, mid+1, hi, max(left, mid+1), right). Ha a jobb gyereknél max(left, mid) szerepel, az A[mid]A[mid] kétszer számolódik, amit a left = right = mid szélső teszt azonnal jelez.

33.3.3.2 Stressztesztelés és a hiba reprodukálhatósága

A stressztesztelés célja, hogy a bemeneti méret növelésével és véletlenszerű inputok generálásával felszínre hozza azokat a hibákat, amelyek csak ritkán, nagy terhelés alatt jelentkeznek.

A stressz-tesztkörnyezetnek a következőket kell tartalmaznia:

  • Determinisztikus seed: A könyv véletlenített algoritmusokra vonatkozó szerződése szerint a seed-et rögzíteni kell. Ez biztosítja, hogy a hiba reprodukálható legyen.
  • Progresszív terhelés: Kezdjük n = 10-zel, majd duplázzuk n = 20, 40, ..., 10^6-ig. Minden méretnél futtassuk le az orákulumot és a mérendő algoritmust is.
  • Invariáns-ellenőrzés futás közben: A stressz-futás során ne csak a végeredményt ellenőrizzük, hanem az adatszerkezet invariánsait is. Például minden beszúrás után ellenőrizzük a piros-fekete fa (alg028) tulajdonságait, vagy minden push után a verem (alg020) méretét.

A tipikus hibák osztályozása a záróprojektben:

  1. Off-by-one hiba: A leggyakoribb hiba, általában az indexek, a hosszak vagy a rekurziós alapeset határán.
  2. Hiányzó alapeset: A rekurzió nem terminál üres bemenetre, vagy a DP-tábla (alg066) inicializálása hiányos.
  3. Hibás invariáns: A ciklus vagy rekurzió belsejében az invariáns nem teljesül, ami a vártnál lassabb futást vagy hibás kimenetet eredményez.
  4. Túlcsordulás és pontosság: Lebegőpontos számoknál a kivonás (x - y) katasztrofális törléshez vezethet, ha x és y közel van egymáshoz.
  5. Aliasing és mellékhatások: A bemenő paraméter módosul a függvényen belül, amit a hívó nem vár.
  6. Memóriakezelési hibák: Dinamikus memória esetén a felszabadítás utáni használat (use-after-free) vagy a szivárgás.

33.3.4.2 Statisztikai alapok: átlag, szórás és percentilisek

Egyetlen futási idő nem elegendő. A környezet zaját (cache-hideg, ütemező, háttérfolyamatok) csak statisztikai mutatókkal lehet elválasztani a valódi teljesítménytől.

A laborban elvárt statisztikai mutatók:

  • Átlag: Az összes mért idő számtani közepe.
  • Medián: A rendezett idők középső eleme; robusztusabb a kiugró értékekre.
  • Szórás: A futási idők szóródása. Ha a szórás nagy (az átlaghoz képest), a mérés zajos, és a következtetés megbízhatatlan.
  • Percentilisek: A 90., 95. és 99. percentilis azt mutatja, hogy a legrosszabb esetek mennyire térnek el a tipikustól. Ez különösen fontos a valós idejű rendszereknél.

Példa (Python mérési váz):

import math
import time
import statistics

def measure(func, *args, repeats=11):
    times = []
    for _ in range(repeats):
        start = time.perf_counter()
        func(*args)
        end = time.perf_counter()
        times.append(end - start)
    return {
        "mean": statistics.mean(times),
        "median": statistics.median(times),
        "stdev": statistics.stdev(times),
        "p90": sorted(times)[math.ceil(0.9 * len(times)) - 1],  # nearest-rank
    }

A 95. és 99. percentilis csak legalább 100 ismétlésnél értelmezhető; 11 futásnál a mediánt és a szórást közöljük.

33.3.5 Összehasonlítás a baseline-nal

33.3.5.1 Mi a baseline?

A baseline egy referencia-megoldás, amelyhez a saját optimalizált implementációnk teljesítményét mérjük. A baseline lehet:

  • Naiv orákulum: A már bemutatott naive_prefix_search. Ez mutatja meg, hogy az optimalizálás mekkora tényleges nyereséget hozott.
  • Standard könyvtári megoldás: Például a C++ std::sort vagy a Python dict. Ez mutatja meg, hogy a saját implementáció mennyire versenyképes a bevált, ipari megoldással.
  • Előző verzió: Ha a projekt célja egy meglévő rendszer gyorsítása, a kiindulási állapot a baseline.

33.3.5.2 Hogyan hasonlítsunk?

A nyers futási idők összehasonlítása nem elég; a skálázódást is össze kell vetni. Ha a saját megoldásunk O(nlog⁡n)O(n \log n) bonyolultságú, a baseline pedig O(n2)O(n^2), akkor a nyereség a bemeneti méret növelésével nő. A benchmarknak ezt a tendenciát kell illusztrálnia.

Módszer:
Rögzítsük a benchmark-szerződést: mindhárom megoldás ugyanazt a qq lekérdezést kapja, és ugyanazt a kimenetet adja vissza (a prefixszel kezdődő tárolt szavak deduplikált, növekvő sorrendű listája). Az építési (előfeldolgozási) időt külön mérjük a lekérdezési időtől. Ezután futtassuk mindhárom megoldást különböző n méretekre, és ábrázoljuk a log–log grafikonon a lekérdezési időt. A pontokra illesztett egyenes meredeksége a komplexitás kitevőjét becsüli meg:

  • Ha t(n)≈c⋅nkt(n) \approx c \cdot n^k, akkor log⁡t≈log⁡c+klog⁡n\log t \approx \log c + k \log n.
  • Az O(nlog⁡n)O(n \log n) algoritmus log–log grafikonon kissé homorú görbét ad; rövid intervallumon a meredekség csak közelítő becslés, nem bizonyíték (lásd a 33.3.7.3. szakaszt (A mért és a várt eredmény elkülönítése)).

Példa (szemléltető, nem futtatott mérés; q=n/10q = n/10 lekérdezés összideje):

Inputméret n Saját trie (ms) Naiv lista, referencia (ms) std::unordered_map, teljes bejárás (ms)
1000 0.2 0.9 0.3
10000 2.3 87.5 30
100000 26 8741.0 3000
1000000 300 timeout timeout

(Szemléltető értékek a kimondott költségmodellhez igazítva, nem mért adatok: q=n/10q=n/10 lekérdezés összideje; a trie ≈ ×10–12, az unordered_map és a naiv oszlop ≈ ×100 évtizedenként.)

A táblázat értelmezése:
A naiv oszlop szuperlineáris növekedése nem mond ellent a referencia lineáris viselkedésének, mert a mért mennyiség q=n/10q = n/10 lekérdezés összideje: egy lekérdezés a szűréssel O(nk)O(nk), a szerződés szerinti deduplikálással és rendezéssel pedig O(nlog⁡n)O(n \log n), így a teljes futás Ω(n2)\Omega(n^2). A trie oszlopa lekérdezésenként O(k+a kimenet összhossza)O(k + \text{a kimenet összhossza}) (kk a prefix hossza, a kimenet összhossza a rr találat szavainak együttes hossza); az építés O(L)O(L) a teljes szöveghosszon, ezt külön kell jelenteni. A std::unordered_map oszlopa teljes kulcsbejárással szűr prefixre, ezért lekérdezésenként O(n)O(n); a konténer std::hash<std::string> alapú, átlagos O(1)O(1) kulcslekérdezéssel, de prefix szerinti bejárást nem támogat. A mérési környezetet a 33.3.4.1. szakasz szerinti napló rögzíti (itt: C++17, GCC 13.1, -O3, x86-64 Linux).

Következtetés (a táblázatból):
A saját trie a naiv referenciához képest a teljes lekérdezési költséget tekintve nagyságrendekkel kedvezőbb, mert a naiv változat minden lekérdezésnél az összes szót bejárja és a találatokat rendezi. A std::unordered_map prefixkeresésre nem alkalmas közvetlenül: a prefixet csak az összes kulcs bejárásával tudja szűrni, ami lekérdezésenként O(n)O(n). A táblázat tendenciája a fenti modellel összhangban van; éles következtetéshez a 33.3.4.3. szakasz szerinti, nyers adatokat is tartalmazó mérési napló szükséges.

33.3.6 Hibaanalízis: amikor a számok nem a vártat mutatják

A benchmarkolás során gyakran kapunk olyan eredményt, amely ellentmond az elméleti várakozásnak. Ilyenkor a hibaanalízis a következő lépéseket foglalja magában:

  1. A mérési hiba kizárása: Ellenőrizzük a környezet stabilitását. A stdev túl magas? Futtassuk újra a mérést, zárjuk be a háttérfolyamatokat, ellenőrizzük a CPU skálázást (frequency scaling).
  2. A konstans tényező elemzése: Az O(n)O(n) algoritmus is lehet lassabb, mint egy O(nlog⁡n)O(n \log n) algoritmus, ha a konstans szorzója nagy. Például a láncolt lista (alg019) sokkal rosszabb cache-viselkedésű, mint egy dinamikus tömb (alg018), ezért lineáris bejárásnál a lista lassabb lehet a rossz memória-hozzáférési mintázat miatt.
  3. A cache-viselkedés vizsgálata: A modern processzorokon a memória-hozzáférés gyakran fontosabb, mint a műveletek száma. A tömörített trie gyorsabb, mint a sima trie, mert kevesebb csúcsot kell bejárni, de ha a tömörített csúcsok nagy stringeket tartalmaznak, a cache-sorok túlcsordulhatnak.
  4. A fordító optimalizálásának ellenőrzése: A benchmarkban a hívott függvényt a fordító kioptimalizálhatja, ha annak nincs mellékhatása. Például ha a prime_count(n) függvény eredményét nem használjuk fel, a C++ fordító -O3 alatt eltávolíthatja a teljes számítást. Ilyenkor a mért idő 0. A megoldás: az eredményt írassuk ki, vagy adjuk hozzá egy volatile változóhoz.

Példa a gyakorlati hibaanalízisre.
A záróprojektben a fejlesztő egy szegmensfát épít a gyakori intervallum-összeg kiszámítására. A mérés szerint a szegmensfa lassabb, mint a naiv lineáris összegzés, ha n < 1000. Ez nem hiba, hanem a szegmensfa konstans tényezője (rekurziós hívások, nagy memóriaelérési lábnyom). A hibaanalízis megállapítja, hogy a szegmensfa csak n > 10^4 felett éri meg. Ezért a projekt egy hibrid megoldást választ: kis tömbökre lineáris keresést, nagyra szegmensfát.

33.3.7 Labor: tesztriport és benchmarkeredmények

33.3.7.1 A labor célja

A záróprojekt ezen szakaszának átadandó eredménye egy reprodukálható jegyzetfüzet (pl. Jupyter Notebook) vagy kódprojekt (pl. Python csomag, C++ projekt), amely a következőket tartalmazza:

  1. Rögzített inputok: A bemenetgenerátor és a használt seedek.
  2. Tesztek: A helyességi tesztek (egység-, szélső eset- és stressz-tesztek).
  3. Mérési napló: A benchmark futtatási paraméterei és a nyers időadatok.
  4. Tesztriport: A mért és a várt eredmény elkülönített dokumentálása.

33.3.7.2 A tesztriport felépítése

A tesztriport a következő szekciókat tartalmazza:

A. Bevezetés és célok.
Röviden összefoglaljuk, mit tesztelünk, és mi a projekt célja (pl. „A cél egy prefix-kereső adatszerkezet, amely n = 10^6 szó esetén minden lekérdezést O(k + r) idő alatt válaszol meg, ahol k a prefix hossza és r a visszaadott találatok száma”).

B. Tesztkörnyezet.
A nyelv, a verzió, a hardver és a függőségek felsorolása.

C. Helyességi tesztek.
Ez a szekció táblázatos formában tünteti fel az összes tesztesetet. Minden sornál szerepel a teszt azonosítója, a leírás, a bemenet, a várt kimenet, a mért kimenet és az eredmény (PASS/FAIL).

Példa sorok a táblázatban:

Azonosító Leírás Bemenet Várt Mért Eredmény
T01 Üres trie [], prefix="" [] [] PASS
T02 Egy elem ["alma"], prefix="a" ["alma"] ["alma"] PASS
T03 Duplikátum ["alma", "alma"], prefix="a" ["alma"] ["alma"] PASS
T04 Nincs találat ["alma"], prefix="z" [] [] PASS

D. Stressz-teszt eredmények.
A differenciális tesztelés eredménye. Például: „1000 véletlen seedre futtatva, n = 100 és n = 1000 méretű bemenetre, minden esetben a trie kimenete megegyezett a naiv implementációval.”

E. Benchmark eredmények.
A futási idők statisztikai összefoglalója, a baseline-nal való összehasonlítás, valamint a mért és a várt komplexitás összehasonlítása.

Példa a költségmodell igazolására (mért vs. várt):

A lekérdezés költsége három részből áll: a prefix csúcsának megkereséséből (O(k)O(k), ahol kk a prefix hossza), a prefix csúcsa alatti részfa bejárásából és a kimenet kiírásából (O(r)O(r), ahol rr a találatok száma), valamint ezek összegéből. A teljes költségmodell O(k+a kimenet összhossza)O(k + \text{a kimenet összhossza}), azaz legfeljebb O(k+r⋅L)O(k + r\cdot L), ha a gyermekek rendezett szerkezetben vannak; a csúcsonkénti sorted(node.children) további O(σlog⁡σ)O(\sigma\log\sigma)-t ad csúcsonként (σ\sigma az ábécé mérete). A trie méretétől (nn) csak annyiban függ, hogy a gyermekkeresés átlagosan O(1)O(1).

Eset kk rr Várt domináns tag
Hiányzó prefix 8 0 O(k)O(k)
Állandó találatszám 8 10 O(k+kimenet összhossza)O(k + \text{kimenet összhossza})
Növekvő találatszám 8 n/10n/10 O(kimenet összhossza)O(\text{kimenet összhossza})

Az első két esetben a futásidő csak a prefix hosszától és a rögzített találatszámtól függ; a harmadikban a kimenet mérete miatt a mért idő az nn növekedésével nő, ezért ott a mérés nem támaszthatja alá az nn-független viselkedést. A táblázat csak a várt modellt szemlélteti, nem mérési eredmény; a tényleges nyers adatokat a 33.3.4.3. szakasz szerinti mérési naplóban kell rögzíteni, és a következtetést a konkrét mért mintatartományra kell korlátozni.

F. Hibaanalízis és megbeszélés.
Itt dokumentáljuk azokat a hibákat, amelyeket a tesztelés során találtunk, és azok javítását. Például: „A stressz-teszt rávilágított, hogy az üres prefix esetén a rekurzív bejárás nem tért vissza, mert a prefix[0] hozzáférés IndexError-t okozott. A hiba javítva egy extra alapeset bevezetésével.”

33.3.7.3 A mért és a várt eredmény elkülönítése

A riport egyik legfontosabb minőségi kritériuma, hogy az olvasó azonnal lássa, mi az, amit az algoritmus elvileg ad, és mi az, amit a gyakorlatban mértünk. A kettő keverése – például a mért futási időből visszaszámolt komplexitás közlése úgy, mintha elméleti eredmény lenne – súlyos módszertani hiba.

Helyes megfogalmazás:

„A vizsgált n∈[105,106]n \in [10^5, 10^6] tartományban a mért adatokra illesztett log–log egyenes meredeksége 1,051{,}05 volt. Ez a tartomány összeegyeztethető az O(nlog⁡n)O(n \log n) modellel, de önmagában nem zárja ki az n1,05n^{1{,}05} vagy egy konstans költségű átmeneti szakasz lehetőségét sem.”

Miért helyes? A meredekség becslés, nem bizonyítás: rövid intervallumon több modell is hasonló meredekséget adhat. A riportban ezért legalább két-három jelölt modellt kell a nyers adatokra illeszteni (pl. nn, nlog⁡nn \log n, n1,05n^{1{,}05}), normalizált görbéket ábrázolni (a mért időt a modell értékével osztva), és a maradékokat, valamint a mérési zajt is bemutatni. A könyvben szereplő pontokhoz a regresszióhoz felhasznált nyers adatokat is mellékelni kell, hogy a számítás reprodukálható legyen. A következtetést a mért nn-tartományra kell korlátozni.

Helytelen megfogalmazás:

„A futási idő pontosan O(n log n) volt.”

A helytelen megfogalmazás azért hibás, mert a futási idő egyetlen mért érték, míg a bonyolultság az aszimptotikus viselkedés elméleti leírása.

33.3.8 Összefoglalás és továbbvezető kérdések
