5.1 auto, structured bindings, if constexpr és consteval/constinit

A modern C++ egyik legfontosabb fordulata, hogy a típusok nemcsak explicit deklarációkkal, hanem a fordító által levezetve is megjelenhetnek. Az auto, a decltype, a structured binding, az if constexpr, a consteval és a constinit mind ugyanazt a célt szolgálják: a típusinformációt és a vezérlést a lehető legkorábbra, jellemzően fordítási időbe helyezzük, miközben a kód rugalmas marad. A következőkben ezeket az eszközöket nem puszta szintaxisként, hanem a fordító viselkedése, a dedukciós szabályok és a gyakori hibák felől vizsgáljuk.

5.1.1 auto és a típusdedukció

Az auto kulcsszó C++11 óta szolgál típuslevezetésre (korábban egy elavult tárolási osztályt jelölt), és a jelentése később finomodott. A legfontosabb szabály: az érték szerinti auto nem vezet le referenciát és elhagyja a felső szintű (top-level) const-ot, ha azt explicit módon nem kérjük. Az alsó szintű (low-level) const, vagyis a mutatott vagy hivatkozott objektum konstansága megmarad: const int* p; auto q = p; esetén q típusa const int*, auto& r = cref; esetén pedig const int&. Az alábbi példa az alapeseteket mutatja be (Szükséges fejléc: <string>, <vector>; GCC 13+, C++20):

#include <string>
#include <vector>

void demo_auto() {
    int value = 42;
    const int& cref = value;

    auto a = value;        // int
    auto b = cref;         // int  (a const és a referencia eltűnik)
    auto& c = value;       // int&
    const auto& d = value; // const int&

    auto&& e = value;      // int&  (lvalue-ra dedukál int&-et)
    auto&& f = 42;         // int&& (rvalue-ra dedukál int&&-et)
}

Az auto&& az univerzális (forwarding) referencia alapsémája, és nem csak sablonkontextusban: bármely auto&& deklaráció a kezdőkifejezés értékkategóriájától függően lvalue vagy rvalue referencia lesz. Ez a szabály analóg a sablonparaméter T&& dedukciójával. Egy auto&& nevű változó neve viszont lvalue, ezért továbbításhoz külön std::forward vagy std::move kell.

Külön figyelmet érdemel a kapcsos zárójeles inicializálás: másolásos listainicializálásnál (auto x = {...}) az auto mindig std::initializer_list-et dedukál; ehhez a lista minden elemének azonos típusúnak kell lennie, különben a program hibás:

auto x = {1, 2, 3};   // std::initializer_list<int>
auto y{1};            // int (N3922; DR-ként a C++11/14 módokban is), a régi szabály szerint initializer_list<int> lett volna

Az N3922 szerint (a C++17 óta, DR-ként a modern fordítók korábbi módjaiban is) a közvetlen listainicializálás (auto y{1}) egyelemű listánál értéktípusú, míg a másolásos (auto y = {1}) továbbra is initializer_list. A korábbi szabály szerint auto y{1} is initializer_list<int> volt, nem „ambiguous”. Ez a különbség gyakori buktató, ezért érdemes az auto mellett mindig egyértelmű zárójelezést használni, vagy explicit típust adni, ha a kifejezés listainicializált.

Az auto használható függvény visszatérési típusaként is (C++14 óta). Ilyenkor a függvény deklarálható előre (auto f();), de a levezetést igénylő használat helyén a definíciónak már láthatónak kell lennie. A levezetés a visszatérési kifejezés típusát követi a fenti szabályok szerint:

auto make_value() {
    int local = 10;
    return local;          // int
}

auto& make_ref(int& input) {
    return input;          // int&
}

Az érték szerinti auto esetében nem jön létre referencia automatikusan, így a make_value egy másolatot ad. Ha referenciát szeretnénk visszaadni, akkor auto& vagy decltype(auto) szükséges.

5.1.2 decltype és a kifejezés–entitás megkülönböztetés

A decltype nem dedukál, hanem a zárójelben lévő kifejezés vagy entitás deklarált típusát adja vissza. A pontos szemantika attól függ, hogy a zárójelben entitás (például változó név) vagy kifejezés áll.

int x = 0;
decltype(x)    y = 1;   // int
decltype((x))  z = x;   // int&  (a zárójelezett x kifejezés lvalue)

A decltype((x)) esetében a zárójelben lévő kifejezés lvalue, ezért a levezetett típus int&. Ez a szabály gyakran okoz lógó referenciát, ha függvény visszatérési típusában használjuk:

decltype(auto) ref_to_param(int& x) {
    return (x);   // int&  – rendben van, mert x élettartama a hívónál van
}

decltype(auto) dangling() {
    int local = 5;
    return (local);   // int& (C++23-ban az implicit move miatt int&& is lehet) – mindkét esetben lógó referencia, UB!
}

A ref_to_param függvény helyes, mert a visszaadott referencia a hívó által biztosított objektumra mutat. A dangling azonban egy lokális változóra ad referenciát, ami a visszatérés után érvénytelen memóriaterületre mutat. A decltype(auto) használata tehát akkor biztonságos, ha a kifejezés mögött álló entitás élettartama a hívónál biztosított, vagy ha a kifejezés prvalue.

A decltype(auto) az auto-tól eltérően megtartja a cv-minősítést és a referenciát is. Ezért használják gyakran tökéletes továbbítású wrapper függvényekben:

template <typename T>
decltype(auto) forward_value(T&& arg) {
    return std::forward<T>(arg);
}

Itt a visszatérési típus pontosan az lesz, amit a std::forward kifejezés képvisel: lvalue esetén T&, rvalue esetén T&&.

Vigyázat: rvalue argumentumnál a visszaadott T&& a hívó oldali ideiglenesre hivatkozik, amely a hívást tartalmazó teljes kifejezés végén megszűnik; az auto&& r = forward_value(std::string("x")); után r lóg (g++ 15.2, -fsanitize=address mellett stack-use-after-scope). A minta ezért csak akkor biztonságos, ha az eredményt ugyanabban a teljes kifejezésben használjuk fel (például továbbadjuk egy másik függvénynek), vagy ha a wrapper érték szerint ad vissza (std::decay_t<T>).

5.1.3 Structured bindings

A C++17-ben bevezetett structured binding lehetővé teszi, hogy egy összetett objektum tagjait egyetlen deklarációban, nevesített változókba bontsuk. A szintaxis:

auto [a, b, c] = expression;

A mechanizmus egy rejtett, névtelen változót hoz létre, majd a jelölt nevek erre a rejtett objektum megfelelő tagjaira hivatkoznak. Az auto itt is ugyanazt a dedukciós logikát követi, de a referenciák kezelése kiemelt figyelmet igényel.

#include <tuple>
#include <string>
#include <cassert>

std::tuple<int, std::string> make_pair_value() {
    return {7, "hello"};
}

void demo_sb() {
    auto [num, text] = make_pair_value(); // a prvalue-ból a rejtett objektum közvetlenül inicializálódik
    num = 10;                             // a rejtett objektum tagját módosítja
}

A fenti esetben a jobb oldali kifejezés prvalue, ezért a rejtett objektum (C++17-től közbenső másolat nélkül) közvetlenül a visszatérési értékből inicializálódik, és a num, text nevek ennek a tagjaira vonatkoznak; eredeti tuple, amelyet módosítanánk, nincs. Lvalue-ból (auto [a, b] = data;) viszont a rejtett objektum a data másolata. Ha a jobb oldalt referenciaként akarjuk megőrizni, explicit auto& kell:

std::tuple<int, std::string> data{3, "world"};

auto& [n, t] = data;
n = 42;                       // data első eleme is 42 lesz
assert(std::get<0>(data) == 42);

A const auto& változat kiolvasást tesz lehetővé másolás nélkül, de a hivatkozott objektum konstans marad. Az auto&& változat megőrzi az értékkategóriát, ami továbbításhoz hasznos.

A strukturált kötés nem csak std::tuple-re működik, hanem olyan osztályra is, amelynek minden nem statikus adattagja publikus és ugyanabban az osztályban (nem egy ősben vagy részben itt, részben ott) van deklarálva, valamint std::array-re és C-tömbökre; anonim union tagja nem köthető:

struct Point {
    int x;
    double y;
};

Point p{5, 2.5};
auto [px, py] = p;    // int, double – másolatok
px = 7;               // p.x nem változik

A rejtett objektum típusa itt a Point másolata (az auto miatt), így a px és py nevek a másolat tagjaira mutatnak. Ha az eredeti objektumot akarjuk módosítani, auto& [px, py] = p; szükséges.

Fontos korlátozás: a strukturált kötés nem működik tetszőleges osztállyal, például std::vector-ral, mert annak nincs megfelelő get mechanizmusa. A lebontás a tuple_size és a get függvényekkel vagy a publikus adattagokkal történik.

Bitmezőre a strukturált kötés neve is köthető, mert a kötésnevek nem referenciák, hanem a rejtett objektum tagjainak álnevei. Hogy másolat vagy az eredeti módosul-e, azt az auto és az auto& választása dönti el, nem a bitmező jellege:

struct BitFields {
    unsigned int a : 3;
    unsigned int b : 5;
};

void demo_bitfields() {
    BitFields bf{2, 9};
    auto [ba, bb] = bf;    // a rejtett objektum bf másolata; ba, bb típusa unsigned int bitmező
    auto& [ra, rb] = bf;   // a rejtett objektum bf-re hivatkozik
    ra = 1;                // bf.a értékét módosítja
}

A fenti deklarációk érvényesek: az auto [ba, bb] esetén a ba és bb a másolat tagjai, az auto& [ra, rb] esetén ra és rb az eredeti bf bitmezői.

5.1.4 if constexpr: fordítási idejű elágazás

Az if constexpr C++17-ben jelent meg, és lehetővé teszi, hogy a fordítási időben ismert feltétel alapján a nem kiválasztott ág ne kerüljön be a példányosításba. Ez különösen sablonokban hasznos, ahol a típusoktól függően más kódot szeretnénk.

#include <type_traits>

template <typename T>
constexpr T abs_generic(T x) {
    if constexpr (std::is_signed_v<T>) {
        return x < 0 ? -x : x;
    } else {
        return x;
    }
}

Az abs_generic függvény egyetlen forrásszöveggel kezeli az előjeles és előjel nélküli egészeket. Az if constexpr feltételének fordítási időben eldönthetőnek kell lennie, és a feltételhez kapcsolódó ágak közül csak a kiválasztott példányosul. A nem kiválasztott ágban csak a sablonparaméterektől függő (dependens) konstrukciók maradnak ellenőrizetlenül (például egy dependens típuson egy nem létező tag hívása); a nem dependens hibákat a fordító a sablondefiníciónál is diagnosztizálja, és sablonon kívül az eldobott ág is teljesen ellenőrzött. A példa a <string> fejlécet igényli:

template <typename T>
std::string describe(const T& obj) {
    if constexpr (std::is_arithmetic_v<T>) {
        return "number";
    } else if constexpr (requires { obj.size(); }) {
        return "container";
    } else {
        return "unknown";
    }
}

A fenti példában a requires kifejezés segítségével a size() meglétét ellenőrizzük. A C++20 requires a C++17 if constexpr-rel együtt is működik, de az if constexpr önmagában is elég a std::is_* típusjellemzőkkel.

A kiválasztott ág return-je a függvényt rendesen lezárja. Ha egyik ág sem alkalmazható, a példányosítást érdemes else ágba tett static_assert-tel kifejezetten megakadályozni, ahelyett hogy a törzs return nélkül érne véget:

template <typename T>
constexpr T half(T x) {
    if constexpr (std::is_integral_v<T>) {
        return x / 2;
    } else if constexpr (std::is_floating_point_v<T>) {
        return x * 0.5;
    } else {
        static_assert(!std::is_same_v<T, T>, "Unsupported type");
    }
}

A static_assert(!std::is_same_v<T,T>, ...) feltétele a sablonparamétertől függ, ezért a hiba csak akkor jelentkezik, ha a példányosítás ebbe az ágba kerül. A CWG2518 (P2593) a szabványba hibajelentésként (DR) került, és a C++23 szövegében szerepel, de a fordítók korábbi módokban is alkalmazzák (a GCC 13 és újabb a C++17/C++20 módban is). Ennek hatására a sablonban álló static_assert(false) is csak példányosításkor ad hibát, a feltételnek nem kell dependensnek lennie. A fenti dependens trükk mindenhol működik, ahol a fordító nem alkalmazza a DR-t (például régebbi fordítóknál), ezért hordozható kódban ez a biztonságosabb forma. Nem sablonkörnyezetben a static_assert(false) továbbra is azonnal hibát ad. Az abs_generic fenti példájánál ráadásul az előjeles INT_MIN esetén az -x előjeles túlcsordulás (UB); a signed trait ezt nem oldja meg, ezért a függvénynek előfeltételt kell megadnia vagy más visszatérési típust.

Az if constexpr nem változtatja meg a függvény aláírását, és nem módosítja a túlterhelési szabályokat. Csupán a függvénytörzsnek egy részét szelektíven hagyja ki a példányosításból.

5.1.5 consteval és constinit: azonnali és statikus inicializáció

A C++20 két új kulcsszót hozott a fordítási idejű értékelés szabályozására: a consteval függvényeket és a constinit változókat.

A consteval deklarációjú függvény csak fordítási időben értékelhető ki (azonnali függvény). A constexpr-től eltérően minden hívásának konstans kifejezésnek kell lennie, de az eredménye felhasználható nem constexpr változó inicializálására is.

consteval int square(int x) {
    return x * x;
}

int main() {
    constexpr int a = square(3);        // OK: fordítási idő
    int b = square(4);                  // OK: azonnali hívás konstans argumentummal, az eredmény futásidejű változót is inicializálhat
    // int n = 4; int d = square(n);    // Hiba: az n nem konstans kifejezés
    static constinit int c = square(5); // OK: statikus tárolási idő
    (void)a;
    (void)b;
    (void)c;
}

Lokális, automatikus tárolási idejű változón a constinit nem használható; a main-en belüli példában ezért kell a static (vagy thread_local) kulcsszó. A constinit csak statikus vagy szál-tárolási idejű változó inicializálását rögzíti fordítási időre.

A hívásnak tehát az argumentumok miatt kell konstans kifejezésnek lennie, nem a célváltozó miatt: a square(4) konstans argumentummal egy futásidejű int változót is inicializálhat, a square(n) viszont egy nem konstans n-nel nem fordul le.

A constinit ezzel szemben változóra vonatkozik. A constinit azt garantálja, hogy a változó inicializálása statikus (konstans inicializálás), tehát nem dinamikus inicializációval történik a main előtt. A szabvány nem ír elő fizikai „fordításkor végrehajtást”, csak a dinamikus inicializálás kizárását. A constinit változó nem lesz automatikusan const, tehát futásidőben módosítható:

consteval int compute_config() {
    return 42;
}

constinit int g_config = compute_config(); // statikus inicializálás

int main() {
    g_config = 10;   // OK: a változó nem konstans
}

A constinit használható static vagy thread_local tárolási időtartamú változókra. A leggyakoribb hiba az, ha a constinit-et const-tal keverik: a constinit nem jelenti a változó konstansságát, csupán az inicializálás idejét rögzíti. A constinit és a constexpr ugyanazon deklarációban nem használható együtt (kizárják egymást): a constexpr változó konstans és használható konstans kifejezésben, a constinit változó csak a dinamikus inicializálást zárja ki, de módosítható.

A consteval és a constinit együttesen segít elkerülni a statikus inicializációs sorrend problémáit (static initialization order fiasco), mert a konstans inicializálás a dinamikus inicializálás előtt megtörténik. A constinit az inicializálási sorrend problémáját a kijelölt változóra szünteti meg, a más fordítási egységekben lévő dinamikusan inicializált változók sorrendjét viszont nem rendezi.

5.1.6 Labor: auto- és constexpr-példák elemzése

A labor célja, hogy a fenti eszközöket egyetlen, reprodukálható fordítófutásban vizsgáljuk. Az alábbi deduction_lab.cpp szemlélteti a dedukciós szabályokat, a structured binding-ot, az if constexpr-t és a consteval/constinit-et. A kód önellenőrző static_assert-ekkel és futásidőbeli assert-tel rendelkezik.

// deduction_lab.cpp
#include <type_traits>
#include <tuple>
#include <cassert>
#include <string>

consteval int square(int x) {
    return x * x;
}

template <typename T>
constexpr T abs_generic(T x) {
    if constexpr (std::is_signed_v<T>) {
        return x < 0 ? -x : x;
    } else {
        return x;
    }
}

struct Point {
    int x;
    double y;
};

constinit int g_config = square(5);   // statikus inicializáció

int main() {
    // auto: a referenciák és kv-minősítők eltűnnek
    int value = 10;
    const int& cref = value;
    auto a = cref;          // int, nem const int&
    auto& b = value;        // int&
    const auto& c = value;  // const int&
    static_assert(std::is_same_v<decltype(a), int>);
    static_assert(std::is_same_v<decltype(b), int&>);
    static_assert(std::is_same_v<decltype(c), const int&>);

    // structured binding: másolat és referencia viselkedése
    Point p{3, 4.5};
    auto [px, py] = p;      // int, double – másolatok
    auto& [rx, ry] = p;     // int&, double& – referenciák
    rx = 7;
    assert(px == 3);        // a másolat nem változik
    assert(p.x == 7);       // az eredeti igen

    // if constexpr: a megfelelő ág kerül példányosításra
    static_assert(abs_generic(-10) == 10);
    static_assert(abs_generic(20u) == 20u);

    // consteval és constinit
    static_assert(square(6) == 36);
    assert(g_config == 25); // square(5) eredménye
    g_config = 100;         // constinit nem konstans
    assert(g_config == 100);

    return 0;
}

A kód lefordításának és futtatásának ajánlott parancssora GCC-vel, C++20 szabvánnyal:

g++ -std=c++20 -O0 -g -Wall -Wextra -pedantic -Werror deduction_lab.cpp -o deduction_lab
./deduction_lab
echo "exit: $?"

A laborban a konkrét környezetben rögzíteni kell a fordítóverziót, az optimalizálási szintet és a standardverziót. Az alábbi táblázat a labor eredményeinek rögzítésére szolgáló mintát mutatja (az értékek illusztrációk):

5.1.7 Összefoglalás és továbbvitt eredmények

Az auto és a decltype segítségével a típusdedukció a kifejezések mögött rejlő típusinformációt használja, de a referenciák és a cv-minősítők kezelése tudatos döntést igényel. A decltype((x)) zárójelezési szabálya és a decltype(auto) referenciamegőrző viselkedése gyakori forrása lógó referenciáknak. A structured binding a leképzést rejtett objektumon keresztül végzi, ezért az auto& és const auto& használata nélkül másolatok jönnek létre. Az if constexpr a sablonoknál egyes utasításokat kizár a példányosításból, a consteval és a constinit pedig a fordítási idejű kiértékelést és a statikus inicializálást szabályozza.

Ezek az eszközök alapozzák meg a következő fejezetek (5.2 modulok, 5.3 ranges, 5.4 kényelmi eszközök) hatékony használatát: a modulok interfészén az auto és a structured binding csökkenti a felesleges típusismétlést, az if constexpr a generic kódokban szelektál, a consteval/constinit pedig a fordítási idejű konfigurációkat ellenőrzi.

5.1.8 Önellenőrző kérdés

Adott az alábbi kódrészlet:

int x = 5;
decltype(auto) f() {
    return (x);
}

int main() {
    auto y = f();
    auto& z = f();
}

Milyen típusú y és z? Mi történik, ha az f egy lokális változóra alkalmazná ugyanezt a zárójelezést? Válaszát indokolja a decltype entitás–kifejezés szabálya alapján.

Megoldásvázlat: f visszatérési típusa int&, mert a return (x); kifejezés lvalue, és a decltype(auto) ezt referenciaként őrzi meg. Az auto y = f(); esetén az auto nem tart meg referenciát, így y típusa int, értéke az x másolata. Az auto& z = f(); esetén z típusa int&, ami x-re hivatkozik. Ha az f egy lokális változóra mutatna referenciát, a visszatérés után lógó referencia keletkezne, ami undefined behavior.
