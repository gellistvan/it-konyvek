9.2 Type traits és type manipulation

A fejezet előző részében (9.1) megismerkedtünk a rekurzív sablonok és a metafüggvények alapjaival: a sablonok mint fordítási idejű függvények, amelyek típusokból típusokat vagy értékekből értékeket állítanak elő. Most a C++ szabványos eszköztárának két kulcsterületére összpontosítunk: a típusjellemzőkre (type traits) és a típusátalakításra (type transformation). Ezek a komponensek teszik lehetővé, hogy a metaprogramozás ne csupán elméleti játék legyen, hanem valós, általános kódban is használható, karbantartható absztrakciókat építsünk.

A <type_traits> fejlécben található eszközök alapvető építőkövei a modern C++ sablonkönyvtáraknak, a standard konténerek implementációjától kezdve a felhasználói keretrendszerekig. A célunk most nem pusztán a felsorolásuk, hanem annak megértése, hogyan épülnek fel, hogyan kombinálhatók, és milyen buktatókat kell elkerülni a gyakorlatban.

9.2.1 A típusjellemzők fogalma

A type trait olyan sablon, amely egy vagy több bemeneti típusból fordítási időben információt szolgáltat. Az információ kétféle lehet: érték (például egy logikai érték, hogy a típus integrál típus-e) vagy típus (például a bemeneti típus referenciájának eltávolítása után kapott típus). Ennek megfelelően két nagy családot különböztetünk meg:

  • Értékadó (value) trait-ek – például std::is_integral<T>::value, std::is_pointer<T>::value, std::is_same<T, U>::value. Ezek rendszerint publikus, statikus constexpr value taggel rendelkeznek (C++11 óta static constexpr bool value). A _v változósablonok (std::is_integral_v<T>) a szabványos könyvtárban C++17-től érhetők el (a változósablon nyelvi lehetősége C++14-es), és ezt a ::value írásmódot rövidítik.
  • Típusadó (type) trait-ek – például std::remove_reference<T>::type, std::add_pointer<T>::type, std::conditional<B, T, F>::type. Ezek rendszerint egy publikus, type nevű belső típust definiálnak. A C++14-től itt is vannak _t aliasok: std::remove_reference_t<T>, std::add_pointer_t<T>, std::conditional_t<B, T, F>.

A kettő között átjárás is lehetséges: egy értékadó trait építhet típusadóra (pl. std::is_same_v<std::remove_cv_t<T>, void>), és a detekciós idióma (7.2) egy type tag létezését vizsgálja. A szabványos könyvtárak sok trait-et ugyanakkor fordítói beépített függvénnyel (__is_class(T) és társai) valósítanak meg, mert ezek tisztán nyelvi eszközökkel nem fejezhetők ki; a szabvány csak az interfészt írja elő.

Fontos megérteni, hogy a trait-ek nem módosítják a bemeneti típust – a bemenet változatlan marad, és az eredmény egy új típus vagy érték. Ez a funkcionális programozási paradigma tükröződik a metaprogramozásban: a típusokkal végzett műveletek tiszták, mellékhatásmentesek.

9.2.1.1 Példa: std::is_integral

A std::is_integral<T> azt vizsgálja, hogy T integrál típus-e. A szabvány a következő típusokat tekinti integrálnak: bool, char, signed char, unsigned char, wchar_t, char8_t (C++20), char16_t, char32_t, short, int, long, long long, ezek unsigned változatai, az implementáció által definiált kiterjesztett egész típusok, valamint mindezek cv-minősített változatai. A trait kifejezetten nem igaz lebegőpontos típusokra, osztálytípusokra, mutatókra vagy enum típusokra (bár a std::underlying_type segítségével az enum alaptípusa vizsgálható).

#include <string>
#include <type_traits>

static_assert(std::is_integral_v<int>);
static_assert(std::is_integral_v<const long>);
static_assert(!std::is_integral_v<float>);
static_assert(!std::is_integral_v<int*>);
static_assert(!std::is_integral_v<std::string>);

A fenti példában a static_assert rávilágít a trait fordítási idejű voltára: ha bármelyik feltétel nem teljesül, a fordítás leáll.

9.2.2 integral_constant: a trait-ek alapja

A szabvány a <type_traits> fejlécben definiálja a std::integral_constant sablont, amely értékeket csomagol be típusba. Ez a metaprogramozás egyik legalapvetőbb építőköve: minden értékadó trait ebből származik, vagy ezzel analóg módon implementálható.

A definíció lényege a következő (egyszerűsítve):

namespace std {
    template<typename T, T v>
    struct integral_constant {
        static constexpr T value = v;
        using value_type = T;
        using type = integral_constant<T, v>;
        constexpr operator T() const noexcept { return v; }
        constexpr T operator()() const noexcept { return v; }
    };
}

Az integral_constant tehát egy olyan típus, amely egy adott értéket típusba emel. Ebből származnak a gyakori specializációk:

template<bool B>
using bool_constant = integral_constant<bool, B>;

using true_type = bool_constant<true>;
using false_type = bool_constant<false>;

Ezekkel a std::true_type és std::false_type típusokkal dolgozunk, amikor egy trait-et definiálunk. Ha például egy osztály specializációjától függ a trait eredménye, akkor a std::true_type-ból vagy std::false_type-ból származtatunk, és a value tag automatikusan öröklődik.

9.2.2.1 Saját trait implementálása integral_constant-tal

Tegyük fel, hogy szeretnénk egy is_void_like trait-et, amely igaz, ha a típus void, const void vagy volatile void. A megvalósítás a következő lehet:

#include <type_traits>

template<typename T>
struct is_void_like : std::false_type {};

template<>
struct is_void_like<void> : std::true_type {};

template<>
struct is_void_like<const void> : std::true_type {};

template<>
struct is_void_like<volatile void> : std::true_type {};

template<>
struct is_void_like<const volatile void> : std::true_type {};

Itt a std::false_type-ból származtatás biztosítja, hogy az alapsablon value tagje false, a std::true_type-ból származtatás pedig true-t ad. A használat:

static_assert(is_void_like<void>::value);
static_assert(is_void_like<const volatile void>::value);
static_assert(!is_void_like<int>::value);

Ez a minta rendkívül gyakori, és a szabványos trait-ek többsége is így épül fel. Fontos megjegyezni, hogy a specializációkban a típust pontosan meg kell adni; a cv-minősítők külön típusokat jelentenek, ezért mind a négy kombinációt fel kell sorolni.

A fenti megoldás azonban redundáns: a std::is_void trait már létezik, és a cv-minősített void típusokra is igaz, így az is_void_like egyszerűen std::is_void. (A típusátalakító és értékadó trait-ek kombinációjára példa: std::is_integral_v<std::remove_cv_t<T>>-szerű összetétel; itt viszont erre nincs szükség.)

9.2.3 enable_if: a fordítási idejű szelekció kulcsa

A std::enable_if (C++11 óta a szabványban, előtte a Boost változata volt használatos) talán a legfontosabb típusmanipulációs eszköz a C++20 előtti metaprogramozásban. A std::enable_if<bool B, typename T = void> sablon úgy van definiálva, hogy ha B == true, akkor rendelkezik egy type taggel, amely a második paraméter (alapértelmezetten void), ha pedig B == false, akkor nincs type tagje. A type tag hiánya SFINAE (Substitution Failure Is Not An Error) környezetben azt eredményezi, hogy a sablonpéldányosítási kísérlet csendben elvetődik, és a fordító más túlterhelést vagy specializációt próbál.

Az enable_if három leggyakoribb használati helye:

  1. Visszatérési típusban, amikor a függvény létezését feltételhez kötjük.
  2. Kiegészítő függvényparaméterben: std::enable_if_t<C>* = nullptr.
  3. Sablonparaméterben, lehetőleg nem típus paraméterként: template<typename T, std::enable_if_t<C, int> = 0>. A template<typename T, typename = std::enable_if_t<C>> alak két túlterhelésnél újradefiniálási hibát ad, mert a default sablonargumentum nem része a szignatúrának; diszjunkt túlterhelésekhez ezért az std::enable_if_t<C, int> = 0 alak kell.

Nézzünk egy példát, amelyben egy print függvényt szeretnénk csak aritmetikai típusokra definiálni:

#include <type_traits>
#include <iostream>

template<typename T>
std::enable_if_t<std::is_arithmetic_v<T>, void>
print_value(T value) {
    std::cout << value << '\n';
}

Itt a visszatérési típus std::enable_if_t<cond, void>; ha a feltétel hamis, a type tag hiányzik, így a visszatérési típus érvénytelen, és a függvény sablonja nem vehető figyelembe (SFINAE). Ez lehetővé teszi, hogy ugyanarra a névre több túlterhelést adjunk, és a feltételek diszjunktak legyenek:

template<typename T>
std::enable_if_t<std::is_integral_v<T>, void>
print_value(T value) {
    std::cout << "Integral: " << value << '\n';
}

template<typename T>
std::enable_if_t<std::is_floating_point_v<T>, void>
print_value(T value) {
    std::cout << "Floating: " << value << '\n';
}

Figyelem: az első, aritmetikai print_value és az utóbbi két változat egy fordítási egységben túlterhelési kétértelműséget okozna (egy int mindkét enable_if-es sablonnak megfelelne), ezért ezek alternatív bemutatások, nem együtt használandó kód.

C++20-tól a requires klóz és a concept-ek gyakran szebb alternatívát kínálnak, de az enable_if továbbra is jelen van a régebbi kódbázisokban és bizonyos szituációkban pontosabb kontrollt ad.

Fontos, hogy a sikertelen helyettesítés (SFINAE) az adott függvénysablon-specializációt kiveszi a jelöltek közül (lásd a 7.1 alfejezetet); ha így egyetlen jelölt sem marad, fordítási hibát kapunk („no matching function”). A sablon deklarációja természetesen létezik, de az adott híváshoz nem vesz részt a túlterhelés-feloldásban. Ez a mechanizmus az alapja a bonyolultabb metaprogramozási mintáknak is.

9.2.4 std::conditional: típusválasztás fordítási időben

A std::conditional<bool B, typename T, typename F> sablon a klasszikus if-else megfelelője típusok számára. Ha B == true, akkor a type tag a T típus, különben az F típus. Ez a trait gyakran egy típusmanipulációs lánc utolsó lépéseként jelenik meg, amikor a kiválasztott típust kell meghatározni.

Példa: válasszunk a std::vector és a std::list közül attól függően, hogy a típus nagyméretű-e (mondjuk méret > sizeof(void*)):

#include <type_traits>
#include <vector>
#include <list>

template<typename T>
using container_t = std::conditional_t<(sizeof(T) > sizeof(void*)),
                                        std::list<T>,
                                        std::vector<T>>;

struct Big { char data[64]; };

static_assert(std::is_same_v<container_t<int>, std::vector<int>>);
static_assert(std::is_same_v<container_t<Big>, std::list<Big>>);

A példa azonban platformfüggő, mert a sizeof(void*) és a sizeof(T) viszonya változhat. Ezért a static_assert-eket óvatosan kell megfogalmazni; a valóságban a feltételt inkább egyértelmű, platformfüggetlen tulajdonságra alapozzuk. A std::conditional maga tehát determinisztikus, de a bemeneti feltétel lehet platformfüggő – ezt mindig dokumentálni kell.

A std::conditional_t C++14-től érhető el. Régebbi kódban a typename std::conditional<B, T, F>::type formát kell használni.

9.2.5 Típusátalakító trait-ek: remove_*, add_*, decay és társaik

A szabvány számos típusátalakító trait-et definiál, amelyek a bemeneti típusból egy új típust állítanak elő. A leggyakoribbak:

  • Referencia eltávolítása: std::remove_reference<T>::type – ha T referencia, akkor az alaptípust adja; ha nem, akkor T-t.
  • CV-minősítők eltávolítása: std::remove_const<T>::type, std::remove_volatile<T>::type, std::remove_cv<T>::type – a megfelelő minősítőt eltávolítja.
  • Mutató eltávolítása: std::remove_pointer<T>::type – ha T mutató, akkor a pointee típust adja; különben T-t.
  • Extent (tömb méret) eltávolítása: std::remove_extent<T>::type – ha T tömb, akkor az elemtípust adja; különben T-t.
  • Hozzáadó (add_*) változatok: std::add_lvalue_reference<T>::type, std::add_rvalue_reference<T>::type, std::add_pointer<T>::type, std::add_const<T>::type, std::add_volatile<T>::type, std::add_cv<T>::type.
  • decay: a legátfogóbb, a C++ típusátalakítási szabályokat utánozza (referencia, cv-minősítő, tömb->mutató, függvény->mutató).

Ezek kombinálásával bonyolult típusmanipulációkat végezhetünk. Például egy olyan normalize trait, amely eltávolítja a referenciát, a cv-minősítőt és a mutatót, majd hozzáad egy const-ot:

template<typename T>
using const_pointee_t = std::add_const_t<
    std::remove_cv_t<                                   // a mutatott típus cv-je
        std::remove_pointer_t<
            std::remove_cv_t<std::remove_reference_t<T>>>>>; // a mutató cv-je

static_assert(std::is_same_v<const_pointee_t<volatile int* const&>, const int>);

Lépésenként a volatile int* const& típusra: remove_reference_t → volatile int* const; remove_cv_t (a mutató felső szintű minősítője) → volatile int*; remove_pointer_t → volatile int; a második remove_cv_t (a mutatott típus minősítője) → int; add_const_t → const int. Ha a második remove_cv_t kimaradna, az eredmény const volatile int lenne, és az assert hamis volna: az első remove_cv csak a felső szintű (mutató) minősítőt távolítja el. A sorrend is lényeges: a remove_pointer referencián nem hatna, ezért a referenciát előbb kell eltávolítani. Minden lépés egy tiszta transzformáció.

9.2.5.1 std::decay részletesen

A std::decay a C++ szabvány által leírt típusátalakításokat foglalja össze, amelyeket például a függvényhívás argumentumai esetében alkalmaz a fordító (pass-by-value esetén). A std::decay_t<T> a következő lépéseket hajtja végre:

  1. Ha T referencia, a referenciát eltávolítja.
  2. Ha a kapott típus függvénytípus, átalakítja függvénymutatóvá.
  3. Ha a kapott típus tömb, átalakítja az első elemre mutató mutatóvá.
  4. Ha a kapott típus felső szintű cv-minősítőt hordoz, azt eltávolítja.

A std::decay tehát a referenciákat, a tömb- és függvénytípusokat, valamint a felső szintű const/volatile minősítőket is normalizálja. Például:

static_assert(std::is_same_v<std::decay_t<const int&>, int>);
static_assert(std::is_same_v<std::decay_t<int[5]>, int*>);
static_assert(std::is_same_v<std::decay_t<void()>, void(*)()>);

A std::decay gyakori használata: sablonos tárolókban az elem típusának normalizálása, hogy a tároló ne tartalmazzon referenciát vagy tömböt.

template<typename T>
class Holder {
public:
    using value_type = std::decay_t<T>;
    // ...
};

Itt ha a felhasználó Holder<int&>-t ír, akkor a value_type int lesz, ami biztonságos tárolást tesz lehetővé.

9.2.6 Típusjellemzők és típusátalakítások gyakorlati kombinálása

A való életben ritkán használunk önmagában egy trait-et; legtöbbször kombináljuk őket, hogy egy konkrét kérdésre válaszoljunk. Például: „Mi az a típus, amit akkor kapunk, ha egy tároló iterátorából kiolvassuk az elemet, és az elemről levesszük a referenciát és a const-ot?” Erre a std::iterator_traits és a std::remove_cvref_t (C++20 előtt a std::decay_t) együttes használata ad választ.

A szabványos std::iterator_traits<It> segítségével hozzáférhetünk az iterátorhoz tartozó típusokhoz: value_type, reference, pointer, difference_type, iterator_category. Ha az iterátor reference típusa T& vagy const T&, akkor a std::remove_cvref_t (C++20-tól) a decay-nél célzottabb, mert nem végzi el a tömb->mutató átalakítást, csak a referenciát és a cv-minősítőt távolítja el.

#include <iterator>
#include <type_traits>
#include <vector>

template<typename It>
using element_t = std::remove_cvref_t<typename std::iterator_traits<It>::reference>;

static_assert(std::is_same_v<element_t<std::vector<int>::iterator>, int>);
static_assert(std::is_same_v<element_t<std::vector<int>::const_iterator>, int>);

A std::remove_cvref_t C++20-tól érhető el, és kényelmesebb, mint a decay, mert nem befolyásolja a tömböket. Proxy-iterátornál (például std::vector<bool>) a reference proxy típus, ezért az element_t nem a logikai értéktípust adja; ott a std::iter_value_t<It> (C++20) a megfelelő eszköz. Korábbi szabványokban a std::decay_t-t használták, bár az tömböknél mutatót eredményezett. A remove_cvref_t nem „hatékonyabb”, hanem pontosabb, célzottabb: csak a referenciát és a cv-minősítőket távolítja el.

9.2.7 Saját type trait implementálása: labor

A fejezet laborfeladata egy saját type trait megvalósítása és tesztelése. A cél, hogy a tanult eszközöket egy konkrét, ellenőrizhető feladatban alkalmazzuk, és a folyamatot reprodukálható módon dokumentáljuk.

9.2.7.1 Feladat

Implementáljunk egy is_specialization_of nevű trait-et, amely azt vizsgálja, hogy egy adott típus egy adott sablon specializációja-e. Például is_specialization_of_v<std::vector<int>, std::vector> igaz legyen, de is_specialization_of_v<int, std::vector> hamis. A trait-et úgy kell megírni, hogy a sablonparaméterek számától függetlenül működjön (a konténer-sablonoknak gyakran több paraméterük van).

A megvalósítás alapötlete: egy részleges specializációt használunk, ahol a sablonparamétereket a vizsgált sablon paramétereire illesztjük. Egy lehetséges megoldás C++17-es feature-ökkel:

#include <type_traits>
#include <vector>
#include <list>

template<typename T, template<typename...> class Template>
struct is_specialization_of : std::false_type {};

template<template<typename...> class Template, typename... Args>
struct is_specialization_of<Template<Args...>, Template> : std::true_type {};

template<typename T, template<typename...> class Template>
inline constexpr bool is_specialization_of_v = is_specialization_of<T, Template>::value;

// Tesztelés
static_assert(is_specialization_of_v<std::vector<int>, std::vector>);
static_assert(is_specialization_of_v<std::list<float>, std::list>);
static_assert(!is_specialization_of_v<int, std::vector>);
static_assert(!is_specialization_of_v<std::vector<int>, std::list>);

Ez a megoldás azonban nem működik olyan sablonokra, amelyeknek nem típusparaméterük is van (például std::array<int, 5>), mert a template<typename...> class Template deklaráció csak típusparamétereket enged meg. A std::array második paramétere size_t, ami nem típus. Egyetlen sablon-sablon paraméter nem fedi le a vegyes (típus- és nem típus-) paraméterlistájú sablonokat; a szabványban nincsenek univerzális sablonparaméterek, ezért minden „paraméter-alakhoz” (pl. template<typename, auto> class) külön specializáció kell. Az egyszerűség kedvéért a labor a típusparaméteres konténerekre korlátozódik; ezt a korlátozást a dokumentációban fel kell tüntetni.

9.2.7.2 A labor környezete és build

A labor futtatásához a következő környezetet rögzítjük:

  • Fordító: GCC 13.2 (a teljes verziót a naplóban rögzíteni kell; Clang és MSVC esetén a platformeltéréseket jelezni kell).
  • Szabvány: C++20 (-std=c++20).
  • Build parancs:
g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -o type_traits_lab type_traits_lab.cpp
  • Tesztek: A teszteseteket static_assert-ekkel és futásidejű ellenőrzésekkel is végezzük. A futásidejű ellenőrzéseknél a std::cout-tal kiírjuk a várt és a kapott értékeket.

A type_traits_lab.cpp tartalma:

#include <type_traits>
#include <iostream>
#include <vector>
#include <list>

// ---- Saját trait ----
template<typename T, template<typename...> class Template>
struct is_specialization_of : std::false_type {};

template<template<typename...> class Template, typename... Args>
struct is_specialization_of<Template<Args...>, Template> : std::true_type {};

template<typename T, template<typename...> class Template>
inline constexpr bool is_specialization_of_v = is_specialization_of<T, Template>::value;

// ---- Fordítási idejű tesztek ----
static_assert(is_specialization_of_v<std::vector<int>, std::vector>);
static_assert(is_specialization_of_v<std::list<float>, std::list>);
static_assert(!is_specialization_of_v<int, std::vector>);
static_assert(!is_specialization_of_v<std::vector<int>, std::list>);

// ---- Futásidejű kiírás ----
int main() {
    std::cout << std::boolalpha;
    std::cout << "is_specialization_of_v<std::vector<int>, std::vector>: "
              << is_specialization_of_v<std::vector<int>, std::vector> << " (expected: true)\n";
    std::cout << "is_specialization_of_v<std::list<float>, std::list>: "
              << is_specialization_of_v<std::list<float>, std::list> << " (expected: true)\n";
    std::cout << "is_specialization_of_v<int, std::vector>: "
              << is_specialization_of_v<int, std::vector> << " (expected: false)\n";
    std::cout << "is_specialization_of_v<std::vector<int>, std::list>: "
              << is_specialization_of_v<std::vector<int>, std::list> << " (expected: false)\n";
}

A fordítást és futtatást követően a kimenetnek a várt értékeket kell mutatnia. A mérési naplóban rögzítjük:

  • Fordítási idő: a time parancs kimenete (<mért>; a példa nem közöl mért értéket).
  • Bináris méret: size parancs kimenete (<mért>).
  • Futási idő: a program futási ideje elhanyagolható, de a time parancsot itt is lefuttatjuk a teljesség kedvéért (<mért>).
  • Várt eredmény: minden kiírt sorban a várt logikai érték.
  • Mért eredmény: a program által kiírt érték.

A mérési naplóban a fenti adatokat táblázatba foglaljuk, és a várt és mért értékeket külön oszlopban tüntetjük fel.

9.2.7.3 Labor kiterjesztés: hibák kezelése

A labor része a tipikus hibák azonosítása is. Az 1–2. eset lefordul, de csendben false-t ad – ezeket static_assert(!...)-tel rögzítsük, majd mutassuk be a javított hívást (is_specialization_of_v<std::remove_cvref_t<T>, std::vector>). A 3. eset már a sablon-sablon argumentum illesztésénél fordítási hibát ad (type/value mismatch), ezért azt kommentben vagy külön, várhatóan hibásan forduló fájlban mutassuk be.

  1. Referencia típus átadása: is_specialization_of_v<std::vector<int>&, std::vector> – a trait false-t ad, mert a részleges specializáció a referenciatípusra nem illeszkedik. A helyes megoldás: előbb std::remove_reference_t-t alkalmazni.
  2. CV-minősített konténer: std::vector<int> const – szintén nem illik, mert a Template<Args...> minta nem fogadja el a const-ot. Megoldás: std::remove_cv_t.
  3. Nem típusparaméteres sablonok: std::array<int, 5> nem illik a template<typename...> class Template mintára: a fordítás hibával leáll, nem false lesz az eredmény. Ez a korlátozás az implementációból fakad.

Ezeket a hibákat a labor dokumentációjában ismertetjük, és bemutatjuk a javítási módokat.

9.2.8 Tipikus hibák és elkerülésük

A type trait-ekkel való munka során több gyakori hibát érdemes megemlíteni:

9.2.8.1 A cv-minősítők elhanyagolása

Amikor egy trait-et definiálunk, a specializációkban pontosan meg kell adni a cv-minősített változatokat, vagy az összeset lefedő technikát kell alkalmazni. Ha például egy is_void_like trait-et csak a void és a const void specializációkkal írunk meg, akkor a volatile void és a const volatile void esetén hamis értéket ad. (Egy is_const<const T> részleges specializáció ezzel szemben a const volatile int-re is illeszkedik, T = volatile int mellett.) A szabványos trait-ek a cv-minősítőket helyesen kezelik, ezért a saját trait-eknél is ügyelni kell a teljes lefedettségre.

9.2.8.2 A referenciák figyelmen kívül hagyása

A referenciák nem ugyanazok, mint az alaptípus. Egy is_integral-hoz hasonló trait-nek explicit módon kell kezelnie a referencia kvalifikációkat, mert a int& nem integrál típus. A szabványos std::is_integral a cv-minősítőket figyelmen kívül hagyja (std::is_integral_v<const int> igaz), de a referenciát nem távolítja el: std::is_integral_v<const int&> hamis. Ha a saját trait-nek referencia-átlátszónak kell lennie, a bemenetet előbb normalizálni kell (pl. std::remove_cvref_t), hacsak a kérdés nem kifejezetten a referenciára vagy a minősítőre vonatkozik.

9.2.8.3 A std::conditional mindkét ág kiértékelődik

A std::conditional csak kiválaszt egy típust, de a típuskifejezés mindkét ágát ki kell értékelni, mielőtt a conditional sablonargumentumként megkapja: mindkét argumentumnak érvényes típusnak kell lennie (a std::conditional maga nem példányosítja az ágak osztálysablon-törzsét, a hiányos típus is lehet argumentum). Ezért ha valamelyik ág érvénytelen típuskifejezést tartalmaz (például typename T::type, ahol T::type nem létezik), a fordítás akkor is hibát ad, ha a feltétel hamis. Például:

template<bool B>
struct Example {
    using type = std::conditional_t<B, int, void*>; // mindkét típus érvényes
};

// Hibás, ha T-nek nincs ::type tagja: a typename T::type akkor is kiértékelődik,
// ha B == false (kényszerített helyettesítés).
// template<bool B, typename T>
// using bad_t = std::conditional_t<B, typename T::type, int>;

Ilyenkor, ha az ág csak feltételesen érvényes, a lusta kiértékelésű technikákat (pl. specializáció vagy void_t) kell alkalmazni.

9.2.8.4 A void_t és a detekciós idióma félreértése

A std::void_t (C++17) egy hasznos eszköz arra, hogy egy típuson belül megvizsgáljuk bizonyos tagok létezését. Gyakori hiba azonban, hogy a void_t-t olyan kontextusban használják, ahol a vizsgált kifejezés nem SFINAE-kompatibilis, vagy a void_t argumentumai között olyan típus szerepel, amely nem instanciálható. A detekciós idióma részletes tárgyalása a 7.2 alfejezetben található.

9.2.8.5 A std::enable_if túlzott használata

Bár az enable_if erőteljes, a C++20 requires klózzal és concept-ekkel sok esetben olvashatóbb és jobb hibaüzeneteket adó megoldás érhető el. A régi kódbázisokban azonban még gyakori, és a megértése elengedhetetlen a karbantartáshoz.

9.2.9 Típusmanipuláció modern eszközökkel: std::type_identity

C++20-ban bevezették a std::type_identity trait-et, amelynek type tagje maga a bemeneti típus, minden módosítás nélkül. Első ránézésre haszontalannak tűnik, de fontos szerepe van a sablonargumentum-dedukcióban. Ha egy függvénysablon paraméterét std::type_identity_t<T>-ként (vagy typename std::type_identity<T>::type-ként) deklaráljuk, akkor a dedukció nem tudja a T-t a függvény argumentumából kikövetkeztetni, így a T-t a többi argumentumból vagy explicit módon kell megadni. A paraméter kizárása a dedukcióból épp engedi az implicit konverziót az explicit vagy másik argumentumból dedukált T-re (lásd az alábbi process<int>(3.14) példát); hasznos, ha a dedukciót szándékosan egy másik argumentumra akarjuk korlátozni.

#include <type_traits>
#include <vector>

template<typename T>
void process(std::type_identity_t<T> value) { (void)value; }

process<int>(3.14); // int-et vár, a double konvertálódik
// process(3.14); // hiba: T nem dedukálható

Ez a technika például olyan függvényeknél hasznos, amelyek egy másik argumentumból dedukált típust akarnak használni, és a többi argumentumot arra konvertálják:

template<typename T>
void fill_with(std::vector<T>& v, std::type_identity_t<T> x) {
    v.assign(v.size(), x);
}

// std::vector<double> d(3);
// fill_with(d, 1); // T = double a vektorból, az 1 double-lé konvertálódik

9.2.10 Összefoglalás

A típusjellemzők és a típusátalakítások a C++ metaprogramozás alapvető építőkövei. A szabványos <type_traits> fejléc számos kész eszközt kínál, amelyekre saját trait-eket építhetünk. A kulcsfogalmak:

  • Az értékadó trait-ek (is_*, is_same, is_convertible stb.) bool értéket szolgáltatnak, gyakran static constexpr bool value formában.
  • A típusadó trait-ek (remove_*, add_*, conditional, decay) új típusokat állítanak elő.
  • Az integral_constant, true_type, false_type az értékek típusba emelésének mechanizmusai.
  • Az enable_if a SFINAE alapú függvénytúlterhelés szelekciót teszi lehetővé.
  • A conditional fordítási idejű típusválasztást végez.
  • A cv-minősítők, referenciák és mutatók kezelése körültekintést igényel; a remove_cvref_t és a decay_t gyakori normalizáló eszközök.

A laborfeladat során egy saját is_specialization_of trait-et implementáltunk, és a build, a tesztelés és a mérés folyamatát reprodukálhatóan dokumentáltuk. A tipikus hibák (cv-minősítők elhagyása, referenciák figyelmen kívül hagyása, a conditional mindkét ágának kiértékelése) ismerete elengedhetetlen a megbízható metaprogramozáshoz.

9.2.11 Önellenőrző kérdés

Adott a következő kódrészlet:

template<typename T>
void foo(T&& t) {
    using U = std::remove_reference_t<T>;
    using V = std::conditional_t<std::is_const_v<U>, U, const U>;
    // ...
}

Magyarázza el, mi lesz a V típus, ha a foo függvényt a következőképpen hívják: int x = 5; foo(x); foo(std::move(x)); foo(3.14);. Hogyan változna az eredmény, ha std::decay_t-t használnánk a remove_reference_t helyett? Válaszát indokolja a referenciakollapszus szabályaival és a típusátalakítások sorrendjével.

Rövid válaszkulcs: foo(x) esetén T = int&, U = int, V = const int; foo(std::move(x)) esetén T = int, U = int, V = const int; foo(3.14) esetén T = double, U = double, V = const double. A std::decay_t ezekben az esetekben ugyanezt adná. U-ban a felső szintű cv-nél eltérés van (a decay eltávolítja), de V-ben const argumentumnál nem (a conditional visszateszi a const-ot); V-ben a volatile (pl. const volatile int → const volatile int a remove_reference_t-vel, de const int a decay_t-vel) és a tömb/függvény (pl. int[3] → const int[3] helyett int* const) esetén látszik különbség.

9.2.12 Teszteset

Az alábbi teszteset a fejezet laborjának automatikus ellenőrzésére szolgál: a labor is_specialization_of trait-jét (a type_traits_lab.cpp definícióját, vagy fejlécbe kiemelve #include "type_traits_lab.hpp") ellenőrzi, kiegészítésként a 9.2.5 típusátalakításait. Fordítsa le C++20 módban (-std=c++20) és futtassa. A program semmit nem ír ki: a siker feltétele, hogy hiba nélkül lefordul (a static_assert-ek mind teljesülnek), és a kilépési kód 0.

#include <type_traits>
#include <vector>

// A labor trait-je (a type_traits_lab.cpp-ből átvéve)
template<typename T, template<typename...> class Template>
struct is_specialization_of : std::false_type {};

template<template<typename...> class Template, typename... Args>
struct is_specialization_of<Template<Args...>, Template> : std::true_type {};

template<typename T, template<typename...> class Template>
inline constexpr bool is_specialization_of_v = is_specialization_of<T, Template>::value;

static_assert(is_specialization_of_v<std::vector<int>, std::vector>);
static_assert(!is_specialization_of_v<int, std::vector>);
static_assert(!is_specialization_of_v<std::vector<int>&, std::vector>);
static_assert(is_specialization_of_v<std::remove_cvref_t<const std::vector<int>&>, std::vector>);

// Kiegészítő teszt: a 9.2.5 típusátalakításai
template<typename T>
using normalized_t = std::remove_cv_t<std::remove_reference_t<T>>;

static_assert(std::is_same_v<normalized_t<const int&>, int>);
static_assert(std::is_same_v<normalized_t<volatile double&&>, double>);
static_assert(std::is_same_v<normalized_t<int* const&>, int*>);

int main() {}

A tesztet a labor mérési naplójában rögzítjük, a fordítóverzióval, a fordítási kapcsolókkal és a futási eredménnyel együtt.
