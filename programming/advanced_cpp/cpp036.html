10.3 Mixin-ek és policy-based design

A policy-based design a C++ sablonmeta-programozás egyik legfontosabb építőköve: olyan osztálysablonok tervezését jelenti, amelyek viselkedését kis, független „politika” osztályokkal paraméterezzük. A technika szorosan kapcsolódik a keverékosztályok (mixin) fogalmához, és a gyakorlatban a statikus polimorfizmus egyik leghatékonyabb formája. Ebben az alfejezetben a politikák és a kompozíció sablonokkal történő megvalósítását, a policy class és host class szerepét, valamint a testreszabhatóság és a kódduplikáció közötti egyensúlyt vizsgáljuk. A cél, hogy az olvasó képes legyen saját, policy-alapú osztályt tervezni, felismerni a tipikus hibákat, és megindokolni, mikor érdemes ezt a megoldást választani a virtuális függvényekkel szemben.

10.3.1 A politika fogalma: policy class

A policy-based design alapgondolata, hogy egy osztály viselkedésének bizonyos aspektusait – például a memóriafelszabadítás módját, a zárolási mechanizmust, a naplózási csatornát vagy a növekedési stratégiát – külön osztályokba szervezzük ki. Ezeket az osztályokat policy class-oknak nevezzük. Egy policy class jellemzően nem tartalmaz adattagot, vagy csak minimális állapotot; a lényege az interfész, amelyet a host class elvár. A policy class nem virtuális függvényekkel dolgozik, hanem statikus, fordítási időben ismert interfésszel. Ez lehetővé teszi a fordító számára az inline-olást és az agresszív optimalizálást.

A policy class gyakran egyszerű struktúra vagy osztály, például:

#include <mutex>

struct NoLock {
    void lock() {}
    void unlock() {}
};

struct MutexLock {
    std::mutex m;
    void lock() { m.lock(); }
    void unlock() { m.unlock(); }
};

Mindkét osztály ugyanazt a két tagfüggvényt (lock, unlock) biztosítja, de eltérő módon. Ez a közös felület az, amit a host class a sablonparaméterként kapott politikától elvár.

10.3.2 A host class

A host class az az osztálysablon, amely a politikákat felhasználja. A politikákat általában sablonparaméterként adjuk át, és a host class vagy örökli őket, vagy tartalmazza őket. Az örökléses megközelítés gyakori, mert így a politika tagfüggvényei közvetlenül elérhetők a host class-on belül, és a fordító üres alaposztály-optimalizálást (EBO, empty base optimization) alkalmazhat, ha a politika nem tartalmaz adattagot.

A felszabadítási politika közönséges (nem sablon) típus, sablonos release taggal, így egyetlen alakban használható mindenhol, a laborban is:

struct DeleteRelease {
    template<typename T>
    void release(T* p) noexcept { delete p; }
};

Példa egy egyszerű host class-ra, amely egy erőforrás zárolását és felszabadítását politizálja (fordító: GCC, -std=c++20; a teljes, fordítható változat a laborban van):

template<typename T,
         typename LockPolicy = NoLock,
         typename ReleasePolicy = DeleteRelease>
class Resource : private LockPolicy, private ReleasePolicy {
    T* ptr = nullptr;
    LockPolicy& lock_policy() noexcept { return *this; }
public:
    explicit Resource(T* p) : ptr(p) {}

    ~Resource() {
        std::lock_guard<LockPolicy> g(lock_policy());   // RAII: kivételnél is unlock
        this->release(ptr);                             // szerződés: nem dob
    }

    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;

    // A tulajdon és a ReleasePolicy állapota együtt mozog; a LockPolicy
    // (pl. mutex) nem mozgatható, az új objektum saját zárat kap.
    // Előfeltétel: az `other` objektumot közben senki nem használja.
    Resource(Resource&& other) noexcept(std::is_nothrow_move_constructible_v<ReleasePolicy>)
        : LockPolicy(),
          ReleasePolicy(std::move(static_cast<ReleasePolicy&>(other))),
          ptr(std::exchange(other.ptr, nullptr)) {}

    Resource& operator=(Resource&& other) noexcept(std::is_nothrow_move_assignable_v<ReleasePolicy>) {
        if (this != &other) {
            std::lock_guard<LockPolicy> g(lock_policy());
            this->release(ptr);   // a régi mutatót a régi politikával szabadítjuk fel
            static_cast<ReleasePolicy&>(*this) = std::move(static_cast<ReleasePolicy&>(other));
            ptr = std::exchange(other.ptr, nullptr);
        }
        return *this;
    }

    T* get() const { return ptr; }   // zár nélkül olvas: lásd a szálbiztonsági megjegyzést

    void reset(T* p = nullptr) {
        std::lock_guard<LockPolicy> g(lock_policy());
        if (p == ptr) return;        // reset(get()) ne szabadítsa fel a saját mutatóját
        this->release(std::exchange(ptr, p));
    }
};

Ebben a példában a LockPolicy és a ReleasePolicy a két politika. A host class privát módon örökli őket, mert a politika nem része a publikus interfésznek; az öröklés pusztán implementációs eszköz. A this->release(...) hívás azért szükséges, mert a release név a függő ReleasePolicy alaposztályból származik, és a kétszakaszos névfeloldás miatt explicit minősítést igényel (vagy using ReleasePolicy::release; deklarációt). A zárpolitikát a lock_policy() segédfüggvény adja át a std::lock_guard-nak.

A ReleasePolicy közönséges típusparaméter (typename), nem sablon-sablon paraméter: egy már teljes típust kap (itt DeleteRelease), amelynek release tagja függvénysablon, így a kezelt típust a híváskor ismeri meg. Ha mégis osztálysablont akarnánk átadni (például DeleteRelease<T>), sablon-sablon paraméter (template<typename> class) kellene; a könyv egységesen az előbbi alakot használja.

Néhány tervezési döntés a példában:

  • Zárkezelés RAII-vel: a kézi lock()…unlock() pár kivételnél elmaradhatna az unlock; ezért std::lock_guard<LockPolicy> védi a szakaszokat (a LockPolicy BasicLockable: lock/unlock).
  • Mozgatás: a mutatóval együtt a ReleasePolicy állapota is átkerül (különben egy állapotos politika, például egy egyedi deleter, az átvett mutatót rossz módon szabadítaná fel). A LockPolicy (pl. mutex) nem mozgatható, az új objektum saját zárat kap; a mozgató műveletek noexcept-je csak a ReleasePolicy mozgatására épül. A zár lock()-ja dobhat (a std::mutex::lock std::system_error-t dobhat), ezért a noexcept csak NoLock-nál indokolt; mutexes politikánál a dobás std::terminate-et okozna – ezt a példa tudatosan vállalja (szigorúbb változatban a specifikáció && noexcept(std::declval<LockPolicy&>().lock()) taggal bővíthető, ha a politika lock()-ját noexcept-nek jelöljük).
  • Felszabadítási szerződés: a release nem dobhat (destruktorból hívódik); különben std::terminate a következmény. Az reset(get()) önreset ellen védett (p == ptr), különben a felszabadított mutató kerülne vissza (dupla delete).
  • Szálbiztonság: a zár csak a reset, a destruktor és az értékadás szakaszát védi. A get() zár nélkül olvas, és a visszaadott nyers mutató a zár elengedése után sem védett; a mozgató konstruktor feltételezi, hogy a forrás közben nem használt. Egy tagmutex tehát nem teszi a teljes felületet szálbiztossá: a hozzáférést külső szinkronizációval, vagy zár alatt futó hozzáférési API-val kell rendezni, és a megsemmisítéssel versengő használatot az életciklus-tervnek kizárnia kell.

10.3.3 Politikák és kompozíció sablonokkal

A policy-based designban a politika és a host class viszonya nem klasszikus „is-a” kapcsolat, hanem inkább „implementáció része” viszony. A privát öröklés ezt jól kifejezi: a host class nem válik a politika altípusává, csupán újrahasznosítja annak kódját.

A mixin kifejezés olyan osztálysablonra utal, amelyet kifejezetten arra terveztek, hogy más osztályok alaposztályaként szolgáljon, és további funkcionalitást adjon hozzá. A policy class gyakran mixin-ként viselkedik: a host class „összekeveri” magában a kiválasztott politikákat. A mixin-ek többnyire nem a fő absztrakciót alkotják, hanem keresztmetszeti viselkedést adnak hozzá, mint például a naplózás, a szinkronizáció vagy az objektumszámlálás.

A kompozíció sablonokkal tehát azt jelenti, hogy a host class nem egyetlen nagy, minden funkciót magában foglaló osztály, hanem kisebb, cserélhető építőelemekből áll össze. Ez a tervezési elv nagyban csökkenti a kódduplikációt, mert ugyanaz a host class sokféle konfigurációban újrahasznosítható.

10.3.4 Több politika kombinálása

Egy host class egynél több politikát is fogadhat. A sorrendnek általában nincs hatása, de ha a politikák közötti függőség van, akkor a sorrendet dokumentálni kell. Például:

template<typename T,
         typename LockPolicy = NoLock,
         typename AllocPolicy = std::allocator<T>>
class SafeContainer : private LockPolicy, private AllocPolicy {
    // ...
};

Itt a LockPolicy a szálbiztonságért, az AllocPolicy a memóriafoglalásért felel. A host class mindkettőt örökli, és a műveletek során megfelelően hívja őket. A politika interfészét a host class feltételezi: a LockPolicy-nak lock()/unlock(), az AllocPolicy-nak allocate()/deallocate() tagfüggvényekkel kell rendelkeznie. Ezt az elvárást C++20-ban concept-ekkel is kifejezhetjük, ami javítja a hibaüzeneteket.

10.3.5 Testreszabhatóság és kódduplikáció

A policy-based design elsődleges előnye, hogy a testreszabhatóságot úgy biztosítja, hogy közben minimálisra csökkenti a kódduplikációt. Gondoljunk egy olyan konténerre, amelynek több viselkedési dimenziója van: növekedési stratégia, szálbiztonság, memóriaforrás. Ha minden kombinációhoz külön osztályt írnánk, a kód robbanásszerűen nőne. Ehelyett a host class-t egyszer megírjuk, és a politikák cseréjével állítjuk elő a kívánt változatokat.

Példa egy Vector osztálysablonra, amely a növekedési politikát és az allokátort paraméterként kapja:

#include <algorithm>
#include <cstddef>
#include <limits>
#include <stdexcept>

constexpr std::size_t kMaxCap = std::numeric_limits<std::size_t>::max() / 2;

struct ExponentialGrowth {
    std::size_t next_capacity(std::size_t current, std::size_t required) const {
        if (required > kMaxCap) throw std::length_error("kapacitás túl nagy");
        std::size_t cap = current ? current : 1;
        // a duplázás nem csordulhat túl: a határ előtt megállunk
        while (cap < required) cap = (cap > kMaxCap / 2) ? kMaxCap : cap * 2;
        return cap;
    }
};

struct FixedGrowth {
    std::size_t increment = 16;
    std::size_t next_capacity(std::size_t current, std::size_t required) const {
        if (required > kMaxCap) throw std::length_error("kapacitás túl nagy");
        std::size_t grown = (current > kMaxCap - increment) ? kMaxCap : current + increment;
        return std::max(required, grown);   // monoton: legalább `required`
    }
};

template<typename T,
         typename GrowthPolicy = ExponentialGrowth,
         typename Alloc = std::allocator<T>>
class Vector : private GrowthPolicy, private Alloc {
    T* data_ = nullptr;
    size_t size_ = 0;
    size_t capacity_ = 0;
public:
    // ...
    void push_back(const T& value) {
        // előfeltétel: size_ < kMaxCap (a size_ + 1 nem csordul túl)
        if (size_ == capacity_) {
            size_t new_cap = this->next_capacity(capacity_, size_ + 1);
            reserve(new_cap);
        }
        // ...
    }
};

A kapacitásszámítás túlcsordulás-védett: a határértéknél std::length_error keletkezik, a növekedés pedig monoton marad. Ebben a példában a Vector osztály kódja egyszer íródik meg, de a GrowthPolicy cseréjével exponenciális vagy lineáris növekedést kapunk. A FixedGrowth politikának ráadásul van egy adattagja (increment), amelyet a host class örököl, és így az objektum méretéhez hozzájárul. Az üres ExponentialGrowth esetén az EBO miatt nem nő a méret.

A politika-alapú megközelítés a virtuális függvényekkel szemben a következő előnyöket kínálja:

  • Nincs futásidejű indirekció: a politika tagfüggvényeit a fordító általában be tudja inline-olni, mert a konkrét típus fordítási időben ismert.
  • Nincs vtable költség: az objektum nem tartalmaz vtable-mutatót, és a hívás nem igényel dinamikus diszpécselést.
  • Jobb optimalizálhatóság: a statikus kötés lehetővé teszi a konstans propagációt, a hurokfelgöngyölítést és más optimalizációkat.
  • Rugalmasabb interfész: a politika nem kényszerül közös absztrakt alaposztályba, így szabadon definiálhat extra tagfüggvényeket, amelyeket a host class kihasználhat.

Ugyanakkor vannak hátrányai is:

  • Fordítási idő: minden politika-kombináció külön példányosítást eredményez, ami növeli a fordítási időt és a bináris méretet.
  • Hibaüzenetek: ha a politika nem teljesíti az elvárt interfészt, a hibák a sablonpéldányosítás mélyén jelentkeznek, és hosszú, nehezen értelmezhető üzeneteket adnak. C++20 concept-ekkel ez mérsékelhető.
  • Kódméret: a sok példányosítás duplikált gépi kódhoz vezethet, bár ez gyakran elfogadható a futásidejű előnyökért cserébe.

10.3.6 Standard library példák

A C++ szabványkönyvtár több helyen is alkalmazza a policy-based design elvét. A legismertebb példák:

  • std::unique_ptr<T, Deleter>: a felszabadítás politikája a Deleter sablonparaméter. Alapértelmezésben std::default_delete<T>, de tetszőleges hívható objektum vagy függvénymutató is megadható.
  • std::char_traits<CharT>: a karaktertípusok műveleteit (összehasonlítás, másolás, EOF stb.) paraméterezi.
  • std::allocator<T>: a memóriafoglalás politikája, amely a konténerekben cserélhető.
  • std::pmr::polymorphic_allocator<T>: futásidejű memóriaforrást használó allokátor, amely a policy-alapú és a virtuális megközelítés közötti hibrid.

Ezek a példák azt mutatják, hogy a nyelv maga is támaszkodik erre a technikára, és a felhasználói kódban is érdemes követni.

10.3.7 Tipikus hibák és megoldások

10.3.7.1 A politika interfészének be nem tartása

A leggyakoribb hiba, hogy a felhasználó olyan politikát ad meg, amely nem biztosítja a host class által elvárt tagfüggvényeket vagy típusokat. Például a fenti LockPolicy esetén a lock()/unlock() hiánya fordítási hibát okoz, de a hibaüzenet a host class belsejére mutat, ami zavaró lehet. C++20-ban concept-ekkel ezt érdemes megelőzni:

template<typename P>
concept LockPolicyConcept = requires(P p) {
    { p.lock() } -> std::same_as<void>;
    { p.unlock() } -> std::same_as<void>;
};

template<typename T,
         LockPolicyConcept LockPolicy = NoLock,
         typename ReleasePolicy = DeleteRelease>
class Resource { /* ... */ };

Ekkor a hiba a sablonparaméter megadásánál, érthetőbb formában jelenik meg.

10.3.7.2 A politikák közötti nem dokumentált függőség

Ha a politikák állapota vagy interfésze egymástól függ, akkor a sorrend és a konstrukció módja fontos. Például ha egy LockPolicy és egy AllocPolicy közösen használ egy erőforrást, akkor a host class-nak garantálnia kell a megfelelő sorrendű inicializálást és destruálást. Az alaposztályok konstruktorai a bázis-specifikátor lista deklarációs sorrendjében futnak le (class H : private A, private B esetén előbb A, majd B), nem a konstruktor inicializálólistájának és nem a sablonparaméterek sorrendjében; a destruktorok fordított sorrendben. Ha a politikák egymástól függnek, ezt a sorrendet kell dokumentálni és a bázislistában betartani.

10.3.7.3 A túlzott sablonparaméterezés

Bár a policy-based design rugalmas, a túl sok politika bevezetése rontja az olvashatóságot és a karbantarthatóságot. Ha egy osztály öt vagy több politikát igényel, érdemes megfontolni, hogy egyes politikákat összevonjunk, vagy átgondoljuk a tervezést. A politika-szám növekedése exponenciálisan növeli a lehetséges kombinációk számát, ami a tesztelési terhet is növeli.

10.3.7.4 A virtuális függvények indokolatlan elkerülése

A policy-based design nem minden esetben jobb, mint a virtuális függvények. Ha a politikát futásidőben kell cserélni, vagy ha a politika típusa csak dinamikusan ismert (például plugin-eknél), akkor a virtuális függvények vagy a type erasure a megfelelő eszköz. A policy-based design elsősorban akkor előnyös, ha a konkrét típus fordítási időben ismert, és a teljesítmény kritikus.

10.3.8 Labor: policy-based osztály tervezése

Ebben a laborban egy olyan erőforrás-kezelő osztályt tervezünk, amely a zárolási és a felszabadítási politikát sablonparaméterként kapja. A feladat célja, hogy a résztvevő:

  1. Elkészítse a Resource host class-t és a NoLock, MutexLock, DeleteRelease, CustomRelease policy osztályokat.
  2. Megvalósítson egy virtuális függvényes változatot ugyanarra a funkcióra.
  3. Méréssel összehasonlítsa a policy-based megoldást a virtuális változattal (az eredmény nem előre rögzített).
  4. A mérési naplóban elkülönítse a várt és a mért eredményeket.

10.3.8.1 A kód

#include <cassert>
#include <chrono>
#include <iostream>
#include <memory>
#include <mutex>
#include <type_traits>
#include <utility>

// -------- Lock policies --------
struct NoLock {
    void lock() {}
    void unlock() {}
};

struct MutexLock {
    std::mutex m;
    void lock() { m.lock(); }
    void unlock() { m.unlock(); }
};

// -------- Release policies (közönséges típusok, sablonos release taggal) --------
struct DeleteRelease {
    template<typename T>
    void release(T* p) noexcept { delete p; }
};

struct CustomRelease {
    int released = 0;   // állapotos politika: számolja a felszabadításokat
    template<typename T>
    void release(T* p) noexcept {
        ++released;     // példa: egyedi naplózás vagy erőforrás-visszaadás
        delete p;
    }
};

// -------- Host class (policy-based) --------
template<typename T,
         typename LockPolicy = NoLock,
         typename ReleasePolicy = DeleteRelease>
class Resource : private LockPolicy, private ReleasePolicy {
    T* ptr = nullptr;
    LockPolicy& lock_policy() noexcept { return *this; }
public:
    explicit Resource(T* p) : ptr(p) {}

    ~Resource() {
        std::lock_guard<LockPolicy> g(lock_policy());   // RAII: kivételnél is unlock
        this->release(ptr);                             // szerződés: nem dob
    }

    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;

    // A tulajdon és a ReleasePolicy állapota együtt mozog; a LockPolicy
    // (pl. mutex) nem mozgatható, az új objektum saját zárat kap.
    // Előfeltétel: az `other` objektumot közben senki nem használja.
    Resource(Resource&& other) noexcept(std::is_nothrow_move_constructible_v<ReleasePolicy>)
        : LockPolicy(),
          ReleasePolicy(std::move(static_cast<ReleasePolicy&>(other))),
          ptr(std::exchange(other.ptr, nullptr)) {}

    Resource& operator=(Resource&& other) noexcept(std::is_nothrow_move_assignable_v<ReleasePolicy>) {
        if (this != &other) {
            std::lock_guard<LockPolicy> g(lock_policy());
            this->release(ptr);   // a régi mutatót a régi politikával szabadítjuk fel
            static_cast<ReleasePolicy&>(*this) = std::move(static_cast<ReleasePolicy&>(other));
            ptr = std::exchange(other.ptr, nullptr);
        }
        return *this;
    }

    T* get() const { return ptr; }   // zár nélkül olvas: lásd a szálbiztonsági megjegyzést

    const ReleasePolicy& release_policy() const noexcept { return *this; }   // csak a tesztekhez

    void reset(T* p = nullptr) {
        std::lock_guard<LockPolicy> g(lock_policy());
        if (p == ptr) return;        // reset(get()) ne szabadítsa fel a saját mutatóját
        this->release(std::exchange(ptr, p));
    }

    void touch(T v) {                // a mérés tárgya: zár + írás, allokáció nélkül
        std::lock_guard<LockPolicy> g(lock_policy());
        *ptr = v;
    }
};

// -------- Virtuális változat --------
struct NoMutex {
    void lock() {}
    void unlock() {}
};

struct ResourceBase {
    virtual ~ResourceBase() = default;
    virtual void reset(int* p = nullptr) = 0;
    virtual void touch(int v) = 0;
};

template<typename M>
struct VResource final : ResourceBase {
    M m;
    int* ptr;
    explicit VResource(int* p) : ptr(p) {}
    ~VResource() override {
        std::lock_guard<M> g(m);
        delete ptr;
    }
    void reset(int* p = nullptr) override {
        std::lock_guard<M> g(m);
        if (p == ptr) return;
        delete std::exchange(ptr, p);
    }
    void touch(int v) override {
        std::lock_guard<M> g(m);
        *ptr = v;
    }
};

// -------- Benchmark segédfüggvény --------
template<typename F>
double measure(F&& f, int iterations) {
    auto start = std::chrono::steady_clock::now();
    for (int i = 0; i < iterations; ++i) {
        f(i);
    }
    auto end = std::chrono::steady_clock::now();
    std::chrono::duration<double, std::nano> ns = end - start;
    return ns.count() / iterations;   // átlagos ns / művelet
}

int main(int argc, char**) {
    constexpr int N = 1'000'000;

    // 1. Helyesség (az assert-ek nem mérés)
    {
        Resource<int, MutexLock, CustomRelease> r(new int(42));
        assert(*r.get() == 42);
        r.reset(new int(7));
        assert(*r.get() == 7);
        assert(r.release_policy().released == 1);   // a régi 42-es felszabadítva
        r.reset(r.get());                       // önreset: nem szabadít fel
        assert(*r.get() == 7);
        auto r2 = std::move(r);
        assert(r.get() == nullptr && *r2.get() == 7);
        assert(r2.release_policy().released == 1);  // a politika állapota átkerült
    }

    // 2. Policy-based: zár + írás
    {
        Resource<int, MutexLock, DeleteRelease> r(new int(0));
        double avg_ns = measure([&](int i) { r.touch(i); }, N);
        std::cout << "Policy-based touch átlag: " << avg_ns << " ns (utolsó érték " << *r.get() << ")\n";
    }

    // 3. Virtuális: a konkrét típust futásidőben választjuk (argc), így a hívás
    //    bázispointeren, nem devirtualizálható módon történik.
    {
        std::unique_ptr<ResourceBase> rb;
        if (argc > 1) rb = std::make_unique<VResource<NoMutex>>(new int(0));
        else          rb = std::make_unique<VResource<std::mutex>>(new int(0));
        double avg_ns = measure([&](int i) { rb->touch(i); }, N);
        std::cout << "Virtuális touch átlag: " << avg_ns << " ns\n";
    }
    return 0;
}

10.3.8.3 Tesztesetek és elvárt eredmény

A fenti kód hat assert-et tartalmaz, amelyek a helyes működést (köztük az állapotos CustomRelease számlálójának átvitelét) ellenőrzik. Emellett egy egyszerű tesztprogramot is írhatunk, amely a Resource mozgatását, a reset működését és a NoLock/CustomRelease kombinációt is ellenőrzi. Az elvárt eredmény: a program hiba nélkül lefut (érdemes -fsanitize=address,undefined mellett is), az assert-ek nem jeleznek hibát, és a kimenetben két átlagos időérték jelenik meg. A szerző a kódot g++ 15 / -std=c++20 -O2 -Wall -Wextra -pedantic -fsanitize=address,undefined kapcsolókkal lefordította és lefuttatta (a sanitizeres időértékek mérésre nem használhatók, ezért itt nincs közölve). A mérés tárgya a zár + írás (touch), nem az allokáció: a new/delete és a mutex költsége elnyomná a diszpécselés különbségét. A virtuális változatnál a konkrét típust futásidőben választjuk, így a hívás bázispointeren, nem devirtualizálható módon történik; ez a megoldás a final osztály helyi objektumán közvetlenül hívott reset-tel szemben valóban virtuális hívást mér. Mérésre std::chrono::steady_clock szolgál (nem high_resolution_clock).

10.3.8.4 Mérési napló

A mérési naplóban a várt és a mért eredményeket külön kell feltüntetni. A várt eredmény hipotézis, nem előírt eredmény: a policy-based változatnál a hívás statikusan kötött és inline-olható, a virtuális változatnál indirekt hívás van, de a zár (mutex) költsége mindkettőben azonos, és a különbség lehet elhanyagolható is. Gyorsulási arányt nem rögzítünk; azt a mérés dönti el. A policy-based felépítés elsősorban forráskód-újrafelhasználást ad; ettől a gépi kód mérete nem lesz automatikusan kisebb.

Példa a mérési naplóra:

Konfiguráció Várt eredmény (relatív) Mért átlag (ns/műv.) Megjegyzés
Policy-based touch hipotézis: nem lassabb <mért>
Virtuális touch baseline <mért>

A táblázat kitöltendő sablon; ebben a kiadásban nincs benne mért adat. A mért értékeket a futtatás után kell kitölteni. A mérést legalább háromszor érdemes megismételni, és a mediánt vagy az átlagot feltüntetni. A mérési körülményeket (CPU típus, órajel, operációs rendszer, fordító verzió) is rögzíteni kell.

10.3.9 Önellenőrző kérdések

  1. Mi a különbség egy policy class és egy host class között? Milyen kapcsolatban állnak egymással?
  2. Miért alkalmaz a policy-based design jellemzően privát öröklést a politikák beépítésére?
  3. Milyen előnyei vannak a policy-based megoldásnak a virtuális függvényekkel szemben? Milyen hátrányai?
  4. Hogyan segíthetnek a C++20 concept-ek a policy interfészek ellenőrzésében?
  5. Milyen szempontokat érdemes mérlegelni, amikor eldöntjük, hogy policy-based vagy virtuális megoldást választunk?

Megoldásvázlat. (1) A policy class egy viselkedési aspektust ad (interfész, jellemzően állapot nélkül), a host class azt használja fel és kompozíciót/privát öröklést alkalmaz. (2) A politika implementációs eszköz, nem altípus („is-a” helyett „implemented-in-terms-of”), és az EBO miatt üres politika nem nő a méret. (3) Előny: statikus kötés, inline-olhatóság, nincs vptr; hátrány: példányosítási és fordítási költség, nehezebb hibaüzenetek, nincs futásidejű csere. (4) A concept a politika elvárt interfészét a sablonparaméternél ellenőrzi, érthetőbb hibaüzenettel. (5) Fordítási vagy futásidejű választás, bővíthetőség (plugin), kódméret, mérés alapján a tényleges költség.

10.3.10 Összefoglalás

A mixin-ek és a policy-based design a C++ sablonmeta-programozás erőteljes eszközei. Lehetővé teszik, hogy egy osztály viselkedését kisméretű, cserélhető építőelemekkel paraméterezzük, csökkentve a kódduplikációt és javítva a testreszabhatóságot. A politika osztályok statikus interfészt biztosítanak, amelyet a host class használ; a privát öröklés a mixin stílust valósítja meg, és kihasználja az üres alaposztály-optimalizálást. A megközelítés elhagyja a futásidejű indirekciót és lehetővé teszi az inline-olást, ezért gyakran gyorsabb lehet a virtuális függvényeknél, de ezt mérni kell, és növelheti a fordítási időt és a bináris méretet. A gyakorlatban a szabványkönyvtár több komponense is ezt a mintát követi, ami mutatja a technika érettségét és fontosságát. A következő alfejezetben a teljesítményre és a karbantarthatóságra gyakorolt hatásokat vizsgáljuk részletesebben, és összevetjük a policy-based designt más statikus polimorfizmus-technikákkal.
