8.1 Concepts és requires

A sablonparaméterek korlátozása a C++ korai változataiban gyakran vezetett nehezen olvasható, törékeny kódhoz. A std::enable_if, a tag dispatch és a detection idiom egyaránt azt a célt szolgálta, hogy egy sablont csak akkor lehessen példányosítani, ha a paraméterei teljesítik a műveletekhez szükséges feltételeket. Ezek a technikák azonban a hibaüzeneteket hosszú, implementációs részletekkel teli szöveggé duzzasztották, és a szándékot nehezen tették kifejezhetővé. A C++20 bevezette a concepts nyelvi eszközt: olyan névvel ellátott predikátumot, amely fordítási időben eldönti, hogy egy típus vagy típuskombináció kielégít-e egy követelményhalmazt. A concept nem új absztrakciós réteg, hanem a meglévő fordítási idejű ellenőrzések egységes, olvasható és karbantartható kerete.

Ebben a fejezetben a conceptek alapjait, a requires kifejezéseket, a constraint-ek összetételét és a standard concepteket tárgyaljuk. A cél, hogy képes legyél saját követelményrendszert definiálni, alkalmazni és a gyakori hibákat felismerni. A következő egység (8.2) erre építve mutatja be a megszorítások normalizálását, a subsumptiont és a requirement-ek összetételét; a range-ekkel való együttműködés a 8.3 témája.

8.1.1 Concept: névvel ellátott követelmény

A concept formailag egy olyan sablon, amelynek sablonparaméterei vannak (jellemzően típusparaméterek, de nem típusparaméter is lehet), és a törzse egy fordítási idejű logikai kifejezés. Szintaxisa:

template <typename T>
concept Integral = std::is_integral_v<T>;

Itt az Integral névvel ellátott predikátum akkor igaz, ha T egész típus. A jobb oldalnak konstans kifejezésnek kell lennie, amelynek típusa pontosan bool. A leggyakoribb formában egy requires kifejezést vagy más concepteket kombinálunk. Például:

template <typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

Az Addable concept igaz, ha a T típusra létezik az operator+. A requires kifejezés itt a concept jobb oldalán áll, és a törzse a követelmények listája.

A conceptek használhatók:

  • constrained template paraméterként: template<Integral T> void f(T);
  • requires clause-ban: template<typename T> requires Integral<T> void f(T);
  • abbreviated function template-ben (röviden): void f(Integral auto x); – ez a forma ugyanazt jelenti, de a paraméter típusát auto-val jelöljük.
  • static_assert-ben: static_assert(Integral<int>);

Fontos megkülönböztetni a concept definícióját és a concept használatát. A definíció egy logikai predikátumot ad meg; a használat egy constraint-et hoz létre, amely a fordítás során ellenőrzésre kerül.

8.1.2 A requires kifejezések

A requires kulcsszó két, egymástól jól elkülöníthető szerepben jelenik meg:

  1. Requires clause: a sablonparaméterekre vagy függvényekre vonatkozó korlátozás. Például template<typename T> requires std::integral<T> void f(T);.
  2. Requires expression: egy olyan kifejezés, amely adott típusokra nézve követelményeket fogalmaz meg, és bool konstanst ad. Például requires(T a, T b) { a + b; }.

A kettő szintaktikai együttese gyakran requires requires alakot eredményez, ami elsőre zavarba ejtő:

template <typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

template <typename T>
    requires requires(T a, T b) { a + b; }
T add(T a, T b) { return a + b; }

Itt az első requires a függvény requires clause-ja, a második pedig a requires expression kezdete. Bár a requires requires szükséges lehet, ha a constraintet közvetlenül a függvényre írjuk, a gyakorlatban sokkal olvashatóbb, ha először definiálunk egy conceptet, majd azt alkalmazzuk.

A requires expression törzse a következő requirement típusokat tartalmazhatja:

8.1.2.1 Simple requirement

Egy olyan kifejezés, amelynek érvényesnek kell lennie. Nem ad vissza értéket, csak azt ellenőrzi, hogy a kifejezés jól formált-e.

template<typename T>
concept HasFoo = requires(T t) {
    t.foo();            // simple requirement: t.foo() érvényes kell legyen
};

8.1.2.2 Type requirement

Egy típusnév, amelynek léteznie kell. Például egy beágyazott típus vagy alias meglétének ellenőrzése.

template<typename T>
concept HasValueType = requires {
    typename T::value_type;   // T-nek rendelkeznie kell value_type típussal
};

A typename kulcsszó itt nem a típusparaméter bevezetésére szolgál, hanem a type requirement jelölésére.

8.1.2.3 Compound requirement

Egy kifejezésnek nemcsak érvényesnek kell lennie, hanem a visszatérési típusára is vonatkozik megkötés. A szintaxis:

{ expression } -> constraint;

ahol a constraint egy type-constraint, azaz concept-név (például std::convertible_to<U> vagy std::same_as<U>). A -> U rövidítés (tetszőleges típus megadása) a Concepts TS-ben létezett, a C++20 szabványban nem érvényes. A vizsgált típus decltype((expression)), tehát az értékkategóriát is megőrzi, és ez a concept első argumentuma.

template<typename T>
concept Incrementable = requires(T x) {
    { ++x } -> std::same_as<T&>;   // ++x T& típusú kell legyen
    { x++ } -> std::convertible_to<T>; // x++ (prvalue T) konvertálható T-re
};

A -> std::same_as<T&> azt jelenti, hogy a std::same_as<decltype((++x)), T&> teljesül. Hasonlóan a -> std::convertible_to<T> a std::convertible_to<decltype((x++)), T> feltételt ellenőrzi.

8.1.2.4 Nested requirement

Egy további requires kifejezés a törzsön belül, amely egy másodlagos feltételt ad meg.

template<typename T>
concept ContainerOfInt = requires(T c) {
    typename T::value_type;
    requires std::same_as<typename T::value_type, int>;
};

A belső requires egy nested requirement: ha az adott feltétel hamis, az egész requires expression hamis.

A requires expression eredménye egy bool konstans. Ha bármelyik requirement nem teljesül, az egész kifejezés hamis; ha mind teljesül, igaz. A requires expression törzsének kifejezései nem futnak le, csak a jólformáltságukat vizsgálja a fordító. Ha a követelményekben a sablonargumentumok helyettesítése érvénytelen típust vagy kifejezést ad, az eredmény false, és nem fordítási hiba. Ez csak a helyettesítés közvetlen (azonnali) kontextusában álló hibákra igaz: egy másik sablon példányosításából eredő hiba (hard error) fordítási hibát okoz, és az olyan követelmény, amely semmilyen T-re nem lehet érvényes (nem dependens hiba), rosszul formált, nem diagnosztizálandó programot (IFNDR) jelenthet.

8.1.3 Constraint-ek és összetételük

A constraints (korlátozások) olyan logikai kifejezések, amelyeket a fordító a sablonparaméterekre és függvényekre alkalmaz. A legegyszerűbb constraint egy atomic constraint: egy olyan kifejezés, amelyet a normalizálás során már nem lehet tovább bontani, és amelynek típusa pontosan bool (például std::is_integral_v<T>). A concept-id (pl. Integral<T>) nem atomi megszorítás: a normalizáláskor a concept definíciójának normálformájára cserélődik. A megszorításokat a && és || operátorokkal kombinálhatjuk.

Példa:

template<typename T>
concept Numeric = std::integral<T> || std::floating_point<T>;

A Numeric concept igaz, ha T vagy egész, vagy lebegőpontos. A jobb oldalon lévő std::integral<T> és std::floating_point<T> concept-id-k, amelyeket a || köt össze; normalizáláskor a definíciójukban szereplő atomi megszorításokra (pl. std::is_integral_v<T>) bomlanak.

Több concept kombinálható:

template<typename T>
concept OrderedCopyable = std::totally_ordered<T> && std::copyable<T>;

A std::totally_ordered<T> a <, <=, >, >= relációkat követeli meg rendezett módon, és már magában foglalja a std::equality_comparable<T>-t (==, !=); ezért std::equality_comparable<T> && std::totally_ordered<T> kombinálása redundáns lenne, és rossz mintát adna.

A normalizálás során a concept definícióját a fordító a jobb oldalon lévő kifejezésre cseréli, majd a && és || operátorokat atomi szintre bontja. Ez lehetővé teszi a részleges rendezést a conceptek között, de ennek részletei a 8.2 témája.

A requires clause a függvényekre és sablonparaméterekre is alkalmazható. Például:

template<typename T>
    requires Numeric<T>
T square(T x) {
    return x * x;
}

Itt a requires Numeric<T> azt jelenti, hogy a square csak olyan T-re hívható, amelyre Numeric<T> igaz. Ugyanez rövidebben:

template<Numeric T>
T square(T x) {
    return x * x;
}

A constrained template paraméter előnye a rövidebb szintaxis és az, hogy a conceptet közvetlenül a paraméter típusához kötjük.

8.1.4 Standard concepts a <concepts> fejlécben

A C++20 szabványosította a leggyakoribb követelményeket a <concepts> fejlécben. Ezek nem „varázslatos” nyelvi elemek, hanem a szabványkönyvtár által definiált conceptek. A legfontosabb kategóriák:

8.1.4.1 Nyelvi alapok

  • std::same_as<T, U>: T és U pontos típusazonossága; a cv-minősítők és a referenciák is számítanak, tehát std::same_as<int, const int> értéke false.
  • std::derived_from<T, Base>: T publikusan és egyértelműen Base-ből származik (vagy azonos osztály); nem osztálytípusokra (pl. int, int) hamis.
  • std::convertible_to<From, To>: From implicit konvertálható To-ra, és static_cast<To> is érvényes; a szabvány szemantikai feltételeket is előír.
  • std::common_with<T, U>: létezik közös típus, amelyre mindkettő konvertálható, és a közös típusra vonatkozó további feltételek is teljesülnek (nem csupán egy közös típus létezése).
  • std::common_reference_with<T, U>: létezik közös referenciatípus, amelyre mindkettő konvertálható.
  • std::assignable_from<T, U>: a T bal oldali lvalue-referencia típus, és a T = U értékadás érvényes (pl. std::assignable_from<int&, int>).
  • std::swappable<T>: T cserélhető a std::ranges::swap customization point object-tel (nem a qualified std::swap-ra épül).

8.1.4.2 Aritmetikai fogalmak

  • std::integral<T>: egész típus.
  • std::signed_integral<T>: előjeles egész.
  • std::unsigned_integral<T>: előjel nélküli egész.
  • std::floating_point<T>: lebegőpontos típus.

8.1.4.3 Objektumtulajdonságok

  • std::destructible<T>: destruálható objektum; a destruktor nem dobhat kivételt (nothrow).
  • std::constructible_from<T, Args...>: T konstruálható az Args... argumentumokból.
  • std::default_initializable<T>: default konstruálható.
  • std::movable<T>: objektumtípus, mozgatással konstruálható, értékadható (assignable_from<T&, T>) és swappable.
  • std::copyable<T>: másolható objektum (a movable követelményeit is magában foglalja).
  • std::semiregular<T>: másolható és default konstruálható, de nem feltétlenül összehasonlítható ==-gyel.
  • std::regular<T>: semiregular és equality_comparable; olyan típus, amely értékszemantikával viselkedik.

8.1.4.4 Összehasonlítási fogalmak

  • std::equality_comparable<T>: == és != támogatott.
  • std::totally_ordered<T>: a relációs operátorok teljes rendezést adnak.

8.1.4.5 Hívható fogalmak

  • std::invocable<F, Args...>: F hívható Args... argumentumokkal.
  • std::regular_invocable<F, Args...>: szintaktikailag invocable; szemantikailag egyenlőségőrző (azonos argumentumokra azonos eredmény) és nem módosítja az argumentumokat. A szemantikai feltételt a fordító nem ellenőrzi, a concept teljesülése még nem jelenti a modellezést.
  • std::predicate<F, Args...>: regular_invocable és az eredmény bool konvertálható.
  • std::relation<F, T, U>: predicate, amely két azonos vagy különböző típusú argumentumon értelmezett reláció.
  • std::equivalence_relation<F, T, U>: reflexív, szimmetrikus és tranzitív reláció.
  • std::strict_weak_order<F, T, U>: szigorú gyenge rendezést adó reláció.

Ezeket a concepteket gyakran közvetlenül használjuk a saját conceptjeinkben. Például:

template<typename T>
concept Container = requires(T c) {
    typename T::value_type;
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::sentinel_for<decltype(c.begin())>;
} && std::destructible<T>;

Itt a std::input_or_output_iterator és a std::sentinel_for a <iterator> fejlécben definiált concept, amelyet a 15.1 egység (Iterátorkategóriák és hierarchia) részletez. Az end() eredményének elég sentinelnek lennie, nem kell iterátornak. A fenti példa szemlélteti, hogy a standard conceptek építőkövekként szolgálnak a saját, magasabb szintű követelmények megfogalmazásához.

Fontos megjegyezni: a <concepts> fejlécben definiált conceptek C++20 óta érhetők el, és a listájuk a jelenlegi szabvány szerint stabil. Ha egy adott szabványverzióhoz kötött, frissen bevezetett conceptet keresel, mindig ellenőrizd a fordítód dokumentációját és a feature-test makrókat: a nyelvi eszközre (concept/requires) a __cpp_concepts, a <concepts> könyvtári conceptjeire a __cpp_lib_concepts (a <version> fejlécből) vonatkozik.

8.1.5 Gyakorlati minta: saját concept definiálása

Tegyük fel, hogy egy Printable conceptet szeretnénk: olyan típusokat szeretnénk elfogadni, amelyeket egy std::ostream-re ki lehet írni a << operátorral. A definíció:

#include <concepts>
#include <iostream>

template<typename T>
concept Printable = requires(std::ostream& os, const T& x) {
    { os << x } -> std::convertible_to<std::ostream&>;
};

A requires kifejezésben deklaráljuk az os és x változókat. A compound requirement { os << x } -> std::convertible_to<std::ostream&> azt követeli meg, hogy az operator<< hívás eredménye konvertálható legyen std::ostream&-re. Ez a gyakori stream-operátorokra teljesül, mert általában std::ostream&-et adnak vissza.

Alkalmazzuk egy constrained függvényre:

template<Printable T>
void print(const T& value) {
    std::cout << value << '\n';
}

A static_assert segítségével ellenőrizhetjük a conceptet:

static_assert(Printable<int>);
static_assert(Printable<std::string>);
struct NotPrintable {};
static_assert(!Printable<NotPrintable>);

A Printable<int> igaz, mert az int kiírható. Az std::string is. A NotPrintable üres osztályra a concept hamis, mert nincs operator<<.

8.1.6 Tipikus hibák

8.1.6.1 A concept jobb oldalán nem bool kifejezés áll

A concept jobb oldala atomi megszorításként pontosan bool típusú konstans kifejezés kell legyen. A definíció önmagában lefordul; a hiba a concept használatakor lép fel, ha a kifejezés típusa nem bool:

template<typename T>
concept Bad = T::value;  // csak akkor helyes, ha T::value pontosan bool típusú konstans

struct B1 { static constexpr bool value = true; };
struct B2 { static constexpr int value = 1; };
static_assert(Bad<B1>);    // rendben
// static_assert(Bad<B2>); // HIBA: a megszorítás típusa int, nem bool

Előbb a szándékot kell meghatározni: létezzen-e T::value, bool típusú legyen-e, konstans kifejezés legyen-e, és igaz legyen-e az értéke. Ha csak az érték igazságára van szükség, és a típus lehet bármi, ami bool-lá alakítható:

template<typename T>
concept Good = static_cast<bool>(T::value);

Ha a pontos bool típust is meg akarjuk követelni: std::same_as<std::remove_cv_t<decltype(T::value)>, bool> && T::value. (Az a változat, amely a value-t typename T::value típuskövetelményként írná elő, rossz, mert a statikus adattag nem típus.)

8.1.6.2 A requires kifejezés elhagyása, ahol szükséges

Ha közvetlenül a függvény requires clause-jában akarunk kifejezést ellenőrizni, gyakori hiba a belső requires elhagyása:

template<typename T>
    requires (T a, T b) { a + b; }  // HIBA: ez nem szintaktikailag érvényes
T add(T a, T b) { return a + b; }

Itt a requires clause után zárójelben lévő rész nem egy érvényes constraint. A helyes megoldás vagy egy conceptet definiálunk, vagy requires requires formát használunk:

template<typename T>
    requires requires(T a, T b) { a + b; }
T add(T a, T b) { return a + b; }

A requires requires rút, de néha szükséges. A legjobb gyakorlat: definiáljunk conceptet, és azt használjuk a clause-ban.

8.1.6.3 A const-ság figyelmen kívül hagyása

A Container concept definiálásakor sokan csak a nem-konstans objektumon ellenőrzik a begin()/end() hívást:

template<typename T>
concept BadContainer = requires(T c) {
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::sentinel_for<decltype(c.begin())>;
};

Ez a concept nem utasítja el automatikusan a const-iterálást (egy nem const objektumon a const tagfüggvény is hívható), de olyan típusra is igaz, amelynek csak nem const begin()-je van (például std::ranges::filter_view), noha az const referencián nem iterálható. Ha a szándék az, hogy a típus const T&-n is iterálható legyen, a const objektumot is vizsgálni kell; ez a concept-et szűkíti (nem szélesíti):

template<typename T>
concept Container = requires(T& c, const T& cc) {
    { c.begin() } -> std::input_or_output_iterator;
    { c.end() } -> std::sentinel_for<decltype(c.begin())>;
    { cc.begin() } -> std::input_or_output_iterator;
    { cc.end() } -> std::sentinel_for<decltype(cc.begin())>;
} && std::destructible<T>;

A T& és const T& paraméterekkel biztosítjuk, hogy a concept a valós használati módokat tükrözze. (Statikus ellenőrzés scratch-fordítással: BadContainer<filter_view> igaz, Container<filter_view> hamis, Container<std::vector<int>> igaz; GCC 15.2, -std=c++20.)

8.1.6.4 Túl tág concept

A concept definiálásakor könnyű pusztán szintaktikai követelményeket megadni, és elfelejteni a szemantikai elvárásokat. Például:

template<typename T>
concept Addable = requires(T a, T b) {
    a + b;
};

Ez igaz olyan típusra, ahol operator+ létezik, de annak eredménye nem feltétlenül értelmes matematikai összeg. A conceptek elsősorban szintaktikai feltételeket rögzítenek; a szemantikai garanciákat a megvalósításnak kell biztosítania és dokumentálnia. Ezért fontos a concept nevének megválasztása és a dokumentáció: az Addable név azt sugallja, hogy az összeadás kommutatív, de ezt a nyelv nem tudja ellenőrizni. A gyakorlatban a standard std::semiregular vagy std::regular conceptek gyakran elegendőek a szemantika egy részének rögzítésére.

8.1.6.5 A requires kifejezésben lévő változók deklarációja hibás

A requires kifejezés paraméterei a törzsön belül használt változókat vezetik be. Ha a törzsben olyan változót használunk, amely nincs deklarálva a requires paraméterlistájában, fordítási hiba lesz. Például:

template<typename T>
concept HasValue = requires {
    { T::value } -> std::convertible_to<bool>;  // helyes: T::value kifejezés, nem igényel változót
};

Ez valójában helyes, mert a T::value kifejezés nem igényel változót. De ha a T egy objektumát akarjuk használni:

template<typename T>
concept HasMethod = requires {
    T().foo();  // Ez ideiglenes T-t hoz létre, ami lehet, hogy default konstruálható, de nem garantált
};

Ha T nem default konstruálható, a concept hamis lesz, ami nem feltétlenül a szándék. A helyes megoldás a változó bevezetése a requires paraméterlistában. A requires expression paraméterei nem konstruálódnak meg, ezért ez nem követeli meg a default konstruálhatóságot; a concept akkor teljesül, ha a foo() hívható:

template<typename T>
concept HasMethod = requires(T t) {
    t.foo();
};

A requires(T t) forma tehát a megfelelő megoldás; std::declval itt felesleges. Ellenőrzés: egy default konstruktor nélküli típusra (struct NoDef { NoDef(int); void foo(); };) a HasMethod<NoDef> igaz (GCC 15.2, -std=c++20, scratch-fordítás).

8.1.7 Labor: saját concept és ellenőrzés

A labor célja, hogy a fenti ismereteket egy kis, fordítható példán alkalmazd. A feladat: definiálj egy Incrementable nevű conceptet, amely azt követeli meg, hogy egy típus támogassa az elő- és utóinkrementálást a szokásos szemantikával. Ezután valósíts meg egy Counter osztályt, amely teljesíti a conceptet, és egy NoIncrement osztályt, amely nem. Ellenőrizd a conceptet static_assert-tel és egy constrained függvénnyel.

8.1.8 Feladatleírás

  1. Definiáld az Incrementable conceptet a <concepts> fejléc segítségével. A concept követelményei:
    • Az ++x kifejezés T& típusú.
    • Az x++ kifejezés T-re konvertálható (std::convertible_to<T>; a kód és a feladat egységesen ezt használja).
  2. Definiálj egy Counter osztályt, amely egy egész értéket tárol, és támogatja az operator++ mindkét formáját.
  3. Definiálj egy NoIncrement osztályt, amelynek nincs operator++-a.
  4. Használj static_assert-et a concept igazolására (Incrementable<Counter> igaz, Incrementable<NoIncrement> hamis).
  5. Írj egy template<Incrementable T> void increment_twice(T& x) függvényt, amely kétszer hívja az ++x-et.
  6. Fordítsd le a kódot, és futtasd a Counter-re vonatkozó tesztet. A NoIncrement-re való hívásnak fordítási hibát kell adnia – ezt kommentben dokumentáld.

8.1.9 Kiinduló kód (példa)

#include <concepts>
#include <iostream>

// 1. Saját concept
template<typename T>
concept Incrementable = requires(T x) {
    { ++x } -> std::same_as<T&>;     // előinkrementálás T&-et ad
    { x++ } -> std::convertible_to<T>; // utóinkrementálás T-re konvertálható
};

// 2. Counter osztály
class Counter {
public:
    Counter(int value = 0) : value_(value) {}
    Counter& operator++() {
        ++value_;
        return *this;
    }
    Counter operator++(int) {
        Counter old = *this;
        ++(*this);
        return old;
    }
    int value() const { return value_; }
private:
    int value_;
};

// 3. NoIncrement osztály
class NoIncrement {
public:
    void other() {}
};

// 4. static_assert ellenőrzés
static_assert(Incrementable<Counter>);
static_assert(!Incrementable<NoIncrement>);

// 5. Constrained függvény
template<Incrementable T>
void increment_twice(T& x) {
    ++x;
    ++x;
}

int main() {
    Counter c{10};
    increment_twice(c);
    std::cout << c.value() << '\n';  // 12-t kell kiírnia
    // NoIncrement n; increment_twice(n); // Fordítási hiba: a megszorítás nem teljesül
}

Fordítási parancs:

Futtatás:

Várt kimenet:

12

Mért kimenet: kitöltendő az olvasó saját futtatása után (a példa szándékolt eredménye 12, ez várt, nem mért érték). A NoIncrement-re vonatkozó increment_twice hívás kikommentelve van, mert az a concept nem teljesülése miatt fordítási hibát ad; a hívás névvel ellátott objektumon történjen, hogy a hiba a megszorításból és ne egy ideiglenes objektum T&-hez kötéséből eredjen.

A labor nem futásidejű teljesítményt mér, hanem a concept helyes működését ellenőrzi. A mérési napló rögzítse:

  • A fordítás sikerességét (várt: sikeres; mért: kitöltendő).
  • A futás kimenetét (várt: 12; mért: kitöltendő).
  • A static_assert-ek eredményét (várt: mindkettő igaz; mért: kitöltendő).

8.1.11 Önellenőrző kérdés

Definiálj egy TotalOrdered conceptet a <concepts> fejléc elemeinek felhasználásával, majd írj egy constrained_min függvényt, amely két azonos típusú argumentum közül a kisebbet adja vissza. Milyen concept(ek)et használsz, és miért? (A megoldás során gondold át, hogy a std::totally_ordered önmagában elegendő-e, vagy szükség van-e std::same_as-re a típusok egyezésének biztosításához.)

Megoldásvázlat: template<std::totally_ordered T> const T& constrained_min(const T& a, const T& b) { return b < a ? b : a; }. Mivel a T egyetlen sablonparaméter, mindkét argumentum azonos típusú, külön std::same_as nem kell; a std::totally_ordered már tartalmazza az std::equality_comparable-t, így az sem szerepel külön.

A fejezetben bemutatott eszközök – a concept definíció, a requires kifejezések, a constraint-ek összetétele és a standard conceptek – képezik az alapját a következő egységnek, ahol a constraint-ek részletesebb formáit, a normalizálást tárgyaljuk (8.2); a range-ek a 8.3-ban következnek. A labor eredményei megmutatják, hogy a conceptek olvashatóbbá teszik a sablonokat, és gyakran célzottabb hibaüzenetet adnak, ami a nagyméretű kódbázisok karbantarthatóságát segítheti.
