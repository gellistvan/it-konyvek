10.2 CRTP és statikus polimorfizmus

A CRTP (Curiously Recurring Template Pattern) a C++ egyik leghatékonyabb eszköze statikus polimorfizmus megvalósítására. A minta lényege, hogy egy alapsablon a saját sablonparamétereként kapja meg a belőle származtatott osztály típusát, így az alaposztály fordítási időben hivatkozhat a származtatott típusra, és meghívhatja annak metódusait anélkül, hogy virtuális függvényekre vagy dinamikus diszpécsre lenne szükség. Ez a technika széles körben elterjedt a teljesítménykritikus könyvtárakban – például az Eigen lineáris algebrai könyvtárban, a Boost különböző komponenseiben, vagy a Microsoft Active Template Library-ben –, mert a virtuális hívások költségét és a vtable indirekcióját teljesen kiküszöböli, miközben megőrzi a kód újrafelhasználhatóságát és a típusbiztonságot.

A fejezet célja, hogy bemutassa a CRTP mint statikus felület működését, a base-to-derived (lefelé történő) static_cast mechanizmusát, valamint a statikus és dinamikus diszpécser közötti választás szempontjait. Az itt tárgyalt fogalmakra épít a következő egység, amely a mixineket és a policy-based designt tárgyalja, ezért fontos, hogy az olvasó pontosan értse a CRTP belső működését és korlátait.

10.2.1 A CRTP alapmintája

A legegyszerűbb CRTP-sémában egy sablon alaposztály a származtatott típust sablonparaméterként kapja meg, és a saját metódusaiban static_cast segítségével hivatkozik arra. Tekintsük a következő példát:

template <typename Derived>
class Base {
public:
    void interface() {
        // A statikus felület meghívja a származtatott implementációt.
        static_cast<Derived*>(this)->implementation();
    }

    // Az alaposztály biztosíthat közös adatokat vagy segédfüggvényeket is.
};

class Concrete : public Base<Concrete> {
public:
    void implementation() {
        // A tényleges művelet.
    }
};

A Concrete osztály a Base<Concrete>-ből származik, tehát a Base sablon a Derived = Concrete típussal példányosodik. Amikor a Base<Concrete>::interface() metódus fut, a static_cast<Derived*>(this) kifejezés a this mutatót Concrete* típusra alakítja, így a Base osztály közvetlenül eléri a Concrete::implementation() metódust. A hívás teljesen statikus: a fordító már fordítási időben ismeri a Derived típust, ezért a függvényhívás közvetlenül, virtuális indirekció nélkül történik.

Ez a minta azért „kuriózusan rekurzív”, mert a Base osztály definíciója a saját sablonparaméterére hivatkozik, ami formálisan egy rekurzív típusdefiníciót eredményez: Concrete örökli Base<Concrete>-t, amely Concrete-re hivatkozik, de ez a rekurzió csak a típus szintjén jelenik meg, futásidőben semmilyen rekurzív hívás nem történik. A fordító a sablon példányosításakor feloldja a típust, és a generált kódban nincs szükség virtuális táblára.

10.2.2 A statikus felület fogalma

A CRTP egyik leggyakoribb alkalmazása egy statikus felület definiálása. A hagyományos objektumorientált programozásban egy absztrakt alaposztály virtuális függvényekkel írja elő a származtatott osztályok számára a megvalósítandó interfészt. A CRTP ugyanezt a célt szolgálja, de a szerződést nem a virtuális függvény, hanem a sablonpéldányosítás kényszeríti ki.

Tekintsünk egy Printable mixint, amely egy print metódust ad minden olyan osztálynak, amelyik megvalósítja a do_print műveletet:

#include <iostream>

template <typename Derived>
class Printable {
public:
    void print(std::ostream& os) const {
        // A statikus felület meghívja a származtatott osztály privát vagy publikus implementációját.
        static_cast<const Derived*>(this)->do_print(os);
    }
};

class Point : public Printable<Point> {
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}

    // A felület által megkövetelt implementáció.
    void do_print(std::ostream& os) const {
        os << '(' << x_ << ", " << y_ << ')';
    }
};

int main() {
    Point p{3, 4};
    p.print(std::cout); // Kiírja: (3, 4)
}

Ebben a példában a Printable<Point> osztály biztosítja a print nyilvános metódust, amely a static_cast<const Point*>(this)->do_print(os) hívással éri el a Point osztály do_print tagfüggvényét. A Point osztály nem rendelkezik virtuális függvényekkel, így az objektumok nem tartalmaznak vtable-mutatót, és a print hívás közvetlenül a do_print-re fordul. A do_print lehet akár privát is, ha a Printable alaposztályt friend-ként deklaráljuk, de a fenti példában publikus.

A statikus felület előnye, hogy a fordító teljesen ellenőrizni tudja a típusok helyességét. Ha a Point osztály nem definiálja a do_print metódust, a p.print() hívás fordítási hibát eredményez, mert a Printable<Point>::print() sablonpéldányosítása során a static_cast<const Point*>(this)->do_print(os) kifejezés érvénytelen lesz. A hibaüzenet ugyan néha hosszú és nehezen olvasható, de a C++20 concepts bevezetésével ez a helyzet jelentősen javítható (lásd a 8.1 egységet).

10.2.3 Base-to-derived cast és annak biztonsága

A CRTP alapvető művelete a static_cast<Derived*>(this), amely a Base<Derived>* mutatót a Derived* típusra alakítja: ez base-to-derived (lefelé történő) cast, nem derived-to-base. A static_cast ebben az irányban csak akkor definiált, ha a mutató ténylegesen egy Derived típusú objektum Base<Derived> alobjektumára mutat; különben a viselkedés nem definiált ([expr.static.cast]). A fordító ezt nem ellenőrzi.

A fő kockázatot a helytelen sablonparaméter jelenti. Tekintsük a következő hibás kódot:

class Wrong : public Base<Other> { // Other nem a Wrong osztály
public:
    void implementation() {}
};

Ebben az esetben a Base<Other> példányosodik, és a static_cast<Other*>(this) a Wrong objektumot Other*-ként kezeli, ami undefined behavior. A program lefordulhat, de futás közben váratlan viselkedést produkálhat.

Kézenfekvő, de nem elégséges védelem a static_assert(std::is_base_of_v<Base<Derived>, Derived>) a konstruktorban: ha Other helyesen származik Base<Other>-ből, akkor a Wrong is örökölheti a Base<Other>-t, a feltétel igaz marad, a Wrong-ból mégis hibás a lefelé cast. A teszt nem bizonyítja a this objektum tényleges típusát. A bevett védelem a privát konstruktor és friend Derived;: csak a Derived hozhatja létre a Base<Derived> alobjektumot, így a Wrong (amely nem Other) nem hívhatja a Base<Other> konstruktorát:

template <typename Derived>
class Base {
    Base() = default;      // privát: csak a Derived érheti el
    friend Derived;
public:
    void interface() {
        static_cast<Derived*>(this)->implementation();
    }
};

class Concrete : public Base<Concrete> {   // OK
public:
    void implementation() {}
};

class Wrong : public Base<Other> {};        // lefordul, de a konstruktora törölt
// Wrong w;  // HIBA: use of deleted function 'Wrong::Wrong()'
//           // (Base<Other>() privát, a Wrong nem friend)

A hiba nem az osztálydefiníciónál, hanem az első Wrong objektum létrehozásakor jelentkezik: a Wrong implicit alapértelmezett konstruktora a hozzáférhetetlen bázis-konstruktor miatt törölt (g++ 15.2, -std=c++20).

A védelem a konstruktor elérhetőségén alapul, nem a konstruktortörzsben futó static_assert-en; a másoló és mozgató konstruktorra ugyanezt a megoldást kell alkalmazni, ha azokat is védeni akarjuk.

Egy másik tipikus hibaforrás, ha a static_cast-ot elfelejtik, és az alaposztály közvetlenül hívja a Derived metódust a this mutatón keresztül:

template <typename Derived>
class Base {
public:
    void interface() {
        // Hiba: a this típusa Base<Derived>*, nem Derived*.
        this->implementation(); // Fordítási hiba, ha nincs ilyen tag.
    }
};

A Base<Derived> osztályban nincs implementation tag, így ez a kód nem fordul le. A static_cast tehát elengedhetetlen a származtatott típus eléréséhez.

10.2.4 Statikus és dinamikus diszpécser összehasonlítása

A CRTP és a virtuális függvények közötti választás alapvető tervezési döntés, amelyet a futásidejű követelmények, a memória- és teljesítménycélok, valamint a kód karbantarthatósága határoz meg. A két mechanizmus közötti különbséget a következő táblázat foglalja össze:

Szempont Dinamikus diszpécser (virtuális) Statikus diszpécser (CRTP)
Hívás feloldása Futásidőben, vtable-n keresztül Fordítási időben, közvetlen hívás
Objektum mérete + egy vtable-mutató (általában 8 bájt) Nincs extra méret
Hívási költség Indirekt hívás; az inline-olást akadályozza (monomorf helyen a mai előrejelzők jól teljesítenek) Közvetlen hívás, gyakran inline-olható
Heterogén kollekció Támogatott (pl. vector<Base*>) Közös alaptípus nincs; statikusan ismert halmazra std::tuple/std::variant, ismeretlenre type erasure
Kódduplikáció Az alaposztályi kód egyszer létezik (az override-ok típusonként külön) Minden leszármazottra külön kód generálódik
Fordítási idő Kisebb Nagyobb lehet (több példányosítás)
Futásidejű típusinformáció RTTI elérhető Nincs dinamikus típus

A CRTP legnagyobb előnye a teljesítmény. Mivel a hívás célja fordítási időben ismert, a fordító beillesztheti a hívott függvény törzsét a hívás helyére, ami lehetővé teszi a további optimalizációkat (konstans propagálás, dead code elimination). Egy virtuális hívásnál a fordító általában nem tudja bizonyítani a tényleges típust, ezért indirekt hívást generál (a vtable beolvasása, a függvénymutató betöltése, az indirekt ugrás). Monomorf hívási helyen a modern indirekt ugrás-előrejelzők ezt jól kezelik, a fő költség általában az inline-olás és az arra épülő optimalizációk elmaradása; a fordító ráadásul bizonyos esetekben devirtualizálhat. Szűk belső ciklusokban a különbség lehet jelentős, de ezt a laborban mérni kell, nem feltételezni.

Ugyanakkor a CRTP-nek ára van. A statikus polimorfizmus nem ad közös alaptípust: a Base<Derived1> és a Base<Derived2> különböző típusok, így vector<Base*> nem készíthető (hacsak nem vezetünk be egy közös, virtuális alaposztályt, ami visszahozza a dinamikus diszpécset). Statikusan ismert típushalmaznál std::tuple vagy std::variant használható, ismeretlen futásidejű típusnál type erasure vagy más dinamikus eszköz. Továbbá minden egyes származtatott típushoz külön kód generálódik, ami növelheti a bináris méretet, különösen sok különböző típus esetén. Ez a kódduplikáció nem feltétlenül probléma, ha a metódusok kicsik és gyakran hívottak, de nagy függvényeknél a fordítási idő és a memóriaigény megnőhet.

A döntési szabály tehát: ha a típusok halmaza fordítási időben ismert, és nincs szükség futásidejű típusfeloldásra, a CRTP kiváló választás. Ha viszont a kódnak ismeretlen, bővíthető típusokkal kell dolgoznia (pl. plugin-rendszerek, dinamikus objektumhierarchiák), a virtuális függvények elkerülhetetlenek. A kettő kombinálható is: egy CRTP-alapú osztály virtuális függvényeket is tartalmazhat, ha szükséges, de ez a statikus diszpécser előnyeit részben eltörli.

10.2.5 CRTP-alapú mixinek

A mixin egy olyan osztály, amelyet arra terveztek, hogy más osztályokhoz örököljenek hozzá, és ezáltal kiegészítő funkcionalitást adjanak. A CRTP-vel kombinálva a mixin hozzáfér a származtatott osztály típusához, így a mixin metódusai a származtatott osztály specifikus műveleteire építhetnek. Ezzel a technikával könnyen összeállítható újrafelhasználható komponensek, amelyek a statikus polimorfizmus előnyeit élvezik.

Példaként tekintsünk egy Counted mixint, amely nyilvántartja az adott típusú objektumok számát:

#include <cstddef>

template <typename Derived>
class Counted {
    static inline std::size_t count_ = 0;
public:
    Counted() { ++count_; }
    Counted(const Counted&) { ++count_; }
    Counted(Counted&&) noexcept { ++count_; }
    // értékadás: a példányszám nem változik, ezért tudatosan defaultolt
    Counted& operator=(const Counted&) = default;
    Counted& operator=(Counted&&) noexcept = default;
    ~Counted() { --count_; }

    static std::size_t instance_count() { return count_; }
};

class Widget : public Counted<Widget> {
    // Widget specifikus adatok és műveletek.
};

class Gadget : public Counted<Gadget> {
    // Gadget specifikus adatok.
};

Itt a Counted<Widget> és a Counted<Gadget> különálló sablonpéldányok, ezért a count_ statikus adattag mindegyik típushoz külön-külön létezik. A Widget osztály öröklése a Counted<Widget>-ből biztosítja, hogy minden Widget objektum létrehozása és megsemmisítése frissíti a számlálót, anélkül, hogy a Widget osztálynak bármit tennie kellene. A mixin tehát tiszta, újrafelhasználható funkcionalitást ad. A felhasználó által deklarált move konstruktor mellett az implicit másoló értékadás törölt lenne, és move értékadás sem keletkezne, ezért az értékadásokat tudatosan = default-ra állítottuk (a számláló értékadáskor nem változik). A sima static inline számláló egyszálú használatra jó; párhuzamos objektumlétrehozásnál adatversenyes, ott std::atomic<std::size_t> számláló kell.

Egy másik gyakori mixin a Comparable, amely a < operátort valósítja meg egy compare metódusra építve:

template <typename Derived>
class Comparable {
public:
    bool operator<(const Derived& other) const {
        return static_cast<const Derived*>(this)->compare(other) < 0;
    }
    // Hasonlóan lehet >, <=, >=...
};

class Version : public Comparable<Version> {
    int major_, minor_;
public:
    Version(int major, int minor) : major_(major), minor_(minor) {}
    int compare(const Version& other) const {
        // összehasonlítás kivonás helyett: a kivonás int szélsőértékeknél túlcsordulhat
        if (major_ != other.major_) return major_ < other.major_ ? -1 : 1;
        if (minor_ != other.minor_) return minor_ < other.minor_ ? -1 : 1;
        return 0;
    }
};

A Comparable<Version> mixin a Version osztály compare metódusára támaszkodva biztosítja a < operátort. A Version osztályban nincs szükség az operátor külön megírására, és a hívás teljesen statikus. A compare szándékosan nem kivonást használ (major_ - other.major_ túlcsordulhatna INT_MAX/INT_MIN közeli értékeknél, ami előjeles túlcsordulás, tehát UB). Az összehasonlító mixinek C++20-ban nagyrészt kiválthatók: lásd a „Modern alternatívák” szakaszt.

A mixinek kombinálhatók is: egy osztály több CRTP-alapú mixinből is származhat, mindegyik a saját funkcionalitását adva hozzá. Például egy Widget lehet Counted<Widget> és Comparable<Widget> is, amennyiben a sablonparaméter mindig a tényleges osztálytípus.

10.2.6 Labor: CRTP-alapú mixin készítése

A labor célja, hogy az olvasó saját kezűleg implementáljon egy CRTP-alapú mixint, és ellenőrizze annak helyességét, valamint megmérje a statikus diszpécser teljesítménybeli előnyét a virtuális függvényes megoldással szemben. A feladat specifikációja a következő:

  1. Készíts egy Printable mixint, amely egy print metódust ad a származtatott osztályoknak. A mixin a származtatott osztály do_print metódusát hívja, amely egy std::ostream& paramétert kap. A mixin ne tartalmazzon virtuális függvényeket.

  2. Készíts egy Counted mixint, amely nyilvántartja az adott típusú példányok számát. A mixin konstruktorai és destruktora frissítik a számlálót, és egy statikus instance_count() metódus kérdezi le az aktuális értéket. A mixin legyen másolható és mozgatható, és a másolás/mozgatás során is helyesen tartsa nyilván a példányszámot.

  3. Definiálj egy Point osztályt, amely mindkét mixinből örököl: Point : public Printable<Point>, public Counted<Point>. A Point tárolja az x és y koordinátákat, és valósítsa meg a do_print metódust.

  4. Írj teszteket (pl. Catch2 vagy egyszerű assert makrók segítségével), amelyek ellenőrzik:

    • A print metódus a várt szöveget írja ki.
    • A Counted mixin helyesen számolja a példányokat, beleértve a másolást és mozgatást is.
    • A Point polimorf-e: static_assert(!std::is_polymorphic_v<Point>) (ez a vtable-mutató hiányának nyelvi ellenőrzése; a sizeof(Point) értéke az ABI-tól, az üresbázis-optimalizációtól és a kitöltéstől függ, ezért önmagában nem bizonyíték).

  5. Készíts egy virtuális függvényes alternatívát ugyanerre a funkcionalitásra, ahol a print egy virtuális függvény egy absztrakt alaposztályban, a számolás pedig virtuális destruktorral és statikus számlálóval történik.

  6. Mérj meg legalább a következőket:

    • A két megoldás bináris méretét (pl. size parancs Linuxon).
    • Egy egyszerű benchmark futásidejét, amely nagy számú (10^7) print hívást hajt végre mindkét változaton (a kiírást irányítsd egy std::ostringstream-be, hogy ne a konzol legyen a szűk keresztmetszet; vedd figyelembe, hogy így főleg a formázást és az allokációt méred, nem csak a diszpécsert, ezért érdemes egy egyszerűbb, azonos munkát végző do_work(int) hívást is mérni, amelynek eredményét felhasználod).
    • A Point objektum méretét mindkét esetben.

  7. Rögzítsd a mérési eredményeket egy naplófájlban, feltüntetve a fordító verzióját (pl. GCC 13.2), a szabványverziót (C++20), az optimalizációs szintet (-O2), a hardvert (CPU típus, memória), valamint a várt és mért értékeket. A várt érték hipotézis, nem előírt eredmény: a CRTP-s változat várhatóan nem nagyobb és nem lassabb, az objektum nem tartalmaz vtable-mutatót, de a mérés eredményét nem kötjük előre: a fordító a virtuális hívást devirtualizálhatja, a bináris mérete pedig a példányosítástól függ.

A feladat megoldásához ajánlott buildrendszer: CMake, amely a -Wall -Wextra -pedantic -Werror kapcsolókkal fordít. A kódot le kell futtatni AddressSanitizer és UndefinedBehaviorSanitizer alatt is, hogy kizárjuk a memóriahibákat és az undefined behaviort. A tesztfuttatásokat izolált környezetben végezd, és a mérési naplóban dokumentáld az eredményeket.

A labor megoldásának egy lehetséges váza:

// printable.hpp
#pragma once
#include <ostream>

template <typename Derived>
class Printable {
public:
    void print(std::ostream& os) const {
        static_cast<const Derived*>(this)->do_print(os);
    }
};

// counted.hpp
#pragma once
#include <cstddef>

template <typename Derived>
class Counted {
    static inline std::size_t count_ = 0;
public:
    Counted() { ++count_; }
    Counted(const Counted&) { ++count_; }
    Counted(Counted&&) noexcept { ++count_; }
    Counted& operator=(const Counted&) = default;
    Counted& operator=(Counted&&) noexcept = default;
    ~Counted() { --count_; }
    static std::size_t instance_count() { return count_; }
};

// point.hpp
#pragma once
#include "printable.hpp"
#include "counted.hpp"

class Point : public Printable<Point>, public Counted<Point> {
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}
    void do_print(std::ostream& os) const {
        os << '(' << x_ << ", " << y_ << ')';
    }
};

A teszteléshez használhatunk egyszerű assert-eket vagy egy keretrendszert. A mérési naplóban külön kell feltüntetni a várt és a mért értékeket, például:

Metrika Várt (CRTP) Mért (CRTP) Várt (virtuális) Mért (virtuális)
Bináris méret hipotézis: nem nagyobb <mért> hipotézis: hasonló vagy nagyobb <mért>
Futásidő (10^7 hívás) hipotézis: nem lassabb <mért> hipotézis: hasonló vagy lassabb <mért>
sizeof(Point) tipikus ABI-n 8 bájt (nincs vptr) <mért> tipikus 64 bites ABI-n 16 bájt <mért>
is_polymorphic_v false <mért> true <mért>

A mérés során minden futtatást többször meg kell ismételni, és az átlagot, illetve a szórást is rögzíteni kell. A pontos módszertant a 22.4 egység tárgyalja, de itt is érvényes, hogy a mérési körülményeket dokumentálni kell.

10.2.7 Tipikus hibák és elkerülésük

A CRTP használata során a leggyakoribb hibák a következők:

  1. Helytelen sablonparaméter: a származtatott osztály nem saját magát adja meg sablonargumentumként. Ez undefined behaviorhez vezethet. Megoldás: privát konstruktor és friend Derived;, ahogy fent bemutattuk (az is_base_of alapú static_assert önmagában nem elég).

  2. Hiányzó static_cast: az alaposztály a this mutatón keresztül próbálja elérni a származtatott osztály tagjait, ami fordítási hibát okoz. Megoldás: mindig static_cast<Derived*>(this) vagy static_cast<const Derived*>(this).

  3. Többszörös öröklődés és nem egyértelmű alaposztály: ha a Derived több Base-ből is örököl (pl. class D : public Base<D>, public OtherBase), a static_cast akkor is érvényes, de ügyelni kell arra, hogy a Base<D> egyértelmű alaposztály legyen. Ha a Derived virtuálisan örökli a Base-t, a static_cast<Derived*>(this) rosszul formált (fordítási hiba), mert virtuális alaposztályról nem lehet static_cast-tal a származtatottra lépni (az alobjektum helye a legmélyebb típustól függ); ilyenkor dynamic_cast kellene, ami viszont már nem statikus megoldás.

  4. Objektumvágás (slicing): a Derived objektumok szabadon másolhatók érték szerint; a veszély a Base<Derived> önálló érték szerinti másolása vagy tárolása: ekkor a származtatott rész elvész, és a static_cast<Derived*>(this) UB-t okoz. Védekezés: a Base konstruktorai és másoló műveletei legyenek protected/privát (+ friend Derived), így a Base önállóan nem másolható.

  5. A Derived hiányos típus a Base<Derived> törzsében: a class Concrete : public Base<Concrete> pontján a Base<Concrete> példányosításakor a Concrete még hiányos (incomplete) típus. Ezért a bázis osztálytörzsében (tagdeklarációk, using, tagváltozók, visszatérési típusok) nem használható a Derived tagja vagy mérete, például using value_type = typename Derived::value_type; vagy sizeof(Derived) fordítási hibát ad. A Derived tagjai csak tagfüggvény-törzsekben érhetők el, mert azok a példányosítás későbbi pontján, a Derived teljessé válása után értékelődnek ki. Megoldás: típuskövetelményt tagfüggvényben, vagy külön trait osztállyal (Traits<Derived>) adjunk meg.

  6. Túlzott kódduplikáció: ha a mixinek nagy metódusokat tartalmaznak, minden leszármazott osztályhoz külön kód generálódik. Ez megnövelheti a bináris méretet. Megoldás: a nagy, típusfüggetlen logikát érdemes nem-sablon segédfüggvényekbe kiszervezni, és a mixin csak a típusfüggő részt tartalmazza.

10.2.8 Modern alternatívák: deducing this és operator<=>

C++23-tól az explicit objektumparaméter („deducing this”, P0847) a CRTP számos felhasználását kiváltja: a tagfüggvény maga kapja meg az objektum tényleges típusát, bázis sablonparaméter és static_cast nélkül. Fordítóigény: GCC 14 vagy újabb, Clang 18 vagy újabb, MSVC 19.32 vagy újabb (a támogatást a saját környezetben ellenőrizzük).

// C++23 (-std=c++23)
#include <iostream>

struct Printable {
    void print(this const auto& self, std::ostream& os) {
        self.do_print(os);   // self a tényleges (származtatott) típus
    }
};

struct Point : Printable {
    int x_, y_;
    void do_print(std::ostream& os) const { os << '(' << x_ << ", " << y_ << ')'; }
};

int main() {
    Point p{{}, 3, 4};  // aggregátum: az első {} a Printable bázis
    p.print(std::cout); // (3, 4)
}

A self a hívás helyén ismert statikus típusra dedukálódik; bázisreferencián (Printable&) át hívva self típusa Printable, és a do_print nem érhető el – a deducing this, akárcsak a CRTP, statikus diszpécser (g++ 15.2, -std=c++23: a példa (3, 4)-et ír ki).

Az összehasonlító mixinek helyett C++20-tól az alapértelmezett háromutas összehasonlítás használható, amely az összes relációs operátort generálja:

// C++20
#include <compare>

class Version {
    int major_, minor_;
public:
    Version(int a, int b) : major_(a), minor_(b) {}
    auto operator<=>(const Version&) const = default;
};

A CRTP továbbra is indokolt, ha C++23 előtti szabványt célzunk, ha a bázisnak típust (nem csak tagfüggvényt) kell a származtatott típushoz kötnie, vagy ha a bázis static tagjai típusonként külön kellenek (például a Counted számláló).

10.2.9 Összegzés és önellenőrző kérdés

A CRTP egy erőteljes eszköz a statikus polimorfizmus megvalósítására. Lehetővé teszi, hogy egy alaposztály hozzáférjen a származtatott típushoz, és annak metódusait virtuális függvények nélkül hívja meg. Ez a technika fordítási időben feloldott, gyors, és gyakran kisebb kódot eredményez, de nem támogatja a heterogén kollekciókat, és kódduplikációhoz vezethet. A mixinekkel kombinálva a CRTP újrafelhasználható, típusbiztos komponensek építését teszi lehetővé.

Önellenőrző kérdés: Magyarázd el, miért nem lehet egy std::vector<Base*> típusú kollekcióban tárolni CRTP-alapú osztályok objektumait, ha a Base egy CRTP-alaposztály. Milyen alternatívát javasolnál, ha szükség van heterogén tárolásra? (A válaszhoz gondold át a statikus és dinamikus típusok közötti különbséget, valamint a type erasure lehetőségét, amelyet a 11.1 egység tárgyal.)

Megoldásvázlat. A Base<D1> és a Base<D2> két különböző, egymással nem rokon típus, így nincs közös Base*, amelyet a vektor tárolhatna; a statikus típus a sablonargumentum része. Alternatívák: közös, nem sablon (virtuális) alaposztály, std::variant<D1, D2, ...> statikusan ismert halmazra, vagy type erasure (a 11.1 egység), amely a statikus interfész fölé dinamikus burkolót tesz.
