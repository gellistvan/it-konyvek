27.3 Modern C++ idiomák: Pimpl, Rule of 0/3/5, CRTP

A modern C++-ban a nyelvi eszközök önmagukban nem teszik karbantarthatóvá a kódot; az idiomák adják meg azt a közös mintakészletet, amellyel a tervezési szándék kifejezhető anélkül, hogy minden alkalommal újra ki kellene találnunk őket. Ebben a fejezetben három, a gyakorlatban szinte minden nem triviális kódbázisban előforduló idiómát vizsgálunk: a Pimpl-et, a Rule of 0/3/5-öt és a CRTP-t. Mindhárom más-más problémát old meg: a Pimpl a fordítási függőségeket és az ABI-stabilitást, a Rule of 0/3/5 az erőforrás-kezelés és a speciális tagfüggvények kapcsolatát, a CRTP pedig a statikus polimorfizmus és a kódújrafelhasználás egy sajátos útját. Bár a három idióma különböző nyelvi szinten működik, közös bennük, hogy a karbantarthatóságot és a helyes absztrakciót szolgálják, és akkor igazán hatékonyak, ha a fejlesztő pontosan érti a mögöttük álló nyelvi szabályokat.

27.3.1 Pimpl: a fordítási tűzfal és ABI-határ

A Pimpl (pointer-to-implementation) – más néven compilation firewall vagy Cheshire Cat technique – egy olyan szerkezet, amelyben az osztály publikus felülete csak egy nem teljes típusra mutató pointert (std::unique_ptr-t) tart, a tényleges implementáció pedig a forrásfájlban definiált, rejtett osztályban található. A minta célja kettős: egyrészt csökkenti a fejlécek közötti függőségeket, másrészt stabil ABI-t biztosít, hiszen a privát adattagok megváltozása nem változtatja meg a publikus osztály objektumlayoutját.

A klasszikus, C++11 előtti változat nyers pointerrel dolgozott, ami manuális memóriakezelést és gyakran hiányos másolási szemantikát eredményezett. A modern C++-ban std::unique_ptr<Impl>-t használunk, ami automatikusan kezeli az élettartamot, de bevezet néhány nem nyilvánvaló követelményt:

  • A publikus osztály destruktorát a headerben deklarálni kell, de a definícióját a forrásfájlban kell megadni, ahol az Impl teljes definíciója már látható. Ennek oka, hogy az std::unique_ptr destruktora static_assert-tel ellenőrzi a pointee teljes típusát; ha a headerben generálódna a publikus osztály destruktora, fordítási hibát kapnánk.
  • A move konstruktort és a move értékadást szintén a headerben deklaráljuk, a = default definíciót pedig a .cpp-be tesszük, ahol az Impl teljes. A move értékadás a cél régi Impl-jét törli, a defaultolt move konstruktor pedig kivételkezelési takarítás miatt a destruktort is példányosítja; mindkettőhöz teljes típus kell, ezért a headerben = default-ként megadva fordítási hibát kapnánk (a GCC-nél pl. invalid application of 'sizeof' to incomplete type 'Widget::Impl'; a hiba csak abban a fordítási egységben jelentkezik, ahol a tagfüggvényt ténylegesen használják). Mozgatás után a forrás pImpl_-je null: ilyen objektumon csak az értékadás és a destruktor megengedett (a do_something()/value() előfeltétele a nem moved-from állapot).
  • A másoló konstruktort és értékadást viszont a forrásfájlban kell definiálni, mert ott kell lemásolni az Impl objektumot, amihez annak teljes típusa szükséges.

Az alábbi példa egy egyszerű Widget osztályt mutat be:

// widget.h
#pragma once
#include <memory>

class Widget {
public:
    Widget();
    ~Widget();                          // out-of-line destructor
    Widget(Widget&&) noexcept;
    Widget& operator=(Widget&&) noexcept;
    Widget(const Widget&);
    Widget& operator=(const Widget&);

    void do_something();   // előfeltétel: nem moved-from objektum
    int value() const;     // előfeltétel: nem moved-from objektum

private:
    class Impl;
    std::unique_ptr<Impl> pImpl_;
};
// widget.cpp
#include "widget.h"

class Widget::Impl {
public:
    void do_something() { ++counter; }   // az int számláló túlcsordulása signed overflow (UB); API-korlát nincs megadva
    int value() const { return counter; }
private:
    int counter{0};
};

Widget::Widget() : pImpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;  // itt már teljes az Impl

Widget::Widget(Widget&&) noexcept = default;
Widget& Widget::operator=(Widget&&) noexcept = default;

Widget::Widget(const Widget& other)
    : pImpl_(other.pImpl_ ? std::make_unique<Impl>(*other.pImpl_) : nullptr) {}

Widget& Widget::operator=(const Widget& other) {
    if (this != &other) {
        if (other.pImpl_) {
            pImpl_ = std::make_unique<Impl>(*other.pImpl_);
        } else {
            pImpl_.reset();
        }
    }
    return *this;
}

void Widget::do_something() { pImpl_->do_something(); }
int Widget::value() const { return pImpl_->value(); }

A Pimpl legnagyobb előnye a fordítási idő csökkentése: ha az Impl adattagjai megváltoznak, csak a widget.cpp-t kell újrafordítani, a felhasználói kódot nem. Ez különösen nagy projekteknél drámai hatású lehet, de a konkrét nyereséget mindig mérni kell (lásd a labort). Az ABI-stabilitás abban nyilvánul meg, hogy a Widget objektum mérete és elrendezése független az Impl belső szerkezetétől, így a könyvtár új verziója binárisan kompatibilis maradhat a régi felhasználókkal – feltéve, hogy a publikus függvények szignatúrája sem változik.

A Pimplnek ára van: minden konstrukció és destruálás egy heap-allokációt igényel, a publikus függvények hívása egy indirekción keresztül történik, és a másolás mély másolatot készít, ami költséges lehet. Emellett a const tagfüggvényeknél a pImpl_ pointer (a const std::unique_ptr<Impl>) const lesz, de az operator-> továbbra is nem-const Impl*-t ad: a mutatott Impl NEM const, ezért a const tagfüggvény const_cast és mutable nélkül is módosíthatja (sekély konstansság). Ha a logikai const-szerződést ki akarjuk kényszeríteni, const-helyes impl() segédfüggvény-pár (const Impl& impl() const) vagy a std::experimental::propagate_const kell; csak tudatosan logikai konstans állapot (pl. cache) legyen módosítható. A Pimpl pontosabb költségmodellje: nem minden konstrukció/destrukció allokál (a destrukció felszabadít, a move csak átvesz, üres forrás másolása nem foglal); a költséget műveletenként kell mérni. A változatlan függvényszignatúra és objektumméret sem teljes ABI-garancia: a fordító, az STL/runtime, a hívási konvenció, a szimbólumláthatóság és más publikus layoutváltozás is számít. Az allokáció szabályozható (pl. saját deleter vagy std::pmr, ekkor a memory_resource élettartama, a konstrukció/destrukció/deallokáció párosítása és a deleter külön tervezendő; a std::unique_ptr-nek nincs allocator sablonparamétere, a pmr nem automatikus csere). Saját deleter is csak akkor kerüli el az out-of-line destruktort, ha operator()-a a headerben csak deklarált, a teljes Impl mellett definiált; a szabványos std::default_delete C++20-ban sem enged hiányos típust. Az ilyen optimalizációk azonban rontják az olvashatóságot, ezért csak méréssel alátámasztott szűk keresztmetszetekben érdemes őket alkalmazni.

27.3.2 Rule of 0/3/5: az erőforrás-kezelés és a speciális tagfüggvények

A szabályok részletes tárgyalása a 4.2. alfejezetben (Move szemantika, RVO és Rule of 0/3/5) található; ott szerepel a Rule of 0, 3 és 5 pontos definíciója, a generálási szabályok és a noexcept move követelménye. Ez a szakasz nem ismétli meg az alapokat, hanem azt mutatja meg, hogyan kapcsolódik a szabály a Pimpl-idiómához és az ABI-stabilitáshoz: a Pimpl-t használó osztályban a destruktornak a fordítási egységben kell lennie, ezért a Rule of 5 tudatos alkalmazása szükséges. A lenti példa ezért a speciális tagfüggvények együttműködését mutatja be, nem pedig az alapdefiníciókat ismétli.

A következő példa egy nyers tömböt kezelő osztályt mutat be a Rule of 5 szerint:

#include <algorithm>
#include <cstddef>
#include <utility>

class Buffer {
public:
    explicit Buffer(std::size_t size)
        : size_(size), data_(size ? new int[size]() : nullptr) {}

    ~Buffer() { delete[] data_; }

    Buffer(const Buffer& other)
        : size_(other.size_), data_(other.size_ ? new int[other.size_] : nullptr) {
        std::copy(other.data_, other.data_ + size_, data_);
    }

    Buffer& operator=(const Buffer& other) {
        if (this != &other) {
            Buffer tmp(other);          // copy-and-swap
            swap(tmp);
        }
        return *this;
    }

    Buffer(Buffer&& other) noexcept
        : size_(other.size_), data_(other.data_) {
        other.size_ = 0;
        other.data_ = nullptr;
    }

    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data_;
            size_ = other.size_;
            data_ = other.data_;
            other.size_ = 0;
            other.data_ = nullptr;
        }
        return *this;
    }

    void swap(Buffer& other) noexcept {
        std::swap(size_, other.size_);
        std::swap(data_, other.data_);
    }

    std::size_t size() const { return size_; }
    int* data() { return data_; }
    const int* data() const { return data_; }

private:
    std::size_t size_;
    int* data_;
};

A copy-and-swap idióma itt is megjelenik a másoló értékadásban: egy ideiglenes másolatot készítünk, majd kicseréljük a tartalmat. Ez garantálja az erős kivételbiztonságot, mert ha a másolás kivételt dob, az eredeti objektum változatlan marad. A move értékadásnál a delete[] utáni átvétel egyszerű, de ügyelni kell arra, hogy a forrás objektum érvényes, üres állapotba kerüljön; a noexcept itt erősen ajánlott, nem nyelvi kötelezettség: a std::vector reallokáció során a std::move_if_noexcept miatt főként a move konstruktor noexcept-je számít, és csak akkor mozgat, ha az nem dobhat (vagy a típus nem másolható). A Buffer copy-and-swapja nem dobó swap mellett helyes; a Rule of 5 sem jelent kötelező mély másolatot minden Pimplhez (a művelet defaultolható, törölhető vagy definiálható). A saját destruktor az implicit move-ot elnyomja, ezért kell mindet kiírni. Nem általános erős garancia: ahhoz nem dobó commit lépés kell.

Ha ugyanezt a funkcionalitást std::vector<int>-tal valósítanánk meg, egyetlen speciális tagfüggvényt sem kellene írnunk – ez a Rule of 0 diadala. A karbantarthatóság szempontjából mindig ezt az utat válasszuk, hacsak nincs nyomós ok (allokáció-szabályozás, ABI-kényszer, teljesítmény) a kézi erőforrás-kezelésre.

27.3.3 CRTP: statikus polimorfizmus és mixin osztályok

A Curiously Recurring Template Pattern (CRTP) egy olyan sablontechnika, amelyben egy osztály egy saját alosztályára sablonparaméterként hivatkozó bázisosztályból származik:

template <typename Derived>
class Base {
public:
    void interface() {
        static_cast<Derived*>(this)->implementation();
    }
};

class Derived : public Base<Derived> {
public:
    void implementation() {
        // konkrét művelet
    }
};

A minta neve onnan ered, hogy a Derived osztály a saját definíciójában jelenik meg a bázisosztály template-argumentumaként – a rekurzió azonban nem végtelen, mert a bázis tagfüggvényei csak használatkor példányosulnak, amikor a Derived már teljes. A static_cast<Derived*>(this) nem futásidejű típusellenőrzés: ha a Base<Derived> önálló objektum, vagy rossz típus származik belőle (class X : Base<Y>), a downcast UB. Konstruktor/destruktor alatt a Derived állapota még/már nem él, ezért ott a downcast-os visszahívás tilos. A CRTP nem tilt más virtuális elemet, és nem garantál minden optimalizálást. A CRTP tehát statikus polimorfizmust valósít meg: a hívás fordítási időben kötődik, nincs virtuális tábla, nincs indirekció, és a fordító teljes mértékben képes optimalizálni a hívásokat. A dinamikus polimorfizmus (virtuális függvények) ezzel szemben futási időben választja ki a megfelelő implementációt, ami rugalmasabb, de költségesebb, és a pontos típust a fordító nem ismeri.

A CRTP leggyakoribb alkalmazásai:

  1. Kódújrafelhasználás bázisosztályban: gyakori műveleteket (például operator!= az operator==-ből, >, <=, >= az operator<-ből, postfix ++ a prefixből; az operator< az ==-ből nem vezethető le) a bázisosztály egyszer definiál, és a származtatott osztály csak a minimális primitívet implementálja.
  2. Mixin rétegek: a CRTP alkalmas arra, hogy egy osztályt több, egymástól független viselkedéssel bővítsünk, például naplózás, sorosítás, gyorstárazás. Minden mixin egy CRTP bázisosztály, amely a Derived típushoz fér hozzá.
  3. Policy-based design: bár a policy-k gyakran nem CRTP-t használnak, a kettő kombinálható, amikor egy policy-nek szüksége van a gazda típus valamilyen interfészére, és a gazda típus a policy-t CRTP-n keresztül hívja vissza.
  4. Clone, comparison, visitor és más generikus műveletek: a CRTP lehetővé teszi, hogy egy bázisosztály clone() függvényt adjon, amely std::make_unique<Derived>(static_cast<const Derived&>(*this))-et hív.

Példa egy CRTP-alapú példányszámlálóra (a std::enable_shared_from_this szintén CRTP, de más célú, és a példának nincs köze a shared_from_this-tulajdonláshoz). Szerződés: egyszálú használat (a nem atomi instances_ több szálból adatrace, UB; többszálúhoz std::atomic<std::size_t> kell, ami viszont nem objektumélettartam-jogosultság):

#include <cstddef>

template <typename Derived>
class Counted {
public:
    static std::size_t count() { return instances_; }

protected:
    Counted() { ++instances_; }
    ~Counted() { --instances_; }
    Counted(const Counted&) { ++instances_; }
    Counted(Counted&&) noexcept { ++instances_; }
    Counted& operator=(const Counted&) = default;
    Counted& operator=(Counted&&) = default;

private:
    static std::size_t instances_;
};

template <typename Derived>
std::size_t Counted<Derived>::instances_ = 0;

class MyType : public Counted<MyType> {
    // MyType automatikusan számlálja a példányait
};

Itt a Counted bázisosztály konstruktora és destruktora frissíti a statikus számlálót, a másoló és move konstruktorok pedig a megfelelő növelést. A védett konstruktorok megakadályozzák a Counted<T> önálló példányosítását, de azt nem, hogy egy másik típus is Counted<MyType>-ból származzon (ezt a private konstruktor + friend Derived megoldás szűkíti). A számláló a bázisrész életét méri, nem kizárólag teljesen megkonstruált Derived objektumokat. A szabályos sablonos statikus tagdefiníció a headerben önmagában nem ODR-hiba. A MyType a Counted<MyType>-ból származik, így minden példányosítás automatikusan számolódik. A statikus instances_ sablononként külön példányosul, ezért minden Derived típus saját számlálóval rendelkezik.

Egy másik gyakori példa a Barton–Nackman trükk utódjaként ismert befriending: ha egy CRTP bázisosztályban definiált operátort a Derived típusra szeretnénk alkalmazni, a lényeg a bázisban definiált rejtett barát (hidden friend), amelyet az ADL talál meg, pl. friend bool operator==(const Base& a, const Base& b) { return a.derived().key() == b.derived().key(); }. A bázis friend deklarációja nem ad automatikus hozzáférést a Derived privát tagjaihoz (a barátság iránya számít; ehhez a Derived-nek kell hozzáférést adnia), és nem generál tetszőleges Derived-hez operator<=>-t; C++20-ban a <=> defaultolása és az egyedi implementáció külön eset. Az operator<-ből rendezési reláció csak megfelelő feltételekkel (szigorú gyenge rendezés) származtatható egyenlőségre/ekvivalenciára, nem teljes == szemantikára.

A CRTP hátránya, hogy a bázisosztály minden egyes Derived típusra külön példányosul, ami növeli a kódméretet és a fordítási időt. Továbbá a Derived típusának teljes definíciója szükséges a bázisosztály tagfüggvényeinek példányosításakor, ami körkörös függőséget okozhat, ha a fejlécek nem jól szervezettek. A Base<Derived> típusok nem rendelkeznek közös bázissal, ezért közvetlenül nem tárolhatók egy std::vector<Base*>-ban; heterogén gyűjteményhez std::variant, type erasure vagy külön közös interfész kell. Ezért a CRTP-t csak akkor válasszuk, ha a típusok fordítási időben ismertek, és a teljesítmény vagy a kódújrafelhasználás indokolja.

27.3.4 Egyéb modern idiomák röviden

A fenti három idióma mellett a modern C++-ban számos további, széles körben használt minta létezik, amelyeket érdemes ismerni:

  • RAII (Resource Acquisition Is Initialization): minden erőforrás (memória, fájl, mutex, socket) egy osztály konstruktorában kerül megszerzésre, destruktorában felszabadításra. A kivételbiztonság alapja.
  • Copy-and-swap: a másoló értékadás implementálása ideiglenes másolatot készít, majd swap-pel cseréli a tartalmat; erős kivételbiztonságot ad, és a Rule of 5-tel jól kombinálható.
  • Type erasure: futásidejű heterogén tárolást tesz lehetővé sablonok nélkül (std::function, std::any, saját type-erased interfész). A CRTP ellentéte: ott a típust fordítási időben ismerjük, itt elrejtjük.
  • Factory és pimpl kombinációja: a Pimpl gyakran egy factory függvénnyel (vagy std::make_unique-val) együtt jelenik meg, így a konkrét típus teljesen elrejthető.
  • Non-copyable/non-movable mixin: gyakran CRTP-vel vagy egyszerű bázisosztállyal letiltjuk a másolást vagy mozgatást, hogy az osztály egyértelmű tulajdonosi szemantikát kapjon.

27.3.5 Labor: idiómakatalógus készítése

A labor célja, hogy a három fő idiómát egy-egy kis, fordítható és tesztelhető osztályon keresztül mutassuk be, és a fordítási időre, bináris méretre, valamint futási teljesítményre vonatkozó állításainkat méréssel támasszuk alá. A Rule of 5 Buffer részleteit a 4.2 alfejezet tárgyalja; itt csak a Pimpl-lel való kapcsolatát vizsgáljuk. Az átadandó eredmény egy idiómakatalógus, amely tartalmazza a forráskódot, a buildrendszert, a teszteket, a mérési naplót és az elemzést.

Feladat specifikációja:

  1. Válassz egy egyszerű, valószerű komponenst, például egy konfigurációt kezelő osztályt (Config). Ez az osztály tároljon kulcs-érték párokat (std::map<std::string, std::string> vagy hasonló).
  2. A Config osztályt valósítsd meg Pimpl használatával: a publikus headerben csak a publikus interfész és egy std::unique_ptr<Impl> legyen, a tényleges implementáció a .cpp-ben.
  3. Készíts egy Rule of 5-öt szemléltető osztályt, amely nyers mutatóval kezel egy dinamikus tömböt (Buffer), és mutasd be, hogy a másolás/mozgatás helyesen működik, a memóriaszivárgás-mentes.
  4. Készíts egy CRTP-t használó osztályt, például egy Cloneable mixint, amely a clone() függvényt adja, vagy egy Ordered mixint, amely az operator<-ből generálja a többi relációs operátort. A Derived osztály csak az operator<-t implementálja.
  5. Mindhárom idiómához írj egységteszteket (például Catch2 vagy doctest keretrendszerrel): ellenőrizd a másolás/mozgatás utáni állapotot, a destruktor hívások számát, a Pimpl-nél a publikus interfész működését, a CRTP-nél az operátorok helyes működését.
  6. Állítsd össze a buildet CMake-vel, minimum GCC és Clang fordítóval, C++20 szabvánnyal. A fordítási kapcsolók: -Wall -Wextra -Wpedantic -Werror (GCC/Clang), MSVC-nél /W4 /WX. A tesztelést AddressSanitizerrel és UndefinedBehaviorSanitizerrel is futtasd.
  7. Mérési terv:
    • Fordítási idő: készíts két kis programot, az egyikben a Config publikus headerét használod, a másikban egy olyan osztályt, ahol minden adattag publikus headerben van. Mérd az újrafordítást három külön esetben: (a) privát implementáció (az Impl a .cpp-ben) módosítása, (b) a publikus header módosítása (touch), (c) clean build; az azonos belső változás a két terv megfelelő helyén történjen. Naplózd, mely fordítási egységek fordultak újra és volt-e újralinkelés. Várt eredmény: a Pimpl privát változtatásnál csak a config.cpp fordul újra; a publikus Pimpl header módosítása viszont a függő felhasználói egységeket is újrafordíttatja, ezért a kísérlet a „csak config.cpp” állítást csak a privát változtatásra igazolja. Rögzítsd a mért értékeket, és hasonlítsd össze.
    • Bináris méret: fordítsd le mindkét változatot release módban (-O2), és mérd a generált objektumfájlok vagy futtatható fájlok méretét. Várt: nincs garantált irány; a stabil header nem garantál minimális binárisméret-növekményt. Külön rögzítsd a size szakaszokat és az objektumfájl-/futtathatófájlméretet (ezek különböző mennyiségek).
    • Futási teljesítmény: a CRTP-s Ordered mixint hasonlítsd össze egy virtuális függvényes megoldással: egy szűk ciklusban hívj egy relációs operátort, és mérd az időt. Várt: nem előre eldöntött; egy fordítási egységen belül, final osztálynál a fordító gyakran devirtualizál, és a ciklust is optimalizálhatja, így a két változat azonos kódot kaphat; ns nagyságrendű műveletnél 100 000 ismétlés a mérési zajon belül lehet. Mindkét változat ugyanazt a megfigyelhető munkát végezze (az eredményt használd fel, hogy ne optimalizálódjon el). Használj std::chrono mérést, sok ismétlést és a szóródás (pl. medián, min–max) rögzítését, és a mérési naplóban tüntesd fel a környezetet (CPU, compiler, optimalizációs szint, futtatások száma).
  8. Mérési napló: a naplóban külön oszlopban szerepeljen a mért érték és a várt érték, valamint a körülmények. Például:
Mérés Várt Mért Környezet
Pimpl: privát Impl módosítása utáni újrafordítás csak config.cpp kitöltendő (mért) <fordító, verzió, kapcsolók>
Nem-Pimpl: privát adattag módosítása utáni újrafordítás az összes függő egység kitöltendő (mért) ugyanaz
CRTP vs virtuális relációs operátor futásideje nem előre eldöntött kitöltendő (mért, szóródással) <CPU, fordító, -O szint, ismétlések>

A táblázat sablon: a „Mért” oszlopot csak valódi futtatás után töltsd ki; a kért zöld tesztfutás leadandó követelmény, nem a könyvben már meglévő bizonyíték. A tesztterv fedje le az üres/moved-from állapotot, a kivételt, az önértékadást és az operátortörvényeket is. A fordítás/sanitizer feltételeket (release, -O2, ASan/UBSan) a labor build-jegyzőkönyve rögzítse.

A labor kimenete egy rövid jelentés, amelyben megindoklod, hogy az adott idióma mikor előnyös, és milyen ára van.

Átadandó eredmény: - Forráskód a három idiómáról, CMake buildrendszerrel. - Tesztcsomag (Catch2/doctest), amely sanitizerekkel is lefut (az eredményt a mérési napló rögzíti). - Mérési napló a fenti táblázattal, a mért és várt értékek elkülönítésével. - Rövid elemzés a tanulságokról.

27.3.6 Összefoglalás

Ebben a fejezetben három alapvető modern C++ idiómát vizsgáltunk. A Pimpl a fordítási függőségek és az ABI stabilizálásának eszköze, amely std::unique_ptr-rel és a speciális tagfüggvények gondos elhelyezésével valósítható meg. A Rule of 0/3/5 az erőforrás-kezelés irányelve: ha lehetséges, ne deklaráljunk speciális tagfüggvényeket (Rule of 0), ha nyers erőforrást kezelünk, mind az ötöt adjuk meg (Rule of 5), és soha ne keverjük a kézi destruktort a default move tagfüggvényekkel anélkül, hogy ismernénk a generálási szabályokat. A CRTP statikus polimorfizmust biztosít, amely fordítási időben oldja fel a hívást, és hatékony kódújrafelhasználást tesz lehetővé, de a típusok fordítási időben rögzítve vannak, és a kódméret nőhet.

Mindhárom idióma a karbantarthatóságot szolgálja, de csak akkor, ha pontosan értjük a mögöttük húzódó nyelvi szabályokat, és a költségeiket méréssel igazoljuk. A labor során készített idiómakatalógus nemcsak a technikák működését mutatja be, hanem azt is, hogyan lehet a fordítási időt, bináris méretet és futási teljesítményt reprodukálható módon összehasonlítani.

Önellenőrző kérdés: Miért kell a Pimpl-t használó osztály destruktorát a forrásfájlban definiálni? Mi történne, ha a headerben adnánk meg a destruktort = default-ként? (Válasz: a headerben generált destruktor az std::unique_ptr<Impl> destruktorát hívná, amely static_assert-t végez a teljes Impl típusra, de a headerben az Impl csak előre deklarált, így fordítási hibát kapnánk. A definíciót a .cpp-ben kell elhelyezni, ahol az Impl teljes definíciója látható.)
