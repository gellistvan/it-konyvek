4.2 Move szemantika, RVO és Rule of 0/3/5

A move szemantika a C++11 egyik legfontosabb nyelvi újítása, amely lehetővé teszi az erőforrások átvételét másolás helyett. Alapja az rvalue referencia (T&&) és az a felismerés, hogy a temporális objektumok erőforrásait biztonságosan el lehet lopni, mert a forrás objektumra a kifejezés kiértékelése után többé nincs szükség. A move nem új művelet, hanem túlterhelések és castok kombinációja: a megfelelő túlterhelés kiválasztását az értékkategória, a tényleges erőforrásátvételt pedig a move konstruktor vagy move assignment operátor végzi el.

Az előző alfejezetben (4.1) megismertük az értékkategóriákat: a prvalue, xvalue, glvalue, lvalue és rvalue fogalmát. A move szemantika szempontjából a legfontosabb az rvalue referencia, amely kizárólag rvalue-hoz kötődhet. Ha egy kifejezés rvalue, akkor a fordító a T&& paraméterű túlterhelést választja a const T& helyett. A std::move ezt a választást befolyásolja, de önmagában nem mozgat semmit: csupán egy feltétel nélküli rvalue-referenciára (X&&) történő castot hajt végre, ahol X az argumentum referencia nélküli típusa. Ennek megértése kulcsfontosságú a helyes C++ kód írásához.

4.2.1 A move konstruktor és a move assignment

Tegyük fel, hogy van egy Buffer osztályunk, amely dinamikusan lefoglalt karaktertömböt kezel. A klasszikus másoló konstruktor új memóriát foglal, majd elemenként átmásolja a tartalmat. A move konstruktor ezzel szemben egyszerűen átveszi a másik objektum mutatóját és méretét, a forrás objektumot pedig üres, de érvényes állapotba hozza.

#include <cstddef>
#include <algorithm>
#include <utility>

class Buffer {
    char* data_;
    std::size_t size_;
public:
    // Konstruktor
    explicit Buffer(std::size_t size)
        : data_(new char[size]()), size_(size) {}  // () : nullázott tartalom

    // Copy konstruktor
    Buffer(const Buffer& other)
        : data_(new char[other.size_]), size_(other.size_) {
        std::copy(other.data_, other.data_ + size_, data_);
    }

    // Move konstruktor
    Buffer(Buffer&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)) {}

    // Copy assignment: előbb másol, aztán cserél (erős garancia)
    Buffer& operator=(const Buffer& other) {
        if (this == &other) return *this;
        Buffer tmp(other);               // ha a foglalás dob, *this érintetlen
        std::swap(data_, tmp.data_);     // nem dobó csere; a régi puffert
        std::swap(size_, tmp.size_);     // a tmp destruktora szabadítja fel
        return *this;
    }

    // Move assignment
    Buffer& operator=(Buffer&& other) noexcept {
        if (this == &other) return *this;
        delete[] data_;
        data_ = std::exchange(other.data_, nullptr);
        size_ = std::exchange(other.size_, 0);
        return *this;
    }

    ~Buffer() { delete[] data_; }
};

A másoló konstruktor a new char[size]() értékinicializálás miatt nullázott puffert másol; az üres vagy már mozgatott forrás másolása (data_ == nullptr, size_ == 0) külön tesztesetet érdemel. (A nullptr + 0 kifejezés a C++20-ban érvényes, ezért az std::copy ilyenkor nem hiba.) A copy assignment a „előbb foglal és másol, aztán cserél” (copy-and-swap) mintát követi: az ideiglenes tmp létrehozása dobhat kivételt, de ekkor *this még érintetlen, így az operátor erős kivételgaranciát ad. A korábbi „előbb delete[] data_, aztán new” változat hibás lenne: ha a new kivételt dob, a data_ felszabadított címen maradna, és a destruktor másodszor is delete[]-et hívna (dupla felszabadítás).

A move konstruktor paramétere Buffer&&, amely csak rvalue-hoz kötődik. A std::exchange segítségével egyszerűen és kivételbiztosan adjuk át az erőforrást, és a forrás objektumot egyidejűleg alapállapotba tesszük. A move assignment operátor először felszabadítja a jelenlegi erőforrást, majd átveszi a másik objektum erőforrását. A noexcept specifikáció kiemelten fontos: ha a move konstruktor nem garantáltan kivételmentes, de az elem másolható, a std::vector reallocation során a std::move_if_noexcept miatt a másoló konstruktorra esik vissza. (Csak mozgatható típusnál a vektor a dobhatós move-ot használja, gyengébb kivételgaranciával; ez a konkrét szabály a vector-ra vonatkozik, nem minden konténerre.) A move assignmentben a this == &other ellenőrzés egy lehetséges megoldás; más helyes implementáció is létezik (például csere alapú), a lényeg, hogy a self-move ne rontsa el az objektumot. A részletesebb magyarázatot a hibákról szóló szakaszban találjuk.

Az implicit move konstruktor és assignment operátor akkor generálódik, ha az osztálynak nincs felhasználó által deklarált destruktora, copy konstruktora, copy assignment operátora, move konstruktora vagy move assignment operátora. Ebben az esetben a fordító minden tagot (és bázist) tagonként mozgat; ha egy tagnak nincs használható move művelete, a túlterhelésfeloldás az adott tag másoló műveletét választja. Ha viszont a defaultolt move művelet törölt lenne (például mert valamelyik tag move-ja = delete), a szabvány ([class.copy.ctor]/10) szerint a túlterhelésfeloldás figyelmen kívül hagyja, és a másolás fut le; ez különbözik az explicit = delete jelölt move-tól, amely részt vesz a feloldásban, és rvalue-ból másolást is megakadályoz. A primitív típusok (int, double, mutatók) esetében a mozgatás ugyanaz, mint a másolás.

A move konstruktor és a move assignment operátor közötti különbség hasonló a copy megfelelőikéhez: a konstruktor egy új objektumot épít fel a forrás erőforrásainak átvételével, az assignment operátor pedig egy már létező objektumot állít át. A szabványos könyvtár típusainál a forrás érvényes, de meghatározatlan állapotban marad; saját típusnál ezt a garanciát nekünk kell vállalnunk és dokumentálnunk (a Buffer esetében a nullptr/0 állapot). A destruktornak mindig hívhatónak kell lennie, és az előfeltétel nélküli műveletek (értékadás, size()) továbbra is használhatók.

4.2.2 Rule of 0, Rule of 3, Rule of 5

A C++ alapvető osztálytervezési irányelvei közé tartoznak a „Rule of 0”, „Rule of 3” és „Rule of 5” néven ismert szabályok. Ezek segítenek elkerülni a memóriakezelési hibákat és az erőforrás-szivárgást.

Rule of 0 (nulladik szabály) szerint ha egy osztály nem kezel közvetlenül erőforrást, akkor ne deklaráljunk benne destruktort, copy konstruktort, copy assignment operátort, move konstruktort vagy move assignment operátort. A tagok és azok típusai (például std::string, std::vector, std::unique_ptr) felelnek a saját erőforrásaikért, így a generált műveletek helyesen fognak viselkedni. Ez a szabály a modern C++ alapvető ajánlása: a kompozíció biztosítja a helyes működést, és kevesebb kód kevesebb hibalehetőséget jelent.

Rule of 3 (hármas szabály) azt mondja, hogy ha egy osztálynak szüksége van egyéni destruktorra, copy konstruktorra vagy copy assignment operátorra, akkor valószínűleg mindháromra szüksége van. A hátteret az erőforrás-kezelés adja: ha például dinamikus memóriát foglalunk, akkor a destruktornak fel kell szabadítania, a copy konstruktornak mély másolatot kell készítenie, a copy assignmentnek pedig a régi erőforrást fel kell szabadítania és a másik erőforrásáról mély másolatot kell készítenie. Ha bármelyik hiányzik, az dupla felszabadításhoz, szivárgáshoz vagy sekély másoláshoz vezethet.

Rule of 5 (ötös szabály) a C++11 óta kiegészíti a hármas szabályt: ha az osztály a copy műveletek vagy a destruktor miatt erőforrást kezel, akkor érdemes a move konstruktort és a move assignment operátort is megvalósítani. A move műveletek lehetővé teszik, hogy az erőforrás átadásakor elkerüljük a felesleges másolást, ami különösen konténerekben és temporálisok esetén jelentős teljesítményjavulást hozhat. Ha az osztály nem másolható (például std::unique_ptr-et tartalmaz), akkor a copy műveletek törölhetők, de a move műveleteket érdemes megtartani.

A generálási szabályok pontosak: ha az osztályban van felhasználó által deklarált destruktor, akkor a move konstruktor és move assignment nem generálódik implicit módon. A copy konstruktor és copy assignment azonban továbbra is implicit generálható, de ez a viselkedés C++11 óta deprecated, és a fordítók figyelmeztethetnek. Ha az osztályban van felhasználó által deklarált move konstruktor vagy move assignment, akkor a copy műveletek töröltként (deleted) viselkednek, kivéve, ha expliciten deklaráljuk őket. Ezért a Rule of 5 azt javasolja, hogy ilyenkor mind az öt műveletet expliciten kezeljük: vagy megvalósítjuk, vagy =default/=delete specifikációval jelezzük.

Az =default és =delete használatával szabályozhatjuk a generált függvényeket. Például:

class NonCopyable {
public:
    NonCopyable() = default;
    NonCopyable(const NonCopyable&) = delete;
    NonCopyable& operator=(const NonCopyable&) = delete;
    NonCopyable(NonCopyable&&) = default;
    NonCopyable& operator=(NonCopyable&&) = default;
};

Ez az osztály mozgatható, de nem másolható. Három különböző eset különítendő el.

  • Ha a move műveleteket nem deklaráljuk, de van felhasználó által deklarált copy konstruktor, copy értékadás vagy destruktor (ezért implicit move nem keletkezik), az rvalue-ból a copy konstruktor másol, mert a const T& rvalue-hoz is kötődik. Ez a „csak másolható” típus helyes megoldása. (Ha semmi sincs felhasználó által deklarálva, a fordító implicit move-ot generál, és az rvalue mozgatódik – ez a Rule of 0 esete.)
  • Ha a move konstruktort explicit = delete-tel töröljük, a törölt függvény részt vesz a túlterhelésfeloldásban, és az rvalue-ra az nyer: a T t = std::move(other); fordítási hiba („use of deleted function”). Ráadásul a move konstruktor deklarálása (akár törölve is) a copy konstruktort implicit módon törli. Az rvalue-ból másolás tehát nem esik vissza a const T&-re.
  • Ha a defaultolt move törölt lenne (például nem mozgatható tag miatt), a túlterhelésfeloldás figyelmen kívül hagyja, és a másolás fut le.

A „csak másolható” típushoz ezért a move műveleteket egyszerűen ne deklaráljuk; ne töröljük őket.

4.2.3 Copy elision, RVO és NRVO

A copy elision (másoláselhagyás) egy fordítóoptimalizálás, amely lehetővé teszi, hogy bizonyos helyzetekben a másoló vagy move konstruktor hívása elmaradjon. A C++17 óta egyes esetekben ez nem csak optimalizálás, hanem kötelező nyelvi szabály.

RVO (Return Value Optimization): amikor a függvény egy prvalue-t ad vissza, például return T(...);, az objektum közvetlenül a hívó kontextusában épül fel, ideiglenes és másoló/move konstruktor nélkül. A C++17 óta ez nem optimalizáció, hanem garantált nyelvi szabály (lásd lentebb); az RVO név történeti, a C++11/14 gyakorlatból maradt meg.

NRVO (Named Return Value Optimization) akkor fordul elő, ha egy lokális, névvel rendelkező objektumot adunk vissza:

Buffer make_buffer() {
    Buffer local(1024);
    // ...
    return local;
}

A NRVO során a fordító a lokális local objektumot közvetlenül a hívó kontextusában foglalhatja le, így nincs másolás vagy mozgatás. A NRVO nem kötelező, de a modern fordítók (GCC, Clang, MSVC) általában elvégzik optimizált build esetén. A szabvány megköveteli, hogy a copy vagy move konstruktor elérhető legyen, mert a kódnak fordítania kellene akkor is, ha az elision nem történik meg. Ez fontos különbség a prvalue esetéhez képest.

A C++17-ben bevezetett guaranteed copy elision azt jelenti, hogy bizonyos esetekben a másolás vagy mozgatás nem csak elhagyható, hanem kötelezően nem történik meg. Ilyen például, amikor egy prvalue-t használunk egy objektum inicializálására:

T t = T(); // nincs másolás vagy mozgatás

Ilyenkor a T() prvalue-t közvetlenül a t létrehozására használjuk, és a copy/move konstruktor nem hívódik meg, még akkor sem, ha törölt. Hasonlóan, a return T(); sem hív másoló vagy move konstruktort: a hívó oldali objektum mezői közvetlenül inicializálódnak. Ez azt is jelenti, hogy az alábbi osztály C++17-ben lefordul, bár nem másolható és nem mozgatható:

struct NonMovable {
    NonMovable() = default;
    NonMovable(const NonMovable&) = delete;
    NonMovable(NonMovable&&) = delete;
};

NonMovable make() { return NonMovable{}; } // OK C++17-től

A copy elision tehát két szinten működik: a garantált prvalue elision a nyelv része, míg a NRVO a fordítási időben alkalmazott optimalizálás. Mindkettő célja a felesleges erőforrás-mozgatások elkerülése.

Az implicit move a return utasításban azt jelenti, hogy ha egy lokális változót vagy egy érték szerinti paramétert adunk vissza, akkor a fordító automatikusan rvalue-nak tekinti, így a move konstruktort választja, ha az elérhető, és a copy elision nem valósul meg. Ezt a viselkedést a C++11 vezette be, és a legtöbb esetben kívánatos. Ha a típusnak nincs deklarált move konstruktora (például mert felhasználó által deklarált copy konstruktora van), a const T& paraméterű copy konstruktor választódik. Ha viszont a move konstruktor explicit = delete, a return local; fordítási hiba – nincs visszaesés a copy-ra. (A szabályt a C++20 [P1825] kiterjesztette, a C++23 [P2266] pedig egyszerűsítette: a visszaadott lokális név xvalue.)

A std::move explicit használata a return utasításban (return std::move(local);) általában hiba, mert megakadályozza az NRVO-t, és move konstruktor-hívást kényszerít ki. Ez ritkán indokolt; ha a lokális objektumot tovább akarjuk adni egy másik függvénynek, akkor természetesen szükséges a std::move.

4.2.4 Gyakori hibák és csapdák

A move szemantika helyes használata számos buktatót rejt, amelyeket fontos felismerni.

A std::move nem mozgat, hanem castol. Ez az egyik leggyakoribb félreértés. A std::move definíciója lényegében static_cast<std::remove_reference_t<T>&&>(x) (nem-referencia X-re static_cast<X&&>(x)), tehát csak az értékkategóriát változtatja meg. A tényleges erőforrásátvételt a meghívott move konstruktor vagy move assignment operátor végzi. Ezért ha egy osztálynak nincs move konstruktora, a std::move után is a copy konstruktor hívódik, feltéve, hogy az elérhető.

A move konstruktor noexcept hiánya. A std::vector reallocation során az erős kivételgaranciát tartja meg: ha az elem másolható, és a move konstruktora nem noexcept, a std::move_if_noexcept miatt a copy konstruktort hívja, ami jelentős teljesítménycsökkenést eredményezhet. Például (GCC, -std=c++20; a viselkedés a vector követelménye, a számok a példa saját számlálói):

#include <cstdio>
#include <vector>

struct Widget {
    static inline int copies = 0, moves = 0;
    Widget() = default;
    Widget(const Widget&) { ++copies; }
    Widget(Widget&&) { ++moves; }   // nem noexcept
};

int main() {
    std::vector<Widget> v;
    v.reserve(1);
    v.emplace_back();   // size == capacity == 1
    v.emplace_back();   // reallokáció: a meglévő elem átkerül az új tárba
    std::printf("copies=%d moves=%d\n", Widget::copies, Widget::moves);
    // várt (és egy futtatott GCC 15.2 -O2 fordítással egyezően):
    // copies=1 moves=0
}

A második emplace_back kapacitásnövelést vált ki (a reserve(1) miatt biztosan), és a nem noexcept move helyett a copy konstruktor hívódik. Ha a típus nem másolható (a move deklarálása a copy-t törli), a vector a dobhatós move-ot használja, gyengébb kivételgaranciával. Ezért a move műveleteket mindig noexcept-nek kell jelölni, ha valóban nem dobhatnak kivételt.

A moved-from objektum állapota. A move után a forrás objektum érvényes, de meghatározatlan állapotú. Ez azt jelenti, hogy a destruktor hívható, az értékadás megengedett, és az előfeltétel nélküli műveletek (például size(), clear()) is végrehajthatók. Például a Buffer osztályban a data_ nullptr lesz, a size_ pedig 0, így a destruktor biztonságosan hívható delete[]-val. Nem a moved-from állapot önmagában okoz UB-t, hanem az előfeltételt igénylő műveletek: például egy üres std::vector front() hívása definiálatlan viselkedés. A kiolvasott érték tehát nem támaszkodhat a korábbi tartalomra.

Self-move assignment. A b1 = std::move(b1); kifejezés veszélyes, mert a move assignment operátor gyakran először felszabadítja a jelenlegi erőforrást, majd átveszi a forrás erőforrását. Ha a forrás és a cél ugyanaz az objektum, akkor a saját erőforrását felszabadítanánk, majd a felszabadított mutatót használnánk. Ezért a move assignment operátornak a self-move esetet kezelnie kell – például a this != &other ellenőrzéssel (ahogy a fenti példában), vagy olyan csere alapú implementációval, amely önmagára alkalmazva is érvényes állapotot hagy.

A const tagok és a referencia tagok. Ha egy osztály const tagot tartalmaz, a move konstruktor nem tudja azt mozgatni, mert a const tagból nem lehet ellopni az erőforrást; a move konstruktor ilyenkor másolni fogja azt a tagot. Hasonlóan, a referencia tagok nem rendelhetők át, így a move assignment operátor nem generálható implicit módon, és saját implementációra vagy =delete-re van szükség.

A virtuális destruktor hatása. Ha egy bázisosztálynak virtuális destruktora van, az felhasználó által deklarált destruktornak számít, ami letiltja az implicit move műveleteket. Ez azonban csak az adott (bázis)osztály implicit move műveleteit nyomja el. A leszármazott osztály, ha maga nem deklarál destruktort vagy copy/move műveletet, kap implicit move műveleteket, de azok a bázis-részobjektumot másolják, mert a bázisnak nincs move-ja. Ha a bázis is mozgatható legyen, a bázisban kell a műveleteket kiírni (Base(Base&&) = default; stb., Rule of 5), és a generálási szabályt osztályonként kell alkalmazni, nem egyetlen kódmintát tanítani.

A std::unique_ptr és a move. A std::unique_ptr nem másolható, csak mozgatható. A mozgatása noexcept, így a std::vector<std::unique_ptr<int>> elemeinek áthelyezésekor a move konstruktor hívódik, ami hatékony. Ez jól mutatja a Rule of 0 előnyét: ha egy osztály std::unique_ptr-et tartalmaz, akkor a generált move műveletek helyesen viselkednek.

4.2.5 Labor: move- és copy-viselkedés mérése

A labor célja, hogy reprodukálható módon mérjük meg a másolások és mozgatások számát egy std::vector feltöltése során, és összehasonlítsuk a copy elision be- és kikapcsolásával.

Feladat: Készítsünk egy Instrumented osztályt, amely globális számlálókkal követi a copy konstruktor, move konstruktor, copy assignment és move assignment hívásait. A számlálókat static inline int tagokkal valósítjuk meg, hogy osztálydefinícióban inicializálhatók legyenek.

#include <cassert>
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

struct Instrumented {
    static inline int copy_ctor_count = 0;
    static inline int move_ctor_count = 0;
    static inline int copy_assign_count = 0;
    static inline int move_assign_count = 0;

    std::string data;

    explicit Instrumented(const std::string& s) : data(s) {}

    Instrumented(const Instrumented& other) : data(other.data) {
        ++copy_ctor_count;
    }

    Instrumented(Instrumented&& other) noexcept
        : data(std::move(other.data)) {
        ++move_ctor_count;
    }

    Instrumented& operator=(const Instrumented& other) {
        if (this != &other) {
            data = other.data;
            ++copy_assign_count;
        }
        return *this;
    }

    Instrumented& operator=(Instrumented&& other) noexcept {
        if (this != &other) {
            data = std::move(other.data);
            ++move_assign_count;
        }
        return *this;
    }

    ~Instrumented() = default;
};

Instrumented make_inst() {
    Instrumented local{"named"};
    return local; // NRVO-képes
}

void reset_counters() {
    Instrumented::copy_ctor_count = 0;
    Instrumented::move_ctor_count = 0;
    Instrumented::copy_assign_count = 0;
    Instrumented::move_assign_count = 0;
}

void test_guaranteed_elision() {
    reset_counters();
    Instrumented inst2 = Instrumented{"other"};
    // C++17 garantált elision: sem copy, sem move ctor nem hívódik
    // (a -fno-elide-constructors sem változtat ezen).
    assert(Instrumented::copy_ctor_count == 0);
    assert(Instrumented::move_ctor_count == 0);
    (void)inst2;
}

int main() {
    reset_counters();

    std::vector<Instrumented> v;
    v.reserve(10);

    // A prvalue materializálódik egy temporálisba, majd a push_back(T&&)
    // a vektor tárterületére move konstruktorral hozza létre az elemet.
    v.push_back(Instrumented{"first"});

    // A make_inst() visszatérése NRVO-val elhagyható (nem kötelező);
    // a temporálisból a vektorba történő beillesztés mindenképp move.
    v.push_back(make_inst());

    // A reserve(10) miatt nincs reallocation. A számlálókat kiírjuk, hogy
    // a mért értékek a naplóba kerülhessenek.
    std::printf("copy=%d move=%d copy_assign=%d move_assign=%d\n",
                Instrumented::copy_ctor_count, Instrumented::move_ctor_count,
                Instrumented::copy_assign_count, Instrumented::move_assign_count);

    // Konfigurációfüggő várt érték: NRVO-val 2 move, NRVO nélkül
    // (-fno-elide-constructors) 3 move (első beillesztés, a névvel
    // rendelkező lokális visszaadása, második beillesztés).
    assert(Instrumented::copy_ctor_count == 0);
    assert(Instrumented::move_ctor_count == 2 || Instrumented::move_ctor_count == 3);

    test_guaranteed_elision();
    return 0;
}

A labor feladata, hogy a fenti kódot lefordítsa a megadott környezetben, és rögzítse a kiírt számlálók értékeit (a program a printf sorban jelenti őket). A méréshez használjunk naplófájlt, amelyben elkülönítjük a mért és a várt értékeket. Minden önálló mérés előtt nullázzuk a számlálókat (reset_counters()).

Buildelési utasítások:

  • GCC 13.2 (Linux, x86-64):
    g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -o lab_move lab_move.cpp
  • Clang 17 (Linux, x86-64):
    clang++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -fsanitize=address,undefined -o lab_move lab_move.cpp
  • MSVC 2022 (Windows, x64):
    cl /std:c++20 /O2 /W4 /EHsc /fsanitize=address /Fe:lab_move.exe lab_move.cpp

A copy elision kikapcsolásához GCC/Clang esetén adjuk hozzá a -fno-elide-constructors kapcsolót. MSVC-nél az NRVO a /Zc:nrvo- kapcsolóval tiltható (/Zc:nrvo engedélyezi); a garantált elision azonban C++17-ben nem kapcsolható ki.

A várt értékeket a szabvány és a fordító viselkedése alapján határozzuk meg. A garantált copy elision a Instrumented{"other"} közvetlen inicializálásakor érvényesül (nincs copy/move), de a push_back esetében a paraméter T&&, ezért a temporálisból a vektorba egy move konstruktor fut. A reserve(10) miatt nincs reallocation; a két push_back így két move konstruktort és nulla copy konstruktort eredményez. A -fno-elide-constructors mellett a make_inst() NRVO-ja elmarad, ezért ott három move konstruktor a várt; a feltétel nélküli == 2 assert itt elbukna, ezért a kód az == 2 || == 3 ellenőrzést használja. (A gyakorló tanári ellenőrzés során egy GCC 15.2, -std=c++20 -O2 fordítás 0 copy / 2 move, -fno-elide-constructors mellett 0 copy / 3 move értéket adott; a hallgatói mérést a megadott fordítókkal kell elvégezni és a naplóba írni.)

Teszteset: a main végén meghívott test_guaranteed_elision() (lásd a fenti kódot) azt ellenőrzi, hogy a Instrumented inst2 = Instrumented{"other"}; inicializálás sem copy, sem move konstruktort nem hív. A labor jegyzőkönyvében rögzíteni kell, hogy a program lefutott (nem esett el az assert), és a mért értékek megegyeznek a konfigurációnak megfelelő vártakkal. Az assert -DNDEBUG mellett kikapcsol, ezért a méréshez ne használjuk azt.

4.2.6 Önellenőrző kérdés

Kérdés: Magyarázd el, miért nem mozgat a std::move, és mi történik, ha a move konstruktor nem noexcept egy std::vector reallocation során. Mi a különbség a garantált copy elision és a NRVO között abból a szempontból, hogy a move konstruktornak elérhetőnek kell-e lennie?

Megoldás vázlata: a std::move csak egy rvalue-referenciára (X&&) történő cast; a tényleges átvételt a kiválasztott move művelet végzi. Ha a move konstruktor nem noexcept és az elem másolható, a vector reallokációkor a copy konstruktort használja (move_if_noexcept); csak mozgatható típusnál a dobhatós move-ot, gyengébb garanciával. A garantált copy elision (C++17, prvalue) esetén a move/copy konstruktornak nem kell elérhetőnek lennie; az NRVO nem kötelező, ezért ott a konstruktornak elérhetőnek kell lennie.

4.2.7 Összefoglalás

  • A std::move cast; a mozgatást a move műveletek végzik, és noexcept-nek kell lenniük.
  • A copy assignmentet előbb másolva, aztán cserélve érdemes írni (erős garancia).
  • Az explicit = delete move rvalue-ból másolást is tilt; a „csak másolható” típushoz a move-ot nem deklaráljuk.
  • A prvalue elision C++17-től garantált, az NRVO nem; a labor várt értékei konfigurációfüggők.
