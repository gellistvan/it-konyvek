26.4 Tesztelés, property-based testing és CI

A helyesség és a biztonság folyamatos ellenőrzése nem egyszeri audit, hanem a fejlesztési ciklusba épített, minden változtatásra kiterjedő visszajelzési folyamat. A C++ különösen érzékeny erre, mert az undefined behavior (UB), a memóriakezelési hibák és a konkurencia problémái gyakran csak adott platformon, adott optimalizációs szinten vagy adott ütemezés mellett jelentkeznek. A 26.2 alfejezetben bemutatott sanitizerek és statikus elemzők, valamint a 26.3 hardening-technikái a hiba detektálására szolgálnak; ebben az alfejezetben azt vizsgáljuk, hogyan válik ez a detektálás folyamatos, reprodukálható és a fejlesztési folyamatba szervesen illeszkedő ellenőrzéssé. A cél nem csupán a tesztek megírása, hanem egy olyan csővezeték kialakítása, amely a hibákat a lehető legkorábban, a lehető legkisebb költséggel fogja meg, és a mért eredményeket elkülönítve dokumentálja a várt értékektől.

A folyamatos ellenőrzés három pillére: a determinisztikus unit és property tesztek, a generált bemenetekkel dolgozó fuzz tesztek, valamint a lefedettség- és regresszióelemzés egy automatizált CI-környezetben. Mindhárom más-más hibát tár fel, és együttesen adnak védelmet a helyesség és a biztonság szempontjából.

26.4.1 A tesztpiramis és a folyamatos visszajelzés

A klasszikus tesztpiramis alján a gyors, izolált unit tesztek állnak; középen az integrációs tesztek, a csúcson pedig a lassú, de átfogó rendszer- és end-to-end tesztek. C++-ban ezt a képet kiegészítik a fordítási időben futó tesztek, a sanitizer-futtatások, a fuzz tesztek és a statikus elemzés. Az alfejezet a piramis aljára, valamint a folyamatos integrációra összpontosít, mert ezek adják a leggyorsabb visszajelzést, és ezekből lehet a legtöbb hibát a legolcsóbban kijavítani.

A folyamatos ellenőrzés azt jelenti, hogy minden commit, minden pull request és minden éjszakai build ugyanazt a pipeline-t futtatja. Ennek előfeltétele a reprodukálhatóság: rögzített fordítóverzió, rögzített szabványverzió, rögzített függőségek, rögzített buildkapcsolók és determinisztikus tesztvégrehajtás. Ha egy teszt csak a fejlesztő gépén fut le, az nem tekinthető folyamatos ellenőrzésnek. A CI-ben a „nálam futott” kifejezés helyettesítése a „a pipeline ezen a konfiguráción, ezen a kódon, ezzel a naplóval zöld” állítás.

26.4.2 Unit tesztek: a determinisztikus alap

A unit teszt a legkisebb viselkedési egységet ellenőrzi, elszigeteli a környezetétől, és determinisztikusan, gyorsan lefut. C++-ban a unit tesztek különösen fontosak az osztályinvariánsok, a kivételbiztonság és az élettartam-kezelés ellenőrzésére. A tesztkeretek – például a GoogleTest, a Catch2, a doctest vagy a Boost.Test – eltérő makrókat és funkciókat kínálnak, de a cél közös: egyetlen sikertelen feltétel esetén a teszt bukjon meg, és a hibaüzenet azonosítsa a fájlt, a sort, valamint a tényleges és várt értéket.

A következő példa egy egyszerű, sablonos fixed_capacity_stack osztályt mutat be, amelyet a további tesztelési rétegek is használnak. Az osztály std::unique_ptr<T[]> tárolót használ, rögzített kapacitással, és a túlcsordulást, illetve az alulcsordulást kivétellel jelzi.

// fixed_capacity_stack.hpp
#pragma once
#include <cstddef>
#include <memory>
#include <stdexcept>
#include <utility>

template <typename T>
class fixed_capacity_stack {
public:
    explicit fixed_capacity_stack(std::size_t capacity)
        : capacity_(capacity), size_(0), data_(std::make_unique<T[]>(capacity)) {}
    // Megjegyzés: a make_unique<T[]> minden slotot létrehoz (T default-konstrukció),
    // ezért ez nem igazi „fixed capacity” tároló, hanem előre foglalt, értékadással töltött puffer.

    fixed_capacity_stack(const fixed_capacity_stack&) = delete;
    fixed_capacity_stack& operator=(const fixed_capacity_stack&) = delete;

    bool empty() const noexcept { return size_ == 0; }
    bool full() const noexcept { return size_ == capacity_; }
    std::size_t size() const noexcept { return size_; }
    std::size_t capacity() const noexcept { return capacity_; }

    void push(const T& value) {
        if (full()) throw std::out_of_range("fixed_capacity_stack::push: stack is full");
        data_[size_] = value;   // a méret csak sikeres értékadás után nő
        ++size_;
    }

    void push(T&& value) {
        if (full()) throw std::out_of_range("fixed_capacity_stack::push: stack is full");
        data_[size_] = std::move(value);
        ++size_;
    }

    T pop() {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::pop: stack is empty");
        T result = std::move(data_[size_ - 1]);   // ha a move dob, a méret nem változik
        --size_;
        return result;
    }

    const T& top() const {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::top: stack is empty");
        return data_[size_ - 1];
    }

    T& top() {
        if (empty()) throw std::out_of_range("fixed_capacity_stack::top: stack is empty");
        return data_[size_ - 1];
    }

private:
    std::size_t capacity_;
    std::size_t size_;
    std::unique_ptr<T[]> data_;
};

Ez a kód C++17 és C++20 alatt is fordítható, de a T típustól több kell, mint a másolhatóság: a std::make_unique<T[]>(capacity) miatt a T-nek default-konstruálhatónak kell lennie, és minden slot azonnal létrejön; a push(const T&) másoló, a push(T&&) mozgató értékadást használ. A törölt másolás miatt implicit mozgatás sincs. A size_ csak a sikeres értékadás után nő, így egy dobó értékadás után nem számít bele logikailag hibás elem; a célslot T értéke azonban részlegesen módosulhat (alap garancia az elemre). A pop a slot értékét kimozgatja, majd csökkenti a méretet: ha a move dob, a méret nem változik; a slot T objektuma a pop után nem pusztul el, erőforrása a felülírásig vagy a tároló destrukciójáig megmaradhat. Az erős kivételgarancia a pop visszatérési értékének átadásánál is csak nem dobó move (std::is_nothrow_move_constructible_v<T>) esetén teljesül; valódi konténerszerű élettartamhoz külön konstrukció/destrukció (például nyers tár és placement new) kellene. A példa a tesztelést szemlélteti; a tesztterv része a dobó T, az erőforrást tartó T, a nulla kapacitás, az üres/telt műveletek és a mozgatási szándék.

A unit tesztek ezen az osztályon a következők lehetnek. A példa a doctest keret szintaxisát használja; a pontos include-ok és makrók a keret verziójától függenek, ezért a futtatás előtt ellenőrizzük a dokumentációt (a példa nem futtatott).

#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include <doctest/doctest.h>
#include "fixed_capacity_stack.hpp"

TEST_CASE("fixed_capacity_stack alapvető műveletek") {
    fixed_capacity_stack<int> stack(3);
    REQUIRE(stack.empty());
    REQUIRE(!stack.full());
    stack.push(1);
    stack.push(2);
    REQUIRE(stack.top() == 2);
    REQUIRE(stack.size() == 2);
    REQUIRE(stack.pop() == 2);
    REQUIRE(stack.pop() == 1);
    REQUIRE(stack.empty());
}

// Névtér-hatókörben: lokális osztálynak nem lehet statikus adattagja.
namespace {
struct Thrower {
    int v = 0;
    static inline bool armed = false;
    Thrower() = default;
    Thrower(const Thrower&) = default;
    Thrower& operator=(const Thrower& o) {
        if (armed) throw std::runtime_error("copy assignment failed");
        v = o.v;
        return *this;
    }
};
}  // namespace

TEST_CASE("fixed_capacity_stack: dobó értékadás után a méret nem változik") {
    fixed_capacity_stack<Thrower> stack(2);
    Thrower t;
    Thrower::armed = true;
    REQUIRE_THROWS_AS(stack.push(t), std::runtime_error);
    Thrower::armed = false;
    REQUIRE(stack.size() == 0);
}

TEST_CASE("fixed_capacity_stack túlcsordulás kivételt dob") {
    fixed_capacity_stack<int> stack(1);
    stack.push(42);
    REQUIRE_THROWS_AS(stack.push(43), std::out_of_range);
    REQUIRE(stack.top() == 42);
}

A keretek eltérő szabályokat követnek. A doctest/Catch2 REQUIRE makrója hamis feltételnél kivétellel megszakítja a tesztesetet, a CHECK rögzíti a hibát és a teszt tovább fut. A GoogleTest ASSERT_* makrója csak a jelenlegi függvényből tér vissza (segédfüggvényből nem szakítja meg automatikusan a teljes tesztet), az EXPECT_* pedig folytat. Fatal ellenőrzést ott érdemes használni, ahol a bukás után a folytatás már nem értelmes (például elbukott erőforrás-létrehozás), nem pusztán azért, mert az elvárás fontos. A halálozási teszt (death test) olyan kódot futtat, amelynek meg kell szakadnia (például assert vagy std::terminate); ez nem minden keret beépített szolgáltatása: a GoogleTest EXPECT_DEATH/ASSERT_DEATH makrói támogatják (külön folyamatban vagy klónozással, platformkorlátokkal), a doctest és a Catch2 nem, ott külön folyamatot kell indítani (például CTest WILL_FAIL vagy saját segédprogram).

26.4.3 Property-based testing: tulajdonságok és generátorok

A property-based testing a unit tesztek általánosítása: nem egyetlen konkrét bemenetre írunk elvárást, hanem egy tulajdonságot, amely a bemenetek egy egész osztályára igaz. A keret véletlenszerű bemeneteket generál, és ellenőrzi a tulajdonságot; ha hibát talál, a legegyszerűbb ellenpéldára zsugorítja (shrink), hogy a hibajavítás könnyű legyen. A C++-ban az egyik elterjedt eszköz a RapidCheck, amelynek pontos API-ja és szabványtámogatása verziófüggő; az alábbi példa a szemléltetést szolgálja, nem helyettesíti a dokumentációt.

A property-based teszt ereje abban rejlik, hogy a specifikációból származó algebrai törvényeket ellenőrzi, nem pedig az implementáció konkrét kimenetét. A verem esetében ilyen tulajdonságok:

  • LIFO: tetszőleges vektor elemeit sorban beszúrva (push), majd mindet kivéve (pop) a fordított sorrendet kapjuk.
  • Méretinvariáns: a verem mérete mindig 0 és a kapacitás között van, és a méret a sikeres push és pop hívások számának különbsége.
  • Mellékhatás-mentesség és méretváltozás: a top nem változtatja a méretet (ez nem idempotencia, hanem mellékhatás-mentesség), a sikeres pop eggyel csökkenti. A pop nem idempotens; a tulajdonságok nem közös törvény.
  • Telítettség: ha a verem tele van, a push kivételt dob; ha üres, a pop kivételt dob.

A következő példa a RapidCheck szintaxisával írja meg ezeket a tulajdonságokat:

#include <cstddef>
#include <vector>
#include <rapidcheck.h>
#include "fixed_capacity_stack.hpp"

int main() {
    // Minden property eredménye az összesítésbe kerül (nincs rövidzár: mind lefut).
    bool ok = true;

    ok &= rc::check("LIFO property", [](const std::vector<int>& input) {
        fixed_capacity_stack<int> stack(input.size() + 1);
        for (int x : input) stack.push(x);
        for (auto it = input.rbegin(); it != input.rend(); ++it) {
            RC_ASSERT(stack.pop() == *it);
        }
        RC_ASSERT(stack.empty());
    });

    ok &= rc::check("size property", [](const std::vector<int>& input) {
        fixed_capacity_stack<int> stack(input.size() + 1);
        std::size_t expected = 0;
        for (int x : input) {
            stack.push(x);
            ++expected;
            RC_ASSERT(stack.size() == expected);
        }
        while (!stack.empty()) {
            (void)stack.pop();
            --expected;
            RC_ASSERT(stack.size() == expected);
        }
    });

    ok &= rc::check("top is non-mutating", [](const std::vector<int>& input) {
        RC_PRE(!input.empty());
        fixed_capacity_stack<int> stack(input.size());
        for (int x : input) stack.push(x);
        const auto size_before = stack.size();
        const auto top_value = stack.top();
        RC_ASSERT(stack.size() == size_before);
        RC_ASSERT(top_value == input.back());
    });

    return ok ? 0 : 1;   // a CI csak a processzstátuszt látja: bukáskor nem nulla
}

A rc::check bool eredménye jelzi, hogy a tulajdonság teljesült-e; ezt nem szabad eldobni, mert a main végére érkezés nulla processzstátuszt adna ellenpélda mellett is. A RC_ASSERT a RapidCheck makrója; a RapidCheck verzióját rögzíteni kell (a példa nem futtatott, a pontos nevek és a viselkedés a használt verziótól függenek). A RC_PRE előfeltételt ad meg: a tulajdonság csak nem üres bemenetre értelmes. A generátorok típusa a lambda paraméter típusából következik, így a std::vector<int> automatikusan generálódik.

Zsugorítás (shrinking) példa. Tegyük fel, hogy a push szándékosan hibás: az 5-nél nagyobb értéket nem menti. A LIFO property bukik; a keret a hosszú, nagy elemeket tartalmazó ellenpéldát lépésenként egyszerűsíti (elemet hagy el, értéket csökkent), és végül egy minimális ellenpéldához jut, például egyetlen, a határ fölötti elemet tartalmazó vektorhoz (illusztráció, nem futtatott kimenet; a tényleges ellenpélda a verziótól és a seedtől függ). A zsugorítás nem garantálja a globálisan legegyszerűbb ellenpéldát, csak egy lokálisan minimálisat; a seed naplózása (RC_PARAMS) teszi reprodukálhatóvá.

A property-based tesztelés nem mindenre való. Akkor hasznos, ha a bemeneti tér nagy, és a konkrét példák nem fedik le a szélső eseteket; ha a rendszernek algebrai tulajdonsága van, például sorrend, összefésülhetőség, idempotencia; ha a bemenetek és a kimenetek között inverz kapcsolat áll fenn. Ha a tulajdonság túl szoros, a teszt a refaktorálást akadályozza; ha túl gyenge, a hibák rejtve maradnak.

26.4.4 Fuzz teszt: generált bemenetek és robusztusság

A fuzz teszt elsősorban azt ellenőrzi, hogy tetszőleges, gyakran szemét bemenetre a kód ne okozzon UB-t, ne omoljon össze, és ne szivárogtasson. A coverage-guided fuzzer – például a libFuzzer vagy az AFL++ (az OSS-Fuzz nem fuzzer motor, hanem fuzzing-szolgáltatás/infrastruktúra) – a bemeneteket aszerint mutálja, hogy mely ágakat fedezték fel; így a tesztelés nem véletlenszerű, hanem a program bejárása által vezérelt.

A C++-ban a libFuzzer belépési pontja egy extern "C" függvény, amely egy bájtsorozatot kap, és azt tetszőlegesen értelmezheti. A következő példa a verem műveleteit vezérli a bemenet bájtjaival:

#include <cstddef>
#include <cstdint>
#include <cstdlib>
#include <vector>
#include "fixed_capacity_stack.hpp"

extern "C" int LLVMFuzzerTestOneInput(const std::uint8_t* data, std::size_t size) {
    fixed_capacity_stack<int> stack(64);
    std::vector<int> model;   // független referenciamodell (orákulum)
    for (std::size_t i = 0; i < size; ++i) {
        switch (data[i] % 3) {
            case 0:
                if (!stack.full()) {
                    stack.push(static_cast<int>(data[i]));
                    model.push_back(static_cast<int>(data[i]));
                }
                break;
            case 1:
                if (!stack.empty()) {
                    if (stack.pop() != model.back()) std::abort();   // rossz LIFO
                    model.pop_back();
                }
                break;
            case 2:
                if (!stack.empty() && stack.top() != model.back()) std::abort();
                break;
        }
        if (stack.size() != model.size()) std::abort();
    }
    return 0;
}

A harness az API előfeltételeit követi (a push/pop/top hívásokat full()/empty() ellenőrzés védi), ezért az API-szerződés megsértése nem fuzzolt; ez nem bizonyítja, hogy „soha nincs UB”. A harness alkalmazási tulajdonságot is ellenőriz: a referenciamodell miatt memóriabiztosan rossz LIFO sem marad rejtve, és a fuzzer akkor is jelez, ha nincs UB. A sanitizer (ASan/UBSan) csak a támogatott és ténylegesen elért hibákat találja meg. A futtatás Clang esetén például:

clang++ -std=c++20 -fsanitize=fuzzer,address,undefined fuzz_stack.cpp -o fuzz_stack
./fuzz_stack corpus/ -max_total_time=60

A -fsanitize=fuzzer Clang-kapcsoló; GCC-vel az AFL++ használható, MSVC-n pedig VS 2022 17.0-tól kísérleti /fsanitize=fuzzer támogatás van, az ASan külön /fsanitize=address opcióval (a vesszős fuzzer,address,undefined forma ott nem érvényes). A pontos kapcsolók eszközönként és platformonként különböznek, ezért a Clang, MSVC és AFL++ buildútját és a támogatási mátrixot külön rögzítjük. A fuzz teszt izolált, eldobható környezetben fut. A libFuzzer corpusa visszajátszható regresszióként is: a corpus-fájlok a futtatást a kereső mód nélkül is lefuttatják, így gyors regressziós ellenőrzést adnak, nem mindig kell unit tesztre átírni.

A fuzzer által talált hibából mindig regressziós unit tesztet kell készíteni, mert a fuzz bemenet önmagában nem dokumentálja a hiba okát, és a futtatás nem része a gyors fejlesztői visszajelzésnek.

26.4.5 Coverage és regresszió

A kódlefedettség megmutatja, hogy a tesztek a forráskód mekkora részét érintik. A leggyakoribb típusok a sorlefedettség (line), az áglefedettség (branch) és a függvénylefedettség. A magas lefedettség nem általános helyességi feltétel, és nem elégséges: a lefedett kód is tartalmazhat hibát, a nem lefedett ágak pedig rejtik a hiányt. Ráadásul a C++ sablonok és inline függvények miatt a generált kód torzíthatja a mérést, ezért a lefedettségi jelentést nem szabad kizárólag százalékos célként kezelni.

A mérés eszközútjai nem felcserélhetők. GCC (és Clang gcov-módban): --coverage fordítás és linkelés, futtatás, majd gcov/lcov (Clang gcov-módnál llvm-cov gcov). Clang forrásalapú lefedettség: -fprofile-instr-generate -fcoverage-mapping, futtatás LLVM_PROFILE_FILE=... mellett, majd llvm-profdata merge -sparse *.profraw -o all.profdata, és llvm-cov report ./test -instr-profile=all.profdata vagy llvm-cov show .... Az MC/DC (Clang 18-tól, -fcoverage-mcdc, kísérleti) a verziótól és az instrumentálástól függ. MSVC-n a natív fedettség használható, de a támogatás verziófüggő. A százalék hatókörét (mely fájlok, sablonok) és hiányait is értékelni kell. A CI-ben a lefedettségi jelentést minden éjszakai buildben érdemes elkészíteni, és a kritikus biztonsági komponenseknél az áglefedettséget vagy akár az MC/DC-t is figyelembe venni.

A regressziós teszt a hibák visszatérését akadályozza meg. Minden javított hiba után egy olyan tesztet kell írni, amely a hibát reprodukálja. A fuzz által talált bemenetből készült unit teszt tipikus példa: a korpusz bemenetét beépítjük a tesztkészletbe, így a hiba a jövőben azonnal jelez. A regressziós védelem nem csak a kódra, hanem a buildre és a függőségekre is kiterjed: ha egy külső könyvtár frissítése megváltoztatja a viselkedést, a teszteknek ezt is jelezniük kell.

26.4.6 CI-terv: build mátrix és pipeline

A folyamatos ellenőrzés gerince a CI-pipeline, amely minden releváns konfigurációt automatizáltan futtat. A reprodukálhatóság alapkövetelmény: a buildkörnyezet rögzített, a lépések verziózottak, az eredmények naplózottak. A build mátrix a támogatott célokhoz és az időbudgethez illeszkedjen (compiler/STL/OS/generátor); a fordítók és szabványverziók száma nem univerzális előírás, a támogatott célokból következik.

Egy tipikus pipeline szakaszai:

  1. Konfiguráció: CMake -DCMAKE_BUILD_TYPE=Debug vagy Release (csak egykonfigurációs generátoroknál; többkonfigurációs generátoroknál, például Visual Studio, --config/ctest -C), -DCMAKE_CXX_STANDARD=20 vagy 23, -DCMAKE_CXX_COMPILER rögzítve; konfigurációnként külön build könyvtár.
  2. Build: párhuzamos fordítás, figyelmeztetések -Wall -Wextra -Wpedantic (MSVC-n /W4 /permissive-), a warnings-as-errors csak a saját kódban.
  3. Unit és property tesztek: gyors, determinisztikus sorrend; a ctest alapból nem áll le az első hibánál (--stop-on-failure), a nulla teszt futtatása hibakapu legyen (--no-tests=error), a property-bukás nem nulla státusz.
  4. Sanitizerek: ASan+UBSan és TSan külön buildben (egymással nem kombinálhatók), Debug módban; a tesztek ugyanazt a kódot futtatják instrumentálva; a sanitizerhiba külön hibakapu.
  5. Statikus elemzés: clang-tidy, cppcheck, MSVC /analyze; a riportok archiválva.
  6. Fuzz rövid futtatás: limitált idő (például 1-2 perc) a corpus frissítésére és a regressziós corpus visszajátszására; a seed naplózott (a naplózott seeddel reprodukálható, a mindig azonos seed szűkíti a keresést). Az időbudget keresési erőforrás, nem helyességi bizonyíték.
  7. Coverage: a unit tesztek lefedettségi jelentése, de nem blokkoló, ha küszöb alatt van, kivéve a kritikus modulokat.
  8. Benchmark: külön futtatás, mert a teljesítmény nem helyesség, de a regresszió jelezheti a nem várt lassulást.

A következő mérési napló sablon (nem futtatott minta): a várt és a mért érték külön oszlopban szerepel, a platform, a fordítóverzió, a szabványverzió és a dátum rögzítendő (<kitöltendő>). A „mért” oszlopot csak valódi futtatás nyers naplójával szabad kitölteni.

Teszt Várt eredmény Mért eredmény Státusz
fixed_capacity_stack_basic az összes REQUIRE teljesül <kitöltendő: assertek száma> <kitöltendő>
fixed_capacity_stack_overflow_throws std::out_of_range <kitöltendő> <kitöltendő>
LIFO_property[100 cases] 100 eset teljesül, kilépési kód 0 <kitöltendő: seed, esetszám> <kitöltendő>
fuzz_stack_60s nincs crash, nincs oom/timeout <kitöltendő: corpus-fájlok száma, mem/lemez> <kitöltendő>
ASan_unit nincs sanitizerhiba <kitöltendő> <kitöltendő>

A napló csak akkor tekinthető bizonyítéknak, ha a futtatás reprodukálható (seed, tesztnevek, esetszám/assertek, corpus, budget, hibastátusz), és a környezet dokumentált; a környezeti napló önmagában nem garantál bitazonos binárist (a megismételhető teszt és a bitazonos build eltérő cél). A nem futtatott benchmarkot vagy ABI-állítást nem szabad ellenőrzött eredményként feltüntetni; ez a tesztnaplóra is érvényes.

A CI-ben a függőségek verziózása és a supply chain biztonság is megjelenik. A csomagkezelő által letöltött könyvtárakat hash vagy lock fájl rögzíti, és a pipeline nem futtat megbízhatatlan forrásból származó kódot. A build reprodukálhatóságát a CI naplók és a build environment rögzítése segíti.

26.4.7 Tipikus hibák

A tesztelés és a CI során a leggyakoribb hibák a következők:

  • Flaky teszt: nem determinisztikus sorrend, időmérés, hálózat, fájlrendszer, rand() fix seed nélkül. A flaky teszt aláássa a bizalmat, mert a fejlesztő ignorálja a hibákat.
  • Globális állapot: statikus objektumok, singletonok, environment változók módosítása; a tesztek sorrendfüggővé válnak.
  • Túlzott mock: az interfész mögött a valós implementációt nem teszteljük; a mock a tesztet tautologikussá teszi.
  • Coverage mint cél: a tesztek a lefedettség növelésére íródnak, nem a specifikációra; a 100% sorlefedettség hamis biztonságérzetet ad.
  • Nem futtatott fuzz/sanitizerek: a CI-ben csak release build fut; a memóriahibák rejtve maradnak.
  • Nem kezelt regresszió: a hibajavítás után nincs reprodukáló teszt, így a hiba visszatérhet.
  • Nem rögzített környezet: a „nálam fut” nem bizonyíték; a CI a fejlesztői géptől eltér.
  • Kizárólag a futásidejű tesztekre hagyatkozás: a fordítási idejű ellenőrzések, például a static_assert, a concepts és a típusrendszer adta lehetőségek kihasználatlanok maradnak.

Ezek a hibák nem a tesztelés hiányából, hanem a tesztelés helytelen céljából erednek. A folyamatos ellenőrzés akkor működik, ha a tesztelés a specifikációt, a biztonsági invariánsokat és a hordozhatóságot szolgálja, nem pedig egy mutatót.

26.4.8 Labor: teszt- és CI-terv készítése

A labor célja, hogy a fenti fixed_capacity_stack (vagy egy saját, hasonlóan kis komponens) teszt- és CI-tervét elkészítsük. A tervnek tartalmaznia kell:

  • A komponens specifikációját: műveletek, előfeltételek, utófeltételek, kivételek.
  • Unit tesztek listáját: legalább öt konkrét eset.
  • Legalább három property-t és egy fuzz target.
  • A lefedettségi stratégiát és a regressziós eljárást.
  • A CI build mátrixot: fordítók, szabványverziók, build típusok, sanitizerek, statikus elemzők.
  • Buildparancsokat, kapcsolókat és mérési napló sablont.

Példa buildparancsok (nem futtatott minta; egykonfigurációs generátor, ASan+UBSan külön build könyvtárban):

# Konfiguráció (Debug, GCC 13+ feltételezve; a verziót rögzítjük)
cmake -S . -B build/debug-gcc -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_COMPILER=g++-13 -DCMAKE_CXX_STANDARD=20 \
  -DCMAKE_CXX_FLAGS="-Wall -Wextra -Wpedantic -fsanitize=address,undefined -fno-omit-frame-pointer"

# Build és teszt (a nulla teszt hibának számít)
cmake --build build/debug-gcc --parallel
ctest --test-dir build/debug-gcc --output-on-failure --no-tests=error --stop-on-failure

# Többkonfigurációs generátornál (például Visual Studio): --config Debug és ctest -C Debug

# Fuzz (külön build, Clang esetén; ASan/TSan külön buildek)
clang++ -std=c++20 -fsanitize=fuzzer,address,undefined fuzz_stack.cpp -o fuzz_stack
./fuzz_stack corpus/ -max_total_time=60

A -max_total_time=60 a libFuzzer kapcsolója; más fuzzer esetén a szintaxis eltér. A -fsanitize=fuzzer Clang-kapcsoló, ezért a buildmátrixban ezt jelezni kell. A CMakeLists.txt minimális vázlata (a függőségeket find_package köti be; a csomag- és célnevek a telepítéstől függenek, a laborban ellenőrizendők):

cmake_minimum_required(VERSION 3.20)
project(stack_testing LANGUAGES CXX)

# A 20-as alapérték nem írja felül a parancssori -DCMAKE_CXX_STANDARD=23 választást.
if(NOT DEFINED CMAKE_CXX_STANDARD)
  set(CMAKE_CXX_STANDARD 20)
endif()
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

include(CTest)   # enable_testing() és a BUILD_TESTING opció

find_package(doctest CONFIG REQUIRED)       # cél: doctest::doctest
find_package(RapidCheck CONFIG REQUIRED)    # cél: RapidCheck::rapidcheck (telepítésfüggő)

add_library(stack_lib INTERFACE)
target_include_directories(stack_lib INTERFACE include)

add_executable(unit_tests tests/unit_tests.cpp)
target_link_libraries(unit_tests PRIVATE stack_lib doctest::doctest)
add_test(NAME unit COMMAND unit_tests)

add_executable(property_tests tests/property_tests.cpp)
target_link_libraries(property_tests PRIVATE stack_lib RapidCheck::rapidcheck)
add_test(NAME property COMMAND property_tests)

A tesztkeretek és a RapidCheck feloldása a csomagkezelőtől függ; a laborban használhatunk például vcpkg-t, Conan-t vagy a FetchContent modult rögzített verzióval/commit-tal, de a pontos csomagneveket és verziókat a környezetben ellenőrizni kell.

A leadandó: a terv dokumentációja, a futtatott tesztek naplója, a build konfiguráció, és a tapasztalatok leírása. A naplóban a mért és várt eredményeket külön oszlopban (a fenti táblázat formájában) kell feltüntetni, a platform, a fordítóverzió, a szabványverzió és a dátum rögzítésével. A napló csak akkor fogadható el, ha a futtatás reprodukálható; a „lokálisan lefutott” megjegyzés nem elegendő.

26.4.9 Önellenőrző kérdések

  1. Mi a különbség a unit teszt és a property-based teszt között? Melyik mikor előnyös? (Válasz: a unit teszt konkrét példát, a property teszt generált bemenetek egész osztályára érvényes tulajdonságot ellenőriz; a property a nagy bemeneti térnél és algebrai törvényeknél, a unit teszt a konkrét szélső eseteknél és a jól érthető dokumentációnál előnyös.)
  2. Hogyan integrálható a fuzz teszt a CI-be anélkül, hogy a futási idő túllépné a korlátot? (Válasz: PR-nál rövid futás és a corpus visszajátszása, éjszaka hosszabb keresés; a seed és a talált bemenetek archiválása.)
  3. Miért nem elégséges a 100%-os sorlefedettség a helyesség igazolásához? Soroljunk fel legalább két konkrét hibát. (Válasz: nem ellenőriz kimenetet; nem fedi le az ágak kombinációit, az adatfüggő hibákat, a versenyhelyzeteket és az UB-t, amely a lefedett soron is lehet.)
  4. A verem példában a pop erős kivételgaranciája milyen feltétellel teljesül? Hogyan tesztelnénk ezt property teszttel? (Válasz: nem dobó move esetén; dobó T-vel, amely tetszőleges művelet után kivételt dob, és a property azt ellenőrzi, hogy a méret és a további elemek változatlanok.)
  5. Hogyan előzhető meg a flaky teszt? Adjunk meg három megelőző intézkedést. (Válasz: fix seed vagy naplózott seed, az időtől/hálózattól/fájlrendszertől való függés megszüntetése, globális állapot izolálása.)

A fenti kérdésekre adott válaszok nemcsak a fejezet anyagát ellenőrzik, hanem azt is, hogy a folyamatos ellenőrzés elveit képesek vagyunk-e a gyakorlatban alkalmazni. A következő egység (27.1) a klasszikus és modern tervezési mintákat tárgyalja, és épít az itt bevezetett tesztelési és CI-szemléletre: a minták bemutatásánál is hangsúlyt kap, hogy a helyesség és a biztonság folyamatos ellenőrzése nem kiegészítő feladat, hanem a tervezés része.
