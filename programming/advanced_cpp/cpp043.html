12.2 Stringizing, token pasting és boilerplate

A preprocesszor két legerősebb, de egyben legfélreérthetőbb eszköze a szövegesítés (#) és a token-összefűzés (##). Mindkettő a makrók helyettesítési listájában kap szerepet, és lehetővé teszi, hogy a fordítási időben szövegeket vagy azonosítókat állítsunk elő. A gyakorlatban ezek nélkül szinte lehetetlen lenne bizonyos boilerplate-kódokat tömören generálni, ugyanakkor a helytelen használatuk rejtélyes fordítási hibákhoz vezethet. Ebben az alfejezetben a két operátor működését, a tipikus buktatókat és a valós felhasználási mintákat járjuk körbe.

12.2.1 A szövegesítés: a # operátor

A # operátor a makró egy argumentumát string literállá alakítja. Ha egy függvényszerű makró helyettesítési listájában egy paraméter előtt # áll, akkor a preprocesszor az adott argumentum tényleges szövegét idézőjelek közé teszi. Például:

#define TO_STRING(x) #x

const char* s = TO_STRING(hello);
// s == "hello"

A TO_STRING(hello) hívás eredménye a "hello" string literál. Fontos, hogy a # operátor a makróhívás helyén megadott argumentum forrásszövegét használja, nem pedig az argumentum értékét. Ha az argumentum egy makró, akkor az nem expandálódik, mielőtt a # alkalmazná. Ez az első fontos buktató:

#define VALUE 42
#define TO_STRING(x) #x

const char* s = TO_STRING(VALUE);
// s == "VALUE", nem "42"!

A VALUE makró nem fejtődik ki, mert a # operátor közvetlenül az argumentum szövegét stringesíti. Ez a viselkedés a legtöbb esetben nem kívánatos, ezért bevezetünk egy köztes makrót, amely először expandálja az argumentumot, és csak utána stringesíti:

#define STRINGIZE_DETAIL(x) #x
#define STRINGIZE(x) STRINGIZE_DETAIL(x)

#define VALUE 42
const char* s = STRINGIZE(VALUE);
// s == "42"

Itt a STRINGIZE(VALUE) hívás során a VALUE argumentum először expandálódik, így a STRINGIZE_DETAIL már a 42 szöveget kapja, és abból lesz "42". Ezt a kétlépcsős mintát double indirection vagy kétlépcsős expandálás néven ismerjük, és a # mellett a ## esetében is elengedhetetlen.

A szövegesítés során a preprocesszor a következő átalakításokat végzi:

  • Az argumentum preprocessing tokenjei közötti whitespace-sorozatok (szóköz, tabulátor, újsor) egyetlen szóközzé olvadnak össze; a vezető és a záró whitespace törlődik. A string- és karakterliterálokon belüli szóközök megmaradnak.
  • Az argumentumban szereplő string- és karakterliterálok " és \ karaktereit a preprocesszor escape-eli (például " → \", \ → \\); az argumentum egyéb részein nem történik escape-elés. A forrás- és a végrehajtási karakterkészlet közötti átalakítás nem a # feladata, azt a fordítás külön fázisa végzi.
  • Ha az argumentum üres, az eredmény "".
  • A # mindig sima (prefix nélküli) string literált állít elő; a L#x alak nem hoz létre széles literált (lásd alább).

Nézzünk egy összetettebb példát:

// HIBÁS (szándékosan): az L és a "hello" két külön token marad
#define WARN_STRING_BAD(x) L#x

// Helyes: a stringesítés után külön lépésben fűzzük az L prefixet a literálhoz
#define WIDEN2(x) L ## x
#define WARN_STRING(x) WIDEN2(#x)

const wchar_t* w = WARN_STRING(hello);   // L"hello"

Az L#x nem hoz létre széles karakteres string literált: a #x eredménye egy sima "hello" string literál, az L pedig külön azonosító token marad, így a const wchar_t* w = WARN_STRING_BAD(hello); fordítási hibát ad (az L nem deklarált). A whitespace elhagyása ezen nem segít, és egyes régebbi preprocesszorok (például a hagyományos MSVC-preprocesszor) elfogadó viselkedése nem hordozható szabály. A helyes megoldás a WIDEN2 segédmakró: a WARN_STRING(hello) először WIDEN2("hello") lesz, majd a ## az L és a "hello" tokent L"hello" széles literállá fűzi. Ugyanígy működik az u8, u és U prefix is (u8 ## x stb.).

A szövegesítés gyakori felhasználása a fordítási idejű diagnosztikai üzenetekben, naplózási makrókban és tesztkeretekben fordul elő. Például egy egyszerű assert makró:

#define ASSERT(cond) \
    do { \
        if (!(cond)) { \
            std::cerr << "Assertion failed: " #cond " at " __FILE__ ":" << __LINE__ << '\n'; \
            std::abort(); \
        } \
    } while (false)

Itt a #cond a feltétel szövegét illeszti a hibaüzenetbe, így a fejlesztő azonnal látja, melyik kifejezés vallott kudarcot.

12.2.2 A token-összefűzés: a ## operátor

A ## operátor (más néven token pasting) két preprocesszor-tokent egyetlen tokenné fűz össze. A művelet a makró helyettesítési listájában hajtható végre, és az eredménynek érvényes preprocesszor-tokennek kell lennie. Például:

#define CONCAT(a, b) a##b

int xy = 1;
int z = CONCAT(x, y); // int z = xy;

A CONCAT(x, y) a x és y tokeneket xy azonosítóvá fűzi össze, így a kód int z = xy; lesz. A ## operátor fontos tulajdonsága, hogy az argumentumokat nem expandálja, mielőtt összefűzné őket. Ez ugyanaz a csapda, mint a # esetében:

#define PREFIX foo
#define CONCAT(a, b) a##b

int foo_bar = 1;
int x = CONCAT(PREFIX, _bar); // hiba: PREFIX_bar nem deklarált

A CONCAT(PREFIX, _bar) a PREFIX és _bar tokeneket PREFIX_bar azonosítóvá fűzi, nem pedig foo_bar-rá, mert a PREFIX makró nem expandálódik; a PREFIX_bar pedig nincs deklarálva, így a fordító hibát jelez. (Ha a példában PREFIX_bar is szerepelne deklarációként, a kód hibátlanul fordulna, de a hibás működést elfedné.) A megoldás itt is a kétlépcsős indirekció:

#define CONCAT_DETAIL(a, b) a##b
#define CONCAT(a, b) CONCAT_DETAIL(a, b)

#define PREFIX foo
int foo_bar = 1;
int x = CONCAT(PREFIX, _bar); // int x = foo_bar;

A kétlépcsős minta garantálja, hogy a CONCAT argumentumai először teljesen expandálódnak, és csak utána történik az összefűzés. Ez az egyik leggyakoribb hiba a preprocesszor használata során, és a legtöbb makrókönyvtár (például a Boost.Preprocessor) is ezt a technikát alkalmazza.

A ## operátorral összefűzött tokennek érvényes preprocesszor-tokennek kell lennie. Ez azt jelenti, hogy a művelet után a fordító szintaktikailag értelmezni tudja az eredményt. Például a CONCAT(+, =) eredménye += lenne, ami érvényes token, de a CONCAT(if, else) eredménye ifelse azonosító, ami szintén érvényes, bár valószínűleg nem kívánt. Ha az összefűzés nem hoz létre érvényes tokent, a viselkedés C++23-ig nem definiált (a C++26 rosszul formálttá teszi, P2621); a GCC és a Clang hibát ad, más preprocesszorok csendben két tokent hagyhatnak, és a diagnosztika gyakran zavaros.

A ## operátor használható üres argumentumokkal is: az üres makróargumentum szabványos (C++11 óta), és a ## ilyenkor egy „placemarker” tokennel dolgozik, amely az összefűzés után eltűnik. Például:

#define JOIN(a, b) a##b
int y = 1;
int x = JOIN(, y); // int x = y; – szabványos, az üres a placemarkerré válik

Az int x = JOIN(, y); tehát az int x = y; sorra bővül; hiba csak akkor keletkezne, ha az y nem lenne deklarálva. A valóban nem hordozható eset a vessző elnyelése variadic makróban, a GNU-féle , ## __VA_ARGS__ forma. A C++20 bevezette a __VA_OPT__ makrót, amely lehetővé teszi a vessző biztonságos elhagyását variadic makrókban, és ezzel kiküszöböli a , ## __VA_ARGS__ trükk szükségességét. Erre a boilerplate generálásánál még visszatérünk.

A ## operátor gyakori felhasználása az azonosítók programozott generálása: függvénynevek, változónevek, struct tagok létrehozása makróhívásból. Ezzel elkerülhető a kézzel írt ismétlődő kód, és a karbantarthatóság is javulhat, ha a generálási szabály egy helyen van definiálva.

12.2.3 Boilerplate generálás a két operátorral

A # és ## együttes használata rendkívül hatékony eszköz a boilerplate-kódok csökkentésére. Tekintsünk egy tipikus problémát: adott egy enum, amelynek értékeihez string reprezentációt szeretnénk rendelni, valamint minden értékhez egy-egy függvényt generálni. Kézzel ez így nézne ki:

enum class Color { Red, Green, Blue };

const char* to_string(Color c) {
    switch (c) {
        case Color::Red:   return "Red";
        case Color::Green: return "Green";
        case Color::Blue:  return "Blue";
    }
    return "Unknown";
}

Ez a kód könnyen redundánssá válik, ha az enum bővül. A preprocesszor segítségével egyetlen listából generálhatjuk mind az enumot, mind a string konverziót:

#define COLOR_LIST(X) \
    X(Red) \
    X(Green) \
    X(Blue)

#define DECLARE_COLOR_ENUM(name) name,
#define STRINGIZE_COLOR(name) #name,

enum class Color {
    COLOR_LIST(DECLARE_COLOR_ENUM)
};

const char* color_names[] = {
    COLOR_LIST(STRINGIZE_COLOR)
};

const char* to_string(Color c) {
    auto idx = static_cast<std::size_t>(c);
    if (idx >= sizeof(color_names) / sizeof(color_names[0])) return "Unknown";
    return color_names[idx];
}

Itt a COLOR_LIST egy X-makró lista, amely minden elemet az X függvénymakróval hív meg. A tömb mérete a listából származik, így új szín felvételekor nincs „mágikus” elemszám, amelyet külön kellene karbantartani. A DECLARE_COLOR_ENUM minden elem után vesszőt tesz, az enum deklarációhoz; a STRINGIZE_COLOR pedig stringesíti a nevet. A # operátor gondoskodik arról, hogy a Red azonosítóból "Red" string literál legyen. Az eredmény:

  • Az enum: Red, Green, Blue,
  • A tömb: { "Red", "Green", "Blue", }

A záró vessző az enum esetében megengedett, a tömb inicializáló listájában is. Ez a minta rendkívül olvashatóvá teszi az enum és a hozzá tartozó adatok karbantartását: új szín hozzáadásához csak a COLOR_LIST-et kell bővíteni.

Most nézzük a ## használatát függvénynevek generálására. Tegyük fel, hogy minden színhez szeretnénk egy is_<color> predikátumfüggvényt:

#define DEFINE_COLOR_PREDICATE(name) \
    bool is_##name(Color c) { return c == Color::name; }

COLOR_LIST(DEFINE_COLOR_PREDICATE)

A ## operátor összefűzi az is_ előtagot a szín nevével, így létrejön az is_Red, is_Green, is_Blue függvény. A makró törzsében a Color::name kifejezésben a name paramétert a ## nélkül, sima helyettesítéssel használjuk, tehát az expandálódik. A generált kód:

bool is_Red(Color c) { return c == Color::Red; }
bool is_Green(Color c) { return c == Color::Green; }
bool is_Blue(Color c) { return c == Color::Blue; }

Ez a technika különösen hasznos tesztelési keretekben, ahol minden esethez egyedi tesztfüggvényt kell regisztrálni, vagy plugin-rendszerekben, ahol szimbolikus nevekből kell függvénypointereket generálni.

12.2.4 Naplózási makrók és forrásinformációk

A # és ## operátorok gyakori kombinációja a naplózási és diagnosztikai makrókban jelenik meg. Például:

#define LOG(level, msg) \
    do { \
        std::cerr << "[" #level "] " << __FILE__ ":" << __LINE__ << ": " << msg << '\n'; \
    } while (false)

LOG(WARNING, "Failed to open file");

Itt a #level stringesíti a level argumentumot, így a kimenet [WARNING] file.cpp:42: Failed to open file lesz. A __FILE__ és __LINE__ szabványos előre definiált makrók, amelyek a forrásfájl nevét és a sor számát adják. A ## operátorra ebben a makróban nincs szükség. A naplózásnál gyakori kérdés a fájlnév megjelenítése: a __FILE__ a teljes (gyakran hosszú) elérési utat adja, a __BASE_FILE__ pedig nem rövidít, hanem a fő forrásfájl nevét adja (nem szabványos GCC/Clang kiterjesztés), ami headerben használt naplózó makrónál félrevezető. A fájlnév rövidítésére a __FILE_NAME__ (Clang 9+, GCC 12+; nem szabványos) használható. Makró nélküli, szabványos alternatíva a C++20 std::source_location:

// g++ -std=c++20
#include <iostream>
#include <source_location>

void log_message(const char* level, const char* msg,
                 std::source_location loc = std::source_location::current()) {
    std::cerr << '[' << level << "] " << loc.file_name() << ':' << loc.line()
              << ": " << msg << '\n';
}

A file_name() itt is a teljes utat adja; a fájlnév-részt például std::filesystem::path(loc.file_name()).filename() vagy a fordító -fmacro-prefix-map kapcsolója segítségével kaphatjuk. A #level stringesítés viszont csak makróval érhető el. A fordítóspecifikus makrók általános kezelését (feature detection, izoláció) a 13.2 és a 13.4 tárgyalja; a __FILE_NAME__ jelenlétét például #ifdef __FILE_NAME__ ággal érdemes vizsgálni, különben a std::source_location és a std::filesystem::path(...).filename() a hordozható út.

12.2.5 Vesszők és üres argumentumok kezelése C++20-ban

A variadic makrók és a ## operátor kombinációja gyakran vezet a hírhedt „túl sok vessző” problémához. Tegyük fel, hogy egy ASSERT makrót szeretnénk készíteni, amely opcionálisan üzenetet is fogad:

#define ASSERT(cond, ...) \
    do { \
        if (!(cond)) { \
            std::cerr << "Assertion failed: " #cond; \
            /* ha van üzenet, írjuk ki */ \
        } \
    } while (false)

A klasszikus megoldás a GNU-féle , ## __VA_ARGS__ trükk volt, amely eltávolítja a vesszőt, ha a variadic argumentum üres. Ez azonban nem szabványos kiterjesztés; bár a Clang és az MSVC is támogatja (utóbbi a hagyományos preprocesszorban beépítetten, a szabványos módban eltérően), a viselkedése fordítók és módok között eltérhet. A C++20 bevezette a __VA_OPT__ makrót, amely a variadic argumentumok jelenléte esetén helyettesíti a zárójelben lévő szöveget, különben üres. Példa:

#define ASSERT(cond, ...) \
    do { \
        if (!(cond)) { \
            std::cerr << "Assertion failed: " #cond __VA_OPT__(<< " Message: " << __VA_ARGS__) << '\n'; \
            std::abort(); \
        } \
    } while (false)

ASSERT(x > 0);
ASSERT(y > 0, "y must be positive");

Itt a __VA_OPT__(...) akkor bővül ki a zárójelben lévő kifejezésre, ha a ... argumentum nem üres. Az első hívásnál nincs üzenet, így a makró std::cerr << "Assertion failed: " #cond << '\n'; lesz, a másodiknál pedig std::cerr << "Assertion failed: " #cond << " Message: " << "y must be positive" << '\n';. Ez a megoldás szabványos (C++20); a 12.1 alfejezettel egységesen a GCC 8+, Clang 6+ (kiterjesztésként a korábbi módokban is), MSVC 19.25+ támogatja, MSVC-nél a szabványos preprocesszort kérő /Zc:preprocessor kapcsolóval. A pontos verziókat az adott fordító dokumentációjában érdemes ellenőrizni. A __VA_OPT__ használata a boilerplate generálásban is elterjedt, mert lehetővé teszi a vesszők feltételes beillesztését anélkül, hogy platformfüggő trükkökhöz folyamodnánk.

12.2.6 Tipikus hibák és elkerülésük

A # és ## operátorokkal kapcsolatos hibák többsége a következő kategóriákba sorolható:

  1. Az argumentumok nem expandálódnak. Ahogy fentebb láttuk, a # és ## közvetlenül az argumentum szövegét használja, anélkül hogy a makrókat először kifejtené. A megoldás a kétlépcsős indirekció. Ezt a hibát nehéz észrevenni, mert a kód lefordul, de nem a várt azonosítót vagy szöveget állítja elő. A tesztelés során mindig ellenőrizzük a generált kódot a -E kapcsolóval (GCC/Clang) vagy /E (MSVC) futtatva, amely a preprocesszor kimenetét mutatja.

  2. Az összefűzés eredménye nem érvényes token. A ## operátornak érvényes preprocesszor-tokent kell létrehoznia. Ha például két olyan tokent fűzünk össze, amelyből nem lesz egyetlen érvényes preprocesszor-token (például CONCAT(., +) vagy CONCAT(foo, +)), a viselkedés C++23-ig nem definiált (a C++26 rosszul formálttá teszi, P2621), és a diagnosztika fordítófüggő. Az összefűzés érvényessége a preprocesszor-token szintjén dől el: a CONCAT(42, foo) eredménye, a 42foo, érvényes pp-number token, a hiba csak később, a 7. fázisban jelentkezik, mert nincs hozzá operator""_foo-szerű felhasználói literál-operátor. Mindig gondoljuk át, milyen tokeneket fűzünk össze, és teszteljük a preprocesszor kimenetét.

  3. A stringesített szöveg whitespace-kezelése. A # operátor a whitespace-eket összevonja, ami általában kívánatos, de ha a forráskódban szándékosan több szóköz van, az elveszik. A stringesítés nem alkalmas a forrásbeli formázás megőrzésére.

  4. A ## operátor és a vesszők. Az üres argumentum és a ## kombinációja szabványos (placemarker), de a vessző elnyelése variadic makróban nem az. A C++20 __VA_OPT__ megoldást kínál, de a korábbi szabványokban a GNU-féle , ## __VA_ARGS__ terjedt el. Ha hordozható kódot írunk, kerüljük az üres argumentumokat, vagy használjunk __VA_OPT__-ot.

  5. A makrók mellékhatásai és a többszörös kiértékelés. Bár ez nem közvetlenül a # vagy ## hibája, a makrók által generált kódban az argumentumok többször is kiértékelődhetnek. Például a fenti ASSERT makróban a cond kifejezést csak egyszer értékeljük ki (a if feltételben), a #cond pedig csak stringesítés, nem kiértékelés. A msg jellegű argumentum viszont zárójelezés nélkül kerül be a kifejezésbe, és például feltételes operátornál megváltoztathatja a kötést; ezért az argumentumokat érdemes zárójelezni, vagy a szerződést dokumentálni. Mindig ügyeljünk arra, hogy a makrók ne értékeljék ki többször az argumentumokat, vagy ha igen, azt dokumentáljuk.

12.2.7 Labor: X-makró lista és generált függvények

Az X-makró technikát a 12.4 alfejezet általánosabban, más alkalmazásokkal együtt tárgyalja; itt csak a # és ## operátorok szerepére koncentrálunk. A labor célja, hogy a # és ## operátorokat egy valós, reprodukálható példán keresztül gyakoroljuk. A feladat egy olyan X-makró lista készítése, amely egy enumot, a hozzá tartozó string neveket és predikátumfüggvényeket generál. Az eredményt egy tesztprogram ellenőrzi.

12.2.7.1 A kód

Hozzunk létre egy color.hpp headert, amely az X-makró listát és a generáló makrókat tartalmazza:

// color.hpp
#pragma once

#include <cstddef>

// Az X-makró lista: minden sor egy elem, az X függvénymakrót hívja.
#define COLOR_LIST(X) \
    X(Red) \
    X(Green) \
    X(Blue)

// Enum deklaráció: minden elemhez vesszőt teszünk.
#define DECLARE_COLOR_ENUM(name) name,

enum class Color {
    COLOR_LIST(DECLARE_COLOR_ENUM)
};

// String nevek tömbje: minden elem szövegesítve.
#define STRINGIZE_COLOR(name) #name,
// inline constexpr: több fordítási egységben is egyetlen definíció (C++17-től)
inline constexpr const char* color_names[] = {
    COLOR_LIST(STRINGIZE_COLOR)
};

// Predikátumfüggvények generálása: is_##name
#define DEFINE_COLOR_PREDICATE(name) \
    inline bool is_##name(Color c) { return c == Color::name; }

COLOR_LIST(DEFINE_COLOR_PREDICATE)

// Konverzió stringre: index alapján
inline const char* to_string(Color c) {
    auto idx = static_cast<std::size_t>(c);
    if (idx >= sizeof(color_names)/sizeof(color_names[0])) return "Unknown";
    return color_names[idx];
}

A color_names tömb inline constexpr, ezért a header több fordítási egységbe is bevonható anélkül, hogy többszörös definíciót (ODR-sértést) okozna; a sima const char* color_names[] külső linkage-ű definíció lenne, amelyre a #pragma once sem véd két fordítási egység között. A color.hpp a #pragma once direktívát használja, ami nem szabványos, de minden releváns fordító támogatja. Hordozhatóbb alternatíva a include guard, de a #pragma once kényelmes és a gyakorlatban elfogadott.

A tesztprogram (test_color.cpp):

// test_color.cpp
#include "color.hpp"
#include <cassert>
#include <iostream>
#include <string>

int main() {
    static_assert(static_cast<int>(Color::Red) == 0);
    static_assert(static_cast<int>(Color::Green) == 1);
    static_assert(static_cast<int>(Color::Blue) == 2);

    assert(std::string(color_names[static_cast<int>(Color::Red)]) == "Red");
    assert(std::string(color_names[static_cast<int>(Color::Green)]) == "Green");
    assert(std::string(color_names[static_cast<int>(Color::Blue)]) == "Blue");

    assert(is_Red(Color::Red));
    assert(!is_Red(Color::Green));
    assert(is_Green(Color::Green));
    assert(is_Blue(Color::Blue));

    assert(std::string(to_string(Color::Red)) == "Red");
    assert(std::string(to_string(static_cast<Color>(99))) == "Unknown");

    std::cout << "All tests passed.\n";
    return 0;
}

A teszt static_assert-ekkel ellenőrzi az enum értékeket, assert-ekkel a string neveket, a generált predikátumfüggvényeket és a to_string konverziót.

12.2.7.2 Build és futtatás

A buildhez rögzítsük a fordítót és a szabványverziót. A példa C++20 módban, magas figyelmeztetési szinten fordítandó (a fordító pontos verzióját a mérési naplóban kell rögzíteni):

g++ -std=c++20 -Wall -Wextra -pedantic -Werror -O2 test_color.cpp -o test_color

A -Werror miatt minden figyelmeztetés hibává válik, így a kód csak akkor fordul le, ha tiszta. A futtatás:

./test_color

Várt kimenet:

All tests passed.

A mérési naplóban rögzítsük a környezetet (a saját futtatás alapján kitöltendő; a könyv nem közöl futtatott eredményt):

  • Fordító és verzió: <kitöltendő>
  • Szabvány: C++20
  • Optimalizáció: -O2
  • Figyelmeztetések: -Wall -Wextra -pedantic -Werror
  • Hardver: <kitöltendő: CPU, magok, RAM>
  • Dátum: <kitöltendő>
  • Eredmény: <kitöltendő>; elvárás: minden ellenőrzés sikeres.

A preprocesszor kimenetének ellenőrzése:

g++ -std=c++20 -E -P test_color.cpp | grep -E -A1 'enum class Color|color_names\[\] =|bool is_Red'

A -P elhagyja a sorjelzőket, így mindhárom generált részlet látszik: az enum (Red, Green, Blue,), a tömb ("Red", "Green", "Blue",) és a predikátumok (is_Red, is_Green, is_Blue); a predikátumok egy sorban jelennek meg, mert a makrókiterjesztés nem tör sort (a parancs GCC 15.2-vel ellenőrizve). Ezt a lépést azért végezzük el, hogy meggyőződjünk a # és ## operátorok helyes működéséről.

12.2.8 Összefoglalás

A # operátor string literállá alakítja a makró argumentumát, a ## operátor pedig tokenné fűzi össze a paramétereket. Mindkettő a preprocesszor legerősebb eszközei közé tartozik, de használatuk során különösen fontos a kétlépcsős expandálás, mert az operátorok közvetlenül az argumentum szövegét használják, nem pedig annak kifejtett értékét. A boilerplate generálásban ezek az operátorok lehetővé teszik, hogy egyetlen X-makró listából enumokat, stringeket és függvényeket állítsunk elő, drasztikusan csökkentve az ismétlődő kódot. A C++20 __VA_OPT__ makró tovább bővíti a lehetőségeket a variadic makrók biztonságos kezelésére. A hibák elkerülésének legjobb módja a preprocesszor kimenetének ellenőrzése és a szigorú figyelmeztetésekkel való fordítás.

12.2.9 Önellenőrző kérdések

  1. Miért van szükség kétlépcsős indirekcióra a # és ## operátorok használatakor? Mutass egy példát, ahol a hiánya hibás kódot eredményez.
  2. Írj egy makrót, amely egy struct tag nevét stringesíti, és egy másik makrót, amely egy getterfüggvényt generál a taghoz get_<tag> néven.
  3. Hogyan lehet szabványos módon kezelni az üres variadic argumentumokat C++20-ban? Hasonlítsd össze a GCC-specifikus , ## __VA_ARGS__ trükkel.

Válaszvázlat: (1) Ha a # vagy ## operandusa maga is makró, az operátor mellett az argumentum nem bővül ki előbb; ezért kell a kétlépcsős forma: #define STR_I(x) #x és #define STR(x) STR_I(x). A STR(__LINE__) a sorszám szövegét adja, az egylépcsős #__LINE__ a "__LINE__" szöveget. (2) #define TAG_NAME(tag) #tag és #define GETTER(tag, type) type get_##tag() const { return tag; }; a ## a get_ előtagot és a tag nevét illeszti össze. (3) C++20-ban a __VA_OPT__ a szabványos megoldás: #define LOG(fmt, ...) std::printf(fmt __VA_OPT__(,) __VA_ARGS__); a GCC-s , ## __VA_ARGS__ nem szabványos kiterjesztés (a GCC és a Clang érti), a __VA_OPT__ hordozható.

A következő alfejezet (12.3) a makrók és sablonok együttműködését vizsgálja, és arra épít, amit itt a szövegesítésről és token-összefűzésről tanultunk.
