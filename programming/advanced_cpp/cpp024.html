7.3 Overload resolution és customization points

A túlterhelésfeloldás (overload resolution) a C++ egyik legfontosabb, de leggyakrabban félreértett mechanizmusa. A generikus kódban nem elég tudni, hogy egy függvénynek több túlterhelése van; azt is pontosan érteni kell, hogyan választja ki a fordító a legmegfelelőbbet, és hogyan lehet ezt a kiválasztást a típusok testre szabására használni. A testreszabási pontok (customization points) ebből a mechanizmusból nőttek ki: olyan hívási felületek, amelyeket a felhasználói típusok a saját szemantikájukhoz igazíthatnak anélkül, hogy a generikus kód módosítására lenne szükség.

Ebben az alfejezetben a túlterhelésfeloldás és a testreszabási pontok kapcsolatát vizsgáljuk. A hangsúly a gyakorlati mintán van: a klasszikus using std::swap; trükkön, az argumentumfüggő névfeloldáson (ADL), a C++20 niebloidokon és a testreszabásipont-objektumokon (CPO). A cél, hogy megértsük, miért alakultak ki ezek a minták, milyen hibákat kerülnek el, és hogyan tervezhetünk saját testreszabási pontot helyesen.

7.3.1 A túlterhelésfeloldás alapjai

A túlterhelésfeloldás akkor lép működésbe, ha egy függvényhívás több lehetséges függvényre is illeszkedhet. A folyamat három fő lépésből áll:

  1. Jelöltek (candidate functions) összegyűjtése – a hívás helyén látható összes azonos nevű függvény, plusz az ADL által bevont függvények.
  2. Megvalósítható jelöltek (viable functions) kiválasztása – azok, amelyek paraméterszáma illeszkedik, és minden argumentum konvertálható a megfelelő paramétertípusra.
  3. A legjobb illeszkedés kiválasztása – a konverziós rangok összehasonlításával.

A konverziós rangok csökkenő sorrendben:

  • pontos illeszkedés (exact match) – az azonos típus, az lvalue-rvalue, tömb-pointer és függvény-pointer átalakítás, a minősítő (cv) hozzáadása, a referenciakötés; érték szerinti paraméternél a felső szintű const elhagyása is ide tartozik (nem konverzió);
  • promóció – az integrális promóció (pl. short, char → int) és a float → double;
  • (szabványos) konverzió – pl. int → long, int → double, származtatott → bázis pointer vagy referencia;
  • felhasználói konverzió (konstruktor vagy konverziós operátor).

Azonos rangon belül további szabályok (pl. referenciakötésnél a kevésbé cv-minősített céltípus jobb) döntenek.

Külön szabály vonatkozik a sablonokra: ha egy nem-sablon függvény és egy függvénysablon is azonos rangú illeszkedést ad, a nem-sablon nyer. Ha két sablon verseng, a specializáltabb (részlegesen rendezés szerint) nyer. Ez a szabály teszi lehetővé, hogy a felhasználói típusokra írt, nem-sablon swap vagy begin függvények elsőbbséget élvezzenek a standard sablonváltozatokkal szemben.

A túlterhelésfeloldás eredménye a generikus kódban is determinisztikus, de a jelöltek halmaza attól függ, mi látszik a hívás helyén. A std::swap például egy függvénysablon a <utility> fejlécben:

template< class T >
void swap( T& a, T& b ) noexcept(/*...*/);

Ha a generikus kódunkban pusztán std::swap(a, b)-t írunk, akkor kizárólag a std névtérbeli túlterhelések vesznek részt, és a felhasználói típusok saját swap függvénye nem látható, hacsak nem a std névtérben definiálták. Ez a gyakorlatban hibás, mert egy osztály hatékony swap műveletét a saját névterébe írják, nem a std-be. A megoldást az ADL és a using deklaráció kombinációja adja.

7.3.2 Argumentumfüggő névfeloldás (ADL)

Az ADL (argument-dependent lookup, más néven Koenig lookup) kiterjeszti a függvényjelöltek halmazát az argumentumok típusaihoz tartozó névterekkel. Ha a hívás argumentuma egy my::S típusú objektum, akkor a fordító automatikusan megvizsgálja a my névteret is, amikor a függvénynevet keresi. Ez az oka annak, hogy a következő kód működik:

#include <utility>

namespace my {
    struct S {
        int x;
    };
    void swap(S& a, S& b) noexcept {
        std::swap(a.x, b.x);
    }
}

int main() {
    my::S a{1}, b{2};
    swap(a, b);  // ADL: megtalálja my::swap-ot
}

A swap(a, b) hívásban a my::S argumentum miatt a my::swap is jelölt lesz, annak ellenére, hogy semmilyen using deklaráció nincs. Az ADL a túlterhelésfeloldás jelölthalmazát bővíti, így a felhasználói függvény legyőzheti a standard sablont, ha jobb illeszkedést ad. Itt a std::swap nem is jelölt (nincs using, és a my::S társult névterei között nincs std), tehát a my::swap verseny nélkül kerül kiválasztásra. Ha a std::swap is jelölt lenne (lásd lent a using std::swap; mintát), azonos rangú illeszkedésnél a nem-sablon my::swap nyerne.

A generikus kód azonban gyakran nem támaszkodhat arra, hogy minden típusnak van saját ADL által elérhető swap-ja. Az alapértelmezett viselkedést a std::swap adja, de a testreszabást az ADL biztosítja. A kettő összekapcsolására szolgál a klasszikus minta:

template<class T>
void sort_and_swap(T& a, T& b) {
    // ... valamilyen feltételvizsgálat
    using std::swap;   // std::swap elérhető a hívásban
    swap(a, b);        // ADL + std::swap közötti választás
}

A using std::swap; deklaráció a std::swap-ot beemeli a hívás aktuális névterébe, így a jelöltek halmaza tartalmazza:

  • a std::swap sablont,
  • az argumentum típusához tartozó névtérben talált swap függvényeket (ADL),
  • minden más, a hívás helyén látható swap-ot.

A túlterhelésfeloldás ezután kiválasztja a legjobbat. Ha a típusnak van saját swap-ja, az általában pontos illeszkedést ad, és nem-sablon vagy specializáltabb sablon; ha nincs, a std::swap általános implementációja érvényesül. A minta tehát helyesen valósítja meg a „testreszabás, ha van, egyébként alapértelmezés” szemantikát.

Az alábbi ábra a my::S példán veti össze a három hívásforma jelölthalmazát: a minősített hívás nem indít ADL-t, a using std::swap; minta két forrásból gyűjt, a std::ranges::swap pedig a hívó oldalon nem, csak belül, kontrolláltan használ ADL-t.

Fontos, hogy a using std::swap; nem nyit ajtót a felhasználói swap explicit hívására; az ADL a típus névterét amúgy is bevonja. A using deklaráció célja csupán az, hogy a std::swap akkor is jelölt legyen, ha a hívás helyén nincs más swap a látható névtérben, és az ADL sem talál semmit.

Hasonló minta érvényes a std::begin és std::end függvényekre. A C++11 óta a <iterator> fejlécben elérhetők a szabad std::begin sablonok, és a generikus kód gyakran így néz ki:

template<class Container>
auto first_element(Container& c) {
    using std::begin;
    return begin(c);  // ADL + std::begin
}

Itt is az ADL teszi lehetővé, hogy a felhasználói konténer saját névterében definiált begin függvénye elsőbbséget élvezzen, míg a using std::begin; az alapértelmezett std::begin-t teszi elérhetővé.

7.3.3 Niebloidok és testreszabásipont-objektumok

A C++20 két, gyakran összekevert fogalmat használ.

A testreszabásipont-objektum (customization point object, CPO) egy inline constexpr függvényobjektum (literal, semiregular osztálytípusú; a másolatai egyenlően viselkednek), amely a hívási felületet adja, és belül kontrollált módon megkeresi a felhasználói testreszabást. Ilyen a std::ranges::swap, std::ranges::begin, std::ranges::size. A CPO maga használ ADL-t a felhasználói függvény megtalálására, de csak a számára meghatározott formában (és mindig a szabványos „poison pill” védelemmel, lásd lent). Mivel objektum, a hívási helyen a nem minősített név (ha ordinary lookup objektumot talál) nem indít ADL-t, így a hívó oldali névtér nem avatkozik a jelöltek közé.

A niebloid (Eric Niebler nevéből; a szabvány újabb szövege „algorithm function object”-nek hívja) ezzel szemben a std::ranges algoritmusok (ranges::sort, ranges::find) függvényobjektum-volta. Nem testreszabási pont: célja, hogy az algoritmus neve ne induljon ADL-t (és ne lehessen explicit sablonargumentumokkal hívni), így a felhasználó névterében azonos nevű függvény ne ütközzön vele.

A CPO-k és a niebloidok egyaránt objektumok, ezért: a címük vehető, referenciához köthetők, másolhatók, és using std::ranges::swap; deklaráció is írható rájuk (a using változóra is érvényes). Ami nem működik, az a függvényként kezelés: nem lehet őket függvény-túlterhelési halmazba bevonni, és nincs rájuk sablonargumentumos hívás. A CPO pontos típusa nem specifikált, a felhasználó csak a nevet használja.

Példa egy leegyszerűsített swap-CPO szerkezetére (vázlat, nem fordítható: a /* ... */ helyére a kiválasztott ág kifejezéséből levezetett noexcept-feltétel kerülne, a swap_impl törzse pedig csak megjegyzés; szemléltetés; saját demo névtérben, mert a std (és std::ranges) névtér bővítése nem megengedett, UB; nem a tényleges szabványos implementáció):

namespace demo {
    inline constexpr struct SwapCPO {
        template<class T, class U>
        constexpr auto operator()(T&& t, U&& u) const
            noexcept(noexcept(swap_impl(std::forward<T>(t), std::forward<U>(u))))
        {
            return swap_impl(std::forward<T>(t), std::forward<U>(u));
        }

      private:
        template<class T, class U>
        static constexpr auto swap_impl(T&& t, U&& u)
            noexcept(/* ... */)
        {
            // A valódi std::ranges::swap sorrendje:
            // 1. ADL-lel talált swap(t, u) (a std::swap-ot "poison pill" zárja ki),
            // 2. azonos méretű tömbökre elemenkénti csere (swap_ranges),
            // 3. egyébként move-konstrukció + move-értékadás alapú csere
            //    (nem a std::swap hívása, és nem a t.swap(u) tagfüggvény).
        }
    } swap;
}

A valódi std::ranges::swap bonyolultabb (konceptellenőrzés, noexcept-levezetés), de a szerkezet jól mutatja a lényeget: a CPO a rejtett swap_impl-ben végzi a keresést, és nem engedi, hogy a hívó környezetéből származó túlterhelések beavatkozzanak.

A CPO előnyei a klasszikus using std::swap; mintával szemben:

  1. Nincs szükség a using deklarációra – a hívás egyértelmű és a szándék explicitebb.
  2. A hívó oldali névtér nem szennyezheti a jelölthalmazt – a CPO objektum, nem függvény, így a névkeresés nem keveredik a hívó névterének swap függvényeivel; az ADL-t a CPO maga, kontrolláltan végzi.
  3. Pontosabb diagnosztika – a CPO belső kifejezései jól ellenőrizhetők, és a hibák a CPO belsejébe mutatnak.
  4. Homogén felület – minden range-adaptor és algoritmus ugyanazt a CPO-stílust használja, így a generikus kód egységesebb.

A niebloidok használata különösen a std::ranges névtérben terjedt el. A std::ranges::begin például nem azonos a std::begin-nel. A std::begin még mindig elérhető, és továbbra is az ADL + using mintát igényli; a std::ranges::begin viszont CPO. (Az algoritmusok, pl. std::ranges::sort, niebloidok, nem CPO-k.) A kettő közötti különbség fontos migrációs szempont.

7.3.4 std::swap és std::begin evolúciója

Tekintsük át röviden, hogyan változott a két legismertebb testreszabási pont.

7.3.5 std::swap

A std::swap a C++98 óta létezik, és a klasszikus minta ismert:

template<class T>
void sort(T* first, T* last) {
    // ...
    using std::swap;
    swap(*first, *last);
}

A C++20-ban megjelent a std::ranges::swap CPO ([concept.swappable]), amely a következőket próbálja sorban:

  1. ha az ADL-lel talált swap(a, b) szabad függvény hívható (a std::swap sablont egy „mérgezett”, törölt deklaráció zárja ki a keresésből), azt hívja;
  2. egyébként azonos méretű tömböknél elemenként cserél (ranges::swap_ranges);
  3. egyébként move-konstrukcióval és move-értékadással cserél (T tmp(std::move(a)); a = std::move(b); b = std::move(tmp);) – ez nem a std::swap hívása.

A ranges::swap nem keresi a a.swap(b) tagfüggvényt, és a klasszikus std::swap sem hívja meg automatikusan a felhasználó swap tagfüggvényét. Egy olyan típusnál, amelynek csak swap tagfüggvénye van (szabad swap nincs), mindkét minta a move-alapú cserét használja, a tagfüggvényt figyelmen kívül hagyja; ha a tagfüggvényt használni akarjuk, írjunk a típus névterébe egy szabad swap-ot, amely meghívja azt (a „hidden friend” forma a bevett).

A CPO tehát hasonló, de nem azonos feloldást végez, mint a using std::swap; minta: a keresés beépített, ellenőrzött módon történik, és a felhasználónak nem kell using deklarációt írnia, csak std::ranges::swap(a, b);-t.

Fontos megjegyezni, hogy a std::swap és a std::ranges::swap együtt él. A régi generikus kód, amely a using std::swap; mintát használja, továbbra is működik, mert az ADL megtalálja a felhasználói swap-ot, és a std::swap az általános eset. Új kódban azonban érdemes a CPO-t használni.

7.3.6 std::begin és std::end

A std::begin és std::end szabad függvények a C++11 óta. A szabványos konténereknek van begin() tagfüggvényük, így az std::begin sablon hívja azt. A felhasználói konténerek a saját névterükben definiálhatnak szabad begin-t, és a using std::begin; begin(c); minta ezt felhasználja.

A C++20-ban bevezették a std::ranges::begin CPO-t, amely ([range.access.begin]) a következő sorrendben dönt:

  • ha az argumentum rvalue, és nem borrowed_range (az iterátor árván maradna), a hívás rosszul formált;
  • ha az argumentum beépített tömb, a tömb első elemére mutató pointert adja;
  • egyébként ha az a.begin() tagfüggvény érvényes és input_or_output_iterator-t ad, azt hívja;
  • egyébként ha ADL-lel talált szabad begin(a) érvényes és iterátort ad (a std::begin nem vesz részt a keresésben), azt hívja;
  • különben a hívás rosszul formált (nem tartomány).

A CPO tehát kiküszöböli a using std::begin; mintát, és a generikus kód egyszerűen std::ranges::begin(r)-t ír. A régi minta továbbra is működik, de a CPO egységesebb, és jobban illeszkedik a std::ranges ökoszisztémához.

7.3.7 Saját testreszabási pont tervezése

A CPO-k bevezetése után a fejlesztők saját testreszabási pontokat is tervezhetnek. Tegyük fel, hogy egy generikus hash_value függvényt szeretnénk, amely a felhasználói típusok számára testre szabható. A klasszikus ADL-alapú megoldás:

// HIBÁS próbálkozás (didaktikus ellenpélda)
template<class T>
size_t compute_hash(const T& value) {
    using std::hash;           // a std::hash osztálysablon, nem szabad függvény: ez nem ad fallbacket
    return hash_value(value);  // ADL keres hash_value-ot; fallback hiányában hibás
}

Itt a std::hash nem szabad függvény, hanem sablonosztály, ezért a using std::hash; nem ad alapértelmezett jelöltet. A klasszikus minta helyes változata a fallbacket egy külön névtérben (itt my_default, hogy ne ütközzön a később bevezetett my::hash_value CPO-val) adja:

namespace my_default {
    template<class T>
    std::size_t hash_value(const T& value) { return std::hash<T>{}(value); }
}

template<class T>
std::size_t compute_hash(const T& value) {
    using my_default::hash_value;   // fallback
    return hash_value(value);       // ADL: a típus névterének nem-sablon hash_value-ja nyer
}

Ez működik, de CPO-val kényelmesebb és szabályosabb. Készítsünk egy hash_value CPO-t, amely a std::hash-hez hasonló testreszabást tesz lehetővé.

#include <concepts>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

// Alapértelmezett hash_value függvény a hash kiterjesztéséhez
template<class T>
    requires std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>
constexpr std::size_t hash_value_default(const T& value) noexcept {
    return std::hash<T>{}(value);
}

// A CPO típus
struct HashValueCPO {
    template<class T>
        requires requires(const T& t) { { my::hash_value_default(t) } -> std::convertible_to<std::size_t>; }
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(my::hash_value_default(value)))
    {
        return my::hash_value_default(value);
    }
};

// A nyilvános CPO példány
inline constexpr HashValueCPO hash_value{};

} // namespace my

Ez a CPO egyelőre csak az alapértelmezett hash_value_default-ot hívja. Bővítsük ki ADL-támogatással: ha a típus a saját névterében szabad hash_value függvényt definiál, azt kell használni; különben az alapértelmezett marad. A kulcs, hogy a CPO belsejében az ADL-t egy detail névtérbeli segédsablon végzi, amelyben a hash_value(value) hívás nem a CPO-t, hanem a T névterében található függvényt látja. Az if constexpr (requires ...) fordítási időben választ a két út közül.

A teljes CPO tehát:

#include <concepts>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

template<class T>
    requires (std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>)
constexpr std::size_t hash_value_default(const T& value) noexcept {
    return std::hash<T>{}(value);
}

namespace detail {
    // "Poison pill": ez a névtérbeli függvénydeklaráció biztosítja, hogy a nem
    // minősített hash_value(...) keresés függvényt találjon, így az ADL
    // mindig lefut, akkor is, ha a my::hash_value objektum már deklarált.
    void hash_value() = delete;

    template<class T>
    concept adl_hashable = requires(const T& v) {
        { hash_value(v) } -> std::convertible_to<std::size_t>;
    };

    template<class T>
    concept default_hashable = requires(const T& v) {
        { my::hash_value_default(v) } -> std::convertible_to<std::size_t>;
    };

    template<class T>
    constexpr std::size_t adl_hash(const T& v)
        noexcept(noexcept(static_cast<std::size_t>(hash_value(v))))
    {
        return static_cast<std::size_t>(hash_value(v));
    }
}

struct HashValueCPO {
    // 1. ág: a típus névterében talált (ADL) hash_value
    template<class T>
        requires detail::adl_hashable<T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(detail::adl_hash(value)))
    {
        return detail::adl_hash(value);
    }

    // 2. ág: alapértelmezett, ha nincs ADL-es hash_value
    template<class T>
        requires (!detail::adl_hashable<T>) && detail::default_hashable<T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(my::hash_value_default(value)))
    {
        return my::hash_value_default(value);
    }
};

inline constexpr HashValueCPO hash_value{};

} // namespace my

A CPO két, kölcsönösen kizáró operator() ágból áll, amelyeket koncepciók választanak ki: az adl_hashable<T> akkor igaz, ha a T névterében van olyan hash_value(const T&), amelynek eredménye std::size_t-vé konvertálható; különben a hash_value_default (integrál, enum, pointer) használható. Ha egyik sem, a hívás nem fordul le (a std::is_invocable_v hamis), nem pedig csendben hibás kódot kap.

Miért kell a detail::hash_value() = delete; „poison pill”? A nem minősített hash_value(v) hívásnál a szabály szerint, ha a hétköznapi névkeresés (ordinary lookup) nem függvényt, hanem objektumot (vagy más nem függvény entitást) talál, az ADL nem fut le. A my::hash_value CPO objektum, és a my névtérben van: ha a segédsablonok után deklaráljuk (mint fent), a definíciós ponton még nem látszik, de egy későbbi átrendezés vagy egy másik fejléc a keresést az objektumra terelheti, és az ADL elmaradna (rekurzió vagy hiba). A szabványos védekezés a poison pill: egy törölt, a detail névtérben deklarált, de soha nem illeszkedő void hash_value() = delete; biztosítja, hogy az ordinary lookup függvényt találjon, így az ADL mindig lefut, a sorrendtől függetlenül. Így működik a std::ranges::swap és a std::ranges::begin is.

A noexcept specifikációt a kiválasztott ág kifejezéséből vezetjük le (noexcept(noexcept(detail::adl_hash(value))), illetve noexcept(noexcept(my::hash_value_default(value)))), nem írjuk rá feltétel nélkül a segédfüggvényre; ha a felhasználói hash_value dobhat, a CPO sem noexcept.

A CPO használata:

#include <cstddef>

// A fenti my::hash_value CPO és a my::hash_value_default definíciója után:
namespace user {
    struct Point {
        int x, y;
    };
    // Felhasználói testreszabás
    std::size_t hash_value(const Point& p) noexcept {
        return static_cast<std::size_t>(p.x) * 31 + static_cast<std::size_t>(p.y);
    }
}

int main() {
    user::Point p{3, 4};
    auto h = my::hash_value(p);  // ADL: user::hash_value hívódik

    int i = 42;
    auto h2 = my::hash_value(i); // nincs ADL, hash_value_default hívódik
    (void)h; (void)h2;
}

Ez a példa mutatja a CPO erejét: a generikus kód egyetlen hívást használ, és a típus testreszabhatja a viselkedést anélkül, hogy a generikus kód módosulna. A my::hash_value CPO nem nyitott a hívó oldali using deklarációkra, és a jelöltek halmaza a CPO belsejében ellenőrzött.

7.3.8 A túlterhelésfeloldás és a CPO kapcsolata

A CPO belső logikája ugyanazt a túlterhelésfeloldást használja, mint bármely más kód, de a jelöltek halmazát a CPO szerzője szabályozza. A fenti hash_value példában a CPO két operator() túlterhelése között a koncepciók (megszorítások) döntenek: az első az ADL-lel talált hash_value-t hívja, a második a my::hash_value_default-ot, amelyet szándékosan minősített névvel hívunk, hogy a típus névteréből az ADL ne téríthesse el; csak az első ág használ (szándékosan) ADL-t. Ez a szerkezet megakadályozza, hogy a hívó oldali környezetből származó véletlen túlterhelések bekerüljenek a jelöltek közé.

Fontos megérteni, hogy a CPO operator()-a maga is túlterhelhető, de a hívó oldalon a CPO egyetlen neve szerepel. A CPO tehát egy jól definiált interfész, amely mögött a túlterhelésfeloldás rejtetten dolgozik.

A klasszikus using std::swap; minta lényegében ugyanezt a logikát valósítja meg, de nyíltan: a generikus kódba be kell írni a using deklarációt, és a hívó oldali környezet befolyásolhatja a jelölteket (például ha a hívó névtérben van egy másik swap függvény). A CPO ezt a befolyást zárja ki.

7.3.9 Tipikus hibák és buktatók

  1. Közvetlen std::swap hívás generikus kódban
    Ha a generikus kód std::swap(a, b);-t ír, a felhasználói swap nem vesz részt a túlterhelésfeloldásban, mert a minősített hívásnál az ADL nem fut le. Ez gyakran teljesítményromláshoz vagy helytelen viselkedéshez vezet. A helyes megoldás a using std::swap; swap(a,b); vagy, C++20-tól, std::ranges::swap(a,b);.

  2. A using std::swap; elhagyása
    Ha a generikus kód swap(a,b);-t ír, de nincs using std::swap;, az ADL megtalálhatja a felhasználói swap-ot, de az alapértelmezett std::swap nem lesz jelölt. Ha a típusnak nincs saját swap-ja, a fordítás hibát ad. A using deklaráció biztosítja a fallback-et.

  3. A felhasználói swap helytelen definiálása a std névtérben
    A std névteret a felhasználó általában nem bővítheti (kivéve bizonyos speciális esetekben, pl. std::hash specializáció). A swap testreszabást a saját típus névterébe kell írni, és az ADL fogja megtalálni. Ha a std névtérbe írunk swap-ot, az sértheti a szabványt, és hiba vagy kétértelműség léphet fel.

  4. A CPO név nem egyezik a felhasználói függvény nevével
    Ha a CPO-t my::hash_value-ként tervezzük, akkor a felhasználói típusnak a saját névterében hash_value nevű függvényt kell definiálnia, nem my::hash_value-t. Az ADL a típus névterét vizsgálja, ezért a felhasználói függvénynek a típus névterében kell lennie.

  5. A niebloidok félreértése
    A std::ranges::swap nem függvény, hanem objektum (CPO). Nem függvényként kell kiterjeszteni (nem túlterhelhető, nem adhatunk neki saját specializációt vagy túlterhelést); using std::ranges::swap; viszont érvényes, mert objektumra is írható using deklaráció. A testreszabást a CPO által támogatott formában kell megadni: a ranges::swap esetén az ADL-lel megtalálható szabad swap-pal (a tagfüggvényt nem keresi). A niebloid (pl. ranges::sort) szintén objektum, de nem testreszabási pont. Ha a felhasználói típus nem a CPO által elvárt módon definiálja a testreszabást, a kód nem fog lefordulni.

  6. A túlterhelésfeloldás félreolvasása
    A std::swap sablon és a felhasználói swap közötti versenyben a nem-sablon nyer. Ez általában kívánatos, de ha a felhasználói swap maga is sablon, akkor a részleges rendezés dönt. Ez ritkán okoz problémát, de érdemes tudni.

  7. A noexcept specifikáció hiánya a CPO-ban
    A CPO operator()-ának noexcept specifikációját a belső kifejezésből kell származtatni. Ha ez hiányzik vagy rossz, a generikus kód nem tudja optimálisan kihasználni a kivételgaranciákat, és a hibaüzenetek is megtévesztők lehetnek.

7.3.10 Labor: Saját testreszabási pont tervezése

A labor célja egy saját CPO tervezése és tesztelése. A feladat egy hash_value testreszabási pont, amely a fenti mintát követi, és működik a felhasználói típusok ADL-alapú testreszabásával. A kódot reprodukálható környezetben kell lefordítani és tesztelni.

7.3.11 Feladatleírás

  1. Hozz létre egy hash_value CPO-t a my névtérben, amely:
    • a felhasználói típusok számára ADL-lel található hash_value szabad függvényt használ, ha az létezik;
    • egyébként egy alapértelmezett hash_value_default-ot hív, amely std::hash-et használ az integrál, enum és pointer típusokra;
    • noexcept specifikációt a kiválasztott ág kifejezéséből származtat (nem feltétel nélküli noexcept).
  2. Definiálj egy Point típust a user névtérben, és adj hozzá saját hash_value függvényt.
  3. Írj teszteseteket, amelyek ellenőrzik:
    • my::hash_value(user::Point{...}) a saját függvény visszatérési értékét adja;
    • my::hash_value(42) az alapértelmezett std::hash<int> értékét adja;
    • a noexcept specifikáció helyes: noexcept felhasználói hash_value-ra igaz, dobhatóra hamis;
    • negatív teszt: olyan típusra, amelynek nincs hash_value-ja és nem integrál/enum/pointer, a CPO nem hívható (std::is_invocable_v hamis).
  4. Fordítsd a kódot C++20 szabvánnyal, és futtasd a teszteket.

7.3.13 Tesztprogram

// test_hash_value.cpp
#include <concepts>
#include <cstddef>
#include <functional>
#include <type_traits>
#include <utility>

namespace my {

template<class T>
    requires (std::is_integral_v<T> || std::is_enum_v<T> || std::is_pointer_v<T>)
constexpr std::size_t hash_value_default(const T& value) noexcept {
    return std::hash<T>{}(value);
}

namespace detail {
    // "Poison pill": ez a névtérbeli függvénydeklaráció biztosítja, hogy a nem
    // minősített hash_value(...) keresés függvényt találjon, így az ADL
    // mindig lefut, akkor is, ha a my::hash_value objektum már deklarált.
    void hash_value() = delete;

    template<class T>
    concept adl_hashable = requires(const T& v) {
        { hash_value(v) } -> std::convertible_to<std::size_t>;
    };

    template<class T>
    concept default_hashable = requires(const T& v) {
        { my::hash_value_default(v) } -> std::convertible_to<std::size_t>;
    };

    template<class T>
    constexpr std::size_t adl_hash(const T& v)
        noexcept(noexcept(static_cast<std::size_t>(hash_value(v))))
    {
        return static_cast<std::size_t>(hash_value(v));
    }
}

struct HashValueCPO {
    // 1. ág: a típus névterében talált (ADL) hash_value
    template<class T>
        requires detail::adl_hashable<T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(detail::adl_hash(value)))
    {
        return detail::adl_hash(value);
    }

    // 2. ág: alapértelmezett, ha nincs ADL-es hash_value
    template<class T>
        requires (!detail::adl_hashable<T>) && detail::default_hashable<T>
    constexpr std::size_t operator()(const T& value) const
        noexcept(noexcept(my::hash_value_default(value)))
    {
        return my::hash_value_default(value);
    }
};

inline constexpr HashValueCPO hash_value{};

} // namespace my

namespace user {
    struct Point {
        int x, y;
    };

    std::size_t hash_value(const Point& p) noexcept {
        return static_cast<std::size_t>(p.x) * 31 + static_cast<std::size_t>(p.y);
    }

    struct Throwing {};  // a hash_value dobhat: nincs noexcept
    std::size_t hash_value(const Throwing&) { return 1; }

    struct Opaque {};    // nincs hash_value, és nem integrál/enum/pointer
}

// Fordítási idejű ellenőrzések
static_assert(noexcept(my::hash_value(std::declval<const user::Point&>())));
static_assert(noexcept(my::hash_value(std::declval<const int&>())));
static_assert(!noexcept(my::hash_value(std::declval<const user::Throwing&>())));
static_assert(!std::is_invocable_v<decltype(my::hash_value), const user::Opaque&>);  // negatív teszt

int main() {
    int failures = 0;
    auto check = [&failures](bool ok) { if (!ok) ++failures; };  // NDEBUG-független

    user::Point p{3, 4};
    check(my::hash_value(p) == 3u * 31u + 4u);          // felhasználói testreszabás
    check(my::hash_value(42) == std::hash<int>{}(42));   // alapértelmezett ág
    check(my::hash_value(user::Throwing{}) == 1u);

    return failures;  // 0, ha minden ellenőrzés sikeres
}

7.3.15 Összefoglalás

Az alfejezetben megvizsgáltuk, hogyan kapcsolódik a túlterhelésfeloldás a testreszabási pontokhoz. A klasszikus using std::swap; minta az ADL-t és a túlterhelésfeloldást használja, hogy a felhasználói típusok testreszabhassák a generikus műveletet. C++20-tól a niebloidok és a CPO-k ezt a mintát szabványosították: a CPO objektum, nem függvény, így az ADL nem avatkozik be, a testreszabást pedig a CPO belső logikája, ellenőrzött keretek között végzi. A std::ranges::swap és std::ranges::begin példái mutatják a modern megközelítést, míg a saját hash_value CPO implementációja a gyakorlati tervezést.

A legfontosabb tanulságok:

  • A generikus kódban a testreszabást a típusok környezetébe kell helyezni, és az ADL-t kell használni a felfedezésére.
  • A using std::swap; minta biztosítja az alapértelmezett fallback-et.
  • A CPO-k kiküszöbölik a using deklarációt, és jobb hibadiagnosztikát adnak.
  • A saját CPO tervezésekor a noexcept specifikációt és a túlterhelésfeloldást gondosan kell kezelni.

7.3.16 Önellenőrző kérdés

Miért nem találja meg a következő generikus kód a felhasználói swap-ot, és hogyan javítanád?

template<class T>
void call_swap(T& a, T& b) {
    std::swap(a, b);   // ???
}

Válasz: A std::swap(a, b) hívás minősített névvel hívja a std névtérbeli swap-ot, így az ADL nem kerül alkalmazásra, ezért a T típus saját swap-ja nem vesz részt a túlterhelésfeloldásban. A javítás:

template<class T>
void call_swap(T& a, T& b) {
    using std::swap;
    swap(a, b);
}

vagy C++20-tól:

std::ranges::swap(a, b);

Mindkét esetben a felhasználói swap (ha van) elsőbbséget élvez; a using std::swap; mintánál a std::swap az alapértelmezett, a std::ranges::swap-nál pedig a move-alapú csere.
