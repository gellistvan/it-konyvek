11.1 Type erasure alapelvei

A type erasure (típuskitörlés) az egyik leghatékonyabb C++-technika, amely lehetővé teszi, hogy különböző, egymással semmilyen kapcsolatban nem álló típusokat egységes, értékalapú interfészen keresztül kezeljünk. Ahelyett, hogy minden konkrét típusnak egy közös ősosztályból kellene származnia, a type erasure egy sablonos adapterréteggel rejti el a konkrét típust, miközben a használó számára egyetlen, jól definiált interfészt kínál. Ebben az alfejezetben az alapelveket, a value semantics szerepét és a hagyományos örökléssel való összehasonlítást járjuk körül, majd egy ellenőrzött labor keretében egyszerű type erasure-t implementálunk.

11.1.1 A típusinformáció elrejtése és a közös interfész

A hagyományos dinamikus polimorfizmus C++-ban az öröklésen és virtuális függvényeken alapul. Egy Shape ősosztályból származtatjuk a Circle, Rectangle stb. osztályokat, és mindegyik felüldefiniálja a virtuális draw() és area() tagfüggvényeket. A használó Shape* vagy Shape& típuson keresztül hívja ezeket, a dinamikus objektum pedig a vtable segítségével a megfelelő implementációt futtatja.

Ez a modell azonban több korláttal jár:

  • Közös ősosztály kényszer: minden típusnak öröklődnie kell a közös interfészből. Külső, harmadik féltől származó típusok vagy primitívek (pl. int, double) nem illeszthetők ilyen hierarchiába anélkül, hogy wrapper osztályt írnánk.
  • Referencia-szemantika: a virtuális polimorfizmus pointerrel vagy referenciával működik, ami élettartam-kezelést igényel (a kézi new/delete nem kötelező: std::unique_ptr/std::shared_ptr kezelheti). A value semantics (értékalapúság) elveszik – a másolásnál nem tudjuk egyszerűen lemásolni a dinamikus objektumot, mert a statikus típus csak az ősosztály.
  • Intruzivitás: a típust módosítani kell, hogy illeszkedjen a rendszerbe, ami nem mindig lehetséges.

A type erasure ezzel szemben nem követeli meg a közös ősosztályt. (Az értékszemantika a fenti Shape példában választott kialakítás, nem a fogalom definíciója: a type erasure lehet kölcsönző, move-only vagy nem virtuális modellű is, például std::function_ref (C++26), std::move_only_function (C++23).) Helyette egy absztrakt, belső interfészt definiál, amelyet egy sablonos tároló osztály valósít meg a konkrét típushoz. A külső wrapper osztály ezt az interfészt birtokolja, gyakran std::unique_ptr formájában, és a hívásokat delegálja. A konkrét típus csak a sablonos konstruktorban jelenik meg, utána a statikus típusból “kitörlődik”. A viselkedés azonban megmarad, mert a belső modell objektum virtuális függvényei továbbítják a hívást a tárolt objektumhoz.

A type erasure tehát futásidejű polimorfizmust ad anélkül, hogy a résztvevő típusoknak bármilyen rokonságban kellene állniuk. A közös interfészt a wrapper osztály definiálja, és bármely típus, amely megfelel a szükséges műveleteknek (azaz concept-szerű követelményeknek), beilleszthető.

11.1.2 Value semantics és concept-based interfész

A modern C++-ban a value semantics (értékalapú szemantika) kiemelt fontosságú: az objektumok úgy viselkednek, mint a beépített típusok – másolhatók, mozgathatók, értékadhatók, és élettartamukat a scope határozza meg. A type erasure gyakori célja, hogy ezt a value semantics-t biztosítsa heterogén típusok számára anélkül, hogy a használó pointerekkel bajlódna.

A concept-based interfész alatt azt értjük, hogy a wrapper osztály nem egy konkrét típust, hanem egy műveleti követelményhalmazt (concept) ír elő. A C++20 bevezette a concept nyelvi elemet, de a type erasure esetén a “concept” nem feltétlenül nyelvi concept, hanem egy implicit szerződés: a típusnak rendelkeznie kell bizonyos tagfüggvényekkel vagy szabad függvényekkel, amelyeket a sablonos modell meg tud hívni.

A tipikus megvalósítás három rétegű:

  1. Absztrakt interfész (ShapeConcept): tisztán virtuális függvényekkel definiálja a nyilvános műveleteket, valamint a value semantics-hoz szükséges klónozó műveletet.

    class ShapeConcept {
public:
    virtual ~ShapeConcept() = default;
    virtual void draw() const = 0;
    virtual double area() const = 0;
    virtual std::unique_ptr<ShapeConcept> clone() const = 0;
};

  2. Sablonos modell (ShapeModel<T>): tárolja a konkrét T objektumot, és implementálja az absztrakt interfészt a T műveleteire delegálva.

    template<typename T>
class ShapeModel final : public ShapeConcept {
public:
    explicit ShapeModel(T value) : value_(std::move(value)) {}

    void draw() const override { value_.draw(); }
    double area() const override { return value_.area(); }

    std::unique_ptr<ShapeConcept> clone() const override {
        return std::make_unique<ShapeModel<T>>(value_);
    }

private:
    T value_;
};

  3. Wrapper (Shape): értékalapú interfész, amely std::unique_ptr<ShapeConcept>-et tart, és a speciális tagfüggvényeket a klónozás segítségével valósítja meg.

    class Shape {
public:
    template<typename T>
        requires (!std::same_as<std::remove_cvref_t<T>, Shape>
                  && std::copy_constructible<T>
                  && requires(const T& t) {
                         t.draw();
                         { t.area() } -> std::convertible_to<double>;
                     })
    Shape(T value)
        : pimpl_(std::make_unique<ShapeModel<T>>(std::move(value))) {}

    Shape(const Shape& other)
        : pimpl_(other.pimpl_ ? other.pimpl_->clone() : nullptr) {}

    Shape& operator=(const Shape& other) {
        if (this != &other) {
            pimpl_ = other.pimpl_ ? other.pimpl_->clone() : nullptr;
        }
        return *this;
    }

    Shape(Shape&&) noexcept = default;
    Shape& operator=(Shape&&) noexcept = default;
    ~Shape() = default;

    void draw() const { pimpl_->draw(); }
    double area() const { return pimpl_->area(); }

private:
    std::unique_ptr<ShapeConcept> pimpl_;
};

Ennek a szerkezetnek köszönhetően a Shape objektum értékként másolható, mozgatható, és a használó számára egyetlen típusnak látszik. A konkrét típus (pl. Circle) csak a konstruktorban jelenik meg explicit módon; a Shape belsejében a ShapeModel<Circle> példány végzi a tényleges munkát.

A value semantics megvalósításának kulcsa a clone() metódus. Ez egy virtuális “copy constructor”, amely a dinamikus objektum pontos típusának ismeretében lemásolja a tárolt értéket, és visszaad egy új std::unique_ptr-t az absztrakt interfészre. A std::unique_ptr másolása tiltott, ezért a clone() nélkül a Shape másoló konstruktora nem is fordulna le; ha pedig nyers pointerre cserélnénk a tárolást, a pointer másolása sekély másolatot és kettős felszabadítást okozna. A clone() biztosítja, hogy minden másolat saját, független tárolt objektumot kapjon. A clone() megléte teszi lehetővé, hogy a Shape értékalapú maradjon, miközben a háttérben dinamikus allokációt használ.

A sablonos konstruktor miatt a Shape implicit konverziót biztosít bármely olyan típusból, amely másolható, és rendelkezik const draw() és area() tagfüggvénnyel (az area() eredménye double-lá konvertálható). A fenti requires kikötés ezt pontosan kifejezi: a clone() másolást igényel, ezért a Shape ebben a kialakításban nem fogad tetszőleges, csak mozgatható típust; a !same_as<..., Shape> tag pedig megakadályozza, hogy a sablonos konstruktor a Shape saját másolásába avatkozzon. Ez a “concept-based interfész” gyakorlati megvalósítása: nincs explicit interfész deklaráció a konkrét típusban, csak a wrapper által támasztott követelmények, a megsértésük pedig a konstruktor megszorításánál, olvasható hibaüzenettel jelentkezik. Megszorítás nélkül (C++11 stílusban) a hiba a modell példányosításakor, mélyebben jelentkezik. A kódhoz #include <concepts>, <memory>, <type_traits> és <utility> szükséges.

Üres (moved-from) állapot. A Shape(Shape&&) = default után a forrásobjektum pimpl_ mutatója üres. Egy ilyen objektumon a draw()/area() hívása null pointer dereferálás, azaz undefined behavior; a megengedett műveletek a megsemmisítés, az értékadás és (a másoló konstruktor other.pimpl_ ? … : nullptr ága miatt) a másolás. A használati szerződés tehát: moved-from Shape-et csak újra értékül adni vagy megsemmisíteni szabad.

11.1.3 Type erasure vs. inheritance

A type erasure nem helyettesíti teljesen az öröklést, hanem egy alternatív eszköz a dinamikus polimorfizmus megvalósítására, amikor a hagyományos hierarchia nem megfelelő. A két megközelítés összehasonlítása:

Szempont Öröklés (virtuális polimorfizmus) Type erasure
Közös ősosztály Szükséges Nem szükséges
Value semantics Nem természetes (pointer/referencia) Igen, értékalapú
Külső típusok adaptálása Nehézkes (wrapper osztály kell) Természetes (sablonos konstruktor)
Dinamikus allokáció Jellemzően igen (new) Igen, általában (de optimalizálható)
Virtuális hívás költsége Egy virtuális hívás (pl. unique_ptr<Shape>-en át) Egy virtuális hívás a modellbe (a pimpl-mutató betöltése nem önálló indirekt vezérlésátadás); a modellből a T tagjának hívása közvetlen és inline-olható
Kódgenerálás Kevésbé (egy vtable) Több (sablonos modell minden típushoz)
Típusbiztonság Fordítási időben ellenőrzött a közös interfész Fordítási időben ellenőrzött a konstruktorban, utána típusbiztos a wrapper
Kiterjeszthetőség Új típus = új osztály, amelynek ismernie kell az ősosztályt és származnia kell belőle Új típus hozzáadása = nincs változás a wrapperben és a típusban sem (elég, ha teljesíti a követelményeket)
Bináris interfész Az absztrakt bázis vtable-je és layoutja a szerződés része A wrapper layoutja a példában nem függ T-től (mindig egy unique_ptr); az ABI-t a sablonos, fejlécbe ágyazott kód verziófüggése és a concept vtable terheli, implementációfüggően

Az öröklés előnye, hogy a közös ősosztály explicitté teszi a szerződést, és a virtuális függvények vtable-je egyetlen, jól meghatározott helyen van. A típusok közötti kapcsolat dokumentált, és a fordító segít a helyes használatban. Emellett az öröklési hierarchia lehetővé teszi a dinamikus típus vizsgálatát (dynamic_cast), ami type erasure esetén nem elérhető (legalábbis nem triviálisan).

A type erasure előnye, hogy nem invazív: bármely meglévő típust be lehet illeszteni anélkül, hogy módosítanánk. A használó egyetlen értékalapú típust lát, amelyet könnyű tárolni, átadni, visszaadni. A különböző konkrét típusok keverhetők egyetlen konténerben (std::vector<Shape>), ami heterogén gyűjteményeket tesz lehetővé értékalapú módon.

A type erasure futási költsége a hívásonkénti egy virtuális hívás (a Shape a pimpl_ mutatón át a ShapeConcept vtable-jét használja); a ShapeModel<T> a T tagfüggvényét már közvetlenül, inline-olhatóan hívja. Ez a költség lényegében ugyanannyi, mint egy std::unique_ptr<Base>-en át végzett virtuális hívásé az öröklési modellben; a különbség a wrapper és a modell együttes allokációjában és a kódgenerálásban jelentkezik, a konkrét mértéket mérni kell. Emellett a sablonos modell minden konkrét típushoz külön kódot generál, ami növelheti a bináris méretet. A dinamikus allokáció is gyakori, bár kis objektum optimalizációval (small buffer optimization) csökkenthető.

Mikor válasszuk a type erasure-t? - Amikor a típusok nem hozhatók közös ősosztály alá (pl. primitívek, külső típusok). - Amikor value semantics-t szeretnénk (pl. std::function, std::any). - Amikor a használó felé egyetlen, egyszerű interfészt akarunk adni, és a konkrét típusokat nem akarjuk kiszivárogtatni. - Amikor a típusok gyakran változnak, és a hierarchia karbantartása nehézkes.

Mikor maradjunk az öröklésnél? - Amikor a típusok természetesen hierarchiába szervezhetők, és a közös ősosztály valódi “is-a” kapcsolatot fejez ki. - Amikor szükség van a dinamikus típus vizsgálatára (dynamic_cast, RTTI). - Amikor az objektumokat nem kell értékként másolni, és a clone()-alapú mély másolás vagy a típusonkénti modellpéldányosítás (kódméret) költsége nem vállalható. - Amikor bináris kompatibilitást kell fenntartani: az absztrakt interfész vtable-elrendezése explicit szerződés lehet, de a sablonos type erasure ABI-jának stabilitása implementáció- és verziófüggő, ezért külön dokumentálandó.

Fontos megjegyezni, hogy a type erasure nem zárja ki az öröklést a belső megvalósításban: a ShapeConcept és ShapeModel<T> közötti kapcsolat éppen öröklés. A type erasure lényege, hogy ezt a hierarchiát a wrapper mögé rejti, és a használó számára értékalapú interfészt ad.

11.1.4 Labor: egyszerű type erasure implementálása

A következő labor célja egy minimális, de teljes type erasure minta elkészítése, amelyet lefordítunk, tesztelünk és mérünk. A kód a fenti Shape példát valósítja meg, de kiegészítjük néhány konkrét típussal és egy teszttel.

11.1.4.1 Fordítási környezet

A laborhoz a következő fordítókat és beállításokat használjuk (a mérési naplóban rögzítjük): - GCC 13.2 – g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -O2 -g -fsanitize=address,undefined - Clang 17.0 – clang++ -std=c++20 -Wall -Wextra -Wpedantic -Werror -O2 -g -fsanitize=address,undefined - MSVC 2022 (19.38) – cl /std:c++20 /EHsc /W4 /WX /O2 /fsanitize=address

A buildrendszer itt egyszerű parancssori fordítás (a laborhoz nem tartozik külön CMake-projekt vagy mellékelt buildfájl). A kód a C++20 szabványt használja, de a type erasure minta C++11-től működik; a std::make_unique C++14-től elérhető.

11.1.4.2 Forráskód

A teljes kód egyetlen fájlban van (shape_erasure.cpp), de a fejezet laborjában külön header és forrásfájl is lehet. A következő kódot használjuk:

#include <concepts>
#include <iostream>
#include <memory>
#include <type_traits>
#include <utility>
#include <vector>

// Belső absztrakt interfész
class ShapeConcept {
public:
    virtual ~ShapeConcept() = default;
    virtual void draw() const = 0;
    virtual double area() const = 0;
    virtual std::unique_ptr<ShapeConcept> clone() const = 0;
};

// Sablonos modell a konkrét típushoz
template<typename T>
class ShapeModel final : public ShapeConcept {
public:
    explicit ShapeModel(T value) : value_(std::move(value)) {}

    void draw() const override { value_.draw(); }
    double area() const override { return value_.area(); }

    std::unique_ptr<ShapeConcept> clone() const override {
        return std::make_unique<ShapeModel<T>>(value_);
    }

private:
    T value_;
};

// Nyilvános, értékalapú wrapper
class Shape {
public:
    template<typename T>
        requires (!std::same_as<std::remove_cvref_t<T>, Shape>
                  && std::copy_constructible<T>
                  && requires(const T& t) {
                         t.draw();
                         { t.area() } -> std::convertible_to<double>;
                     })
    Shape(T value)
        : pimpl_(std::make_unique<ShapeModel<T>>(std::move(value))) {}

    Shape(const Shape& other)
        : pimpl_(other.pimpl_ ? other.pimpl_->clone() : nullptr) {}

    Shape& operator=(const Shape& other) {
        if (this != &other) {
            pimpl_ = other.pimpl_ ? other.pimpl_->clone() : nullptr;
        }
        return *this;
    }

    Shape(Shape&&) noexcept = default;
    Shape& operator=(Shape&&) noexcept = default;
    ~Shape() = default;

    // Előfeltétel: a Shape nem moved-from (pimpl_ != nullptr).
    void draw() const { pimpl_->draw(); }
    double area() const { return pimpl_->area(); }

private:
    std::unique_ptr<ShapeConcept> pimpl_;
};

// Konkrét típusok – semmilyen közös ősosztályt nem igényelnek
class Circle {
public:
    explicit Circle(double radius) : radius_(radius) {}
    void draw() const { std::cout << "Drawing circle with radius " << radius_ << '\n'; }
    double area() const { return 3.14159 * radius_ * radius_; }
private:
    double radius_;
};

class Rectangle {
public:
    Rectangle(double width, double height) : width_(width), height_(height) {}
    void draw() const { std::cout << "Drawing rectangle " << width_ << "x" << height_ << '\n'; }
    double area() const { return width_ * height_; }
private:
    double width_, height_;
};

int main() {
    std::vector<Shape> shapes;
    shapes.emplace_back(Circle{2.0});
    shapes.emplace_back(Rectangle{3.0, 4.0});

    for (const auto& shape : shapes) {
        shape.draw();
        std::cout << "Area: " << shape.area() << '\n';
    }

    // Másolás tesztelése
    Shape copied = shapes[0];
    copied.draw(); // ugyanazt rajzolja, mint az eredeti
    std::cout << "Copied area: " << copied.area() << '\n';

    return 0;
}

11.1.4.3 Tesztelés és elvárt eredmény

A program fordításakor semmilyen figyelmeztetés nem keletkezhet (-Werror). Futtatáskor a sanitizereknek nem szabad hibát jelezniük. A kimenet a következő:

Drawing circle with radius 2
Area: 12.5664
Drawing rectangle 3x4
Area: 12
Drawing circle with radius 2
Copied area: 12.5664

A kimenet hat sor; a Shape copied = shapes[0]; copied.draw(); külön „Drawing circle with radius 2” sort ír a „Copied area” elé. A területértékek double számok, a kiírt 6 értékes jegyű szöveges forma (alapértelmezett std::cout precizitás) csak szemrevételezésre alkalmas; automatikus ellenőrzéshez toleranciás összehasonlítás kell (például std::abs(copied.area() - 12.56636) < 1e-4, mert a példa 3.14159-et használ π\pi helyett). A teszteset a main függvényben található; a teljes laborhoz külön tesztfájl is készíthető.

11.1.5 Ellenőrző kérdés

Miért van szükség a clone() metódusra a ShapeConcept interfészben? Mi történne, ha a Shape másoló konstruktora egyszerűen lemásolná a pimpl_ pointert?

Válasz: A clone() metódus az úgynevezett “virtuális másoló konstruktor”, amely a dinamikus típus ismeretében új, azonos típusú dinamikus objektumot hoz létre. A pimpl_ = other.pimpl_ értékadás std::unique_ptr esetén fordítási hiba (a másoló művelet törölt), mert a unique_ptr kizárólagos tulajdonos. Ha a tárolást nyers pointerre (vagy shared_ptr-re) cserélnénk, a pointer másolása ugyanarra a dinamikus objektumra mutató másolatot adna: nyers pointernél ez sekély másolat és kettős felszabadítás (double free) kockázata, shared_ptr-nél pedig közös állapot, ami megsérti az értékszemantikát. A clone() nélkül a value semantics nem valósítható meg biztonságosan; ezért minden type erasure wrappernek, amely értékalapú másolást ígér, rendelkeznie kell valamilyen klónozó mechanizmussal.

11.1.6 Összegzés

A type erasure alapelve a típusinformáció elrejtése egy belső absztrakt interfész mögött, és a konkrét típusok sablonos modellen keresztüli adaptálása. Ezáltal heterogén típusokat értékalapú, egységes interfészen keresztül kezelhetünk anélkül, hogy közös ősosztályra lenne szükség. A value semantics fenntartásához klónozó műveletre van szükség, amely a dinamikus objektum pontos típusát ismerve készít másolatot. A type erasure és az öröklés egymást kiegészítő eszközök: az öröklés explicit hierarchiát ad, míg a type erasure rugalmasságot és értékalapúságot biztosít; a hívásköltség mindkettőnél egy virtuális hívás, a különbség az allokációban, a másolásban és a kódméretben van (mérendő). A következő alfejezetben a standard könyvtár type erasure eszközeit (std::any, std::variant, std::function) vizsgáljuk meg, amelyek ezt a mintát készen kínálják.
