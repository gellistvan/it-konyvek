25.3 Pimpl, compilation firewall és plugin API

A fordítási és bináris határok megértése nélkül a Pimpl és a plugin API csupán trükknek tűnik. A C++ fordítási modellje a fordítási egységekre (translation unit, TU) épül: minden .cpp fájl a benne szereplő #include direktívák után egy önálló egységet alkot, amelyet a fordító külön dolgoz fel. A TU-k közötti kapcsolatot a deklarációk teremtik meg: egy headerben deklarált függvény vagy osztály lehetővé teszi, hogy más TU-k hivatkozzanak rá anélkül, hogy ismernék a definícióját. Ez a fordítási határ: amit a header tartalmaz, az minden azt include-oló TU-ba bekerül, így annak bármilyen változása az összes érintett TU újrafordítását kényszeríti ki.

A bináris határ ezzel szemben a lefordított objektumfájlok, statikus könyvtárak és megosztott könyvtárak közötti interfész. Itt már nem forráskód, hanem gépi kód, szimbólumtábla és hívási konvenciók léteznek. A bináris határon az osztályok elrendezése, a virtuális függvénytábla (vtable) felépítése, a függvények névtorzítása (name mangling) és a paraméterátadás módja mind rögzített. Ha ezek bármelyike megváltozik, a bináris kompatibilitás megszakad, és a régi binárisok nem működnek együtt az új könyvtárral.

A Pimpl (pointer-to-implementation) minta éppen e két határ kezelésére szolgál: a fordítási határon csökkenti a függőséget, a bináris határon pedig stabil ABI-t biztosít. A plugin API-k pedig a bináris határ legszigorúbb formáját valósítják meg: olyan interfészt, amely akár különböző fordítóval vagy nyelvvel készült binárisok között is működik.

25.3.1 Pimpl és opaque pointer

A Pimpl alapötlete, hogy az osztály publikus headerje ne tartalmazza a privát adattagok típusát, csak egy mutatót egy előre deklarált, nem teljes típusra. A tényleges adattagok a .cpp fájlban definiált struktúrában élnek. Ezt a mutatót gyakran opaque pointernek nevezik, mert a header szempontjából a mutatott típus átlátszatlan.

Tekintsünk egy naiv Logger osztályt, amelynek privát adattagjai között szerepel egy std::ofstream és egy std::mutex:

// naive_logger.h
#pragma once
#include <fstream>
#include <mutex>
#include <string>
#include <string_view>

class Logger {
public:
    explicit Logger(std::string filename);
    void log(std::string_view message);

private:
    std::ofstream file_;
    std::mutex mutex_;
    std::string filename_;
};

Ennek a headernek minden felhasználója kénytelen include-olni a <fstream>, <mutex> fejléceket, és a privát adattagok bármilyen változása – például egy új puffer hozzáadása – újrafordítja az összes include-oló TU-t. Ráadásul az osztály mérete és elrendezése a bináris határon is rögzül, így a könyvtár frissítésekor a felhasználó binárisai elavulhatnak.

A Pimpl verzió a következő:

// logger.h
#pragma once
#include <memory>
#include <string_view>
#include <string>

class Logger {
public:
    explicit Logger(std::string filename);
    ~Logger();                      // destruktor a cpp-ben

    Logger(Logger&&) noexcept;      // move konstruktor
    Logger& operator=(Logger&&) noexcept;

    Logger(const Logger&) = delete; // másolás letiltva
    Logger& operator=(const Logger&) = delete;

    void log(std::string_view message);

private:
    class Impl;                     // előre deklarált, nem teljes típus
    std::unique_ptr<Impl> pImpl_;
};

A header mostantól csak a std::unique_ptr és a std::string_view deklarációit igényli, a nehéz fejléceket (<fstream>, <mutex>) nem. Az Impl osztály definíciója a .cpp fájlban található:

// logger.cpp
#include "logger.h"
#include <fstream>
#include <mutex>
#include <utility>   // std::move

class Logger::Impl {
public:
    explicit Impl(std::string filename)
        : file_(std::move(filename)), mutex_() {}

    void log(std::string_view message) {
        // Egyszerűsítés: a megnyitási/írási hibát nem vizsgáljuk (lásd lent)
        std::lock_guard<std::mutex> lock(mutex_);
        file_ << message << '\n';
    }

private:
    std::ofstream file_;
    std::mutex mutex_;
};

Logger::Logger(std::string filename)
    : pImpl_(std::make_unique<Impl>(std::move(filename))) {}

Logger::~Logger() = default;  // itt az Impl teljes típusa ismert

Logger::Logger(Logger&&) noexcept = default;
Logger& Logger::operator=(Logger&&) noexcept = default;

void Logger::log(std::string_view message) {
    pImpl_->log(message);   // moved-from Loggerre (pImpl_ == nullptr) UB; ne hívjuk
}

A destruktor default definíciója a .cpp fájlban létfontosságú: ha a headerben lenne (implicit vagy = default), a std::unique_ptr<Impl> destruktora ott példányosodna, ahol az Impl még nem teljes, a delete pedig teljes típust igényel. A std::default_delete ezt static_assert-tel jelzi, de ez az implementációk gyakorlata, nem az ISO szabvány által előírt diagnosztikai mechanizmus; a lényeg az, hogy a nem teljes típus törlése a szabvány szerint nem megengedett. A helyes megoldás az, hogy a destruktort abban a TU-ban definiáljuk, ahol az Impl teljes.

A move konstruktort és a move értékadást is a .cpp-ben definiáljuk (= default). A move értékadás kötelezően teljes Impl-et igényel, mert törli a cél régi objektumát; a puszta move konstrukció általában nem igényelne, de a kivételkezelési kód miatt egyes fordítók ott is teljes típust várnak, ezért a gyakorlat az, hogy mindkettőt out-of-line definiáljuk. A move új allokáció nélkül hoz létre objektumot, de a moved-from Logger pImpl_-je null: csak megsemmisíthető vagy értékadható. A copy műveletek törölve vannak; ez az = delete itt világos szerződés (nem a unique_ptr véletlen másolhatóságának ellenszere: a unique_ptr tag eleve törölté tenné az implicit másolást). Ha másolható Logger-t akarunk, kézzel kell implementálni a copy konstruktort és értékadót, amelyek új Impl-et hoznak létre.

Az alábbi ábra egyszerre mutatja a Pimpl két hatását: elvágja az include-függőséget (a kliens TU-k nem látják a nehéz fejléceket) és a layoutfüggőséget (a Logger mérete egy mutató marad), amikor a privát részhez egy új tag (buffer_) kerül.

A Pimpl minta tehát a következő előnyöket nyújtja:

  1. Fordítási tűzfal (compilation firewall): a privát adattagok változása nem érinti a header felhasználóit, így a build idő jelentősen csökkenhet nagy projektekben.
  2. Bináris stabilitás: az osztály mérete és elrendezése a headerben csak egy std::unique_ptr marad, amelynek mérete az alapértelmezett deleterrel gyakorlatilag egy mutató (egyedi deleternél nagyobb is lehet). Layoutstabilitást csak rögzített publikus típus, deleter és toolchain mellett állíthatunk. Így a privát implementáció bővítése nem változtatja meg az osztály layoutját, és a felhasználó binárisok újrafordítás nélkül működhetnek.
  3. Jobb izoláció: a header nem szivárogtatja ki a belső típusokat, csökkentve a névütközéseket és a felesleges include-okat.

Hátrányai is vannak: minden objektum egy heap allokációt igényel, a hívások egy indirekción mennek keresztül (a költség mérhető, de nem garantáltan nem nulla), és a kód bonyolultabbá válik. A header sem mindig elég a deklarációhoz: ha a klienskód érték szerint használja az osztályt, a <string> és társai továbbra is kellenek a publikus API-hoz. A std::unique_ptr használata miatt az osztály automatikusan nem másolható; ha másolásra van szükség, azt explicit módon kell megvalósítani, ami gyakran az Impl mély másolását jelenti.

25.3.2 Kivételbiztonság és erőforrás-kezelés

A Pimpl konstruktorban a std::make_unique<Impl> hívás kivételt dobhat, például std::bad_alloc-ot, vagy ha az Impl konstruktora kivételt dob (pl. explicit if (!file_) throw std::runtime_error{...};). A std::ofstream sikertelen megnyitáskor alapból nem dob kivételt, csak failbit-et állít, hacsak nem kapcsoljuk be az exceptions() maszkot; a fenti Logger ezt nem vizsgálja, ezért éles kódban vagy ellenőrizzük a megnyitást, vagy engedélyezzük a kivételeket. Kivétel esetén a std::unique_ptr még nem vette át a tulajdonjogot, így nem történik szivárgás, és ha a konstruktor törzsében dobunk, a már létrehozott pImpl_ automatikusan felszabadul. Ez a RAII elv természetes következménye.

A destruktor kivételt ne dobjon: a destruktor implicit noexcept, tehát ha az Impl destruktorából kivétel szökik ki, a program std::terminate-et hív, és a felszabadításra nincs általános garancia (a deleterből kiszökő kivétel a std::unique_ptr követelményeit is sérti, a viselkedés nem definiált). A fájl lezárási hibáit ezért külön API-n (pl. flush()/close() visszatérési kóddal) jelezzük.

25.3.3 Pimpl és ABI stabilitás

A Pimpl egyik legfontosabb alkalmazási területe a bináris kompatibilitás megőrzése. Tegyük fel, hogy egy megosztott könyvtár Logger osztályt exportál. Ha a naiv verzióban hozzáadunk egy std::string buffer_; adattagot, az osztály mérete megváltozik, és minden olyan kliens bináris, amely a régi headerrel lett lefordítva, hibásan fog működni, mert a tagok eltolása megváltozik. A Pimpl verzióban az osztály mérete változatlan marad, mert a headerben csak egy mutató van. A bővítés az Impl osztályt érinti, amely a .cpp fájlban van, így a kliens binárisok továbbra is érvényesek maradnak.

Fontos megjegyezni, hogy a Pimpl önmagában nem garantál teljes ABI kompatibilitást: ha a publikus függvények szignatúrája változik, vagy a névtorzítás eltér, a bináris kompatibilitás megszakad (a publikus tagfüggvények mangled neve a paramétertípusokat is kódolja). A Pimpl csak a privát adattagok változásától véd.

25.3.4 C ABI és plugin loading

A plugin API-k olyan bináris interfészek, amelyek lehetővé teszik, hogy a program futás közben töltsön be további kódbővítményeket. A plugin lehet külön folyamatban, de a leggyakoribb esetben ugyanabban a folyamatban, dinamikus könyvtárként töltődik be. A plugin határán a C++ típusok, kivételek, RTTI és memóriaallokátorok használata veszélyes, mert ezek ABI-ja nem stabil a különböző fordítók és verziók között. Ezért a plugin interfészeket gyakran C ABI-val definiálják: extern "C" függvények, egyszerű C típusok, és opak mutatók.

A C ABI alapelve:

  • A függvények extern "C" deklarációval rendelkeznek, így a nevük nem lesz torzított, és a hívási konvenciót az extern "C" nem módosítja: az a platform alapértelmezett konvenciója marad (lásd 25.1). A C linkage önmagában nem garantál minden platformon díszítetlen exportnevet, és nem teljes bináris kompatibilitás.
  • A paraméterek és visszatérési értékek csak olyan típusok lehetnek, amelyek elrendezése C-ben is definiált: alap típusok, mutatók, struktúrák, amelyek nem tartalmaznak C++-specifikus elemeket (virtuális függvények, std::string, stb.).
  • A hibakezelés visszatérési kódokkal vagy hibakódokkal történik, nem kivételekkel, mert a kivételek a C ABI-n keresztül nem terjednek.
  • A memóriakezelés explicit: a plugin által lefoglalt memóriát a plugin szabadítja fel, vagy a gazdaprogram egy megadott callback segítségével.

Egy egyszerű plugin interfész például egy szöveges üzeneteket feldolgozó modul:

// plugin_api.h (C ABI)
#ifndef PLUGIN_API_H
#define PLUGIN_API_H

#include <stddef.h>   // size_t

#ifdef __cplusplus
extern "C" {
#endif

// Opaque handle: a plugin belső állapotát rejti.
typedef struct plugin_handle_t plugin_handle_t;

// Plugin API verziója. A gazdaprogram ezzel ellenőrzi a kompatibilitást.
int plugin_api_version(void);

// Létrehoz egy plugin példányt. A visszatérési érték NULL hiba esetén.
plugin_handle_t* plugin_create(void);

// Feldolgoz egy üzenetet. Visszatérés: 0 siker, -1 hiba (null argumentum,
// belső hiba), -2 az output puffer túl kicsi (a lezáró nullával együtt
// result.size() + 1 bájt kell).
int plugin_process(plugin_handle_t* handle, const char* message,
                   char* output, size_t output_size);

// Felszabadítja a plugin példányt.
void plugin_destroy(plugin_handle_t* handle);

#ifdef __cplusplus
}
#endif

#endif /* PLUGIN_API_H */

Windowsra a szimbólumok exportját (__declspec(dllexport)) és a hívási konvenciót külön makróval kell szerződésbe foglalni (lásd 25.2). Az extern "C" nem noexcept: a kivétel kiszökése a C határon C-fogyasztónál nem definiált, kompatibilis C++ hívónál pedig ABI-függő, ezért a plugin minden belépési pontja elkapja a kivételeket. A plugin_handle_t egy opak típus: a gazdaprogram csak mutatót lát, a tényleges definíciót a plugin tartalmazza. Ez ugyanaz az opaque pointer elv, mint a Pimpl esetében, de itt a C ABI szintjén.

A plugin implementációja C++-ban a következő lehet:

// plugin_impl.cpp
#include "plugin_api.h"
#include <string>
#include <cstring>

struct plugin_handle_t {
    std::string prefix;
};

extern "C" int plugin_api_version(void) {
    return 1;
}

extern "C" plugin_handle_t* plugin_create(void) {
    try {
        return new plugin_handle_t{"[plugin] "};
    } catch (...) {
        return nullptr;
    }
}

extern "C" int plugin_process(plugin_handle_t* handle, const char* message,
                              char* output, size_t output_size) {
    if (!handle || !message || !output) return -1;
    try {
        std::string result = handle->prefix + message;
        if (result.size() + 1 > output_size) return -2; // puffer túl kicsi
        std::memcpy(output, result.c_str(), result.size() + 1); // csak az eredmény + lezáró nulla
        return 0;
    } catch (...) {
        return -1;
    }
}

extern "C" void plugin_destroy(plugin_handle_t* handle) {
    delete handle;
}

A gazdaprogram dinamikusan tölti be a plugint. POSIX rendszeren a dlopen, dlsym, dlclose függvényekkel, Windows-on a LoadLibrary, GetProcAddress, FreeLibrary függvényekkel. A példa POSIX-rendszerre:

A host és a plugin közti hívássorrendet, a hibaágakat és a két egymásba ágyazott élettartamot (a modulé a dlopen–dlclose, a handle-é a plugin_create–plugin_destroy között) az alábbi szekvenciadiagram foglalja össze; a kimenetek a lenti kód lefuttatásából származnak.

// host.cpp
#include "plugin_api.h"
#include <dlfcn.h>
#include <iostream>
#include <string>
#include <cstring>

int main() {
    void* lib = dlopen("./libplugin.so", RTLD_NOW);
    if (!lib) {
        std::cerr << "dlopen failed: " << dlerror() << '\n';
        return 1;
    }

    auto version_fn = reinterpret_cast<int (*)()>(
        dlsym(lib, "plugin_api_version"));
    auto create_fn = reinterpret_cast<plugin_handle_t* (*)()>(
        dlsym(lib, "plugin_create"));
    auto process_fn = reinterpret_cast<int (*)(plugin_handle_t*, const char*, char*, size_t)>(
        dlsym(lib, "plugin_process"));
    auto destroy_fn = reinterpret_cast<void (*)(plugin_handle_t*)>(
        dlsym(lib, "plugin_destroy"));

    if (!version_fn || !create_fn || !process_fn || !destroy_fn) {
        std::cerr << "missing symbols\n";
        dlclose(lib);
        return 1;
    }

    if (version_fn() != 1) {
        std::cerr << "incompatible plugin version\n";
        dlclose(lib);
        return 1;
    }

    plugin_handle_t* handle = create_fn();
    if (!handle) {
        std::cerr << "plugin_create failed\n";
        dlclose(lib);
        return 1;
    }

    char buffer[256];
    int rc = process_fn(handle, "hello", buffer, sizeof(buffer));
    if (rc == 0) {
        std::cout << "Result: " << buffer << '\n';
    } else {
        std::cerr << "plugin_process failed with code " << rc << '\n';
    }

    destroy_fn(handle);
    if (dlclose(lib) != 0) {
        std::cerr << "dlclose failed: " << dlerror() << '\n';
        return 1;
    }
    return rc == 0 ? 0 : 1;   // a hiba exit státuszban is látszik
}

A példa jól mutatja a C ABI használatát: a void*–függvénypointer konverzió az ISO C++ szerint legfeljebb feltételesen támogatott, a POSIX dlsym szerződése viszont garantálja (ezért POSIX-specifikus recept, nem általános C++ minta); a dlerror() protokollja (hívás előtt törölni, hívás után ellenőrizni) szintén a POSIX része; a példa egyszerűsítve csak a NULL visszatérést vizsgálja, ami függvényszimbólumnál elegendő. A példa további elemei: a verzióellenőrzés, a hibakezelés, és az erőforrások felszabadítása. A plugin_handle_t opak típus, a gazdaprogram nem fér hozzá a belső std::string taghoz.

25.3.5 A plugin API tervezési szempontjai

A plugin interfész tervezésekor a következő szempontokat kell figyelembe venni:

  1. Verziókezelés: a plugin API-nak mindig tartalmaznia kell egy verziószámot, amelyet a gazdaprogram a betöltéskor ellenőriz. Ez lehet egy függvény (plugin_api_version()), vagy egy struktúra, amely a verziót és a funkciópointereket tartalmazza. A verziószám növelése jelzi az inkompatibilis változásokat.

  2. Hibakezelés: a C ABI-n keresztül nem dobhatunk kivételeket, ezért minden függvénynek visszatérési kóddal kell jeleznie a sikert vagy hibát. A hibakódok értelmezését dokumentálni kell. A plugin implementációban minden kivételt el kell kapni, és hibakóddá kell alakítani.

  3. Memóriakezelés: a plugin által lefoglalt memória felszabadítását a plugin végzi, mert a gazdaprogram esetleg más allokátort használ. Ha a gazdaprogram ad át puffert, annak méretét explicit paraméterben kell megadni, és a plugin nem írhat túl rajta.

  4. Szálbiztonság: ha a plugin függvényeit több szálból hívják, a plugin belső állapotát szinkronizálni kell. A C ABI nem tartalmaz szinkronizációs primitíveket, ezért a plugin dokumentációjában rögzíteni kell a szálbiztonsági garanciákat.

  5. Nyelvfüggetlenség: a C ABI lehetővé teszi, hogy a plugin más nyelven (C, Rust, Python CFFI) is implementálható legyen. Ez növeli a rugalmasságot, de a típusoknak C-kompatibilisnek kell lenniük.

25.3.6 Tipikus hibák és elkerülésük

A Pimpl és plugin API használata során a következő hibák gyakoriak:

  • Destruktor a headerben (inline definíció): Ha a destruktort a headerben deklaráljuk ~Logger() = default; és az Impl nem teljes, a fordító hibát ad, mert a std::unique_ptr destruktora nem tudja törölni a nem teljes típust. A megoldás: a destruktort a .cpp fájlban definiáljuk.

  • Másolás engedélyezése véletlenül: std::unique_ptr tag esetén az implicit másolás törölt, így a hiba csak használatkor fordítási hiba. A veszélyes eset a nyers Impl* tag (lásd 25.1 Pimpl-példa): ott az implicit másolás kettős delete-hez vezet, ezért a másolást = delete-tel kell tiltani vagy mélyen implementálni.

  • Kivétel a plugin határon: Ha a plugin függvényben kivétel dobódik, és az nem kerül elkapásra a extern "C" függvényen belül, a kivétel átlépi a C ABI határt, ami undefined behavior. Minden plugin függvényt try/catch blokkba kell zárni.

  • Nem megfelelő verzióellenőrzés: A gazdaprogramnak mindig ellenőriznie kell a plugin verzióját a betöltés után, különben inkompatibilis plugin esetén a viselkedés nem definiált.

  • Szimbólumnevek ütközése: Azonos extern "C" belépési pontnevek két plugin között dlopen(…, RTLD_LOCAL) és dlsym(handle, …) használatakor nem ütköznek (a plugin-rendszerek éppen azonos belépési pontnevekre épülnek). Ütközés (interpozíció) RTLD_GLOBAL esetén, vagy a plugin belső, nem rejtett C++ és C szimbólumainál léphet fel; a teljes elérési út a dlopen-nél ezt önmagában nem akadályozza meg. Védekezés: -fvisibility=hidden és csak a belépési pontok exportja (lásd 25.2), egyedi előtagok a belső szimbólumokon.

  • Erőforrás-szivárgás a plugin életciklusban: A gazdaprogramnak mindig párosítania kell a create és destroy hívásokat, és a dlclose előtt minden handle-t fel kell szabadítani. A modul őrzője (a dlopen handle) éljen tovább minden tőle függő objektumnál, függvénypointernél, callbacknél és folyamatban lévő hívásnál; unload után ne maradjon használt alias. A dlclose nem garantál azonnali unmapet, de a modul kódjára hivatkozni utána nem szabad (UB). A dlclose hibáját is kezeljük, és nyers handle mellett RAII-burkolót (pl. unique_ptr egyedi deleterrel) érdemes használni, hogy egy későbbi kivétel ne okozzon szivárgást.

25.3.7 Labor: Pimpl- és plugin-API tervezése

A labor célja a fenti minták gyakorlati alkalmazása. A feladat:

  1. Készíts egy Config osztályt Pimpl mintával, amely egy JSON-szerű konfigurációt tárol. A header csak a publikus interfészt tartalmazza, a privát implementáció a .cpp fájlban van. Az osztály támogassa a move szemantikát, a másolást mély másolással, és a destruktort a .cpp-ben definiálja.

  2. Tervezz egy plugin API-t C ABI-val egy egyszerű szűrő modulhoz, amely szöveges üzeneteket transzformál (pl. nagybetűsítés, előtag hozzáadása). A plugin API tartalmazzon verziókezelést, hibakódokat, opak handle-t, és a memória kezelését.

  3. Valósítsa meg a plugint és a gazdaprogramot, amely dinamikusan tölti be a plugint, ellenőrzi a verziót, feldolgoz egy üzenetet, és felszabadítja az erőforrásokat.

Referenciamegoldás nincs a csomagban: a Config (mély másolás: a copy konstruktor és értékadás új Impl-et klónoz) és a szűrő plugin az olvasó feladata, a fenti Logger és plugin_* példák mintájára. A szűrő plugin API vázlata: plugin_api_version, plugin_create, plugin_process (visszatérés: 0 siker, -1 hiba, -2 kis puffer), plugin_destroy.

25.3.8 Build és tesztkörnyezet

A labor elvégzéséhez a következő build konfigurációt javasoljuk:

  • Fordító: GCC 13 vagy Clang 17, C++20 standard (-std=c++20).
  • Optimalizáció: -O2 -g a fejlesztéshez, -O3 -DNDEBUG a méréshez.
  • Figyelmeztetések: -Wall -Wextra -Wpedantic -Wconversion -Wsign-conversion.
  • Sanitizerek: -fsanitize=address,undefined a teszteléshez.
  • Dinamikus könyvtár: -fPIC -shared a plugin fordításhoz.
  • Linkelés: -ldl régebbi glibc-nél a dlopen használatához (glibc 2.34 óta a libc része; más POSIX rendszeren eltérhet).

A build parancsok például (Linux, GCC):

# Pimpl osztály fordítása
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic -c config.cpp -o config.o

# Plugin fordítása megosztott könyvtárrá
g++ -std=c++20 -O2 -fPIC -shared plugin_impl.cpp -o libplugin.so

# Gazdaprogram fordítása
g++ -std=c++20 -O2 -Wall -Wextra -Wpedantic host.cpp config.o -ldl -o host

# Sanitizeres változat (a tesztprogram is: test_config.cpp feltételezett fájlnév)
g++ -std=c++20 -O1 -g -fsanitize=address,undefined config.cpp test_config.cpp -o test_config

A tesztprogramban az assert-ek -DNDEBUG mellett kiesnek; a tesztet ezért -DNDEBUG nélkül, a méréseket külön buildben végezzük.

25.3.9 Tesztcsomag

A tesztek a következő eseteket fedik le:

  • A Config osztály konstrukciója és destruálása nem szivárog (ASan ellenőrzés).
  • A Config másolása mély másolatot hoz létre, a módosítás nem érinti az eredetit.
  • A plugin betöltése sikeres, a verzió ellenőrzése megtörténik.
  • A plugin process függvénye hibásan null mutatóval hívva -1-et ad vissza.
  • A plugin_process 1 bájtos kimeneti puffernél -2-t ad, és a puffert nem írja túl (ASan alatt is tiszta); pontosan strlen("[plugin] hello") + 1 = 15 bájtos puffernél 0-t.
  • A „destroy után a gazdaprogram nem hívja a plugint” követelmény kódellenőrzési (review) szempont, nem automatizált teszteset.

A teszteket egy egyszerű C++ teszt keretrendszerrel (pl. Catch2, doctest) vagy saját assert alapú main-nel lehet futtatni.

25.3.10 Mérési napló

A mérési naplóban rögzíteni kell a következőket:

  • Fordítási idő: a Pimpl verzió és a naiv verzió build ideje. Két külön kísérlet kell: (a) az Impl (a .cpp) változtatása nem érinti a függő TU-kat, csak a .cpp-t kell újrafordítani és újralinkelni; (b) a publikus header változása minden függő TU-t újrafordít. Módszer: privát tag hozzáadása után make időzítés (pl. time make) a Pimpl és a naiv változatnál; a statikus és a dinamikus linkelést külön mérjük. A várt eredmény: (a) esetben a build idő csökken; a mért értékeket a napló „mért” oszlopába kell írni.
  • Bináris méret: a Pimpl osztályt használó kliens objektumfájl mérete várhatóan változatlan, ha az Impl bővül; a közvetlenül belinkelt config.o változásakor a host fájlmérete viszont nem garantáltan állandó.
  • Futásidő: a Pimpl indirekció költsége mérhető egy benchmarkkal, amely sok hívást végez. A várt eredmény: a költség minimális, de nem nulla.

A mérési naplóban külön kell választani a mért értékeket a várt értékektől, és rögzíteni kell a hardver, az operációs rendszer, a fordító verzióját és az optimalizációs szintet.

25.3.11 Önellenőrző kérdések

  1. Miért kell a Pimpl osztály destruktorát a .cpp fájlban definiálni?
  2. Hogyan biztosítja a Pimpl a bináris kompatibilitást a privát adattagok változása esetén?
  3. Miért használunk C ABI-t a plugin interfészeknél?
  4. Milyen hibákat okozhat, ha a plugin függvényben kivétel dobódik és nem kapjuk el?
  5. Hogyan ellenőrzi a gazdaprogram a plugin verzióját, és miért fontos ez?

Ezek a kérdések segítenek ellenőrizni a fejezetben tárgyalt fogalmak megértését.

Rövid válaszvázlat: (1) a unique_ptr destruktorához teljes Impl kell, ez csak a .cpp-ben áll fenn; (2) a header csak egy mutatót tartalmaz, a privát tagok az Impl-ben élnek; (3) a C ABI nem függ a fordító C++ ABI-jától; (4) a kivétel kiszökése a C határon nem definiált viselkedés / std::terminate; (5) a plugin_api_version() visszatérési értékét hasonlítja az elvárthoz, mert eltérő verziójú plugin layoutja vagy szerződése inkompatibilis lehet.
