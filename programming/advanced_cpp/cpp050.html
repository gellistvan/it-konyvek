14.1 STL allokátor modell és PMR

Az STL allokátor modell és a polymorphic memory resource (PMR) a C++ memóriakezelésének két kulcsfontosságú absztrakciója. Az allokátorok lehetővé teszik, hogy a konténerek és algoritmusok ne közvetlenül a globális new-t és delete-et használják, hanem tetszőleges memóriaforrásból dolgozzanak. A PMR ezt az absztrakciót futásidőben cserélhető, type-erased erőforrásként valósítja meg, és a beágyazott rendszerektől a nagy teljesítményű szerveralkalmazásokig egységes megoldást kínál. Ebben az alfejezetben először az allokátor modell alapjait tekintjük át, majd a PMR-t és annak gyakorlati használatát mutatjuk be egy reprodukálható laborral.

14.1.1 Az STL allokátor modell

A konténerek (például a std::vector, std::list, std::map) sablonparaméterként egy allokátor típust kapnak. Az allokátor feladata a nyers memória allokálása és felszabadítása; az objektumok konstrukcióját és destruálását a konténer az allocator_traits segítségével végzi. Az allokátorokra vonatkozó követelmények (Allocator requirements; a cppreference „Named Requirement: Allocator” néven hivatkozza) már a C++98 óta léteznek; a C++11 óta elég az interfész minimális része, a többit az allocator_traits pótolja. Az allokátor egy érték típusú osztály, amely definiálja a value_type típust, valamint az allocate és deallocate tagfüggvényeket. Az std::allocator<T> az alapértelmezett allokátor; ez a ::operator new és ::operator delete függvényekre épül.

Az allokátor lehet állapot nélküli (stateless) vagy állapottal rendelkező (stateful). Egy stateless allokátor például csak naplózást végez, mint az alábbi logging_allocator (fordító: GCC, -std=c++17 vagy újabb; a g++ 15.2 -std=c++17 és -std=c++20 módban -Wall -Wextra -Wpedantic mellett figyelmeztetés nélkül lefordította és std::vector-ral futtatta):

#include <cstddef>
#include <cstdio>
#include <new>
#include <type_traits>

template <typename T>
class logging_allocator {
public:
    using value_type = T;

    logging_allocator() noexcept = default;
    template <typename U>
    logging_allocator(const logging_allocator<U>&) noexcept {}

    T* allocate(std::size_t n) {
        if (n > static_cast<std::size_t>(-1) / sizeof(T))
            throw std::bad_array_new_length(); // n * sizeof(T) túlcsordulása
        std::printf("allocate %zu * %zu bytes\n", n, sizeof(T));
        // az igazítást is átadjuk: a túligazított T-t is helyesen kezeli
        return static_cast<T*>(::operator new(n * sizeof(T), std::align_val_t{alignof(T)}));
    }

    void deallocate(T* p, std::size_t n) noexcept {
        // printf: nem dob kivételt (az ostream exception maszkja mellett a
        // noexcept deallocate-ben std::terminate-ot okozhatna)
        std::printf("deallocate %zu * %zu bytes\n", n, sizeof(T));
        ::operator delete(p, std::align_val_t{alignof(T)});
    }

    template <typename U>
    bool operator==(const logging_allocator<U>&) const noexcept { return true; }
    template <typename U>
    bool operator!=(const logging_allocator<U>&) const noexcept { return false; }
};

Ez az osztály C++17-ben megfelel az allokátor követelményeknek, mert az std::allocator_traits<logging_allocator<T>> automatikusan biztosítja a hiányzó típusokat (például pointer, size_type) és a rebind műveletet. Az allocator_traits-nek nincs saját operator==-ja. A C++20-tól az operator!= megadása elhagyható, mert az a != b kifejezést a fordító !(a == b)-ként írja át (rewritten candidate); C++17-ben a != megadása a követelmények része.

A stateful allokátorok jellemzően egy memóriaterületre, például egy poolra mutatnak. Az alábbi arena_allocator egy egyszerű arena mutatót tárol:

#include <cstddef>
#include <type_traits>

class arena {
public:
    void* allocate(std::size_t bytes, std::size_t alignment);
    void deallocate(void* p, std::size_t bytes, std::size_t alignment);
};

template <typename T>
class arena_allocator {
public:
    using value_type = T;
    using propagate_on_container_move_assignment = std::true_type;

    // Előfeltétel: a nem null, élő arenára mutat, amely túléli az allokátort
    // és minden belőle allokált objektumot.
    explicit arena_allocator(arena* a) noexcept : arena_(a) {}

    template <typename U>
    arena_allocator(const arena_allocator<U>& other) noexcept : arena_(other.arena_) {}

    T* allocate(std::size_t n) {
        return static_cast<T*>(arena_->allocate(n * sizeof(T), alignof(T)));
    }

    void deallocate(T* p, std::size_t n) noexcept {
        arena_->deallocate(p, n * sizeof(T), alignof(T));
    }

    template <typename U>
    bool operator==(const arena_allocator<U>& other) const noexcept {
        return arena_ == other.arena_;
    }
    // C++20-tól a != ebből képződik; C++17 alatt külön operator!= szükséges.

private:
    arena* arena_;
    template <typename> friend class arena_allocator;
};

Itt a propagate_on_container_move_assignment típusdefiníció std::true_type, ami azt jelzi, hogy a konténer move assignment során az allokátort is át lehet venni a forrásból. Ha ezt nem definiálnánk, az allocator_traits default std::false_type-ot adna, ami eltérő viselkedést eredményezne.

14.1.2 Az allocator_traits és a konténer-műveletek

A konténerek nem közvetlenül hívják az allokátor tagfüggvényeit, hanem az std::allocator_traits<Alloc> sablonon keresztül. Ez a traits osztály biztosítja a szükséges típusokat és függvényeket, és lehetővé teszi az allokátor interfész minimálisra csökkentését. Az allocator_traits többek között a következő tagtípusokat és -függvényeket definiálja:

  • rebind_alloc<U>: az allokátor újra-kötése egy másik értéktípusra (a rebind_traits<U> a megfelelő allocator_traits-t adja).
  • pointer, const_pointer, size_type, difference_type.
  • allocate, deallocate, construct, destroy, max_size.
  • select_on_container_copy_construction.
  • propagate_on_container_copy_assignment, propagate_on_container_move_assignment, propagate_on_container_swap.
  • is_always_equal.

A propagate_on_container_move_assignment különösen fontos a teljesítmény szempontjából. Amikor egy konténert move assignment segítségével áthelyezünk, a cél konténernek át kell vennie a forrás memóriáját. Ha az allokátor propagate_on_container_move_assignment értéke std::true_type, akkor a cél allokátora is megkapja a forrás allokátorát, és a memória közvetlenül átvehető. A puffer átvétele ilyenkor O(1) lehet, de a cél korábbi elemeit előbb meg kell semmisíteni, így a teljes move assignment költsége a cél korábbi méretétől is függ. Ha az érték std::false_type, az átvétel csak akkor lehet O(1) jellegű, ha a forrás és a cél allokátorai egyenlőek (operator==); egyébként a forrás elemeit a cél allokátorával kell újraallokálni és elemenként áthelyezni, ami O(n) műveletigényt, allokációt és kivételt okozhat.

Az is_always_equal azt jelzi, hogy az allokátorok mindig egyenlőek-e. Ha ez std::true_type, akkor a konténerek közötti memóriaátvitel mindig megengedett, függetlenül az egyenlőségvizsgálattól. Az std::allocator esetében ez igaz, mert nincs állapota. A PMR polymorphic_allocator esetében azonban az is_always_equal std::false_type, mert az egyenlőség a resource-októl függ: két polymorphic_allocator pontosan akkor egyenlő, ha *a.resource() == *b.resource(), azaz a resource-ok is_equal() függvénye szerint egyenlők (logikailag egyenlő, de különböző objektumok egyenlők lehetnek; az egyenlőség szerződése, hogy az egyikkel allokált memória a másikkal felszabadítható). Különböző típusú vagy különböző állapotú resource-ok (például két külön monotonic_buffer_resource) viszont nem egyenlők.

A select_on_container_copy_construction a másoló konstruktor által használt allokátor kiválasztására szolgál. Amikor egy konténert lemásolunk, az új konténer allokátora nem feltétlenül a forrás allokátorának másolata; ehelyett a select_on_container_copy_construction eredményét használják. Ez lehetővé teszi, hogy a másolat más memóriaforrást használjon. Például a std::pmr::polymorphic_allocator::select_on_container_copy_construction() egy alapértelmezett, a get_default_resource()-ot használó allokátort ad vissza (maga a polymorphic_allocator másoló konstruktora viszont a forrás resource-át másolja); a konténer másoló konstruktora az előbbit használja. Ez fontos: ha egy PMR vektort egy monotonic buffer resource-szal le akarunk másolni, a másolat már a globális default resource-t fogja használni, nem az eredeti buffert. Ennek elkerülésére explicit módon kell megadni az allokátort.

14.1.3 Polymorphic memory resource (PMR)

A C++17-ben bevezetett <memory_resource> fejléc a memóriaforrások egységes, futásidőben cserélhető absztrakcióját adja. A központi osztály az std::pmr::memory_resource, amely egy absztrakt alaposztály. A publikus allocate, deallocate és is_equal függvények a virtuális do_allocate, do_deallocate és do_is_equal privát függvényeket hívják. A do_allocate visszatérési értéke legalább bytes méretű, alignment igazítású nyers memória; do_deallocate felszabadítja a korábban allokált blokkot (a bytes és alignment értékének meg kell egyeznie az allokáláskor használttal). A do_is_equal két resource objektum logikai egyenlőségét vizsgálja.

Az std::pmr::polymorphic_allocator<T> egy allokátor, amely egy std::pmr::memory_resource*-ot tárol, így a memóriaforrás futásidőben cserélhető. Ez a type erasure egyik példája: a konténer típusa nem függ a konkrét resource típusától, csak a memory_resource interfésztől. A PMR konténerek, például a std::pmr::vector<T>, nem mások, mint std::vector<T, std::pmr::polymorphic_allocator<T>> aliasok.

A leggyakrabban használt konkrét resource a std::pmr::monotonic_buffer_resource. Ez egy növekvő, nem felszabadító (non-deallocating) arena, amely ideiglenes allokációk gyors kiszolgálására szolgál. A memóriát egy vagy több pufferként foglalja le az upstream resource-tól; az egyes elemek felszabadítása nem adja vissza a memóriát, csak a resource megsemmisülésekor szabadul fel minden. Ez rendkívül hatékony, ha sok kis allokációt egy jól körülhatárolt szakaszon belül végzünk, például egy függvény vagy egy keretrendszerbeli task futása alatt.

A monotonic_buffer_resource konstruktorai lehetővé teszik kezdeti puffer megadását, upstream resource megadását, vagy mindkettőt. Ha kezdeti puffert adunk, az első allokációk abból szolgálhatók ki heap allokáció nélkül. Ha a puffer elfogy, a resource az upstream-től (alapértelmezetten a get_default_resource()) kér egy nagyobb blokkot, és a régi puffert megtartja. A release() metódus felszabadítja az összes, az upstream-től kapott puffert; ezután a resource újra használható, de a korábban kiosztott mutatók érvénytelenné válnak.

A PMR használatának alapmintája az alábbi:

#include <memory_resource>
#include <vector>
#include <array>
#include <cstddef>

void pmr_example() {
    std::array<std::byte, 1024> buffer;
    std::pmr::monotonic_buffer_resource resource(buffer.data(), buffer.size(),
                                                 std::pmr::null_memory_resource());
    std::pmr::vector<int> numbers{&resource};
    numbers.reserve(100); // 400 bájt, egyetlen blokk: nincs növekedési sorozat
    for (int i = 0; i < 100; ++i) {
        numbers.push_back(i);
    }
    // A vektor a stack puffert használja; ha az nem elég, a null_memory_resource
    // std::bad_alloc-ot dob, így a heapmentesség szerződés, nem remény.
}

Az alapértelmezett upstream (get_default_resource()) esetén a puffer elfogyása után a monotonic_buffer_resource újabb blokkot kér az upstream-től; ez nem feltétlenül heap (a default resource lecserélhető). A 100 elem és az 1024 bájt nem általános heapmentességi határ: a növekedési sorozat és az igazítás is helyet fogyaszt, és a régi blokkokat a resource megtartja, ezért az itt látható reserve(100), a méretezett puffer és a null_memory_resource upstream együtt ad kemény szerződést.

14.1.4 Tipikus hibák és helyes gyakorlat

A PMR és az allokátor modell használata során a leggyakoribb buktatók a következők:

  1. A resource élettartama rövidebb, mint a konténeré. Ha a monotonic_buffer_resource a konténer előtt semmisül meg, a konténerben lévő mutatók érvénytelenné válnak, és a destruktor nem definiált viselkedést okoz. A resource-nak legalább addig élnie kell, amíg a belőle allokált objektumok élnek.

  2. A monotonic_buffer_resource nem dealokál. Az elemek törlése vagy a konténer clear() hívása nem adja vissza a memóriát a resource-nak. Ha egy hosszú életű alkalmazásban nagy adatokat ideiglenesen tárolunk, a memória felhalmozódik. Ilyenkor a resource-ot rövid életű scope-ba kell helyezni, vagy más resource-t (pl. pool resource-ot) kell választani.

  3. A select_on_container_copy_construction figyelmen kívül hagyása. Ha egy PMR konténert le akarunk másolni, az alapértelmezett viselkedés a default resource használata. Ez gyakran nem kívánt, mert a másolat a globális heap-re kerül, nem a kívánt memóriaterületre. Ilyenkor explicit allokátort kell átadni a másoló konstruktornak.

  4. A propagate_on_container_move_assignment figyelmen kívül hagyása. Ha egy allokátor propagate_on_container_move_assignment értéke false, és az allokátorok nem egyenlőek, a move assignment elemenkénti, O(n) művelet lesz, és allokálhat vagy kivételt dobhat. A PMR polymorphic_allocator egyik propagate_on_* tulajdonsága sem igaz (false_type; a szabványban mem.poly.allocator.class), tehát két, különböző (nem egyenlő) resource-t használó PMR konténer közötti move assignment elemenként mozgat, és nem veszi át az allokátort. Ez a PMR egyik legfontosabb buktatója: a PMR konténerek mozgatása csak azonos (egyenlő) resource esetén olcsó. Hasonlóan, a másolás és a swap sem terjeszti automatikusan az allokátort.

  5. Az allokátor egyenlőségének helytelen implementálása. Ha két allokátor ugyanarra a memóriaterületre mutat, akkor egyenlőnek kell lenniük; ha nem, a konténerek közötti kommunikáció hibás lehet. A PMR resource-oknál az egyenlőséget a felüldefiniált do_is_equal határozza meg (az operator== erre épül: &a == &b || a.is_equal(b)); csak akkor adjon true-t, ha az egyik resource-szal allokált memória a másikkal felszabadítható.

A PMR propagációs szabályai egy helyen (polymorphic_allocator):

Művelet Viselkedés
másoló konstruktor select_on_container_copy_construction: alapértelmezett polymorphic_allocator (get_default_resource()), nem a forrás resource-a
másoló értékadás propagate_on_container_copy_assignment = false_type: a cél megtartja a saját resource-át, az elemek másolódnak
move assignment propagate_on_container_move_assignment = false_type: egyenlő resource-ok esetén a puffer átvehető, különben elemenkénti mozgatás (O(n), allokálhat/dobhat)
swap propagate_on_container_swap = false_type: egyenlőtlen resource-ok esetén a swap viselkedése nem definiált, ezért azonos resource-ra kell támaszkodni

14.1.5 Labor: PMR-alapú konténer tervezése

A labor célja egy PMR-alapú konténer memóriaallokációs viselkedésének mérése és összehasonlítása a heap-alapú megoldással. A kód egy counting_memory_resource osztályt definiál, amely továbbítja az allokációkat egy upstream resource-hoz, de közben megszámolja a hívásokat és a lefoglalt bájtokat. Ezt a resource-ot használjuk mind a hagyományos heap-úthoz, mind a monotonic_buffer_resource upstream-jeként.

A mérés során a std::pmr::vector<int>-et egyszer közvetlenül a counting_memory_resource-szal, egyszer pedig a monotonic_buffer_resource-szal hozzuk létre, és mindkét esetben feltöltjük N elemmel. Az allokációk száma és a lefoglalt bájtok mennyisége a két esetben eltérő lesz: a heap-alapú megoldás minden kapacitásbővítésnél új heap blokkot kér, míg a monotonic buffer resource az upstream-től csak néhány nagyobb puffert allokál, és a kisebb bővítéseket a meglévő blokkokból szolgálja ki; a legnagyobb vektorblokkok saját upstream blokkot igényelnek (a mérési táblázatban a monotonic változat 8 upstream kérést mutat; a pontos számot a saját mérésed adja).

A kód C++20-as; az ellenőrző fordítás g++ 15.2.0-val és GCC 13.3-mal is ugyanazt a számlálóértéket adta. A labor reprodukálhatósága érdekében a buildparancs, a teszt és a mérési napló rögzítve van.

14.1.6 A labor kódja

#include <cstddef>
#include <iostream>
#include <memory_resource>
#include <vector>
#include <cassert>
#include <iomanip>

// Olyan memory_resource, amely számolja az upstream felé továbbított
// allokációkat és a lefoglalt bájtokat.
class counting_memory_resource : public std::pmr::memory_resource {
public:
    explicit counting_memory_resource(std::pmr::memory_resource* upstream = std::pmr::get_default_resource())
        : upstream_(upstream), allocations_(0), bytes_allocated_(0) {}

    std::size_t allocations() const noexcept { return allocations_; }
    std::size_t bytes_allocated() const noexcept { return bytes_allocated_; }
    void reset() noexcept { allocations_ = 0; bytes_allocated_ = 0; }

private:
    std::pmr::memory_resource* upstream_;
    std::size_t allocations_;
    std::size_t bytes_allocated_;

    void* do_allocate(std::size_t bytes, std::size_t alignment) override {
        ++allocations_;
        bytes_allocated_ += bytes;
        return upstream_->allocate(bytes, alignment);
    }

    void do_deallocate(void* p, std::size_t bytes, std::size_t alignment) override {
        upstream_->deallocate(p, bytes, alignment);
    }

    bool do_is_equal(const std::pmr::memory_resource& other) const noexcept override {
        return this == &other;
    }
};

// Lefuttatja a mérést: feltölt egy std::pmr::vector<int>-et N elemmel,
// majd kiírja az upstream allokációk számát és a lefoglalt bájtokat.
void run_case(std::pmr::memory_resource* resource,
              counting_memory_resource* counter,
              std::size_t N,
              const char* label) {
    counter->reset();
    {
        std::pmr::vector<int> vec(resource);
        for (std::size_t i = 0; i < N; ++i) {
            vec.push_back(static_cast<int>(i));
        }
        // Alapvető konzisztenciaellenőrzés
        assert(vec.size() == N);
        for (std::size_t i = 0; i < N; ++i) {
            assert(vec[i] == static_cast<int>(i));
        }
    }
    std::cout << label << ": allocations=" << counter->allocations()
              << ", bytes_allocated=" << counter->bytes_allocated() << "\n";
}

int main() {
    constexpr std::size_t N = 10000;

    counting_memory_resource heap_counter(std::pmr::new_delete_resource());
    std::pmr::monotonic_buffer_resource monotonic(&heap_counter);

    std::cout << "Heap-backed PMR vector:\n";
    run_case(&heap_counter, &heap_counter, N, "heap");

    std::cout << "Monotonic buffer PMR vector:\n";
    run_case(&monotonic, &heap_counter, N, "monotonic");

    return 0;
}

14.1.7 Build és teszt

A buildhez a következő parancsot használjuk (GCC 13 vagy újabb, Linux x86-64; az alábbi mért értékek g++ 15.2.0-ból származnak):

g++ -std=c++20 -O2 -Wall -Wextra -Werror -pedantic -o pmr_lab pmr_lab.cpp

A teszt futtatása:

./pmr_lab

A program lefut, az assert-ek ellenőrzik a vektorok tartalmát, és a kimenet tartalmazza a mérési eredményeket. A teszt sikeres, ha a kimenet megjelenik, és a visszatérési kód 0.

14.1.8 Mérési napló

A mérést a fenti kóddal, g++ 15.2.0-val, -std=c++20 -O2, Linux x86-64 környezetben végeztük el (GCC 13.3-mal ugyanezeket a számlálóértékeket kapjuk). A counting_memory_resource az upstream std::pmr::new_delete_resource() felé továbbít, így a számolt allokációk tényleges heap blokkokat jelentenek; a számlálók determinisztikusak, ezért átlagolásra nincs szükség. A számláló a hívásokat és a kért bájtokat összegzi (nem a tényleges kapacitást, és a sikertelen kéréseket is előre számolja); az összes, az élő és a csúcs bájt különböző mennyiség – itt az összes kért bájt szerepel.

A mért értékek a std::pmr::vector és a monotonic_buffer_resource implementációjától függenek; más standard könyvtárral eltérhetnek. A várt érték a libstdc++ kapacitás-duplázásából levezetett modell, nem szabványos garancia.

A tényleges eredmény árnyalja a képet: ebben az elrendezésben (a kezdeti puffer nélküli monotonic_buffer_resource) az upstream allokációk száma 15-ről 8-ra csökkent, de a lefoglalt bájtok száma kissé nőtt, mert a resource a korábbi blokkokat sem adja vissza. A monotonic resource valódi előnye nem az, hogy „drasztikusan” kevesebb bájtot foglal, hanem hogy a konténer elemei és a régi vektorblokkok nem igényelnek egyedi felszabadítást, a memória egyetlen lépésben szabadul fel, és megfelelően méretezett kezdeti pufferrel (például a pmr_example stack-tömbje) a heap-allokáció akár teljesen elmaradhat. A futásidő mérését itt nem végeztük el.

14.1.9 Önellenőrző kérdés

  1. Mi a különbség az std::allocator és az std::pmr::polymorphic_allocator között? Melyik esetben előnyös a PMR használata?
  2. Hogyan befolyásolja a propagate_on_container_move_assignment a konténer move assignment komplexitását? Mi történik, ha az értéke false és az allokátorok nem egyenlőek?
  3. Miért kell figyelni a select_on_container_copy_construction viselkedésére PMR konténerek másolásakor? Adjon példát arra, amikor ez nem várt eredményhez vezet.

A válaszok megtalálhatók a fenti szövegben; az olvasó önellenőrzésként írja le őket saját szavaival, és tesztelje a labor kódját más N értékekkel is.

Válaszvázlat: (1) Az std::allocator típusparaméterként a konténer típusának része (vector<T, A>); a polymorphic_allocator egyetlen típus, a memory_resource* futásidőben cserélhető, így a különböző erőforrást használó konténerek típusa azonos. Ára egy mutató és egy indirekt hívás; előnyös, ha az allokációs stratégiát (pl. aréna) típusváltoztatás nélkül kell cserélni. (2) Ha a POCMA true, az allokátor a move-értékadáskor átmozog, így a művelet O(1) mutatócsere; ha false és az allokátorok nem egyenlők, az elemeket egyenként kell a célallokátorral mozgatni (O(n), és dobhat). (3) A select_on_container_copy_construction mondja meg, milyen allokátorral készül a másolat; a polymorphic_allocator esetében ez az alapértelmezett erőforrás (get_default_resource()), nem az eredeti aréna, ezért a másolat váratlanul a heapre kerülhet.
