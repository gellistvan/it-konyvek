5.2 Modules és header units

Ez az alfejezet a C++20 modulrendszert mutatja be a fejléc-alapú fordítási modell problémáin keresztül: a modul interfész- és implementációs egységeit, a partíciókat, a header unitokat és a C++23 import std; szabványkönyvtár-modult, majd a build rendszer és a parancssori fordítók kapcsolóit egy reprodukálható laborral. A példák alapfeltevése: C++20, GCC 14 vagy újabb (a -fmodules-ts kapcsolóval), illetve Clang 17+ és MSVC 17.4+; a pontos kapcsolók verziófüggők.

5.2.1 A modulok mint a header-problémák megoldása

A hagyományos C++ fordítási modell egyik legnagyobb gyakorlati fájdalma a szövegszerű include. Amikor egy fordítási egységben #include <vector> szerepel, a preprocesszor beilleszti a teljes fejléc forrásszövegét, majd a fordító elölről kezdi az elemzést. Ez nem csupán lassú, hanem számos nyelvi és eszközláncproblémát is okoz:

  • Ismételt fordítás: ugyanazt a fejlécet minden fordítási egységben újra és újra elemezni kell, ami a nagy rendszereknél a fordítási idő jelentős részét teszi ki.
  • ODR-kockázat: a fejlécekben definiált inline függvények, sablonok és konstansok minden fordítási egységben új példányt hoznak létre. A linker ugyan összeolvasztja őket, de a szabály megsértése (pl. eltérő makró-definíciók miatt eltérő kód) undefined behaviorhez vezethet.
  • Makrószivárgás: a fejlécben definiált makrók a befoglaló fordítási egységben is láthatók maradnak, így a #define max(a,b) tönkreteheti a std::max hívását, vagy éppen fordítva. A fejlécek sorrendje befolyásolhatja a fordítást, ami karbantarthatatlanná teszi a kódot.
  • Rejtett függőségek: egy fejléc használhat egy másik fejlécet anélkül, hogy azt a fogyasztónak tudnia kellene. Ez a „működik, mert véletlenül include-oltad” jelenséghez vezet, ami a build izolációját gyengíti.
  • Körkörös include: két fejléc kölcsönösen hivatkozik egymásra, amit include guardokkal és forward deklarációkkal lehet csak feloldani, de ez törékeny mintákhoz vezet.

A C++20-ban bevezetett modulok ezeket a problémákat hivatottak kezelni. A modul nem szövegszerű beillesztés, hanem a fordítási egységek egy új szervezési formája, amelyben az interfész és az implementáció szétválik, a függőségek explicitté válnak, a named module-okból a makrók nem szivárognak át, és a fordító a modul interfészt egyszer lefordítja, majd annak lefordított reprezentációját (ún. Binary Module Interface, BMI) használja a többi fordítási egységben. Ez a megközelítés csökkenti a fordítási időt, javítja az izolációt és kiküszöböli a makró- és include-sorrendből adódó hibák nagy részét.

Fontos leszögezni: a modulok nem a névtereket helyettesítik, hanem a fordítási egységek szervezésének új rétegét adják. Egy modul exportálhat típusokat, függvényeket, sablonokat, sőt akár egész névtereket is, de a fogyasztó továbbra is a hagyományos névtér-szabályok szerint éri el az entitásokat. A modul neve azonosító, nem feltétlenül kapcsolódik fájlnévhez vagy névtérhez.

5.2.2 Module interface és implementation unit

A modulok alapvető építőkövei a modul egységek (module units). Ezek közül a legfontosabb a module interface unit, amelyet az export module deklaráció vezet be. Ez az egység deklarálja a modul nevét, és meghatározza, hogy mely entitások láthatók a modult importáló fordítási egységek számára.

A legegyszerűbb modul interfész így néz ki:

// math_utils.cppm – module interface unit
export module math_utils;

export namespace math_utils {

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b);

} // namespace math_utils

Itt az export module math_utils; deklarálja a modult. Fontos: a modul neve és a névtér neve két független dolog; a export module math_utils; önmagában nem hoz létre math_utils névteret. A példában ezért az export namespace math_utils { ... } blokk teszi a függvényeket a math_utils névtérbe, így a fogyasztó math_utils::add(2, 3) formában érheti el őket. Az export kulcsszó a névtérre vonatkozik: a benne deklarált entitások lesznek elérhetők az importálók számára. A multiply függvénynek csak a deklarációja van itt, a definíciója külön egységben, az implementation unitben található.

Az implementation unit a következőképpen néz ki:

// math_utils.cpp – module implementation unit
module math_utils;

namespace math_utils {

int multiply(int a, int b) {
    return a * b;
}

} // namespace math_utils

Ennek az egységnek a deklarációja nem tartalmazza az export kulcsszót, tehát nem interfész, hanem a modul belső implementációja. Az implementation unit automatikusan hozzáfér minden olyan entitáshoz, amelyet a modul interfésze deklarál vagy definiál, de az itt definiált entitások nem láthatók kívülről, hacsak az interfészben nem lettek exportálva. A multiply definíciója itt kap helyet, és az interfészben lévő deklarációval párosul.

A modul interfész és implementation unit közötti kapcsolat a következő:

  • Az interfészben lévő deklarációk (mint a multiply deklaráció) a modul összes egységében láthatók, tehát az implementation unit definiálhatja őket.
  • Az implementation unitben definiált entitások nem exportálódnak automatikusan; csak az interfészben export-tal jelölt entitások válnak a modul külső API-jává.
  • Ha egy függvényt az interfészben export nélkül deklarálunk, az a modulon belül használható, de kívülről nem érhető el. Ez lehetővé teszi belső segédfüggvények elrejtését.

A gyakorlatban a modul interfész gyakran tartalmaz definíciókat (ahogy az add), sablonokat és deklarációkat, míg a nagyobb implementációk az implementation unitbe kerülnek. Figyelem: egy named modul interfészében definiált függvény nem lesz automatikusan inline; ha a definíciót több egységben is láthatóvá akarjuk tenni inline-kezeléssel, az inline specifiert ki kell írni (az add ezért nem inline, definíciója pusztán az interfész egységben áll). Az, hogy egy implementation unit a saját modul interfészét implicit módon importálja, csak a nem partíció implementation unitra igaz (module math_utils;); a partíciók láthatósága explicit importoktól függ. Ez a szétválasztás hasonló a header/source felosztáshoz, de a modul interfész nem szövegszerűen kerül beillesztésre, így a header-problémák nagy része megszűnik.

5.2.3 Az export és import szabályai

A export kulcsszó csak a modul interfész egységben jelenhet meg, és csak a modul deklaráció után. Többféle szintaxisa van:

  • Egyedi entitás exportálása: export int f();
  • Export blokk: export { int g(); double h(); } – a blokkban lévő összes deklaráció exportálva lesz.
  • Névtér exportálása: export namespace utils { int helper(); } – a névtérben lévő deklarációk exportálva lesznek, és a fogyasztó utils::helper() formában éri el őket. A névtér neve itt nem külön entitásként, hanem a benne exportált nevek minősítőjeként jelenik meg; a modul neve ettől független.

Az import deklaráció használatával egy fordítási egység elérhetővé teszi egy másik modul interfészét:

// main.cpp
import math_utils;
#include <iostream>

int main() {
    std::cout << math_utils::add(2, 3) << '\n';
}

Fontos megérteni: az import math_utils; nem szövegszerű beillesztés, hanem a modul által exportált entitások név láthatóságát biztosítja a fordítási egységben. A math_utils::add hívás itt a modul add függvényét éri el. A #include <iostream>-ot itt hagyományos fejlécként használjuk, de később látni fogjuk, hogy header unitként is importálható.

Az export és import kombinálásával újraexportálás is lehetséges:

export module geometry;

export import math_utils; // math_utils összes exportált entitása a geometria modul része lesz

Ezzel egy modul aggregálhat más modulok API-ját, ami hasznos nagy rendszerekben.

5.2.4 Module partíciók

A nagyobb modulokat fel lehet osztani partíciókra. A partíció a modul egy belső egysége, amelynek neve a modul neve után kettősponttal következik. A partíciók lehetővé teszik az interfész és az implementáció további szervezését anélkül, hogy a modul neve sérülne.

Példa egy modul partícióra, amely az interfész egy részét tartalmazza:

// geometry_core.cppm – interfész partíció
export module geometry:core;

export struct Point {
    double x, y;
};

export double distance(const Point& a, const Point& b);

A partíció deklarációja export module geometry:core;. A partíció nevét a modul neve és a kettőspont után kell megadni. Az export itt azt jelzi, hogy ez a partíció interfész-partíció, és az általa exportált entitások a modul többi része számára láthatók lesznek.

A modul fő interfésze ezt a partíciót importálja:

// geometry.cppm – fő interfész
export module geometry;

export import :core; // a :core partíció exportált entitásai a modul külső API-jává válnak

A export import :core; szintaxis azt jelenti, hogy a geometry:core partíció által exportált entitások a geometry modul részeként exportálódnak. A fogyasztó számára csak a geometry modulnév látszik, a partíciók belső szervezési részletek.

Az implementation partíció hasonló, de nem tartalmazza az export kulcsszót:

// geometry_impl.cpp – implementation partíció
module;                // globális modulfragmentum kezdete
#include <cmath>       // a hagyományos include ide tartozik, a modul deklarációja ELŐTT
module geometry:impl;  // innentől a modul hatóköre (purview)

import :core; // hozzáfér a core partíció interfészéhez (az import a purview többi deklarációja előtt áll)

double distance(const Point& a, const Point& b) {
    double dx = a.x - b.x;
    double dy = a.y - b.y;
    return std::sqrt(dx*dx + dy*dy);
}

Az implementation partíció module geometry:impl; deklarációval kezdődik, és nem exportál. Két szabály: (1) a szabványos fejlécet a globális modulfragmentbe (module; és a modul deklaráció közé) kell tenni, a modul deklaráció után nem szabad #include-olni; (2) az import deklarációknak a modul deklaráció után közvetlenül, minden más deklaráció előtt kell állniuk. A distance definíciójának használatához a fogyasztónak nem kell importálnia ezt a partíciót: a definíció linkeléskor kapcsolódik a deklarációhoz. Ha a partíciót mégis a modul belső részeként akarjuk használni, a fő interfésznek explicit import :impl; (nem újraexportálva) kell, hogy legyen, a teljes importgráf pedig körmentes: geometry → :core, és :impl → :core. Az egyszerűbb, szokásos forma a nem partíció implementation unit (module geometry;), ugyancsak globális modulfragmenttel a <cmath>-hoz. A partíciók segítségével elkerülhető, hogy egyetlen hatalmas interfész fájl legyen, miközben a modul egységes marad.

5.2.5 Header units

A modulok bevezetése mellett a C++20 támogatja a header unitok fogalmát is. Egy hagyományos header fájl (#include-landó) importálható modulként, ha import "header.h"; vagy import <header>; szintaxist használunk. Ebben az esetben a fejlécet a fordító elkülönített fordítási egységként kezeli, és a belőle exportált entitások (tipikusan az összes deklaráció, inline definíció és sablon) elérhetővé válnak az importálóban.

Ez fontos különbség a hagyományos #include-hoz képest:

  • Makrók: a header unit (import "header.h";) exportálja a fejlécben definiált preprocesszor-makrókat, éppen ezért alkalmas a meglévő, makrókat használó fejlécek fokozatos bevezetésére. Ezzel szemben a named module (export module M;) nem exportál makrókat: a modulban definiált makrók nem válnak láthatóvá az importálóban. Ez a különbség magyarázza, miért nem szivárognak át a makrók a modulokból, miközben a header unitok továbbra is biztosítják a régi fejlécek makróinak elérhetőségét.
  • Include guardok: a header unit esetén a fejlécet a fordító egyszer elemzi, és a belső include guardok nem befolyásolják a többi fordítási egységet. Nincs szükség arra, hogy a fogyasztó include guardokat kezeljen.
  • Függőségek és makrók iránya: a header unit minden deklarációja implicit módon importálható; ez a belőle szövegesen #include-olt további fejlécek deklarációira is igaz, tehát a header unit nem szünteti meg a tranzitív láthatóságot, és a rejtett függőségeket sem csökkenti. A makrók iránya egyirányú: a header unit makrói az importáló egységben megjelennek, de az importáló az import előtt definiált makrói általában nem konfigurálják az előre lefordított header unitot úgy, mint egy szöveges #include-ot.

A header unit importálása a következőképpen néz ki:

// main.cpp
import <iostream>;   // standard fejléc header unitként
import "legacy_config.h"; // saját header unitként
#include "other_header.h" // hagyományos include továbbra is működik

int main() {
    std::cout << "Hello\n";
}

Fontos megjegyezni, hogy a standard fejlécek header unitként való importálása (import <iostream>;) a C++20 része (az „importálható fejlécek”), a támogatottsága és a build-integrációja azonban fordítónként eltér. Ettől különálló újdonság a C++23 szabványos könyvtármodulja: az import std; a teljes std névteret hozza (a <print> stb. is benne van), az import std.compat; ezen felül a C-könyvtár globális névtérbeli neveit is. Támogatása a build rendszertől és a fordítótól függ (pl. GCC 15, Clang 18–19+ és MSVC 17.5+ környezetben, a szabványos könyvtár modul-forrásának előzetes lefordításával, CMake-nél CXX_MODULE_STD); ezt a laborban nem futtattuk, a használatát a telepített toolchain dokumentációja szerint ellenőrizzük. A import <iostream>; hatására a std::cout és a standard könyvtár többi eleme elérhetővé válik, anélkül hogy a teljes fejléc szövegét minden fordítási egységben újra kéne elemezni. A pontos támogatottság azonban a toolchain verziójától függ, ezért a laborban ezt ellenőrizni kell.

5.2.6 Build rendszer és fordítási folyamat

A modulok bevezetése alapvetően megváltoztatja a build folyamatot. A hagyományos make/ninja alapú rendszerekben a fejlécek függőségi gráfja implicit, míg a moduloknál a modulok közötti importok explicit függőségi éleket képeznek, amelyeket a build rendszernek fel kell oldania.

A fordítási folyamat a következő lépésekből áll:

  1. Module interface unit fordítása: az interfész egységet le kell fordítani, és a fordító egy Binary Module Interface (BMI) fájlt állít elő. Ez a fájl a modul exportált entitásainak lefordított reprezentációja, amelyet a fogyasztó fordítási egységek használnak.
  2. Module implementation unit fordítása: az implementation unitet ugyanúgy le kell fordítani, de neki szüksége van a saját modul interfészének BMI-jére.
  3. Fogyasztó fordítási egységek fordítása: a import modul; deklarációt tartalmazó egységeknek szükségük van a modul BMI-jére.
  4. Header unitok fordítása: a header unitok is BMI-t vagy hasonló lefordított reprezentációt igényelnek.

Az alábbi ábra a fejezet laborjának kézi GCC-sorozatán mutatja, mely fájlból mely köztes termék keletkezik, és melyik fordítás melyik BMI-re vár; a (b) rész a partíciós példa körmentes importgráfja.

A build rendszernek tehát ismernie kell a modulok közötti függőségeket, és a megfelelő sorrendben kell lefuttatnia a fordítási parancsokat. Ezt a feladatot a modern CMake (3.28+) a FILE_SET CXX_MODULES konstrukcióval támogatja, de csak Ninja (1.11+) vagy Visual Studio generátorral, és GCC esetén csak GCC 14-től (a P1689 függőségszkennelés miatt); GCC 13.3-mal a CMake natív modulszkennelése nem működik. A CMake a header unitokat nem kezeli: a CXX_MODULES file set kizárólag named module interfész egységeket vár, header unitot nem.

Egy lehetséges CMake konfiguráció:

cmake_minimum_required(VERSION 3.28)
project(modules_lab CXX)

# Modul könyvtár létrehozása
add_library(math_utils)
target_sources(math_utils
    PUBLIC FILE_SET CXX_MODULES FILES math_utils.cppm
    PRIVATE math_utils.cpp
)
target_compile_features(math_utils PUBLIC cxx_std_20)

# Fogyasztó alkalmazás
add_executable(test_app main.cpp)
target_link_libraries(test_app PRIVATE math_utils)
target_compile_features(test_app PRIVATE cxx_std_20)

# Header unit: a CMake nem támogatja (a CXX_MODULES file set nem header unitra való),
# ezért a CMake-változatban a legacy_config.h hagyományos #include marad.

A FILE_SET CXX_MODULES a CMake 3.28-tól kezdve kezeli a modul interfész fájlokat. A .cppm kiterjesztés nem kötelező, de gyakori; a CMake a fájl tartalma alapján azonosítja a modul interfészt. A header unit előállítása és importálása külön, kézi fordítói lépés (lásd lent).

A parancssori fordítás esetén a GCC, Clang és MSVC különböző kapcsolókat igényel:

A három fordítóhoz egy-egy teljes sorozat (BMI → implementation → fogyasztó → linkelés) a math_utils modulra. A parancsok a dokumentációk alapján készültek, a könyv írásakor nem futtattuk őket minden fordítón; a pontos kapcsolókat a használt verzió dokumentációja szerint ellenőrizzük.

  • GCC 14+ (-fmodules-ts; a .cppm kiterjesztést a -x c++ jelöli C++ forrásnak). A BMI-t a GCC nem az include útvonalon keresi: a gcm.cache/ könyvtárba írja a fordítás munkakönyvtárához képest, és onnan olvassa a modulmapper szabályai szerint (a -fmodule-mapper= kapcsolóval módosítható):

    g++ -std=c++20 -fmodules-ts -x c++ -c math_utils.cppm -o math_utils_if.o   # BMI: gcm.cache/math_utils.gcm
g++ -std=c++20 -fmodules-ts -c math_utils.cpp -o math_utils_impl.o
g++ -std=c++20 -fmodules-ts -c main.cpp -o main.o
g++ main.o math_utils_if.o math_utils_impl.o -o test_app

  • Clang 17+ (szabványos C++20 modulok; a -fmodules és -fbuiltin-module-map a Clang saját, module map alapú rendszeréhez tartozik, nem ide):

    clang++ -std=c++20 --precompile math_utils.cppm -o math_utils.pcm
clang++ -std=c++20 -c math_utils.pcm -o math_utils_if.o
clang++ -std=c++20 -fmodule-file=math_utils=math_utils.pcm -c math_utils.cpp -o math_utils_impl.o
clang++ -std=c++20 -fmodule-file=math_utils=math_utils.pcm -c main.cpp -o main.o
clang++ main.o math_utils_if.o math_utils_impl.o -o test_app

    (A -fprebuilt-module-path=. a -fmodule-file= alternatívája, ha a .pcm fájlok neve a modulnévvel egyezik.)

  • MSVC 17.4+ (a /interface kapcsoló vagy az .ixx kiterjesztés jelöli az interfész egységet; a /module:interface a VS 2017-es kísérleti kapcsoló volt):

    cl /std:c++20 /EHsc /c /interface /TP math_utils.cppm /Fo:math_utils_if.obj
cl /std:c++20 /EHsc /c /reference math_utils=math_utils.ifc math_utils.cpp /Fo:math_utils_impl.obj
cl /std:c++20 /EHsc /c /reference math_utils=math_utils.ifc main.cpp
link main.obj math_utils_if.obj math_utils_impl.obj /OUT:test_app.exe

Az interfész- és az implementációs egység külön .obj nevet kap (/Fo), mert a cl /c alapértelmezésben a forrásfájl alapneve szerint nevezi el az objektumfájlt, így a második parancs felülírná az interfészegység objektumát. (Az MSVC-sorozat nem futtatott, a GCC/Clang-sorozattal analóg vázlat.)

Mivel a toolchain-ek gyorsan fejlődnek, a könyv írásakor a fenti kapcsolók egy adott verzióra vonatkoznak, és a pontos parancsokat mindig a használt fordító dokumentációjában kell ellenőrizni.

5.2.7 Labor: modul- és header unit vázlat

A fejezet laborja egy kis, reprodukálható modulrendszert épít fel. A cél, hogy az olvasó a gyakorlatban is megtapasztalja a modulok és header unitok használatát, és ellenőrizze a build folyamatot.

Specifikáció:

  • Készítsünk egy math_utils modult, amely két függvényt exportál: add és multiply.
  • Készítsünk egy legacy_config.h fejlécet, amely egy legacy_double inline függvényt és egy LEGACY_MODE makrót tartalmaz.
  • A főprogram importálja a math_utils modult. A legacy_config.h fejlécet a CMake-változatban #include-oljuk (a CMake nem támogat header unitot); a kézi parancssori változatban header unitként is importálható.
  • A program írja ki az add(2,3), multiply(2,3) és legacy_double(4) értékeit.

Fájlok:

math_utils.cppm (module interface unit):

export module math_utils;

export namespace math_utils {

int add(int a, int b) {
    return a + b;
}

int multiply(int a, int b);

} // namespace math_utils

math_utils.cpp (module implementation unit):

module math_utils;

namespace math_utils {

int multiply(int a, int b) {
    return a * b;
}

} // namespace math_utils

legacy_config.h:

#ifndef LEGACY_CONFIG_H
#define LEGACY_CONFIG_H

inline int legacy_double(int x) {
    return x * 2;
}

#define LEGACY_MODE 1

#endif

main.cpp:

import math_utils;
#include "legacy_config.h" // CMake-változat; header unitként: import "legacy_config.h";
#include <iostream>

int main() {
    std::cout << math_utils::add(2, 3) << ' '
              << math_utils::multiply(2, 3) << ' '
              << legacy_double(4) << '\n';
}

Build lépések:

A reprodukció érdekében rögzítsük a toolchain-t és a szabványverziót: C++20, GCC 14 vagy újabb (a CMake natív modultámogatásához), CMake 3.28+ és Ninja 1.11+; a GCC 13.3 a CMake-es modulszkenneléshez nem elég, vele csak a kézi parancssori sorozat használható. A CMake-változatban a legacy_config.h hagyományos #include; a header unitos változatot a GCC kézi parancsaival építjük (lásd a build futtatása után).

A CMake build:

cmake_minimum_required(VERSION 3.28)
project(modules_lab CXX)

add_library(math_utils)
target_sources(math_utils
    PUBLIC FILE_SET CXX_MODULES FILES math_utils.cppm
    PRIVATE math_utils.cpp
)
target_compile_features(math_utils PUBLIC cxx_std_20)

add_executable(test_app main.cpp)
target_link_libraries(test_app PRIVATE math_utils)
target_compile_features(test_app PRIVATE cxx_std_20)
# A header unitot a CMake nem kezeli; a legacy_config.h #include-dal kerül be.

A build futtatása:

cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=g++-14   # GCC 14+ szükséges
cmake --build build
./build/test_app

A header unitos változat kézi GCC-parancsokkal (a main.cpp-ben import "legacy_config.h";; a -fmodules-ts mellett a header unit BMI-jét előbb elő kell állítani; ezt a sorozatot a könyv írásakor nem futtattuk, a pontos kapcsolók verziófüggők):

g++ -std=c++20 -fmodules-ts -x c++-user-header -c legacy_config.h
g++ -std=c++20 -fmodules-ts -x c++ -c math_utils.cppm -o math_utils_if.o
g++ -std=c++20 -fmodules-ts -c math_utils.cpp -o math_utils_impl.o
g++ -std=c++20 -fmodules-ts -c main.cpp -o main.o
g++ main.o math_utils_if.o math_utils_impl.o -o test_app

Mérési napló:

A labor során mérjük a következőket:

  • Fordítási idő: külön a tiszta build (build könyvtár törlése/újrakonfigurálása után) és külön az inkrementális, változatlan forrású (no-op) build; a második és harmadik egymás utáni cmake --build ugyanis nem teljes fordítás. Mindkettőt legalább háromszor mérjük, és vegyük a mediánt.
  • Bináris méret: a létrejött végrehajtható fájl mérete bájtban vagy KiB-ben (1 KiB = 1024 bájt).
  • Futási kimenet: a program kimenete.

A mért és várt eredményt külön táblázatban rögzítsük:

Mérőszám Mért érték (medián) Várt tartomány (szemléltető)
Tiszta build idő (s) kitöltendő < 5
No-op build idő (s) kitöltendő < 1
Bináris méret (KiB) kitöltendő 20–100
Kimenet kitöltendő „5 6 8”

A mért oszlopot a saját környezetben (fordító- és CMake-verzió, gép) kell kitölteni; a várt tartományok tájékoztató, szemléltető becslések, nem mért adatok; a cél a reprodukálhatóság és a modulok használatának igazolása, nem a teljesítményoptimalizálás.

Ellenőrzés:

A labor során ellenőrizzük, hogy:

  • A modul interfész és implementation unit helyesen van-e szétválasztva.
  • A header unit importálása (a kézi parancssori változatban, ha támogatott) átadja a fejléc makróit: a LEGACY_MODE makró elérhető a main.cpp-ben, akárcsak a #include esetén. A named module ezzel szemben nem exportál makrókat; ezt egy külön modullal demonstrálhatjuk, ahol a modulban definiált makró az importálóban nem látszik.
  • A build rendszer helyesen kezeli-e a modul függőségeket: ha a main.cpp-t a modul interfész nélkül próbáljuk fordítani, a fordítás hibát ad.

A labor átadandó eredménye a build parancsok, a forrásfájlok, a mérési napló és a futtatási kimenet.

5.2.8 Tipikus hibák és elkerülésük

A modulok használata során számos gyakori hiba merülhet fel, amelyeket érdemes előre ismerni.

  1. Export szintaxis hibás használata:
    • Az export csak a modul interfész egységben jelenhet meg, és csak a modul deklaráció után. Az implementation unitben vagy a partícióban (ha nem interfész partíció) az export használata fordítási hibát okoz.
    • Az export nem alkalmazható minden deklarációra, például nem lehet exportálni egy static változót vagy egy belső linkage-ű entitást. A modul interfészben csak olyan entitás exportálható, amelynek külső linkage-je van.
  2. A modul nevének ütközése:
    • Két modul nem viselheti ugyanazt a nevet ugyanabban a programban. A modul neve globális azonosító, ezért a nagy rendszerekben ügyelni kell az egyedi nevekre (pl. cég vagy projekt prefix).
  3. Helytelen partícióhasználat:
    • A partíció nevének a modul nevével kell kezdődnie, kettősponttal elválasztva. A module :part; deklaráció hiányos modulnév esetén hibás.
    • A partíciók közötti importálásnál a partíció nevét kell használni, nem a modul nevét: import :core; a helyes; az import geometry:core; forma szabványosan hibás (partíciót csak ugyanazon modulon belül, import :core; alakban lehet importálni).
  4. A globális modul fragment figyelmen kívül hagyása:
    • Ha a modul interfészben #include direktívát szeretnénk használni, akkor azt a globális modul fragmentben kell elhelyezni, amely a module; deklarációval kezdődik az export module előtt. Ez a rész csak preprocesszor direktívákat tartalmazhat, és az itt include-olt fejlécek entitásai nem lesznek a modul részei, hacsak nem exportáljuk őket külön.

Példa a globális modul fragmentre:

module;
#include <cstdint> // ez a fejléc nem lesz a modul része
export module mymod;

export std::int64_t get_value(); // itt a std::int64_t már látható, mert a globális fragmentben include-oltuk

Helytelen viszont, ha az export module mymod; deklaráció után #include-ot használunk: a modul hatókörében (purview) beillesztett fejléc deklarációi a modulhoz tartoznának, ami csatolási és ODR-kockázatot jelent. A module; utáni, az export module előtti rész (a globális modulfragmentum) a helyes hely a hagyományos fejléceknek.

  1. Header unit nem megfelelő kezelése:
    • Nem minden header alkalmas header unitként való importálásra. Ha a header kódból függ a makrók szivárgásától, vagy ha a header állapotot tart fenn include guardokon keresztül, a header unit importálása más viselkedést eredményezhet. Általában a jól megírt, önálló fejlécek működnek header unitként, de ezt tesztelni kell.
    • A header unit importálása átadja a fejlécben definiált makrókat; a named module-ok viszont nem. Ha a fogyasztó kód a fejlécben definiált makrót szeretné használni, header unit vagy hagyományos #include szükséges, named module nem elegendő.
  2. Build rendszer hiányos konfigurációja:
    • Ha a build rendszer nem ismeri a modulok függőségeit, akkor a párhuzamos fordítás során versenyhelyzet alakulhat ki a BMI fájlok generálásakor. A modern CMake kezeli ezt, de a kézi makefile-okban explicit függőségi szabályokat kell írni.
    • A modul interfészeket mindig a fogyasztó fordítási egységek előtt kell lefordítani. Ha a BMI hiányzik, a fordítás hibát ad.

5.2.9 Összefoglalás

A C++20 modulok a header-alapú fejlesztés strukturális problémáira adnak választ: megszüntetik a szövegszerű include ismétlődését, csökkentik a makrók és a rejtett függőségek okozta kockázatokat, és explicitté teszik a függőségi gráfot. A modul interfész és implementation unit szétválasztása lehetővé teszi a kód szervezését, a partíciók a nagy modulok belső tagolását, a header unitok pedig fokozatos átmenetet biztosítanak a hagyományos fejlécekről a modulokra.

A modulok bevezetése azonban nem triviális: a build rendszereknek, a toolchaineknek és a fejlesztőknek is alkalmazkodniuk kell. A gyakorlati használathoz elengedhetetlen a build folyamat pontos ismerete, a hibák korai felismerése és a reprodukálható tesztek alkalmazása. A laborban felépített kis modulrendszer ezt a folyamatot gyakoroltatja. A következő alfejezet a ranges és views témakörrel a modern C++ egy másik, a modulokkal egymástól független, de szintén C++20-ban bevezetett kulcsterületét tárgyalja.

5.2.10 Önellenőrző kérdés

Miben különbözik a import <vector>; (header unit) a #include <vector> direktívától a makrók és a fordítási idő szempontjából? Magyarázza el, miért adja át a header unit a fejlécben definiált makrókat, miközben egy named module (export module M;) nem exportálja a saját makróit.

Megoldás (vázlat): a import <vector>; header unit: a fejlécet a fordító egyszer elemzi és lefordított formában használja újra, ezért gyorsabb lehet a szöveges beillesztésnél, a fejléc makrói viszont az importálóban megjelennek (de az importáló előzetes makrói általában nem hatnak a header unitra). A #include <vector> minden fordítási egységben újra elemzi a szöveget, és az include-előtti makrók befolyásolják. A header unit azért adja át a makrókat, mert célja a meglévő fejlécek fokozatos, a viselkedést megőrző átvezetése; a named module viszont szándékosan nem exportál makrókat, hogy az izolációt biztosítsa. A tényleges gyorsulás mérendő, ezért itt nincs szám.
