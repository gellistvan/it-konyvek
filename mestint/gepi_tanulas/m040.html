11.4 Adatvalidáció

Ahogy a korábbi fejezetekben megtisztítottuk és kódoltuk az adatainkat, nagy a kísértés, hogy azonnal a modellépítésre ugorjunk. A valós ML mérnöki munka azonban megkövetel egy közbenső lépést: az adatvalidációt. Ha a modell egy gyártósor, az adat a nyersanyag. Nem elég egyszer ránézni a nyersanyagra; a futószalag elé szerelni kell egy automata kaput, amely minden egyes beérkező tételt ellenőriz. Ez a kapu az adatvalidáció.

Ez a fejezet az adat-előkészítés záróköve. A 11.1. (hiányzó adatok), 11.2. (outlier és tisztítás) és 11.3. szakaszban (kategorikus kódolás) az észlelt hibákat egyszeri tisztítással javítottuk. Most egy olyan rendszert építünk, amely folyamatosan szűri ezeket a hibákat.

11.4.1 Alapfogalmak: Séma, tartomány és adatminőség

A gépi tanulásban az adatvalidáció három fogalmi pilléren nyugszik. Bár a mindennapi munkában gyakran egybefolynak, programozóként érdemes őket élesen elkülöníteni.

11.4.1.1 Séma: A szerkezet szerződése (Schema)

A séma az adatok statikus, kódolási szintű leírása. Amikor Pythonban típust deklarálunk, vagy SQL-ben CREATE TABLE parancsot adunk ki, sémát írunk le. A gépi tanulás kontextusában a séma a belépő adatmátrix 𝐗∈ℝN×d\mathbf{X} \in \mathbb{R}^{N \times d} oszlopainak szerződése.

A séma validálása során a következő kérdésekre keressük a választ:

  • Típus: A mező int64, float32, object vagy datetime64[ns]? Mi történik, ha egy numerikus oszlop szövegként ("42" stringként) érkezik? A pandas a szövegként érkező numerikus oszlopot csendben szöveges (object, pandas 3-tól str) típusúnak olvassa be, ami később némán hibás működést okozhat.
  • Üresség (Nullability): Mely oszlopokban lehet NaN? Egy modell betanítása után a produkciós rendszerben gyakran váratlanul jelenik meg NULL érték olyan helyen, ahol a tanító adatban soha nem volt.
  • Unicitás: Van-e duplikált elsődleges kulcs? Az adatbetöltés során gyakori hiba a duplikált sorok generálódása (pl. egy JOIN művelet helytelen logikája miatt).

Példa sémaszerződés (Confluent Schema vagy pandera stílusban):

# Schema definíció pszeudokód
schema = {
    "user_id":  DataType.INTEGER, 
    "age":      DataType.FLOAT,     
    "category": DataType.CATEGORICAL,
    "created":  DataType.DATETIME
}
# Ellenőrzés: ha `age` típusa nem int/float -> SÉMA HIBÁT dobunk

11.4.1.2 Tartomány: Az értékek határai (Domain / Range)

A tartomány az adatok logikai és matematikai lehetséges értékkészletét jelenti. Ez túlmutat a puszta típuson. Ha egy mező típusa float, az még nem jelenti azt, hogy bármilyen float érték fizikailag vagy üzletileg érvényes.

Példák tartományi megsértésekre:

  • Matematikai: Az életkor (age) értéke age=−5age = -5. Bár ez egész szám, a valós világban lehetetlen.
  • Üzleti: A havi fizetés (salary) 10000000001\,000\,000\,000 értéket kap. A float típus elbírja, de a valós bérek tartománya ezt kizárja.
  • Halmaztagsági: Egy kategorikus mező célzott értékkészlete (pl. az osztályzat csak ["A", "B", "C"] lehet), de váratlanul megjelenik egy "D".

A tartományi validáció során a [min⁡,max⁡][\min, \max] intervallumokat, halmazbeli tagságot, valamint a reguláris kifejezéseket (formátum-ellenőrzés, pl. irányítószám) ellenőrizzük.

11.4.1.3 Adatminőség: A tartalom egészsége (Data Quality)

Az adatminőség a legsokrétűbb fogalom. Ide tartozik minden, ami a séma és a tartomány ellenőrzésén átmegy, de statisztikailag vagy informatikailag mégis „gyanús”.

  • Integritás: A relációs kulcsok érvényessége. Az orders tábla minden user_id értéke (idegen kulcs) megtalálható a users tábla user_id elsődleges kulcsai között? (pandasban: orders["user_id"].isin(users["user_id"]).all())
  • Konzisztencia: A teljes adathalmazon belül a definíciók nem változnak-e? Tipikus eset: az első 1000 sorban a NaN jelezte a hiányzó értéket, a következő 1000 sorban pedig egy sentinel érték, például a -1.
  • Statisztikai sodródás (Data Drift): A beérkező új adatok átlaga vagy szórása eltér-e a tanító adatétól? Az adatminőségi ellenőrzés ki kell, hogy számolja a várt (baseline) és a mért (current) statisztikákat, és riasszon, ha ezek túlzottan eltérnek.

A drift mérésére két gyakori eszköz a Population Stability Index (PSI) és a kétmintás Kolmogorov–Smirnov-próba. A PSI a baseline kvantilis-vödrei szerint hasonlítja össze az arányokat: PSI=∑k(ck−bk)ln⁡(ck/bk)\mathrm{PSI}=\sum_k (c_k-b_k)\ln(c_k/b_k), ahol bkb_k és ckc_k a baseline és az új adat aránya a kk-adik vödörben. Elterjedt, de nem univerzális ökölszabály: PSI<0,1\mathrm{PSI}<0{,}1 stabil, 0,10{,}1–0,250{,}25 figyelendő, >0,25>0{,}25 jelentős eltolódás; a küszöböt a feladathoz kell hangolni.

# Vázlat; a könyv írásakor nem futtattuk.
import numpy as np
from scipy.stats import ks_2samp

def psi(baseline, current, bins=10, eps=1e-6):
    edges = np.quantile(baseline, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf
    b = np.histogram(baseline, edges)[0] / len(baseline)
    c = np.histogram(current, edges)[0] / len(current)
    b, c = np.clip(b, eps, None), np.clip(c, eps, None)
    return float(np.sum((c - b) * np.log(c / b)))

# baseline_age: tanító adat; current_age: az utóbbi hét produkciós adata
# stat, pval = ks_2samp(baseline_age, current_age)   # kétmintás KS-teszt
# riasztás: psi(baseline_age, current_age) > 0.25 vagy pval < 0.01

11.4.2 Implementációs alapok: A Python validációs eszköztár

A Python ökoszisztémában több eszköz is létezik az automatizált adatvalidációra. A cél nem a manuális EDA (Exploratory Data Analysis) megismétlése, hanem egy programozott, folyamatosan futó szerződés.

11.4.2.1 Egyszerű alapok: egyéni ellenőrző függvények

A legkisebb projektek esetén elegendő lehet egy dedikált validate.py vagy notebook cella, amely explicit ellenőrzésekkel és kivételdobással (raise) védi a pipeline-t (az assert erre nem alkalmas, lásd lent).

import pandas as pd
import numpy as np

def validate_raw_input(df: pd.DataFrame) -> None:
    # 1. SÉMA: típusok ellenőrzése
    if not pd.api.types.is_numeric_dtype(df["age"]):
        raise ValueError("Age nem numerikus!")

    # 2. TARTOMÁNY: intervallumok ellenőrzése. A between() a NaN-ra False-t ad,
    #    ezért a hiányzó értékeket külön kezeljük (lásd a 4. pontot).
    if not df["age"].dropna().between(0, 120).all():
        raise ValueError("Lehetséges életkor kívül esik a [0, 120] tartományon!")

    # 3. TARTOMÁNY: halmaz-tagság
    valid_cats = {"A", "B", "C"}
    if not df["grade"].isin(valid_cats).all():
        raise ValueError("Ismeretlen kategória!")

    # 4. MINŐSÉG: hiányossági arány küszöb alatt tartása
    missing_ratio = df["age"].isna().mean()
    if missing_ratio > 0.05:
        raise ValueError(f"Túl sok hiányzó életkor: {missing_ratio:.2%}")

# Használat
data = pd.read_csv("raw_data.csv")
validate_raw_input(data)

Előny: Nincs függőség, azonnali. Hátrány: Nem skálázható, a hibák kézzel írt üzenetei törékenyek.

Megjegyzés: az assert utasítást a python -O kikapcsolja, ezért éles validációra nem alkalmas; a fenti példa ezért kivételt dob (raise), ahogy a labor is.

11.4.2.2 Ipari szintű megoldások: Sémakönyvtárak

Nagyobb projektekben (vagy a könyv későbbi MLOps részében, a kísérletkövetésnél) a deklaratív sémaellenőrző könyvtárak jobban karbantarthatók. A pandera kifejezetten pandas DataFrame-ek (oszlopszintű) validálására készült; a pydantic ezzel szemben sorszintű/objektum-validáló (például API-bemenetre), nem DataFrame-sémakönyvtár. A példa pandera ≥ 0.24 mellett import pandera.pandas as pa formában ajánlott (régebbi, 0.14–0.23 verzióknál import pandera as pa); a verziót a labor rögzítse.

# Illusztratív példa pandera használatára (nem futtattuk)
import pandera.pandas as pa   # pandera >= 0.24; régebbi (0.14–0.23) verziónál: import pandera as pa
from pandera.typing import Series

class InputSchema(pa.DataFrameModel):   # a SchemaModel elavult alias
    # nullable=True: a hiányzás arányát külön minőségi szabály korlátozza (<= 5%)
    age: Series[float] = pa.Field(ge=0, le=120, nullable=True)
    grade: Series[str] = pa.Field(isin=["A", "B", "C"])
    user_id: Series[int] = pa.Field(unique=True)

# A validation lefut, hibát dob, ha a DataFrame megsérti a sémát
validated_df = InputSchema.validate(data)

A deklaratív séma előnye, hogy maga a sémaobjektum verziózható, publikus (contract), és a hibaüzenetek automatikusan generálódnak.

11.4.3 A validáció három kapuja

Az adatvalidáció nem csak a betanítás előtt, hanem a betanítás során és az inferencia során is létfontosságú. A gépi tanulási életciklus korai, életciklust tárgyaló fejezetének munkafolyamatában az adatvalidációnak három elkülönített kaput kell képeznie.

11.4.3.1 Betanítási kapu (Training Gate)

Itt validáljuk a nyers adatot a szakterületi tudás (domain knowledge) alapján definiált szabályok szerint. Ha itt megy át az adat, elkezdhetjük a feature engineeringet (12.1. szakasz).

11.4.3.2 Szolgáltatási kapu (Serving Gate)

A modell betanítása után a produkciós rendszerbe érkező élő adatnak pontosan ugyanazokon a transzformációkon és ellenőrzéseken kell átesnie, mint a tanító adatnak. Ennek a követelménynek a megsértését, vagyis a tanítási és a kiszolgálási adatfeldolgozás eltérését nevezzük training–serving skew-nak. Ha a tanításkor bemenetként szolgáló age oszlop float, a predikciókor pedig string, a validációs kapunak ezt el kell kapnia, nem pedig a modellnek kellene kivételt dobnia.

11.4.3.3 Monitorozási kapu (Monitoring Gate)

A produkcióban a beérkező adat eloszlását folyamatosan össze kell vetni a tanító adat baseline-jával (PSI, KS-teszt; lásd fent), és riasztani kell, ha az eltérés meghalad egy előre rögzített küszöböt. Ez a kapu fogja meg a séma- és tartományellenőrzésen átmenő, de statisztikailag elcsúszott adatot.

11.4.4 Módszertani hiba: a teszthalmaz „bestoppolása”

Az egyik legtipikusabb hiba, amikor a validációt követő adatból tanult javításokat (outlier-küszöb, mediánimputálás, skálázás) a split után a teljes adathalmazon (tanító + teszt) hajtjuk végre (a split a 12.2. szakaszban szerepel).

Helytelen munkafolyamat: 1. Split →\rightarrow X_train, X_test 2. Validáció: talál 3 hibás sort X_test-ben. 3. Javítás (például mediánimputálás, outlier-törlés) a concat(X_train, X_test) adaton.

Ez adatszivárgást (data leakage) okoz, mert a javításhoz használt statisztikákat (medián, küszöb) a teszt adat is befolyásolja, így a teszt információt ad a tanító adat előkészítéséhez.

Helyes munkafolyamat: a javításokat két osztályra kell bontani. 1. Szabályalapú ellenőrzések (séma, tartomány, egyediség, ismert hibakódok, halmaztagság) az adatból tanult statisztikát nem igényelnek, ezért a split előtt, a nyers adaton elvégezhetők, és a bizonyítottan hibás sorok ekkor jelölhetők vagy kivehetők. 2. Adatból tanult javítások (imputálás, winsorizálás, skálázás, kódolók) csak a tanítóhalmazon illeszthetők (fit), és a validációs/teszt adatra csak a megtanult paraméterekkel alkalmazhatók (transform). 3. A teszthalmaz statisztikáját (átlag, szórás, medián) soha ne használjuk fel a tanító halmaz imputálására vagy skálázására.

11.4.5 A szándékosan hibás példa elemzése

A valós adatvalidáció a mélységi védelem elvét követi. Vegyünk egy egyszerű, szándékosan rossz adathalmazt, amely például hibás astype hívás vagy hibás string kódolás miatt keletkezhetett (ez a példa szándékosan hibás adatot tartalmaz).

Tegyük fel, hogy a várható séma d=3d = 3 dimenzió, N=5N = 5 mintával: - name: str - height: float - weight: float

A beérkező adat CSV-ben (a height oszlopban egy n.a. jelölő szerepel):

import io
import pandas as pd

csv = io.StringIO('''name,height,weight
A,1.75,75.0
B,n.a.,80.0
C,1.80,90.0
D,2.50,100.0
E,1.70,-5.0
''')
df = pd.read_csv(csv)
print(df["height"].dtype)   # várt: object (pandas 2.x) vagy str (pandas >= 3.0) – a lényeg: nem numerikus; az "n.a." nincs az alapértelmezett na_values listán

Fontos: a read_csv alapértelmezett na_values listája tartalmazza az "N/A", "NA", "NaN", "null" és az üres sztring jelölőket, ezért ezek automatikusan NaN-ná alakulnak, és az oszlop float64 marad. A height oszlop csak olyan jelölővel lesz object, amely nincs a listán (például "n.a.", "?", "-"), vagy ha keep_default_na=False-t adunk meg. Az object oszlopot ellenőrzött konverzióval tehetjük numerikussá, a gyanús sztringet NaN-ná alakítva: df["height"] = pd.to_numeric(df["height"], errors="coerce"). Ekkor a séma érvényes (float64), de a B sor magassága hiányzik.

Azonban ezután jön a tartományi validáció. Vigyázat: a between a NaN-ra False-t ad, ezért a hiányzó értéket a tartományellenőrzés csendben „hibásnak” számítaná. A hiányzást és a tartományon kívüliséget ezért külön kezeljük:

def is_valid_domain(df):
    missing_height = df['height'].isna()
    # Height: emberi magasság (0.5m - 2.3m); a NaN-t külön számoljuk
    bad_height = ~df['height'].between(0.5, 2.3) & ~missing_height
    # Weight: emberi tömeg (2kg - 200kg)
    bad_weight = ~df['weight'].between(2, 200)
    print(f"Hiányzó magasság: {missing_height.sum()}, "
          f"tartományon kívüli: {(bad_height | bad_weight).sum()}")
    return df[~(missing_height | bad_height | bad_weight)]

df_clean = is_valid_domain(df)
print(f"Kiesett sorok: {len(df) - len(df_clean)}")
# Várt (kézzel levezetett) kimenet:
# Hiányzó magasság: 1, tartományon kívüli: 2
# Kiesett sorok: 3 (B: hiányzó magasság, D: 2,5 m, E: -5 kg)

Látjuk, hogy a B sor magassága hiányzik, a D sor magassága 2,5 méter (tartományi hiba), az E sor súlya -5 kg (logikai/matematikai hiba, a tartomány [2, 200]). Ha a hiányzást nem választanánk külön, a between a B sort is „tartományon kívülinek” minősítené, akkor is, ha egyébként a hiányzó érték imputálható lenne. Az adatminőségi ellenőrzés pedig ezek statisztikai jelenlétét monitorozná: ha a tömeg átlaga hirtelen 180 kg lesz, az driftszerű. (A kimenet kézzel levezetett, nem futtatott érték.)

11.4.6.3 A szintetikus nyers adat generálása

Rögzítsük a mért és várt értékeket. Célunk, hogy az adat 5%-a (10 sor a 200-ból) hibás legyen.

N = 200
categories = ['A', 'B', 'C']
df_ok = pd.DataFrame({
    'id': range(N),
    'category': rng.choice(categories, N),
    'value': rng.normal(50, 10, N)  # elvárt tartomány: [0, 100]
})

# Szándékos hibák beinjektálása egy másolatba
df_bad = df_ok.copy()
noise_idx = rng.choice(N, size=10, replace=False)

# Hiba 1: érték a tartományon kívül (5 sor)
df_bad.loc[noise_idx[:5], 'value'] = -999

# Hiba 2: ismeretlen kategória, 'D' (5 sor)
df_bad.loc[noise_idx[5:], 'category'] = 'D'

11.4.6.4 A validációs szkript

A validációnak ki kell írnia a mért és a várt értékeket, és minden ellenőrzés lefuttatása után kivételt kell dobnia, ha hiba van (a hibákat gyűjtjük, így a mért hibaszám is látszik).

class DataValidationError(Exception):
    pass

def run_validation(df: pd.DataFrame):
    # VÁRT ÉRTÉKEK (Definíciók)
    expected_categories = {'A', 'B', 'C'}
    expected_value_range = (0.0, 100.0)
    expected_unique_ratio = 1.0  # minden id egyedi
    errors = []

    # SÉMA ELLENŐRZÉS
    if not pd.api.types.is_numeric_dtype(df['value']):
        errors.append("SÉMA: 'value' nem numerikus!")
    if not pd.api.types.is_integer_dtype(df['id']):
        errors.append("SÉMA: 'id' nem egész szám!")

    # TARTOMÁNY ELLENŐRZÉS (a mért hibaszámot is megőrizzük)
    n_bad_cat = int((~df['category'].isin(expected_categories)).sum())
    if n_bad_cat:
        errors.append(f"TARTOMÁNY: {n_bad_cat} ismeretlen kategória")
    lo, hi = expected_value_range
    n_bad_val = int((~df['value'].between(lo, hi)).sum())
    if n_bad_val:
        errors.append(f"TARTOMÁNY: {n_bad_val} érték kívül esik a [{lo}, {hi}] tartományon")

    # ADATMINŐSÉG (Integritás)
    measured_unique_ratio = df['id'].nunique() / len(df)
    if measured_unique_ratio != expected_unique_ratio:
        errors.append(f"MINŐSÉG: duplikált ID! Mért: {measured_unique_ratio}, Várt: {expected_unique_ratio}")

    n_bad_rows = int((~df['category'].isin(expected_categories) | ~df['value'].between(lo, hi)).sum())
    print(f"Mért hibás sorok: {n_bad_rows}/{len(df)}; várt (injektált): 10/{len(df)} = 5%")
    if errors:
        raise DataValidationError("; ".join(errors))
    print("Validáció sikeres. Minden adat konzisztens.")

# Tiszta ág: nem dobhat kivételt
run_validation(df_ok)        # várt: 0 hibás sor, sikeres validáció
# Hibás ág: kivételt kell dobnia
try:
    run_validation(df_bad)   # várt: 5 ismeretlen kategória + 5 tartományon kívüli érték
except DataValidationError as e:
    print(f"Validáció meghiúsult: {e}")

Mért és várt eredmény elválasztása: a expected_* értékek a szabályok, a Mért ... sor pedig a ténylegesen megszámolt hibák; a futtatás eredményét (a mért értékeket) a jegyzőkönyvbe kell rögzíteni (<mért – kitöltendő>), és össze kell vetni a várt 5%-os, injektált hibaaránnyal.

  • Ha a tartományi szabály (-inf, +inf) lenne a value mezőre, akkor milyen típusú hibákat nem kapnánk el?

11.4.7 Továbbvezetés: A validáció kapcsolata a feature engineeringgel

Az itt felépített sémavalidátor a következő alfejezetek alapköve. Amikor a 12.1. szakaszban a jellemzőtranszformációkhoz (pl. log⁡(x)\log(x) transzformáció) érünk, fontos látni, hogy az adatvalidációnak a transzformációk előtt és után is futnia kell.

Vegyünk egy klasszikus hibát: a value mezőben a 0 érték fizikailag érvényes lehet (pl. „nincs vásárlás”), de ha a feature engineering során log⁡(value)\log(value) transzformációt hajtunk végre, a 0 értéken a transzformáció −∞-\infty-t adna, amely már sémailag és tartományilag is érvénytelen. A validációs kapu itt fogja meg a hibát, mielőtt a modell a NaN vagy -inf értékkel találkozna.

Az adatvalidáció tehát nem egy megoldandó adminisztratív feladat, hanem egy szabályozó rendszer. Ha helyesen építjük fel, akkor az adathibák a forrásnál pattannak le ahelyett, hogy a modell tanulási folyamatában csapódnának ki furcsa, nehezen debugolható veszteségfüggvény-értékekben.

11.4.8 Önellenőrző kérdések

  1. Séma vs. tartomány: Adott egy osztályzat oszlop int64 típusban. Az értékei között szerepel a 6. Ez séma vagy tartományi hiba, és miért?
  2. Értékelési hiba: A mediánimputálást a teljes adaton végeztük, és csak utána választottuk le a tesztet. Miért torzítja ez a teszteredményt, és mi a helyes sorrend? (Válasz: az imputáló statisztikát a teszt is befolyásolja – szivárgás; helyesen: split → fit a tanítón → transform a teszten, lásd a szivárgásról szóló részt.)
  3. Drift: A betanító adatban a age átlaga 4040 év volt. A produkciós adatban az utóbbi hét átlaga 5555 év. Ez miért jelent adatminőségi kockázatot, még akkor is, ha a séma és a tartomány minden értéken átmegy? Milyen mérőszámmal és küszöbbel (PSI, KS-teszt) riasztanál?
