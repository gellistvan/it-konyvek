9.4 Kiadási kapu és biztonsági követelmények

A kiadási kapu (release gate) a szoftverfejlesztési folyamat azon pontja, ahol a biztonsági ellenőrzések eredménye alapján dől el, hogy egy változtatás továbbhaladhat-e a következő környezetbe (staging, production). A kapu nem pusztán technikai akadály, hanem a szervezet kockázatvállalási döntésének formalizálása: a R=L×IR = L \times I kockázati modell alapján a magas valószínűségű és nagy hatású hibák blokkolást igényelnek. Ebben az alfejezetben az automatizált ellenőrzés és az emberi jóváhagyás együttműködését, valamint az ezeket támadó vagy meggyengítő tipikus mintákat mutatjuk be. A gyakorlati laborban egy kis Python-alapú kaput készítünk, amely egy sebezhetőségi jelentés alapján hoz döntést.

9.4.1 Automatizált ellenőrzés: a pipeline mint döntéshozó

Az automatizált ellenőrzés a CI/CD-csővezetékben futó szoftveres szabályok összessége, amelyeknek az a feladata, hogy megbízhatóan rögzítsék, teljesülnek-e a kiadás előtti biztonsági követelmények. A SAST, DAST, IAST és fuzzing alfejezetben tárgyalt SAST-, DAST-, IAST- és fuzzing-eszközök, valamint a függőség-ellenőrzők, titokszkennerek és konténer-vizsgálók mind bemenetet adnak a kapunak. A kapu azonban nem maga a teszt, hanem az a döntési logika, amely a teszteredményeket kiértékeli, és enged vagy blokkol.

A legegyszerűbb kapu egy előre definiált küszöbérték: például ha a függőség-ellenőrző kritikus súlyosságú sebezhetőséget (critical) talál CVSS ≥9,0\geq 9{,}0 értékkel, akkor a pipeline megszakad. A CVSS itt nem azonos az üzleti kockázattal, de a nagyságrendje jó első szűrő. A kapu szabályait érdemes policy as code formában, verziózottan tárolni, hogy a döntés reprodukálható és auditálható legyen. Az alábbi YAML-részlet egy olyan pipeline-lépést mutat, amely egy SAST-jelentést dolgoz fel, és kritikus találat esetén leállítja a folyamatot.

# .gitlab-ci.yml – helyes kapu
security_scan:
  stage: verify
  script:
    - ./run_sast.sh
    - set -o pipefail; python3 evaluate_sast.py reports/sast.json | tee reports/release_decision.log
  allow_failure: false          # a hiba blokkolja a pipeline-t
  artifacts:
    when: always                # hibás job esetén is menti a bizonyítékot
    paths:
      - reports/sast.json
      - reports/release_decision.log
    expire_in: 7 days

A evaluate_sast.py felel a döntésért: beolvassa a JSON-jelentést, és a szabályok alapján kilép 0 (enged) vagy 1 (blokkol) értékkel. A allow_failure: false beállítás biztosítja, hogy a kilépési kód valóban megállítja a pipeline-t, tehát a kapu nem üres. A when: always azért kell, mert a paths alatti egyszerű artefaktumok alapértelmezésben csak sikeres job esetén töltődnek fel; egy blokkoló kapu viszont éppen hibás jobot eredményez, és a bizonyítéknak ilyenkor is meg kell maradnia. A reports: kulcs alatt csak a GitLab által ismert reporttípusok (például sast, dependency_scanning, secret_detection) adhatók meg, és csak akkor, ha a fájl a megfelelő GitLab-sémát követi; egy egyedi napló nem release_decision reporttípus, hanem egyszerű artefaktum.

A pipeline YAML érvényességét a CI Lint-tel kell ellenőrizni, például a GitLab CLI-vel:

glab ci lint .gitlab-ci.yml

vagy a CI Lint API-val:

curl --header "PRIVATE-TOKEN: <TOKEN>" --header "Content-Type: application/json" \
  --data '{"content":"<A_YAML_TARTALMA>"}' \
  "https://gitlab.example.invalid/api/v4/projects/<PROJECT_ID>/ci/lint"

A régi, példányszintű /ci/lint végpont a GitLab 16.0 óta nem érhető el; a projektszintű végpontot használd (a GitLab-dokumentációval kiadás előtt egyeztetendő).

A policy as code előnye, hogy a szabályok is felülvizsgálhatók, tesztelhetők és visszagörgethetők. Egy másik gyakori eszköz az Open Policy Agent (OPA), amelynek Rego nyelvén például a következő szabály definiálható:

package release

default allow := false

deny contains "missing_input" if {
  not input.scanner.status
}

deny contains "scanner_failed" if {
  input.scanner.status != "success"
}

deny contains "missing_build" if {
  not input.build.id
}

deny contains "build_mismatch" if {
  input.build.id != input.expected_build_id
}

deny contains "critical_vulns" if {
  input.critical_vulns > 0
}

deny contains "too_many_high" if {
  input.high_vulns > 3
}

deny contains "blocker_license" if {
  count(input.blocker_licenses) > 0
}

deny contains "missing_field" if {
  not input.critical_vulns
}

deny contains "missing_field" if {
  not input.high_vulns
}

deny contains "missing_field" if {
  not input.blocker_licenses
}

deny contains "missing_field" if {
  not input.expected_build_id
}

allow if {
  count(deny) == 0
}

Ez a szabály csak akkor enged, ha a scanner sikeresen lefutott, a vizsgált build azonosítója egyezik a várt builddel, nincs kritikus sebezhetőség, legfeljebb három magas súlyosságú találat van, nincs blokkoló licenc, és a kötelező mezők mind jelen vannak. Az OPA v1-ben a szabálytörzs if kulcsszót igényel; a régi, if nélküli OPA 0.x szintaxis nem használható. A hiányzó vagy hibás bemenet nem csendes „allow”, hanem a deny halmazban megjelenő hiba, amely blokkol.

Az OPA-t a pipeline-nak kell meghívnia, és a döntést exit kóddá kell fordítania, mert a opa eval kimenete önmagában nem kapu:

opa eval --format=raw --data policy.rego --input input.json 'data.release.allow' > decision.txt 2> opa.err

if [ $? -ne 0 ]; then
  echo "[HIBA] az OPA futtatása vagy a bemenet érvénytelen" >&2
  exit 2
fi

decision=$(cat decision.txt)
case "$decision" in
  true)  exit 0 ;;   # engedélyezett
  false) exit 1 ;;   # policy által blokkolt
  *)     echo "[HIBA] érvénytelen OPA-döntés: $decision" >&2; exit 2 ;;
esac

A 0 az engedélyezett, az 1 a policy által blokkolt, a 2 az OPA futási hibájának (olvashatatlan bemenet, policy-szintaxishiba) hibakódja. Az OPA-változatban a hiányzó mező, a scanner-hiba és a build-eltérés is policy-blokk (1), mert a deny halmazban jelenik meg; a 9.4.5 labor Python-kapuja ettől eltérően a hiányzó bemenetet, a scanner-hibát és a build-eltérést is 2-vel jelzi. Az eltérés a két implementáció kilépési kódjainak összehasonlításakor számít: az éles pipeline-ban válassz egyetlen megállapodást, és dokumentáld. A három esetet a CI-ben külön kell dokumentálni és tesztelni. Az OPA saját tesztjei is futtathatók:

package release

test_allow if {
  allow with input as {
    "scanner": {"status": "success"},
    "build": {"id": "build-2026-001"},
    "expected_build_id": "build-2026-001",
    "critical_vulns": 0,
    "high_vulns": 2,
    "blocker_licenses": []
  }
}

test_block_critical if {
  decision := allow with input as {
    "scanner": {"status": "success"},
    "build": {"id": "build-2026-001"},
    "expected_build_id": "build-2026-001",
    "critical_vulns": 1,
    "high_vulns": 0,
    "blocker_licenses": []
  }
  decision == false
}

test_block_scanner_failure if {
  decision := allow with input as {
    "scanner": {"status": "failed"},
    "build": {"id": "build-2026-001"},
    "expected_build_id": "build-2026-001",
    "critical_vulns": 0,
    "high_vulns": 0,
    "blocker_licenses": []
  }
  decision == false
}

test_block_build_mismatch if {
  decision := allow with input as {
    "scanner": {"status": "success"},
    "build": {"id": "build-2026-002"},
    "expected_build_id": "build-2026-001",
    "critical_vulns": 0,
    "high_vulns": 0,
    "blocker_licenses": []
  }
  decision == false
}

test_block_missing_expected_build if {
  decision := allow with input as {
    "scanner": {"status": "success"},
    "build": {"id": "build-2026-001"},
    "critical_vulns": 0,
    "high_vulns": 0,
    "blocker_licenses": []
  }
  decision == false
}
opa test policy.rego policy_test.rego

A tesztek akkor megfelelőek, ha az engedélyező eset allow, a kritikus, scanner-hibás és build-eltérés eset pedig false döntést ad; a hiányzó expected_build_id is false döntést ad. (A critical_vulns, high_vulns és blocker_licenses mezők hiányát hasonló teszttel érdemes lefedni. A tesztek tényleges lefutását laborban ellenőrizd.)

A tipikus hibás minták közé tartozik, amikor valaki a kaput kikapcsolja vagy meglazítja, hogy a build ne akadjon el. Például:

# HIBÁS – a biztonsági lépés nem blokkol
security_scan:
  stage: verify
  script:
    - ./run_sast.sh
  allow_failure: true           # ← HIBÁS: a hiba nem állítja meg a folyamatot

Itt a kapu formálisan létezik, de a hibái nem látszanak a pipeline állapotában, így a sebezhetőség átcsúszhat. Hasonlóan veszélyes, ha a küszöbértéket túl magasra állítják (például csak CVSS 10,0 blokkol), vagy ha a szabályt kommentbe teszik. Az ilyen változtatásokat a policy as code felülvizsgálati folyamata hivatott megfogni.

9.4.2 Emberi jóváhagyás: a kontroll második rétege

Az automatizált kapu gyors és következetes, de nem érti az üzleti kontextust. Egy adott sebezhetőség lehet kritikus az egyik szolgáltatásban, de elfogadható egy izolált belső eszközben, ha kompenzáló kontrollok vannak. Az emberi jóváhagyás (manual approval) olyan folyamat, amelyben egy illetékes személy – biztonsági mérnök, security champion, alkalmazástulajdonos – átnézi az automatizált ellenőrzések eredményeit, és formálisan jóváhagyja vagy elutasítja a továbbhaladást. Ez a „négy szem elv” gyakorlati megvalósítása, amely csökkenti az automatizált szabályok tévedésének vagy kikerülésének kockázatát.

A jóváhagyási folyamatot célszerű a változáskezelő rendszerhez kötni. GitLab esetében a merge request jóváhagyás nem a .gitlab-ci.yml része, hanem projekt- vagy csoportszintű beállítás és approval rule; a pipeline YAML csak a biztonsági ellenőrzéseket futtatja. Az approval rule-ok, a jóváhagyási beállítások és a code owner jóváhagyás a GitLab Premium/Ultimate szintjén érhetők el; Free szinten a védett ág és a „Pipelines must succeed” használható (a licencszintet kiadás előtt a GitLab-dokumentációval ellenőrizd). A helyes konfiguráció négy rétegből áll:

  1. Projektbeállítások (Settings → Merge requests → Approvals): „Prevent approval by author”, „Prevent approvals by users who add commits”, „Require user password to approve” és „Remove all approvals when commits are added” bekapcsolása. Ezek megakadályozzák, hogy a szerző vagy a commitot hozzáadó felhasználó saját maga hagyja jóvá a változtatást.
  2. Approval rule: például „Security review” néven egy kötelező jóváhagyás a security_champion csoporttól. Ez UI-ban vagy API-val hozható létre.
  3. Ágvédelem (Settings → Repository → Protected branches): a main ágra közvetlen push senkinek ne legyen engedélyezett, a merge csak Maintainer szinten történhessen, és legyen kötelező a code owner jóváhagyás.
  4. Merge checks (Settings → Merge requests): „Pipelines must succeed” és „All threads must be resolved”. Így a merge csak sikeres biztonsági pipeline és lezárt beszélgetések után lehetséges.

A beállítások API-val is rögzíthetők, ami auditálható és reprodukálható:

# Kötelező biztonsági jóváhagyás
curl --request POST --header "PRIVATE-TOKEN: <TOKEN>" \
  --data "name=Security review" \
  --data "approvals_required=1" \
  --data "group_ids[]=<SECURITY_CHAMPION_GROUP_ID>" \
  "https://gitlab.example/api/v4/projects/<PROJECT_ID>/approval_rules"

# Védett main ág: senki nem pusholhat közvetlenül, csak Maintainer mergelhet
curl --request POST --header "PRIVATE-TOKEN: <TOKEN>" \
  --data "name=main" \
  --data "push_access_level=0" \
  --data "merge_access_level=40" \
  --data "allow_force_push=false" \
  --data "code_owner_approval_required=true" \
  "https://gitlab.example/api/v4/projects/<PROJECT_ID>/protected_branches"

# Merge only with successful pipeline and resolved threads
curl --request PUT --header "PRIVATE-TOKEN: <TOKEN>" \
  --data "only_allow_merge_if_pipeline_succeeds=true" \
  --data "only_allow_merge_if_all_discussions_are_resolved=true" \
  "https://gitlab.example/api/v4/projects/<PROJECT_ID>"

A push_access_level=0 a közvetlen push tiltását, a merge_access_level=40 a Maintainer szintű merge-et jelenti. A code_owner_approval_required=true és a CODEOWNERS fájl együtt biztosítja, hogy a biztonsági szempontból kritikus fájlok módosítását a megfelelő tulajdonos is jóváhagyja. Az approval rule és az ágvédelem beállítása változásként naplózódik, így utólag visszakereshető, ki és mikor módosította a kaput.

Az emberi jóváhagyás azonban önmagában nem csodaszer. Tipikus támadási minta a social engineering: a támadó sürgető, hibásan megfogalmazott kéréssel veszi rá a jóváhagyót, hogy kattintson az „Approve” gombra anélkül, hogy a jelentést valóban megnézné. Egy másik gyakori hiba, hogy a jóváhagyók túlterheltek, ezért rutinszerűen jóváhagynak mindent (approval fatigue). A védelmi döntés ilyenkor a rotáció, a kötelező képzés, a kockázatalapú kiválasztás (csak a kritikus változtatásoknál emberi jóváhagyás), valamint az automatizált kapu további erősítése, például aláírt commitok vagy artefactum-ellenőrzés. A cél, hogy az emberi döntés ne legyen egyetlen védvonal, hanem kiegészítő réteg.

9.4.3 Tipikus támadási és védelmi minták

A kiadási kaput magát is támadhatják, mert ha sikerül megkerülni, akkor az összes többi kontroll hatástalanná válik. Az alábbiakban a leggyakoribb mintákat foglaljuk össze.

Támadási minta: a kapu közvetlen megkerülése

Ha a fejlesztők rendelkeznek jogosultsággal a main ágra történő közvetlen push-ra, akkor a merge request és a hozzá tartozó pipeline-kapu kikerülhető. A támadó egy kompromittált fejlesztői fiók segítségével közvetlenül feltölti a rosszindulatú kódot a védett ágra. A védelem a branch protection szabályok alkalmazása: a main ágra csak merge requesten keresztül, sikeres pipeline és jóváhagyás után lehessen beolvasztani, és a push műveletet tagadja meg a rendszer. Emellett a commitok aláírása (pl. GPG- vagy SSH-aláírás) növeli a hitelességet, bár ez önmagában nem állítja meg a támadót, ha a kulcs kompromittálódott.

Támadási minta: a kapu szabályainak meggyengítése

A támadó egy ártalmatlannak tűnő változtatással módosítja a pipeline YAML-jét vagy az OPA-policy-t, hogy az a jövőben minden sebezhetőséget átengedjen (például allow_failure: true, vagy a input.critical_vulns > 0 deny-feltételt input.critical_vulns > 10-re módosítja). Mivel a pipeline definíciója is verziózott, ez a támadás egy nem megfelelően felülvizsgált merge requestben bukkanhat fel. A védelem a policy as code-ra vonatkozó szigorú felülvizsgálati szabály: a .gitlab-ci.yml vagy a .rego fájlokat csak külön jóváhagyással, biztonsági szakember bevonásával lehessen módosítani, és a módosításokat automatikusan naplózza a rendszer. Hasznos még a pipeline definíciókra vonatkozó rejtett-csapda (honeypot) teszt: egy szándékosan hibás policy-verziót letesztelve azonnal riasztást kapunk, ha a kapu átenged.

Támadási minta: hamis bizonyíték bemutatása

A támadó módosíthatja a pipeline által előállított jelentést (pl. a SAST JSON-t), hogy az üresnek tűnjön, vagy éppen a saját rosszindulatú kódját fedje le. Ha a jelentést a pipeline egyszerű fájlként kezeli, és nincs integritásvédelem, a támadó a pipeline futtatása közben vagy után felülírhatja. A védelem az artefaktumok aláírása és a pipeline által generált fájlok kezelésének szigorítása: a jelentéseket a pipeline-hoz tartozó, aláírt artifact tárolóba kell helyezni, és a kapu csak az aláírt, ellenőrzött jelentést fogadja el. A 10.3 alfejezet (SLSA, Sigstore és in-toto) tárgyalja részletesen az aláírt artefaktumokat és a provenance-ot, ezért itt csak utalunk a koncepcióra.

Támadási minta: emberi jóváhagyó megkerülése

A támadó social engineeringgel vagy a jóváhagyó fiókjának kompromittálásával szerez jóváhagyást. Emellett előfordul, hogy a jóváhagyó nem nézi meg a tényleges kockázatot, hanem vakon rábólint. A védelem a többtényezős hitelesítés a jóváhagyó fiókján, a jóváhagyások naplózása, valamint a biztonsági eseményekre vonatkozó riasztás. Jó gyakorlat, ha a jóváhagyási felület automatikusan megjeleníti a pipeline összesített biztonsági eredményét, és a jóváhagyónak egy kockázati összefoglalót kell jóváhagynia, nem pedig egyetlen gombot.

9.4.4 Ellenőrzési, naplózási és dokumentációs szempontok

A kiadási kapu döntése csak akkor ellenőrizhető, ha a folyamat minden lépése naplózott, és a bizonyítékok megőrzöttek. A következő elemeket érdemes rögzíteni:

  • Pipeline-naplók: minden lépés kimenete, a használt eszközök verziója, a környezet azonosítója, az időbélyeg. A naplókat a kiadás életciklusa alatt meg kell őrizni, utána a szervezeti adatmegőrzési szabályok szerint lehet törölni.
  • Bizonyíték-artefactumok: a sebezhetőségi jelentések, SBOM, policy-értékelések, tesztjegyzőkönyvek. Ezeket aláírt formában, a pipeline artifact store-jában kell tárolni.
  • Audit trail: ki, mit, mikor, miért. A pipeline-trigger személye, a commit hash, a jóváhagyó személye, a jóváhagyás időpontja. A rendszernek képesnek kell lennie megválaszolni: „Miért ment át ez a build a kapun?”
  • Dokumentáció: a kiadási jegyzőkönyv (release record) tartalmazza a biztonsági kontrollok állapotát, az eltéréseket (pl. elfogadott közepes súlyosságú sebezhetőség), a jóváhagyások neveit, valamint a kapu döntését. A dokumentáció a későbbi audit során bizonyítja, hogy a szervezet megfelelően kezelte a kockázatot.

A pipeline YAML-jében a naplózás beállítása például így nézhet ki:

release_gate_job:
  stage: post-verify
  script:
    - echo "Release gate decision for commit $CI_COMMIT_SHA"
    - ./evaluate_release.sh >> release_decision.log
  artifacts:
    when: always
    paths:
      - release_decision.log
    expire_in: 30 days

Itt a release_decision.log fájl a napló és a bizonyíték szerepét is betölti, és a pipeline a when: always miatt hibás kapu esetén is megőrzi. A reports: kulcs alatt csak a GitLab által ismert reporttípusok adhatók meg (például sast: reports/sast.json), és csak akkor, ha a fájl a megfelelő GitLab-sémát követi. Egy egyedi döntési napló nem release_decision reporttípus, ezért egyszerű paths artefaktumként kell kezelni; ha mégis szabványos SAST-jelentést szeretnénk, a scannernek GitLab SAST JSON-t kell előállítania, és a reports: sast: kulcsot kell használni.

9.4.5 Labor: kiadási kapu definiálása és tesztelése

A labor célja, hogy a tanult fogalmakat egy minimális, helyi környezetben kipróbáld. Nem éles rendszer ellen dolgozunk, hanem egy független Python-szkriptet írunk, amely egy JSON-formátumú sebezhetőségi jelentést értékel ki. A TerraSecure fiktív környezetéhez hasonlóan a labor a ~/cyber-labor/cch08/ könyvtárban zajlik, és semmilyen külső hálózati kapcsolatot nem igényel.

Hatókör: saját, izolált munkakönyvtár; valós rendszer elleni támadás nem megengedett.

1. lépés – A kapu szkriptjének elkészítése

Hozd létre a release_gate.py fájlt az alábbi tartalommal:

#!/usr/bin/env python3
# Kiadási kapu: sémaellenőrzés + kritikus sebezhetőség blokkolása.
import json
import sys

EXIT_ALLOW = 0
EXIT_BLOCK = 1
EXIT_INVALID = 2

VALID_SEVERITIES = {"none", "low", "medium", "high", "critical"}

def fail(message):
    print(f"[HIBA] {message}")
    sys.exit(EXIT_INVALID)

def expected_severity(cvss):
    if cvss >= 9.0:
        return "critical"
    if cvss >= 7.0:
        return "high"
    if cvss >= 4.0:
        return "medium"
    if cvss > 0.0:
        return "low"
    return "none"

def validate_report(data):
    if not isinstance(data, dict):
        fail("a jelentés felső szintje objektum legyen")

    required_top = {"scanner", "build", "expected_build_id", "vulnerabilities"}
    missing = required_top - data.keys()
    if missing:
        fail(f"hiányzó mezők: {sorted(missing)}")
    extra = data.keys() - required_top
    if extra:
        fail(f"ismeretlen mezők: {sorted(extra)}")

    scanner = data["scanner"]
    if not isinstance(scanner, dict) or set(scanner.keys()) != {"status", "name", "version"}:
        fail("a scanner mező sérti a sémát")
    if scanner["status"] != "success":
        fail(f"a scanner nem futott sikeresen: {scanner['status']!r}")
    if not isinstance(scanner["name"], str) or not scanner["name"]:
        fail("a scanner neve üres")
    if not isinstance(scanner["version"], str) or not scanner["version"]:
        fail("a scanner verziója üres")

    build = data["build"]
    if not isinstance(build, dict) or set(build.keys()) != {"id"}:
        fail("a build mező sérti a sémát")
    if not isinstance(build["id"], str) or not build["id"]:
        fail("a build azonosítója üres")
    if data["expected_build_id"] != build["id"]:
        fail("a vizsgált build nem azonos a várt builddel")

    vulns = data["vulnerabilities"]
    if not isinstance(vulns, list):
        fail("a vulnerabilities lista legyen")  # az üres lista érvényes: sikeres scan, nincs találat

    for index, vuln in enumerate(vulns, start=1):
        if not isinstance(vuln, dict):
            fail(f"{index}. tétel nem objektum")
        if set(vuln.keys()) != {"id", "severity", "cvss"}:
            fail(f"{index}. tétel mezői hibásak")
        if not isinstance(vuln["id"], str) or not vuln["id"].startswith("LAB-"):
            fail(f"{index}. tétel azonosítója nem LAB- formátumú")
        if vuln["severity"] not in VALID_SEVERITIES:
            fail(f"{index}. tétel ismeretlen severity: {vuln['severity']!r}")
        cvss = vuln["cvss"]
        if isinstance(cvss, bool) or not isinstance(cvss, (int, float)):
            fail(f"{index}. tétel CVSS értéke nem szám")
        if not 0.0 <= cvss <= 10.0:
            fail(f"{index}. tétel CVSS értéke tartományon kívül: {cvss}")
        if expected_severity(cvss) != vuln["severity"]:
            fail(f"{index}. tétel severity/CVSS ellentmondás: {vuln['severity']} vs {cvss}")

    return vulns

def evaluate(vulns, critical_threshold=9.0):
    """Visszaadja a blokkoló sebezhetőségek listáját."""
    blockers = []
    for vuln in vulns:
        if vuln["severity"] == "critical" and vuln["cvss"] >= critical_threshold:
            blockers.append(vuln)
    return blockers

def main(argv):
    if len(argv) != 2:
        print("Használat: python3 release_gate.py <jelentes.json>")
        return EXIT_INVALID

    try:
        with open(argv[1], "r", encoding="utf-8") as f:
            data = json.load(f)
    except (OSError, json.JSONDecodeError) as exc:
        print(f"[HIBA] a jelentés nem olvasható vagy nem érvényes JSON: {exc}")
        return EXIT_INVALID

    vulns = validate_report(data)
    blockers = evaluate(vulns)

    if blockers:
        for vuln in blockers:
            print(f"[BLOKKOL] {vuln['id']} (CVSS {vuln['cvss']})")
        print("Kiadási kapu: NEM ENGEDÉLYEZETT")
        return EXIT_BLOCK

    print("Kiadási kapu: ENGEDÉLYEZETT")
    return EXIT_ALLOW

if __name__ == "__main__":
    sys.exit(main(sys.argv))

A szkript először validálja a bemeneti sémát, csak utána értékeli a sebezhetőségeket. A séma rögzíti a felső szintű mezőket (scanner, build, expected_build_id, vulnerabilities), a scanner állapotát és verzióját, a vizsgált build azonosítóját, valamint minden tétel id, severity és cvss mezőjét. A CVSS értéknek 0,0 és 10,0 között kell lennie, a severity értékének pedig összhangban kell lennie a CVSS-sávval (0,0 = none, 0,1–3,9 = low, 4,0–6,9 = medium, 7,0–8,9 = high, 9,0–10,0 = critical). Az oktatási azonosítók LAB-001 formátumúak, nem CVE-ként kinéző, félreérthető azonosítók. A kilépési kódok: 0 engedélyezett, 1 policy által blokkolt, 2 érvénytelen bemenet vagy használat.

Az alábbi ábra a szkript ellenőrzéseit és a labor fixture-jeinek útját mutatja: melyik ellenőrzés melyik kilépési kódhoz vezet, és mi történik utána a CI-ben.

3. lépés – A kapu tesztelése kritikus jelentéssel

Futtasd a szkriptet:

python3 release_gate.py vulns_critical.json
echo $?

Várható kimenet:

[BLOKKOL] LAB-001 (CVSS 9.8)
Kiadási kapu: NEM ENGEDÉLYEZETT
1

A kilépési kód 1, tehát a kapu policy alapján blokkolt. A LAB-001 a szándékosan mesterséges, oktatási célú azonosító; nem valós CVE.

4. lépés – Ártalmatlan jelentés tesztje külön fixture-rel

Hozd létre a vulns_safe.json fájlt; a korábbi kritikus fixture-t ne írd felül:

{

  "build": {"id": "build-2026-001"},
  "expected_build_id": "build-2026-001",
  "vulnerabilities": [

Futtasd:

Várható kimenet:

A sikeres, de találat nélküli scan (a legkívánatosabb eredmény) ugyanígy engedélyezett. Hozd létre a vulns_clean.json fájlt, amelyben a "vulnerabilities" üres lista ([]), a többi mező pedig megegyezik a vulns_safe.json mezőivel; a kapu ENGEDÉLYEZETT üzenettel és 0 kóddal lép ki. Ezzel szemben a hiányzó vulnerabilities mező továbbra is 2-t ad (a required_top ellenőrzés miatt), mert a hiányzó adat nem azonos a „nincs találat” állapottal.

5. lépés – Érvénytelen bemenetek és hibakódok

A 0, 1 és 2 hibakódokat külön kell tartani: a 2 nem policy-döntés, hanem érvénytelen bemenet vagy konfiguráció. Hozd létre a következő fixture-öket.

vulns_invalid.json – a severity és a CVSS ellentmond (9,8-as CVSS nem lehet high):

{
  "scanner": {"status": "success", "name": "terrasecure-sast", "version": "1.0.0"},
  "build": {"id": "build-2026-001"},
  "expected_build_id": "build-2026-001",
  "vulnerabilities": [
    {"id": "LAB-004", "severity": "high", "cvss": 9.8}
  ]
}

vulns_scanner_failed.json – a scanner nem futott sikeresen:

{
  "scanner": {"status": "failed", "name": "terrasecure-sast", "version": "1.0.0"},
  "build": {"id": "build-2026-001"},
  "expected_build_id": "build-2026-001",
  "vulnerabilities": [
    {"id": "LAB-005", "severity": "medium", "cvss": 5.5}
  ]
}

vulns_empty.json – üres objektum, hiányzó kötelező mezőkkel:

{}

Futtasd mindhármat, és ellenőrizd, hogy mindegyik 2-vel lép ki:

python3 release_gate.py vulns_invalid.json; echo $?
python3 release_gate.py vulns_scanner_failed.json; echo $?
python3 release_gate.py vulns_empty.json; echo $?

Várható kimenet mindhárom esetben [HIBA] ..., majd 2. A [HIBA] üzenet konkrétan megnevezi a sértett mezőt (severity/CVSS ellentmondás, scanner-állapot, hiányzó mezők). A hiányzó vagy hibás bemenet tehát nem csúszik át „engedélyezett” döntésként.

6. lépés – Hibás kapukonfiguráció szimulálása

Most próbáld ki, mi történik, ha a kapu túl megengedő. Készíts másolatot, és módosítsd a másolatban a küszöbértéket:

cp release_gate.py release_gate_bad.py
sed -i 's/critical_threshold=9.0/critical_threshold=10.0/' release_gate_bad.py
python3 release_gate_bad.py vulns_critical.json
echo $?

Várható kimenet: a kapu engedélyez (0), mert a CVSS 9,8 nem éri el a 10,0 küszöböt. Ez a rossz konfiguráció a valóságban katasztrófához vezethet, mert a kritikus sebezhetőség átcsúszik. A jó release_gate.py és a vulns_critical.json változatlan marad, ezért a két kapu összehasonlítható.

7. lépés – A hibakódok és a tesztmátrix dokumentálása

Eset Bemenet Kilépési kód Jelentés
Engedélyezett vulns_safe.json 0 nincs kritikus blokkoló
Tiszta scan vulns_clean.json ("vulnerabilities": []) 0 sikeres scan, nincs találat
Policy-blokk vulns_critical.json 1 kritikus sebezhetőség
Érvénytelen séma vulns_invalid.json, vulns_empty.json 2 severity/CVSS ellentmondás vagy hiányzó mező
Scanner-hiba vulns_scanner_failed.json 2 a scanner nem futott sikeresen

A labor akkor teljes, ha a kritikus, az ártalmatlan és a hibás bemenet külön fixture, és a 0, 1, 2 kódok dokumentáltan elválnak. A CI-ben ugyanezt a mátrixot kell futtatni; a hibás bemenet 2 kódja is blokkolja a pipeline-t, de a naplóban megkülönböztethető a policy-döntéstől.

Visszaállítás

A labor után töröld a létrehozott fájlokat, vagy hagyd a munkakönyvtárat további gyakorláshoz. Ha konténert használtál, állítsd le és távolítsd el a docker rm -f paranccsal, de ebben a laborban nem volt szükség konténerre. A helyi fájlok törlése:

cd ~
rm -rf ~/cyber-labor/cch08/

Mit tanultunk?

A labor megmutatta, hogy a kiadási kapu lényege a döntési logika. Ugyanaz a sebezhetőség-jelentés más eredményre vezethet a küszöbérték beállításától függően. A kritikus küszöb túl magasra állítása gyakorlatilag kikapcsolja a kaput, míg a megfelelően beállított kapu blokkol. A laborban a kilépési kód a kapu kimenete, amelyet a CI/CD rendszer felhasznál a pipeline leállítására vagy továbbengedésére. A sémaellenőrzés és a scanner/build azonosítók ellenőrzése nélkül a kapu üres JSON-ra vagy hibás jelentésre is tévesen dönthet; ezért a 2 hibakód külön kategória.

Hogyan védjük ki a hibás kapukonfigurációt?

Védekezésképpen a kapu szabályait verziózottan kell kezelni, és a küszöbértékeket felülvizsgálat mellett szabad csak módosítani. A szabályok változásáról riasztást kell küldeni, a pipeline definícióját pedig aláírt commitokkal kell védeni. A laborban tapasztalt hiba elkerülhető automatikus tesztekkel, amelyek a kapu policy-ját is tesztelik: például egy ismert kritikus sebezhetőségnek blokkolnia kell, egy ismert közepesnek pedig át kell engednie. A bemeneti séma, a numerikus tartomány, a scanner sikere és a vizsgált build azonosítója külön ellenőrizendő; a hiányzó vagy hibás bemenet 2 kóddal, ne csendes engedélyezéssel végződjön. Az OPA-szabályokat opa test-tel, a YAML-t CI Lint-tel, a pipeline-t pedig szándékosan hibás és sikeres fixture-rel is tesztelni kell.

9.4.6 Összefoglalás és önellenőrző kérdés

A kiadási kapu a biztonságos SDLC kritikus eleme: az automatizált ellenőrzés gyors és következetes döntést hoz, az emberi jóváhagyás pedig az üzleti kontextust viszi be. A két réteg együttesen csökkenti annak kockázatát, hogy egy sebezhetőség észrevétlenül eljusson a termelésbe. A kapu támadható, ezért a szabályokat, naplókat és bizonyítékokat ugyanolyan gonddal kell kezelni, mint magát a termékkódot. A részletesebb ellátási lánc védelmét a 10. fejezet tárgyalja.

Önellenőrző kérdés: tételezzük fel, hogy a SAST-jelentés 5 kritikus és 2 magas súlyosságú sebezhetőséget mutat. A kapu jelenlegi szabálya szerint csak akkor blokkol, ha a kritikus találatok száma meghaladja a 10-et. Miért veszélyes ez a beállítás? Milyen lépéseket tennél a kapu megerősítésére, és hogyan dokumentálnád a döntést?

Elvárt válasz: veszélyes, mert az 5 kritikus találat (sőt akár 10) is átjut: a kapu gyakorlatilag ki van kapcsolva (vö. a 6. laborlépés hibás küszöbével). Erősítés: a szabály critical_vulns > 0 legyen, a magas találatokra külön küszöb (például > 3) vonatkozzon; a policy-változás kötelező biztonsági jóváhagyással, opa test-tel és ismert kritikus fixture-rel fusson. Dokumentálás: a release recordban a kapu döntése, a policy verziója/commitja, a találatok listája, az esetleges kivétel indoklása, felelőse és lejárata, valamint a jóváhagyó neve és időpontja.
