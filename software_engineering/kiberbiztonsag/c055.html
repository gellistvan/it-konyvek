15.3 Artefaktum- és deployment-integritás

A Artefaktum- és deployment-integritás alfejezet célja, hogy az olvasót eljuttassa a „megírtam a kódot és lefutott a pipeline” gondolkodásmódtól a „bizonyítani tudom, hogy pontosan azt telepítem, amit megépítettem” szintre. Az előző, Pipeline secret és runner biztonság jelű egységben megtanultuk, hogyan védjük a pipeline titkait és futási idejű környezetét. Most arra fókuszálunk, hogy mi történik a pipeline kimenetével.

A modern szoftverellátási láncban a támadók célja gyakran nem a forráskód vagy a futó pipeline közvetlen feltörése, hanem az, hogy a buildelési folyamat után, a telepítési folyamat előtt kicseréljenek egy artefaktumot. Ha a deployment rendszer nem ellenőrzi az artefaktum hitelességét, a támadó saját, rosszindulatú kódját juttathatja el a produkciós környezetbe anélkül, hogy a forráskódhoz valaha hozzáférne.

Ebben a fejezetben három kulcsfontosságú védelmi pillért vezetünk be:

  1. Aláírás: Kriptográfiai bizonyíték arra, hogy az artefaktumot az arra jogosult fél hozta létre.
  2. Provenance: Hitelesített metaadat, amely leírja, hogy az artefaktum milyen forrásból, milyen környezetben és milyen folyamattal készült.
  3. Deployment-kapu: Automatizált ellenőrzés, amely megtagadja a telepítést, ha az aláírás vagy a provenance érvénytelen.

15.3.1 1. Alapfogalmak: Aláírás, Provenance, Deployment-kapu

15.3.1.1 1.1 Mi az az Artefaktum?

Mielőtt az integritásról beszélnénk, definiáljuk az alanyt, azaz az artefaktumot. A CI/CD gyakorlatban az artefaktum bármilyen, a pipeline által előállított, verziózott bináris vagy csomag:

  • Konténer image (pl. OCI, Docker)
  • Futtatható bináris (pl. Go, C, Rust lefordított állománya)
  • Függőségi csomag (pl. Python wheel, Java JAR, npm tarball)
  • Helm chart, Terraform modul vagy egyéb telepítési leíró

Az integritás kérdése itt az: a telepítés pillanatában használt bájtok pontosan megegyeznek-e a buildelés pillanatában létrehozott bájtokkal?

15.3.1.2 1.2 Az Aláírás

Az aláírás aszimmetrikus kulcsú kriptográfiai művelet, nem titkosítás. A privát kulccsal egy aláírás-sémát (például RSA-PSS, ECDSA vagy Ed25519) futtatunk; a publikus kulcs csak az ellenőrzésre szolgál, és a publikus kulcsból nem lehet érvényes aláírást készíteni. A hash nem „titkosított lenyomat”, hanem az aláírás-séma bemenete: a gyakorlatban (például ECDSA-nál) az aszimmetrikus műveletet nem a teljes artefaktumon, hanem annak rögzített méretű kriptográfiai lenyomatán végezzük, mert a művelet költséges; az Ed25519 és az RSA-PSS a hash-elést a sémán belül végzi.

Legyen a teljes artefaktum egy MM üzenet. Az aláírás létrehozásához nem az MM-en végzünk titkosítást, hanem annak hash-értékét számítjuk ki:

h=H(M) h = H(M)

ahol HH egy kriptográfiai hash-függvény (pl. SHA-256). Ezután a buildrendszer a privát kulccsal (KprivK_{priv}) létrehozza az aláírást a hash felett:

S=Sign(Kpriv,h) S = \mathrm{Sign}(K_{priv}, h)

Az ellenőrzés során a védő oldal újraszámolja a hash-t, és a publikus kulccsal (KpubK_{pub}) ellenőrzi az aláírást:

Verify(Kpub,H(M′),S)=?true \mathrm{Verify}(K_{pub}, H(M'), S) \overset{?}{=} \mathrm{true}

A Verify nem „visszafejtés”: a publikus kulcsú művelet csak azt ellenőrzi, hogy az aláírás az adott kulcshoz és az adott üzenethez tartozik-e. Ha M′≠MM' \neq M (azaz valaki egyetlen bájtot is megváltoztatott), a hash nem egyezik, és az ellenőrzés hamis eredményt ad. A gyakorlatban ezt nem kézzel végezzük, hanem olyan eszközökkel, mint a Cosign (a Sigstore projekt része), amely natívan kezeli az OCI image-ek és blobok aláírását.

15.3.1.3 1.3 A Provenance

Az aláírás önmagában csak azt bizonyítja, hogy valaki, aki birtokolja a privát kulcsot, jóváhagyta az artefaktumot. De nem bizonyítja, hogy a jó buildelési folyamat hozta létre. Mi van, ha a támadó feltöri a privát kulcsot, és aláírja a saját rosszindulatú binárisát?

A provenance (származás, eredetigazolás) választ ad erre. A provenance egy hitelesített állítás (attestation), amely összeköti az artefaktumot a buildelési környezettel. A legismertebb keretrendszer erre a SLSA (Supply-chain Levels for Software Artifacts, „salsa”).

Egy SLSA-kompatibilis provenance dokumentum legalább a következőket tartalmazza: - Subject: Az artefaktum neve és digest-je (hash-e). - BuildDefinition: A build típusa (buildType), a külső paraméterek (pl. forrás URI, commit, ref) és a feloldott függőségek (resolvedDependencies). - RunDetails: A builder azonosítója és a futás metaadatai (pl. invocationId, kezdés és befejezés).

Példa egy in-toto Statement v1 és SLSA provenance v1 sémájú, egyszerűsített állításra (a <...> helyőrzőket valós, 64, illetve 40 hexadecimális karakteres értékre kell cserélni):

{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [
    {
      "name": "terrasecure/app",
      "digest": { "sha256": "<64 hex sha256>" }
    }
  ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://example.invalid/buildtypes/github-actions@v1",
      "externalParameters": {
        "source": {
          "uri": "git+https://git.example.invalid/terrasecure/app",
          "digest": { "gitCommit": "<40 hex commit>" },
          "ref": "refs/heads/main"
        }
      },
      "resolvedDependencies": [
        {
          "uri": "git+https://git.example.invalid/terrasecure/app",
          "digest": { "gitCommit": "<40 hex commit>" }
        }
      ]
    },
    "runDetails": {
      "builder": { "id": "https://github.com/actions/runner" },
      "metadata": {
        "invocationId": "https://example.invalid/invocations/12345",
        "startedOn": "2026-01-01T00:00:00Z",
        "finishedOn": "2026-01-01T00:05:00Z"
      }
    }
  }
}

A _type és a predicateType együtt rögzíti az állítás sémájának verzióját: itt in-toto Statement v1 és SLSA provenance v1. A régi Statement/v0.1 és provenance/v0.2 formátum nem keverendő a v1-gyel, és a használt verziót a laborjegyzőkönyvben is fel kell tüntetni. A subject.digest.sha256 értékének ugyanannak a digestnek kell lennie, amelyet a deployment telepít; a buildDefinition a build bemeneteit és a forrás commitját, a runDetails a buildert és a futás azonosítóját írja le.

A provenance fontos tulajdonsága, hogy azt is aláírják. Így a védő nemcsak azt látja, hogy az artefaktum aláírt, hanem azt is, hogy melyik folyamat írta alá. Az aláírás azonban csak akkor bizonyít sokat, ha a kapu az aláíró identitását és a subject digestjét is ellenőrzi.

15.3.1.4 1.4 A Deployment-kapu

A deployment-kapu (vagy release gate) egy olyan automatizált ellenőrzési pont a CI/CD rendszerben, amely blokkolja a továbblépést, amíg bizonyos feltételek nem teljesülnek.

Míg a buildelés (compile) és a tesztelés a funkcionális helyességet ellenőrzi, a deployment-kapu a biztonsági követelményeket kényszeríti ki. A kapu tipikus szabályai: 1. Az artefaktumot a megbízható kulcstartóban lévő publikus kulccsal azonosított privát kulcs írta alá. 2. A provenance aláírójának identitása (OIDC issuer, workflow, repository és ág) megegyezik az elvárt buildelési identitással; a builder és a forrás commit is az elvárt érték. 3. A provenance subject digestje megegyezik azzal a digesttel, amelyet a deployment ténylegesen telepíteni fog. 4. A sérülékenység-szkenner (pl. Trivy, Grype) nem talált blokkoló (HIGH/CRITICAL) hibát az image-ben. 5. Az SBOM (Software Bill of Materials) létezik és generálódott; az SBOM azonban nem provenance, és önmagában nem teljesíti a provenance-követelményt.

Az alábbi ábra egy láncra rakja az aláírást, a provenance-t és a kapu öt szabályát, és megjelöli a 2. szakasz négy támadási pontját, valamint azt az ellenőrzést, amelyik az egyes támadásokat megfogja.

15.3.2 2. Tipikus támadási minták és ellenpéldák

15.3.2.1 2.1 Támadási minta: Az aláírás nélküli artefaktum

Támadó szemszög: A támadó kompromittálja a deployment rendszert vagy a registry-t, és kicseréli a terrasecure/app:latest image-et. Mivel a deployment script egyszerűen letölti a latest taget, és a kapu nem ellenőrzi az aláírást, a támadó kódja azonnal élesbe kerül.

Védekezés: A telepítést végző runtime sosem a latest taget húzza le, hanem egy pontos digest-et (@sha256:...) használ. A kapu pedig megtagadja a telepítést, ha a cosign verify-blob vagy cosign verify parancs nem 0-ás kilépési kóddal tér vissza.

15.3.2.2 2.2 Támadási minta: Provenance-hamisítás

Támadó szemszög: A támadó feltöri a buildagentet, vagy kihasznál egy sebezhetőséget a build sablonban. Nem az artefaktumot írja alá rossz kulccsal, hanem meghamisítja a provenance-t: azt állítja, hogy a build a hivatalos forrásból származik, miközben valójában egy rosszindulatú forkból jött.

Védekezés: A provenance-t a buildrendszer nem interaktív módon, a build során automatikusan generálja és írja alá, nem pedig a fejlesztő a laptopján. Az automatikus aláírás azonban csak akkor jelent külön kontrollt, ha a buildkód nem tud tetszőleges, megbízhatónak látszó állítást gyártani: a build platformnak izoláltnak kell lennie, és az aláírási identitást a build kódjától elkülönítve kell védenie. A deployment-kapuban nem elég az issuer egyezését nézni: ellenőrizni kell az OIDC issuer, a workflow, a repository és az ág együttes identitását, a builder azonosítóját, valamint azt, hogy a provenance subject digestje megegyezik a telepítendő digesttel. A Rekor bejegyzés támogatja a bizonyítást, de nem helyettesíti ezt a policy-ellenőrzést.

15.3.2.3 2.3 Támadási minta: A kulcs exfiltrálása

Támadó szemszög: A build pipeline be van állítva aláírásra, de a privát kulcsot a fejlesztő a repository-ba commitolja, vagy egy nem védett CI változóban tárolja (ld. előző fejezet hibái). A támadó egy egyszerű env dump segítségével megszerzi a kulcsot, és a saját gépéről ír alá.

Védekezés: A privát kulcs soha nem hagyja el a védett hardveres környezetet (HSM, KMS). Ha szoftveres kulcsot használunk (pl. helyi laborban), a kulcsot erős jelszóval védjük, és a CI rendszeren kívül, elkülönített tárolóban tartjuk. A modern gyakorlat a keyless signing (kulcs nélküli aláírás): a build során rövid életű, efemer kulcs generálódik, és a hosszú távú identitást az OIDC token (pl. GitHub Actions token) biztosítja. A Rekor nyilvános naplóba az aláírás, a rövid életű tanúsítvány és a bejegyzés metaadatai kerülnek, a privát kulcs nem. Ez csökkenti a hosszú távú kulcslopás kockázatát, de nem szünteti meg a buildkörnyezet kompromittálását: a futás idején a folyamat memóriájában létező efemer kulcsot egy ott futó támadó elérheti, ezért a build izolációja és az OIDC-identitás szigorú ellenőrzése továbbra is kötelező.

15.3.2.4 2.4 Veszélyes konfiguráció: A || true kapu

Támadó szemszög: A fejlesztőcsapat siet, mert az aláírás néha hibát dob. A pipeline-t így módosítják: cosign verify ... || true. Ez azt jelenti, hogy a parancs hibája esetén is folytatódik a deployment.

Védekezés: A kapunak fail-closed (hiba esetén záró) üzemmódban kell működnie. Nincs || true, nincs allow_failure: true. Ha az ellenőrzés nem tudja egyértelműen igazolni az integritást, a folyamat leáll, és riasztást küld.

15.3.3 3. Gyakorlati minta: Aláírt artefaktum és deployment-ellenőrzés

Ebben a laborban a TerraSecure környezetét szimuláljuk. A cél egy Python alkalmazás buildelése, aláírása, majd a deployment-kapu szimulációja.

15.3.3.1 3.1 Labor előkészítése

A labor izolált, saját könyvtárban dolgozunk. Használjuk a Cosign eszközt, amely natívan képes blobok és konténerek aláírására. A labor a Cosign 2.x sorozat dokumentált sign-blob/verify-blob felületét használja. A telepítésnél rögzítsd a cosign version kimenetét, és a jegyzőkönyvben tüntesd fel a verziót. A bemutatott ág offline: saját kulcspárral, --key és --signature opciókkal dolgozik, és nem igényel Rekort, OIDC-t vagy hálózati kapcsolatot. A keyless/Rekor ág külön, hálózatot igénylő labor; a kettőt ne keverd.

# 0. Az eszköz és a verzió ellenőrzése (a telepítés külön lépés)
command -v cosign >/dev/null 2>&1 || { echo "HIBA: a cosign nincs telepítve; telepítsd a hivatalos Sigstore kiadásból."; exit 1; }
cosign version

# 1. Labor könyvtár létrehozása
mkdir -p ~/cyber-labor/c055 && cd ~/cyber-labor/c055

# 2. Kulcspár generálása (a jelszó helyi, véletlen érték; nem valódi titok)
COSIGN_PASSWORD="$(python3 -c 'import secrets; print(secrets.token_urlsafe(24))')"
test -n "$COSIGN_PASSWORD" || { echo "HIBA: a jelszógenerálás sikertelen"; exit 1; }
printf '%s\n' "$COSIGN_PASSWORD" > cosign-password.txt
chmod 600 cosign-password.txt
# Ez szimulálja a "védő" által birtokolt privát kulcsot
COSIGN_PASSWORD="$COSIGN_PASSWORD" cosign generate-key-pair
# Kimenet: cosign.key (privát), cosign.pub (publikus)

15.3.3.2 3.2 Az artefaktum és az aláírás létrehozása

Hozzunk létre egy egyszerű szöveges artefaktumot, amely a TerraSecure egy konfigurációs fájlját szimulálja.

# Az artefaktum (build kimenet)
echo "TerraSecure App Config - v1.0 - biztonságos" > artifact.txt

# A privát kulccsal aláírjuk a fájlt.
# A 'cosign sign-blob' a fájl bájtjait hash-eli, és azokra készít aláírást;
# nincs szükség külön .sha256 fájlra.
# A COSIGN_PASSWORD környezeti változó lehetővé teszi a nem interaktív futtatást.
COSIGN_PASSWORD="$(cat cosign-password.txt)"
test -n "$COSIGN_PASSWORD" || { echo "HIBA: hiányzó cosign-password.txt"; exit 1; }
export COSIGN_PASSWORD
cosign sign-blob --key cosign.key --tlog-upload=false --output-signature artifact.sig artifact.txt
unset COSIGN_PASSWORD

Most van egy artifact.txt nevű fájlunk és egy artifact.sig aláírásunk. Az aláírás a artifact.txt bájtjaihoz kötődik: a cosign verify-blob a megadott fájlt hash-eli, és az aláírást ehhez a hash-hez ellenőrzi. A sha256sum önmagában csak integritás-ellenőrzés, nem aláírás; ha külön demonstrációban használjuk, a .sha256 fájlt hitelesített csatornán kell átadni, mert önmagában nem bizonyítja a származást.

15.3.3.3 3.3 A Deployment-kapu szimulálása (Sikeres eset)

A deployment-kapu egy egyszerű shell script, amely exit 1-gyel tér vissza, ha az integritás nem igazolható.

deploy_gate.sh:

#!/bin/bash
set -e  # Bármilyen nem nulla kilépési kód esetén leáll

echo "[GATE] Artefaktum integritás ellenőrzése..."

# Fail-closed: a szükséges eszköz és fájlok hiánya is hiba
command -v cosign >/dev/null 2>&1 || { echo "[GATE] HIBA: a cosign nincs telepítve."; exit 1; }
test -r cosign.pub || { echo "[GATE] HIBA: a cosign.pub nem olvasható."; exit 1; }
test -r artifact.sig || { echo "[GATE] HIBA: az artifact.sig nem olvasható."; exit 1; }
test -r artifact.txt || { echo "[GATE] HIBA: az artifact.txt nem olvasható."; exit 1; }

# A Cosign a megadott fájl bájtjait ellenőrzi az aláíráshoz kötve.
cosign verify-blob \
  --key cosign.pub \
  --signature artifact.sig \
  --insecure-ignore-tlog=true \
  artifact.txt

echo "[GATE] Az aláírás érvényes. Továbbítás a deploymenthez..."
# Itt történne a kubectl apply / scp / deploy parancs
exit 0

A kapu feltétele a cosign verify-blob nem nulla kilépési kódja, nem egy konkrét hibaüzenet. A pontos szöveg a Cosign verziójától függ. A Cosign 2.x alapból a nyilvános Rekor-naplóba tölt fel, és onnan ellenőriz. Az offline laborban ezt a --tlog-upload=false, illetve az --insecure-ignore-tlog=true kapcsoló kapcsolja ki; élesben ez gyengítés (a naplózás a Rekor feladata), ezért ilyen kapuban csak a laborban szabad használni. A kapcsolók nevét és alapértékét a rögzített verzió cosign sign-blob --help / cosign verify-blob --help kimenetével kell igazolni (nem futtatva, laborban ellenőrizendő). A kulcsalapú ellenőrzés így nem igényel OIDC-t.

Futtassuk a kaput:

chmod +x deploy_gate.sh
./deploy_gate.sh
# Kimenet: Verified OK
# [GATE] Az aláírás érvényes...

15.3.3.4 3.4 Támadási szimuláció: Illetéktelen módosítás

Most lépjünk a támadó szerepébe. Tegyük fel, hogy a támadó hozzáfér a hálózathoz, és módosítja a konfigurációs fájlt egy rosszindulatú bejegyzéssel.

# A támadó módosítja az artefaktumot
echo "TerraSecure App Config - v1.0 - ROSSZINDULATÚ BEJEGYZÉS" >> artifact.txt

# A védő újra futtatja a meglévő deployment-kaput
./deploy_gate.sh

Várt kimenet (vázlat, a pontos szöveg a Cosign verziójától függ):

[GATE] Artefaktum integritás ellenőrzése...
Error: verifying blob artifact.txt: signature does not match

A pontos hibaüzenet a Cosign verziójától függ; a kapu szempontjából az a döntő, hogy a cosign verify-blob nem nulla kilépési kóddal tér vissza. A script a set -e miatt azonnal leáll, és nem hajtja végre a deployment parancsot.

Ugyanezt a viselkedést kell kapni akkor is, ha a publikus kulcs rossz, az artifact.sig hiányzik vagy csonkolt, illetve ha az aláírást egy másik fájlhoz készítették. Ezeket a negatív eseteket külön futtasd, és mindegyiknél a nem nulla kilépési kódot rögzítsd a jegyzőkönyvben.

15.3.3.5 3.5 Mit tanultunk?

A laborban azt láttuk, hogy egyetlen bájt megváltoztatása elegendő ahhoz, hogy a kriptográfiai hash megváltozzon. Mivel a támadó nem fér hozzá a cosign.key privát kulcshoz, nem tud új, érvényes aláírást generálni. A deployment-kapu ezért meghiúsul. A rendszer biztonsága a privát kulcs titkosságán és a kapu integritásán múlik.

15.3.3.6 3.6 Hogyan védjük ki?

Az ilyen típusú támadás ellen a legerősebb védelem a keyless signing (OIDC + Sigstore) használata. Ebben az esetben a privát kulcs nem létezik hosszú távon; a build során generálódik, és a folyamat memóriájában él. A Rekor nyilvános naplóba az aláírás, a rövid életű tanúsítvány és a metaadatok kerülnek, a privát kulcs nem. Így a támadó nem tud hosszú távú kulcsot lopni, de a buildkörnyezet futás közbeni kompromittálása továbbra is kockázat: az efemer kulcsot a futó folyamatból meg lehet szerezni. Ezért a build izolációja, az OIDC-identitás ellenőrzése és a provenance digestjének ellenőrzése elengedhetetlen.

Ezen kívül a kaput is védeni kell: a cosign.pub kulcsot ne a repository-ból töltsük le, hanem egy védett, read-only konfigurációból, hogy a támadó ne cserélhesse ki a publikus kulcsot a sajátjára.

15.3.4 4. Provenance alkalmazása és ellenőrzése

A pusztán aláírt artefaktum nem ad választ arra a kérdésre: ki írta alá, és miért bízhatunk meg benne? Ha a szervezet nagy, több csapat is rendelkezhet aláírási joggal.

15.3.4.1 4.1 SLSA szintek a gyakorlatban

A gyakorlatban a TerraSecure csapata a következő lépésekben növeli az érettségét (a SLSA Build szintek a slsa.dev specifikációja szerint; a hivatkozott verziót és az URL-t az aktuális slsa.dev oldalról kell igazolni): - SLSA Build L1: A build automatikusan generál provenance-t, amely leírja a build bemeneteit és a buildert. Az L1 a provenance meglétéről szól; az SBOM önmagában nem provenance, és nem teljesíti ezt a szintet. - SLSA Build L2: Hosztolt buildplatform generál aláírt provenance-t, és a platform védi az aláírási identitást. A kapu a provenance aláírójának identitását és a subject digestjét ellenőrzi. - SLSA Build L3: Megerősített buildplatform: a buildek izoláltak, az aláírási kulcsok a build kódja elől el vannak zárva, és a provenance ellenáll a build során történő manipulációnak. Ez nem egy sudo szabály kérdése, hanem a platform biztonsági tulajdonsága.

15.3.4.2 4.2 A kapu kiterjesztése: Policy ellenőrzés

A modern rendszerekben a deployment-kapu nem egy egyszerű script, hanem egy policy motor. Erre dokumentált lehetőségek például az OPA, a Kyverno, a Sigstore policy-controller Kubernetes admission controller. A kapunak legalább a következőket kell ellenőriznie:

Pszeudokód (nem futtatható Rego); a valós szabályt OPA 1.x if szintaxissal vagy CUE-ban kell megírni. GitHub Actions esetén a tanúsítvány-subject valós formátuma https://github.com/<org>/<repo>/.github/workflows/<file>@<ref>.

allow := true {
    # 1. Az aláírás érvényes
    signature.valid == true
    # 2. A tanúsítvány/állítás identitása az elvárt workflow-hoz és repository-hoz tartozik
    cert.issuer == "https://token.actions.githubusercontent.com"
    cert.subject == "https://github.com/<org>/<repo>/.github/workflows/release.yml@refs/heads/main"   # <org>/<repo>: helyőrző
    # 3. A builder és a forrás az elvárt érték
    provenance.runDetails.builder.id == "https://github.com/actions/runner"
    provenance.buildDefinition.externalParameters.source.uri == "git+https://git.example.invalid/terrasecure/app"
    provenance.buildDefinition.externalParameters.source.digest.gitCommit == expected_commit
    # 4. Ugyanazt a digestet ellenőrizzük, mint amit telepítünk
    some s in provenance.subject
    s.digest.sha256 == deployment.digest.sha256
}

Az issuer egyezése önmagában nem elég: a támadó egy másik repositoryból vagy workflow-ból is kaphat érvényes OIDC tokent ugyanattól az issuertől. Ezért kell a workflow, a repository, az ág, a builder és a forrás commit együttes ellenőrzése, valamint annak biztosítása, hogy a provenance subject digestje pontosan a telepítendő digest legyen.

Ez azért fontos, mert a hibás konfiguráció itt a leggyakoribb: a fejlesztők gyakran csak az aláírást ellenőrzik, de a provenance identitását és digestjét nem. Ha a támadó megszerzi a privát kulcsot, az aláírás átmehet, de a provenance identitás- és digest-ellenőrzése elbukik, feltéve, hogy a build platform az aláírási identitást valóban elkülöníti a build kódjától.

15.3.5 5. Ellenőrzés, naplózás és dokumentáció

Az integritás nem csak technikai, hanem szervezeti kérdés is. Ehhez tartozik a naplózás:

  • Immutable naplózás: Amikor artefaktumot aláírunk, az aláírási eseményt egy írásvédett (append-only) naplóba írjuk. Ez a Sigstore esetében a Rekor (Transparency Log). Ez biztosítja, hogy a támadó ne tudjon utólag törölni egy aláírást.
  • Deployment napló: Minden deployment kapu tranzakciót naplózni kell. json { "timestamp": "2024-05-01T12:00:00Z", "artifact": "terrasecure/app", "digest": "sha256:3f6a...", "gate_results": { "signature_check": "PASS", "provenance_check": "PASS", "vuln_scan": "PASS" }, "decision": "DEPLOY", "environment": "production", "actor": "ci-pipeline" }
  • Dokumentáció: A csapatnak rendelkeznie kell egy SECURITY.md fájllal, amely leírja, hogy hol vannak az aláíró kulcsok, mi a teendő kompromittálódás esetén, és hogyan kell új kulcsot kiadni.

15.3.6 6. Védelmi döntések és indoklás (Best Practices)

A fejezet zárásaként foglaljuk össze, hogyan döntünk a védelmi mechanizmusokról:

  1. Használjunk digest-et, ne csak taget. A latest tag mutálódhat. A sha256:... digest viszont megváltoztathatatlan hivatkozás. A kapu csak digestre hivatkozó deploymentet engedjen.
  2. Különítsük el a kulcsokat. A buildeléshez használt aláíró kulcs soha ne legyen a deployment rendszerben. Ha a deployment rendszert feltörik, a támadó ne tudjon új artefaktumot aláírni.
  3. Fail-Closed. Ha a kapu nem tudja elérni a publikus kulcsot vagy a sebezhetőség-szkennert, leáll, nem továbbenged. A rendelkezésre állás átmeneti csökkenése elfogadhatóbb kockázat, mint egy sérült artefaktum telepítése.
  4. Keyless signing bevezetése. Kerüljük a hosszú távú privát kulcsok tárolását. Használjunk OIDC-alapú, rövid élettartamú aláírásokat, ahol a bizalom gyökere a buildrendszer identitása (pl. GitHub Actions repo neve, workflow refje), nem a fájlban tárolt kulcs. A kapu a tanúsítvány identitását és a provenance digestjét is ellenőrizze, ne csak az issuer egyezését.

15.3.7 7. Önellenőrző kérdések

  1. Fogalom: Mi a különbség az artefaktum aláírása és a provenance között? Miért nem elegendő pusztán az aláírás?
  2. Alkalmazás: A deploy_gate.sh scriptben azt láttuk, hogy a cosign verify-blob nem nulla kilépési kóddal tér vissza, ha hibás a fájl. Mi történne, ha a script elején nem lenne set -e?
  3. Hibakeresés: Egy fejlesztő panaszkodik, hogy a deployment elakadt. A cosign verify (image) naplójában az áll: Error: no matching signatures. Mi a legvalószínűbb oka? (a) A kapu más publikus kulccsal vagy identitással ellenőriz, mint amellyel aláírtak, (b) a telepítendő digesthez nem készült aláírás (például újraépített image), (c) túl sok a sebezhetőség az image-ben.
  4. Védelmi indoklás: Miért jobb a keyless signing (OIDC) a hagyományos privát kulcs tárolásánál egy nyilvános CI/CD szolgáltatás (például GitHub Actions) esetén?
  5. Ellenőrzés: Egy artefaktum érvényes aláírással és érvényes issuerrel rendelkező provenance-t kapott, de a provenance egy másik repository commitjára és más digestre hivatkozik. Miért kell a kapunak elutasítania, és mely mezőket kell összevetni?

Válaszvázlat. (1) Az aláírás az artefaktum integritását és a kulcs birtokosát igazolja, a provenance azt, hogy ki, mivel és miből építette; kulcs birtokában hamis build is aláírható. (2) A set -e nélkül a hibás ellenőrzés után a szkript tovább futna, és végrehajtaná a telepítést. (3) (a) vagy (b); a (c) nem aláírási hiba. (4) Nincs hosszú életű kulcs, amit el lehetne lopni; az identitást a buildrendszer és a tanúsítvány köti. (5) Mert a provenance nem a telepítendő artefaktumra vonatkozik; a subject digestet, a forrás URI-t és commitot, a builder-azonosítót és a tanúsítvány-subjectet kell összevetni.

Ez a fejezet megadta az alapot ahhoz, hogy a következő, Policy as code és ellenőrzés egységben az Policy as code fogalmával mélyítsük el a deployment-kapukat, ahol a scriptek helyett deklaratív, verziózott szabályrendszerekkel fogjuk leírni a biztonsági elvárásainkat.
