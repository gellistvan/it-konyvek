24.4 Audit és compliance

Az audit célja nem a büntetés, hanem annak bizonyítása, hogy a rendszer a vállalt biztonsági követelményeknek megfelelően működik, és az eltérések kimutatása, mielőtt azok támadási lehetőséggé válnának. A compliance (megfelelőség) ennek a külső elvárásokra – törvény, szabvány, ügyfélszerződés, belső politika – való alkalmazása. Az üzemeltetési biztonságban az audit három pilléren áll: bizonyíték (evidence), kontrollok (controls) és jelentés (report). Ebben az alfejezetben ezt a három fogalmat járjuk körbe, majd egy izolált laborban auditcsomagot állítunk össze.

24.4.1 Bizonyíték: mi számít megbízható adatnak?

A bizonyíték olyan rögzített, visszakereshető adat, amely alátámasztja, hogy egy kontroll létezik és az adott időpontban működött. Nem elég azt mondani, hogy „a tűzfal be van kapcsolva”; be kell mutatni a konfigurációt, a futó folyamatot, a naplóbejegyzést vagy a teszt kimenetét.

A jó bizonyíték tulajdonságai:

  • Hitelesség: a forrás ismert, és a gyűjtés folyamata dokumentált.
  • Integritás: a bizonyítékot a gyűjtés után nem módosították. Ezt tipikusan kriptográfiai hash (SHA-256) és azonnali, védett tárolás biztosítja.
  • Időbeliség: a bizonyítékhoz időbélyeg tartozik. A rendszerek óráját NTP-vel kell szinkronizálni, különben a naplóbejegyzések nem összehasonlíthatók.
  • Reprezentativitás: egyetlen minta ritkán elegendő. Ha például a jelszópolicy-t vizsgáljuk, több felhasználói fiók beállítását kell ellenőrizni, nem csak egyet.

A bizonyítékok tipikus formái:

  • konfigurációs fájlok másolatai (/etc/ssh/sshd_config, webszerver site-definíció);
  • parancsok kimenetei (systemctl status, iptables -L, docker inspect, ps aux);
  • naplóbejegyzések (/var/log/auth.log, journalctl, docker logs);
  • automata ellenőrző eszközök jelentései (CIS-CAT, OpenSCAP, saját szkript);
  • képernyőmentések vagy terminálfelvételek, ha más módszer nem áll rendelkezésre;
  • interjúk és dokumentum-ellenőrzések jegyzőkönyvei.

A bizonyítékgyűjtés során a kimeneteket ne csak a képernyőn nézzük, hanem mentsük el fájlba, és azonnal számítsunk hash-t a későbbi manipuláció kizárására. Az alábbi collect-evidence.sh minta ezt automatizálja:

#!/usr/bin/env bash
# Audit bizonyítékgyűjtő – kizárólag a megnevezett laborcélra.
set -euo pipefail

TARGET="${TARGET:?Add meg a laborcél konténernevet, például: TARGET=audit-target}"
LAB_NETWORK="${LAB_NETWORK:-terra-audit}"
TARGET_IP="${TARGET_IP:-192.0.2.10}"
CLIENT_IMAGE="${CLIENT_IMAGE:-curlimages/curl:8.10.1}"
RUN_ID="$(date -u +%Y%m%dT%H%M%SZ)-$$"
EVIDENCE_DIR="evidence-${TARGET}-${RUN_ID}"

umask 077
mkdir -p "$EVIDENCE_DIR"
printf '%s\n' "$EVIDENCE_DIR" > latest-evidence.txt

STATUS_LOG="$EVIDENCE_DIR/status.tsv"
printf 'check\tstate\texit_code\tstarted_utc\tfinished_utc\n' > "$STATUS_LOG"

TARGET_ID="$(docker inspect -f '{{.Id}}' "$TARGET")"
TARGET_IMAGE="$(docker inspect -f '{{.Config.Image}}' "$TARGET")"
TARGET_DIGEST="$(docker image inspect -f '{{index .RepoDigests 0}}' "$TARGET_IMAGE" 2>/dev/null || printf 'n/a')"
CLIENT_DIGEST="$(docker image inspect -f '{{index .RepoDigests 0}}' "$CLIENT_IMAGE" 2>/dev/null || printf 'n/a')"
NETWORK_INTERNAL="$(docker network inspect -f '{{.Internal}}' "$LAB_NETWORK")"
PLATFORM="$(docker version -f '{{.Server.Os}}/{{.Server.Arch}}')"

if [ "$NETWORK_INTERNAL" != "true" ]; then
    echo "A(z) $LAB_NETWORK hálózat nem internal; a labor csak zárt hálózaton futtatható." >&2
    exit 2
fi
if [ "$TARGET_DIGEST" = "n/a" ] || [ "$CLIENT_DIGEST" = "n/a" ]; then
    echo "Hiányzó image digest; a cél- és kliensimage-et rögzített digesttel kell használni." >&2
    exit 2
fi

{
    printf 'collected_at_utc=%s\n' "$(date -u --iso-8601=seconds)"
    printf 'target=%s\n' "$TARGET"
    printf 'target_id=%s\n' "$TARGET_ID"
    printf 'target_image=%s\n' "$TARGET_IMAGE"
    printf 'target_digest=%s\n' "$TARGET_DIGEST"
    printf 'client_image=%s\n' "$CLIENT_IMAGE"
    printf 'client_digest=%s\n' "$CLIENT_DIGEST"
    printf 'platform=%s\n' "$PLATFORM"
    printf 'lab_network=%s\n' "$LAB_NETWORK"
    printf 'lab_network_internal=%s\n' "$NETWORK_INTERNAL"
} > "$EVIDENCE_DIR/target.txt"

record() {
    local name="$1" mode="$2"
    shift 2
    local out="$EVIDENCE_DIR/${name}.txt"
    local start finish rc state
    start="$(date -u --iso-8601=seconds)"
    set +e
    case "$mode" in
        exec)   docker exec "$TARGET" "$@" >"$out" 2>&1 ;;
        logs)   docker logs --tail 50 "$TARGET" >"$out" 2>&1 ;;
        client) docker run --rm --network "$LAB_NETWORK" "$CLIENT_IMAGE" "$@" >"$out" 2>&1 ;;
        *)      printf 'ismeretlen mod: %s\n' "$mode" >"$out"; false ;;
    esac
    rc=$?
    set -e
    finish="$(date -u --iso-8601=seconds)"
    if [ "$rc" -ne 0 ]; then
        state="failed"
    elif [ -s "$out" ]; then
        state="success"
    else
        state="empty"
    fi
    printf '%s\t%s\t%s\t%s\t%s\n' "$name" "$state" "$rc" "$start" "$finish" >> "$STATUS_LOG"
}

record nginx-config       exec nginx -T
record nginx-version      exec nginx -v
record nginx-process      exec sh -c 'ps aux 2>/dev/null || cat /proc/1/cmdline'
record listening-ports    exec sh -c 'ss -tlnp 2>/dev/null || netstat -tlnp 2>/dev/null || cat /proc/net/tcp'
record nginx-logs         logs
record synthetic-response client -sS -D - -o /dev/null "http://${TARGET_IP}/"

date -u --iso-8601=seconds > "$EVIDENCE_DIR/TIMESTAMP"
(
    cd "$EVIDENCE_DIR"
    sha256sum -- *.txt status.tsv TIMESTAMP > SHA256SUMS
)

echo "Bizonyítékok: $EVIDENCE_DIR"
echo "Státuszok: $STATUS_LOG"
echo "Integritás: ( cd $EVIDENCE_DIR && sha256sum -c SHA256SUMS )"

A record minden ellenőrzésnél rögzíti a kezdő és záró időt, az eredeti kilépési kódot, valamint a success, empty vagy failed állapotot. Így egy hibás parancs nem rejtőzik el (nem nyeli el például egy || true): a hibás, az üres és a sikeres ellenőrzés a status.tsv-ben megkülönböztethető. A gyűjtés kizárólag a megnevezett TARGET konténerre irányul; a gazdagép SSH-konfigurációját, auth-naplóját, Docker- és hálózati adatait nem gyűjti. Az nginx access.log az image-ben stdout-ra mutathat, ezért a naplót véges docker logs --tail 50 gyűjti, nem tail.

A SHA256SUMS és a bizonyítékfájlok ugyanazzal a hozzáféréssel írhatók, ezért a hash integritást bizonyít, de hitelességet nem: nem igazolja, ki készítette a csomagot. A teljes, adatminimalizált csomagot írásvédett, külön fiókkal védett tárolóba kell tenni, és külső horgonnyal vagy védett archiválással (például WORM-tároló, RFC 3161 időbélyeg, szervezeti jegykezelő) kell hitelesíteni.

Ellenpélda. Egy auditor csak annyit ír a jegyzőkönyvbe: „A naplózás be van kapcsolva”. Ez nem bizonyíték, mert nem mutatja meg, melyik naplóforrás, milyen szinten, hová küldi az adatot, és milyen retention vonatkozik rá. A megfelelő bizonyíték például a rsyslog.conf releváns sorai, a systemctl status rsyslog kimenete és egy tesztüzenet megjelenése a központi gyűjtőben.

24.4.2 Kontrollok: mit vizsgálunk?

A kontroll olyan intézkedés, amely a kockázatot csökkenti. Három fő típusa:

  • Preventív (megelőző): megakadályozza a nemkívánatos eseményt. Például tűzfal, jelszókomplexitási szabály, fájlrendszer-jogosultság, bemeneti validálás.
  • Detektív (felderítő): észleli a nemkívánatos eseményt, ha az már bekövetkezett vagy folyamatban van. Például IDS, naplófigyelés, fájlintegritás-ellenőrzés (Tripwire, AIDE), SIEM-riasztás.
  • Korrektív (helyreállító): csökkenti a bekövetkezett esemény hatását, és visszaállítja a normál működést. Például backup-restore, patch-kezelés, incidenskezelési terv, kényszerített jelszóváltoztatás.

Az audit során minden kontrollnál a következőket vizsgáljuk:

  1. Létezik-e a kontroll? Van-e dokumentált szabály, konfiguráció, technikai megvalósítás?
  2. Megfelelően van-e konfigurálva? A tűzfal nemcsak fut, hanem a szabályrendszere ténylegesen korlátoz is.
  3. Működik-e éles környezetben? Egy teszt vagy naplóbejegyzés igazolja a hatását.
  4. Van-e felelőse és felülvizsgálati ciklusa? A kontrollokat időről időre újra kell értékelni.

A keretrendszerek ezt a vizsgálatot rendezik átfogó katalógusba. A NIST Cybersecurity Framework 2.0 (2024) hat funkcióra bontja a kockázati tevékenységeket: Govern, Identify, Protect, Detect, Respond, Recover. A Govern a 2.0-ban új funkció; a korábbi 1.1-es változat öt funkciót (Identify, Protect, Detect, Respond, Recover) használt, ezért a fejezetben mindig meg kell jelölni, melyik verzióra hivatkozunk. A CIS Controls (a v8-as verzió az elterjedt) 18 kontrollcsoportot ad, például „Inventory and Control of Enterprise Assets” vagy „Account Management”. A CIS Benchmarks konkrét technikai konfigurációs ajánlásokat tartalmaz operációs rendszerekre, felhőszolgáltatásokra, konténerekre. Az ISO/IEC 27001:2022 A melléklete pedig irányítási és technikai kontrollokat sorol fel. A megfelelőség soha nem egyenlő a biztonsággal; egy szabvány teljesítése szükséges lehet, de nem elegendő.

Példa kontrollmátrix. A TerraSecure auditjához a következő részletet rögzíthetjük:

Tipikus hiba. A kontroll létezik a dokumentációban, de a rendszer nem érvényesíti. Például a jelszópolicy szerint a jelszó legalább 12 karakter, de a Linux PAM-konfiguráció csak 8-at kényszerít ki. Az audit feladata, hogy a dokumentum és a tényleges konfiguráció közötti eltérést megtalálja. Ezért a bizonyítékgyűjtés során mindig a futó rendszerből dolgozunk, nem pedig a leírásból.

24.4.3 Jelentés: hogyan kommunikáljuk az eredményt?

Az auditjelentés célja, hogy a vezetőség és a műszaki csapat számára döntési alapot adjon. Nem elég felsorolni a hibákat; rangsorolni kell őket a kockázat alapján, és kezelhető javaslatokat kell adni.

A jelentés tipikus felépítése:

  1. Vezetői összefoglaló: egy-két bekezdés a legfontosabb megállapításokról, az összesített kockázati szintről és a javasolt prioritásokról.
  2. Hatókör és kritériumok: mely rendszereket, adatokat, hálózati szegmenseket vizsgáltuk, és milyen szabvány vagy belső politika szerint.
  3. Módszertan: milyen eszközökkel, mintavétellel, teszteléssel gyűjtöttünk bizonyítékot, és ki vett részt.
  4. Megállapítások: minden eltéréshez tartozik leírás, bizonyíték-hivatkozás, kockázatértékelés és javaslat.
  5. Jóváhagyás és következő lépések: ki felelős a javításokért, milyen határidővel, és mikor lesz újraellenőrzés.
  6. Függelékek: bizonyítékfájlok, naplórészletek, konfigurációs kivonatok, hash-összesítők.

A kockázatot a könyv egészében használt R=L×IR = L \times I képlettel fejezzük ki, ahol LL a bekövetkezés valószínűsége (likelihood), II pedig a hatás (impact), mindkettő 1–5 skálán. A RR érték így 1 és 25 között van. A CVSS-pontszám technikai súlyosságot mér, de az üzleti kockázat ennél több: figyelembe veszi az adatérzékenységet, a szolgáltatás kritikusságát és a támadási felületet. Példa: egy közepes CVSS-értékű, de nyilvánosan kihasználható sebezhetőség egy bevételkritikus webes alkalmazásban L=4L=4, I=5I=5, így R=20R=20, ami azonnali beavatkozást igényel. Ugyanaz a CVSS-érték egy belső, izolált tesztrendszeren L=1L=1, I=2I=2, R=2R=2, ami elfogadható kockázat lehet.

A megállapítások minősítése (TerraSecure audit-skála, v1):

  • Kritikus: azonnali, üzletleállást vagy adatvesztést okozhat; R≥20R \ge 20.
  • Magas: jelentős kockázat, rövid határidőn belül javítandó; R=15–19R = 15\text{–}19.
  • Közepes: korlátozott hatás, de kezelni kell; R=8–14R = 8\text{–}14.
  • Alacsony: kisebb eltérés, hosszú távon javítható; R≤7R \le 7.
  • Info: észrevétel, amely nem hiba, de jó gyakorlat.

Ez a beosztás a TerraSecure audit helyi küszöbrendszere, amely nem azonos a Kockázatbecslés és kockázatkezelés által bevezetett sávokkal (ott Alacsony 1–4, Közepes 5–9, Magas 10–16, Kritikus 17–25). A két fejezet számait nem szabad közvetlenül összevetni: aki a Kockázatbecslés és kockázatkezelés skáláját használja, annak az itteni példákat is azzal a beosztással kell újraszámolnia. A jelentésben rögzíteni kell, melyik skálát alkalmaztuk, és a küszöböket a vizsgálat megkezdése előtt írásban kell rögzíteni.

Minta megállapítás a TerraSecure jelentésből:

## MEG-004 – Hiányzó rate limiting a /api/login végponton

- **Státusz:** Eltérés
- **Kontroll:** TS-AC-04 (sikertelen bejelentkezések korlátozása; minta: NIST SP 800-53 AC-7)
- **Bizonyíték:** evidence/auth-log-tail.txt, 42 sikertelen POST /api/login 60 másodperc alatt ugyanazon IP-címről.
- **Kockázat:** L=4 (automatizált brute-force valószínű), I=4 (fiókátvétel lehetséges), R=16 (magas)
- **Javaslat:** Vezessünk be IP- és fiókalapú rate limitinget (pl. 5 próbálkozás / 15 perc / fiók), exponenciális késleltetéssel, és naplózzuk a zárlatokat.
- **Felelős:** alkalmazásbiztonsági csapat
- **Határidő:** 2025-03-31 (ellenőrzendő dátum)

A javaslat legyen SMART: specifikus, mérhető, az adott környezetben elérhető, releváns, timeboxolt – azaz határidőhöz kötött. A fenti példa ilyen: pontosan megmondja, mit, milyen paraméterrel, ki és mikorra.

24.4.4 Tipikus támadási és védelmi minták, valamint ellenpéldák

Az audit során a támadói gondolkodásmód segít felismerni, mely hiányosságok válnak kihasználhatóvá. Néhány gyakori minta:

1. Hiányzó vagy nem központosított naplózás

  • Támadási minta: a támadó megváltoztatja a jelszót, majd törli a helyi auth.log-ot. Ha nincs központi, immutábilis naplótárolás, a nyomok elvesznek.
  • Védelmi döntés: központi naplógyűjtés (pl. rsyslog vagy Fluent Bit) TLS-en, céloldali WORM (write-once-read-many) tárolás, naplóforrások óra-szinkronizálása.
  • Audit ellenőrzés: a forráson ss -tnp state established '( dport = :6514 )' (élő kapcsolat a gyűjtő felé), a konfigurációban a TLS-beállítás (DefaultNetstreamDriver="gtls" vagy az omfwd StreamDriver="gtls", StreamDriverMode="1", StreamDriverAuthMode="x509/name"); a gyűjtőn ss -tlnp '( sport = :6514 )'; végül tesztüzenet (logger -t audit-test <egyedi azonosító>) megjelenése a gyűjtőben. A @@ csak a TCP-továbbítást jelzi, a TLS-t nem. (Szintaxis laborban ellenőrizendő.)

2. Gyenge hozzáférés-vezérlés a mentésekhez

  • Támadási minta: a backup könyvtár laza jogosultságú (chmod 777), így bármely felhasználó kiolvashatja az adatbázis dumpot.
  • Védelmi döntés: a mentéseket dedikált, legkisebb jogosultságú fiók írja, a könyvtárat 0700, a mentési fájlokat 0600 jogosultsággal tároljuk, és a hozzáférést naplózzuk.
  • Audit ellenőrzés: ls -la /backup, getfacl, a mentési folyamat naplóinak áttekintése.

3. Nem frissített, sebezhető szoftververzió

  • Támadási minta: a konténer egy elavult nginx:1.23.4 image-et futtat. Az elavult verzió önmagában kontrollhiány, de konkrét CVE-t csak ellenőrzött verzió-, csomag- és konfigurációadat alapján szabad hozzárendelni. A példában ezért vagy egy ellenőrzött CVE/KEV-bejegyzés szerepel forrással, vagy egyértelműen fiktív LAB-CVE-FIXTURE-001 fixture; a kettő nem keverhető.
  • Védelmi döntés: automatikus függőség- és image-frissítés a CI/CD-ben, SBOM-alapú sebezhetőségkeresés, deployment-kapu érvényesítése, rögzített digest és ellenőrzött baseline.
  • Audit ellenőrzés: docker inspect audit-target --format '{{.Config.Image}}', majd docker image inspect <image> --format '{{index .RepoDigests 0}}'; a digestet és a platformot a lab-baseline.txt-hoz kell hasonlítani. A tag önmagában nem igazolja a futó tartalmat. A server_tokens eltérését a futó HTTP-válasz Server: fejléce és a docker exec audit-target nginx -T kimenete együtt igazolja.

4. Kényelmi konfiguráció, amely megkerüli a biztonsági kontrollt

  • Támadási minta: a tűzfalon az „all open” szabály van elöl, mert a fejlesztőknek gyorsan kellett a hozzáférést biztosítani; a szigorúbb szabályok utána következnek, így soha nem érvényesülnek.
  • Védelmi döntés: a tűzfalszabályokat alapértelmezés szerint tiltó (deny-by-default) logikával kell felépíteni, és a szabályrendszert verziókezelten felülvizsgálni.
  • Audit ellenőrzés: iptables -L -v -n vagy nft list ruleset, és a szabályok sorrendjének elemzése. A tűzfal futásának puszta ténye nem elég.

5. Hiányzó MFA a rendszergazdai hozzáféréseknél

  • Támadási minta: a TerraSecure adminisztrátori panelje csak felhasználónévvel és jelszóval védett. Egy kiszivárgott jelszó azonnal teljes hozzáférést ad.
  • Védelmi döntés: kötelező MFA (TOTP, FIDO2/passkeys) minden privilegizált fiókhoz, kockázatalapú fiókzárlat, naplózott MFA-események.
  • Audit ellenőrzés: az IdP konfigurációjának áttekintése, valamint a bejelentkezési naplókban az MFA-módszer és -eredmény metaadatának igazolása (például auth_method=fido2, mfa_result=success, mfa_result=failed). Az OTP-, illetve bearer-token értékét vagy a hitelesítő adatot a napló nem rögzítheti; a napló csak a módszerre és az eredményre utaló metaadatot tartalmazza.

Az ellenpéldák közös tanulsága: a kontroll neve nem helyettesíti a működését. Az audit során mindig a futó konfigurációt, a naplókat és a tesztkimeneteket vizsgáljuk.

24.4.5 Ellenőrzési, naplózási és dokumentációs szempontok

Az audit maga is egy folyamat, amelynek nyomait rögzíteni kell. A következő szempontok garantálják, hogy az eredmény később is reprodukálható és védhető legyen.

Audit trail. Minden adminisztratív műveletet – felhasználó létrehozás, jogosultságmódosítás, konfigurációváltoztatás – naplózni kell, és a naplót a változtatást végző személyhez kell kötni. Linuxon az auditd vagy a systemd-journald megfelelő szabályokkal képes erre. Az ausearch rekordtípus, eredmény és időtartomány szerint kérdezi le az auditnaplót:

# A ma éjfél óta rögzített sikertelen bejelentkezések és hitelesítések
# (24 órához: -ts "$(date -d '24 hours ago' '+%x %T')")
ausearch -m USER_LOGIN,USER_AUTH --success no -ts today -i

Naplózás. A hitelesítési naplókat, a tűzfal-eseményeket, az alkalmazásnaplókat és a webes hozzáférési naplókat központi gyűjtőbe kell irányítani. A gyűjtőben a naplófájloknak írásvédettnek (immutábilisnak) kell lenniük, a retention időt pedig a jogszabályi vagy belső előírásokhoz kell igazítani. A logrotate önmagában nem elég, mert a régi fájlok felülírhatók. A központi tároló biztosíthat például object lock funkciót (WORM). A TerraSecure laborban a docker logs mint helyi bizonyíték szerepel, de valós környezetben ez nem helyettesíti a központi gyűjtőt.

Dokumentáció verziózása. A konfigurációs fájlokat, a kontrollmátrixot és a jelentést verziókezelt tárolóban (Git) kell vezetni. Minden változtatáshoz tartozzon commit üzenet, jóváhagyó és dátum. Ezzel a „mi változott az előző audit óta?” kérdés megválaszolható:

git log --oneline --since="2024-01-01" -- audit/controls.yaml

A controls.yaml például a kontrollok leírását és a bizonyítékok elérési útját tartalmazhatja:

controls:
  - id: TS-AC-01
    source: "TerraSecure SSH-politika 4.2; minta: NIST SP 800-53 IA-2"
    description: SSH csak kulcsalapú hitelesítéssel
    type: preventive
    evidence: evidence/sshd-config.txt
    status: passed
  - id: TS-CM-01
    source: "TerraSecure konténer-baseline 1.0; minta: CIS Docker Benchmark"
    description: A konténer a rögzített, ellenőrzött baseline szerinti (legutóbbi stabil) javítóverziót futtatja
    type: preventive
    evidence: evidence/docker-inspect.txt
    status: failed
    finding: MEG-002

Automatizálás. Az audit ne csak évente egyszer, manuálisan történjen. A kontrollokat folyamatosan, kódként (compliance as code) is ellenőrizhetjük. Eszközök: OpenSCAP a Linux hardeninghez, CIS-CAT a CIS Benchmarks ellenőrzéséhez, Chef InSpec a futó rendszerek kódként leírt ellenőrzéséhez, Terraform/IaC-hez pedig például Checkov vagy a Pulumi CrossGuard szabálycsomagjai (az eszközneveket kiadás előtt a projektoldalakon ellenőrizni kell). A lényeg, hogy a bizonyítékgyűjtés ismételhető legyen, és a friss rendszerállapotról ne csak szubjektív benyomásunk legyen.

24.4.6 Labor: auditcsomag összeállítása a TerraSecure laboron

Cél: egy izolált, helyi konténer auditálása, bizonyítékok gyűjtése, kontrollmátrix rögzítése és egy rövid jelentés elkészítése a megadott sablon szerint.

Hatókör. Kizárólag a labor saját konténere, a 192.0.2.0/24 dokumentációs hálózaton. Valós rendszer elleni támadás nem megengedett. A labor audit tevékenység, nem támadás; a talált eltéréseket csak a laboron belül értelmezzük.

Előkészítés. Hozd létre a munkakönyvtárat, majd indítsd el a cél konténert izolált hálózaton:

mkdir -p ~/cyber-labor/c092
cd ~/cyber-labor/c092

# Zárt hálózat: az --internal megszünteti a kimenő internet-hozzáférést.
docker network create --internal --subnet=192.0.2.0/24 terra-audit
docker network inspect -f '{{.Internal}}' terra-audit
# Elvárt kimenet: true

# Rögzített verziók és digestek.
docker pull nginx:1.23.4
docker pull curlimages/curl:8.10.1
TARGET_IMAGE="$(docker image inspect nginx:1.23.4 --format '{{index .RepoDigests 0}}')"
CLIENT_IMAGE="$(docker image inspect curlimages/curl:8.10.1 --format '{{index .RepoDigests 0}}')"
printf 'platform=%s\ntarget_image=%s\nclient_image=%s\n' \
  "$(docker version --format '{{.Server.Os}}/{{.Server.Arch}}')" \
  "$TARGET_IMAGE" "$CLIENT_IMAGE" > lab-baseline.txt

# Célkonténer indítása a rögzített digesttel.
docker run -d --name audit-target \
  --network terra-audit \
  --ip 192.0.2.10 \
  "$TARGET_IMAGE"

A nginx:1.23.4 verzió szándékosan régebbi, hogy legyen mit találni, de a régi verzió önmagában még nem bizonyít konkrét CVE-t. A controls.yaml-ban vagy egy ellenőrzött CVE/KEV-bejegyzést kell megadni a verzióhoz és a csomaghoz, vagy egyértelműen fiktív LAB-CVE-FIXTURE-001 fixture-t kell használni. A „legutóbbi stabil” verziót a labor napján, a registryben kell ellenőrizni; a rögzített digestet a target.txt és a lab-baseline.txt őrzi.

1. lépés: Bizonyítékgyűjtés. Mentsd el a collect-evidence.sh scriptet a fenti tartalommal, módosítsd a docker parancsokat a konténerre, és futtasd:

chmod +x collect-evidence.sh
TARGET=audit-target LAB_NETWORK=terra-audit ./collect-evidence.sh

A script a latest-evidence.txt fájlba írja az egyedi gyűjtési könyvtár nevét, és csak a audit-target konténer adatait csomagolja. A status.tsv külön jelöli a sikeres, üres és hibás ellenőrzéseket.

2. lépés: Ellenőrzés a konténerben és szintetikus klienssel. Nyiss interaktív shell-t a konténerben, és nézd meg a jellemző konfigurációkat:

docker exec -it audit-target sh
# A futó folyamatok és a nyitott portok
cat /proc/1/cmdline; echo
cat /proc/net/tcp
# A webszerver tényleges konfigurációja
nginx -T 2>&1 | grep -n 'server_tokens' || echo 'server_tokens nincs explicit beallitva (default: on)'
cat /etc/nginx/nginx.conf
cat /etc/nginx/conf.d/default.conf
# Naplók: az access.log stdout-ra mutathat, ezért a gazdagépen véges docker logs kell
exit
docker logs --tail 20 audit-target

A futó HTTP-választ külön, szintetikus klienskonténerből ellenőrizd, hogy a host és a cél ne szennyezze a mérést:

CLIENT_IMAGE="$(docker image inspect curlimages/curl:8.10.1 --format '{{index .RepoDigests 0}}')"
docker run --rm --network terra-audit "$CLIENT_IMAGE" \
  -sS -D - -o /dev/null http://192.0.2.10/

A Server: fejléc és a nginx -T együtt mutatja, hogy a server_tokens beállítás ténylegesen érvényesül-e. Ha a server_tokens sor hiányzik, az alapértelmezés on, ezért a hiány is eltérés. A kézi nginx-config.txt ne maradjon a munkakönyvtár gyökerében: a collect-evidence.sh a bizonyítékokat az egyedi gyűjtési könyvtárba menti.

3. lépés: Kontrollok definiálása és értékelése. Hozz létre egy controls.yaml fájlt a fenti minta alapján, de a TerraSecure laborra szabva. Legalább öt kontrollt rögzíts, például:

  • TS-CM-01: a konténer a rögzített, ellenőrzött baseline szerinti (legutóbbi stabil) javítóverziót futtatja; típus: preventív (forrás: TerraSecure konténer-baseline 1.0).
  • TS-AU-01: a hozzáférési naplók elérhetők és tartalmaznak időbélyeget (forrás: TerraSecure naplózási szabvány 2.1).
  • TS-AC-03: a webszerver nem szivárogtat ki verzióinformációt (server_tokens off); forrás: TerraSecure webszerver-hardening 3.4.
  • TS-AC-04: van-e bármilyen rate limiting a / végponton; forrás: TerraSecure API-védelmi szabályzat 2.2.
  • TS-OP-01: létezik-e egészségügyi végpont a konténerhez; forrás: TerraSecure üzemeltetési szabvány 1.2.

A TS- előtaggal jelölt azonosítók helyiek: nem a NIST SP 800-53 vagy a CIS azonosítói, hanem a TerraSecure saját kontrollkatalógusának elemei, amelyek a Forrás mezőben megadott szabályzathoz és mintához kötődnek.

A docker inspect és a konfigurációs fájlok alapján állapítsd meg a státuszt (passed / failed / partial), és minden eltéréshez írj egy megállapítást.

4. lépés: Jelentés összeállítása. Készíts report.md fájlt az alábbi fejezetekkel: vezetői összefoglaló, hatókör, módszertan, megállapítások (legalább 3 eltérés, mindegyikhez kockázatértékelés és SMART javaslat), összefoglaló táblázat. Használd a fenti mintát. Például a hiányzó server_tokens off megállapítás:

## MEG-001 – Webszerver verzióinformáció kiszivárogtatása

- **Státusz:** Eltérés
- **Kontroll:** TS-AC-03 (webszerver-verzióinformáció visszatartása; forrás: TerraSecure webszerver-hardening 3.4)
- **Bizonyíték:** `evidence-audit-target-<RUN_ID>/nginx-config.txt`: a `nginx -T` kimenetében nincs `server_tokens` direktíva (alapérték: `on`); `synthetic-response.txt`: `Server: nginx/<verzió>` fejléc.
- **Kockázat:** L=3 (könnyen kihasználható felderítés), I=2 (csak támadási előkészület), R=6 (alacsony)
- **Javaslat:** állítsd be a `server_tokens off;` direktívát, és ellenőrizd a hibaválaszok fejléceit.
- **Felelős:** üzemeltető csapat
- **Határidő:** 2025-04-15 (ellenőrizendő)

5. lépés: Auditcsomag becsomagolása. A bizonyíték könyvtárat, a controls.yaml és a report.md fájlokat tömörítsd. Csak az aktuális, egyedi gyűjtési könyvtárat csomagold, ne wildcarddal az összes korábbi futást:

EVIDENCE_DIR="$(cat latest-evidence.txt)"
test -d "$EVIDENCE_DIR"
tar -czvf "audit-csomag-$(basename "$EVIDENCE_DIR").tar.gz" \
  "$EVIDENCE_DIR" controls.yaml report.md
sha256sum "audit-csomag-$(basename "$EVIDENCE_DIR").tar.gz" \
  > "audit-csomag-$(basename "$EVIDENCE_DIR").sha256"

A csomag hash-e csak integritást bizonyít; a hitelességhez a csomagot írásvédett, külön fiókkal védett tárba kell helyezni, és külső időbélyeggel vagy védett archiválással kell hitelesíteni.

Visszaállítás. A labor után távolítsd el a konténert és a hálózatot:

docker stop audit-target
docker rm audit-target
docker network rm terra-audit

A ~/cyber-labor/c092/ könyvtárban lévő bizonyítékokat megtarthatod, ha a későbbi újraellenőrzéshez kell, de ne tartalmazhatnak valós hitelesítő adatokat.

Átadandó eredmény. Az audit-csomag-<gyűjtés>.tar.gz és a hozzá tartozó .sha256 fájl. A csomagnak tartalmaznia kell az aktuális bizonyítékfájlokat, a status.tsv-t, a hash-összesítőt, a kontrollmátrixot és a jelentést; korábbi futások bizonyítékai nem kerülhetnek bele.

24.4.7 Mit tanultunk?

Az audit három pillére a bizonyíték, a kontroll és a jelentés. A bizonyíték csak akkor ér valamit, ha hiteles, integritását hash védi, időbélyeggel rendelkezik, és reprezentatív. A kontrollokat típusuk szerint (preventív, detektív, korrektív) és működésük szerint vizsgáljuk, nem a nevük alapján. A jelentés pedig üzleti döntést támogat, ezért kockázatértékelést és SMART javaslatokat kell tartalmaznia.

A laborban megtanultuk, hogyan kell izolált környezetben bizonyítékot gyűjteni, kontrollokat értékelni és egy átlátható auditcsomagot összeállítani. A cél nem a hibák puszta felsorolása, hanem a javítási út kijelölése.

24.4.8 Hogyan védjük ki?

  1. Automatizált, folyamatos audit: ne csak évente egyszer ellenőrizzünk; a kontrollokat kódként, CI/CD-ben is futtassuk.
  2. Központi, immutábilis naplózás: a bizonyítékokhoz nem elég a helyi napló; azokat védett, központi tárolóba kell irányítani.
  3. Konfiguráció-verziózás és változáskezelés: minden módosítás legyen nyomon követhető és jóváhagyott.
  4. A dokumentáció és a futó rendszer összhangja: rendszeresen egyeztessük a leírt policy-t a tényleges konfigurációval.
  5. Kockázatarányos javítás: a jelentésben rangsorolt eltéréseket a R=L×IR=L\times I alapján kezeljük, nem egyenlő erőfeszítéssel.

24.4.9 Önellenőrző kérdés

Sorolj fel három olyan tipikus auditmegállapítást, amelyet egy webes alkalmazásnál gyakran észlelnek, és mindegyikhez indokold meg, miért jelent kockázatot, valamint milyen védelmi kontrollt javasolnál. A válaszodban használd a preventív / detektív / korrektív felosztást, és a R=L×IR = L \times I képletet legalább egy példán.

24.4.10 Források és ellenőrzési igény

A fejezet a NIST Cybersecurity Framework 2.0 (2024), a CIS Controls v8 és CIS Benchmarks, az ISO/IEC 27001:2022, valamint a SANS incidenskezelési és auditálási anyagai által leírt alapelvekre épít. A konkrét verziószámokat, a Docker image-ek aktuális tag-jeit és a példában szereplő dátumokat a felhasználás időpontjában ellenőrizni kell. A hivatkozott szabványok és keretrendszerek a hivatalos kiadói oldalakon érhetők el; a fejezet a felsorolt követelményeket a hivatkozott verziók szerint tárgyalja, a linkek tartalmát a felhasználás előtt friss állapotukban kell ellenőrizni. A laborban talált eltérések kizárólag a TerraSecure izolált környezetére vonatkoznak, és nem használhatók valós rendszer elleni támadáshoz.
