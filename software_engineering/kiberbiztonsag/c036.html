10.4 Reprodukálható build és CI/CD

Az ellátási lánc biztonságában a forráskód és a futtatott szoftver közötti kapcsolatot csak akkor tudjuk bizonyítani, ha a build folyamata megbízható, és a keletkező műtermék (artifact) bit-azonos úton reprodukálható. Az előző alfejezetben megismertük a SLSA keretrendszert, a Sigstore aláírási eszközöket és az in-toto láncbiztosítékokat. Ebben a fejezetben a gyakorlati megvalósításra koncentrálunk: hogyan tehetjük a buildet determinisztikussá, hogyan védjük a CI/CD pipeline integritását, és hogyan ellenőrizzük az eredményt naplókkal és bizonyítékokkal.

10.4.1 Determinisztikus build

A determinisztikus (más néven reprodukálható) build azt jelenti, hogy adott forráskód, adott függőségi halmaz, adott build környezet és adott build parancs esetén a kimenet minden futtatáskor bit-azonos. Ha egy build nem determinisztikus, a műtermékbe bekerülhetnek időbélyegek, véletlen azonosítók, fájlrendszer-elérési utak vagy más környezeti zaj. Ilyenkor két, látszólag azonos forrásból készült bináris eltérő hash-t ad, ami lehetetlenné teszi a független ellenőrzést: nem tudjuk eldönteni, hogy a különbség a forráskód módosításából vagy egyszerűen a build környezet zajából adódik.

A reprodukálhatóság a verifiable build alapja. Ha a védő képes ugyanazt a buildet futtatni, és a kapott hash megegyezik a kiadott műtermék hash-ével, akkor nagy biztonsággal kijelenthető, hogy a műtermék a deklarált forrásból készült. Ez a tulajdonság különösen fontos nyílt forráskódú projekteknél, ahol bárki ellenőrizheti a kiadott binárist. A gyakorlatban a teljes bit-azonosság elérése nehéz, de a főbb nem-determinisztikus elemek kiküszöbölésével a legtöbb projekt közelíthet hozzá.

10.4.2 A determinisztikus build elérésének eszközei

  1. Rögzített függőségi verziók és hash-ek. A függőségi fájlban ne csak verziószámot adjunk meg, hanem a csomag tartalomhash-ét is. Pythonban a pip install --require-hashes opcióval ellenőrizhetjük a letöltött csomagok SHA256 hash-ét. JavaScriptben a package-lock.json, Go-ban a go.sum hasonló szerepet tölt be.

    A --require-hashes a teljes tranzitív függőségi gráf pontos verzióját és hash-ét megköveteli, ezért a requirements.txt-t géppel kell előállítani, nem kézzel. Például:

    # A közvetlen függőségek a requirements.in fájlban vannak.
pip-compile --generate-hashes --output-file requirements.txt requirements.in

    A kapott fájl minden csomagra (Flask és annak összes tranzitív függősége) tartalmaz == verziót és --hash=sha256:... bejegyzést. A laborhoz a wheelhouse-t előre töltsd le a célplatformra:

    pip download --only-binary=:all: --dest wheelhouse \
  --platform manylinux2014_x86_64 --python-version 3.12 \
  --implementation cp --abi cp312 -r requirements.txt

    A pip install a wheelhouse könyvtárból, hálózat nélkül telepít:

    pip install --no-index --find-links=wheelhouse --require-hashes -r requirements.txt

  2. Időbélyeg és nem-determinisztikus elemek kikapcsolása. A build eszközök gyakran beágyazzák az aktuális időt, a felhasználónevet vagy a munkakönyvtár elérési útját. A következő környezeti változók segítenek:

    • SOURCE_DATE_EPOCH: a build időbélyegének rögzített értéke (Unix idő), amelyet a fordítók, tömörítők és csomagolók használnak.
    • ZERO_AR_DATE: az ar archívum (pl. statikus könyvtárak) dátumát nullára állítja.
    • PYTHONDONTWRITEBYTECODE=1: megakadályozza, hogy a Python a .pyc fájlokat a build során generálja, amelyek időbélyeget és elérési utat tartalmazhatnak.
    • Docker BuildKit esetén a --build-arg SOURCE_DATE_EPOCH=... átadható; a rétegekben lévő fájlok időbélyegét az exporter rewrite-timestamp=true beállítása igazítja hozzá.

  3. Rögzített build környezet. A konténer alaprétegének (base image) pontos digest-je határozza meg a build környezetet. Ha a Dockerfile FROM python:3.12-slim@sha256:... formát használ, a base image tartalma rögzített, így a build nem függ a változó latest tagtől.

  4. Reprodukálható build eszközök. Egyes eszközök, mint a Docker BuildKit, a buildah vagy a ko (Go konténerekhez) eleve támogatják a determinisztikus kimenetet, ha megfelelően konfiguráljuk őket. A build lépéseit mindig szkriptben rögzítsük, ne interaktívan adjuk ki.

Példa egy determinisztikus Python webalkalmazás Dockerfile-jára. A base image-et nem helyőrző digesttel, hanem a labor elején feloldott, valódi digesttel kell átadni:

# syntax=docker/dockerfile:1
ARG PYTHON_IMAGE
FROM ${PYTHON_IMAGE} AS builder
ARG SOURCE_DATE_EPOCH
ENV PYTHONDONTWRITEBYTECODE=1 \
    ZERO_AR_DATE=1 \
    SOURCE_DATE_EPOCH=${SOURCE_DATE_EPOCH}
WORKDIR /app
COPY requirements.txt ./
COPY wheelhouse /wheelhouse
RUN pip install --no-cache-dir --no-index --find-links=/wheelhouse \
    --require-hashes -r requirements.txt
COPY app.py ./
# A futtató réteg külön, hogy a build függőségek ne kerüljenek a végleges image-be
FROM ${PYTHON_IMAGE}
ARG SOURCE_DATE_EPOCH
ENV PYTHONDONTWRITEBYTECODE=1 \
    SOURCE_DATE_EPOCH=${SOURCE_DATE_EPOCH}
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY app.py ./
USER 10001
CMD ["python", "app.py"]

Az ARG SOURCE_DATE_EPOCH mindkét szakaszban deklarálva van, mert egy szakaszban deklarált ARG hatóköre a szakasz végéig tart. A base image digestjét a labor elején oldd fel, és a buildnek argumentumként add át:

PYTHON_IMAGE="python:3.12-slim@$(docker buildx imagetools inspect python:3.12-slim \
  --format '{{json .Manifest.Digest}}' | tr -d '"')"
echo "$PYTHON_IMAGE"

docker buildx build \
  --no-cache \
  --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" \
  --build-arg SOURCE_DATE_EPOCH=1700000000 \
  --output type=docker,name=terra/secure-web:1.0,rewrite-timestamp=true \
  --metadata-file build1.json \
  .

A SOURCE_DATE_EPOCH build-argumentum az image-konfiguráció és a history időbélyegét rögzíti; a rétegekben lévő fájlok módosítási idejét (például a RUN pip install által létrehozott fájlokét) az exporter rewrite-timestamp=true beállítása állítja a SOURCE_DATE_EPOCH értékére (BuildKit 0.13 vagy újabb; a rögzített BuildKit-hez: docker buildx create --driver docker-container --driver-opt image=moby/buildkit:v0.<x>.<y> --use). Enélkül a két build digestje várhatóan eltér (laborban ellenőrizendő).

A két független, cache nélküli build összehasonlítása a BuildKit által rögzített manifest digest alapján történik:

docker buildx build --no-cache \
  --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" \
  --build-arg SOURCE_DATE_EPOCH=1700000000 \
  --output type=docker,name=terra/secure-web:1.0,rewrite-timestamp=true \
  --metadata-file build2.json .
python3 - <<'PYCODE'
import json
a = json.load(open("build1.json"))["containerimage.digest"]
b = json.load(open("build2.json"))["containerimage.digest"]
print(a, b, "egyezik" if a == b else "ELTÉR")
PYCODE

A --no-cache önmagában nem garantálja a bitazonos kimenetet; a rögzített base digest, a wheelhouse, a SOURCE_DATE_EPOCH, a ZERO_AR_DATE és a rögzített BuildKit-verzió együtt szükséges. Az image ID a helyi, réteghash-ekből számított azonosító, amely nem feltétlenül egyezik a registryben látott manifest digesttel; a reprodukálhatósági összehasonlítást ezért a manifest digesten vagy egy exportált OCI-artefaktumon kell végezni.

Az alábbi ábra szemlélteti, hogy a manifest digest a konfig- és a rétegdigestekből áll össze, és hogy a nem rögzített bemenetek közül melyik melyik komponenst változtatja meg. A rétegekben lévő fájlok módosítási idejét a BuildKit exporterének rewrite-timestamp beállítása igazítja a SOURCE_DATE_EPOCH értékéhez.

10.4.3 Kihívások és fokozatos bevezetés

A teljes reprodukálhatóság nem minden ökoszisztémában elérhető egy csapásra. Például a Java build eszközök (Maven, Gradle) a függőségek letöltési sorrendjétől vagy a fájlrendszer időbélyegétől függően eltérő JAR-okat hozhatnak létre. A reprodukálhatóság érdekében a következő lépéseket érdemes fokozatosan bevezetni:

  • rögzítsük a build eszköz pontos verzióját;
  • használjunk konténerizált build környezetet;
  • kapcsoljuk ki a nem-determinisztikus beállításokat;
  • dokumentáljuk a build parancsot és a környezeti változókat;
  • végezzünk rendszeres reprodukálhatósági tesztet (két build hash-ének összehasonlítása).

A nem reprodukálható build nem jelenti automatikusan, hogy a szoftver rosszindulatú, de megnöveli a támadási felületet, mert a különbségek elfedhetik a rosszindulatú módosítást.

10.4.4 Pipeline-integritás

A pipeline-integritás azt jelenti, hogy a CI/CD folyamat minden lépése megbízható: a forráskód, a build környezet, a build parancs és a műtermék nem módosítható jogosulatlanul. A pipeline maga is szoftver, és gyakran magas jogosultságokkal rendelkezik: hozzáfér a forráskódhoz, a titkokhoz, a regisztrációs adatbázishoz és a telepítési környezethez. Ezért a támadók számára vonzó célpont.

A pipeline-integritás védelme a következő rétegekből áll:

10.4.5 Forráskód-védelem

  • Branch protection: a fő ágra (pl. main) közvetlenül ne lehessen pusholni; változás csak jóváhagyott pull requesten keresztül kerülhessen be.
  • Signed commit: a fejlesztők GPG- vagy SSH-aláírással hitelesítsék a commitjaikat, így a commit szerzője ellenőrizhető.
  • Code review: legalább egy jóváhagyó, aki nem a szerző, átnézi a változást.

10.4.6 Pipeline-definíció védelme

A pipeline konfiguráció (pl. .github/workflows/*.yml vagy Jenkinsfile) ugyanolyan felülvizsgálatot igényel, mint a termékkód. A pipeline módosításait is alá kell írni, és a jogosultságokat a legkisebb szükségesre kell korlátozni. A pipeline ne tartalmazzon közvetlenül titkokat, és ne futtasson nem ellenőrzött külső szkriptet.

Példa egy minimális jogosultságú GitHub Actions workflow-ra (a pontos szintaxis ellenőrizendő):

name: build-and-sign
on:
  push:
    branches: [main]
permissions:
  contents: read
  id-token: write   # OIDC token kérése a Sigstore aláíráshoz
  packages: write   # push a GHCR-be
jobs:
  build:
    runs-on: ubuntu-24.04  # pontos verziót ellenőrizni
    steps:
      - uses: actions/checkout@<COMMIT_SHA>
        with:
          ref: ${{ github.sha }}
      - uses: docker/setup-buildx-action@<COMMIT_SHA>
      - uses: docker/login-action@<COMMIT_SHA>
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Base image digest feloldása
        run: |
          echo "PYTHON_IMAGE=python:3.12-slim@$(docker buildx imagetools inspect python:3.12-slim --format '{{json .Manifest.Digest}}' | tr -d '"')" >> "$GITHUB_ENV"
      - name: Build és push
        run: |
          docker buildx build --no-cache \
            --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" \
            --build-arg SOURCE_DATE_EPOCH=1700000000 \
            --output type=image,name=ghcr.io/<ORG>/secure-web:1.0,push=true,rewrite-timestamp=true \
            --metadata-file build.json .
          echo "DIGEST=$(python3 -c 'import json;print(json.load(open("build.json"))["containerimage.digest"])')" >> "$GITHUB_ENV"
      - name: Generate SBOM
        uses: anchore/sbom-action@<COMMIT_SHA>
        with:
          image: ghcr.io/<ORG>/secure-web@${{ env.DIGEST }}
      - uses: sigstore/cosign-installer@<COMMIT_SHA>
      - name: Sign
        run: cosign sign --yes ghcr.io/<ORG>/secure-web@${DIGEST}

A fenti példában a permissions blokk csak a szükséges jogosultságokat adja meg, a titkokat nem tároljuk a workflow-ban, az aláírás OIDC token alapján történik, és a regiszterbe pusholt image digestjét írjuk alá, nem egy mozgó taget. Egy lépésben uses és run nem szerepelhet együtt, ezért a cosign telepítése és az aláírás külön lépés. Az actionöket teljes commit-SHA-ra rögzítjük (<COMMIT_SHA> helyőrző), a workflow szintaxisát actionlint-tel ellenőrizzük; a példa szemléltető, nem futtatott.

10.4.7 Runner izoláció és titkok

  • A runner legyen ephemeral (rövid életű, minden futtatás után megsemmisül), hogy a build környezet ne szennyeződjön.
  • A lépések konténerben fussanak, így a runner fájlrendszere nem válik támadási felületté.
  • A titkokat csak a szükséges lépések kapják meg, és soha ne logoljuk őket. A titkok tárolása dedikált szolgáltatásban (pl. Vault, cloud secret manager) történjen, és a CI/CD csak rövid életű hitelesítő adatot kapjon (pl. OIDC token).
  • A cache-t (pl. Maven, npm) hitelesíteni kell, mert a cache poisoning támadás során a támadó rosszindulatú csomagot helyezhet el a megosztott cache-ben.

10.4.8 Artifact hitelesítés

A build végén a műterméket alá kell írni, és csatolni kell hozzá egy attestation (bizonyíték) dokumentumot, amely igazolja a build inputjait (forráskód hash, függőségek hash-e, build parancs, környezet). A Sigstore cosign és az in-toto eszközök lehetővé teszik az ilyen aláírt bizonyítékok létrehozását és ellenőrzését. Az aláírás nélküli műterméket a telepítési folyamatnak el kell utasítania.

A SLSA Build track szintjei (lásd 10.3.3) a pipeline-integritás fokozatait írják le: a Build L2 hosted platform által generált, aláírt provenance-t, a Build L3 megerősített, izolált build platformot és hamisíthatatlan provenance-t követel meg. A forráskód hitelessége a Source track, a független újraépítés pedig kiegészítő ellenőrzés, nem újabb Build-szint.

10.4.9 Tipikus támadási és védelmi minták, ellenpéldák

10.4.10 1. Rosszindulatú függőség befecskendezése

Támadás: A támadó létrehoz egy olyan csomagot, amelynek neve hasonlít egy népszerű belső csomagra (typosquatting), vagy kihasználja a dependency confusion támadást: a build rendszer a belső registry helyett a nyilvános registry-ből tölt le egy ugyanolyan nevű, rosszindulatú csomagot.

Védelem: - A függőségek hash-ének rögzítése (pip --require-hashes, package-lock.json, go.sum). - Belső registry használata, és a nyilvános registry elérésének korlátozása. - A függőségek rendszeres auditálása (pl. pip-audit, npm audit). - SBOM generálása, amely tartalmazza az összes függőséget és azok hash-ét.

10.4.11 2. Build környezet kompromittálása

Támadás: A támadó hozzáfér a build runnerhez, például egy rosszindulatú pull requestben elhelyezett kód kihasználásával. Ha a runner nem megfelelően izolált, a támadó ellophatja a titkokat, módosíthatja a build kimenetet, vagy későbbi build lépésekbe injektálhat kódot (cache poisoning).

Védelem: - Ephemeral, konténerizált runner használata. - Minimális jogosultságok a pipeline-ban (a fenti permissions blokk). - A pull requestekből származó kód futtatása csak korlátozott jogosultságú, ideiglenes környezetben. - A titkok megadása csak a szükséges lépéseknek, és rövid életű tokenek használata.

10.4.12 3. Artifact csere a pipeline végén

Támadás: A támadó a build után, a regisztrációs adatbázisban (pl. Docker Hub, npm registry) lecseréli a jó műterméket egy rosszindulatúra. A letöltő kliens nem tudja ellenőrizni, hogy a műtermék a hiteles buildből származik.

Védelem: - A műtermék aláírása (cosign, notary). - A letöltő oldalon az aláírás ellenőrzése. - Az attestation (SLSA provenance) csatolása, amely igazolja a build inputjait. - A registry hozzáférésének auditálása és a műtermékek megváltoztathatatlansága (immutable tag).

10.4.13 Ellenpélda: nem rögzített Docker image tag

# HIBÁS: a mozgó tag (python:3.12-slim) tartalma változhat, a build nem reprodukálható
FROM python:3.12-slim
RUN pip install flask
COPY app.py .

Miért rossz? A python:3.12-slim tag mögötti image tartalma idővel változhat, így a build kimenete nem lesz ugyanaz. A pip install flask verzió és hash-ellenőrzés nélkül fut, így a függőség is változhat. A javítás a hash-elt base image és a --require-hashes használata, ahogy fent láttuk.

10.4.14 Ellenpélda: túlzott jogosultságú pipeline

# HIBÁS: a pipeline teljes körű jogosultságot kap
permissions: write-all
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          export SECRET_TOKEN="${{ secrets.PRODUCTION_TOKEN }}"
          ./deploy.sh --production

Miért rossz? A write-all jogosultság lehetővé teszi a pipeline számára, hogy módosítsa a forráskódot, a registry-t és más erőforrásokat. A titok környezeti változóba kerül, és a deploy.sh esetleg naplózza. A javítás: minimális permissions (pl. contents: read, id-token: write), a titkokat ne exportáljuk, és a deploy lépést külön environmenthez kössük.

10.4.15 Ellenőrzési, naplózási és dokumentációs szempontok

A determinisztikus build és a pipeline-integritás csak akkor értékes, ha az eredményt ellenőrizni és naplózni tudjuk. A következő adatokat kell rögzíteni:

  • Build inputok: forráskód commit hash, függőségi hash-ek, build környezet verziószámai (pl. Docker image digest, tool verziók), build parancs.
  • Build kimenet: a műtermék hash-e (SHA256), az aláírás, az attestation tartalma, az SBOM.
  • Pipeline események: minden lépés kezdete és vége, a futtató runner azonosítója, a felhasználó, aki elindította a pipeline-t, a lépések kimeneti naplója (kivéve titkok).
  • Audit log: a naplókat integritásvédelemmel kell tárolni (pl. immutable log, mint a Rekor a Sigstore-ban), hogy utólag ne lehessen módosítani.

A dokumentáció része a reprodukálási utasítás: pontosan milyen parancsokkal, milyen környezetben lehet a buildet újra előállítani. Ez a dokumentáció akkor hasznos, ha a buildet független fél szeretné ellenőrizni.

10.4.16 Labor: Reprodukálható build teszt és CI-napló ellenőrzése

Ebben a laborban a TerraSecure fiktív projektjén keresztül gyakoroljuk a determinisztikus buildet és a pipeline napló elemzését. A labor kizárólag saját, izolált környezetben fut, valós rendszer ellen nem irányul.

Előkészítés

Hozd létre a labor könyvtárat:

mkdir -p ~/cyber-labor/cch09/repro-build
cd ~/cyber-labor/cch09/repro-build

Győződj meg arról, hogy a Docker telepítve van, és a BuildKit engedélyezett (alapértelmezésben az újabb Docker verziókban igen). A pontos verziókat ellenőrizd a saját környezetedben. Szükséges még a hoston Python 3.12 és a pip-tools (python3 -m venv .venv && . .venv/bin/activate && pip install pip-tools==<rögzített verzió>). A pip-compile, a pip download és a docker buildx imagetools inspect hálózatot igényel (előkészítő szakasz); maga a build a wheelhouse-ból, hálózat nélkül fut.

10.4.17 1. lépés: Alkalmazás létrehozása

Készíts egy egyszerű Python webalkalmazást app.py néven:

# app.py - TerraSecure demo alkalmazás
from flask import Flask

app = Flask(__name__)

@app.route("/")
def index():
    return "TerraSecure: reproducible build demo\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=8080)

Készíts requirements.in fájlt a közvetlen függőségekkel (például flask==3.0.0), majd generáld le a teljes, tranzitív hash-elt requirements.txt-t:

pip-compile --generate-hashes --output-file requirements.txt requirements.in

A pip-compile minden közvetlen és tranzitív csomagra beírja a pontos verziót és a --hash=sha256:... értékeket. Ezután töltsd le a célplatform wheelhouse-át:

pip download --only-binary=:all: --dest wheelhouse \
  --platform manylinux2014_x86_64 --python-version 3.12 \
  --implementation cp --abi cp312 -r requirements.txt

A kézzel írt, csak a Flaskot tartalmazó hash-sor nem elég: a --require-hashes a teljes tranzitív gráf minden csomagjára pontos verziót és hash-t követel, ezért a fájlt a pip-compile állítja elő.

10.4.18 2. lépés: Determinisztikus Dockerfile

Készíts Dockerfile-t a fenti mintának megfelelően. A base image digestjét a labor elején oldd fel:

PYTHON_IMAGE="python:3.12-slim@$(docker buildx imagetools inspect python:3.12-slim \
  --format '{{json .Manifest.Digest}}' | tr -d '"')"
echo "$PYTHON_IMAGE"

A Dockerfile a PYTHON_IMAGE build argumentumot használja, a SOURCE_DATE_EPOCH pedig mindkét szakaszban deklarált. A wheelhouse-t a build kontextusába másolva, --no-index --find-links=/wheelhouse --require-hashes kapcsolókkal telepíts, hogy a build ne függjön hálózattól.

10.4.19 3. lépés: Build kétszer és digest-összehasonlítás

Futtasd a buildet kétszer, mindkét alkalommal --no-cache opcióval és --metadata-file kimenettel:

docker buildx build --no-cache \
  --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" \
  --build-arg SOURCE_DATE_EPOCH=1700000000 \
  --output type=docker,name=terra/secure-web:1.0,rewrite-timestamp=true \
  --metadata-file build1.json .

docker buildx build --no-cache \
  --build-arg PYTHON_IMAGE="$PYTHON_IMAGE" \
  --build-arg SOURCE_DATE_EPOCH=1700000000 \
  --output type=docker,name=terra/secure-web:1.0,rewrite-timestamp=true \
  --metadata-file build2.json .

Hasonlítsd össze a containerimage.digest mezőt a két metadata-fájlban. Az image ID a helyi réteghash-ekből számított azonosító, amely nem feltétlenül egyezik a registry manifest digestjével; a reprodukálhatóságot a manifest digesten vagy exportált OCI-artefaktumon mérd. Ha eltér, keresd a nem determinisztikus elemet: hiányzó hash, eltérő base digest, SOURCE_DATE_EPOCH elmaradása, hiányzó rewrite-timestamp=true, eltérő BuildKit-verzió vagy nem rögzített wheelhouse.

10.4.22 Mit tanultunk?

  • A determinisztikus build akkor érhető el, ha minden input rögzített: a forráskód, a függőségek hash-e, a base image digest, a build környezet és a build parancs.
  • A nem-determinisztikus elemek (időbélyeg, elérési utak, cache) kiküszöbölésével a build kimenete bit-azonos lesz.
  • A CI-napló ellenőrzése lehetővé teszi a pipeline integritásának utólagos auditálását.

10.4.23 Hogyan védjük ki?

  • Használj --require-hashes típusú ellenőrzést a függőségeknél.
  • Rögzítsd a base image digest-jét, soha ne használj latest taget.
  • Állítsd be a SOURCE_DATE_EPOCH-ot és a kapcsolódó változókat.
  • Futtasd a buildet ephemeral, konténerizált runnerben, minimális jogosultságokkal.
  • Írd alá a műterméket, és csatolj SLSA attestationt.
  • Naplózd a build inputjait és kimenetét, és tárold a naplókat integritásvédelemmel.

10.4.24 Önellenőrző kérdések

  1. Mi a különbség a determinisztikus build és a pipeline-integritás között? Miért van szükség mindkettőre az ellátási lánc biztonságához?
  2. Sorolj fel három nem-determinisztikus elemet, amelyek megakadályozzák a reprodukálható buildet, és add meg mindegyikre a kiküszöbölés módját.
  3. Egy CI-naplóban azt látod, hogy a build során a pip install parancs --require-hashes nélkül futott. Milyen támadási lehetőséget nyit ez, és hogyan javítanád?

Elvárt válaszok:

  1. A determinisztikus build azt biztosítja, hogy ugyanabból a bemenetből ugyanaz a kimenet keletkezzen (független ellenőrzés); a pipeline-integritás azt, hogy a bemenetet és a folyamatot senki ne módosíthassa jogosulatlanul. Az egyik a kompromittált pipeline-t nem zárja ki, a másik nélkül nincs független ellenőrzés.
  2. Például: időbélyeg → SOURCE_DATE_EPOCH és rewrite-timestamp; mozgó base tag → digest; nem rögzített függőség → hash-elt requirements.txt és wheelhouse; .pyc időbélyeg → PYTHONDONTWRITEBYTECODE=1.
  3. Hash-ellenőrzés nélkül egy kompromittált regiszter vagy tükör, egy dependency confusion vagy egy újrafeltöltött csomag más tartalmat adhat ugyanazzal a verziószámmal; javítás: pip-compile --generate-hashes, --require-hashes, --no-index a wheelhouse-ból, és olyan CI-kapu, amely a kapcsoló hiányában megáll.

10.4.25 Összegzés

Ebben a fejezetben megtanultuk, hogy a reprodukálható build és a pipeline-integritás az ellátási lánc bizalmának két alappillére. A determinisztikus build lehetővé teszi a független ellenőrzést, a pipeline-integritás pedig megakadályozza, hogy a build folyamata maga váljon támadási felületté. A laborban egy kis Python alkalmazáson gyakoroltuk a hash-elt függőségek, a rögzített base image és a SOURCE_DATE_EPOCH használatát, valamint egy CI-napló ellenőrzését. A következő fejezet (TLS és PKI) a hálózati biztonság alapjaira épít, ahol a hitelesítés és a titkosítás protokollszintű részleteit vizsgáljuk meg.
