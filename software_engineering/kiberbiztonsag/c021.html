7.1 Hitelesítés és session hibák

Amikor a hitelesítés megtörtént, a szerver már nem kér jelszót minden HTTP-kérésnél; ehelyett egy munkamenet-azonosító (session token) képviseli a felhasználót. Ez a token a munkamenet idejére gyakorlatilag a jelszóval azonos hozzáférést ad, de hatóköre és élettartama korlátozott, ezért kezelése, élettartama és érvénytelenítése kritikus. Ebben az egységben három, egymással összefüggő hibát vizsgálunk: a session fixationt, a tokenkiszivárgást és a logout-hibákat. A kockázatot továbbra is R=L×IR = L \times I alakban értelmezzük: ha egy session token kikerül (valószínűség, LL) és azzal teljes fiókátvétel lehetséges (hatás, II), a kockázat magas akkor is, ha a sérülékeny komponens önmagában csak egy apró része a rendszernek.

7.1.1 Session fixation

A session fixation olyan támadás, amelyben a támadó előre rögzít egy munkamenet-azonosítót, majd ráveszi a felhasználót, hogy ugyanezzel az azonosítóval jelentkezzen be. A rendszer akkor válik sérülékennyé, ha a bejelentkezéskor nem cseréli le a session azonosítót, hanem a meglévőt emeli jogosultsági szintre. A támadó ezek után a saját, általa ismert azonosítóval átveszi a már hitelesített munkamenetet.

A tipikus lépéseket a TerraSecure izolált laborjában az alábbi szekvenciadiagram mutatja, a szerveroldali munkamenet-tár állapotával együtt (a labor tényleges címzése: http://127.0.0.1:8080):

Megjegyzés: a laborhatár a c021-lab-net belső Docker-hálózat, a publikáláshoz használt c021-front hálózat és a hoszt 127.0.0.1:8080 portja; a szerver és a két kliens is ehhez a laborhoz tartozik, valós rendszer nem érintett. A visszaállítás a konténer leállítása és a hálózat törlése; a minta eredményeit csak a labor saját azonosítóira alkalmazza.

Miért nem elég a Flask alapértelmezett sessionje? A Flask session objektuma aláírt, kliensoldali cookie: az adatok a böngészőben vannak, a szerver csak az aláírást ellenőrzi. Ebben a modellben nincs állandó, szerveroldali munkamenet-azonosító, ezért a session fixation klasszikus, szerveroldali ID-cserés bemutatására önmagában nem alkalmas (a session.clear() csak egy új aláírt cookie-t készít, nem egy szerveroldali rekordot cserél). Az alábbi, valódi minilabor saját szerveroldali session-tárat használ: a cookie csak egy véletlen ts_sid azonosítót hordoz, az állapot a szerver memóriájában van.

A c021_lab.py teljes, futtatható forrása (a telepítést, az indítást és az audit lépéseit a fejezet laborja írja le):

# c021_lab.py – TerraSecure szándékosan sérülékeny session-labor (csak izolált laborban)
import os
import secrets
import time

from flask import Flask, make_response, redirect, request

app = Flask(__name__)

MODE = os.environ.get("TERRASECURE_C021_MODE", "vulnerable")
IDLE_TIMEOUT = int(os.environ.get("TERRASECURE_C021_IDLE", "900"))
ABSOLUTE_TIMEOUT = int(os.environ.get("TERRASECURE_C021_ABSOLUTE", "28800"))
COOKIE_NAME = "ts_sid"

FELHASZNALOK = {
    "alice": "AliceLabPass!2026",
    "bob": "BobLabPass!2026",
}

SESSION_STORE = {}  # ts_sid -> {"user_id", "csrf", "created", "last_seen"}

LOGIN_FORM = (
    '<form method="post" action="/login">'
    '<label>Felhasználónév <input name="username"></label>'
    '<label>Jelszó <input type="password" name="password"></label>'
    '<button type="submit">Bejelentkezés</button></form>'
)


def uj_sid() -> str:
    return secrets.token_urlsafe(32)  # 256 bites véletlen azonosító


def uj_rekord(felhasznalo=None):
    most = time.time()
    return {
        "user_id": felhasznalo,
        "csrf": secrets.token_urlsafe(32),
        "created": most,
        "last_seen": most,
    }


def lejart(rec) -> bool:
    most = time.time()
    return (
        most - rec["last_seen"] > IDLE_TIMEOUT
        or most - rec["created"] > ABSOLUTE_TIMEOUT
    )


def aktualis_rekord():
    sid = request.cookies.get(COOKIE_NAME)
    rec = SESSION_STORE.get(sid) if sid else None
    if rec is not None and lejart(rec):
        SESSION_STORE.pop(sid, None)
        rec = None
    if rec is not None:
        rec["last_seen"] = time.time()
    return sid, rec


def get_or_create():
    sid, rec = aktualis_rekord()
    if rec is not None:
        return sid, rec, False
    # Csak sérülékeny módban: javított módban URL-ből nem veszünk át azonosítót.
    atvett = request.args.get("sid") if MODE == "vulnerable" else None
    if atvett and atvett in SESSION_STORE and not lejart(SESSION_STORE[atvett]):
        sid = atvett
        rec = SESSION_STORE[sid]
    else:
        sid = uj_sid()
        rec = uj_rekord()
        SESSION_STORE[sid] = rec
    rec["last_seen"] = time.time()
    return sid, rec, True


def oldal(cim: str, torzs: str) -> str:
    return (
        '<!doctype html><html lang="hu"><head><meta charset="utf-8">'
        f"<title>{cim}</title></head><body><h1>{cim}</h1>{torzs}</body></html>"
    )


def valasz(cim: str, torzs: str, status: int = 200):
    return make_response(oldal(cim, torzs), status)


@app.get("/healthz")
def healthz():
    return "ok", 200


@app.get("/")
def index():
    sid, rec, uj = get_or_create()
    torzs = (
        f"<p>Mód: <strong>{MODE}</strong></p>"
        f"<p>Munkamenet-azonosító (ts_sid): <code>{sid}</code></p>"
        f"<p>Hitelesített felhasználó: <code>{rec['user_id'] or 'névtelen'}</code></p>"
        '<ul><li><a href="/login">Bejelentkezés</a></li>'
        '<li><a href="/dashboard">Védett oldal</a></li>'
        '<li><a href="/whoami">Munkamenet állapota</a></li></ul>'
    )
    response = valasz("TerraSecure c021 labor", torzs)
    if uj:
        response.set_cookie(COOKIE_NAME, sid, httponly=True, samesite="Lax", path="/")
    return response


@app.get("/whoami")
def whoami():
    sid, rec = aktualis_rekord()
    if rec is None:
        return valasz("Munkamenet", "<p>401 – nincs érvényes munkamenet.</p>", 401)
    return valasz(
        "Munkamenet",
        f"<p>sid: <code>{sid}</code></p>"
        f"<p>user_id: <code>{rec['user_id'] or 'None'}</code></p>",
    )


@app.route("/login", methods=["GET", "POST"])
def login():
    sid, rec, uj = get_or_create()
    if request.method == "GET":
        return valasz("Bejelentkezés", LOGIN_FORM)
    if FELHASZNALOK.get(request.form.get("username", "")) != request.form.get("password", ""):
        return valasz("Bejelentkezés", "<p>401 – hibás hitelesítő adatok.</p>", 401)
    if MODE == "vulnerable":
        # HIBA: a meglévő, támadó által ismert anonim sid emelődik hitelesítetté
        rec["user_id"] = request.form["username"]
        uj_sid_ertek = sid
    else:
        # JAVÍTÁS: hitelesítéskor új sid, a régi rekord törlése
        SESSION_STORE.pop(sid, None)
        uj_sid_ertek = uj_sid()
        SESSION_STORE[uj_sid_ertek] = uj_rekord(request.form["username"])
    response = redirect("/dashboard")
    response.set_cookie(COOKIE_NAME, uj_sid_ertek, httponly=True, samesite="Lax", path="/")
    return response


@app.get("/dashboard")
def dashboard():
    sid, rec = aktualis_rekord()
    if rec is None or rec["user_id"] is None:
        return valasz("Védett oldal", "<p>401 – nincs hitelesített munkamenet.</p>", 401)
    torzs = (
        f"<p>Bejelentkezve: <strong>{rec['user_id']}</strong></p>"
        f"<p>Munkamenet-azonosító: <code>{sid}</code></p>"
        '<form method="post" action="/logout">'
        f'<input type="hidden" name="csrf" value="{rec["csrf"]}">'
        '<button type="submit">Kijelentkezés ezen az eszközön</button></form>'
        '<form method="post" action="/logout-all">'
        f'<input type="hidden" name="csrf" value="{rec["csrf"]}">'
        '<button type="submit">Kijelentkezés minden eszközön</button></form>'
    )
    return valasz("Védett oldal", torzs)


@app.post("/logout")
def logout():
    sid, rec = aktualis_rekord()
    if rec is None:
        return valasz("Kijelentkezés", "<p>401 – nincs érvényes munkamenet.</p>", 401)
    if not secrets.compare_digest(request.form.get("csrf", ""), rec["csrf"]):
        return valasz("Kijelentkezés", "<p>403 – érvénytelen CSRF-token.</p>", 403)
    SESSION_STORE.pop(sid, None)  # tényleges szerveroldali törlés
    response = redirect("/")
    response.delete_cookie(COOKIE_NAME, path="/")  # ugyanaz a név, útvonal, domain
    return response


@app.post("/logout-all")
def logout_all():
    sid, rec = aktualis_rekord()
    if rec is None or rec["user_id"] is None:
        return valasz("Kijelentkezés", "<p>401 – nincs hitelesített munkamenet.</p>", 401)
    if not secrets.compare_digest(request.form.get("csrf", ""), rec["csrf"]):
        return valasz("Kijelentkezés", "<p>403 – érvénytelen CSRF-token.</p>", 403)
    for kulcs in [k for k, v in SESSION_STORE.items()
                  if v["user_id"] == rec["user_id"]]:
        SESSION_STORE.pop(kulcs, None)  # minden eszköz rekordjának törlése
    response = redirect("/")
    response.delete_cookie(COOKIE_NAME, path="/")
    return response


if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)

A sérülékeny és a javított viselkedés ugyanazon a kódon, a TERRASECURE_C021_MODE környezeti változóval kapcsolható (a módot importáláskor olvassa be, ezért váltáskor a konténert újra kell indítani):

  • TERRASECURE_C021_MODE=vulnerable: a login megtartja a bejelentkezés előtti, anonim ts_sid-et. Ezt az azonosítót a támadó ismeri, ezért a bejelentkezés után ugyanezzel a cookie-val éri el a hitelesített munkamenetet.
  • TERRASECURE_C021_MODE=fixed: a login új, véletlen ts_sid-et generál, a régit pedig törli a SESSION_STORE-ból. A támadó által ismert eredeti ID visszajátszása így 401-et ad, és URL-ből (?sid=) sem vesz át munkamenet-azonosítót.

A két klienssel végzett reprodukciót, a pontos parancsokat és az elvárt kimeneteket a fejezet laborja tartalmazza.

Emellett a védő beállítja a cookie-k biztonsági attribútumait: HttpOnly (JavaScript ne férjen hozzá), Secure (csak TLS kapcsolaton), SameSite=Strict vagy Lax (CSRF ellen) és lehetőleg __Host- prefixet használ. A WSTG Session Management tesztcsoportjai (különösen a session fixation vizsgálat) adnak módszertant az ellenőrzéshez; a pontos verziószám a kiadvány aktuális, ellenőrzött kiadásától függ.

Mit tanultunk? A session fixation kihasználja, hogy a szerver megbízik egy olyan azonosítóban, amelyet a támadó már ismer. Hogyan védjük ki? Minden privilegizált állapotváltásnál generáljunk új session azonosítót, és állítsuk be a cookie-k védelmi attribútumait.

7.1.2 Tokenkiszivárgás

A tokenkiszivárgás azt jelenti, hogy a titkos token bárki számára olvasható csatornába kerül: URL-query paraméterbe, naplófájlba, HTTP Referer fejlécbe, hibajelentésbe, verziókezelőbe vagy a felhasználó böngészőjének külső kiterjesztésébe. A támadó ilyenkor nem feltöri a rendszert, csak összegyűjti a már kiszivárgott azonosítókat.

A token fogalmát érdemes három rétegre bontani, mert a session token, az API-kulcs és a JWT nem ugyanaz a szerep:

Réteg Kérdés Példa
Funkció Mit engedélyez? munkamenet, API-hozzáférés, egyszeri művelet
Formátum Átlátszatlan vagy önhordozó? opaque token, JWT
Szállítás Hogyan jut el a klienshez? HttpOnly cookie, Authorization fejléc, URL-query (kerülendő)

Ugyanaz a szállítási mód több funkciót is hordozhat, de a token hatóköre és élettartama a funkciótól függ; egy rövid élettartamú munkamenet-token hatóköre nem automatikusan azonos egy jelszóéval.

A leggyakoribb kiszivárgási csatornák:

  1. URL-query paraméter: https://terrasecure.example.invalid/dashboard?sid=<TOKEN> – a token megjelenik a böngésző előzményeiben, proxy- és szervernaplókban; külső hivatkozásnál a Referer fejlécbe is bekerülhet, de ez a Referrer-Policy beállításától függ.
  2. Szerveroldali naplózás: a fejlesztő a teljes HTTP-kérést naplózza, beleértve a Authorization fejlécet.
  3. Kliensoldali tárolás: a localStorage vagy sessionStorage használata XSS esetén a JavaScript számára elérhetővé teszi a tokent. A HttpOnly cookie csak a közvetlen JavaScript-olvasást gátolja: XSS esetén a támadó kód a cookie-t nem tudja kiolvasni, de a böngésző a kérésekhez továbbra is hozzácsatolja, így a token nevében műveleteket indíthat.
  4. Verziókezelőbe került titok: .env fájl vagy konfiguráció, amelybe valódi tokent írtak.
  5. Metadata szolgáltatások: felhőkörnyezetben a http://169.254.169.254/latest/meta-data/ ideiglenes hitelesítő adatokat adhat ki, ha a támadó SSRF révén eléri. A 169.254.169.254 a felhőben valós, link-local metaadatcím; a laborban csak a CSRF, SSRF és open redirect mock-szolgáltatását használjuk. Erre a Capital One-incidens kapcsán térünk ki.

A Referer-kiszivárgás egyetlen, jól követhető példája: a dashboard oldalon van egy külső hivatkozás.

<a href="https://kulso.example.invalid/">Külső oldal</a>

Ha az oldal URL-je https://terrasecure.example.invalid/dashboard?sid=<TOKEN>, a külső kérésnél küldött Referer értéke a választott politikától függ:

Referrer-Policy Mit küld külső kérésnél?
no-referrer semmit
strict-origin-when-cross-origin (a modern böngészők alapértelmezése) csak az origin-t: https://terrasecure.example.invalid/
unsafe-url a teljes URL-t, benne a ?sid=<TOKEN> query-vel

A tanulság: a token URL-be tétele nem a Referrer-Policy hibája, hanem a token szállítási csatornájának hibája. A no-referrer csak enyhíti a következményt, a tokent a böngésző-előzményekből, a proxy- és szervernaplókból nem tünteti el.

Egy hibás, szándékosan sérülékeny naplózási minta:

# hibás: token naplózva
import logging

@app.route("/api/profile")
def profile():
    token = request.headers.get("Authorization")
    logging.info(f"User token: {token}")
    return get_profile(token)

A javított változat csak azt rögzíti, hogy a token jelen van-e, magát a tokent soha:

# javított: token jelenlétét naplózzuk, az értéket nem
import logging

@app.route("/api/profile")
def profile():
    token = request.headers.get("Authorization")
    logging.info("Authorization header present: %s", bool(token))
    return get_profile(token)

A védő ezen felül a következőket teszi:

  • Minden tokennek rövid élettartamot ad (pl. JWT esetén exp claim).
  • A hosszú élettartamú refresh tokeneket külön, nem elérhető tárolóban tartja.
  • A cookie-khoz HttpOnly, Secure, SameSite attribútumot rendel.
  • A naplózáshoz redakciós szűrőt alkalmaz, és a kimenő hibaválaszokból eltávolítja a tokeneket.
  • A verziókezelőbe beépített titokkeresést futtat (pl. pre-commit hook).

Az ellenőrzés során a támadó szerepét felvevő auditor megpróbálja a tokent kicsalogatni: rákérdez olyan végpontra, amely hibát okoz, megnézi a böngésző hálózati forgalmát, és átvizsgálja a szerver naplófájljait. A védő ezeket a kísérleteket detektálja, és a naplózott eseményeket elemzi.

Mit tanultunk? A token akkor biztonságos, ha a csatornáiban marad; a kiszivárgás sok esetben nem a token generálásának hibája, hanem a titokkezelés hiánya. Hogyan védjük ki? Soha ne tegyünk tokent URL-be vagy naplóba; használjunk HttpOnly cookie-t, rövid TTL-t és redakciót, a korrelációhoz pedig célhoz kötött esemény- vagy session-korrelációs azonosítót.

7.1.3 Logout-hibák

A logout nem csupán kényelmi funkció: biztonsági kontroll, amely megszakítja a felhasználó és a szerver közötti bizalmi kapcsolatot. A leggyakoribb hibák:

  1. A szerver nem érvényteleníti a sessiont – a kliens oldalon törlik a cookie-t, de a token a szerveren továbbra is érvényes marad. A támadó a korábban megszerzett token értékével még mindig hozzáférhet.
  2. Hiányzó timeout – a session addig él, amíg a felhasználó ki nem jelentkezik; ha elhagyja a gépet, a munkamenet nyitott marad.
  3. Az „aktuális eszköz” és a „minden eszköz” kijelentkeztetése összekeveredik – a legtöbb rendszernek külön kell kínálnia a jelenlegi munkamenet lezárását és az összes eszköz revokációját. Az, hogy egy termék csak az aktuális eszközt tudja kijelentkeztetni, önmagában nem logout-hiba, ha ezt dokumentálja; a hiba az, ha a felület „minden eszköz” címen csak a jelenlegit zárja le.

Egy hibás logout implementáció:

# hibás: logout csak kliensoldali cookie-törlésre hagyatkozik
@app.route("/logout")
def logout():
    response = redirect("/")
    response.delete_cookie("session")
    # HIBA: a szerver oldali session érvényben marad
    return response

A javított változat POST-ot, CSRF-védelmet, tényleges szerveroldali rekordtörlést és a cookie-val egyező név/útvonal/domain beállítást használ:

# javított: POST + CSRF + tényleges szerveroldali törlés
@app.post("/logout")
def logout():
    sid = request.cookies.get("ts_sid")
    rec = SESSION_STORE.get(sid)
    if rec is None:
        return "nincs érvényes munkamenet", 401
    if not secrets.compare_digest(request.form.get("csrf", ""), rec["csrf"]):
        return "érvénytelen CSRF-token", 403
    SESSION_STORE.pop(sid, None)                 # a szerveroldali rekord törlése
    response = redirect("/")
    response.delete_cookie("ts_sid", path="/")   # ugyanaz a név, útvonal, domain
    return response

A „minden eszköz” változat ugyanezt teszi az adott felhasználó összes rekordjára:

# javított: minden eszköz kijelentkeztetése
@app.post("/logout-all")
def logout_all():
    sid = request.cookies.get("ts_sid")
    rec = SESSION_STORE.get(sid)
    if rec is None or rec["user_id"] is None:
        return "nincs hitelesített munkamenet", 401
    if not secrets.compare_digest(request.form.get("csrf", ""), rec["csrf"]):
        return "érvénytelen CSRF-token", 403
    for kulcs in [k for k, v in SESSION_STORE.items()
                  if v["user_id"] == rec["user_id"]]:
        SESSION_STORE.pop(kulcs, None)
    response = redirect("/")
    response.delete_cookie("ts_sid", path="/")
    return response

A védő emellett beállítja az abszolút és az inaktivitási időkorlátot. Az abszolút timeout a token maximális élettartamát korlátozza (pl. 8 óra), az idle timeout pedig az utolsó kérés óta eltelt időt (pl. 15 perc). Mindkettőt a szerver ellenőrzi a munkamenet-rekord időbélyegei alapján:

def lejart(rec) -> bool:
    most = time.time()
    return (most - rec["last_seen"] > IDLE_TIMEOUT
            or most - rec["created"] > ABSOLUTE_TIMEOUT)

A süti lejárati ideje (Max-Age, Expires) csak a böngésző viselkedését szabályozza; a szerveroldali idle timeoutot nem teszteli. Az inaktivitási korlát igazolásához külön szerveroldali órateszt kell: rövid TERRASECURE_C021_IDLE értékkel bejelentkezés után várakozni, majd a még meglévő cookie-val kérni egy védett oldalt – az elvárt válasz 401.

Az ellenőrzéshez a támadó szerepét felvevő auditor a következőket teszteli:

  • Mentse el a cookie-t a logout előtt, majd a logout után egy másik kliensből próbáljon hozzáférni a védett oldalhoz ugyanazzal az értékkel; az elvárt eredmény 401 vagy bejelentkezésre irányítás.
  • A logout után a böngészőben a vissza gomb, illetve a szerver naplójában a korábbi Cookie fejléc újrahasznosítását figyeli.
  • Az inaktivitási és az abszolút időkorlátot külön, szerveroldali órateszttel vizsgálja (rövid timeouttal), nem a süti lejárati idejéből következtet.
  • Külön teszteli az „aktuális eszköz” és a „minden eszköz” kijelentkeztetést: az első csak a jelenlegi rekordot törli, a második az adott felhasználó összes rekordját.

Mit tanultunk? A logout akkor hatásos, ha a szerver oldalon is megszünteti a sessiont, és a timeout politikát is beállítja. Hogyan védjük ki? Szerveroldali érvénytelenítés, abszolút és idle timeout, valamint az „aktuális eszköz” és a „minden eszköz” kijelentkeztetés tudatos megkülönböztetése.

7.1.4 Ellenőrzési, naplózási és dokumentációs szempontok

A session- és tokenkezelés auditjánál a védő és az auditor az alábbi ellenőrzési listát használja:

Témakör Ellenőrző kérdés Elvárt viselkedés
Session fixation A bejelentkezés létrehoz-e új session ID-t? Igen, a régi ID elvetendő
Session fixation A cookie attribútumai (HttpOnly, Secure, SameSite) be vannak-e állítva? Igen
Tokenkiszivárgás A token megjelenik-e URL-ben, naplóban, hibaválaszban? Nem
Tokenkiszivárgás A tokenek élettartama korlátozott-e? Igen, dokumentált TTL
Logout A logout szerver oldalon érvényteleníti-e a sessiont? Igen, tényleges rekordtörlés vagy revokáció
Logout Külön kezelhető-e az aktuális eszköz és a minden eszköz kijelentkeztetése? Igen, dokumentált viselkedéssel

Naplózás A naplófájlok tartalmazzák-e a session token értékét? Nem; csak a token jelenléte (igen/nem) és a célhoz kötött esemény-/session-korrelációs azonosító szerepel, külön mezőben

A naplózás során a védő a sikeres és sikertelen bejelentkezést, a jogosultságváltást, a kijelentkezést és a session érvénytelenítését naplózza, de magát a tokent nem. A korrelációhoz ne a nyers tokent és ne is a token hash-ét használjuk elsődleges kulcsként, hanem a token rekordjához rendelt, célhoz kötött esemény- vagy session-korrelációs azonosítót. A naplóban a token jelenléte és a korrelációs érték külön mező; a korrelációs azonosítóból a token nem állítható vissza, és a két érték nem mosható össze egyetlen naplómezővé.

A dokumentációban a rendszer üzemeltetője rögzíti:

  • Milyen típusú session tokeneket használ (cookie, JWT, opaque token).
  • Milyen cookie-attribútumok érvényesek.
  • Mi a token maximális élettartama és az idle timeout.
  • Hogyan történik a logout és a párhuzamos sessionök érvénytelenítése.
  • Melyik naplóesemények tartalmaznak tokenekkel kapcsolatos információt, és azok hogyan vannak redakciózva.

7.1.5 Esettanulmány: a Capital One-incidens (2019) SSRF-tanulságai

A 2019-es Capital One-incidens elsődleges iratai: az Amerikai Egyesült Államok Nyugati Kerületi Bíróságán (W.D. Wash.) indult büntetőügy, United States v. Paige A. Thompson, az ügyszám a PACER/DOJ sajtóközlemény alapján ellenőrizendő (2019), valamint az OCC (Office of the Comptroller of the Currency) 2020. augusztusi hivatalos határozata a Capital One, N.A. ellen (Consent Order). A bírósági iratok szerint a támadó egy hibásan konfigurált webalkalmazás-tűzfalon keresztül szerzett ideiglenes szerepkör-hitelesítő adatokat, és ezekkel az AWS API-k felé hitelesítve fért hozzá a tárolókhoz; hogy ez SSRF-en és az EC2 metadata-szolgáltatáson keresztül történt, az utólagos szakmai elemzések következtetése (a forrás a kiadás előtt megnevezendő), nem a hatósági iratok szó szerinti állítása. Az ezt követő oktatási értelmezés – a tokenkezelés tanulságai, a legkisebb jogosultság és a monitorozás – a mi elemzésünk, nem a határozat szó szerinti állítása.

Fontos megkülönböztetés: az IMDSv2 X-aws-ec2-metadata-token tokenje kizárólag a metadata-szolgáltatás felé hitelesít. A válaszként kapott AccessKeyId, SecretAccessKey és SessionToken hármas az a szerepkör-hitelesítő adat, amellyel a támadó az AWS API-k felé hitelesíteni tud. A kettő nem ugyanaz a hitelesítő adat, és a kiszivárgás tárgya az utóbbi.

A fókuszunk nem az SSRF-technika, hanem a tokenkezelés tanulságai:

  1. A metadata-szolgáltatásból kikerülő szerepkör-hitelesítő adat is titok. A http://169.254.169.254/latest/meta-data/ által kiadott ideiglenes IAM hitelesítő adatokat úgy kell védeni, mint bármely más titkot. A támadó nem a jelszót törte fel, hanem egy sérülékeny útvonalon át megszerezte az ideiglenes hitelesítő adatot.
  2. A legkisebb jogosultság hiánya növelte a hatást. Ha a csatolt szerepkör túl sok engedéllyel rendelkezett, a megszerzett token is túl sok mindenhez fért hozzá. A legkisebb jogosultság elve (R=L×IR = L \times I hatáscsökkentés) itt kritikus védelmi kontroll lett volna.
  3. A token élettartama és a forgatás. A rövid élettartamú tokenek és az automatikus forgatás csökkentik az ablakot, de önmagukban nem elegendőek, ha a hozzáférési szint túl széles. A védőnek a token kiadását és használatát is monitoroznia kell.

A védelmi kontrollok ebből az incidensből:

  • SSRF elleni védelem a hálózati rétegben és az alkalmazásban (lásd CSRF, SSRF és open redirect).
  • Metadata szolgáltatás védelme (pl. IMDSv2, X-aws-ec2-metadata-token header): az IMDSv2 tokenje csak PUT kéréssel és egyedi fejléccel kérhető, ezért egy egyszerű, GET-alapú SSRF nem éri el a hitelesítő adatokat; ha azonban a sebezhető komponens tetszőleges metódust és fejlécet továbbít, az IMDSv2 nem véd, ezért a legkisebb jogosultság és az egress-korlát továbbra is szükséges (a hop limit részletét az AWS EC2 dokumentációja alapján, verzióval rögzítve kell megadni).
  • IAM szerepkörök minimalizálása és a felhőkörnyezet hálózati szegmentációja.
  • A metadata kérések és a szerepváltások naplózása, riasztás a gyanús mintákra.
  • Token élettartamok dokumentálása és forgatási politika.

A tanulság nem a támadás részlete, hanem az: a hitelesítő adatok kiszivárgása mindig a hitelesítési lánc valamelyik gyenge pontján történik, és a védő feladata, hogy a lánc minden elemét – a session tokeneket, az IAM szerepköröket és a metadata hozzáférést – ellenőrizze.

7.1.8 Audit lépések

A parancsok a hoszt termináljában futnak, és a curl cookie-jar mechanizmusát használják két külön kliens szimulálására. A példákban az A a támadó, a B az áldozat kliense.

  1. Az eredeti anonim ID rögzítése (A kliens).

    curl -s -c /tmp/c021-a.jar http://127.0.0.1:8080/ -o /dev/null
A_ID=$(awk '$6=="ts_sid" {print $7}' /tmp/c021-a.jar)
echo "A_ID=$A_ID"
curl -s -b /tmp/c021-a.jar http://127.0.0.1:8080/whoami

    Az elvárt kimenet: user_id: None, és a sid megegyezik az A_ID értékkel. Ezt az ID-t a hitelesítéstől függetlenül, külön rögzítse.

  2. A fixált ID átadása (B kliens).

    curl -s -c /tmp/c021-b.jar "http://127.0.0.1:8080/?sid=$A_ID" -o /dev/null
curl -s -b /tmp/c021-b.jar http://127.0.0.1:8080/whoami

    Az elvárt kimenet: a B kliens sid-je szintén A_ID, user_id: None. A két kliens tehát ugyanazt az anonim munkamenetet használja.

  3. Bejelentkezés a B kliensben, az ID sorsa.

    curl -s -b /tmp/c021-b.jar -c /tmp/c021-b.jar \
  -d 'username=alice&password=AliceLabPass!2026' \
  http://127.0.0.1:8080/login -o /dev/null
curl -s -b /tmp/c021-b.jar http://127.0.0.1:8080/whoami

    Sérülékeny módban (vulnerable) a sid továbbra is A_ID, a user_id pedig alice. Javított módban (fixed) a sid új érték, az A_ID rekordja pedig törlődött.

  4. Az eredeti ID visszajátszása (A kliens). Ez a fixation-teszt tényleges ellenőrzése:

    curl -s -b /tmp/c021-a.jar http://127.0.0.1:8080/dashboard \
  -w '\nHTTP %{http_code}\n'

    Sérülékeny módban HTTP 200 és Bejelentkezve: alice. Javított módban HTTP 401. A minta eredményét csak a labor saját A_ID értékére alkalmazza; valós rendszer azonosítóját ne használja.

    4b. Javított mód. Állítsa le a konténert, indítsa újra -e TERRASECURE_C021_MODE=fixed értékkel (az indítás ugyanaz, mint fent), és ismételje meg az 1–4. lépést; a 3. lépésben a sid új érték, a 4. lépésben HTTP 401. Az újraindítás a memóriabeli munkamenet-tárat is törli, ezért az A_ID-t újra rögzíteni kell. A 2. lépés ?sid= átvétele javított módban nem működik, ezért ott a B kliens sid-je új érték lesz.

  5. Logout teszt (mentett cookie visszajátszása). Jelentkezzen be a B kliensben, majd a logout előtt mentse el a cookie-t:

    cp /tmp/c021-b.jar /tmp/c021-b-mentett.jar

curl -s -b /tmp/c021-b.jar http://127.0.0.1:8080/logout -o /dev/null -w 'HTTP %{http_code}\n'   # 405
curl -s -b /tmp/c021-b.jar -X POST http://127.0.0.1:8080/logout -o /dev/null -w 'HTTP %{http_code}\n'   # 403

7.1.9 Önellenőrző kérdések

  1. Miért nem elegendő a logout során kizárólag a kliensoldali cookie törlése?

    Rövid megoldás: a cookie törlése csak azt éri el, hogy az adott böngésző többé nem küldi el a session ID-t; a szerveroldali munkamenet-rekord ettől még érvényben marad. Ha a tokent korábban ellopták, lemásolták vagy egy másik eszközön is megvan, a támadó a törlés után is be tud lépni vele. A kijelentkezés ezért a szerveren történő érvénytelenítést (a rekord törlését vagy visszavonását) jelenti, a kliensoldali cookie törlése csak ennek kiegészítése.

    Tipikus tévedés: azt gondolni, hogy a böngészőből eltűnt cookie egyben a szerver állapotát is törli. A kettő külön rendszer: a cookie a kliensnél van, a munkamenet-rekord a szervernél; a logout akkor helyes, ha mindkettőt kezeli, és a szerveroldali lépés a kötelező érvényű.

  2. Soroljon fel három csatornát, amelyeken keresztül session token kiszivároghat.

    Rövid megoldás: például (a) URL query paraméterben átadott token, amely a böngésző-előzménybe, a szerver- és proxy-naplókba, valamint a Referer fejlécen át külső oldalra kerülhet; (b) naplófájlba vagy hibaválaszba írt token (túlságosan részletes naplózás, kivétel-üzenet); (c) XSS, amely a document.cookie-t olvassa, vagy a HttpOnly ellenére a böngésző nevében kéréseket indít. További csatorna a titkosítatlan átvitel, a rosszindulatú böngészőbővítmény és a megosztott gép böngészőprofilja.

    Tipikus tévedés: csak a hálózati lehallgatást említeni, és kihagyni az alkalmazás saját naplóit, a Referer fejlécet és az XSS-t. A HttpOnly az olvasást nehezíti, de nem szünteti meg a token nevében történő kérések lehetőségét, ezért nem mentesít a rövid élettartam és a szerveroldali visszavonás alól.

  3. Melyik biztonsági kontroll akadályozza meg a session fixationt a legközvetlenebbül, és miért?

    Rövid megoldás: a hitelesítés pillanatában történő session ID csere (regenerálás): a bejelentkezés után a szerver új, véletlen azonosítót ad, és a régi, anonim rekordot érvényteleníti. Így a támadó által ismert, bejelentkezés előtti ID a hitelesítés után már nem használható, mert nem ahhoz a munkamenethez tartozik, amelybe az áldozat belépett. Kiegészítő kontrollok: a munkamenet-azonosító csak cookie-ban, HttpOnly/Secure/SameSite jelzőkkel utazik, és a szerver a bejelentkezés előtti anonim ID-t nem fogadja el hitelesített munkamenetként.

    Tipikus tévedés: a fixációt a jelszó erősségével vagy a cookie HttpOnly jelzőjével összekeverni. A fixation nem jelszófeltörés: a támadó a saját maga által kiváltott ID-t csempészi az áldozathoz, ezért a megoldás az ID hitelesítéskori cseréje és a régi rekord érvénytelenítése, nem a jelszó bonyolultsága.
