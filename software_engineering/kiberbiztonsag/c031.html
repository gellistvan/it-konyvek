9.3 SAST, DAST, IAST és fuzzing

A modern szoftverfejlesztés egyik legnagyobb félreértése, hogy a biztonsági hibákat kizárólag kézi kódreview-val vagy utólagos pen teszttel lehet megtalálni. A gyakorlatban a hatékony biztonsági tesztelés rétegzett: a forráskód statikus elemzése, a futó alkalmazás dinamikus vizsgálata, a kettőt ötvöző interaktív megközelítés és a véletlen vagy félig determinisztikus bemenetgenerálás (fuzzing) egymást kiegészítve fedik le a tipikus hibákat. Ez az alfejezet bemutatja a négy eszközkategória helyét a biztonságos SDLC-ben, azok korlátait, és gyakorlati módszert ad a tömegesen keletkező riasztások priorizálására.

9.3.1 A négy eszközkategória elhelyezése az SDLC-ben

A biztonsági tesztelő eszközök alapvetően két dimenzió mentén osztályozhatók: mikor futnak (fejlesztés közben, build fázisban, futó rendszeren), és milyen információval dolgoznak (forráskód, bináris, hálózati forgalom, futás közbeni végrehajtás). A következő kategóriák terjedtek el:

  • SAST (Static Application Security Testing): statikus elemzés, amely a forráskódot vagy bytecode-ot vizsgálja anélkül, hogy a programot futtatná. Jellemzően a CI/CD folyamatba integrálva a build előtt vagy közben fut.
  • DAST (Dynamic Application Security Testing): dinamikus elemzés, amely a futó alkalmazáshoz hálózati kérésekkel fér hozzá, és a válaszokat vizsgálja biztonsági hibák után kutatva. Általában a deployolt, tesztkörnyezetben futó alkalmazáson alkalmazzák.
  • IAST (Interactive Application Security Testing): az alkalmazást futás közben instrumentáló megoldás, amely a kód és a futtatókörnyezet között elhelyezett szenzorok segítségével észleli a valós támadási mintákat, miközben a kód éppen az adott kérést dolgozza fel. Gyakran a staging vagy tesztkörnyezetben fut.
  • Fuzzing: bemenetgeneráló technika, amely véletlen vagy mutált adatokkal bombázza a program interfészeit, és az összeomlásokat, hibás memóriakezelést vagy nem várt kimeneteket figyeli. Fejlesztői környezetben vagy CI/CD-ben fut.

Az eszközöket nem „vagy-vagy” alapon kell választani, hanem rétegesen: a SAST a fejlesztés legkorábbi fázisában, a DAST a futó rendszeren, az IAST a kettő közötti szürke zónában, a fuzzing pedig a bemenetek robusztusságának tesztelésére.

Az alábbi ábra a két dimenziót egyszerre mutatja: vízszintesen azt, hogy az eszköz mikor fut, függőlegesen azt, hogy milyen információval dolgozik; alul a fejezet későbbi „Jó minta” háromlépcsős pipeline-ja látható.

9.3.2 SAST: statikus elemzés a forráskódból

A SAST-eszközök szintaktikai, adatfolyam- és kontrollfolyam-elemzéssel keresik a hibamintákat. Modern képviselőik (például Semgrep, CodeQL, SonarQube, Bandit) szabályalapú vagy lekérdezésalapú módon dolgoznak. A SAST legfontosabb előnye, hogy a hibát a kód keletkezésének pillanatában képes jelezni, még egyetlen sor sem fut le élesben.

Tekintsük a következő, szándékosan sebezhető Python Flask kódot:

# sebezheto_app.py - SZÁNDÉKOSAN SEBEZHETŐ
import sqlite3
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route('/')
def index():
    # A DAST crawlerek csak bejárható linkből találják meg a paraméteres végpontot.
    return '<a href="/search?q=Alice">Keresés</a>'

@app.route('/search')
def search():
    q = request.args.get('q', '')
    # SZÁNDÉKOS SQL INJECTION: bemenet közvetlen összefűzése
    conn = sqlite3.connect('users.db')
    try:
        cursor = conn.execute("SELECT * FROM users WHERE name LIKE '%" + q + "%'")
        results = cursor.fetchall()
    finally:
        conn.close()
    # SZÁNDÉKOS SSTI ÉS XSS: bemenet escape nélkül a HTML-válaszban és a Jinja-sablonban
    return render_template_string('<h1>Találatok: ' + q + '</h1><ul>{% for r in results %}<li>{{ r }}</li>{% endfor %}</ul>', results=results)

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)

Egy SAST-eszköz, például a Semgrep, az SQL lekérdezés építésének mintáját felismeri: a közvetlen + operátorral összefűzött SQL string-höz bemeneti változó kerül. Jelzése világos, az adatfolyamot visszaköveti a request.args elemtől a execute hívásig. Az XSS helyett itt szerveroldali sabloninjekció (SSTI) a fő hiba: a render_template_string hívásban a felhasználói bemenet a Jinja sablon forrásába kerül, ezért a Jinja a q értékében lévő {{ ... }} kifejezést kiértékeli. A laborban a ?q={{7*7}} ártalmatlan aritmetikai próbával ellenőrizhető, hogy a válasz <h1> címsorában 49 jelenik meg. Az SSTI a környezettől függően a szerveroldali változók, fájlok és akár a folyamat eléréséhez vezethet, ezért súlyosabb, mint a reflektált XSS. A minta emellett XSS-t is mutat, mert a q escapelés nélkül kerül a HTML-címbe; a {{ r }} rekordok viszont a Jinja alapértelmezett escape-elésén mennek át. A SAST-ek a render_template_string és a tainted bemenet kombinációját eltérő pontossággal ismerik fel.

Javított változat: a sablon legyen állandó string, a bemenet csak adatként kerüljön bele, az SQL pedig paraméterezett legyen. A labor seedje is legyen megismételhető, hogy újrafuttatáskor ne duplázódjanak a rekordok:

# javitott_app.py - a sebezhető minta javított változata
import sqlite3
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route('/')
def index():
    return '<a href="/search?q=Alice">Keresés</a>'

@app.route('/search')
def search():
    q = request.args.get('q', '')
    conn = sqlite3.connect('users.db')
    try:
        cursor = conn.execute("SELECT * FROM users WHERE name LIKE ?", ('%' + q + '%',))
        results = cursor.fetchall()
    finally:
        conn.close()
    # Állandó sablon: a bemenet adat, nem sablonforrás; a Jinja escapel.
    return render_template_string(
        '<h1>Találatok: {{ q }}</h1><ul>{% for r in results %}<li>{{ r }}</li>{% endfor %}</ul>',
        q=q, results=results)

if __name__ == '__main__':
    app.run(host='127.0.0.1', port=5000)

A javított változatban a LIKE ? helyőrzőhöz a % karaktereket is paraméterként adjuk át, a kapcsolatot finally zárja le, a sablon pedig nem tartalmaz felhasználói bemenetet.

Korlátok: A SAST nem látja a futás közbeni konfigurációt, a keretrendszer specifikus védelmi mechanizmusait (például a template engine escape funkcióját) vagy a dinamikusan betöltött kódot. Hamis pozitívokat adhat, ha a kódban egyébként létezik bemeneti validálás, amelyet az elemző nem tud megfelelően értelmezni. Hamis negatívjai akkor keletkeznek, ha a hiba csak bizonyos környezeti feltételek mellett lép fel, vagy ha a támadási minta nem szerepel a szabálykészletben.

9.3.3 DAST: dinamikus vizsgálat a futó alkalmazáson

A DAST-eszközök (például OWASP ZAP, Burp Suite) a futó webalkalmazást HTTP-kérésekkel vizsgálják, mint egy támadó, de ellenőrzött módon. Aktív és passzív szkennelést végeznek: a passzív mód a forgalmat figyelve azonosítja a sérülékeny mintákat, az aktív mód pedig különböző payloadokat küld (SQL injection, XSS, path traversal stb.) és a válaszokat elemzi.

A DAST előnye, hogy a ténylegesen futó rendszer viselkedését méri, így olyan hibákat is észlelhet, amelyek nem látszódnak a forráskódból (például a webszerver konfigurációja, a framework bizonyos védelmi viselkedése, vagy a dinamikusan generált tartalom). A fenti Flask alkalmazásban a DAST aktív szkenneléskor SQL injection payloadot küld (' OR '1'='1), és a válasz alapján meg tudja állapítani, hogy a lekérdezés átjutott a bemeneti szűrésen. Az XSS esetében az <script>alert(1)</script> bemenetre a válaszoldalban visszakapott tartalom megvizsgálható: ha a script tagek változatlanul visszaérkeznek, az riasztást vált ki.

Korlátok: A DAST csak az elérhető HTTP interfészeket látja, a belső logika rejtett hibáit (például egy hibás fájlművelet, üzleti logika manipuláció) nem feltétlenül. Az aktív szkennelés mellékhatásokkal járhat, ezért elkülönített tesztkörnyezetben kell futtatni. A teljes lefedettséghez crawlerre van szükség, amely nem mindig jár be minden állapotot (például JavaScript által dinamikusan betöltött útvonalakat). A hagyományos DAST-ok gyakran vakok az autentikáció utáni felületekre, hacsak nem kapnak megfelelő session-kontextust.

9.3.4 IAST: az interaktív köztes réteg

Az IAST az alkalmazás futási környezetébe ágyazott szenzorokkal dolgozik: a kérések beérkezésekor a szenzorok látják a kód pontos végrehajtási útját, a bemenet változók értékét, a függvényhívásokat és az adatbázis-lekérdezéseket. Amikor egy bemenet eljut egy veszélyes sink-hez (például egy SQL lekérdezéshez) anélkül, hogy megfelelő validáláson esett volna át, az IAST riasztást generál. Ezáltal egyesíti a SAST forráskód-közeli látásmódját a DAST futásidejű valóságával.

Az IAST előnye a pontosság: mivel a tényleges adatfolyamot figyeli, a hamis pozitívok aránya jellemzően alacsonyabb, mint a tiszta SAST-nél. Ugyanakkor a szenzorok telepítést és a futtatókörnyezet módosítását igénylik, teljesítményhatással járnak, és csak azokon a felületeken működnek, amelyekre az instrumentáció kiterjed. Az IAST eszközök (például Contrast, Seeker, Dynatrace security része) kereskedelmi megoldások, nyílt forráskódú lefedettségük korlátozott.

9.3.5 Fuzzing: a bemenetek robusztussági tesztje

A fuzzing nem a tipikus webes sebezhetőségek detektálására szolgál, hanem a szoftver bemeneti kezelésének megbízhatóságára összpontosít. A fuzzer véletlen adatokat generál, azokat a célprogramba táplálja, és figyeli a hibákat: szegmenshibák, assert-ek megsértése, váratlan exception, vagy hosszú futási idő. A modern coverage-guided fuzzerek (például libFuzzer, AFL++, Atheris Pythonhoz) a kódbejárási lefedettséget mérik, és a bemeneteket úgy mutálják, hogy új kódutakat fedezzenek fel.

Egy egyszerű Python példa, amelyet fuzzolni lehet:

# fuzz_cel.py - SZÁNDÉKOSAN PONTATLAN BEMENETKEZELÉS
def parse_int(s: str) -> int:
    # Erőforrás-korlát: a hosszkorlát megvan, de nem azonos az elfogadott nyelvvel.
    if len(s) > 10:
        raise ValueError("Túl hosszú")
    return int(s)

def process(data: bytes) -> int:
    # Az errors='ignore' eldobja az érvénytelen UTF-8 sorozatokat, ezért a
    # hibás bájtokból álló bemenet is érvényes szövegként jut tovább.
    text = data.decode('utf-8', errors='ignore')
    n = parse_int(text)
    return n * 2

A fuzzing eredményének értékeléséhez előbb rögzíteni kell a szerződést. Elfogadott bemeneti nyelv: a process bemenete olyan UTF-8 bájtokból álló szöveg, amely pontosan 1–10 ASCII decimális karakter, azaz a ^[0-9]{1,10}$ minta illeszkedik rá; a vezető nullák megengedettek, az előjel, a whitespace és a nem ASCII számjegy nem. Elvárt eredmény: az értelmezett szám kétszerese, egész számként. Harness-invariáns: minden bemenetre vagy a fenti nyelvnek megfelelő eredmény születik, vagy a függvény dokumentáltan elutasít (ValueError a nem megfelelő alakra, UnicodeDecodeError az érvénytelen UTF-8-ra); más kivétel, illetve a nyelven kívüli bemenet elfogadása invariánssértés.

Ebben a példában a valódi szemantikai hiba nem a hosszkorlát hiánya – az len(s) > 10 ág megvan –, hanem hogy a hosszkorlát nem elegendő a nyelv meghatározásához. Az int() elfogadja a " 5 ", "+5", "-5", "5\n" és a nem ASCII decimális számjegyeket tartalmazó alakokat is, a decode(..., errors='ignore') pedig a b'\xff5' bemenetből csendben "5"-öt csinál. Ezek a bemenetek a szándékolt nyelven kívül esnek, mégis sikeres eredményt adnak, ami az invariáns megsértése. A ValueError ezzel szemben elfogadható elutasítás: a fuzzer nem talált hibát, ha a bemenet a nyelven kívüli, de a függvény egyértelműen elutasítja.

A javított változat a nyelvet explicit módon ellenőrzi, és a dekódolási hibát nem nyeli el:

import re

_ALLOWED = re.compile(r"[0-9]{1,10}\Z")

def parse_int(s: str) -> int:
    if not _ALLOWED.fullmatch(s):
        raise ValueError("nem a megengedett decimális alak")
    return int(s)

def process(data: bytes) -> int:
    text = data.decode("utf-8", errors="strict")
    return parse_int(text) * 2

A harnessnek ezt a szerződést kell ellenőriznie, nem elég a kivételeket elkapni:

# fuzz_harness.py
import re
import sys
import atheris

with atheris.instrument_imports():
    from fuzz_cel import process

_ALLOWED_BYTES = re.compile(rb"[0-9]{1,10}\Z")

def TestOneInput(data: bytes) -> None:
    try:
        result = process(data)
    except (ValueError, UnicodeDecodeError):
        return  # dokumentált, elfogadható elutasítás
    if not _ALLOWED_BYTES.fullmatch(data):
        raise AssertionError(f"a nyelven kívüli bemenetet elfogadta: {data!r}")
    assert result == int(data) * 2, f"hibás eredmény: {result}"

if __name__ == "__main__":
    atheris.Setup(sys.argv, TestOneInput)
    atheris.Fuzz()

Futtatás: python3 fuzz_harness.py -runs=100000. A hibás fuzz_cel.py-n a fuzzer várhatóan AssertionError-ral áll meg (például a b'\xff5' bemenetre), a javítotton a megadott futásszám végéig nem talál hibát (a futtatást itt nem ellenőriztük; a harness logikáját tiszta Pythonban ellenőriztük).

Így a fuzzer nem attól „talál hibát”, hogy egy elutasított bemenet kivételt okoz, hanem attól, hogy egy elfogadott bemenet megsérti az elvárt eredményt vagy a bemeneti nyelvet. Az Atheris a nem elkapott kivételt tekinti összeomlásnak, ezért a dokumentált elutasítást a harnessben kell elkapni; a ValueError és a UnicodeDecodeError elkapása nem rejti el a valódi hibákat, mert ezek a szerződés szerinti kimenetek.

Korlátok: A fuzzing erőforrás-igényes, és nem találja meg azokat a biztonsági hibákat, amelyek nem vezetnek összeomláshoz (például jogosultsági problémák vagy adatkiszivárgás). Az alkalmazásrétegben a fuzzing inkább a parser-ek, protokollimplementációk és fájlformátum-feldolgozók tesztelésére alkalmas.

9.3.6 A jelzések priorizálása

A fenti eszközök mindegyike tömegesen termeli a riasztásokat. Egy tipikus SAST futás egy közepes méretű kódbázison több száz vagy több ezer figyelmeztetést adhat, amelyek nagy része hamis pozitív vagy alacsony kockázatú. A védő csapatok akkor járnak el hatékonyan, ha a találatokat nem naiv nagyságrendben javítják, hanem a következő dimenziók mentén értékelik:

  1. Kihasználhatóság (exploitability): A hiba mennyire könnyen és mekkora hatással kihasználható? A CVSS 3.1 pontszám jó kiindulópont, de nem azonos az üzleti kockázattal. A CVSS-alappontszám nem azonos az üzleti kockázattal; azt a következő pont, az elérhetőség és a CVSS környezeti metrikái (például Modified Attack Vector) módosítják.
  2. Elérhetőség (reachability): A támadó valóban eléri-e a sérülékeny kódot a hálózatról? A SAST jelzés gyakran olyan függvényre mutat, amely csak tesztekben vagy admin felületen fut. Ugyanaz a 9,8-as alappontszámú SQL injection egy internetről, hitelesítés nélkül elérhető oldalon nagyobb kockázat, mint egy olyan belső komponensben, amelyet csak a hálózati szegmentáció mögül lehet elérni.
  3. Üzleti hatás: Milyen adat vagy szolgáltatás kerül veszélybe? Az adatvédelmi szempontból érzékeny adatokat kezelő komponens hibája magasabb prioritást kap.
  4. Javítási költség: Mennyi erőfeszítés a hiba kijavítása? Az alacsony költségű, magas kockázatú hibákat azonnal, a magas költségű, alacsony kockázatúakat később érdemes javítani.

A priorizálásra egyszerű pontozós modellt lehet alkalmazni:

prioritás=CVSS×elérhetőség×üzleti súly \text{prioritás} = \text{CVSS} \times \text{elérhetőség} \times \text{üzleti súly}

ahol az elérhetőség és az üzleti súly 0 és 1 közötti, csapatonként kalibrálandó érték. A CVSS 0–10 skálán adott, a szorzat maximális értéke 10. A képlet nem helyettesíti a szakértői döntést, de segít a tömeges találatok sorba rendezésében. A R = L × I kockázati modellhez hasonlóan itt is fontos, hogy a tényezőket dokumentáltan, konzisztens módon határozzuk meg.

Gyakorlati szabály: a SAST-ből érkező jeleket először a reachability alapján szűrjük – ha a sérülékeny kód nem elérhető kívülről, a prioritás alacsony. A DAST-ből érkező jeleket általában magasabb prioritással kezeljük, mert azok a ténylegesen futó rendszeren bizonyítottan elérhetők. A fuzzingből származó hibák pedig a minőségi problémák indikátoraiként szolgálnak: egy összeomlás a termelési rendszeren DoS-t okozhat.

9.3.7 Tipikus támadási és védelmi minták, ellenpéldák

Rossz minta: A csapat csak a SAST kimenetét nézi, és a „zero findings” eredményt a biztonság garanciájának tekinti. Egy adott nyílt forráskódú Python projekt SAST elemzése tiszta lehet, miközben a DAST futás közben talál egy SSRF hibát, amelyet a statikus elemző nem látott, mert a hívás láncolat dinamikus konfigurációtól függött.

Rossz minta: A DAST futtatása éles rendszeren, mert a tesztelő nem akar külön tesztkörnyezetet felépíteni. Ez szolgáltatásmegtagadáshoz vagy adatvesztéshez vezethet, és sérti az etikus tesztelés határait.

Jó minta: A CI/CD folyamat három lépcsőben biztosítja a rétegzést: - A fejlesztői gép pre-commit hookjában futó statikus elemzés (miniatűr SAST) azonnal visszajelzést ad. - A pull request pipeline-ban a teljes SAST fut, és a találatok SARIF formátumban kerülnek a fejlesztői dashboardra. - A tesztkörnyezetbe deployolt build-re automatikusan DAST fut, amely az OWASP ZAP-ot egy dedikált, izolált konténerhálózatban futtatja.

Ellenpélda: A fuzzingot a csapat „kipipálja” évente egyszer, és az összeomlásokat egyszerűen figyelmen kívül hagyja, mert „eddig még senki nem használta ki”. A gyakorlatban a fuzzer által talált hibák a protokollimplementációkban gyakran támadhatók távolról, és a kihasználásuk fejlettebb támadók számára nem megterhelő.

Védelmi minta: A riasztásokat a priorizálás után a kódreview-val együtt kezeljük. A SAST jelzésre a fejlesztő megvizsgálja az adatfolyamot, és ha a hiba tényleges, akkor a javítást a következőképpen dokumentálja: hivatkozás a találatra, a hiba rövid leírása, a javítás elve (például parametrizált lekérdezésre való áttérés), és a verifikáció módja (újra futó SAST, vagy DAST igazolás).

9.3.8 Ellenőrzési, naplózási és dokumentációs szempontok

A biztonsági tesztelés eredményeinek reprodukálhatónak és nyomon követhetőnek kell lenniük. A következő adatokat rögzíteni kell minden vizsgálati futtatáskor:

  • Eszköz és verzió: például Semgrep 1.x, OWASP ZAP 2.15.0, Atheris 2.x. A verziószám eltérései miatt a találatok nem összehasonlíthatóak, ezért a kiadott jelentésekben a pontos verziót fel kell tüntetni.
  • Konfiguráció és szabálykészlet: SAST esetén a használt szabálykészlet (például egy rögzített commitú helyi semgrep-rules könyvtár vagy egyedi YAML), DAST esetén a scan policy (aktív, passzív, súlyossági küszöb). A registryből futásidőben letöltött --config=auto nem reprodukálható, ezért a jelentésben a szabálykészlet forrása és commitja szerepeljen.
  • Célkörnyezet leírása: a tesztelt alkalmazás verziója, a környezet jellege (izolált teszt, staging), a hálózati izoláció módja.
  • Időbélyeg: a futtatás pontos ideje, a build azonosítóval összekapcsolva.
  • Nyers kimenet: a találatokat géppel feldolgozható formátumban (például SARIF, JSON, XML) tároljuk, nem csak képernyőképként.
  • Triage döntés: minden találatra rögzítsük, hogy mit kezdtünk vele: elfogadott hamis pozitív (indoklással), javítva (kódhivatkozással), későbbre halasztva (kockázatindoklással), vagy nem reprodukálható.

A naplózás során a TerraSecure fiktív rendszerben a vizsgálati eredmények egy központi security dashboardba kerülnek, ahol a trendek nyomon követhetők: csökken-e a nyitott találatok száma, javul-e a MTTR (mean time to remediate). A naplóbejegyzések nem tartalmazhatnak valódi hitelesítő adatokat, csak hivatkozásokat.

A dokumentációs gyakorlatok közé tartozik a találatokhoz tartozó „védelmi döntés” mező: miért választottuk az adott védelmi kontrollt (például parametrizált SQL helyett ORM-re váltás), és hogyan igazoltuk a hatásosságát.

9.3.9 Labor: statikus és dinamikus vizsgálat egy izolált mintán

A következő labor bemutatja a SAST és DAST futtatását egy szándékosan sebezhető Flask alkalmazáson, helyi, izolált környezetben. Hatókör: kizárólag a saját gépeden futó ~/cyber-labor/c031/ könyvtárban található alkalmazás. Laborhatár: az alkalmazás és a ZAP egy internal: true compose-hálózaton (c031-lab-net) fut, kimenő forgalom nélkül; az alkalmazás csak ezen a hálózaton, app:5000 néven érhető el, a hostra nincs portpublikálás (a 127.0.0.1:5000 csak a konténeren belül érvényes). Visszaállítás: a labor végén a konténereket és a hálózatot eltávolítjuk. Az előkészítés (a ZAP image letöltése és a Semgrep szabálykészletének rögzítése) hálózatot igényel; maga az elemzés a rögzített image-dzsel és a helyi szabálykészlettel hálózat nélkül is lefuttatható.

Az alábbi ábra a labor topológiáját mutatja a docker-compose.yml alapján: mi fut a hoston, mi a belső hálózaton, és melyik komponens mit ér el.

9.3.10 1. Környezet előkészítése

Hozd létre a munkakönyvtárat:

mkdir -p ~/cyber-labor/c031
cd ~/cyber-labor/c031

Szükséges eszközök: Docker, semgrep (pip-ből vagy futtatható binárisként), és az OWASP ZAP hivatalos, rögzített Docker image-e. A Flask alkalmazás a labor saját konténerében fut, a ZAP ugyanazon az izolált hálózaton éri el a szolgáltatásnevet.

9.3.11 2. A szándékosan sebezhető alkalmazás

Hozd létre a sebezheto_app.py fájlt a fenti kódpélda alapján, az if __name__ == '__main__' blokkal együtt. Emellett szükséged lesz egy SQLite adatbázisra néhány rekorddal. Készíts egy init_db.py fájlt:

# init_db.py - adatbázis inicializálás a laborhoz
import sqlite3

conn = sqlite3.connect('users.db')
# Megismételhető seed: minden futás tiszta táblával indul, így nem duplázódnak a rekordok.
conn.execute('DROP TABLE IF EXISTS users')
conn.execute('CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL)')
conn.execute("INSERT INTO users (name, email) VALUES ('Alice', 'alice@example.invalid')")
conn.execute("INSERT INTO users (name, email) VALUES ('Bob', 'bob@example.invalid')")
conn.commit()
conn.close()
print("users.db létrehozva")

A konténeres futtatáshoz készíts egy Dockerfile-t és egy docker-compose.yml-t. A Flask és a ZAP ugyanazon a belső hálózaton lesz, ezért a ZAP a app szolgáltatásnevet éri el, nem a host gateway-címét:

FROM python:3.12-slim
WORKDIR /app
RUN pip install flask==3.0.3
COPY sebezheto_app.py init_db.py ./
RUN python init_db.py
EXPOSE 5000
CMD ["python", "sebezheto_app.py"]
# docker-compose.yml – izolált SAST/DAST labor
services:
  app:
    build: .
    networks:
      - c031-lab-net
  zap:
    image: ghcr.io/zaproxy/zaproxy:2.15.0
    networks:
      - c031-lab-net
    volumes:
      - ./zap-wrk:/zap/wrk:rw
    depends_on:
      - app

networks:
  c031-lab-net:
    driver: bridge
    internal: true

Indítsd el az alkalmazást, és ellenőrizd a működését az alkalmazás konténerén belül (a ZAP a 4. lépésben fut; hálózati elérését az ottani futás igazolja):

mkdir -p zap-wrk
docker compose up -d --build app
docker compose exec app \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:5000/search?q=Alice').status)"

A ZAP a konténerben a zap (UID 1000) felhasználóként ír a ./zap-wrk könyvtárba; ha a host-felhasználód UID-je (id -u) nem 1000, a compose zap szolgáltatásához add hozzá a user: "${UID}:${GID}" sort, vagy tedd a könyvtárat az 1000-es UID számára írhatóvá, különben a riport írása „Permission denied” hibával elbukik.

A várt eredmény 200. A http://app:5000/search?q=Alice egyben a DAST célútvonala; a gyökér / oldal linket ad rá, hogy a crawler megtalálja. Ellenőrizd az SSTI-t egy ártalmatlan aritmetikai próbával is:

docker compose exec app \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:5000/search?q=%7B%7B7%2A7%7D%7D').read().decode())"

A válaszban a címnek Találatok: 49-et kell tartalmaznia. Ez bizonyítja, hogy a bemenet a Jinja sablonforrásba került; a próba nem használ fájl- vagy parancsvégrehajtást.

9.3.12 3. SAST futtatás Semgrep-pel

A Semgrep telepítése (aktuális utasítás szerint, például pip install semgrep vagy a hivatalos bináris), majd a verzió rögzítése:

semgrep --version

A labor deklaráltan helyi és offline fut, ezért nem használjuk a --config=auto beállítást: az a Semgrep registryből töltené le a szabályokat, és a telemetriai beállításoktól függően hálózati forgalmat is generálhat. Helyette a szabálykészletet az előkészítés során, még hálózattal rendelkező gépen rögzítjük egy ismert commitra, és a laborban már erről a helyi másolatról futtatjuk:

mkdir -p ~/cyber-labor/tools
git clone https://github.com/semgrep/semgrep-rules.git ~/cyber-labor/tools/semgrep-rules
git -C ~/cyber-labor/tools/semgrep-rules checkout <rögzített-commit>

A szabálytárat szándékosan a labor könyvtárán (~/cyber-labor/c031/) kívülre klónozzuk: a semgrep-rules minden szabály mellé szándékosan sebezhető tesztfájlt tartalmaz, és ha a szkennelés a labor könyvtárát vizsgálná, ezek tömeges találatai elnyomnák a sebezheto_app.py találatait.

A <rögzített-commit> helyére a laborjegyzőkönyvbe is beírt commit-hash kerül; így a szabálykészlet verziója később is azonosítható. A futtatás már a helyi könyvtárból történik, telemetria és verzióellenőrzés nélkül:

semgrep scan \
  --config=$HOME/cyber-labor/tools/semgrep-rules/python \
  --metrics=off \
  --disable-version-check \
  --sarif -o semgrep.sarif sebezheto_app.py

A --metrics=off kikapcsolja a használati adatok küldését, a --disable-version-check pedig a futás közbeni verzióellenőrzést. A --config értéke helyi könyvtár vagy YAML fájl legyen, ne registry-azonosító. A futtatást érdemes --network none konténerben vagy unshare -n alatt megismételni: ha így is lefut és ugyanazt a SARIF-ot adja, igazolt, hogy a szabályok és a motor nem igényelnek hálózatot.

Az elemző lánc működését előbb egy saját, ismert próbaszabállyal ellenőrizzük, mert így a valódi szabálykészlet hibája elkülöníthető a környezet hibájától. Készítsünk egy pozitív és egy negatív fixture-t egy külön probe/ alkönyvtárba (mkdir -p probe), hogy a próbafájlok ne kerüljenek a valódi szkennelés céljába:

# probe/probe_positive.py
probe_marker_8f3a = 1
# probe/probe_negative.py
valtozo = 1
# probe/probe-rule.yml
rules:
  - id: c031-probe
    languages: [python]
    severity: INFO
    message: "A próbaszabály illeszkedett."
    pattern: probe_marker_8f3a
semgrep scan --config=probe/probe-rule.yml --metrics=off --disable-version-check probe/probe_positive.py
semgrep scan --config=probe/probe-rule.yml --metrics=off --disable-version-check probe/probe_negative.py

Az első parancsnak egy c031-probe találatot kell adnia, a másodiknak nulla találatot. Ha ez nem teljesül, a hiba a Semgrep telepítésében, a szabályszintaxisban vagy az útvonalban van, nem a vizsgált alkalmazásban.

Ezután futtasd a valódi szabálykészletet a sebezheto_app.py fájlon. A kimenetben figyeld meg a találatokat. Az SQL injection jelzés várhatóan megjelenik, de a szabály azonosítója registry-verziónként és szabálykészlet-commitonként változhat, ezért a riportban a szabály azonosítóját és a szabálykészlet commitját együtt rögzítsd; egy korábbi dokumentációból átvett python.lang.security.audit.sql-injection azonosító nem garantált. Az SSTI-t (és az abból következő XSS-t) előfordulhat, hogy nem találja, mert a sablonba történő összefűzést nem minden szabály kezeli. A találat hiánya önmagában nem bizonyítja a hiba hiányát; a kézi ellenőrzés és a DAST kiegészíti a SAST-ot.

9.3.13 4. DAST futtatás OWASP ZAP-pal

A ZAP ugyanazon a belső hálózaton fut, mint a Flask, ezért a cél a http://app:5000 szolgáltatásnév. A riportot a /zap/wrk írható kötetbe mentjük, mert a ZAP image ezt a könyvtárat használja a kimenetre. Először a baseline (passzív) futás:

docker compose run --rm zap \
  zap-baseline.py -t http://app:5000 -r /zap/wrk/zap-baseline.html

A baseline csak passzív vizsgálatot végez, ezért nem garantál aktív SQLi/XSS találatot; a passzív szabályok a fejlécekre, a cookie-kra, a hibakezelésre és a felfedezett tartalomra koncentrálnak. Ezután külön futásban a full scan (aktív) következik, amely a paraméterezett útvonalat támadja:

docker compose run --rm zap \
  zap-full-scan.py -t "http://app:5000/search?q=Alice" -r /zap/wrk/zap-full.html

A két jelentést hasonlítsd össze: a baseline jellemzően kevesebb és inkább konfigurációs jellegű találatot ad, a full scan vállalja az aktív payloadokat, és a szándékosan sebezhető alkalmazáson megjelenhet az SQL injection és az XSS. A ZAP image verziója rögzített (2.15.0); a frissítés csak tudatos verzióváltással történjen.

9.3.14 5. Eredmények értelmezése és priorizálása

Hasonlítsd össze a két jelentést:

Eszköz Talált hibák Megjegyzés
Semgrep (SAST) SQL injection; SSTI (ha a szabálykészlet tartalmaz erre szabályt) Hamis pozitív? Nem, a kód tényleg sebezhető.
ZAP baseline (passzív) jellemzően fejléc/cookie/hibakezelési jelzések Aktív SQLi/XSS találat nem várható; ez nem hiba, hanem a passzív mód korlátja.
ZAP full scan (aktív) SQL injection, XSS; SSTI (ha a scan-policy tartalmazza) A futó rendszeren, a app:5000/search paraméterezett útvonalán bizonyítja a hibákat.

Priorizálás: a találatok mindegyike elérhető a http://app:5000/search útvonalon (a labor hálózatán belül), tehát a reachability 1,0. Az üzleti súly egy izolált laborban alacsony (0,2), de a hiba típusa (SQL injection) magas CVSS-t kapna, így a priorizálás magas lenne, ha ez egy éles rendszer lenne. A laborban a cél a tanulás, nem a kockázat kezelése, de a döntési folyamatot ugyanúgy dokumentálni kell.

9.3.15 6. Dokumentáció és cleanup

Készíts egy lab-eredmenyek.md fájlt, amely tartalmazza: - A labor időpontját. - Az eszközök verzióját (pl. semgrep --version, docker --version). - A SAST és DAST jelentések elérési útját. - A találatok triage-táblázatát: azonosító, leírás, döntés (javításra ajánlott, hamis pozitív, stb.). - A javítási javaslatot: az SQL injection ellen parametrizált lekérdezés (? placeholder), az SSTI és az XSS ellen állandó sablon, amelybe a q csak sablonváltozóként ({{ q }}) kerül (lásd a javitott_app.py-t). A bemenet HTML-escape-elése a sablonforrásba fűzés előtt nem véd az SSTI ellen: a {{7*7}} a {, } és * karakterek miatt változatlanul 49-re értékelődne.

A labor végén a compose-projekt saját erőforrásait név szerint távolítsd el:

docker compose down --volumes --remove-orphans

A docker compose down a c031-lab-net hálózatot is eltávolítja; globális docker network prune nem szükséges. A Semgrep a hoston fut, a ZAP konténer a --rm miatt a futás után törlődik.

A users.db és a teszteredmények a labor könyvtárban maradhatnak, de valós környezetben az ideiglenes adatokat érdemes törölni.

9.3.16 Mit tanultunk?

  • A SAST, DAST, IAST és fuzzing négy különböző réteget alkotnak, és együttesen fedik le a szoftverhibák széles spektrumát; egyik sem helyettesíti a másikat.
  • A SAST korán, a forráskódból jelez, de hamis pozitívokkal terhelt és nem látja a futásidejű konfigurációt.
  • A DAST a futó rendszeren bizonyít, de csak a hálózati interfészeken lát, és mellékhatásokkal járhat.
  • Az IAST ötvözi a kettő előnyeit, de szenzorokat igényel.
  • A fuzzing a bemeneti robusztusságot teszteli, de a logikai hibákat gyakran nem találja.
  • A jelzéseket mindig priorizálni kell a kihasználhatóság, elérhetőség, üzleti hatás és javítási költség alapján; a CVSS pontszám önmagában nem elég.

9.3.17 Hogyan védjük ki?

  • A fejlesztői környezetben integráljuk a SAST-ot pre-commit hook vagy IDE plugin formájában, hogy a hibák már a kódírás pillanatában láthatók legyenek.
  • A CI/CD folyamatban a teljes SAST futás kaput képezzen; a találatok SARIF formátumban kerüljenek a review folyamatba.
  • A tesztkörnyezetben automatizáljuk a DAST futtatást izolált hálózaton, és a találatokat ugyanabba a triage-csatornába vezessük.
  • A kritikus bemeneti parserek esetében alkalmazzunk fuzzingot a CI/CD részeként, és a hibákat azonnal javítsuk.
  • A riasztásokat dokumentáljuk, a hamis pozitívokat indoklással zárjuk le, és a javításokat verifikáljuk a következő futásban.

9.3.18 Önellenőrző kérdés

Egy fejlesztő SQL injection jelzést kap a SAST-ből, de a DAST nem találja a hibát a futó alkalmazáson. Mi lehet az oka? Legalább három lehetséges magyarázatot adj, és mindegyikhez írd le, hogyan ellenőriznéd.

Elvárt válasz. (1) A SAST hamis pozitív (például a bemenetet egy, az elemző által nem ismert validátor szűri): ellenőrzés a kódútvonal kézi átnézésével és célzott egységteszttel. (2) A sérülékeny kód nem érhető el a DAST számára (admin felület, autentikáció mögött, nem linkelt végpont): ellenőrzés a crawler által bejárt URL-listával és autentikált scan-kontextussal. (3) A DAST csak passzív (baseline) módban futott, vagy a scan-policy nem tartalmazza a releváns payloadot: ellenőrzés a scan-policy és a futási mód naplójából, majd aktív (full) scannel. (4) A hiba csak bizonyos konfigurációban vagy adatállapotban jelentkezik: ellenőrzés IAST-tal vagy célzott, kézi kéréssel.
