16.5 Service deploy, debug és rollback labor

16.5.1 Motiváció

Egy C++ worker daemon üzemeltetése nem áll meg a bináris lefordításánál és átmásolásánál. A systemd unit a szolgáltatás futási szerződése: megmondja, melyik user futtat, milyen resource limit véd, milyen configot olvas, és hogyan áll le. Ha ezt a szerződést nem verifikáljuk deploy előtt, egy rossz Restart=on-failure beállítás könnyen úgynevezett failure loop-ba viszi a szolgáltatást: a worker elindul, hibával kilép, a systemd újraindítja, majd ismét hiba, amíg a daemon el nem éri a start limitet. A rollback sem csupán a régi bináris visszamásolása; a current release pointer, a config séma és a running process együtt alkot egy visszaállítható release-t. Ez a labor egy egyszerű, de teljes deploy service contractját mutatja be.

16.5.2 Definíció és működés

A service release contract egy bináris artifactból, verzióval és build identitással ellátott manifestből, sémázott configból, valamint a systemd unitból és drop-injaiból áll. A unit verify a systemd szintaktikai és unit-tulajdonságok szerinti ellenőrzése, például systemd-analyze verify. Nem helyettesíti az alkalmazás configjának validálását; a kettő egymástól elkülönülő réteg. A failure loop azt jelenti, hogy a processz sikertelenül lép ki, a Restart= policy ismételten újraindítja, és a PID1 végül a start-limit találat után megtagadja a további indítást. A rollback itt nem fájlok visszamásolását jelenti, hanem a current symlink visszairányítását egy korábban már bevált release-re, majd a service restartját.

A systemd három fő réteget fog össze: a unit definíciót, a PID1 által létrehozott cgroupot és a journald-t. A systemctl daemon-reload újraolvassa a unit fájlokat, de a már futó service-t nem indítja újra. A systemctl start indítja a processzt a unit [Service] szekciója szerint, a systemctl stop leállítja, a systemctl restart stop/start párt hajt végre. A systemctl show -p Property parancs a betöltött unit aktuális observed state-jét mutatja, beleértve a PID1 által érvényesített resource control értékeket is. A journal a journalctl -u <unit> csatornán keresztül kapcsolható össze metric extractionnel.

16.5.3 Kidolgozott példa

A laborban a lab-vm1 hoston root felhasználó deployol. A worker neve lab-worker, a release 0.1.0, az előző stabil release 0.0.9. A service user lab-worker rendszerfiók, shell nélkül. A binary a /opt/lab-worker/releases/<version>/bin/lab-worker, a current symlink erre mutat, az adatkönyvtár /var/lib/lab-worker, a config release-enként a /opt/lab-worker/releases/<version>/lab-worker.toml, amelyre a /etc/lab-worker/lab-worker.toml symlink a current-en keresztül mutat.

Először készítsük el a usert és a könyvtárstruktúrát:

# lab-vm1, root
id lab-worker || useradd --system --home-dir /nonexistent \
  --shell /usr/sbin/nologin lab-worker

install -d -o root -g lab-worker -m 0750 /opt/lab-worker/releases/0.1.0/bin
install -d -o root -g lab-worker -m 0750 /opt/lab-worker/releases/0.0.9/bin
install -d -o root -g lab-worker -m 0750 /etc/lab-worker
install -d -o lab-worker -g lab-worker -m 0750 /var/lib/lab-worker

Telepítsük a release artifactot. A manifest.json az artifact tulajdonosát, forrásrevisionjét és build identitását rögzíti:

# lab-vm1, root
# mindkét release binárisa, manifestje és configja a saját könyvtárába
for v in 0.1.0 0.0.9; do
  r=/opt/lab-worker/releases/$v
  install -m 0755 /tmp/lab-worker-$v/bin/lab-worker "$r/bin/lab-worker"
  install -m 0644 /tmp/lab-worker-$v/manifest.json "$r/manifest.json"
  install -m 0640 -o root -g lab-worker \
    /tmp/lab-worker-$v/config/lab-worker.toml "$r/lab-worker.toml"
done
ln -sfn /opt/lab-worker/releases/0.1.0 /opt/lab-worker/current
# a /etc alatti config a current release configjára mutat
ln -sfn /opt/lab-worker/current/lab-worker.toml /etc/lab-worker/lab-worker.toml
stat -L -c '%U:%G %a' /etc/lab-worker/lab-worker.toml
# várt: root:lab-worker 640

A manifest leírja a release-t:

{
  "binary": "lab-worker",
  "version": "0.1.0",
  "source_revision": "lab-src-111",
  "build_id": "lab-worker-0.1.0-20250101",
  "artifact_owner": "platform-lab",
  "config_schema_version": 1,
  "binary_sha256": "replace-with-sha256-from-build"
}

A config megadja a listen címet, state dir-t és log szintet:

# /opt/lab-worker/releases/0.1.0/lab-worker.toml
# (a /etc/lab-worker/lab-worker.toml a current-en át erre mutat)
version = "0.1.0"
listen = "127.0.0.1:8081"
state_dir = "/var/lib/lab-worker"
log_level = "info"

A unit a worker futási szerződése. A ProtectSystem=full a /usr, /boot és /etc fájlrendszereket read-onlyvá teszi, a ReadWritePaths csak a state dir-t engedi. A Restart=on-failure az érdemi hibáknál újraindít, de a SuccessExitStatus= nélkül a SIGTERM-es leállást nem tekinti hibának. A drop-in a resource control értékeket adja meg:

# /etc/systemd/system/lab-worker.service
[Unit]
Description=lab-worker C++ daemon
After=network.target
# explicit start-limit: 60 s alatt legfeljebb 5 indítás
StartLimitIntervalSec=60s
StartLimitBurst=5

[Service]
User=lab-worker
Group=lab-worker
ExecStart=/opt/lab-worker/current/bin/lab-worker \
    --config /etc/lab-worker/lab-worker.toml
Restart=on-failure
RestartSec=2s
TimeoutStopSec=15s
KillSignal=SIGTERM
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=true
ReadWritePaths=/var/lib/lab-worker

[Install]
WantedBy=multi-user.target
# /etc/systemd/system/lab-worker.service.d/10-resource.conf
[Service]
CPUWeight=100
MemoryHigh=512M
MemoryMax=768M
TasksMax=64
IOWeight=100

A deploy után mindig verifikáljuk a unitot és a configot:

# lab-vm1, root
systemd-analyze verify /etc/systemd/system/lab-worker.service
sudo -u lab-worker /opt/lab-worker/current/bin/lab-worker \
  --config /etc/lab-worker/lab-worker.toml --config-check
systemctl daemon-reload

A systemd-analyze verify a unit mellől a lab-worker.service.d/*.conf drop-ineket is beolvassa (a drop-in fájlt argumentumként nem fogadja el); az összefésült képet a daemon-reload után a systemctl cat lab-worker.service mutatja. A --config-check a worker saját, release-szerződésbe foglalt opciója. Ha a config sémája nem egyezik, a bináris nem indul el, és hibakódot ad.

Indítsuk el és végezzünk start/readiness/stop smoke test-et:

# lab-vm1, root
systemctl start lab-worker.service
systemctl is-active lab-worker.service
systemctl show -p ActiveState -p SubState -p MainPID lab-worker.service
journalctl -u lab-worker.service --since "-2 minutes" --no-pager
ss -lnp | grep 8081

A systemctl is-active kimenete active kell legyen, a SubState running, a MainPID egy pozitív PID, a journalban a worker listening on 127.0.0.1:8081 üzenete, a ss kimenetben a listener socket. A resource limit és permission fixture ellenőrzése:

# lab-vm1, root
systemctl show -p User -p Group -p MemoryHigh -p MemoryMax -p CPUWeight \
  -p NoNewPrivileges -p ProtectSystem lab-worker.service

# 1. mode-réteg: a hoszt namespace-ében a könyvtár módja tilt
sudo -u lab-worker touch /etc/lab-worker/test
# várt (illusztratív): touch: cannot touch '/etc/lab-worker/test':
#   Permission denied

# 2. sandbox-réteg: a unit beállításaival futtatott ideiglenes szolgáltatás
systemd-run --wait --pipe -p User=lab-worker -p ProtectSystem=full \
  touch /etc/lab-worker/test
# várt (illusztratív): touch: cannot touch '/etc/lab-worker/test':
#   Read-only file system

A MemoryHigh a memory throttle pont, a MemoryMax a hard limit. A két permission-teszt két külön réteget mutat. A hosti sudo -u hívásra a unit sandboxa nem hat: ott a /etc/lab-worker root:lab-worker 0750 módja (nincs csoportírás) adja a Permission denied-et. A ProtectSystem=full read-only mountját csak a unit kontextusában (például systemd-run -p ProtectSystem=full) lehet igazolni; ott az üzenet Read-only file system, akkor is, ha a mód engedné az írást.

A metrikát a journalból és a systemd propertykből nyerjük ki. Ez illusztratív jq alapú extrakció:

# lab-vm1, root
# a journal JSON-ban a PRIORITY string, ezért számmá alakítjuk
journalctl -u lab-worker.service -o json --since "-10m" \
  | jq -s 'length as $n | {log_lines_10m: $n,
      errors_10m: ([.[] | select((.PRIORITY|tonumber) <= 3)] | length)}'
systemctl show lab-worker.service -p CPUUsageNSec -p MemoryCurrent \
  -p NRestarts \
  | awk -F= 'BEGIN { m["CPUUsageNSec"]  = "cpu_usage_nsec"
                    m["MemoryCurrent"] = "memory_current_bytes"
                    m["NRestarts"]     = "restarts_total" }
             $2 ~ /^[0-9]+$/ { printf "lab_worker_%s %s\n", m[$1], $2 }'

Az átalakítás a systemd tulajdonságneveket explicit leképezéssel Prometheus-szerű metrikanévvé alakítja, a nem numerikus értékeket (például [not set]) kihagyja. A pontos property nevek a labhost systemd verziójától függenek, így ezeket ellenőrizni kell.

Az alábbi ábra lépésenként mutatja, mikor egyezik a futó processz a current symlinkkel (stored és observed state), alatta a 16.5.4 failure loop ágával.

A rollback a current symlink visszairányítása és a service restartja:

# lab-vm1, root
r=/opt/lab-worker/releases/0.0.9
# a symlink-csere csak sikeres config-check után
if test -x "$r/bin/lab-worker" && sudo -u lab-worker "$r/bin/lab-worker" \
     --config "$r/lab-worker.toml" --config-check; then
  ln -sfn "$r" /opt/lab-worker/current
  systemctl restart lab-worker.service
fi
/opt/lab-worker/current/bin/lab-worker --version
systemctl is-active lab-worker.service
journalctl -u lab-worker.service --since "-1 minute" --no-pager

A desired state: a current symlink (és vele a config) a 0.0.9-re mutat, a --version a 0.0.9-et írja ki, a service active, a journalban nincs hiba. A rollback akkor hiteles, ha a korábbi release binárisa és configja változatlanul működik.

16.5.4 Hibák és ellenpróbák

A leggyakoribb hiba a failure loop. Tünet: a systemctl status lab-worker.service kimenetében start-limit-hit vagy a Restart számlálója gyorsan növekszik. Hipotézis: a config file sérült, a state dir hiányzik, vagy a worker exit code nem nulla. Adatgyűjtés:

# lab-vm1, root
journalctl -u lab-worker.service -n 50 --no-pager
systemctl show -p NRestarts lab-worker.service
systemctl show -p ExecMainCode -p ExecMainStatus lab-worker.service

Ha a journalban config parse failed: invalid listen szerepel, a configot javítjuk. Ezután a failure state resetelése és az indítás:

# lab-vm1, root
systemctl reset-failed lab-worker.service
systemctl start lab-worker.service
systemctl is-active lab-worker.service

A reset-failed törli a start-limit számlálót; anélkül a javított config ellenére sem indul újra a service.

A shutdown hiba tünete: a systemctl stop 15 másodpercnél tovább tart, a journalban Main process exited, code=killed, status=9/KILL. Hipotézis: a worker nem kezeli a SIGTERM-et, ezért a TimeoutStopSec=15s után a systemd SIGKILL-t küld. A diagnózist a journal és a processz exit state visszaigazolja. A javítás a worker oldalán a SIGTERM graceful kezelése, vagy ha átmeneti mentés kell, a TimeoutStopSec és a KillSignal módosítása. A laborban a SIGKILL ténye a systemctl status kimenetéből is látszik.

A version mismatch ellenpróbája: a config version = "0.1.0", de a régi 0.0.9 binary --config-check-je elutasítja, mert a séma 0. A rollback során tehát nem elég a binárist visszaállítani; a hozzá tartozó configot is. Ezért tároljuk a configot release-enként (/opt/lab-worker/releases/<version>/lab-worker.toml), és ezért mutat a /etc/lab-worker/lab-worker.toml symlink a current-en keresztül: a current cseréje a binárist és a configot együtt váltja, a csere előtt pedig a célrelease --config-check-je fut.

16.5.5 Feladatok

16.5.5.1 F1 – Unit verify és effektív resource policy

A lab-vm1 hoston futtasd a systemd-analyze verify parancsot a lab-worker.service unitra és a drop-inra, majd a systemctl cat lab-worker.service kimenetéből állapítsd meg, hogy mekkora a MemoryHigh és MemoryMax érték. Magyarázd el, miért kell a MemoryHigh értékét a MemoryMax alá vinni, és miért nem elég a MemoryMax önmagában a jól működő terheléshez.

16.5.5.2 F2 – Release deploy, smoke test és rollback

A lab-vm1 root felhasználójaként deployold a 0.1.0 release-t a fenti manifesttel, configgal, userrel és unit drop-innal. Indítsd a service-t, ellenőrizd a readiness-t, majd rollbackelj a 0.0.9 release-re. A feladat postconditionje: a current symlink a 0.0.9-re mutat, a lab-worker --version a 0.0.9-et írja ki, a systemctl is-active lab-worker.service kimenete active, és a journalban az utolsó 2 percben nincs error szintű üzenet.

16.5.5.3 F3 – Failure loop diagnosztika és recovery

A lab-worker.toml configban állítsd a listen mezőt érvénytelen abc értékre, majd indítsd el a service-t. Diagnosztizáld a kialakult failure loopot a journal, az NRestarts és a start-limit állapot alapján. Javítsd a configot, resetteld a failure state-et, és indítsd a service-t. Igazold, hogy a service aktív, a MainPID pozitív, és a journalban a config parse failed nem szerepel.

16.5.6 Megoldások

16.5.6.1 F1 megoldása

# lab-vm1, root
systemd-analyze verify /etc/systemd/system/lab-worker.service
systemctl cat lab-worker.service

A systemctl cat mutatja a unit és a drop-in összefésült képét. A MemoryHigh=512M, MemoryMax=768M. A MemoryHigh a cgroup v2 memória-throttle pontja, amely a processzt lassítja, amikor a felhasználás eléri a beállított értéket. A MemoryMax a kemény limit, amely felett a kernel OOM kill-t hajthat végre a cgroupban. Ha a MemoryHigh nagyobb a MemoryMax-nál, a throttle pont soha nem érhető el a hard limit előtt, így a MemoryHigh hatástalan. A MemoryHigh alacsonyabbra állítása a hirtelen memóriakitörés esetén ad lassulást és observability ablakot, mielőtt a MemoryMax OOM-ot váltana ki.

16.5.6.3 F3 megoldása

A configot rontsd el:

# /etc/lab-worker/lab-worker.toml
version = "0.1.0"
listen = "abc"
state_dir = "/var/lib/lab-worker"
log_level = "info"

Indítás után a systemd Restart=on-failure miatt többször újraindítja a service-t, amíg a start-limit el nem éri:

# lab-vm1, root
systemctl start lab-worker.service
systemctl status lab-worker.service --no-pager -l
journalctl -u lab-worker.service -n 50 --no-pager
systemctl show -p NRestarts lab-worker.service
systemctl show -p ActiveState -p SubState -p Result lab-worker.service

A hipotézis: a listen mező érvénytelen, a worker --config-check és a valódi indítás is hibával kilép. A journalban config parse failed: invalid listen szerepel. A Restart számláló növekszik, a Result start-limit hibát mutat.

Javítás: a listen visszaállítása 127.0.0.1:8081-re:

# lab-vm1, root
# szerkeszd a configot
systemctl reset-failed lab-worker.service
systemctl start lab-worker.service
systemctl is-active lab-worker.service
systemctl show -p MainPID lab-worker.service
journalctl -u lab-worker.service --since "-1 minute" --no-pager

Postcondition: a service active, a MainPID pozitív, a journalban nincs config parse failed, és a NRestarts nem növekszik tovább.

16.5.7 Rövid összefoglaló

A service deploy akkor ismételhető, ha a bináris artifact, verzió, config séma, unit és drop-in egyaránt verifikált. A systemd-analyze verify a unit syntaxisát, a worker --config-check az alkalmazásconfigot validálja; a kettő együttesen védi ki a failure loopot. A resource control és permission fixture a systemctl show propertykben ellenőrizhető, a journal és a propertyk metrikává normalizálhatók. A rollback a current symlink cseréjéből és a service restartjából áll, de a config sémának is a release-hez kell tartoznia. Továbbhasznált definíciók: service release contract, failure loop, rollback symlink.

  • systemd-analyze verify (unitfájl-argumentum): systemd-analyze(1) – https://manpages.ubuntu.com/manpages/noble/man1/systemd-analyze.1.html; systemd-run -p … --wait --pipe: systemd-run(1) – https://manpages.ubuntu.com/manpages/noble/man1/systemd-run.1.html
  • journal JSON-mezők (a PRIORITY string): systemd.journal-fields(7) – https://www.freedesktop.org/software/systemd/man/latest/systemd.journal-fields.html; journalctl(1) -o json – https://manpages.ubuntu.com/manpages/noble/man1/journalctl.1.html; jq tonumber: jq 1.7 manual – https://jqlang.github.io/jq/manual/v1.7/
  • Prometheus metrikanév-konvenciók: https://prometheus.io/docs/practices/naming/

Reprodukciós állapot: dátumozott futtatási napló a 24.04-es labhoston még nem készült; a példák laborban ellenőrizendők.

Ellenőrzési hiányok: a lab-worker bináris, a --config-check opció, a manifest.json séma és a config példa nem valós laborból származik, hanem illusztratív. A systemctl show --property nevek, például CPUUsageNSec, MemoryCurrent, a labhost tényleges systemd verzióján ellenőrizendők.
