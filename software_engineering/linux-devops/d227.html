46.2 Remote state, locking és recovery

46.2.1 Motiváció

Amikor egy csapat egyetlen fejlesztő helyett több emberrel üzemelteti ugyanazt az infrastruktúrát, a lokális terraform.tfstate fájl azonnal szűk keresztmetszetté válik. Két párhuzamos apply felülírhatja egymás állapotát, a titkos adatokat tartalmazó fájl a laptopon utazik, a rosszul mentett verzióból pedig nem tudunk visszaállni. A remote state ezt a problémát úgy oldja meg, hogy a state egy megosztott, védett, verziózott objektumtárolóba kerül, ahol a hozzáférés, a konkurencia és a helyreállítás szerződésbe foglalható. Ez az alfejezet azt tanítja meg, hogyan adjunk a state-hez ownership-, access-, backup- és concurrency-szerződést, és mi a különbség a state helyreállítása és a tényleges felhőerőforrás helyreállítása között.

46.2.2 Definíció és működés

46.2.2.1 Remote state és backend

A remote state az OpenTofu/Terraform állapotfájljának olyan tárolása, amely nem a lokális fájlrendszeren, hanem egy megosztott, hálózati szolgáltatásban él. A backend az a konfigurációs blokk, amely meghatározza, hová kerül a state, hogyan történik a lock, és milyen identitással férünk hozzá. A remote backend tipikusan objektumtárolóra (például AWS S3, Google Cloud Storage, Azure Blob) és egy lock-táblára (például AWS DynamoDB) épül.

A remote state egy állapotfájl, amely nemcsak az erőforrások azonosítóit és függőségeit tartalmazza, hanem olyan érzékeny attribútumokat is, mint:

  • adatbázis jelszavak,
  • TLS privát kulcsok,
  • IAM access key szövege,
  • belső végpontok és VPC CIDR-ek.

Ezért a remote state-et nem szabad verziókezelőbe (Git) commitolni, és a tárolón titkosítást, verziózást és szigorú hozzáférést kell biztosítani.

46.2.2.2 Remote backend és identity

A remote backendhez a klienst (OpenTofu CLI, CI runner, lokális fejlesztő) egy adott felhő-identitás nevében fér hozzá. Ez lehet:

  • lokális fejlesztő esetén egy IAM user vagy egy role-t felvevő sso login,
  • CI rendszernél egy ephemerális role,
  • szolgáltatás esetén workload identity.

A backendnek adott jogosultságot a legkisebb jogkör elve szerint kell meghatározni: a state olvasásához, írásához, lockoláshoz és feloldáshoz külön policy elemek tartoznak. Például AWS S3 esetén az s3:ListBucket a bucketre (a key prefixre szűkítve), a s3:GetObject, s3:PutObject, s3:DeleteObject engedélyek a state fájlra, a DynamoDB-nél pedig dynamodb:GetItem, dynamodb:PutItem, dynamodb:DeleteItem a lock-táblára. Ügyelni kell arra, hogy a titkosítás (például SSE-KMS) további IAM jogot igényelhet a KMS kulcsra is.

46.2.2.3 State lock és lease

A state lock olyan kölcsönös kizárási mechanizmus, amely biztosítja, hogy egyszerre csak egy folyamat módosíthassa a state-et. Mivel a state az infrastruktúra „source of truth”-ja, két párhuzamos apply esetén az egyik a másik által már megváltoztatott valóságot próbálná frissíteni, ami elveszett update-hez vagy inkonzisztens tervekhez vezetne.

A Terraform/OpenTofu S3 backendjének lockja nem lease: a lock-tábla rekordja egy egyedi kulcsot (LockID) és egy Info mezőt tartalmaz (ID, Operation, Who, Created), lejárati időbélyeg vagy TTL nélkül. Ha a folyamat szabályosan befejezi a műveletet, törli a rekordot; ha a folyamat keményen megszakad, a rekord lejárat nélkül ott marad, amíg a tulajdonos el nem engedi, vagy force-unlock nem törli. Várakozással tehát nem oldódik fel; a hibajelenséget diagnosztizálni kell.

A lease ezzel szemben a lock időhöz kötött bérlete: a tulajdonosnak rendszeresen meg kell újítania, különben lejár, és más átveheti. Lease-alapú (TTL-es) lockot más rendszerek adnak, például az etcd lease vagy a Kubernetes Lease objektum; ott a lejárat a fencing-problémát hozza (lásd M1).

46.2.2.4 Interrupted apply

Ha az apply futása közben a hálózat megszakad, a CI folyamat kemény leállítást kap (például SIGKILL timeout után), vagy a lokális gép lefagy, a lock-rekord a táblában maradhat. (Egy SIGINT, azaz Ctrl-C, erre nem elég: a Terraform/OpenTofu ilyenkor „graceful stop”-ot végez – megvárja a folyamatban lévő provider-hívásokat, kiírja a state-et és elengedi a lockot.) A következő plan vagy apply ekkor hasonló hibát ad:

Error acquiring the state lock

Ilyenkor meg kell győződni arról, hogy valóban nincs másik aktív folyamat. Ha a lock gazdája már nem fut, akkor a force-unlock parancs törli a rekordot. A force-unlock veszélyes művelet, mert ha tévedünk, és mégis fut egy másik apply, akkor két folyamat fogja módosítani a state-et és a felhőerőforrásokat. Ezért a lock ID-t a hibaüzenet Lock Info blokkjából kell kivenni, és a tulajdonos folyamat kilétét ellenőrizni kell.

46.2.2.5 Import, moved és state műveletek

A state nemcsak a plan/apply terméke, hanem explicit módon is manipulálható. A fontosabb műveletek:

  • Import: a configban már deklarált resource-címhez a meglévő valós erőforrás felvétele a state-be (tofu import ADDRESS ID; a resource blokknak léteznie kell, különben a parancs hibát ad). Deklaratívan import { to = …, id = … } blokkal is megtehető (OpenTofu 1.5+/Terraform 1.5+); ennél a tofu plan -generate-config-out=generated.tf a hiányzó resource blokk vázlatát is legenerálhatja. Ezután a plan már követni tudja a driftet.
  • Moved: amikor egy erőforrás címét megváltoztatjuk a konfigurációban, a moved blokk jelzi a state-nek, hogy a régi címet az újra kell képezni, elkerülve a törlés/újraépítés folyamatot.
  • State operation: tofu state list, tofu state mv, tofu state rm, tofu state pull, tofu state push – ezek a state fájl tartalmának ellenőrzésére és alacsony szintű javítására szolgálnak. A mv egy erőforrás áthelyezése egy másik címre, a rm eltávolítása a state-ből anélkül, hogy a valós erőforrás megsemmisülne.

Ezek a műveletek mind potenciálisan veszélyesek, mert a state módosítása anélkül, hogy a valós erőforrást is módosítanánk, driftet okozhat. Ezért minden ilyen parancs előtt backupot kell készíteni.

46.2.2.6 Backup, encryption és restore

A remote state backend általában támogatja a verziózást. Ennek segítségével a state minden alkalommal mentésre kerül, amikor megváltozik. A verziózás nem helyettesíti a valós backupot, de biztosítja a rövid távú visszamenő visszaállítást. Emellett tofu state pull parancsot rendszeresen futtathatunk, és a kimenetet titkosított, hosszú távú tárolóba menthetjük.

A titkosítás két szinten történik:

  • Encryption at rest: a bucket szintjén bekapcsolt SSE-S3 a fizikai adathordozó ellen véd, de átlátszó: aki s3:GetObject jogot kap, a visszafejtett state-et olvassa. Ha a hozzáférést a bucket-jogtól függetlenül szűkíteni kell, SSE-KMS customer managed kulcs kell, amelynek kulcspolicyja csak a state-szerepköröknek ad kms:Decrypt/kms:GenerateDataKey jogot.
  • Encryption in transit: minden kérés TLS-en keresztül történik.

A restore akkor hiteles, ha utána tofu plan nem mutat semmilyen különbséget a jelenlegi konfiguráció és a visszaállított state között. Ha a state elveszett, a visszaállítás csupán a state-et hozza vissza, de a valós erőforrásokhoz képest drift lehet; ilyenkor a tofu import szükséges lehet.

46.2.2.7 State workspace, account és environment isolation

A state-t érdemes erős határokkal elkülöníteni a különböző környezetek között. Két elterjedt modell:

  • Workspace: ugyanazon backend konfigurációban a workspace megváltoztatja a state kulcsát (például a dev workspace state-je az S3 backendben env:/dev/environments/dev/terraform.tfstate kulcson él; a prefix a workspace_key_prefix argumentummal állítható, alapértéke env:). Ez hasznos ideiglenes ágaknál, de nem ad elég erős izolációt, mert ugyanaz a bucket és lock-tábla.
  • Separate backend config: minden környezetnek külön backend-kulcs és gyakran külön bucket, külön lock-tábla, sőt külön felhő-account. Ez a production-recommended megoldás, mert az account határ hiba esetén is védi a production state-et.

A workspace-ek és a state fájlok elkülönítése nemcsak a szervezést szolgálja, hanem a failure domain csökkentését is: ha egy fejlesztő véletlenül törli a staging state-et, az ne érintse a production-t.

46.2.3 Kidolgozott példa: S3 remote state DynamoDB lockkal

A példa egy AWS sandbox accountot használ. Hipotetikus, nem futtatott parancsok; az azonosítók és a régió tetszőlegesek, de a labon kívül nem léteznek. Cél: egy kis S3 bucket létrehozása OpenTofuval, remote state-tel és lockkal.

Előfeltételek:

  • AWS sandbox account, lab-tfstate-123456789012 nevű S3 bucket és lab-tfstate-lock nevű DynamoDB tábla a us-east-1 régióban.
  • A lokális gép (labVM) rendelkezik friss OpenTofu CLI-vel és IAM credentialokkal.

Hozzuk létre a main.tf fájlt a backend blokkal és egy egyszerű erőforrással:

terraform {
  required_version = ">= 1.6"
  backend "s3" {
    bucket         = "lab-tfstate-123456789012"
    key            = "environments/dev/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "lab-tfstate-lock"
  }
}

resource "aws_s3_bucket" "example" {
  bucket = "lab-example-bucket-123456789012"
}

A dynamodb_table alapú lock a példa >= 1.6 verzióprofiljában a szokásos megoldás. Újabb kiadásokban (a Terraform 1.10–1.11, illetve az OpenTofu 1.10 körül; a pontos verzió a hivatalos changelogból ellenőrizendő) a natív S3-lock (use_lockfile = true) az ajánlott, a dynamodb_table pedig elavult; a labor verzióprofiljához kell igazítani.

Futtassuk az inicializálást és az alkalmazást:

# Target: labVM (UID=1000), us-east-1 sandbox account
tofu init
tofu plan
tofu apply

Várt kimenet init után: a backend inicializálódik, a state elérési útja a S3 bucketben van. A plan során a CLI lockot szerez a DynamoDB táblán, majd a zárás után elengedi. A táblában emellett tartósan megmarad egy lab-tfstate-123456789012/environments/dev/terraform.tfstate-md5 LockID-jú, Digest mezős rekord: az S3 backend ezzel ellenőrzi a state konzisztenciáját, ez nem lock. A tofu apply létrehozza a bucketet, és a state fájl a távoli bucketbe kerül.

A state megtekintése:

tofu state list
# Várt: aws_s3_bucket.example

A lock működésének ellenőrzéséhez indítsunk egy hosszú apply folyamatot egy terminálban, majd egy másik terminálban próbáljunk plan-t futtatni:

# 1. terminál: hosszú apply; a meglévő bucket mellett "No changes" lenne,
# ezért a lab egy time_sleep resource-ot (create_duration = "120s") ad hozzá
tofu apply -auto-approve
# 2. terminál: rögtön ezután
tofu plan

A második parancs várhatóan hibát ad:

Error acquiring the state lock: ConditionalCheckFailedException

A lock ID a hibaüzenet Lock Info blokkjában látható. Ha az első folyamat szabályosan véget ér (vagy Ctrl-C-vel, gracefully áll le), a lock eltűnik, és a második parancs lefut. Ha az első folyamat keményen megszakad (SIGKILL, gép- vagy hálózatkiesés), a lock lejárat nélkül fennmarad.

46.2.4 Hibák és ellenpróbák

46.2.4.1 Tünet: Error acquiring the state lock

Hipotézis: egy másik folyamat tartja a lockot, vagy egy korábbi megszakadt futás hagyta hátra.

Adatgyűjtés: A hibaüzenet Lock Info blokkjából (ID, Who, Operation, Created) azonosítsuk a tulajdonost, és ellenőrizzük azon a gépen vagy CI-jobon, hogy fut-e még (pl. pgrep -a tofu, illetve a CI-job állapota). A DynamoDB tábla Info mezős rekordja ugyanezt mutatja.

Egy változtatás: Ha nincs aktív folyamat, használjuk a tofu force-unlock -force <lock_id> parancsot (a kapcsoló a lock ID előtt áll). Ha van aktív folyamat, ne force-unlockoljunk, hanem várjuk meg, amíg befejeződik, vagy állítsuk le azt a folyamatot; a lock magától nem jár le.

Verifikáció: Újra tofu plan, ami sikeresen lefut.

Ellenpróba: Ha force-unlock után a plan ismét lock hibát ad, akkor egy másik folyamat (újra) lockot szerzett; a Lock Info új ID-jét és tulajdonosát kell megvizsgálni.

46.2.4.2 State vs resource recovery

A tünet: a state fájl sérült vagy törlődött, de az erőforrások a felhőben megvannak. Ha csak a state-t állítjuk vissza egy backupból, a tofu plan diff-et mutat, mert a state nem tartalmazza az aktuális resource konfigurációt. Ekkor nem a backupot kell erőltetni, hanem a state-et kell a valósághoz igazítani: tofu import a hiányzó leképezésekre (a configban deklarált címekre), moved blokk az átnevezett címekre. A resource recovery más: ha a felhőerőforrás törlődik, a state-ben továbbra is szerepel, és a tofu apply újból létrehozza, ha a konfiguráció változatlan.

Ezért a kettőt mindig külön kell kezelni:

Művelet State hatás Resource hatás
tofu state rm eltávolítja a state-ből nem törli a felhőerőforrást
tofu destroy eltávolítja a state-ből törli a felhőerőforrást
tofu import hozzáadja a state-hez nem hozza létre, csak felveszi
Backup restore visszaállítja a state-et nem érinti a felhőerőforrásokat

46.2.5 Feladatok

46.2.5.1 F1 – Magyarázó feladat

Magyarázza el, mi a különbség a Terraform/OpenTofu S3 backend lejárat nélküli state lockja és egy lease-alapú (TTL-es) lock között, és miért nem elegendő egy lokális fájlrendszerbeli lock fájl remote csapat esetén. Adjon meg egy-egy hibajelenséget mindkét modellre (beragadt lock, illetve lejárt, de még élő tulajdonos), és írja le, mit tesz.

Postcondition: A hallgató szövegesen meg tudja indokolni a lock szükségességét, a két modell különbségét, és a force-unlock kockázatát.

46.2.5.2 F2 – Adminisztrációs és konfigurációs feladat

Állítson be OpenTofu remote S3 backendet DynamoDB lockkal egy sandbox accountban. A bucketben kapcsolja be a verziózást és a titkosítást (SSE-S3). Hozzon létre egy egyszerű erőforrást (például egy S3 bucketet), majd ellenőrizze, hogy a state fájl a távoli bucketben van, és hogy a lock tábla rekordja létrejön-e az apply alatt.

Postcondition: A tofu state list mutatja az erőforrást. A S3 bucketben létezik a environments/dev/terraform.tfstate objektum. A DynamoDB táblában az apply befejezése után nincs Info mezős lock-rekord (aws dynamodb scan --table-name lab-tfstate-lock --filter-expression 'attribute_exists(Info)' → Count: 0); a lab-tfstate-123456789012/environments/dev/terraform.tfstate-md5 digest rekord megmarad.

46.2.5.3 F3 – Diagnosztikai és recovery feladat

Szimuláljon interrupted apply-t: indítson egy legalább egy percig tartó tofu apply parancsot, majd szakítsa meg keményen (kill -KILL; a Ctrl-C graceful stopot végez és elengedi a lockot). Ellenőrizze, hogy a lock a DynamoDB táblában marad. Készítsen a megszakítás után, a force-unlock előtt tofu state pull segítségével backupot a state-ről, majd használja a tofu force-unlock parancsot a lock felszabadítására. Törölje a state fájlt a bucketből (vagy ürítse ki), majd állítsa vissza a backup segítségével tofu state push parancsot használva. Ellenőrizze tofu plan futásával, hogy nincs diff.

Postcondition: A lock megszűnt, a state visszaállt, és a tofu plan nem mutat változtatást a jelenlegi konfigurációhoz képest.

46.2.6 Megoldások

46.2.6.1 M1 – Magyarázó

A state lock kizárólagos jog a state módosítására. A Terraform/OpenTofu S3 backendjében ez egy lejárat nélküli rekord (LockID + Info): a tulajdonos elengedi, vagy force-unlock törli; magától soha nem jár le. A lease általános fogalomként a lock időkorlátos bérlete (például etcd lease, Kubernetes Lease): a tulajdonosnak meg kell újítania, különben lejár, és más átveheti. A lokális fájlrendszerbeli lock fájl nem működik remote csapatban, mert minden gép saját fájlrendszerrel rendelkezik, és nem látják egymás lockját.

Hibajelenség a lejárat nélküli lockkal: a keményen megszakított apply után a lock beragad, és várakozással nem oldódik fel; a tulajdonos ellenőrzése után force-unlock kell. Hibajelenség a lease-zel: a lease lejár (például a tulajdonos szünetel vagy hálózatilag elszigetelődik), de a régi folyamat ténylegesen még fut, és egy új folyamat megszerzi a lockot, miközben a régi még ír. Ilyenkor a lejárat hamis biztonságot ad; ezt fencing tokennel (monoton növekvő lock-sorszám, amelyet a tároló ellenőriz) lehet kivédeni. Mindkét esetben ellenőrizni kell a tulajdonos folyamat állapotát.

46.2.6.2 M2 – Konfigurációs

A backend blokk a fentiekben látható. A bucket verziózását és titkosítását manuálisan kell bekapcsolni az AWS konzolon vagy CLI-vel. A CLI parancsok:

# Target: labVM (UID=1000), us-east-1 sandbox account
aws s3api put-bucket-versioning \
  --bucket lab-tfstate-123456789012 \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket lab-tfstate-123456789012 \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'

(Megjegyzés: a aws parancs itt illusztratív; a pontos API a jelenlegi AWS CLI verziójában ellenőrizendő. Az SSE-S3 csak a fizikai adathordozó ellen véd: aki s3:GetObject jogot kap, olvassa a state-et. Szűkebb olvasási körhöz SSE-KMS customer managed kulcs és szűk kulcspolicy kell.)

Ezután tofu init és tofu apply. A tofu apply közben a DynamoDB táblában a digest rekord mellett egy Info mezős lock-rekord is van; a befejezés után a lock-rekord eltűnik, a …/terraform.tfstate-md5 digest rekord megmarad. Ezt ellenőrizheti:

aws dynamodb scan --table-name lab-tfstate-lock \
  --filter-expression 'attribute_exists(Info)' --select COUNT
# várt az apply után: "Count": 0

46.2.6.3 M3 – Diagnosztikai és recovery

  1. Indítsunk egy legalább 60 s-ig tartó applyt: a configba egy time_sleep resource kerül (hashicorp/time provider, create_duration = "120s"), majd tofu apply -auto-approve. Egy másik terminálban keményen leállítjuk a folyamatot (Ctrl-C vagy kill -INT erre nem jó, mert graceful stopot végez és elengedi a lockot):
kill -KILL "$(pgrep -f 'tofu apply')"

A lock a táblában marad. A lock ID lekérdezése:

aws dynamodb scan --table-name lab-tfstate-lock \
  --filter-expression 'attribute_exists(Info)'
  1. Készítsünk backupot a megszakítás után, a force-unlock előtt (így a backup a félbeszakadt apply utáni állapotot rögzíti, nem az apply előttit):
tofu state pull > /tmp/dev-state-backup.tfstate
  1. Force-unlock (a -force kapcsoló a lock ID előtt áll):
# LOCK_ID: a Lock Info / a lock-rekord ID mezője
tofu force-unlock -force "$LOCK_ID"
  1. Töröljük a state objektumot:
aws s3 rm s3://lab-tfstate-123456789012/environments/dev/terraform.tfstate
  1. Pusholjuk vissza a backupot:
tofu state push /tmp/dev-state-backup.tfstate
  1. Ellenőrizzük:
tofu plan

Várt: No changes. Your infrastructure matches the configuration. Ha a megszakított apply félig létrehozott erőforrást hagyott (például a time_sleep nem került a state-be), a plan ezt létrehozandóként mutatja; ezt a következő applyval vagy – külső erőforrásnál – tofu import-tal kell rendezni, mielőtt a „No changes” állapotot elfogadjuk.

Postcondition: A tofu plan sikeres, nincs törlés vagy létrehozás, a lock táblában nincs Info mezős lock-rekord (a digest rekord megmaradhat), a state fájl visszaállt.

46.2.7 Rövid összefoglaló

A remote state a Terraform/OpenTofu állapotfájljának megosztott, védett, verziózott tárolása, amely lehetővé teszi a csapatos, reprodukálható infrastruktúrakezelést. A backendhez identitáskötött hozzáférés tartozik, a state érzékeny adatai miatt titkosítás és szigorú IAM szükséges. A state lock biztosítja, hogy egyszerre csak egy folyamat módosítsa a state-et; az S3 backend lockja nem jár le magától, ezért a keményen megszakadt folyamatok által hátrahagyott lockot a force-unlock kezeli, de csak a tulajdonos ellenőrzése után. A state módosítható import, moved és state parancsokkal, amelyek nem érintik a valós erőforrásokat; a recovery során a state és a resource helyreállítása két külön folyamat, és a kettőt össze kell hangolni.

Továbbhasznált definíciók: remote state — az IaC állapotfájl megosztott, hálózati tárolóban lévő, verziózott és titkosított példánya; state lock — a state módosítására vonatkozó kizárólagos jog, amely megakadályozza a párhuzamos írást (az S3 backendben lejárat nélküli rekord); lease — időkorlátos, megújítandó lock, amelynél a lejárat fencinget igényel; state recovery vs resource recovery — a state fájl backupból való visszaállítása, illetve a valós felhőerőforrás helyreállítása, amelyek egymástól független, de összehangolandó műveletek.

46.2.8 Források és ellenőrzési hiányok

Az alábbi hivatkozások kiindulópontok, nem olvasott, ellenőrzött bizonyítékok. A backendek pontos szintaxisa, a lock-tábla viselkedése, a verziózás és titkosítás opciói, valamint az AWS API-k a jelenlegi verziókban változhatnak, ezért a konkrét labkörnyezetben ellenőrizendők.

  • OpenTofu documentation — „Backend Type: s3” (dynamodb_table, use_lockfile, workspace_key_prefix, szükséges IAM-jogok), „Command: force-unlock”, „Command: import” és „Import” blokk, „State: Locking”; hivatkozott verzió: OpenTofu 1.6.x (a példa required_version = ">= 1.6" korlátja), a natív S3-lockhoz a későbbi kiadások changelogja.
  • Terraform documentation — ugyanezek a Terraform S3 backendre; a dynamodb_table elavulását a changelog jelzi.
  • Amazon S3 User Guide — „Protecting data with server-side encryption” (SSE-S3 vs SSE-KMS), versioning; AWS KMS Developer Guide — „Key policies”; DynamoDB scan a AWS documentation DynamoDB API-referenciájában.
  • Lease és fencing token általános fogalma: az etcd dokumentáció „lease” API-ja és a Kubernetes Lease objektum (https://kubernetes.io/docs/concepts/architecture/leases/).

Ellenőrzési státusz: a backend-labor sikeres ága és hibaágai (beragadt lock SIGKILL után, state push/restore) sandbox accountban ellenőrizendők; dátumozott futtatási napló még nem készült.
