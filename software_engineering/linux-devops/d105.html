21.5 Hardening és hozzáférési recovery labor

21.5.1 Motiváció és definíciók

A hardening (keményítés) ebben a laborban nem egy ellenőrizetlen checklist, hanem mérhető állapotváltozás: a lab-worker.service és az SSH admin út a lehető legkisebb privilégiummal fusson, a változás előtt pedig bizonyítékot gyűjtünk arról, hogy a jogosult út továbbra is működik, a tiltott út pedig valóban zárva van. A positive access test azt igazolja, hogy egy jogosult identitás a tervezett hozzáférést megkapja. A negative access test azt igazolja, hogy egy tiltott identitás, hitelesítési módszer vagy erőforrás-elérés nem kap hozzáférést. A két teszt együtt véd a túlzott engedélyezés és a lockout ellen is.

A recovery console olyan out-of-band hozzáférés a labhosthoz, amely nem a módosítandó SSH úttól függ: például libvirt serial console, cloud vendor konzol vagy fizikai IPMI/BMC. A biztonsági változtatás során ezt előre azonosítjuk, nem a lockout után keressük. A baseline a kiinduló megfigyelt állapot; a service privilege diff a baseline és a kívánt állapot közötti, ellenőrzött tulajdonságkülönbség. A labor Ubuntu Server 24.04 LTS profilt használ, ezért a kernel policy itt AppArmor; a SELinux csak RHEL-családban, külön példaprofilon jelenik meg.

21.5.2 Baseline és service privilege diff

A labhost: lab-worker-1; a labservice a d080-ból ismert lab-worker.service; az SSH admin user: labops; a service user tervezett neve: labapp. A d102-ben bemutatott SSH host key és user key, valamint a d104-ben tárgyalt credential runtime átadás itt kap ellenőrzött permissiont és rotationt. A bináris a d080 szerinti helyen van: /opt/lab-worker/releases/<verzió>/bin/lab-worker, amelyre a /opt/lab-worker/current symlink mutat. A d080 service usere lab-worker volt; ebben a laborban a cél a labapp. A baseline-t megfigyeljük, nem feltételezzük:

# target: labops@lab-worker-1, privileges: sudo
sudo systemctl show -p User,Group,NoNewPrivileges,ProtectSystem \
  -p PrivateTmp,ReadWritePaths lab-worker.service
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication)'
sudo sshd -T \
  | grep -E '^(kbdinteractiveauthentication|x11forwarding|allowgroups)'
sudo aa-status
sudo stat -c '%a %U %G %n' /etc/lab-worker/lab-worker.toml \
  /etc/lab-worker/credentials.env

A diff táblázat a kívánt állapottal:

Tulajdonság Baseline (observed) Desired state Ellenőrző parancs
service user root (a d080-ban lab-worker) labapp systemctl show -p User --value lab-worker.service
NoNewPrivileges no yes systemctl show -p NoNewPrivileges --value lab-worker.service
ProtectSystem no strict systemctl show -p ProtectSystem --value lab-worker.service
AppArmor profil nincs lab-worker (enforce) sudo ps -eZ \| grep lab-worker
SSH PermitRootLogin yes no sshd -T \| grep permitrootlogin
SSH PasswordAuthentication yes no sshd -T \| grep passwordauthentication
SSH AllowGroups nincs labssh-admin sshd -T \| grep allowgroups
service config permission 0644 root:root 0440 root:labapp stat -c '%a %U %G'
service secret permission 0644 root:root 0400 root:labapp stat -c '%a %U %G'

A sshd -T a ténylegesen érvényes konfigurációt mutatja, ezért jobb ellenőrzés, mint a fájlok manuális olvasása. A syntax validálás külön sshd -t.

21.5.3 Kidolgozott példa: labservice és SSH admin út minimális policy

A változtatás előtt a baseline-t mentsük el, és rögzítsük a recovery utat. A laborban a recovery login labadmin a hypervisor-konzolon, sudo group tag.

# target: labops@lab-worker-1, privileges: sudo
mkdir -p ~/security-baseline/2025-01-15
B=~/security-baseline/2025-01-15
sudo cp /etc/ssh/sshd_config.d/*.conf "$B"/ 2>/dev/null || true
sudo systemctl cat lab-worker.service > "$B"/lab-worker.service.cat
sudo sshd -T > ~/security-baseline/2025-01-15/sshd-effective.txt

A labapp service user létrehozása csak akkor, ha nem létezik:

# target: labops@lab-worker-1, privileges: sudo
sudo getent passwd labapp || sudo useradd --system \
  --home-dir /var/lib/lab-worker --shell /usr/sbin/nologin \
  --create-home labapp
sudo mkdir -p /etc/lab-worker
sudo chown root:labapp /etc/lab-worker

A systemd drop-in a service privilégiumát szűkíti. Az /etc/systemd/system/lab-worker.service.d/10-hardening.conf tartalma:

[Service]
User=labapp
Group=labapp
NoNewPrivileges=yes
PrivateTmp=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/lab-worker
CapabilityBoundingSet=
UMask=0027
RestrictAddressFamilies=AF_UNIX AF_INET

A CapabilityBoundingSet= üres lista: a service nem kap semmilyen Linux capability-t. A useradd --system explicit --uid nélkül a rendszerfiók-tartományból (Ubuntun 100–999) oszt UID-et, így nem ütközik a következő emberi felhasználóval. Ha a workernek például az 1024 alatti portra kötéshez CAP_NET_BIND_SERVICE kellene, azt mindkét rétegben explicit módon hozzá kell adni (CapabilityBoundingSet=CAP_NET_BIND_SERVICE, AmbientCapabilities=CAP_NET_BIND_SERVICE és az AppArmor-profilban capability net_bind_service,), és ezt a systemd-analyze security exposure levelje is mutatja. Ebben a laborban a worker nem kötődik privilegizált portra, ezért egyik rétegben sincs capability. A ProtectSystem=strict a teljes fájlrendszert read-only-vá teszi, kivéve a ReadWritePaths alatt megadott adatkönyvtárat.

Az SSH drop-in /etc/ssh/sshd_config.d/20-lab-hardening.conf:

PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
X11Forwarding no
AllowGroups labssh-admin

A labops user legyen a labssh-admin csoportban:

# target: labops@lab-worker-1, privileges: sudo
sudo groupadd --gid 1502 labssh-admin 2>/dev/null || true
id labops | grep -q '(labssh-admin)' \
  || sudo usermod -aG labssh-admin labops

Az AppArmor profil a lab-worker számára csak a szükséges fájlokat engedi, capability-t nem (összhangban az üres CapabilityBoundingSet=-tel). Az AppArmor a symlink feloldása utáni útvonalra illeszt, ezért a profil fejléce a releases könyvtárra mutat glob-bal, nem a current symlinkre:

# target: labops@lab-worker-1, privileges: sudo
sudo tee /etc/apparmor.d/lab-worker <<'EOF'
#include <tunables/global>

profile lab-worker /opt/lab-worker/releases/*/bin/lab-worker {
  #include <abstractions/base>

  /etc/lab-worker/lab-worker.toml r,
  /var/lib/lab-worker/** rw,
}
EOF
sudo apparmor_parser -r /etc/apparmor.d/lab-worker
sudo aa-enforce lab-worker
# a szolgáltatás újraindítása után a processz a profil alatt fut:
sudo ps -eZ | grep lab-worker     # várt: lab-worker (enforce) ... lab-worker

A credential permission és rotation előfeltétele, hogy a lab-worker bináris a root tulajdonában legyen, a service user ne írhassa:

# target: labops@lab-worker-1, privileges: sudo
sudo chown root:labapp /opt/lab-worker/current/bin/lab-worker
sudo chmod 0750 /opt/lab-worker/current/bin/lab-worker
sudo chown root:labapp /etc/lab-worker/lab-worker.toml \
  /etc/lab-worker/credentials.env
sudo chmod 0440 /etc/lab-worker/lab-worker.toml
sudo chmod 0400 /etc/lab-worker/credentials.env

A credentials.env-et a systemd EnvironmentFile=/LoadCredential= mechanizmusa PID 1-ként, root jogon olvassa; a service user közvetlenül nem olvashatja, ezért a 0400 helyes.

Az SSH admin kulcs rotációja: a privát kulcs helye a munkaállomás, ezért az új kulcspárt ott generáljuk; a szerveren az authorized_keys hozzáfűzéssel bővül, és a régi sort csak az új kulcs pozitív tesztje után távolítjuk el (különben kizárnánk magunkat):

# target: labops workstation, privileges: none
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/id_ed25519_2025 \
  -C labops-2025-01-15
ssh-copy-id -i ~/.ssh/id_ed25519_2025.pub labops@lab-worker-1
# pozitív teszt az ÚJ kulccsal:
ssh -oBatchMode=yes -oIdentitiesOnly=yes -i ~/.ssh/id_ed25519_2025 \
  labops@lab-worker-1 -- id

Csak sikeres pozitív teszt után, a szerveren töröljük a régi kulcs sorát (a példában a régi kulcs megjegyzése labops-2024):

# target: labops@lab-worker-1, privileges: labops
grep -v 'labops-2024' ~/.ssh/authorized_keys > ~/.ssh/ak.new
install -m 0600 ~/.ssh/ak.new ~/.ssh/authorized_keys
stat -c '%a %U %G %n' ~/.ssh/authorized_keys

Végül negatív teszt a munkaállomásról a RÉGI kulccsal (-i ~/.ssh/id_ed25519 -oIdentitiesOnly=yes): Permission denied (publickey) a várt eredmény.

Várt kimenet: az authorized_keys 600 labops labops, a munkaállomáson a privát kulcs 0600. A credential rotation a credentials.env tartalmát cseréli egy új labsecretre, majd a service restarttal veszi át; a régi titok nem marad a konfigurációs könyvtárban.

A változtatások validálása és alkalmazása:

# target: labops@lab-worker-1, privileges: sudo
sudo systemd-analyze verify lab-worker.service
sudo sshd -t
sudo systemctl daemon-reload
sudo systemctl restart lab-worker.service ssh.service

A positive/negative access tesztek futtatása a laborhost és a munkaállomás között:

# pozitív SSH: target labops workstation -> lab-worker-1
ssh -oBatchMode=yes -oConnectTimeout=5 -oIdentitiesOnly=yes \
  -i ~/.ssh/id_ed25519_2025 labops@lab-worker-1 -- id

# negatív SSH: jelszó – a szerver által felkínált módszerek listája
ssh -v -oPubkeyAuthentication=no -oConnectTimeout=5 \
  -oPreferredAuthentications=password,keyboard-interactive \
  labops@lab-worker-1 true 2>&1 | grep 'Authentications that can continue'

# negatív SSH: root
ssh -oBatchMode=yes -oConnectTimeout=5 root@lab-worker-1 -- id

Várt eredmény: a pozitív teszt uid=1000(labops) és a labssh-admin csoporttagságot mutatja; a jelszavas teszt elfogadási feltétele a debug1: Authentications that can continue: publickey sor (nem szerepel benne password), nem a visszatérési kód – BatchMode=yes mellett az ssh jelszót sem kérne, így a hardening előtt is bukna; a root-teszt Permission denied (publickey) hibaüzenettel és nem nulla visszatérési kóddal zár.

A service privilege és AppArmor denial fixture:

# target: labops@lab-worker-1, privileges: sudo
W=/opt/lab-worker/current/bin/lab-worker
# pozitív: a saját config olvasása engedélyezett
sudo -u labapp -- "$W" --access-check /etc/lab-worker/lab-worker.toml

# negatív DAC-teszt: a 0400 root:labapp credential-fájlt már a DAC
# tiltja (EACCES), ezért itt NEM keletkezik apparmor="DENIED" sor
sudo -u labapp -- "$W" --access-check /etc/lab-worker/credentials.env

# negatív AppArmor-teszt: a DAC enged (0640 root:labapp), a profil nem
sudo install -m 0640 -o root -g labapp /dev/null \
  /etc/lab-worker/apparmor-probe.txt
sudo -u labapp -- "$W" --access-check /etc/lab-worker/apparmor-probe.txt

A kernel a DAC-tagadás után az LSM-hookot nem hívja meg, ezért AppArmor-naplósort csak olyan fájlra várhatunk, amelyet a DAC enged.

Várt denial napló a journalctl -k kimenetben:

# target: labops@lab-worker-1, privileges: sudo
sudo journalctl -k --since '5 min ago' | grep 'apparmor="DENIED"'
# illusztratív sor:
# audit: type=1400 audit(...): apparmor="DENIED" operation="open"
#   profile="lab-worker" name="/etc/lab-worker/apparmor-probe.txt"
#   requested_mask="r" denied_mask="r"

Az audit és access smoke check egy minimális, idempotens lab-security-smoke.sh script, amely a fenti positive/negative feltételeket gépi feldolgozásra alkalmas kimenettel ellenőrzi:

#!/usr/bin/env bash
set -euo pipefail
fail=0

check() {
  local desc="$1" cmd="$2" expected="$3"
  # grep -q helyett teljes olvasás: a korai kilépés SIGPIPE-ot (141)
  # okozna a bal oldalon, és pipefail mellett hamis FAIL-t adna
  if eval "$cmd" | grep -- "$expected" >/dev/null; then
    echo "PASS: $desc"
  else
    echo "FAIL: $desc"
    fail=1
  fi
}

check "ssh service active" "systemctl is-active ssh" "^active$"
check "lab-worker service active" "systemctl is-active lab-worker" "^active$"
check "lab-worker user" "systemctl show -p User --value lab-worker" "^labapp$"
check "sshd root login disabled" "sudo sshd -T" "^permitrootlogin no$"
check "sshd password disabled" "sudo sshd -T" \
  "^passwordauthentication no$"
check "credential permission" \
  "stat -c '%a' /etc/lab-worker/credentials.env" "^400$"
# a módot is vizsgáljuk; a JSON alakot a labhoston ellenőrizni kell
check "apparmor enforce" "sudo aa-status --json" '"lab-worker": "enforce"'
exit "$fail"

21.5.4 Hibák és ellenpróbák

A leggyakoribb hiba a security change során a lockout: például az AllowGroups labssh-admin helyett AllowGroups labssh kerül a drop-inba. Az sshd -t ezt nem jelzi, mert a konfiguráció szintaktikailag helyes, de a labops user nem tagja a megadott csoportnak. A tünet: a pozitív SSH teszt hirtelen Permission denied (publickey) hibát ad. A diagnózis a recovery console-ról:

# target: labadmin@lab-worker-1 console, privileges: sudo
sudo journalctl -u ssh -n 50
sudo sshd -T | grep '^allowgroups'

Várt kimenet: allowgroups labssh. A javítás egyetlen változtatás: a csoportnév javítása labssh-admin-re, majd sudo sshd -t && sudo systemctl restart ssh. Az ellenpróba a pozitív SSH ismételt futtatása. Ha a hiba bizonytalan, a rollback a drop-in fájl eltávolítása:

# target: labadmin@lab-worker-1 console, privileges: sudo
sudo mv /etc/ssh/sshd_config.d/20-lab-hardening.conf \
  ~/rollback-2025-01-15-20-lab-hardening.conf
sudo sshd -t && sudo systemctl restart ssh

A rollback után az SSH baseline állapotba tér, de ez a baseline gyenge policy-t jelent; ezért a javítás, nem a védelem kikapcsolása a cél.

Az alábbi ábra a lockout és a konzolos recovery lépéseit (T0–T7) egy idővonalon mutatja a két hozzáférési úttal, alatta a tesztmátrix állapotával; a HTML-változatban a rollback ág is kipróbálható.

AppArmor denial téves diagnózis, ha a worker valójában nem az AppArmor miatt, hanem POSIX permission miatt kap Permission denied-t. A megkülönböztetés: a journalctl -k denial sor apparmor="DENIED" mezőt tartalmaz; a POSIX hiba a syscall EACCES visszatérésben jelenik meg, AppArmor napló nélkül. A javítás rétegenként: a POSIX permission chmod/chown, az AppArmor profil apparmor_parser -r módosítás.

A credential permission túlzott szűkítése miatt a service nem indul. A tünet systemctl status lab-worker szerint Permission denied a config olvasásakor. A diagnózis sudo -u labapp -- /opt/lab-worker/current/bin/lab-worker --access-check /etc/lab-worker/lab-worker.toml; a javítás a config permission 0440 root:labapp, nem 0400 root:root. Az ellenőrzés a service restart és az active státusz.

21.5.5 Feladatok

  1. Magyarázó feladat: access test terv. A megadott baseline és desired state táblázat alapján készítsen hét positive/negative tesztet az SSH admin útra és a lab-worker service hozzáférésére. Minden teszthez adja meg a futtató user, a parancs, a várt kimenet és az accept visszatérési kód feltételét. Indokolja, miért nem elegendő egyetlen pozitív teszt a lockout ellen.

  2. Adminisztrációs feladat: hardening alkalmazása. A laborhoston hozza létre a 10-hardening.conf systemd drop-int, a 20-lab-hardening.conf SSH drop-int, az AppArmor profilt, és állítsa be a credential permissionöket a kidolgozott példa szerint. A változtatás előtt rögzítse a baseline-t, majd alkalmazás után futtassa a lab-security-smoke.sh ellenőrzéseket, valamint a positive/negative SSH teszteket. A sudo sshd -t és sudo systemd-analyze verify lab-worker.service kimenetét őrizze meg.

  3. Diagnosztikai/failure feladat: lockout recovery. Szimulálja azt a hibát, hogy az SSH drop-inban AllowGroups labssh szerepel a helyes labssh-admin helyett. A hiba bevezetése után állapítsa meg a lockout tünetét a pozitív SSH teszttel. A recovery console-ról diagnosztizálja a hibát, javítsa egyetlen változtatással, majd ellenőrizze a pozitív és negatív tesztekkel. Írja le a rollback parancsot is arra az esetre, ha a hiba nem lenne azonnal egyértelmű.

21.5.6 Megoldások

  1. Access test terv. A tesztek a labops admin user, a root SSH login, a jelszóautentikáció, az AllowGroups, a service user, a POSIX permission és az AppArmor engedély köré szerveződnek. Például pozitív: ssh -oBatchMode=yes -oIdentitiesOnly=yes -i ~/.ssh/id_ed25519_2025 labops@lab-worker-1 -- id várt kimenet uid=1000(labops), kód 0; negatív jelszó: ssh -v -oPubkeyAuthentication=no -oPreferredAuthentications=password,keyboard-interactive labops@lab-worker-1 true, elfogadás: az Authentications that can continue sorban csak publickey szerepel (BatchMode=yes itt nem bizonyítana, mert jelszót sem kérne); negatív: ssh -oBatchMode=yes root@lab-worker-1 -- id várt kimenet Permission denied, kód nem 0; pozitív service: sudo -u labapp -- /opt/lab-worker/current/bin/lab-worker --access-check /etc/lab-worker/lab-worker.toml kód 0; negatív DAC: … --access-check /etc/lab-worker/credentials.env várt EACCES, AppArmor-sor nélkül, kód nem 0; negatív AppArmor: … --access-check /etc/lab-worker/apparmor-probe.txt (DAC 0640 root:labapp) várt apparmor="DENIED" naplósor, kód nem 0. Egyetlen pozitív teszt nem elég, mert a lockoutot a pozitív teszt okozza: a negatív teszt a túlzott engedélyezést, a pozitív teszt a túlzott szűkítést jelzi. Postcondition: a tesztmatrix lefedi az összes említett hozzáférési útvonalat.

  2. Hardening alkalmazása. A baseline mentés után a sudo useradd --system --home-dir /var/lib/lab-worker --shell /usr/sbin/nologin --create-home labapp létrehozza a service usert (UID a rendszerfiók-tartományból). A drop-inok, az AppArmor profil és a permissionök a kidolgozott példa szerint kerülnek a helyükre. A sudo systemd-analyze verify lab-worker.service a unit syntax; a sudo sshd -t a SSH config syntax; a aa-enforce lab-worker az AppArmor profil betöltését ellenőrzi. A lab-security-smoke.sh futtatása kimenetében minden sor PASS, a positive/negative tesztek várt eredményűek. Postcondition: systemctl is-active lab-worker ssh active, sshd -T no/no/no/allowgroups labssh-admin, stat -c '%a' /etc/lab-worker/credentials.env 400, sudo ps -eZ | grep lab-worker a lab-worker (enforce) profilt mutatja.

  3. Lockout recovery. A 20-lab-hardening.conf fájlban az AllowGroups labssh hiba bevezetése után a pozitív SSH teszt Permission denied hibát ad, a parancs visszatérési kódja nem nulla. A recovery console-ról sudo journalctl -u ssh -n 50 mutatja a kapcsolódási kísérletet, sudo sshd -T | grep '^allowgroups' a hibás labssh csoportot. A javítás: a fájlban az AllowGroups labssh-admin beírása, majd sudo sshd -t && sudo systemctl restart ssh. A pozitív SSH ismét uid=1000(labops); a negatív root és jelszóteszt Permission denied; a rollback a fájl áthelyezése sudo mv /etc/ssh/sshd_config.d/20-lab-hardening.conf ~/rollback-..., restart, majd a policy újra bevezetése. Postcondition: az SSH admin út a desired state szerint engedélyezett, a tiltott utak zárva, a rollback a recovery console-ról működőképes.

21.5.7 Rövid összefoglaló

A hardening akkor üzemeltethető, ha a baseline megfigyelt, a kívánt állapot mérhető, és a változás előtti/utáni positive/negative access tesztek automatikusan jelzik a lockoutot vagy a túlzott engedélyezést. A lab-worker.service privilégiumát systemd sandbox, AppArmor enforce és POSIX permission együttesen csökkenti. Az SSH admin út a sshd -T effektív állapotot, az sshd -t syntax validálást és a recovery console out-of-band tartalékot használ. A credential permission és rotation a titkokhoz való hozzáférést a service userre korlátozza, a régi kulcsok eltávolításával. Továbbhasznált definíciók: positive/negative access test, recovery console, service privilege diff.
