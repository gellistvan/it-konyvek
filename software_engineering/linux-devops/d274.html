55.4 Incidensek: DNS/TLS/FD/OOM/disk/network

55.4.1 Motiváció

Egy üzemeltetett Linux szolgáltatásnál a felhasználó által látott hiba ritkán közvetlenül a gyökérok. A „nem tölt be az oldal” mögött DNS, TLS-lánc, route, reverse proxy, backend, elfogyott FD, OOM, telített disk vagy párhuzamosan futó háttérterhelés is állhat. Ebben a záróprojekt-incidensgyakorlatban ezért nem egyetlen hibát javítunk, hanem kontrollált, névvel azonosított labhibákkal gyakoroljuk a hipotézisvezérelt recoveryt. A cél az, hogy a szenior C++ fejlesztő a Linux stacket ugyanúgy diagnosztizálja, mint egy natív release artifact hibáját: tünet, bizonyíték, egy változtatás, verification.

A korábbi d160 hálózati incidensmódszertan és d110 teljes Linux bottleneck diagnosztika itt egy szolgáltatásszintű gyakorlatban fut össze. Ami ott egy rétegen belül tanult, az itt több függőségi és erőforrásrétegen keresztül jelenik meg.

55.4.2 Definíció és működés

Incidens (incident): egy szolgáltatás tervezett állapotától (desired state) való, felhasználót érintő eltérés. A lab gyakorlatban fault injection segítségével szándékosan hozunk létre incidenst. A fixture itt a hibás állapot pontos leírása: melyik gépen, melyik fájlban, melyik parancs hajtotta végre, és mi a várt tünet.

A recovery műveleteket meg kell különböztetni:

  • Mitigation: ideiglenesen csökkenti a user impactot, de a gyökérok megmaradhat. Például FD-limit emelése, ha a szolgáltatás FD leak-es.
  • Rollback: a release artifactot, konfigurációt vagy route-ot visszaállítja egy ismert jó állapotba. Nem garantálja, hogy az adatintegritás is helyreállt.
  • Restore: adatot vagy teljes fájlrendszert ellenőrzött backupból állít vissza. Csak sikeres, integritásellenőrzött restore után tekinthető igazolt recoverynek.

A diagnosztika alapja a tünet-réteg hozzárendelés. Egy tünetet nem elég látni, a réteget is azonosítani kell:

Tünet Valószínű réteg Elsődleges bizonyíték
A név rossz IP-t ad vagy timeout DNS/NSS/hosts getent ahosts, dig, /etc/hosts
TLS kézfogás hiba, „unable to get local issuer certificate” TLS-lánc, trust openssl s_client, openssl verify
TCP SYN után timeout, DNS/TLS rendben route, firewall, PMTU ip route get, ss -tn, tcpdump
accept: Too many open files FD-limit /proc/PID/limits, FD-count
Process exit 9/KILL, OOM-kill log memória/cgroup systemctl status, journalctl -k
Magas latency, magas I/O wait blokk-I/O, cgroup throttle iostat -xz, pidstat -d, /proc/pressure/io
No space left on device, töredéknyi szabad blokk inode/quota df -h, df -i, quota
HTTP 502/504 backend/proxy nginx error log, backend systemd state
Adat sérült vagy hiányzik storage/alkalmazás durabilitása checksum, backup restore

A táblázat sorait a diagnosztika egy hipotézisvezérelt sorrendben zárja ki; az alábbi döntési fa ezt a sorrendet mutatja a labfixture-ök bizonyítékaival.

A labban minden módosítás lab- prefixszel nevesített disklab/disposable erőforráson történik. A hibainjektálás előtt mindig baseline-t rögzítünk; a recovery után ugyanazzal a smoke teszttel ellenőrzünk.

55.4.3 Kidolgozott példa

55.4.3.1 Labtopológia és baseline

A gyakorlat a d271 kanonikus záróprojekt-stackjének egy incidenslab-változatát használja: a szerepek ugyanazok (edge/proxy, alkalmazás, backup), de a backendet két példányra bővítjük, hogy a proxy drain és a backend-kiesés gyakorolható legyen, és a backup repository külön hoston, külön failure domainben van. A nevek ezért eltérnek a d271–d273 neveitől; a megfeleltetés: lab-lb ↔︎ lab-edge (d271 és d273), lab-app-a/lab-app-b ↔︎ lab-app (d271) / lab-app-1/lab-app-2 (d273), lab-backup ↔︎ a lab-data restic-szerepe. A d273 runbookjai (runbooks/checkout-error-budget.md, runbooks/disk-capacity.md) szerep szerint alkalmazandók; a d273 HAProxy-drainjének itt az Nginx-upstream drain felel meg. A gyakorlat végén a labváltozatot eldobjuk, a kanonikus stack nem változik.

Objektum Cím/Interfész Szerep
lab-lb 192.0.2.10/24, 198.51.100.10/24 Nginx TLS reverse proxy
lab-app-a 198.51.100.20/24 lab-order-svc systemd service
lab-app-b 198.51.100.21/24 ugyanaz a service, második backend
lab-client 192.0.2.50/24 teszt kliens
lab-backup 198.51.100.30/24 restic repository

A dokumentációs címek az RFC 5737 tartományból valók. Az élő név lab-svc.example, amely az A rekorddal a lab-lb 192.0.2.10-es címére mutat.

Baseline ellenőrzés:

# target: lab-client, user: lab-admin, privilege: sudo
getent ahosts lab-svc.example
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt kimenet:
# 192.0.2.10 STREAM lab-svc.example
# 200

# target: lab-lb, user: lab-admin, privilege: sudo
openssl verify -CAfile /etc/ssl/lab/lab-ca-chain.pem /etc/ssl/lab/lab-leaf.pem
ip route get 198.51.100.20
# várt kimenet:
# /etc/ssl/lab/lab-leaf.pem: OK
# 198.51.100.20 dev eth1 src 198.51.100.10

Ez a három ellenőrzés egyszerre mutatja a DNS-, TLS- és route-függőséget. Ha bármelyik eltér, a hiba már a kapcsolat felépítése előtt jelentkezik.

55.4.3.2 Hibafixture: wrong DNS, TLS chain, route

Wrong DNS: a lab-client DNS-feloldását egy hibás /etc/hosts sorral térítjük el a forgalom elől. Ez jól szimulálja a rossz DNS-rekordot, de NSS szinten könnyen visszafordítható.

# target: lab-client, user: lab-admin, privilege: sudo
echo '192.0.2.99 lab-svc.example' | sudo tee -a /etc/hosts

# tünet és bizonyíték
curl -sS -v https://lab-svc.example/health 2>&1 \
  | grep -E 'Trying|Connected|failed'
getent ahosts lab-svc.example
# várt/illusztratív: Trying 192.0.2.99..., connection timed out
# getent: 192.0.2.99 STREAM lab-svc.example

A hipotézis: a névfeloldás rossz célt ad, nem a proxy vagy a hálózat hibás. Ellenőrzésként a getent mutatja a hibás IP-t. Rollback:

sudo sed -i '/192.0.2.99 lab-svc.example/d' /etc/hosts
getent ahosts lab-svc.example
# postcondition: ismét 192.0.2.10

TLS chain: a lab-lb Nginx chain fájljában csak a leaf certet hagyjuk meg, a köztes CA kikerül a chainből. A kliens ekkor nem tudja felépíteni a láncot.

# target: lab-lb, user: lab-admin, privilege: sudo
sudo cp /etc/ssl/lab/lab-fullchain.pem /etc/ssl/lab/lab-fullchain.pem.bak
sudo cp /etc/ssl/lab/lab-leaf.pem /etc/ssl/lab/lab-fullchain.pem
sudo nginx -t && sudo systemctl reload nginx

# target: lab-client
curl -sS -v https://lab-svc.example/health 2>&1 \
  | grep -E 'SSL certificate problem|openssl'
# hány tanúsítványt küld ki a szerver?
# (</dev/null: az s_client ne várjon stdinre)
openssl s_client -connect lab-svc.example:443 -servername lab-svc.example \
  -showcerts </dev/null 2>/dev/null | grep -c 'BEGIN CERTIFICATE'
# várt/illusztratív: 1 (csak a leaf); baseline-ban 2 (leaf + köztes CA)
# target: lab-lb – a konfigurált láncfájl elemszáma
openssl crl2pkcs7 -nocrl -certfile /etc/ssl/lab/lab-fullchain.pem \
  | openssl pkcs7 -print_certs -noout | grep -c 'subject='

A tünet „SSL certificate problem: unable to get local issuer certificate”. A curl hibája önmagában félrevezethető lenne: lehetne rossz CA store vagy órahiba is. Ezért a kliensről megszámoljuk, hány tanúsítványt küld ki a szerver a kézfogásban, és a lab-lb oldalán megnézzük a konfigurált láncfájlt: a lab-fullchain.pem-ben csak egy cert van, a lab-leaf.pem másolata. Rollback:

sudo cp /etc/ssl/lab/lab-fullchain.pem.bak /etc/ssl/lab/lab-fullchain.pem
sudo nginx -t && sudo systemctl reload nginx
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# postcondition: 200

Route fixture: a route-hiba ott okoz felhasználói tünetet, ahol az útvonal a kérés útjának része. A lab-client a proxyt ugyanazon a /24-en éri el, a backend-hálózatra nincs szüksége; ezért a fixture a lab-lb-n fut, és a lab-app-a felé egy, a connected /24-nél specifikusabb, rossz gatewayre mutató host-route-ot ad. A DNS és a TLS rendben marad, a proxy → backend TCP SYN mégis elveszik.

# target: lab-lb, user: lab-admin, privilege: sudo
sudo ip route add 198.51.100.20/32 via 192.0.2.99 dev eth0

# bizonyíték
ip route get 198.51.100.20
# várt/illusztratív: 198.51.100.20 via 192.0.2.99 dev eth0 src 192.0.2.10 ...
# (az ip route get nem jelez hibát: a rossz gateway csak a forgalomnál derül ki)
sudo tail -n 20 /var/log/nginx/error.log
# várt/illusztratív: upstream timed out / connect() failed
#   ... 198.51.100.20:18080

# target: lab-client
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt/illusztratív: lassú válasz vagy 502/504 a lab-app-a-ra eső kéréseknél,
# amíg az Nginx a max_fails után ki nem veszi a backendet

Rollback:

# target: lab-lb
sudo ip route del 198.51.100.20/32 via 192.0.2.99 dev eth0
ip route get 198.51.100.20
# postcondition: 198.51.100.20 dev eth1 src 198.51.100.10 (a baseline szerint)
# target: lab-client
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# postcondition: HTTP 200

55.4.3.3 Erőforrás-hibák: FD leak, OOM, throttle, IO bottleneck

Az erőforrás-incidensek közös jellemzője, hogy a külső tünet későn jelentkezik, mert a deployment eleinte működik. A labban a lab-order-svc release artifactjait a lab-install-release helper telepíti. A helper a natív binaryt, a source revisiont, a build-id-t és a systemd unit verzióját együtt írja le.

FD leak: telepítjük a 0.2.0-fdleak jelű hibás release-t. Minden health-kérés után egy socket/file descriptor nyitva marad.

# target: lab-app-a, user: lab-admin, privilege: sudo
sudo lab-install-release lab-order-svc 0.2.0-fdleak
sudo systemctl restart lab-order-svc

# terhelés: kérésenként +1 FD, ezért a 1024-es limithez ~1000 kérés kell;
# a ciklus az első hibánál megáll (accept4: Too many open files)
for i in $(seq 1 1100); do
  curl -sS http://127.0.0.1:18080/health >/dev/null || break
done

# miután az FD-limit közelébe ért:
PID=$(systemctl show -p MainPID --value lab-order-svc)
test "$PID" != "0" || exit 1
sudo ls "/proc/$PID/fd" | wc -l
sudo grep 'Max open files' "/proc/$PID/limits"
sudo journalctl -u lab-order-svc -n 30 --no-pager
# várt/illusztratív:
# fd count: 1019
# Max open files: 1024
# accept4: Too many open files

A hipotézis az FD-limit elérés, a bizonyíték a magas FD-count és a Max open files = 1024. A mitigation egy ideiglenes LimitNOFILE drop-in, de a gyökérok megmarad:

sudo mkdir -p /etc/systemd/system/lab-order-svc.service.d
cat <<'EOF' \
  | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-fd-mitigation.conf
[Service]
LimitNOFILE=4096
EOF
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

A valódi recovery a jó release visszaállítása és a provizórikus drop-in eltávolítása:

sudo lab-install-release lab-order-svc 0.1.9-good
sudo rm /etc/systemd/system/lab-order-svc.service.d/10-fd-mitigation.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

# terheléses postcondition (ugyanannyi kérés, mint a fixture-nél)
for i in $(seq 1 1100); do
  curl -sS http://127.0.0.1:18080/health >/dev/null || break
done
PID=$(systemctl show -p MainPID --value lab-order-svc)
sudo ls "/proc/$PID/fd" | wc -l
# postcondition: FD-count stabil, jóval 1024 alatt; a limit nem emelt

OOM: a 0.2.1-oom release memóriafogyasztása folyamatosan nő. A unitra szigorú memóriakorlátot teszünk, hogy a hiba a szolgáltatás cgroupjában maradjon, és ne a VM többi folyamatát szorítsa ki.

# target: lab-app-a, user: lab-admin, privilege: sudo
cat <<'EOF' \
  | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-oom-fixture.conf
[Service]
MemoryHigh=384M
MemoryMax=512M
EOF
sudo systemctl daemon-reload
sudo lab-install-release lab-order-svc 0.2.1-oom
sudo systemctl restart lab-order-svc
# a release a MemoryHigh/MemoryMax alatt először működik,
# majd OOM-kill következik

Az OOM-nál a bizonyítékot a restart előtt kell rögzíteni:

sudo systemctl status lab-order-svc --no-pager
# várt/illusztratív: code=killed, status=9/KILL
# a kernel OOM-killer sorai kernel-transportként jönnek,
# a -u szűrő nem látja őket
sudo journalctl -k -b --no-pager | grep -i -E 'oom-kill|killed process'
# a systemd saját unit-szintű bejegyzése külön
sudo journalctl -u lab-order-svc -b --no-pager | grep -i 'oom'
# memóriacsúcs közvetlenül a cgroup v2 fájlból (kernel >= 5.19)
cat /sys/fs/cgroup/system.slice/lab-order-svc.service/memory.peak
systemctl show lab-order-svc -p MemoryCurrent -p MemoryPeak
# a MemoryPeak property meglétét a 24.04-es systemd 255-ön ellenőrizni kell;
# ha nincs, üres értéket ad – ilyenkor a memory.peak a forrás
# várt/illusztratív: memory.peak közel a MemoryMax-hoz;
# MemoryCurrent az OOM-kill után lényegesen kisebb

A recovery a jó release visszaállítása, majd a hibás fixture drop-in eltávolítása. A MemoryHigh/MemoryMax drop-in csak akkor marad meg, ha a baseline kifejezetten előírja; itt a rollbackhez megszüntetjük.

sudo systemctl stop lab-order-svc
sudo lab-install-release lab-order-svc 0.1.9-good
sudo rm /etc/systemd/system/lab-order-svc.service.d/10-oom-fixture.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc
systemctl show lab-order-svc -p SubState -p MemoryCurrent
# postcondition: active/running; MemoryCurrent tartósan a baseline alatt

Throttle/IO bottleneck: itt nem a service release hibás, hanem a rendszerkonfiguráció fogja vissza a szolgáltatást. A lab-order-svc service alá egy drop-in mesterségesen CPUQuota=10%-ot és IOReadBandwidthMax-ot adhat. A méréshez a d273-ban használt Prometheus lab_order_request_duration_seconds metrikát vagy a lokális lab_bench --quantiles eszközt használjuk.

# target: lab-app-a, user: lab-admin, privilege: sudo
cat <<'EOF' \
  | sudo tee /etc/systemd/system/lab-order-svc.service.d/10-throttle.conf
[Service]
CPUQuota=10%
IOReadBandwidthMax=/dev/vdb 2M
EOF
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc

# mérés: előtte az IOPS-t és a p50/p95-öt rögzítjük, a throttle alatt ismét
iostat -xz 1 5
systemd-cgtop --depth=1 --iterations=5
# lab_bench --url http://127.0.0.1:18080/health --quantiles p50,p95,p99

A bizonyíték itt a request latency és a blokk-IO várakozás egyidejű növekedése. A hibás drop-in eltávolítása a recovery:

sudo rm /etc/systemd/system/lab-order-svc.service.d/10-throttle.conf
sudo systemctl daemon-reload
sudo systemctl restart lab-order-svc
# postcondition: a p50/p95 visszatér a baseline közelébe,
# a CPUQuota és IO limit megszűnik

55.4.3.4 Disk/inode/quota és service data

A „write nem sikerül” tünetet könnyű félreértelmezni, ha csak df -h-t nézünk. A labban inode-kimerülést okozunk egy, a service adatkönyvtára alá csatolt, szándékosan kevés inode-dal létrehozott kis lab-fájlrendszeren. Egy alapértelmezett ext4 kötet ~16 KiB-onként kap inode-ot (1 GiB-on ~65 536-ot), ezt néhány ezer fájl nem merítené ki; a dedikált 64 MiB-os, 2048 inode-os image viszont kiszámíthatóan betelik:

# target: lab-app-a, user: lab-admin, privilege: sudo
sudo mkdir -p /var/lib/lab-disks /srv/lab-order-svc/lab-fill
sudo truncate -s 64M /var/lib/lab-disks/lab-inode.img
sudo mkfs.ext4 -q -N 2048 -F /var/lib/lab-disks/lab-inode.img
sudo mount -o loop /var/lib/lab-disks/lab-inode.img /srv/lab-order-svc/lab-fill
sudo chown lab-svc:lab-svc /srv/lab-order-svc/lab-fill
sudo -u lab-svc bash -c 'for i in $(seq 1 3000); do
  : > "/srv/lab-order-svc/lab-fill/f$i" || break
done'

# bizonyíték
df -h /srv/lab-order-svc/lab-fill
df -i /srv/lab-order-svc/lab-fill
# várt/illusztratív: df -i 100% használt, df -h kb. 10% alatt;
# a ciklus „No space left on device” hibával áll meg

A tünet a service oldalán No space left on device lehet akkor is, ha blokk szinten van szabad kapacitás. Ennek oka az inode-kimerülés. A rollback a lab-fixture leválasztása; az image-et nem töröljük, hanem félreállítjuk:

sudo umount /srv/lab-order-svc/lab-fill
sudo mv /var/lib/lab-disks/lab-inode.img /var/lib/lab-disks/lab-inode.img.done
df -i /srv
sudo -u lab-svc touch /srv/lab-order-svc/.write-test
sudo -u lab-svc rm /srv/lab-order-svc/.write-test
# postcondition: inode-használat a baseline, a service adatkönyvtára írható

Kvóta esetén a bizonyíték a quota vagy xfs_quota report kimenete, és a recovery a per-user limit feloldása vagy emelése. A service adatknál mindig rögzítjük a használt adatútvonalat: /srv/lab-order-svc, a tulajdonost, a backup idősorát és a du -x --max-depth=2 kimenetet.

55.4.3.5 Backend failure és proxy drain

A lab-lb Nginx upstream konfigurációja; a lab_backend upstream egyetlen helye a /etc/nginx/conf.d/lab-upstream.conf (ha máshol is definiálnánk, az nginx -t „duplicate upstream” hibát adna):

upstream lab_backend {
    server 198.51.100.20:18080 max_fails=2 fail_timeout=30s;
    server 198.51.100.21:18080;
}

A backend leállítása előtt nem szeretnénk 5xx-et adni. A proxy drain azt jelenti, hogy a maintenance alá vont backendet először kivonjuk a routing döntésből, majd megvárjuk, amíg az aktív kapcsolatok lecsengenek, és csak utána állítjuk le a service-t.

# target: lab-lb, user: lab-admin, privilege: sudo
# mentés a módosítás ELŐTT
sudo cp -a /etc/nginx/conf.d/lab-upstream.conf \
  /etc/nginx/conf.d/lab-upstream.conf.pre-drain
sudo sed -i 's|^\( *server 198.51.100.20:18080[^;]*\);|\1 down;|' \
  /etc/nginx/conf.d/lab-upstream.conf
sudo nginx -t && sudo systemctl reload nginx
# a reload után a régi workerek még kiszolgálják a futó kéréseket
while pgrep -f 'nginx: worker process is shutting down' >/dev/null; do
  sleep 1
done

# target: lab-app-a – a backendre érkező kapcsolatok lecsengtek?
ss -Htn state established '( sport = :18080 )' | wc -l
# várt: 0; csak ezután állítjuk le a service-t
sudo systemctl stop lab-order-svc

# target: lab-client
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt/illusztratív: 200, mert a lab-app-b továbbra is kiszolgál

A recovery sorrendje fordított: előbb a backend indul és egészséges, csak utána kerül vissza a routingba, különben az Nginx egy leállított backendre küldene forgalmat:

# target: lab-app-a
sudo systemctl start lab-order-svc
# target: lab-lb – a backend közvetlen health-ellenőrzése
curl -fsS http://198.51.100.20:18080/health
# csak sikeres health után: a drain előtti konfiguráció visszaállítása
sudo cp -a /etc/nginx/conf.d/lab-upstream.conf.pre-drain \
  /etc/nginx/conf.d/lab-upstream.conf
sudo nginx -t && sudo systemctl reload nginx
# postcondition: mindkét backend újra aktív; curl 200

Ha mindkét backend kiesne, a tünet 502 lesz. Ezt a log bizonyítja, nem elég a curl hibakód. A hiba különválasztásához mindig rögzítjük:

# target: lab-lb
sudo tail -n 50 /var/log/nginx/error.log
# target: lab-app-a és lab-app-b
systemctl is-active lab-order-svc
ss -lntp | grep 18080

55.4.3.6 Backup restore és data integrity

A backup csak akkor jelent valós recoveryt, ha a restore utáni adat checksummal és szolgáltatáshealth-tel igazolt. A gyakorlatban restic repository-t használunk a lab-backup gépen (198.51.100.30), SFTP-n keresztül: a repository így nem ugyanazon a hoston és fájlrendszeren van, mint a védett adat. A repository jelszófájlja root:root 0600, a szolgáltatás-user (lab-svc) sem a jelszót, sem a repót nem éri el; a restore root-ként fut. A mentéskor a backup-script a snapshot mellé egy MANIFEST.json-t is ment a fájlok SHA-256 hashével (a manifest formátuma a lab backup-scriptjének szerződése).

Injektálás: a service aktuális adatfile-ját felülírjuk hibással.

# target: lab-app-a, user: lab-svc
echo corrupt > /srv/lab-order-svc/orders/current.dat
sha256sum /srv/lab-order-svc/orders/current.dat

A restore előtt a repository legfrissebb snapshotját kérjük le, majd egy külön target könyvtárba restore-olunk, hogy az élő adatot ne írjuk felül bizonyíték előtt:

# target: lab-app-a, user: lab-admin, privilege: sudo
REPO=sftp:lab-restic@lab-backup:/srv/restic/lab-order-svc
PW=/etc/lab-backup/password.txt
sudo restic -r "$REPO" --password-file "$PW" snapshots --latest 1
# a snapshot-ID-t rögzítjük az evidence-be
SNAP=$(sudo restic -r "$REPO" --password-file "$PW" snapshots --latest 1 \
  --json | jq -r '.[-1].short_id')

sudo systemctl stop lab-order-svc
sudo mkdir -p /var/tmp/lab-restore
sudo restic -r "$REPO" --password-file "$PW" restore "$SNAP" \
  --target /var/tmp/lab-restore \
  --include /srv/lab-order-svc/orders/current.dat \
  --include /srv/lab-order-svc/MANIFEST.json

# helyreállított fájl ellenőrzése a mentéskori manifest ellen
R=/var/tmp/lab-restore/srv/lab-order-svc
expected=$(jq -r '.files["orders/current.dat"].sha256' "$R/MANIFEST.json")
echo "$expected  $R/orders/current.dat" | sha256sum -c -
# várt: .../orders/current.dat: OK

A sérült élő fájl és a mentéskori hash eltérése igazolja a sérülést; a visszaírás csak sikeres sha256sum -c után, leállított szolgáltatás mellett történik:

R=/var/tmp/lab-restore/srv/lab-order-svc
echo "$expected  $R/orders/current.dat" | sha256sum -c - \
  && sudo install -o lab-svc -g lab-svc -m 0640 "$R/orders/current.dat" \
       /srv/lab-order-svc/orders/current.dat
sudo sha256sum /srv/lab-order-svc/orders/current.dat
sudo systemctl start lab-order-svc
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/health
# postcondition: checksum egyezik a manifesttel; health 200

A restic restore --target paramétere nem az élő adatot írja felül, ezért a visszaírás előtt a checksum-összehasonlítás bizonyítható. A rollout/backup műveleteknél mindig meg kell nevezni, hogy a snapshot/replication nem azonos a backup/restore-ral; a konténerekben vagy VM snapshotban is lehetnek félig írt adatfájlok.

55.4.3.7 Timeline, evidence és postmortem

A labban minden incidensről a következő formátumú idővonalat készítjük. Az időértékek falikór-időben (wall clock) vannak, illusztratívak:

T+perc Esemény Megfigyelt állapot Bizonyíték
0 Baseline 200 health curl -w, getent, openssl verify
4 Wrong DNS fixture client timeout getent ahosts rossz IP
9 DNS rollback névfeloldás jó getent ahosts
11 TLS chain fixture SSL certificate problem openssl s_client chain
16 TLS rollback 200 curl
21 Route fixture (lab-lb) lassú válasz / 502–504, DNS és TLS jó ip route get, nginx error.log
26 Route rollback 200 curl

A postmortem vezető szempontjai:

  1. Mi volt a felhasználói tünet?
  2. Mi volt a gyökérok, és milyen bizonyíték támasztotta alá?
  3. Mi volt a contributing factor, amit nem kell gyökéroknak nevezni?
  4. A mitigation, rollback és restore közül melyik mit oldott meg?
  5. Melyik mérést kell regressziós smoke tesztként megtartani?

Például a wrong DNS incidensnél a gyökérok a hibás /etc/hosts sor, a contributing factor a reverse proxyhoz tartozó névfeloldás cache-elése lehetett. A tanulság nem az, hogy „rossz a DNS”, hanem hogy a curl timeoutot DNS-bizonyíték nélkül nem szabad route-hibaként kezelni.

55.4.4 Hibák és ellenpróbák

A tünetet azonnal a rossz réteghez kötjük. A connection timed out nem feltétlenül route-hiba. Ellenpróba: getent ahosts lab-svc.example, ip route get 198.51.100.20, ss -tn state syn-sent '( dport = :443 )'. Ha a név rossz IP-t ad, az a DNS réteg; ha a route célorientáció helyes, de a SYN nem hagyja el a gépet, a route/ACL/firewall a következő.

A TLS chain hibáját kizárólag a kliensnapjából diagnosztizáljuk. A curl hibaüzenete nem mondja meg, hogy a szerver chain hiányos vagy a kliens CA store rossz. Ellenpróba a kliensről futtatott openssl s_client -showcerts (a kiküldött tanúsítványok száma és a Verify return code), valamint a lab-lb konfigurált láncfájljának elemszáma; a kettő összevetése mutatja az eltérő chain-t.

Az OOM bizonyítékot a restart elrontja. Ha a MemoryPeak és a status=9/KILL nem rögzítettük, a friss systemd state csak a restart kísérletet mutatja. A labban előbb journalctl -k-t és systemctl show-t rögzítünk, utána restart.

A disk tele van, de df -h szerint nincs tele. Ellenpróba a df -i. A blokk-kapacitás és inode-kapacitás külön erőforrás; egy fájlrendszerben az inode-kimerülés ugyanolyan írásképtelenséget okoz.

A proxy drain elmarad. Ha a backendet leállítjuk, mielőtt a proxy routing döntéséből kivontuk volna, aktív kérések esnek el. Ellenpróba a ss -tnp és az Nginx access log aktív kapcsolatai. A drain sorrend: remove from upstream, reload, active connections drain, stop service; a visszaállításé: start service, health, return to upstream, reload.

A restore azonnal felülírja az élő adatot. Ellenpróba: először /var/tmp/lab-restore-ba restore-olunk, ott a mentéskori manifest ellen checksumot ellenőrzünk, és csak azután másoljuk vissza. Ha a backup maga sérült, a rossz restore nem rontja tovább az élő adatot.

A rollbacket összekeverjük a restore-ral. A rossz release visszavonása nem hozza vissza a törölt adatfile-t. Az adatsérülésnél rollback utáni restore is kell, és a healthcheck az adat sértetlenségét igazolja.

55.4.5 Feladatok

55.4.5.1 1. feladat: tünet-réteg hozzárendelés

A lab-client-en a curl https://lab-svc.example/health hibát ad: SSL certificate problem: unable to get local issuer certificate. A getent ahosts lab-svc.example visszaadja a 192.0.2.10-et. Az ip route get 198.51.100.20 rendben mutatja a via-t. Melyik réteg a legerősebb hipotézis? Milyen parancssal döntöd el, hogy a kliens CA store vagy a szerver TLS chain hibás? Ne telepíts semmit.

55.4.5.2 2. feladat: DNS/route fixture recovery

Készítsd el a labban a wrong DNS és a wrong route fixture-t a fenti parancsokkal. Mindkét hibát külön állítsd vissza, és igazold a postconditiont. A módosító parancsoknál nevezd meg a targetet, a privileget, a rollbacket és a vegyes ellenőrzést. Külön figyelj arra, hogy a DNS-hiba és a route-hiba tünete hasonló lehet.

55.4.5.3 3. feladat: FD leak/OOM diagnosztika és timeline

Telepítsd a 0.2.0-fdleak release-t, terheld a health endpointot, majd rögzítsd a tünetet és a FD-countot. Állítsd helyre a jó release-t. Ezután telepítsd a 0.2.1-oom release-t, figyeld a service state-et, majd készíts postmortem-t. A postmortem tartalmazza a gyökérokot, a contributing factort, a mitigation/rollback lépéseket és a regressziós smoke tesztet.

55.4.5.4 4. feladat: disk/inode, backup restore és data integrity

Töltsd fel inode-okkal a lab-order-svc service adatkönyvtárát, diagnosztizáld a No space left on device tünetet, majd tisztítsd a lab-fixture-t. Ezután rontsd el a current.dat adatfile-t, és bizonyítsd a backupból való restore-t: checksum, restart, healthcheck. A megoldásban indokold, miért restore-olsz előbb /var/tmp/lab-restore-ba, és miért nem közvetlenül az élő adatkönyvtárba.

55.4.6 Megoldások

55.4.6.1 1. feladat megoldás

A legvalószínűbb réteg a TLS trust/chain, mert a DNS-feloldás és a route is rendben van. A kérdés (kliens CA store vagy szerver chain) a kliens oldaláról dönthető el: hány tanúsítványt küld ki a szerver a kézfogásban, és a kliens saját trust store-jával mi a verify-eredmény. A lab-lb lokális openssl verify-ja ezt nem dönti el, mert a lemezen lévő leafet egy helyi láncfájllal ellenőrzi, nem azt, amit az Nginx kiküld.

# target: lab-client, user: lab-admin (nem telepítünk semmit)
openssl s_client -connect lab-svc.example:443 -servername lab-svc.example \
  -showcerts </dev/null 2>/dev/null | grep -c 'BEGIN CERTIFICATE'
# 1 -> a szerver csak a leafet küldi (chain hiányos); 2 -> a lánc teljes
openssl s_client -connect lab-svc.example:443 -servername lab-svc.example \
  -CApath /etc/ssl/certs </dev/null 2>/dev/null | grep 'Verify return code'
# 21 (unable to verify the first certificate): hiányos szerverlánc
# 20 (unable to get local issuer certificate) vagy 19: tipikusan kliensoldali
#    trust-hiány (a lab CA nincs a kliens store-jában)

# target: lab-lb – a konfigurált láncfájl elemszáma
openssl crl2pkcs7 -nocrl -certfile /etc/ssl/lab/lab-fullchain.pem \
  | openssl pkcs7 -print_certs -noout | grep -c 'subject='

Postcondition: a hibaforrás a kiküldött tanúsítványszám és a kliens verify-kódja alapján egyértelműen az egyik oldalhoz rendelt, nem a DNS-hez vagy a route-hoz.

55.4.6.2 2. feladat megoldás

A parancsok megegyeznek a kidolgozott példa wrong DNS és route fixture szakaszaival. A DNS-visszaállítás után:

# target: lab-client
getent ahosts lab-svc.example
# várt: 192.0.2.10

A route-visszaállítás után:

# target: lab-lb
ip route get 198.51.100.20
# várt: 198.51.100.20 dev eth1 src 198.51.100.10 (baseline)
# target: lab-client
curl -sS -o /dev/null -w '%{http_code}\n' https://lab-svc.example/health
# várt: 200

A DNS-hiba és a route-hiba elkülönítése: a DNS-fixture alatt a getent ahosts rossz IP-t ad; route-fixture alatt a getent jó, a TLS-kézfogás is sikerül, de a lab-lb-n az ip route get 198.51.100.20 a rossz gatewayt mutatja, és az Nginx error logban upstream timed out / connect() failed sorok jelennek meg. Ez a két ellenpróba megakadályozza a tünet összemosását.

55.4.6.3 3. feladat megoldás

A release telepítése után a tünet akkor jelenik meg, ha a /proc/PID/limits és a FD-count együtt mutatja a kimerülést:

PID=$(systemctl show -p MainPID --value lab-order-svc)
sudo ls "/proc/$PID/fd" | wc -l
sudo grep 'Max open files' "/proc/$PID/limits"
# várt: FD-count 1024 környékén, Max open files 1024

A jó release visszaállítása után FD-count ismét stabil alacsony. Az OOM-nál a systemctl status lab-order-svc nem Restarting, hanem failed vagy activating, és a journalctl -k -b OOM-kill bejegyzést ad. A memory.peak (vagy, ha a systemd-verzió támogatja, a MemoryPeak) a MemoryMax közelében van.

A postmortem:

  • Gyökérok: a 0.2.1-oom release memóriafogyasztása növekedett; a cgroup MemoryMax=512M elérése után OOM-kill.
  • Contributing factor: a health requestek a memóriaelfogyás előtt is magas kihasználtságot okoztak, de az OOM-ot a release okozta.
  • Mitigation: a service systemctl stop-ja, hogy megőrizzük a bizonyítékot; ha szükséges, a loadbalancerből kivonás.
  • Rollback: 0.1.9-good release visszaállítása, a 10-oom-fixture drop-in eltávolítása.
  • Regressziós smoke teszt: 5 perces health-terhelés után a MemoryCurrent nem közelíti a limitet, FD-count stabil, HTTP 200.

55.4.7 Rövid összefoglaló

A kontrollált incidenslab a tünetet előbb rendeli erőforrás- vagy dependency-réteghez, és csak utána változtat. A DNS, TLS-lánc és route mind függőségi hiba; a hibás /etc/hosts, a hiányos CA chain és a rossz route ugyanazt a látszólagos timeoutot adhatja, ezért mindegyikhez külön bizonyíték kell. Az FD leak, OOM, throttle és IO bottleneck erőforráshiba; itt a release, a cgroup limit és a /proc adatok választják el a hibatípust. A backend failure-nél a proxy drain megelőzi az 5xx-et, a restore pedig csak checksumolt backupból, külön targetből írja vissza az élő adatot. A timeline és postmortem a megfigyelést, a gyökérokot és a regressziós smoke tesztet külön kezeli.

  • Fixture: szándékosan hibás, névvel és postconditionnel azonosított labállapot.
  • Rollback: release/konfiguráció visszaállítása ismert jó állapotba; nem adatrestore.
  • Restore: adat integritásellenőrzött visszaállítása backupból; minimum checksum és szolgáltatáshealth igazolja.

  • OpenSSL s_client és OpenSSL verify – -showcerts, Verify return code, a 19/20/21-es verify-hibakódok; a 24.04 OpenSSL 3.0 sorozata.
