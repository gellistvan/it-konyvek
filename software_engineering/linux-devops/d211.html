43.1 Clusterprofil, bootstrap és HA topológia

43.1.1 Motiváció

A d167-ben felépített libvirt-KVM laborban egyetlen VM indítása jól kontrollálható. Egy Kubernetes cluster viszont több node-ból, közös control plane-ből, etcd-ből, load balancerből, CNI/CSI/DNS addonból és csatlakoztatott credentials-ekből áll. Ha ezeket ad hoc módon, dokumentálatlan verziókkal bootstrapeljük, akkor az első upgrade vagy control-plane node kiesés olyan unknown-unknown hibát hoz, amelyet a szenior C++ fejlesztő a build/dependency világából “dependency hell”-ként ismer. A clusterprofil ezért nem egy telepítési jegyzet, hanem a clusster desired state leírása: verzió, runtime, cgroup, network, storage, topology, failure domain és credential lifecycle. A d210-ben megismert RBAC/admission biztonsági rétegek csak akkor működnek, ha ez a profil előre rögzített, auditálható és reprodukálható.

43.1.2 Definíció és működés

A clusterprofil az a verziózott, géppel olvasható vagy explicit dokumentált leírás, amely egy Kubernetes cluster összes komponensének kiadását, konfigurációját, hálózati címtartományait, csomópontjait és failure domain hozzárendelését rögzíti. A bootstrap az a folyamat, amelyben üres, előkészített Linux node-okból control plane és worker node-ok, majd működő cluster lesz. A HA control plane olyan topológia, amelyben a kube-apiserver és az etcd több node-on fut, és a többségi quorum megtartása mellett egy node kiesése nem állítja le az API-t.

Két alapvető üzemeltetési modell létezik:

  • Self-managed (például kubeadm): a cluster tulajdonosa telepíti, frissíti és menti az etcd-et, a control plane komponenseket és a node-okat. Teljes kontroll, cserébe a control plane, certifikátumok, etcd backup/restore és verzióskew is a mi felelősségünk.
  • Managed (felhőszolgáltató Kubernetes API-ja): a cloud provider a control plane-t és az etcd-et menedzseli, a felhasználó node-okat, workload-ot, CNI/CSI és policy összeállítást üzemeltet. A managed nem jelenti azt, hogy nincs verzió- és addon-kompatibilitási feladat, csak a felelősségi határ máshol van.

A version skew a Kubernetes komponensek megengedett maximális verzióeltérése. A gyakorlatban a kubelet nem lehet újabb a kube-apiservernél, és legfeljebb pár minor verzióval lehet régebbi; a kubeadm, kubectl, kubelet és apiserver közötti megengedett eltérést a hivatalos support matrix rögzíti. A container runtime (például containerd) és a CNI/CSI plugin verzióját ugyanígy kezelni kell: egy új Kubernetes minor gyakran újabb runtime- vagy CNI-verziót követel, így a profilba a teljes support mátrix beletartozik, nem csak a v1.X.Y string.

A laborban kubeadm self-managed clustert használunk, mert a cél a látható rétegek tanulása; felhőben a managed control plane fekete dobozként viselkedne.

43.1.3 Kidolgozott példa

A labor célja egy 3 control-plane + 1 worker node-os HA topológia egyetlen libvirt hoston. A példa verziói hipotetikusak; a tényleges laborban a hivatalos Kubernetes, containerd, CNI és Linux kernel support mátrixot ellenőrizni kell. A példában a v1.31.0 jelölésű verziót használjuk.

Labtopológia és failure domain

Név Szerep IP vCPU/RAM/disk (lab illusztratív) Failure domain
lab-lb kube-apiserver TCP LB (HAProxy) 10.42.0.10 2/2 GiB/20 GiB labhost1
lab-cp1 control plane + etcd tag 10.42.0.11 2/4 GiB/40 GiB labhost1
lab-cp2 control plane + etcd tag 10.42.0.12 2/4 GiB/40 GiB labhost1
lab-cp3 control plane + etcd tag 10.42.0.13 2/4 GiB/40 GiB labhost1
lab-worker1 worker 10.42.0.21 2/4 GiB/40 GiB labhost1

A laborban minden node ugyanazon a libvirt hoston fut, ezért a fizikai failure domain közös: egy host újraindítás vagy tápkimaradás az összes node-ot érinti. Ez a laborra elfogadható, de productionben a control plane node-okat külön rackbe, switchbe és tápkörbe kellene tenni, az etcd quorum miatt legalább három node-ot. A dokumentáció lab-lb.lab nevet 10.42.0.10 IP-re mutató lab DNS-rekordként feltételezzük; ennek hiányában a node-ok /etc/hosts bejegyzése is elegendő. A DNS-rekord önmagában nem load balancer: a controlPlaneEndpoint címen egy TCP-proxynak kell hallgatnia, amely a három kube-apiserverre továbbít, és a kiesett tagot health check alapján kiveszi.

0. Load balancer a lab-lb node-on

A kubeadm init a controlPlaneEndpoint-ot írja az admin.conf-ba és a komponensek kubeconfigjaiba; ha a 10.42.0.10:6443 címen semmi nem hallgat, az init későbbi fázisai, a kubectl és a kubeadm join „connection refused” hibát adnak. Ezért a load balancer az első lépés:

# Target: lab-lb (root)
sudo apt-get update
apt-cache madison haproxy         # a labprofil szerinti verzió kiválasztása
sudo apt-get install -y haproxy   # =<rögzített verzió> a labprofil szerint
# /etc/haproxy/haproxy.cfg (kiegészítés a csomag alapkonfigurációjához)
frontend k8s-api
    bind 10.42.0.10:6443
    mode tcp
    option tcplog
    default_backend k8s-cp

backend k8s-cp
    mode tcp
    option tcp-check
    balance roundrobin
    server lab-cp1 10.42.0.11:6443 check
    server lab-cp2 10.42.0.12:6443 check
    server lab-cp3 10.42.0.13:6443 check
# Target: lab-lb (root)
# várt: Configuration file is valid
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl restart haproxy
ss -ltn 'sport = :6443'                       # várt: LISTEN 10.42.0.10:6443

A kubeadm init előtt a backendek még DOWN állapotúak; ez várt, a lab-cp1 az init alatt jelenik meg. A labor lab-lb-je maga is egyetlen hibapont (single point of failure); productionben két LB-példány keepalived-vel kezelt VIP-pel, vagy külső/felhős load balancer kell.

1. Közös host-prerekvizitek minden node-on

# Target: lab-cp1, lab-cp2, lab-cp3, lab-worker1
# UID: root (sudo); minden módosító parancs lab előtti állapotból indul
sudo modprobe overlay
sudo modprobe br_netfilter
printf 'overlay\nbr_netfilter\n' | sudo tee /etc/modules-load.d/k8s.conf
printf 'net.ipv4.ip_forward = 1\nnet.bridge.bridge-nf-call-iptables = 1\n' \
  | sudo tee /etc/sysctl.d/99-kubernetes.conf
sudo sysctl --system

A kubelet alapértelmezésben (failSwapOn: true) nem indul aktív swap mellett, és a kubeadm init/join preflight [ERROR Swap] hibával leáll; az Ubuntu Server 24.04 telepítője alapból /swap.img swapfájlt hoz létre. A swap-támogatás (NodeSwap) verziófüggő, külön konfigurációt igényel, ezért a laborban kikapcsoljuk:

# Target: lab-cp1, lab-cp2, lab-cp3, lab-worker1 (root)
swapon --show
sudo swapoff -a
sudo sed -i.bak '/\sswap\s/ s/^/#/' /etc/fstab
swapon --show     # várt: üres kimenet
free -h           # várt: Swap: 0B

Rollback: sudo cp /etc/fstab.bak /etc/fstab és sudo swapon -a.

A bridge-nf-call-iptables régebbi kernelben szükséges, modern nftables/i iptables-nft esetén is megőrizzük, mert a pod network bridge-n átmenő forgalmat a netfilternek látnia kell. A cgroup v2 ellenőrzése:

# Target: minden node (root)
stat -fc %T /sys/fs/cgroup/
# Várt (Linux 5.8+ default): cgroup2fs

2. Container runtime és kubeadm binárisok telepítése

A kubelet, kubeadm és kubectl csomag nem része az Ubuntu 24.04 archívumának: a pkgs.k8s.io minorcsatornás repositoryját kell beállítani (a pontos parancsokat a cél minorhoz a hivatalos telepítési útmutatóból kell ellenőrizni). A csomagverziót rögzítjük, hogy a kubernetesVersion: v1.31.0 profillal egyezzen; enélkül a csatorna legfrissebb patch-e települne, a hold pedig csak ezt az ellenőrizetlen verziót zárolná:

# Target: minden node (root)
K8S_MINOR=v1.31
K8S_PKG=1.31.0-1.1     # az apt-cache madison kimenetéből ellenőrizendő
REPO=https://pkgs.k8s.io/core:/stable:/$K8S_MINOR/deb/
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL "${REPO}Release.key" \
  | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
KR=/etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=$KR] $REPO /" \
  | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
apt-cache madison kubeadm containerd
sudo apt-get install -y containerd \
  kubelet="$K8S_PKG" kubeadm="$K8S_PKG" kubectl="$K8S_PKG"
sudo apt-mark hold containerd kubelet kubeadm kubectl
kubeadm version -o short    # várt: v1.31.0

A containerd csomag az Ubuntu archívumból jön; a verzióját a madison kimenete alapján a labprofilban rögzíteni kell (containerd=<verzió>).

A containerd rendszerszintű cgroup driverét systemd-re állítjuk, mert a kubelet is systemd cgroup driverrel fut:

# Target: minden node (root)
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' \
  /etc/containerd/config.toml
sudo systemctl restart containerd

A sed itt illusztratív és törékeny; productionben a teljes containerd konfigurációt a clusterprofil részeként kell verziózni.

3. Bootstrap profil a kubeadm számára

# cluster-profile.yaml
# Cél: lab-cp1; nem közvetlenül éles klaszterre, a verziók ellenőrizendők
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
kubernetesVersion: v1.31.0
controlPlaneEndpoint: "lab-lb.lab:6443"
networking:
  podSubnet: "10.244.0.0/16"
  serviceSubnet: "10.96.0.0/12"
apiServer:
  certSANs:
    - "lab-lb.lab"
---
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
nodeRegistration:
  name: "lab-cp1"
  kubeletExtraArgs:
    cgroup-driver: "systemd"

Az első control plane inicializálása:

# Target: lab-cp1 (root)
sudo kubeadm init \
  --config=cluster-profile.yaml \
  --upload-certs

A --upload-certs segítségével a második és harmadik control plane node a kubeadm join --control-plane --certificate-key úton kapja meg a control plane certifikátumokat. A várt kimenet tartalmazza a kubeadm join parancsot a worker és a control plane node-ok számára, valamint azt, hogy a cluster inicializálása sikeres volt.

4. Admin kubeconfig és CNI

5. Control plane és worker join

A második control plane node:

# Target: lab-cp2 (root)
sudo kubeadm join lab-lb.lab:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash> \
  --control-plane \
  --certificate-key <key>

A <token>, <hash> és <key> a kubeadm init kimenetéből származik; a token 24 óra TTL-t kap, a certificate key rövid életű. A lab-cp3 join ugyanígy történik. A worker join:

# Target: lab-worker1 (root)
sudo kubeadm join lab-lb.lab:6443 \
  --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

Végső ellenőrzés:

# Target: lab-cp1, context lab-cluster
kubectl get nodes -o wide
# Várt: 4 Ready node, a control-plane node-okon control-plane role
kubectl get endpointslices -n default \
  -l kubernetes.io/service-name=kubernetes
# Várt: 10.42.0.11,10.42.0.12,10.42.0.13 (6443-as port)

A control-plane endpoint (lab-lb.lab:6443) a node-ok kubeconfigjában marad. A kube-apiserver certifikátum SAN listája tartalmazza a lab-lb.lab nevet; mivel a HAProxy TCP-módban, TLS-bontás nélkül továbbít, a kliens bármelyik control-plane node-hoz jut is, ugyanazt a lab-lb.lab nevet ellenőrzi, így a TLS-verification működik.

43.1.4 Hibák és ellenpróbák

Tünet: A kubeadm init leáll, mert a kubelet nem tudja elindítani a control plane podjait.
Hipotézis: A containerd cgroup driver SystemdCgroup beállítása nem került érvényesítésre.
Adatgyűjtés: sudo journalctl -u kubelet -n 50 --no-pager és crictl ps -a.
Egy változtatás: sudo sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml && sudo systemctl restart containerd.
Verifikáció: sudo crictl ps mutatja a futó kube-apiserver, etcd, controller-manager, scheduler konténereket.

Tünet: A node NotReady, a CoreDNS pod Pending.
Hipotézis: A CNI addon nem települt, vagy rossz pod CIDR-t adtunk.
Adatgyűjtés: kubectl describe node lab-cp1 | grep NetworkReady, kubectl get pods -n kube-system.
Egy változtatás: A clusterprofilban rögzített CNI manifest alkalmazása (kubectl apply -f lab-cni.yaml).
Verifikáció: A NetworkReady condition True, a CoreDNS pod Running.

Tünet: A kubeadm join lefut, de a node nem jelenik meg a kubectl get nodes listában.
Hipotézis: A bootstrap token lejárt, vagy a discovery CA hash nem egyezik.
Adatgyűjtés: kubeadm token list az első control plane-on, openssl x509 -in /etc/kubernetes/pki/ca.crt -sha256 -noout -fingerprint.
Egy változtatás: Új token és hash generálása: sudo kubeadm token create --print-join-command, majd a worker node-on az új paranccsal join.
Verifikáció: A node kubectl get nodes kimenetben megjelenik, és a kubelet a join után regisztrálja magát.

Tünet: etcd quorum hiba a második control plane join után.
Hipotézis: A control plane node-ok között hálózati packet loss vagy az etcd peer URL téves; a 3 node egyike még a régi, egyedülálló etcd cluster tagja.
Adatgyűjtés: sudo crictl logs <etcd-container> vagy kubectl logs -n kube-system etcd-lab-cp1 (kubeadm stacked topológiában az etcd static pod, nem systemd unit, ezért a journalctl -u etcd üres).
Egy változtatás: Ellenőrizni a --etcd-servers/--initial-cluster paramétereket a kubeadm configban, majd a sérült etcd tag újraindítása vagy a kubeadm reset után újrajoin.
Verifikáció: a pod Running állapota nem bizonyít quorumot; az etcdctl endpoint health mindhárom tagra is healthy-t ad (a parancsot lásd a 2. megoldásban), és az API elérhető a lab-lb.lab:6443 endpointon (kubectl get --raw='/readyz?verbose').

43.1.5 Feladatok

  1. Magyarázó feladat: Miért van szükség legalább három etcd tagra a HA control plane-ben, és miért nem elég két node? Milyen különbség van a stacked és az external etcd topológia között a bootstrap, backup és failure domain szempontjából? Indokolja a labor topológiáját.

  2. Konfigurációs feladat: A labhoston építsen egy új, önálló HA clustert a fenti topológia szerint. Készítse el a cluster-profile.yaml profilt, futtassa a host-prerekviziteket, a kubeadm init-et, a CNI telepítést, majd csatlakoztassa a második és harmadik control plane node-ot, végül egy worker node-ot. Adja meg a szükséges parancsokat, és írja le az expected postcondition-t.

  3. Diagnosztikai/failure feladat: A clusterben a lab-worker1 node hirtelen NotReady lett, és a kubectl describe node lab-worker1 azt mutatja, hogy a kubelet leállt. A node-ot újraindították, de a kubelet nem indul el, mert a CA tanúsítvány és a bootstrap credential érvénytelenné vált. Hogyan állítja helyre a node-ot anélkül, hogy a többi node-ot vagy az API-servert bántaná? Írja le a diagnosztikai lépéseket, a helyreállítást és a postcondition-t.

43.1.6 Megoldások

  1. Az etcd Raft-konzisztens: írni csak a quorummal, azaz ⌊n/2⌋+1 tag többségével lehet. Két node esetén a quorum 2, egy node kiesése után nincs többség, így a cluster nem tud commitolni, az API nem működik. Három node esetén a quorum 2, egy kiesés is megtartja (2/3); ez a minimális production HA. Páros taglétszám is működik, de nem növeli a hibatűrést (n = 4 esetén a quorum 3, így szintén csak 1 kiesést tűr, mint n = 3), viszont több tagnak kell válaszolnia; ezért páratlan taglétszámot választunk – ez hatékonysági, nem működési feltétel. A stacked topológiában az etcd a control plane node-okon fut, így kevesebb VM/operációs cost, de a kube-apiserver és az etcd failure domainje közös. Az external etcd külön node-okon fut, így a control plane és az etcd karbantartása függetlenül ütemezhető, de több node-ot kell üzemeltetni. A laborban stacked topológiát használunk, mert a cél az oktatás és a minimális erőforrás; productionben az etcd disk I/O és a control plane CPU-ról külön failure domainbe érdemes tenni.

  2. A parancsok a fenti kidolgozott példában szerepelnek (0. lépéstől: load balancer, swap, rögzített csomagverziók). A várható postcondition:

    kubectl get nodes -o wide
# várt: 4 node Ready, VERSION oszlop: v1.31.0 (a kubelet verziója)
kubectl get --raw='/readyz?verbose'
# várt: readyz check passed
EP=https://10.42.0.11:2379,https://10.42.0.12:2379,https://10.42.0.13:2379
PKI=/etc/kubernetes/pki/etcd
kubectl -n kube-system exec etcd-lab-cp1 -- etcdctl --endpoints=$EP \
  --cacert=$PKI/ca.crt --cert=$PKI/server.crt --key=$PKI/server.key \
  endpoint health
# várt: mindhárom endpoint "is healthy"

    A kubernetes Service EndpointSlice-a három control-plane IP-t tartalmaz, a clusterprofil YAML a git repóban van. A kubectl version csak a kliens és az API server verzióját adja, a kubeletét a get nodes -o wide VERSION oszlopa mutatja; a kubectl get cs (componentstatuses) 1.19 óta deprecated, és nem megbízható quorum-bizonyíték.

  3. Először a hatókört kell eldönteni: ha valóban a cluster CA cserélődött, az minden node-ot érint, és nem egy node helyreállítása a feladat. Ha csak a lab-worker1 hibás, a leggyakoribb ok a kubelet kliens-tanúsítványának lejárta vagy hibás rotációja. Diagnosztika a worker node-on (root):

    journalctl -u kubelet -n 100 --no-pager
P=/var/lib/kubelet/pki/kubelet-client-current.pem
openssl x509 -in "$P" -noout -enddate -issuer
openssl x509 -in /etc/kubernetes/pki/ca.crt -noout -fingerprint -sha256

    A CA ujjlenyomatát a control plane-en (/etc/kubernetes/pki/ca.crt) ugyanígy lekérdezzük és összevetjük. Unauthorized vagy x509: certificate has expired és lejárt notAfter esetén a node kliens-credentialje érvénytelen; eltérő CA-ujjlenyomatnál a node rossz CA-t ismer. Helyreállítás, a többi node érintése nélkül:

    # Target: lab-cp1, context lab-cluster
kubectl drain lab-worker1 --ignore-daemonsets --delete-emptydir-data
kubectl delete node lab-worker1
sudo kubeadm token create --print-join-command
# Target: lab-worker1 (root)
sudo kubeadm reset --force
sudo kubeadm join lab-lb.lab:6443 --token <token> \
  --discovery-token-ca-cert-hash sha256:<hash>

    A drain a régi Podokat szabályosan áthelyezi (különben Terminating/Unknown állapotban ragadhatnak); a Node-objektum törlése a régi lease-eket és a hozzá tartozó állapotot is eltávolítja. A join új Node-objektumot hoz létre, ezért uncordon nem kell. Postcondition: kubectl get node lab-worker1 Ready, a kubectl get csr kimenetében az új node-CSR Approved,Issued, a többi node változatlan.

43.1.7 Rövid összefoglaló

A Kubernetes clusterprofil a verzió, runtime, cgroup, network, storage, topology és credential lifecycle együttes desired state-je. Self-managed kubeadm esetén a control plane, etcd, certifikátumok és version skew a cluster üzemeltetőjének felelőssége; managed Kubernetes ezt a control plane-t kimozgatja, de a node-ok, addonok és policy továbbra is a felhasználóé. A HA control plane legalább három etcd tagot igényel; a páratlan taglétszám a hatékony választás, mert a páros nem növeli a hibatűrést. A bootstrap során a CNI hiánya blokkolja a DNS-t, a cgroup v2 és a systemd cgroup driver mismatch pedig a kubelet indítását. A clusterprofil legyen géppel olvasható, és a certifikátum-, token- és node-életciklus minden lépését rögzítse.

Továbbhasznált definíciók: Clusterprofil — verziózott leírás egy Kubernetes cluster kívánt állapotáról. Version skew — a Kubernetes komponensek megengedett maximális verzióeltérése. HA control plane — olyan control-plane/etcd topológia, amely egy node kiesését is elviseli többségi quorummal.
