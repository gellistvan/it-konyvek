50.5 Full-stack telemetria és alert labor

A full-stack telemetria labor célja, hogy ugyanazt a hibát ne csak egy nézetben lássuk. A metrika, log és trace eltérő felbontású bizonyítékot ad: a metrika aggregált statisztika, a log eseményszintű napló, a trace pedig parent-child ok-okozati lánc. Egy p99-es latency-növekedéshez például a metrika megmondja, hogy a /api/query lassult, a log megmutatja, hogy sok request DB_TIMEOUT hibával zárult, a trace pedig megmutatja, hogy a lassúság a auth_token feloldásból vagy a database response-ból ered. Ebben a laborban egy izolált Prometheus/Loki/Tempo/Grafana stacket és egy C++ labszolgáltatást építünk, hibát generálunk, három nézetben vizsgáljuk, és olyan riasztást adunk ki, amelyhez runbook tartozik.

50.5.1 Definíció és scope

Full-stack telemetria alatt itt azt értjük, hogy a rendszer minden rétegéből gyűjtünk jelet: a Linux hosztból node exporterrel, az alkalmazásból Prometheus metric endpointtal és OpenTelemetry (OTel) tracer/log bridge-dzsel, valamint a hálózati útból a normál request logokkal. A jelek a collector/backend rétegbe kerülnek, ahol erőforráskorlátot és retention policy-t kapnak.

A labban három adatosztályt különböztetünk meg:

  1. Metric: numerikus idősor, például lab_order_http_requests_total vagy lab_order_http_request_duration_seconds_bucket. Aggregálásra, alertingra és dashboard trendre jó, de egyedi request nem azonosítható belőle.
  2. Log: strukturált esemény, például request_start vagy db_timeout; a request_id és a trace_id a JSON-sor mezője (Lokiban szükség esetén structured metadata), nem stream-label (lásd Központi logplatform és adatpipeline). Labelben csak alacsony kardinalitású dimenziók vannak (job, namespace, host); a nagy kardinalitású mezőkre lekérdezéskor | json | request_id="…" szűréssel keresünk.
  3. Trace: span-fa. A root span a bejövő request, a gyermek spanek a külső hívások. A trace_id az egész requestet, a span_id az egy lépést, a parent_span_id a hívási relációt jelöli.

Az alert pipeline az a lánc, amely a Prometheus-riasztást Alertmanagernek küldi, ahol a route, group_by, silence dönt arról, hány értesítés megy ki, és milyen retry/intervallum mellett. Az alerthez mindig kapcsolunk egy runbook_url annotációt, mert a riasztás nem a megoldás, hanem az üzemeltetési szerződés kezdőpontja.

A C++ szolgáltatásban a metric és trace azonos requestcontextből indul (fogalmi vázlat; a prometheus-cpp és az opentelemetry-cpp API-ja a pinelt verzión ellenőrizendő):

auto tracer = trace::Provider::GetTracerProvider()->GetTracer(
    "lab-order-svc", "lab2025.01");

// A Register() családot (Family<Counter>&) ad; az Add() a sorozatot.
// A build_id deployonként egy érték: alacsony kardinalitású label.
auto& requests_family = prometheus::BuildCounter()
    .Name("lab_order_http_requests_total")
    .Help("Total HTTP requests")
    .Labels({{"build_id", BUILD_ID}})
    .Register(*registry);

auto& duration_family = prometheus::BuildHistogram()
    .Name("lab_order_http_request_duration_seconds")
    .Help("HTTP request latency")
    .Labels({{"build_id", BUILD_ID}})
    .Register(*registry);
auto& duration = duration_family.Add(
    {{"namespace", "lab-order"}, {"endpoint", "/api/query"}},
    prometheus::Histogram::BucketBoundaries{0.05, 0.1, 0.25, 0.5, 1.0});

void HandleQuery(const Request& req, Response& resp) {
  auto span = tracer->StartSpan("/api/query");
  auto ctx = span->GetContext();
  LogEvent("request_start", {
      {"trace_id", ctx.trace_id().ToLowerBase16()},
      {"span_id", ctx.span_id().ToLowerBase16()},
      {"request_id", req.request_id},
      {"build_id", BUILD_ID}});

  // ... a kérés feldolgozása, resp kitöltése ...

  duration.Observe(req.latency_seconds);
  requests_family
      .Add({{"namespace", "lab-order"},
            {"endpoint", "/api/query"},
            {"status", std::to_string(resp.status)}})
      .Increment();
  span->End();  // End() nélkül a span nem exportálódik
}

A build_id a deploymentkorrelációhoz kell: a metrikákon konstans labelként (deployonként egy érték, tehát alacsony kardinalitású), a logban és a trace-ben mezőként szerepel, így ha a hiba csak egy buildhez tartozik, mindhárom nézetben build_id szerint szűrhetünk. A request_id nagy kardinalitású, ezért csak a logban és a trace-attribútumban él, metrikalabelben nem. A pontos API (például Labels() a builderen, a BucketBoundaries típus) a pinelt prometheus-cpp verzión ellenőrizendő.

50.5.3 Dashboard és tesztelt PromQL

A Grafana dashboard nem csak képet rajzol, hanem a query-t futtatható lekérdezésként is kezeli. A laborpanorámában két panellel dolgozunk.

Hibaarány:

sum by (namespace, endpoint) (
  rate(lab_order_http_requests_total{status=~"5.."}[5m])
)
/
sum by (namespace, endpoint) (
  rate(lab_order_http_requests_total[5m])
)

P99 latency:

histogram_quantile(0.99,
  sum by (le, namespace, endpoint) (
    rate(lab_order_http_request_duration_seconds_bucket[10m])
  )
)

Ezeket a Grafana „Explore” nézetben is lefuttatjuk, mielőtt alertbe tesszük. A tesztelt PromQL itt azt jelenti, hogy a query-t legalább normál, nulla-forgalmú, valamint generált hibás időszakban is kiértékeljük, és promtool test rules syntax/fixture teszten is átengedjük. A riasztásszabály:

groups:
  - name: lab-order-service
    rules:
      - alert: LabOrderHighErrorRate
        expr: |
          sum by (namespace, endpoint) (
            rate(lab_order_http_requests_total{status=~"5.."}[5m])
          )
          /
          sum by (namespace, endpoint) (
            rate(lab_order_http_requests_total[5m])
          ) > 0.05
        for: 5m
        labels:
          severity: page
          lab: d250
        annotations:
          summary: >-
            5xx error rate > 5% on
            {{ $labels.namespace }}/{{ $labels.endpoint }}
          runbook_url: "https://git.invalid/lab-runbooks/d250-error-rate.md"

A fixture-alapú PromQL unit teszt egy pozitív és egy negatív esettel:

rule_files:
  - lab-service.rules.yml
evaluation_interval: 1m
tests:
  # Pozitív eset: 10 hibás / 100 sikeres kérés percenként
  # hibaarány = 10 / 110 ≈ 9,1% > 5%
  - interval: 1m
    input_series:
      - series: >-
          lab_order_http_requests_total{status="500",
          endpoint="/api/query",namespace="lab-order"}
        values: '0+10x10'
      - series: >-
          lab_order_http_requests_total{status="200",
          endpoint="/api/query",namespace="lab-order"}
        values: '0+100x10'
    promql_expr_test:
      - expr: |
          sum by (namespace, endpoint) (
            rate(lab_order_http_requests_total{status=~"5.."}[5m])
          )
          /
          sum by (namespace, endpoint) (
            rate(lab_order_http_requests_total[5m])
          ) > bool 0.05
        eval_time: 10m
        exp_samples:
          - labels: '{namespace="lab-order", endpoint="/api/query"}'
            value: 1
    alert_rule_test:
      - eval_time: 10m
        alertname: LabOrderHighErrorRate
        exp_alerts:
          - exp_labels:
              severity: page
              lab: d250
              namespace: lab-order
              endpoint: /api/query
            exp_annotations:
              summary: "5xx error rate > 5% on lab-order//api/query"
              runbook_url: "https://git.invalid/lab-runbooks/d250-error-rate.md"
  # Negatív eset: 1 hibás / 100 sikeres kérés percenként
  # hibaarány = 1 / 101 ≈ 0,99% < 5%
  - interval: 1m
    input_series:
      - series: >-
          lab_order_http_requests_total{status="500",
          endpoint="/api/query",namespace="lab-order"}
        values: '0+1x10'
      - series: >-
          lab_order_http_requests_total{status="200",
          endpoint="/api/query",namespace="lab-order"}
        values: '0+100x10'
    alert_rule_test:
      - eval_time: 10m
        alertname: LabOrderHighErrorRate
        exp_alerts: []

A pozitív eset 10 hibás és 100 sikeres kérést ad percenként: a hibaarány 10/110≈0,09110/110 \approx 0{,}091, azaz kb. 9,1%, így a > bool 0.05 kifejezés értéke 1, és a for: 5m letelte után az alert firing. A bool módosító nélkül az összehasonlítás szűrő volna: a feltételt teljesítő sorozat az eredeti hányadossal (≈ 0,091) maradna, nem 1-gyel. A negatív eset (1 hibás / 100 sikeres, 1/101≈0,00991/101 \approx 0{,}0099, kb. 0,99%) nem tüzel. A hivatalos promtool verzió és a fixture-szintaxis a labban pinelt Prometheus kiadáson ellenőrizendő; a promtool test rules futtatása még nem történt meg.

50.5.4 Log/request/trace/deploy correlation

A korreláció kulcsa, hogy a logba írt trace_id megegyezik a Tempóban élő span trace azonosítójával. A hibás request logját a Lokihoz intézett query-vel keressük:

{job="lab-order-svc"} | json | request_id="req-7f3a"
  | line_format "{{.msg}} level={{.level}}"

Ha a request_id-t nem ismerjük, a hibaarányos időablakban a db_timeout eseményeket keressük:

{job="lab-order-svc"} |= "db_timeout" | json
  | line_format "build_id={{.build_id}} trace_id={{.trace_id}}"

A kinyert trace_id-t a Grafana/Tempo trace nézetbe illesztve megkapjuk a span-fát, például:

Span Parent Duration Error
/api/query root 810 ms true
postgres.query root 800 ms true
auth_token.resolve root 5 ms false

A deploymentkorrelációhoz a panelen a sum by (build_id) (rate(lab_order_http_requests_total{status=~"5.."}[5m])) query-t használjuk; ez azért működik, mert a 50.5.2 vázlatában minden lab_order_* metrika konstans build_id labelt kap. Ha a hibás időablak csak a build_id="b-2025.07-test" értéknél látszik, akkor a hiba változtatásból ered, nem fizikai degradációból. Ez nem bizonyítja a root cause-t, de a hibát scope-olja.

50.5.5 Error/latency/saturation fixture

A labor hiba- és terhelésgenerátora a lab szolgáltatásban kap egy /_lab/error és /_lab/saturate endpointot. A /_lab/error?mode=500 bekapcsolása után a lab-order-svc minden /api/query kérésnél DB-timeoutot szimulál: a kérés egy postgres.query spanben 800 ms-ot vár, a spant Error státusszal zárja, db_timeout eseményt naplóz trace_id-val, növeli a lab_order_db_timeouts_total számlálót, és HTTP 500 választ ad (a lab_order_http_requests_total{status="500"} nő). A hibamód csak a beérkező forgalmon látszik, ezért mellette terhelést kell generálni. A /_lab/saturate egy rövid, CPU-bound spin függvényt hív, amellyel a node_cpu_seconds_total és a process CPU idősor emelkedik, de a szolgáltatás maga nem ír ki hibát.

Egyetlen kérés a lab-app-01 hoston (az URL idézőjelben, mert a ? shellben globkarakter):

lab-app-01$ curl -s -o /dev/null -w '%{http_code}\n' \
  'http://127.0.0.1:8080/api/query?item=100'

Az incidens szimulációja: a hibamód bekapcsolása, majd kb. 300 s-os terhelés (10 kérés/s), a válaszkódok összesítésével:

# target: lab-app-01
curl -s -X POST 'http://127.0.0.1:8080/_lab/error?mode=500'
for i in $(seq 1 3000); do
  curl -s -o /dev/null -w '%{http_code}\n' \
    'http://127.0.0.1:8080/api/query?item=100'
  sleep 0.1
done | sort | uniq -c

A CPU-fixture PromQL-je a host-szintű CPU-kihasználtságot (utilization) adja; a nevező a magszám, mert a mode="idle" sorozatból CPU-nként pontosan egy van:

sum by (instance) (
  rate(node_cpu_seconds_total{mode!="idle",job="node"}[5m])
)
/
count by (instance) (node_cpu_seconds_total{mode="idle",job="node"})

A node_cpu_seconds_total CPU-nként nyolc mode sorozatot ad (idle, iowait, irq, nice, softirq, steal, system, user), ezért a szűretlen count a magszám nyolcszorosát adná. Ez a USE-modell (Metrics/logs/traces és service questions) szerinti utilization, nem saturation: 80%-os kihasználtság mellett lehet nulla várakozás. Valódi telítettségi jel a CPU-ra várakozás, például a PSI-metrika rate(node_pressure_cpu_waiting_seconds_total[5m]) (ha a node_exporter pressure collectora engedélyezett), vagy a node_load1 és a magszám aránya 1 fölött. A pontos képlet NUMA és throttle szempontból a laborban finomítandó.

50.5.6 Alertmanager routing, grouping, silence

Az Alertmanager configban a route fa a severity=page riasztásokat a lab-page receiverbe, a többit a lab-default receiverbe irányítja:

route:
  receiver: lab-default
  group_by: ['alertname', 'namespace', 'endpoint']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 1h
  routes:
    - matchers: ['severity="page"']
      receiver: lab-page
      group_by: ['alertname', 'namespace']

receivers:
  - name: lab-default
    webhook_configs:
      - url: "http://gitops-lab-webhook.invalid/alerts"
  - name: lab-page
    webhook_configs:
      - url: "http://gitops-lab-webhook.invalid/page"

A group_by lényege, hogy ugyanazon endpoint több alertje egyetlen értesítésben menjen ki, ne okozzon notification floodot. A group_wait 30 másodpercet vár, amíg további riasztások érkeznek ugyanabba a groupba. A repeat_interval csak akkor küld ismétlést, ha a firing state továbbra is fennáll.

A false-positive ellenőrzéshez ideiglenes silence-t hozunk létre:

lab-mon-01$ sudo -u alertmanager amtool \
  --alertmanager.url=http://127.0.0.1:9093 \
  silence add alertname=LabOrderHighErrorRate \
  --duration=2h \
  --comment="lab d250 false-positive test, runbook_verify"

A silence nem oldja meg a hibát, csak az értesítést tartja nyugton, amíg a runbookot ellenőrizzük. A silencet expiráció és a csapatba való visszajelzés nélkül nem hagyhatjuk meg; a teszt végén kézzel lezárjuk:

lab-mon-01$ amtool --alertmanager.url=http://127.0.0.1:9093 \
  silence expire $(amtool --alertmanager.url=http://127.0.0.1:9093 \
    silence query -q alertname=LabOrderHighErrorRate)

50.5.7 Retention, query és access, cleanup

A backend-retention a Prometheusnál --storage.tsdb.retention.time=7d és --storage.tsdb.retention.size=10GB; a Loki vagy Tempo esetében a laborban külön config szükséges. A retention célja a kapacitás és a query-latency kordában tartása, nem a backup. A labban a 7d/10GB csak a laboron belüli rövid ablakra van tervezve.

A Grafana access control szintjén a laborban három szerep van: admin a stack tulajdonosnak, viewer a fejlesztőnek, és nincs anonymous access. A Prometheus query API-t és a Grafana datasource-ot nem tesszük ki a laboron kívülre. Ha a query túl drága, a kapcsolódó backend logban query timeout vagy query frontend hiba jelenik meg; ilyenkor a query-t szűkítjük, nem a limitet emeljük meg automatikusan.

A labor tisztításához a lab saját compose projectjét állítjuk le:

lab-mon-01$ docker compose --project-name lab-telemetry down -v
# Csak a lab-telemetry projecthez tartozó volume-ok törlődnek.

A -v csak a named volume-ot törli; ha bind mount config van, az a lab repository része marad.

  2. Alert és runbook: ha a 50.5.6 false-positive silence-ét már létrehoztad, előbb szüntesd meg (amtool … silence expire, lásd fent), mert aktív silence mellett az Alertmanager nem értesít. Ezután a LabOrderHighErrorRate alert firing az Alertmanagerben; a group_by miatt egyetlen page jön. A runbook lépései: ellenőrizd a Prometheus up{job="lab-order-svc"} == 0 kifejezést; ha up 0, a scrape hibás, ne az alkalmazást deployold; húzd ki a log/trace korrelációt; ha a hiba build_id változás után jött, rollback legyen az első akció; ha a db_timeout span folyamatosan időzik, a database query-t vizsgáld.

  3. Postcondition: az Alertmanager aktív alertje a LabOrderHighErrorRate, a Grafana dashboard mindhárom adatforrásból mutat jeladást, a runbook ellenőrzése megtörtént, a false-positive teszt silence-e kézzel lezárva (amtool silence query üres).

50.5.10 Feladatok

50.5.10.1 1. Magyarázó feladat: három nézet leképezése

Adott a következő hibajel: LabOrderHighLatencyP99 alert tüzei, de a LabOrderHighErrorRate nem. Logban slow_query események jelennek meg egy build_id érték után. Melyik metrika, log és trace kifejezés segít a hibát scope-olni? Indokold, miért nem elég a metrika önmagában.

50.5.10.2 2. Adminisztratív/konfigurációs feladat: alert és silence

Írj Prometheus alert rule-t LabOrderHighCpuUtilization néven, amely akkor tüzel, ha a lab-app-01 node_exporterén mért CPU-kihasználtság (utilization) 10 percen át 80% feletti. Állítsd be az Alertmanager route-ot úgy, hogy a severity=page alert a lab-page receiverbe menjen, és a riasztás mellé csatolj runbook URL-t. Hozz létre egy 30 perces silence-t a false-positive teszteléshez, és írd le az ellenőrzést.

50.5.10.3 3. Diagnosztikai/failure feladat: hibaüzemeltetés és runbook

A lab-order-svc db-timeout hibát mutat, a Prometheusban a lab_order_db_timeouts_total növekszik, a logban db_timeout események trace_id-val, a trace-ben a postgres.query span 500 ms-os. Írj rövid runbookot a következő formában: hipotézis, adatgyűjtés, egy változtatás, verification, rollback. Melyik PromQL megerősítené, hogy a hiba a postgres.query spanből, és nem az autentikációból ered?

50.5.11 Megoldások

50.5.11.1 1. Megoldás

A metrika a 250 ms-nál lassabb kérések aránya buildenként: 1 - (sum by (build_id) (rate(lab_order_http_request_duration_seconds_bucket{le="0.25"}[5m])) / sum by (build_id) (rate(lab_order_http_request_duration_seconds_count[5m]))). A le="0.25" bucket a 250 ms-nál gyorsabb vagy azzal egyenlő kérések kumulatív számlálója, ezért a lassú arány az 1-ből kivont hányados. A build_id a 50.5.2 vázlata szerint a metrikák konstans labelje (deployonként egy érték), így a bontás megmutatja, hogy a lassulás adott buildhez tartozik-e. A log: {job="lab-order-svc"} |= "slow_query" | json | line_format "{{.build_id}} {{.trace_id}} {{.msg}}". Ez kinyeri a trace_id-t és a build_id-t. A trace: a trace_id lekérdezés a Tempo által megmutatja, hogy a postgres.query span a lassú, és nem a auth_token.resolve. A metrika önmagában azért nem elég, mert csak aggregált idősoron látunk, nem tudjuk, hogy a lassúságot egy lassú adatbázislekérdezés vagy a request queue-ban eltöltött várakozás okozta-e, ami a backlog-saturation jele.

50.5.11.2 2. Megoldás

Prometheus rule:

- alert: LabOrderHighCpuUtilization
  expr: |
    (
      sum by (instance) (
        rate(node_cpu_seconds_total{mode!="idle",job="node"}[5m])
      )
      /
      count by (instance) (node_cpu_seconds_total{mode="idle",job="node"})
    ) > 0.8
  for: 10m
  labels:
    severity: page
    lab: d250
  annotations:
    summary: "CPU utilization > 80% on {{ $labels.instance }}"
    runbook_url: "https://git.invalid/lab-runbooks/d250-cpu-utilization.md"

A nevező a magszám: a mode="idle" sorozatból CPU-nként egy van. A count by (instance) (rate(node_cpu_seconds_total[5m])) nevező hibás volna, mert CPU-nként mind a nyolc mode sorozatot számolja: egy teljesen terhelt 4 magos hoston az arány 4/32=0,1254/32 = 0{,}125 lenne 1,0 helyett, és a szabály sosem tüzelne. Ellenpróba: promtool test rules 4 cpu × 8 mode input sorozattal, ahol teljes terhelésnél a kifejezés értéke 1,0. A szabály utilizationt mér; ha telítettségre (saturation) kell riasztani, a PSI-alapú rate(node_pressure_cpu_waiting_seconds_total[5m]) a megfelelő jel.

Alertmanager route a severity=page matcherrel a lab-page receiverbe irányul; a receiver webhook URL-je http://gitops-lab-webhook.invalid/page. A silence:

lab-mon-01$ sudo -u alertmanager amtool \
  --alertmanager.url=http://127.0.0.1:9093 \
  silence add alertname=LabOrderHighCpuUtilization \
  --duration=30m \
  --comment="lab d250 false-positive test"

Ellenőrzés: amtool silence query alertname=LabOrderHighCpuUtilization. Postcondition: a silence 30 percig aktív; a severity=page route a lab-page receiverbe irányít; a Prometheus alerts felületén a rule firing vagy pending állapotú, de Alertmanager nem értesít.

50.5.11.3 3. Megoldás

Runbook vázlat:

  • Hipotézis: a db-timeout a postgres.query spanben jelentkezik, és a hiba az új buildkód-változásból érkezett.
  • Adatgyűjtés: rate(lab_order_db_timeouts_total[5m]), rate(lab_order_http_requests_total[5m]) arány, loki query {job="lab-order-svc"} |= "db_timeout", tempo trace trace_id. A PromQL sum by (build_id) (rate(lab_order_db_timeouts_total[5m])) megmutatja, hogy csak a rossz buildnél nőtt a timeout.
  • Egy változtatás: rollback a korábbi buildre, mert a deployment révén a hiba a buildhez köthető.
  • Verification: a lab_order_db_timeouts_total rate 5 perc alatt 0-ra csökken, az alert inactive.
  • Rollback: ha a build-rollback nem javít, a változtatás nem segített: állítsd vissza az új buildet (vagy maradj a régin, ha az stabil), és új hipotézisként vizsgáld a DB oldali okot, például a connection pool telítettségét.

A span-időtartamot PromQL-ből csak akkor lehet lekérdezni, ha valami span-metrikát állít elő: a jelen stackben ilyen nincs. Ha a Collectorban spanmetrics connector fut (a pinelt contrib-verzión ellenőrizendő; a metrikanév a connector beállításától és a Prometheus-exporttól függ), a p95 span-időtartam: histogram_quantile(0.95, sum by (le, span_name) (rate(<spanmetrics duration bucket>{span_name=~"postgres.query|auth_token.resolve"}[10m]))). Ha a postgres.query p95-je kb. 500 ms, az auth_token.resolve-é pedig 5 ms alatt marad, a hiba nem az autentikációból ered. Span-metrika nélkül a megerősítés a Tempo trace-ekből történik (a db_timeout logok trace_id-jai alapján).

50.5.12 Rövid összefoglaló

A full-stack telemetria labor a hiba ok-okozati láncát metrika, log és trace korrelációjával vizsgálja. A Prometheus alert nem önálló ábra, hanem üzemeltetési szerződés: a rule-hoz runbook URL tartozik, az Alertmanager route/grouping/silence pedig a notification policy-t tartja kordában. A laborban a PromQL query-t előbb fixture-teszttel ellenőrizzük, majd a generált hibát három nézetben azonosítjuk. A retention, query access és cleanup a backend kapacitás- és jogosultsági határait rögzíti.

Továbbhasznált definíciók:

  • Metric/log/trace correlation: a trace_id és a request_id az egyes nézetekben ugyanazt az eseményt címezi, így a hibát nem kell szövegkereséssel összeilleszteni.
  • Alert pipeline: Prometheus rule evaluation -> Alertmanager routing/grouping/silence -> notification receiver -> runbook.
  • Saturation fixture: a rendszer telítettségét szimuláló, ellenőrzött hibaterhelés, amely nem tévesztendő össze a valódi termelési hibaforgással.
