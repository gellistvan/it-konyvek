37.5 C++ image build és artifact audit labor

37.5.1 Motiváció és cél

Szenior C++ fejlesztőként a forráskód buildelése, tesztelése és a kiadási csomag előállítása ismert. A konténeres üzemeltetésben azonban a release artifact nem a bináris vagy a tarball, hanem az OCI image: a futtatókörnyezetet, könyvtárakat, konfigurációt és az alkalmazást együtt tartalmazó, tartalomcímzett csomag. Ebből következik, hogy az image-et verzióval, digesttel és manifesttel kell rögzíteni, hogy a production rollback ne egy latest tag legyen. A labor célja, hogy egy meglévő, natív C++ programból olyan image-csomagot készítsünk, amely buildelhető, futtatható, auditálható (SBOM, scan, signature), és digest alapján visszagörgethető.

A példák izolált labkörnyezetben futnak: labhost: labvm-02, felhasználó labuser UID 1000, munkakönyvtár /home/labuser/lab-cpp-image. A registry a laborhálózatban registry.lab.example:5000, a cert self-signed. A parancsok docker-t használnak; a Podman parancsok többnyire azonosak, de a registry hitelesítő adat kezelése eltérhet.

37.5.2 Definíció és működés

A konténeres release artifact rétegelt, tartalomcímezhető entitás. Az image manifest (application/vnd.oci.image.manifest.v1+json) leírja a konfiguráció digestjét és a rétegek listáját. A image digest (például sha256:...) a manifest hash-e, ezért egy image tartalmának egyértelmű, immutable azonosítója. A tag (lab-1, 1.2.3, latest) mutató, amely másik digestre mutatható át. A Provenance (Származási nyilvántartás) azt rögzíti, hogy milyen forrásból, build-környezetből, paraméterekkel készült az artifact; a SBOM (Software Bill of Materials) a komponenslistát, verziókat és függőségeket tartalmazza. A signature (aláírás) az image digesthez köti a kiadó kulcsát. Az audit e három elem ellenőrzését jelenti.

A build leggyakoribb mintája a multi-stage build: az első szakasz fordít, a második csak a futáshoz szükséges állományokat csomagolja. Így a production image nem tartalmazza a teljes GCC-t, fejléceket, build-eszközöket. A natív C++ programnál a futtató szakaszban a dinamikus könyvtárak (libstdc++, libgcc, glibc, egyéb ABI-függő komponensek) jelenlétét explicit módon kell biztosítani. A C++ ABI azt garantálja, hogy a std::string, virtuális metódus, exception és standard library típusok bináris kompatibilisek legyenek a build és runtime között. Ha a build image újabb GCC-t használ, mint a runtime libstdc++, a betöltés akár a GLIBCXX_... symbol verzió hiányával is meghiúsulhat.

Az image futásidejű szerződése:

  • nonroot: a process nem root felhasználóként fut, UID/GID explicit.
  • readonly root filesystem: a root fájlrendszer csak olvasható, a scratch/adat külön tmpfs vagy volume.
  • data volume: a persistens vagy futásidejű adat a kijelölt /data köteten van, nem az image rétegben.

A smoke test a build része, és nem a kiadás opcionális lépése. Azt ellenőrzi, hogy az image elindul, a belépési pont lefut, és a minimális funkcionalitás (adatírás, hálózati válasz, kimenet) teljesül.

37.5.3 Kidolgozott példa

37.5.3.1 A C++ program

A program egy számláló, amely a /data/counter.txt fájlt olvassa, növeli és visszaírja. Ez a read-only root és a data volume szerződést is teszteli.

main.cpp a lab-cpp-image/src/ mappában:

#include <iostream>
#include <fstream>
#include <string>

int main() {
    const std::string path = "/data/counter.txt";
    unsigned long count = 0;
    std::ifstream in(path);
    if (in) {
        in >> count;
    }
    ++count;
    std::ofstream out(path, std::ios::trunc);
    if (!out) {
        std::cerr << "cannot write " << path << "\n";
        return 1;
    }
    out << count << "\n";
    std::cout << "run " << count << "\n";
    return 0;
}

A program libstdc++-t igényel, így a runtime image-nek tartalmaznia kell azt.

37.5.3.2 Multi-stage Dockerfile

# build stage: ugyanaz a distro-kiadás, mint a runtime
FROM ubuntu:24.04 AS build
RUN apt-get update \
    && apt-get install -y --no-install-recommends g++ \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /src
COPY src/main.cpp .
RUN g++ -O2 -Wall -o cpp-counter main.cpp

# runtime stage
FROM ubuntu:24.04
RUN apt-get update \
    && apt-get install -y --no-install-recommends libstdc++6 \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /src/cpp-counter /usr/local/bin/cpp-counter
# az ubuntu:24.04 image-ben az 1000-es UID-ot az "ubuntu" user foglalja
RUN userdel --remove ubuntu \
    && useradd --create-home --uid 1000 appuser \
    && mkdir -p /data && chown 1000:1000 /data
WORKDIR /data
USER 1000:1000
ENTRYPOINT ["/usr/local/bin/cpp-counter"]

A builder és a runtime ugyanabból a distro-kiadásból (Ubuntu 24.04) épül, így a runtime libstdc++6 legalább olyan új, mint a builder GCC-jéé. Ha a builder újabb GCC-vel fordít, mint amilyen libstdc++-t a runtime ad (például gcc:13-bookworm builder és debian:bookworm-slim runtime: a GCC 13 minden <iostream>-et használó programban GLIBCXX_3.4.32 szimbólumverziót kér, a bookworm GCC 12-es libstdc++6-ja ezt nem tartalmazza), a program version GLIBCXX_3.4.32 not found hibával nem indul. A /data könyvtárat a runtime stage appuser tulajdonába adjuk: a WORKDIR magától root tulajdonú könyvtárat hozna létre, és egy új, üres named volume első csatolásakor a Docker az image /data könyvtárának tartalmát és tulajdonosát is a kötetbe másolja. Mindkét base image a kiadáskor digestgel rögzítendő (ubuntu:24.04@sha256:...), nem a mozgó taggel.

37.5.3.3 Build, digests és manifest rögzítés

# labhost: labvm-02, user: labuser, UID 1000
# cwd: /home/labuser/lab-cpp-image
IMAGE=registry.lab.example:5000/cpp-counter
TAG=lab-1
docker build -t "$IMAGE:$TAG" .
# a helyi image config digestje (image ID); a manifest digest még nincs
docker image inspect --format '{{.Id}}' "$IMAGE:$TAG"

A manifest és az index adatai a push után, a registryből kérdezhetők le: a docker manifest inspect és a docker buildx imagetools inspect nem a helyi image store-ból olvas, a docker image ls --digests pedig push előtt <none> digestet mutat. A push előtt a registryvel meg kell győződni a TLS és auth konfigurációról (lásd lent):

docker login registry.lab.example:5000
docker push "$IMAGE:$TAG"
docker image ls --digests "$IMAGE"
docker manifest inspect --verbose "$IMAGE:$TAG" > manifest-remote.json
docker buildx imagetools inspect "$IMAGE:$TAG" > image-index.txt

A manifest-remote.json tartalmazza a config digestet és a layer digesteket. A docker buildx imagetools inspect akkor hasznos, ha multiarch indexet is kezelni akarunk; platform-specifikus kiépítéshez a --platform linux/amd64 opciót explicit meg kell adni.

Az image digest rögzítése:

DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' "$IMAGE:$TAG")
echo "$DIGEST" > release-digest.txt

A release-digest.txt a release contract része; ezt kell commitolni, nem a taget.

37.5.3.4 Smoke test

docker run --rm --read-only --tmpfs /tmp --volume lab-data:/data \
  --name cpp-counter-smoke "$IMAGE:$TAG"

Várható kimenet:

run 1

Ellenőrzés: a konténer 0-ás exit kóddal leállt, és a kimenet run <n> mintát ad. A --read-only a root fájlrendszert csak olvashatóvá teszi; a /tmp-re az alkalmazás nem ír, de a std::ifstream és std::ofstream a /data köteten dolgozik.

37.5.3.5 Registry and signature folyamat

A laborban a registry certje self-signed. A Docker daemonnak megbíznia kell a CA-ban:

sudo mkdir -p /etc/docker/certs.d/registry.lab.example:5000
sudo cp /home/labuser/lab-registry-ca.crt \
  /etc/docker/certs.d/registry.lab.example:5000/ca.crt
sudo systemctl restart docker

A hitelesítő adatokat ne tartsuk shell historyban; a laborban dummy jelszó használható, de a production secret kezelését a d104-es fejezet tárgyalja.

SBOM előállítása és scan:

syft docker:"$IMAGE:$TAG" -o spdx-json > sbom.json
trivy image --severity HIGH,CRITICAL "$IMAGE:$TAG"

Aláírás, attestation és verify cosignnal, a push után rögzített digestre ($DIGEST a name@sha256:... alakú RepoDigest, lásd fent):

cosign generate-key-pair
cosign sign --key cosign.key "$DIGEST"
cosign verify --key cosign.pub "$DIGEST"
# aláírt SLSA v1 provenance attestation készítése és ellenőrzése
cosign attest --key cosign.key --type slsaprovenance1 \
  --predicate provenance.json "$DIGEST"
cosign verify-attestation --key cosign.pub --type slsaprovenance1 \
  "$DIGEST"

A cosign attach attestation nem erre való: egy már aláírt DSSE-borítékot csatol, predicate-ből nem készít aláírt attestationt. A slsaprovenance1 típus SLSA v1 predicate-et jelent (a slsaprovenance v0.2-t, más mezőkkel); a típusneveket a pinelt cosign-verzió cosign attest --help kimenetével kell ellenőrizni. A provenance.json SLSA v1 predicate: buildDefinition (buildType, externalParameters, resolvedDependencies) és runDetails (builder.id, metadata). A Git commit hash, a build ID és az image digest szerepeljen benne. A bináris natív build ID-ja a binárisból kinyerhető readelf -n segítségével, de az nem része az image manifestnek, hanem a provenance artifact leírásának.

37.5.3.6 Digest-alapú rollback

Tegyük fel, hogy a lab-2 tag hibás, és a lab-1 digestje sha256:good.... A rollback nem a tag átírását jelenti, hanem a pontosan azonosított digest futtatását:

# például: registry.lab.example:5000/cpp-counter@sha256:good...
GOOD_DIGEST=$(cat release-digest.txt)
docker pull "$GOOD_DIGEST"
docker run --rm --read-only --tmpfs /tmp --volume lab-data:/data "$GOOD_DIGEST"

Ha a taget is frissíteni kell a registryben, az új taget a jó digestre mutatva toljuk fel:

docker tag "$GOOD_DIGEST" "$IMAGE:lab-stable"
docker push "$IMAGE:lab-stable"

37.5.4 Hibák és ellenpróbák

37.5.4.1 Hiányzó futtató könyvtár

Tünet:

/lib/x86_64-linux-gnu/libstdc++.so.6: version `GLIBCXX_3.4.32' not found

vagy

error while loading shared libraries: libstdc++.so.6:
cannot open shared object file: No such file or directory

(a második üzenet a valóságban egy sorban jelenik meg). A hiba a runtime stage-ben van: a libstdc++.so.6 hiányzik, vagy régebbi, mint a build image g++ verziójához tartozó könyvtár. Diagnosztika:

docker run --rm --entrypoint /bin/bash "$IMAGE:$TAG" \
  -c 'ldd /usr/local/bin/cpp-counter'
# a bináris által kért legmagasabb GLIBCXX-verzió (a build hoston):
objdump -T cpp-counter | grep -o 'GLIBCXX_3\.4\.[0-9]*' | sort -V | tail -1

Az ldd megmutatja, melyik shared libraryt vagy szimbólumverziót nem találja. Javítás: a runtime libstdc++ legalább a builder GCC-jének verziójához tartozó legyen – vagyis ugyanabból a distro-kiadásból épüljön a builder és a runtime (a fenti ubuntu:24.04 páros), vagy a binárist -static-libstdc++ -static-libgcc kapcsolókkal fordítjuk. Egy régebbi distro runtime-jában az apt-get install libstdc++6 nem segít, mert a csomag újabb verziót nem kínál. Ha a base image frissítése változtatja a kiadást, a digest megváltozik, tehát a release-digestet újra rögzíteni kell.

37.5.4.2 Architektúra mismatch

Tünet:

exec format error

Ha az image linux/amd64-re épült, de a futtató hoszt linux/arm64, a bináris formátum nem futtatható. Diagnosztika:

docker image inspect "$IMAGE:$TAG" | jq '.[0].Architecture'
uname -m

Javítás: multiarch build docker buildx build --platform linux/amd64,linux/arm64 --push -t "$IMAGE:$TAG" . és a futtatásnál a megfelelő platform kiválasztása. Előfeltétel: az idegen architektúrájú RUN lépésekhez QEMU binfmt-regisztráció kell (például docker run --privileged --rm tonistiigi/binfmt --install arm64, vagy a hoston a qemu-user-static csomag); ellenőrzés: docker buildx inspect --bootstrap | grep Platforms listájában szerepel a linux/arm64. Az ABI különbségek miatt a libstdc++ sem cserélhető platformok között.

37.5.4.3 Registry TLS hiba

Tünet:

x509: certificate signed by unknown authority

A Docker daemon nem bízik a registry self-signed CA-jában. A laborban a CA-t a /etc/docker/certs.d/ alá kell telepíteni, nem szabad insecure-registry-t beállítani. Ellenpróba: openssl s_client -connect registry.lab.example:5000 -showcerts megmutatja a certet, és ellenőrizhető, hogy a CA megegyezik-e a labor CA-val.

37.5.4.4 Authentication failure

Tünet push közben:

unauthorized: authentication required

A docker login nem futott le, vagy a credential store nem találja a bejegyzést. Diagnosztika:

docker logout registry.lab.example:5000
docker login registry.lab.example:5000
docker push "$IMAGE:$TAG"

Ellenőrzés: a login után a ~/.docker/config.json hitelesítő adatot tartalmazhat (bár titkos tárolásban), de a laborban dummy credential.

37.5.4.5 Smoke test hiba

Tünet:

cannot write /data/counter.txt

Lehetséges okok:

  1. A /data (és így az első csatoláskor belőle feltöltött új kötet) root tulajdonú, mert a runtime stage nem adta át az appuser-nek (a WORKDIR önmagában root tulajdonú könyvtárat hoz létre). Ha a lab-data kötet már root tulajdonnal létrejött, a Dockerfile javítása után a laborban docker volume rm lab-data és újralétrehozás kell, mert a Docker csak üres kötetet tölt fel az image tartalmából.
  2. A /data kötet nincs csatolva: --read-only mellett ekkor az image-réteg /data könyvtára sem írható. (A hibás kötetnév nem ezt okozza: új, üres kötet jön létre, ugyanazzal a tulajdonossal.)

--read-only nélkül a /data image-rétegbe írás sikeres lehet, mégis a production szerződés sérül. A hibakereséshez ellenőrizni kell a felhasználót, a tulajdont és a mount listát:

docker run --rm --read-only --tmpfs /tmp --volume lab-data:/data \
  --entrypoint /bin/sh "$IMAGE:$TAG" \
  -c 'id; ls -ldn /data; mount | grep /data; touch /data/probe'
# hibás állapotban: uid=1000 ..., a /data tulajdonosa 0 0,
# touch: cannot touch '/data/probe': Permission denied

37.5.5 Feladatok

37.5.5.1 1. feladat — magyarázó

Magyarázd el, miért nem elegendő a latest vagy lab-1 tag a release artifact azonosításához, és milyen szerepe van a manifest digestnek a rollbackben. Tégy javaslatot, milyen mezőket tárolj a release-jegyzőkönyvben.

37.5.5.2 2. feladat — adminisztrációs/konfigurációs

Építsd fel a példa image-et a fenti Dockerfile-lal és main.cpp-vel. Konfiguráld:

  • nonroot felhasználó appuser UID 1000;
  • read-only root futás;
  • /data volume lab-data;
  • lab-1 tag.

Végezd el a push-t a registry.lab.example:5000 registrybe, rögzítsd a digestet, generálj SBOM-ot, futtass trivy image-t, majd cosign sign és verify. Végül mutasd be a digest-alapú rollbacket: tedd a lab-1 digestet elérhetővé lab-stable tagként, és indítsd el sikeres smoke testtel.

37.5.5.3 3. feladat — diagnosztikai/failure/recovery

A laborban az alábbi hibák közül legalább egyet reprodukálj, diagnosztizálj, egyetlen változtatással javíts, és ellenőrizd:

  1. A runtime image-ből hiányzik a libstdc++; indításkor cannot open shared object file. Reprodukció (szándékos hibainjektálás a laborban): a runtime stage COPY --from=build sora után ideiglenesen vedd fel a RUN rm -f /usr/lib/x86_64-linux-gnu/libstdc++.so.6* sort. Változat: GCC 13-as builder (gcc:13-bookworm) és debian:bookworm-slim runtime → GLIBCXX_3.4.32 not found.
  2. A registry login nem történt; push unauthorized hibával leáll.
  3. A konténer exec format error-rel indul, mert a build linux/arm64-re készült, de a futtató hoszt amd64.

A javítás után a smoke test run 1 kimenetet adjon.

37.5.6 Megoldások

37.5.6.1 1. feladat megoldása

A tag mutató, bármikor átállhat egy másik digestre, így nem alkalmas immutable release rögzítésre. A latest ráadásul nem hordoz verziót. A digest a manifest kriptográfiai hash-e, tehát a konfiguráció és a rétegek együttes tartalmát egyértelműen azonosítja. Rollbackkor a jó digestet kell futtatni, nem a taget. A release jegyzőkönyv minimális mezői: image név, tag, digest, source revision (git commit), build timestamp, builder ID, SBOM digest, signature digest, provenance digest, deployment cél.

37.5.6.2 2. feladat megoldása

A parancsok a fentiek szerint futnak. A build:

IMAGE=registry.lab.example:5000/cpp-counter
docker build -t "$IMAGE:lab-1" .
docker push "$IMAGE:lab-1"
DIGEST=$(docker inspect --format='{{index .RepoDigests 0}}' \
  "$IMAGE:lab-1")
echo "$DIGEST" > release-digest.txt

SBOM, scan és sign:

syft docker:"$IMAGE:lab-1" -o spdx-json > sbom.json
trivy image --severity HIGH,CRITICAL "$IMAGE:lab-1"
cosign generate-key-pair
cosign sign --key cosign.key "$DIGEST"
cosign verify --key cosign.pub "$DIGEST"

Rollback digest alapján:

docker tag "$DIGEST" registry.lab.example:5000/cpp-counter:lab-stable
docker push registry.lab.example:5000/cpp-counter:lab-stable
docker run --rm --read-only --tmpfs /tmp --volume lab-data:/data \
  "registry.lab.example:5000/cpp-counter:lab-stable"

Postcondition: a release-digest.txt a digestet tartalmazza; a registryben a lab-stable tag ugyanarra a digestre mutat; a smoke test run <n> kimenetet ad 0 exit kóddal; a cosign verify aláírással tér vissza.

37.5.6.3 3. feladat megoldása

  1. Missing libstdc++: a runtime image-ből hiányzik a libstdc++.so.6 (a hibainjektáló rm sor), az ldd kimenetében libstdc++.so.6 => not found áll. Javítás: a hibát okozó sor eltávolítása, hogy a runtime stage a builderrel azonos kiadású libstdc++6 csomagot tartalmazza; rebuild. A változat (GLIBCXX_3.4.32 not found) javítása: azonos distro-kiadású builder és runtime, vagy -static-libstdc++ -static-libgcc fordítás – a régi runtime-ba telepített libstdc++6 nem segít. Verifikáció: docker run --rm --entrypoint /bin/sh "$IMAGE:$TAG" -c 'ldd /usr/local/bin/cpp-counter | grep -c "not found"' kimenete 0, a smoke test kimenete run 1.

  2. Unauthorized: a docker login registry.lab.example:5000 futtatása szükséges a push előtt. Verifikáció a push sikeres.

  3. Exec format error: a buildkor --platform linux/arm64 szerepelt. Javítás: docker buildx build --platform linux/amd64 --load -t "$IMAGE:$TAG" . és újrabuild; a docker-container driverű buildx builder (a d182 lab-builder-e) --load vagy --push nélkül az eredményt csak a build cache-ben hagyná, és a smoke test a régi image-et látná. Verifikáció docker image inspect Architecture mező amd64, smoke test sikeres.

Postcondition minden esetben: a smoke test a run 1 kimenetet adja; a release digest rögzítve van; a registryben a tag a javított digestre mutat.

37.5.7 Rövid összefoglaló

A konténeres release artifact az OCI image, amelyet manifest és digest azonosít; a tag csak mutató. A multi-stage build a build és runtime környezetet szétválasztja, a runtime image-ben a C++ ABI-kompatibilis könyvtárakat explicit módon telepíteni kell. A production image nonroot, read-only root fájlrendszerrel és adatvolume-mal fut. Az auditálhatóságot SBOM, vulnerability scan és cosign aláírás/verify adja; a rollback a jó digest futtatását jelenti. A réteghibák (missing library, arch, auth, TLS) a megfelelő réteg azonosításával és egyetlen változtatással javíthatók.
