37.3 Registry auth, push/pull és retention

37.3.1 Motiváció és definíció

A build pipeline eredménye akkor válik futó szolgáltatássá, ha a Kubernetes node vagy a céleszköz le tudja húzni a tárolt image-et. A registry ezért nem egyszerű HTTP fájlszerver, hanem elérhetőséggel, hitelesítéssel, integritással és retention élettartammal rendelkező szolgáltatás. Ha a DNS-feloldás, a TLS-lánc, a token-scope vagy a manifest bármely rétege hibás, a pull nem jön létre, és a hiba a fejlesztő buildjétől függetlenül áll elő.

Az előzményekből d182 az OCI image, digest és tag modellt, d142 a TLS- és tanúsítványláncot, d111 az inventory, desired state és drift fogalmát adja. Itt ezeket a registry mint artifact distribution szolgáltatás üzemeltetési nézetébe kapcsoljuk.

Registry endpoint: az a hálózati erőforrás, amely az OCI Distribution API-t kiszolgálja; a repository nevekkel és reference-ekkel együtt értelmezett, ezért nem csak IP-cím vagy port. Például https://registry.lab.example:5000 az endpoint, amelyen belül a lab-team/cpp-service repository érhető el.

OCI Distribution API: szabványos HTTP API image manifestek és blobok feltöltésére, lekérdezésére és törlésére; a specifikáció biztosítja, hogy a Docker, Podman, containerd, skopeo és más OCI-kliens közös protokollt beszéljen. A scope itt a regisztrációkliens és registry közötti hitelesített, tartalomcímzett műveletekre terjed ki, nem a node-ra való kép pull scheduler működésére.

A munkafolyamatot így modellezzük:

Ppull=DNS→TCP/TLS→Auth→Manifest→Blobs P_{pull} = \text{DNS} \rightarrow \text{TCP/TLS} \rightarrow \text{Auth} \rightarrow \text{Manifest} \rightarrow \text{Blobs}

ahol minden lépés előfeltétele a következőnek; a digest-verifikáció a manifest és blob réteg integritását együtt zárja.

37.3.2 Registry endpoint és OCI Distribution API

A registry elérhetőség értékelése mindig a fenti lánc mentén halad. A DNS-feloldás a service name, port és feloldott címek közötti kapcsolatot ellenőrzi; a TLS a hitelesítést; a HTTP az API elérhetőségét. Az endpoint állapota tehát nem bináris: a curl https://registry... sikeréhez mindhárom rétegnek működnie kell.

A leggyakoribb OCI Distribution API műveletek:

Művelet Metódus Példa útvonal Cél
API discovery GET /v2/ végpont verzió és support ellenőrzése
Tag lista GET /v2/<name>/tags/list referencia felsorolás
Manifest HEAD/GET/PUT/DELETE /v2/<name>/manifests/<reference> manifest és digest műveletek
Blob létezés HEAD /v2/<name>/blobs/<digest> tartalomcímzett blob ellenőrzés
Blob upload POST/PUT /v2/<name>/blobs/uploads/ rétegfeltöltés

A reference lehet tag (1.0.0) vagy digest (sha256:...). A tag mutálható, a digest immutable. Emiatt a laborban mindig digestet kérünk, amikor a tényleges artifactot azonosítjuk, a tag csak kényelmi index.

A registry endpoint láthatósága a build agent, a Kubernetes node és a fejlesztői gép felől azonos vizsgálattal történik: getent hosts, openssl s_client, curl -I /v2/. A /v2/ API-válasz rate-limit és auth szempontból is diagnosztikus; a 401 válasz a hitelesítés szükségességéről árulkodik, a 200-as válasz az API elérhetőségét jelenti.

37.3.3 Auth token/scope és credential helper

A registry kétféle hitelesítési modellt használhat, és a kliens a 401 Unauthorized válasz WWW-Authenticate fejlécéből tudja meg, melyik van érvényben:

  • HTTP Basic (WWW-Authenticate: Basic realm="..."): a kliens minden kérésnél Authorization: Basic <base64(user:jelszó)> fejlécet küld. Nincs token-szerver és nincs scope; a realm csak megjelenített szöveg, nem URL. A Docker Distribution registry beépített htpasswd backendje ilyen.
  • Bearer token (WWW-Authenticate: Bearer realm="<token-URL>",service="...",scope="..."): a kliens a hitelesítőadataival a challenge-ben megadott realm URL-től rövid életű tokent kér, majd azt Authorization: Bearer <token> fejlécben csatolja. A token-végpont útvonalát nem a szabvány rögzíti, hanem a challenge adja meg; a Distribution registryben ehhez külön token-szerver és az auth.token konfigurációs blokk (realm, service, issuer, rootcertbundle) kell.

Bearer modellben a token scope a jogosultság határát jelöli, nem csupán a user létezését. Például:

repository:lab-team/cpp-service:pull
repository:lab-team/cpp-service:pull,push

Az első csak pullra használható, a második pushra is. A docker login / podman login nem a rövid életű Bearer tokent tárolja, hanem a hitelesítő adatot (a base64-kódolt felhasználó–jelszó párt vagy egy identity tokent); a scope-hoz kötött tokent a kliens műveletenként maga kéri. A tárolás helye Dockernél ~/.docker/config.json, rootless Podmannál alapértelmezetten ${XDG_RUNTIME_DIR}/containers/auth.json (például /run/user/1000/containers/auth.json); a helyet a --authfile kapcsoló vagy a REGISTRY_AUTH_FILE változó felülírja, a ~/.config/containers/auth.json csak olvasott tartalék. A credential helper külső bináris (például docker-credential-secretservice vagy egy vállalati Vault-integráció), amely a hitelesítő adatot a fájl helyett külső tárban tartja (store/get/erase műveletek); ezt a konfigurációban a credHelpers (registrynként) vagy a credsStore (alapértelmezett) kulcs jelöli. A tokencserét nem a helper, hanem a kliens végzi.

A labregistry a Distribution beépített htpasswd backendjét használja, vagyis HTTP Basic hitelesítést (scope és token nélkül). A backend TLS-t követel, és bcrypt-hash-t vár:

# registry lab config.yml kivonat (Basic auth, törlés engedélyezve)
version: 0.1
auth:
  htpasswd:
    realm: "lab-registry"
    path: /auth/htpasswd
storage:
  delete:
    enabled: true
# registry-üzemeltető, a registry hostján (apache2-utils csomag);
# a -B kapcsoló bcrypt-hash-t kér
htpasswd -Bbn labuser '<jelszó>' > /auth/htpasswd

Ezzel a konfigurációval a curl -I https://registry.lab.example:5000/v2/ várt fejléce WWW-Authenticate: Basic realm="lab-registry". A user hozzáadása a htpasswd fájlhoz a registry üzemeltető művelete; a kliens oldalán a podman login a Basic hitelesítő adat tárolását végzi. A login után érdemes ellenőrizni, hogy a mentett credential tényleg a kívánt endpointra vonatkozik: a config fájlban a key a teljes endpoint (host és port), nem csak a registry hostname.

37.3.4 Push/pull/digest verify

A push nem egyszerű fájl feltöltés, hanem OCI Distribution API szekvencia. A kliens először a blobokat tölti fel, majd manifestet ír. A manifest PUT után a registry visszaadja az artifact manifest digestjét; ez az érték az immutable referencia.

A pull során a kliens a manifestet kéri le, megkapja a blob digest listát, letölti a blobokat, és minden réteg tartalmát ellenőrzi a manifestben hivatkozott digest ellen. Ez a digest verify: nem elég a tag azonosítása, a tartalmat a manifestben rögzített sha256 értékekhez kell kötni.

Fontos különbség: a podman push --digestfile <fájl> által kiírt (Docker esetén a docker push záró digest: sha256:... sorában szereplő) digest a manifest digest; a blob réteg digest-ek pedig a manifest layers[].digest mezői. A referenciaintegritás akkor teljes, ha a manifest digestet és a blob digesteket együtt tudjuk reprodukálni. A laborban ezt a skopeo inspect vagy a crane digest parancs mutatja meg.

A deployment protokollban a manifest digestet kell pin-elni, nem a taget. A Kubernetes Pod spec image mezője közvetlenül fogad digestet: image: registry.lab.example:5000/lab-team/cpp-service@sha256:<digest>; ha a tag és a digest együtt szerepel (:1.0.0@sha256:...), a digest a mérvadó, a tag csak olvashatósági címke. Az imagePullPolicy csak azt dönti el, mikor húz a kubelet, digestet nem pinel.

37.3.5 Proxy mirror/cache és air gap

A proxy registry (registry mirror) egy köztes HTTP gyorsítótár. A kliens a mirrorhoz fordul; ha a kért manifest nincs cache-ben, a mirror lekéri az upstream registryből, tárolja, majd továbbítja. A mirror célja a network egress csökkentése és a pull latency javítása, de nem helyettesíti az upstream auth policy-t, mert a mirror csak az artifact-ot cache-ezi.

A Podman és Docker konfigurációjában a mirror deklaratívan megadható. Podmannál a host /etc/containers/registries.conf fájlja TOML formátumú (v2 séma, containers-registries.conf(5)); a mirrort a [[registry.mirror]] tábla definiálja:

# /etc/containers/registries.conf lab kivonat
unqualified-search-registries = ["registry.lab.example:5000"]

[[registry]]
prefix = "docker.io"
location = "docker.io"

[[registry.mirror]]
location = "mirror.lab.example:5000"

Ebben a formában a kliens először a mirrort próbálja, és ha az nem elérhető, az upstreamhez (docker.io) fordul. Ha ezt a visszaesést tiltani kell (air gap), a helyes eszköz a location átírása (location = "mirror.lab.example:5000" mirror-tábla nélkül): ekkor minden docker.io hivatkozás kizárólag a belső registryre megy. A két mód viselkedése tehát eltér, és a konfigurációban külön kell választani.

Az air gap környezetben nincs egress; a mirror nem tud upstreamhez fordulni. Ilyenkor az image-et szállítható köztes formátumba kell írni, majd a céloldali registrybe importálni. A skopeo copy --all megőrzi a digestet; --all nélkül multiarch tagnél csak a helyi platform manifestje kerül át, és az index digest a célon eltér:

# labvm-02, labuser UID 1000; a forrásoldalon (van hozzáférés a registryhez)
skopeo copy --all \
  docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 \
  dir:./lab-airgap
# céloldali, egress nélküli registrybe
skopeo copy --all dir:./lab-airgap \
  docker://registry.airgap.lab:5000/lab-team/cpp-service:1.0.0

A dir: köztes formátum manifest és blob mellett hordozza az integritási adatokat, ezért a digest-verify a céloldalon újra futtatható.

37.3.6 Retention/garbage collection/referenced blob

A registry tárolója content-addressable: a blobokat digestjük azonosítja, a manifestek hivatkoznak rájuk. A tag törlése önmagában nem törli a blobokat, mert más tag vagy manifest tovább hivatkozhat rájuk. A garbage collection (GC) az a folyamat, amely a hivatkozás nélküli blobokat ténylegesen felszabadítja.

A retention policy azt adja meg, hogy mely tag-ek vagy manifestek őrződnek meg, és melyek törölhetők. A megadás mindig a registry product specifikus API-ján vagy konfigurációján keresztül történik; a labregistry Docker Distribution image-ben nincs beépített retention, ezért ott a törlés API-műveletekkel, a GC pedig a registry image parancsával demonstrálható. A retention policy-t tehát ne a kliens docker rmi parancsával keverjük: az a helyi cache-ből töröl, nem a registryből.

A referenced blob fogalma: a blob akkor törölhetetlen, ha legalább egy manifest config.digest vagy layers[].digest mezője rá hivatkozik (indexnél a manifests[].digest a manifestekre mutat; a schemaVersion csak a manifest formátumverziója). Amíg a hivatkozó manifest nem törlődött, a GC-nek meg kell tartania a blobot. Ez a hivatkozási gráf a retention célja: mindig a manifest-törlés az előfeltétel, a blob törlés csak utána következhet.

A labban a retention policy karbantartása így válik ellenőrizhetővé: a tag lista, a manifest digest lekérés, a DELETE művelet és a GC utáni du méretváltozás külön lépésekben jelentkezik.

37.3.7 Rate limit/egress és availability

A registry mint szolgáltatás rate limit alá eshet. Ha a kliens túl sok requests-et ad, a registry 429 Too Many Requests HTTP választ adhat, gyakran Retry-After headerrel. Az anonim pull korlátozott, a bejelentkezett user többet kaphat; a policy a provider által meghatározott.

A registry availability nem azonos a registry endpoint elérhetőségével. A node-on már letöltött image cache, a Kubernetes imagePullPolicy és a replicaset process mind külön réteg. A pod csak akkor lép kép pullra, ha a node nem rendelkezik az image-t, vagy a pull policy ezt előírja. A read-only file system és a registry SLO szempontjából a lekért artifact digest rögzítése csökkenti a mutálódó tagre mutató dependencyt.

A rate limit és egress hibát a registry oldali log, a curl -I válasz és a kliens HTTP-napló együttesen jelzi. A metric a pull kérés száma, a manifest és blob letöltési ideje; a nagy blob pull a throughput méréshez tartozik. Az availability service level indicator (SLI) a sikeres pull időbeli aránya; a rate limit által visszautasított kéréseket a policy explicit módon kizárhatja vagy belevonhatja.

37.3.8 Kidolgozott példa: labregistry push és digest verify

A példa a labvm-02 Ubuntu 24.04 VM-en fut, labuser (UID 1000), rootless Podmannal; a forrás-image a d181-ben buildelt localhost/lab-cpp-service:1.0.0. A registry a lab hálózatban fut (registry-lab nevű konténer, registry:2 image), dokumentációs címpéldában 192.0.2.10 IP-vel, service név registry.lab.example:5000, a fenti Basic auth + storage.delete.enabled: true konfigurációval. A lab DNS /etc/hosts bejegyzésre épül. A TLS tanúsítványban subjectAltName = DNS:registry.lab.example kötelező: a Go-alapú kliensek (Podman, skopeo, Docker) a Common Name-et hostnév-ellenőrzésre nem használják, SAN nélküli tanúsítványra x509: certificate relies on legacy Common Name field hibát adnak. A várt kimenetek szemléltetők, nem futtatott labornaplóból származnak.

1. DNS és TLS ellenőrzés:

# labvm-02, labuser UID 1000
getent hosts registry.lab.example
openssl s_client -connect registry.lab.example:5000 \
  -servername registry.lab.example </dev/null 2>/dev/null | \
  openssl x509 -noout -subject -ext subjectAltName -dates

Várható kimenet (szemléltető):

192.0.2.10  registry.lab.example
subject=CN = registry.lab.example
X509v3 Subject Alternative Name:
    DNS:registry.lab.example
notBefore=...   notAfter=...

2. Login és push:

# labvm-02, labuser UID 1000;
# LAB_REGISTRY_USER/PASSWORD a lab inventory dummy változóiból
podman login registry.lab.example:5000 \
  --username "$LAB_REGISTRY_USER" \
  --password-stdin <<<"$LAB_REGISTRY_PASSWORD"

podman tag localhost/lab-cpp-service:1.0.0 \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

podman push --digestfile /tmp/lab-cpp-service.push.digest \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

A podman push kimenete Copying blob ..., Copying config ..., Writing manifest to image destination sorokkal zárul, digestet alapból nem ír ki; a manifest digestet a --digestfile kapcsoló írja fájlba.

3. Pull és digest verify:

# digest pinning a tag helyett
REG_DIGEST=$(skopeo inspect \
  docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 | \
  jq -r .Digest)

echo "$REG_DIGEST"
test "$REG_DIGEST" = "$(cat /tmp/lab-cpp-service.push.digest)" \
  && echo DIGEST-OK

podman pull "registry.lab.example:5000/lab-team/cpp-service@${REG_DIGEST}"

Ellenőrzési feltétel: a DIGEST-OK sor megjelenik, és a podman images --digests kimenetben a megfelelő image digest megegyezik $REG_DIGEST értékével.

4. Retention demonstráció:

A labregistry Basic hitelesítést használ, ezért a curl közvetlenül -u kapcsolóval hitelesít; Bearer modellben előbb a 401-es challenge realm, service és scope értékéből kellene tokent kérni. A manifest-DELETE csak storage.delete.enabled: true mellett engedélyezett, különben 405 Unsupported a válasz.

AUTH="$LAB_REGISTRY_USER:$LAB_REGISTRY_PASSWORD"
REPO="https://registry.lab.example:5000/v2/lab-team/cpp-service"

# Tag lista lekérés
curl -fsS -u "$AUTH" "$REPO/tags/list"
# Várható: {"name":"lab-team/cpp-service","tags":["1.0.0"]}

# A manifest digest lekérése a DELETE-hez: az Accept fejléc nélkül
# a registry nem garantáltan a pusholt manifest digestjét adja
curl -fsSI -u "$AUTH" \
  -H 'Accept: application/vnd.oci.image.manifest.v1+json' \
  -H 'Accept: application/vnd.docker.distribution.manifest.v2+json' \
  "$REPO/manifests/1.0.0" | grep -i docker-content-digest

# DELETE reference (digesttel); várt státusz: 202 Accepted
curl -sS -o /dev/null -w '%{http_code}\n' -u "$AUTH" -X DELETE \
  "$REPO/manifests/sha256:..."

# GC: csak read-only módba kapcsolt registryn (a configban
# storage.maintenance.readonly.enabled: true, majd újraindítás),
# különben a GC alatt feltöltött blobok törlődhetnek;
# először próbafuttatás, végül a read-only mód visszakapcsolása
podman exec registry-lab /bin/registry garbage-collect --dry-run \
  /etc/docker/registry/config.yml
podman exec registry-lab /bin/registry garbage-collect \
  /etc/docker/registry/config.yml

A GC utáni blob felszabadulást a registry storage kötet méretváltozása mutatja. A tag nélküli manifestek csak a --delete-untagged kapcsolóval törlődnek. A retention policy itt implicit; production registry product esetén a policy megadás vagy a webes API, vagy konfigurációs YAML.

37.3.9 Hibák és ellenpróbák

Hiba: dial tcp: lookup registry.lab.example: no such host.
Hipotézis: a DNS-feloldás nem éri el a lab domain nevet.
Adatgyűjtés: getent hosts registry.lab.example, dig +short registry.lab.example.
Egy változtatás: a lab host /etc/hosts bejegyzését hozzáadni, vagy a lab DNS A rekordját javítani.
Verifikáció: getent hosts ismételt futtatása a várt IP-t adja.

Hiba: certificate signed by unknown authority.
Hipotézis: a kliens nem bízik meg a lab registry CA-ban.
Adatgyűjtés: openssl s_client -showcerts a lánc megtekintéséhez.
Egy változtatás: a lab CA certet a Podman/Docker trust store-ba másolni (Docker: /etc/docker/certs.d/registry.lab.example:5000/ca.crt; Podman: /etc/containers/certs.d/registry.lab.example:5000/ca.crt, rootless felhasználónál ~/.config/containers/certs.d/registry.lab.example:5000/ca.crt). Ha a hiba x509: certificate relies on legacy Common Name field, a tanúsítványból hiányzik a SAN, és újra kell kiállítani.
Verifikáció: podman pull újraindítása, a TLS kapcsolat sikeres.

Hiba: unauthorized: authentication required, bár a login korábban sikeres volt.
Hipotézis: a mentett credential más endpoint-kulcs alatt van (például port nélkül), más auth-fájlban van, mint amit a kliens olvas, vagy (Bearer modellben) a kért scope hiányos.
Adatgyűjtés: podman login --get-login registry.lab.example:5000, echo "$REGISTRY_AUTH_FILE", podman push --log-level=debug a hitelesítési lépések megtekintéséhez.
Egy változtatás: podman logout registry.lab.example:5000, majd új podman login (ez a ténylegesen használt auth-fájl bejegyzését törli és írja újra).
Verifikáció: a push sikeres, a debug logban a hitelesítési fejléc (Basic auth esetén Authorization: Basic, token-szervernél Authorization: Bearer) jelen van.

Hiba: push után a podman images --digests más digestet mutat, mint a manifest inspect.
Hipotézis: a helyi image réteg digest eltér a registry manifestben rögzítettől; vagy a tag mutálódott.
Adatgyűjtés: skopeo inspect a registry manifest digestre, és a helyi podman image inspect RepoDigests mezőjére.
Egy változtatás: a deploy reference-et digestre cserélni, ahogy a példában.
Verifikáció: a podman pull @digest sikeres, a podman rmi a taget törli, de a digest image megmarad.

37.3.10 Feladatok

1. Magyarázó feladat

Írd le, miért nem elegendő a podman push visszatérési értéke a registry artifact integritás bizonyításához, és miért kell a manifest digest mellé a blob digesteket is ellenőrizni. Sorold fel az OCI Distribution API három olyan műveletét, amely a digest-verify szempontjából releváns.

2. Adminisztrációs/konfigurációs feladat

A labregistryben hozz létre egy lab-team repository-t, végpontot, login konfigurációt, és tölts fel egy image-t. Ezután rögzítsd a manifest digestet fájlba, és bizonyítsd a pull utáni azonosságot. A feladat célja a credential helper és digest-pinning használata; a push és pull parancsok mellett a skopeo inspect kimenet is szerepeljen.

3. Diagnosztikai/failure feladat

A build agent nem tud pullolni a registryből, a hiba toomanyrequests. A kezdeti hipotézis az, hogy a registry túlterhelt vagy rate limit lépett életbe. Nyújts diagnosztikai eljárást: milyen HTTP kódot vársz, hogyan olvasod le a Retry-After headert, és milyen registry logot vizsgálnál. Adj meg egy változtatást, amely a pull rate limitet csökkenti anélkül, hogy az auth policy-t megsértené.

37.3.11 Megoldások

1. megoldás

A podman push visszatérési kódja csak a művelet sikerességét jelzi, nem a tartalom integritását. A manifest digest a manifest tartalmát hash-eli; a blob rétegek digestjei a manifestben hivatkoznak. Ha egy blob sértül, a manifest digest változatlan marad, ezért a réteghash ismerete nélkül a sérülést nem észleljük. A három releváns OCI Distribution API művelet: HEAD /v2/<name>/manifests/<reference> a digest lekéréshez, GET /v2/<name>/blobs/<digest> a rétegek letöltéséhez, HEAD /v2/<name>/blobs/<digest> a blob létezésének ellenőrzéséhez. A helyes podman pull @digest mindhárom műveletet elvégzi a kliensben. Postcondition: a pull után a kliens képes a manifest és blob digesteket együttesen ellenőrizni.

2. megoldás

A Distribution registryben a repository nem külön művelettel jön létre: az első push implicit hozza létre. A credential helpert a felhasználói auth-fájl credHelpers kulcsa köti az endpointhoz (containers-auth.json(5)); a helper binárisnak (itt docker-credential-secretservice) telepítve kell lennie a PATH-on.

{
  "credHelpers": {
    "registry.lab.example:5000": "secretservice"
  }
}
# labvm-02, labuser UID 1000; a fenti JSON a
# ${XDG_RUNTIME_DIR}/containers/auth.json fájlban
podman login registry.lab.example:5000 \
  --username "$LAB_REGISTRY_USER" \
  --password-stdin <<<"$LAB_REGISTRY_PASSWORD"
# a jelszó a helperbe kerül, az auth.json-ban nincs "auth" bejegyzés:
grep -c '"auth"' "${XDG_RUNTIME_DIR}/containers/auth.json"
# Várható: 0

podman tag localhost/lab-cpp-service:1.0.0 \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

mkdir -p ~/lab-cpp-service/release
DIGEST_FILE=~/lab-cpp-service/release/cpp-service-1.0.0.digest
podman push --digestfile "$DIGEST_FILE" \
  registry.lab.example:5000/lab-team/cpp-service:1.0.0

skopeo inspect \
  docker://registry.lab.example:5000/lab-team/cpp-service:1.0.0 \
  | jq -r .Digest
# Várható: ugyanaz a sha256:... érték, mint a $DIGEST_FILE tartalma

podman pull \
  "registry.lab.example:5000/lab-team/cpp-service@$(cat "$DIGEST_FILE")"

Indoklás: a skopeo inspect a registryben tárolt artifact-ot kérdezi le, függetlenül a lokális cache-től. A podman pull @digest a manifest digestet pin-eli; a podman images --digests kimenetben az azonosítónak egyeznie kell. A digestfájl a projekt release/ könyvtárában újraindítás után is megmarad. Postcondition: a lokális image digest megegyezik a cpp-service-1.0.0.digest fájl tartalmával, és az auth-fájlban nincs nyílt hitelesítő adat.

3. megoldás

A toomanyrequests hibát a 429 Too Many Requests HTTP válasz jelzi. A Docker Distribution registrynek (a saját labregistrynek) nincs beépített rate limitere, ezért a 429 tipikusan az upstream registrytől (például Docker Hubtól) jön. Az első lépés tehát annak megállapítása, melyik host adta a választ: a build agent pull-logja ezt mutatja.

# build agent; a 429-et adó host és a kért reference kiderítése
podman pull --log-level=debug docker.io/library/debian:bookworm-slim \
  2>&1 | grep -i -E 'toomanyrequests|429|registry-1\.docker\.io'

# az upstream kvótafejlécei a manifest-kérésen jelennek meg (nem a /v2/-n);
# $TOKEN: az upstream challenge alapján kért pull token
curl -sI -H "Authorization: Bearer $TOKEN" \
  https://registry-1.docker.io/v2/library/debian/manifests/bookworm-slim \
  | grep -i -E 'ratelimit|retry-after'

A várt fejlécek (ratelimit-limit, ratelimit-remaining, esetleg retry-after) konkrét értéke a provider aktuális policyjától függ, ezért itt nem adunk meg számot. Az egy változtatás: egy pull-through cache (a Distribution registry proxy: blokkja: remoteurl: https://registry-1.docker.io, valamint username/password a mirror saját upstream-fiókjához), és a build agent /etc/containers/registries.conf fájlja [[registry.mirror]] táblával erre mutat. Az ismételt kérések így a cache-ből szolgálódnak ki; az upstream felé a mirror a saját, konfigurált fiókjával és annak kvótájával hitelesít, nem továbbítja a kliens hitelesítő adatát, ezért ezt a fiókot az upstream auth policy szerint kell kezelni. Postcondition: a build agent ismételt pull kérései a mirrorból teljesülnek, az upstream felé menő kérések száma csökken, a podman pull sikeres.

37.3.12 Rövid összefoglaló

A registry endpoint elérhetősége és hitelesítése a DNS, TLS, Auth és Manifest rétegek együttes működésétől függ. A push/pull mindig digest-verify mellett történik: a tag mutálható, a manifest digest immutable referencia. A registry Basic vagy Bearer hitelesítést használ; Bearer modellben a token scope határozza meg a pull/push jogot, a credential helper pedig a hitelesítő adatot tárolja külső tárban. A mirror cache csökkenti az egress terhelést, de az air gap eszköz nélkül nem érhető el; ilyenkor skopeo copy köztes dir: formátummal szállít. A retention policy a tag/manifest törlés és a hivatkozatlan blob GC sorrendjét rögzíti. A rate limit és availability külön service réteg.

  • Digest: az artifact tartalomra számított immutable hash, hivatkozási azonosító.
  • Credential helper: a registry hitelesítő adatát külső tárban tároló és visszaadó (store/get/erase) klienskomponens; a tokencserét a kliens végzi.
  • Referenced blob: olyan blob, amelyet legalább egy manifest hivatkozik, ezért a GC nem törölheti.
