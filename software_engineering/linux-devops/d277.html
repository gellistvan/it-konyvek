56.2 CI image, Helm/Kustomize és GitOps delivery

A d240 pipeline outputja egy natív C++ release artifact és egy container image, de a deployment szempontjából a tag nem identitás. A d277 célja, hogy a konténerartifactot változatlan digesttel vigye végig a környezeteken, és minden lépéshez mérhető bizonyítékot kapcsoljon. A fejlesztői szempont ismerős: ha egy release buildet minden környezetre újrafordítanánk, az olyan, mintha egy megosztott könyvtárnak minden fogyasztónál más-más build-id-je lenne; a diagnosztika, a visszafejtés és a rollback is megszűnik reprodukálhatónak lenni.

56.2.1 Definíció és működés

A delivery lánc itt a natív build/bináris artifact előállításától a futó podig terjed. A cél egy olyan bizonyítéklánc, amely megválaszolja: milyen forrásból, milyen bemenetekkel, milyen tesztekkel, melyik image digestből és milyen environment konfigurációval lett a clusterben ténylegesen futó processz.

A kulcsfogalmak:

  • Immutable artifact promotion: az artifact egy tartalomalapú azonosítóval — itt container image digest, a natív binárisnál a tartalom SHA-256 és a build-id — utazik a környezetek között. A tag csak emberi név, a digest a hivatkozás.
  • GitOps reconcile: a cluster desired state-ét egy Git repository tartalmazza, a GitOps agent pedig folyamatosan kiegyenlíti az observed state-et a desired state-hez. A kézi kubectl apply nem része a promotionnek.
  • Release evidence: a kiadást leíró, verziózott, lehetőleg aláírt bizonyítékcsomag; tartalmazza a source revisiont, pipeline futást, binary hasheket, SBOM-ot, attestationt, rendered manifest digestet, policy validation eredményt és rollout eredményt.
  • Data-compatible rollback: olyan visszaállítás, ahol a régebbi bináris a jelenlegi adat- és konfigurációformátumot még kezelni tudja. A config migration ezért expand/contract mintát igényel: az új kód először olvassa a régi formátumot, a régi kódot addig nem cseréljük le, amíg minden új fogyasztó stabil nem lett.

A lánc lépései:

  1. Native test/build/image pipeline: a forrásrevisionből egyetlen Linux amd64 release binárist készítünk és tesztelünk; a sanitizer vizsgálat egy külön, csak tesztre szolgáló buildben fut — a sanitizeres bináris nem release artifact. A binárist tömörített archívumba csomagoljuk, és SHA-256-tal azonosítjuk. A build rögzíti a build-id-t, a libc és a linker környezetet, mert egy natív C++ service ABI-függőségei a konténer runtime image-től is függenek.
  2. SBOM, digest, attestation és registry: a konténer build ugyanezt a binárist helyezi egy minimal runtime rétegbe. A build nem második fordítást végez, hanem artifactot telepít. A registry-be push során a rendszer SBOM-ot (software bill of materials) és provenance attestationt készít. A promotion hivatkozás mindig @sha256:... formátumú.
  3. Rendered manifest/policy validation: a Helm chart vagy Kustomize overlay a környezeti values-szal rendered manifestet állít elő. Ezt API séma-szinten (kubeconform) és policy-szinten (conftest, OPA/Gatekeeper) ellenőrizzük, még a GitOps sync előtt.
  4. GitOps reconcile és environment promotion: a promotion nem közvetlen cluster művelet, hanem Git commit a megfelelő environment path-on. A staging sikeres kiértékelése után ugyanaz az image digest jelenik meg a prod desired state-ben.
  5. Probe, rollout, PDB, canary: a Deployment rolling update során readiness/liveness probe-okkal, PodDisruptionBudgettel és opcionálisan canary lépésekkel biztosítjuk, hogy a forgalom csak egészséges podokra kerüljön. A canary részletes gyakorlatát a Progressive delivery és recovery labor tartalmazza.
  6. Release evidence és config migration: a kiadás csak akkor nevezhető késznek, ha a release evidence fájl létrejött, és a configVersion váltás kompatibilitási feltételeit ellenőriztük.

Az alábbi ábra a hat lépést a keletkező azonosítókkal és az ellenőrzési pontokkal köti össze: a digest a CI-ben keletkezik, és változatlanul halad stagingből prodba, csak a környezeti értékek térnek el.

56.2.2 Kidolgozott példa

A példa a d276 kanonikus azonosítóit használja: cluster lab-k8s, kubeconfig context lab-k8s-admin, a staging/prod promotionhoz két namespace (lab-app-staging, lab-app-prod; mindkettőre a d276 quota-, NetworkPolicy- és RBAC-sablonja vonatkozik), Argo CD app lab-app-staging és lab-app-prod, GitOps repository lab-platform. A labtarget gitops-lab-control (UID 1000). A service neve payment-srv; a product repository payment-srv tartalmazza a C++ forrást és a pipeline-t. Az image registry ghcr.io/lab-org/payment-srv. A digesteket a pipeline és a registry adja; a fejezetben a sha256:1111… dummy digest csak a kifejezetten elméleti példákban szerepel.

A natív CI pipeline releváns része (nem futtatott minta). A <…> helyőrzőket a futtatás előtt a release-matrix szerint ki kell tölteni: a context.md supply-chain szabálya szerint minden uses: teljes, 40 hexás commit SHA-val pinelt; kitöltetlenül a workflow nem indul el („Unable to resolve action”). Ellenőrzés: grep -nE 'uses: [^@]+@[0-9a-f]{40}' .github/workflows/release.yml.

name: release-payment-srv
on:
  push:
    tags: ["release/payment-srv/*"]
permissions:
  contents: read
  id-token: write    # keyless cosign aláírás
  packages: write    # push a ghcr.io-ba
jobs:
  build-test:
    runs-on: ubuntu-24.04 # lab-fixture: runner verzió rögzítendő
    steps:
      - uses: actions/checkout@<40-hexás-commit-SHA> # vX.Y.Z
      - name: cache dependency fixture
        uses: actions/cache@<40-hexás-commit-SHA> # vX.Y.Z
        with:
          path: .cache
          key: payment-srv-fixture-${{ hashFiles('fixtures/**') }}
      - name: sanitizer build and test (csak teszt, nem release artifact)
        run: |
          cmake -S . -B build-asan \
            -DCMAKE_BUILD_TYPE=RelWithDebInfo \
            -DPAYMENT_PLATFORM=linux-amd64 \
            -DPAYMENT_ENABLE_SANITIZERS=ON
          cmake --build build-asan --target payment-srv
          ctest --test-dir build-asan --output-on-failure
      - name: release build and test
        run: |
          cmake -S . -B build-release \
            -DCMAKE_BUILD_TYPE=RelWithDebInfo \
            -DPAYMENT_PLATFORM=linux-amd64 \
            -DPAYMENT_ENABLE_SANITIZERS=OFF
          cmake --build build-release --target payment-srv
          ctest --test-dir build-release --output-on-failure
      - name: package release binary
        run: |
          mkdir -p dist
          tar --zstd -cf dist/payment-srv-linux-amd64.tar.zst \
            -C build-release/bin payment-srv
          cd dist
          sha256sum payment-srv-linux-amd64.tar.zst \
            > payment-srv-linux-amd64.tar.zst.sha256
      - name: store binary artifact
        uses: actions/upload-artifact@<40-hexás-commit-SHA> # vX.Y.Z
        with:
          name: payment-srv-linux-amd64
          path: |
            dist/payment-srv-linux-amd64.tar.zst
            dist/payment-srv-linux-amd64.tar.zst.sha256
          retention-days: 14
  image:
    needs: build-test
    runs-on: ubuntu-24.04
    env:
      IMAGE: ghcr.io/lab-org/payment-srv
    steps:
      - uses: actions/checkout@<40-hexás-commit-SHA> # vX.Y.Z
      - name: fetch the tested release binary
        uses: actions/download-artifact@<40-hexás-commit-SHA> # vX.Y.Z
        with:
          name: payment-srv-linux-amd64
          path: dist/
      - name: verify and unpack binary (nincs második fordítás)
        run: |
          (cd dist && sha256sum -c payment-srv-linux-amd64.tar.zst.sha256)
          mkdir -p dist/rootfs
          tar --zstd -xf dist/payment-srv-linux-amd64.tar.zst -C dist/rootfs
      - uses: docker/setup-buildx-action@<40-hexás-commit-SHA> # vX.Y.Z
      - uses: docker/login-action@<40-hexás-commit-SHA> # vX.Y.Z
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: build and push image
        run: |
          docker buildx build \
            --platform linux/amd64 \
            --sbom=true \
            --provenance=mode=min \
            -f Dockerfile.runtime \
            -t "${IMAGE}:v0.4.2" \
            --push .
      - name: resolve digest
        run: |
          digest="$(docker buildx imagetools inspect "${IMAGE}:v0.4.2" \
            --format '{{ .Manifest.Digest }}')"
          {
            echo "IMAGE_DIGEST=${digest}"
            echo "IMAGE_REF=${IMAGE}@${digest}"
          } >> "${GITHUB_ENV}"
      - name: sign image
        run: |
          cosign sign --yes "${IMAGE}@${IMAGE_DIGEST}"

A docker/setup-buildx-action egy docker-container driveres buildert hoz létre; az --sbom/--provenance attestationt a klasszikus docker driver nem támogatja. A provenance attestationt a --provenance kapcsoló már csatolja az image-hez, ezért külön cosign attest lépés nem kell (ha mégis kell, a predicate fájlt egy korábbi lépésnek kellene előállítania). A permissions blokk megadásakor minden fel nem sorolt GITHUB_TOKEN-jog none, ezért kell a packages: write.

A runtime image nem fordít, csak a CI által ellenőrzött binárist telepíti:

# Dockerfile.runtime
# a runtime image glibc/libstdc++ verziója a build környezettel kompatibilis
FROM ubuntu:24.04@sha256:<pinned-runtime-digest>
COPY dist/rootfs/payment-srv /opt/payment-srv/bin/payment-srv
USER 65532:65532
ENTRYPOINT ["/opt/payment-srv/bin/payment-srv"]

A Helm values a staging környezethez:

# config/staging/values.yaml
image:
  repository: ghcr.io/lab-org/payment-srv
  digest: ""   # a promotion lépés írja be: sha256:<64 hexa jegy>
  pullPolicy: IfNotPresent
replicaCount: 3
configVersion: "2"
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 512Mi

  livenessPath: /livez     # a processz él és válaszol

A digest mezőt nem kézzel írjuk: a promotion lépés a registryből visszaolvasott értéket írja be (sha256: + 64 hexa jegy). A readiness és a liveness szándékosan külön végpont: ha a konfiguráció hibás, a /readyz 503-at ad és a pod kikerül a Service mögül, a /livez viszont 200 marad, így a kubelet nem indítja újra a konténert — a pod Running, de nem Ready. Azonos végpontnál a liveness is bukna (15 s × 5 = 75 s után), és a pod restart-ciklusba kerülne.

Várható kimenet: a helm lint nem jelez hibát; a grep -c 1 találatot ad; a kubeconform összegzésben valid állapotot ír; a conftest kilépési kódja nulla, és a policy tesztek PASS eredményt adnak. Ha a --namespace payment.srv kimarad, a conftest az alapértelmezett main csomagot keresi, 0 szabályt értékel ki — ez nem PASS. A configVersion típusát a Helm alapból nem ellenőrzi (a template idézőjelbe teszi, így 2 is "2"-ként renderelődik); a típushibát a chart values.schema.json-ja fogja meg ("configVersion": {"type": "string", "enum": ["1", "2"]}), amelyet a helm lint/helm template kiértékel; a policy a renderelt ConfigMap verzióját ellenőrzi.

A release evidence fájlt nem kézzel töltjük ki: a géppel előállított mezőket egy generátor gyűjti a CI-ből, a registryből és az Argo CD-ből, és egy release gate elutasítja, ha bármely mező helyőrző maradt. A kézzel kitöltendő adat (jóváhagyó, change ticket) külön manual objektumba kerül. A generátor a CI release jobjában fut (a keyless aláíráshoz a GitHub OIDC token kell); a bemeneti változókat a korábbi lépések exportálják:

# target: CI release job (GitHub Actions), a korábbi lépések kimeneteivel
ev=build/release-evidence-staging-v0.4.2.json
run_url="$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID"
bin_hex="$(cut -d' ' -f1 dist/payment-srv-linux-amd64.tar.zst.sha256)"
rendered_hex="$(sha256sum build/payment-srv-staging-rendered.yaml \
  | cut -d' ' -f1)"
jq -n \
  --arg rev "$GITHUB_SHA" \
  --arg run "$run_url" \
  --arg bin_sha "sha256:$bin_hex" \
  --arg build_id "$BUILD_ID" \
  --arg digest "$IMAGE_DIGEST" \
  --arg rendered "sha256:$rendered_hex" \
  --arg rollout "$ROLLOUT_STATUS" \
  --arg approver "$APPROVER" \
  '{service: "payment-srv", environment: "staging",
    generated: {git_revision: $rev, ci_run_url: $run,
      binary_artifact: {name: "payment-srv-linux-amd64.tar.zst",
        sha256: $bin_sha, build_id: $build_id, config_version: "2"},
      image: {repository: "ghcr.io/lab-org/payment-srv", digest: $digest},
      rendered_manifest_digest: $rendered,
      policy_validation: {kubeconform: "valid", conftest: "PASS"},
      rollout_status: $rollout},
    manual: {approver: $approver}}' > "$ev"

# release gate: nincs helyőrző, minden digest valódi sha256 alakú
if grep -nE '<[^>]*>|PLACEHOLDER|lab-[a-z-]*-digest' "$ev"; then
  echo "HIBA: helyőrző az evidence-ben" >&2
  exit 1
fi
jq -e '[.generated.binary_artifact.sha256, .generated.image.digest,
        .generated.rendered_manifest_digest]
       | all(test("^sha256:[0-9a-f]{64}$"))' "$ev"

# aláírás és ellenőrzés: helyi fájlhoz sign-blob/verify-blob kell
cosign sign-blob --yes --bundle "$ev.sigstore.json" "$ev"
wf="https://github.com/lab-org/payment-srv/.github/workflows"
cosign verify-blob --bundle "$ev.sigstore.json" \
  --certificate-identity \
  "$wf/release-payment-srv.yml@refs/tags/release/payment-srv/v0.4.2" \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  "$ev"

A cosign sign/cosign verify OCI-registryben lévő image-hivatkozást vár; helyi fájlra a sign-blob/verify-blob való. Keyless ellenőrzésnél a --certificate-identity a tanúsítvány SAN-értéke (GitHub Actionsnél a workflow-ref URL), mellette a --certificate-oidc-issuer kötelező. A gate-et unit tesztként is érdemes rögzíteni: egy helyőrzős fixture-nek buknia, egy kitöltött evidence-nek át kell mennie.

A configVersion: "2" migration feltétele: a payment-srv:v0.4.2 bináris mind v1, mind v2 config formátumot olvas. Amíg stagingben és prodban is csak v2 pod fut, a ConfigMap v2-t ír. A rollbackhez a v1 binárisnak is ismernie kell a v2 configot, vagy a rollback commitnak a v1 values-szal kell visszaállnia.

A prod promotion ugyanezt a digestet használja:

A környezetek közötti különbség csak a config/ alatti environment-specific values; a chart és a digest azonos. A rendered manifestet a prod promotion előtt is le kell generálni, mert a replicaCount vagy a nodeSelector változhat.

A rollout biztonsági paraméterei két különböző mechanizmushoz tartoznak: a rolling update alatt a Deployment controller a maxUnavailable: 0/maxSurge: 1 szerint cserél podot (a PDB-t nem veszi figyelembe), a PDB minAvailable: 2 pedig a drain/eviction (karbantartás) alatt garantál legalább két elérhető podot. A readiness probe az új podot csak akkor engedi a Service mögé, ha a /readyz válaszol. Ha valamelyik pod lassan indul, a minReadySeconds-t a platformterv szerint érdemes beállítani.

Canary esetben a staging és prod között a d245 progressive delivery lépései használhatók: a digest először egy kis súlyú canary Deploymentbe vagy Argo Rollouts lépésbe kerül, majd SLO- és telemetria jelekkel növeljük a forgalmat. Itt a GitOps commit ugyanaz, de a platform chart a rollout stratégia mezőt is environment values-szal vezérli.

56.2.3 Tipikus hibák és ellenpróbák

A tag promotálása digest helyett. Tünet: a klusterben lévő pod image mezője payment-srv:v0.4.2, és a git log szerint a promotion sikeres, mégis más kód fut. Hipotézis: a registryben a tagot időközben újratolták. Adatgyűjtés: docker buildx imagetools inspect a tag digestjére, és kubectl get pod -l app=payment-srv -o jsonpath='{.items[0].status.containerStatuses[0].imageID}' összehasonlítás. Ellenpróba: a desired state-ben tag szerepel, nem @sha256. Javítás: a values image.digest mezőre áll át, a taget csak CI kényelemként használjuk. Verifikáció: a pod imageID digestje megegyezik a release evidence image digestjével.

A rendered manifest nincs a GitOps repositoryban. Tünet: a CI-ben a helm template más eredményt ad, mint amit az Argo CD szinkronizál, mert a clusterben egy korábbi kubectl apply maradt. Hipotézis: a GitOps source nem a teljes desired state, hanem részleges overlay. Adatgyűjtés: argocd app diff lab-app-staging és kubectl get all -n lab-app-staging -o yaml összehasonlítása. Ellenpróba: a diff a payment-srv Deployment image digest mezőben eltér. Javítás: minden módosítást a Git repository path-on kell commitolni, és az app sync policy automated + self-heal. Verifikáció: az argocd app diff üres, a kubectl apply-t nem használjuk.

A config migration egyirányú. Tünet: a v2 release rollout közben a régebbi pod ConfigMap parse hibát logol, a readiness probe nem válaszol. Hipotézis: a v2 config mezőneveket átneveztük, de a régi bináris nem ismeri őket. Adatgyűjtés: kubectl logs -l app=payment-srv --tail=50, a ConfigMap kubectl get cm payment-srv-config -n lab-app-staging -o yaml. Ellenpróba: a configVersion mező 2, de a deployment podjai között még v1 image fut. Javítás: először a v2 binárisnak kell tudnia olvasni a v1 configot; a rollout után átállunk v2 configra; rollback esetén a v1 binárisnak is olvasnia kell v2-t, vagy a config értéket a revert commit is visszaállítja. Az adatbázis séma esetén hasonló expand/contract migráció kell: az új séma először write-compatible, destruktív oszloptörlés csak a stabil lefutás után.

A surge pod nem ütemezhető. Tünet: kubectl rollout status hosszan fut, a kubectl get pods egy pod Pending. Hipotézis: a maxSurge: 1 többlet podját a cluster nem tudja ütemezni, mert az adott nodeSelector vagy resource request túl magas. A maxUnavailable: 0 miatt a régi pod csak az új pod Ready állapota után áll le, ezért a rollout megakad, és a progressDeadlineSeconds (alapértelmezés 600 s) után a Deployment ProgressDeadlineExceeded állapotot jelez. Adatgyűjtés: kubectl -n lab-app-staging describe pod <pending-pod> (Events: Insufficient cpu), kubectl get events -n lab-app-staging --sort-by=.metadata.creationTimestamp | tail -20, kubectl get rs -n lab-app-staging, kubectl describe nodes | grep -A8 'Allocated resources'. Ellenpróba: a PDB a rolling update-re nem hat, csak a drain/eviction műveletekre; a hiba ütemezési kapacitás, nem PDB-sértés. Javítás: a deployment resource requestjét a platform capacity budgethez igazítjuk, vagy a promotion előtt a kubectl top nodes és az allocatable értékeket ellenőrizzük. Verifikáció: a rollout successfully rolled out, a kubectl get rs szerint az új ReplicaSet 3/3.

A hibakeresés során egy változtatást érdemes egyszerre végezni: először a digestet rögzítjük, utána a configVersion feltételt, végül a resource requestet. A GitOps diff és a release evidence minden lépésben megmondja, mi változott.

56.2.4 Feladatok

  1. Magyarázó feladat. Adott ez a deployment hivatkozás: ghcr.io/lab-org/payment-srv:v0.4.2. Magyarázza el, miért nem elegendő ez a promotion azonosító, és milyen bizonyíték hiányzik ahhoz, hogy a forrástól a futó podig egyértelmű legyen a lánc. Listázza a hiányzó mezőket, és adjon meg egy helyes image hivatkozást a dummy digesttel.

  2. Adminisztrációs feladat. A lab-platform repositoryban a staging values jelenleg image.digest: sha256:old-digest. Készítse elő a v0.4.2 promotion commitot a registryből visszaolvasott új digesttel. Renderelje le a manifestet, futtassa a kubeconform és conftest validálást, majd Argo CD sync parancsot adjon a staging alkalmazásra. A kimenetben mutassa be a várható image mezőt és a rollout státuszt.

  3. Diagnosztikai/failure feladat. A staging rollout után a podok Running állapotúak, de Ready nem lesznek: a readiness /readyz 503-at ad, a liveness /livez 200-at, ezért a kubelet nem indítja újra őket. A naplóban Config parse error: unknown key settings.retry.milliseconds látszik. A rollout előtti pod még v1 image volt, a ConfigMap v2-t ír. Határozza meg a kiváltó okot, dolgozzon ki adatgyűjtési lépéseket, és hajtsa végre a data-compatible rollbacket a Git rebase/revert és Argo CD sync segítségével.

56.2.5 Megoldások

  1. A tag nem tartalomazonosító; ugyanahhoz a taghez tartozó manifestet bárki újratolhat. A promotion csak akkor reprodukálható, ha a desired state @sha256:1111... digestet használ. A hiányzó bizonyítékok: binary artifact SHA-256, build-id, SBOM digest, attestation URL, rendered manifest digest, policy validation eredmény, rollout status. Helyes hivatkozás: ghcr.io/lab-org/payment-srv@sha256:1111111111111111111111111111111111111111111111111111111111111111. Postcondition: a pod imageID digestje egyezik a release evidence digestjével, és a tag nem jelenik meg a desired state-ben.

  2. A megoldás lépései (a kidolgozott példával azonos kapcsolókkal):

cd lab-platform
git switch -c promote/payment-srv/staging-v0.4.2
new_digest="$(docker buildx imagetools inspect \
  ghcr.io/lab-org/payment-srv:v0.4.2 --format '{{ .Manifest.Digest }}')"
[[ "$new_digest" =~ ^sha256:[0-9a-f]{64}$ ]] || exit 1
export new_digest
yq -i '.image.digest = strenv(new_digest)' config/staging/values.yaml
helm lint ./charts/payment-srv --values ./config/staging/values.yaml
mkdir -p build
helm template payment-srv ./charts/payment-srv \
  --namespace lab-app-staging \
  --values ./config/staging/values.yaml \
  > build/payment-srv-staging-rendered.yaml
kubeconform -strict -summary -kubernetes-version 1.31.0 \
  build/payment-srv-staging-rendered.yaml
conftest test --policy ./policy/rendered --namespace payment.srv \
  build/payment-srv-staging-rendered.yaml
git add config/staging/values.yaml build/payment-srv-staging-rendered.yaml
git commit -s -m "promote payment-srv v0.4.2 digest to staging"
git push -u origin promote/payment-srv/staging-v0.4.2
gh pr create --base main --fill
gh pr merge --squash --delete-branch   # a kötelező review után
git switch main
git pull --ff-only origin main
argocd app sync lab-app-staging --revision "$(git rev-parse origin/main)"
kubectl --context lab-k8s-admin -n lab-app-staging \
  get deployment payment-srv \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'

Várt kimenet: a kubeconform valid, a conftest PASS (ha a conftest 0 tesztet futtat, az nem PASS: a policy namespace hiányzik), az image mező ghcr.io/lab-org/payment-srv@<new_digest>, a rollout successfully rolled out. Postcondition: a staging desired state-ben a digest a release evidence-szel egyezik, az Argo CD sync revision a main HEAD, és az app Synced.

  1. A kiváltó ok: a rollout egyszerre váltotta a configverziót és az image verziót, de a régi bináris nem olvassa a v2 configot. A helyes eljárás adatgyűjtés:
ns=(--context lab-k8s-admin -n lab-app-staging)
kubectl "${ns[@]}" get pods -l app=payment-srv -o wide
kubectl "${ns[@]}" get cm payment-srv-config -o yaml
kubectl "${ns[@]}" logs -l app=payment-srv --tail=30
kubectl "${ns[@]}" describe deployment payment-srv

Az ellenőrzés megmutatja, hogy a configVersion 2, de a readiness probe hibát jelez. A rollback a promotion commit tényleges SHA-jának revertje, PR-ral, ugyanúgy, mint a promotion:

cd lab-platform
git switch main
# divergens lokális history esetén a --ff-only hibával megáll: ekkor
# a lokális változtatásokat előbb tisztázni kell, nem felülírni
git pull --ff-only origin main
promote_sha="$(git log origin/main -1 --format=%H \
  --grep='promote payment-srv v0.4.2 digest to staging')"
test -n "$promote_sha" || { echo "nincs promotion commit" >&2; exit 1; }
git show --stat "$promote_sha"
git switch -c rollback/payment-srv/staging-v0.4.2
git revert --no-edit "$promote_sha"
git push -u origin rollback/payment-srv/staging-v0.4.2
gh pr create --base main --fill
gh pr merge --squash --delete-branch   # a kötelező review után
git switch main
git pull --ff-only origin main
argocd app sync lab-app-staging --revision "$(git rev-parse origin/main)"
ns=(--context lab-k8s-admin -n lab-app-staging)
kubectl "${ns[@]}" rollout status deployment/payment-srv
kubectl "${ns[@]}" get deployment payment-srv \
  -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'
kubectl "${ns[@]}" get cm payment-srv-config \
  -o jsonpath='{.metadata.labels.config-version}{"\n"}'

A rollback akkor elfogadható, ha a v1 bináris a konfigurációt v1 formátumban kapja (a revert a values configVersion mezőjét is visszaállítja), és az adatbázisban nem történt olyan séma módosítás, amelyet a v1 már nem tud olvasni. Postcondition: a staging deployment image digestje visszaáll a korábbi release digestre, a podok Ready állapotúak, a ConfigMap configVersion 1, és az Argo CD app Synced.

56.2.6 Rövid összefoglaló

A d277 a CI artifacttól a cluster desired state-ig vezethető immutable láncot tanítja. A natív C++ build egyetlen binary artifactot állít elő; a container build azt telepíti, SBOM-mal, digestsztel és attestationnel látja el. A GitOps promotion ugyanazt a digestet mozgatja environmentek között, a környezeti különbséget a rendered manifest values adja. A rollout biztonságát probe-ok, PDB és rolling/canary stratégia adja; a rollback csak akkor érvényes, ha a config és data migration visszafelé is kompatibilis. Továbbhasznált definíciók: immutable artifact promotion, GitOps reconcile, data-compatible rollback.

56.2.7 Források és ellenőrzési hiányok

Az alábbiak ellenőrizendő kiindulópontok, nem ebben a munkamenetben olvasott bizonyítékok. Állításonként, a hivatkozott verzióval (Kubernetes v1.31 profil; a többi eszköz verzióját a lab release-matrixa rögzíti):

  • GitHub Actions: Security hardening – action-pinning teljes commit SHA-val; Automatic token authentication – permissions, packages: write.
  • Docker Build: Attestations – --sbom, --provenance, a docker-container driver követelménye; docker/setup-buildx-action, docker/login-action.
  • Sigstore cosign: Signing blobs – sign-blob/verify-blob, --bundle; Verifying signatures – --certificate-identity, --certificate-oidc-issuer.
  • Helm: Charts – Schema files – values.schema.json; helm template.
  • kubeconform – -kubernetes-version, -schema-location, -strict; Conftest: Options – --namespace, az alapértelmezett main csomag.
  • Kubernetes: Deployments – maxSurge/maxUnavailable, progressDeadlineSeconds; Disruptions – a PDB hatóköre; Liveness, Readiness and Startup Probes.
  • Argo CD Documentation – argocd app sync --revision, app get, app diff, Automated Sync Policy.
  • GitHub CLI manual – gh pr create, gh pr checks, gh pr merge.
  • OpenGitOps, OpenTelemetry Documentation, SRE Books.

Ellenőrzési státusz: a workflow, a promotion/rollback és a release gate sikeres és hibás ága (helyőrzős evidence, 0 conftest-szabály, nem ütemezhető surge pod) laborban ellenőrizendő; dátumozott futtatási napló (eszközverziókkal és parancskimenettel) még nem készült.

Ellenőrzési hiányok: a konkrét actions/* verziók, docker buildx SBOM/provenance flag támogatás, cosign aláírás parancssori formátuma, kubeconform és conftest policy sémák, Argo CD sync paraméterek, valamint a Kubernetes RollingUpdate és PDB pontos API verziója a lab inventoryban rögzítendő.
