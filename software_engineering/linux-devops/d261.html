53.1 Database kapcsolatok, resource és health

53.1.1 Motiváció és működtetési feladat

Egy szenior C++ fejlesztő számára az adatbázis gyakran „fekete doboz”: a szerveroldali kód kiad egy SQL lekérdezést, majd valamilyen későbbi időpontban választ kap. A Linux/DevOps rendszerszemléletben azonban a PostgreSQL-szolgáltatás nem egyetlen komponens, hanem több rétegen átívelő adatút, amelyben a kapcsolatfelvétel, a tranzakció, a lock, a memória és a storage mind saját latency- és erőforrásköltséggel rendelkezik. Amikor egy C++ alkalmazás p95 latency romlását tapasztalja, a hiba lehet a TCP-kapcsolat felépítésében, a connection pool kimerülésében, egy nem indexelt lekérdezésben, lock-várakozásban vagy éppen a WAL flush lassúságában. A d261 alfejezet célja, hogy ezeket a rétegeket egy referencia PostgreSQL-szolgáltatáson működtetési szempontból láttassa: ne csak a DB belső állapotát, hanem az OS/network/storage jeleket is együtt kezeljük.

Előfeltételek: izolált labVM (például Ubuntu Server 24.04 LTS), telepített PostgreSQL (a pontos verziót az apt release rögzíti; itt illusztrációként postgresql és postgresql-contrib csomagok), root vagy sudo jogosultság a rendszerbeállításokhoz, valamint a d047 alfejezetben tárgyalt fsync/dirty page és a d223 storage fogalmai. A példákban a labhost neve labhost01, a lab database lab_db, az alkalmazás role lab_app.

53.1.2 Definíciók és scope

  • Database latency alatt a kliens oldaláról mért teljes válaszidőt értjük, amely felbontható: connection establishment + query planning/execution + lock wait + storage I/O + hálózati oda-vissza idő. E rétegek mindegyike külön mérhető, és eltérő diagnosztikai paranccsal figyelhető.
  • Connection pool/limit egy olyan erőforrásgazdálkodási korlát, amely meghatározza, hány egyidejű háttérfolyamatot (backend) indít a PostgreSQL, és ebből mennyit használhat egy alkalmazás. A pool célja a process-indítási költség elkerülése és a DB memória védelme.
  • Working set a gyakran elért adat- és indexoldalak halmaza. Ha ez nem fér a shared_buffers és az OS page cache együttes méretébe, a lekérdezések fizikai blokkiolvasásra kényszerülnek, ami nagyságrendi latency növekedést okoz.
  • WAL (Write-Ahead Log) a tranzakciók redo rekordjainak folyamatos naplója; a commit tartóssága a WAL fsync-jén múlik, nem közvetlenül a data file kiírásán.

A Database latency rétegeinek időbeli helyét az alábbi ábra mutatja: a kliens által mért végponti időből csak a PQexec hívás ideje tartalmazza a szerveroldali végrehajtást, a lock-várakozást és az I/O-t.

A scope itt egyetlen PostgreSQL instance működtetése: kapcsolatkezelés, erőforráskorlát, tranzakciós lockok, memória, WAL, hitelesítés/TLS és telemetria. Nem tárgyaljuk a replikációt, failovert vagy backupot (későbbi alfejezetekben), és nem tanítunk SQL-t vagy C++ szintaxist.

53.1.3 Rétegek és operatív következmények

53.1.3.1 Kapcsolat, pool, limit és timeout

A PostgreSQL process-modellt használ: a postmaster főfolyamat minden klienskapcsolathoz egy-egy backend process-t indít (fork). Ezért minden új kapcsolat drága: memória (kb. 5–10 MiB privát terület kapcsolatonként), process-létrehozás, authentikáció és TCP handshake. A superuser_reserved_connections néhány külön slotot tart fenn adminisztrációnak, ezért egy alkalmazáspool kimerülése nem zárja ki a diagnosztikát. Egy nem szuperuser kliens ezért már a max_connections - superuser_reserved_connections határon hibát kap: FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute (PostgreSQL 16 szövege; a pontos üzenetet a telepített verzió logjából kell rögzíteni). A FATAL: sorry, too many clients already akkor jelenik meg, ha a fenntartott slotok is elfogytak, például szuperuser kapcsolatoknál.

Működtetési gyakorlat: alkalmazás és DB közé PgBouncer (transaction mode connection pooler) ajánlott, mert így az alkalmazás sok kliensét kevés valódi PostgreSQL backend szolgálja ki, a process-per-connection modell hátrányai nélkül. Korlát: transaction módban a kliens tranzakciónként más szerver-backendet kaphat, ezért a session-szintű állapot (SET, session advisory lock, LISTEN, temp table, prepared statement – utóbbit a PgBouncer 1.21+ a max_prepared_statements beállítással protokollszinten kezeli) nem marad meg tranzakciók között. Ha az alkalmazás ilyet használ (például PQprepare-t vagy session-szintű SET statement_timeout-ot), session mode vagy alkalmazásoldali pool kell; a pontos képességet a telepített PgBouncer-verzió dokumentációjából kell ellenőrizni. Időtúllépéseket a statement_timeout (egy SQL utasítás maximális futásideje), a connect_timeout (kliens oldali kapcsolódási timeout) és az idle_in_transaction_session_timeout (nyitott tranzakcióban tétlenül álló session lelövése) szabályoz. Ha egy C++ szolgáltatás RAII-vezérelt tranzakciója elfelejti a COMMIT-et, az utóbbi timeout nélkül hosszú ideig lockot tarthat.

53.1.3.2 Tranzakció, lock, isolation operatív következményei

A PostgreSQL alapértelmezett izolációs szintje Read Committed. Minden UPDATE/DELETE a táblán RowExclusiveLock módot szerez (ez táblaszintű, egymással kompatibilis lock mód), az érintett sorokon pedig sorszintű zárat (ez a sor fejlécében tárolódik, nem RowExclusiveLock-ként látszik a pg_locks-ban). Ha egy másik tranzakció már zárolta a sort, a várakozó a zároló tranzakció ID-jére vár: wait_event_type = 'Lock', wait_event = 'transactionid'. A hosszú idle in transaction a sorzárral más írókat blokkol, a régi snapshotjával (backend_xmin) pedig visszatartja a VACUUM takarítását: a halott sorverziók nem távolíthatók el, ami bloatot okoz. A deadlock (kölcsönös várakozás) a PostgreSQL által automatikusan felismerésre kerül, és az egyik tranzakció ERROR: deadlock detected hibával visszagördül. A log_lock_waits = on bekapcsolása naplózza a lockvárakozásokat; a deadlock_timeout alapértelmezetten 1 s.

Működtetési nézet: a pg_stat_activity state oszlopa (active, idle, idle in transaction, idle in transaction (aborted), ritkábban fastpath function call, disabled) és a wait_event írja le, hogy a process éppen CPU-n fut, I/O-ra vár, lockra vár, vagy nincs teendője. A hibadiagnosztika ezért itt kezdődik, nem az alkalmazás logjában.

53.1.3.3 Query, index és working set memória

A PostgreSQL memóriahasználata három fő részből áll: a shared_buffers (a DB saját page cache-e, általában a RAM 25%-a), az OS page cache (a fájlok bufferelt olvasása), és a work_mem (egy rendezési vagy hash plan-csomópont felső korlátja; egy lekérdezés több ilyen csomópontot és parallel workert is használhat, a hash-műveletek a hash_mem_multiplier-rel – PG15+ alapérték 2.0 – szorzott keretig). Durva felső becslés: max_connections × (csomópontok/lekérdezés) × work_mem, ezért a work_mem-et a max_connections-szel együtt kell budgetelni. A query tervező akkor választ sequential scan-t, ha az index nem szelektív, vagy ha a költségbecslés szerint kevesebb I/O-t igényel. A work_mem túl alacsony értéke külső sort eredményez (external merge, temp file a pgsql_tmp alatt), ami felesleges lemez I/O-t és latency-t hoz be. A working set mérete akkor optimális, ha a gyakran olvasott adatok a shared_buffers-ben találhatók; ezt a pg_stat_database.blks_hit és blks_read arányával mérjük. Ha a blks_hit aránya 99% alatt van, az OS page cache és a shared_buffers mérete felülvizsgálandó.

53.1.3.4 WAL, checkpoint és fsync adatút

A commit tranzakció a WAL-ba írja a redo rekordot, majd a synchronous_commit = on esetén a wal_sync_method (gyakran fdatasync) kiírja a WAL fájlt a storage-ra. A data file-ok csak később, a checkpoint során frissülnek. A checkpoint_timeout (alapértelmezetten 5 perc) és a max_wal_size szabályozza, milyen gyakran fut a checkpoint. Ha a storage fsync latency magas (például write cache nem védett power loss ellen), a commit latency minden tranzakciónál megjelenik. Az OS szintű iostat és a PostgreSQL pg_stat_bgwriter (checkpoint_write_time, checkpoint_sync_time; PostgreSQL 17-től a pg_stat_checkpointer nézet write_time/sync_time oszlopai) együttesen mutatják meg, hogy a tartóssági határ hol szűk keresztmetszet.

53.1.3.5 Auth, TLS, role és migration

A PostgreSQL hitelesítési lánca a pg_hba.conf szabályokból áll: local kapcsolatok peer módon (OS user alapján), host kapcsolatok scram-sha-256 jelszóval vagy cert, illetve gssapi/ldap nagyobb környezetben. A ssl = on és a tanúsítvány beállításával a TCP kapcsolat TLS-titkosított. Működtetési szempontból a migration (séma) jogosultsága ne keveredjen az alkalmazás runtime jogosultságával: a lab_app role csak SELECT/INSERT/UPDATE/DELETE jogokat kapjon a szükséges táblákon, míg a lab_migrator role tulajdonosként futtathat DDL-t. A GRANT ... ON ALL TABLES IN SCHEMA folytatható, de új tábláknál a DEFAULT PRIVILEGES biztosítja a folyamatos hozzáférést.

53.1.3.6 DB/app/host telemetry

A DB belső telemetriája a pg_stat_activity, pg_stat_database, pg_stat_bgwriter, pg_stat_statements (bővítmény) nézetekből olvasható. A pg_stat_statements per query-kulcsot tárolja a total_exec_time, mean_exec_time, rows, blk_read_time, blk_write_time, wal_bytes statisztikákat, így pontosan azonosítható a legdrágább SQL és annak I/O/fsync költsége. Az OS telemetria: vmstat (CPU, swap, context switch), iostat -x (átlagos várólista, await, utilization), sar -n ETCP 1 5 (retrseg/s: újraküldött TCP-szegmensek), sar -n TCP 1 5 (új kapcsolatok active/s/passive/s – kapcsolat-churn jelzésére), ss -tnp (kapcsolatok állapota). A réteghatár-diagnosztika sorrendje: először a DB aktív sessionök és lockok, majd a lassú query-k, végül az OS I/O és CPU telítettség.

53.1.4.3 3. Kapcsolódási teszt és telemetria

# labhost01, UID 1000, kliens oldali timeout beállítás
PGPASSWORD=dummy_pw psql \
  "host=127.0.0.1 port=5432 dbname=lab_db user=lab_app
   sslmode=require connect_timeout=3" \
  -c 'SELECT 1 AS ok;'

(A libpq kapcsolati sztringben a kulcs–érték párokat tetszőleges szóköz, sortörés is elválaszthatja.)

Várható kimenet: ok oszlop 1 értékkel. Ha a pg_hba.conf hibás, a hiba FATAL: no pg_hba.conf entry for host ...; ha a statement_timeout túl alacsony, a hosszú query ERROR: canceling statement due to statement timeout üzenetet ad.

Aktív sessionök és lockok ellenőrzése:

-- sudo -u postgres psql -d lab_db
SELECT state, count(*) 
FROM pg_stat_activity 
GROUP BY state;

SELECT a.pid, a.usename, a.state, a.wait_event_type, a.wait_event,
       now() - a.query_start AS duration, left(a.query, 80) AS query
FROM pg_stat_activity a
WHERE a.state <> 'idle'
ORDER BY a.query_start;

SELECT l.pid, l.locktype, l.mode, l.granted, a.query
FROM pg_locks l
JOIN pg_stat_activity a ON l.pid = a.pid
WHERE l.granted = false;

-- ki blokkol kit: a várakozók és a blokkoló PID-ek
SELECT pid, state, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

Illusztratív kimenet: egy aktív process wait_event_type='Lock', wait_event='transactionid', granted='f' egy másik tranzakcióval szemben. A lock tulajdonosát a pg_blocking_pids() adja meg. A beavatkozás a blokkoló állapotától függ: ha active (futó lekérdezés), a SELECT pg_cancel_backend(pid) megszakítja az utasítást; ha idle in transaction, nincs futó utasítás, amit a cancel megszakíthatna – ilyenkor a SELECT pg_terminate_backend(pid) bontja a kapcsolatot (a tranzakció ROLLBACK-kel végződik), vagy a hibás alkalmazás zárja le a tranzakciót.

53.1.4.4 4. Egy hibás állapot szimulációja és javítása

Simuláljuk a connection limit kimerülést: az alábbi snippet 50 kapcsolatot indít, mindegyik 30 másodpercig alszik. A háttérben futó psql jelszót kap (exportált PGPASSWORD; éles helyett ~/.pgpass 0600 joggal), és a session szintű SET statement_timeout = '60s' felülírja a 10 s-os alapértéket, különben a pg_sleep(30)-at a szerver 10 s után megszakítaná. Csak izolált labhoston, az alkalmazás leállított poolja mellett futtassuk.

# labhost01, tesztelési szándékkal, ne élesben
export PGPASSWORD=dummy_pw
for i in $(seq 1 50); do
  psql "host=127.0.0.1 dbname=lab_db user=lab_app sslmode=require" \
    -c "SET statement_timeout = '60s'; SELECT pg_sleep(30);" \
    >/dev/null 2>"/tmp/lab-conn-$i.err" &
done
sleep 2
grep -h FATAL /tmp/lab-conn-*.err | sort | uniq -c
wait
unset PGPASSWORD

Várható (szemléltető) kimenet: 50 − 3 = 47 kapcsolat sikerül, a 48.-tól kezdve a kapcsolatok a fenntartott slotokba ütköznek, és a grep ilyen sorokat számol: FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute (PostgreSQL 16; a pontos szöveget a telepített verzió logjából kell rögzíteni). A diagnosztika SELECT count(*) FROM pg_stat_activity WHERE usename='lab_app'; mutatja, hogy elérte a max_connections - superuser_reserved_connections korlátot. Rollback: a wait után a tesztprocessek kilépnek és a slotok felszabadulnak; azonnali leállításhoz pkill -u "$USER" -f 'pg_sleep\(30\)'. Működtetési megoldás: PgBouncer bevezetése transaction poolinggal (a session-állapot fent leírt korlátjával), vagy alkalmazás oldali connection timeout és retry.

53.1.5 Tipikus hibák és ellenpróbák

  1. Kapcsolatkimerülés – tünet: új kapcsolat hibával tér vissza (remaining connection slots are reserved … a nem szuperuser kliensnél, sorry, too many clients already, ha a fenntartott slotok is elfogytak), a régi kliensek még működnek. Hipotézis: a max_connections kimerült; a pg_stat_activity szerint a sessionök idle vagy idle in transaction állapotban ülnek. Adatgyűjtés: SELECT count(*) FROM pg_stat_activity WHERE state='idle'; Egy változtatás: idle_in_transaction_session_timeout csökkentése vagy pool bevezetése. Verifikáció: a hiba eltűnik, a sessionök száma a korlát alatt marad.
  2. Hosszú query, de a CPU nem telített – tünet: p95 query latency magas, vmstat CPU idle magas. Hipotézis: lock wait vagy I/O várakozás. Adatgyűjtés: pg_stat_activity.wait_event_type mutatja, hogy Lock vagy IO. Ha Lock, a log_lock_waits naplóbejegyzések megadják a várakozó PID-et; ha IO, az iostat -x await értéke magas, és a pg_stat_statements blk_read_time szintén. Egy változtatás: index hozzáadása (lock esetben a tranzakció rövidítése, IO esetben cache növelés). Verifikáció: a wait_event eltűnik az aktív processekből.
  3. Checkpoint I/O burst diszket telít – tünet: időszakos storage latency kiugrás iostat await-ben. Hipotézis: a max_wal_size túl kicsi az írási terheléshez, ezért sok a kért checkpoint (checkpoints_req ≫ checkpoints_timed, a logban checkpoints are occurring too frequently). Adatgyűjtés: pg_stat_bgwriter checkpoints_timed, checkpoints_req, checkpoint_write_time, checkpoint_sync_time (PG17-től pg_stat_checkpointer). Egy változtatás: a max_wal_size emelése (például 1GB → 4GB, a WAL-kötet kapacitásának ellenőrzésével). A checkpoint_completion_target PostgreSQL 14 óta 0.9 alapértékű, így PG16-on az írás szétterítése már alapból adott; régebbi verzión ez is jelölt. Verifikáció: a checkpoints_req aránya csökken, a burst await csökken.

53.1.6 Feladatok

53.1.6.1 1. Magyarázó feladat: latency breakdown rétegenként

Adott egy C++ alkalmazás, amely SELECT count(*) FROM large_table lekérdezést futtat, és a p95 latency 120 ms. Az alkalmazás naplója szerint a PQexec hívás 20 ms-ot vár. Hol lehet a maradék 100 ms? Nevezd meg legalább három réteget, és mindegyikhez rendelj egy PostgreSQL vagy OS parancsot, amely igazolja vagy cáfolja a réteg érintettségét. Ne írj C++ kódot. (A rétegek időbeli helyét a „Database latency” definíciója utáni idővonal-ábra mutatja.)

53.1.6.2 2. Adminisztrációs/konfigurációs feladat: connection budget és pool

Készíts egy lab_db adatbázist lab_app role-lal, ahol a max_connections = 50, statement_timeout = 5 s, idle_in_transaction_session_timeout = 2 min, és csak 127.0.0.1-ről engedélyezett SCRAM hitelesítés. A megoldás részeként írd le a postgresql.conf és pg_hba.conf módosításokat, valamint a szükséges systemctl reload vagy restart parancsot – indokold, melyik kell. Miért nem elegendő a max_connections emelése a pool nélkül?

53.1.6.3 3. Diagnosztikai/failure feladat: lock contention helyreállítása

Egy élesnek nevezett labkörnyezetben a pg_stat_activity a következőt mutatja (illusztratív):

pid  | usename  | state       | wait_event_type | wait_event      | duration
-----+----------+-------------+-----------------+-----------------+----------
101  | lab_app  | active      | Lock            | transactionid   | 00:04:21
102  | lab_app  | idle in transaction |       |                 | 00:04:25

Melyik session blokkol, és miért? Írd le a diagnosztikai lekérdezést a lock tulajdonos azonosítására, majd a beavatkozás parancsát. Mi a postcondition?

53.1.7 Megoldások

53.1.7.1 1. Latency breakdown

A PQexec szinkron hívás: a szerver válaszáig blokkol, így a szerveroldali végrehajtás, a lock-várakozás, a storage I/O és a WAL-írás mind a 20 ms-on belül van. A maradék 100 ms tehát a hívás előtt vagy után keletkezik; lehetséges rétegei:

  • Kapcsolatfelvétel, ha a kód kérésenként nyit kapcsolatot: TCP handshake + TLS handshake + SCRAM-hitelesítés + backend fork. Ellenőrzés: a log_connections/log_disconnections sorok gyakorisága, ss -tan state time-wait '( dport = :5432 )' | wc -l, sar -n TCP 1 5 (active/s).
  • Pool-várakozás az alkalmazásban vagy a PgBouncerben: a kérés szabad kapcsolatra vár. Ellenőrzés: PgBouncer SHOW POOLS; (cl_waiting, maxwait), illetve az alkalmazás pool-acquire metrikája.
  • DNS-feloldás a DB host nevére: ellenőrzés resolvectl query <host> időzítésével.
  • Az alkalmazás saját feldolgozása és CPU-ütemezése (eredmény-feldolgozás, szerializálás, várakozás a run queue-ban): vmstat 1 (run queue), pidstat -t 1.

A 20 ms-on belüli bontáshoz külön mérés kell: a pg_stat_statements.mean_exec_time a szerveroldali végrehajtási időt adja; a kettő különbsége (20 ms − szerveroldali idő) a hálózati oda-vissza időt és a protokoll-többletet mutatja. Ezen belül lehet lock wait (wait_event_type='Lock') vagy storage I/O (blk_read_time, iostat -x), de ezek a hiányzó 100 ms-ot nem magyarázhatják.

53.1.7.2 2. PostgreSQL connection budget

A postgresql.conf releváns sorai (a teljes fájlba illesztendők):

listen_addresses = '127.0.0.1'
max_connections = 50
superuser_reserved_connections = 3
password_encryption = 'scram-sha-256'
statement_timeout = '5s'
idle_in_transaction_session_timeout = '2min'

A pg_hba.conf:

# TYPE  DATABASE USER      ADDRESS       METHOD
local   all      postgres               peer
host    lab_db   lab_app   127.0.0.1/32 scram-sha-256

Alkalmazási parancs: a max_connections, a superuser_reserved_connections és a listen_addresses postmaster kontextusú, ezért restart kell (a reload csak a timeoutokat és a pg_hba.conf-ot venné át, a többinél pending_restart = t maradna):

# labhost01, sudo szükséges
sudo systemctl restart postgresql@16-main
sudo -u postgres psql -Atc "SHOW max_connections;"   # várt: 50

A max_connections emelése önmagában nem oldja meg a terhelést, mert minden kapcsolat privát backend process-t és memóriát fogyaszt; ha az alkalmazás 1000 kliensből nyitna kapcsolatot, a rendszer memóriája és a processütemező nyomása nő. A PgBouncer transaction pooling révén kevés valódi backend szolgál ki sok klienst, és a várakozó kliensek a pooler szintjén sorban állnak, nem fogyasztanak DB process-slotot.

53.1.7.3 3. Lock contention helyreállítás

A pid=102 a blokkoló: idle in transaction állapotban tart nyitva egy tranzakciót, amely sorzárat tart. A pid=101 Lock wait-en van. A tulajdonos azonosítása a pg_blocking_pids() függvénnyel:

SELECT pid, usename, state, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by,
       now() - xact_start AS xact_age, left(query, 80) AS last_query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;

-- a blokkoló részletei
SELECT pid, state, now() - xact_start AS xact_age,
       now() - state_change AS idle_for, left(query, 80) AS last_query
FROM pg_stat_activity
WHERE pid = 102;

A pid=102 query oszlopa nem NULL: az utoljára futtatott utasítást mutatja (például a lockot szerző UPDATE-et), nem a most futót – ez a diagnosztika egyik legfontosabb nyoma. Beavatkozás: az idle in transaction sessionnek nincs futó utasítása, ezért a pg_cancel_backend() nem hat rá; a tranzakciót csak a kapcsolat bontása zárja le:

SELECT pg_terminate_backend(102);

A nyitott tranzakció ROLLBACK-kel végződik, az alkalmazás kapcsolati hibát kap. A pg_cancel_backend() akkor használható, ha a blokkoló active állapotú, futó lekérdezés. Hosszabb távú javítás: idle_in_transaction_session_timeout és az alkalmazás tranzakciókezelésének javítása. Postcondition: a pid=102 nincs a pg_stat_activity-ben, a pg_blocking_pids(101) üres, a pid=101 végrehajtja a query-t, és SELECT count(*) FROM pg_locks WHERE NOT granted = 0.

53.1.8 Rövid összefoglaló

A PostgreSQL működtetéséhez a latency-t connection, query, lock és storage rétegre kell bontani, mert mindegyik más diagnosztikai nézetben és más beavatkozással kezelhető. A connection pool csökkenti a process-per-connection modell költségét, a timeoutok pedig megakadályozzák az elhúzódó tranzakciók lock-tartását. A memória (shared_buffers, work_mem, page cache) és a WAL/checkpoint/fsync adatút közvetlenül befolyásolja a query és commit latency-t. A telemetria a pg_stat_activity, pg_stat_database, pg_stat_bgwriter és pg_stat_statements nézetekből, valamint az OS vmstat, iostat és ss parancsokból áll össze.

Továbbhasznált definíciók:

  • Connection pool: kapcsolat-újrafelhasználó réteg, amely kevés valódi DB backendet oszt meg sok kliens között, csökkentve a process-indítási és memóriaköltséget.
  • Working set: a gyakran elért adat- és indexoldalak halmaza; ha nagyobb a shared_buffers + OS page cache együttes méreténél, a lekérdezések fizikai olvasásra kényszerülnek, és a latency az I/O miatt nő.
  • WAL/fsync: a commit tartóssága a write-ahead log fsync-jén múlik; a data file-ok később, checkpointtal frissülnek.
