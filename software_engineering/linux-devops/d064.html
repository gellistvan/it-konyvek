13.4 Admin script: idempotencia, hiba és locking

13.4.1 Motiváció, definíció és előfeltételek

Egy üzemeltetési változtatás nem egy egyszeri parancs, hanem kis működtetési szerződés: ugyanaz a futás ugyanazt a kívánt állapotot (desired state) adja, konkurens futás ne írjon egymás fölé, hiba esetén maradjon auditnyom és visszaút. A szenior C++ tudás itt is használható: a resource lifetime fegyelmet, a determinisztikus destruktort és a tranzakciós gondolkodást a shellben részben trap, mktemp, mv és flock pótolja. A shell azonban nem C++: a hibák nem kivételek, hanem exit code-ok és processzhatárok.

Definíciók:

  • Idempotens admin script: ismételt futtatás ugyanazt a postconditiont adja; a már elért állapotot nem módosítja újra.
  • Atomic rename: ugyanazon fájlrendszeren belüli rename()-alapú mv; a cél név alatt vagy a régi, vagy az új inode látszik, részleges tartalom nem.
  • Advisory flock lock: a kernel a nyitott file descriptorhoz kötött lockot tárol; a processz kilépésekor az FD záródik, a lock automatikusan felszabadul.

Előfeltételek: Shell parsing, quoting és expansion, Stream, pipe, redirection és process exit; Működtetési szerződés, runbook és változtatás. Labhost: labhost1, Ubuntu Server 24.04 LTS, felhasználó labuser, emelt jog sudo-val.

13.4.2 Shell hiba- és folyamatmodell admin scripthez

13.4.2.1 set -euo pipefail és kivételek

A set -e fail-fast alapot ad: ha egy egyszerű parancs nonzero exit kóddal tér vissza, a script leáll. A set -u undefined változót, a set -o pipefail a pipelineban a jobb szélső nemnulla exitet is hibának tekinti.

A set -e azonban nem mindenhol lép: if, while, until feltételben, &&/|| bal oldalán, ! negációval, illetve bizonyos subshell-helyzetekben nem állítja meg a scriptet. Ezért például az if diff -q "$a" "$b" >/dev/null; then ... kifejezésben a diff 1-es visszatérési értéke elvárt jelzés, nem hibaüzenet. A megbízható admin script ezért nem kizárólag a set -e-re támaszkodik, hanem explicit if ! parancs; then ...; fi blokkokat használ.

13.4.2.2 Explicit error path, trap, mktemp és atomic rename

A die() függvény üzenetet ír stderrre, majd exit 1-gyel kilép. A trap cleanup EXIT C++-analógiával a determinisztikus destruktor szerepét tölti be: a script lefutása után, hiba esetén is takarít. Nem véd a SIGKILL ellen, mert az a processzt azonnal megszakítja. Az EXIT trap utolsó parancsának hibája a script exit kódját felülírhatja (egy hamis [[ … ]] && rm … lista például 1-et ad), ezért a cleanup mindig 0-val térjen vissza.

A kritikus fájlfrissítéshez a mktemp a cél könyvtárban hoz létre egyedi nevű ideiglenes fájlt. A tartalom kiírása után a chmod, majd az mv -f atomi csere. Ha a /tmp külön fájlrendszer, a mktemp -p /tmp után a mv átmásolás + unlink, nem atomi; ezért a példában a temp a cél /etc/sysctl.d alá kerül.

13.4.2.3 Instance locking flock

A kritikus frissítést konkurens futtatás ellen flock védi. Az exec 9>"$LOCK" megnyitja a lock fájlt, a flock -n 9 nem blokkoló lockot próbál szerezni. Ha egy másik példány már tartja, a script hibaüzenettel kilép. A lock nem a fájl tartalmától függ, hanem a kernelben tárolt nyitott FD-től, ezért a processz elhalásakor nem marad dead lock.

A lock fájl elérési útja /run/${PROG}.lock. A /run 0755-ös, root tulajdonú könyvtár, így a lockfájlt csak root hozhatja létre. A /run/lock ezzel szemben Ubuntun 1777-es (sticky, mindenki írhatja): ott bármely helyi felhasználó előre létrehozhatná a lockfájlt és tarthatna rajta flock-ot, amivel a root scriptet tartósan blokkolná. Ha mégis a /run/lock-ot használod, ellenőrizd a lockfájl tulajdonosát (stat -c %U). A need_root ellenőrzés a lock előtt fut.

13.4.2.4 Privilege boundary és sudo

A script maga soha nem hív sudo-t, és nem ismétli magát emelt joggal. A hívó explicit módon sudo /home/labuser/bin/lab-tune --dry-run parancsot használ. A script elején a need_root az EUID-ot ellenőrzi, és ha nem root, kilép. A lock, a célfájl és a sysctl alkalmazás így azonos, root trust osztályba tartozik.

13.4.2.5 Dry-run, diff, rollback és audit trail

A --dry-run ugyanazt a desired fájlt előállítja, de nem ír célfájlt, nem futtat sysctl-t, csak diff -u-val mutatja a különbséget. A tényleges futás – csak ha valóban változtat – készít egy backupot, majd a logger parancsot használ audit sorként. A backup a célfájl eredeti tartalmán kívül azt is rögzíti, hogy a célfájl létezett-e, és mennyi volt a kezelt kulcsok runtime értéke a változtatás előtt. A log tartalmazza a régi és új sha256sum-ot, a backup nevét és a célt. A rollback visszaállítja a célfájlt (vagy törli, ha eredetileg nem létezett), újra alkalmazza a sysctl beállításokat, majd a mentett runtime értékeket is visszaírja és ellenőrzi, mert a sysctl --system csak a fájlokban szereplő kulcsokat állítja be, a máshol nem szereplő kulcsot nem nullázza.

13.4.3 Kidolgozott példa: lab-tune sysctl admin script

A példa a vm.swappiness=10 és a net.ipv4.ip_forward=0 persistent beállítást írja a /etc/sysctl.d/99-lab-tune.conf fájlba a labhost1 rendszeren. A config-state a fájl, a runtime-state a sysctl -n vm.swappiness és a sysctl -n net.ipv4.ip_forward. A cél nem egy sablon; a script csak ezt a saját 99-lab-tune célfájlját kezeli, a labban más sysctl.d fájlok nem módosulnak.

A script elérési útja: /home/labuser/bin/lab-tune. Telepítés után chmod 0755; futtatás sudo-val.

#!/usr/bin/env bash
set -euo pipefail

PROG="${0##*/}"
TARGET="/etc/sysctl.d/99-lab-tune.conf"
BACKUP_ROOT="/var/lib/lab-tune"
LOCK="/run/${PROG}.lock"    # a /run 0755 root: csak root hozhatja létre
AUDIT_TAG="lab-tune"
KEYS=(vm.swappiness net.ipv4.ip_forward)
mode="${1:-}"               # üres vagy "apply": alkalmazás
TMP_FILE=

cleanup() {
    if [[ -n ${TMP_FILE:-} && -f $TMP_FILE ]]; then
        rm -f -- "$TMP_FILE"
    fi
    return 0                # az EXIT trap ne írja felül az exit kódot
}
trap cleanup EXIT

usage() {
    cat >&2 <<'EOF'
Usage:
  sudo lab-tune [apply|--dry-run]
  sudo lab-tune --rollback BACKUP_DIR
EOF
    exit 2
}
die() { echo "$PROG: $*" >&2; exit 1; }
log() { logger -t "$AUDIT_TAG" -p local1.info -- "$1"; }

need_root() {
    [[ $EUID -eq 0 ]] || die "run as root with sudo"
}

acquire_lock() {
    exec 9>"$LOCK"
    flock -n 9 || die "another instance holds $LOCK"
}

make_desired() {
    local f="$1"
    cat >"$f" <<'EOF'
# Managed by lab-tune. Do not edit manually.
vm.swappiness=10
net.ipv4.ip_forward=0
EOF
    chmod 0644 "$f"
}

# A backup egy könyvtár: a célfájl eredeti tartalma (ha létezett),
# a létezés jelzője és a kulcsok változtatás előtti runtime értéke.
make_backup() {
    local dir="$1" k
    if [[ -f "$TARGET" ]]; then
        cp -p -- "$TARGET" "$dir/target.conf"
        echo "existed=1" >"$dir/state"
    else
        echo "existed=0" >"$dir/state"
    fi
    for k in "${KEYS[@]}"; do
        printf '%s=%s\n' "$k" "$(/sbin/sysctl -n "$k")" >>"$dir/runtime"
    done
}

apply_sysctl() {
    local backup="$1"
    if ! /sbin/sysctl --system >/dev/null; then
        echo "$PROG: config written, but sysctl --system failed" >&2
        echo "Rollback with: sudo $PROG --rollback $backup" >&2
        return 1
    fi
}

replace_from_backup() {
    local src="$1" tmp
    tmp=$(mktemp -p /etc/sysctl.d .99-lab-tune.tmp.XXXXXXXXXX) \
        || die "mktemp"
    TMP_FILE="$tmp"
    cp -p -- "$src" "$tmp"
    mv -f -- "$tmp" "$TARGET"
    TMP_FILE=
}

rollback() {
    local backup="$1" line k v
    [[ -f "$backup/state" && -f "$backup/runtime" ]] \
        || die "not a lab-tune backup: $backup"
    if grep -qx 'existed=1' "$backup/state"; then
        replace_from_backup "$backup/target.conf"
    else
        rm -f -- "$TARGET"   # a célfájl a változtatás előtt nem létezett
    fi
    apply_sysctl "$backup"
    # a sysctl --system nem állítja vissza a kulcsokat, amelyekhez
    # már egyetlen fájl sem rendel értéket: a mentett értéket írjuk vissza
    while IFS= read -r line; do
        /sbin/sysctl -q -w "$line"
    done <"$backup/runtime"
    while IFS='=' read -r k v; do
        [[ "$(/sbin/sysctl -n "$k")" == "$v" ]] || die "runtime mismatch: $k"
    done <"$backup/runtime"
    log "rollback applied from $backup"
    echo "Rollback complete from $backup"
}

main() {
    need_root
    acquire_lock
    case "$mode" in
        --dry-run)
            local tmp
            tmp=$(mktemp -p /etc/sysctl.d .99-lab-tune.tmp.XXXXXXXXXX) \
                || die "mktemp"
            TMP_FILE="$tmp"
            make_desired "$tmp"
            if [[ ! -f "$TARGET" ]]; then
                echo "DRY-RUN: $TARGET would be created:"
                cat "$tmp"
            elif diff -q "$TARGET" "$tmp" >/dev/null; then
                echo "OK: $TARGET already matches desired state"
            else
                echo "DRY-RUN: $TARGET would be changed:"
                diff -u "$TARGET" "$tmp" || true
            fi
            exit 0
            ;;
        --rollback)
            [[ $# -ge 2 ]] || usage
            rollback "$2"
            exit 0
            ;;
        ""|apply)
            ;;
        *)
            usage
            ;;
    esac

    local tmp backup old_sum new_sum
    if [[ -L "$TARGET" ]]; then die "refusing to replace symlink $TARGET"; fi
    tmp=$(mktemp -p /etc/sysctl.d .99-lab-tune.tmp.XXXXXXXXXX) || die "mktemp"
    TMP_FILE="$tmp"
    make_desired "$tmp"

    if [[ -f "$TARGET" ]] && diff -q "$TARGET" "$tmp" >/dev/null; then
        echo "OK: $TARGET already matches desired state"
        exit 0
    fi

    # backup csak akkor készül, ha valóban változtatunk
    install -d -m 0700 "$BACKUP_ROOT"
    backup=$(mktemp -d -p "$BACKUP_ROOT" backup.XXXXXXXXXX) || die "mktemp"
    make_backup "$backup"

    old_sum=none
    if [[ -f "$TARGET" ]]; then
        old_sum=$(sha256sum "$TARGET" | cut -d' ' -f1)
    fi
    new_sum=$(sha256sum "$tmp" | cut -d' ' -f1)

    mv -f -- "$tmp" "$TARGET"
    TMP_FILE=
    apply_sysctl "$backup"
    echo "Applied. Backup: $backup"
    log "applied $TARGET old=$old_sum new=$new_sum backup=$backup"
}

main "$@"

A futtatási lépések a labhost1 hoston:

# 1. Dry-run
sudo /home/labuser/bin/lab-tune --dry-run
# Várható kimenet, ha a célfájl még nem létezik:
# DRY-RUN: /etc/sysctl.d/99-lab-tune.conf would be created:
# # Managed by lab-tune. Do not edit manually.
# vm.swappiness=10
# net.ipv4.ip_forward=0

# 2. Alkalmazás
sudo /home/labuser/bin/lab-tune
# Várható kimenet: Applied. Backup: /var/lib/lab-tune/backup.ZZ...

# Ellenőrzés
sysctl -n vm.swappiness
# Várt: 10

# 3. Idempotencia ellenőrzés
sudo /home/labuser/bin/lab-tune
# Várható kimenet:
# OK: /etc/sysctl.d/99-lab-tune.conf already matches desired state
# (új backup nem keletkezik)

# 4. Rollback a kiírt backup névvel
sudo /home/labuser/bin/lab-tune --rollback /var/lib/lab-tune/backup.ZZ...
# Várható kimenet: Rollback complete from ...
sysctl -n vm.swappiness
# Várt: a backup runtime fájljában mentett érték, például 60
test -e /etc/sysctl.d/99-lab-tune.conf || echo "target removed"
# Várt, ha a célfájl korábban nem létezett: target removed

A rollback utáni runtime érték a backup runtime fájljában tárolt, a változtatás előtt mért érték, akkor is, ha a célfájl korábban nem létezett. A postcondition így: a célfájl állapota (tartalma vagy hiánya) és a runtime-state egyezik a backupban rögzítettel. A kimenetek illusztratívak, nem futtatott eredmények.

Az alábbi ábra az apply-ág lépéseit és a négy állapotnézetet (célfájl, backup, temp, runtime) mutatja, a két tipikus megszakadási ponttal.

13.4.4 Hibák és ellenpróbák

A set -e nem áll le if feltételben. Ha a felhasználó önállóan ír diff -q "$TARGET" "$tmp" parancsot, a script leáll, ha a fájlok eltérnek. Ellenpróba: a --dry-run ágban a diff -u hívás után || true kell, mert a különbség elvárt, nem hiba.

A trap túl széles köre. Ha a trap a backup fájlt is törli a kilépéskor, akkor a rollback elveszik. Tünet: az Applied. kiírás után a backup nem létezik. Hipotézis: a cleanup minden tempet töröl. Javítás: a cleanup csak a TMP_FILE-t kezelje, a backupot soha ne.

A temp és a cél eltérő fájlrendszeren. Ha a temp a /tmp-ben készül, az mv nem atomi. Tünet: a célfájl rövid ideig hiányos olvasható másolás lehet. Javítás: a mktemp -p a cél könyvtárat használja.

A lock nem blokkoló ellenőrzése. A flock -n hibásan konfigurált esetben azonnal meghiúsul. A tipikus hibaüzenet: another instance holds /run/lab-tune.lock. Ennél ellenőrizni kell, hogy a másik processz valóban fut-e még, vagy csak egy régi FD maradt nyitva. Adatgyűjtés: lslocks vagy fuser -v /run/lab-tune.lock – kinek a processze tartja? Világ által írható lock-könyvtárban (/run/lock) egy idegen felhasználó processze is tarthatja. A kernel lock nem marad dead lock, ha a processz megszűnik; a fájl tartalma nem a lock forrása.

A sysctl alkalmazás hibája. Ha a config fájlba kerül egy hibás sor, például vm.swappiness=not_a_number, akkor a sysctl --system kiírja a hibát, és a script leáll. A fájl már új, a runtime régi. Ilyenkor a kiírt rollback parancs a backupból visszaállítja a konzisztens állapotot. A script ezt a --dry-run-nal nem fogja meg, mert a dry-run csak a configot hasonlítja össze; a sysctl --system futtatása a tényleges validáció.

13.4.5 Feladatok

  1. Magyarázó: A lab-tune --dry-run ága diff -u "$TARGET" "$tmp" || true-t használ. Magyarázd el, miért van itt szükség az explicit || true-ra a set -e mellett, és mutass egy egyszerű parancssort, ahol enélkül a script leállna.

  2. Adminisztrációs/konfigurációs: Készítsd el a lab-limits scriptet a /etc/security/limits.d/99-lab-nproc.conf fájlhoz a következő desired tartalommal:

    # Managed by lab-limits.
* soft nproc 4096
* hard nproc 8192

    A script legyen idempotens, készítsen backupot, használjon flockot, mktemp-et és atomic rename-et. A lock fájl neve /run/lab-limits.lock, a scripté /home/labuser/bin/lab-limits.

  3. Diagnosztikai/failure/recovery: Indítsd el a lab-tune-ot kétszer párhuzamosan ugyanazon a hoston. Figyeld meg a második hibaüzenetét. Jegyezd fel a lab-tune által kiírt Backup: útvonalat. Ezután írd a TARGET-ba a vm.swappiness=not_a_number sort, futtasd a sudo /sbin/sysctl --system-et (várhatóan hibát ír), majd állítsd helyre a feljegyzett backupból a sudo lab-tune --rollback <backup> paranccsal. Ellenőrizd a fájl tartalmát és a runtime értéket is, végül futtasd kétszer a sudo lab-tune-ot.

13.4.6 Megoldások

  1. A diff akkor tér vissza 1-essel, ha a fájlok különböznek. A --dry-run esetén ez elvárt állapot, nem valódi hiba. A set -e az ilyen nonzero exitet hibaként kezelné, és a script leállna. Az explicit || true ezt a visszatérési értéket 0-ra normalizálja. Példa: diff -u /etc/hostname /etc/hostname.old eltérő fájlokkal set -e alatt a scriptet megszakítja, ha nincs kezelés.

    Postcondition: a --dry-run eltérő fájlok esetén is befejeződik 0 exit kóddal, és kiírja a különbséget.

  2. A lab-limits script a lab-tune mintát követi (mode="${1:-}", mindig 0-val visszatérő cleanup, backup csak tényleges változtatáskor). A TARGET="/etc/security/limits.d/99-lab-nproc.conf", a desired tartalmat a make_desired írja, a backup mktemp -d -p /var/lib/lab-limits backup.XXXXXXXXXX könyvtár a célfájl másolatával és a létezés jelzőjével (runtime érték itt nincs, a limitek a következő bejelentkezéskor lépnek életbe), a lock /run/lab-limits.lock. A futtatás:

    sudo /home/labuser/bin/lab-limits --dry-run
sudo /home/labuser/bin/lab-limits
sudo /home/labuser/bin/lab-limits

    Postcondition: a 99-lab-nproc.conf a desired tartalmat tartalmazza; a második futtatás OK üzenetet ad, és nem hoz létre új backupot; az első futás backupja létezik; a lock felszabadult.

  3. A párhuzamos futásnál az első példány lockot szerez, a második flock -n hibaüzenettel kilép: lab-tune: another instance holds /run/lab-tune.lock (ha az első példány már végzett, a második nem ütközik; ekkor ismételd). A hibás sor beírása után a kézzel futtatott sysctl --system stderrre hibát ír a vm.swappiness kulcsra; a lab-tune ebben a lépésben nem fut. A rollback a feljegyzett backupból:

    sudo /home/labuser/bin/lab-tune --rollback /var/lib/lab-tune/backup.ZZ...
sysctl -n vm.swappiness
ls -l /etc/sysctl.d/99-lab-tune.conf
sudo /home/labuser/bin/lab-tune   # várt: Applied. Backup: …
sudo /home/labuser/bin/lab-tune   # várt: OK: … already matches …

    Postcondition: a célfájl a lab-tune előtti állapotot hordozza (ha korábban nem létezett, nincs is meg), a sysctl -n vm.swappiness a backupban mentett értéket adja. Mivel ez nem a desired állapot, a következő lab-tune futás újra Applied.-ot ír ki (nem OK-t), és csak az azutáni futás ad OK-t.

13.4.7 Rövid összefoglaló

Az admin script kis változtatási szerződés: idempotens, hibakezelt, konkurens futás ellen védett és visszaállítható. A set -euo pipefail fail-fast alapot ad, de a feltételben szereplő parancsok kivételek; explicit if és die kell. A trap cleanup takarít, a mktemp + mv atomi cserét ad, az flock processzhez kötött lockot biztosít. A sudo-t a hívó adja, a script root ellenőrzést végez. A dry-run, backup, rollback és logger audit költsége kicsi, de a recovery képesség alapja.

Definíciók:

  • Idempotens admin script: ismételt futás ugyanazt a postconditiont adja, újabb módosítás nélkül.
  • Atomic rename: ugyanazon fájlrendszeren belüli mv; a cél név alatt vagy régi, vagy új tartalom látszik.
  • Advisory flock lock: a kernel a nyitott FD-hez kötött lockot tartja; processz halálakor felszabadul.

13.4.8 Források és ellenőrzési hiányok

Állításonkénti források (laborprofil: Ubuntu Server 24.04 LTS, GNU Bash 5.2, util-linux 2.39, procps-ng 4.0, systemd 255; a noble kézikönyvoldalak ehhez a kiadáshoz tartoznak):

  • set -e kivételei, pipefail, trap … EXIT: Bash Reference Manual, 4.3.1 „The Set Builtin” és 4.1 „Bourne Shell Builtins” (trap) – https://www.gnu.org/software/bash/manual/bash.html#The-Set-Builtin
  • flock és az FD-hez kötött advisory lock: flock(1) – https://manpages.ubuntu.com/manpages/noble/man1/flock.1.html; flock(2) – https://man7.org/linux/man-pages/man2/flock.2.html
  • atomi csere: rename(2) – https://man7.org/linux/man-pages/man2/rename.2.html; mktemp(1) – https://manpages.ubuntu.com/manpages/noble/man1/mktemp.1.html
  • sysctl --system betöltési sorrendje és a -w/-n kapcsolók: sysctl(8) – https://manpages.ubuntu.com/manpages/noble/man8/sysctl.8.html; a /etc/sysctl.d/*.conf szintaxisa: sysctl.d(5) – https://www.freedesktop.org/software/systemd/man/latest/sysctl.d.html
  • a vm.swappiness jelentése: Linux kernel dokumentáció, „Documentation for /proc/sys/vm/” – https://docs.kernel.org/admin-guide/sysctl/vm.html
  • /run és /run/lock szerepe: Filesystem Hierarchy Standard 3.0, 3.15 „/run: Run-time variable data” – https://refspecs.linuxfoundation.org/fhs.shtml
  • audit sor: logger(1) – https://manpages.ubuntu.com/manpages/noble/man1/logger.1.html

Reprodukciós állapot: dátumozott futtatási napló még nem készült; a sysctl --system hibás sorral adott visszatérési viselkedése, a /run/lock 1777-es jogosultsága és a teljes apply/idempotencia/rollback ciklus a 24.04-es labhoston ellenőrizendő. A kimenetek futás nélküli, illusztratív kimenetek.
