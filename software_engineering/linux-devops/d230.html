46.5 Idempotens provision és interrupted change labor

46.5.1 Motiváció

Egy szenior C++ fejlesztő számára a program fordítási idejű determinizmus és a repository-ból való reprodukálhatóság magától értetődő. Az infrastruktúra-provisioning esetén ugyanez a garancia nem adódik ingyen: a felhő vagy virtualizációs API hívása távoli, állapotukat egy külön statefile tartja nyilván, és egy félbeszakadt apply után a tényleges erőforrás, a konfiguráció és a state három különböző állapotot mutathat. Ez a laborkör azt gyakoroltatja, hogyan ellenőrizzük a desired state és az observed state közötti egyezést, hogyan építsük fel a plan → apply → no-op plan ellenőrzési láncot, és hogyan lábadozzunk driftből, importból, moved műveletből, valamint félbeszakadt provisioningből anélkül, hogy a teljes erőforráskészletet megsemmisítenénk vagy a state-et kézzel hamisítanánk.

46.5.2 Definíció és működés

Az idempotens provision azt jelenti, hogy ugyanazon konfigurációból kiindulva ismételt plan/apply futtatás nem hoz létre újabb erőforrást, és a meglévőket nem módosítja indokolatlanul. Ez nem általános távoli exactly-once garancia; a konfiguráció a desired state-et írja le, a statefile a tárolt leképzést a távoli azonosítókhoz, a plan pedig a refreshelt observed state és a desired state közötti különbséget mutatja. Ha a konfiguráció és a state megegyezik a távoli erőforrással, a plan no-op plan: 0 add, 0 change, 0 destroy.

A state lock a working directory state írását védő zár. Hosszabb apply alatt egy második parancs lockhibát kaphat; a -lock-timeout opcióval megadható, hány időtartamig várakozzon a zár feloldására. A provider lock ezzel szemben a .terraform.lock.hcl fájlban rögzíti a provider verzióját és checksumjait, így a init újra lehívható reprodukálható módon. A két zár célja különböző: előbbi a state-adat integritását védi, utóbbi a provider-ellátási láncot rögzíti.

A drift olyan állapot, amikor a távoli erőforrás megváltozott a provsioneren kívül (például egy fájlt kézzel módosítottak). A plan ilyenkor change-et vagy destroy/replace-t mutat. A partial success olyan apply eredmény, amelynél egyes erőforrások létrejöttek, mások hibát kaptak; a statefile és a config szerinti következő apply csak a hiányzó vagy hibás erőforrásokat pótolja. Az import meglévő távoli objektumot visz a statebe anélkül, hogy provisioninget futtatna, a moved blokk pedig akkor frissíti a state erőforrás-címét, ha a HCL-ben átnevezzük az erőforrást. A destroy -target csak a megadott erőforrás-címeket és a tőlük függőket törli, ezért alkalmas a lab resource set explicit szűkítésére.

46.5.3 Kidolgozott példa

A példa izolált labhoston, labvm01, felhasználó lab (UID 1000), working directory /home/lab/iac/d230. A cél egy helyi, fixtúra jellegű erőforrás-készlet a local és null providerrel. A konfiguráció main.tf:

terraform {
  required_version = "~> 1.6"
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.4"
    }
    null = {
      source  = "hashicorp/null"
      version = "~> 3.2"
    }
  }
}

resource "local_file" "lab_file" {
  filename = "/home/lab/iac/d230/lab.txt"
  content  = "d230 idempotens provision\n"
}

resource "null_resource" "lab_wait" {
  depends_on = [local_file.lab_file]

  triggers = {
    content_sha = sha256(local_file.lab_file.content)
    cmd         = "echo lab_wait-ok"
  }

  provisioner "local-exec" {
    command = "${self.triggers.cmd} >> /home/lab/iac/d230/lab_wait.log"
  }
}

A local_file erőforrás a fájlt a megadott tartalommal hozza létre; a null_resource egy állapot nélküli placeholder, amelynek provisionere egy shell parancsot futtat. A provisioner szándékosan külön fájlba (lab_wait.log) ír: ha a local_file által kezelt lab.txt-hez fűzne hozzá, a fájl eltérne a desired state-től, és a következő plan sem lehetne no-op. A depends_on rögzíti a sorrendet (először a fájl, utána a provisioner). A triggers térkép a null_resource „bemenete”: bármelyik értékének változása cserét (replace) kényszerít, és csak ekkor fut újra a létrehozáskor futó (creation-time) provisioner; a provisioner blokk szövegének módosítása önmagában nem része a diffnek. A lab célja nem a szolgáltatás, hanem a state-kezelés, ezért elegendő.

Az alábbi lépések mindegyikét a lab felhasználó, a labvm01 hoston, a /home/lab/iac/d230 munkakönyvtárban hajtjuk végre.

  1. Provider inicializálás és lockfile létrehozása:
# target: labvm01, user: lab (UID 1000), workdir: /home/lab/iac/d230
tofu init
tofu providers lock -platform=linux_amd64

Várható kimenet init esetén: OpenTofu has been successfully initialized!, majd a lockfile .terraform.lock.hcl létrejön. Az aktuális provider release-t és a tofu verzióját a labor előtt ellenőrizni kell; az itt szereplő verziószámok illusztratívak.

  1. Terv készítése és apply:
tofu plan -out=lab.plan
tofu apply lab.plan

A plan kimenete: Plan: 2 to add, 0 to change, 0 to destroy. Az apply létrehozza a lab.txt-t, majd a null_resource provisionere a lab_wait.log-ba írja a lab_wait-ok sort; a lab.txt tartalma pontosan a konfigurációban megadott marad. A statefile terraform.tfstate létrejön.

  1. No-op ellenőrzés:
tofu plan

Várható: No changes. Your infrastructure matches the configuration. Ezzel bizonyítottuk, hogy a provision idempotens.

  1. Drift generálása és észlelése:
echo "manual-edit" >> /home/lab/iac/d230/lab.txt
tofu plan -detailed-exitcode
echo "exit code: $?"

A plan 2-es exit code-ot ad, és a kimenet jelzi, hogy a local_file.lab_file újra létrejön (will be created, összesítő: 1 to add), mert a fájl tartalma eltér a desired state-től. A hashicorp/local provider local_file erőforrásának nincs helyben módosítása (in-place update): a refresh a megváltozott tartalmú fájlt hiányzónak tekinti, ezért nem „1 to change”, hanem újralétrehozás látszik; a pontos kimenetet a labor futtatásakor kell rögzíteni. A null_resource nem cserélődik, mert a content_sha triggere a konfigurált tartalomból számolódik, az pedig nem változott. A driftből való kiindulás:

tofu apply -auto-approve
tofu plan

Az apply visszaállítja a fájlt a desired state-be, a második plan ismét no-op.

  1. moved fixture: átnevezzük az erőforrást a HCL-ben lab_file-ról lab_data-ra (a null_resource depends_on és triggers hivatkozását is local_file.lab_data-ra írjuk át). moved blokk nélkül a plan destroy/create-et mutatna. Helyette moved blokk:
moved {
  from = local_file.lab_file
  to   = local_file.lab_data
}

Ezután:

tofu plan
tofu apply -auto-approve
tofu state list

A state-listában local_file.lab_data jelenik meg, a lab_file nem; a plan nem mutat destroy/create-et.

  1. State backup:
tofu state pull > lab-state-$(date -u +%Y%m%dT%H%M%SZ).json
jq '.resources | length' < lab-state-*.json

A backup fájl egy friss terraform.tfstate JSON-t tartalmaz; a jq kimenete 2. A visszaállítás csak kényszerű esetben: tofu state push lab-state-....json, de egy párhuzamos apply-t előbb le kell állítani, mert a push felülírja a state-et.

  1. Partial success szimulálása: a main.tf-ben a null_resource cmd triggerét false-ra cseréljük. A provisioner blokk szövegének átírása nem lenne elég, mert az nem része a resource diffjének; a trigger változása viszont cserét kényszerít, így a provisioner ténylegesen újra lefut:
  triggers = {
    content_sha = sha256(local_file.lab_data.content)
    cmd         = "false"
  }

Ekkor a tofu apply -auto-approve a null_resource.lab_wait cseréjét tervezi; a régi példány törlődik, az új létrehozása közben a provisioner hibázik, az apply nem 0 exit code-ot ad. A hibás provisioner után a null_resource tainted állapotba kerül (tofu state show null_resource.lab_wait, illetve a következő plan jelzi, hogy a tainted erőforrást cserélni kell). A local_file.lab_data érintetlen: a state-ben változatlanul szerepel, a fájl tartalma nem módosult. A hibás részt javítva (cmd = "echo lab_wait-ok") a következő tofu apply csak a tainted null_resource-t cseréli, a többit nem kezdi újra. Ugyanez a hatás a konfiguráció módosítása nélkül is elérhető: tofu apply -replace=null_resource.lab_wait -auto-approve.

  1. Destroy explicit lab resource seten:
tofu destroy -target=null_resource.lab_wait
tofu state list

A null_resource.lab_wait törlődik, a local_file.lab_data megmarad. Ez a destroy csak a nevezett erőforrásra terjed ki; a teljes erőforráskészlet törléséhez tofu destroy (explicit megerősítéssel) és a munkakönyvtár takarítása szükséges.

46.5.4 Hibák és ellenpróbák

Lock timeout hiba

Tünet: Error acquiring the state lock vagy Timeout while waiting for state lock. Oka: párhuzamos apply vagy álló state lock. Adatgyűjtés: ps -ef | grep tofu. Hipotézisellenőrzés: várjunk a lock feloldására, vagy tofu apply -lock-timeout=60s. Ha a lock tartósan beragadt (például megölt folyamat maradványa), akkor a tofu force-unlock <lock-id> használható, de előbb ellenőrizni kell, hogy nincs tényleges apply futásban; a force-unlock nem rollback, hanem a lock ellenőrizetlen feloldása.

Drift észrevétlen marad

Tünet: a plan nem mutat change-et, pedig a távoli erőforrás megváltozott. Oka: a konfiguráció nem írja le a teljes desired state-et, vagy a state külsőleg frissült. Hipstézis: az apply előtti plan refresh nélkül készült. Ellenőrzés: tofu plan -refresh-only lefuttatása. Ha a provider nem támogat bizonyos attribútum refreshét, a drift nem detektálható; ilyenkor explicit disk- vagy API-ellenőrzést kell végezni.

Import rossz resource címmel

Tünet: a tofu import hibával áll meg, mert a megadott resource-cím nem létezik a konfigurációban (a pontos hibaszöveget a labor futtatásakor kell rögzíteni). Oka: a HCL-ben nincs ilyen resource, vagy a resource típus/cím nem illik. Javítás: a main.tf-ben először hozzuk létre a resource blokkot a kívánt címmel, és csak utána futtassuk a tofu import <cím> <azonosító> parancsot; import után a tofu plan no-op kell legyen, ha a konfiguráció megegyezik a meglévő objektummal. Fontos korlát: az import csak olyan erőforrástípuson működik, amelynek providere importot támogat. A labor local_file és null_resource erőforrásainál ez a használt hashicorp/local/hashicorp/null verzió registry-dokumentációjában ellenőrizendő; ha a típus nem importálható, a meglévő lab.txt-t a következő apply újra létrehozza, az import-folyamatot pedig importálható erőforráson (például sandbox aws_s3_bucket-en) kell gyakorolni.

Partial apply ismételt sikertelensége

Tünet: az apply újra és újra hibaüzenettel áll meg ugyanazon erőforrásnál. Oka: a provisioner vagy provider oldali függőség nem idempotens, vagy a lokális oldali feltétel nem teljesül. Adatgyűjtés: tofu state list, tofu show, provider log TF_LOG=DEBUG. Egy változtatás: a hibás erőforrást töröljük a stateből tofu state rm paranccsal, majd az apply újra provisioningel; ez veszélyes, ezért előbb backupot kell készíteni.

46.5.5 Feladatok

1. Magyarázó feladat: no-op plan értelmezése

Futtassa le a konfigurációt a példa szerint, majd készítsen egy no-op-plan.txt fájlt, amelyben a tofu plan kimenetét rögzíti. Magyarázza meg, miért bizonyítja ez a kimenet, hogy a provision idempotens; jelölje meg, melyik sor mutatja, hogy nincs tervezett művelet, és ellenőrizze tofu plan -detailed-exitcode futtatással, hogy az exit code 0.

2. Konfigurációs/adminisztrációs feladat: drift és moved

A kiinduló labresource-ből kézzel módosítsa a lab.txt fájlt úgy, hogy a tartalom már ne egyezzen a konfigurációval. Készítsen plan -detailed-exitcode-ot, mentsen el a kimenetet. Ezután állítsa vissza a fájlt apply segítségével, és ellenőrizze no-op plan-nel. Végül nevezze át az erőforrást lab_file-ról lab_moved-ra a HCL-ben, és oldja meg moved blokkal, hogy a state ne legyen destroy/create.

3. Diagnosztikai/failure feladat: partial success és recovery

Szimuláljon partial apply-t: a null_resource.lab_wait cmd triggerét cserélje false-ra, futtasson apply-t, rögzítse az exit kódot és a null_resource tainted állapotát. Készítsen state backupot a hibás állapotról. Állítsa vissza a triggert echo lab_wait-ok-ra, futtasson újra apply-t, és ellenőrizze, hogy a korábban sikeres local_file nem alakult át, valamint hogy a null_resource.lab_wait cserélődött. Végül destruálja a null_resource-t, és igazolja, hogy a local_file megmaradt.

46.5.6 Megoldások

1. feladat

A tofu plan kimenete a konfiguráció és a state refresh utáni egyezését mutatja (szemléltető, nem futtatott; a magyarázó második sor verziónként eltér):

No changes. Your infrastructure matches the configuration.

Változás nélküli tervnél nincs „Plan: … to add” összesítősor; a „No changes” sor jelzi, hogy nincs tervezett művelet. Gépi bizonyítékként a tofu plan -detailed-exitcode 0-s exit code-ja szolgál (2 jelentene változást, 1 hibát). Ez bizonyítja, hogy a második apply nem hozna létre újra erőforrást, mert a state és a desired egyezik. Postcondition: a no-op-plan.txt a munkakönyvtárban van, tartalma a fenti kimenet, és a state local_file.lab_file-t tartalmaz.

2. feladat

Drift készítése: echo "manual-edit" >> /home/lab/iac/d230/lab.txt. A tofu plan -detailed-exitcode kimenete:

Plan: 1 to add, 0 to change, 0 to destroy.

(Szemléltető, nem futtatott összesítősor: a local provider a megváltozott tartalmú fájlt hiányzónak tekinti, ezért a local_file.lab_file újra létrejön; a pontos kimenetet a labor futtatásakor kell rögzíteni.) Az exit code 2. A javítás tofu apply -auto-approve után a fájl tartalma a konfigurációban megadott, a no-op plan 0 add/0 change/0 destroy. Az átnevezés: a main.tf-ben resource "local_file" "lab_moved" { ... }, és a moved blokk:

moved {
  from = local_file.lab_file
  to   = local_file.lab_moved
}

A null_resource hivatkozásait is local_file.lab_moved-ra kell átírni. A tofu plan csak az áthelyezést jelzi (has moved to), add/change/destroy művelet nélkül. tofu apply után tofu state list a local_file.lab_moved-et mutatja, a lab_file nem létezik. Postcondition: a stateben az erőforrás új címe szerepel, a fájl tartalma változatlan, no-op plan.

3. feladat

A main.tf null_resource triggere cmd = "false". A trigger változása miatt a plan a null_resource.lab_wait cseréjét tervezi; az apply -auto-approve alatt a provisioner hibázik, az exit code nem 0. A state terraform.tfstate a local_file erőforrásra vonatkozóan változatlanul tartalmazza a kívánt paramétereket, a null_resource pedig tainted állapotban van (tofu state show null_resource.lab_wait; a következő plan cserét tervez rá). State backup: tofu state pull > partial-state-$(date -u +%Y%m%dT%H%M%SZ).json. Javítás után cmd = "echo lab_wait-ok", tofu apply -auto-approve: csak a tainted null_resource cserélődik. A local_file no-op plan-nel igazolhatóan változatlan marad. Végül tofu destroy -target=null_resource.lab_wait, majd tofu state list: a local_file.lab_moved megmarad, a null_resource eltűnt. Postcondition: a stateben a local_file a lab_moved címen szerepel, a null_resource törölve, a backup fájl érvényes JSON.

46.5.7 Rövid összefoglaló

Ez a labor a provision folyamat ellenőrzésére tanította be az idempotens desciplinát: a plan-ből kiderül, hogy a konfiguráció, a state és a tényleges erőforrás egyezik-e; a no-op plan a reprodukálhatóság bizonyítéka. A driftből apply-vel vagy refresh-only módban lehet kilábalni; import és moved eszközökkel a state igazítható a meglévő erőforrásokhoz. Félbeszakadt apply után a state rendben lévő erőforrásai nem sérülnek, és a következő apply csak a hiányzó részeket pótolja. A destroy-t csak explicit lab resource címre szűkítve futtassuk, és minden elágazásnál készítsünk state backupot. Továbbhasznált definíciók: desired state – a konfigurációban leírt célállapot; observed state – a refreshelt távoli állapot; no-op plan – olyan plan, amely 0 add/change/destroy értéket jelez.

46.5.8 Források és ellenőrzési hiányok

Az alábbiak ellenőrizendő kiindulópontok, nem ebben a munkamenetben olvasott bizonyítékok. Állításonként:

  • plan/apply, -detailed-exitcode, -replace, -refresh-only, -lock-timeout, force-unlock, state pull/push/rm/list, import, moved blokk, provisioner és tainted állapot: OpenTofu dokumentáció, a „CLI commands” és a „Language” (Resources, Provisioners, Refactoring/moved) fejezetek; hivatkozott verzió: OpenTofu 1.6.x (a main.tf required_version = "~> 1.6" korlátja).
  • Provider lock (.terraform.lock.hcl, tofu providers lock): ugyanott a „Dependency Lock File” oldal, OpenTofu 1.6.x.
  • local_file és null_resource viselkedése (ForceNew argumentumok, triggers, importtámogatás): a Terraform Registry hashicorp/local 2.4.x és hashicorp/null 3.2.x providerdokumentációja.
  • Terraform-kompatibilitás: HashiCorp Terraform dokumentáció – a Terraform és az OpenTofu szintaktikai kompatibilitása nem teljes minden feature-re.
  • AWS dokumentáció – a lab ebben a fejezetben nem használ AWS erőforrást; az importgyakorlat importálható sandbox erőforrásához használható, a sandbox scope korlátjával.

Ellenőrzési státusz: a kidolgozott példa sikeres ága (no-op plan) és hibaágai (drift, tainted null_resource, import) laborban ellenőrizendők; dátumozott futtatási napló (eszközverziókkal és parancskimenettel) még nem készült.

A jelen szövegben szereplő providerverziók, az OpenTofu 1.6 kompatibilitási állítások és a tofu providers lock pontos viselkedése nem ellenőrzött a kiadási dokumentációban; ezeket a labor futtatása előtt a hivatalos release notes és provider registry ellenőrzésével kell alátámasztani. Nincs ténylegesen futtatott kimenet, minden megadott output illusztratív.
