33.5 Routing/overlay haladó labor

33.5.1 Motiváció

Adatközponti fabric alatt egy alkalmazáskimaradás gyakran két rétegben egyszerre jelentkezik: a fizikai vagy IP-útvonali underlay kiesik, miközben a VXLAN overlay ugyanarról a forgalomról már nem is tud. A hibakeresés akkor hatékony, ha a két réteget külön bizonyítékokkal lokalizáljuk, majd control-plane változtatás után konvergenciát mérünk. Ebben a laborban egy kicsinyített, de valódi FRR/namespace topológián gyakoroljuk az underlay/overlay szétválasztást, a single link/node failure utáni reconvergence-t és a VXLAN encapsulation adatútjának ellenőrzését.

33.5.2 Definíció és működés

Az underlay az a hálózati réteg, amely tényleges IP-kapcsolatot és útvonalakat biztosít a hálózati eszközök között. Legyen BGP-alapú, spine–leaf felépítésű IP-fabric: minden leaf két spine-nal peerel, így egy link kiesése után is marad alternatív útvonal.

Az overlay ezen a transporton szeparált, címzett virtuális hálózatot hoz létre. A VXLAN egy UDP-s encapsulation (RFC 7348): a belső Ethernet frame-et egy külső IP/UDP fejlécbe csomagolja, és a VXLAN Network Identifier (VNI) azonosítja a tenant hálózatot. A VTEP (VXLAN Tunnel Endpoint) a fogadó/küldő pont: esetünkben minden leaf egy VTEP, amely a belső bridge-ben VXLAN portként jelenik meg.

A control plane a BGP prefixek cseréjét és a VTEP loopback címek elérhetőségét terjeszti. A data plane a tényleges VXLAN payload továbbítást végzi. A konvergencia az az idő, amíg egy hiba után az útvonalválasztás újra jóvá lesz, és a forgalom ismét át tud haladni az alternatív úton.

A laborban FRR-t (Free Range Routing) használunk BGP daemonként, network namespace-eket eszköziportunkénti izolációra, Linux bridget VXLAN-összekötésre.

33.5.3 Laborterv és topológia

A labhost labvm01, UID root (a módosító parancsok előfeltétele). A dedicated labobjektumok mind lab- előtaggal készülnek; cleanup csak ezekre terjed ki.

Namespace Szerep Loopback/overlay
lab-spine1 spine, AS 65000 –
lab-spine2 spine, AS 65000 –
lab-leaf1 leaf, AS 65010 10.255.0.1/32 VTEP
lab-leaf2 leaf, AS 65020 10.255.0.2/32 VTEP

Underlay linkek /31 pont-pont alhálózatokkal:

Link leaf IP spine IP
lab-le1-sp1 ↔︎ lab-sp1-le1 10.0.0.0/31 10.0.0.1/31
lab-le1-sp2 ↔︎ lab-sp2-le1 10.0.1.0/31 10.0.1.1/31
lab-le2-sp1 ↔︎ lab-sp1-le2 10.0.2.0/31 10.0.2.1/31
lab-le2-sp2 ↔︎ lab-sp2-le2 10.0.3.0/31 10.0.3.1/31

Az alábbi ábra a két táblázatot egy képben mutatja: az underlay /31-es linkeket, a VTEP-ek közötti overlay-alagutat, a leaf1 uplinkjén látható fejléceket, valamint a lab-le2-sp1 kiesése utáni új utat.

A leaf-eken lab-br0 bridge, alá lab-vxlan0 VXLAN interface kerül. A hostok lab-h1 és lab-h2 egy-egy veth párral csatlakoznak a bridge-hez. Az overlay MTU 1450 byte, mert az underlay MTU 1500, és a VXLAN overhead tipikusan 50 byte. A VXLAN-encapsulált frame 1500 + 50 = 1550 byte lenne, ezért a belső hálózatnak kisebb MTU-t adunk.

33.5.4 Kidolgozott példa: namespace/VXLAN/bridge setup és FRR konfiguráció

A következő script a topológia teljes hálózati rétegét létrehozza (mind a hat namespace, mind a négy underlay link, mindkét VTEP és mindkét host), éles adatot nem érint. A scriptet ebben a munkamenetben nem futtattuk; a sikeres és a hibás laborágat a labhoston kell igazolni, dátumozott futtatási napló még nincs. A tranzit spine-oknak IP-csomagot kell továbbítaniuk: az új hálózati névtér az IPv4-beállításokat a host alapértékeiből örökli (net.core.devconf_inherit_init_net=0 mellett), egy alap Ubuntu-hoston tehát net.ipv4.ip_forward=0, ezért a spine-okon explicit bekapcsoljuk. Enélkül a BGP-session él és a route-ok megvannak, de a VTEP-forgalom a spine-on elvész.

#!/usr/bin/env bash
set -euo pipefail
# Labhost: labvm01, UID: root, disposable lab-only objektumok.
NS="lab-spine1 lab-spine2 lab-leaf1 lab-leaf2 lab-h1 lab-h2"
for ns in $NS; do ip netns add "$ns"; done

# leaf1 uplinkek
ip link add lab-le1-sp1 type veth peer name lab-sp1-le1
ip link add lab-le1-sp2 type veth peer name lab-sp2-le1
ip link set lab-le1-sp1 netns lab-leaf1
ip link set lab-le1-sp2 netns lab-leaf1
ip link set lab-sp1-le1 netns lab-spine1
ip link set lab-sp2-le1 netns lab-spine2

# leaf2 uplinkek
ip link add lab-le2-sp1 type veth peer name lab-sp1-le2
ip link add lab-le2-sp2 type veth peer name lab-sp2-le2
ip link set lab-le2-sp1 netns lab-leaf2
ip link set lab-le2-sp2 netns lab-leaf2
ip link set lab-sp1-le2 netns lab-spine1
ip link set lab-sp2-le2 netns lab-spine2

# host veth-ek
ip link add lab-h1-veth type veth peer name lab-leaf1-h1
ip link add lab-h2-veth type veth peer name lab-leaf2-h2
ip link set lab-h1-veth netns lab-h1
ip link set lab-h2-veth netns lab-h2
ip link set lab-leaf1-h1 netns lab-leaf1
ip link set lab-leaf2-h2 netns lab-leaf2

# IP-címek, underlay
ip netns exec lab-leaf1 ip addr add 10.0.0.0/31 dev lab-le1-sp1
ip netns exec lab-spine1 ip addr add 10.0.0.1/31 dev lab-sp1-le1
ip netns exec lab-leaf1 ip addr add 10.0.1.0/31 dev lab-le1-sp2
ip netns exec lab-spine2 ip addr add 10.0.1.1/31 dev lab-sp2-le1
ip netns exec lab-leaf2 ip addr add 10.0.2.0/31 dev lab-le2-sp1
ip netns exec lab-spine1 ip addr add 10.0.2.1/31 dev lab-sp1-le2
ip netns exec lab-leaf2 ip addr add 10.0.3.0/31 dev lab-le2-sp2
ip netns exec lab-spine2 ip addr add 10.0.3.1/31 dev lab-sp2-le2

# linkek up
for ns in $NS; do ip netns exec "$ns" ip link set lo up; done
ip netns exec lab-leaf1 ip link set lab-le1-sp1 up
ip netns exec lab-leaf1 ip link set lab-le1-sp2 up
ip netns exec lab-leaf2 ip link set lab-le2-sp1 up
ip netns exec lab-leaf2 ip link set lab-le2-sp2 up
ip netns exec lab-spine1 ip link set lab-sp1-le1 up
ip netns exec lab-spine1 ip link set lab-sp1-le2 up
ip netns exec lab-spine2 ip link set lab-sp2-le1 up
ip netns exec lab-spine2 ip link set lab-sp2-le2 up

# a tranzit spine-ok továbbítanak (a netns nem kapcsolja be magától)
for ns in lab-spine1 lab-spine2; do
  ip netns exec "$ns" sysctl -w net.ipv4.ip_forward=1
done

# leaf loopback (VTEP source)
ip netns exec lab-leaf1 ip addr add 10.255.0.1/32 dev lo
ip netns exec lab-leaf2 ip addr add 10.255.0.2/32 dev lo

# bridge, VXLAN, host csatolás mindkét leafen; overlay MTU 1450
for n in 1 2; do
  LEAF="lab-leaf$n"
  LOCAL="10.255.0.$n"
  REMOTE="10.255.0.$((3 - n))"
  ip netns exec "$LEAF" ip link add lab-br0 type bridge
  ip netns exec "$LEAF" ip link add lab-vxlan0 type vxlan id 100 \
    local "$LOCAL" dstport 4789 nolearning
  ip netns exec "$LEAF" ip link set lab-vxlan0 mtu 1450
  ip netns exec "$LEAF" ip link set lab-vxlan0 master lab-br0
  ip netns exec "$LEAF" bridge fdb append 00:00:00:00:00:00 \
    dev lab-vxlan0 dst "$REMOTE"
  ip netns exec "$LEAF" ip link set lab-vxlan0 up
  ip netns exec "$LEAF" ip link set "lab-leaf$n-h$n" mtu 1450
  ip netns exec "$LEAF" ip link set "lab-leaf$n-h$n" master lab-br0
  ip netns exec "$LEAF" ip link set "lab-leaf$n-h$n" up
  ip netns exec "$LEAF" ip link set lab-br0 up
  ip netns exec "lab-h$n" ip link set "lab-h$n-veth" mtu 1450
  ip netns exec "lab-h$n" ip addr add "192.168.100.$n/24" dev "lab-h$n-veth"
  ip netns exec "lab-h$n" ip link set "lab-h$n-veth" up
done

A dev nélkül létrehozott lab-vxlan0 nem tudja levonni az 50 bájtos overheadet egy alsó eszköz MTU-jából, ezért 1500-on maradna; ezt is explicit 1450-re állítjuk, mindkét leafen, és mindkét host veth-jén.

Az FRR mind a négy routerhez saját konfigurációs fájlt kap (/etc/frr/<namespace>/frr.conf). A leaf és a spine között eBGP-session van; az FRR 7.4 óta alapértelmezett bgp ebgp-requires-policy (RFC 8212) miatt in/out policy nélkül az eBGP-szomszéd felé semmi nem hirdetődik és tőle semmi nem fogadódik el (a summary (Policy)-t mutat). A zárt laborban ezt a no bgp ebgp-requires-policy sorral kapcsoljuk ki; éles fabricben helyette prefix-listás route-map kell (például ip prefix-list LAB-VTEP seq 5 permit 10.255.0.0/24 ge 32, és neighbor ... route-map ... in/out). Az ECMP-hez a leafeken maximum-paths 2-t adunk meg. A leaf1 konfigurációja (/etc/frr/lab-leaf1/frr.conf):

hostname lab-leaf1
router bgp 65010
 bgp router-id 10.255.0.1
 no bgp ebgp-requires-policy
 no bgp default ipv4-unicast
 neighbor 10.0.0.1 remote-as 65000
 neighbor 10.0.0.1 timers 1 3
 neighbor 10.0.1.1 remote-as 65000
 neighbor 10.0.1.1 timers 1 3
 address-family ipv4 unicast
  network 10.255.0.1/32
  neighbor 10.0.0.1 activate
  neighbor 10.0.1.1 activate
  maximum-paths 2
 exit-address-family

A leaf2 konfigurációja (/etc/frr/lab-leaf2/frr.conf):

hostname lab-leaf2
router bgp 65020
 bgp router-id 10.255.0.2
 no bgp ebgp-requires-policy
 no bgp default ipv4-unicast
 neighbor 10.0.2.1 remote-as 65000
 neighbor 10.0.2.1 timers 1 3
 neighbor 10.0.3.1 remote-as 65000
 neighbor 10.0.3.1 timers 1 3
 address-family ipv4 unicast
  network 10.255.0.2/32
  neighbor 10.0.2.1 activate
  neighbor 10.0.3.1 activate
  maximum-paths 2
 exit-address-family

A spine1 konfigurációja (/etc/frr/lab-spine1/frr.conf):

hostname lab-spine1
router bgp 65000
 bgp router-id 10.0.0.1
 no bgp ebgp-requires-policy
 no bgp default ipv4-unicast
 neighbor 10.0.0.0 remote-as 65010
 neighbor 10.0.0.0 timers 1 3
 neighbor 10.0.2.0 remote-as 65020
 neighbor 10.0.2.0 timers 1 3
 address-family ipv4 unicast
  neighbor 10.0.0.0 activate
  neighbor 10.0.2.0 activate
 exit-address-family

A spine2 konfigurációja (/etc/frr/lab-spine2/frr.conf):

hostname lab-spine2
router bgp 65000
 bgp router-id 10.0.1.1
 no bgp ebgp-requires-policy
 no bgp default ipv4-unicast
 neighbor 10.0.1.0 remote-as 65010
 neighbor 10.0.1.0 timers 1 3
 neighbor 10.0.3.0 remote-as 65020
 neighbor 10.0.3.0 timers 1 3
 address-family ipv4 unicast
  neighbor 10.0.1.0 activate
  neighbor 10.0.3.0 activate
 exit-address-family

Az ip netns exec csak a hálózati névteret választja el, a fájlrendszert nem: ha a négy zebra/bgpd példány ugyanazzal a pid-fájllal, zserv.api-val és vty-sockettel indulna, a második példány nem indulna el, vagy a másik router daemonjához csatlakozna. Ezért minden routert külön FRR-útvonaltérrel (pathspace, -N) indítunk; ez a futásidejű és a konfigurációs útvonalakba is beilleszti a nevet. A d162-ben esetleg elindított host-szintű frr.service-t előbb le kell állítani (systemctl stop frr), hogy ne ütközzön:

for r in lab-leaf1 lab-leaf2 lab-spine1 lab-spine2; do
  install -d -o frr -g frr "/etc/frr/$r"   # ide kerül a fenti frr.conf
  ip netns exec "$r" /usr/lib/frr/zebra -d -N "$r"
  ip netns exec "$r" /usr/lib/frr/bgpd -d -N "$r"
  ip netns exec "$r" vtysh -N "$r" -b      # /etc/frr/$r/frr.conf betöltése
done

A -N kapcsoló pontos viselkedését és a daemonútvonalat a telepített FRR-csomag /usr/lib/frr/zebra --help kimenetével kell igazolni, mert a disztribúció verziójától függ (Ubuntu 24.04 LTS: vtysh -c 'show version'). Minden lekérdezés ugyanígy a router pathspace-ét adja meg (vtysh -N lab-leaf2 ...), különben a vtysh nem az adott router állapotát mutatja.

A cleanup csak a lab- objektumokra terjed ki; a namespace törlése a benne lévő veth-eket is megszünteti:

for r in lab-leaf1 lab-leaf2 lab-spine1 lab-spine2; do
  pkill -f -- "-N $r" || true      # az adott pathspace zebra/bgpd példányai
done
for ns in lab-spine1 lab-spine2 lab-leaf1 lab-leaf2 lab-h1 lab-h2; do
  ip netns del "$ns" 2>/dev/null || true
done

Smoke teszt (sikeres ág): ip netns exec lab-h1 ping -c 3 192.168.100.2 és ip netns exec lab-leaf1 ping -c 3 -I 10.255.0.1 10.255.0.2 sikeres. Hibás ág: a lab-br0 alól kivett lab-leaf2-h2 mellett az első ping timeoutol, a második továbbra is sikeres (lásd a 3. feladatot).

33.5.5 Ellenőrzés: underlay, overlay, payload path

Az underlay bizonyítékát a BGP session és a tanult prefixek adják:

ip netns exec lab-leaf2 vtysh -N lab-leaf2 -c 'show bgp ipv4 unicast summary'
ip netns exec lab-leaf2 vtysh -N lab-leaf2 \
  -c 'show bgp ipv4 unicast 10.255.0.1/32'
ip netns exec lab-leaf2 ip route show

Elvárt kimenet: a 10.255.0.1/32 prefixet lab-leaf2 mindkét spine-on át látja, és a show bgp ... summary mindkét szomszédnál Established állapotú sessiont és a State/PfxRcd oszlopban prefixszámot mutat (nem (Policy)-t).

Az overlay payload path-ja a következő lépésekben ellenőrizhető:

  1. A VTEP-elérhetőség ellenőrzése a VTEP-címről indított pinggel. Forráscím nélkül a kernel a kimenő link címét (10.0.0.0 vagy 10.0.1.0) választaná, ezeket a /31 linkhálózatokat azonban senki nem hirdeti, így a leaf2-nek nincs útja vissza, és a ping hamisan underlay-hibát mutatna.
  2. h1 és h2 közötti ping a belső hálózaton.
  3. Capture a leaf1 mindkét uplinkjén, hogy a VXLAN UDP 4789 forgalom látszik. L3 hash mellett (fib_multipath_hash_policy=0) a VTEP-ek közötti forgalom egyetlen külső IP-párt használ, ezért egyetlen uplinken megy; hogy melyiken, azt az ip route get mutatja meg.
  4. A bridge FDB entry ellenőrzése.
ip netns exec lab-leaf1 ping -c 3 -I 10.255.0.1 10.255.0.2
ip netns exec lab-leaf1 bridge fdb show dev lab-vxlan0
ip netns exec lab-leaf1 ip route get 10.255.0.2 from 10.255.0.1
ip netns exec lab-leaf1 tcpdump -ni any -c 5 'udp port 4789' &
ip netns exec lab-h1 ping -c 3 192.168.100.2

A VTEP-ping sikeres, a bridge fdb kimenetében látszik a dst 10.255.0.2, a belső ping sikeres, a tcpdump pedig az ip route get által mutatott uplinken encapsulált VXLAN-csomagot mutat.

Az MTU ellenőrzése DF beállítással, mindkét irányból (egy egyoldalú hiba csak az egyik irányban látszik):

ip netns exec lab-h1 ping -M do -s 1422 -c 3 192.168.100.2
ip netns exec lab-h2 ping -M do -s 1422 -c 3 192.168.100.1

A payload 1422 byte; az ICMP 8 plusz IP 20 headerrel együtt 1450 byte, ami a beállított belső MTU-nak felel meg. Ha a ping „message too long” hibát ad, a küldő oldali belső MTU kisebb a vártnál; a nagyobb (-s 1423) próbának ugyanezzel a hibával kell elbuknia.

33.5.6 Single link/node failure és konvergenciamérés

A failure fixture egyetlen link leállítása. A lab-leaf2 és lab-spine1 közötti linket kapcsoljuk le, így a lab-leaf2 VTEP loopbackjéhez vezető underlay útnak át kell térnie lab-spine2-n keresztül.

A mérést időbélyegzett pinggel végezzük:

ip netns exec lab-leaf1 ip route get 10.255.0.2 from 10.255.0.1  # aktív út
ip netns exec lab-h1 ping -D -i 0.2 192.168.100.2 > /tmp/lab-ping.log &
PING_PID=$!
sleep 2
ip netns exec lab-leaf2 ip link set lab-le2-sp1 down
sleep 8
kill "$PING_PID"
grep -E '^\[[0-9]' /tmp/lab-ping.log

A ping -D az EPOCH időbélyeget adja. A hibainjekció előtt minden csomagnak 64 bytes válasza van. Kiesés csak akkor látható, ha a VTEP-forgalom a hibainjekció előtt a spine1-en haladt: L3 hash mellett minden csomag ugyanazon a spine-on megy, és ha az a spine2, a mérés nem mutat kiesést. Az előzetes ip route get ezért rögzíti, melyik út aktív; ha a spine2, a spine2 oldali linket (lab-le2-sp2) kell leállítani.

A linkdown helyi interfészesemény: a leaf2 zebra azonnal látja, az FRR (alapértelmezett fast-external-failover) azonnal bontja a közvetlenül kapcsolt eBGP-sessiont, a veth-peer carriert veszít, így a spine1 is azonnal bont. A kiesést ezért nem a 3 s-os hold timer, hanem a withdraw terjedése és a FIB-frissítés ideje határozza meg. Hipotetikus, illusztratív laboradat (nem mért):

idősor [s] válasz megjegyzés
0.0–2.0 success kiinduló állapot, a spine1-es út aktív
2.2 timeout interface-down → azonnali session-bontás és withdraw
2.4 success alternatív path aktív, VXLAN folyam újra megy

A konvergenciát a linkdown pillanata és az első sikeres válasz között számítjuk; ez a hipotetikus példában néhány száz ms, a 0,2 s-os pingintervallum felbontásán belül. A hold timer (1 s keepalive, 3 s hold) csak olyan hibánál számít, amely nem okoz linkeseményt: ennek méréséhez a spine1-en például nft-szabállyal kell eldobni a 179-es TCP-port forgalmát, így a link fent marad, de a session a hold timer lejártakor bomlik. Ha a konvergencia az elvártnál lassabb, gyorsabb timert vagy BFD-t kell alkalmazni.

A route bizonyítékot a linkdown után:

ip netns exec lab-leaf1 vtysh -N lab-leaf1 \
  -c 'show bgp ipv4 unicast 10.255.0.2/32'
ip netns exec lab-leaf1 ip route get 10.255.0.2 from 10.255.0.1

A kimenet azt mutatja, hogy a következő hop 10.0.1.1 (spine2) lett.

33.5.7 Gyakori hibák és ellenszer

  1. Overlay timeout, de underlay OK. A VTEP loopback ping lab-leaf1 → 10.255.0.2 (ping -I 10.255.0.1 10.255.0.2) sikeres, de a belső ping mégsem megy. Ilyenkor a VXLAN bridge-FDB entry hiányos vagy a host veth nincs a bridge-ben. Ellenőrzés: bridge fdb show és bridge link show. Fix: a 00:00:00:00:00:00 flood entry beírása.

  2. MTU mismatch. A belső interfészek (gyakran csak az egyik leaf oldalán) 1500 MTU-val maradtak. A Linux VXLAN alapból nem állít DF-et a külső fejlécre (df unset), ezért a túl nagy keret fragmentálva átmegy, ami teljesítményt és megbízhatóságot ront; df set mellett viszont eldobódik, és a nagy csomagok nem mennek át, a kicsik igen. Ellenőrzés: ping -M do -s 1422 mindkét hostról. Fix: a lab-vxlan0, a leaf-oldali és a host veth MTU 1450-re állítása mindkét oldalon.

  3. Nem konvergáló BGP route. A linkdown után a backup path nem jelenik meg; a BGP session nem Established. Oka lehet rossz AS, rossz neighbor IP, vagy hiányzó network hirdetés. Ellenőrzés: show bgp ipv4 unicast summary. Fix: a config javítása, majd a BGP session restartja.

  4. Stale FDB entry. Ha a VXLAN data plane learning korábbi bejegyzéseket hagy hátra, a bridge fdb régi dst-t mutat. Megoldás: statikus flood entry használata, és bridge fdb delete a régi entry törlésére.

  5. Túl lassú konvergencia. A default BGP hold timer 180 s. Ez a labban elfogadhatatlan. Explicit neighbor ... timers 1 3 vagy BFD szükséges. A rollbacknél a szándékos gyorsítás után a configot vissza kell állítani a defaultokra, ha a lab célja a viselkedés bemutatása.

33.5.8 Feladatok

  1. Magyarázó feladat. A fenti topológiában azonosítsd be egy h1 → h2 ping adatútján a következő rétegeket: belső Ethernet frame, VNI 100, outer IP 10.255.0.1 → 10.255.0.2, UDP 4789, underlay útválasztás. Listázd, hogy a leaf1 bridge, vxlan0, spine1, spine2 és leaf2 bridge melyik réteghez tartozik.

  2. Adminisztrációs/konfigurációs feladat. Építsd fel a topológiát, állítsd be a FRR BGP timereket 1 3 értékkel. Injektálj single link failure-t a lab-le2-sp1 leállításával. Mérd a konvergenciát időbélyegzett pinggel, és utána állítsd vissza a linket. A mérés után készíts rollbacket a BGP timer default értékekre (pl. a timers sor eltávolításával) és igazold, hogy a session továbbra is Established.

  3. Diagnosztikai/failure/recovery feladat. Szimuláld a hibát: h1 ping h2 irányába timeout, miközben a VTEP loopback ping (ip netns exec lab-leaf1 ping -I 10.255.0.1 10.255.0.2) sikeres. A leaf2 bridge lab-br0 alól törölj egy bridge fdb entry-t vagy töröld a host veth master kapcsolatát. Helyezd vissza, és tcpdump/capture segítségével bizonyítsd, hogy a hiba az overlay layer-ben volt, nem az underlayben.

33.5.9 Megoldások

  1. A payload path rétegei:

    • belső Ethernet frame: overlay L2 a h1 és h2 között;
    • VNI 100: overlay tenant azonosító a VXLAN fejlécben;
    • outer IP 10.255.0.1 → 10.255.0.2: underlay transport, a VTEP loopbackek;
    • UDP 4789: VXLAN dest port, underlay transport;
    • underlay útválasztás: BGP-learned route a spine-okon.
      A leaf1 lab-br0 és vxlan0 az overlay bridge- és VTEP-side részei; a spine-ok az underlay forwardingot végzik; leaf2 lab-br0 a h1 → h2 irányban az overlay kilépési (decap) oldala.

  2. A konvergenciamérés lépései a fenti kódban. A BGP timer explicit neighbor ... timers 1 3 sorokat tartalmazó configgal. A linkdown után a ping rövid kiesést mutat, majd a backup path átveszi a forgalmat. A rollback a timers sorok törlése és a BGP session újraindítása; a postcondition vtysh -N lab-leaf2 -c 'show bgp ipv4 unicast summary' Established session, és a show ip route továbbra is mindkét VTEP loopbacket tartalmazza.

  3. A diagnosztika: a sikeres VTEP ping bizonyítja az underlayt, a belső ping timeout az overlay hibájára utal. A leaf2 bridge bridge link show kimenetében a host veth nem szerepel masterként. A helyreállítás ip link set lab-leaf2-h2 master lab-br0. A leaf2 uplinkjén (tcpdump -ni lab-le2-sp2 udp port 4789, illetve az aktív uplinken) beérkezik a VXLAN-csomag, a lab-vxlan0-on (tcpdump -ni lab-vxlan0 icmp) látszik a kicsomagolt belső ICMP, de a lab-leaf2-h2 porton nem. Postcondition: h1 ping h2 sikeres, a bridge link show mutatja a host veth-et master alatt.

33.5.10 Rövid összefoglaló

Az alfejezet a VXLAN overlay és BGP underlay együttes diagnosztikáját tanítja. A labor FRR/namespace topológiával, VXLAN bridge- és MTU-konfigurációval, valamint single link failure fixture segítségével méri a control-plane konvergenciát. A rétegzett ellenőrzés sorrendben: underlay route/bgp evidence, overlay bridge/FDB, payload path capture. Továbbhasznált definíciók: underlay – a tényleges IP transport és útválasztási réteg; VXLAN – UDP 4789 feletti L2 encapsulation VNI azonosítóval; konvergencia – az idő a hiba bekövetkezése és a helyreállt forgalomátvitel között.

33.5.11 Források és ellenőrzési hiányok

  • RFC 7348 – VXLAN: 5. szakasz (VXLAN-keretformátum, UDP 4789, VNI) – a külső fejléc és az 50 bájtos overhead alapja.
  • RFC 4271 – BGP-4: 4.4 (KEEPALIVE), 6.5 (Hold Timer expiry) – a hold timer szerepe a konvergenciában.
  • RFC 8212 – Default EBGP Route Propagation Behavior without Policies: az FRR bgp ebgp-requires-policy alapértékének háttere.
  • Linux kernel – VXLAN: ip link add ... type vxlan, statikus FDB-bejegyzés.
  • ip-link(8): a vxlan típus local, dstport, nolearning, df paraméterei; Ubuntu 24.04 LTS iproute2-csomag.
  • FRRouting – BGP: bgp ebgp-requires-policy, timers, maximum-paths, network; a „latest” dokumentáció nem automatikusan az Ubuntu 24.04 LTS frr csomagjának verziója, a laborban vtysh -c 'show version' rögzítendő.
  • FRRouting – alapvető daemonkapcsolók: a -N/pathspace és a vtysh -b működése.

A példák laborban ellenőrizendők; ebben a munkamenetben nem történt laborfuttatás, dátumozott futtatási napló még nincs. Az FRR daemon pontos verzióját, a -N kapcsoló viselkedését és az Ubuntu 24.04 LTS csomagelérési útját a labhoston kell verifikálni (/usr/lib/frr/zebra --help, dpkg -s frr).
