38.5 Container/Compose működtetési labor

38.5.1 Motiváció

A d189 Compose-mintái (healthcheck, secret, named volume, profil) alapján itt egy önálló, a laborhoz előkészített stack (C++ service, proxy és persistens adat) lesz élesítési gyakorlat alanya. A fejlesztő gyakran csak annyit lát, hogy a container „rossz”, de a javítás akkor lesz gyors és biztonságos, ha a hibát a megfelelő réteghez rendeli: image (tartalom, digest, config), runtime (engine/daemon, containment), host (kernel, cgroup, filesystem) vagy network (bridge, DNS, port). A másik gyakori kudarc: a docker compose down -v törli a named volume-ot, ezért a fejlesztői adat elveszik. A labor célja, hogy ezt a két kockázatot egy data-safe lifecycle keretben gyakoroljuk.

38.5.2 Definíció és működés

Containerhiba rétegelése. A konténeres rendszerben a hívás útja az image-ből indított processzen, a runtime által alkalmazott cgroup/namespace-eken, a host kernel erőforrásain és a hálózati stacken át vezet. A hiba diagnosztizálásánál az első kérdés: melyik réteg tünete a hiba?
- Image/config hiba: a konténer nem indul el, hiányzó fájl, rossz belépési pont vagy rossz environment. Ellenőrzés: docker inspect, docker logs, image history, compose config.
- Runtime hiba: az engine/daemon nem érhető el, vagy a konténer létrehozása után azonnal meghal. Ellenőrzés: docker info, systemctl status docker, docker events.
- Host hiba: a hoston elfogy a lemez, inode, PID, memória, vagy a kernel OOM killer leállítja a processzt. Ellenőrzés: df -h, dmesg, /proc/sys/fs/file-nr, host metrikák.
- Network hiba: a konténer nem éri el a nevet, a portot vagy a külvilágot. Ellenőrzés: docker network inspect, getent hosts, ss -tlnp, curl a bridge IP-címre.

Digest és config-based deployment. A tag helyett digestre pinelés azt jelenti, hogy a compose.yaml-ben az image azonosítója registry/name@sha256:... alakú. Így a pull során pontosan ugyanaz a content kerül minden környezetbe; a tag mozgó célpont. A config verziót gitben tároljuk, a secretet és environmentet nem a képbe sütjük: a nem titkos konfigurációt (például a digesteket) .env-ből, a titkot a d189 mintája szerint secrets fájlként adjuk át (a jelszó environment-ben a docker inspect kimenetéből kiolvasható volna). A laborban a docker compose config az ellenőrző parancs, mielőtt bármit indítanánk.

Data-safe rebuild és rollback. A docker compose down alapértelmezésben nem törli a named volume-ot. A down -v viszont törli. Data-safe eljárás: mielőtt bármilyen destruktív műveletet végzünk, készítsünk docker volume inspect-et a volume leltárhoz, majd a művelet után smoke testtel bizonyítjuk az adatmegmaradást. A rebuild a down + up -d pár, ahol a volume a régi konténerből az újba költözik. Rollback esetén az image visszacserélése a config-gitből történhet, a volume-ot nem bántjuk.

Memórialimit és OOM-kill (nem throttling). A Compose-ban a mem_limit (Compose v2: deploy.resources.limits.memory is) a konténer cgroup memória limitjét állítja. Amikor a konténer processze átlépi, a kernel OOM killer leöli (SIGKILL, ExitCode=137). Ez nem throttling: throttlingról a CPU-korlátnál (cpus, cgroup cpu.max) beszélünk, ott a processz lassul, de nem hal meg. A restart: unless-stopped az OOM-kill után néhány száz ms-on belül újraindítja a konténert; ekkor a Docker a State blokkot az új futásra állítja, így a State.OOMKilled jelző false-ra áll vissza (a RestartCount megmarad). Az OOM bizonyítéka ezért a docker events oom és die eseménye, valamint a kernel log; a konténer saját stdoutjában nem lehet nyom, mert a processz nem kap lehetőséget írni.

Log/FD/mount inspect. A konténer megfigyeléséhez a docker logs (vagy podman logs) az alkalmazásnaplót, a docker inspect a mountokat, a PID-ből a /proc alrendszer az FD-ket és limiteket mutatja. Compose alatt a konténer neve <projekt>-<service>-<sorszám> alakú (itt lab-stack-lab-app-1), ezért a konténerre a docker compose ps -q <service> által adott ID-val hivatkozunk. Példa: cid=$(docker compose ps -q lab-app), pid=$(docker inspect --format '{{.State.Pid}}' "$cid"), majd ls -l /proc/$pid/fd. A mountokhoz: docker inspect --format '{{json .Mounts}}' "$cid".

38.5.3 Kidolgozott példa

Előfeltételek és jogosultsági modell. A labhost a 38. fejezet kanonikus labhostja, lab-vm1 (Ubuntu 24.04 LTS, rootful Docker Engine és Docker Compose v2), a felhasználó labuser (UID 1000). A d186 szerint a docker csoport tagsága hostszintű root jogosultsággal egyenértékű; ebben a laborban kivételesen és tudatosan egy eldobható labor-VM-en a labuser a docker csoport tagja, hogy a parancsok olvashatók maradjanak. Élesben ez tilos: ott sudo docker vagy rootless Podman a helyes választás. A projekt könyvtára /home/labuser/lab-compose, a Compose-projekt neve lab-stack; a stack független a d189 lab-cpp-stack projektjétől.

A labor három image-e:

Service Image Eredet
lab-db docker.io/library/postgres:16@${DB_DIGEST} hivatalos image, digestre pinelve
lab-app registry.lab.example:5000/lab-app@${APP_DIGEST} a laborcsomag lab-app/ könyvtárából buildelt C++ szolgáltatás (a d185 Ubuntu 24.04 alapú multi-stage mintája szerint, USER 1000:1000, a /data könyvtár chown 1000:1000-rel), a d183 labregistrybe pusholva
lab-proxy docker.io/library/nginx:1.27-alpine@${PROXY_DIGEST} hivatalos image, a lenti proxy/default.conf konfigurációval

A lab-app HTTP-szolgáltatás a 8080-as porton, három, kizárólag laborcélú végponttal: GET /health → {"status":"ok"}; POST /allocate?size_mb=N → N MiB memóriát foglal és érint (az OOM-demóhoz); GET /leak-fd?count=N → N socketet nyit és szándékosan nem zár be (az FD-demóhoz).

A proxy konfigurációja (proxy/default.conf):

upstream lab_app {
    server lab-app:8080;
}
server {
    listen 80;
    location / {
        proxy_pass http://lab_app;
    }
}

  1. Digest lekérése és config előkészítése.

    # host=lab-vm1; user=labuser
cd /home/labuser/lab-compose
docker pull registry.lab.example:5000/lab-app:dev
docker image inspect registry.lab.example:5000/lab-app:dev \
  --format '{{.RepoDigests}}'

    Várt kimenet: [registry.lab.example:5000/lab-app@sha256:0123...] (a pontos digest a laborban eltér). A postgres:16 és az nginx:1.27-alpine digestjét ugyanígy kérjük le. A digesteket az .env fájlba írjuk (DB_DIGEST=sha256:..., APP_DIGEST=sha256:..., PROXY_DIGEST=sha256:...), a jelszót pedig secret-fájlba:

    mkdir -p secrets
umask 077
printf '%s' 'lab-dummy-password' > secrets/db_password.txt

    A fájl tulajdonosa a labuser (UID 1000), módja 0600; rootful Docker alatt a bind mountként csatolt secret ezt a tulajdont tartja meg, így a rootként olvasó PostgreSQL entrypoint és az 1000-es UID-dal futó lab-app is olvashatja.

services:
  lab-db:
    image: docker.io/library/postgres:16@${DB_DIGEST}
    environment:
      POSTGRES_USER: lab
      POSTGRES_DB: labdb
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U lab -d labdb"]
      interval: 5s
      retries: 12
    volumes:
      - lab-db-data:/var/lib/postgresql/data
    networks:
      - lab-net
    mem_limit: 512m
    restart: unless-stopped
  lab-app:
    image: registry.lab.example:5000/lab-app@${APP_DIGEST}
    user: "1000:1000"
    environment:
      DB_HOST: lab-db
      DB_PORT: 5432
      DB_USER: lab
      DB_PASSWORD_FILE: /run/secrets/db_password
      DB_NAME: labdb
    secrets:
      - db_password
    volumes:
      - lab-app-data:/data
    networks:
      - lab-net
    mem_limit: 256m
    restart: unless-stopped
    depends_on:
      lab-db:
        condition: service_healthy
  lab-proxy:
    image: docker.io/library/nginx:1.27-alpine@${PROXY_DIGEST}
    volumes:
      - ./proxy/default.conf:/etc/nginx/conf.d/default.conf:ro
    ports:
      - "127.0.0.1:8081:80"
    networks:
      - lab-net
    mem_limit: 128m
    restart: unless-stopped
    depends_on:
      - lab-app
secrets:
  db_password:
    file: ./secrets/db_password.txt

  lab-net:

  lab-db-data:
  lab-app-data:

    Az .env csak a digesteket tárolja, a jelszó a secret-fájlban van. A docker compose config --quiet ellenőrzi az interpolációt. A name: lab-stack miatt a Compose az objektumokat lab-stack_lab-net (hálózat), lab-stack_lab-db-data és lab-stack_lab-app-data (volume), valamint lab-stack-lab-app-1 stb. (konténer) néven hozza létre; a parancsokban ezért a docker compose ps -q <service> ID-jét használjuk.

  2. Indítás és egészségellenőrzés.

    docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
curl -s http://127.0.0.1:8081/health

    Várt kimenet (szemléltető): a lab-app, lab-proxy és lab-db Up (a lab-db healthy), a health válasz {"status":"ok"}.

  3. Network/DNS/port ellenőrzés.

    docker compose exec lab-app getent hosts lab-db
docker network inspect lab-stack_lab-net \
  --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{"\n"}}{{end}}'
sudo ss -ltnp | grep 8081

    A lab-db nevet a hálózat feloldja. A 8081-es porton az alapértelmezett "userland-proxy": true mellett a docker-proxy hallgat; kikapcsolt userland proxy mellett nincs listener, a leképezést a DNAT adja (d188).

  4. Volume permission teszt.

    docker compose exec lab-app \
  sh -c 'id -u; ls -ldn /data; touch /data/test && echo OK'

    Várt kimenet: 1000, a /data sorában 1000 1000 tulajdon, majd OK. A lab-app rootful Docker alatt nem root (UID 1000) felhasználóként fut; az új, üres lab-stack_lab-app-data named volume az első csatoláskor az image /data könyvtárának tulajdonosát örökli. Ha az image ezt nem állítaná be, a volume root:root tulajdonú lenne, és a touch Permission denied hibát adna.

  5. OOM és restart demonstrálása.
    Állítsuk a lab-app mem_limit értékét 64 MiB-ra a compose fájlban, majd hozzuk létre újra a konténert:

    docker compose up -d lab-app
cid=$(docker compose ps -q lab-app)
curl -s -X POST 'http://127.0.0.1:8081/allocate?size_mb=128'
sleep 2
docker events --since 1m --until "$(date +%s)" \
  --filter container="$cid" --filter event=oom --filter event=die \
  --format '{{.Time}} {{.Action}} {{.Actor.Attributes.exitCode}}'
docker inspect "$cid" --format '{{.RestartCount}}'
sudo journalctl -k --since '-2min' | grep -i 'oom-kill'

    Várt kimenet (szemléltető): egy oom, majd egy die sor 137-es exit kóddal; a RestartCount legalább 1; a kernel logban oom-kill sor. A docker inspect ... {{.State.OOMKilled}} itt jellemzően már false, mert a restart után a State az új futást írja le. Ha az OOMKilled=true jelzőt is látni akarjuk, a demóhoz ideiglenesen restart: "no" kell (ekkor true és ExitCode=137). A túl alacsony limit visszaállítása után a szolgáltatás stabil.

  6. Data-safe down/up.

    docker compose exec lab-db psql -U lab -d labdb -c \
  "CREATE TABLE IF NOT EXISTS counter(n int);
   INSERT INTO counter VALUES (42);"
docker compose down
docker volume ls --filter name=lab-stack_lab-db-data
docker compose up -d
docker compose exec lab-db psql -U lab -d labdb -c "SELECT * FROM counter;"

    Várt kimenet: a down után a volume létezik, a SELECT visszaadja a 42 értéket. Ez a data-safe recreate.

  7. Log/FD/mount inspect.

    cid=$(docker compose ps -q lab-app)
pid=$(docker inspect --format '{{.State.Pid}}' "$cid")
sudo ls -l "/proc/$pid/fd" | tail -n 5
sudo grep 'Max open files' "/proc/$pid/limits"
docker inspect "$cid" --format '{{json .Mounts}}' | jq .

    A FD-lista az alkalmazás által nyitott socketeket és fájlokat mutatja; a Max open files tipikusan 1024 vagy több, de a ulimits a compose-ban módosítható.

  8. Runtime inventory és cleanup.

    # inventory
docker system df -v
docker compose ps
docker network ls --filter name=lab-stack_lab-net
docker volume ls --filter name=lab-stack_
# nem destruktív cleanup: konténerek és projekthálózat törlése,
# a named volume-ok megmaradnak
docker compose down

    A volume törlése destruktív, ezért külön, csak explicit döntésre futtatható blokk, és előtte ellenőrzött backup kell:

    # DESTRUKTÍV: csak ellenőrzött backup után!
mkdir -p backup
docker run --rm -v lab-stack_lab-db-data:/src:ro \
  -v "$PWD/backup":/dst alpine:3.20 \
  tar -C /src -czf "/dst/lab-db-data-$(date +%F).tgz" .
tar -tzf backup/lab-db-data-*.tgz | head
# a backup listázható és nem üres -> csak ezután:
docker volume rm lab-stack_lab-db-data lab-stack_lab-app-data

    A fájlszintű tarball a leállított adatbázis volume-járól konzisztens; futó adatbázisnál a d096–d100 logikai backupja (pg_dump) és a restore-próba a helyes út.

38.5.4 Hibák és ellenpróbák

Image pull manifest unknown. Tünet: docker compose pull hibaüzenete szerint a digest nem létezik. Ok: a registry-ben nincs ilyen digest, vagy a docker pull régi cache-t használ. Ellenpróba: docker manifest inspect registry.lab.example:5000/lab-app@${APP_DIGEST}; ha a manifest hiányzik, a digest elgépelt vagy a push nem sikerült. Javítás: a CI push után újra lekérni a digestet, és a compose fájlt frissíteni.

DNS feloldás sikertelen a lab-db névre. Tünet: a lab-app logjában connection refused vagy could not translate host name. Ellenpróba: docker compose exec lab-app getent hosts lab-db; ha nincs kimenet, a konténerek nem ugyanazon a user-defined networkön vannak. Javítás: a networks szekció minden szolgáltatásnál azonos legyen, vagy a szolgáltatásnevek egyedi DNS-nevek.

Permission denied a volume mountnál. Tünet: a konténer nem tud írni a /data kötetbe. Ok: a hoston a named volume alapból root:root tulajdonú, a konténer processze nem root (pl. USER 1000). Ellenpróba: docker compose exec lab-app sh -c 'id -u; ls -ldn /data'. Javítás: a Dockerfile-ban RUN mkdir -p /data && chown 1000:1000 /data (és USER 1000:1000), majd – mivel a Docker csak üres volume-ot tölt fel az image-ből – a már root tulajdonnal létrejött volume újralétrehozása (adatmentés után); a compose user: "1000:1000" önmagában a tulajdont nem javítja. Rootless Podman esetén a subuid-leképezést is figyelembe kell venni (d188).

OOM-killed és restart loop. Tünet: a konténer RestartCount növekszik, minden indítás után meghal. Ellenpróba: docker events --since 10m --until "$(date +%s)" --filter container="$(docker compose ps -q lab-app)" --filter event=oom; ha van oom esemény (a restart miatt az OOMKilled jelző már false lehet), a memória limit túl alacsony. Javítás: a mem_limit emelése, vagy a C++ service memóriahasználatának csökkentése. A restart: on-failure explicit max próbálkozással megakadályozza a végtelen ciklust.

Adatvesztés a down -v miatt. Tünet: a down -v után a volume eltűnt. Ellenpróba: docker volume ls --filter name=lab-stack_lab-db-data. Javítás: a d100-ban tanult backupból restore, vagy a labouról készített docker volume export. A megelőzés: soha ne futtassuk a down -v-t mielőtt a backup megerősített.

Port ütközés. Tünet: docker compose up hiba bind: address already in use. Ellenpróba: ss -ltnp | grep 8081. Javítás: a hostport megváltoztatása a compose ports mezőben, vagy a másik processz leállítása.

38.5.5 Feladatok

  1. Réteghez rendelés (magyarázó). Adott négy hibatünet a labor stacken:

    1. docker compose up hiba Cannot connect to the Docker daemon;
    2. a lab-app konténer OOMKilled=true;
    3. curl http://127.0.0.1:8081/health 502 Bad Gateway;
    4. a lab-proxy nem indul, mert a config fájlban hiányzik az upstream lab-app sor.
      Rendelje mindegyiket a megfelelő réteghez (image/config, runtime, host, network), és adja meg az első diagnosztikai parancsot.

  2. Digest-pinelt deployment és OOM (adminisztrációs). Kérje le a lab-app digestjét a lokális registryből, írja be az .env fájlba, indítsa el a stacket, majd állítsa a lab-app memóriakorlátját 64 MiB-ra, és a POST /allocate?size_mb=128 kéréssel igazolja az OOM-killt (eseménynaplóval). Végül állítsa vissza a 256 MiB korlátot, és ellenőrizze a stabilitást curl segítségével.

  3. Data-safe rebuild és FD diagnosztika (diagnosztikai/recovery). Végezzen el egy beszúrást a counter táblába, futtasson docker compose down parancsot, majd up -d-t, és SELECT-tel bizonyítsa, hogy az adat megmaradt. Ezután szimuláljon fájlleíró-szivárgást a lab-app-ben (pl. nyisson meg 100 socketet, de ne zárja be), az ls -l /proc/$pid/fd segítségével mutassa meg a megnövekedett FD-számot, majd állítsa vissza a szolgáltatást a korábbi image digestre, és igazolja, hogy a rollback megtörtént, és a korábbi verzió ugyanarra a terhelésre nem szivárog.

38.5.6 Megoldások

1. feladat
a) Runtime réteg: a Docker daemon nem fut. Első parancs: systemctl status docker.
b) Host/kernel (cgroup) réteg: a memória limit túl alacsony. Első parancs: docker events --since 10m --until "$(date +%s)" --filter container="$(docker compose ps -q lab-app)" --filter event=oom, illetve docker inspect "$(docker compose ps -q lab-app)" --format '{{.State.OOMKilled}} {{.RestartCount}}'.
c) Network/application réteg: a proxy eléri a portot, de a backend nem egészséges. Első parancs: docker compose ps, docker compose logs lab-proxy, majd docker compose exec lab-app ss -ltn.
d) Image/config réteg: a proxy konfigja hibás. Első parancs: docker compose config, majd docker compose logs lab-proxy.

2. feladat
Parancsok:

# host=lab-vm1; user=labuser; cwd=/home/labuser/lab-compose
docker pull registry.lab.example:5000/lab-app:dev
docker image inspect registry.lab.example:5000/lab-app:dev \
  --format '{{.RepoDigests}}'
# A kapott digestet beírjuk .env: APP_DIGEST=sha256:...
docker compose up -d
# mem_limit csökkentés a compose.yaml-ben 64m-re, majd:
docker compose up -d lab-app
cid=$(docker compose ps -q lab-app)
curl -s -X POST 'http://127.0.0.1:8081/allocate?size_mb=128'
sleep 2
docker events --since 1m --until "$(date +%s)" \
  --filter container="$cid" --filter event=oom --filter event=die \
  --format '{{.Action}} {{.Actor.Attributes.exitCode}}'
# Várt: "oom", majd "die 137"
docker inspect "$cid" --format '{{.RestartCount}}'
# Várt: >= 1
# Visszaállítás 256m-re, up -d, curl /health -> {"status":"ok"}

Postcondition: az oom és a die (exitCode=137) esemény és a RestartCount>=1 bizonyítja a memória-limit miatti OOM-killt (nem throttlingot: az a CPU-korlát jelensége); a visszaállítás után a /health 200-at ad.

3. feladat
Parancsok:

# host=lab-vm1; user=labuser; cwd=/home/labuser/lab-compose
docker compose exec lab-db psql -U lab -d labdb \
  -c "INSERT INTO counter VALUES (7);"
docker compose down
docker volume ls --filter name=lab-stack_lab-db-data
docker compose up -d
docker compose exec lab-db psql -U lab -d labdb -c "SELECT * FROM counter;"
# Várt: a 7-es érték megjelenik.

# FD-szivárgás az új (hibás) digesten: a laborvégpont 100 socketet
# nyit, és nem zárja be
fdcount() {
  local pid
  pid=$(docker inspect --format '{{.State.Pid}}' \
    "$(docker compose ps -q lab-app)")
  sudo ls "/proc/$pid/fd" | wc -l
}
fdcount                                   # kiinduló érték
curl -s 'http://127.0.0.1:8081/leak-fd?count=100'
fdcount                                   # kb. +100

# Rollback: APP_DIGEST a korábbi digestre az .env-ben, majd:
docker compose up -d lab-app
docker inspect "$(docker compose ps -q lab-app)" --format '{{.Image}}'
docker compose images lab-app             # a korábbi digest látszik
fdcount                                   # friss processz
curl -s 'http://127.0.0.1:8081/leak-fd?count=100'
fdcount     # a régi digesten nem nő tartósan (ha az nem hibás)

Postcondition: a counter tábla adata megmaradt a down/up után. A rollback bizonyítéka a futó konténer image-digestje (docker inspect ... {{.Image}} és docker compose images), nem az FD-szám visszaesése: bármilyen rekreáció vagy docker restart új processzt indít, így az FD-szám akkor is visszaesik, ha a hibás digest fut tovább – a puszta újraindítás enyhítés, nem a hiba javítása. A szivárgás megszűnését az igazolja, hogy ugyanaz a /leak-fd?count=100 terhelés a régi digesten nem növeli tartósan az FD-számot, az újon igen.

38.5.7 Rövid összefoglaló

A konténerhiba megoldása a rétegazonosítással kezdődik: image/config, runtime, host, network. A digestre pinelt deployment kiszámíthatóvá teszi az image-t, a named volume pedig a data-safe restart kulcsa. A laborban a docker compose down megőrzi a volume-ot, a down -v törli, ezért a cleanup előtt mindig ellenőrizni kell a backupot. Az OOM-kill és az FD-szivárgás a host és az alkalmazás rétegét teszi láthatóvá. A gyakorlatban a docker inspect, a docker compose logs, a /proc/PID/fd és a docker volume ls a négy alapvető diagnosztikai pillér.

Továbbhasznált definíciók:
- Layer-scoped container incident: olyan hiba, amelyet az image/config, runtime, host vagy network réteg egyedi tünete alapján osztályozunk.
- Data-safe restart: docker compose down + up -d, ahol a named volume változatlan marad.
- Digest-pinelt deployment: az image azonosítás registry/name@sha256:... formában, ami elkerüli a tag mozgó célpontját.
