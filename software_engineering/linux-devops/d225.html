45.5 Cloud packet/storage/recovery labor

45.5.1 Motiváció és méréshatár

A cloudban egy alkalmazáshiba mögött gyakran egymásra rétegzett okok állnak: a guest Linux útválasztás, a provider VPC route/firewall/szolgáltatásvégpont, az IAM identity, a DNS és a tárolóréteg. Ha csak a guestben nézel, a VPC endpoint hiánya vagy az IAM tiltás a homályban marad; ha csak a provider konzoljában nézel, nem tudod, hogy az alkalmazás valóban próbált-e kapcsolódni. A d225 labor célja, hogy egy topológiafixture segítségével a provider és a guest oldali bizonyítékokat egyetlen diagnosztikai láncba kösd, és a javítást, a helyreállítást, valamint a cleanup utófeltételt ugyanabban a folyamatban bizonyítsd.

A példában AWS-szerű parancsokat és erőforrásneveket használunk, de a logika más cloud providerre is lefordítható. A parancsok explicit profile, region, VPC, instance és bucket azonosítót tartalmaznak. A módosító parancsok mindig csak a lab- prefixummal jelölt, erre a laborra létrehozott erőforrásokra terjednek ki. A példa nem éles accountot feltételez, hanem egy elkülönített sandbox vagy offline policy-fixture alapján tanít.

45.5.2 Definíciók és topológiafixture

Provider manifest: a VPC, subnet, route table, security group, IAM role/policy, VPC endpoint, bucket és volume desired-state leírókészlete. A manifest a helyreállítás és a cleanup ellenőrzésének forrása; amit nem tartalmaz, az nem tartozik a labor hatókörébe.

Flow log: a provider által rögzített hálózati eseményrekord. A VPC, subnet vagy ENI szintjén mutatja a forrás/cél/pont/port, valamint az ACCEPT/REJECT döntést anélkül, hogy a payloadot megosztaná. A flow log a hálózati réteghatárok legfontosabb provider oldali bizonyítéka.

Recovery postcondition: egy parancssorozattal igazolt állapot, amely bizonyítja, hogy az erőforrás a helyreállítás után is működik, és a cleanup nem hagy hátra labon kívüli, nem kívánt erőforrást. A postcondition tartalmazza a várt bemenetet, a várt kimenetet és a megfigyelt állapotot. Nem elegendő „a backup létezik”, mert a visszaállítás csak a sikeres smoke teszttel válik bizonyítottá – ahogyan a d100 is tanítja.

A fixture topológiája:

Erőforrás Név Leírás
VPC lab-vpc 10.44.0.0/16, DNS resolution engedélyezett
Privát subnet lab-subnet-app 10.44.10.0/24
Bastion subnet lab-subnet-bastion 10.44.20.0/24, internet gateway
Route table lab-rt-app a privát subnetre asszociálva, S3 endpoint route hiányzik
VPC endpoint lab-vpce-s3 S3 gateway endpoint, route asszociáció nélkül
Ec2 instance lab-instance-app privát subnetben, IAM role: lab-s3-role
S3 bucket lab-bucket-<account> versioning engedélyezve, fixture objektum
IAM role lab-s3-role trust: EC2, kezdetben nincs S3 policy
Flow log lab-vpc-flow a lab-vpc minden forgalmát rögzíti

A desired state: a lab-instance-app a lab-bucket-111122223333 bucket lab-fixture/data.txt objektumát az instance role-jával aláírt kéréssel eléri, a tartalom pedig lab-ok. A megfigyelt állapot kezdetben timeout, majd a route javítása után 403 AccessDenied, a két különböző réteg két egymás utáni hibája.

A labor két különböző tesztet használ, és ezeket nem szabad összekeverni. A sima curl nem ír alá AWS-kérést (SigV4) az instance profile ideiglenes hitelesítő adataival, ezért csak a hálózati elérhetőséget (DNS, TCP, TLS, HTTP-válasz érkezik-e) méri: egy privát objektumra mindig anonim 403-at kap, a role jogaitól függetlenül. A jogosultság-tesztet az aws s3api get-object végzi, amely az IMDS-ből vett role-credentiallel aláírja a kérést.

45.5.3 Kidolgozott példa: privát bucket elérés javítása

A példa laborablakában először a provider manifestet olvassuk be, majd a guestből és a provider oldalról végzünk mérést. Az alábbi parancsok mind a lab profile-ban, eu-central-1 régióban futnak.

Az alábbi ábra ugyanazt a kérést mutatja a három javítási állapotban: hol akad el, melyik bizonyíték melyik réteghez tartozik, és mi változik az egyes javítások után.

45.5.3.1 Első kör: route hiány

Bekérjük az instance és a route table állapotát:

# provider oldal, lab account, eu-central-1, lab-instance-app cél
QI='Reservations[].Instances[]'
QI+='.[InstanceId,State.Name,PrivateIpAddress,SubnetId]'
aws ec2 describe-instances --profile lab --region eu-central-1 \
  --filters "Name=tag:Name,Values=lab-instance-app" \
  --query "$QI"

QR='RouteTables[].Routes[]'
QR+='.[DestinationCidrBlock,DestinationPrefixListId,GatewayId]'
aws ec2 describe-route-tables --profile lab --region eu-central-1 \
  --filters "Name=association.subnet-id,Values=subnet-0a1b2c3d" \
  --query "$QR"

aws ec2 describe-vpc-endpoints --profile lab --region eu-central-1 \
  --filters "Name=vpc-id,Values=vpc-0e1f2g3h" \
  --query 'VpcEndpoints[].[VpcEndpointId,ServiceName,State,RouteTableIds]'

Várt, illusztratív kimenet: az instance running, privát 10.44.10.10 címmel; a lab-rt-app route table csak a helyi 10.44.0.0/16 bejegyzést mutatja (nincs S3 prefixlistás, pl-… célú route a vpce-… felé), az S3 endpoint lista RouteTableIds eleme üres. A VPC endpoint available állapotú, de nincs asszociálva a privát subnet route table-jéhez.

A guest oldalon a hibát tünetként rögzítjük. A lab-instance-app konzolján:

# lab-instance-app, 10.44.10.10, lab account
# csak hálózati elérhetőség-teszt (nem aláírt kérés)
S3_HOST=lab-bucket-111122223333.s3.eu-central-1.amazonaws.com
ip route
getent hosts "$S3_HOST"
curl -Iv --max-time 10 "https://$S3_HOST/lab-fixture/data.txt"

Várt kimenet: az ip route a default via 10.44.10.1 dev ens5 sort mutatja (illusztratív interfésznév) – a guest mindig a subnet routerének küld, DHCP-ből kapott default route-tal, akár privát a subnet, akár nem; a public/private jelleg a provider route table-jében él (lásd 45.1). A DNS getent sikeresen feloldja a bucket nevet a VPC resolveren keresztül; a curl azonban timeoutot ad, mert a provider lab-rt-app route table-jéből hiányzik az S3 felé vezető útvonal (nincs se endpoint-route, se NAT).

A flow logot a provider oldalon kapcsoljuk be, majd a sikertelen curl után lekérdezzük. CloudWatch Logs célhoz a VPC Flow Logs szolgáltatás által átvehető delivery role kell (trust principal: vpc-flow-logs.amazonaws.com, logs:CreateLogStream/logs:PutLogEvents jogokkal); itt lab-flowlogs-role, amely a manifest része:

# flow log létrehozása a lab-vpc-n, provider oldal
aws ec2 create-flow-logs --profile lab --region eu-central-1 \
  --resource-type VPC --resource-ids vpc-0e1f2g3h \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name lab-vpc-flow \
  --deliver-logs-permission-arn \
  arn:aws:iam::111122223333:role/lab-flowlogs-role \
  --tag-specifications \
  'ResourceType=vpc-flow-log,Tags=[{Key=Name,Value=lab-vpc-flow}]'
# ellenőrzés: FlowLogId és DeliverLogsStatus = SUCCESS
aws ec2 describe-flow-logs --profile lab --region eu-central-1 \
  --filter Name=resource-id,Values=vpc-0e1f2g3h \
  --query 'FlowLogs[].[FlowLogId,DeliverLogsStatus]'

A CloudWatch Logs Insights lekérdezés:

fields @timestamp, srcAddr, dstAddr, dstPort, action, bytes
| filter srcAddr = '10.44.10.10' and dstPort = 443
| sort @timestamp desc
| limit 20

Az elsődleges bizonyíték a route table: a lab-rt-app-ban nincs S3 prefixlistás route, és az endpoint RouteTableIds listája üres. Ez elég a hipotézishez: a privát subnet route table nem tudja, hogy az S3 forgalmat az endpointra kell küldeni. A flow log csak kiegészítő, időablakhoz és delivery státuszhoz kötött megfigyelés: a rekordok késleltetve (jellemzően perces aggregációs ablakkal) érkeznek, és egy üres eredmény önmagában lehet késés, rossz időablak vagy sikertelen kézbesítés (DeliverLogsStatus) következménye is. Ha a DeliverLogsStatus SUCCESS, és elegendő idő után sincs ACCEPT/REJECT rekord a 10.44.10.10 és a 443-as cél között, az összhangban van a route-hiánnyal, de nem önálló bizonyíték.

Az első javítás a VPC gateway endpoint és a route table kapcsolása. Gateway endpointnál ezt a modify-vpc-endpoint --add-route-table-ids végzi (külön „association” alparancs nincs); előbb ellenőrizzük, hogy az endpoint Gateway típusú:

# provider oldali módosítás, lab- prefix, eu-central-1, lab account
aws ec2 describe-vpc-endpoints --profile lab --region eu-central-1 \
  --vpc-endpoint-ids vpce-0abc1234 \
  --query 'VpcEndpoints[].[VpcEndpointType,ServiceName]'
aws ec2 modify-vpc-endpoint \
  --profile lab --region eu-central-1 \
  --vpc-endpoint-id vpce-0abc1234 \
  --add-route-table-ids rtb-0def5678
# rollback: ugyanez --remove-route-table-ids rtb-0def5678 kapcsolóval

A route table ellenőrzése (describe-route-tables, mint fent) most már tartalmaz egy S3 prefixlistás (pl-…) route-ot a vpce-0abc1234 felé, és az endpoint RouteTableIds listájában megjelenik az rtb-0def5678. A guest curl most már nem timeoutot ad, hanem HTTP-választ (a nem aláírt kérésre anonim 403-at). Ezzel a route réteg rendben van; a jogosultságot a következő kör vizsgálja.

45.5.3.2 Második kör: IAM policy hiány

A jogosultság-tesztet a guestben aláírt kéréssel végezzük: az AWS CLI az instance profile credentialjét az IMDS-ből veszi.

# lab-instance-app, guest oldal; aláírt kérés a lab-s3-role nevében
aws s3api get-object --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --key lab-fixture/data.txt /tmp/lab-data.txt

A válasz a guest oldalon (illusztratív):

An error occurred (AccessDenied) when calling the GetObject operation:
User: arn:aws:sts::111122223333:assumed-role/lab-s3-role/i-0abcd1234
is not authorized to perform: s3:GetObject
on resource: "arn:aws:s3:::lab-bucket-111122223333/lab-fixture/data.txt"

A hibaüzenet önmagában is az IAM rétegre mutat, de az ellenpróbához ellenőrizzük a role policy meglétét:

# provider oldal, identity réteg
aws iam get-role --profile lab --role-name lab-s3-role \
  --query 'Role.[RoleName,Arn]'

aws iam list-role-policies --profile lab --role-name lab-s3-role

Várt kimenet: a role létezik, de a policy lista üres. A guestben a nem aláírt curl már HTTP-választ kap a buckettől, tehát a hálózati út és a DNS egyaránt működik. A hiba már nem a packet path, hanem a hozzáférés-engedély hiánya.

A javításhoz létrehozunk egy S3 olvasási policy-t. A lab-s3-policy.json:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::lab-bucket-111122223333/lab-fixture/*"
    }
  ]
}

Alkalmazzuk:

# provider oldali módosítás, lab- role, lab account
aws iam put-role-policy --profile lab --region eu-central-1 \
  --role-name lab-s3-role \
  --policy-name lab-s3-read-fixture \
  --policy-document file://lab-s3-policy.json

A végső smoke test a guestből, ugyanazzal az aláírt kéréssel, mint a hibás állapotban (csak az IAM policy változott, így csak ennek az eredménye változhat):

# lab-instance-app, guest oldal; aláírt kérés a lab-s3-role nevében
aws s3api get-object --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --key lab-fixture/data.txt /tmp/lab-data.txt
cat /tmp/lab-data.txt

Várt kimenet: a get-object JSON-metaadatot ad vissza (hiba nélkül), a cat pedig lab-ok-ot. A nem aláírt curl továbbra is anonim 403-at kap, ami helyes: a bucket privát. A postcondition bizonyított: a route table, az endpoint asszociáció, a DNS, a flow log és az IAM policy mind a megfelelő rétegben működik. A recovery nem egyszerűen „újra próbálkozott”, hanem a route és az identity hibát külön, ellenőrzött lépésben javította.

45.5.4 Hibák és ellenpróbák

A cloud incidensben a tüneteket a réteghez kell kötni. A leggyakoribb hibamódok:

Tünet Valószínű réteg Ellenőrzés Ellenpróba
Timeout, nincs hálózati válasz VPC route, subnet, security group ip route, flow log, aws ec2 describe-security-groups A bastionból indított próba eljut-e ugyanoda?
HTTP 403, AccessDenied IAM, bucket policy, KMS aws sts get-caller-identity, list-role-policies A role nélküli publikus teszt objektum elérhető-e?
DNS nem oldódik VPC DNS resolver, privat hosted zone getent, dig, DNS query logs IP-címmel, Host headerrel sikeres-e a kérés?
VcpuLimitExceeded (EC2 RunInstances) Region quota aws service-quotas get-service-quota Másik régióban vagy csökkentett méretben sikerül-e?
InvalidAMI / API eltérés Region mismatch, deprecation describe-images region, describe-subnets availability zone Ugyanaz az image másik regionban megtalálható-e?
Storage NoSuchVersion Bucket versioning, lifecycle list-object-versions, get-bucket-lifecycle Egy másik verzió head-object válasza

Az ellenpróba mindig egyetlen feltételt változtat. Ha a 403 javításához egyszerre cserélsz route table-t, security groupot és IAM policy-t, nem tudod megmondani, melyik hiba melyik rétegben volt. A fent leírt példában a route javítása után a hálózati teszt már HTTP-választ kapott, az aláírt kérés viszont AccessDenied-del bukott, ezért a hálózati réteg kizárhatóvá vált.

A region/quota/identity hibák tipikus jele: az API hívás azonnal AccessDenied/UnauthorizedOperation, VcpuLimitExceeded vagy UnsupportedOperation hibát ad (a pontos kódok az adott szolgáltatás hivatalos hibakódlistáján ellenőrizendők). Ilyenkor nem a guestben kell keresni, hanem a provider control plane-ben. A guest oldali hiba pedig akkor látszik hálózatinak, ha az API válasz késik vagy timeoutol; ez regionális kapcsolati, route vagy DNS hibára utalhat.

A flow log hiányossága, hogy nem mutatja a tartalmat és nem minden esetben a teljes adatutat. A REJECT rekord mellett az üres log is értelmezhető jelzés, ha a forgalom nem éri el a megfigyelt erőforrást – de csak kiegészítőként: a rekordok késleltetve érkeznek, ezért az üres eredményt az időablakhoz és a DeliverLogsStatus-hoz kell kötni, az elsődleges bizonyíték pedig a route table.

45.5.5 Feladatok

45.5.5.1 1. Feladat – Tünetek réteghez rendelése

A példában a lab-instance-app először timeoutot, majd 403-at adott. Magyarázd el, milyen provider oldali bizonyítékok alapján döntöd el, hogy a második hiba már nem hálózati, hanem IAM hiba. Sorold fel a rétegeket, a megfigyelt jelet és a megerősítő ellenpróbát.

45.5.5.2 2. Feladat – Object lifecycle és restore fixture

Kapcsold be a lab-bucket-<account> bucket verziókezelését, tölts fel egy lab-fixture/v2.txt objektumot, majd töröld az objektumot verzióazonosító nélkül (delete marker keletkezik; ez nem a verzió végleges törlése). Állítsd vissza az objektumot a verziókezelésből, és bizonyítsd a postconditiont: a head-object válasz ContentLength megegyezik a manifestben rögzített hosszal. A parancsokban explicit bucket, régió és profile szerepeljen.

45.5.5.3 3. Feladat – Region/quota hibák és cleanup postcondition

Szimuláld a következő hibát: egy új lab-instance-app2 indítása VcpuLimitExceeded hibát ad. Diagnosztizáld, hogy a hiba quota, region vagy IAM, és ne a guestben keress hálózati tünetet. Ezután hajtsd végre a teljes cleanup-t a labor összes lab- prefixumú erőforrására, és bizonyítsd, hogy egyik sem maradt meg. Ne legyen mentség a policy-fixture: ha a parancsok nem futtathatók, a pszeudokódot és a postcondition-ellenőrzés leírását akkor is add meg.

45.5.6 Megoldások

45.5.6.1 1. Megoldás – Tünetek réteghez rendelése

A tünetek réteghez rendelése:

  • Network/route réteg: a guest curl timeout; az ip route default route-ja a VPC routerre mutat, tehát a guest oldali routing rendben van; a provider lab-rt-app route table-je nem tartalmaz S3 prefixlistás route-ot, és az endpoint RouteTableIds listája üres (elsődleges bizonyíték); a flow log – sikeres kézbesítés és elegendő időablak mellett – nem tartalmaz forgalmat a forrás és a 443-as cél között (kiegészítő jel). Az ellenpróba: a route table endpointhoz kapcsolása után a timeout megszűnik, a nem aláírt curl HTTP-választ kap, ez bizonyítja a route hiányt.
  • Identity/IAM réteg: az aláírt aws s3api get-object AccessDenied hibát ad, a hibaüzenet és az aws sts get-caller-identity a lab-s3-role-t mutatja, a list-role-policies üres. Az ellenpróba: a policy hozzáadása után ugyanaz az aláírt kérés sikeres (csak az IAM policy változott).
  • DNS réteg: a getent hosts sikeres volt, tehát a DNS nem volt hiba. Ha sikertelen lett volna, a curl Could not resolve host jelzett volna.

A postcondition: a guestből az aláírt kéréssel letöltött lab-fixture/data.txt tartalma lab-ok, a flow log ACCEPT rekordot mutat a 443-as porton. Ez a három bizonyíték együtt igazolja, hogy a hálózati és identity réteg is rendben van.

45.5.6.2 2. Megoldás – Object lifecycle és restore fixture

A verziókezelés bekapcsolása:

# lab account, eu-central-1, lab-bucket, provider oldal
aws s3api put-bucket-versioning --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --versioning-configuration Status=Enabled

Feltöltés, törlés, visszaállítás. A manifestben rögzített hossz 11 bájt: a v2-content 10 karakter, plusz a záró újsor (wc -c /tmp/lab-v2.txt → 11):

# upload fixture, provider oldal
printf 'v2-content\n' > /tmp/lab-v2.txt
wc -c /tmp/lab-v2.txt        # várt: 11
aws s3api put-object --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --key lab-fixture/v2.txt --body /tmp/lab-v2.txt

# delete object verzióazonosító nélkül: delete marker keletkezik
aws s3api delete-object --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 --key lab-fixture/v2.txt

# a verziók listázása megmutatja a delete markert és annak VersionId-ját
aws s3api list-object-versions --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --prefix lab-fixture/v2.txt

# a delete marker eltávolítása visszaállítja a legfrissebb verziót
DM_ID=$(aws s3api list-object-versions --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 --prefix lab-fixture/v2.txt \
  --query 'DeleteMarkers[?IsLatest].VersionId' --output text)
aws s3api delete-object --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 \
  --key lab-fixture/v2.txt --version-id "$DM_ID"

# postcondition
aws s3api head-object --profile lab --region eu-central-1 \
  --bucket lab-bucket-111122223333 --key lab-fixture/v2.txt \
  --query ContentLength

Várt kimenet: a list-object-versions először a törölt objektum DeleteMarker elemét mutatja; a törlési marker eltávolítása után a head-object ismét elérhető objektumot jelez, ContentLength = 11 bájt (10 karakter + újsor), egyezően a manifesttel. A postcondition: az objektum ismét elérhető, és a verziótörténetben a VersionId nem törlődött.

45.5.6.3 3. Megoldás – Region/quota hibák és cleanup postcondition

Diagnosztika:

# quota: a futó on-demand példányok vCPU-kvótájának kódját a listából
# választjuk ki ("Running On-Demand Standard (A, C, D, H, I, M, R, T, Z)
# instances"); a kód (itt L-1216C47A) a hivatalos listán ellenőrizendő
QQ='Quotas[?contains(QuotaName, `Running On-Demand Standard`)]'
QQ+='.[QuotaName,QuotaCode,Value]'
aws service-quotas list-service-quotas --profile lab --region eu-central-1 \
  --service-code ec2 --query "$QQ" --output table
aws service-quotas get-service-quota --profile lab --region eu-central-1 \
  --service-code ec2 --quota-code L-1216C47A

# IAM ellenőrzés: az indítást a --profile lab mögötti operátori identity
# kéri, nem a futó példány lab-s3-role instance role-ja
aws sts get-caller-identity --profile lab
CALLER_ARN=$(aws sts get-caller-identity --profile lab \
  --query Arn --output text)
# assumed-role ARN esetén a policy-source-arn a role ARN-je
# (arn:aws:iam::111122223333:role/<név>), nem az sts-session ARN
aws iam simulate-principal-policy --profile lab \
  --policy-source-arn "$CALLER_ARN" \
  --action-names ec2:RunInstances

# region ellenőrzés: a kért AMI elérhető-e a cél regionban?
aws ec2 describe-images --profile lab --region eu-central-1 \
  --image-ids ami-0lab0001

A VcpuLimitExceeded azt jelzi, hogy a futó példányok vCPU-összege a kéréssel együtt meghaladná a kvóta Value mezőjét; a hiba nem a guestben, hanem a provider control plane-ben jelentkezik. Ha a quota engedélyezett, az operátori identity jogának hiánya UnauthorizedOperation hibát adna (a simulate-principal-policy implicitDeny/explicitDeny eredménye), ami elkülöníthető. A region hibát pedig az AMI elérhetősége mutatja (InvalidAMIID.NotFound).

A cleanup a manifest összes lab- erőforrására, függőségi sorrendben. Az azonosítók a fixture dummy értékei; a bastion subnet, az IGW, a nem default security group és a flow log azonosítóját a manifestből kell venni:

P="--profile lab --region eu-central-1"
B=lab-bucket-111122223333

# 1. instance terminate, és megvárjuk a terminated állapotot
aws ec2 terminate-instances $P --instance-ids i-0abcd1234
aws ec2 wait instance-terminated $P --instance-ids i-0abcd1234

# 2. flow log és a CloudWatch log group törlése
aws ec2 delete-flow-logs $P --flow-log-ids fl-0lab0001
aws logs delete-log-group $P --log-group-name lab-vpc-flow

# 3. bucket: verziózott bucketben az "aws s3 rm --recursive" csak
#    delete markert tesz, ezért a verziókat és a delete markereket
#    verzióazonosítóval töröljük (1000 objektumonként lapozva)
Q='{Objects: [Versions, DeleteMarkers][][].{Key: Key, VersionId: VersionId}}'
aws s3api list-object-versions $P --bucket "$B" --max-items 1000 \
  --query "$Q" --output json > /tmp/lab-del.json
aws s3api delete-objects $P --bucket "$B" --delete file:///tmp/lab-del.json
aws s3api delete-bucket $P --bucket "$B"

# 4. VPC endpoint
aws ec2 delete-vpc-endpoints $P --vpc-endpoint-ids vpce-0abc1234

# 5. subnetek (app, bastion); ezzel megszűnnek a route table-asszociációk
aws ec2 delete-subnet $P --subnet-id subnet-0a1b2c3d
aws ec2 delete-subnet $P --subnet-id subnet-0bastion1

# 6. a nem main route table (az asszociáció megszűnése után)
aws ec2 delete-route-table $P --route-table-id rtb-0def5678

# 7. bastion IGW leválasztása és törlése
aws ec2 detach-internet-gateway $P --internet-gateway-id igw-0lab0001 \
  --vpc-id vpc-0e1f2g3h
aws ec2 delete-internet-gateway $P --internet-gateway-id igw-0lab0001

# 8. nem default security groupok, majd a VPC
aws ec2 delete-security-group $P --group-id sg-0lab0001
aws ec2 delete-vpc $P --vpc-id vpc-0e1f2g3h

# 9. IAM: inline policy, instance profile, role (a flow log role is)
aws iam delete-role-policy --profile lab --role-name lab-s3-role \
  --policy-name lab-s3-read-fixture
aws iam remove-role-from-instance-profile --profile lab \
  --instance-profile-name lab-s3-role --role-name lab-s3-role
aws iam delete-instance-profile --profile lab \
  --instance-profile-name lab-s3-role
aws iam delete-role --profile lab --role-name lab-s3-role

Ha a bucketben több mint 1000 verzió van, a 3. lépés listázását és törlését addig kell ismételni, amíg a lista üres. A lab-flowlogs-role törlése ugyanígy (inline policy, majd delete-role).

A cleanup postcondition ellenőrzése, szűrt lekérdezésekkel (szűrő nélkül a describe-vpcs a régió default VPC-jét is listázná, a describe-instances pedig a terminated példányt még kb. egy óráig visszaadja):

# listázás: a lab- prefixumú erőforrások ne jelenjenek meg
aws ec2 describe-instances $P \
  --filters "Name=tag:Name,Values=lab-*" \
  "Name=instance-state-name,Values=pending,running,stopping,stopped" \
  --query 'Reservations[].Instances[].InstanceId'
aws ec2 describe-vpcs $P --filters "Name=tag:Name,Values=lab-*" \
  --query 'Vpcs[].VpcId'
aws s3api head-bucket $P --bucket "$B"          # várt: 404 / Not Found
aws iam get-role --profile lab --role-name lab-s3-role  # várt: NoSuchEntity

Várt kimenet: üres listák, a head-bucket 404-et, a get-role NoSuchEntity hibát ad; nincs lab- prefixummal rendelkező maradék. A parancsok nem futtatottak ebben a kérésben, ezért a várt kimenet illusztratív.

45.5.7 Rövid összefoglaló

A cloud hibákat rétegenként kell lokalizálni: a provider VPC route/firewall/endpoint, az IAM identity, a DNS, a storage és a guest Linux egyaránt hibásodhat. A route table a route-hiány elsődleges bizonyítéka, a flow log kiegészítő, időablakhoz és kézbesítési státuszhoz kötött provider oldali jel; a guest ip route/curl a hálózati elérhetőséget, az aláírt aws s3api kérés a jogosultságot mutatja. A javítás után a postcondition minden rétegben mérhető: az aláírt get-object sikere (lab-ok), a flow log ACCEPT bejegyzése és az IAM policy jelenléte együtt igazolják a helyreállítást. A cleanup csak a lab- prefixumú erőforrásokra terjed, függőségi sorrendben, és a szűrt leftover-ellenőrzés üres listát vár. A bucket verziókezelés a törlés ellenére visszaállítható, ezért a data integrity postcondition a head-object válasz.

Továbbhasznált definíciók:

  • Provider manifest: a VPC, route, firewall, IAM, endpoint és tároló desired-state leírókészlete.
  • Flow log: a provider által rögzített hálózati esemény, amely a forrás/cél/port/pont és ACCEPT/REJECT döntést mutatja.
  • Recovery postcondition: a javítás után mérhető állapot, amely bizonyítja a szolgáltatás működését és a cleanup hatókörét.
