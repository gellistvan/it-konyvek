12.2 Telepítés, partition és elérhetőség

12.2.1 Motiváció

Egy Linux hoszt üzembe állítása akkor válik működtethetővé, ha a telepítés nem egyszeri, megismételhetetlen kattintgatás, hanem verziózott, auditálható telepítési profilból (installation profile) hajtható végre. A szenior C++ fejlesztő a build automatizálásából ismeri a reprodukálhatóság és az artifact ellenőrzés értékét; ugyanez a szemlélet kell egy új VM kiépítéséhez. Ennek a szakasznak a célja, hogy egy rögzített profillal, hitelesített forrásból, konzol- és SSH-eléréssel rendelkező Linux hosztot hozzunk létre, majd az üzemeltetéshez szükséges alaptermék-nyilvántartást (inventory) rögzítsük. A mélyebb lemezkezelést a Block device, partition, LVM és titkosítás adminisztrációja, a mountok részletes szemantikáját a Mount, fstab és namespace tárgyalja.

12.2.2 Telepítési profil definíció és működési rétegek

Definition. A telepítési profil az az újraépíthető, verziózott specifikáció, amely az operációs rendszer image forrását, integritás-ellenőrző adatát, a platform által elvárt boot és lemez layoutot, az admininstrációs hozzáférést, a hálózati minimumprofilt, valamint a konzol/SSH recovery útvonalat írja le.

A telepítés rétegei:

  1. Forrás image réteg: az ISO vagy cloud image beszerzése, ellenőrző összeg (checksum) és aláírás ellenőrzése. Ez adja az artifact identitását.
  2. Installer/provision réteg: az automatizált telepítő inputja (Ubuntu Server 24.04 LTS esetén autoinstall/cloud-init seed), amely a lemezt, a felhasználót, a hálózatot és az SSH-t állítja be.
  3. Boot és mount réteg: UEFI firmware, boot loader, /boot és a root filesystem mountjai. A rendszer itt válik elérhetővé.
  4. Elérhetőségi réteg: konzol, SSH, hálózat és DNS. A recovery útvonal akkor is megmarad, ha a hálózati elérés kiesik.
  5. Post-install inventory réteg: a telepített állapot rögzítése és a biztonsági frissítések alkalmazása.

Az egyes rétegek kimenete ellenőrizhető állapotot ad; ha a következő réteg hibázik, a korábbi rétegek állapotából indítható a diagnosztika.

12.2.3 Kidolgozott példa: lab-vm1 telepítése

A példa az izolált lab infrastruktúrában (Izolált, újraépíthető Linux labor) fut. Az inventory:

Szerep Host/VM Account Privilege Hálózat Megjegyzés
Hypervisor lab-hv-01 lab-admin sudo root mgmt telepítés vezérlése
Új VM lab-vm1 lab-admin sudo a VM-ben lab-net célrendszer
Telepítési kép ISO — — — disztribútor release oldala

A VM DHCP-ről kap címet; a tényleges címet a hypervisoron a sudo virsh domifaddr lab-vm1 adja. A példákban szereplő 192.0.2.10 documentation cím csak akkor a VM címe, ha a lab-net hálózat XML-jében statikus DHCP-foglalás rögzíti (ezt az Izolált, újraépíthető Linux labor inventory dokumentálja); egyébként a virsh domifaddr kimenetét használjuk. A módosító parancsok a lab-hv-01 gazdagépen futnak, lab-admin felhasználóval és sudo-val.

12.2.3.1 1. ISO hitelesség és checksum

A forrás ISO pontos nevét, a kiadási URL-t és az Ubuntu CD Image Signing Key ujjlenyomatát a lab release jegyzék tárolja. Az itteni URL nem ellenőrzött, csak a folyamatot mutatja; az ISO-név a SHA256SUMS bejegyzésével azonos alakú (ubuntu-24.04.x-live-server-amd64.iso, „ubuntu-server-” előtag nélkül), és a helyi fájl is ezen a néven mentődik, mert a sha256sum -c a listában szereplő néven keresi:

# target: lab-hv-01, user: lab-admin, privilege: user
mkdir -p ~/lab-install && cd ~/lab-install
ISO=ubuntu-24.04.1-live-server-amd64.iso   # a release jegyzék szerinti név
REL="<release-url>"                          # a release jegyzék szerinti URL
curl -fL -O "$REL/$ISO" -O "$REL/SHA256SUMS" -O "$REL/SHA256SUMS.gpg"
# 1. az ellenőrzőösszeg-lista aláírása (a kulcs ujjlenyomata a jegyzékben)
gpg --keyid-format long --verify SHA256SUMS.gpg SHA256SUMS
# 2. az ISO hash-e a hitelesített lista alapján
sha256sum -c --ignore-missing SHA256SUMS

Várt kimenet (illusztratív): a gpg Good signature from "Ubuntu CD Image Automatic Signing Key …" sort ír, és az aláíró kulcs ujjlenyomata egyezik a jegyzékben rögzítettel; a sha256sum ubuntu-24.04.1-live-server-amd64.iso: OK sort ad. Az aláírás-ellenőrzés nélkül a checksum önmagában nem hitelesít, mert ugyanarról a szerverről jön, mint az ISO. A valós hash értéket a letöltött, aláírással ellenőrzött SHA256SUMS fájlból kell rögzíteni.

12.2.3.2 2. Telepítő seed profil

Az Ubuntu autoinstall számára a user-data rögzíti a hostidentitást, SSH-t, minimális lemezelrendezést és hálózatot. A jelszó csak példa, saját hash-t mkpasswd -m sha-512 paranccsal kell generálni:

#cloud-config
autoinstall:
  version: 1
  identity:
    hostname: lab-vm1
    username: lab-admin
    # Példa hashelt jelszó; dummy, nem éles.
    password: "$6$rounds=656000$example..." 
  ssh:
    install-server: true
    allow-pw: false
    authorized-keys:
      - "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIexample lab-admin@lab-hv-01"
  storage:
    layout:
      name: lvm
      match:
        size: largest
  network:
    version: 2
    ethernets:
      enp1s0:
        dhcp4: true

A meta-data mellé:

instance-id: lab-vm1
local-hostname: lab-vm1

A subiquity lvm gyorsbeállítása automatikusan létrehozza a UEFI ESP-t, a /boot-ot, egy ubuntu-vg volume groupot és benne egyetlen ubuntu-lv root logikai kötetet; a VG egy része alapból kiosztatlan marad. Swap LV-t nem hoz létre: swapként a telepítő egy /swap.img swapfájlt készít. Külön /srv/data kötet sem jön létre; az elkülönített adatterületet (a szabad VG-részből) a storage admin alfejezet hozza létre. Itt a példa csak a minimális, reprodukálható alapréteget célozza. A várt layout egy 20 GiB-os lemezen (a pontos méretek telepítőverzió-függők, a labon lsblk rögzíti):

Mount Eszköz példa FS Méret Szerep
/boot/efi vda1 vfat kb. 1 GiB UEFI ESP
/boot vda2 ext4 kb. 2 GiB kernel/initramfs
/ ubuntu-vg/ubuntu-lv ext4 a VG egy része OS
— ubuntu-vg szabad része — maradék későbbi LV-k (pl. /srv/data)
swap /swap.img swapfájl telepítő választja swap

Ha a terv külön swap és adat LV-t ír elő, a layout: gyorsbeállítás helyett explicit storage: config: (curtin action-lista) kell, és a lemezméretet is ehhez kell igazítani. Ellenőrzés a telepítés után: lsblk -o NAME,FSTYPE,SIZE,MOUNTPOINTS, sudo vgs, swapon --show.

12.2.3.3 3. Telepítés indítása

A live-server telepítő a cloud-init-ből érkező autoinstall-konfigurációnál – ha a kernel parancssorán nincs autoinstall paraméter – interaktív „Continue with autoinstall?” megerősítést kér, hogy véletlenül ne törölje a lemezt. --cdrom és --noautoconsole mellett ezt senki nem látná, és a VM a promptnál várna. Ezért --location-nel a kernelt és az initrd-t közvetlenül indítjuk, és a kernel parancssorára tesszük az autoinstall és a soros konzol paramétert:

# target: lab-hv-01, user: lab-admin, privilege: sudo
D=/home/lab-admin/lab-install
ISO=ubuntu-24.04.1-live-server-amd64.iso
sudo virt-install \
  --name lab-vm1 \
  --memory 4096 \
  --vcpus 2 \
  --disk path=/var/lib/libvirt/images/lab-vm1.qcow2,format=qcow2,size=20 \
  --network network=lab-net,model=virtio \
  --boot uefi \
  --location "$D/$ISO,kernel=casper/vmlinuz,initrd=casper/initrd" \
  --extra-args 'autoinstall console=ttyS0,115200n8' \
  --cloud-init "user-data=$D/user-data,meta-data=$D/meta-data" \
  --noautoconsole

A telepítés sudo virsh console lab-vm1-gyel követhető (kilépés: Ctrl+]). Alternatíva a --cdrom indítás, de akkor a konzolon a promptnál yes-t kell beírni. A virt-install részletei a KVM, QEMU és libvirt komponensek témakörhöz tartoznak; itt a profil az irányadó. A telepítés végén a VM leáll vagy újraindul: sudo virsh domstate lab-vm1, majd sudo virsh list --all mutatja a VM-et.

12.2.3.4 4. Network, DNS és SSH ellenőrzés

A VM DHCP-ről kap IP-t. Az első belépés SSH-val, a seedben megadott kulccsal:

# target: lab-hv-01, user: lab-admin, privilege: sudo a cím lekérdezéséhez
sudo virsh domifaddr lab-vm1
IP=$(sudo virsh domifaddr lab-vm1 | awk '/ipv4/{print $4}' | cut -d/ -f1)
ssh -i ~/.ssh/lab_admin "lab-admin@$IP" -- hostnamectl

SSH kiesése esetén a konzol a recovery útvonal:

# target: lab-hv-01, user: lab-admin, privilege: sudo
sudo virsh console lab-vm1
# kilépés: Ctrl+]

A konzolon bejelentkezve a hálózati állapot akkor is ellenőrizhető, ha a hálózat nem elérhető a gazdáról.

12.2.3.5 5. Post-install inventory és frissítések

Az alaptermék-nyilvántartáshoz a következő adatokat rögzítjük a VM-en:

# target: lab-vm1, user: lab-admin, privilege: sudo az utolsó parancsnál
hostnamectl
uname -r
lsblk -o NAME,FSTYPE,SIZE,MOUNTPOINTS
findmnt --real
systemctl is-system-running
resolvectl status

A frissítés módosító művelet, ezért előtte a hypervisoron VM snapshot készül (a snapshot kezelést lásd VM block storage, snapshot és backup). A frissítés és az újraindítás utáni ellenőrzés:

# target: lab-vm1, user: lab-admin, privilege: sudo
sudo apt update
sudo apt full-upgrade -y
sudo systemctl reboot

Reboot után újra ellenőrizzük az SSH-elérést és a rendszer állapotát.

12.2.4 Hibák és ellenpróbák

Tünet: a telepítő lefut, de az SSH login nem fogadja a kulcsot.
Hipotézis: a user-data-ban rossz a publikuskulcs-formátum.
Adatgyűjtés: ssh -vvv kimenet, valamint cloud-init status és /var/log/cloud-init.log a konzolon.
Egy változtatás: a seedben a authorized-keys sort javítani kell, majd a VM-et törölni és újraépíteni.
Ellenőrzés: az SSH belépés újrapróbálása.

Tünet: a VM elérhető IP-n, de a DNS nem old fel neveket.
Hipotézis: a lab-net DHCP-szervere nem ad DNS-szervert (vagy rosszat ad); a netplan use-dns alapértéke true, így a VM oldalán ez nem kapcsoló.
Adatgyűjtés: networkctl status, resolvectl status (van-e DNS Servers sor az interfészen), /etc/netplan/*.yaml, /etc/resolv.conf; a hypervisoron a lab-net XML-je (sudo virsh net-dumpxml lab-net).
Egy változtatás: a DHCP-szerver DNS-opciójának javítása a lab-net hálózaton; vagy ha ez nem lehetséges, nameservers: explicit megadása egy saját /etc/netplan/60-lab.yaml fájlban (a cloud-init által írt 50-cloud-init.yaml-t ne szerkesszük, mert felülíródhat), majd sudo netplan try.
Ellenőrzés: dig vagy resolvectl query egy belső névre.

Tünet: frissítés után a VM nem bootol.
Hipotézis: initramfs vagy kernel/video illesztőhiba, boot menü beavatkozás szükséges.
Adatgyűjtés: hypervisor konzol (virsh console) kimenet, GRUB menü.
Egy változtatás: boot során egy korábbi kernel választása a menüben, vagy a mentett VM snapshot visszaállítása.
Ellenőrzés: a VM ismét csatlakozik a lab hálózathoz, SSH/konzol elérhető.

12.2.5 Feladatok

12.2.5.1 Feladat 1: Telepítési profil írása

Készítsen egy egylapos telepítési profil specifikációt a lab-vm1 hoszthoz az alábbi adatokkal: Ubuntu Server 24.04 LTS amd64, UEFI boot, minimálisan /boot/efi, /boot, root, swap; admin user lab-admin; hálózat DHCP; SSH key és konzol recovery. Írja le, milyen mezőket kell rögzíteni a release jegyzékben az image hitelességéhez.

12.2.5.2 Feladat 2: Automatizált telepítés

Generáljon egy SSH kulcsot lab-admin felhasználóhoz, készítse el a user-data és meta-data fájlt a fenti profilhoz, indítsa el a virt-install parancsot a lab-hv-01 gazdagépen, majd ellenőrizze a VM elérését SSH-val és konzollal. A VM címét a virsh domifaddr adja (vagy a lab-net dokumentált DHCP-foglalása, például 192.0.2.10).

12.2.5.3 Feladat 3: SSH recovery diagnosztika

A lab-vm1 a konzolon elérhető, de az SSH kapcsolat timeoutot ad. A cél: a konzolon gyűjtsön adatot, állapítsa meg, hogy a hiba a hálózatban, a DNS-ben, a tűzfalban vagy az SSH szolgáltatásban van, és állítsa helyre. Rögzítse a hibás és a javított állapotot.

12.2.6 Megoldások

12.2.6.1 Megoldás 1

A profil mezői: forrás URL és ellenőrző hash típusa/értéke; boot mód (UEFI); minimális lemezelrendezés; mountpontok és filesystem; admin user; SSH publikus kulcs; hálózati mód (DHCP); konzol recovery mód. A release jegyzékben rögzíteni kell a pontos image verziót, a letöltött SHA256SUMS fájlt, a hash-t, a letöltés dátumát és a forrás URL-t. Postcondition: a profil egyértelmű, más mérnök ugyanazt a gépet tudja újraépíteni.

12.2.6.2 Megoldás 2

A kulcsgenerálás ssh-keygen -t ed25519 -f ~/.ssh/lab_admin -C lab-admin@lab-vm1. A seedben a publikus kulcsot kell a authorized-keys listába illeszteni. A virt-install parancs a fenti mintával futtatható (--location + autoinstall kernelparaméter, különben a telepítő megerősítést kér); a diszk mérete 20 GiB, a hálózat lab-net. A telepítés után a címet a sudo virsh domifaddr lab-vm1 adja, és ssh -i ~/.ssh/lab_admin lab-admin@<IP> -- systemctl is-system-running ellenőrzi az elérést; a konzol sudo virsh console lab-vm1. Postcondition: a VM SSH-n és konzolon keresztül elérhető, a hostname lab-vm1, az admin user lab-admin.

12.2.6.3 Megoldás 3

Egy IP-címre irányuló SSH-kapcsolat timeoutját DNS-hiba nem okozza, ezért a sorrend a hálózat, a szolgáltatás és a tűzfal. A konzolon először a hálózati interfész állapotát és a routeokat ellenőrizzük: ip -br a, ip route – egyezik-e a cím a hypervisoron látott virsh domifaddr címmel. Ha nincs IP vagy route, a netplan configot vizsgáljuk és javítjuk (sudo netplan try). Ha az IP megvan, az SSH szolgáltatást nézzük: systemctl status ssh és ss -tlnp 'sport = :22' (figyel-e a 22-es porton). Ezután a tűzfalat: sudo nft list ruleset vagy sudo ufw status. Végül a hypervisorról: ping <IP> és nc -zv <IP> 22. A timeout (nem Connection refused) jellemzően eldobó tűzfalszabályra vagy hibás címre/route-ra utal. A DNS-ellenőrzés (resolvectl status) külön tünethez, a névfeloldási hibához tartozik. Postcondition: az SSH a VM tényleges (vagy dokumentáltan foglalt) címén elérhető, a hiba oka és a javítás előtti/utáni állapot rögzítve van.

12.2.7 Rövid összefoglaló

A Linux VM telepítését telepítési profilként kell kezelni: verziózott forrásimage, hitelesség-ellenőrzés, automatikus installer seed, UEFI és minimális lemezelrendezés, admin user, hálózati/DNS minimum, valamint konzol/SSH recovery. A telepítés után inventory és biztonsági frissítés következik, snapshot rollbackkel. A példában Ubuntu Server 24.04 LTS autoinstall/cloud-init folyamatot használtunk; a pontos release/version ellenőrzendő. Ez a fejezet a storage admin és a hypervisor réteg felé nyit: a lemezelrendezés, a snapshot és a boot hiba mély kezelését későbbi szakaszok tanítják. Az állapotok desired, observed, config-source és stored állapotként dokumentáltak.

Továbbhasznált definíciók: telepítési profil, recovery path, image hitelesség.

12.2.8 Források és ellenőrzési hiányok

  • Ubuntu Server documentation — kiindulópont, nem ellenőrzött; az autoinstall/cloud-init release-specifikus mezőit hivatalos dokumentációból kell ellenőrizni.
  • Debian documentation — distro kontraszt, ebben a példában nem használt; a Debian telepítőprofil eltérő.
  • systemd — boot/mount egységekhez hivatkozott, itt nem kifejtett.

Állításonkénti forrásindex (viszonyítási pont: Ubuntu Server 24.04 LTS live-server, a 24.04 libvirt/virt-install csomagja):

  • Autoinstall (autoinstall kernelparaméter és megerősítés, storage: layout: lvm, storage: config:): https://canonical-subiquity.readthedocs-hosted.com/en/latest/ – „Autoinstall reference” és „Providing autoinstall” oldalak.
  • ISO-ellenőrzés (SHA256SUMS + gpg): https://ubuntu.com/tutorials/how-to-verify-ubuntu.
  • virt-install (--location kernel/initrd, --extra-args, --cloud-init): https://manpages.ubuntu.com/manpages/noble/man1/virt-install.1.html; virsh domifaddr: https://www.libvirt.org/manpages/virsh.html.
  • Netplan (dhcp4-overrides, nameservers, netplan try): https://netplan.readthedocs.io/en/stable/.

A példák laborban ellenőrizendők; dátumozott futtatási napló (gpg/sha256 kimenet, telepítési napló, lsblk, domifaddr) még nem készült.

Ellenőrzési hiányok: a konkrét Ubuntu 24.04 ISO URL és SHA256SUMS hash, az aktuális autoinstall/cloud-init verzió és mezőkészlet, a virt-install --cloud-init opció pontos elérhetősége, a generált lvm layout automatikus partícióméretei, valamint az aktuális kernel/csomagfrissítések verziószintje. Ezeket a lab release jegyzékből és a hivatalos vendor dokumentációból kell ellenőrizni.
