10.3 Buffered/direct/async I/O és diagnosztika

10.3.1 Motiváció

Egy C++ szolgáltatás latency SLO-ja romlik, miközben a benchmark szép számokat mutat. A fejlesztő a std::fstream-mel mért írási sebességet látja, de a production adatbázis vagy storage motor nem ugyanazt az elérési utat használja: a page cache miatt a write() memóriába dolgozik, a tényleges device flush később vagy a durable media nem a benchmarknak megfelelő állapotban van. A réteghatárok és az API-módok közötti különbség nélkül a mérés félrevezető: a cache találati arány, a writeback késleltetés és az alignment hibák mind más-más rétegben jelentkeznek. Ez az alfejezet a buffered, direct és async I/O API-módokat, azok lifetime és alignment szerződéseit, valamint a diagnosztikát tanítja, hogy a mért szám mögött látni lehessen a kernel adatutat.

10.3.2 Definíció és működés

A buffered I/O (lásd d047 alfejezetet) a Linux page cache-en keresztül ír és olvas. A read()/write() syscall a user buffer és a page cache között másol, a kernel pedig a writeback-kel aszinkron, az fsync()-kel kérésre írja ki a dirty lapokat. Az alkalmazás előnye az egyszerűség: tetszőleges buffer, offset és hossz, a kernel kezeli a lapozást, az előreolvasást (readahead) és az I/O ütemezést. Hátránya: kétszeres másolás, cache thrashing, és a tartóssági szerződés nem explicit.

A direct I/O (O_DIRECT) megkerüli a page cache-t. A syscall közvetlenül a device felé viszi az adatot, a user bufferből DMA útba. A szerződés szigorú: a user buffer, a file offset és a hossz az eszköz logical block size-ához (tipikusan 512 B vagy 4096 B) igazítva kell legyen, különben EINVAL. A logikai blokkméretet az lsblk -no LOG-SEC <eszköz> vagy a /sys/block/<dev>/queue/logical_block_size adja; kernel 6.1+ alatt a statx(STATX_DIOALIGN) stx_dio_mem_align/stx_dio_offset_align mezői fájlonként megmondják a pontos követelményt. A stat -c %o (st_blksize) ezzel szemben csak az ajánlott I/O-méret, nem igazítási követelmény. A 4096 B-os igazítás mindkét tipikus esetben megfelel. A hívás szinkron a syscall szintjén, de a device write cache még mindig képes az adatot a volatile cache-be venni; a durable állapot csak fsync-kel garantált. Direct I/O akkor hasznos, ha az alkalmazás saját cache-t, adatbázis puffert vagy flash-re optimalizált réteget üzemeltet.

Az mmap felület a fájlt a processz virtuális címterébe képezi. A hozzáférés page faulton keresztül tölti be a lapokat a page cache-ből, a dirty lapokat a kernel writeback írja ki. Nincs explicit read/write syscall, de a memória hozzáférés processz-kontextusban fut; a módosítások msync-ig vagy a writebackig nem feltétlenül device-on. mmap tisztán olvasásnál kényelmes, írásnál a lapozási thrashing és a SIGBUS hiba lehetősége miatt diagnosztikai nehézség.

A sync/async completion elválasztja a syscall visszatérését az adat tényleges elkészültétől. A szinkron read/write a hívás visszatérésekor a másolás megtörtént – a direct I/O-nál a buffer tartalma már nem használható, amíg a hívás nem tért vissza. Az async I/O a completion csatornát (Linux AIO io_submit/io_getevents, vagy io_uring) használ: a buffer lifetime a completion beérkezéséig, nem a submit call visszatéréséig tart. A io_uring a modern kernel asynchronous I/O felülete (kernel 5.1+), amely submission/completion ring buffert használ; a verziószámot a labhoston ellenőrizni kell, mert a régebbi kerneleken csak a libaio vagy az O_DIRECT szinkron út elérhető. A buffer lifetime megszegése use-after-free vagy adatcsere hibához vezet.

A short IO részleges read/write: a kernel kevesebb bájtot másolhat vagy írhat, mint a kért hossz. Szinkron read-nél a signal, a socket vagy a csonka device ad; write-nél hasonlóan. Az alkalmazásnak ciklusban kell újrapróbálni, nem pedig hibaként eldobni. A direct I/O és a nagy blokkok esetén a short IO gyakoribb, mert a device queue, a flexibilis layout vagy a signal megszakíthatja a hosszabb utat.

10.3.3 Kidolgozott példa

A labhost: lab-vm01, UID 1000, user: labuser. A dedicated labkönyvtár: /srv/lab-data egy ext4 filesystemen. A cél megmérni a buffered és direct írási utat. A futtatható C++ program (io-modes.cpp) az 1 MiB-os írást végzi O_DIRECT flaggel vagy anélkül, és két időt ír ki külön: a write()-ciklusét (write_ms) és az fsync()-ét (fsync_ms). Az igazítási követelményt a logikai blokkméret adja (lsblk -no LOG-SEC "$(findmnt -no SOURCE --target /srv/lab-data)"); a stat -c %o csak az ajánlott I/O-méretet mutatja.

// io-modes.cpp; a g++ a _GNU_SOURCE-t (O_DIRECT) előre definiálja
#include <fcntl.h>
#include <unistd.h>
#include <cerrno>
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <cstring>

int main(int argc, char** argv) {
    using clk = std::chrono::steady_clock;
    const size_t size = 1ULL * 1024 * 1024;  // 1 MiB
    void* buf = nullptr;
    if (posix_memalign(&buf, 4096, size) != 0) {
        std::perror("posix_memalign");
        return 1;
    }
    std::memset(buf, 0x5a, size);

    bool direct = (argc > 1 && std::strcmp(argv[1], "direct") == 0);
    int flags = O_WRONLY | O_CREAT | O_TRUNC;
    if (direct) flags |= O_DIRECT;

    int fd = open("/srv/lab-data/io-test.bin", flags, 0644);
    if (fd < 0) {
        std::perror("open");
        std::free(buf);
        return 1;
    }

    auto t0 = clk::now();
    size_t written = 0;
    while (written < size) {
        ssize_t rc = write(fd, static_cast<char*>(buf) + written,
                           size - written);
        if (rc < 0 && errno == EINTR) continue;
        if (rc <= 0) {  // hiba vagy 0 bájt: ne ciklusozzon végtelenül
            std::fprintf(stderr, "write failed: rc=%zd errno=%d\n",
                         rc, rc < 0 ? errno : 0);
            close(fd);
            std::free(buf);
            return 1;
        }
        written += static_cast<size_t>(rc);  // short write kezelés
    }
    auto t1 = clk::now();
    // Tartóssági pont: direct esetén is kell fsync (volatile write cache)
    if (fsync(fd) < 0) {
        std::perror("fsync");  // tartóssági hiba = sikertelen mérés
        close(fd);
        std::free(buf);
        return 1;
    }
    auto t2 = clk::now();

    using ms = std::chrono::duration<double, std::milli>;
    std::printf("mode=%s bytes=%zu write_ms=%.2f fsync_ms=%.2f\n",
                direct ? "direct" : "buffered", size,
                ms(t1 - t0).count(), ms(t2 - t1).count());
    close(fd);
    std::free(buf);
    return 0;
}

Előfeltétel, fordítás és futtatás a labhoston:

# target: lab-vm01, user: labuser, uid=1000, cwd: /home/labuser
# előfeltétel: /srv/lab-data ext4, size >= 1 GiB; a /srv root tulajdonú,
# ezért a labuser írási jogát egyszer létre kell hozni:
sudo install -d -o labuser -g labuser -m 0750 /srv/lab-data
findmnt -no FSTYPE --target /srv/lab-data          # ext4
lsblk -no LOG-SEC "$(findmnt -no SOURCE --target /srv/lab-data)"
g++ -O2 -Wall -std=c++17 io-modes.cpp -o io-modes

./io-modes buffered
./io-modes direct

# cleanup
rm -f /srv/lab-data/io-test.bin

Várható, illusztratív kimenet (hipotetikus, nem mért):

mode=buffered bytes=1048576 write_ms=0.30 fsync_ms=1.10
mode=direct bytes=1048576 write_ms=1.20 fsync_ms=0.15

A két idő szétválasztása mutatja, hol van a device-idő. Buffered módban a write_ms kicsi, mert csak a page cache-be másol; a device-írás és a flush az fsync_ms-ben jelenik meg. Direct módban a write_ms már maga a device-ra írás ideje, az fsync_ms jellemzően csak a write cache flush (és a metaadat). Írásnál a page cache „hideg/meleg” állapota nem számít: az O_TRUNC eldobja a fájl lapjait, az fsync minden futásban kikényszeríti a device-írást. A cache-hatást olvasással lehet megmutatni (lásd a 2. feladatot). A mérési jegyzőkönyvben fel kell tüntetni a filesystem típusát, a logikai blokkméretet, a processz scheduler classát és az fsync jelenlétét.

10.3.4 Hibák és ellenpróbák

Hiba 1: EINVAL O_DIRECT esetén. Ha a buffer nem 4K-aligned (pl. new[]-ból származik), a write EINVAL hibát ad. Diagnosztika: perror, majd a logikai blokkméret ellenőrzése (lsblk -no LOG-SEC, /sys/block/<dev>/queue/logical_block_size vagy statx STATX_DIOALIGN), és a buffer címének, az offsetnek és a hossznak ehhez igazítása. Ellenpróba: malloc és posix_memalign közötti különbség; a malloc általában 16 byte-hoz igazított, nem elég.

Hiba 2: Short write figyelmen kívül hagyása. Ha a program csak a write visszatérését vizsgálja, és nem ciklusban retry-ol, a fájl tartalma hiányos lehet. Normál fájlra a nem nulla hosszú write 0-t nem ad; ha mégis, azt hibaként kell kezelni, különben a retry-ciklus végtelen lesz. A helyes minta a fenti példában látható: while (written < size), EINTR-re újrapróbálás, rc <= 0 esetén kilépés.

Hiba 3: Async buffer lifetime megsértése. A io_uring submit call gyorsan visszatér, de a buffer még a kernel használatában lehet. Ha az alkalmazás a stack bufferre mutató pointert ad le, majd a függvény visszatér, a completion beérkezésekor use-after-free következik be. Diagnosztika: AddressSanitizer, vagy io_uring debug. A verzióellenőrzés: uname -r (kernel 6.8 az Ubuntu 24.04 LTS-ben) és a liburing csomag verziója; a régi kerneleken az io_uring opcode-ok hiányozhatnak.

Hiba 4: A benchmark a page cache-t méri, nem a device sebességet. A dd vagy fio buffered módban nagy memóriára meleg cache mellett irreálisan magas értéket mutat. Először drop_caches vagy direct=1 fio-ban, és a --direct=1 esetén az alignmentet az fio kezeli. A mérési jegyzőkönyvben rögzítendő a fsync megléte, mert anélkül a write cache is torzít.

Ellenpróba: 6.6 előtti kerneleken a tmpfs O_DIRECT megnyitása EINVAL-t adott; a 6.6-os kernel óta (így az Ubuntu 24.04 6.8-as kernelén is) a megnyitás sikeres, de a tmpfs nem kényszerít igazítást, ezért az alignment-hiba tesztjét ext4/XFS labdisken végezd. Az O_DIRECT-támogatás hiányát (és a fallback buffered módot) például egy FUSE-mounton vagy régebbi kernelű tmpfs-en lehet kipróbálni; a statx STATX_DIOALIGN lekérdezésben a 0 értékű stx_dio_offset_align jelzi, hogy a fájlra nincs direct I/O támogatás.

10.3.5 Feladatok

  1. Magyarázó: Miben különbözik a buffered és direct írás tartóssági szerződése? Milyen alignment feltételeket kell teljesíteni a O_DIRECT-hez, és miért?

  2. Adminisztrációs: A lab-vm01-en a /srv/lab-data könyvtárban futtasd le a kidolgozott példát buffered és direct módban, és rögzítsd a write_ms/fsync_ms értékeket. Ezután a cache-hatást olvasással mérd: olvasd be a fájlt drop_caches után (hideg) és még egyszer (meleg). Rögzítsd az időket, a kernel verziót, a filesystem típust, a logikai blokkméretet és a stat -c %o értékét. Értelmezd a különbséget.

  3. Diagnosztikai: Módosítsd a programot úgy, hogy a buffer new[]-ból származzon (malloc-kal) és O_DIRECT flaggel fusson. Jegyezd fel a hibát, az errno-t. Javítsd posix_memalign-re, és futtasd újra. Sikeres-e a direct írás? Ha tmpfs-en próbálod a 6.8-as kernelen, mi történik, és miért nem alkalmas a tmpfs az alignment-teszthez?

10.3.6 Megoldások

1. feladat megoldása: A buffered írás a page cache-be megy, és a write() visszatérése nem jelenti az adat tartósságát; a kernel writeback aszinkron. Direct írásnál a write() közvetlenül a device-ra másol, de a device volatile write cache miatt a tartósságot külön fsync biztosítja. A O_DIRECT alignment feltétele: a user buffer címe, a file offset és a hossz az eszköz logikai blokkméretének (tipikusan 512 B vagy 4096 B; lsblk -no LOG-SEC, kernel 6.1+ alatt statx STATX_DIOALIGN) egész számú többszöröse kell legyen. Ennek oka a kernel/DMA korlát, mert a közvetlen device hozzáférés nem tud tetszőleges címről másolni. Postcondition: a tanuló meg tudja mondani, miért kaphat EINVAL hibát, és hogyan kell ellenőrizni a logikai blokkméretet (nem a stat -c %o-val, ami csak ajánlott I/O-méret).

2. feladat megoldása: A futtatás sorrendje:

# target: lab-vm01, UID 1000, cwd: /home/labuser
# írás: a page cache állapota itt nem számít (O_TRUNC + fsync)
./io-modes buffered   # write_ms kicsi, fsync_ms hordozza a device-időt
./io-modes direct     # write_ms = device-írás, fsync_ms főleg flush

# olvasás: itt látszik a cache-hatás
sync; echo 3 | sudo tee /proc/sys/vm/drop_caches   # root: csak a labVM-en
dd if=/srv/lab-data/io-test.bin of=/dev/null bs=1M   # hideg: device-ról
dd if=/srv/lab-data/io-test.bin of=/dev/null bs=1M   # meleg: page cache
uname -r
findmnt -no FSTYPE --target /srv/lab-data
stat -c %o /srv/lab-data/io-test.bin

A várt trend: íráskor a buffered write_ms jóval kisebb a direct write_ms-nél, de az fsync_ms-sel együtt a két út összideje hasonló nagyságrendű, mert az fsync mindkettőnél a device-ra kényszerít. Olvasáskor a meleg cache-es dd sokkal gyorsabb, mert page cache-találat, nem megy device-ra. A kernel verzió, a filesystem típus és a logikai blokkméret rögzítendő; a stat -c %o csak az ajánlott I/O-méret. Postcondition: a tanuló el tudja választani a cache hatást a device sebességtől.

3. feladat megoldása: A new[] a malloc-hoz hasonlóan általában 16 byte-hoz igazított, nem 4K-hoz. Az O_DIRECT hívásnál a write EINVAL hibát ad, mert a buffer címe nem felel meg. A posix_memalign(&buf, 4096, size) használata megoldja az alignmentet. Ha a fájl tmpfs-en van, 6.6 előtti kernelen az open O_DIRECT-tel EINVAL-t adott; a 6.8-as kernelen a megnyitás sikeres, és tmpfs-en az igazítatlan buffer sem ad EINVAL-t, mert a tmpfs nem kényszerít igazítást – ezért az alignment-tesztet ext4/XFS labdisken kell végezni. Postcondition: a tanuló a hibát képes az errno, a filesystem típus és a buffer cím ismeretében root-cause-ra vezetni, és nem a kernel hibáját feltételez.

10.3.7 Rövid összefoglaló

A buffered I/O a page cache-en át dolgozik, a write() nem garantál tartósságot; a direct I/O (O_DIRECT) a cache-t megkerüli, de a user buffer, az offset és a hossz az eszköz logikai blokkméretéhez igazított kell legyen, különben EINVAL. A direct írás után is szükség lehet fsync-re a device volatile cache miatt. Az async I/O (libaio, io_uring) a buffer lifetime-ot a completionig hosszabbítja; a short read/write ciklusban retryolandó. A benchmark csak akkor értelmes, ha a page cache state, a fsync és a filesystem típus rögzítve van. Továbbhasznált definíciók: buffered I/O, O_DIRECT alignment contract, async completion buffer lifetime.
