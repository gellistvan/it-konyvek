9.5 Memória-, swap- és cgroup labor

9.5.1 Motiváció

Egy üzemeltetett Linux szolgáltatásnál a legkellemetlenebb memóriaproblémák ritkán reprodukálhatók a fejlesztői gépen. A host free kimenete még „elég memóriát” mutat, miközben a service belassul, vagy a cgroup OOM killer (out-of-memory killer) leöli a folyamatot. A feladat ilyenkor nem a host egészének kimerítése, hanem az, hogy egy korlátozott, megismételhető laborban megértsük, hogyan számolja el a Linux a memóriát process és cgroup nézetben, mi történik egy túl alacsony MemoryMax limitnél, és milyen bizonyítékokból lehet javítási tervet készíteni. A cél az alábbiakban az, hogy a szenior fejlesztő a C++ allocator és virtual memory hátterét a Linux üzemeltetési modelljéhez kösse anélkül, hogy a hostot veszélyeztetné.

9.5.2 Definíció és működés

A cgroup v2 erőforrásmodell alfejezetben bevezetett cgroup v2 memóriamodell szerint a kernel minden cgroup számára karbantartja a memory.current számlálót: ez az adott cgroupba tartozó processzek és kernelstruktúrák által jelenleg foglalt, fizikailag lefoglalt memóriát jelenti. A Lapozás, page fault, mmap és copy-on-write és a Page cache, reclaim, swap és overcommit alfejezet alapján a virtuális címfoglalás malloc/mmap esetén nem azonnal fizikai lapfoglalás; a lapok demand-zero vagy file-backed módon akkor jönnek létre, amikor a processz címeire először írunk.

A processz nézetben a leggyakrabban használt mutatók:

  • RSS (resident set size): a processzhez tartozó, fizikai RAM-ban lévő lapok, swap nélkül.
  • PSS (proportional set size): a megosztott lapok arányosított része; több processzt is tartalmazó mappingek vizsgálatánál igazságosabb.
  • USS (unique set size): csak az adott processz által privát módon használt lapok.

A cgroup nézet memory.current ettől eltér: tartalmazza az anon (névtelen) lapokat, a file (page cache) lapokat, a kernel stack, slab és socket memóriát is, még akkor is, ha azok nem jelennek meg a processz RSS-ében. Ezért a ps RSS és a cgroup memory.current összehasonlítása fontos diagnosztikai lépés.

A kernel PSI (Pressure Stall Information) felülete a /proc/pressure/memory alatt azt mutatja, hogy a processz(ek) mennyi időt várakoztak memória-visszanyerésre (reclaim) az adott időablakban. A some avg10=... azt jelzi, hogy legalább egy processz stallolt; a full avg10=... azt, hogy minden processz. A PSI ezért jobb „lassulásmérő”, mint a pillanatnyi szabad memória.

A systemd MemoryHigh és MemoryMax propertyket a cgroup v2 memory.high és memory.max írja be. A MemoryHigh egy puha limit, amelyik throttlingot és agresszív reclaimet indít; a MemoryMax kemény felső határ, amelynél a kernel a cgroupon belül OOM killt hajthat végre. A Restart=on-failure és a StartLimitBurst/StartLimitIntervalSec együtt szabályozza, hogy egy OOM miatt elhalt service ne jusson végtelen újraindulási ciklusba.

A C++ allocator szempontjából a malloc/new char[] által visszaadott (nem inicializált) virtuális terület csak akkor válik RSS-sé, ha írunk bele. Figyelem: a std::vector<char>(n) konstruktor érték-inicializál, azaz nullával tölt, így már a konstruktor érinti a lapokat. Az ilyen foglalásokat a kernel gyakran demand-zero page-ként adja vissza: minden lap ugyanarra a nullás lapra mutat, amíg írás nem éri. Ezért a „memória fogy” állítás csak akkor igaz, ha a mért mutató a memory.current vagy a tényleges RSS, nem a processz virtuális mérete (VSZ, VmSize).

A transparent hugepage (THP) a kernel 2 MiB-os (x86-64) lapokba is összefoghat anon mappingeket; a AnonHugePages az smaps-ban látható. Ez nem csökkenti a memóriaszámítást, de befolyásolja a reclaim és a mérési pontosságot. NUMA esetén a numa_maps/numastat megmutatja, hogy a memória melyik NUMA node-on van; egyetlen node-os laborban ez triviális, de a fogalmi modellt akkor is megfigyelhetjük.

9.5.3 Kidolgozott példa

A labor a labhost1 nevű izolált Ubuntu Server 24.04 LTS labVM-en fut; a parancsokat labuser (UID 1000) adja, a rendszermódosításokhoz sudo van. A laborerőforrások lab- prefixet kapnak; a host memóriáját nem visszük a 80%-os kihasználtság fölé.

Előfeltétel: a g++ telepítése és a systemd cgroup v2 mount ellenőrzése:

# labhost1; labuser (uid=1000)
g++ --version | head -n 1
test "$(stat -fc %T /sys/fs/cgroup/)" = "cgroup2fs" && echo "cgroup v2 OK"

Készítsünk egy rövid, kizárólag a memóriaviselkedést vizsgáló programot, amely paraméterként MiB-ot kap, foglal, érinti a memóriát, majd 30 másodpercig fut. Ez nem új C++ nyelvi oktatás, hanem a Linux memóriamodellhez kötött mérőeszköz:

// lab_mem_alloc.cpp
#include <chrono>
#include <cstdio>
#include <cstring>
#include <iostream>
#include <memory>
#include <string>
#include <thread>

int main(int argc, char **argv) {
    if (argc != 2) {
        std::cerr << "usage: lab_mem_alloc MIB\n";
        return 2;
    }
    const std::size_t mib = std::stoull(argv[1]);
    const std::size_t bytes = mib * 1024 * 1024;
    // default-init: csak virtuális cím (overcommit), nincs nullázás
    std::unique_ptr<char[]> buffer(new char[bytes]);
    // touch: a lapok az írásnál válnak residentté
    std::memset(buffer.get(), 0x55, bytes);
    // a pointer kiírása megakadályozza, hogy a fordító elhagyja a puffert
    std::printf("touched %zu MiB at %p\n", mib,
                static_cast<void*>(buffer.get()));
    std::fflush(stdout);
    std::this_thread::sleep_for(std::chrono::seconds(30));
    return 0;
}

Fordítás és telepítés:

# labhost1; labuser -> sudo a telepítéshez
g++ -std=c++20 -O2 -Wall -Wextra -o lab_mem_alloc lab_mem_alloc.cpp
sudo install -o root -g root -m 0755 lab_mem_alloc /usr/local/bin/lab_mem_alloc

Indítsuk a programot systemd transient unitban, kemény 128 MiB korláttal; a program viszont 256 MiB-ot próbál foglalni és érinteni. Így a MemoryMax alatt várhatóan OOM kill következik be. A Restart=on-failure a crash loopot is demonstrálja, amit a StartLimitBurst korlátoz:

# labhost1; labuser -> sudo: rendszerszintű systemd-run
sudo systemd-run \
  --unit=labmemtest \
  --property=MemoryHigh=96M \
  --property=MemoryMax=128M \
  --property=MemorySwapMax=0 \
  --property=Restart=on-failure \
  --property=StartLimitIntervalSec=30 \
  --property=StartLimitBurst=3 \
  /usr/local/bin/lab_mem_alloc 256

A foglalás viselkedését külön terminálból figyeljük. A process- és cgroup nézetet egyszerre használjuk:

# labhost1; labuser; csak olvasás
systemctl show labmemtest -p MainPID -p ControlGroup \
  -p MemoryCurrent -p MemoryPeak -p ActiveState -p SubState -p Result
PID=$(systemctl show -p MainPID --value labmemtest)
ps -o pid,rss,vsz,cmd -p "$PID"
grep -E '^(Rss|Pss|AnonHugePages)' "/proc/$PID/smaps_rollup"
CG=/sys/fs/cgroup/system.slice/labmemtest.service
grep -E '^anon |^file |^slab ' "$CG/memory.stat"
cat /proc/pressure/memory

Az első sorban a MainPID még élhet, a MemoryCurrent folyamatosan nő, ahogy a memset ír. Illusztratív közbenső kimenet:

MainPID=11234
ControlGroup=/system.slice/labmemtest.service
MemoryCurrent=67108864
MemoryPeak=67108864
ActiveState=active
SubState=running
Result=success

A 128 MiB-on a kernel a cgroupban OOM killt hajt végre; a process SIGKILL-t kap, a systemd ezt oom-kill resultként mutatja. A MemoryPeak értéke a limithez közeli. A kill utáni restart-késleltetésben (alapértelmezés 100 ms) a minta például:

MainPID=0
ControlGroup=/system.slice/labmemtest.service
MemoryCurrent=0
MemoryPeak=134217728
ActiveState=activating
SubState=auto-restart
Result=oom-kill

A MainPID=0 és a SubState=auto-restart azt jelzi, hogy a systemd a restart-késleltetésben van; ezért 0 a MemoryCurrent. Az újraindított processz már új PID-et kap, és a MemoryCurrent újra nőni kezd.

A naplóban a kernel és a systemd nézet is látható:

# labhost1; labuser; csak olvasás
journalctl -u labmemtest -b --no-pager | tail -n 30
journalctl -k -b --no-pager | grep -i 'Killed process' | tail -n 5

Várható, nem mért, hibajelenséget mutató sorok:

labmemtest.service: A process of this unit has been killed by the OOM killer.
Memory cgroup out of memory: Killed process 11234 (lab_mem_alloc) total-vm:...
systemd[1]: labmemtest.service: Failed with result 'oom-kill'.

A memória-limit és restart politika kapcsolatát a systemctl status labmemtest mutatja. Ha a unit többször elhal, a StartLimitBurst elérése után start-limit-hit állapotba kerül, és nem próbálkozik tovább:

systemd[1]: labmemtest.service: Start request repeated too quickly.
systemd[1]: labmemtest.service: Failed with result 'start-limit-hit'.

A THP/NUMA megfigyeléshez a futó PID-et használjuk, mielőtt a limit elérné:

# labhost1; labuser; csak olvasás; ha a PID él
PID=$(systemctl show -p MainPID --value labmemtest)
cat /sys/kernel/mm/transparent_hugepage/enabled
grep -E '^(AnonHugePages|FilePmdMapped|ShmemPmdMapped)' /proc/$PID/smaps \
  | head -n 5
cat /proc/$PID/numa_maps | head -n 5
# ha a numactl csomag telepítve van:
numastat -p $PID

Az /sys/kernel/mm/transparent_hugepage/enabled tényleges kimenete a kernelprofil függvénye; a fájl mindig mindhárom opciót listázza, a kiválasztott szögletes zárójelben, például always [madvise] never vagy [always] madvise never. A numa_maps pedig legalább egy NUMA node-hoz rendeli a mappingeket; a labVM gyakran egyetlen node-ot lát.

A kidolgozott példa végén csak a unitot takarítjuk; a lab_mem_alloc bináris és forrás a Feladatokhoz megmarad (a teljes cleanup az alfejezet végén, a Megoldások után áll):

# labhost1; labuser -> sudo
sudo systemctl stop labmemtest.service 2>/dev/null || true
sudo systemctl reset-failed labmemtest.service 2>/dev/null || true

Postcondition: a labmemtest.service nem aktív, nem failed; a /usr/local/bin/lab_mem_alloc megmarad; a labor egyéb folyamatai és a host memóriaállapota nem károsodtak.

9.5.4 Hibák és ellenpróbák

Tünet: a service OOM killt kap, de a free -h sok szabad memóriát mutat.
Hipotézis: a MemoryMax cgroup limit alacsony, nem a host memória fogyott el.
Adatgyűjtés: systemctl show labmemtest -p MemoryMax, journalctl -k | grep 'Memory cgroup', cat /sys/fs/cgroup/system.slice/labmemtest.service/memory.max.
Egy változtatás: növeld a MemoryMax értéket a tényleges munkakészlet fölé, vagy csökkentsd a program által foglalt MiB-ot.
Verification: a process 30 másodpercig fut, Result=success, MemoryPeak a limit alatt marad.

Tünet: a malloc/vector hívás sikeres, mégis OOM kill jön később.
Hipotézis: a Linux overcommit miatt a malloc/new char[] csak virtuális címet foglal; a lapok az első írásnál (itt a memset-nél) jönnek létre, és ott ütköznek a cgroup limitbe. (A std::vector<char>(n) már a konstruktorban nulláz, ott maga a konstruktor ütközik a limitbe.)
Adatgyűjtés: cat /proc/sys/vm/overcommit_memory, journalctl -k.
Javítás: ne az allokáció visszatérését tekintsd sikernek; a tényleges lapérintést is mérni kell. A tervezésnél a MemoryHigh/MemoryMax headroomot a peak working setre kell igazítani.

Tünet: a service ismételten újraindul, majd start-limit-hit állapotba kerül.
Hipotézis: a Restart=on-failure OOM után is újraindul, de a túl alacsony limit miatt mindig újra elhal.
Adatgyűjtés: systemctl status labmemtest, journalctl -u labmemtest -b.
Javítás: változtass egyszerre egy dolgot: emeld a MemoryMax-ot a munkakészlet fölé, és systemctl reset-failed labmemtest.service; ne kapcsold ki globálisan a cgroup limitet.

Tünet: a process RSS nagyon alacsony, de a cgroup memory.current magas.
Hipotézis: a memory.current tartalmazza a page cache, slab és kernel stack memóriát, ami az RSS-ben nem jelenik meg.
Adatgyűjtés: grep -E '^anon |^file |^slab ' /sys/fs/cgroup/.../memory.stat.
Következmény: a service-es diagnosztikában ne csak a ps RSS-t figyeld; a cgroup memory.current az operatív számláló.

A THP/NUMA megfigyelésnél gyakori hiba, hogy a mérést a service rövid élettartama miatt kihagyjuk. Érdemes a mérést a MemoryHigh alatt, a memset lefutása után, de a 30 másodperces sleep közben végezni. A másik hiba, hogy a MemoryCurrent=0 értékből arra következtetünk, hogy nincs memóriafogyás; valójában a MainPID=0 és SubState=auto-restart szerint a unit a kill utáni restart-késleltetésben van.

9.5.5 Feladatok

9.5.5.1 1. Magyarázó feladat

Futtasd a lab_mem_alloc programot korlát nélkül systemd-run-ben, 128 MiB-tal, majd 256 MiB-tal is. Minden futásnál rögzítsd a process RSS-t (ps), a cgroup memory.current értéket és a smaps_rollup Rss/Pss/AnonHugePages értékeket. Magyarázd el, miért lehet a memory.current nagyobb a process RSS-nél, és miért nem elegendő az allokáció méretéből következtetni a fizikai memóriafoglalásra.

9.5.5.2 2. Adminisztrációs/konfigurációs feladat

Készíts tartós systemd unitot labmemtest-svc.service néven, amely a lab_mem_alloc programot 192 MiB paraméterrel futtatja. Állíts be MemoryHigh=224M, MemoryMax=256M, MemorySwapMax=0, Restart=on-failure, StartLimitIntervalSec=30 és StartLimitBurst=3 értékeket (figyelj arra, melyik kulcs melyik unit-szakaszba tartozik). Indítsd el, és ellenőrizd, hogy a service 30 másodpercig fut, nem OOM-ol, és a memory.current a MemoryHigh alatt stabilizálódik. Írd le a pull request/runbook szintű állapotot: desired state, observed state, várt postcondition.

9.5.5.3 3. Diagnosztikai/failure/recovery feladat

A laborban a labmemtest service OOM-killt szenvedett, majd start-limit-hit állapotba került. Gyűjts bizonyítékot journalctl, systemctl show, PSI, smaps és numa_maps segítségével. Készíts root-cause alapú javítási tervet: döntsd el, hogy a MemoryMax növelése vagy a program munkakészletének csökkentése indokolt. Módosíts pontosan egy változót, indítsd újra a service-t, és ellenőrizd, hogy a 30 másodpercnyi futás OOM nélkül teljesül.

9.5.6 Megoldások

9.5.6.1 1. Megoldás

A korlát nélküli futtatáshoz:

# labhost1; labuser -> sudo
sudo systemd-run --unit=labmemtest-open \
  --property=MemoryMax=infinity /usr/local/bin/lab_mem_alloc 128
sleep 5
systemctl show labmemtest-open -p MainPID -p ControlGroup \
  -p MemoryCurrent -p MemoryPeak
PID=$(systemctl show -p MainPID --value labmemtest-open)
ps -o pid,rss,vsz,cmd -p "$PID"
grep -E '^(Rss|Pss|AnonHugePages)' /proc/$PID/smaps_rollup
CG=/sys/fs/cgroup/system.slice/labmemtest-open.service
grep -E '^anon |^file |^slab ' "$CG/memory.stat"
# cleanup
sudo systemctl stop labmemtest-open.service
sudo systemctl reset-failed labmemtest-open.service

A 128 MiB toucholt lap után az RSS és a cgroup memory.current közelít egymáshoz, de a cgroup tartalmazhat néhány MiB kernel stacket/slab-et is. A 256 MiB-os változatnál a memory.current ~256 MiB körül lesz, a PSS/RSS szintén. A magyarázat: a memory.current a cgroup teljes memóriaéletciklusát tartalmazza; a process RSS csak a processhez rendelt anon/file resident lapokat; a shared lapok PSS körül látszanak. A new char[] nem garantál fizikai foglalást addig, amíg a memset nem ír a lapokra (a std::vector<char>(n) viszont már a konstruktorban nulláz és érint). Postcondition: a labmemtest-open unit nem fut; a /usr/local/bin/lab_mem_alloc megmarad a további feladatokhoz.

9.5.6.2 2. Megoldás

A tartós unit:

# /etc/systemd/system/labmemtest-svc.service
# labhost1; labuser -> sudo a telepítéshez
[Unit]
Description=Lab memory-limited service
# a start-limit kulcsok a [Unit] szakaszba tartoznak
StartLimitIntervalSec=30
StartLimitBurst=3

[Service]
ExecStart=/usr/local/bin/lab_mem_alloc 192
MemoryHigh=224M
MemoryMax=256M
MemorySwapMax=0
Restart=on-failure

[Install]
WantedBy=multi-user.target

Telepítés és indítás:

# labhost1; labuser -> sudo
sudo install -o root -g root -m 0755 lab_mem_alloc /usr/local/bin/lab_mem_alloc
sudo cp labmemtest-svc.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start labmemtest-svc
sleep 5
systemctl status --no-pager labmemtest-svc
systemctl show labmemtest-svc -p MainPID -p MemoryCurrent \
  -p MemoryPeak -p Result
CG=/sys/fs/cgroup/system.slice/labmemtest-svc.service
grep -E '^anon |^file |^slab ' "$CG/memory.stat"
grep -E '^(high|max|oom_kill) ' "$CG/memory.events"

A unitfájl telepítés előtt ellenőrizhető: systemd-analyze verify labmemtest-svc.service nem adhat „Unknown key” figyelmeztetést (ha a StartLimit* kulcsok a [Service] szakaszba kerülnének, a systemd figyelmen kívül hagyná őket).

Desired state: aktív service, Result=success, MemoryCurrent 192–200 MiB, MemoryHigh 224 MiB, MemoryMax 256 MiB. Observed state: a systemd unit active (running), MainPID stabil, MemoryCurrent ≈ 192 MiB ≤ MemoryPeak < MemoryHigh (224 MiB), a memory.events high 0, oom_kill 0. Ellenpróba: MemoryHigh=160M mellett a 192 MiB-os, swap nélküli munkakészlet nem fér a puha limit alá; a memory.events high számlálója gyorsan nő, a memory.pressure some avg10 megugrik, a futás lelassul – ez a throttle bizonyítéka, nem stabil állapot. A postcondition: a service 30 másodperc után kilépett, a unit inactive (dead); a labor nem hagy futó processzt. A rollback: sudo systemctl stop labmemtest-svc, sudo rm /etc/systemd/system/labmemtest-svc.service, sudo systemctl daemon-reload.

9.5.6.3 3. Megoldás

Diagnosztikai lépések:

# labhost1; labuser; csak olvasás
systemctl status --no-pager labmemtest
journalctl -u labmemtest -b --no-pager | grep -E 'OOM|oom-kill|start-limit'
journalctl -k -b --no-pager | grep -i 'Killed process' | tail -n 5
cat /proc/pressure/memory

A mért MemoryPeak a 128 MiB-os limitnél áll meg, a program 256 MiB-ot igényelt; tehát a hiba oka a limit és a working set eltérése. A javítási terv: egyetlen változó, a MemoryMax emelése 128 MiB-ról 320 MiB-ra; a program továbbra is 256 MiB-tal fut, a többi property (köztük a MemoryHigh=96M) változatlan. (A 96 MiB-os MemoryHigh a 256 MiB-os munkakészletet throttle-olja; ha ez a futásidőt elfogadhatatlanul nyújtja, a MemoryHigh emelése egy második, külön mért lépés.) A transient unit nem fájlból él, ezért nem szerkesztjük: a failed állapot törlése után ugyanazzal a névvel, az egy módosított propertyvel indítjuk újra. A rollback: ugyanez a parancs MemoryMax=128M-mel.

# labhost1; labuser -> sudo
sudo systemctl stop labmemtest.service 2>/dev/null || true
sudo systemctl reset-failed labmemtest.service
sudo systemd-run --unit=labmemtest \
  --property=MemoryHigh=96M \
  --property=MemoryMax=320M \
  --property=MemorySwapMax=0 \
  --property=Restart=on-failure \
  /usr/local/bin/lab_mem_alloc 256

Ellenőrzés:

sleep 5
systemctl show labmemtest -p MemoryMax -p MemoryPeak -p Result
journalctl -u labmemtest -b --no-pager | tail -n 20
sleep 30
systemctl show labmemtest -p Result -p ActiveState

Várható (illusztratív): MemoryMax=335544320, MemoryPeak ≈ 256–262 MiB, OOM-kill nincs, a 30 másodperc után Result=success és a unit inaktív. A PSI some értéke a MemoryHigh fölötti throttle miatt a foglalás alatt emelkedik, a futás után visszaesik. Postcondition: OOM nem következik be, a start-limit feloldódott, a labmemtest 256 MiB-tal sikeresen lefut.

9.5.7 Rövid összefoglaló

A memóriaüzemeltetésben a processz RSS és a cgroup memory.current más kérdésre válaszol: az RSS az adott processz resident lapjait, a cgroup a teljes memóriaélettér számlálóját mutatja. A MemoryMax a cgroup v2 kemény limitje, a MemoryHigh puha throttling; a Restart=on-failure és StartLimitBurst együttesen kezeli a crash loopot. A labor a lab_mem_alloc C++ programmal, systemd-run/unit korlátokkal és smaps/PSI/NUMA megfigyeléssel bizonyítja, hogy a nem inicializált (malloc/new char[]) memória csak lapérintés után válik residentté, és hogy a túl alacsony limit OOM killhez, nem a host kimerüléséhez vezet. A javítási terv mindig egy változóra koncentráljon: emeljük a limitet, vagy csökkentsük a munkakészletet, és mérjük a cgroup MemoryPeak-ot.

Továbbhasznált definíciók: RSS a processhez tartozó fizikai resident lapok; memory.current a cgroup aktuális, fizikailag foglalt memória mennyisége; OOM kill a kernel által a cgroup memory.max túllépésekor végrehajtott processz leállítás.

Az alábbi hivatkozások kiindulópontok, nem olvasott bizonyítékok ebben a kérésben:

  • Linux proc man pages
  • systemd dokumentáció

Állításonkénti forrásindex (viszonyítási pont: Ubuntu Server 24.04 LTS, 6.8-as GA kernel, systemd 255):

A systemd-run transient unit Restart/StartLimit* property támogatását, a smaps_rollup pontos mezőit és a numastat/numa_maps kimenetet a labor indításakor az adott kernel ellenőrzése előtt nem veszem adottnak.
