56.4 Platform game day és recovery

56.4.1 Motiváció és definíció

A d278-ban felépített platform már rendelkezik GitOps deliveryvel, observabilityvel, network policyvel és állapotmentéssel. A d279 game day célja, hogy ezeket a képességeket ne dokumentációból, hanem ellenőrzött hibainjektálással tesztelje. A gyakorlat során a csapat előre definiált hibafixture-öket kap, és az a feladata, hogy a tüneteket a megfelelő rendszerréteghez rendelje, adatokkal igazolja a hipotézist, majd egyetlen változtatással hajtsa végre a controlled recoveryt. A game day nem az “ügyeskedés” versenye, hanem a runbook, a timeline és a postmortem minőségének auditja.

Definíciók:

  • Game day (platform game day): szimulált, előre megtervezett hibagyakorlat, amelyben a produkciószerű környezetet izolált labclusteren, kontrollált blast radius mellett terhelik. Minden injektált hiba visszafordítható, és a gyakorlat után a teljes erőforráskészlet cleanup alá esik.

  • Controlled recovery: olyan helyreállítás, amely nem egyetlen sürgős művelet, hanem döntési pontokkal tagolt folyamat: tünet rögzítése, hipotézis, adatgyűjtés, egy változtatás, verification, és szükség esetén rollback. A döntést az SLO és az adatállapot együttesen vezérli, nem a “minél gyorsabban bármit” elv.

  • Fixture: a game day előre elkészített hibás állapota, amelyet a gyakorlatvezető vagy a pipeline aktivál. A fixture nem production adatot használ, hanem lab- prefixű, eldobható erőforrásokat.

A tünetek rétegbe sorolása a Kubernetes verem mentén:

Réteg Példa tünet Elsődleges diagnosztikai objektum
Node/runtime NotReady, OOMKilled, CrashLoopBackOff, ImagePullBackOff kubectl describe node, kubectl get events -n ..., kubelet log
Network Pending, Gateway 503, DNS timeout, MTU frag, policy drop kubectl get endpoints, kubectl describe httproute, kubectl exec + tcpdump
Storage PVC Pending, attach error, volume corruption, capacity full kubectl describe pvc, csi driver log, kubectl exec + fsck/checksum
Policy/identity RBAC denied, admission rejected, secret rotation hiba kubectl auth can-i, admission event, kubectl describe secret
Control plane API lassú, etcd quorum loss, scheduler leáll kubectl get --raw=/readyz, etcdctl endpoint health

56.4.2 Kidolgozott példa: canary image pull + secret rotation

Környezet

A labcluster a d276 kanonikus lab-k8s clustere (lab-k8s-admin context), a workload a lab-app namespace, a GitOps repository a lab-platform, az Argo CD Application a lab-app-platform. A stabil payment-srv Deployment 3 replikát futtat, a canary payment-srv-canary Deployment 1 replikát kap, és a Gateway API payment-srv-route HTTPRoute a canary súlyát 10%-ra állítja. A d277 digest-alapú promotionje szerint mindkét Deployment digesttel hivatkozik az image-re: a canary a lab-registry.local:5000/payment-srv@sha256:<rc1-digest> (a v2.1.0-rc.1 release) image-et futtatja, a registry-hitelesítéshez a lab-registry-cred Secretet használja, amelyet az External Secrets Operator a lab titokkezelőjéből tölt (d278).

A hiba beinjektálása

A game day vezető két, egymástól független hibát injektál:

  1. a GitOps repóban a canary image-hivatkozását egy nem létező digestre állítja (…/payment-srv@sha256:<nem-létező-digest>, a meg nem épült rc.2 „release”);
  2. a registryben visszavonja a lab-deploy tokent, de a titokkezelőben, így a clusterben is a régi token marad — a credential tehát minden pullnál érvénytelen, a meglévő image-eknél is.

Tünet

A canary pod ImagePullBackOff állapotba kerül, a Gateway 5xx-et ad vissza a canary útvonalon. 80 másodperc után a kubectl get pods -n lab-app ezt mutatja (illusztratív):

NAME                                  READY   STATUS             RESTARTS   AGE
payment-srv-7d5f9c8b-abc1             1/1     Running            0          10m
payment-srv-7d5f9c8b-def2             1/1     Running            0          10m
payment-srv-7d5f9c8b-ghi3             1/1     Running            0          10m
payment-srv-canary-6f4d8c9-xyz7       0/1     ImagePullBackOff   0          80s

A csapat a tünetet a runtime réteghez rendeli, mert a pod nem indul el. Az első hipotézis: az image-hivatkozás rossz. A helyes döntés előtt ellenőrizni kell a registry credential állapotát is, mert a fixture két hibát tartalmaz.

Adatgyűjtés

A pod eseményei:

Várható kimenetrészlet (illusztratív, rövidítve; a R a lab-registry.local:5000/payment-srv rövidítése):

A not found csak az első hibát mutatja. A második hibát egy biztosan létező image (a stabil rc1 digest) pullja választja el, amely a lejárt tokennel 401 Unauthorized-dal bukik. A token érvényességét nem a Secret tartalma, hanem a registry válasza dönti el:

# target: lab-wn2 (worker node), privilege: sudo
# a stabil rc1 digest a d277 szerinti release evidence-ből
RC1_DIGEST=$(jq -r .generated.image.digest release-evidence-rc1.json)
sudo crictl pull --creds "lab-deploy:$TOKEN" \
  "lab-registry.local:5000/payment-srv@${RC1_DIGEST}"
# vagy közvetlenül a registry API-ja:
curl -sS -o /dev/null -w '%{http_code}\n' -u "lab-deploy:$TOKEN" \
  https://lab-registry.local:5000/v2/
# Várt (illusztratív): 401 – a clusterben lévő token érvénytelen

A $TOKEN a clusterben lévő Secretből kiolvasott érték; a parancsot a token kiírása nélkül, a game day-jegyzőkönyvbe csak az eredményt rögzítve futtatjuk. A diagnózis megerősíti, hogy két hiba együtt áll fenn: a hivatkozott image nem létezik, és a credential sem érvényes.

Az alábbi ábra a game day időbeli lefutását és a controlled recovery döntési logikáját mutatja. A burn rate a hibaarány és a hibakeret hányadosa: 99,9%-os SLO mellett 3% / 0,1% = 30×.

Controlled recovery döntés

A canary a forgalom 10%-át kapja, így a user-facing SLI romlik: a 5xx arány 0,1%-ról 3%-ra nő. A d276 99,9%-os SLO-ja (budget 0,1%) mellett ez 3 / 0,1 = 30-szoros burn rate (hipotetikus, lab fixtureből számított érték). Ha a canary minden kérése hibás lenne, a 10%-os súly kb. 10%-os hibaarányt és 100-szoros burn rate-et adna; a 3% azt feltételezi, hogy a Gateway a kérések egy részét a stabil backendre újrapróbálja. A d255-ben tanultak szerint ez egyértelmű rollback trigger. A recovery nem a registry image létrehozása, hanem a canary forgalmának elvétele és a canary visszaállítása a stabil digestre. Emellett a tokent a titokkezelőben rotálni kell, hogy a jövőbeli promotion ne ütközzön ugyanebbe.

A változtatás a lab-platform GitOps repository apps/payment-srv/ könyvtárában egyetlen commit. A canary Deployment (teljes manifest, hogy a selector és a pod-label is látszódjon):

# apps/payment-srv/canary.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-srv-canary
  namespace: lab-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: payment-srv
      track: canary
  template:
    metadata:
      labels:
        app: payment-srv
        track: canary
    spec:
      imagePullSecrets:
        - name: lab-registry-cred
      containers:
        - name: payment-srv
          image: lab-registry.local:5000/payment-srv@sha256:<rc1-digest>

A HTTPRoute ugyanebben a commitban a canary súlyát 0-ra állítja (részlet, csak a módosított mező; # ... a változatlan részek helyén):

# apps/payment-srv/route.yaml (részlet)
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: payment-srv-route
  namespace: lab-app
spec:
  # ...
  rules:
    - backendRefs:
        - name: payment-srv
          port: 8080
          weight: 100
        - name: payment-srv-canary
          port: 8080
          weight: 0

A registry-credentialt nem commitoljuk nyers Secretként: a base64 nem titkosítás. A repóban csak az ExternalSecret hivatkozás van; a rotációt a titokkezelőben végezzük (új lab-deploy token), az operátor a refreshInterval szerint frissíti a clusterbeli Secretet:

# apps/payment-srv/registry-cred.yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: lab-registry-cred
  namespace: lab-app
spec:
  refreshInterval: 1h
  secretStoreRef:
    kind: ClusterSecretStore
    name: lab-vault
  target:
    name: lab-registry-cred
    template:
      type: kubernetes.io/dockerconfigjson
      data:
        .dockerconfigjson: "{{ .dockerconfig }}"
  data:
    - secretKey: dockerconfig
      remoteRef:
        key: lab/registry/lab-deploy
        property: dockerconfigjson

A commit után az Argo CD szinkronizál; előtte megnézzük a diffet. A --force kapcsolót nem használjuk: az törli és újralétrehozza az erőforrást, recoveryben csak indokolt esetben kell:

argocd app diff lab-app-platform
argocd app sync lab-app-platform

A verification:

ns=(--context lab-k8s-admin --namespace lab-app)
kubectl "${ns[@]}" rollout status deployment/payment-srv-canary
kubectl "${ns[@]}" get pods -l app=payment-srv
kubectl "${ns[@]}" get httproute payment-srv-route \
  -o jsonpath='{.spec.rules[0].backendRefs[*].weight}{"\n"}'
# Várt: 100 0

A rollout sikeres, a canary pod Running a stabil digesttel, és a HTTPRoute súlyai szerint a Gateway csak a stabil backendre irányít. A Secret rotáció utáni image pull teszt egy explicit, a rotált Secretet használó pod:

ns=(--context lab-k8s-admin --namespace lab-app)
RC1_DIGEST=$(jq -r .generated.image.digest release-evidence-rc1.json)
kubectl "${ns[@]}" run lab-pull-test \
  --image="lab-registry.local:5000/payment-srv@${RC1_DIGEST}" \
  --image-pull-policy=Always --restart=Never \
  --overrides='{"spec":{"imagePullSecrets":[{"name":"lab-registry-cred"}]}}' \
  --command -- /bin/true
kubectl "${ns[@]}" get pod lab-pull-test -o jsonpath='{.status.phase}{"\n"}'
# Várt: Succeeded (ha az image-ben nincs /bin/true, a Pulled esemény és az
# ErrImagePull hiánya igazolja a pullt)
kubectl "${ns[@]}" delete pod lab-pull-test

A postcondition: a canary Deployment a stabil digestet használja, a canary súlya 0, a registry-token érvényes (a pull teszt sikeres), az SLI visszaáll a baseline-ra. A timeline rögzíti a tünet észlelésétől a rollout befejezéséig eltelt időt.

56.4.3 Tipikus hibák és ellenpróbák

  1. Réteg-attribúció nélküli “mindent megpróbálok” – A CrashLoopBackOff esetén a csapat először skáláz, töröl podot, újraindít node-ot, de a root cause egy admission vagy secret hiba. Az ellenpróba: minden beavatkozás előtt explicit hipotézis és az ahhoz tartozó, egyetlen megfigyelhető adat.

  2. A GitOps desired state figyelmen kívül hagyása – A canary manifest kézzel kubectl edit-tel javítva drifthez vezet. Az Argo CD a következő sync során felülírja a javítást, mert a Git repository a source of truth. A d241 szerint a GitOps reconciliation a desired state-ből indul. Az ellenpróba: a változtatást csak a Git repository-ban, commit + sync formában hajtjuk végre.

  3. Az etcd restore túlzott alkalmazása – Amikor egyetlen deployment hibás, az etcd restore az összes névtér állapotát visszaállítja, és az utána keletkezett adatok elvesznek. Az adatállapot döntésnél a blast radius a döntő. Az ellenpróba: először a hiba hatókörét mérjük fel; az etcd restore csak a control plane korrupció vagy quorum loss esetén indokolt.

  4. A volume integritás ellenőrzésének kihagyása – A restore után a pod fut, de az adat checksum hibás. A PVC restore akkor sikeres, ha az alkalmazás szintű integritásellenőrzés (pl. sha256sum, pg_dumpall) zöld. Az ellenpróba: a restore verification mindig tartalmaz alkalmazásbeli read és checksum műveletet.

  5. Timeline nélküli game day – A gyakorlat során a csapat nem rögzíti az időpontokat, ezért a postmortem nem tudja megmondani, hogy az MTTR javult-e. Az ellenpróba: a game day script minden lépést date -u +%FT%TZ-vel pecsétel.

56.4.4.2 2. feladat (konfigurációs): Node failure és PodDisruptionBudget gyakorlat

A lab-app namespace-ben a payment-srv Deployment 3 replikát futtat, és van egy payment-srv-pdb PodDisruptionBudget minAvailable: 2. A gyakorlat célja, hogy a csapat a lab-wn1 node-ot kubectl cordon-nal kivonja, majd kubectl drain-nel leürítse. A feladat: ellenőrizze a PDB-t, és döntse el, kell-e módosítani ahhoz, hogy a drain sikeres legyen, miközben a szolgáltatás SLO-ja nem sérül; ha a drain mégis tartósan blokkol, keresse meg az okát. Használja a kubectl --context lab-k8s-admin parancsot. A megoldás után a node SchedulingDisabled állapotú, a podok Running-ok a másik workeren.

56.4.4.3 3. feladat (diagnosztikai/recovery): PVC adatvesztés és restore integritással

A lab-app namespace-ben a lab-data StatefulSet egy 1 GiB-os PVC-t használ (volumeClaimTemplates neve data, így a PVC neve data-lab-data-0). Előfeltétel: a laborban snapshot-képes CSI driver fut (a d276 matrixa szerint lab-csi StorageClass és lab-snapclass VolumeSnapshotClass), és a lab-data-snapshot VolumeSnapshot használható (kubectl get volumesnapshot lab-data-snapshot -o jsonpath='{.status.readyToUse}' → true). A feladat: rögzítse a /data/important.txt checksumját, szimuláljon adatvesztést a fájl törlésével, a VolumeSnapshotból hozzon létre egy új PVC-t lab-data-restored néven, csatolja egy ideiglenes podhoz, és ellenőrizze, hogy a checksum egyezik a törlés előttivel. Ha egyezik, állítsa vissza az adatot a StatefulSet PVC-jére. Az eredeti adatot (PV) ne veszítse el addig, amíg a restore integritásellenőrzése nem zöld. A parancsok kubectl --context lab-k8s-admin --namespace lab-app targettel fussanak.

56.4.5.2 2. feladat megoldása

A PDB:

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: payment-srv-pdb
  namespace: lab-app
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: payment-srv

Először a PDB állapota, majd a drain (--force nélkül, időkorláttal):

k=(--context lab-k8s-admin)
kubectl "${k[@]}" -n lab-app get pdb payment-srv-pdb \
  -o jsonpath='{.status.disruptionsAllowed}{"\n"}'
# Várt: 1 (3 egészséges pod, minAvailable: 2)
kubectl "${k[@]}" cordon lab-wn1
kubectl "${k[@]}" drain lab-wn1 --ignore-daemonsets \
  --delete-emptydir-data --timeout=300s
kubectl "${k[@]}" get pods -n lab-app -o wide

3 replika és minAvailable: 2 mellett disruptionsAllowed: 1: a drain podonként evictál, és a következő eviction előtt megvárja, hogy a pótló pod a másik workeren Ready legyen. A PDB módosítása ezért nem szükséges, a maxUnavailable: 1 ugyanezt a budgetet adná. Tartós blokkolás akkor van, ha a pótló pod nem ütemezhető (kapacitás, anti-affinity, PVC-kötés) vagy egy pod nem Ready — ilyenkor a kapacitást vagy a pod állapotát kell rendezni, nem a PDB-t lazítani. A --force a nem kontroller által kezelt podokra vonatkozik, a PDB-t nem kerüli meg; itt nincs rá szükség.

Postcondition: a lab-wn1 SchedulingDisabled, a podok a lab-wn2-n futnak, a drain hibakód nélkül lefutott, a disruptionsAllowed a pótlás után ismét 1. A karbantartás végén kubectl --context lab-k8s-admin uncordon lab-wn1.

56.4.5.3 3. feladat megoldása

A törlés előtti checksum rögzítése és az adatvesztés szimulálása:

ns=(--context lab-k8s-admin --namespace lab-app)
kubectl "${ns[@]}" exec lab-data-0 -- sha256sum /data/important.txt \
  | tee lab-data-before.sha256
kubectl "${ns[@]}" exec lab-data-0 -- rm /data/important.txt
# Ellenőrzés
kubectl "${ns[@]}" exec lab-data-0 -- ls -l /data/important.txt

Várható: No such file or directory.

Restore a VolumeSnapshotból egy új PVC-be:

kubectl --context lab-k8s-admin --namespace lab-app apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: lab-data-restored
  namespace: lab-app
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  dataSource:
    name: lab-data-snapshot
    kind: VolumeSnapshot
    apiGroup: snapshot.storage.k8s.io
  storageClassName: lab-csi
EOF

Ideiglenes pod a restore ellenőrzéséhez:

kubectl --context lab-k8s-admin --namespace lab-app apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: lab-restore-check
  namespace: lab-app
spec:
  containers:
    - name: checker
      image: busybox:1.36
      command: ["sh", "-c", "sha256sum /mnt/important.txt && sleep 3600"]
      volumeMounts:
        - name: restored
          mountPath: /mnt
  volumes:
    - name: restored
      persistentVolumeClaim:
        claimName: lab-data-restored
  restartPolicy: Never
EOF

ns=(--context lab-k8s-admin --namespace lab-app)
a=$(kubectl "${ns[@]}" logs lab-restore-check | awk '{print $1}')
b=$(awk '{print $1}' lab-data-before.sha256)
[ -n "$a" ] && [ "$a" = "$b" ] && echo MATCH

A checksum a törlés előtt rögzített értékkel egyezzen (MATCH). Ha az eredmény e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855, az üres fájl hash-e: ez restore-hiba jele, nem siker.

A StatefulSet volumeClaimTemplates mezője nem módosítható, és egy PVC nem nevezhető át, ezért a visszaállítás a StatefulSet saját data-lab-data-0 PVC-jére történik. A legkisebb kockázatú út a visszamásolás:

ns=(--context lab-k8s-admin --namespace lab-app)
# 1. az eredeti PV megőrzése akkor is, ha a PVC-t később törölnénk
pv=$(kubectl "${ns[@]}" get pvc data-lab-data-0 \
  -o jsonpath='{.spec.volumeName}')
kubectl --context lab-k8s-admin patch pv "$pv" \
  -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
# 2. az Argo CD auto-sync szüneteltetése, a StatefulSet leállítása
argocd app set lab-app-platform --sync-policy none
kubectl "${ns[@]}" scale statefulset lab-data --replicas=0
kubectl "${ns[@]}" delete pod lab-restore-check
# 3. visszamásolás egy ideiglenes podban (mindkét PVC csatolva)
kubectl "${ns[@]}" apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: lab-restore-copy
  namespace: lab-app
spec:
  restartPolicy: Never
  containers:
    - name: copy
      image: busybox:1.36
      command: ["cp", "-a", "/src/important.txt", "/dst/important.txt"]
      volumeMounts:
        - {name: src, mountPath: /src}
        - {name: dst, mountPath: /dst}
  volumes:
    - name: src
      persistentVolumeClaim: {claimName: lab-data-restored}
    - name: dst
      persistentVolumeClaim: {claimName: data-lab-data-0}
EOF
kubectl "${ns[@]}" wait pod/lab-restore-copy --timeout=120s \
  --for=jsonpath='{.status.phase}'=Succeeded
kubectl "${ns[@]}" delete pod lab-restore-copy
# 4. visszaindítás, ellenőrzés, auto-sync vissza
kubectl "${ns[@]}" scale statefulset lab-data --replicas=1
kubectl "${ns[@]}" rollout status statefulset/lab-data
kubectl "${ns[@]}" exec lab-data-0 -- sha256sum /data/important.txt
argocd app set lab-app-platform --sync-policy automated --self-heal

Alternatíva: az eredeti data-lab-data-0 PVC törlése után (a PV a Retain miatt megmarad) ugyanezzel a névvel új PVC létrehozása dataSource: lab-data-snapshot-tal; a StatefulSet a visszaindításkor ezt a PVC-t veszi fel.

Postcondition: a lab-data-0 pod Running, a /data/important.txt checksumja egyezik a lab-data-before.sha256 értékével, az eredeti PV Retain állapotban megmaradt a manuális cleanupig, és az Argo CD app ismét automatikus syncben van.

56.4.6 Timeline, runbook és postmortem

A game day során a csapat egy közös timeline dokumentumot vezet, amely minden beavatkozást időbélyeggel rögzít. A timeline minimális mezői: time_utc, actor, target, command, observed_state, hypothesis, decision. A d005 runbook konvenciói szerint a timeline a postmortem elsődleges inputja. A game day után a postmortem a d255-ben tanult template-et követi: rövid összefoglaló, timeline, root cause, hatás, recovery, megelőzés. A cleanup a lab erőforrásokra terjed ki: a lab-app namespace minden fixture erőforrása, a game dayhez visszavont registry-token helyén kiadott új token rögzítése, az ideiglenes pod és PVC, a cordonozott node visszavonása (ha szükséges). A lab-app namespace a d276 kanonikus namespace-e, ezért nem töröljük; a cleanup a fixture-erőforrások (lab-pull-test, lab-restore-check, lab-data-restored) törlésére és a Retain állapotú régi PV ellenőrzött felszabadítására terjed ki, a backup/restore demonstráció sikere után.

56.4.7 Rövid összefoglaló

A d279 game day a platform operation csúcspontja: a tüneteket node/runtime/network/storage/policy rétegekhez rendeli, majd az SLO burn rate és az adatállapot alapján dönt a controlled recoveryről. A gyakorlat során a canary rollback, a node drain, a PVC restore és az etcd quorum loss mind ugyanazt a folyamatot követi: tünet, hipotézis, adatgyűjtés, egy változtatás, verification, postcondition. A GitOps desired state és a timeline a runbook gerince; a cleanup csak sikeres restore után hajtható végre. A game day sikere az, ha a csapat nem improvizál, hanem a működtetési szerződést bizonyítja.

Továbbhasznált definíciók:

  • Controlled recovery: döntési pontokkal tagolt helyreállítás, amely az SLO-t és az adatállapotot együttesen veszi figyelembe.
  • Fixture: előre elkészített, izolált hibás állapot a game day gyakorlathoz.
  • Timeline: időbélyegzett beavatkozáslista, amely a postmortem és az MTTR mérés alapja.

56.4.8 Források és ellenőrzési hiányok

Az alábbiak ellenőrizendő kiindulópontok, nem ebben a munkamenetben olvasott bizonyítékok. Állításonként; a hivatkozott verzió a labor Kubernetes v1.31 profilja, a többi eszközé a lab release-matrixa:

  • Kubernetes: Images – ImagePullBackOff, imagePullSecrets, digest-hivatkozás; Pull an Image from a Private Registry.
  • crictl – node-oldali crictl pull.
  • Gateway API: HTTPRoute és Traffic splitting – backendRefs[].weight.
  • External Secrets Operator – ExternalSecret, target.template.type, refreshInterval; az API-verzió (v1beta1/v1) a telepített operátorhoz igazítandó.
  • Kubernetes: Disruptions és Safely Drain a Node – PDB, disruptionsAllowed, eviction.
  • Kubernetes: StatefulSets – volumeClaimTemplates, PVC-névképzés; Volume Snapshots; Change the Reclaim Policy of a PersistentVolume.
  • CSI hostpath driver – snapshot-képes labprofil.
  • Argo CD Documentation – argocd app diff, app sync (--force jelentése), app set --sync-policy; a pinned CLI-verzió argocd app sync --help kimenetével igazolandó.
  • Google SRE Workbook: Alerting on SLOs – burn rate; OpenGitOps, OpenTelemetry Documentation.

Ellenőrzési státusz: a fixture-ek (nem létező digest, visszavont token, PDB-drain, PVC-restore) sikeres és hibás ága laborban ellenőrizendő; dátumozott futtatási napló (eszközverziókkal és parancskimenettel) még nem készült.

Ellenőrzési hiányok: a kubectl pontos kimeneti formátuma a cluster verziójától függ; az argocd app sync --force viselkedése az Argo CD verziójától függ; a VolumeSnapshot restore elérhetősége a CSI driver és a snapshot controller verziójától függ; az etcd restore pontos lépései a cluster telepítési módjától (kubeadm, managed) függenek; a lab registry credential base64 értéke dummy, nem production token.
