14.5 Package- és dependency incidenslabor

14.5.1 Motiváció: amikor a csomagkezelő szerint minden rendben, a futás mégis meghiúsul

Egy szenior C++ fejlesztő a natív build és a linker részét jól ismeri, de éles üzemeltetésben a hiba gyakran nem a forrásban van. Tipikus eset: egy éjszakai frissítés vagy kézi „gyors beavatkozás” után a szolgáltatás nem indul, a naplóban pedig csak ennyi áll:

jq: error while loading shared libraries: libjq.so.1:
  cannot open shared object file: No such file or directory

(A hibaüzenet egyetlen sor, itt a tördelés a szedés miatt van.)

A jq csomag telepítettnek látszik, mégis hiányzik egy megosztott könyvtára. Ez a fejezet azt a módszert építi fel, amellyel a telepített csomagadatbázis és a futtatókörnyezet valós állapota közötti eltérést hipotézisvezérelten felderítjük, javítjuk, majd rebuildelhető manifesttel és változtatási naplóval dokumentáljuk. Minden módosító parancs labhoston, izolált VM-en fut, a --force-depends típusú beavatkozást éles rendszeren soha ne alkalmazzuk.

14.5.2 Definíció és működés

A vizsgált állapot három rétege:

  1. Installed package manifest – a dpkg adatbázisa (/var/lib/dpkg/status, /var/lib/dpkg/info) tárolja, hogy melyik bináris csomag milyen verzióban és architektúrában telepített. Lekérdezése:

    dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n'

    Ez a csomagkezelő tárolt állapota (stored state); a desired state a csomag-selection (dpkg --get-selections, a dpkg -l kimenet első betűje).

  2. Runtime library állapot – a dinamikus linker (ld.so) a /etc/ld.so.cache és a szabványos könyvtárkereső utak alapján oldja fel a futtatható állomány DT_NEEDED bejegyzéseit. Az ldd ezt a feloldást a dinamikus betöltő nyomkövető módjával (LD_TRACE_LOADED_OBJECTS=1) mutatja meg; ismeretlen binárisnál inkább readelf -d használandó (lásd Runtime könyvtár, ABI és natív dependency). A hiányzó .so itt azonnal látszik.

  3. Repository és package cache állapot – az apt a /etc/apt/sources.list és /etc/apt/sources.list.d/*.sources fájlokból tudja, melyik repóból és milyen verzió telepíthető. A /var/cache/apt/archives/ a letöltött .deb csomagok gyorsítótára. Az apt-cache policy <package> mutatja a jelölt és a telepített verziót, valamint a forrást.

A package DB és a runtime inkonzisztencia azt jelenti, hogy a dpkg adatbázisa szerint egy függőség nem hiányzik, a fájlrendszerből mégis hiányzik a csomag által szolgáltatott fájl. Ennek tipikus okai: dpkg --remove --force-depends, kézi fájltörlés, sérült csomagarchívum, félbeszakadt frissítés.

14.5.3 Kidolgozott példa: hiányzó shared library javítása

A labor környezet: labhost01 VM, labuser sudo joggal, Ubuntu Server 24.04 LTS alapprofil. A csomagneveket a labor előtt ellenőrizni kell a tényleges repóban, mert a t64 átállás módosíthatja az utótagokat. A hibát egy levél-szintű, nem kritikus könyvtáron injektáljuk: a libjq1-et csak a jq parancssori JSON-feldolgozó használja. Rendszerszintű könyvtárat (például a libbz2-1.0-t, amelytől maga a dpkg és a libapt-pkg is függ) tilos így eltávolítani: utána a dpkg és az apt sem indulna el, és a csomagkezelő csak snapshotból vagy kézi kicsomagolással lenne menthető.

14.5.3.1 1. Baseline manifest és bizonyíték

# target: labhost01
# user: labuser, sudo szükséges a későbbi lépésekhez
sudo apt-get install -y jq     # ha még nincs telepítve
mkdir -p "$HOME/package-lab/baseline"
cd "$HOME/package-lab"

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  jq libjq1 > baseline/packages.tsv

ldd /usr/bin/jq > baseline/ldd.txt

sha256sum /usr/bin/jq > baseline/jq.sha256

Várt kimenet (illusztratív, nem tényleges futtatásból):

$ cat baseline/packages.tsv
jq      1.7.1-3build1  amd64
libjq1  1.7.1-3build1  amd64

$ grep libjq baseline/ldd.txt
libjq.so.1 => /lib/x86_64-linux-gnu/libjq.so.1 (0x00007f...)

14.5.3.2 2. Hiba injektálása

A --force-depends szándékosan megkerüli a függőségellenőrzést. Csak labhoston használjuk, mert törött csomagállapotot hoz létre. Előfeltétel: VM-snapshot (lab-pre-inject), és annak ellenőrzése, hogy a könyvtártól csak a célprogram függ – a kimenetben nem szerepelhet dpkg, apt vagy libapt-pkg:

apt-cache rdepends --installed libjq1
# várt (illusztratív): libjq1 / Reverse Depends: / jq
sudo dpkg --remove --force-depends libjq1

A csomagkezelő eltávolítja a libjq1 csomagot, de a jq csomagot a függőségi hiba ellenére a helyén hagyja. A jq bináris megmarad, a szükséges .so azonban eltűnik.

14.5.3.3 3. Diagnosztika

A hibát először a runtime oldalról látjuk:

# target: labhost01
ldd /usr/bin/jq

Várt kimenet:

linux-vdso.so.1 (0x00007ffd...)
libjq.so.1 => not found
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
/lib64/ld-linux-x86-64.so.2 (0x00007f...)

A not found megmutatja, hogy a linker nem találja a libjq.so.1 fájlt. Most ellenőrizzük a csomagadatbázist:

dpkg -l libjq1 jq
apt-get check
dpkg --audit

Várt eredmény:

$ dpkg -l libjq1 jq
Desired=Unknown/Install/Remove/Purge/Hold
| Status=Not/Inst/Conf-files/Unpacked/halF-conf/Half-inst/trig-aWait/Trig-pend
|/ Err?=(none)/Reinst-required (Status,Err: uppercase=bad)
||/ Name           Version      Architecture Description
+++-==============-============-============-=================================
un  libjq1         <none>       <none>       (no description available)
ii  jq             1.7.1-3build1 amd64       lightweight and flexible JSON …

A libjq1 állapota un (unknown, not installed), míg jq ii (installed). Az apt-get check a függőségi hiba miatt nem üres:

You might want to run 'apt --fix-broken install' to correct these.
The following packages have unmet dependencies:
 jq : Depends: libjq1 but it is not installed

A dpkg --audit nem feltétlenül ad ki hibát, mert a --force-depends eltávolítás után a jq csomag metainformációi nem sérültek, csak a függősége nem teljesül. Az apt-get check a függőségi szintet, a dpkg --audit a csomagjelek konzisztenciáját vizsgálja.

A repository állapot ellenőrzése:

apt-cache policy libjq1
ls -l /var/cache/apt/archives/libjq1_*

Ez megmutatja, hogy a csomag letölthető-e a beállított repóból, és van-e már cache-ben a .deb.

14.5.3.4 4. Javítás

A legegyszerűbb a jq függőségét újratelepíteni:

sudo apt-get -f install

Ez a törött függőséget úgy javítja, hogy telepíti a hiányzó libjq1 csomagot. Ha a cache-ben nincs meg, letölti a repóból. Élesben először always szimuláljunk:

apt-get -s -f install

A -s (simulate) megmutatja, mit tenne a rendszer, anélkül, hogy módosítana. A postcondition ellenőrzése:

# target: labhost01
ldd /usr/bin/jq | grep libjq
apt-get check
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  jq libjq1

Várt kimenet:

libjq.so.1 => /lib/x86_64-linux-gnu/libjq.so.1 (0x00007f...)

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  jq libjq1
jq      1.7.1-3build1  amd64
libjq1  1.7.1-3build1  amd64

Az apt-get check üres kimenettel jelzi, hogy nincs törött függőség.

14.5.3.5 5. Provenance report és rebuildelhető manifest

A javítás után készítsünk dokumentumot a csomageredetről:

# target: labhost01
mkdir -p "$HOME/package-lab/post-fix"
cd "$HOME/package-lab"

apt-cache policy jq libjq1 > post-fix/policy.txt
dpkg -s jq libjq1 > post-fix/status.txt

# Rebuildelhető manifest a teljes gépről
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  > post-fix/installed-manifest-$(date -I).tsv

A policy.txt tartalmazza a repository prioritásokat, a status.txt a csomag maintained by, szekció, forrás és más metadatokat. A manifest a teljes telepített készletet rögzíti, így később egy másik hoston reprodukálható.

A változtatási napló legyen egyszerű, de ellenőrizhető:

2025-04-01 10:15 UTC labhost01 labuser
  baseline: packages.tsv, ldd.txt, jq.sha256
  command: sudo dpkg --remove --force-depends libjq1
  symptom: ldd /usr/bin/jq -> libjq.so.1 => not found
  fix: sudo apt-get -f install
  postcondition: apt-get check clean, ldd resolves libjq.so.1
  rollback: VM-snapshot visszaállítása a lab-pre-inject pontra
  cleanup: diff baseline/packages.tsv <(dpkg-query -W ... jq libjq1) üres

14.5.4 Hibák és ellenpróbák

  • ldd félrevezethet nem megbízható bináris futtatásakor, mert egyes esetekben a dinamikus linker kódot is futtathat. Ezért a laborban csak ismert, kontrollált binárist (/usr/bin/jq) használunk.
  • A apt-get -f install néha eltávolít csomagokat, ha a függőségi gráf másképp nem oldható fel. Ezért mindig -s szimulációval ellenőrizzük, és rollback tervet rögzítünk.
  • A dpkg --verify nem észlel minden hiányzó fájlt, mert a csomagok egy részének nincs md5sums listája, illetve a konfigurációs fájlokat külön kezeli. A jelen példában a hiányzó .so a másik csomaghoz tartozik, ezért a dpkg --verify jq nem jelez hibát.
  • A dpkg --remove --force-depends élesben tilos. Helyette a függőségi gráfot módosító csomagváltozásoknál az apt szokásos parancsait használjuk, vagy dedikált labon reprodukáljuk az incidenst.
  • A package cache nem biztonsági mentés. A /var/cache/apt/archives/ gyorsítótár, nem garantáltan tartalmazza az összes régi csomagot, ezért a rollbackhez a manifest és a repository verziók használandók.

14.5.5 Feladatok

14.5.5.1 1. feladat: Baseline manifest és hipotézis felállítása

Futtasd le a fenti baseline lépéseket egy labhost01 labVM-en. Rögzítsd a jq és libjq1 csomagok verzióját, architektúráját és a jq ldd kimenetét. Hipotézisként írd le: mi történik, ha a libjq1 csomagot --force-depends módon eltávolítjuk? Melyik réteg (manifest, runtime, repository) mutat először hibát?

14.5.5.2 2. feladat: Hiba injektálása, diagnosztika és javítás

A labon hajtsd végre a kidolgozott példa injektálási lépését, majd a hibát a ldd, dpkg -l, apt-get check és apt-cache policy segítségével diagnosztizáld. Javítsd apt-get -f install paranccsal. Ellenőrizd a postconditiont: ldd /usr/bin/jq mutatja a libjq.so.1-t, az apt-get check üres, és a dpkg-query mindkét csomagot ii állapotúnak jelzi. Készíts változtatási naplót a fenti formátumban.

14.5.5.3 3. feladat: Partial upgrade állapot diagnosztikája és recovery

Szimulálj partial upgrade állapotot: állíts elő determinisztikusan egy kicsomagolt, de nem konfigurált csomagot (dpkg --unpack). A cél az, hogy a csomagrendszer unpacked állapotú csomagot hagyjon. Diagnosztizáld a dpkg --audit, /var/log/dpkg.log és /var/log/apt/term.log segítségével. Javítsd sudo dpkg --configure -a majd sudo apt-get -f install paranccsal. Ellenőrizd, hogy az apt-get check és dpkg --audit nem jelez hibát. A jq és libjq1 csomagok maradjanak telepített, konzisztens állapotban. Rögzítsd a recovery lépéseket a változtatási naplóban.

14.5.6 Megoldások

14.5.6.1 1. feladat megoldása

A baseline manifest:

# target: labhost01, user: labuser
mkdir -p "$HOME/package-lab/baseline"
cd "$HOME/package-lab"

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  jq libjq1 > baseline/packages.tsv
ldd /usr/bin/jq > baseline/ldd.txt
sha256sum /usr/bin/jq > baseline/jq.sha256

Hipotézis: a dpkg --remove --force-depends eltávolítja a libjq1 csomagot, de a jq bináris a helyén marad. Elsőként a runtime réteg (az ldd) fog hibát jelezni, mert a fájlszintű linkfeloldás már a program indítása előtt meghiúsul. A manifest szint csak az apt-get check futásakor mutat törött függőséget.

14.5.6.2 2. feladat megoldása

# target: labhost01, user: labuser, sudo szükséges
sudo dpkg --remove --force-depends libjq1

# Diagnosztika
ldd /usr/bin/jq
dpkg -l libjq1 jq
apt-get check
dpkg --audit
apt-cache policy libjq1

# Javítás szimulációval
apt-get -s -f install

# Tényleges javítás
sudo apt-get -f install

# Postcondition ellenőrzése
ldd /usr/bin/jq | grep libjq
apt-get check
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' \
  jq libjq1

Postcondition: az ldd a libjq.so.1-t elérési úttal mutatja, az apt-get check üres, a dpkg-query mindkét csomagot telepített ii állapotban listázza. A változtatási napló a példa formátumban készül.

14.5.6.3 3. feladat megoldása

A partial upgrade állapotot determinisztikusan állítjuk elő: a csomagot letöltjük, és csak kicsomagoljuk, konfigurálás nélkül (csak eldobható VM-en, snapshot után):

# target: labhost01, user: labuser, sudo szükséges
cd "$HOME/package-lab"
apt-get download jq
sudo dpkg --unpack ./jq_*.deb
dpkg-query -W -f='${Status}\n' jq    # várt: install ok unpacked

Egy futó apt háttérjob (sudo apt install … &) a jobra küldött SIGKILL-lel nem szakítható meg megbízhatóan: a job a sudo folyamat, a SIGKILL-t a sudo nem továbbítja, így az apt/dpkg gyermek tovább futhat, vagy a dpkg-zárat tartva maradhat. Ha valódi megszakítást akarunk, egy második terminálban sudo pkill -KILL -x dpkg a kicsomagolás közben, majd sudo fuser -v /var/lib/dpkg/lock-frontend ellenőrzés – ennek kimenetele azonban időzítésfüggő.

Diagnosztika:

dpkg --audit
tail -n 50 /var/log/dpkg.log
grep -i "error\|warning" /var/log/apt/term.log | tail -n 50

A dpkg --audit kilistázza azokat a csomagokat, amelyek nincsenek teljesen telepítve. A naplók a megszakadt művelet pontos pontját mutatják.

Recovery:

sudo dpkg --configure -a
sudo apt-get -f install

A dpkg --configure -a a félbemaradt konfigurációs lépéseket fejezi be, az apt-get -f install a függőségi problémákat javítja. Postcondition: dpkg --audit üres, apt-get check üres, dpkg-query -W -f='${Status}\n' jq → install ok installed, dpkg -l jq libjq1 telepített állapotú. A változtatási napló tartalmazza a megszakítás okát, a diagnosztikai bizonyítékot és a recovery parancsokat.

14.5.7 Rövid összefoglaló

A package- és dependency incidens lényege, hogy a csomagkezelő tárolt állapota (stored state, a dpkg-adatbázis) és a fájlrendszerbeli observed state eltér egymástól. A hiányzó shared library diagnosztikája mindig három réteget vizsgál: a runtime linker ldd kimenetét, a dpkg manifestet (dpkg-query, dpkg -l) és a repository/cache állapotot (apt-cache policy). A javítás előtt szimuláljuk az apt-get -s -f install kimenetét, majd a tényleges parancs után ellenőrizzük a postconditiont. A változás mindig rebuildelhető manifestet és változtatási naplót kap, hogy a rendszer állapota reprodukálható legyen. Továbbhasznált definíciók: installed package manifest, package DB és runtime inkonzisztencia, rebuildelhető manifest.

14.5.8 Források és ellenőrzési hiányok

Állításonkénti források (laborprofil: Ubuntu Server 24.04 LTS, dpkg 1.22, apt 2.7/2.8; a noble kézikönyvoldalak ehhez a kiadáshoz tartoznak):

  • --force-depends, --remove, --unpack, --configure -a, --audit, --verify, --get-selections és a csomagállapotok: dpkg(1) – https://manpages.ubuntu.com/manpages/noble/man1/dpkg.1.html
  • dpkg -l kimenet (Desired/Status/Err oszlopok), dpkg-query -W -f: dpkg-query(1) – https://manpages.ubuntu.com/manpages/noble/man1/dpkg-query.1.html
  • apt-get check, -f install, -s, download: apt-get(8) – https://manpages.ubuntu.com/manpages/noble/man8/apt-get.8.html; apt-cache rdepends, policy: apt-cache(8) – https://manpages.ubuntu.com/manpages/noble/man8/apt-cache.8.html
  • ldd és a LD_TRACE_LOADED_OBJECTS: ldd(1) – https://man7.org/linux/man-pages/man1/ldd.1.html; ld.so(8) – https://man7.org/linux/man-pages/man8/ld.so.8.html
  • a jq/libjq1 csomag a 24.04-es archívumban: https://packages.ubuntu.com/noble/jq
  • Essential/Priority: required csomagok szerepe: Debian Policy, 3.8 „Essential packages” – https://www.debian.org/doc/debian-policy/ch-binary.html

Reprodukciós állapot: dátumozott futtatási napló a 24.04-es labhoston még nem készült; a jq/libjq1 pontos csomagneve és verziója, valamint az apt-cache rdepends --installed libjq1 kimenete a lab előtt ellenőrizendő. A példákban szereplő kimenetek illusztratívak, nem tényleges futtatásból származnak.
